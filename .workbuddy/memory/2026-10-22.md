## 偶发测试失败记录：7 失败的成因甄别

### 现象
组合运行测试时出现 **7 个失败**，非稳定复现。

### 定位：集中在进程击杀 / 时序敏感测试
- `tests/test_process_recovery.py`：`_kill_at_boundary()` 起子进程后固定 `sleep(0.85)` 再 `worker.kill()`，
  击杀点相对检查点写入位置是**写死的时序假设**——CPU 负载一高，子进程没走到预期边界就被杀，断言即失败。
- `tests/test_run_ownership.py`：含 `sleep(0.4)`、deadline 轮询等同类时序假设。

### 两个叠加成因（本次记录的重点）
1. **测试自身时序敏感**：上述击杀点假设在机器空闲时成立，高负载下边界漂移。
2. **并行会话同时在跑测试 + 在途改动**：记录时 `git status` 可见对方在途文件
   （controller.py / authorization.py / app.py / api/server.py / budget.py / schema/goals.py 等），
   工作区状态本身不干净，且对方跑全量 pytest 时与本方抢 CPU，正好命中第 1 条。

### 证据
- 失败组合重跑 → **89 全过**。
- 刚刚单独重跑两个涉事文件 → **15 passed in 14.75s**（当前机器空闲）。

### 沉淀的做法
- 这类失败**单次运行不作数**：记录进台账/日志前必须重跑；重跑不过再用
  `git worktree add <tmp> HEAD --detach` 干净复本隔离验证（比 stash 安全，不碰对方工作区）。
- 判定"是不是我的问题"永远靠隔离验证，不靠猜。
- 当前工作区有并行会话在途（ALN-12/13/14/15/17/20），测试基线以「跑那一刻的工作区状态」为准，
  交付基线应说明排除项。
