# EvoAgent 全系统架构一致性审计报告
**版本：** Audit Draft v0.1  
**日期：** 2026-10-21  
**状态：** 初步审计基线；待补齐全部专项原稿后进行第二轮逐项核验  
**适用部署方向：** 个人用户、本地优先、Windows/Linux 主机，Android 作为可选交互端；后续可连接独立服务端

## 0. 执行摘要

本报告基于当前可读取的 EvoAgent PRD/TAD V0.1 基线、DeepSeek Harness 适配分析、离线日志与可靠同步设计、服务端逻辑服务协同设计、双端协同进化与版本分发补充设计，以及当前项目对话中可见的架构决策摘要，完成第一轮一致性审计。

**重要范围说明：** 当前可读取的历史文件并不包含全部 50+ 专项的完整原稿。因此，本报告是可执行的第一轮架构审计和设计汇编基线，不会宣称已逐字合并所有专项原文。文末给出专项台账和缺口状态，后续应按台账逐项补齐、核对与合并。

### 审计结论

1. 核心方向可统一为“本地优先、模块化单体起步、逻辑服务边界清晰、远程能力可选、稳定执行与候选进化隔离”。
2. Android 优先交互战略与 Windows/Linux 本地运行并不必然冲突；应将“交互端优先级”和“运行宿主部署策略”拆成两个独立决策维度。
3. 八个逻辑服务是服务端/宿主逻辑划分，不意味着必须部署八个微服务。个人部署 V0.1 应优先采用单进程或少量进程的模块化架构。
4. 任务路由、规划、ReAct、DAG、恢复、资源调度和自主目标治理之间需要明确控制权，不能由多个模块同时拥有最终决策权。
5. 运行事件、恢复检查点和外部副作用账本是三种不同事实，不能合并为一套模糊的“任务日志”。
6. 诊断、评测、批准、发布与回滚必须分离；候选智能体不得自行修改安全边界、评测门槛或稳定版本指针。
7. 记忆、上下文和压缩机制应共享策略框架，但保留不同命名空间、保留规则、权限和数据生命周期。
8. 领域专家可拥有独立工具、技能、工作流、提示词、评测集与领域记忆；但共享内核的安全、状态、权限、事件和预算规则不得被领域专家绕过。
9. “无限进化”应被工程化解释为持续提出候选、验证、发布、观察与回滚的长期能力，而不是无限权限、无限任务或无限资源。
10. V0.1 应只验证一个可运行的任务闭环，不应一次实现全部专家、移动端自动化、自动工作流编译和自动发布。

## 2. 统一后的目标架构

### 2.1 架构原则

- 本地优先：核心任务状态、日志、检查点、技能/工作流资产与基本评测能力在本地可运行。
- 模块化单体起步：先定义逻辑服务和契约，避免过早拆微服务。
- 稳定轨道与进化轨道隔离：候选变更不直接影响稳定执行。
- 控制面自有、运行时可替换：DeepSeek Harness 可作为候选 Runtime，通过适配器隔离；不得成为产品架构的唯一基础。
- 证据优先：每个关键结论关联可追踪的运行证据、评测结果或明确的用户决策。
- 可恢复：版本不可变、任务有检查点、副作用可对账、发布可回滚。
- 最小权限：模型提出动作，运行时与策略层决定是否允许。
- 领域隔离：专家拥有领域资产空间，不能直接改写全局规则。
- 进化有门禁：候选创建、候选验证、批准、发布、观察、回滚分别建模。
- 允许停止：目标无价值、无进展、预算耗尽、授权失效时，系统应暂停或结束。

### 2.2 统一逻辑分层

1. 交互层：Android、桌面 UI、CLI/API（按版本逐步交付）。
2. 任务入口与治理层：意图解析、风险识别、目标注册、授权与审批。
3. 编排与执行层：Router、Planner、ReAct Runtime、DAG Scheduler、状态机、检查点、恢复控制器。
4. 能力层：工具注册表、技能注册表、领域专家、工作流、能力包、模型适配器。
5. 上下文与资产层：会话上下文、用户记忆、项目记忆、领域知识、任务状态、资产注册与依赖图。
6. 观测与诊断层：事件、Trace、工具健康、故障分类、问题案例。
7. 评测与质量层：回归集、独立验收、基准比较、失败注入、安全检查。
8. 进化与发布层：候选生成、隔离实验、晋级门禁、版本分发、灰度、回滚。
9. 基础设施层：SQLite、文件系统、Git、可选队列/对象存储、密钥与配置管理。

## 3. 部署策略冲突审计

### 3.1 表面冲突

历史讨论涉及：
- 手机优先战略与 EvoAgent Android；
- Windows 10/11 桌面端 V0.1 全本地运行；
- 个人电脑或 Mini PC、微型 Linux 主机作为个人宿主；
- 后续接入独立服务器的可能性。

### 3.2 统一解释

将两个决策轴拆开：

**交互端路线：**
- Android 是移动交互与受控设备操作端；
- Windows 桌面端适合开发、调试、长任务与本地工具执行；
- CLI/API 是测试与自动化接口；
- 交互端不决定所有任务必须在该设备上运行。

**运行宿主路线：**
- V0.1 优先支持本地单机运行；
- 核心服务以 Python 模块化单体起步，存储以 SQLite + 文件系统 + Git 为主；
- Android 可以独立运行部分本地功能，也可以连接用户自有宿主；
- 远程服务端作为可选扩展，不是个人版核心闭环的先决条件；
- 离线情况下必须保留本地任务状态、事件记录、基本工具能力和导出能力。

### 3.3 决策建议

采用“本地优先、端侧多入口、宿主可替换”的架构。不要把“手机优先”解释为所有复杂任务必须在手机上执行，也不要把“桌面本地 V0.1”解释为放弃 Android 路线。

状态：**建议统一；需在正式 ADR 中由项目所有者确认。**

## 4. 模块职责与控制权审计

### 4.1 控制权矩阵

| 决策/职责 | 最终负责模块 | 协作模块 | 禁止事项 |
|---|---|---|---|
| 识别用户意图与候选专家 | Intent Router | Context Manager、领域注册表 | 不直接执行高风险动作 |
| 决定是否匹配已有工作流 | Workflow Matcher/Router | KCLG/资产注册表、Planner | 不因相似度高而跳过契约检查 |
| 分解目标与生成计划 | Planner | AGIG、Router、预算策略 | 不自行扩大授权范围 |
| 决定单步模型动作 | ReAct Runtime | 模型适配器、上下文管理 | 模型不能直接执行工具 |
| 执行工具动作 | Tool Gateway/Action Guard | 工具适配器、TSEG 策略 | 不允许绕过 Schema、权限和预算 |
| 管理 DAG 节点状态 | DAG/Workflow Runtime | 状态机、检查点 | 不与长期 Goal 状态混为一体 |
| 恢复和重试 | RERA/Recovery Manager | 副作用账本、工具健康 | 不盲目重放不确定外部副作用 |
| 分配模型/并发/资源 | APRO/Resource Scheduler | AGIG、任务队列 | 不突破用户预算和前台保护策略 |
| 发现主动目标 | AGIG Opportunity Detector | GECO、QEEG、RERA、KCLG | 不直接将候选视为已授权执行任务 |
| 诊断根因 | 诊断器（如 SOCDEA，名称待核） | GECO、QEEG、工具健康 | 不凭单次失败自动改生产配置 |
| 判断质量是否合格 | QEEG/Evaluator | 评测集、独立验证器 | 候选系统不能自行降低门槛 |
| 批准并发布版本 | SELCIA/受保护发布控制器 | TSEG、QEEG、制品管理 | 不允许候选修改稳定指针 |
| 管理知识/技能/工作流资产 | KCLG/Asset Governance | 评测、依赖图、版本管理 | 不把一次成功自动晋升为稳定能力 |
| 记录运行事实 | GECO/Event Store | 所有运行模块 | 日志不是可信命令，不替代检查点 |
| 任务长期目标状态 | AGIG Goal Registry | Planner、Scheduler | 不直接代替 DAG 节点状态机 |
| 权限与风险策略 | TSEG/Policy Gate | Action Guard、审批 UI | 领域专家不得自行放宽全局安全策略 |
| 用户进度与审批展示 | HACCG/交互控制台（名称待核） | AGIG、运行时、审批服务 | 不作为底层执行控制器 |

注：AGIG、APRO、RERA、QEEG、KCLG、TSEG、SELCIA、GECO 等缩写在对话中出现过，但某些缩写的正式全称与边界仍需对照原始专项文档核验。上表是职责建议，不代表所有命名已冻结。

### 4.2 Router、Planner、ReAct 与 DAG 的关系

- Router：判断任务领域、能力需求、风险与可能的执行模式；可以多层路由，但最终必须输出可解释的选择及置信/缺口。
- Planner：为当前目标生成可执行计划，选择固定 DAG、混合 Agent 工作流或动态规划。
- DAG Runtime：管理依赖、分支、并发、重试、检查点和节点状态。
- ReAct：适用于需要根据观察动态选择下一步的局部执行节点；不是整个系统唯一的任务管理器。
- Expert Agent：提供领域知识、领域策略和工具选择能力；不能替代共享内核。
- Evaluator：独立判断结果是否满足验收契约，不由执行模型自评作为唯一依据。

## 5. 记忆、上下文与压缩审计

### 5.1 建议区分的数据类型

1. 用户长期偏好与授权：跨任务可复用，但需可查看、可纠正、可撤销。
2. 项目记忆：特定项目的决策、约束、状态和历史。
3. 领域知识：领域可复用事实、方法、限制与来源。
4. 会话上下文：当前交互所需的近期信息。
5. 任务工作记忆：当前任务的计划、未决问题、证据和中间产物。
6. 运行证据：事件、工具结果、版本、评测和失败记录。
7. 派生摘要：从原始来源压缩得到的视图，必须保留来源引用和更新时间。

### 5.2 “压缩是否全局共用”的结论

压缩**策略框架可以共享，压缩后的内容不能全局混用**。

共享部分：
- Token/容量预算；
- 重要性评分策略；
- 冲突识别；
- 摘要质量评测；
- 来源追踪规则；
- 丢失关键约束的回归测试。

隔离部分：
- 用户、项目、领域、任务命名空间；
- 权限与隐私范围；
- 保留期与删除策略；
- 不同领域的术语和证据标准；
- 当前任务所需的临时上下文。

压缩应优先保留目标、约束、决策、验收标准、未决事项、关键证据与来源；不能只按时间截断。摘要不得成为比原始事实更高权威的来源。

### 5.3 记忆写入规则

- 候选记忆与已确认记忆分开；
- 用户明确决策优先于旧的项目假设；
- 用户偏好不能覆盖客观事实、安全要求和验收契约；
- 技术事实需来源、版本或验证状态；
- 派生摘要可重建，原始来源与删除要求需可追踪；
- 不同专家的领域记忆默认隔离，通过显式共享接口复用。

## 6. 能力、技能、工作流与专家审计

### 6.1 概念边界

- Tool：可调用的原子操作，有 Schema、权限、幂等和错误契约。
- Skill：可复用的知识/操作策略，可包含提示词、代码、约束与示例。
- Workflow/DAG：节点依赖、分支、重试、审批、验收和恢复条件构成的可执行流程。
- Expert：领域能力组合，包括提示策略、技能、工具、工作流、领域记忆和评测集。
- Capability Pack：面向业务目标的打包能力，例如编程、AI 漫剧制作或受控手机操作。
- Model Profile：模型与特定任务/工具环境的版本化适配档案。
- Evaluation Suite：固定版本的验收与回归测试集。
- Runtime/Harness：驱动模型循环、工具调用和局部执行的机制。
- Release：经过批准的不可变版本组合及其适用范围。

### 6.2 技能生命周期

候选发现 → 候选实现 → 契约验证 → 独立评测 → 批准 → 正式使用 → 观察 → 退化/冻结/弃用/退役。

每次正式发布必须有不可变版本、内容摘要、依赖清单、来源、适用范围、评测证据与回滚指针。技能改动不得原地覆盖历史版本。

### 6.3 专家隔离

领域专家可独立拥有：
- system/role 配置；
- 领域知识命名空间；
- 专用工具与适配器；
- 领域工作流；
- 领域评测集；
- 模型偏好与成本策略；
- 能力包版本。

共享内核负责任务身份、权限、预算、事件、状态、恢复、评测门禁和发布安全。一个领域的改进不得无条件改变其他领域。

## 7. 运行证据、恢复与同步边界

| 机制 | 事实职责 | 不负责什么 |
|---|---|---|
| Event/Trace Store | 记录发生了什么、使用哪个版本、工具结果与错误 | 不保证任务能恢复 |
| Checkpoint | 保存恢复所需的状态、游标、DAG 节点和引用 | 不等于完整审计日志 |
| Side-effect Ledger | 记录外部副作用的意图、提交、确认与对账状态 | 不替代业务验收 |
| Sync Receipt | 证明服务端已持久化接收指定事件/附件 | 不证明事件内容真实可信 |
| Runtime Manifest | 固定一次运行实际使用的组件版本组合 | 不代表这些版本质量合格 |
| Evaluation Record | 记录测试集、环境、结果和门禁判断 | 不替代发布授权 |
| Release Manifest | 定义可分发版本、依赖、签名、范围和回滚信息 | 不保证客户端已成功激活 |

离线同步采用至少一次传输、稳定事件 ID、服务端幂等去重、持久化后 ACK、部分成功明确回执、退避重试和隔离永久错误。版本分发与日志补传是独立队列，不能互相阻塞。

## 8. 进化闭环与发布治理

建议统一流程：
运行证据 → 机会候选 → 根因假设 → 改进提案 → 候选实现 → 隔离评测 → 安全/兼容门禁 → 授权批准 → 不可变发布 → 灰度/观察 → 晋级或回滚 → 结果回流。

强制规则：
- 执行模型不能控制自己的独立评测集和门禁；
- 候选代码不能直接访问稳定生产数据或修改稳定版本指针；
- 安全策略、权限机制和评测门槛不得由普通自进化流程自行放宽；
- 自动发布初期仅限明确 allowlist 的低风险配置；
- 一次成功轨迹只能形成候选，不能自动成为稳定工作流；
- 实际收益要通过真实任务观察验证；
- 进化失败时保留证据，避免重复尝试同一无效策略。

## 9. 自主目标管理（AGIG）审计

AGIG 负责“为什么做、是否值得、是否获准、何时停止”；Planner 负责“怎样做”；DAG/ReAct 执行器负责“如何运行”；APRO 负责资源安排；QEEG 负责结果验证。

每个长期目标应有：
- 明确成功条件；
- 来源、所有者与父目标；
- 授权引用；
- 预算与截止/失效条件；
- 子目标数量/深度限制；
- 无进展阈值；
- 等待、暂停、取消与恢复语义；
- 结果记录与后续观察条件。

主动发现只创建机会候选；候选要经过价值、证据、成本、风险和授权评估。目标完成后不得为了继续“显得有用”自动扩展任务。

## 10. 本地优先部署基线

### V0.1 建议

- Python 3.11+（具体版本应由依赖测试冻结）；
- SQLite 保存任务、状态、资产元数据、审批和评测索引；
- JSONL/结构化事件作为可追溯日志；
- 文件系统保存大产物，Git 管理工作流、提示词、配置和版本化文本资产；
- 模块化单体，不把八个逻辑服务立即拆成八个微服务；
- Mock Runtime/模型用于无密钥测试；
- 一个真实模型适配器作为可选集成；
- 所有外部工具调用通过 Tool Gateway/Action Guard；
- 本地离线仍可创建/查询任务、记录事件、运行确定性工具、导出诊断包；
- 远程模型不可用时明确降级，不伪装成完整智能能力。

### 后续可选

- PostgreSQL/队列/对象存储；
- 独立远程进化服务；
- Android App 连接个人宿主；
- 多设备版本分发；
- 多模型路由；
- 沙箱容器与更强隔离。

## 11. V0.1 冻结建议

### 必须交付
- Task/Run/Node 状态机；
- 工具注册表与 Schema 校验；
- Action Guard；
- 一个受控 ReAct 执行循环；
- 结构化事件；
- 最小检查点和取消；
- 幂等键与副作用状态；
- 最终验收器；
- 失败分类与有限恢复；
- SQLite + 文件存储；
- Mock 模式和至少一个真实模型适配接口；
- 单元/集成/回归测试；
- 可运行启动说明和端到端示例。

### 延后
- 自动工作流编译与自动发布；
- 完整 AGIG 长期目标自主推进；
- 多专家自动进化；
- 全量 Android 无障碍操作；
- AI 漫剧端到端生产能力；
- 多设备自动版本分发；
- 复杂分布式队列和微服务拆分。

### 暂不允许
- 候选修改核心 Runtime 后直接上线；
- 候选修改权限/安全/评测门禁；
- 未经授权的高风险外部操作；
- 未经幂等与状态对账的自动重放；
- 将模型自评当作唯一验收；
- 将所有成功轨迹自动固化为工作流。

## 13. 审计结论与冻结门槛

第一轮审计建议通过以下条件后冻结 V0.1：
1. 核心实体与状态机有唯一权威定义；
2. 模块职责和控制权矩阵获确认；
3. 本地部署目标与客户端路线分离；
4. 工具动作统一经过权限与预算检查；
5. 事件、检查点和副作用账本分离；
6. 候选进化与稳定运行隔离；
7. 最小端到端流程具有自动化验收；
8. 所有未决决策进入 ADR 台账；
9. 专项目录标注来源完整性，不能将待重建专项冒充原文已合并；
10. 关键离线、取消、恢复、重复副作用和回滚测试通过。

**建议的冻结声明：** 冻结 V0.1 的核心职责、数据契约、权限边界和执行闭环；不冻结领域专家数量、技能内容、工作流内容和模型供应商选择。新增能力优先通过插件/资产/工作流扩展，不轻易改变稳定内核。
