# 离线日志与可靠同步子系统设计

全量架构设计补充文件｜版本 1.0

主题：本地持久化、断联补传、幂等回执、诊断包导出与受控导入

## 文档说明

本文档补充 EvoAgent Android App 与服务端的离线日志、可靠同步和人工诊断通道设计。目标是在网络不稳定、服务端不可用或用户需要手动提供诊断材料时，仍能保留可追溯的运行证据。

本文属于全量目标架构补充，而非仅针对 V0.1 的实现清单。具体研发可分阶段交付，但本地持久化、可靠同步、隐私控制、导出与导入应采用统一协议和数据模型。

## 一、核心设计原则

1. 先本地持久化，再异步同步。 关键事件应先可靠写入本地存储，不能依赖网络请求成功后才算记录。

1. 日志采集、日志同步、日志导出相互独立。 服务端不可用不应阻止本地记录和离线导出。

1. 同步至少一次传输，服务端幂等去重。 网络重试可能重复发送，但同一事件不能重复产生业务效果。

1. 服务端回执必须有明确持久化语义。 只有完成必要的持久化后才能确认接收，不能先确认后落盘。

1. 历史运行版本不可被新版本覆盖。 每条事件关联运行时版本清单，确保后续可以还原运行环境。

1. 日志是证据，不是可信命令。 导入的事件和诊断包必须校验、隔离和审计，不得直接执行其中内容。

1. 隐私最小化。 默认优先传输结构化事件；原始对话、截图和文件按授权与必要性处理。

1. 日志不能替代任务恢复机制。 任务续跑还需要独立检查点、幂等副作用控制和恢复策略。

## 二、子系统总体架构

```text
Android App
  ├─ Runtime Event Collector（运行事件采集）
  ├─ Local Event Store（Room / SQLite）
  ├─ Attachment Store（诊断附件，可选）
  ├─ Sync Coordinator（同步状态机与批次管理）
  ├─ WorkManager Jobs（后台同步调度）
  ├─ Export Manager（离线诊断包导出）
  └─ Import Validator（诊断包校验与隐私检查）
             │ HTTPS：事件批次、附件、回执、版本对账
             ▼
服务端
  ├─ Sync API（认证、校验、幂等去重）
  ├─ Durable Event Store（可靠事件存储）
  ├─ Receipt Service（同步回执）
  ├─ Runtime Manifest Registry（运行版本关联）
  ├─ Diagnostic Intake（诊断包受控导入）
  └─ Evolution Pipeline（诊断、评测、候选进化）
```

Android 推荐采用 Room/SQLite 保存结构化事件，WorkManager 调度可延迟的网络任务。具体实现需遵循 Android 后台执行、网络约束、电量和存储限制；不能承诺系统在任意时刻立即运行后台任务。

## 三、本地日志数据模型

### 3.1 运行事件字段

| 字段 | 含义 | 约束 |
| --- | --- | --- |
| event_id | 全局唯一事件标识 | UUID/ULID；重试时保持不变 |
| task_id / run_id | 任务和一次执行标识 | 创建后保持稳定 |
| sequence_no | 同一 run 内的事件序号 | 单调递增；时间戳不能替代顺序号 |
| runtime_manifest_id | 运行版本组合引用 | 引用不可变清单 |
| event_type | 规划、工具、错误、验收、恢复等 | 使用版本化枚举或命名空间 |
| created_at | 事件产生时间 | 记录时钟来源；允许设备时钟偏差 |
| sync_status | 待同步、处理中、已确认、失败 | 状态转换可审计 |
| payload | 结构化事件数据 | 有大小限制、模式版本和隐私级别 |
| privacy_level | 数据敏感级别 | 决定上传和导出策略 |
| attachment_refs | 附件引用 | 附件单独管理、单独校验 |



### 3.2 建议的本地逻辑表

- runtime_manifests：任务实际使用的组件版本快照。

- runtime_events：结构化运行事件及同步状态。

- sync_batches：批次 ID、事件范围、尝试次数和最近错误。

- sync_receipts：服务端确认信息及确认时间。

- attachments：文件路径、大小、摘要、隐私等级和上传状态。

- checkpoints：任务恢复所需状态引用；与事件日志分离。

- export_jobs：导出范围、文件生成状态、完成位置和过期策略。

这些是逻辑实体。可根据事务和查询需求合并物理表，但不能把运行证据、同步状态和任务恢复状态混为一个不可区分的字段。

## 四、离线期间的记录与容量治理

1. 关键事件先写入事务型本地存储，再推进任务状态；对关键状态转移可采用同一事务写入状态与事件。

1. 按事件类别定义保留等级：关键故障与验收记录、普通执行事件、可重新生成的调试信息。

1. 附件使用独立文件仓库；数据库仅保存附件引用、摘要和状态，避免大文件拖慢事务。

1. 为本地事件库设置容量上限、预警阈值、附件上限和保留期限。

1. 空间紧张时优先清理已确认上传且超过保留期限的可重建数据；不得静默删除未同步的关键事件。

1. 如果必须清理未同步数据，应记录数据损失标记、原因和范围，并向用户明确提示。

1. 设备时间可能不准确，因此同一运行的因果顺序主要依赖 sequence_no 和事件关系，而非仅依赖墙上时钟。

## 五、恢复联网后的可靠同步协议

### 5.1 同步状态机

```text
PENDING
   │ 选入批次
   ▼
IN_FLIGHT
   ├─ 超时/断网/临时错误 ──► PENDING（退避后重试）
   ├─ 永久校验错误 ───────► QUARANTINED / NEEDS_REVIEW
   └─ 收到持久化回执 ─────► ACKNOWLEDGED
```

状态机应支持进程被杀、设备重启和重复调度。IN_FLIGHT 不能永久卡死；过期批次应能重新进入待同步队列。

### 5.2 批次与回执协议

1. App 为每个批次生成稳定 batch_id，并记录事件 ID 列表或可验证的连续范围。

1. 上传事件时保留原始 event_id；重试不得重新生成事件 ID。

1. 服务端先验证认证、模式版本、大小限制和必要字段，再执行幂等写入。

1. 服务端只有在事件已经持久化并可检索后才返回 ACK。

1. 回执包含 batch_id、已确认事件 ID 或可验证范围、服务端接收时间及协议版本。

1. 批次部分成功时，明确列出已确认与未确认事件，不能模糊返回整体成功。

1. App 依据回执更新状态；不得仅凭 HTTP 请求发出或连接成功就标记已同步。

1. 使用退避重试和抖动，避免网络恢复时大量客户端同时冲击服务端；永久错误进入隔离队列而非无限重试。

### 5.3 版本关联与版本对账

同步前或同步过程中，App 应确保 Runtime Manifest 可被服务端解析。历史事件必须引用当时的不可变版本清单；若服务端暂时不认识某个版本，应先上传清单或标记为待关联，不得用当前最新版本替代。

日志补传与更新下载应是独立队列。先传日志不要求先下载更新；更新服务不可用也不应阻止事件上传。

## 六、附件上传与完整性校验

- 大附件采用独立上传任务，记录 attachment_id、文件大小、SHA-256 摘要和上传进度。

- 支持分块或可恢复上传；服务端校验完整摘要后才标记附件完成。

- 事件可以先上传并标注附件待上传；附件完成后再关联完整诊断材料。

- 截图、屏幕录制、原始对话和文件内容属于高敏感诊断材料，应默认关闭或单独征得授权。

- 上传与导出前执行密钥、令牌、个人信息和其他敏感内容的脱敏策略。

## 七、离线诊断包导出

App 应在设置中提供“运行日志与诊断”入口，允许用户查看积压、立即同步、按任务和时间筛选、离线导出诊断包。导出通过 Android 系统文件选择器完成，不依赖服务端，也不应自动触发上传。

### 7.1 建议的诊断包结构

```text
evoagent-diagnostics/
├── manifest.json
├── device-info.json
├── runtime-manifests.jsonl
├── task-runs.jsonl
├── events.jsonl
├── sync-status.json
├── evaluation-results.jsonl
├── errors/
│   └── error-details.jsonl
├── attachments/
│   └── ...
└── checksums.sha256
```

### 7.2 导出规则

1. 支持导出全部日志、指定任务、指定时间段、指定能力和仅失败任务。

1. 导出清单记录包格式版本、导出时间、筛选范围、包含文件及脱敏状态。

1. 生成文件摘要以便验证导出过程是否损坏；摘要不代表内容来源一定可信。

1. 导出前显示将包含的敏感材料类别，并允许用户排除附件或原始内容。

1. 导出使用临时文件，成功完成后再交付；失败时清理未完成的临时包。

1. 导出操作不改变原始事件同步状态，也不默认删除本地数据。

## 八、诊断包受控导入

1. 服务端提供受控导入入口；导入前检查包大小、格式版本、文件路径、摘要和模式合法性。

1. 防止 ZIP 路径穿越、解压炸弹、恶意文件和超大嵌套结构；附件类型采用白名单。

1. 导入数据进入隔离区并标记来源为 offline_import，不与线上设备事件混淆。

1. 校验 task_id、run_id、runtime_manifest_id 的关联关系；缺失或冲突时标记待人工审查。

1. 导入内容只能作为证据，不执行其中任何命令、脚本或工具调用请求。

1. 经过验证后才能进入诊断流程；导入行为、操作者、时间和结果写入审计日志。

## 九、隐私、安全与数据完整性

- 默认上传结构化事件和必要错误元数据；原始对话、截图、录屏和文件按需授权。

- API 密钥、访问令牌、密码、会话 Cookie 等不得进入普通日志；导出前执行二次扫描。

- 传输使用 TLS；本地敏感数据按威胁模型评估是否采用加密存储及密钥保护。

- 为事件和附件设置访问控制、保留期限、删除策略与审计记录。

- 日志中的模型输出、工具参数和导入附件均视为不可信数据，不能直接当作指令执行。

- 提供数据删除和导出控制，并明确删除本地记录不等于撤回已上传到服务端的数据。

## 十、与任务恢复机制的边界

日志用于追溯发生了什么，检查点用于保存可恢复的任务状态，两者不可互相替代。

| 机制 | 职责 |
| --- | --- |
| 运行事件日志 | 记录状态变化、模型请求结果、工具调用结果、异常与验收证据。 |
| 任务检查点 | 保存恢复所需的任务状态、DAG 节点状态、输入输出引用和恢复游标。 |
| 副作用账本 | 记录发送消息、提交表单、创建文件等外部副作用是否已发生，防止重复执行。 |
| 恢复策略 | 决定重试、继续、补偿、请求用户确认或安全停止。 |



恢复任务前必须重新验证外部状态。不能因为日志显示某一步曾经发起，就假设该操作已成功或可以安全重放。

## 十一、建议的验收标准

| 测试项 | 验收标准 |
| --- | --- |
| 断网记录 | 执行期间断网，关键事件仍写入本地；重启 App 后记录仍存在。 |
| 中途断网续传 | 批次上传到一半断网，恢复后只补传未确认事件。 |
| 重复上传 | 同一事件重复发送多次，服务端只形成一份逻辑事件。 |
| 回执一致性 | 服务端返回 ACK 后，事件可查询；未持久化事件不得提前确认。 |
| 乱序与时钟偏差 | 按 sequence_no 还原单次运行顺序，不依赖设备时钟绝对准确。 |
| 服务端长期不可用 | App 可持续记录并离线导出；存储接近上限时明确告警。 |
| 导出完整性 | 导出包清单、摘要和筛选范围正确，且导出不修改同步状态。 |
| 敏感信息脱敏 | 测试令牌、密码和敏感内容不会意外进入默认导出包或上传批次。 |
| 恶意导入 | 路径穿越、超大压缩包、格式错误和异常附件均被拒绝或隔离。 |
| 版本追溯 | 历史事件始终关联运行时实际版本，不用最新版本覆盖旧清单。 |
| 任务恢复隔离 | 日志补传失败不会阻止安全处理；日志本身不会触发任务自动重放。 |



## 十二、与 EvoAgent 总体架构的关系

- 任务编排服务产生任务状态与执行事件。

- Runtime Manifest 为每次运行提供不可变版本追溯。

- 同步与观测服务接收事件并提供持久化回执。

- 进化与诊断服务消费经过验证的证据，创建诊断案例。

- 评测与发布门禁决定候选是否通过，不由日志同步服务作出。

- 版本分发服务与日志同步独立运行，互不阻塞。

- App 离线时仍可记录、查询和导出；服务端恢复后再同步。

## 十三、最终架构结论

EvoAgent 必须把离线日志能力作为一等基础设施，而不是普通调试日志的附属功能。它应覆盖本地可靠记录、容量治理、断点续传、服务端持久化回执、幂等去重、版本追溯、诊断包导出、受控导入和隐私保护。

最终保障目标是在网络中断时尽可能保留可诊断证据；在连接恢复后可靠同步；在长期无法连接时仍允许用户导出；并且任何日志同步或导入都不会绕过任务恢复、安全评测和版本发布门禁。

日志先落地，上传要有回执，重复必须幂等，导出不依赖网络，进化必须经过独立验证。
