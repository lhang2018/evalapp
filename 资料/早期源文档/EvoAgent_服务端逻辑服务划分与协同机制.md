# 服务端逻辑服务划分与协同机制

全量架构设计补充文件｜版本 1.0

主题：八个逻辑服务、双业务链、部署边界、控制权与故障隔离

## 文档说明

本文档补充 EvoAgent 总体架构，明确服务端逻辑服务的数量、职责边界、协同方式和建议部署形态。本文是全量架构目标设计，不代表相关服务已经实现或部署。

核心决策：采用“一个统一服务端平台、八个逻辑服务、两条业务链、四个受保护控制器”的架构。逻辑服务先划分清楚，物理部署再依据规模、可用性、资源和运维能力决定；不要求一开始就将每个逻辑服务部署为独立微服务。

## 一、架构决策摘要

- 目标架构划分为八个逻辑服务：任务编排、模型网关、能力与工具、记忆与上下文、同步与观测、进化与诊断、评测与发布门禁、版本分发。

- 八个逻辑服务分为稳定运行服务群与进化交付服务群。

- 稳定运行与进化实验在权限、资源、运行环境和发布流程上隔离。

- 服务间通过统一任务标识、运行标识、事件协议、版本清单和制品协议协同。

- 逻辑服务数量不等于服务器数量；可以先以模块化后端部署，后续再按负载和故障域拆分。

- 外部大语言模型 API 是模型网关连接的外部依赖，不计为 EvoAgent 自有逻辑服务。

- 数据库、对象存储、Git、队列、监控和密钥管理属于共享基础设施，不计入八个逻辑服务。

## 二、总体逻辑架构

系统包含 Android App、统一 API 入口、稳定运行服务群、进化与交付服务群以及共享基础设施。

```text
Android App
   │
   ▼
统一 API 入口 / 身份认证 / 协议校验
   │
   ├── 稳定运行服务群
   │     1. 任务编排服务
   │     2. 模型网关服务 ───── 外部云端模型 API
   │     3. 能力与工具服务
   │     4. 记忆与上下文服务
   │
   ├── 进化与交付服务群
   │     5. 同步与观测服务
   │     6. 进化与诊断服务
   │     7. 评测与发布门禁服务
   │     8. 版本分发服务
   │
   └── 共享基础设施
         事务数据库 / 对象存储 / Git / 任务队列
         制品仓库 / 监控 / 密钥管理
```

## 三、八个逻辑服务的职责

### 1. 任务编排服务

统一任务状态、意图路由、Planning、ReAct 协调、工作流调度、检查点和恢复。

职责边界：当前任务的权威状态由运行时控制器管理。

### 2. 模型网关服务

接入不同模型 API，完成模型路由、请求适配、工具调用格式处理、超时、限流和成本计量。

职责边界：模型供应商是外部依赖；模型网关不等于模型本身。

### 3. 能力与工具服务

管理领域专家、能力契约、工具注册、工具版本、工作流资产和可远程执行的工具。

职责边界：手机原生接口、无障碍操作等仍由 App 端执行。

### 4. 记忆与上下文服务

管理记忆生命周期、可信状态、检索、冲突检测、上下文装配和压缩策略。

职责边界：记忆事实、运行证据和诊断假设必须区分。

### 5. 同步与观测服务

接收 App 事件、去重归档、处理同步回执、关联版本清单、接收健康与回滚反馈。

职责边界：必须支持幂等、断点续传、隐私过滤和事件保留策略。

### 6. 进化与诊断服务

分析根因、排序问题、生成候选改进、管理实验计划和隔离实验资源。

职责边界：不得直接覆盖生产版本或绕过发布门禁。

### 7. 评测与发布门禁服务

执行契约测试、回归、端到端评测、成本比较、兼容性和安全门禁。

职责边界：候选自评或模型解释不能替代独立评测证据。

### 8. 版本分发服务

管理发布清单、签名制品、能力包、策略包、工作流包、客户端制品、灰度、晋级和撤回。

职责边界：App 必须校验签名、兼容性、授权范围和回滚方案。

## 四、两条业务链如何协同

### 4.1 任务执行链

1. App 提交任务目标、约束、风险信息及当前能力环境。

1. 任务编排服务创建任务并决定领域专家、执行模式和验收条件。

1. 记忆与上下文服务提供经过治理的上下文；模型网关选择合适模型并返回行动建议。

1. 任务编排服务在权限、状态和预算约束下调度能力、工作流和工具。

1. 工具执行结果返回后，执行器与验收机制检查真实状态；必要时恢复、等待或停止。

1. 任务关键事件和运行版本清单被持久化，供后续诊断和追溯。

并非每个任务都必须经过全部服务。简单的本地手机操作可以由 App 在本地完成；复杂长任务则可以调用云端规划、工具和工作流。

### 4.2 进化反馈链

1. App 将必要的结构化运行事件写入本地持久化队列。

1. 同步与观测服务接收事件批次，去重并关联 task_id、run_id 和 Runtime Manifest。

1. 进化与诊断服务根据证据建立诊断案例，分析可能的根因和影响范围。

1. 进化控制器创建隔离候选，明确基线版本、变更范围、预算和评测计划。

1. 评测与发布门禁服务验证质量、稳定性、安全、兼容性和成本收益。

1. 版本分发服务为获批候选生成签名发布清单和制品。

1. App 对账、下载、验证并在安全时机应用更新。

1. App 回传应用状态与后续真实运行指标，供晋级、暂停或回滚决策使用。

## 五、四个受保护控制器

### 运行时控制器

掌握当前任务的执行权，管理任务状态、权限、预算、工具授权、检查点、取消与恢复。

### 进化控制器

掌握授权范围内的实验编排权，决定分析什么、生成什么候选、使用多少实验预算。

### 评测门禁控制器

依据独立测试证据判定候选是否满足质量、安全、兼容性和成本要求。

### 发布控制器

决定哪些获批版本可以发布、分发、晋级、暂停或回滚，并保留审计记录。

这四个控制器可以作为逻辑模块实现，不要求分别部署成四台服务器，但其权限和状态所有权必须明确。进化控制器不能因为候选由自己生成，就自行判定候选正确并直接发布。

## 六、建议的部署边界

| 部署单元 | 建议包含的逻辑服务 | 主要原则 |
| --- | --- | --- |
| 稳定任务后端 | 1、2、3、4 | 优先保障任务执行可用性；进化实验不能争抢其关键资源。 |
| 进化控制后端 | 5、6、7 | 隔离候选代码、测试环境和实验资源；限制网络、凭证与副作用。 |
| 版本分发后端 | 8 | 独立管理制品、签名、发布范围、客户端状态与回滚。 |
| 外部模型服务 | 外部供应商 API | 通过模型网关接入，允许按任务与成本策略切换。 |
| 共享基础设施 | 数据库、对象存储、Git、队列、监控、密钥管理 | 依据可靠性、访问模式和规模分别部署与备份。 |



上述部署边界是建议，而非要求从第一天起采用微服务。初期可将稳定任务服务内部模块化部署，但进化实验执行环境应与生产任务隔离；当负载、团队规模或可用性要求提高时，再拆分高负载服务。

## 七、服务之间如何通信

### 7.1 同步调用

适合有明确即时响应需求的操作，例如创建任务、读取当前版本清单、获取能力描述、模型调用和检查工具契约。

### 7.2 异步事件

适合运行事件上传、长任务状态变更、诊断案例创建、评测任务调度、候选状态变化、发布结果和客户端应用回执。

### 7.3 统一关联字段

- task_id：用户任务的稳定标识。

- run_id：一次实际执行的标识。

- correlation_id：跨服务追踪同一业务链。

- causation_id：标识由哪个事件或动作触发。

- runtime_manifest_id：关联运行所使用的不可变版本组合。

- candidate_id / release_id：关联候选与正式发布。

- event_id / idempotency_key：支持事件去重和副作用保护。

## 八、共享基础设施与数据所有权

| 基础设施 | 用途与约束 |
| --- | --- |
| 事务数据库 | 任务状态、版本元数据、候选状态、发布记录、记忆索引与审计索引。 |
| 对象存储 | 大体积产物、评测报告、必要诊断附件、生成素材和发布制品。 |
| Git 仓库 | 源代码、提示词、策略配置、工作流定义、测试代码和架构资产。 |
| 任务队列 | 异步诊断、评测、制品构建、同步处理与分发任务。 |
| 制品仓库 | 保存有摘要、版本、来源与签名信息的发布资产。 |
| 监控与日志系统 | 记录服务健康、时延、错误率、资源使用、成本和告警。 |
| 密钥管理 | 隔离模型 API 密钥、签名密钥与其他敏感凭证，限制访问权限。 |



## 九、故障隔离与降级原则

| 故障 | 应有行为 | 禁止行为 |
| --- | --- | --- |
| 进化服务不可用 | 继续使用已批准稳定版本；积压事件待恢复后同步。 | 阻塞正常任务或自动启用未验证候选。 |
| 模型 API 不可用 | 使用已批准的备用路径；不满足条件时安全停止。 | 无限重试或绕过预算限制。 |
| 同步服务不可用 | 事件保存在本地队列，重连后幂等补传。 | 因上传失败丢弃关键事件。 |
| 发布服务不可用 | 保留现有版本，继续执行兼容任务。 | 将不完整或未验证制品直接激活。 |
| 候选评测失败 | 拒绝晋级，保留失败证据。 | 以模型自评代替独立门禁。 |
| 更新后健康异常 | 停止推广，按适用机制回滚或停用候选。 | 假设所有更新均可无条件逆转。 |



## 十、关键架构约束

1. 逻辑服务先于物理拆分。 明确职责、接口和状态所有权，但不要求每个逻辑服务独立部署。

1. 稳定执行与进化实验隔离。 候选代码、测试数据、凭证和资源不能默认继承生产权限。

1. 每次运行可追溯。 运行事件必须关联 task_id、run_id 和实际 Runtime Manifest。

1. 候选不能自批自发。 进化、评测门禁和发布控制器具有独立职责与权限。

1. 成本由程序化控制器约束。 正式任务与进化实验采用独立预算，模型建议不能覆盖硬预算。

1. 离线能力不依赖进化服务。 App 保留已批准能力、检查点和本地事件队列。

1. 发布包必须兼容且可恢复。 校验签名、依赖、目标范围、发布授权和回滚方案。

1. 数据最小化。 只上传诊断所需且获准共享的数据，敏感内容按策略处理。

## 十一、架构结论

EvoAgent 的目标架构划分为八个逻辑服务：任务编排、模型网关、能力与工具、记忆与上下文、同步与观测、进化与诊断、评测与发布门禁、版本分发。

它们组成两条业务链：稳定任务执行链与持续进化反馈链。两条链通过统一任务标识、运行版本清单、事件协议、候选评测记录和签名发布清单协同。

推荐先冻结逻辑职责、接口契约、状态所有权和安全边界，再依据负载、可靠性和运维能力确定物理部署。这可以防止架构因部署规模变化而反复推翻，同时避免过早采用复杂微服务。

最终原则：执行权归运行时控制器；实验权归进化控制器；正确性由独立评测门禁判断；发布权归发布控制器。
