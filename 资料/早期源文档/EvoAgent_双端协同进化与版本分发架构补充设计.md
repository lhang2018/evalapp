# 双端协同进化与版本分发架构补充设计

全量架构设计补充文件｜版本 1.0

主题：App 运行证据上行、服务端进化、能力更新下发、客户端验证与回滚

## 文档说明

本文档补充 EvoAgent 总体架构中“双端协同进化与版本分发”部分。前述总体架构已覆盖日志、版本清单、制品管理和发布机制，但需要进一步明确 App 与服务端之间的完整闭环协议。

本设计不是 V0.1 范围说明，而是面向 EvoAgent 全量产品的架构约束。研发可以分阶段实施，但双向同步、版本追溯、更新兼容、验证与回滚必须作为统一设计目标。

## 一、核心结论

服务端优化要真正改善手机端智能体，不能只做到“上传日志”和“下载更新”。必须形成一条可追溯、可验证、可恢复的闭环：

运行问题 → 版本化证据 → 根因诊断 → 局部改进 → 隔离评测 → 受控发布 → App 应用 → 线上验证 → 继续进化

核心原则：服务端进化不等于每次发布新的 Android 安装包。提示词、策略参数、模型路由和兼容的工作流通常可以通过版本化能力包更新；涉及原生执行器、权限机制、底层状态机等变化时，才需要客户端软件更新。

## 二、总体架构与职责边界

建议将双端协同能力提升为独立子系统，包含两个正式模块：

- Evolution Sync Service：负责运行事件上传、同步确认、版本对账、候选状态同步和应用结果回传。

- Release & Capability Delivery Service：负责策略包、工作流包、模型适配包及客户端制品的版本化发布和分发。

这两个模块应与进化控制器分离，避免候选生成、评测与生产发布混为一体。

### 2.1 Android App：稳定执行端

- 执行已批准的任务、策略和工作流。

- 记录结构化运行事件、关键状态、版本清单引用和验收结果。

- 将事件先写入本地持久化队列，网络恢复后再同步。

- 验证收到的更新包、依赖、签名、兼容性和发布资格。

- 在安全时机激活兼容更新，监测健康状况并在必要时回滚。

- 服务端不可用时，继续运行允许离线执行的能力。

### 2.2 服务端：诊断与进化中心

- 接收并归档经过隐私过滤的运行证据。

- 根据任务、运行和版本标识还原当时的组件组合。

- 建立诊断案例，分析模型、提示词、上下文、记忆、工具、工作流或环境根因。

- 创建隔离候选，执行自动评测、成本比较、兼容性检查和安全门禁。

- 生成发布清单与签名制品，分发给适用的客户端。

- 接收 App 应用结果与线上运行反馈，决定晋级、暂停或回滚。

## 三、App 运行日志如何与服务端关联

关联的关键不是上传一个日志文件，而是为每次任务执行建立完整追溯链。每个任务运行都应记录任务身份、设备安装实例、组件版本组合、执行事件、检查点、成本和验收结果。

### 3.1 每次运行必须记录的身份信息

| 类别 | 建议记录内容 |
| --- | --- |
| 任务身份 | task_id、run_id、parent_task_id（如适用） |
| 设备身份 | 匿名化 device_id、安装实例标识、客户端版本 |
| 能力身份 | 专家 ID/版本、能力包 ID/版本、工作流 ID/版本 |
| 模型身份 | 模型标识、模型适配版本、路由策略版本 |
| 执行组件 | 提示词、Planning、ReAct、Harness、工具适配器版本 |
| 环境信息 | Android 版本、必要的权限状态、相关环境特征 |
| 运行证据 | 状态变化、工具调用结果、错误码、检查点引用 |
| 验收信息 | 目标是否达成、验收方法、验收证据引用 |
| 资源消耗 | 模型调用次数、时延、可获得的费用、重试次数 |



### 3.2 Runtime Manifest：运行版本清单

Runtime Manifest 是每次运行的版本快照或不可变引用，记录该次运行实际使用的组件组合。它必须在运行期间保持可追溯，不能随着后续配置更新而被覆盖。

逻辑关联关系：

Task → TaskRun → RuntimeManifest → App / ModelProfile / Prompt / Harness / Tool / Workflow Versions
                         ├── RuntimeEvents
                         ├── Checkpoints
                         ├── Artifacts
                         └── EvaluationResult

服务端通过 task_id、run_id 和 Runtime Manifest 关联日志、组件版本、诊断案例、候选实验和发布记录。如果无法确定根因，必须保留多个假设，而不能凭一条失败日志直接修改某个组件。

### 3.3 本地事件队列与上传协议

1. 运行时事件首先写入本地持久化队列，避免进程退出或断网造成关键证据丢失。

1. 每条事件包含唯一 event_id、task_id、run_id、时间戳、事件类型和版本清单引用。

1. 网络可用时，按批次上传经过隐私过滤的事件。

1. 服务端返回同步回执；App 只有在确认后才将事件标记为已同步。

1. 上传失败时保留事件并采用有限重试；重复上传必须幂等。

1. 默认优先上传结构化事件。完整对话、截图、文件和界面内容按必要性、用户授权及隐私策略处理。

## 四、服务端优化成果如何影响 App

更新必须按资产类型分类，不能用一个通用的“下载更新”流程处理所有变化。

| 更新类型 | 典型内容 | 客户端应用方式 |
| --- | --- | --- |
| 策略与配置 | 提示词、已批准重试策略、路由参数、非关键配置 | 版本化配置包；校验后激活，可回滚 |
| 领域能力与工作流 | 专家策略、DAG、节点模板、验收规则 | 能力包/工作流包；要求执行器和工具契约兼容 |
| 模型适配 | 模型 API 适配、工具调用格式、模型专用策略 | 更新模型档案与适配包；重新检查兼容性 |
| 客户端代码 | 原生执行器、核心状态机、底层数据库、权限机制 | 构建、测试、签名，并通过合规的 App 更新机制交付 |



服务端能够改进行为策略，并不意味着旧客户端自动获得新的原生能力。如果候选工作流需要旧 App 不具备的工具接口或权限能力，则该更新必须被判定为不兼容，并先交付相应客户端能力，或者提供兼容的替代路径。

## 五、发布清单与能力包分发

### 5.1 发布清单应包含的信息

- release_id、发布通道、目标平台、目标领域或能力。

- 基线发布版本与依赖组件版本。

- 能力包、策略包、工作流包或客户端制品的 ID、版本和摘要。

- 最低兼容 App 版本、必需工具契约和运行环境要求。

- 评测报告引用、门禁状态、发布授权范围。

- 制品签名、完整性信息、回滚目标和启用策略。

- 必要的预算、安全策略与数据格式兼容信息。

### 5.2 App 收到更新后的检查流程

1. 检查目标平台、目标能力和当前版本是否匹配。

1. 检查最低兼容版本与所需工具契约是否满足。

1. 验证制品签名、摘要和完整性。

1. 检查发布资格、授权范围和评测状态。

1. 检查存储空间、运行资源和当前任务是否允许切换。

1. 确认存在可用回滚目标或明确的恢复方案。

1. 任何必要检查失败时拒绝激活，保留当前稳定版本。

### 5.3 安全激活与回滚

对于可独立版本化的策略和能力包，采用双版本槽位或等价的原子切换机制：下载候选 → 校验 → 隔离测试 → 准备激活 → 切换版本引用 → 健康监测 → 晋级或回滚。

Android 原生代码更新必须采用符合平台要求的应用更新机制，不能把普通配置热更新当成 APK 热替换。运行中的任务默认固定使用启动时记录的版本清单；新版本通常只对后续任务生效。

## 六、从一次失败到实际改善的完整闭环

1. App 发现问题：操作后状态与预期不符，验收器判定失败；记录事件、证据引用和当前版本清单。

1. 证据上行：同步协议上传允许共享的事件，服务端根据 task_id、run_id、组件版本和环境建立诊断案例。

1. 根因分析：分析页面变化、工具异常、模型行为、上下文遗漏或执行验证缺陷；不确定时保留多个假设。

1. 创建局部候选：仅修改证据支持的组件或领域能力，避免无必要地改动共享内核。

1. 隔离评测：使用固定案例、异常场景和恢复测试比较基线与候选，同时评估质量、成本、时延与误操作风险。

1. 发布门禁：通过兼容性、安全、质量和成本门禁后，生成签名发布清单。低风险候选可按授权自动发布。

1. App 应用：App 验证目标、版本、签名和依赖，在适当时机启用更新。

1. 线上反馈：持续监测真实任务表现；改善得到证据支持则保留，否则停止推广或回滚。

## 七、离线、断网与版本对账

| 故障场景 | App 行为 | 恢复后的处理 |
| --- | --- | --- |
| 进化服务离线 | 继续使用已批准的稳定版本 | 上传积压事件，恢复诊断与进化 |
| 网络完全中断 | 执行允许离线的任务，持久化检查点与事件 | 重连后按回执同步事件和状态 |
| 模型 API 不可用 | 使用已批准的备用路径，否则安全停止 | 根据证据诊断依赖故障或适配问题 |
| 更新服务不可用 | 不影响现有稳定版本 | 恢复版本对账和更新分发 |
| 更新校验失败 | 拒绝激活，继续使用稳定版本 | 记录发布故障并重新检查制品 |
| 新版本运行异常 | 停止推广或按策略回滚 | 分析线上证据并创建后续候选 |



App 恢复联网后不能盲目逐个安装离线期间积累的所有历史版本。它应与服务端进行版本对账，选择一个兼容、已授权、经过验证且具有明确迁移路径的目标版本。

## 八、建议新增或明确的逻辑数据实体

| 实体 | 用途 |
| --- | --- |
| device_installations | 设备安装实例与同步状态 |
| runtime_manifests | 每次任务实际使用的组件版本组合 |
| runtime_events | App 运行事件 |
| sync_batches | 事件同步批次 |
| sync_receipts | 服务端接收确认 |
| evolution_cases | 由运行问题建立的诊断案例 |
| evolution_candidates | 候选改进及其基线和状态 |
| evaluation_runs | 候选测试与评测结果 |
| release_manifests | 正式发布清单 |
| release_artifacts | 策略包、能力包和客户端制品 |
| device_release_states | 安装实例的当前版本与目标版本 |
| deployment_records | 发布、下载、激活与部署记录 |
| rollback_records | 回滚原因、目标版本与恢复结果 |



上述为逻辑实体，不要求全部实现为独立物理表。实际物理模型应根据事务边界、数据规模、查询模式和保留策略确定。

## 九、必须写入总体架构的四条规则

1. 每次运行都必须可追溯到版本组合。 否则服务端无法准确判断问题来自哪个组件或环境。

1. 每项进化成果必须声明适用范围和兼容条件。 领域改进不能无条件影响其他领域；新模型或工作流不能默认适用于旧客户端。

1. 所有更新必须经过验证、授权和可恢复的激活流程。 候选生成、发布成功、客户端应用成功和真实质量改善是不同状态。

1. App 是执行端和证据采集端，但不是无限制的自修改端。 本地可进行授权范围内的恢复与配置选择；核心代码变更必须经过隔离构建、测试、签名和受控更新。

## 十、建议的模块边界与接口

### 10.1 Evolution Sync Service

- 接收事件批次并返回同步回执。

- 提供版本对账接口，返回适用的目标发布清单。

- 接收客户端应用结果、健康指标和回滚事件。

- 提供断点续传、去重、批次状态查询和事件补传能力。

### 10.2 Release & Capability Delivery Service

- 存储和分发签名的版本清单及制品。

- 根据平台、App 版本、能力、工具契约和发布通道筛选适用更新。

- 维护发布状态、灰度范围、晋级、暂停与撤回记录。

- 确保已发布制品可追溯到候选、评测报告和基线版本。

### 10.3 App 侧更新管理器

- 周期性或在合适时机进行版本对账。

- 下载前检查目标，下载后校验签名与完整性。

- 在安全时机准备和激活更新。

- 保留当前稳定版本引用，记录启用结果。

- 将更新成功、失败、健康检查和回滚结果回传服务端。

## 十一、最终架构结论

EvoAgent 的双端协同不是简单的日志上传和配置下载，而是由运行证据、版本追溯、根因诊断、候选评测、受控发布和线上反馈组成的基础设施。

执行权由运行时控制器掌握；改进权由进化控制器在授权范围内行使；正确性由独立验收体系验证；发布权由受保护的发布控制器管理；所有关键行为都必须可追溯、可约束、可恢复。

只有将上行证据链、下行发布链和线上反馈链真正连接起来，服务端的进化成果才能持续改善手机上的智能体，而不是停留在服务端生成了一份更好的提示词或代码。

## 附录 A：建议的端到端协议摘要

1. 运行时创建 task_id、run_id，并固定 Runtime Manifest。

1. 关键运行事件先持久化到本地队列。

1. 网络可用时上传事件批次，服务端返回幂等同步回执。

1. 服务端将异常聚合为诊断案例，记录证据和根因假设。

1. 进化控制器创建隔离候选并关联基线、评测集和预算。

1. 评测系统给出质量、成本、安全与兼容性证据。

1. 发布控制器生成签名清单和制品，并定义目标范围与回滚策略。

1. App 进行版本对账、依赖检查、签名验证和安全激活。

1. App 回传应用状态及后续运行指标。

1. 发布控制器依据真实表现晋级、暂停或回滚版本。
