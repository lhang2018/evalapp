## 1. 当前项目处于什么阶段

**目前是已有较完整基础模块的个人智能体参考实现，可靠同步做得较深入；距离正式设计要求的“能安全执行、持续改进、分发真实能力并长期自主推进”仍有明显差距。**

主要差距集中在三处：

1. **执行边界尚未闭合**：专家工具白名单只是模型可见列表；工作流审批可被绕过；未知副作用在异常路径上不能可靠落账，工作流还会重试。
2. **闭环中的记录管理超过了实际行为能力**：候选、评测、发布、客户端槽位都有管理逻辑，但候选变更未装载进评测运行时，客户端也未真正下载、独立验证和装载能力制品。
3. **长期自主目标体系基本缺失**：Goal Registry、目标状态机、自主等级、子目标治理、APRO 调度和收益归因没有形成实现。

不建议继续引用旧报告“38%”或更早“66%”作为当前完成率。现有台账同时包含历史结论和最新局部更新；按字段、按主题、按端到端验收会得到不同数字。**本报告用具体链路和验收条件判断，不给未经全面验收的单一完成百分比。**

## 4. 必须优先处理的五类问题：均有最小复现

探针只使用临时数据库/文件和无外部副作用的假工具。脚本与原始结果保存在本报告第 9 节所列审查目录。

### P0-1 专家工具白名单没有执行时强制检查

设计对应 R-09 / C-03 / S-01 / S-03。

`ReactEngine.run()` 的 `allowed_tools` 只用于筛选发给模型的 Schema，随后直接按模型返回的工具名调用全局注册表。工具注册表不接收当前专家或任务的允许列表。

**复现：传 allowed_tools=[]，假模型提出调用已注册工具，工具仍被执行。**

证据：[react/engine.py:75](E:/evalapp/evoagent/react/engine.py:75)、[react/engine.py:129](E:/evalapp/evoagent/react/engine.py:129)。

验收要求：在执行网关根据任务授权、专家允许列表、工具权限及目标范围统一检查；即使模型返回不在 Schema 中的工具名，也必须在调用 runner 前拒绝并留事件。

### P0-2 工作流审批节点可以未经审批执行

设计对应 R-06 / R-09 / A-01。

controller 以 `check_op("workflow_node_confirm", ...)` 判断审批；该操作未列入 high_risk_ops，check_op 默认允许。ApprovalStore 已存在，但这个分支根本没有进入高风险决策与记账。

**复现：PermissionController(high_risk_mode="deny").check_op("workflow_node_confirm", ...) 返回 allow。**

证据：[controller.py:479](E:/evalapp/evoagent/core/controller.py:479)、[permissions.py:45](E:/evalapp/evoagent/core/permissions.py:45)、[permissions.py:76](E:/evalapp/evoagent/core/permissions.py:76)。

验收要求：审批节点必须得到绑定任务/节点/动作摘要的有效授权；没有授权进入可恢复等待态。补 approve/reject/撤销/过期接口和客户端流程，不能把“有审批表”视为完成。

### P0-3 副作用账本没有覆盖最需要保护的时机和异常路径

设计对应 R-12 / R-11 / ADR-006。

当前 ReAct 在工具**返回后**才调用 record_from_tool_result；进程在“外部已提交→结果返回→落账”之间崩溃时，没有预先落库的操作意图。另一个确定性漏洞是：注册表异常返回的 failed.evidence 只有 attempts，缺 side_effect_level，账本因此直接忽略。

**复现：外部工具抛 TimeoutError，result.side_effect_uncertain=True，但 ledger_id=null、pending=0。**

证据：[registry.py:195](E:/evalapp/evoagent/tools/registry.py:195)、[registry.py:209](E:/evalapp/evoagent/tools/registry.py:209)、[side_effects.py:98](E:/evalapp/evoagent/core/side_effects.py:98)、[react/engine.py:135](E:/evalapp/evoagent/react/engine.py:135)。

验收要求：工具网关统一在执行前持久化 planned/submitted、稳定 effect/idempotency 身份，所有正常/异常/超时路径回写结果。重启必须能发现 submitted/unknown；对账前阻断重放，不能只靠 force 跳过检查。

### P0-4 DAG 会重试结果未知的外部动作

设计对应 R-06 / R-12。

WorkflowEngine 把失败 ToolResult 转成普通 RuntimeError，丢掉 side_effect_uncertain、幂等性和外部回执等信息；节点循环对普通异常按 max_retries 重试。DAG 的工具调用也没有接入 ReAct 的副作用记账 sink。

**复现：假工具返回 side_effect_uncertain=True、max_retries=1，同一节点执行两次；没有账本记录。**

证据：[workflows/engine.py:191](E:/evalapp/evoagent/workflows/engine.py:191)、[workflows/engine.py:302](E:/evalapp/evoagent/workflows/engine.py:302)。

此外，超时采用 daemon 线程 join 超时，不能停止旧工具线程；此时开始节点重试还可能与上一调用重叠。此项为代码推断，本轮没有调用真实外部服务验证。

验收要求：DAG 与 ReAct 共用动作网关，保留结构化结果；unknown→等待对账，无重试、替代或补偿重放；用受控进程或外部调用取消协议处理超时。

### P0-5 发布校验不能证明制品正文完整

设计对应 O-07 / S-11 / 系统验收 14。

build_manifest 生成摘要与签名；verify 只验证“存储的摘要对应签名”及“文件中的摘要字段等于内存摘要”，**没有重新计算文件正文摘要**。当制品文件不存在时 artifact_ok 仍默认 True。

**复现：修改临时制品的 version/min_app_version，保留 artifact_digest，verify 返回 ok=True；删除制品文件后仍返回 ok=True。**

证据：[release/manager.py:87](E:/evalapp/evoagent/release/manager.py:87)、[release/manager.py:150](E:/evalapp/evoagent/release/manager.py:150)。

验收要求：明确签名载荷与规范化编码，签名绑定制品正文、兼容声明及依赖；重新计算完整摘要；文件缺失、正文变化、摘要/签名变化全部拒绝。端侧持受信公钥独立验证真实下载字节。

## 5. 其余核心差距与补齐方向

### 5.1 任务控制、身份与恢复：部分完成

- `request_user` 只让 ReAct 返回 needs_user，controller 随后仍进入 VERIFYING；没有统一“保存问题→等待→提交答案→恢复当前步骤”流程。
- 分类阶段 critical 低置信会进入 WAITING_USER，但 resume_task 只支持 SUSPENDED/FAILED，API 未提供澄清答案入口。
- 工作流主动暂停被 pause_task 显式拒绝；审批等待和补偿恢复没有完整的任务级语义。
- run_id 固定为 `run_<task_id>`，恢复仍使用相同 ID；save_run 使用 INSERT OR REPLACE，会覆盖同任务的上次执行记录，偏离“一次执行/恢复一次 run，关联父 run”的契约。
- 检查点支持 latest 及 DAG 输出复用，但恢复控制还依赖进程内 _active；不能据此认定杀进程后任务能自动正确续跑。

证据：[controller.py:162](E:/evalapp/evoagent/core/controller.py:162)、[controller.py:618](E:/evalapp/evoagent/core/controller.py:618)、[controller.py:634](E:/evalapp/evoagent/core/controller.py:634)、[persistence.py:67](E:/evalapp/evoagent/core/persistence.py:67)。

建议先定义 Task/Run/Node/Approval 的联合状态转移，再补跨端交互，避免各层自行把等待映射成失败。

### 5.2 进化：已有管理骨架，缺少实际变更的对照实验

- 自动信号采集已接到运行事件；消费方法 run_signal_pipeline/run_evolution_round 目前只有内部方法及测试调用，没有生产调度入口。采集器窗口、冷却和 tickets 也主要在内存。
- EvolutionCandidate 保存问题、假设、证据和评测状态，没有绑定实际候选 patch/配置包及内容摘要。Evaluator 的 baseline 标记主要进入报告，baseline/candidate 都调用同一 ControllerTaskRunner。
- ControllerTaskRunner 只有 model_id 等覆盖项，没有按 candidate_id 装载候选策略/工具/代码。**当前两次评测不能证明某个候选变更产生了收益。**模型迁移已有固定目标模型的专用路径，应与通用候选改进区分。
- FailureRegressionBuilder 生成 EvalCase 后追加到内存 datasets；没有持久化回归资产、环境/故障夹具和发布版本。_pick_dataset 默认也不选择 failures_regression。
- 新增 run_evolution_round 用状态计数限制进行中评测，但无原子占槽；直接 evaluate_candidate 也不经过该限制。不能视为全入口并发控制已完成。
- 首轮 E-13 的“第二轮没有新证据应停止”失败；同日其他在途改动加入评测流量过滤后，专项 7 项均通过。后续仍需验证所有事件入口、重启与持续调度，防止评测失败持续制造下一轮候选。
- 内置任务评测仅 smoke 3 条 + holdout 1 条，全部是时间/计算；路由专用集不能替代编程、漫剧、手机任务的能力验收。
- 依赖分析现在有真实调用，但选集只是 affected_closure→holdout；没有逐项消费 must_rerun_tests，并且信号 target 为 expert/<id> 等、图中 ID 是 file_toolset/coding_tasks，需要统一映射。

证据：[evolution/controller.py:187](E:/evalapp/evoagent/evolution/controller.py:187)、[evolution/controller.py:230](E:/evalapp/evoagent/evolution/controller.py:230)、[evolution/controller.py:368](E:/evalapp/evoagent/evolution/controller.py:368)、[runner.py:37](E:/evalapp/evoagent/evolution/runner.py:37)、[regression.py:27](E:/evalapp/evoagent/evolution/regression.py:27)、[datasets.py:12](E:/evalapp/evoagent/evolution/datasets.py:12)。

建议验收一个可观察变更：同一失败用例，稳定版本失败、候选版本通过；实际运行清单能定位两份不同的不可变资产；拒绝候选不改变生产，批准发布后真实行为改变并可回滚。

### 5.3 发布更新：状态机可测，实际交付链未实现

### 5.4 手机操作：原生能力和自然语言任务仍是两条路径

DeviceBroker、Kotlin 无障碍、前后观察、连续未验证停止、高风险确认已有具体实现。App 的快捷操作通过 runDevice→broker.execute 调用。

离线任务实际只允许 time_query；其他任务可靠排队已有，但未形成按模型/服务端/网络/同步故障划分的完整能力降级矩阵。端侧存储为 AsyncStorage JSON 加实例内串行链，与设计要求的事务型 Task/Run/事件/检查点存储仍有差距，需补跨前台/headless 并发与崩溃一致性验收。
