## 认领与开工

1. 读本页及[开发任务认领表](开发任务认领表.md)，选定一个任务卡。
2. 集成人处理[ALN-00 基线发布](任务卡/00-基线发布.md)，把实际 commit 写入 workboard.json。默认此前只准备接口、夹具和独立草稿；本轮用户已明确授权 ALN-04-R/UI 在共享候选工作区开发与接线，该授权记录在 working_basis。
3. 在 [workboard.json](workboard.json) 对应任务卡填写 owner、reviewer、branch、状态。ALN-04-R/UI 已由 codex-runtime 认领并进入 review；其他负责人的状态保留其实际登记，不代替他们宣布完成。
4. 从公布的同一个基线 commit 建自己的分支/工作树；读任务卡中的独占路径与共享文件规则。
5. 先提交接口约定和最小行为测试，再实现本卡；超出边界的改动由集成人协调。不要在同一工作目录同时开发多个相互覆盖的任务。
6. 完成后按[交付模板](交付模板.md)记录行为、迁移、测试、兼容和限制；由 reviewer 验证，集成人处理共享接线并更新台账。

示例（BASELINE_COMMIT 必须替换为已发布的真实 commit）：

```powershell
git worktree add -b codex/aln-06-assets ../evalapp-aln06 BASELINE_COMMIT
```

已有工作区含未提交改动，不能用重置、清理或整目录覆盖来“同步基线”。不同分支分别占用工作树即可。

## 建议分工：四条开发线，加一项集成职责

人数不足时一人可承担多项职责；人数更多时先按独占目录细分，再增加并发。没有预设真实人员或工期。

| 开发线 | 第一项交付 | 主要范围 | 首轮任务卡 |
|---|---|---|---|
| 运行内核 | 进程中断后的运行所有权、接管与安全恢复 | ALN-01、02、04，后续 07、13、14、15、20 | [运行恢复](任务卡/04-运行恢复.md) |
| 资产与发布/进化 | 统一资产身份、不可变版本和最小装载边界 | ALN-03、06，后续 09、10、17、18、19 | [资产基础](任务卡/06-资产基础.md) |
| 模型与上下文/证据 | 全层路由评测、真实计量与未知费用处理 | ALN-08，后续 05、16 | [模型与计量](任务卡/08-模型与计量.md) |
| Android | 管理员完整参数审阅及批准/拒绝页面 | ALN-04 的 UI 子任务，后续 11、12、21 | [Android 审批](任务卡/04-Android审批.md) |

这是一组可以分工推进的首轮增量，不是允许跳过原有依赖。资产和模型线先产出协议/独立实现；消费者接入和整包关闭仍按[原实施计划](../全量对齐与下一步实施计划_2026-10-22.md)的前置条件执行。

## 批次与整合顺序

| 波次 | 启动内容 | 合入/退出条件 |
|---|---|---|
| 基线准备 | ALN-00；其余四线准备接口和夹具 | 发布真实基线 commit；源码与测试清单一致；在途改动有归属 |
| 第一轮并行 | 运行接管、资产身份、路由/计量、审批 UI | 接口先审阅；独立模块测试通过；共享文件集中接线；不直接关闭整包 |
| 第二轮接线 | 运行闭环验收；ContextManifest、Goal 授权、计划修订、手机协议；候选隔离按依赖启动 | 相应 ALN 前置证据满足，再接到真实执行路径；跨域契约一次定义 |
| 第三轮业务闭环 | 候选变更/回归门禁 → 制品下发与装载；APRO/持续目标；真实能力包 | 依赖、权限、费用、回滚和真实产物均可验证；真机/供应商验证有证据 |
| 最终验收 | ALN-22 | 正式版 20 条系统验收及约定的全量主题闭合；不以测试数量代替端到端行为 |

## 共享文件怎么处理

详细归属、接口变更与迁移流程见[协作规则与共享文件](协作规则与共享文件.md)。首轮最容易冲突的是 controller.py、persistence.py、migrations.py、server.py、App.tsx、api.ts 和 Task/事件契约。各人独立开发域模块，提交“接线需求＋小补丁”，由归属角色串行整合。

新增表使用已有域 schema 自动发现机制。新增路由使用装饰器注册表，但模块导入仍需要集成人登记；不能把 load_registered() 的空实现当成已自动加载新路由。新增表不等于 CRUD 可以随意塞进共享 persistence.py。
