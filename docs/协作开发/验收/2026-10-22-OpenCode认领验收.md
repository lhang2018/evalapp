## OC-09-01 / P1：恢复重置单候选实验预算

位置：`evoagent/evolution/controller.py:145-163`、恢复循环 `284-296`。

每次恢复都重新调用 `_make_candidate_budget`，构造零用量 BudgetController，未读取此前已计入 `candidate:<id>` 的持久账本用量。评测已扣费但异常退出时，候选停在 EVALUATING；下一轮再次恢复并获得完整额度。日/月池记录仍在，但无法替代单候选预算上限。

复现：候选上限 2 次调用 / 成本 0.25；runner 每次检查预算、记录一次调用及 0.1 成本后抛出中断。连续运行四轮，同一候选仍 EVALUATING，持久候选账本累计 **4 次 / 0.4**。

建议：恢复同一候选沿用持久预算用量和耗时；用明确的实验 attempt 区分重新评测，并让 attempt 累计受候选总预算约束。补扣费后崩溃、重启和多次恢复测试。此问题是新增恢复策略与原预算机制之间的不匹配，不把原预算构造器的全部实现归于本批提交。

## OC-09-02 / P2：正常在途评测被误判为崩溃残留

位置：`evoagent/evolution/controller.py:279-296`。

恢复仅凭 TESTING/EVALUATING 状态，未判断是否仍有存活执行者。同一控制器中，一个线程正在真实评测，另一线程运行编排轮时会尝试恢复同一候选。当前评测锁避免了模型调用直接重入，但第二线程等待前一评测完成后，仍按旧快照再次执行，报 `IllegalCandidateTransition: APPROVAL_PENDING -> TESTING`，把正常并发记为评测错误。

建议：锁内重新检查状态，区分本进程活跃评测与重启装载的残留；跨进程恢复另需租约和所有权证明。复现通过 Event 精确同步，不靠 sleep 猜测时序。

## OC-INT-01 / P2：自动提案的基线与发布契约未对齐

位置：`evoagent/evolution/controller.py:192-198`、`227` 与 `739-743`。

`_baseline_version` 返回发布清单的 `version`，例如 `stable-v1`，自动提案将它同时写进 baseline_version / rollback_version；当前发布入口要求二者等于精确 current_release_id，例如 `rel_...`。因此自动提案可完成评测、获得批准，但最终发布一律被“稳定基线或回滚目标不一致”拒绝。直接手工传 release_id 的既有测试没有覆盖此链路。

建议：提案时固定精确 release_id，版本展示字段独立保存；完整覆盖信号 → 提案 → 评测 → 批准 → 发布。**这是原信号提案与 codex-runtime 后续收紧的发布契约之间的共享接线缺口，不能全归责 opencode。**

## OC-09-03 / P2：轮审计写失败后静默返回正常结果

位置：`evoagent/evolution/controller.py:346-365`。

`_audit_round` 吞掉所有写入异常，返回报告没有任何持久化失败标记。真实 SQLite trigger 仅拒绝 evolution_round 行时，编排结果 errors 仍为空、审计记录为零。即使允许运行继续，也不能把缺失恢复/审计证据报告成正常。

建议：返回明确 audit_persisted / audit_error，保留 round_id 与可重试写入；由调用方按持久化要求阻止后续自动推进。已有不可变回归快照与轮审计是不同证据，前者不能证明后者落库成功。

## OC-09-04 / P2：错误/预算出口重复登记同一编排轮

位置：`evoagent/evolution/controller.py:323-339`。

新就绪候选评测抛错时，except 中先 `_audit_round`，break 后又执行循环外 `_audit_round`，各自生成新 UUID。一轮产生两条完全相同的结果，无法由 round_id 识别为重写；预算中途耗尽的 break 分支也有相同结构。

复现：一个新就绪候选的 evaluator 抛错，一次 `run_evolution_round` 落 **2 条**审计。

建议：一轮分配稳定 round_id，只在统一收尾位置提交最终结果，或使用同 ID 幂等更新。异常信息与审计重试应保持可追踪。
