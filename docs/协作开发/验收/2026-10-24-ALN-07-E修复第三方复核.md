## 一、结论先说：6 个发现都是真的，是我原实现的缺陷

审核报告指出的 6 项（PR07E-01/02/03/04 为 P1，PR07E-05/06 为 P2）**我逐条复现成功，
无一冤枉**。它们不是「测试写法之争」，而是我写这个模块时的真实疏忽：

| 编号 | 缺陷实质 | 我原实现的错在哪 |
|---|---|---|
| PR07E-01 | 跨任务混淆 | `EffectRecord` 投影**丢掉了 `task_id`**，`task_id` 参数只当标签用。于是 task-B 的 confirmed 记录可以满足 task-A 的声明 |
| PR07E-02 | 重复抵扣 | 我完全没检查 `effect_id` 唯一性，同一 effect_id 传两次就能抵扣两条声明、报出「一致」 |
| PR07E-03 | 假确定性 | 多声明时我用 `pool.pop(0)` 按 `step_id` 排序取，**这是字典序硬配对，与真实关联无关**；更糟的是 pending 步骤能抢走 done 步骤的记录 |
| PR07E-04 | 结论可伪造 | `from_dict` 直接信任传入的 `ok`；报告用可变 `list`，调用方 `clear()` 就能让明细与结论脱节 |
| PR07E-05 | 放行空输入 | `plan=None` 时 `getattr(None,"steps",None)` → 空声明，配合空记录得到 **ok=True** |
| PR07E-06 | 语义混淆 | 把 `failed`（明确未执行）与 `planned/submitted/unknown` 一起塞进 `uncertain`，丢掉了「已定论」这个关键差别 |

其中 PR07E-03 最伤：我把「因为排序稳定所以结果确定」误当成了「归因正确」。
**确定性不等于正确性**——排序稳定只能保证每次算得一样，不能证明配对了。
这是我这套「纯读 + 确定性」设计里最该被指出的一处想当然。

## 六、契约变化（使用方需知）

复核确认以下语义变化是**有意为之且合理**，但属破坏性变更，下游需注意：

1. `EffectRecord` 新增**必需**的 `task_id` 投影——缺该字段的旧投影会被拒绝。
   旧持久报告缺任务来源时，必须从实际账本重新生成，不再被认作已验证。
2. `ReconciliationReport.ok` 改为**派生字段**（`init=False`），并做 9 项一致性
   校验；`from_dict` 忽略不符明细的布尔 ok 并重算，坏明细直接拒绝。
3. 报告明细改为冻结序列（`_SnapshotList`），`to_dict()` 仍返回新的 JSON 结构。
4. 新增 `ambiguous`（多声明无绑定的已确认记录）与 `resolved`
   （`failed`/`compensated` 已定论）两类及对应汇总字段。
5. `ok` 现在额外要求 `ambiguous` 为空；`resolved` **不影响** `ok`
   （它是「已定论」，不是偏差）。
6. `reconcile(..., step_bindings={effect_id: step_id})`：关联由可信宿主提供，
   模块不证明该关联真实性、也不把它当动作授权凭据。

## 七、仍保留的边界（复核确认未越界）

- 只比较工具字面与记录身份，**不验证参数、版本、文件或效果语义等价**；
- `tool_hint` ≠ 注册表 `side_effect_level`，本卡不自造工具/权限权威；
- 默认范围为单一 task（可跨 run），不宣称同 task 不同计划/运行间已自动绑定；
- `ok` 仅表示「当前声明与记录没有已观察到的偏差」，**不是整个 Task 完成标志**；
  `pending_declarations` 可仍存在；
- `unexecuted` 只表示「done 声明没有已确认且可归因的效果」，**不证明外部一定没发生**；
- 不读/写账本以外的执行权威、不裁决 unknown、不释放 pending、不补偿；
- 未接运行时，运行时如何消费结论仍另验；ALN-07 整包不关闭。

## 八、非阻断观察项

1. `uncertain` 与 `resolved` 的边界依赖账本 `status` 字面值
   （`failed`/`compensated`）。若未来账本新增终态（如 `abandoned`），
   需同步扩展 `RESOLVED_STATUSES`，否则会退回到 `uncertain`。建议在
   `side_effects.py` 增删状态时做交叉检查。
2. `step_bindings` 的键是 `effect_id`——调用方必须先从账本拿到 effect_id
   才能绑定。这意味着宿主需要在**规划阶段之后、对账之前**保存这份关联；
   若宿主丢失绑定，多声明场景会如实判 `ambiguous`（这是正确行为，但会降低
   `ok` 覆盖率，运营侧需预期）。
3. 复核未覆盖 `compensated` 状态的实际路径（仅用 `failed` 验证 V9），
   原因是我没有构造出产生 `compensated` 的最小夹具；`compensated` 的分类
   由修复后的状态一致性校验与被审方测试覆盖，本报告如实声明未独立验证。
