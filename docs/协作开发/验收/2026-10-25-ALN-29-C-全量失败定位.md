## 三、真实缺陷：schema 幂等约定被违反

### 现象

```
AssertionError: False is not true : 非幂等语句：CREATE UNIQUE INDEX IF NOT EXISTS idx_feedback_agg ON user_f
tests\test_collab_base.py:30
```

### 隔离复现（最小组合）

```
$ python -m pytest tests/test_feedback.py tests/test_collab_base.py -q
1 failed, 37 passed
```

单独跑 `tests/test_collab_base.py` 也失败；单独跑 `tests/test_feedback.py` 不失败——
**只要 29-C 的 schema 被加载，该断言必失败**，与运行顺序无关。

### 根因

`evoagent/core/schema/feedback.py`（ALN-29-C 新增）的第三条语句：

```python
"CREATE UNIQUE INDEX IF NOT EXISTS "
"idx_feedback_agg ON user_feedback(agg_key)",
```

而 `tests/test_collab_base.py::TestSchemaDomainSplit::test_every_statement_is_idempotent`
约定：**所有 schema 语句必须是 `CREATE TABLE IF NOT EXISTS` 或 `CREATE INDEX IF NOT EXISTS`
开头**（每次连接都重放全部语句，因此前缀统一是幂等性的前提）。

该文件的 docstring 也自述"stmt 幂等：每次连接重放"，但实现用了第三个前缀
`CREATE UNIQUE INDEX`，破坏了统一约定与既有机器检查。

### 两种修法（供作者选择）

**方案 A：改用普通索引，保留唯一性由应用层保证**
把 `CREATE UNIQUE INDEX` 改为 `CREATE INDEX`（与同文件另两条 `idx_feedback_task` 一致），
在 `evoagent/observability/feedback.py` 的聚合写入处用应用层去重保证 `agg_key` 唯一。
优点：不改既有断言。代价：唯一性从数据库约束降为应用约定。

**方案 B：放宽机器检查，允许 UNIQUE 索引**
把 `tests/test_collab_base.py` 的断言从"两种前缀"放宽为
"`CREATE TABLE IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS` / `CREATE UNIQUE INDEX IF NOT EXISTS`"。
优点：保留数据库层唯一性。代价：放宽的是**全项目**的 schema 约定，
影响面大于单卡修复。

**倾向**：方案 B 更符合原设计意图——`agg_key` 的唯一性本来就该由数据库保证
（重复反馈合并计数是 29-C 的核心语义，应用层去重会引入竞态）。
但方案 B 改的是共享测试文件，需在卡内说明放宽理由与影响范围。

### 影响面

当前为**测试门禁失败**，不影响运行时行为（该语句本身在 SQLite 中是幂等的）。
但它会让**任何基于干净提交的验收为红**，包括 ALN-29-C 自身的复核。
