# ALN-04-R：RUNNING 进程中断后的安全接管

建议角色：runtime。整合依赖 ALN-00-B；此前可准备接口/故障夹具。原 ALN-01/02 的网关、账本和本卡共享接口仍需一并审阅，本卡不绕过它们的剩余要求。

## 目标

已经实现独立 Run、问答/审批原动作恢复和暂停状态跨 App 重启，不需要重做。补齐当前没有的运行所有权、失联判断和中断接管；让 RUNNING 中被杀的进程可按证据恢复，且不会自动重复外部动作。

## 写入边界

可独占拟新增的 core/leases.py 或同职责模块、域 schema 和 tests/test_run_ownership.py、tests/test_process_recovery.py。名称为建议，现阶段并不存在这些新文件。

运行线维护 runs.py、controller.py、Task/状态机及引擎边界；persistence.py、migrations.py、API 装配/鉴权与 CLI 的修改单列，由 integration 排号合入。不能另写一套 Task 权威、工具网关或私有 approvals/effects 表来绕开现有约束。

## 第一份交付：接口及故障矩阵

先定义 worker/session 身份、租约/失联判据、epoch/fencing 代次、领取/续租/释放/接管的比较条件，以及旧运行与父子运行的关系。区分“租约过期”“进程已停止”“外部操作未发生”三件事；旧进程复活不能继续领取新动作。

列出真实故障点：模型调用中；批准已消费到网关记账之间；planned/submitted 后；外部成功但回执未写；账本已 confirmed 但检查点未写；检查点完成但 Run 尚未结束。决定恢复入口的角色和自动/人工边界，再提交 schema/契约提案。

## 实施顺序

1. 用独立进程和共享 SQLite 建可控故障夹具，验证现有 claim_run 只是执行领取，不是持久租约。
2. 实现原子所有权及心跳/代次校验；旧 owner 失效后阻止其新动作。进程已发出的外部调用仍按账本与供应商回执处理。
3. 接管事务关闭旧运行并建立子运行，恢复预算、清单、待答问题、待审批原动作和已完成节点；版本不兼容明确拒绝。
4. 接到受控恢复入口；遇 submitted/unknown 保守等待对账，不能靠 force、换键或新建 Task 绕过。
5. 回归现有问答、审批、取消、并发上限和历史 Run；所有权与状态迁移故障要留下可追溯事件。

## 验收

- 两个独立进程竞争同任务只有一个有效 owner；接管后旧 owner 的续租/提交失败。
- 真实杀进程再启动，从持久记录恢复；不能仅在测试中改成 SUSPENDED 来代替。
- 外部动作计数不因接管增加；未知结果没有伪造成功或无限自动重试。
- 父子 Run、旧 Run 结束原因、预算和检查点完整；等待答案/审批不丢失；批准后的原动作不重新询问模型。
- 迁移兼容、时钟/心跳失败和磁盘失败有明确行为；不承诺租约能取消已发出的网络请求。

## 交付

接口提案、故障矩阵、原子仓储实现、真实进程故障测试、共享接线补丁、执行命令及日志，使用统一交付模板。通过后仍需 ALN-04 的节点取消/指定检查点/真机组合验收证据才能整包关闭。

可复制给接手者：

> 认领 ALN-04-R。先读本卡、运行/审批交付记录和共享文件规则，在已发布基线上补持久 owner/lease/fencing 及 RUNNING 中断恢复。先交接口与故障矩阵，再做原子事务和真实多进程测试。保留现有网关、审批、预算和副作用账本，unknown 不自动重放。共享 schema/API/装配补丁交 integration；不要把暂停状态重建 App 的测试当作强杀验收。
