# 环境异常与规避（2026-10-25）

本文记录**开发环境自身**的异常——不是业务缺陷，也不是产品需求。它们的共同特点是：
**会让验收结论失真**（跑出来的数字不可信）或**让操作被环境拦住**（以为是自己写错了）。

全部条目在本机实测复现过，每条给出**取证命令**与**规避做法**。取证来源有二：
①命令实跑输出；②WorkBuddy 审计日志 `~/.workbuddy/audit-log/`（该目录记录环境的
命令安全与文件安全决策，含 `category` / `eventType` / `decision` / `messageParams`）。

---

## 一、批量删除守卫误伤 pytest（本日实发，影响验收结论）

### 现象

后台跑全量测试时进程被环境中止，日志无 pytest 报错、也无通过输出，只剩退出码异常。
一度被误判为"测试本身有问题"，实为**环境守卫命中 pytest 自己的临时目录清理**。

### 机制（已取证，非推测）

审计日志 `~/.workbuddy/audit-log/2026-10-25.jsonl` 中本日唯一一条：

```json
{
  "category": "file-safety",
  "eventType": "file-safety.bulk-delete.approved",
  "decision": "approved",
  "messageParams": {
    "count": 1867,
    "threshold": 50,
    "targets": "\\\\?\\C:\\Users\\lhang\\AppData\\Local\\Temp\\workbuddy-update-x64\\pytest-of-lhang\\garbage-803e8d06-..."
  }
}
```

即：pytest 每次运行会在 `pytest-of-lhang/` 下创建 `pytest-<N>/` 临时目录，**并在
下一轮运行前把上一轮的陈旧目录改名为 `garbage-<uuid>/` 再删除**。一次全量留下的
临时文件数量（1867）远超守卫阈值（50），于是 pytest 被当成"批量删除操作"拦下。

### 证据范围

`file-safety.bulk-delete.approved` 事件在 `~/.workbuddy/audit-log/` 全部日期共 **34 条**
（10-14 起至 10-25），**每一条的 targets 都是 pytest 的 `garbage-<uuid>` 目录**，
count 分布 80~1867，全部超过 threshold=50。**这不是偶发，是 pytest 的稳定行为**。

取证命令：

```bash
grep -h "bulk-delete" ~/.workbuddy/audit-log/2026-10-25.jsonl | head -1
```

### 规避

1. **后台跑全量时把输出重定向到文件**，不要用管道接 `tail`：

   ```bash
   pytest tests/ -q > run.log 2>&1; echo "exit=$?"; tail -6 run.log
   ```

   本日 14:58 那次即用此写法通过（审计事件 `decision: approved`）。
2. **删除量随测试规模增长**——全量（1700+ 用例）比单文件更容易触发；
   跑单文件时通常不触发。
3. 守卫命中的是 **pytest 临时目录**，不涉及仓库内容；即便被拦，仓库与工作区不受损。
4. 判定"是不是我的代码问题"时，**先查审计日志的 `file-safety` 事件**，再下结论。
   参见 `docs/协作开发/验收/` 下各复核报告的"环境因素"章节写法。

## 二、`pytest` 不带路径参数会炸出上万 errors（主工作区专属）

### 现象

在**主工作区**执行 `pytest`（不带 `tests/` 参数）：

```
!!!! Interrupted: 5471 errors during collection !!!!
1817 tests collected, 5471 errors in 12.15s
```

### 机制

主工作区 `outputs/` 下有 **62 份历史复核用的仓库副本**（`aln05-05a7cf4/`、
`aln07e-review-26aaec7/` 等），每份都含完整的 `tests/` 目录（合计 **5471** 个测试文件）。
pytest 默认从 rootdir 递归收集，于是把这些副本里的测试**重复收集**并因模块重名而报错。

`outputs/` 已在 `.gitignore` 第 6 行，**所以干净 checkout 里没有这个问题**——
但主工作区一直在，且目录只会越积越多。

取证命令：

```bash
ls -1 outputs/ | wc -l                    # 62
find outputs/ -name "test_*.py" | wc -l   # 5471
pytest --collect-only -q | tail -3        # 复现 5471 errors
```

### 规避

1. **永远显式带路径**：`pytest tests/ -q`。带路径时收集 1752 项、无 error。
2. **全量验收必须在干净 worktree 跑**（`git worktree add <dir> <commit> --detach`），
   干净 worktree 里 `outputs/` 为空，无参数收集也正常（实测 1767 项、0 error）。
3. `outputs/` 下的历史副本是复核证据，**清理前先确认无人在用**；本条不授权删除。

## 三、只有系统 Python 3.10.11 装了 pytest

### 实测

```
C:/Users/lhang/AppData/Local/Programs/Python/Python310/python.exe  → 3.10.11, pytest 8.4.2 ✅
~/.workbuddy/binaries/python/versions/3.13.12/python                → 3.13.14, 无 pytest ❌
python3 -c "import os; print(os.path.isdir('/tmp'))"                → False
```

### 规避

- **固定用绝对路径**调解释器：
  `C:/Users/lhang/AppData/Local/Programs/Python/Python310/python.exe -m pytest ...`
- `python3` 指向的是 Windows 原生解释器，**认不到 `/tmp`**；临时文件请用
  `.planning/` 下的相对路径，或 `E:/tmp-*` 形式的 Windows 绝对路径。
- 记忆条目里"managed 3.13.12 无 pytest"属实；但**版本号已从 3.13.12 升到 3.13.14**，
  路径未变。

## 五、瞬时收集错误（观察到一次，未能复现——按协议不作数）

15:09 前后在主工作区执行 `pytest tests/ --collect-only -q`，出现过一次：

```
Interrupted: 71 errors during collection
714 tests collected, 71 errors in 5.62s
```

**紧接着的复跑全部正常**：单跑三次 → `1770 collected`；后台全量仍在跑时连续 8 次 →
`1772 collected`、0 error；并发跑单文件时收集亦正常。**错误内容未能取到**（输出已被
覆盖），未能复现，故按本项目"偶发失败不作数"的协议**不作为确定结论**。

可能相关因素（均未证实）：同一时刻有后台全量在写 `tests/__pycache__/*.pyc`。

**给下次的处置**：
- 收集阶段报错时，**先原样重跑一次**再下结论，不要立刻改代码；
- 重跑仍报错再取完整错误输出（`| grep -A6 ERROR`），并用干净 worktree 隔离验证；
- 若错误只在主工作区出现、干净 worktree 不出现 → 按"主工作区状态污染"处理，
  不动业务代码。

## 六、并行工作流的"结果失真"类异常（非环境 bug，但同属"别把数字当证据"）

| 异常 | 表现 | 规避 |
|---|---|---|
| 主工作区跑全量 | 数字含未提交改动与他人在途改动 | 用干净 worktree 固定 commit |
| 认领表 stale | 在主工作区 `--render` 读的是旧版 `.planning` 基线，与固定源码有偏差 | 在隔离 worktree 内渲染再回填 |
| 台账引用未入库文件 | 干净 checkout 上校验器报 43 条 `missing task card` | 新增卡片必须同时入库卡文件 |
| `json.dump(indent=2)` 重写整份 workboard | 产生数千行格式噪音，掩盖真实差异 | 精确文本替换 + `hash-object`/`update-index` 外科手术式暂存 |

## 七、复核清单（下次再遇先跑这三条）

```bash
# 1. 是环境拦的还是代码错的？——查守卫事件
grep -h "bulk-delete\|blocked\|Dangerous" ~/.workbuddy/audit-log/$(date +%Y-%m-%d).jsonl | head -3

# 2. 收集阶段是否干净？——必须显式带 tests/
pytest tests/ --collect-only -q | tail -2

# 3. 数字来自固定源码吗？——隔离 worktree
git worktree add /e/tmp-verify <commit> --detach && cd /e/tmp-verify && pytest tests/ -q
```

**判别力要求**：任何"环境导致"的结论，都要有一条可复现命令 + 一条日志/输出佐证，
不能只写"被环境误伤"。
