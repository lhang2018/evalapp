# README 新增设计梳理与实施映射（2026-10-25）

本轮范围：根 README 新增的 chat/ 设计来源，以及随后新增的产品路线总纲。核对基于提交 8be14cf；这是设计与实现差距梳理，不是功能验收、任务认领或基线发布。

## 1. 新内容改变了什么

目标从继续堆叠治理专项，转向“用户能把工作交给系统，并拿到可验证、可继续修改的成果”。技术治理仍然是实现这些用户能力的基础。

- **用户的三种使用方式**：聊天问答、工作交付、主动帮助。直接问答应轻量；复杂任务应有计划、过程和成果；主动帮助应理解近期工作并提出有理由的建议。
- **运行时三条工作轨道**：核心执行优先；主动分析有独立预算和停止机制；后台进化隔离试验、经评测后发布。使用方式与运行轨道是两种划分，不能混为一谈。
- **八个产品模块**：统一任务入口、聊天/工作模式、任务工作区、成果管理、项目与持续工作、主动帮助、能力与信任中心、进化体验。EA-PRODUCT-007 列出 28 个 UX 编号；EA-UX-008 给出 17 条用例。
- **验收从“服务存在”转为“真实用户任务闭环”**：每项功能需要输入、行为、可观察产物、失败恢复、可重复用例及开放条件。

重点原文：[产品功能规格（qa156）](../chat/extracted/156_qa.md)、[四条首发主线与验收用例（qa157）](../chat/extracted/157_qa.md)、[首发范围与发布门禁 EA-REL-005（qa154）](../chat/extracted/154_qa.md)、[主动思考与主动建议 v1.1（qa166）](../chat/extracted/166_qa.md)。

“不打扰”不等于禁止主动建议。整理对话、补充资料、发现工作机会是设计目标；核心执行的质量、效率和授权边界必须保持。提出建议与执行外部操作应分别判断授权。

## 3. 与当前工程的差距

已有后端任务、执行、记忆、机会评估、能力资产与诊断基础，不宜另起一套任务权威。以下是本轮源码核对与设计对照，未通过新一轮端到端验收。

| 用户需求 / 新增约束 | 已有基础 | 仍需落实 | 关联正式工作包 |
|---|---|---|---|
| 统一入口，聊天与工作模式 | Android 任务入口；Task 已有目标、约束、验收条件和计划引用；服务端意图分类器 | 主入口只用简单规则给 general 等意图；非空 hint 会直接被分类器采纳，需核验完整主链并统一契约、澄清和模式切换 | 01 / 07 / 12 |
| 任务工作区，变更与恢复 | 任务权威、执行计划、暂停/取消/恢复接口 | 把计划、节点态、变更影响和可执行恢复操作接到用户页面；不可用模型描述伪造进度 | 04 / 07 / 12 |
| 成果交付与局部修改 | Task.result、result_evidence，已有资产链 | 可预览/下载的真实产物、版本、验收与限制；修改只重做受影响部分 | 05 / 06 / 10 |
| 项目、记忆与持续工作 | 记忆存储、上下文组装、目标治理 | 用户可管理项目上下文、近期工作和持续目标；可见来源、纠错、隔离与过期 | 05 / 12 / 13 |
| 主动帮助 | OpportunityService、GoalGovernor、预算控制 | 将近期工作输入、触发、建议展示和关闭语义接成闭环；验证资源不足时让出主链，不等同于有预算计数就已隔离 | 13 / 14 / 15 |
| 能力与信任中心、首次使用 | 工具/专家注册、权限和更新页面 | 能力可用性、依赖、实验状态与开放条件如实展示；渐进授权和撤销可走通 | 01 / 03 / 06 / 12 |
| 用户可理解的进化体验 | 诊断、候选、评测和发布门禁 | 说明真实变化、证据、收益和回滚，不把候选成功说成用户收益已验证 | 09 / 10 / 11 / 16 |
| 动态团队、迁移与能力缺口规划 | ExpertRegistry、依赖闭包、DAG、记忆与资产 | 跨专家输入输出契约、冲突处理、适用域和迁移有效性；从失败证据到能力缺口候选的真实链路 | 05 / 06 / 07 / 14 / 18 |
| 兼容、影响图、回归选择与因果收益 | 兼容/迁移、候选回归、追踪等已有实现 | 按模型/工具/环境组合验证真实消费路径；覆盖选择与发布后指标形成证据链；生产数据集和非干扰测量不能用 Mock 测试替代 | 03 / 06 / 08 / 09 / 10 / 11 / 16 / 20 / 22 |

源码入口：[Android 页面和提交](../android-app/App.tsx)、[意图分类](../evoagent/planning/intent.py)、[运行控制器](../evoagent/core/controller.py)、[机会评估](../evoagent/goals/opportunities.py)。

因此新增内容既有用户产品缺口，也有运行时接线、资源隔离和真实场景评测缺口；不能全部归为“界面待补”或“只差取证”。

## 4. 首发四条主线与发布条件

| 主线 | 验收用例 | 最小可交付结果 |
|---|---|---|
| F01 问答与连续对话 | F01-01/02 | 普通问答轻量完成，追问正确继承上下文 |
| F02 多步任务与实际成果 | F02-01/02/03 | 从目标、计划到真实产物与验收状态，产物可使用 |
| F03 目标变更、失败、取消与恢复 | F03-01…05 | 用户知道发生了什么、影响什么、可以怎样继续，取消后不盲目重放 |
| F04 近期工作整理与机会发现 | F04-01…04 | 主动建议有依据、有收益、可关闭；不抢占核心任务资源 |
| 跨主线约束 | GLOBAL-01…03 | 共享质量、真实性和控制要求按原用例执行 |

合计 14 条主线用例 + 3 条全局用例 = 17。此处是需求清单，尚未声明测试通过。

EA-REL-005 正文已经在 qa154，不能再标成“未捕获，需重建”。原文称“七道”但实际列出 **G0—G7 八道**，实施时按八项逐项记录：

G0 构建与安装；G1 核心任务质量；G2 安全与权限；G3 稳定性与恢复；G4 效率与成本；G5 后台非干扰；G6 版本/发布/回滚；G7 产品可用性与运维准备。

当前证据应区分版本：台账 prepared_candidate 为 532a364，status=candidate，published_commit=null；f550d90 是其历史验证来源。后续通知修复 271378e 有客户端 252 项、类型检查与构建证据，但本轮未重新跑业务测试，最新通知 APK 的安装/真机投递也未在该证据中验证。上述证据不足以宣布新产品八道门禁全通过。

## 5. 实施顺序与认领边界

已有 [产品目标形态与实施路线](产品目标形态与实施路线_2026-10-25.md) 提出 ALN-23—29 与首轮卡片。它们目前是**拆分提案**；正式 workboard 仍是 ALN-00—22。建议负责人不等于已经认领，本文不修改认领、验收或发布状态。

1. **先统一需求来源与验收表**：按 exchange/final 规范化提取，保留消息版本和原编号；把 28 UX、17 用例、八道门禁列出“未测/通过/失败/证据版本”，消除文档口径冲突。
2. **P0 打通一个真实任务纵切片**：沿用 Task 权威，完成统一输入契约 → 聊天/工作分流 → 计划与进度 → 真实成果 → 验收状态。优先覆盖 F01/F02，而非先铺满八个模块空页面。
3. **P0 补变更与恢复路径**：完成 F03，验证副作用、取消与恢复在后端和客户端语义一致；同步验证 17 用例中的全局约束。
4. **P1 接入有限范围主动帮助**：复用已有机会/目标服务，先做近期工作整理与建议，再做授权后的动作；配套独立预算、停止、资源让出及 F04 非干扰实测。
5. **按真实任务暴露的问题补技术域**：兼容矩阵、能力缺口、跨专家协作、知识迁移、因果评测与发布后收益；每项挂原专项和现有包，必要时按提案正式建卡，不能因有近似服务就关缺口。

基线发布继续走 ALN-00-B 的复核与发布决定；它约束正式发布，不应无差别阻塞来源梳理、接口设计和可独立验证的开发。漫剧、多端等后续场景按原依赖推进。
