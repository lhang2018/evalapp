## 二、做成什么样：目标形态

### 2.1 产品定位与四支柱【原文，1.0 PRD §1 + 语料产品总梳理】

> **一个以目标完成为核心、以工作流为可复用执行资产、以可验证的持续改进为后台能力的个人通用智能体系统。**

1.0 PRD 给出的是终端形态约束（"Android 手机优先、本地优先的个人通用智能体系统"）；语料总梳理给出的是价值主张。二者合成同一件事，**不冲突**。

**四支柱**：① 完成任务 ② 积累可复用能力 ③ 发现并解决问题 ④ 可靠地持续改进。
**五层架构**：L1 交互与产品入口 → L2 执行内核 → L3 能力与工作流平台 → L4 可靠性与评测平台 → L5 独立进化与发布平台（分层理由是变化速度与稳定性要求不同）。

### 2.2 产品功能全景：八个模块、28 个 UX 功能【原文，EA-PRODUCT-007】

EA-PRODUCT-007 规定的产品核心体验是：

> **用户提出目标 → 系统理解并执行 → 用户查看真实进展 → 系统验证结果 → 交付成果 → 在合适的时候提供额外帮助。**

并规定每项用户功能必须明确六件事：用户为什么需要、在哪怎么用、系统实际执行什么、用户最终得到什么、出错如何处理、如何验证真正有效。

| 模块 | UX 编号 | 对应功能 | 客户端现状 |
|---|---|---|---|
| 一、统一任务入口 | UX-01~03 | 自然语言输入 / 语音入口 / 自动分类与路由 | 🟡 基础在（任务页有文字语音提交、澄清补全），缺统一契约与路由纠正 |
| 二、聊天与工作模式 | UX-04~06 | 聊天模式 / 工作模式 / 模式自动转换 | ❌ 缺（提交即执行） |
| 三、任务工作区 | UX-07~10 | 任务计划 / 状态与进度 / 任务控制 / 异常恢复 | ❌ 缺（只有任务列表） |
| 四、结果与成果管理 | UX-11~13 | 结果验收 / 成果交付 / 成果继续编辑 | ❌ 缺（产物散在任务详情） |
| 五、项目、记忆与连续工作 | UX-14~17 | 任务历史 / 项目空间 / 跨会话延续 / 记忆管理 | 🟡 部分（有记忆页与纠正删除，缺项目层） |
| 六、主动帮助 | UX-18~21 | 当前任务增益 / 近期工作整理 / 机会发现 / 主动程度控制 | ❌ 缺 |
| 七、能力与信任中心 | UX-22~25 | 能力状态展示 / 权限审批 / 隐私数据 / 成本资源 | 🟡 部分（有权限页，缺能力目录与渐进授权） |
| 八、持续进化的用户体验 | UX-26~28 | 问题反馈 / 改进效果说明 / 稳定版本与更新控制 | ❌ 缺 |

**EA-PRODUCT-007 规定的三张关键枚举**（都是可直接落代码的规格）：

- 能力状态六档：可用 / 需要授权 / 依赖外部服务 / 实验中 / 暂不可用 / 未开放
- 主动程度四档：关闭 / 低 / 标准 / 高（**"这些级别是产品策略，不是对自主执行权限的自动授权"**）
- 产品层级与开放依据六层：基础任务 → 连续工作 → 领域能力 → 主动帮助 → 持续进化 → 长期自主

### 2.3 四类用户流程与 17 条端到端验收用例【原文，EA-UX-008】

EA-UX-008 把 28 个功能收敛为四类流程：

| 流程 | 范围 | 验收条件（原文要点） |
|---|---|---|
| **F01 快速问答与连续对话** | 简单问答直接回答，不强制建任务；上下文相关但不无限继承；复杂问题可自然升级 | 不无故启动复杂工作流 / 正确继承上下文 / 纠正后不再用错信息 / 不靠模型自述作外部证据 |
| **F02 多步骤任务执行** | 理解与任务契约 → 规划与准入 → 执行与进度 → 独立验收 → 交付 | 计划执行验收共用同一目标约束 / 工具失败不无限重试 / 预算耗尽停新调用 / 真实产物通过验收才标成功 / 失败时已产成果不丢 |
| **F03 改目标、失败与恢复** | 六类变更（补充/调优先级/改交付格式/改核心目标/扩权限/取消）+ 七步失败决策 + 中断恢复核对 | 不抹除已发生事实 / 只重做受影响步骤 / 变更后重新验收 / 授权不随任务扩张 / 取消后不盲目重放 / 重启后能恢复真实状态或明确说无法确认 |
| **F04 主动整理近期工作与机会发现** | 五步分析（确认范围→建证据集合→整理状态→发现机会→筛选交付）+ 七条资源隔离 | 事实可追溯到授权来源 / 区分事实与推断 / 低价值建议被过滤 / 主动失败不影响核心任务 / 关闭后核心与安全提示仍正常 / 建议不会自动变成未授权动作 |

**17 条端到端验收用例编号**（可直接转成测试用例 ID）：
`UX-F01-01/02`、`UX-F02-01/02/03`、`UX-F03-01/02/03/04/05`、`UX-F04-01/02/03/04`、`UX-GLOBAL-01/02/03`。

EA-UX-008 明确要求："每个用例都需要实际运行记录、明确断言和测试结果。**测试未执行时必须标记为未测试**。"

### 2.4 用户可见状态与内部状态的映射【原文】

EA-UX-008 §七给出九态映射，**这是"页面状态必须有真实系统状态作依据"的规范**：

| 用户界面 | 内部状态/条件 | 允许的下一步 |
|---|---|---|
| 正在理解 | 任务解析与分类中 | 继续处理或请求澄清 |
| 需要补充信息 | `needs_user` 或澄清等待 | 用户补充、取消 |
| 正在执行 | `running` | 查看进度、补充约束、取消 |
| 等待授权 | `waiting_approval` | 批准、拒绝、取消 |
| 正在恢复 | `recovering` | 查看恢复进度、取消可取消步骤 |
| 正在验收 | `verifying` | 等待验收或处理验收失败 |
| 已完成 | `succeeded` 且验收证据满足 | 查看成果、继续讨论 |
| 部分完成 | 有有效成果但部分目标未满足 | 查看缺口、继续或结束 |
| 未完成 | `failed` / `cancelled` / 其他终止条件 | 查看原因、重新运行或结束 |

两条硬规则：**"页面状态必须来自任务记录和事件，不得仅依据模型返回的自然语言推断"**；实现时还应区分等待网络 / 等待外部服务 / 等待用户决策，不得把等待统一显示成"执行中"。

### 2.5 主动帮助的边界【原文，四处来源一致】

- **语料 10-24 14:03**（在原始抓取 `chat/原稿归档/2026-10-25/source1/` 内，不在 `chat/extracted/`）：主动智能"应区分**观察、建议、准备和执行**"；"高质量完成明确任务仍是最高优先级"。
- **语料 10-24 14:11**：主动智能"**绝不能影响正在运行的智能体任务、执行质量、响应时延、稳定性或既定资源预算**"；"只能作为有严格隔离、可限流、可暂停、可降级的次级能力运行"；需设资源配额、优先级调度、主任务保护、熔断与降级规则。
- **EA-PRODUCT-007 UX-18~21**：主动帮助是差异化价值但不能干扰核心执行；每条建议必须说明**提出理由、潜在收益和所需操作**；主动帮助用独立预算，资源紧张时优先暂停。
- **EA-UX-008 F04 §6.3**：七条资源隔离规则——核心任务运行期间不得抢占必要资源；资源不足先暂停主动分析；不得修改核心任务状态；用户关闭后不再启动新主动任务；**已生成的建议不等于用户授权执行建议**；外部操作仍需权限/风险/预算检查；主动任务须有完成条件、最大运行范围与无进展停止策略。

**建议的呈现格式**（EA-UX-008 原文）：**发现了什么 → 为什么值得关注 → 可以怎么做 → 需要什么权限或成本**；**"如果没有足够有价值的建议，允许不输出额外建议"**。

### 2.6 产品的开放顺序与统一验收规则【原文 EA-PRODUCT-007 §11、§13】

**开放顺序（原文表）**：

| 产品层级 | 功能范围 | 开放依据 |
|---|---|---|
| 基础任务 | 统一入口、问答、任务执行、状态、验收、交付 | 真实任务链通过验收 |
| 连续工作 | 历史、项目、记忆、暂停恢复、工作流复用 | 状态一致性和回归测试通过 |
| 领域能力 | 编程、旅游、手机操作、AI 漫剧等 | 对应专家具有独立评测和安全边界 |
| 主动帮助 | 任务增益、工作整理、机会发现 | 相关性、用户收益和非干扰测试通过 |
| 持续进化 | 候选改进、独立评测、受控发布、回滚 | 进化与发布闭环通过验证 |
| 长期自主 | 目标跟进、定时任务、跨端协同 | 停止机制、授权、预算与状态恢复通过 |

**统一验收规则（每项用户功能至少要有八条）**：真实使用场景 / 明确的用户输入 / 预期的系统行为 / 可观察的输出 / 失败与恢复规则 / 对应的专项设计 / 可重复执行的验收用例 / 发布前的开放条件。

EA-PRODUCT-007 另有两句定调的话，**直接约束我们的开发方式**：

> "如果某项功能只有界面而没有真实执行能力，应标记为演示或实验功能。如果有真实执行能力但缺少结果验证，应限制开放范围。"
> "实际映射时必须引用原有专项的准确编号和版本。**不能为了填满表格而臆造编号**。"

**【原文】首发范围与门禁**：EA-REL-005 正文已在 [qa154](../chat/extracted/154_qa.md)。其中列出 G0 构建安装、G1 核心质量、G2 安全权限、G3 稳定恢复、G4 效率成本、G5 后台非干扰、G6 版本发布回滚、G7 产品可用性与运维；原文“七道”与实际八项不一致，实施按 G0—G7 逐项取证。六层开放顺序不能替代门禁。

### 2.7 怎么判定"真的在进化"【原文】

不能用"改了多少次代码 / 加了多少条工作流 / 优化了多少次提示词"证明。指标以任务结果为中心，**按任务类型分别统计**：任务成功率、首次成功率、恢复成功率、单任务成本、端到端耗时、工具故障率、工作流复用率、回归缺陷率、自动发布回滚率。

进化的真正含义：**在任务质量不降低、安全边界不放宽的前提下**，同类任务越来越稳定、越来越高效，或同成本下结果更好。

### 2.8 目标形态与 1.0 的一致性核对

**产品层重设计没有推翻 1.0 的任何一条硬边界**：四支柱 ↔ 1.0 §1；五层 ↔ 1.0 §3/§4；三种执行模式 ↔ 1.0 §6；"一次成功只形成候选" ↔ 1.0 §9/§10。EA-PRODUCT-007/EA-UX-008 是把 1.0 的 89 主题**翻译成用户可见形态**，不新增技术内核。

用户可见形态层（八模块 / 28 UX / F01~F04 / 17 用例）是本轮主要增量；技术专项还需核对运行时接线、资源隔离、兼容组合与真实任务评测，不能一概视为已有实现或只差取证。

### 阶段 0：发布收口（正式发布前置）

准备候选为 `532a364`，历史验证来源为 `f550d90`，候选记录 1661/1 + 228 + typecheck 与 Android 证据；`published_commit` 仍为空。完成 00-B 的复核与发布决定后才可发布。后续通知修复的客户端 252 项与构建证据单列，不能并入旧候选；发布等待不无差别阻塞接口设计与独立开发。

**但不把"尚未发布"当成所有开发的屏障**（台账 `execution_note` 原话）——阶段 0 可与阶段 1 的取证并行。

### 阶段 1：真实化取证（把 0/23 推到第一批）

**这一阶段大部分产出是证据文件，不是代码。** 具体动作：真机故障矩阵（断网/杀进程/重启，ALN-12）、审批四路径（04-UI）、能力包健康失败→回滚（11-W）、生产信任材料换装（ALN-03）、真实供应商与真实账单（ALN-08/15）、一次端到端进化收益实验（E-11）。

其中 **E-11 一次真实收益实验**是全项目"自进化"三个字与现状之间最大的距离，值得单独排期：哪怕只做一个小领域（如 time_query 扩展），只要证明候选→门禁→发布→指标改善真实发生。

### 阶段 2：主链接线（说目标 → 真实动作 → 证据回执 → 成果）

打通 ALN-12 自然语言 App 主链；ALN-07 绑定从"记录"升级为"参与放行判定"的准确形态（**绑定≠授权**：绑定只答"哪一步触发"，放行仍由 Action Guard 决定）；ALN-11 制品在主链被真实消费。

这条链同时是 ALN-12 的剩余差距、EA-PRODUCT-007"基础任务"层的开放依据、以及阶段 3 的验收载体——**它是三条线的交点，优先级最高**。

### 阶段 3：产品层交付（八模块补成用户能用的形态）

按 §2.2 逐模块补齐（新包 ALN-23/24/25/29）。约束：**每张卡必须挂在某个 UX 编号上**，否则不立项。

验收口径直接用 EA-UX-008 的 17 条用例：每条要有实际运行记录、明确断言、测试结果；**未执行的必须标记为未测试**。

### 阶段 4：进化收益闭环（把 E-11 从口号变成一次真实证明）

把收益证明做成可重复流水线：基线对照 → 样本量 → 十维收益 → 晋级/回滚；并让 UX-26~28（问题反馈 / 改进效果说明 / 版本控制）对用户可见。

### 阶段 5：能力包与多端

ALN-19（漫剧）、ALN-21（多端）、ALN-20 外部 Runtime PoC、ALN-22 全量收口。
