# EvoAgent 第三十六专项：自进化闭环与改进因果归因

这一轮进入 EvoAgent 的核心中的核心：**系统如何发现自己的问题，选择正确的改进对象，证明改进有效，并在改进失败时安全回退。**

你最初提出的目标，不只是让智能体能够做更多事情，而是让它能够分析自己在执行过程中暴露的问题，持续提升执行质量、效率和稳定性。

前面已经设计了：

- 多专家与动态任务 DAG；
- ReAct、Planner 和工具运行时；
- 记忆、上下文与模型路由；
- RCAE 根因分析；
- EQEAG 独立评测；
- ODERI 运行证据；
- L3RG 故障恢复；
- SBAAG 安全授权；
- MACTDG 多专家协作治理。

现在要把这些能力组合成真正可靠的自进化闭环。

本专项建议定义为：

**Self-Evolution Loop & Causal Improvement Attribution，简称 SELCIA。**

它负责问题发现、改进假设、候选生成、实验设计、因果归因、发布决策、效果监测和回滚。

## 一、第一性原理：系统不能因为自己认为变好了，就认定自己真的变好了

假设 EvoAgent 发现，编程专家最近的任务成功率从 80% 降到了 65%。

它可能提出以下解释：

- 路由选错了专家；
- 上下文压缩丢失了关键约束；
- 模型版本变化导致代码生成质量下降；
- 工具接口发生了变化；
- Planner 的任务分解方式不适合近期任务；
- 最近的任务本身更复杂；
- 测试环境出现了故障。

如果系统直接修改 Planner，随后恰好有一批简单任务执行成功，它可能误以为改进有效。

这会形成一个危险的循环：

发现异常 → 猜测原因 → 修改系统 → 偶然成功 → 宣布进化成功。

真正的自进化必须建立在更严格的流程上：

# 二、首先要解决一个根本问题：究竟什么叫“变好”？

如果 EvoAgent 只追求任务成功率，就可能通过无限重试、调用更贵的模型、增加专家数量或放宽验收标准来提高成功率。

如果只追求速度，又可能跳过必要验证。

如果只追求成本，则可能使用能力不足的模型，导致后续返工更多。

因此，进化系统不能依赖一个孤立的指标。

## 2.1 建立多维质量模型

建议至少同时评估以下维度。

| 维度 | 核心问题 |
|---|---|
| 任务质量 | 最终产物是否满足用户目标与验收标准？ |
| 成功率 | 同类任务中有多少真正完成？ |
| 效率 | 完成任务需要多少时间和交互步骤？ |
| 成本 | 每个合格交付物消耗多少模型、工具和外部服务资源？ |
| 稳定性 | 不同任务、输入变化和故障条件下表现是否稳定？ |
| 恢复能力 | 失败后能否正确恢复，是否丢失成果或重复副作用？ |
| 安全性 | 是否遵守权限、隐私和副作用边界？ |
| 可维护性 | 生成的代码、工作流和配置是否容易理解、测试与继续修改？ |

不同任务需要不同的权重。

例如，编程任务可能重视正确性、测试通过率和可维护性；视频生成任务可能重视画面质量、角色一致性、时长与成本；普通聊天任务则可能更重视相关性、准确性和用户体验。

**全局系统可以共享评测框架，但不能强迫所有专家使用完全相同的质量目标。**

## 2.2 区分硬约束和优化目标

建议将指标分成两类。

**硬约束：** 不允许为了其他指标的提升而突破，例如安全授权、关键正确性门槛、预算上限和必须满足的交付要求。

**优化目标：** 在硬约束满足的前提下继续改善，例如成本、耗时、返工率和额外质量收益。

因此，某候选版本即使速度提高 30%，如果未授权操作风险增加，也不能被视为有效进化。

对于无法简单转换成同一单位的指标，不要直接把它们粗暴相加。应当使用明确的优先级、约束门槛和多目标比较机制。

# 三、问题发现：不要把所有失败都当成进化机会

EvoAgent 每天可能产生大量失败、重试、超时和用户修改请求。如果每出现一次失败就启动自进化，系统会消耗大量资源，还可能不断修改原本正常的模块。

因此，需要建立问题分级与进化触发机制。

## 3.1 将问题分为五类

  {#each [
    ["A · 偶发执行故障","例如短暂网络中断、一次工具超时。优先使用恢复机制，不必立即修改能力。"],
    ["B · 重复性缺陷","同类任务持续出现相同错误，说明可能存在系统性问题，适合进入根因分析。"],
    ["C · 质量退化","成功率、用户满意度或交付质量在一定时间内持续下降，需要检查基线与环境变化。"],
    ["D · 效率或成本问题","任务虽然成功，但重试、调用、等待或返工明显增加。"],
    ["E · 架构与能力缺口","现有专家、工具、工作流或上下文策略无法满足一类新任务，需要设计新的能力。"]
  ] as item}

      {item[1]}

    {#if item[0]!=="E · 架构与能力缺口"}

    {/if}
  {/each}

这五类问题需要不同的处理路径。

偶发故障优先由 L3RG 和任务恢复机制处理；重复性缺陷交给 RCAE 分析；持续质量退化由 SHCRG 发现并结合 ODERI 证据定位；能力缺口则进入候选能力设计流程。

不能让自进化控制器成为所有异常的默认处理器。

## 3.2 建立问题价值评分

可以为候选问题计算一个优先级：

\[
P_{\text{issue}}
=
f(F,I,C,R,E)
\]

其中：

- \(F\)：发生频率；
- \(I\)：对任务结果的影响；
- \(C\)：累计成本；
- \(R\)：风险严重性；
- \(E\)：现有证据的充分程度。

这里的 \(f\) 是待设计的评分策略，不应该直接假设所有因素都能用一个简单公式准确衡量。

例如，一个发生次数不多、但可能导致未授权外部操作的问题，优先级仍然应当很高；一个频繁出现、但只影响非必要日志格式的小问题，则可以降低优先级。

## 3.3 发现问题后先查已有解决方案

系统应当先检查：

- 是否已有经过验证的恢复策略；
- 是否已有相同问题的诊断记录；
- 是否有可以复用的工作流；
- 是否是已知工具故障；
- 是否已有针对该问题的候选修复；
- 是否只是环境或输入发生变化。

如果已有可靠方案，就不应该为了体现自进化而重新发明一次。

# 四、根因分析：建立可证伪的假设，而不是寻找一个看起来合理的解释

这是整个进化闭环最关键的环节之一。

假设近期代码任务的失败率增加。RCAE 应当建立一组候选假设，而不是立即指定一个模块负责修复。

例如：

| 假设 | 支持证据 | 需要的验证 |
|---|---|---|
| H1：路由错误 | 失败任务集中在不熟悉的项目类型 | 比较不同专家在同一批任务上的结果 |
| H2：上下文丢失 | 失败任务中出现遗漏的项目约束 | 检查构建后的上下文与原始约束 |
| H3：工具版本退化 | 错误开始时间与工具升级接近 | 对照旧版和新版工具 |
| H4：任务难度上升 | 最近任务包含更多文件与依赖 | 按难度和任务类型分层比较 |
| H5：验收环境异常 | 多种专家都在同一测试环境失败 | 使用独立环境重跑测试 |

这些假设可能同时成立，也可能全部不成立。

## 4.1 必须区分相关性与因果关系

例如，失败率上升的同时，模型版本也发生了变化。

这只能说明两者在时间上相关，不能直接证明模型升级导致了失败。

还可能存在其他变化：

- 任务难度同时增加；
- 工具版本也发生了变化；
- 验收标准更加严格；
- 样本构成发生了变化。

如果这些因素没有得到控制，系统就可能把错误归因于模型，并修改路由策略，结果反而让系统变差。

## 4.2 为每个假设定义反证条件

一个好的诊断假设不仅要解释当前现象，还应该说明什么证据会让它被否定。

例如：

> 假设：上下文压缩策略导致代码约束丢失。

支持证据可能是失败任务的关键约束在压缩后消失。

反证条件可以是：在同样的任务输入下，完整上下文与压缩上下文均保留了相关约束，并且错误在两种条件下都同样发生。

这会迫使系统通过证据更新判断，而不是不断寻找支持自己最初结论的信息。

## 4.3 诊断置信度必须与证据强度相匹配

建议为诊断记录：

- 当前最可能的解释；
- 备选解释；
- 每个解释的支持证据；
- 反证与缺失证据；
- 已执行的验证；
- 尚未验证的部分；
- 下一步最有价值的实验。

系统可以给出概率或置信等级，但不应仅凭语言模型自我评估的信心，就认为根因已经得到证明。

# 五、改进对象选择：到底应该修改哪个模块？

EvoAgent 是一个分层系统。同一个表面问题，可能由不同层级的缺陷引起。

建议建立统一的改进对象分类。

| 改进对象 | 典型问题 | 可能的候选改进 |
|---|---|---|
| Router | 专家选择错误 | 路由特征、分类规则、置信度门槛 |
| Planner | 计划不完整或分解不合理 | 规划策略、依赖分析、停止条件 |
| ReAct 策略 | 反复尝试、缺乏进展 | 行动选择、观察策略、退出条件 |
| 专家能力包 | 特定领域表现差 | 领域规则、专用算法、专业工具 |
| 上下文系统 | 关键约束遗漏 | 检索、压缩、排序、信息保留策略 |
| 模型路由 | 模型不适合任务 | 能力匹配、成本策略、回退机制 |
| 工具运行时 | 调用失败或结果不可靠 | 接口适配、超时、幂等、结果核验 |
| 工作流 | 重复步骤、依赖错误 | DAG 模板、并行策略、局部重规划 |
| 记忆与经验 | 错误经验重复影响决策 | 记忆验证、过期策略、冲突处理 |
| 共享内核 | 多领域都出现相同问题 | 公共契约、状态管理、通用执行策略 |

改进对象选择的基本原则是：

**修复能够解释问题的最小充分范围，不要因为一个局部缺陷就修改整个通用内核。**

例如，如果错误只发生在代码专家的 AST 重构能力上，优先调整代码能力包，而不是修改所有专家共用的上下文压缩策略。

但如果相同的上下文遗漏在多个领域专家中反复出现，就值得进一步检查共享上下文系统。

## 5.1 建立改进影响图

建议将模块依赖关系扩展为一张“改进影响图”。

例如：

- 修改 Router，可能影响所有依赖该路由的专家；
- 修改共享上下文压缩策略，可能影响所有专家的输入质量；
- 修改代码专家，只影响相关代码任务；
- 修改工具运行时，可能影响所有调用该工具的工作流；
- 修改授权门禁，可能影响所有具有副作用的操作。

候选改进的评测范围应由影响图决定，而不是只测试触发问题的那一个案例。

## 5.2 区分局部改进与共享内核改进

建议为改进范围设置四个层级：

- **L1：任务级修复**——只修复当前任务或当前产物；
- **L2：专家级改进**——只改变某个领域专家的策略或能力；
- **L3：共享能力改进**——改变模型路由、上下文、工具或公共执行机制；
- **L4：系统根规则改进**——涉及权限根规则、核心状态语义或整体安全边界。

L1 和 L2 可以拥有相对快速的验证流程；L3 需要更广泛的回归测试；L4 不能被普通的自动进化流程直接修改，必须进入独立的架构与安全治理流程。

这样可以避免一个专家的问题污染整个系统，也可以降低共享内核变更的风险。

# 六、实验设计：如何证明改进真的有效？

这是本专项最重要的技术问题。

系统需要区分：

1. 改进前后的表现是否不同；
2. 这种差异是否由候选改动造成；
3. 这种提升能否推广到目标任务范围；
4. 提升是否伴随着其他维度的退化。

仅仅运行一次改进前的任务和一次改进后的任务，通常不足以得出可靠结论。

## 6.1 建立不可变的基线

每次改进实验开始前，应记录：

- 稳定版本；
- 候选版本；
- 测试数据集版本；
- 任务类型与难度；
- 模型与工具版本；
- 运行配置；
- 验收标准；
- 成本和时间限制；
- 安全与权限约束；
- 评测结果的计算方式。

测试集和验收规则不能因为候选版本表现不佳，就临时修改成更容易通过的形式。

否则，系统可能通过降低标准制造出虚假的提升。

## 6.2 优先使用配对对照

假设要测试新的代码规划策略。

可以选择一组代表性的代码任务，让稳定版本和候选版本在尽可能一致的条件下运行，再比较结果。


    <grid-item>

        <title size="md">A · 稳定版本</title>
        相同任务、相同验收规则、受控运行条件。

    </grid-item>
    <grid-item>

        <title size="md">B · 候选版本</title>
        相同任务、相同验收规则、只改变目标改进因素。

    </grid-item>



    **对比结果**
    质量、成功率、耗时、成本、重试次数、稳定性与安全约束。


配对测试的优势在于，可以减少任务难度不同造成的偏差。

但也要注意随机性：如果模型生成存在明显波动，可以在适当情况下重复运行，或使用固定种子、确定性工具和可重放输入来减少噪声。并非所有外部模型或生成服务都支持完全可重复的运行，因此仍需记录无法控制的随机因素。

## 6.3 采用分层测试，防止总体指标掩盖局部退化

假设新路由策略让所有代码任务的平均成功率提高了 5%，但复杂仓库任务的成功率下降了 20%。

如果只看整体平均值，就可能错误发布。

因此，应按以下维度分层：

- 任务类别；
- 难度；
- 专家；
- 模型与工具版本；
- 是否需要多专家协作；
- 资源条件；
- 是否涉及外部副作用。

候选改进应当在它声称适用的任务范围内进行评估，而不是只报告一个全局平均数。

# 七、因果归因：不只知道哪个版本更好，还要知道为什么

实验发现候选版本表现更好，并不意味着我们已经完全理解收益来源。

例如，一个新版本同时修改了：

- Router 的专家选择策略；
- 上下文压缩算法；
- Planner 的任务分解方式。

如果最终成功率提高，我们仍然不知道是哪一项修改起作用，也不知道是否有某一项其实降低了质量，只是被其他改动掩盖。

这会给下一轮进化带来问题：系统可能保留无效改动，甚至在其他任务中触发退化。

## 7.1 默认一次只改变一个主要因素

对于能够独立测试的改进，建议优先使用单因素实验。

例如，先单独测试新的上下文压缩策略；确认收益后，再测试新的 Planner 策略。

这样更容易识别收益来源，也便于失败时回滚。

## 7.2 多个因素必须一起修改时，使用分阶段实验

有些改进存在强依赖，无法完全拆开。

例如，新版 Planner 只有配合新版工具契约才能正常工作。

这时可以将其作为一个有明确边界的候选组合进行评测，再在后续实验中逐步分离因素。

如果样本量和成本允许，也可以使用析因实验或分阶段消融实验，研究不同因素之间的交互作用。

关键是记录哪些因素同时发生了变化，不能把整个组合的效果武断地归因于其中一个模块。

## 7.3 关注效果差异，而不只是单个成功率

例如，稳定版本在 100 个测试任务中成功 80 个，候选版本成功 85 个。

观察到的提升是 5 个百分点，但是否足以证明候选版本具有稳定优势，还取决于：

- 样本代表性；
- 任务之间的相关性；
- 运行随机性；
- 失败类型；
- 评测指标是否可靠；
- 额外成本与风险；
- 统计不确定性。

因此，系统应该保存样本数量、原始结果、差异分布和不确定性，而不是只保留“提升 5%”这样的结论。

## 7.4 建立证据等级

建议将改进结论分为以下几级：

| 等级 | 含义 |
|---|---|
| E0 · 未验证 | 只有问题观察或改进想法 |
| E1 · 初步证据 | 有诊断依据或少量测试支持 |
| E2 · 受控验证 | 在明确的测试条件下完成对照评测 |
| E3 · 稳健验证 | 在多个代表性场景中重复验证，且关键回归门槛通过 |
| E4 · 运行验证 | 发布后在实际任务中持续观察到收益，未发现不可接受的退化 |

这是建议的治理等级，不是概率或统计显著性的直接替代。

对于高风险的共享内核改动，仅达到 E2 可能还不够；对于低风险的局部优化，经过适当的受控验证后，可能就已经具备有限发布资格。

# 八、候选改进对象：让每次进化都有完整档案

建议建立统一的 `EvolutionCandidate` 数据对象。

每个候选改进都应当记录：

- 候选 ID；
- 问题 ID；
- 目标模块；
- 根因假设；
- 改动范围；
- 稳定基线版本；
- 候选版本；
- 预期收益；
- 可能的负面影响；
- 测试范围；
- 评测结果；
- 证据等级；
- 安全与兼容性检查；
- 发布状态；
- 回滚条件；
- 后续监测结果。

例如：

```json
{
  "candidate_id": "evo-042",
  "target": "context_compression",
  "hypothesis": "关键约束在长任务压缩过程中被遗漏",
  "baseline_version": "stable-12",
  "candidate_version": "candidate-13",
  "expected_benefit": [
    "减少约束遗漏",
    "降低返工率"
  ],
  "guardrails": [
    "不降低关键验收通过率",
    "不突破上下文预算",
    "不改变权限规则"
  ],
  "evaluation_status": "PENDING"
}
```

这只是示意结构。正式 Schema 还需要包括实验数据引用、版本哈希、指标计算版本、适用范围和审计信息。

## 8.1 候选改进不等于正式版本

候选版本必须与稳定版本分离。

它可以运行在独立测试环境、候选配置空间或受控实验任务中，但不能在尚未获得发布资格时，直接覆盖正式专家策略。

尤其是涉及共享内核、任务状态、授权、安全根规则和恢复机制的改动，需要更加严格的隔离与验证。

# 九、发布治理：改进有效，不代表可以立即全量上线

候选版本通过实验后，还需要判断它是否适合真实任务。

建议建立五级发布流程。

  {#each [
    ["S0 · 草案","只记录问题、假设和候选方案，尚未执行验证。"],
    ["S1 · 隔离评测","在独立环境中运行测试和回归检查，不影响稳定任务。"],
    ["S2 · 受控试运行","在限定任务、预算和权限范围内运行候选版本。"],
    ["S3 · 正式发布","满足质量、安全、兼容和回滚条件后，更新稳定版本引用。"],
    ["S4 · 持续验证","监测真实运行数据，发现退化时暂停推广或回滚。"]
  ] as item}


        {item[0]}


        {item[1]}


    {#if item[0]!=="S4 · 持续验证"}

    {/if}
  {/each}

这些是逻辑发布阶段，不要求每种改进都采用完全相同的发布流程。

例如，某个低风险提示词调整可能在通过回归测试后直接发布；而共享上下文策略的变化，需要覆盖多个专家；涉及安全授权或核心状态语义的改动，则不能仅凭普通任务成功率提升就发布。

## 9.1 采用风险驱动的发布门槛

建议至少检查：

- 主要质量指标是否达到预设目标；
- 关键任务类别是否发生明显退化；
- 成本与耗时是否在可接受范围内；
- 是否通过安全与权限测试；
- 是否通过兼容性测试；
- 是否保留稳定版本和恢复路径；
- 是否存在尚未解决的关键副作用；
- 实验数据是否足够支持此次发布。

任何候选版本都不能通过修改验收规则来绕过发布门槛。

## 9.2 回滚条件必须在发布前定义

例如：

- 关键验收通过率低于最低门槛；
- 未授权操作或数据完整性风险出现；
- 单位合格任务成本持续超过预算；
- 某类任务出现显著退化；
- 错误率或无进展循环超过限制；
- 运行环境无法兼容当前版本。

具体阈值应根据任务类别和风险等级确定，而不是对所有模块采用同一个固定数字。

回滚后还应记录：

- 哪个候选版本被撤回；
- 触发了什么条件；
- 受影响的任务有哪些；
- 哪些产物需要重新验收；
- 是否需要进一步根因分析；
- 原候选是否允许在修复后重新进入评测。

# 十、避免自进化中的几个危险陷阱

真正的自进化系统不仅要能优化，还必须避免优化机制本身产生系统性偏差。

## 10.1 指标投机

如果只奖励任务成功率，系统可能无限重试；如果只奖励速度，可能跳过验证；如果只奖励低成本，可能选择不合适的模型。

应当通过硬约束、多个质量指标和独立验收，防止系统利用指标漏洞。

## 10.2 评测集过拟合

如果候选策略反复针对同一组测试案例优化，最终可能只会解决这些案例，而无法泛化到真实任务。

建议区分：

- 开发测试集；
- 验证测试集；
- 保留的最终评测集；
- 实际运行监测数据。

对重要改进，最终评测集不应被无限次用于调参，否则其独立验证价值会下降。

## 10.3 多个改动同时发布

如果同时更新模型、上下文、路由和 Planner，就很难判断出现退化时应回滚哪一项。

应尽量保持候选改动范围明确，必要时将强依赖改动组合成一个可整体回滚的发布单元。

## 10.4 诊断与执行互相证明

如果 RCAE 提出某项修复，候选生成器实施修复，评测系统又直接采纳 RCAE 自己的解释作为成功证据，就容易形成自我强化。

因此，根因假设与改进方案可以来自同一条诊断链，但评测结果必须基于独立的验收标准和真实运行证据。

## 10.5 过度进化

系统不应该因为可以优化，就不断修改已经稳定的模块。

每项改进都应考虑预期收益、实施成本、回归风险与维护成本。

有时最好的决定是保留稳定版本，继续积累证据，而不是立刻生成新候选。

# 十一、让诊断能力与执行能力保持分离

这是你之前特别关注的问题：如果诊断和执行耦合在一起，当系统判断错误时，怎么知道究竟是诊断出了问题，还是执行能力出了问题？

SELCIA 建议从架构上明确分离三个角色。


    <title size="md">RCAE · 诊断与根因分析</title>
    分析运行证据，提出根因假设、反证条件与验证建议。它不直接修改正式系统。



    <title size="md">Evolution Controller · 进化控制器</title>
    选择改进目标，管理候选版本、实验预算、发布资格与回滚。它不自行宣布候选有效。



    <title size="md">EQEAG · 独立评测</title>
    依据预先定义的测试集、验收规则和安全门槛，判断候选改进是否达到发布要求。


这三者共同使用 ODERI 的运行证据，但具有不同的职责。

## 11.1 分别评测诊断能力与执行能力

建议至少建立两组独立评测。

**诊断能力评测：**

- 能否识别真正的失败现象；
- 能否提出合理的候选原因；
- 能否区分事实与推测；
- 能否找到反证；
- 能否提出有效的验证实验；
- 能否在证据不足时承认不确定性。

**执行能力评测：**

- 能否正确实施候选修复；
- 能否通过功能和回归测试；
- 能否遵守权限与预算；
- 能否在失败时正确恢复；
- 能否保持其他任务类别的表现。

如果诊断正确，但修复实施错误，应该改进执行能力；如果修复实施完全符合方案，却没有解决问题，则需要重新审视根因假设；如果修复有效，但破坏了其他专家，则说明影响范围或回归评测不足。

这样，系统才不会把所有失败都归咎于同一个模块。

# 十三、下一专项：能力学习、经验沉淀与长期知识演化

SELCIA 解决了“如何发现问题并证明改进有效”。

但还有一个问题没有完全解决：

**当 EvoAgent 在一次任务中学到了有价值的东西，如何判断它应该被保存在哪里、适用于哪些场景，以及何时可以成为系统长期能力的一部分？**

例如，EvoAgent 完成了一次复杂代码重构，发现 AST 分析结合测试验证比直接文本替换更可靠。

这条经验可能有四种不同的去向：

- 保存为当前项目的经验；
- 沉淀为代码专家的领域知识；
- 形成可复用的代码重构工作流；
- 最终转化为通用工具或正式能力。

它们的作用范围、验证要求和失效条件都不同。

如果系统把每次成功经验都直接写入通用记忆，就会导致知识污染；如果什么都不沉淀，则每次任务都可能重复探索；如果只记录成功而不记录失败条件，还可能把偶然成功的策略推广到不适合的场景。

因此，下一专项建议定义为：

**Capability Learning, Experience Consolidation & Long-Term Knowledge Evolution，简称 CLEK。**

重点研究：

1. 如何区分事实、用户偏好、任务经验、工作流与正式能力；
2. 如何判断一条经验是否具有长期价值；
3. 如何确定经验应该属于当前任务、当前项目、某个专家还是共享内核；
4. 如何记录经验的适用条件、证据来源和失效条件；
5. 如何防止错误经验、偶然成功和过时知识进入长期记忆；
6. 如何将重复经验逐渐转化为结构化规则、工作流或工具；
7. 如何处理不同专家之间的经验冲突；
8. 如何检测旧经验是否仍然有效；
9. 如何让新经验影响后续任务，同时避免改变正在执行的任务；
10. 如何通过评测决定经验升级、降级、废弃或回滚；
11. 如何区分用户个人偏好与对所有用户或所有任务都成立的通用规律；
12. 如何让记忆、上下文、工作流和正式能力之间形成清晰的晋升与退役机制。

这一专项将进一步连接 MEEG、CERG、MACTDG、SELCIA 和独立进化控制器。

它的核心目标是：

**让 EvoAgent 不只是积累越来越多的信息，而是逐渐形成越来越可靠、适用范围越来越清晰、能够被验证和更新的长期能力。**

下一轮将从第一性原理开始，研究“经验如何从一次任务中的观察，逐步变成经过验证、可复用、可退役的系统能力”，并明确哪些内容可以自动沉淀，哪些必须经过独立评测。
