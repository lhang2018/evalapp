## ChatGPT

可以，而且你这句话实际上把 EvoAgent 的产品方向进一步明确了：你要做的不是一个专门研究如何进化的智能体，而是一个真正安装在手机上、理解你的意图、能够操作软件、帮你完成事情，并且越用越可靠的个人智能体。

这里有一个非常重要的产品逻辑：

-
进化系统是后台能力，负责学习、诊断、验证、升级。

-
手机智能体是前台产品，负责理解你、执行任务、操作应用、交付结果。

-
稳定版本是交付标准，一旦某个版本已经可靠，就应该长期稳定运行，而不是为了“持续进化”而频繁修改。

-
模型适配档案是长期资产，换模型时重新验证适配，而不是把已经稳定的版本直接覆盖。

因此，我建议将整个产品升级为两个紧密配合、但生命周期不同的系统：EvoAgent Mobile（手机执行端）和 EvoAgent Evolution Platform（后台进化平台）。

## 一、你真正需要的手机智能体是什么样？

举几个具体场景。

场景 1：理解意图，打开正确的软件

你说：“帮我给刚才联系的那个人回个消息，告诉他我晚十分钟到。”

智能体需要理解你的意图、识别联系人和对话上下文、打开相应应用、定位正确的聊天窗口、填写消息，并在发送前按权限要求向你确认。

场景 2：识别软件功能并完成操作

你说：“帮我把这个软件的通知关掉。”

智能体需要判断你指的是哪个应用，理解系统设置路径，识别当前界面，找到通知设置，执行操作，并检查结果是否真的生效。

场景 3：跨应用完成一个完整任务

你说：“整理一下今天的安排，看看有没有冲突，把重要事项列出来。”

智能体需要查询授权的数据源、理解时间和优先级、分析冲突，再生成一份结果。它不是简单打开几个 App，而是要把整个任务做完。

场景 4：失败后能够自己恢复

软件没打开、按钮没找到、网络超时，或者界面更新了。

智能体应识别失败，尝试安全的恢复方式；如果无法确定当前状态，就停止危险操作并告诉你原因，而不是不断乱点。

这些场景需要的并不只是大模型的意图识别能力，而是一整套从自然语言到真实操作、再到结果验证的执行系统。

## 二、产品架构要重新设计：手机端负责做事，后台负责进化

我建议把 EvoAgent 分成三个层次，而不是把所有功能都塞进一个 Agent。

## 第一层：EvoAgent Mobile

你真正使用的 Android 手机助手

意图识别

理解自然语言

界面理解

识别当前页面

应用操作

打开软件、点击、输入

结果验证

确认任务完成

### 第二层：Agent Runtime

真正决定任务怎么完成的执行内核

任务规划ReAct 循环上下文管理工具路由异常恢复权限控制
### 第三层：EvoAgent Evolution Platform

独立的进化、验证和发布平台

运行质量分析

工具故障诊断

候选版本实验

模型适配归档

这三个层次之间的关系很重要。

手机端不能依赖后台进化服务每次都在线才能完成基本任务。即使网络断开，仍然应该可以执行一部分本地操作，例如打开已知应用、查询本地任务状态、运行确定性的快捷操作。

需要云端模型的复杂任务，在联网后再交给云端。后台进化系统则负责产生经过验证的更新包，供手机端有控制地安装。

## 三、意图识别不能只靠一个大模型

你说“帮我打开软件，识别功能”，其实至少涉及五种不同的能力。

| 能力 | 系统需要理解什么 | 实现方式 |
|---|---|---|
| 意图分类 | 用户到底想干什么 | 规则、轻量分类器或大模型 |
| 实体识别 | 哪个 App、哪个人、什么时间、哪条消息 | 结构化解析、授权数据检索、澄清机制 |
| 任务规划 | 需要执行几个步骤，先做什么 | 任务规划器和 ReAct |
| 界面理解 | 当前页面是什么、哪些控件可以操作 | Android 无障碍节点、应用接口或视觉识别 |
| 结果确认 | 操作到底成功没有 | 状态检查、界面检查、数据回读 |

例如，你说：

帮我打开微信，找到昨天小王发来的消息，整理一下重点。

智能体内部不应该只生成一段回答，而应该形成一个结构化任务：

这只是目标数据结构的示例，并不意味着 Android 上的微信一定开放了读取历史消息的接口。真实实现必须考虑目标 App 的接口限制、登录状态、系统权限，以及其界面是否能够被合法、可靠地访问。

如果系统无法确认“小王”究竟是谁，或者无法可靠定位目标消息，它应该先问你，而不是猜一个人然后执行。

这就是高质量意图识别和普通聊天模型之间的区别：前者必须对后续真实操作负责。

## 四、安装到 Android 手机后，究竟怎样操作其他软件？

这部分必须在产品设计阶段讲清楚。因为手机系统有权限边界，不是安装一个 APK，就能不受限制地读取和控制所有应用。

我建议按四种操作方式建立工具层，按照可靠性和权限需求，从优先到兜底选择。

方式 A：Android 原生应用启动与系统接口

优先使用
通过 Android Intent、已知的应用包名、Deep Link 和公开系统 API 打开应用或执行明确的操作。路径固定、执行快，通常比识别屏幕坐标更稳定。

方式 B：Android AccessibilityService

重要能力
在用户明确启用无障碍服务后，根据系统允许的能力读取可访问的界面节点、识别控件并执行部分点击和输入操作。不同应用的可访问性、系统限制和安全页面会影响实际效果。

方式 C：屏幕视觉理解

在有明确授权的情况下，通过屏幕内容识别界面布局和控件。适用于没有可用语义节点的部分场景，但坐标点击容易受屏幕尺寸、弹窗和布局变化影响，应作为有验证机制的补充。

方式 D：应用官方 API 或集成接口

可用时最可靠
对于支持公开 API、官方分享接口、系统内容提供接口或授权集成的应用，优先通过这些接口完成任务，而不是模拟人工点击。

### 这里有三条硬边界

第一，Android 的权限管理、隐私保护和应用自身限制必须遵守。无障碍服务并不意味着可以无限制访问所有应用数据；密码管理器、支付确认、受保护页面和其他敏感界面可能无法或不应该被自动操作。

第二，Android 后台执行有生命周期和系统调度限制。不能假设一个普通 APK 可以永久在后台运行、随时读取屏幕或持续监听所有操作。需要根据实际任务选择前台服务、用户发起的执行会话、系统调度任务等适当机制。

第三，如果计划上架应用商店，还需要考虑无障碍 API 的使用政策、权限披露和审核要求。产品不能以绕过其他应用的安全限制作为设计目标。

因此，我建议先针对你自己的 Android 手机做一个受控的本地执行端，先实现打开应用、识别当前界面、操作少量允许的控件和验证操作结果，再逐步扩展到更多 App。

## 五、你提到的两个逻辑，其实应该成为 EvoAgent 的两条独立运行轨道

你说得很重要：

一个是稳定后不经常迭代，一个是能够高效、稳定地帮我做事。

这不是两个互相矛盾的目标，而是需要通过产品架构分开实现。

我会把它设计成 Stable Track（稳定运行轨道）和 Evolution Track（进化实验轨道）。

## A. 稳定运行轨道

负责每天真正帮你做事。

-
固定的 Agent Core、工具接口和安全规则。

-
已经验证的提示词、上下文策略和模型适配档案。

-
默认不接受实验性改动，只接受必要的安全修复和经过批准的稳定更新。

-
本地保存最后一个可用版本，更新失败能够恢复。

-
对常用操作建立确定性流程，减少每次临时规划带来的不确定性。

通过版本化更新包和发布门禁连接

## B. 进化实验轨道

负责研究如何做得更好。

-
分析真实运行中的失败和低效步骤。

-
测试新的工具选择策略、提示词、上下文治理和模型。

-
在独立分支、隔离环境或测试设备中运行实验。

-
通过固定回归集、真实任务验收和安全检查后，才生成稳定版候选。

-
保留旧版本和全部实验记录。

### 稳定不是停止学习，而是停止无条件变化

稳定轨道仍然可以记录新问题、收集使用反馈、检测模型 API 变化和工具故障，但不必每次发现问题就立即修改自身。

例如，EvoAgent 在一次手机操作中发现某个 App 更新了界面：

1.
稳定版检测到原来的控件路径失效。

2.
本次任务停止不安全的后续点击，并记录故障证据。

3.
如果存在经过验证的备用路径，就尝试恢复；否则向你说明情况。

4.
进化轨道使用测试设备或隔离环境研究新的控件定位方法。

5.
候选版本通过回归测试后，生成新的稳定更新包。

6.
手机端在合适的时机安装更新，并保留旧版本以便回滚。

这样，你的日常助手不会因为后台正在进行实验，就突然改变行为。

## 六、手机智能体的核心工作流程

我建议每个任务都走同一条执行流水线。简单任务走快速路径，复杂任务走完整规划路径。

### 01

接收意图

语音、文字或用户主动发起的任务。

### 02

解析与澄清

提取目标、对象、约束和成功条件；必要时询问用户。

### 03

规划与授权

选择工具和执行步骤，识别敏感操作并确定确认要求。

### 04

执行与观察

通过原生接口、无障碍节点或受控视觉操作执行，并观察界面变化。

### 05

验证与恢复

核验结果；失败时分类、重试、切换安全路径或停止。

### 06

交付与记录

明确报告完成情况，将结构化事件和问题写入本地日志。

### 07

后台改进

在独立实验轨道分析问题、验证候选方案，必要时发布稳定更新。

这里有一个我非常重视的原则：高效不等于让所有任务都经过复杂的 ReAct 循环。

例如“打开相机”是明确的单步任务，不应该每次都调用云端大模型、反复规划和评估。

而“帮我整理今天的会议资料，并找出需要回复的事项”是多步骤任务，才需要更完整的规划、工具调用、上下文管理和结果验收。

因此，EvoAgent 应当具备一个任务路由器：

-
简单且确定的任务 → 本地快捷流程。

-
需要理解界面或多个步骤的任务 → Agent Runtime。

-
需要外部知识或复杂分析的任务 → 云端模型辅助。

-
涉及高风险或无法验证的任务 → 请求确认或停止。

这会同时提高速度、稳定性并降低 API 成本。

## 七、我会怎样规划手机端的第一版？

建议采用 Android 原生应用作为手机执行端，后台 EvoAgent 引擎可以继续使用 Python。两者通过明确的任务协议通信，不必强行用同一种语言实现所有部分。

## M0

基础助手

安装后可以使用

文字输入、语音入口、应用启动、意图解析、少量确定性任务、运行记录、手动确认。

## M1

界面操作

能理解当前屏幕

无障碍节点读取、控件定位、受控点击和输入、界面状态验证、失败恢复。

## M2

任务执行

能够完成多步骤任务

ReAct 循环、跨应用任务规划、任务状态持久化、异常恢复、授权管理和完整验收。

## M3

稳定进化

越用越可靠，但不乱变

后台故障归因、工具自检、候选版本实验、稳定版本更新、模型切换和自动回滚。

第一版不需要立即实现所有 App 的自动操作。应先选择几种常用且允许访问的场景，验证从意图识别到真实执行、再到结果确认的完整链路。

## 八、最后一个产品决定：你想让手机端以什么方式工作？

这个选择会直接决定 Android 前台交互、无障碍服务、后台运行和权限管理的设计。

1. 你希望怎样唤起它？

像语音助手一样，说一句话就开始做事打开一个专属 App，在里面文字或语音下达任务两种都支持，后续增加快捷入口
2. 你希望它怎样操作其他 App？

先支持打开应用和系统允许的明确操作尽早实现无障碍服务，识别界面并点击控件优先设计综合方案：原生接口、无障碍和视觉识别协同
3. 你希望它的自主执行程度？

先执行低风险任务，发送消息、付款、删除等操作前确认常规任务授权后自动执行，敏感操作仍需确认尽可能自动完成任务，但保留硬性权限边界和安全停止机制
4. 网络或云端模型不可用时？

以云端模型为主，离线时只保留基本功能云端负责复杂理解，本地负责快捷操作和基本恢复尽量使用本地模型，优先保证离线可用
我的建议是：先把它做成一个可以在你自己的 Android 手机上真实操作应用的个人助手，再逐步把后台进化能力接上去。 先证明它能稳定完成你每天真正需要的几类事情，然后再让它学习怎样做得更好。这样，进化才是在服务产品，而不是让产品围着进化本身转。
