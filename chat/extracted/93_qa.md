# EvoAgent 第四十一专项：长期任务自治、执行恢复与跨会话连续性

本轮解决 EvoAgent 从“能够执行复杂任务”走向“能够持续执行复杂任务，并在中断后可靠恢复”的问题。

对个人使用的 EvoAgent 来说，这一点非常重要。你的部署方向是手机优先，同时允许个人电脑或微型 Linux 主机承担更多计算与服务能力。设备可能休眠、应用可能被系统回收、网络可能断开，云端生成服务也可能临时不可用。

因此，**长期任务不能依赖一个一直运行的模型会话，而必须建立在持久化任务状态、可恢复执行记录和经过验证的产物之上。**

例如，一项 60 秒 AI 漫剧制作任务可能需要数小时，包含剧本、角色设计、分镜、素材生成、配音、视频合成和质量验收。

如果在视频合成阶段发生断电，系统恢复后必须知道：

- 哪些节点已经完成；
- 哪些产物已经保存；
- 哪些产物对应哪个版本的分镜；
- 哪个节点正在执行；
- 哪些外部生成请求的结果尚不确定；
- 哪些操作可以安全重试；
- 哪些验收需要重新执行。

如果系统只是读取最后一段聊天记录，就无法可靠回答这些问题。

本专项建议定义为：

**Long-Horizon Task Autonomy & Recovery，简称 LTAR。**

它负责长期任务状态持久化、检查点、断点恢复、执行一致性、跨会话连续性、取消与暂停、离线排队及恢复后的状态核验。

## 一、第一性原理：恢复的对象是任务状态，不是聊天记录

首先要区分五类数据。


    <title size="md">1. 任务状态</title>
    目标、约束、DAG 节点状态、依赖关系、进度、预算、暂停原因和恢复策略。



    <title size="md">2. 执行日志</title>
    发生了什么、何时发生、调用了什么工具、返回了什么结果、出现了什么异常。



    <title size="md">3. 产物与检查点</title>
    代码文件、视频片段、素材、测试报告、中间文件及其版本和完整性信息。



    <title size="md">4. 模型上下文</title>
    某次调用使用的上下文快照、检索知识、摘要版本和来源引用。



    <title size="md">5. 长期记忆与经验</title>
    可跨任务复用的用户偏好、项目知识、已验证经验和专家策略。


这五类数据相互关联，但不能互相替代。

例如，日志记录了“FFmpeg 执行成功”，并不代表最终视频文件完整、已经持久化或通过质量验收。

同样，模型上下文中写着“已经生成全部镜头”，也不能代替对真实素材文件的检查。

因此，LTAR 的首要原则是：

**以持久化任务状态为执行依据，以真实产物和可验证证据确认状态，以日志解释发生过什么。**

# 二、建立任务状态机：每个任务必须处于明确状态

建议将长期任务设计成显式状态机，而不是用一段不断增长的文本描述进度。

任务级状态建议包括：

| 状态 | 含义 |
|---|---|
| `CREATED` | 任务已创建，尚未开始执行 |
| `READY` | 前置条件满足，可以调度 |
| `RUNNING` | 正在执行 |
| `WAITING` | 等待用户、设备、服务或外部条件 |
| `PAUSING` | 正在安全地暂停 |
| `PAUSED` | 已暂停，状态已经持久化 |
| `RECOVERING` | 正在核对状态并恢复 |
| `CANCELLING` | 正在取消并处理正在执行的操作 |
| `COMPLETED` | 任务已通过规定的最终验收 |
| `PARTIAL` | 产生了可交付的部分结果，但目标尚未全部完成 |
| `FAILED` | 任务无法继续，且没有自动恢复路径 |
| `CANCELLED` | 任务已按取消流程终止 |

这些状态必须有明确的合法转换规则。

例如，`RUNNING → PAUSED` 不能只是将状态字段改成 `PAUSED`，还需要确保已经执行的步骤、产物引用和未完成操作的状态得到持久化。

`COMPLETED` 也不能只因为所有 DAG 节点都显示成功就自动设置。如果任务定义要求最终验收，那么最终验收必须通过。

## 2.1 任务状态与节点状态分开管理

一个长期任务可能包含几十个 DAG 节点。即使整体任务处于 `RUNNING`，某些节点也可能已经完成，另一些正在执行，还有一些因依赖关系而等待。

建议节点状态至少包括：

- `PENDING`：尚未开始；
- `READY`：依赖已满足；
- `RUNNING`：正在执行；
- `SUCCEEDED`：执行结果已通过节点验收；
- `RETRY_WAIT`：等待重试；
- `BLOCKED`：被前置条件或外部条件阻塞；
- `UNKNOWN`：无法确认执行是否产生了结果；
- `FAILED`：节点失败；
- `CANCELLED`：节点已取消；
- `SKIPPED`：经规则允许而跳过。

其中，`UNKNOWN` 非常重要。

如果远程视频生成请求已经提交，但网络在返回结果前断开，系统不能简单地将节点标记为失败并再次提交，因为第一次请求可能仍然在运行，甚至已经完成并产生费用。

必须先进行状态核验，再决定是否重试。

# 三、任务检查点：把可以恢复的状态保存下来

检查点（Checkpoint）不是简单地保存一段摘要，而是记录一个任务在特定时刻能够被恢复所需要的最小充分状态。

建议定义 `TaskCheckpoint`，包含以下内容：

| 字段 | 用途 |
|---|---|
| `checkpoint_id` | 检查点唯一标识 |
| `task_id` | 所属任务 |
| `checkpoint_sequence` | 检查点顺序号 |
| `task_state_version` | 对应的任务状态版本 |
| `dag_version` | 当前任务 DAG 版本 |
| `completed_nodes` | 已完成节点及验收结果引用 |
| `active_nodes` | 正在执行或结果尚不确定的节点 |
| `pending_nodes` | 尚未执行的节点 |
| `artifact_refs` | 已持久化产物及其版本、哈希 |
| `budget_snapshot` | 已消耗和剩余预算 |
| `external_operation_refs` | 外部操作的关联 ID 与核验状态 |
| `context_refs` | 必要的上下文快照引用 |
| `created_at` | 检查点创建时间 |

检查点应引用已有日志、产物和上下文，而不是把所有内容重复复制进去。

## 3.1 哪些时刻应该创建检查点？

建议至少覆盖以下情况：

- 任务正式开始执行前；
- 一个重要 DAG 节点完成并通过验收后；
- 即将启动高成本或长时间运行的操作前；
- 外部副作用执行后，获得可验证结果时；
- 任务暂停或进入等待状态前；
- 应用主动退出或服务计划重启前；
- 资源预算接近阶段性上限时；
- 系统完成恢复并确认新的权威状态后。

对于高成本任务，检查点可以更频繁；对于简单、可快速重建的任务，则不需要过度保存。

**检查点频率应该由恢复成本、数据丢失风险和存储开销共同决定。**

## 3.2 检查点必须具备一致性

假设一个节点执行了以下操作：

1. 生成视频片段；
2. 将片段保存到文件；
3. 写入素材数据库；
4. 更新 DAG 节点状态。

如果系统只完成了第 2 步就突然断电，恢复后可能出现文件存在、数据库没有记录的情况。

因此，检查点需要与产物持久化、数据库状态更新和日志记录协调。

对于同一台设备上的本地任务，可以通过事务、临时文件、原子替换和校验等机制提高一致性。对于跨设备或跨服务的任务，通常无法依靠单个数据库事务保证所有操作同时成功，需要使用操作记录、幂等机制、补偿操作和恢复核验。

# 四、执行恢复：恢复之前，先确定真实状态

建议建立独立的 `RecoveryManager`，不让普通模型直接决定从哪一步继续。

恢复流程如下。

恢复不是将历史上下文直接交给模型，然后让模型自由决定下一步。

模型可以参与解释异常、建议修复路径或重新规划，但任务状态重建、权限检查和操作去重应由确定性机制负责。

## 4.1 恢复后不一定从原节点继续

恢复结果可以分为四种：

- **直接继续：** 产物和节点状态都已经验证；
- **重新执行：** 节点没有产生有效结果，且执行可安全重试；
- **先核验：** 外部操作的执行结果不确定；
- **局部重规划：** 原依赖或环境发生变化，旧计划已不再适用。

例如，视频生成节点的请求已经成功，但本地没有下载完成的素材。恢复后应优先尝试获取已有生成结果，而不是重新生成视频。

相反，如果本地 FFmpeg 合成任务未完成、临时文件已损坏，且该节点没有不可逆外部副作用，则可以清理无效临时产物并重新执行合成。

# 五、幂等与副作用治理：防止恢复造成重复执行

这是长期任务可靠性的核心问题。

对于普通的本地计算，重复执行可能只增加成本；对于远程生成、付费 API、发送消息、发布文件或修改数据库，重复执行可能产生重复费用或不可逆后果。

建议建立统一的 `OperationLedger`，记录每个可能产生副作用的操作。

每项操作至少记录：

- `operation_id`：稳定的操作标识；
- `task_id` 和 `node_id`；
- `idempotency_key`：服务支持时使用的幂等键；
- `request_digest`：请求内容摘要；
- `status`：待提交、已提交、执行中、成功、失败或结果未知；
- `external_operation_id`：外部服务返回的操作标识；
- `result_ref`：结果引用；
- `retry_policy`：允许的重试规则；
- `last_verified_at`：最后一次状态核验时间。

## 5.1 区分三种操作

| 类型 | 示例 | 恢复策略 |
|---|---|---|
| 可重复执行 | 本地只读分析、确定性计算 | 满足条件时可以安全重跑 |
| 可幂等执行 | 使用相同幂等键提交的受支持请求 | 由服务端保证重复请求不会产生重复效果时，可按契约重试 |
| 非幂等或结果不明 | 不支持幂等的付费生成、发送消息、外部发布 | 先查询状态或核验结果，必要时请求人工判断 |

这里不能假设所有服务都支持幂等键，也不能假设提供幂等键就一定覆盖所有业务副作用。必须根据具体服务的契约确定其有效范围和保留时间。

## 5.2 不要承诺无法保证的“恰好执行一次”

在分布式系统中，如果请求已经发出，但客户端在收到结果前断线，客户端可能无法判断远端是否完成了操作。

因此，通用系统不能仅依靠本地状态实现所有外部操作的“恰好一次执行”。

更现实的设计是：

- 对可重复操作采用至少一次执行并确保幂等；
- 对支持幂等键的服务使用稳定的请求标识；
- 对结果未知的操作优先查询或核验；
- 对无法核验且重复执行风险较高的操作暂停并请求判断；
- 对跨系统的部分成功情况提供补偿或人工恢复路径。

**目标不是假装不会出现不确定状态，而是让不确定状态能够被发现、隔离和安全处理。**

# 六、任务暂停、取消与中断：三者必须区分

暂停、取消和进程中断并不是同一种情况。

## 6.1 暂停：保留继续执行的能力

暂停意味着任务暂时不再启动新的执行步骤，但保留已完成的工作和后续恢复所需的状态。

建议流程：

1. 停止派发新的节点；
2. 对正在执行的节点执行安全暂停或等待策略；
3. 记录无法立即停止的操作；
4. 持久化任务状态、产物引用和预算；
5. 确认检查点有效；
6. 将任务标记为 `PAUSED`。

对于无法中断的外部操作，暂停并不意味着远端任务已经停止。系统必须记录其真实状态，并在恢复时继续核验。

## 6.2 取消：停止后续工作并处理副作用

取消意味着用户不再希望继续原任务。

取消流程应当：

- 停止启动新的节点；
- 向支持取消的工具或服务发送取消请求；
- 等待或核验正在运行的操作；
- 保留已完成产物；
- 清理允许清理的临时文件；
- 对必要的部分成功操作执行补偿；
- 持久化取消结果。

取消请求不能保证所有外部操作都能撤销。例如，已经发送的邮件可能无法撤回，已经完成的云端生成也可能已经产生费用。

因此，系统需要区分“任务取消成功”和“所有副作用均已撤销”。

## 6.3 进程意外中断：由恢复管理器接管

应用被系统回收、设备重启或服务崩溃时，可能完全来不及执行暂停流程。

此时不能假设最后一次正常保存的状态就是实际执行状态。

恢复管理器必须通过检查点、日志、操作记录和真实产物进行对账，再决定继续、重试、等待或停止。

# 七、跨会话连续性：新会话应该接管任务，而不是重新猜测任务

用户可能今天启动一个复杂任务，明天再继续；也可能在手机上查看进度，在个人电脑上执行重计算任务。

建议将长期任务设计成独立于聊天会话的持久化实体。

也就是说：

- 聊天会话负责交互；
- 任务 ID 负责标识长期工作；
- 任务状态保存执行进度；
- 检查点支持恢复；
- 记忆与上下文引用支持理解历史；
- 产物仓库保存实际成果。

当用户开启新会话并选择继续某项任务时，系统应当根据任务 ID 恢复其状态，而不是把新会话当作一个全新任务。

## 7.1 建立 `TaskResumeContext`

建议恢复时向模型提供一份专门的恢复摘要，包含：

- 当前任务目标；
- 当前有效约束；
- 最后一个有效检查点；
- 已验收的成果；
- 尚未完成的节点；
- 结果未知的操作；
- 当前预算与剩余预算；
- 已知风险；
- 恢复后建议的下一步；
- 需要用户确认的事项。

这份摘要由权威任务状态和相关证据构建，不应仅从聊天历史自动生成。

模型可以使用它理解任务，但实际调度仍由任务协调器和恢复管理器控制。

## 7.2 任务计划变更必须有版本

如果用户在第二天修改了需求，不能直接把旧任务的目标字段覆盖掉。

建议建立版本化变更记录：

- 旧目标和旧约束；
- 新目标和新增、删除或修改的约束；
- 已完成产物是否仍然适用；
- 哪些 DAG 节点需要重跑；
- 哪些节点可以继续复用；
- 预算和验收标准是否需要重新确认。

例如，用户将视频时长从 60 秒改为 90 秒，不代表剧本、角色素材和所有已完成镜头都必须丢弃。但分镜、配音、合成和最终验收可能需要重新规划。

系统应该根据依赖图进行局部失效分析，而不是无条件从头执行。

# 八、手机、个人电脑与微型 Linux 主机：全局任务状态，本地能力执行

结合你此前确定的手机优先战略，以及个人电脑、微型 Linux 主机作为后续执行设备的方向，建议 LTAR 采用设备能力与任务状态分离的架构。

核心原则是：

**任务可以跨会话恢复；具体执行能力由当前设备和可用服务决定。**


    <title size="md">Android 手机</title>
    创建任务、查看进度、审批操作、轻量执行、保存本地状态，以及在系统允许时调度后台工作。



    <title size="md">个人电脑</title>
    适合代码项目、大文件处理、复杂工具执行、本地模型和需要较高计算资源的任务。



    <title size="md">微型 Linux 主机</title>
    适合长期运行的任务协调器、状态数据库、日志接收、轻量模型和后台调度，具体能力取决于硬件。



    <title size="md">可选云端服务</title>
    承担已授权的远程模型推理、素材生成或其他外部任务；其状态必须独立核验。


这些设备不需要各自维护互相矛盾的任务真相。

如果采用多设备部署，应明确一个任务状态的权威写入者，或者使用具备事务和冲突解决机制的协调服务。不能让手机和 Linux 主机各自修改同一个任务状态，却没有版本检查。

## 8.1 设备离线时的处理

如果手机与主机断联：

- 手机可以继续查看已经同步的状态；
- 允许在本地创建离线任务草稿；
- 已有授权的本地任务可以按策略继续；
- 需要主机或云端能力的节点进入等待状态；
- 恢复连接后，通过任务 ID、事件序号和版本信息同步状态。

离线期间的状态不应直接覆盖主机上更新的权威状态。

对于冲突的任务修改，需要通过版本比较和明确的冲突解决规则处理。

## 8.2 Android 后台执行需要遵守平台限制

手机应用可能受到后台运行、耗电优化、进程回收和网络限制的影响。

因此，不能承诺 Android 应用在任何情况下都可以无限期后台执行。

对于长时间任务，更可靠的方案是将执行安排在具备持续运行能力的主机或服务上，手机主要负责控制和观察；纯本地手机任务则应根据系统支持的后台任务机制、持久化和恢复策略设计。

# 九、离线队列与恢复同步：连接恢复后如何避免重复工作？

LTAR 需要与此前设计的日志同步、设备关联和断点恢复机制共同工作。

建议建立本地持久化的 `TaskEventOutbox`，记录尚未同步的任务事件。

每条事件至少包括：

- `event_id`：全局唯一事件 ID；
- `task_id`：所属任务；
- `device_id`：事件产生设备；
- `sequence_number`：设备或任务内的单调递增序号；
- `base_state_version`：事件基于哪个任务状态版本产生；
- `event_type`：节点完成、任务暂停、产物生成、操作结果等；
- `payload_ref`：事件数据或产物引用；
- `created_at`：事件产生时间；
- `sync_status`：待同步、已确认或冲突待处理。

## 9.2 日志同步不等于任务状态合并

日志通常是追加式的，比较容易通过唯一事件 ID 去重。

任务状态则可能包含互相冲突的更新。例如，手机离线时将任务标记为暂停，而主机在此期间完成了一个节点。

系统不能简单采用“最后写入者获胜”，因为设备时间可能不一致，较晚到达的事件也不一定代表更权威的状态。

建议：

- 使用服务端状态版本或明确的版本比较机制；
- 对任务状态变化执行合法性检查；
- 对可自动合并的独立字段使用明确规则；
- 对互相矛盾的关键状态进入冲突处理；
- 对权限、预算和不可逆操作保留更严格的协调机制。

如果只是日志上传成功，但任务状态仍存在冲突，系统不应该自动恢复可能产生副作用的节点。

# 十、产物版本与依赖失效：任务恢复不意味着所有旧成果都能复用

长期任务通常会产生大量中间成果。

例如，代码任务可能产生补丁、测试报告和构建产物；AI 漫剧任务可能产生剧本、分镜、角色图、音频、视频片段和最终视频。

每项产物都应该具备：

- 稳定的 `artifact_id`；
- 版本或内容哈希；
- 生成它的任务和节点；
- 输入产物引用；
- 工具或模型版本；
- 生成状态；
- 验收状态；
- 文件位置或存储引用。

## 10.1 使用依赖图判断哪些成果需要重建

假设视频制作 DAG 为：

剧本 → 分镜 → 视频镜头 → 配音 → 合成 → 最终验收。

如果用户只修改了字幕字体，系统可能只需要重新执行合成和最终验收，而不必重新生成视频镜头。

如果角色设定发生变化，则可能需要使依赖该角色设定的分镜、镜头和相关合成节点失效。

建议通过输入版本和依赖关系建立产物有效性判断。

某个节点的旧结果只有在以下条件满足时才可复用：

- 输入版本仍然匹配；
- 工具契约兼容；
- 任务约束没有改变其适用性；
- 产物完整且可访问；
- 必要验收仍然有效。

如果无法证明旧结果仍然有效，就应重新验证或重建，而不是盲目复用。

# 十一、长期任务的可观测性：如何知道恢复机制本身有没有出错？

LTAR 也需要独立评测，不能只检查任务最终是否完成。

建议建立以下指标：

| 指标 | 含义 |
|---|---|
| 恢复成功率 | 中断后能够恢复到正确可执行状态的比例 |
| 恢复时间 | 从启动恢复到重新进入可执行状态的耗时 |
| 重复执行率 | 因恢复逻辑错误导致的重复操作比例 |
| 状态不一致率 | 任务状态与真实产物、外部操作状态不一致的比例 |
| 检查点恢复损失 | 中断后需要重做的有效工作量 |
| 产物复用率 | 在有效性确认后成功复用已有产物的比例 |
| 冲突处理准确率 | 设备间状态冲突被正确识别与解决的比例 |
| 未决操作处理质量 | 结果未知的外部操作是否被安全核验 |
| 预算恢复准确率 | 恢复后剩余预算是否与真实消耗一致 |
| 取消与暂停正确性 | 任务暂停或取消后是否仍出现不应发生的操作 |

## 11.1 建立故障注入测试

建议在隔离环境中主动模拟：

- 写入检查点前后突然断电；
- 产物保存成功但数据库更新失败；
- 数据库更新成功但日志同步失败；
- 外部请求成功但响应丢失；
- 手机与主机在不同节点上同时更新状态；
- 恢复时发现工具版本已经变化；
- 任务预算在暂停期间发生调整；
- 取消请求到达时，外部操作仍在执行；
- 产物文件存在但内容不完整；
- 检查点引用的某个文件已经被删除。

每种故障都需要预期结果和验收标准。

例如，模拟外部请求成功但响应丢失时，正确结果不一定是自动重试，而可能是先查询外部操作状态，确保不会重复扣费。

# 十三、下一专项：任务并发、资源隔离与多任务协同调度

LTAR 解决了长期任务如何保存、暂停和恢复，但还存在一个自然延伸的问题：

**如果 EvoAgent 同时运行多个任务、多个专家和多个工具，如何避免任务相互干扰、争抢资源、覆盖文件或耗尽预算？**

例如，EvoAgent 可能同时执行：

- 一个大型代码重构；
- 一个 AI 漫剧视频合成任务；
- 一个后台知识整理任务；
- 一个等待外部服务恢复的远程生成任务。

如果这些任务共享同一台个人电脑或微型 Linux 主机，就会出现 CPU、内存、GPU、磁盘、模型调用配额和外部服务预算之间的竞争。

如果多个任务修改同一个项目，还可能发生文件覆盖、基于过期代码生成补丁，或者一个任务清理了另一个任务仍在使用的临时文件。

下一专项建议定义为：

**Multi-Task Scheduling, Resource Isolation & Coordination，简称 MTSRIC。**

重点研究：

1. 如何决定多个任务的执行优先级；
2. 如何为任务、专家、工具和模型调用分配资源；
3. 如何防止多个任务争抢同一设备资源；
4. 如何识别任务之间的文件、数据库和产物冲突；
5. 如何在 DAG 内部并行执行，同时保持正确的依赖顺序；
6. 如何在多个长期任务之间分配 CPU、GPU、内存、磁盘和网络；
7. 如何隔离不同任务的工作目录、临时文件、记忆和执行状态；
8. 如何管理共享模型服务与外部 API 配额；
9. 如何在高优先级任务到来时暂停或让出资源；
10. 如何防止一个失败任务反复重试，拖垮其他任务；
11. 如何跨手机、个人电脑和微型 Linux 主机调度可迁移任务；
12. 如何在资源不足时选择排队、降级、暂停或终止；
13. 如何保证任务隔离不破坏专家之间必要的知识共享；
14. 如何通过并发、冲突和资源压力测试验证调度质量。

它将连接 LTAR、ARCBG、DAG 执行器、工具运行时、设备能力注册表和任务状态协调机制。

最终目标是：

**让 EvoAgent 不仅能可靠完成一个长期任务，还能在有限的个人设备资源下，安全、可预测地协调多个长期任务。**
