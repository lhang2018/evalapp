## 二、记忆和上下文为什么必须分开？

这是我认为需要在总体架构中明确冻结的关键设计。

| 对比 | 记忆系统 | 上下文治理 |
|---|---|---|
| 核心问题 | 什么值得长期保存？ | 当前任务需要哪些信息？ |
| 工作方式 | 写入、更新、检索、归档、遗忘或失效处理 | 选择、排序、压缩、组装和裁剪 |
| 时间尺度 | 跨任务、跨会话，部分信息长期存在 | 面向当前模型调用，持续变化 |
| 典型内容 | 用户偏好、经过验证的经验、历史项目事实 | 当前目标、最近观察、相关记忆、工具结果、计划状态 |
| 常见故障 | 错误记忆、过期记忆、记忆冲突 | 重要信息遗漏、无关信息过多、上下文截断 |
| 主要评测 | 记忆准确率、检索召回率、更新正确性 | 信息覆盖率、相关性、Token 成本、任务影响 |

举个例子：用户告诉 EvoAgent，制作漫剧时角色的服装必须保持一致。

- **记忆系统**判断这是值得保存的长期项目约束，并记录适用范围。
- **上下文治理**在下一次制作相关角色的分镜时，才把这条约束放入当前模型调用。
- **漫剧专家**根据这条约束制定角色一致性策略。
- **Planner**将角色一致性检查加入工作流。
- **ReAct**在生成结果后检查实际画面，必要时触发修正。

记忆里有这条规则，不代表每一次模型调用都必须携带它；反过来，如果上下文组装时漏掉它，记忆系统再完整也没有用。

## 三、三个核心层之间还存在一个容易忽略的问题：隔离

EvoAgent 不是一个专家共用一份无限增长的记忆、共用一份无限扩张的上下文。

我建议至少区分以下记忆范围：

- **用户通用记忆**：跨领域适用的偏好和明确授权保存的事实。
- **专家领域记忆**：编程经验、旅游偏好、漫剧制作经验等。
- **项目记忆**：某个具体项目的约束、素材、决策和进度。
- **任务短期状态**：当前执行的目标、步骤、观察结果和检查点。
- **运行与进化证据**：日志、失败案例、评测结果和候选改进。

这些数据可以使用统一的记忆基础设施，但必须具有明确的命名空间、权限、来源、有效期和可信程度。

例如，编程专家的一次错误经验不能直接成为全局记忆；一条来自模型猜测的信息，也不能与用户明确确认的事实享有相同的可信等级。

## 四、它们应该怎样参与自进化？

这里不能只优化提示词。每个核心层都需要自己的诊断指标和改进路径。

| 观察到的问题 | 优先检查的组件 | 可能的改进 |
|---|---|---|
| 选错领域专家 | 路由系统 | 修正候选召回、专家描述或决策阈值 |
| 专家不知道之前的项目约束 | 记忆检索与上下文治理 | 改善检索、适用范围和上下文组装 |
| 模型拿到很多无关信息 | 上下文治理 | 优化相关性排序、分层注入和压缩 |
| 任务步骤遗漏或依赖错误 | Planner / DAG | 改进拆解策略、前置条件和验证节点 |
| 明明有计划却重复调用工具 | ReAct 运行时 | 改善状态判断、停止条件和动作去重 |
| 工具返回错误但被误认为成功 | 工具适配器与验收器 | 改进错误契约、结果校验和故障分类 |
| 相同问题反复出现 | 进化系统 | 关联历史案例，生成候选修复并验证是否有效 |

还必须允许**多因一果**：一个任务失败可能同时由错误路由、错误记忆、上下文遗漏和工具异常导致。诊断器应当比较证据，而不是把问题强行归给一个模块。

## 五、我建议再补充一个更重要的原则

EvoAgent 的进化对象，不应该只是一段提示词或者一个专家，而应该是一个**具有明确边界、可独立版本化、可独立评测的能力组件**。

例如：

- 可以单独优化漫剧专家的角色一致性策略。
- 可以单独优化上下文系统对长任务状态的保留方式。
- 可以单独优化记忆系统的冲突检测。
- 可以单独优化 ReAct 的工具重试策略。
- 也可以优化多个专家共享的通用组件，但必须进行跨专家回归测试。

并且，每个候选改进都要同时评估质量、稳定性、延迟、模型调用成本和副作用。不能为了提高一点成功率，就无限增加模型调用次数。

**因此，我建议将专家系统、记忆系统、上下文治理列为 EvoAgent 的三大核心能力层；Planning、ReAct 和自进化分别承担计划、执行和改进职责。** 六者通过统一的任务状态、版本清单、日志和评测机制协同，但不能混成一个无法定位问题的巨大智能体循环。
