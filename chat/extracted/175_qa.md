## 一、产品目标与设计边界

### 1.1 本专项要解决什么

EvoAgent 的内部系统已经覆盖目标管理、任务规划、领域专家、知识检索、故障诊断、自进化和后台自主执行等能力。

但从用户角度看，这些能力最终必须回答六个问题：

1. 我能让它帮我做什么？
2. 它现在正在做什么？
3. 它为什么这样做，有没有偏离我的目标？
4. 它究竟完成了什么，结果是否可靠？
5. 如果出现问题，我能否及时介入？
6. 我如何确认它正在持续改善，而不是只增加复杂度？

本专项将设计统一的产品交互层，让内部复杂能力以清晰、可操作、可信赖的方式呈现给用户。

### 1.2 设计原则

**原则一：任务结果优先。**

优先展示用户需要的最终结果、交付物和验收结论。内部过程只展示与用户决策、风险判断或问题处理有关的信息。

**原则二：状态必须真实。**

任务进度必须来自真实执行事件、节点状态和验收证据。没有证据时，不显示虚构的完成百分比。

**原则三：用户拥有控制权。**

用户可以在适当状态下暂停、继续、取消、修改目标、调整预算和管理授权。系统必须说明这些操作的实际影响。

**原则四：主动帮助有价值，但不喧宾夺主。**

主动建议应与用户目标相关，有明确依据和预期收益。不能让提醒、项目报告和后台活动淹没主要任务结果。

**原则五：界面与执行内核解耦。**

界面负责呈现和收集用户操作，任务状态由正式任务系统维护。不能因为界面显示错误，就直接修改任务的真实状态。

**原则六：复杂度由系统承担。**

用户不应被迫理解 ReAct、DAG、上下文压缩、工具路由和进化分支，才能完成一个普通任务。高级用户可以查看技术细节，但默认交互应尽可能简单。

## 二、产品信息架构

### 2.1 一级导航

建议 Android 首版采用四个主要入口。

| 入口 | 核心用途 |
|---|---|
| 对话 | 随时提出问题、讨论想法、要求解释或获取建议 |
| 任务 | 查看正在执行、已完成、等待处理和失败的具体任务 |
| 目标 | 管理长期项目、阶段进展、关键依赖和持续工作 |
| 控制中心 | 管理权限、预算、主动帮助、设备、后台执行和运行状态 |

语音输入应作为贯穿各个主要页面的交互能力，而不是独立割裂的任务系统。

任务列表与目标列表必须保持区别：任务回答“这件事执行得怎么样”，目标回答“长期想实现的结果推进到了哪里”。

### 2.2 用户界面的四个层次

建议采用由简到繁的展示结构。

**第一层：直接交付**

展示回答、结果、文件、执行结论或建议。普通任务不要求用户先查看任务仪表盘。

**第二层：任务卡片**

展示任务状态、已完成成果、当前阻塞和需要用户处理的事项。

**第三层：任务详情**

展示计划、关键执行事件、验收结果、错误、恢复记录和交付物。

**第四层：高级诊断**

为需要排查问题的用户提供版本清单、工具调用摘要、错误码、运行事件、预算消耗和诊断证据。

高级诊断是可选能力，不能成为普通用户完成任务的前置条件。

## 三、核心页面设计

### 3.1 对话首页

首页的首要任务是让用户可以自然地开始工作。

建议包括：

- 统一文字与语音输入；
- 当前对话；
- 与当前任务有关的附件和上下文；
- 正在运行的重要任务的简洁状态；
- 必要的待确认事项；
- 与当前目标相关的少量高价值建议。

首页不应默认展示大量后台任务、全部日志或复杂的系统指标。

当用户正在等待某项任务的结果时，界面应优先展示该任务，而不是主动推送无关机会。

### 3.2 任务列表

任务列表需要支持以下视图：

- **进行中：** 正在执行、规划、恢复或验证；
- **等你处理：** 需要补充信息、确认授权或解决阻塞；
- **已完成：** 已通过相应验收的任务；
- **未完成：** 失败、取消或因条件不足而停止的任务；
- **后台任务：** 已获准在后台执行的工作。

列表应支持按项目、时间、状态和任务来源筛选。

每个任务卡片至少展示：

- 任务名称；
- 当前状态；
- 所属目标或项目；
- 最近一次有意义的进展；
- 是否需要用户介入；
- 最终结果或主要阻塞；
- 适用时的预算使用情况。

任务来源可以标记为用户发起、计划任务、目标派生或主动发现，帮助用户理解任务为什么存在。

### 3.3 任务详情页

建议采用以下内容结构：

1. **任务目标：** 用户要求完成什么。
2. **当前状态：** 任务现在处于哪个阶段。
3. **执行摘要：** 已经做了什么，接下来做什么。
4. **计划与依赖：** 关键步骤、前置条件和需要等待的事项。
5. **验收结果：** 哪些条件已经通过，哪些仍未通过。
6. **交付物：** 文件、结果、链接、代码、报告或其他成果。
7. **问题与恢复：** 已发生的失败、处理措施和未解决风险。
8. **资源消耗：** 预算、模型调用、外部服务或运行时间等适用指标。
9. **操作控制：** 暂停、继续、取消、修改范围或请求进一步处理。

不必把全部内容一次性展开。默认突出当前状态、结果和用户需要处理的事项，其他内容按需查看。

### 3.4 长期目标页

每个长期目标应展示：

- 目标描述；
- 成功标准；
- 当前阶段；
- 已验证完成的里程碑；
- 正在执行的关联任务；
- 关键依赖和阻塞；
- 已知风险；
- 预算与期限；
- 下一步候选行动；
- 最近一次有意义的状态变化。

目标进度应由真实里程碑和验收证据计算或汇总。

如果无法合理量化完成度，应展示已完成事项、剩余事项和阻塞，不应强行生成一个精确百分比。

### 3.5 控制中心

控制中心负责用户对智能体运行行为的整体管理，建议分为：

- **自主执行：** 允许执行的任务类型、后台运行范围和停止条件；
- **权限与授权：** 已授权的工具、动作范围、有效期限和撤销入口；
- **预算：** 全局、目标和任务级预算及超限策略；
- **主动帮助：** 建议类型、提醒偏好、主动准备和后台发现规则；
- **设备与连接：** Android、Windows、个人服务器及同步状态；
- **运行健康：** 当前版本、最近异常、稳定性和恢复状态；
- **数据与隐私：** 日志保存、敏感信息处理、导出与删除策略。

控制中心不应要求用户理解内部模块的名称。所有设置应围绕用户可以控制的实际行为组织。

## 四、统一任务状态展示

### 4.1 正式状态与用户语言分离

界面应复用正式 Task 状态，不另造一个与后端不一致的执行状态系统。

建议映射如下：

| 正式状态 | 用户可见表达 | 需要说明的内容 |
|---|---|---|
| `created` | 已接收 | 任务已创建 |
| `classified` | 正在理解需求 | 仅在持续时间足以让用户感知时展示 |
| `planned` | 正在准备执行 | 必要时展示计划与待确认条件 |
| `running` | 正在执行 | 当前有意义的工作进展 |
| `waiting_approval` | 等待你确认 | 具体需要确认的动作与影响 |
| `recovering` | 正在处理问题 | 正在尝试的恢复方式及限制 |
| `verifying` | 正在验证结果 | 正在检查哪些验收条件 |
| `succeeded` | 已完成 | 展示验收结果和交付物 |
| `failed` | 未能完成 | 失败原因、已完成部分和后续选项 |
| `cancelled` | 已取消 | 已停止的工作及仍然存在的外部影响 |
| `needs_user` | 需要你处理 | 缺失信息、阻塞或需要用户决定的事项 |

短暂的内部状态不必频繁闪现。界面应合并过于细碎的状态变化，突出有实际意义的进展。

### 4.2 不能混淆任务状态与同步状态

移动端离线执行时，任务可能已经在本地完成，但事件尚未同步到服务端。

因此，界面应分别表达：

- 本地任务是否完成；
- 结果是否通过验收；
- 运行记录是否已同步；
- 远端是否已确认持久化。

不能因为网络请求成功就显示“所有数据已安全同步”。正式同步回执才是同步确认依据。

### 4.3 不能混淆执行完成与业务成功

工具返回成功、DAG 节点完成、文件生成或模型输出结束，都不一定意味着用户目标已经实现。

例如，代码已写入文件，但测试未通过；视频已合成，但画面质量不达标；手机操作已执行，但目标页面未达到预期状态。

界面必须展示实际验收结果，而不是仅展示执行器的完成状态。

## 五、进度透明度与执行解释

### 5.1 用户真正需要知道什么

每次重要状态变化，界面应尽量回答：

- 发生了什么；
- 为什么重要；
- 对最终结果有什么影响；
- 是否需要用户处理；
- 下一步会发生什么。

例如，与其显示“正在执行节点 7/18”，不如显示“主要镜头已生成，正在检查角色一致性；有两个镜头需要重新生成”。

技术节点数量可以在高级详情中查看，但不应成为默认的进度指标。

### 5.2 进度来源

优先采用：

- 正式任务事件；
- DAG 节点状态；
- 工具执行回执；
- 验收器结果；
- 文件和外部状态检查；
- 已确认的用户决策；
- 实际资源消耗。

模型生成的自然语言总结可以用于解释，但不能单独作为任务已经完成的证据。

### 5.3 计划变更透明度

如果任务执行过程中改变了计划，应说明：

- 原计划发生了什么问题；
- 为什么需要调整；
- 调整后有什么变化；
- 是否改变了范围、成本或风险；
- 是否需要用户确认。

局部、低风险且符合原始目标的调整可以自动执行；涉及重要范围变化、预算扩大或外部副作用的调整，应遵循相应授权规则。

### 5.4 解释执行，而非暴露全部内部推理

用户需要的是可验证的执行依据和决策解释，包括：

- 观察到的事实；
- 使用的工具或资料；
- 关键决策及其理由；
- 未解决的不确定性；
- 验收证据；
- 失败与恢复情况。

不需要把所有内部推理过程逐字展示给用户。透明度的重点是让用户能够判断行为是否合理、结果是否可靠，以及如何进行干预。

## 六、结果交付规范

### 6.1 统一交付结构

任务完成后，应根据任务类型形成统一的结果交付结构：

1. **结论：** 任务是否完成，以及最重要的结果。
2. **交付物：** 可直接使用的文件、内容、代码或操作结果。
3. **验收：** 哪些标准已经通过，哪些没有通过。
4. **限制：** 尚未解决的问题、假设和风险。
5. **后续建议：** 最有价值的下一步，必要时才展示。

简单任务不必机械地显示全部五个部分。复杂任务则应完整展示。

### 6.2 部分完成

如果任务只完成了一部分，应明确说明：

- 已经完成的内容；
- 尚未完成的内容；
- 未完成的原因；
- 已有成果是否可用；
- 继续完成需要什么条件。

不能为了让结果看起来完整而隐去失败或未经验证的部分。

### 6.3 交付物管理

交付物应具有清晰的名称、类型、版本和来源，并与任务及其验收结果关联。

适用时应支持：

- 在线预览；
- 打开或保存文件；
- 查看版本差异；
- 查看验收报告；
- 重新生成或继续处理；
- 定位产生交付物的任务记录。

文件链接和下载入口必须指向真实存在且已确认可访问的资源，不能仅凭模型生成的文件名创建虚假入口。

### 6.4 结果可追溯

重要交付物应能追溯到：

- 原始任务；
- 相关执行运行；
- 使用的组件版本；
- 关键输入与输出引用；
- 验收结果；
- 必要的授权记录；
- 相关修复或版本变更。

这使用户能够理解结果如何产生，并在发生问题时定位原因。

## 七、用户控制与操作语义

### 7.1 暂停

暂停应阻止后续可暂停的执行步骤，并在安全检查点保存状态。

界面应说明：

- 任务是否已成功暂停；
- 当前是否存在不可立即中断的操作；
- 已经产生的外部影响；
- 恢复时需要满足的条件。

点击暂停不应在尚未确认实际状态时就显示“已安全暂停”。

### 7.2 继续

继续执行前，系统应检查：

- 任务是否仍有效；
- 依赖是否可用；
- 预算是否足够；
- 组件版本是否兼容；
- 授权是否仍有效；
- 外部副作用状态是否明确。

如果条件发生变化，应先说明需要解决的问题，而不是盲目恢复。

### 7.3 取消

取消任务需要区分：

- 阻止尚未开始的步骤；
- 停止可安全中断的操作；
- 处理正在进行的外部操作；
- 保留已产生的成果；
- 必要时执行获准的补偿操作。

取消不能保证已经发送的消息、已提交的请求或其他外部副作用自动消失。界面应准确说明仍然存在的影响。

### 7.4 修改任务

允许用户修改：

- 目标；
- 输出格式；
- 范围；
- 优先级；
- 期限；
- 预算；
- 验收条件。

如果修改会影响已经完成的工作，应展示可能的返工和成本影响。

对于重要变更，应形成可追溯的任务契约更新，而不是静默覆盖原始要求。

### 7.5 授权与预算调整

授权应绑定具体动作范围、对象、权限和有效条件。

用户批准一个明确的动作，不代表系统获得对所有类似动作的无限授权。

预算调整应明确展示新增资源、适用范围和可能的总成本。不能因为任务尚未完成，就自动扩大预算。

## 八、通知与主动帮助体验

### 8.1 通知原则

通知应以用户行动价值为中心，而不是以后台事件数量为中心。

建议仅在以下情况优先通知：

- 需要用户确认；
- 重要任务发生阻塞；
- 出现影响结果的重大风险；
- 关键里程碑通过验收；
- 预算或期限达到预警条件；
- 任务需要用户提供信息才能继续。

普通节点完成、低价值发现和重复状态变化可以汇总到任务详情中。

### 8.2 通知与当前对话协调

如果用户正在与智能体讨论同一问题，系统应优先在当前对话中提供相关信息，避免同时产生重复通知。

用户已知晓的问题，不应因为后台重复检测而不断提醒，除非出现新的重要证据或风险变化。

### 8.3 主动建议的展示格式

高价值建议应尽量包含：

- 发现了什么；
- 为什么与当前目标有关；
- 预期收益；
- 可能成本与风险；
- 推荐的下一步；
- 是否需要授权。

每次展示应优先突出最重要的建议，而不是一次列出大量未经筛选的机会。

### 8.4 不要让主动帮助污染任务交付

任务交付内容必须优先展示。

额外建议应放在结果之后，并且与当前任务存在明确关联。

如果用户正在等待重要结果，主动帮助不能为了增加互动而延迟交付，也不能把完成当前任务所必需的工作拆成额外的可选建议。

## 九、Android 优先的交互设计

### 9.1 主要交互方式

Android 端应同时支持：

- 文字输入；
- 语音输入；
- 语音与文字结果；
- 文件与图片输入；
- 任务卡片与详情；
- 必要的系统通知；
- 获授权的手机操作状态展示。

语音任务结束后，应提供可阅读的结果摘要、交付物和必要的控制入口，不能只依赖一段语音播报。

### 9.2 手机端任务详情

优先展示：

- 当前状态；
- 最近一次有效进展；
- 是否需要用户处理；
- 最终交付物；
- 暂停、继续和取消等适用操作。

复杂的事件序列、版本信息和错误细节可以放在可展开的诊断区域。

### 9.3 权限引导

当任务需要无障碍、文件访问、通知或其他系统权限时，应解释：

- 为什么需要该权限；
- 权限会被用于什么动作；
- 不授权会有什么限制；
- 如何在系统设置中管理或撤销权限。

不应为了让任务尽快运行而隐藏权限用途或扩大授权范围。

### 9.4 离线状态

手机离线时，界面应明确区分：

- 本地可执行任务；
- 依赖云端而暂时等待的任务；
- 已完成但尚未同步的任务；
- 因权限、依赖或状态不确定而无法安全恢复的任务。

离线不是所有任务都失败的理由，也不是可以假装云端工作已完成的理由。

## 十、Windows 与个人服务器的协同

### 10.1 统一任务视图

Android、Windows 和个人服务器应展示一致的任务身份、目标关联和验收结果。

同一个逻辑任务不能因为在另一台设备恢复执行，就被展示成一个完全无关的新任务。

### 10.2 设备状态与任务状态分离

用户需要能够区分：

- 设备在线或离线；
- 任务是否正在运行；
- 运行所有权归属哪台设备；
- 任务是否等待同步；
- 当前结果是否已经验证。

设备离线不一定意味着任务失败；设备在线也不代表任务已经完成。

### 10.3 服务端不可用时

个人服务器或后续服务端不可用时：

- 本地任务视能力和授权继续执行；
- 不依赖服务器的基本交互仍应可用；
- 服务端独有的任务应进入明确的等待状态；
- 运行记录按离线策略本地保存；
- 重连后通过正式同步回执确认持久化状态；
- 恢复前对账未知的外部副作用。

不能把服务器可用性作为所有用户任务的共同前置条件。

## 十一、异常与失败的用户体验

### 11.1 错误信息必须可行动

错误展示应包含：

- 发生了什么；
- 对任务有什么影响；
- 系统已经尝试了什么；
- 当前是否安全；
- 用户需要做什么；
- 是否能够恢复；
- 是否存在已经产生的外部影响。

不应只显示内部异常栈或无法理解的错误码。

高级诊断中可以提供错误码和事件引用，但普通用户首先需要知道问题的实际影响与下一步。

### 11.2 自动恢复的透明度

当系统自动恢复时，应记录恢复尝试，并在恢复失败、风险变化或需要用户介入时进行说明。

成功恢复且不影响用户决策的低风险问题，可以在任务摘要中简要说明，不必对每次重试单独发出通知。

### 11.3 不确定状态

如果外部操作的实际结果尚不明确，应明确显示“正在确认执行结果”或“需要核实操作状态”。

不能因为没有收到成功回执，就断言操作一定失败；也不能因为超时，就直接重复一个可能产生外部副作用的操作。

## 十二、质量指标与用户体验评估

### 12.1 核心指标

| 指标 | 衡量目的 |
|---|---|
| 任务结果可理解率 | 用户是否能够理解最终结果 |
| 状态准确率 | 界面展示是否与真实执行状态一致 |
| 验收透明度 | 用户是否清楚哪些标准已通过 |
| 交付物可用率 | 交付物是否真实存在且可使用 |
| 控制操作成功率 | 暂停、取消、恢复等操作是否按约定生效 |
| 错误处理有效率 | 用户能否理解并解决阻塞 |
| 重复通知率 | 是否反复打扰用户 |
| 用户介入必要性准确率 | 是否只在确有必要时请求用户介入 |
| 任务状态追溯完整率 | 是否能够定位关键运行证据 |
| 主动建议实际收益 | 建议是否改善任务或减少遗漏 |
| 主任务交付时延 | 界面和主动功能是否拖慢交付 |
| 离线恢复正确率 | 断联与重连后状态是否正确 |

### 12.2 不应优化的虚假指标

以下指标不能单独作为成功标准：

- 页面访问次数；
- 用户查看日志的次数；
- 通知发送数量；
- 任务卡片数量；
- 计划步骤数量；
- 后台活动时长；
- 用户点击“继续”的次数；
- 未经验收的任务完成数量。

这些数字增加，可能意味着系统更复杂、失败更多或用户更难理解，而不一定意味着产品价值提升。

### 12.3 用户反馈闭环

用户可以对交付结果、状态展示、建议和异常说明提供反馈。

反馈应进入对应的质量分析流程，并区分：

- 任务本身执行失败；
- 结果正确但展示不清晰；
- 状态信息不准确；
- 控制操作没有按预期生效；
- 建议不相关；
- 通知时机不合适；
- 交付物不完整。

不能把所有用户不满都归因于模型能力，也不能仅靠改进文案掩盖真正的执行问题。

## 十六、完成判定

只有满足以下条件，才能认定本专项实施验收完成：

- 用户能够直接开始普通任务，而不必理解内部架构；
- 任务与长期目标具有清晰的区分和关联；
- 界面展示的状态能够追溯到真实运行证据；
- 用户能够理解任务是否真正完成以及验收结果；
- 部分成果、失败原因和未解决风险得到明确展示；
- 用户能够在允许的范围内暂停、继续、取消和修改任务；
- 授权与预算控制不会绕过正式执行治理；
- 主动帮助不会遮挡主要任务结果；
- 离线状态、同步状态与执行状态能够正确区分；
- Android、Windows 和个人服务器的任务身份保持一致；
- 关键交付物真实存在并可追溯；
- 用户体验优化不会以牺牲任务质量和状态真实性为代价；
- 所有关键验收场景均有真实执行证据。

**最终目标：让用户不必理解 EvoAgent 内部的复杂机制，也能够放心地把任务交给它；能够清楚知道发生了什么、取得了什么结果、还有什么问题，并且随时保有合理的控制权。只有当内部能力真正转化成可理解、可验证、可控制的用户价值时，EvoAgent 才从实验性智能体走向成熟的个人智能体产品。**</WritingBlock>

## 下一项专项：#93

建议继续推进 **#93：首次启动、能力引导、渐进式授权与用户信任建立**。

#92 解决了用户日常使用时如何看状态、拿结果和控制任务。#93 则解决用户第一次安装 EvoAgent 时，怎样在不被复杂配置劝退的情况下，逐步建立信任并开始使用。

重点包括：

1. 首次启动时，如何让用户理解 EvoAgent 能做什么、不能做什么；
2. 如何让用户通过一个真实任务体验核心价值，而不是先配置大量模型、工具和专家；
3. 如何按任务需要逐步申请 Android 权限；
4. 如何让用户理解本地执行、云端模型调用和后台任务的边界；
5. 如何让用户选择自主程度，而不是面对抽象的技术参数；
6. 如何在首次任务中验证工具、权限、模型和环境是否可用；
7. 如何解释失败、恢复和结果验收，避免建立不切实际的能力预期；
8. 如何让用户逐步启用长期记忆、主动帮助和后台执行；
9. 如何通过真实任务结果建立信任，而不是通过夸大的能力介绍建立信任。

我建议把 #93 作为下一步，因为产品是否容易上手，决定了前面所有架构能力能否真正被用户使用。**先让用户轻松完成一件真实的事，再逐步开放更强的自主能力。**
