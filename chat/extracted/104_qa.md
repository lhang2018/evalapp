# EvoAgent 第五十二专项：全局事件总线、运行可观测性与因果追踪

<text color="secondary" size="sm">GECO · Global Event & Causal Observability</text>

本专项继续沿着 EvoAgent 的总体架构向下设计，解决多专家、自进化控制器、任务 DAG、工具执行、记忆系统和多设备运行所带来的一个基础问题：

**系统如何知道自己实际做了什么、为什么这么做、哪里出了问题，以及怎样用可靠证据指导下一次改进？**

此前的 MEODT 已经定义了多个专家如何组队、分工、交接和恢复。CEKCE 定义了经验如何沉淀为可复用能力。SOCDEA 负责故障诊断，UQEAG 负责质量验收，SELCIA 负责受控进化。

但这些模块都依赖同一个前提：它们必须能够获取可信、完整、可关联的运行记录。

例如，一个编程任务失败了。最终结果只显示“测试未通过”，这远远不够。系统还需要知道：

- Router 为什么选择了编程专家 A，而不是专家 B？
- Planner 使用的是哪一版计划？
- AST 技能读取了哪个代码版本？
- 某个工具调用是否真正执行，还是只返回了超时？
- 测试失败发生在代码修改前还是修改后？
- 专家是否使用了过期的上下文？
- 是否存在另一个并行节点覆盖了文件？
- 系统为什么认为可以继续重试？
- 最终的失败究竟是代码缺陷、能力选择错误、任务依赖错误，还是恢复机制的问题？

如果这些信息分散在各个模块的普通日志里，系统即使积累了大量数据，也可能无法回答这些问题。

因此，建议将 GECO 定义为 EvoAgent 的**全局运行事实与可观测性基础设施**。

它不负责代替专家做判断，也不负责直接修复故障。它负责建立一套跨模块、跨任务、跨设备的统一事件与证据体系，使其他模块能够依据可追溯的事实进行分析、验收和改进。

本专项的核心原则是：

**所有重要运行事实都应可记录、可关联、可验证、可追溯；但时间上的先后关系不能直接当作因果关系，日志中的描述也不能直接当作已验证的事实。**

# 一、第一性原理：没有可信的运行事实，就没有可靠的自进化

EvoAgent 的进化闭环可以简化为：

\[
\text{执行}\rightarrow\text{观测}\rightarrow\text{诊断}
\rightarrow\text{验证}\rightarrow\text{改进}\rightarrow\text{再执行}
\]

这里最容易被忽视的是“观测”。

如果执行结果没有被准确记录，那么后续诊断就只能依赖模型对零散信息的猜测；如果诊断依据不完整，那么改进方案可能针对错误的根因；如果改进前后使用的评测环境不同，那么系统甚至无法确定是否真的进步。

因此，GECO 不是一个可有可无的日志模块，而是整个自进化体系的基础设施。

## 1.1 必须区分六种数据

<box border radius="xl" padding={3} gap={3}>
  {#each [
    ["事件 Event","某个离散事实发生了，例如任务被创建、工具调用返回或用户撤销授权。"],
    ["状态 State","某个对象当前处于什么状态，例如任务正在运行、已暂停或已完成。"],
    ["日志 Log","用于解释和调试的文本、结构化消息或运行细节。"],
    ["指标 Metric","经过聚合的数值，例如成功率、延迟、重试次数和单位任务成本。"],
    ["追踪 Trace","一组具有关联关系的执行活动，用于重建一次请求经过了哪些模块。"],
    ["因果关系 Causal Link","一个事件或条件对另一个结果存在经过证据支持的因果影响。"]
  ] as item}
    <box gap={1}>
      <title size="md">{item[0]}</title>
      <text color="secondary" size="sm">{item[1]}</text>
    </box>
    {#if item[0]!=="因果关系 Causal Link"}
      <divider color="subtle"/>
    {/if}
  {/each}
</box>

这六类数据相互关联，但不能混为一谈。

例如：

- 事件记录“测试失败”；
- 状态记录“任务处于验收失败状态”；
- 日志记录测试输出中的错误详情；
- 指标统计这类任务的失败率；
- 追踪展示代码修改、测试执行和验收之间的执行链路；
- 因果分析进一步判断失败是否由某次代码修改导致。

最后一步需要证据。不能因为代码修改发生在测试失败之前，就直接认定它是失败的根因。

## 1.2 GECO 的职责边界

GECO 负责：

- 定义统一事件协议；
- 采集并持久化关键运行事件；
- 关联跨模块的执行链路；
- 维护可重建的任务状态；
- 提供查询、追踪、指标和回放能力；
- 为 SOCDEA、UQEAG、CEKCE 等模块提供证据接口。

GECO 不负责：

- 决定任务目标是否值得执行；
- 代替安全系统批准操作；
- 直接决定专家如何分工；
- 代替 UQEAG 判定产物是否合格；
- 将相关性直接解释为因果关系；
- 自动把日志中的内容升级为可信知识。

这些边界是必要的，否则观测系统本身就会成为另一个拥有过多职责的智能体。

# 三、事件模型：所有重要模块必须使用同一套基本语言

建议建立统一的 `EventEnvelope`，作为所有运行事件的公共外层结构。

具体事件可以具有不同的业务载荷，但公共标识、时间、来源和关联关系应尽可能保持一致。

## 3.1 核心事件结构

| 字段 | 含义 |
|---|---|
| `event_id` | 全局唯一的事件标识 |
| `event_type` | 事件类型，例如 `tool.call.completed` |
| `schema_version` | 事件协议版本 |
| `producer_id` | 产生事件的模块、设备或运行实例 |
| `device_id` | 事件产生所在的设备 |
| `occurred_at` | 事件实际发生的时间，或来源报告的时间 |
| `recorded_at` | 事件被持久化记录的时间 |
| `sequence_id` | 同一事件流中的顺序标识 |
| `trace_id` | 所属执行追踪的标识 |
| `span_id` | 当前执行活动的标识 |
| `parent_span_id` | 当前活动的直接上游活动 |
| `goal_id` | 关联的目标标识 |
| `task_id` | 关联的任务标识 |
| `node_id` | 可选的 DAG 节点标识 |
| `team_id` / `member_id` | 可选的团队和成员标识 |
| `causation_id` | 直接触发当前事件的已知事件标识 |
| `correlation_id` | 用于关联同一业务过程的标识 |
| `payload` | 当前事件的具体业务数据 |
| `sensitivity` | 数据敏感级别与访问约束 |
| `content_ref` | 可选的外部产物或大数据载荷引用 |

不要求每个事件都具有全部业务标识。例如，系统启动事件可能尚未关联任务；用户消息接收事件可能还没有 `task_id`。

但一旦进入任务执行链路，相关标识就应逐步补齐。

## 3.2 为什么要同时记录发生时间与记录时间？

假设 Linux 主机离线执行了一个任务，数小时后才与 Android 同步。

如果系统只记录事件进入中央存储的时间，就可能误以为所有操作都在同步时发生。

因此，需要区分：

- 事件发生时间；
- 事件记录时间；
- 事件接收或同步时间。

不同设备的系统时钟也可能存在偏差，所以不能单靠时间戳重建严格的事件顺序。关键状态变更还需要依赖事件序列号、版本号、父子关系和执行器回执。

## 3.3 事件 ID 与任务 ID 必须分开

一个任务会产生大量事件，一个事件也可能关联多个业务对象。

例如，同一个 `task_id` 可能对应：

- 一次 Router 决策；
- 三个 DAG 节点；
- 十次工具调用；
- 两次失败恢复；
- 一次验收失败；
- 一次最终交付。

因此，`event_id` 必须标识单个事件，而 `task_id` 标识整个任务。

如果直接用任务 ID 作为事件 ID，就会丢失事件的唯一性，也无法正确处理重试、重复同步和状态变更。

# 四、事件分类：哪些事情必须被记录？

GECO 不能只记录异常和错误。对于自进化系统，成功路径同样重要，否则系统无法比较改进前后的执行过程。

建议建立统一的事件分类目录。

## 4.1 核心事件域

| 事件域 | 示例 | 主要用途 |
|---|---|---|
| `system.*` | 启动、关闭、恢复、健康状态变化 | 系统生命周期与运维 |
| `user.*` | 请求接收、目标变更、授权撤销 | 追溯用户意图和控制行为 |
| `goal.*` | 目标创建、评估、暂停、完成 | GVAAG 目标治理 |
| `router.*` | 候选专家、路由结果、拒绝原因 | Router 准确性评测 |
| `team.*` | 组队、分工、交接、冲突、成员退出 | MEODT 协作诊断 |
| `plan.*` | 计划创建、DAG 变更、节点依赖变化 | 计划执行追踪 |
| `expert.*` | 专家开始工作、提交结果、报告阻塞 | 专家级表现分析 |
| `tool.*` | 调用开始、成功、失败、超时、取消 | 工具可靠性与副作用追踪 |
| `artifact.*` | 产物创建、修改、版本提交、验证 | 产物版本与数据血缘 |
| `memory.*` | 记忆检索、压缩、引用、更新 | 记忆质量与上下文诊断 |
| `approval.*` | 请求批准、批准、拒绝、过期、撤销 | 授权审计 |
| `quality.*` | 验收开始、测试失败、验收通过 | UQEAG 质量证据 |
| `recovery.*` | 重试、检查点恢复、替代专家、回滚 | 故障恢复分析 |
| `capability.*` | 技能选择、版本使用、晋升、冻结 | CEKCE 能力治理 |
| `evolution.*` | 改进候选、评测、发布、回滚 | SELCIA 进化闭环 |
| `resource.*` | 预算预警、资源耗尽、限流 | MTSRIC 与 ARCBG 资源管理 |
| `security.*` | 权限拒绝、越权尝试、策略阻断 | 安全监控与审计 |

这些是逻辑事件域。实现时应建立稳定的命名规则、Schema 注册机制和兼容性策略，避免每个模块随意创造同义但不兼容的事件名称。

## 4.2 区分业务事件与调试日志

例如，工具执行过程中可能输出数百行调试日志，但真正影响任务状态的事件可能只有：

- 工具调用开始；
- 调用超时；
- 取消请求发出；
- 执行器确认停止；
- 工具返回结果；
- 产物校验失败。

业务事件应具有明确的结构和状态语义；调试日志可以保留更详细的执行信息，但不能取代这些关键事件。

## 4.3 建立关键事件清单

建议将事件分为三个采集等级。

<box border radius="xl" padding={3} gap={3}>
  <box gap={1}>
    <title size="md">E0 · 必须可靠记录</title>
    <text color="secondary" size="sm">目标与授权变更、任务状态转换、工具副作用、产物提交、验收结论、安全阻断、检查点创建、恢复与回滚结果。</text>
  </box>
  <divider color="subtle"/>
  <box gap={1}>
    <title size="md">E1 · 关键诊断事件</title>
    <text color="secondary" size="sm">路由候选与选择理由、计划变更、重试原因、专家交接、冲突处理、资源预警和能力选择依据。</text>
  </box>
  <divider color="subtle"/>
  <box gap={1}>
    <title size="md">E2 · 可配置的详细诊断数据</title>
    <text color="secondary" size="sm">高频调试输出、详细性能采样、低层执行日志和其他成本较高的诊断数据。</text>
  </box>
</box>

E0 和 E1 的具体字段可以按事件类型配置，但不能因为磁盘空间不足，就静默丢弃关键的授权与副作用记录。

如果系统无法保证关键事件已经持久化，应明确标记观测能力降级，并根据操作风险决定是否允许继续执行。

# 五、追踪模型：怎样重建一次任务的完整执行链路？

单纯拥有事件列表还不够。

GECO 需要能够将一条用户请求经过的所有模块、专家、工具和产物串联起来。

建议采用 `Trace → Span → Event` 的分层模型。

- `Trace` 表示一次完整的逻辑执行过程。
- `Span` 表示其中一个可独立追踪的操作阶段。
- `Event` 记录该阶段内发生的关键事实。

例如，一次代码修复任务可以形成这样的追踪树：

  </box>
</box>

实际执行时，某些 Span 可以并行发生，不能强制所有事件都形成一棵简单的树。跨专家协作、重试和多个产物依赖可能形成更复杂的关系图。

因此，建议同时维护：

1. **执行追踪树**：展示父子调用与阶段边界。
2. **任务依赖图**：展示 DAG 节点之间的依赖关系。
3. **产物血缘图**：展示某个产物由哪些输入、工具和版本生成。
4. **因果证据图**：展示已验证或待验证的原因与结果关系。

这四种图可以相互关联，但不能用一个简单的调用树代替所有关系。

## 5.1 失败诊断时应当能反向追踪

当测试失败时，系统应能够从失败事件向前追踪：

- 失败测试使用了什么代码版本；
- 该代码版本由哪个工具调用产生；
- 该调用使用了什么技能和配置；
- 计划为什么要求执行这一步；
- 哪个专家负责；
- 相关输入来自哪里；
- 验收依据是什么。

这种反向追踪能够让 SOCDEA 从最终失败快速定位到相关执行链路，避免重新扫描所有日志。

## 5.2 不要把追踪树当作因果证明

如果两个 Span 存在父子关系，只能说明它们在追踪结构中存在执行关联。

例如，Router 调用后触发 Planner，并不意味着 Router 的决策一定是后续失败的根因。

GECO 必须保留“执行关联”和“因果证据”之间的明确区别。

# 六、因果追踪：系统如何从“发生了什么”走向“为什么发生”？

这是 GECO 与普通日志系统最大的区别之一。

普通日志系统可以帮助开发者查看错误；GECO 还需要支持系统进行结构化根因分析，为 SOCDEA 提供证据基础。

但因果分析最容易犯的错误，就是把时间顺序、相关性或模型生成的解释当作已经证实的原因。

建议建立 `CausalEvidenceGraph`。

## 6.1 因果关系必须具有证据状态

每条候选因果关系至少应包含：

| 字段 | 含义 |
|---|---|
| `cause_ref` | 候选原因事件或条件 |
| `effect_ref` | 被解释的结果事件 |
| `relationship_type` | 依赖、触发、阻断、影响或其他关系 |
| `evidence_refs` | 支持该关系的日志、测试、产物或实验 |
| `confidence` | 诊断置信度及其依据 |
| `validation_method` | 如何验证该关系 |
| `status` | 候选、支持、已验证、被否定或未知 |
| `scope` | 在什么环境和条件下成立 |
| `analyst` | 提出或验证该关系的模块或流程 |

这里的 `confidence` 不能被解释为客观概率，除非该数值确实经过校准。对于缺少可靠统计依据的根因分析，应优先记录定性置信等级与具体证据。

## 6.2 区分四种关系

- **时间关系：** A 发生在 B 之前。
- **执行依赖：** B 必须等待 A 的输出。
- **统计关联：** A 和 B 在历史样本中共同出现。
- **因果关系：** 有证据支持 A 对 B 的发生具有实际影响。

例如，某类任务在使用新版本技能后失败率升高，这是一个重要的统计信号，但不能直接证明新版本技能是根因。

可能同时发生了模型切换、测试集变化或运行环境变化。

系统需要通过对照、回放、受控实验或其他适当方法，尽量区分这些因素。

## 6.3 根因诊断采用证据分级

建议使用以下状态：

- `HYPOTHESIS`：提出了候选解释；
- `EVIDENCE_SUPPORTED`：已有证据支持，但尚未充分验证；
- `VALIDATED`：通过适当验证，在指定范围内成立；
- `REFUTED`：已有证据反驳该解释；
- `INCONCLUSIVE`：证据不足，暂时无法判断。

例如：

“测试失败可能与 AST 重构后的代码变更有关”属于假设。

如果失败集中出现在重构涉及的函数上，并且差异分析支持该判断，可以升级为有证据支持。

如果通过受控回放证明旧版本代码在相同环境下通过，而新版本稳定复现失败，则可以在该测试条件下将原因验证到更高程度。

但即使根因被验证，也应保留其适用范围，不能直接推断它解释了所有类似失败。

## 6.4 让诊断结果能够影响后续改进

GECO 只提供事实、关联与因果证据。SOCDEA 根据这些信息形成根因判断，CEKCE 可以据此生成技能改进候选，SELCIA 再通过独立评测决定是否发布。

这样可以避免 GECO 直接将自己的统计结论写成全局规则。

# 七、事件存储与状态恢复：怎样保证任务历史可靠？

GECO 不能只保存一份容易被覆盖的“当前状态 JSON”。

对于长期运行的任务，系统需要知道当前状态，也需要知道状态是如何变化到现在的。

建议采用**事件记录为事实来源、状态快照为加速机制**的设计。

## 7.1 事件与状态快照的关系

假设某个任务经历了：

1. 创建；
2. 计划生成；
3. 开始执行；
4. 第一个节点完成；
5. 第二个节点失败；
6. 创建检查点；
7. 恢复执行；
8. 最终验收通过。

GECO 应当保留这些关键状态转换的事件，而不是只保留“任务已完成”。

与此同时，系统可以定期生成状态快照，加速任务列表展示和故障恢复。

状态快照是可重建状态的缓存，不应成为唯一的历史依据。

## 7.2 不必将所有数据都塞进事件日志

建议分开保存三类数据：

- **事件记录：** 发生了什么、何时发生、由谁产生、关联什么对象。
- **业务产物：** 代码、报告、视频、测试结果和其他文件。
- **派生视图：** 当前任务状态、统计指标、依赖索引和团队进度。

事件可以通过 `content_ref` 引用实际产物，而不必把大型文件直接写入事件存储。

这样可以避免事件库膨胀，也能独立管理文件版本、存储配额和访问权限。

## 7.3 事件记录与业务操作需要处理一致性

例如，代码文件已经修改成功，但进程在记录 `artifact.updated` 事件之前崩溃。

如果系统只依赖事件判断文件是否发生变化，就可能产生不一致。

建议对重要副作用采用以下模式：

1. 生成唯一的操作标识；
2. 在执行前记录操作意图；
3. 由执行器执行实际操作；
4. 获取执行结果或可验证的实际状态；
5. 记录操作结果事件；
6. 如果进程中断，通过执行器记录、产物版本和检查点进行对账。

这里的“操作意图”不是实际成功的证明。系统必须明确区分“计划执行”“已经尝试”“执行器报告成功”和“实际效果已经核验”。

对于无法确认的操作，应标记为状态未知，避免恢复时重复执行不可逆操作。

## 7.4 不同事件需要不同的一致性要求

并非所有事件都需要相同的持久化策略。

例如：

- 关键授权撤销、外部副作用和任务状态转换需要严格的可靠记录；
- 高频调试信息可以采用较低成本的采集策略；
- 统计指标可以从事件聚合得到，不必将每次指标计算都作为关键事实事件保存；
- 状态快照可以重新生成，但不能因此删除仍处于保留期内的审计记录。

对于 SQLite 等本地存储，可以通过事务、唯一约束和持久化队列实现基础可靠性；是否需要独立消息代理，应根据实际并发量、跨设备需求和运行负担决定。

**第一版不需要为了“全局事件总线”而引入复杂的分布式消息系统。**

# 八、跨设备与离线运行：没有中央服务器，事件体系还能工作吗？

可以，而且这应当是 EvoAgent 的默认设计目标之一。

你的部署方向是个人电脑、Android 和后续可能的微型 Linux 主机。因此，GECO 应支持每台设备独立记录本地事件，并在连接恢复后进行同步。

## 8.1 建立本地事件日志

每台设备至少需要：

- 本地事件序列；
- 唯一设备标识；
- 事件 Schema 版本；
- 本地持久化状态；
- 待同步事件队列；
- 同步游标；
- 重复事件去重机制；
- 本地时间与设备时钟信息。

当网络不可用时，任务执行节点仍可以记录本地运行事件。

如果某项关键事件无法可靠持久化，系统应根据风险决定是否暂停相关操作，而不是继续运行并假装所有操作都有完整审计记录。

## 8.2 同步不能简单地采用“最后写入者获胜”

假设 Android 记录任务已暂停，而 Linux 主机离线期间完成了一个节点。

两条记录不一定矛盾：任务可能在手机发出暂停请求后，主机才收到请求，因此该节点确实已经完成。

系统需要结合：

- 事件发生顺序；
- 设备本地序列；
- 任务状态版本；
- 控制请求的接收与生效记录；
- 执行器实际结果；
- 产物版本和检查点；

来重建真实过程。

不能仅根据同步到达时间覆盖状态。

## 8.3 同步机制必须支持重复投递

网络重试可能导致同一事件被发送多次。

因此，事件接收端应根据 `event_id` 或等效的幂等键进行去重。

但要注意：**事件去重不等于工具操作幂等。**

即使 GECO 只保存了一条 `tool.call.completed` 事件，也不能保证远端工具只执行过一次。

工具执行本身仍然需要 TERSO 管理操作标识、重试语义和实际副作用核验。

## 8.4 跨设备追踪需要统一逻辑关联

不同设备可以拥有独立的本地事件序列，但应当共享逻辑上的 `trace_id`、`task_id` 和相关产物标识。

这样，一次由 Android 发起、Linux 执行、Windows 进行人工接管的任务，仍然可以在恢复同步后形成统一的追踪视图。

## 8.5 设备离线时要明确观测盲区

如果 Linux 主机失去连接，Android 不能假装自己仍然能够实时观测主机上的所有事件。

界面应区分：

- 已确认的最后状态；
- 断联期间的未知状态；
- 已发送但未确认的控制请求；
- 恢复连接后待对账的事件。

这既是运行可靠性问题，也是 HACCG 用户控制权设计的一部分。

# 九、事件回放：怎样复现问题而不再次造成真实副作用？

事件回放是自进化系统的重要能力，但必须明确区分两种完全不同的操作：

- 重建过去发生了什么；
- 再次执行过去做过的事情。

前者通常是安全的只读分析，后者可能重新修改文件、调用 API、产生费用或发送外部请求。

因此，建议建立 `ReplayEngine`，并提供三种不同的回放模式。

## 9.1 三种回放模式

<box border radius="xl" padding={3} gap={3}>
  <box gap={1}>
    <title size="md">R1 · 历史重建</title>
    <text color="secondary" size="sm">根据事件、状态快照和产物版本重建原始任务状态。默认只读，不执行外部操作。</text>
  </box>
  <divider color="subtle"/>
  <box gap={1}>
    <title size="md">R2 · 模拟回放</title>
    <text color="secondary" size="sm">使用记录的工具结果、固定输入和虚拟执行器，重现计划、状态转换与诊断逻辑，不产生真实外部副作用。</text>
  </box>
  <divider color="subtle"/>
  <box gap={1}>
    <title size="md">R3 · 隔离重执行</title>
    <text color="secondary" size="sm">在沙箱或独立测试环境中重新运行相关步骤，用于验证候选修复。必须重新检查依赖、权限、预算与外部访问限制。</text>
  </box>
</box>

R1 适合追踪和审计；R2 适合测试 Router、Planner、状态机和故障恢复策略；R3 适合 SOCDEA 与 SELCIA 验证改进方案。

## 9.2 回放必须记录环境差异

相同输入在不同环境中可能产生不同结果。

因此，回放记录应包含：

- 模型与模型适配器版本；
- 专家与技能版本；
- 计划与配置版本；
- 输入产物版本；
- 工具及依赖版本；
- 运行时与操作系统；
- 关键随机种子或随机参数（如适用）；
- 外部数据的快照或引用；
- 与原执行环境之间的差异。

如果外部服务的响应没有被记录，系统可能无法精确复现原始任务。

这时应明确标记回放为近似重建，而不是宣称已经完整复现。

## 9.3 外部操作必须默认禁止自动重放

历史记录里可能包含发送消息、提交代码、修改文件、下单或调用付费服务等操作。

这些操作不能因为出现在历史轨迹中，就在回放时再次执行。

建议在 ReplayEngine 中默认使用只读数据和虚拟工具；任何真实副作用都必须经过独立的运行模式切换、授权与风险检查。

# 十、隐私与审计：完整记录不等于保存所有内容

GECO 需要足够完整的证据来支持诊断，但不能因此无限保存用户对话、私人文件、凭据和完整模型上下文。

对于个人智能体，数据最小化尤其重要，因为所有记录可能长期留存在用户自己的设备上。

## 10.1 采用分层存储策略

| 数据类别 | 建议策略 |
|---|---|
| 关键状态与授权事件 | 可靠持久化，按审计要求保留 |
| 普通执行事件 | 保留必要字段，支持按任务查询 |
| 调试日志 | 设置容量、期限和详细级别 |
| 大型产物 | 独立存储，事件只保留引用与版本 |
| 完整提示词和上下文 | 默认不全部复制到全局事件库，按必要性和权限保存 |
| 密钥、访问令牌、凭据 | 不写入普通事件与日志，必要时只记录安全的引用或脱敏标识 |
| 用户私有文件内容 | 采用最小必要采集、明确访问控制和可删除策略 |

## 10.2 记录事实，不等于记录所有原始内容

例如，Router 的路由事件可以记录：

- 选中了哪个专家；
- 使用了哪版路由策略；
- 候选能力及其排除原因；
- 路由依据的特征摘要；
- 最终任务是否成功。

这不意味着必须把用户完整对话、所有专家内部推理和整个上下文永久复制进事件库。

对诊断确有必要的内容，可以通过受权限保护的引用按需读取。

## 10.3 建立事件访问审计

GECO 自身也需要被治理。

系统应记录谁或哪个模块读取了敏感事件、访问了哪些产物，以及是否发生了导出或删除操作。

不同模块应当只获得完成职责所需的访问范围。

例如，资源监控模块通常只需要任务耗时、调用量和内存数据，不需要读取用户的完整私人对话。

## 10.4 删除与审计之间需要明确策略

某些历史记录可能因安全审计或任务恢复而需要保留，但用户私人内容也可能需要删除。

建议将事件元数据与大型敏感载荷分离存储，使系统能够按策略删除或加密销毁相应内容，同时保留不包含敏感内容的必要审计事实。

具体保留期限、删除范围和恢复能力应在产品隐私策略中明确，而不是由某个专家自行决定。

# 十一、运行指标：怎样知道 EvoAgent 整体是否越来越好？

GECO 不仅要支持单次故障诊断，还应提供跨任务的运行指标。

建议建立 `ObservabilityMetricCatalog`，让不同模块使用统一的指标定义。

## 11.1 基础运行指标

| 指标域 | 核心指标 |
|---|---|
| 任务质量 | 成功率、验收通过率、返工率、用户纠正率 |
| 路由质量 | 专家选择准确率、错误路由率、回退率 |
| 执行效率 | 端到端耗时、关键路径耗时、等待时间 |
| 工具可靠性 | 超时率、失败率、取消确认率、重试率 |
| 资源成本 | 模型调用量、Token 消耗、CPU、内存、GPU 与外部费用 |
| 恢复质量 | 检查点恢复成功率、重复副作用率、状态对账冲突率 |
| 能力表现 | 技能复用成功率、版本回归率、能力退役率 |
| 协作质量 | 交接失败率、重复工作量、冲突处理耗时 |
| 观测质量 | 关键事件缺失率、事件持久化延迟、追踪关联完整率 |

这些指标需要统一定义分母、统计窗口和排除条件。

例如，任务成功率必须明确：被用户取消的任务、因外部服务不可用而暂停的任务，以及未达到验收条件的任务，分别如何计入。

否则，不同版本的统计结果无法可靠比较。

## 11.2 必须保留任务类型和环境分组

全局平均值可能掩盖局部退化。

例如，整体成功率上升了，但代码重构任务的成功率下降；又或者 Windows 上运行稳定，Linux 上因为依赖问题频繁失败。

因此，关键指标应支持按以下维度分组：

- 专家类型；
- 任务类型；
- 技能版本；
- 模型版本；
- 设备与操作系统；
- 执行模式；
- 任务风险级别；
- 是否发生恢复；
- 是否使用多专家团队。

同时应设置最小样本量与不确定性提示，避免根据少量任务得出过度确定的结论。

## 11.3 指标不能直接替代诊断

例如，某个专家的失败率突然升高。

指标系统可以发现异常，但不能仅凭这一点就断言是专家能力退化。

真正原因可能是：

- Router 选择了更困难的任务；
- 模型版本发生变化；
- 新工具适配器引入缺陷；
- 测试集更严格；
- 设备资源不足；
- 用户改变了任务要求。

因此，指标用于发现问题，GECO 追踪用于定位相关执行链路，SOCDEA 再结合证据进行根因分析。

# 十二、与现有模块的协作边界

GECO 应当成为统一的观测基础设施，而不是另一个独立的决策智能体。

| 模块 | 与 GECO 的协作方式 |
|---|---|
| Router | 记录路由决策、候选专家、依据与结果 |
| Planner / DAG | 记录计划版本、节点依赖、计划变更与执行状态 |
| MEODT | 记录团队组建、交接、冲突和成员替换 |
| TERSO | 记录工具操作、实际结果、取消与副作用证据 |
| LTAR | 提供任务状态、检查点、恢复与生命周期事件 |
| ACMO | 记录上下文构建、压缩与信息引用的必要元数据 |
| MEEG / CLEK | 记录记忆检索、更新与知识来源引用 |
| UQEAG | 消费产物、测试与运行证据，生成验收事件 |
| SOCDEA | 消费追踪与因果证据，形成根因假设并进行验证 |
| CEKCE / CIL | 关联技能版本、复用表现、失败模式与能力候选 |
| SELCIA | 记录改进实验、评测结果、发布与回滚事件 |
| GVAAG | 消费历史成本、收益和失败数据，辅助目标评估 |
| HACCG | 展示可信进度、控制请求状态和用户可见的决策记录 |
| MTSRIC / ARCBG | 提供资源消耗、预算预警和调度事件 |
| CGVCM | 管理事件 Schema、接口契约与兼容性变更 |

建议所有模块通过统一 SDK、事件协议或受控接口产生和消费事件。

对于关键状态变更，不应依赖模型临时生成一段自然语言来推断发生了什么，而应由对应模块产生结构化事件，并明确事件的实际状态语义。

## 14.1 第一版的最小验收标准

建议先用一个真实的代码修复任务验证完整链路。

系统应当能够：

1. 记录用户请求和目标；
2. 记录 Router 的选择；
3. 记录计划版本与 DAG 节点；
4. 记录技能、工具和输入产物版本；
5. 记录测试失败及其证据；
6. 关联代码修改与回归测试；
7. 在任务恢复后还原关键状态；
8. 让 SOCDEA 查询相关执行链路；
9. 让 UQEAG 根据真实测试证据判定结果；
10. 在回放时不意外重新执行外部副作用。

只要这条链路可靠运行，GECO 就已经具备支撑自进化闭环的基础价值。

# 十五、下一专项：安全边界、信任体系与自进化治理

GECO 解决了系统如何观测和追溯运行事实的问题，但它也会让 EvoAgent 掌握越来越多的执行记录、工具结果、用户数据和内部能力资产。

与此同时，CEKCE 允许系统形成和复用技能，MEODT 允许多个专家协作，SELCIA 允许经过评测的改进进入运行环境。

这些能力组合起来，会产生一个必须单独解决的问题：

**当智能体可以创建技能、调用工具、跨专家共享信息、修改自身组件并长期运行时，如何防止错误、恶意输入或未经授权的改进突破系统的安全边界？**

建议将下一专项定义为：

**Trust, Security & Evolution Governance，简称 TSEG。**

重点研究：

1. 如何建立统一的身份、信任等级与权限体系；
2. 如何区分用户指令、外部数据、工具输出和智能体生成内容的可信程度；
3. 如何防止外部网页、文件、技能包和工具返回内容通过提示注入影响系统决策；
4. 如何限制专家、工作流、工具适配器和可执行技能的权限；
5. 如何隔离不同专家、不同用户数据和不同任务之间的敏感信息；
6. 如何防止技能通过组合调用间接获得未授权的能力；
7. 如何管理凭据、密钥、令牌和外部服务访问；
8. 如何确保自进化控制器不能自行修改安全规则、授权边界或发布门槛；
9. 如何检测能力供应链风险、依赖污染和不可信更新；
10. 如何处理安全事件、紧急阻断、凭据撤销和故障恢复；
11. 如何验证系统在离线运行、设备断联和同步恢复期间仍然遵守安全策略；
12. 如何建立独立的安全评测、红队测试和策略回归机制；
13. 如何在个人电脑、Android 和微型 Linux 主机的资源限制下实现实用的安全隔离；
14. 如何证明一项改进没有通过修改评测逻辑、隐藏事件或改变权限声明来绕过治理。

本专项的核心原则是：

**自进化系统可以提出修改自己的方案，但不能同时拥有不受约束地修改安全规则、批准修改并证明修改安全的全部权力。**

GECO 提供运行证据，SOCDEA 分析问题，CEKCE 管理能力资产，SELCIA 管理受控进化，而 TSEG 将定义它们都不能突破的安全边界。

这也是 EvoAgent 从“能够不断改进的智能体”，走向“能够在长期自主运行中保持可信、可审计、可撤销的智能体系统”所必须完成的基础专项。
