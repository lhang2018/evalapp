<WritingBlock id="58294" variant="document"># EvoAgent 专项设计 #79：发布后效果监测、退化检测与自动回滚治理

**专项编号：** #79

**英文名称：** Post-release Monitoring, Regression Detection & Automated Rollback Governance

**文档版本：** 1.0

**所属体系：** EvoAgent 自进化智能体专项设计集

**关联专项：** #75 兼容性治理、#76 依赖与变更影响传播、#77 回归测试与证据治理、#78 对照实验与收益归因

**设计状态：** 正式专项设计提案，待实施与验收。

## 一、专项目标

建立发布后的持续质量治理机制，使 EvoAgent 能够在新版本进入稳定通道后，持续判断其实际运行表现是否仍然符合预期。

本专项必须解决以下问题：

1. 如何识别新版本引入的质量、稳定性和效率退化？
2. 如何区分真实退化与正常的任务难度变化、网络波动和随机误差？
3. 如何识别影响范围，避免一个专家的问题导致整个系统停摆？
4. 哪些情况可以自动回滚，哪些情况必须立即停止相关动作？
5. 如何保证回滚本身不会破坏正在运行的任务？
6. 如何处理已产生外部副作用、数据迁移或不可逆操作的任务？
7. 手机与服务端断联时，如何在本地发现问题并执行安全限制？
8. 回滚后如何验证恢复成功，并将故障反馈到下一轮改进？

**核心目标：让 EvoAgent 不仅能够发布经过验证的改进，还能够在真实环境出现退化时及时发现、限制影响、恢复稳定状态，并保存完整的故障证据。**

## 二、设计原则

### 2.1 先保护用户任务，再保护候选版本

当候选版本出现严重问题时，系统不应为了维持实验完整性而继续执行危险动作。

优先顺序是：

1. 阻止新增的危险动作；
2. 保护用户数据与外部副作用；
3. 停止或隔离受影响的执行路径；
4. 恢复已验证的稳定配置；
5. 验证恢复后的任务状态；
6. 分析故障并决定后续修复。

### 2.2 回滚范围应当与故障范围匹配

如果只是旅游专家的路由策略出现退化，且依赖图能够证明其他专家不受影响，应优先回滚旅游专家相关配置，而不是关闭所有专家。

如果故障位于共享内核、任务状态机、权限控制或数据完整性机制，则可能需要扩大限制范围。

回滚范围由证据和依赖关系决定，不能固定采用全局回滚或局部回滚中的某一种策略。

### 2.3 回滚不等于撤销已经发生的现实动作

软件版本可以恢复，现实中的外部副作用未必可以撤销。

例如：

- 已经发送的消息不会因回滚而自动收回；
- 已经修改的文件不会因切换旧版本而自动恢复；
- 已经执行的手机操作不会因程序回滚而自动消失；
- 已经写入的数据可能需要独立的补偿或恢复流程。

因此，系统必须区分版本回滚、任务停止、数据恢复和外部副作用补偿。

### 2.4 后台进化与用户侧执行保持隔离

后台监测、实验和诊断不应无约束地修改正在运行的稳定任务。

候选版本的监测结论由独立的发布与运行治理模块处理，不允许候选自身决定是否继续发布。

## 三、整体架构与处理链路

发布后治理链路如下：

```text
稳定版本或灰度版本发布
          ↓
采集运行事件与质量指标
          ↓
按版本、专家、任务类型分组
          ↓
检测异常与指标退化
          ↓
判断严重程度与影响范围
          ↓
 ┌────────┼───────────┐
 ↓        ↓           ↓
继续观察  限制新任务    紧急停止受影响动作
 ↓        ↓           ↓
更新证据  局部回滚      安全隔离与应急处置
 └────────┼───────────┘
          ↓
验证恢复结果
          ↓
形成故障报告与回归案例
          ↓
进入下一轮独立诊断与优化
```

本专项定义检测、决策依据和恢复流程，不替代现有 Runtime Controller、Evaluation Gate Controller 或 Release Controller 的职责。

## 四、发布后监测对象

### 4.1 需要持续监测的对象

| 对象 | 监测重点 |
|---|---|
| 模型档案 | 任务成功率、结构化输出失败、时延、成本 |
| Router | 路由准确率、专家选择错误、回退比例 |
| Planner | 计划可执行性、无效步骤、重规划次数 |
| ReAct 执行循环 | 无进展循环、无效工具调用、重试次数 |
| 工具及适配器 | 调用成功率、超时、契约错误、异常副作用 |
| 领域专家 | 任务成功率、验收通过率、用户返工 |
| 工作流与 DAG | 节点失败率、恢复成功率、端到端时延 |
| 上下文与记忆策略 | 关键约束丢失、摘要错误、上下文冲突 |
| 共享通用内核 | 任务状态一致性、预算控制、取消与恢复 |
| Android 执行能力 | UI 识别失败、点击失败、权限错误、设备兼容性 |
| 发布与回滚控制 | 发布状态、健康检查、恢复完成率 |

监测对象必须关联具体资产版本与运行配置。

如果只知道某个任务失败，却无法确认它使用了哪个模型、专家和工具版本，就无法可靠判断故障是否由最近的发布引起。

### 4.2 核心质量指标

持续监测至少包括以下指标：

- 任务成功率；
- 最终产物验收通过率；
- 严重错误率；
- 工具调用成功率；
- 路由准确率；
- 恢复成功率；
- 任务异常终止率；
- 关键约束违反率；
- 用户返工率；
- 运行时兼容性故障率。

指标必须根据实际任务类型分别计算。

例如，手机操作任务的成功率应依据实际操作结果和状态验证，而不是仅依据模型是否输出“操作成功”。

### 4.3 效率与成本指标

- 端到端任务时延；
- 高分位时延；
- 每个成功任务的平均成本；
- 模型调用次数；
- 工具调用次数；
- 重试与恢复成本；
- 资源消耗；
- 失败任务消耗的资源。

如果调用次数下降，但任务失败率增加，不能直接将其判断为优化成功。

## 五、数据采集与观测链路

### 5.1 事件与指标的关联

继续复用正式数据契约中的 `task_id`、`run_id`、`event_id`、`runtime_manifest_id` 和资产版本。

每条关键事件应能够关联：

- 逻辑任务；
- 实际执行；
- 运行组件组合；
- 相关专家和工作流；
- 发生的错误或异常；
- 相关验收结果；
- 必要的日志和产物引用。

新增的发布监测记录应关联 `release_id`，从而区分不同发布批次。

### 5.2 采集事件类别

建议建立统一事件类别：

- `release.activated`：新版本开始生效；
- `release.health_degraded`：发布后健康指标退化；
- `runtime.quality_regressed`：任务质量指标出现退化；
- `runtime.compatibility_failed`：运行时发现兼容性问题；
- `runtime.safety_violation`：发现安全或权限违规；
- `rollback.requested`：提出回滚请求；
- `rollback.started`：开始执行回滚；
- `rollback.completed`：回滚完成；
- `rollback.failed`：回滚失败；
- `recovery.verified`：恢复结果经过验证。

这些是建议新增的逻辑事件类别，落地时应沿用现有 Runtime Event Schema 的版本管理规则，不直接假定现有事件枚举已经包含它们。

### 5.3 断联时的采集

Android App 与服务端断联时：

1. 将必要的运行事件写入本地持久化队列；
2. 为事件分配稳定的 `event_id`；
3. 保存任务和运行版本信息；
4. 本地执行适用的安全规则；
5. 网络恢复后按既有同步协议增量上传；
6. 通过服务端持久化回执确认同步结果。

网络连接成功不等于日志已经持久化成功。

如果服务端无法及时收到事件，客户端仍必须能够根据本地安全策略限制高风险操作。不能把在线监测当作本地安全控制的唯一保障。

## 六、退化检测机制

不能把任何一次失败都视为版本退化，也不能因为总体平均指标正常，就忽略某一类任务持续出现的严重错误。

### 6.1 三类检测方法

**第一类：硬规则检测。**

适用于能够明确判断的严重故障，例如：

- 未授权动作被执行；
- 必要权限检查被绕过；
- 任务状态发生非法转换；
- 非幂等外部操作被错误重复提交；
- 数据完整性检查失败；
- 发布版本与实际运行配置不一致。

此类问题不需要等待大量统计样本才能采取安全措施。

**第二类：基线对比检测。**

将新版本与已批准的稳定基线比较，观察任务成功率、错误率、成本和时延等指标是否出现显著变化。

比较时应控制任务类型、环境和数据分布差异。

**第三类：趋势与异常检测。**

观察指标是否持续恶化，例如：

- 工具超时连续上升；
- 恢复成功率持续下降；
- 特定专家的返工率逐渐增加；
- 某个模型版本的结构化输出错误持续增多。

趋势检测用于发现尚未达到严重故障阈值的问题，但不能替代明确的安全规则。

### 6.2 退化检测必须分层

检测结果至少应按以下维度分析：

- 发布版本；
- 专家；
- 工作流；
- 模型与工具组合；
- 任务复杂度；
- 任务风险等级；
- 设备与运行环境；
- 网络状态；
- 任务是否涉及恢复或外部副作用。

全局指标正常，不代表每个领域都正常。

### 6.3 基线不能随意漂移

候选版本发布后的质量基线必须明确。

如果系统不断使用最近的数据自动调整基线，可能逐渐把持续退化误认为正常状态。

因此：

- 稳定基线必须由独立治理流程批准；
- 新版本不能自行修改自己的质量门槛；
- 基线更新必须有版本记录和证据；
- 关键安全阈值不能通过普通趋势学习自动放宽；
- 任务分布变化时，应区分环境变化和版本退化。

## 七、退化等级与处置策略

建议定义四个运行治理等级。

| 等级 | 触发情况 | 处理策略 |
|---|---|---|
| L0：正常 | 指标处于批准范围 | 继续运行 |
| L1：观察 | 出现轻微或证据不足的异常 | 增加监测，收集更多证据 |
| L2：退化 | 关键质量指标持续恶化，或特定能力明显失效 | 限制新任务使用，启动调查或局部回滚 |
| L3：严重事件 | 发生安全违规、数据完整性风险或严重副作用 | 立即停止受影响动作，执行隔离与应急流程 |

具体阈值应按任务类型、风险等级和指标特征配置。

本专项不设定一个通用的固定失败率或固定样本数来决定所有专家的回滚。低频高风险故障和高频低风险错误必须采用不同的判断策略。

### 7.1 L1：观察

- 保留异常事件；
- 检查环境和任务分布；
- 扩大必要的监测样本；
- 不因为单次轻微异常就自动回滚；
- 若出现独立的硬性安全失败，立即升级处理。

### 7.2 L2：退化

- 停止扩大灰度范围；
- 评估受影响资产及其依赖；
- 根据风险限制新的任务准入；
- 对必要测试进行复验；
- 判断是否局部回滚；
- 向用户展示相关能力的真实受限状态。

### 7.3 L3：严重事件

- 立即阻止新增的危险动作；
- 对在途任务执行适用的安全停止策略；
- 识别受影响的任务、运行和资产；
- 隔离问题版本；
- 检查已提交的外部副作用；
- 根据可信回滚目标恢复稳定配置；
- 记录完整事件证据；
- 在验证恢复前禁止相关能力重新激活。

对于不可逆或状态未知的外部动作，必须优先对账，不得为追求快速回滚而盲目重放。

## 八、回滚范围与策略

### 8.1 回滚层级

| 层级 | 回滚对象 | 适用情况 |
|---|---|---|
| R1 | 单个资产 | 某个工具或提示词版本出现局部退化 |
| R2 | 单个专家或工作流组合 | 多个组件组合后出现问题 |
| R3 | 共享能力组合 | 共享工具、路由或上下文策略影响多个专家 |
| R4 | 共享内核或运行时版本 | 任务状态、安全控制或基础运行能力发生严重问题 |
| R5 | 全局发布组合 | 存在跨领域严重问题，且局部隔离无法充分控制风险 |

回滚范围应由依赖图、影响分析和安全风险决定。

### 8.2 回滚前置检查

正式回滚前，应确认：

- 目标版本存在；
- 目标版本未被撤销；
- 目标版本仍符合当前安全要求；
- 目标版本与当前 App、Core 和数据 Schema 兼容；
- 目标版本所依赖的工具仍然可用；
- 必要的配置和资源仍然存在；
- 回滚不会破坏当前任务的状态一致性；
- 必要的数据恢复或迁移方案已经明确。

如果历史版本已被确认存在严重安全缺陷，就不能仅因为它曾经稳定运行而恢复它。

### 8.3 回滚目标

回滚应使用明确的 `rollback_ref` 或等价的不可变发布引用，而不是简单切换到“上一个版本”标签。

正式发布记录应保存：

- 当前 `release_id`；
- 回滚目标；
- 回滚原因；
- 触发事件；
- 受影响资产；
- 相关运行；
- 回滚操作结果；
- 恢复验收证据。

### 8.4 版本回滚与数据回滚分离

应用配置回滚与数据恢复必须是不同的操作。

如果新版本已经写入了新的数据 Schema，旧版本可能无法直接读取这些数据。

因此，涉及数据迁移的发布应提前定义：

- 向后兼容策略；
- 数据迁移状态；
- 恢复目标；
- 必要的备份或重建机制；
- 回滚后的数据校验。

不能把恢复软件版本等同于恢复整个系统的历史状态。

## 九、自动回滚状态机

建议定义以下逻辑状态：

`MONITORING → SUSPECTED → CONFIRMED → MITIGATING → ROLLING_BACK → VERIFYING → RECOVERED`

异常分支包括：

- `BLOCKED`：回滚前置条件不满足；
- `ROLLBACK_FAILED`：回滚动作失败；
- `RECOVERY_FAILED`：回滚后验证失败；
- `ESCALATED`：需要更高权限或人工处理。

### 9.1 状态转换规则

**MONITORING → SUSPECTED**

监测系统发现异常指标或错误事件。

**SUSPECTED → CONFIRMED**

通过进一步证据确认退化，或触发无需统计确认的硬性安全规则。

**CONFIRMED → MITIGATING**

限制新增任务、停止灰度扩展或隔离受影响能力。

**MITIGATING → ROLLING_BACK**

确认回滚目标可用，且回滚范围符合风险要求。

**ROLLING_BACK → VERIFYING**

执行回滚并检查实际激活的资产与配置。

**VERIFYING → RECOVERED**

恢复后的健康检查、必要回归测试和状态一致性检查通过。

如果验证失败，则进入 `RECOVERY_FAILED`，不得仅因为回滚操作返回成功，就宣布恢复完成。

### 9.2 回滚幂等性

同一退化事件可能被多个监测节点重复发现。

系统必须通过稳定的事件标识和发布操作标识避免重复执行相互冲突的回滚操作。

如果重复请求到达，应返回当前回滚状态，而不是重复切换版本或重复执行数据恢复。

### 9.3 回滚权限隔离

候选版本和实验执行器不得拥有修改回滚目标、关闭严重告警或取消安全隔离的权限。

回滚控制器应独立于候选改进逻辑，并且在候选模型不可用时仍能执行必要的安全控制。

## 十、回滚后的恢复验证

回滚完成只是中间步骤，不是最终成功条件。

恢复验证至少包括：

1. 检查实际激活的 `release_id`；
2. 检查 `runtime_manifest_id` 与预期组件组合是否一致；
3. 确认问题版本不再接收新的相关任务；
4. 执行必要的健康检查；
5. 验证任务状态与数据完整性；
6. 对未知外部副作用进行对账；
7. 运行必要的回归测试；
8. 确认相关能力恢复到可接受状态；
9. 保存恢复报告。

如果系统恢复了旧版本，但外部服务依然故障，就不能仅凭版本切换成功认定问题已解决。

### 10.1 恢复后任务处理

对于已经失败或中断的任务，应分别处理：

- 可以安全继续的任务；
- 需要从检查点恢复的任务；
- 需要创建新运行的任务；
- 必须等待用户决策的任务；
- 因外部副作用不确定而需要对账的任务。

不得在恢复过程中自动重新执行所有失败任务。

## 十一、Android 与服务端断联策略

EvoAgent 采用手机优先战略，因此发布后治理必须考虑移动设备断联场景。

### 11.1 服务端在线

服务端负责：

- 汇总不同设备的运行指标；
- 分析跨任务和跨专家的退化；
- 运行统计分析；
- 管理候选发布和回滚策略；
- 下发经过批准的稳定配置。

手机端负责执行当前已批准的能力，并在本地执行必要的安全限制。

### 11.2 服务端离线

手机端必须：

- 持续记录必要事件；
- 检测本地可识别的硬性错误；
- 限制已知存在安全问题的能力；
- 使用当前已批准且仍然适用的稳定配置；
- 缓存需要同步的诊断证据；
- 不因无法连接服务端就允许未经验证的候选版本激活。

### 11.3 App 离线或重启

恢复时，应根据本地持久化任务记录、运行版本、检查点和副作用账本核对状态。

对于状态未知的外部操作，优先对账，不应直接重放。

### 11.4 恢复连接后

设备将新增事件增量同步到服务端。

服务端合并事件后，应检查：

- 是否存在重复事件；
- 是否存在缺失序列；
- 是否有尚未确认的关键副作用；
- 本地版本是否仍然允许使用；
- 是否存在需要进一步限制的能力。

如果设备在断联期间继续使用某个后来被撤销的版本，服务端应评估实际影响，并在重新连接后应用适当的安全策略。

## 十二、用户可见的降级与回滚体验

后台治理的最终目标是保护用户体验，而不是让用户理解复杂的发布系统。

### 12.1 普通退化

用户使用某项能力时，如果该能力暂时被限制，应展示：

- 当前能力状态；
- 简明的受限原因；
- 是否有替代执行路径；
- 任务是否仍在运行；
- 已完成成果是否保留。

### 12.2 严重问题

如果正在执行的任务因安全原因停止，界面应清楚说明：

- 任务已暂停或停止；
- 已完成的成果是否保留；
- 是否存在尚未确认的外部操作；
- 用户是否需要确认下一步。

不得将安全停止伪装成普通的网络等待或无关错误。

### 12.3 恢复完成

恢复后，系统可以告知用户相关能力已恢复，并说明受影响任务的当前状态。

只有在实际验证完成后，才能显示“已恢复”。

系统不应将内部候选版本、敏感运行日志或不必要的技术细节全部暴露给用户。

## 十三、故障归因与回归闭环

回滚的目的不仅是恢复稳定，还要减少同类问题再次发生。

### 13.1 故障处理流程

```text
发现退化
    ↓
保存事件与运行证据
    ↓
限制影响并回滚
    ↓
验证稳定状态
    ↓
独立诊断故障原因
    ↓
形成故障案例
    ↓
补充回归测试
    ↓
生成修复候选
    ↓
重新经过 #75—#78
    ↓
批准后重新发布
```

### 13.2 诊断与执行解耦

故障诊断器负责分析证据并提出原因假设，但不能直接修改稳定版本。

回滚控制器负责执行经过授权的恢复动作，但不能仅凭自身执行成功就判定根因已查明。

修复候选必须重新经过兼容性、影响分析、回归和收益验证。

### 13.3 防止重复事故

系统应记录：

- 故障类型；
- 触发条件；
- 受影响版本；
- 真实影响范围；
- 根因及其可信程度；
- 已采取的缓解措施；
- 修复内容；
- 新增回归案例；
- 后续观察结果。

如果根因仍不确定，应明确标记为未确定，而不是让模型生成一个听起来合理的解释就结束调查。

## 十四、关键验收测试矩阵

| 测试 ID | 场景 | 通过标准 |
|---|---|---|
| ROL-01 | 单个专家发生退化 | 只限制实际受影响的能力 |
| ROL-02 | 共享内核发生严重问题 | 扩大限制范围并保护核心任务 |
| ROL-03 | 单次轻微异常 | 不无条件触发全局回滚 |
| ROL-04 | 发生硬性安全违规 | 不等待统计样本，立即执行适用的安全处置 |
| ROL-05 | 监测系统重复发送回滚请求 | 不重复执行相互冲突的操作 |
| ROL-06 | 回滚目标已被撤销 | 不激活不安全的历史版本 |
| ROL-07 | 回滚后配置与预期不一致 | 不标记恢复成功 |
| ROL-08 | 软件回滚但数据 Schema 不兼容 | 触发数据恢复或阻止旧版本激活 |
| ROL-09 | 外部副作用状态未知 | 先对账，不盲目重放 |
| ROL-10 | 服务端断联 | 本地安全控制仍然有效 |
| ROL-11 | 手机重新联网 | 正确同步离线事件并核对版本 |
| ROL-12 | 候选版本不可用 | 独立回滚控制仍可执行 |
| ROL-13 | 回滚成功但外部服务仍故障 | 不错误宣称整体恢复 |
| ROL-14 | 恢复后的回归测试失败 | 能力继续受限并升级处理 |
| ROL-15 | 回滚后产生新故障 | 保存独立的后续事件与运行记录 |
| ROL-16 | 回滚后重新执行旧任务 | 根据任务状态、检查点和副作用账本决定是否允许 |
| ROL-17 | 新版本只影响特定任务类型 | 支持按任务类型和专家隔离 |
| ROL-18 | 退化来自任务分布变化 | 区分环境变化与版本退化，不直接做无依据的回滚 |
| ROL-19 | 监测数据缺失 | 对关键能力采取保守策略，不伪造健康结论 |
| ROL-20 | 发布后问题转化为回归案例 | 故障、修复和测试之间能够追踪关联 |

所有测试都需要真实执行并保存结果。文档定义完成不等于实施验收通过。

## 十五、关键监控指标

建议重点跟踪：

| 指标 | 目的 |
|---|---|
| 退化检测延迟 | 衡量问题被发现的及时性 |
| 严重故障止损延迟 | 衡量安全处置速度 |
| 回滚成功率 | 衡量回滚操作的可靠性 |
| 恢复验证通过率 | 衡量回滚后的实际恢复质量 |
| 回滚后再次退化率 | 识别恢复方案是否有效 |
| 误触发回滚率 | 发现监测规则过于敏感的问题 |
| 漏检退化率 | 发现监测覆盖不足 |
| 受影响任务数量 | 评估故障实际影响范围 |
| 单次故障资源损失 | 评估退化带来的成本 |
| 断联期间安全事件数 | 衡量移动端独立防护效果 |

指标应按专家、资产类型、版本、风险等级和环境分别分析。

不能只追求更少的回滚。回滚次数下降也可能是系统漏检了退化。

## 十六、与正式数据契约的衔接

本专项优先复用以下正式对象：

- `release_id`：标识正式发布；
- `runtime_manifest_id`：固定实际运行组件组合；
- `task_id` 和 `run_id`：定位受影响的任务与运行；
- `event_id`：关联退化和恢复事件；
- `asset_id + version`：定位具体资产版本；
- `rollback_ref`：关联资产的回滚目标；
- `evaluation_evidence_refs`：关联验证证据；
- Side-effect Ledger：核对外部副作用状态。

建议新增的发布后监测报告、回滚操作记录和恢复验证报告，应与现有数据契约协调设计。不能因为新增一个监测服务，就重复创建任务、资产和发布的身份体系。

## 十八、完成判定

只有满足以下条件，才能认为本专项实施验收完成：

1. 运行指标能够关联到准确的发布版本和实际执行组合；
2. 系统能够识别硬性安全错误与统计性退化；
3. 退化检测能够按专家、任务类型和风险等级分层；
4. 回滚范围能够依据依赖关系和故障证据确定；
5. 回滚目标经过兼容性与安全检查；
6. 回滚操作具有幂等性和可追踪记录；
7. 软件回滚、数据恢复和外部副作用补偿相互区分；
8. 回滚后必须验证实际恢复结果；
9. 服务端断联时，本地必要安全控制仍然有效；
10. 故障能够反馈至独立诊断和回归测试体系；
11. 候选版本无法自行取消监测、修改回滚目标或宣布恢复成功；
12. 所有关键验收测试都有真实执行证据。

**最终目标：让 EvoAgent 的稳定性不再依赖“希望新版本不会出问题”，而是依赖持续监测、明确止损边界、可靠回滚和可验证的恢复机制。即使进化过程引入了新的问题，系统也能尽可能限制影响范围，保护用户正在进行的任务，并将故障转化为下一轮有证据支撑的改进。**</WritingBlock>
