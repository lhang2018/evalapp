## 一、产品体验的核心原则

EvoAgent 的交互设计必须遵守六条原则。

1. **用户表达目标，系统负责执行。** 用户不需要理解专家路由、ReAct、DAG 或模型配置。
2. **能直接完成的任务，不要增加流程。** 简单问题直接回答，复杂任务才展示计划和进度。
3. **执行过程可信，最终结果可验证。** 不用虚假的进度和完成提示掩盖实际问题。
4. **用户始终能够控制任务。** 重要操作可以确认，执行可以取消，失败可以查看和恢复。
5. **主动帮助有价值，但不强行打扰。** 优先完成主任务，额外帮助默认可忽略。
6. **系统进化不能牺牲当前体验。** 后台优化与用户任务隔离，更新需要验证、可追溯、可回滚。

产品应当给用户一种明确的感受：我不必管理一个复杂的软件系统，只需要告诉它我想做什么，并且能够检查它是否真的做好了。

## 三、首次启动：让用户快速获得第一次成功

### 3.1 欢迎页面

用户首次打开 App 时，应当看到产品价值，而不是架构说明。

建议的欢迎文案：

> 告诉我你想完成什么。我会尽可能帮你完成任务、检查结果，并在遇到需要你决定的事情时及时询问。

页面只需要三个主要入口：

- 开始使用；
- 了解隐私与权限；
- 查看当前支持的能力。

不要求用户在首次启动时配置专家、模型、工作流和进化策略。

### 3.2 必要设置

首次设置应当尽量精简。

| 设置项 | 首次启动要求 |
|---|---|
| 基本交互偏好 | 提供默认值，允许稍后修改 |
| 模型服务配置 | 如果运行依赖用户配置的 API，则明确提示并验证连接 |
| 隐私与数据使用 | 清楚说明数据来源、处理方式和保留规则 |
| Android 权限 | 仅在实际使用相关功能时申请 |
| 主动智能 | 默认采用低打扰策略 |
| 离线能力 | 明确说明哪些功能可离线使用 |

不能因为用户完成了首次启动，就推定用户已经授权访问文件、通知、无障碍服务或其他应用数据。

### 3.3 首次体验任务

建议在首页提供一个可跳过的示例任务，例如：

“帮我把一段文字整理成一份结构清晰的摘要。”

示例任务的目标不是展示所有能力，而是让用户在短时间内体验完整闭环：

1. 输入目标；
2. 系统完成处理；
3. 展示结果；
4. 用户可以修改、复制或保存成果。

如果示例使用模拟数据，必须明确标记为演示；不能将模拟结果冒充真实工具执行。

**验收标准：** 新用户无需理解内部架构，就能完成第一次任务并找到交付结果。

### 4.2 首页行为规则

- 默认输入框是主要操作入口。
- 普通问答不需要用户选择专家。
- 用户明确要求执行多步骤任务时，系统自动进入相应工作流程。
- 正在执行的任务可以继续查看，但不应占据整个首页。
- 待处理事项必须来自真实任务状态、明确的用户授权或可信的事件。
- 没有高价值主动建议时，不展示空洞的推荐内容。

### 4.3 语音交互

语音输入应当与文字输入共用同一任务入口。

语音转写完成后，系统按照任务的风险和歧义决定是否直接执行。

例如：

- “解释一下什么是 AST。”直接回答。
- “把这几份资料整理成报告。”进入文件处理流程。
- “替我发送这条消息。”如果具备对应能力，则按照操作风险和授权要求处理。

语音输入本身不构成执行外部操作的额外授权。

## 五、任务执行过程：用户只需要关注关键节点

### 5.1 简单任务

对于不需要复杂规划的任务，直接回答或交付结果。

不应为了展示智能体能力，强行展示任务计划、专家名称、工具列表和冗长的执行日志。

### 5.2 复杂任务

对于研究、文件制作、代码修改或多步骤操作，可以展示一份简明计划。

例如：

**任务：生成项目研究报告**

1. 整理现有资料。
2. 识别关键问题和证据缺口。
3. 形成报告结构并撰写内容。
4. 检查关键结论与格式。
5. 交付最终文件。

系统应当根据实际执行动态更新步骤，而不是把最初计划当作不可改变的固定流程。

### 5.3 执行期间的用户控制

用户在任务执行过程中应当能够：

- 补充目标和约束；
- 查看当前进度；
- 取消任务；
- 处理授权请求；
- 查看已经产生的中间成果；
- 在允许的情况下暂停或继续任务。

任务发生实质性变化时，系统需要重新评估计划、成本、权限和验收标准。

用户不应需要理解底层错误码才能知道下一步怎么做。

### 5.4 进度表达

进度展示必须以实际状态为依据。

推荐使用：

- 正在分析任务；
- 正在整理资料；
- 已完成资料整理；
- 正在生成文件；
- 正在检查结果；
- 等待你确认；
- 暂时遇到问题，正在尝试恢复。

只有当系统能够计算可靠进度时，才展示百分比。否则，显示当前阶段和已完成步骤，比一个不准确的百分比更可信。

## 六、授权与风险控制：只在必要时打断用户

### 6.1 授权原则

授权界面应当回答三个问题：

1. 系统具体想做什么？
2. 为什么需要这项操作？
3. 如果同意，可能产生什么影响？

例如，系统可以说明将要在哪个应用中执行哪项操作，以及操作是否会对外发送信息或产生不可逆结果。

### 6.2 减少无意义的确认

低风险、可逆且已在授权范围内的操作，可以按照预先设置的策略自动执行。

但涉及对外发送、删除、支付、重要提交等高风险动作时，必须按照适用的权限和审批规则处理。

不能为了追求“高度自主”而把所有操作都自动放行，也不能为了安全而要求用户确认每一个无风险的小步骤。

### 6.3 授权失败或用户拒绝

当用户拒绝授权时，系统应当：

- 停止相关的受保护动作；
- 保留已经合法完成的工作；
- 提供不需要该权限的替代路径；
- 清楚说明当前任务还能完成哪些部分。

拒绝一项授权，不应导致整个应用失去基本可用性。

## 七、结果交付：让成果成为体验的中心

### 7.1 结果页面

任务完成后，结果页面应当优先展示实际产物，而不是执行过程。

根据任务类型显示：

- 文本或摘要；
- 文档、表格、代码或其他文件；
- 研究报告及来源；
- 实际操作结果；
- 验收通过情况；
- 未完成事项与限制；
- 适当的下一步建议。

### 7.2 三种交付状态

**已完成：** 所有必需的验收条件均满足。

**部分完成：** 有可用成果，但仍有未完成的目标或未通过的验收项。

**未完成：** 没有达到任务的最低完成标准，或者执行被阻塞。

这三种状态必须清楚区分。不能因为系统已经生成一份文件，就认为报告中的事实、格式和内容都已经通过验收。

### 7.3 交付后的操作

用户可以：

- 打开或保存成果；
- 继续修改；
- 要求重新生成某个部分；
- 让系统检查遗漏；
- 将经过验证的流程保存为候选工作流；
- 结束任务。

用户要求修改成果时，应尽量基于现有结果继续，而不是无理由地从头执行全部步骤。

## 八、失败体验：让错误成为可恢复的状态

失败不可避免，但失败不应该让用户失去控制。

### 8.1 失败分类与用户提示

| 问题 | 用户看到的解释 | 系统后续行为 |
|---|---|---|
| 输入不完整 | 还缺少一项关键信息 | 询问必要问题 |
| 网络不可用 | 当前无法连接所需服务 | 使用可用离线能力或等待重连 |
| 工具执行失败 | 某一步没有成功完成 | 检查错误并判断是否能安全重试 |
| 权限不足 | 需要你授权某项操作 | 请求授权或提供替代方案 |
| 验收失败 | 结果还不符合要求 | 尝试修复或明确剩余问题 |
| 预算耗尽 | 已达到本次任务的资源限制 | 停止新增调用，展示已有成果 |
| 状态无法确认 | 无法确定某项外部操作是否已经生效 | 先核对状态，不盲目重放 |

### 8.2 恢复策略

系统应优先尝试风险可控、成本合理的恢复方法，例如：

- 修正工具参数；
- 重新规划未完成步骤；
- 更换兼容的工具；
- 从可靠检查点继续；
- 在安全条件下有限重试；
- 将任务转为等待用户处理。

无法恢复时，应保留已经完成的部分，明确说明失败点和下一步选项。

### 8.3 用户不应该看到的行为

- 无限制重试却不告知用户；
- 任务失败后丢失全部中间成果；
- 取消后继续创建新的外部动作；
- 仅凭模型自述就宣称外部操作成功；
- 通过隐藏错误来维持“任务成功率”。

## 九、长期使用：从聊天记录变成连续工作

EvoAgent 的长期价值不仅在于记住历史，而在于帮助用户持续推进事情。

### 9.1 项目空间

用户可以创建或自动归集相关项目，例如：

- 长期研究主题；
- 正在开发的软件；
- 持续制作的内容；
- 需要跟进的个人事务。

项目空间包含目标、已确认决策、重要约束、相关任务、已交付成果和待解决事项。

自动归集的结果应允许用户纠正。系统推断的项目关系不能直接当作已确认事实。

### 9.2 继续上次的工作

当用户说“继续上次的项目”时，系统应当：

1. 识别可能对应的项目或任务；
2. 检查最近状态与未完成事项；
3. 恢复必要上下文；
4. 如果存在多个合理候选，询问用户；
5. 在确认当前目标后继续工作。

系统不应只恢复旧对话文本，还应恢复必要的任务状态、版本信息和约束。

### 9.3 工作流复用

当同类任务反复执行成功后，系统可以提出保存为工作流的建议。

工作流需要经过独立测试才能进入稳定资产库。用户可以查看其输入、执行范围、依赖和验收标准，并随时停止或回滚不合适的版本。

## 十、主动帮助：在正确的时间提供额外价值

主动帮助分为三类。

### 10.1 当前任务的额外价值

用户要求生成一份报告时，系统可以发现缺少的证据、明显的逻辑矛盾或更合适的交付方式。

如果问题影响主任务的正确性，应在必要时及时处理或澄清；如果只是额外增强，则优先在主任务完成后提出。

### 10.2 近期工作整理

在用户授权的范围内，系统可以整理近期讨论，形成：

- 已完成事项；
- 当前重点；
- 尚未解决的问题；
- 相关资料；
- 可行的下一步。

它不应默认读取所有应用、所有通知或所有历史资料。

### 10.3 主动机会提醒

只有在机会明确、价值较高且时机合适时才展示建议。

例如：

“你之前整理的资料已经足够形成一份初步方案。如果你愿意，我可以把它转化为带有优先级和时间安排的行动计划。”

建议必须与用户当前目标相关，而不是为了显得主动而不断推荐无关功能。

### 10.4 用户控制

用户应当可以：

- 关闭主动帮助；
- 降低建议频率；
- 选择允许分析的项目或数据源；
- 关闭某类建议；
- 设置额外分析的资源限制。

关闭主动帮助后，核心任务执行、结果验证和正常的错误提示仍应工作。

## 十一、后台进化：用户不用管理，但系统必须可追溯

后台进化不是面向普通用户的主界面功能，而是改善产品质量的基础设施。

### 11.1 后台能够做什么

- 分析失败任务和工具异常；
- 识别重复出现的问题；
- 生成提示词、路由或工作流的候选改进；
- 运行隔离的回归评测；
- 比较候选与稳定版本的质量、时延和成本；
- 提出发布或回滚建议。

### 11.2 后台不能做什么

- 绕过评测门禁直接发布；
- 自行扩大用户授权；
- 在主任务运行期间任意切换关键版本；
- 因后台分析失败而影响用户任务；
- 在没有证据的情况下宣称系统已经进化成功。

### 11.3 用户应该感受到的变化

随着系统持续运行，用户应当看到同类任务更稳定、重复纠错减少、失败恢复更快、执行成本更合理。

用户不必每天查看后台实验记录，但系统应提供必要的版本信息、重要改进摘要和问题追溯能力。

## 十二、通知和打扰管理

通知不是越多越好。

建议按以下优先级处理：

1. **必须处理：** 任务需要用户授权、关键风险需要确认。
2. **与用户目标直接相关：** 用户明确设置的待办、任务完成、重要项目阻塞。
3. **可选增强：** 一般性的资料建议、工作整理、效率提升机会。

第三类通知应当默认低频，并尽量在用户合适的时间或进入 App 时展示。

用户拒绝或关闭某类建议后，应降低同类建议再次出现的频率。

主动提醒的效果不能只用点击率衡量，还要关注无关提醒比例、关闭率、用户实际收益和对正常工作的干扰。

## 十三、隐私、数据与设备边界

首发产品必须清楚区分：

- App 自己产生的任务记录；
- 用户主动提供的资料；
- 用户明确授权读取的数据源；
- 外部模型或服务实际接收的数据；
- 后台诊断和评测需要保留的数据。

应当遵守数据最小化原则。

离线时，App 继续提供已经验证的本地能力，并保存必要的任务状态和事件。需要云端模型或远程工具的任务则明确显示等待、受限或不可用状态。

重新联网后，系统按幂等规则同步事件，并核对可能存在的外部副作用。不能因为客户端重新连接，就直接重放所有未确认动作。

## 十四、用户体验验收清单

| 编号 | 验收项目 | 通过标准 |
|---|---|---|
| UX-01 | 首次启动 | 用户不必先配置复杂技术参数即可开始使用 |
| UX-02 | 首次成功 | 用户能完成一次真实任务并获得实际成果 |
| UX-03 | 统一入口 | 不同领域任务不要求用户手动理解内部路由 |
| UX-04 | 执行进度 | 显示的状态与实际运行状态一致 |
| UX-05 | 用户控制 | 任务能够按规则取消、等待、恢复 |
| UX-06 | 授权 | 受保护动作未获必要授权时不会执行 |
| UX-07 | 结果交付 | 成果可访问，验收状态清晰 |
| UX-08 | 失败恢复 | 错误有明确解释和可行的后续选项 |
| UX-09 | 长期项目 | 能恢复必要上下文，不把过时状态当作当前事实 |
| UX-10 | 主动帮助 | 额外建议非阻塞、可关闭且有依据 |
| UX-11 | 资源隔离 | 后台活动不破坏核心任务的资源与时延门槛 |
| UX-12 | 版本透明 | 关键运行和发布信息可以追溯 |
| UX-13 | 离线体验 | 不支持的操作明确说明限制，不伪造成功 |
| UX-14 | 隐私控制 | 用户能够理解并控制授权范围与数据使用 |

只有经过实际测试的项目才能标记为通过。界面设计完成不等于用户体验验收完成。

## 十五、首发产品的交付顺序

### 阶段一：第一次成功

完成首页、任务入口、真实任务执行、结果交付、基础状态显示和错误提示。

目标是让用户可以开始使用并完成真实任务。

### 阶段二：可靠工作

完善任务历史、取消、恢复、审批、预算控制、结果验收和诊断追溯。

目标是让用户可以把多步骤工作交给系统，而不必全程监督每个细节。

### 阶段三：连续工作

增加项目空间、长期上下文、工作流复用和必要的离线恢复能力。

目标是减少重复解释和重复执行。

### 阶段四：主动帮助

开放完成后增强、项目整理、待办跟进和可配置主动提醒。

目标是让智能体在不打扰用户的前提下，创造额外价值。

### 阶段五：受控进化与能力扩展

逐步开放独立评测、候选版本自动晋级、更多领域专家和跨端能力。

目标是让真实任务的完成质量、效率与稳定性持续提高。

以上阶段定义的是实施顺序，不意味着所有阶段都必须串行开发。可以并行开发，但依赖关系和发布门禁必须保持清晰。

## 最终设计结论

EvoAgent 的用户体验不应该是“用户向智能体发出指令，然后观察它思考”。

更合理的体验是：

**用户提出目标，EvoAgent 负责把工作推进到可以交付的状态；遇到必须由用户决定的事情时才请求介入；完成后交付可验证的成果；在获得授权且确有价值时，再主动提供下一步帮助。**

这条体验主线必须贯穿普通对话、复杂工作、领域专家、主动智能和后台进化。只有这样，技术能力的持续增长才会真正转化为用户价值。
