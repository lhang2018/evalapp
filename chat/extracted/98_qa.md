# EvoAgent 第四十六专项：系统可观测性、因果诊断与进化效果归因

本轮继续深入 EvoAgent 的自进化核心：系统运行后，如何从海量日志、任务结果、版本变化和失败案例中，准确判断问题发生在哪里，为什么发生，以及修改之后是否真的变好了。

此前已经讨论了专家路由、上下文设计、记忆系统、任务 DAG、ReAct、Plan、长期任务恢复、多任务调度、工具运行时、安全治理和版本兼容。

这些模块相互影响，意味着一个失败结果通常不能直接归因于某个模块。

例如，一次代码任务失败，可能源于路由错误，也可能是上下文压缩遗漏了需求、规划遗漏了测试节点、工具执行超时，或者验收标准设置错误。甚至可能是几个小问题共同造成的。

因此，本专项建议定义为：

**System Observability, Causal Diagnosis & Evolution Attribution，简称 SOCDEA。**

它负责建立跨模块观测、运行轨迹关联、根因假设生成、诊断实验、改进效果归因和独立评测机制。

最重要的设计原则是：

**执行系统负责完成任务，诊断系统负责解释任务表现，进化系统负责验证并实施改进。这三个职责需要协作，但不能相互替代。**

## 一、第一性原理：不能从结果直接跳到根因

假设某次任务失败，系统记录到以下事实：

- 用户要求修改一个项目；
- Router 选择了编程专家；
- Planner 创建了六个 DAG 节点；
- 上下文压缩后长度减少了 60%；
- 第四个节点运行测试失败；
- 工具返回退出码非零；
- 最终任务未通过验收。

这些是可观察的事实，但它们并没有直接证明根因。

例如，上下文压缩比例较高，并不代表关键约束一定丢失；测试失败也可能是代码本身有问题，而不是工具运行时异常。

建议把诊断过程分成四个层次。

  {#each [
    ["第一层：事实","系统实际记录了什么？包括输入、输出、状态、耗时、资源消耗与版本信息。"],
    ["第二层：异常","哪些观测值偏离了正常范围或任务预期？"],
    ["第三层：根因假设","哪些上游因素可能解释这些异常？每个假设有什么支持与反对证据？"],
    ["第四层：因果验证","通过回放、对照实验、故障注入或其他可检验方法，判断哪个因素确实影响了结果。"]
  ] as item}

      {item[1]}

    {#if item[0]!=="第四层：因果验证"}

    {/if}
  {/each}

并不是每个问题都需要进行严格的因果实验。明显的程序异常可以通过堆栈和错误码直接定位；但涉及模型能力、路由策略、上下文压缩和任务质量的复杂问题，通常需要更谨慎的归因。

系统必须明确区分：

- 已确认的事实；
- 有证据支持的推断；
- 尚未验证的假设；
- 当前证据无法判断的部分。

不能把模型生成的解释直接写成已经确认的根因。

# 二、总体架构：建立独立的诊断与归因控制层

建议 SOCDEA 不直接嵌入某个专家，也不与执行过程共享全部控制权，而是作为横跨各模块的诊断层。


    <title size="md">执行系统</title>
    Router、专家、Planner、DAG、工具运行时、记忆、调度与验收。



    统一事件、指标、版本与结果证据


    <title size="md">SOCDEA 可观测性层</title>
    统一事件模型、运行轨迹、指标、异常检测与跨模块关联。





    <grid-item>

        <title size="sm">诊断引擎</title>
        故障分类、根因假设、证据与不确定性。

    </grid-item>
    <grid-item>

        <title size="sm">因果验证引擎</title>
        回放、对照、消融实验与故障注入。

    </grid-item>





    <title size="md">独立评测与进化治理</title>
    将验证结果交给 EQEAG、RCAE 与 SELCIA，决定是否接受改进、灰度发布或回滚。


其中有三条重要边界：

1. 可观测性层尽可能记录事实，不负责自行改变执行策略。
2. 诊断引擎可以提出根因假设，但不能把假设直接升级为系统配置。
3. 因果验证结果可以作为改进依据，但仍须通过独立评测和变更治理。

这样可以降低一种常见风险：诊断器误判问题后，直接修改执行系统，随后又把修改产生的新现象当作原诊断正确的证据。

# 三、统一运行事件模型：让所有模块说同一种“诊断语言”

如果 Router 记录一种日志格式、工具运行时记录另一种格式、记忆系统没有关联任务 ID，那么即使每个模块都留下了日志，也很难还原一次完整执行过程。

因此，SOCDEA 的第一项基础设施不是复杂的根因分析模型，而是统一事件协议。

建议建立 `AgentEvent`，作为各模块向可观测性系统报告事实的标准格式。

## 3.1 统一事件的核心字段

| 字段 | 用途 |
|---|---|
| `event_id` | 全局唯一事件标识 |
| `event_type` | 事件类型，例如路由完成、工具失败、检查点保存 |
| `timestamp` | 事件发生时间 |
| `device_id` | 事件产生的设备 |
| `task_id` | 所属任务 |
| `run_id` | 本次执行实例 |
| `trace_id` | 跨模块执行轨迹标识 |
| `span_id` | 当前操作片段标识 |
| `parent_span_id` | 上游操作片段标识 |
| `module_id` | 产生事件的模块 |
| `module_version` | 模块实际运行版本 |
| `policy_version` | 相关策略版本 |
| `input_ref` | 输入或证据引用 |
| `output_ref` | 输出或产物引用 |
| `status` | 执行结果或状态变化 |
| `duration_ms` | 操作耗时 |
| `resource_usage` | 资源消耗摘要 |
| `error_code` | 结构化错误代码 |
| `correlation_ids` | 关联节点、工具执行、操作和授权记录的标识 |

不要求每条事件都填写所有字段，但必须能够关联到适用的任务和运行轨迹。

时间戳用于分析时间顺序，不能单独作为跨设备因果关系的依据。对于跨设备事件，还应使用事件序号、父子关系、消息关联和权威状态版本辅助重建。

## 3.2 事件必须表达事实，而不是只有自然语言描述

例如，工具运行时不应该只记录：

“执行失败，可能是环境问题。”

更合适的事件应该记录：

- 工具 ID 和版本；
- 输入参数的摘要；
- 实际执行环境；
- 进程退出码；
- 标准错误的受控引用；
- 超时与取消状态；
- 已产生的产物；
- 资源消耗；
- 失败发生的具体阶段。

自然语言诊断可以作为补充字段，但不能代替结构化证据。

## 3.3 建立统一事件分类

建议至少覆盖以下事件类别：

- 任务生命周期事件；
- Router 路由事件；
- 专家执行事件；
- 计划生成与 DAG 状态事件；
- 上下文构建、压缩与检索事件；
- 记忆读写事件；
- 工具执行和外部操作事件；
- 资源分配与调度事件；
- 授权、安全与策略事件；
- 检查点、恢复和设备同步事件；
- 验收、评分与用户反馈事件；
- 配置升级、模型切换与进化发布事件。

这些事件最终应能够形成一个跨模块的执行轨迹，而不是互不关联的日志集合。

# 四、统一因果关联：从用户请求追踪到最终结果

统一事件模型解决的是“记录什么”，接下来需要解决“如何关联”。

建议采用分布式追踪思想，建立 `ExecutionTrace`。

一条典型轨迹可能是：

用户请求 → Router → 专家选择 → 上下文构建 → Planner → DAG 节点 → 工具执行 → 结果验收 → 任务完成。

其中，每个步骤可能调用多个子步骤，形成树状或有向无环的执行关系。

## 4.1 不同关联 ID 不能混为一谈

建议保留以下概念：

- `task_id`：同一个长期任务的稳定身份；
- `run_id`：一次具体的执行尝试；
- `trace_id`：一条端到端执行轨迹；
- `span_id`：轨迹中的一个操作；
- `node_id`：DAG 中的节点；
- `tool_execution_id`：一次工具执行；
- `operation_id`：可能产生外部副作用的业务操作；
- `experiment_id`：一次诊断或对照实验；
- `change_id`：一次系统变更或候选发布。

例如，同一个任务可能经历三次恢复，拥有三个 `run_id`，但仍使用同一个 `task_id`。

如果系统把它们全部记录成一个执行实例，就很难判断失败发生在第一次运行，还是恢复后重试时。

## 4.2 执行轨迹不是严格的单线程调用树

ReAct、DAG 并行和多专家协作都可能产生并行执行。

例如，两个 DAG 节点同时执行，最后汇合到一个验收节点。此时需要同时记录父子关系、数据依赖和汇合关系，而不能假设所有操作都按单一时间顺序串行发生。

建议明确区分：

- **调用关系：** 谁触发了谁；
- **数据依赖：** 哪个步骤消费了哪个步骤的产物；
- **状态依赖：** 哪个状态变化允许后续执行；
- **时间关系：** 事件实际发生的时间范围。

只有这些关系结合起来，系统才有条件分析上游因素是否可能影响下游结果。

## 4.3 隐私与可观测性必须同时设计

完整诊断并不意味着无限制保存所有对话、文件和模型上下文。

建议默认记录结构化摘要和证据引用；确实需要保留原始输入时，根据敏感等级、诊断价值、用户授权和保留期限进行管理。

诊断器应能回答“上下文中是否缺少必要约束”，而不必在所有情况下复制完整的私人对话。

# 五、根因诊断引擎：从故障分类到可检验假设

建议将诊断引擎拆成五个部分，而不是让一个大模型直接阅读所有日志后给出结论。

  {#each [
    ["1. 异常检测","发现任务成功率、耗时、错误率、资源消耗或验收指标的异常变化。"],
    ["2. 故障分类","识别路由、上下文、规划、工具、资源、记忆、授权或验收等可能的问题类别。"],

## 5.1 建立统一故障分类体系

建议从以下根因类别开始：

| 类别 | 典型问题 |
|---|---|
| 意图与路由 | 用户目标理解错误、专家选择不匹配 |
| 上下文与记忆 | 关键约束丢失、记忆过期、检索错误 |
| 规划与依赖 | DAG 缺失节点、依赖错误、循环或过度规划 |
| 模型与推理 | 推理不足、输出格式不合规、模型能力不匹配 |
| 工具与环境 | 参数错误、工具缺陷、依赖缺失、执行环境变化 |
| 资源与调度 | 超时、资源不足、队列饥饿、并发冲突 |
| 验收与评价 | 验收标准错误、评测器偏差、结果证据不足 |
| 数据与状态 | 检查点损坏、版本不兼容、状态同步冲突 |
| 安全与权限 | 授权不足、策略冲突、越权尝试被正确拦截 |
| 用户与外部条件 | 需求变化、外部服务故障、输入信息不完整 |

这些类别可以多选。真实故障往往存在多个共同原因，不应该强迫系统总是输出唯一根因。

## 5.2 诊断结论必须包含反证

例如，系统怀疑“上下文压缩丢失了项目约束”。

支持证据可能是：

- 原始上下文包含指定的运行环境；
- 压缩后上下文不再包含该约束；
- 后续工具选择与该约束冲突。

但系统仍然需要检查：

- 该约束是否通过其他结构化字段传递；
- 专家是否确实读取了压缩后的上下文；
- 工具是否忽略了正确参数；
- 项目环境是否在执行期间发生变化。

如果忽略反证，诊断器就可能把所有失败都归咎于上下文压缩。

## 5.3 不确定性必须成为正式输出

建议每个诊断结论至少包括：

- 根因假设；
- 支持证据；
- 反对证据；
- 证据缺失项；
- 影响范围；
- 当前判断等级；
- 建议的验证实验；
- 尚未排除的替代解释。

判断等级可以使用“已确认”“强支持”“待验证”“证据不足”等状态。

不建议仅输出一个看似精确的置信度数字，却没有定义这个数字如何校准和验证。

# 六、因果验证：如何区分真正的根因与表面相关性？

这是 SOCDEA 最核心的部分。

假设新版本上线后，任务成功率下降，同时上下文平均长度也下降了。

这两个现象同时发生，并不证明上下文压缩导致成功率下降。新版本可能还修改了模型、路由和工具重试策略。

因此，需要通过设计合理的对照实验，区分不同因素的影响。

## 6.1 建立四种验证方法


    <title size="md">方法 A：确定性故障定位</title>
    用于明确的程序异常，例如 Schema 校验失败、文件不存在、权限拒绝或确定的版本不兼容。通过错误码、堆栈和状态证据直接定位。



    <title size="md">方法 B：历史轨迹回放</title>
    在受控环境中重放历史输入、上下文和配置，比较新旧模块的行为差异。适合检测回归，但不能保证重现所有真实环境。



    <title size="md">方法 C：单因素消融与替换实验</title>
    只改变一个候选因素，例如替换上下文压缩器，其他条件尽量保持一致，观察结果是否发生稳定变化。



    <title size="md">方法 D：受控对照与故障注入</title>
    通过对照组、随机分配、模拟故障或改变特定条件，验证某个因素是否导致质量、延迟或稳定性变化。


不同方法的证据强度不同。

如果执行环境具有随机性，就需要重复试验或采用合适的统计分析。对于无法安全重放的外部副作用，应使用模拟器、测试环境或经过隔离的实验替代，而不是直接重复真实操作。

## 6.2 用一个例子说明

假设 EvoAgent 的代码任务成功率下降，初步怀疑是上下文压缩问题。

建议按以下步骤验证：

1. 从失败任务中筛选出具有代表性的案例；
2. 检查原始上下文与压缩后上下文的差异；
3. 确认关键约束是否确实缺失；
4. 在受控环境中分别使用旧压缩器和新压缩器；
5. 保持模型、任务输入、工具版本和验收标准尽可能一致；
6. 重复运行，比较最终质量与资源消耗；
7. 检查改善是否只发生在特定任务类别；
8. 将结果交给独立评测系统复核。

如果新压缩器确实造成关键约束丢失，而且替换回旧版本后结果稳定改善，就有了更强的因果证据。

如果替换压缩器后结果没有明显变化，则需要继续排查其他因素。

## 6.3 不要假设所有因素都能独立优化

例如，路由器和上下文压缩器可能存在交互作用。

某个专家需要大量结构化上下文，而另一个专家只需要简短摘要。压缩器单独评测可能表现良好，但与特定专家组合时却明显退化。

因此，SOCDEA 需要同时支持：

- 单模块效果分析；
- 多模块交互分析；
- 特定任务类别分析；
- 端到端系统效果分析。

不能因为某个模块单独得分提高，就断言整个 EvoAgent 变得更好。

# 七、诊断与执行隔离：避免系统在诊断过程中制造新问题

诊断系统需要读取日志、查看任务状态、分析产物，有时还需要运行实验。

但诊断本身也可能产生风险。

例如，诊断器怀疑代码构建失败，于是直接在真实项目中修改依赖；修改后构建成功，却破坏了原有环境。系统随后可能把这个成功误判为原根因已经被证实。

建议建立严格的诊断执行边界。

## 7.1 诊断模式分级

| 模式 | 能力 | 默认限制 |
|---|---|---|
| 观察模式 | 查询事件、指标、状态与证据 | 不修改任务和生产配置 |
| 分析模式 | 生成假设、比较版本、建立因果关系 | 不执行有副作用的操作 |
| 实验模式 | 在隔离环境中运行回放、消融与故障注入 | 使用受控数据、资源和权限 |
| 修复候选模式 | 生成补丁、策略调整或配置候选 | 不直接发布到生产环境 |
| 受控实施模式 | 将已验证候选交给发布治理 | 必须通过授权与变更门槛 |

诊断器不应默认拥有生产环境写权限。

如果某项诊断必须读取敏感数据，应通过明确授权获取最小必要数据；如果实验需要运行代码，则应由 TERSO 与 MTSRIC 控制执行环境和资源。

## 7.2 保留诊断前后的状态差异

每次诊断实验都应记录：

- 实验前状态；
- 实验配置；
- 改变的因素；
- 未改变的关键因素；
- 执行过程；
- 结果与副作用；
- 实验后状态；
- 是否需要清理或恢复。

这样才能避免实验产生的文件修改、缓存变化或外部状态污染后续评测。

## 7.3 防止诊断器与执行器形成自我确认循环

建议明确禁止以下模式：

“诊断器认为问题来自 Router → Router 自动修改自身参数 → 诊断器使用修改后的 Router 验证自己正确 → 系统自动发布。”

正确流程应该是：

诊断器提出假设 → 形成独立候选 → 在受控环境中对照验证 → 独立评测 → 受控发布 → 线上监测。

诊断器可以参与解释结果，但不能独自完成假设、验证和批准全部环节。

# 八、进化效果归因：系统到底有没有变好？

发现问题只是第一步。对于 EvoAgent，最终还需要回答：这次进化是否真正提高了执行质量？

建议建立统一的 `EvolutionExperiment`，把每次改进视为一个可追溯的实验。

## 8.1 每个进化实验必须记录什么？

- `experiment_id`：实验标识；
- `change_id`：候选变更标识；
- `hypothesis`：希望验证的假设；
- `target_component`：目标模块；
- `baseline_version`：基线版本；
- `candidate_version`：候选版本；
- `dataset_version`：评测集版本；
- `control_conditions`：对照条件；
- `primary_metrics`：主要指标；
- `guardrail_metrics`：不可退化的保护指标；
- `sample_size`：实际样本数量；
- `result_summary`：结果摘要；
- `uncertainty_analysis`：不确定性分析；
- `approval_status`：评测与发布状态。

这样，系统可以追溯某项改进的来源，而不是只知道当前配置是多少。

## 8.2 必须同时定义主要指标和保护指标

例如，优化上下文压缩器时：

主要指标可以是任务成功率、关键约束保留率和上下文成本。

保护指标则应包括：

- 敏感信息泄漏；
- 关键事实丢失；
- 工具参数错误；
- 长期任务恢复失败；
- 重要任务类别的明显退化。

如果只优化 Token 消耗，系统可能通过过度压缩来提高表面效率，却导致任务质量下降。

如果只优化成功率，也可能通过无限重试、调用更昂贵的模型或放宽安全限制来取得更高分数。

因此，进化评测必须包含不可随意交换的硬性约束。

## 8.3 对照组与基线必须稳定

建议为关键任务类别维护固定的回归评测集，并定期使用新任务补充评测集。

其中：

- 固定集用于比较新旧版本；
- 新增集用于检测系统是否过度适应历史案例；
- 对抗集用于检查安全与异常行为；
- 长期任务集用于验证恢复、状态持久化和跨会话连续性。

评测集自身也必须版本化，避免因为测试样本变化而错误地认为系统进步或退步。

对于随机性较强的模型任务，应记录随机种子或其他可控条件；如果模型服务无法保证确定性，则应通过重复运行、对照设计和不确定性报告降低误判风险。

# 九、诊断质量评测：不仅要看任务诊断是否正确，还要看诊断器是否知道自己不知道

诊断器本身也会犯错。

它可能把相关性当作因果关系，也可能遗漏真正的根因，或者在证据不足时给出过度自信的结论。

因此，SOCDEA 必须拥有独立于执行系统的评测机制。

## 9.1 建立诊断能力的五个维度

| 维度 | 评测问题 |
|---|---|
| 根因识别 | 是否找到了真正导致故障的因素？ |
| 证据质量 | 结论是否有可靠证据支持，是否识别反证？ |
| 假设区分能力 | 能否区分多个看起来相似的根因？ |
| 不确定性校准 | 证据不足时，是否能够承认无法确定？ |
| 验证效率 | 是否用较少的实验成本获得足够的诊断证据？ |

其中，不确定性校准尤其重要。

一个能够正确说“当前证据不足，需要进一步验证”的诊断器，往往比一个总能给出确定答案、却经常猜错的诊断器更适合长期自进化系统。

## 9.2 构造已知根因的故障样本

建议在隔离测试环境中主动注入已知问题，例如：

- 故意让 Router 选择错误专家；
- 从压缩上下文中移除一条必要约束；
- 让 DAG 缺少一个必要依赖；
- 让工具返回格式错误的结果；
- 模拟内存不足；
- 让检查点引用一个不存在的产物；
- 让工具契约与执行器版本不兼容；
- 让安全策略拒绝一项本应允许的测试操作。

这些样本具有明确的故障来源，可以用来评估诊断器能否定位问题，并识别哪些证据真正支持结论。

但测试不能只使用单一故障。真实系统中经常出现多个问题同时发生的情况，因此还需要多故障样本与难以区分的对照案例。

## 9.3 诊断器也需要版本治理

诊断器升级时，必须记录：

- 诊断模型与提示词版本；
- 故障分类体系版本；
- 证据检索策略版本；
- 诊断评测集版本；
- 根因判断与不确定性校准指标；
- 新旧版本的差异。

不能因为新版诊断器写出的分析更完整、更有说服力，就认定其诊断能力提高了。

最终仍需通过已知根因样本、历史故障回放和独立评测来验证。

# 十、运行时可观测性与因果诊断的边界

这里需要特别明确一个架构问题：SOCDEA 不是让所有模块把全部数据都发给一个中央模型。

对于你的个人设备部署方向，更合理的是采用分层可观测性。


    <title size="md">设备本地采集</title>
    在 Android、Windows 或 Linux 设备上记录必要的事件、资源状态和执行结果。



    <title size="md">本地持久化与关联</title>
    将事件关联到任务和执行轨迹，支持离线存储、去重与恢复后同步。



    <title size="md">诊断与实验执行</title>
    根据任务风险与资源情况，在本地或经授权的其他设备上分析证据和执行隔离实验。



    <title size="md">独立评测与发布治理</title>
    汇总诊断结果，验证改进是否有效，再由受控的进化发布流程决定是否启用。


这种结构有三个好处：

- 设备离线时仍然可以记录和分析本地故障；
- 不需要把所有原始日志和私人数据上传到外部服务；
- 诊断实验可以根据资源和安全要求选择执行位置。

对于微型 Linux 主机，轻量级规则诊断和统计分析可以常驻运行；需要较大模型或复杂实验时，再根据能力调用本地模型或已授权的远程服务。

**诊断系统不应该为了提高诊断能力而无限收集数据，也不应该为了追求自动化而默认拥有生产环境修改权。**

# 十二、下一专项：统一质量评测、结果验收与质量进化

SOCDEA 解决了系统如何发现异常、分析根因，以及验证某项改进是否产生效果。

但还存在一个更基础的问题：

**EvoAgent 如何定义什么叫“任务完成得好”？不同专家、不同任务、不同用户要求之间，能否使用统一的质量评测体系？**

例如：

- 编程任务需要正确性、测试覆盖、可维护性和安全性；
- AI 漫剧任务需要角色一致性、画面质量、音画同步和叙事连贯性；
- 旅游任务需要事实准确、行程可行、时间合理和用户偏好匹配；
- 手机操作任务需要动作成功、状态正确、权限合规和可恢复性；
- 通用对话需要事实可靠、上下文连贯和对用户意图的正确理解。

这些任务不能使用同一套简单评分规则。

更重要的是，任务执行成功不等于结果质量合格。工具退出码为零、DAG 全部节点执行完成、模型给出高置信度回答，都不能独立证明用户真正得到了满意的结果。

下一专项建议定义为：

**Unified Quality Evaluation & Acceptance Governance，简称 UQEAG。**

重点研究：

1. 如何建立全局统一的质量评价框架，同时允许各专家定义领域专属指标；
2. 如何区分任务完成、结果正确、结果有用和用户满意；
3. 如何将用户的自然语言要求转化为可检验的验收条件；
4. 如何处理无法完全自动验证的主观质量；
5. 如何结合规则检查、程序化测试、模型评审和用户反馈；
6. 如何防止评测模型与执行模型出现共同偏差；
7. 如何处理多个质量指标之间的冲突；
8. 如何在任务开始前确定验收标准，避免完成后临时修改标准；
9. 如何对部分完成、质量不足和不可验证结果进行准确分类；
10. 如何将质量评测与 DAG 节点、最终产物和任务状态关联；
11. 如何防止自进化系统通过优化评分规则而非真正改善结果来刷分；
12. 如何把质量缺陷转化为可复用的改进案例，并交给 RCAE、EQEAG 与 SELCIA 的治理流程处理。

核心原则是：

**质量标准应在执行前尽可能明确，结果应由与执行过程适当独立的证据进行验证；系统不能通过修改验收标准来证明自己已经进步。**

这将进一步补齐 EvoAgent 的质量闭环：不仅能够执行任务、恢复任务、诊断失败和验证进化，还能更加可靠地判断交付成果究竟是否达到用户真正需要的质量。
