# EvoAgent 第三专项：工作记忆与任务状态系统全量设计

这一轮我们要解决一个非常实际的问题：**智能体怎样在长时间、多步骤、多专家、可中断的任务中，始终准确地知道自己正在做什么、已经做了什么，以及接下来应该做什么。**

这与前面设计的长期记忆、用户习惯和上下文压缩密切相关，但它们不能混成一个系统。

例如，让 EvoAgent 制作一部 60 秒 AI 漫剧，可能需要经历剧本生成、角色设计、分镜、图像生成、视频生成、配音、合成和验收。任务执行数小时后，手机可能进入后台，云端生成服务也可能断联。

恢复时，智能体不能只靠重新读取聊天记录来猜测进度。它必须知道：

- 用户最终确认的目标是什么；
- 当前生效的是哪一版计划；
- 哪些步骤已经完成且通过验收；
- 哪些步骤执行失败；
- 哪些步骤正在运行或结果未知；
- 已经生成了哪些素材；
- 哪些外部操作可能产生了副作用；
- 剩余预算和截止时间是多少；
- 恢复后应该从哪里继续。

因此，我建议为 EvoAgent 建立一个独立的**工作记忆与任务状态系统（Working Memory & Task State System）**，由它负责保存任务运行事实，并为 Planner、ReAct、DAG 引擎、专家和上下文引擎提供统一的当前状态。

# 一、首先划清四个系统的职责


    <title size="lg">长期记忆系统</title>
    **回答：过去值得保留什么？**
    用户偏好、项目决策、领域知识、验证过的经验和历史事实。


    <title size="lg">工作记忆系统</title>
    **回答：当前任务的真实状态是什么？**
    目标、计划版本、节点进度、执行尝试、未决事项、检查点和恢复信息。


    <title size="lg">上下文治理系统</title>
    **回答：本次模型调用需要看到什么？**
    从任务状态、长期记忆、证据和当前输入中选择相关信息，并控制 Token 预算。


    <title size="lg">执行控制系统</title>
    **回答：接下来允许执行什么？**
    根据状态机、权限、依赖、预算和停止条件调度 ReAct、工具及工作流。


这四个系统的关系不是四份独立的“记忆”。

工作记忆保存任务事实；上下文系统读取这些事实并形成模型输入；执行控制器校验动作并推动状态转换；长期记忆则在合适的时候提供历史经验。

例如，模型认为“视频已经生成”，不等于工作记忆可以将视频节点标记为完成。只有获得可信的执行结果和相应验证证据，任务状态才能发生对应变化。

# 二、工作记忆内部应该分成什么？

我建议工作记忆由七个逻辑部分组成，而不是一个不断追加文本的 `task_memory` 字段。

| 组成部分 | 保存内容 | 主要用途 |
|---|---|---|
| 目标与约束 | 用户目标、验收标准、硬性限制、已确认的修改 | 防止执行过程中偏离目标 |
| 当前计划 | Plan 版本、DAG 节点、依赖关系、重规划历史 | 确定任务结构 |
| 执行账本 | 每次执行尝试、工具调用、结果、错误与副作用状态 | 防止重复执行和丢失证据 |
| 当前进度 | 已完成、待执行、阻塞、等待中的节点 | 判断下一步行动 |
| 关键事实与证据 | 已验证事实、产物引用、测试结果、外部状态 | 支持决策与验收 |
| 未决事项 | 未确认问题、待用户输入、失败原因和风险 | 防止遗忘关键问题 |
| 恢复检查点 | 可恢复状态、版本清单、资源引用和恢复条件 | 支持中断后继续 |

这里的“七个部分”是逻辑划分，不意味着必须分别建七张表。真正重要的是每类数据的更新规则、持久化要求和权威来源不同。

## 2.1 工作记忆还需要区分三种状态信息

**第一种：已经确认的事实。**

例如，某个视频素材已成功生成，文件已保存，并且通过了分辨率检查。这类信息可以作为后续步骤的输入。

**第二种：当前观察到的状态。**

例如，云端生成任务仍在运行，或者手机当前显示某个应用的登录界面。这类信息可能过期，需要在恢复或继续操作前重新检查。

**第三种：模型提出的判断。**

例如，模型推测视频生成失败可能是因为提示词不清晰。这只是诊断假设，不应被写成已确认事实。

三者必须在数据结构中明确区分。否则，模型的猜测可能被下一轮模型当作真实历史，经过多轮推理后变成错误的“事实”。

# 三、工作记忆与 Plan、DAG、ReAct 究竟是什么关系？

这是 EvoAgent 的核心执行架构之一。

我的建议是：

- **Plan** 决定整体目标和行动策略。
- **DAG** 表达具有依赖关系的任务节点。
- **ReAct** 在执行过程中进行观察、判断、行动和反馈。
- **工作记忆** 保存当前任务的权威进度和执行事实。
- **任务控制器** 检查状态转换，并决定哪些动作可以被调度。

它们不是互相替代的四种智能体。


    **Plan / Planner**
    提出计划或修订方案



    **DAG / 工作流引擎**
    根据节点依赖生成可执行工作



    **任务控制器**
    校验权限、预算、状态与执行条件



    **ReAct / 工具执行器**
    执行、观察结果，必要时提出下一步动作



    **工作记忆与事件账本**
    持久化结果、证据、状态变更与恢复信息


  执行结果反馈给任务控制器；必要时触发 ReAct 继续、DAG 重试或 Planner 重规划。

注意，这里的流程不是严格的单向流水线。ReAct 可以在节点内部循环；Planner 可以在执行过程中提出新计划；DAG 可以并行运行多个独立节点。但每次有意义的状态变化，都必须回到统一的任务状态管理机制中。

## 3.1 什么情况下只需要 ReAct，什么情况下需要 DAG？

简单任务，例如“打开手机上的计算器并输入一个数”，可能只需要短程的 ReAct 执行，不需要建立复杂的 DAG。

复杂任务，例如“制作一部 60 秒 AI 漫剧”，则适合使用 DAG 编排生成剧本、角色素材、分镜、视频、配音和合成。

更重要的是：DAG 也不必完全固定。遇到失败时，可以局部重试、替换某个节点的实现，或由 Planner 提出经过校验的新计划版本。

**无论任务是简单循环还是复杂工作流，工作记忆都使用统一的任务、执行和证据模型。** 这样不会因为换了一种执行模式，就需要重新设计一套状态管理系统。

这些对象应该关联统一的 `task_id`、必要的 `trace_id`、执行版本和时间信息，但不能要求每个对象都重复保存完整的任务上下文。

## 4.1 一个关键的数据结构示例

例如，某个节点执行失败后，不能只把状态写成 `FAILED`。还需要知道它执行的是哪个版本、使用了什么输入、是否产生了外部副作用，以及能否安全重试。

<CodeBlock language="json" editable>
{
  "execution_id": "exec-008",
  "task_id": "task-123",
  "plan_version": 4,
  "node_id": "generate_video",
  "attempt": 2,
  "status": "FAILED",
  "input_refs": [
    "storyboard-v3",
    "character-assets-v2"
  ],
  "runtime_manifest_id": "manifest-021",
  "error_code": "PROVIDER_TIMEOUT",
  "side_effect_state": "UNKNOWN",
  "retry_policy": "QUERY_BEFORE_RETRY",
  "evidence_refs": [
    "provider-request-008"
  ],
  "started_at": "timestamp",
  "finished_at": "timestamp"
}
</CodeBlock>

这里最关键的不是字段数量，而是 `side_effect_state`。

如果云端视频服务超时，可能有三种情况：

1. 请求根本没有被接受；
2. 请求已经被接受，但响应丢失；
3. 视频已经生成，结果还没有被设备记录。

如果系统一律重试，就可能生成两次视频并产生两次费用。因此，状态未知时必须先核实，而不是直接创建新的生成任务。

# 五、检查点机制：如何在中断后真正恢复任务？

检查点不应该只是“把当前聊天内容总结一下”。

一个可靠的检查点至少需要保存：

- 当前任务及计划版本；
- 已完成节点及其验收结果；
- 正在执行或结果未知的节点；
- 各节点输入输出的产物引用；
- 未解决问题和等待条件；
- 当前预算和资源状态；
- 当前运行版本清单；
- 事件账本的位置；
- 恢复前必须重新验证的条件。

这里建议采用**事件账本 + 周期性快照 + 必要的产物持久化**。

事件账本保存发生了什么，快照加速恢复，产物存储保存真正需要继续使用的文件。三者共同构成恢复依据。

## 5.1 检查点何时创建？

不建议每产生一个 Token 就写入数据库，也不能只在任务全部完成时才保存。

应该在以下关键时刻创建持久化边界：

- 用户确认了目标或关键约束；
- 计划版本正式生效；
- 一个节点完成并通过必要验收；
- 外部副作用执行前后；
- 一个生成产物成功持久化；
- 任务暂停、取消或进入等待；
- 重规划改变了后续执行路径；
- 任务跨越设备、服务或重要版本边界。

对于长时间运行的节点，还需要保存进度游标或远端任务 ID；如果外部服务不支持恢复，则必须明确该步骤只能重新执行、查询状态或进行补偿。

## 5.2 不能把数据库提交和外部操作当作一个原子事务

这是工程上特别容易遗漏的地方。

假设手机先向云端提交“开始生成视频”，然后才保存本地任务状态。如果此时 App 崩溃，系统可能不知道请求是否已经发出。

建议采用持久化意图与执行账本：

1. 先保存待执行的操作记录和幂等键。
2. 检查权限与预算，并记录执行许可。
3. 发出外部请求。
4. 保存响应、远端任务 ID 或未知状态。
5. 通过查询、回调或对账确认最终结果。
6. 将已确认的结果提交为任务事实。

即使系统无法在所有情况下实现真正的端到端 exactly-once，也可以通过幂等键、状态核查和对账降低重复执行风险。

**不能因为一次请求超时，就把它当成从未发生过。**

# 六、Android 进程被杀、断网后，如何恢复？

这部分必须结合手机优先战略来设计。

Android 端不是一个始终运行的服务器。进程可能被系统回收，WorkManager 也不能保证任意长任务持续执行。因此，恢复机制必须依赖持久化状态，而不是依赖内存中的 Agent 对象。

建议将任务执行划分为三类。

| 任务类型 | 示例 | 恢复方式 |
|---|---|---|
| 本地短任务 | 简单计算、读取本地文件 | 重新加载本地任务状态，继续执行 |
| 本地长任务 | 大文件处理、FFmpeg 合成 | 持久化检查点与产物，按 Android 后台执行规则恢复 |
| 云端长任务 | 视频生成、复杂研究任务 | 保存远端任务 ID，重新连接后查询真实状态 |

## 6.1 断网时的处理策略

当设备与服务器断联时，任务控制器需要判断当前节点是否具备独立执行条件。

- 如果节点完全依赖本地能力，可以按既定权限和预算继续。
- 如果节点必须调用云端模型，应进入等待、降级或经过授权的替代路径。
- 如果远端任务已经提交，则保存远端任务标识，稍后查询，而不是盲目重新提交。
- 如果日志无法上传，应继续本地持久化，等待网络恢复后同步。
- 如果当前状态无法确认，应明确标记为待核实，不应伪造成功或失败。

## 6.2 恢复时的检查顺序

我建议使用固定的恢复协议：

  {#each [

    ["3. 核实外部状态","查询云端任务、文件写入或其他可能产生副作用的操作。"],

# 七、工作记忆如何与上下文压缩协同？

这是接下来设计上下文系统时必须依赖的接口。

我建议工作记忆向上下文引擎提供一个结构化的 `TaskContextView`，而不是把全部任务历史直接拼接给模型。

例如：

<CodeBlock language="json" editable>
{
  "task_id": "task-123",
  "goal": "完成并验收一部60秒AI漫剧",
  "active_plan_version": 4,
  "completed_nodes": [
    "script",
    "character_design",
    "storyboard"
  ],
  "blocked_nodes": [
    {
      "node_id": "generate_video",
      "reason": "等待远端任务状态核实"
    }
  ],
  "next_eligible_nodes": [
    "prepare_voice_assets"
  ],
  "open_issues": [
    "video_generation_status_unknown"
  ],
  "hard_constraints": [
    "target_duration_60_seconds",
    "budget_limit_enforced"
  ],
  "evidence_refs": [
    "script-v2",
    "storyboard-v3"
  ],
  "runtime_manifest_id": "manifest-021"
}
</CodeBlock>

这个视图只是模型本次调用可以使用的信息，不是权威状态本身。

上下文引擎可以根据不同阶段进一步裁剪：

- Planner 需要目标、约束、整体进度和未决事项。
- ReAct 需要当前节点、最近观察、可执行动作和停止条件。
- 验收器需要验收契约、实际产物和证据。
- 故障诊断器需要失败尝试、工具结果和版本信息。
- 记忆系统需要任务结束后的结果摘要与证据引用。

这意味着不同模块不需要看到全部信息。上下文应该是**按角色、按阶段、按预算生成的视图**，而不是一个全局共享的大型提示词。

如果压缩后的摘要缺少关键细节，系统应该能通过引用回查工作记忆和原始证据。不能让压缩摘要取代真实任务状态。

# 八、工作记忆本身也要有质量评测

如果工作记忆只是被动存储任务状态，它只能帮助恢复，不能保证恢复后做对事情。

我们还需要评估工作记忆有没有保存正确的信息，以及它是否能够让执行系统准确地继续任务。

| 评测维度 | 核心问题 |
|---|---|
| 状态准确性 | 记录的任务状态是否与实际执行情况一致？ |
| 进度准确性 | 是否正确识别已完成、未完成和阻塞的节点？ |
| 恢复正确率 | 进程重启后，是否能恢复到正确的执行位置？ |
| 重复副作用率 | 恢复后是否重复发送消息、创建任务或产生额外费用？ |
| 证据完整性 | 任务结论是否能够追溯到真实执行证据？ |
| 版本一致性 | 恢复后是否错误地混用了新旧组件？ |
| 资源账本准确性 | 预算预留、实际消耗和剩余额度是否一致？ |
| 恢复成本 | 恢复需要多少时间、模型调用和人工介入？ |

还需要建立故障注入测试，模拟：

- 工具调用过程中进程被杀；
- 外部服务成功但响应丢失；
- 任务执行到一半时断网；
- 数据库提交失败；
- 同一任务被两个执行器同时恢复；
- 旧版本工作流在新版本应用上恢复；
- 用户在任务暂停期间撤销权限；
- 任务恢复后发现远端结果与本地记录冲突。

这些测试比单纯测试正常执行路径更重要。只有通过这些场景，才能证明工作记忆不仅能保存信息，还能支持可靠恢复。

    "Plan、DAG、ReAct 和工作记忆分工明确，通过统一任务状态协议协同。",
    "任务、计划、节点、执行尝试和外部操作分别记录，不相互覆盖。",
    "使用事件账本、检查点和持久化产物支持任务恢复。",
    "外部副作用状态必须可区分已提交、部分完成、未发生和未知。",
    "状态未知时优先核查，不允许无条件重试。",
    "上下文引擎读取结构化任务视图，不直接把全部工作记忆塞入模型。",
    "恢复任务必须检查原版本兼容性、权限、预算与远端实际状态。",
    "工作记忆需要独立的恢复测试、状态一致性测试和重复执行测试。"
  ] as item}

这些可以作为工作记忆系统的设计基线。具体的数据库事务、事件顺序、并发控制、恢复算法和 Android 后台执行方案仍需通过详细设计与实现测试验证。

# 十、下一步：设计上下文组装引擎

现在，我们已经分别梳理了：

1. 长期记忆系统：决定什么信息值得保存；
2. 用户习惯与个性化系统：决定怎样根据用户和情境调整协作方式；
3. 工作记忆与任务状态系统：决定当前任务的真实进度和恢复依据。

接下来就到了三者的交汇点：**上下文组装与治理系统（Context Engineering System）**。

我建议下一轮重点研究：

- 系统提示词、专家提示词、任务指令、记忆和工具结果如何组织；
- 哪些内容是硬性约束，哪些只是参考信息；
- Planner、ReAct、验收器和故障诊断器是否需要不同的上下文模板；
- 长任务如何选择历史对话，而不是无差别地保留全部聊天；
- 上下文窗口有限时，如何分配 Token 预算；
- 多专家之间如何共享必要信息而不互相污染；
- 如何记录每次模型调用实际使用的上下文，以便诊断和评测；
- 如何在上下文压缩后恢复原始事实与证据。

**这一步将直接连接记忆、个性化、Plan、ReAct、多专家、工具调用和自进化系统。** 如果上下文组装设计得好，智能体才能在有限的模型调用成本下，既记得重要信息，又不会被无关历史拖累。
