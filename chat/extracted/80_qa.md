# EvoAgent 第二十七专项：工具运行时与能力插件治理

这一轮要解决 EvoAgent 扩展能力时的基础问题：**如何让智能体不断获得新工具和新能力，同时不让系统变得不可控、不可维护，或者因为工具升级而破坏已有专家。**

你之前提出过一个非常关键的设计方向：编程专家可能需要 AST 语法树、静态分析和测试工具；AI 漫剧专家需要图像生成、视频生成、配音和 FFmpeg；其他领域也可能拥有自己的专用技术。

这些能力不应该全部塞进通用智能体，也不应该让每个专家自己随意安装、调用和管理工具。

更合理的方式是建立一个统一的工具运行时，同时允许领域专家声明自己的能力需求、工具组合和验收标准。

本专项建议定义为：

**Tool Runtime & Capability Plugin Governance，简称 TRCPG。**

它负责工具注册、能力发现、工具契约、执行隔离、结果验证、版本兼容、工具健康监测和插件生命周期管理。

## 一、第一性原理：工具、技能、工作流和专家不是同一种东西

首先要建立清晰的概念边界，否则系统会不断出现重复抽象。


    <title size="md">1. 工具 Tool</title>
    完成一个边界明确的操作，例如解析 Python AST、读取文件、运行测试、调用视频生成 API。



    <title size="md">2. 技能 Skill</title>
    将领域知识、判断方法、工具使用策略和验收要求组织起来，指导智能体完成某类工作。



    <title size="md">3. 工作流 Workflow</title>
    定义多个步骤的依赖、分支、并行、重试、恢复和验收关系。



    <title size="md">4. 专家 Expert</title>
    拥有领域目标理解、任务策略、专属记忆、能力选择和质量标准的领域智能体。



    <title size="md">5. 模型适配策略 Model Adapter</title>
    负责将不同模型的输入输出、工具调用、上下文限制和能力差异适配到统一接口。


举一个编程任务的例子：

- AST 解析器是工具；
- “跨文件重构前先分析符号引用”是技能或策略；
- “分析、修改、测试、验收、失败恢复”是工作流；
- 编程专家负责理解用户的代码目标并决定使用哪种方案；
- 模型适配器负责将该专家的推理请求转换为具体模型可执行的形式。

这样，领域专家可以选择不同工具组合，而不用将所有工具实现细节写入提示词。

## 二、建立三层能力架构

我建议采用“能力声明层、工具治理层、执行运行时层”三层结构。


    **能力声明层**
    专家、技能、工作流声明所需能力与验收要求



    **工具治理层**
    工具注册、能力发现、契约验证、权限策略、版本与健康状态



    **工具执行运行时**
    参数校验、授权检查、资源调度、隔离执行、结果核验与审计



    <grid-item>

        **本地工具**
        文件、AST、Git、FFmpeg、本地模型

    </grid-item>
    <grid-item>

        **外部工具**
        搜索、云端模型、生成服务、外部 API

    </grid-item>


这三层之间通过明确的接口协作，但不需要部署成三个独立服务。

对个人使用的 EvoAgent，我建议先将工具治理和执行运行时放在同一个本地进程中；对需要隔离的命令执行、第三方插件或高风险工具，再使用独立子进程或受限执行环境。

# 三、工具注册表：系统如何知道自己拥有哪些能力？

不能仅仅保存一张“工具名称列表”。

如果系统只知道存在一个叫 `python_tool` 的工具，却不知道它能读取哪些目录、是否允许联网、会不会修改文件、支持什么参数、运行在哪个平台，那么就无法安全地选择和执行它。

因此，建议建立统一的 **Tool Registry（工具注册表）**。

每个工具都必须声明：

- 工具身份与版本；
- 能力类别和用途；
- 输入与输出 Schema；
- 执行平台与运行环境；
- 文件、网络、设备等访问需求；
- 副作用类型；
- 超时、取消和重试能力；
- 幂等性与恢复能力；
- 资源需求与费用；
- 结果验证方式；
- 兼容版本与依赖；
- 健康状态和历史评测结果。

## 3.1 工具能力不是一句自然语言描述

例如，下面是一个概念性工具声明：

<CodeBlock language="json" editable>
{
  "tool_id": "python.ast_analyzer",
  "version": "1.0.0",
  "category": "code_analysis",
  "description": "Parse Python source and extract syntax structure",
  "capabilities": [
    "parse_python",
    "extract_symbols",
    "report_syntax_errors"
  ],
  "input_schema": {
    "source_path": "authorized_workspace_file",
    "python_version": "supported_runtime_version"
  },
  "output_schema": {
    "syntax_valid": "boolean",
    "symbols": "array",
    "diagnostics": "array"
  },
  "side_effects": {
    "filesystem": "read_only",
    "network": "none"
  },
  "execution": {
    "platforms": ["windows", "linux"],
    "timeout_seconds": 10,
    "cancellable": true
  },
  "verification": {
    "method": "parse_result_and_diagnostics"
  }
}
</CodeBlock>

这里的字段用于展示设计思路，不代表已经存在这个工具或已完成实现。实际 Schema 应采用明确的数据类型、必填约束和可执行的参数校验规则。

特别需要注意：工具自己声明“只读”，并不意味着它就真的只能读取。执行运行时仍然需要通过操作系统权限、受限工作目录和实际执行方式来约束它。

## 3.2 工具声明、工具能力和工具权限必须分开

这是三个不同的概念：

- **声明能力：** 工具声称能够做什么。
- **验证能力：** 系统通过测试确认它实际上能做什么。
- **授予权限：** 系统允许它在当前任务中做什么。

一个工具可能具有删除文件的技术能力，但某个任务只允许它读取文件。

一个第三方插件也可能声明自己不访问网络，但在缺乏沙箱和运行时限制的情况下，系统不能仅凭声明就信任它。

因此，注册成功并不意味着自动获得全部权限。

# 四、能力发现与工具选择：专家如何找到合适的工具？

当用户提出任务时，专家不应该凭工具名称猜测，也不应该让模型在所有工具中随意挑选。

建议将工具选择设计为一个受约束的过程。

  {#each [
    ["01 · 需求提取","从任务目标中识别所需操作、输入输出、质量要求与环境约束。"],
    ["02 · 能力匹配","从注册表中查找具备对应能力的工具，而不是只做名称匹配。"],
    ["03 · 硬性过滤","排除平台不兼容、权限不足、版本不匹配或健康状态不合格的工具。"],
    ["04 · 成本与质量排序","比较验证效果、可靠性、延迟、费用和资源需求。"],
    ["05 · 执行前检查","核验当前授权、预算、参数、目标资源和副作用。"],
    ["06 · 运行与验证","执行工具，核验输出，并将真实结果交给任务状态机。"]
  ] as item}


        {item[0].slice(0,2)}


        **{item[0].slice(5)}**
        {item[1]}


    {#if item[0]!=="06 · 运行与验证"}

    {/if}
  {/each}

## 4.1 选择工具不能只优化调用价格

假设两个代码分析工具都能检查语法错误：

- 工具 A：调用便宜、速度快，但无法解析项目的真实运行环境；
- 工具 B：速度稍慢、成本较高，但能够识别特定版本的语法与类型约束。

对于简单语法检查，A 可能更合适；对于复杂迁移任务，B 可能更值得使用。

建议工具排序综合考虑：

- 能力是否匹配；
- 历史验收效果；
- 输入输出契约是否可靠；
- 当前版本是否兼容；
- 权限与风险是否可接受；
- 预期总成本；
- 执行延迟；
- 失败恢复能力。

硬性约束必须先过滤，不能通过一个综合分数让高分工具绕过权限或兼容性检查。

## 4.2 不要为所有任务都重新搜索全部工具

工具发现也需要控制成本。

建议对工具注册表建立能力索引，并按领域、输入类型、输出类型、平台和任务类型缩小候选范围。

例如，编程专家优先查询代码分析、文件操作、测试和版本控制能力；漫剧专家优先查询图像、视频、音频和媒体处理能力。

但如果领域内没有合适工具，系统仍然可以查询经过授权的共享工具，而不是把领域划分变成绝对封闭的工具列表。

# 五、统一工具执行契约：调用成功不等于结果正确

这是工具系统中最重要的工程边界之一。

工具返回了一个正常结果，不代表任务已经成功；进程退出码为 0，也不代表生成的产物满足用户要求。

例如：

- FFmpeg 成功退出，但输出视频时长不正确；
- 代码测试命令执行成功，但实际上没有发现任何测试；
- 浏览器提交表单成功，但目标业务状态尚未更新；
- 图像生成服务返回图片，但角色一致性不合格；
- AST 分析器解析成功，但没有覆盖目标文件；
- 文件写入成功，但写入了错误的工作目录。

因此，工具执行需要分成至少四个阶段。

  {#each [
    ["调用已接受","工具接收了经过校验的请求，不代表执行已经完成。"],
    ["执行已结束","工具报告执行结束，并返回结果、错误或外部操作标识。"],
    ["结果已核验","通过契约检查、产物检查或业务状态查询验证实际结果。"],
    ["任务已验收","任务级验收器确认结果满足用户目标与质量要求。"]
  ] as item}

      <title size="md">{item[0]}</title>
      {item[1]}

    {#if item[0]!=="任务已验收"}

    {/if}
  {/each}

这四个阶段应该分别记录状态和证据。

## 5.1 统一执行结果结构

建议工具执行器统一返回：

- `tool_call_id`；
- 工具身份和实际版本；
- 输入摘要与参数校验结果；
- 执行状态；
- 开始和结束时间；
- 输出数据或产物引用；
- 错误类别；
- 外部任务 ID；
- 副作用记录；
- 结果验证证据；
- 是否支持安全重试；
- 是否需要后续对账。

大型图片、视频、日志或代码文件应通过产物引用传递，而不是全部塞进一次工具返回值。

## 5.2 统一错误分类

工具失败不能只有一个 `error` 字符串。

建议至少区分：

- `INVALID_INPUT`：参数或 Schema 不合法；
- `PERMISSION_DENIED`：授权不足；
- `UNAVAILABLE`：工具或外部服务不可用；
- `TIMEOUT`：等待超时；
- `RATE_LIMITED`：触发限流；
- `EXECUTION_FAILED`：执行失败；
- `OUTPUT_INVALID`：结果格式或产物不符合契约；
- `VERIFICATION_FAILED`：结果存在，但未通过核验；
- `OUTCOME_UNKNOWN`：执行结果无法确定；
- `CANCELLED`：操作已取消或取消请求已确认生效。

这些错误应该触发不同处理策略。

例如，参数错误通常应修正输入；限流可能需要等待；权限不足不能通过无限重试解决；外部操作状态未知时必须先对账，而不是直接再次提交。

## 5.3 重试必须由执行契约决定

不能统一规定所有工具失败后都重试三次。

对于只读、无副作用的操作，重试通常比较安全；对于支付、视频生成、消息发送和文件覆盖等操作，重复调用可能造成额外费用或重复副作用。

因此，重试策略至少需要考虑：

- 是否具有幂等键；
- 外部系统是否支持查询操作状态；
- 失败发生在提交前还是提交后；
- 当前操作是否已经产生副作用；
- 是否满足重试条件；
- 预算和截止时间是否仍然允许。

如果无法确认上一次操作是否已经执行，应该进入对账状态，而不是假设它失败了。

# 六、执行隔离：工具可以扩展，但不能随意获得本机控制权

EvoAgent 未来可能加载各种第三方工具和插件。它们的可信程度、运行方式和副作用差异很大，因此不能采用“注册成功就直接执行”的模式。

我建议建立四种执行环境。




      <title size="md">E0 · 受控内置工具</title>

    适用于经过审核的本地工具，例如只读文件查询、结构化数据校验和安全的计算操作。仍然必须执行参数与权限检查。





      <title size="md">E1 · 受限工作区执行</title>

    适用于文件修改、代码测试、媒体合成等任务。只访问授权工作区，限制可写目录和资源使用。





      <title size="md">E2 · 隔离进程或沙箱</title>

    适用于第三方插件、不可信代码和需要较强隔离的执行。根据平台能力限制文件、网络、进程和资源访问。





      <title size="md">E3 · 外部服务执行</title>

    适用于云端模型、视频生成和外部 API。需要独立处理凭据、预算、网络错误、远端状态和数据传输边界。


这里的 E0–E3 是 EvoAgent 的逻辑执行环境分类，不代表所有操作系统都能提供相同级别的隔离能力。

## 6.1 第三方插件不能直接继承主进程的全部权限

例如，一个新插件只需要解析 Markdown 文件，就不应该因为运行在 EvoAgent 内部而自动获得完整磁盘访问权、环境变量和网络访问权。

建议遵循：

- 插件默认没有额外权限；
- 每项资源访问都需要明确授权；
- 不可信插件优先运行在独立进程或受限环境；
- 高风险操作经过统一执行网关；
- 插件升级后重新验证能力与权限；
- 插件不能自行修改注册表中的权限声明；
- 插件不能直接修改安全根规则。

尤其需要注意，单纯使用子进程并不等于实现了安全沙箱。如果子进程仍继承了全部环境变量、文件访问权和网络能力，隔离效果可能非常有限。

## 6.2 工具与凭据分离

工具注册表只需要引用凭据标识和所需权限，不应该把 API 密钥、密码或其他秘密直接写进普通工具描述、日志或模型上下文。

实际调用时，由凭据管理组件在经过授权后提供必要凭据，并尽量限制：

- 可调用的服务；
- 可访问的数据；
- 可用的费用额度；
- 凭据有效期；
- 是否允许委托；
- 是否允许将请求内容发送到外部服务。

工具日志也必须避免记录完整凭据和不必要的敏感数据。

# 七、插件生命周期：安装、升级、停用和撤销都需要治理

如果 EvoAgent 允许持续扩展工具能力，就必须管理插件从引入到退出的整个生命周期。

建议定义以下状态：

  {#each [
    ["DISCOVERED","发现插件或工具来源，尚未信任。"],
    ["INSPECTED","完成来源、清单、依赖和权限声明检查。"],
    ["VALIDATING","在受控环境中运行契约测试、安全检查和能力评测。"],
    ["APPROVED","通过对应治理门槛，获准在明确范围内使用。"],
    ["ACTIVE","已启用，并可以被符合条件的任务发现和调用。"],
    ["QUARANTINED","发现异常、版本不匹配或安全疑点，暂时停止调用。"],
    ["DISABLED","已停用，不再接受新调用。"],
    ["REVOKED","不再信任该版本或来源，阻止重新启用，除非完成正式复核。"]
  ] as item}


        {item[0]}


        {item[1]}


    {#if item[0]!=="REVOKED"}

    {/if}
  {/each}

## 7.1 安装与启用分开

下载一个插件不等于启用它。

建议安装过程先验证：

- 来源与完整性；
- 版本和依赖；
- 工具声明；
- 所需权限；
- 契约测试；
- 已知风险；
- 当前平台兼容性。

通过检查后，才允许在指定范围内启用。

## 7.2 升级必须产生新版本

不要原地覆盖正在使用的工具实现。

建议每次升级都创建新版本，记录变更内容、依赖和评测结果。

新版本可以先在候选环境运行，再通过相关任务的回归测试和治理门槛后替换稳定版本。

如果升级失败，应当能够恢复到已知稳定版本。正在执行的任务则应根据前面设计的配置快照与兼容性规则继续使用旧版本、迁移或安全暂停。

## 7.3 工具可以失去资格

工具注册并启用后，仍然可能因为以下情况被降级或停用：

- 输出契约反复失效；
- 失败率显著升高；
- 发生未授权访问；
- 费用异常增长；
- 当前版本出现已知缺陷；
- 外部服务长期不可用；
- 实际能力与声明不一致。

健康监测应将这些信息传递给 SHCRG，而是否停用、隔离或回滚则由工具治理与安全策略共同决定。

# 八、领域专用能力包：让专家使用专业技术，而不是堆提示词

这一部分直接回应你之前提出的 AST、编程优化，以及其他领域可能拥有特殊技术的问题。

我建议在工具治理层之上，建立可版本化的 **Capability Pack（能力包）**。

能力包不是单个工具，而是围绕某一类任务组织起来的一组能力资产。

## 8.1 编程专家能力包示例


    <title size="md">静态分析与 AST</title>
    语法树解析、符号提取、依赖分析、调用关系与诊断结果。



    <title size="md">代码编辑与重构</title>
    结构化代码修改、补丁生成、差异检查、冲突检测与格式保持。



    <title size="md">测试与验收</title>
    单元测试、静态检查、类型检查、集成测试和任务级验收。



    <title size="md">Git 与变更管理</title>
    独立工作区、变更集管理、版本比较、提交记录和受控合并。



    <title size="md">代码质量诊断</title>
    错误分类、根因证据、修复候选、回归风险和失败模式分析。


编程专家不需要知道每个工具的所有底层实现，但必须知道各能力的适用条件、前置要求、输出契约和验收标准。

例如，简单文本修改可以使用常规编辑工具；跨文件重构则可能要求 AST、符号索引和调用关系分析。

这不是让 AST 成为所有编程任务的固定步骤，而是让专家根据任务类型和风险选择适当的专业技术。

## 8.2 AI 漫剧能力包示例

漫剧能力包可以包含：

- 剧本结构化与分镜规划；
- 角色与场景素材管理；
- 图像生成与角色一致性检查；
- 视频生成与片段验收；
- 配音、音频处理与字幕生成；
- FFmpeg 合成；
- 产物索引与版本管理；
- 最终视频质量验收；
- 预算、重试与失败恢复。

每一项能力可以使用不同工具实现，但整个能力包应保持稳定的接口和验收语义。

例如，替换视频生成供应商时，不应该让整个漫剧专家重写；只要新工具满足所需契约，并通过适配与回归测试，就可以替换对应实现。

## 8.3 能力包也需要独立版本

建议每个能力包记录：

- 能力包 ID 与版本；
- 支持的任务类型；
- 所需工具及兼容版本；
- 前置条件；
- 权限与资源需求；
- 工作流模板；
- 验收规则；
- 评测集；
- 已知限制；
- 变更历史；
- 依赖和回滚方案。

能力包可以独立升级，但升级后的行为仍然必须受到任务配置快照、发布治理和回归测试的约束。

# 九、工具进化：如何判断一个工具是否真的值得保留？

工具数量增加不等于能力增强。

假设 EvoAgent 安装了五个功能相似的代码分析器，其中两个长期没有带来额外收益，一个在复杂项目中经常失败，另一个只在旧环境中工作。

如果没有工具评测和治理，注册表就会越来越复杂，工具选择成本也会增加。

因此，建议让工具本身也接受评测，但必须区分：

- 工具实现是否正确；
- 工具是否适用于某类任务；
- 工具相对其他工具是否有实际优势；
- 工具是否值得承担维护和资源成本。

## 9.1 建立工具评测体系

每个重要工具应当有相应的测试：

| 评测维度 | 示例 |
|---|---|
| 契约正确性 | 输入校验、输出 Schema、错误格式 |
| 能力有效性 | 是否完成声明的具体操作 |
| 结果可靠性 | 是否存在漏检、误报或错误产物 |
| 资源表现 | 延迟、内存、CPU、GPU 与外部费用 |
| 恢复能力 | 超时、取消、重试和未知状态处理 |
| 安全性 | 权限边界、路径限制、凭据与网络访问 |
| 兼容性 | 不同平台、依赖和上下游版本 |
| 维护成本 | 安装难度、依赖复杂度、故障诊断难度 |

工具评分不能只依赖它自己的输出。例如，代码分析器报告“没有错误”，不代表它真的没有漏检。评测应该使用已知结果的测试案例，验证实际能力。

## 9.2 工具评测结果应反馈到路由和能力治理

如果工具 A 在简单任务上速度更快，而工具 B 在复杂任务上准确率更高，系统可以形成条件化的工具选择策略。

如果某工具在新版本中退化，则可以降低其适用范围、暂停新任务调用或回滚到稳定版本。

但不能仅凭某一次失败就立即永久淘汰工具。应根据问题类型、样本规模、影响程度和可复现性决定处理方式。

## 9.3 工具选择也必须考虑成本上限

对于一个需要十几步执行的任务，工具调用成本可能远远超过最初的一次模型请求。

因此，工具治理应当与预算系统共享同一套任务级约束。

工具可以报告预计成本，但最终能否执行仍由资源调度和授权策略决定。

当工具实际成本高于预计成本时，应更新预算记录，并根据任务策略决定是否继续、降级或暂停。

# 十、工具系统如何与其他专项协作？

工具治理不是一个孤立的模块。它需要与前面已经设计的系统形成明确的接口。

| 相关系统 | 工具治理需要提供或接收的内容 |
|---|---|
| Router | 各专家可用能力、平台约束和工具适用范围 |
| Planner / TODG | 工具前置条件、输入输出契约、依赖与恢复语义 |
| ReAct | 可调用工具的受限清单、执行结果与错误分类 |
| Memory Engine / MEEG | 工具使用经验、失败案例、验证过的适用条件 |
| Context Engine | 工具 Schema、必要说明、当前可用性和结果摘要 |
| ASEGE | 权限决策、执行环境要求、风险分类和审计 |
| SHCRG | 工具健康指标、失败率、成本趋势与版本退化 |
| SIEC | 事件、状态、版本、执行结果和跨模块关联协议 |
| TLCIG | 任务隔离、并发配额、资源租约、取消与恢复 |
| RCAE | 工具故障证据、诊断假设与候选修复建议 |

这里有一个重要的设计原则：

**工具运行时负责可靠地执行操作，但不应该替代专家的领域判断，也不应该自己决定任务已经满足最终目标。**

例如，FFmpeg 工具可以确认编码进程已经结束；漫剧工作流仍然需要检查视频时长、分辨率、音轨、画面连续性和其他交付要求。

同样，AST 工具可以返回符号引用分析结果；编程专家仍然需要判断这些结果是否足以支持当前重构方案。

# 十二、下一专项：上下文工程与推理过程治理

现在，我们已经设计了专家、工具、任务 DAG、记忆、经验进化、资源调度与安全治理。

但还有一个核心问题值得专门研究：

**当智能体拥有大量记忆、工具、历史任务、工作流和专业知识时，究竟应该向模型提供什么信息、以什么顺序提供、提供多少，以及如何判断这些上下文真正帮助了推理？**

这是一个不能仅靠增加上下文窗口解决的问题。

例如：

- 编程专家检索了 50 条历史经验，但真正相关的只有 3 条；
- Planner 生成了很长的计划，执行时却遗漏了用户最初的硬性约束；
- ReAct 每轮都重新注入完整历史，导致 Token 成本持续增长；
- 上下文压缩删除了失败恢复所需的关键状态；
- 不同专家共享同一种压缩策略，导致领域特定信息被错误丢弃；
- 工具结果包含大量日志，挤占了真正重要的任务目标；
- 长任务中模型切换后，原有上下文结构不再适配新模型。

下一专项建议定义为：

**Context Engineering & Reasoning Governance（上下文工程与推理治理，简称 CERG）。**

重点研究：

1. 如何区分系统规则、当前指令、任务状态、记忆、工具结果和历史推理材料；
2. 如何构建按任务阶段变化的动态上下文，而不是每轮重复拼接所有历史；
3. 如何在压缩过程中保留硬约束、未完成状态、关键证据和失败恢复信息；
4. 如何为不同专家设计独立的上下文策略，同时复用必要的通用机制；
5. 如何在 Planner、ReAct、DAG 节点和工具调用之间传递最小充分信息；
6. 如何评估上下文检索的相关性、遗漏率、冗余度与实际收益；
7. 如何管理 Token 预算、上下文窗口、成本和延迟；
8. 如何防止记忆、网页、工具输出中的不可信内容污染高优先级指令；
9. 如何在模型切换、任务恢复和版本升级时保持上下文语义一致；
10. 如何通过实验验证某种上下文组织方式是否真正提高了成功率、稳定性和效率。

这一专项会直接影响 EvoAgent 的整体质量和调用成本：不仅要让模型获得更多信息，更要让它在正确的时间获得真正有用、可信、适用的信息。
