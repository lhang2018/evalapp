## 第三份基线：EvoAgent 产品能力覆盖与缺口台账

<WritingBlock id="62483" variant="document"># EvoAgent 产品能力覆盖与缺口台账

**文档编号：** EA-DELIVERY-003  
**版本：** 1.0  
**性质：** 产品需求、技术实现、验收证据之间的追踪台账  
**目标：** 将已有架构设计转化为有明确优先级、实施责任和验收条件的开发工作。

## 一、状态口径

本台账严格区分设计状态、代码实现状态和产品验收状态。

| 状态 | 含义 |
|---|---|
| 已有设计 | 正式文档已定义相关职责或规则 |
| 待补充设计 | 方向已明确，但仍缺少实现所需的具体规则 |
| 待代码核验 | 需要检查实际源码、依赖和入口 |
| 待测试 | 需要实际执行测试并保存结果 |
| 已验收 | 具有真实运行证据和符合要求的验收记录 |

**当前限制：** 现有正式文档能够证明设计基线已经建立，但不能单独证明各模块已经完成编码或通过端到端测试。因此，下表将未获得实现证据的模块统一标记为“待代码核验”，不预设它们一定不存在。

## 二、P0：产品成立所需的核心能力

这些能力决定 EvoAgent 能否从技术实验变成可用产品。

| ID | 能力 | 用户可见价值 | 必须具备的技术能力 | 验收证据 |
|---|---|---|---|---|
| P0-01 | 统一任务入口 | 用户只需描述目标 | 输入解析、任务创建、会话关联 | 真实输入能形成可追踪任务 |
| P0-02 | 任务契约 | 系统理解目标和约束 | 目标、约束、产物、验收标准、预算 | 关键约束在执行中得到保留 |
| P0-03 | 任务状态管理 | 用户知道进展和结果 | Task/Run/Node 状态机、持久化 | 状态转换合法且重启后可恢复 |
| P0-04 | 模型调用 | 实际使用配置的模型 | 模型适配、超时、错误处理、成本记录 | 真实服务调用成功并记录结果 |
| P0-05 | 工具执行 | 系统能实际完成操作 | 工具注册表、Schema、Tool Gateway | 真实工具执行且参数经过校验 |
| P0-06 | 动作安全控制 | 防止越权或错误操作 | Action Guard、审批、权限策略 | 未授权动作被阻断 |
| P0-07 | 任务规划与执行 | 多步骤工作能够推进 | Planner、ReAct、DAG Runtime | 多步骤任务实际运行并保存状态 |
| P0-08 | 结果验收 | 防止假完成 | 验收契约、独立 Evaluator | 不合格结果不能标记为成功 |
| P0-09 | 成果交付 | 用户得到可使用的产物 | 文件管理、结果索引、交付接口 | 真实产物存在、可访问且符合要求 |
| P0-10 | 预算与停止 | 避免无限调用 | 预算账本、步数限制、超时、取消 | 达到限制后停止新增调用 |
| P0-11 | 失败恢复 | 失败后可以恢复或明确终止 | 检查点、幂等键、副作用账本 | 恢复不会盲目重复外部动作 |
| P0-12 | 运行追溯 | 可以定位失败原因 | 事件协议、运行 ID、Runtime Manifest | 能追溯任务使用的关键版本和错误 |
| P0-13 | 基础交互界面 | 用户能够操作产品 | 首页、任务工作区、结果页面 | 能完成一项真实端到端任务 |
| P0-14 | 端到端测试 | 证明产品确实可用 | 自动化测试、真实服务测试、验收报告 | 核心任务通过可重复的真实测试 |

**实施要求：** P0 必须以真实任务闭环验收，不能以接口存在、Mock 返回成功或单元测试通过代替完整产品验收。

## 三、P1：可靠性、长期使用与效率提升

| ID | 能力 | 用户可见价值 | 技术支撑 | 验收证据 |
|---|---|---|---|---|
| P1-01 | 专家路由 | 自动选择合适的专业能力 | 路由评分、专家注册、置信度阈值 | 路由评测集通过，低置信度能够回退 |
| P1-02 | 分层记忆 | 减少重复解释 | 用户、项目、专家、会话和任务记忆 | 信息隔离、纠错和过期处理测试通过 |
| P1-03 | 上下文治理 | 长任务中不丢失关键要求 | ContextManifest、检索、压缩 | 压缩后硬约束和验收标准仍然保留 |
| P1-04 | 工作流复用 | 重复任务更快完成 | DAG Runtime、资产注册、版本管理 | 同一工作流能够重复执行并通过验收 |
| P1-05 | 工具健康治理 | 减少工具故障导致的失败 | 健康检查、契约测试、故障分类 | 能区分工具异常与模型或路由异常 |
| P1-06 | 诊断与案例库 | 从真实失败中找到问题 | 运行轨迹、诊断案例、根因假设 | 诊断结论有证据并可独立验证 |
| P1-07 | 资源隔离 | 后台活动不影响主任务 | 优先级队列、并发限制、资源配额 | 并行负载测试满足核心任务门槛 |
| P1-08 | 主动增强 | 任务完成后获得额外帮助 | 机会筛选、相关性评估、独立队列 | 建议非阻塞，低价值建议能够被过滤 |
| P1-09 | Android 离线恢复 | 断网或重启后保留进度 | 本地事件队列、检查点、同步协调 | 断网、重启和恢复同步测试通过 |
| P1-10 | 用户控制 | 用户能够调整能力和主动性 | 设置界面、权限管理、主动等级 | 设置生效，关闭主动智能不影响核心任务 |

## 四、P2：持续进化与领域能力扩展

| ID | 能力 | 用户可见价值 | 技术支撑 | 验收证据 |
|---|---|---|---|---|
| P2-01 | 候选改进生成 | 系统能提出针对真实问题的改进 | Evolution Controller、候选资产 | 每项候选关联明确问题和基线 |
| P2-02 | 独立自动评测 | 判断改进是否真正有效 | 回归集、隐藏测试、对照实验 | 质量、成本、安全和兼容性结果完整 |
| P2-03 | 受控自动发布 | 低风险改进可以减少人工维护 | Evaluation Gate、Release Controller | 未通过门禁的候选无法发布 |
| P2-04 | 自动回滚 | 退化版本可以快速恢复 | 版本指针、健康检查、回滚机制 | 注入故障后能恢复稳定版本 |
| P2-05 | 主动目标管理 | 跟进长期项目和用户明确目标 | Goal Registry、停止条件、预算 | 目标可以暂停、完成或因无进展而停止 |
| P2-06 | 编程专家 | 完成专业代码任务 | AST、LSP、测试、构建、代码审查 | 实际代码变更通过项目测试 |
| P2-07 | 手机操作专家 | 执行更多受控 Android 操作 | 原生桥接、无障碍、视觉识别 | 每种操作有明确授权和结果验证 |
| P2-08 | AI 漫剧专家 | 交付可播放的视频成果 | 生成服务、素材库、FFmpeg、质量检查 | 真实视频通过文件和内容验收 |
| P2-09 | 跨端扩展 | 同一能力能够跨设备复用 | 统一协议、能力契约、版本治理 | 不同终端通过对应兼容性测试 |

P2 的能力并非不重要，而是必须建立在核心任务链、可靠性和独立评测机制之上。任何领域专家都不能绕过共享安全边界。

## 五、需要重点核验的架构与代码对应关系

现有架构将系统划分为八个逻辑服务和四个受保护控制器。这些职责应当在代码中找到清晰的实现边界，但不意味着必须部署为十二个独立进程。

### 5.1 八个逻辑服务

| 逻辑服务 | 代码核验重点 | 主要风险 |
|---|---|---|
| SV-01 任务编排 | 状态机、路由、Plan、ReAct、DAG、恢复 | 任务状态错乱或无限循环 |
| SV-02 模型网关 | 供应商适配、超时、限流、成本记录 | 调用失败被掩盖或成本失控 |
| SV-03 能力与工具 | 工具、专家、工作流注册及依赖 | 未注册或不兼容能力被调用 |
| SV-04 记忆与上下文 | 命名空间、检索、压缩、来源追踪 | 记忆污染、关键信息丢失 |
| SV-05 同步与观测 | 事件存储、幂等同步、版本关联 | 记录丢失或重复同步 |
| SV-06 进化与诊断 | 失败案例、根因假设、候选生成 | 诊断错误直接影响生产 |
| SV-07 评测与门禁 | 独立评测、安全与兼容性检查 | 候选自行修改评价标准 |
| SV-08 版本分发 | 签名、灰度、激活、回滚 | 错误版本进入稳定执行 |

### 5.2 四个受保护控制器

| 控制器 | 必须独立保证的权责 | 重点验收 |
|---|---|---|
| CTRL-01 Runtime Controller | 执行状态、权限、预算、取消和恢复 | 所有外部动作受统一控制 |
| CTRL-02 Evolution Controller | 生成候选、分配实验预算、管理停止条件 | 不能自行批准生产发布 |
| CTRL-03 Evaluation Gate Controller | 独立判断质量、安全和兼容性 | 候选不能修改自身门槛 |
| CTRL-04 Release Controller | 控制稳定版本、灰度、激活和回滚 | 发布和回滚过程可追溯 |

实现时应优先保证模块职责和信任边界，而不是为了形式上的架构完整，过早拆分大量微服务。

## 六、统一缺口优先级规则

当代码审核发现多个缺口时，按照以下顺序处理：

1. **P0-A：安全与数据完整性。** 未授权动作、状态丢失、重复副作用、越权发布。
2. **P0-B：任务闭环缺失。** 不能真实调用模型或工具、无法验证结果、不能交付产物。
3. **P0-C：核心稳定性。** 取消、超时、预算、恢复和错误处理失效。
4. **P0-D：可观测性缺失。** 失败无法定位、版本无法追溯、测试无法复现。
5. **P1-A：执行质量与效率。** 路由错误、上下文丢失、工作流不稳定、重试不合理。
6. **P1-B：产品体验。** 用户看不到进度、结果或需要处理的异常。
7. **P2：能力扩展。** 新专家、复杂主动目标、更多跨端能力。

优先级应由实际缺口及其对用户任务的影响决定。不能因为某个新技术模块更有趣，就优先于已经影响任务完成的故障。

## 七、每个缺口必须具备的记录

每项缺口至少记录以下字段：

| 字段 | 要求 |
|---|---|
| 缺口 ID | 稳定且唯一 |
| 对应 PRD | 指明受影响的产品需求 |
| 用户影响 | 说明用户会遇到什么问题 |
| 代码位置 | 核验后填写实际文件、类或函数 |
| 当前证据 | 代码、日志、测试结果或复现步骤 |
| 根因判断 | 区分已证实根因与待验证假设 |
| 修复方案 | 描述最小有效改动及其影响范围 |
| 回归范围 | 明确必须重跑的测试 |
| 验收标准 | 说明什么结果代表问题已解决 |
| 发布与回滚 | 说明如何安全激活和恢复 |

在代码位置、根因和验收证据尚未核验前，不应把缺口描述成已经确认的代码缺陷。

## 八、项目状态与完成判定

每个功能使用以下状态之一：

- `DESIGN_ONLY`：只有设计。
- `IMPLEMENTATION_UNKNOWN`：需要核验实现情况。
- `IMPLEMENTED_UNVERIFIED`：代码已存在，但没有充分测试证据。
- `TESTING`：正在执行测试。
- `ACCEPTED`：已满足验收条件。
- `BLOCKED`：受到外部依赖或其他条件阻塞。
- `DEPRECATED`：已被明确废弃。

功能从设计到验收必须经过证据验证。不得因为存在接口、Mock 或演示页面，就将其标记为可用。

## 九、下一阶段的交付要求

产品与工程工作继续并行。

产品侧需要完成：
1. 冻结首批真实用户任务；
2. 明确每个任务的输入、产物、验收标准和异常处理；
3. 定义用户界面和任务状态的对应关系；
4. 明确主动帮助的范围、频率和非干扰条件；
5. 将用户价值指标与进化评测指标建立关联。

工程侧由实际代码审核确定：
1. 哪些核心模块已经实现；
2. 哪些模块仅有接口或 Mock；
3. 哪些能力已经通过单元测试但尚未通过端到端测试；
4. 哪些缺口会阻塞第一条真实任务链；
5. 下一轮最小且有效的修复集合。

最终目标是让每个重要的技术改动都能回答一个产品问题：它让用户完成哪项任务变得更好，依据是什么，以及如何证明没有破坏其他能力。

**本台账的最终验收标准：任何核心产品功能都能追溯到真实实现、测试证据和用户价值，而不是停留在设计清单中。**</WritingBlock>

## 下一步：把“有能力”转成“用户能用”

接下来最有价值的工作，是形成第四份基线：**《EvoAgent 首发产品定义与完整用户体验流程》**。

它将明确从安装应用、首次启动、发起任务、授权、执行、查看结果，到长期使用、主动帮助和能力升级的完整用户旅程，并区分首发必须可用的功能与后续逐步开放的功能。

这一步会把目前的产品架构真正转化为用户能够理解和使用的产品，而代码审核继续独立进行。
