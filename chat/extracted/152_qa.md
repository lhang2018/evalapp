## ChatGPT

核心思路是：**不要把一次成功的 Agent 对话直接保存成工作流，而是把它提炼成一份可执行、可验证、可复用、可版本化的流程定义。**

对于 EvoAgent，我建议建立一个独立的 **Workflow Compiler（工作流编译器）+ Workflow Runtime（工作流运行时）+ Workflow Evolution（工作流进化系统）**。

它们分别解决三个问题：

- **编译器：** 从一次跑通的任务中，提取哪些步骤可以固定，哪些步骤需要动态决策。
- **运行时：** 按照流程执行任务，处理分支、重试、异常、状态持久化和结果验收。
- **进化系统：** 根据多次运行的数据，发现瓶颈、提出改进、进行对比实验，并决定是否升级稳定流程。

比如，你第一次让 EvoAgent 制作 AI 漫剧，它可能需要反复探索剧本生成、角色设定、镜头生成、配音和剪辑的顺序。等整个流程跑通后，它就不应该每次都重新探索，而应该把经过验证的步骤保存为一个正式的工作流。

以后你只需要说：“帮我制作一部新的 AI 漫剧”，智能体就调用这条已经验证的工作流，只把新故事、角色、时长和预算作为参数传入。

注意，**一次成功只能产生候选工作流，不能直接证明它已经稳定。** 如果流程只在一个故事、一个模型或一次运行中成功，它可能只是碰巧跑通了。

我建议至少区分三个状态：

- `Draft`：从成功轨迹提炼出的候选流程。
- `Validated`：经过独立测试和回归验证的流程。
- `Stable`：正式发布、可以被默认调用的流程。

此外，`Deprecated` 和 `RolledBack` 用来管理废弃版本和回滚版本。

## 二、工作流不能只是录制操作，而要提炼出可复用的执行逻辑

这是整个系统最关键的设计。

假设你第一次制作漫剧时，智能体完成了以下步骤：

1. 生成剧本。
2. 生成角色参考图。
3. 生成分镜。
4. 生成视频片段。
5. 生成配音。
6. 合成视频。
7. 检查成片。
8. 修复一个字幕时间错误，再次合成。

如果只是把这八步按顺序录下来，得到的只是一个“操作录像”，不是成熟的工作流。

因为下一次可能出现不同情况：

- 角色参考图生成失败。
- 视频模型返回的时长不符合要求。
- 配音比镜头长。
- 合成后发现音画不同步。
- 某个模型不可用，需要换一个工具。

因此，EvoAgent 必须把执行轨迹提炼成**带有条件、数据契约、分支和恢复策略的任务图**。

例如：

<CodeBlock language="mermaid" editable={false}>flowchart TD
    A[解析创作需求] --> B[生成剧本]
    B --> C[生成角色设定]
    C --> D{角色设定验收}
    D -->|通过| E[生成分镜]
    D -->|失败| C
    E --> F[生成视频片段]
    E --> G[生成配音与字幕]
    F --> H[合成成片]
    G --> H
    H --> I{成片质量检查}
    I -->|通过| J[交付成片]
    I -->|音画问题| K[调整时间线]
    I -->|画面问题| L[重做指定镜头]
    K --> H
    L --> H</CodeBlock>

这里最重要的变化是：流程不仅知道“下一步是什么”，还知道**什么条件下执行下一步、失败后从哪里恢复、什么情况才算成功**。

而且，视频生成与配音生成可以并行执行，不必无谓地等待前一个任务完全结束。

## 四、把流程保存为版本化的 Workflow Definition

不要把工作流只存进数据库的一段文本，也不要把它写死在 Python 代码里。

我建议使用 **YAML 或 JSON 作为工作流定义格式**，数据库保存版本、状态和运行记录，Git 保存经过审查的工作流源文件。

例如，漫剧流程可以保存为 `workflows/comic_drama/v1.yaml`：

<CodeBlock language="yaml" editable>
workflow:
  id: comic_drama
  version: 1.0.0
  name: AI 漫剧制作
  input_schema:
    title: string
    duration_seconds: integer
    style: string
    budget_usd: number

  limits:
    max_parallel_tasks: 3
    max_retries_per_node: 2
    max_total_cost_usd: "$input.budget_usd"

  nodes:
    - id: script
      type: agent
      capability: story_planner
      input:
        title: "$input.title"
        style: "$input.style"
      output_schema: script_v1

    - id: characters
      type: agent
      capability: character_designer
      depends_on: [script]
      output_schema: character_bible_v1

    - id: storyboard
      type: agent
      capability: storyboard_planner
      depends_on: [characters]
      output_schema: storyboard_v1

    - id: video
      type: tool
      capability: video_generator
      depends_on: [storyboard]
      retry:
        max_attempts: 2
        on: [timeout, transient_provider_error]

    - id: voice
      type: tool
      capability: tts_generator
      depends_on: [storyboard]

    - id: assemble
      type: tool
      capability: ffmpeg_assembler
      depends_on: [video, voice]

    - id: quality
      type: tool
      capability: quality_gate
      depends_on: [assemble]

  terminal:
    success_when: "quality.passed == true"
</CodeBlock>

这段 YAML 是建议采用的工作流定义示例。要真正运行，还需要相应的 Schema、表达式解析器、节点注册表和执行引擎；不能直接把 YAML 当作已经实现的程序。

几个设计原则值得固定下来：

- `workflow.id` 标识工作流，`version` 标识不可变版本。
- `input_schema` 明确用户可以传入什么。
- `depends_on` 明确任务依赖，支持自动构建 DAG。
- `output_schema` 规定每个节点必须交付什么。
- `retry` 明确哪些错误可以重试。
- `terminal` 明确整个工作流什么时候算完成。
- 预算、权限和并发限制由运行时强制执行，而不是仅依赖模型遵守 YAML 中的文字描述。

未来你开发新能力时，只需要新增工具适配器和工作流定义，就能复用同一套运行时。

## 五、如何从一次成功运行中，自动提炼出工作流？

这里需要一个独立模块：`WorkflowCompiler`。

它不是简单地把日志交给大模型总结，而是分成五个步骤。

<list marker="number" gap={2}>
  <list-item>**收集执行轨迹。** 记录每个步骤的输入摘要、输出引用、工具名称和版本、耗时、费用、错误、重试、最终验证结果。</list-item>
  <list-item>**识别可复用的步骤。** 将多次出现的相似操作归并成候选节点，例如“生成字幕”或“验证视频文件”。同一工具的重复调用不一定代表同一种业务步骤。</list-item>
  <list-item>**识别数据依赖。** 根据真实输入输出建立依赖关系，而不是只根据步骤发生的先后顺序。例如视频生成与配音生成都依赖分镜，因此可以并行。</list-item>
  <list-item>**提取异常分支。** 从失败轨迹中归纳超时重试、备用工具、重新生成和人工接管等策略。未经过测试的恢复路径不能直接进入稳定版。</list-item>
  <list-item>**生成候选工作流。** 输出 YAML/JSON 定义、输入输出 Schema、测试用例和来源轨迹的引用，交给验证器，而不是直接发布。</list-item>
</list>

这里有一个特别容易忽略的问题：**执行轨迹不是可信的程序规格。**

日志里可能包含模型幻觉、错误的工具调用、偶然成功的路径，甚至由错误前提导致的结果。因此，编译器必须结合工具契约、任务成功标准和独立评测来判断哪些步骤值得固化。

例如，某次漫剧成功是因为视频模型返回了一个特别好的镜头，并不意味着相同提示词每次都会得到同样的结果。能固化的是调用协议、参考图约束、预算策略和验收逻辑，而不是把一次随机生成的结果当成普遍规律。

## 六、固定流程和动态 Agent 应该如何共存？

这是 EvoAgent 和传统自动化工作流的关键区别。

我不建议所有任务都被强制固化成完全固定的流程，也不建议所有任务都由 Agent 每次自由规划。

应该采用三种运行模式。

<box gap={3}>
  <box border radius="lg" padding={3} gap={1}>
    <title size="md">模式 A：固定工作流</title>
    <badge color="success">稳定优先</badge>

    适合重复性高、步骤明确、成功条件可客观验证的任务。

    例如：把已批准的视频素材按指定时间线合成、压制字幕、导出 MP4、检查文件。

    <text color="secondary" size="sm">运行时按已发布的 DAG 执行，不需要重新规划整个流程。</text>
  </box>
  <box border radius="lg" padding={3} gap={1}>
    <title size="md">模式 B：工作流内嵌 Agent</title>
    <badge>推荐默认模式</badge>

    适合主流程相对固定，但部分步骤需要模型判断的任务。

    例如：漫剧制作的步骤固定，但剧本、镜头设计和失败原因分析需要模型辅助。

    <text color="secondary" size="sm">工作流控制任务顺序和权限，Agent 只负责被授权的局部决策。</text>
  </box>
  <box border radius="lg" padding={3} gap={1}>
    <title size="md">模式 C：动态规划</title>

    适合首次遇到的新任务、需求不完整或者没有成熟工作流的任务。

    例如：用户要求完成一个系统尚未支持的复杂创作项目。

    <text color="secondary" size="sm">Agent 可以规划并探索，但受工具白名单、预算、执行步数和风险策略约束。任务成功后，再评估是否值得沉淀成工作流。</text>
  </box>
</box>

最理想的运行逻辑是：

`用户目标 → 匹配已有工作流 → 判断适用性 → 执行或动态规划 → 验收 → 记录 → 必要时提炼新工作流`

如果现有工作流已经适用，优先复用。如果只是部分适用，可以在明确的扩展点内执行。如果完全不适用，就回到动态规划模式。

## 七、工作流本身也需要版本管理和独立进化

我建议为每条工作流维护自己的版本历史，而不是跟随 Agent Core 一起整体更新。

例如：

</box>

每次运行都必须绑定一个确定的工作流版本。运行过程中即使有新版本发布，也不应自动改变当前任务使用的流程。

进化系统可以提出两类改进：

- **参数级改进：** 调整重试次数、并发上限、预算分配、提示词版本等。经过允许的测试后，可以自动晋级。
- **结构级改进：** 增加节点、改变依赖关系、修改恢复分支或替换工具。需要更严格的回归测试，必要时要求人工批准。

一条新工作流能否晋级，不应只看成功率，还要检查成本、耗时、失败恢复、安全约束和最终结果质量是否退化。

| `trace_events` | 保存运行过程中的结构化事件 |
| `workflow_evaluations` | 保存候选版本的测试结果和指标 |
| `workflow_releases` | 保存发布、回滚和版本切换记录 |
| `evolution_proposals` | 保存自动发现的问题和改进提案 |

需要额外强调：大体积的视频、图片和音频文件应存入素材存储，而不是直接塞进数据库。数据库保存资产 ID、路径或对象存储 URI、哈希值、版本和元数据。

### 运行时的核心伪代码

```python
async def run_workflow(workflow, inputs):
    validate_input(workflow.input_schema, inputs)

    run = await create_run(
        workflow_id=workflow.id,
        workflow_version=workflow.version,
        inputs=inputs,
    )

    while not run.is_terminal():
        ready_nodes = await scheduler.find_ready_nodes(run)

        if not ready_nodes:
            await scheduler.check_deadlock_or_wait(run)
            continue

        for node in ready_nodes:
            await action_guard.check(node, run)

            try:
                result = await execute_node(node, run)
                await validate_output(node.output_schema, result)
                await checkpoint.save(run, node, result)
            except Exception as error:
                await recovery.handle(run, node, error)

    return await verify_terminal_result(run)
```

这段是结构示意，不是可以直接运行的完整实现。真正的执行器还需要处理并行节点的同步、持久化事务、进程崩溃、重复执行、取消和恢复。

对于视频生成这类可能耗时很长、涉及付费调用的任务，必须特别处理幂等性：如果请求超时，不应不加判断地再次提交生成任务，否则可能重复扣费。

## 九、我建议把第一阶段的目标定得非常明确

先不追求一个可以自动生成所有工作流的万能系统，而是完成以下闭环：

1. 手动定义一条简单的工作流，并成功运行。
2. 自动记录所有节点的输入输出、工具调用、错误和验收结果。
3. 从成功运行轨迹中生成一份候选工作流定义。
4. 对候选工作流进行 Schema 检查、依赖检查和安全检查。
5. 用不同输入重复执行候选流程。
6. 与稳定版本比较成功率、耗时、成本和错误类型。
7. 通过发布门禁后，创建一个不可变的新版本。
8. 新任务开始时，自动选择适合的稳定工作流。
9. 如果新版本表现退化，停止晋级或回滚到旧版本。

**最终要形成的不是一堆越来越复杂的提示词，而是一个不断积累、验证和复用可靠工作流的系统。**

还有一个非常重要的取舍：不必让智能体把每个成功任务都编译成工作流。只有重复出现、具备稳定输入输出、能够定义验收条件的任务，才值得固化。偶发任务可以继续使用动态规划；固定步骤中需要判断的部分，则保留为受控 Agent 节点。

这样，EvoAgent 才能同时拥有两种能力：面对新任务时灵活探索，面对已经跑通的任务时稳定、快速、低成本地重复执行。
