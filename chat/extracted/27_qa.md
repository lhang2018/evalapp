# EvoAgent 深度设计第六轮：模型切换后，如何保留能力而不是推倒重来？

这一轮，我们要解决你最初提出的一个核心目标：

> EvoAgent 应该能够针对当前的大语言模型、工具和运行环境不断适配，形成一个稳定、可靠的版本。当未来更换模型时，旧版本的成果完整保留，从新的模型分支继续进化，而不是重新开始。

我认为这里有一个特别重要的架构判断：

**我们不应该把“智能体版本”与“模型版本”绑定成同一个东西。**

如果 EvoAgent 的每次发布都只是一个整体快照，那么切换模型时，我们很难区分哪些能力可以直接复用，哪些策略只适用于旧模型，哪些问题来自模型本身，哪些来自 Harness、上下文、工具或记忆系统。

更合理的方式，是把智能体看成一组有依赖关系、能够独立版本化的能力资产，并让每个发布版本明确记录这些资产的组合。

这样，模型切换就不再是“重新做一个智能体”，而是一次有控制、有证据的**能力迁移与重新适配过程**。

## 一、第一性原理：什么才是应该被保存的“能力资产”？

假设 EvoAgent 已经在模型 A 上运行了一段时间，形成了一个稳定的编程专家。

它可能包含：

- 通用 ReAct 执行引擎。
- 编程专家的系统提示词。
- 特定模型的上下文组装策略。
- 代码工具的调用与恢复策略。
- 编程领域记忆和项目知识。
- 代码修复工作流。
- 模型 A 的适配配置。
- 经过验证的评测集与运行证据。
- 生产环境的稳定发布配置。

现在我们准备切换到模型 B。

这些资产不应该被简单地整体复制或整体废弃，因为它们与模型的关系并不相同。


    <title size="lg">可以直接保留的资产</title>
    例如领域任务定义、工具契约、经过确认的项目知识、测试案例和用户明确约束。这些资产通常不依赖某个特定模型，但仍需检查格式、权限和接口兼容性。



    <title size="lg">可以继承，但需要重新验证的资产</title>
    例如 ReAct 策略、规划规则、记忆检索方法、错误分类与恢复策略。它们可能具有通用价值，但在新模型上的效果不一定相同。



    <title size="lg">需要独立适配的资产</title>
    例如模型专用提示词、结构化输出模式、工具调用参数、上下文预算、模型路由和采样配置。这些都可能随模型能力、API 和限制变化。



    <title size="lg">必须重新验证的发布结论</title>
    例如旧模型上的成功率、成本效率、稳定性和发布资格。旧模型上的评测结果不能直接证明新模型也具有相同表现。


这里需要严格区分两件事：

- **资产可以保留。**
- **资产在新环境中的有效性需要重新证明。**

例如，Python 异步调试能力的定义不需要因为换模型而改变，但其提示词、工具调用策略和实际成功率可能发生变化。

因此，EvoAgent 应当保留原有能力定义和证据，同时为新模型建立独立的实现版本和验证记录。

# 二、最重要的设计：模型、能力、环境、发布，四条版本线独立管理

我建议 EvoAgent 正式采用四条相互关联、但不互相替代的版本线。




      **A. 模型适配线**

    记录模型提供方、模型标识、API 版本、上下文限制、工具调用能力、结构化输出支持、已知限制和适配配置。
    示例：`model-A-adapter-v3`、`model-B-adapter-v1`





      **B. 能力实现线**

    记录编程、旅游、漫剧等领域的能力定义、提示词、规划策略、记忆策略、工具使用策略和工作流实现。
    示例：`coding-agent-v7`、`travel-planner-v4`





      **C. 运行环境线**

    记录工具版本、API 契约、依赖、执行环境、Android 版本、权限条件和外部服务配置。
    示例：`runtime-profile-v5`





      **D. 发布组合线**

    锁定某个正式版本实际使用的模型适配、能力实现、工具版本、运行环境和验收证据。
    示例：`evoagent-release-0.8.0`


为什么一定要分开？

假设编程专家从模型 A 切换到模型 B，但代码工具、编程能力定义和评测集都没有变化。

如果所有东西都绑定在一个版本里，我们可能不得不复制整套智能体，并在新分支中维护大量重复资产。

但采用四条版本线后，我们只需要：

1. 保留模型 A 的适配档案。
2. 创建模型 B 的新适配档案。
3. 让编程专家在候选发布中引用模型 B 的适配。
4. 重新运行必要的能力测试。
5. 生成新的发布组合。

其他经过验证且兼容的资产可以继续复用。

**这不是简单地把模型名做成配置项，而是让系统知道每项能力究竟依赖哪个版本，以及换掉某个依赖之后，哪些结论需要重新验证。**

# 三、模型适配档案应该保存什么？

不能只保存 API 地址、模型名称和密钥。

模型适配档案应该描述这个模型在 EvoAgent 中的真实行为特征，以及我们对这些特征掌握了多少证据。

建议分成四部分。

| 部分 | 应记录的内容 |
|---|---|
| 身份与接口 | 提供方、模型 ID、API 版本、请求格式、结构化输出和工具调用协议 |
| 能力特征 | 指令遵循、规划、代码生成、长上下文处理、工具调用、视觉理解等能力的实测表现 |
| 资源与限制 | 上下文上限、速率限制、延迟、价格、并发限制和服务可用性 |
| 适配与证据 | 专用提示词、参数配置、兼容性测试、能力评测、失败模式和已知限制 |

其中有两个重要原则。

**第一，模型能力特征必须来自证据，而不是只相信模型说明文档。**

官方宣称支持工具调用，并不代表它在 EvoAgent 的实际工具协议下始终可靠。官方上下文窗口很大，也不代表它在接近上限时还能准确保留关键约束。

所以，档案应该同时保存声明值和实测值。

**第二，模型适配不是永久结论。**

模型提供方可能更新底层模型，改变 API 行为或调整限流规则。即使模型名称没有变化，原来的适配结论也可能失效。

因此，模型档案还应该关联验证时间、接口版本和已知变更记录，并在关键依赖变化后触发重新验证。

# 四、换模型后，不是所有测试都要从头运行

这是我们前面能力依赖图设计在这里的直接应用。

假设一个发布组合包含：

- 共享 ReAct 引擎。
- 编程专家。
- 模型 A 适配器。
- Python 执行工具。
- 编程记忆策略。
- 代码修复工作流。
- 代码质量验收器。

现在只更换模型 A 为模型 B。

应该先根据依赖图确定哪些资产受到影响，而不是机械地运行整个系统的所有测试。




      **仍然适用的基础测试**

      例如 Python 执行器自身的契约测试、固定输入输出的工具测试，以及不依赖模型的权限检查。若这些依赖未变化且证据仍然有效，可以复用其结果。






      **必须重新运行的模型相关测试**

      例如工具调用正确率、结构化输出、指令遵循、上下文约束保留、任务规划和代码修复成功率。






      **需要按风险决定是否扩展的测试**

      如果新模型改变了工具调用行为或上下文组织方式，就可能影响共享 ReAct 引擎及其他专家。此时应扩大测试范围，而不是只测试编程专家。



因此，我们应该让每个测试声明它验证的对象及其依赖，例如：

- 验证模型工具调用能力。
- 验证 ReAct 状态转换。
- 验证 Python 执行器接口。
- 验证编程专家端到端任务。
- 验证共享内核的安全约束。

这样，测试选择器可以根据变更清单和依赖图生成一份最小必要测试集，再根据风险增加额外测试。

不过，所谓“最小必要测试集”并不意味着只运行少量测试就能保证安全。它只是建立在依赖关系准确、组件契约完整的前提上。对高风险变更，仍然需要更广泛的回归测试和真实环境验证。

# 五、模型切换时，应该怎样建立新分支？

我建议将模型切换视为一次**适配分支迁移**，而不是直接修改生产配置。

例如，当前稳定版运行在模型 A 上。

<CodeBlock language="mermaid" editable={false}>flowchart TD
    S[稳定发布：模型 A + 编程专家 v7] --> F[创建模型 B 适配分支]
    F --> A[继承兼容的能力资产]
    A --> B[建立模型 B 适配档案]
    B --> C[运行模型兼容性测试]
    C --> D{基础兼容性通过？}
    D -->|否| E[记录失败并修复适配]
    E --> C
    D -->|是| G[运行能力回归测试]
    G --> H[对比质量、成本、延迟与风险]
    H --> I{满足发布门槛？}
    I -->|否| J[保留候选或放弃迁移]
    I -->|是| K[建立候选发布组合]
    K --> L[小流量或受控任务验证]
    L --> M{真实运行稳定？}
    M -->|否| N[停止推广并回滚]
    M -->|是| O[批准新稳定发布]
    O --> P[保留模型 A 的历史发布与适配档案]</CodeBlock>

这里的关键是：模型 B 的分支可以继承旧模型积累的知识和能力定义，但不能直接继承旧模型的有效性结论。

同时，模型 A 的稳定版继续保持可运行、可回滚。模型 B 的实验失败，不应该迫使系统修改模型 A 的生产配置。

## Git 分支应该怎样设计？

Git 可以管理提示词、代码、工作流定义、评测配置和适配档案等文本资产，但它不是所有运行数据的唯一存储系统。

我建议使用这样的分支策略：

```text
main
├── stable/model-A
├── adapt/model-B
│   ├── exp/tool-calling
│   ├── exp/context-policy
│   └── exp/planning
└── shared-capability
    ├── context-engine
    └── recovery-policy
```

每个分支都应该有明确的用途：

- `main`：经过验证的基础代码和公共契约。
- `stable/model-A`：当前模型 A 的稳定适配资产。
- `adapt/model-B`：模型 B 的适配和回归工作。
- `exp/*`：隔离的实验候选。
- `shared-capability/*`：共享组件的独立改进。

正式发布还需要生成不可变的发布清单，记录实际依赖的 Git 提交、模型 ID、工具版本、配置版本、评测报告和制品摘要。

**Git 分支是开发与实验隔离机制；发布清单才是还原某个稳定运行版本的依据之一。**

另外，模型 API 密钥、用户记忆、私有项目数据和大量原始运行日志不应直接进入普通 Git 分支。它们需要独立的密钥管理、数据存储、权限控制和保留策略。

# 六、旧模型上的经验，怎样迁移到新模型？

这是整个设计最有价值的部分。

假设模型 A 上积累了一条经验：

“在复杂编程任务中，先列出关键约束，再分步执行，可以降低遗漏率。”

模型 B 的规划能力可能更强，也可能对冗长提示词更敏感。

如果直接复制整份提示词，可能反而降低效果。

因此，我建议将旧模型的适配资产分成三类迁移：


    <title size="lg">第一类：直接继承的语义资产</title>
    例如能力定义、用户硬约束、领域知识、工具契约、工作流业务规则和验收标准。

    继承后仍需检查接口和环境兼容性，但通常不需要因为模型更换而重新发明。



    <title size="lg">第二类：需要重新适配的执行策略</title>
    例如提示词结构、上下文组织、Planning 深度、工具调用格式、重试策略和模型路由参数。

    保留旧版作为候选来源，在新模型上重新比较，而不是默认全部照搬。



    <title size="lg">第三类：需要重新建立的有效性证据</title>
    例如新模型的成功率、延迟、成本、工具调用稳定性和跨任务泛化表现。

    旧模型的证据保留在原档案中，不能直接替代新模型的验收结果。


我们还可以进一步建立一份“迁移映射表”，记录旧模型上的每项策略：

- 是否继承。
- 是否重新实现。
- 是否需要重新测试。
- 是否已经在新模型上验证。
- 是否存在新模型特有的限制。
- 是否值得继续维护旧模型专用分支。

这可以防止迁移过程变成一次不可控的大规模提示词重写。

## 七、模型 B 表现更差时，怎么办？

这是模型迁移设计必须提前考虑的情形。

如果模型 B 的成本更低，但工具调用可靠性下降，那么系统不应该只因为平均成本降低就自动替换模型 A。

可以考虑三种处理方式：

1. **调整模型 B 的适配策略。** 例如修改工具调用协议、上下文组织或验证流程，再进行有限实验。
2. **限定模型 B 的适用范围。** 例如让它处理低风险、简单的任务，而将复杂编程任务保留给模型 A。
3. **拒绝当前迁移。** 保留模型 A 的稳定发布，直到模型 B 达到规定门槛，或者未来出现新的改进方案。

这意味着，EvoAgent 不一定要强迫整个系统同时切换模型。

在模型能力差异明显时，可以采用**按任务类型或能力选择模型**的策略，但路由决策必须基于实测收益、延迟、成本和风险，并接受持续监测。

最终目标不是让所有专家都使用最新模型，而是为每类任务选择经过验证、符合预算和质量要求的模型组合。

# 八、如何判断某项能力真正具备跨模型兼容性？

我建议引入一个新的概念：**能力兼容性契约（Capability Compatibility Contract）**。

它不要求不同模型使用相同的提示词或内部推理方式，而是要求它们在特定条件下满足相同的外部行为要求。

例如，代码修复能力的契约可以规定：

- 输入包含代码、错误信息和用户约束。
- 输出必须包含可应用的修复结果。
- 不得擅自删除用户要求保留的功能。
- 必须运行指定测试，或者明确说明无法验证。
- 不得把“生成了代码”冒充成“代码已经修复成功”。

模型 A 和模型 B 可以采用完全不同的提示词、Planning 策略和工具调用方式，但最终都必须通过相同的能力契约测试。

这给模型迁移带来一个很大的好处：

**我们可以保持能力目标稳定，让具体实现随着模型变化，而不必每次都重新定义整个智能体。**

但能力契约不能覆盖所有质量差异。对于代码风格、创作质量和复杂规划等任务，还需要领域专用的质量评测；对于无法确定性判断的结果，还需要独立语义评测与必要的人工校准。

所以，跨模型兼容性应当由三部分共同决定：

1. 能力契约是否满足。
2. 领域质量是否达到要求。
3. 成本、延迟、安全和稳定性是否符合发布门槛。

## 九、V0.1 如何落地？

第一版不需要实现复杂的自动模型迁移算法，但应该预留正确的数据结构和发布流程。

建议先实现以下五个模块：

| 模块 | V0.1 实现 |
|---|---|
| 模型注册表 | 保存模型身份、API 版本、限制和适配档案 |
| 能力兼容性契约 | 定义能力输入输出、约束和验收标准 |
| 迁移实验器 | 对新模型运行基础兼容性测试和能力回归 |
| 版本与依赖清单 | 锁定每个发布版本的模型、能力、工具和配置 |
| 迁移发布控制器 | 评估质量、成本和风险，支持批准、拒绝和回滚 |

数据库可以增加：

- `model_profiles`：模型档案与接口版本。
- `model_adapters`：模型专用配置和策略版本。
- `compatibility_contracts`：能力兼容性契约。
- `migration_runs`：模型迁移实验记录。
- `release_manifests`：不可变发布依赖清单。
- `compatibility_results`：兼容性与回归测试结果。

实际发布时，应当同时记录模型提供方的模型标识、API 版本和可用的模型快照标识。如果服务商不提供不可变的模型快照，就必须承认模型行为可能发生变化，并通过周期性回归检测处理。

# 十一、现在还剩下哪个关键问题？

经过这几轮，我们已经逐渐形成了 EvoAgent 的核心架构：

- 能力图谱管理系统拥有哪些能力及其依赖关系。
- 经验迁移机制决定哪些经验可以共享。
- 进化决策中枢决定优先改进什么、投入多少资源。
- 独立评测系统验证改进是否真实有效。
- 模型适配与版本系统保证能力能够跨模型继承和重新验证。

但还有一个必须深入研究的问题：

**当 EvoAgent 在真实环境中长期运行时，它应该如何管理持续变化的世界？**

例如，工具突然失效、模型 API 行为改变、Android 系统升级、用户偏好发生变化，甚至一个昨天有效的工作流今天突然失败。

这些变化不一定来自智能体自身的缺陷。如果系统把所有异常都当成能力退化，就会不断修改提示词和策略；如果它只把问题归咎于外部环境，又可能错过真正需要改进的能力。

下一轮，我建议专门研究 **环境变化检测、运行时适应和能力退化诊断**，把外部变化、系统缺陷和真实能力进化区分开来。

这一步会把 EvoAgent 从一个“能通过测试后升级自己的系统”，进一步推向一个能够长期感知环境变化、保持稳定运行，并在必要时安全调整自身的智能体平台。
