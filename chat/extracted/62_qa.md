# EvoAgent 第七专项：路由、规划、执行与验收协同控制系统

这一轮要解决 EvoAgent 的一个核心问题：**各个模块单独看都很强，不代表组合起来就能稳定完成任务。**

路由器可能选错专家，Planner 可能制定错误计划，ReAct 可能反复尝试，工具可能返回错误结果，验收器可能误判成功，诊断器还可能把问题归因给错误的组件。

如果每个模块只优化自己的局部指标，整个智能体甚至可能越进化越差。

例如：

- 路由器为了提高分类准确率，把更多模糊任务交给昂贵的专家；
- Planner 为了降低漏步骤的概率，把所有任务都拆成复杂 DAG；
- ReAct 为了提高成功率，不断增加反思和重试；
- 验收器为了减少误报失败，放宽验收标准；
- 诊断器为了快速提出修复方案，频繁修改提示词。

每个模块都可能在自己的指标上变好，但最终系统却变得更慢、更贵、更复杂，甚至更不可靠。

因此，我建议建立一个独立的 **Agent Orchestration & Control System（智能体协同控制系统）**，统一管理从用户输入到任务完成的决策、执行、验收和恢复。

它不是一个更大的智能体，也不是另一个通用专家，而是负责约束和协调整个智能体运行的控制层。

# 一、先确定协同控制系统的职责

我建议将整体职责划分为四个层面。


    <title size="lg">第一层：任务理解与路由</title>
    识别用户目标、任务类型、风险、约束与所需能力，决定由哪个专家或哪些专家参与。


    <title size="lg">第二层：规划与编排</title>
    决定使用短程 ReAct、固定工作流、动态 DAG，还是多个专家协同。


    <title size="lg">第三层：执行与控制</title>
    检查权限、预算、前置条件、重试、并发、状态一致性和停止条件。


    <title size="lg">第四层：验收与反馈</title>
    独立验证结果、记录证据、分析故障，并决定继续、恢复、重规划或结束任务。


这四层使用前面已经设计的记忆、上下文、工具、工作流和进化系统，但不取代它们。

例如，路由器不负责维护长期记忆；Planner 不负责直接执行高风险工具；验收器不负责修改工具实现；诊断器也不能自行发布新版本。

**协同控制系统负责做出可追溯的运行决策，而底层系统负责提供事实、能力和执行结果。**

# 二、路由：不是简单地把用户问题分类到一个专家

这是第一道决策关口。

用户说“帮我做一个 AI 漫剧”，并不意味着直接交给漫剧专家就够了。系统还需要判断用户究竟想要什么：

- 了解 AI 漫剧的制作方法；
- 写一个漫剧剧本；
- 生成一段 60 秒的视频；
- 搭建一套可重复运行的漫剧工作流；
- 诊断现有制作流程为什么失败；
- 优化已有工作流的成本和质量。

这些任务属于同一个领域，但需要的执行方式完全不同。

因此，路由结果不能只有一个 `expert_id`，还应该包含任务类型、需要的能力、风险等级、置信度、未决问题和路由依据。

## 2.1 路由器应该输出什么？

建议采用结构化的 `RoutingDecision`：

<CodeBlock language="json" editable>
{
  "routing_id": "route-1042",
  "task_id": "task-123",
  "intent": "build_reusable_workflow",
  "domains": [
    "ai_drama",
    "workflow_engineering"
  ],
  "primary_expert": "ai_drama_expert",
  "supporting_experts": [
    "workflow_engineering_expert"
  ],
  "required_capabilities": [
    "media_generation",
    "workflow_orchestration",
    "quality_verification"
  ],
  "risk_class": "CONTROLLED",
  "routing_confidence": 0.89,
  "unresolved_questions": [],
  "fallback_strategy": "GENERAL_PLANNER",
  "decision_evidence_refs": [
    "intent-evidence-1042"
  ]
}
</CodeBlock>

这里的置信度只是一个示例字段。生产环境必须对置信度进行校准，不能把模型自己给出的 `0.89` 直接当成 89% 的真实准确率。

## 2.2 路由策略应分三步

**第一步：理解用户目标。**

提取用户想要的结果、任务对象、约束条件和当前阶段。对于“帮我看看这个”，如果缺少必要对象，就先澄清，而不是盲目调用专家。

**第二步：匹配能力，而不只是匹配领域。**

例如，一个编程任务可能需要代码理解、AST 重构、测试执行和安全审查；一个旅游任务可能只需要检索信息，也可能需要多日行程规划、预订查询和预算计算。

**第三步：决定路由方式。**

路由器可以选择：

- 单个专家；
- 一个主专家加辅助专家；
- 多专家并行；
- 已验证的工作流；
- 通用智能体先澄清或先做初步分析。

不能因为系统拥有多个专家，就强制每个任务都经过多个专家。简单任务应该保持简单。

## 2.3 路由什么时候需要升级为多专家协作？

建议只有在存在明确的跨领域依赖时，才增加专家协作。

例如：

- 制作 AI 漫剧，需要漫剧专家负责创作、媒体能力负责生成和合成、验收器负责技术质量检查；
- 修改 Android 应用，需要编程专家负责实现、测试能力负责验证、发布控制器负责版本安全；
- 制定复杂旅行计划，可能需要旅游专家、预算分析能力和实时预订查询。

但多个专家参与不意味着它们可以互相无限调用。协作必须有明确的任务分工、输入输出契约、权限范围和完成条件。

# 三、路由准确率如何评估与进化？

路由器是一个可以独立评测、独立版本化的组件。

不能只统计“最终任务成功率”，否则无法知道任务失败究竟是因为选错专家，还是专家执行得不好。

我建议至少建立以下指标：

| 指标 | 解释 |
|---|---|
| 意图识别准确率 | 是否正确理解用户想完成什么 |
| 主专家选择准确率 | 是否选中了适合当前任务的专家 |
| 必要能力召回率 | 是否漏掉完成任务必需的能力 |
| 不必要路由率 | 是否调用了无关专家或昂贵能力 |
| 澄清决策准确率 | 应该询问时是否询问，不需要时是否直接执行 |
| 路由后任务成功率 | 采用该路由策略后，任务最终完成情况如何 |
| 路由成本 | 路由本身使用的模型调用、Token 和延迟 |
| 领域间干扰率 | 某个路由改动是否让其他领域任务退化 |

## 3.1 路由错误必须和执行错误分开

例如，用户要求修改 Python 代码，但路由器选择了通用聊天专家，导致它只给出解释而没有修改代码。

这属于路由或任务理解问题。

如果路由器正确选择编程专家，而编程专家调用 AST 工具时传入错误参数，则主要问题属于执行链路。

如果编程专家和工具都正确完成操作，但验收器错误地报告失败，则应该诊断验收系统。

因此，每次任务都应保留路由决策快照，包括当时的候选专家、能力匹配依据、被排除的选项和最终选择。

这些信息可以帮助后续重放同一任务，并比较不同路由策略的真实效果。

## 3.2 路由进化的发布门禁

建议采用：

1. 建立有明确正确答案的路由评测集；
2. 对候选路由策略进行离线回放；
3. 检查不同领域的回归；
4. 比较调用成本与最终任务质量；
5. 在不影响正式任务的条件下开展影子评测；
6. 通过门禁后逐步灰度发布；
7. 持续监控并保留回滚能力。

对于无法明确标注唯一正确路由的复杂任务，应允许多个合理方案，并根据最终效果、成本和风险综合评估，而不是强行把一个专家标签当成唯一标准答案。

# 四、Planner：决定任务应该怎样完成

路由解决的是“谁来处理、需要什么能力”，Planner 解决的是“如何完成任务”。

这里需要一个重要设计原则：

**不是所有任务都需要 DAG，也不是所有任务都应该完全依赖 ReAct 自由探索。**

我建议建立四种执行模式。


    <title size="lg">模式 A：直接执行</title>
    适合目标明确、低风险、步骤少且结果容易验证的任务。
    示例：打开指定应用、查询一个明确的数据。


    <title size="lg">模式 B：短程 ReAct</title>
    适合需要观察环境、动态选择下一步，但不值得提前建立完整工作流的任务。
    示例：打开应用后，根据实际页面决定下一步点击哪里。


    <title size="lg">模式 C：固定或参数化工作流</title>
    适合重复出现、步骤与验收规则已经验证的任务。
    示例：固定的媒体合成流程、重复执行的数据处理任务。


    <title size="lg">模式 D：动态 DAG 与多专家协作</title>
    适合复杂任务、依赖关系多、需要并行工作或执行中可能重规划的任务。
    示例：制作 AI 漫剧、开发完整应用、复杂研究项目。


这里的模式不是四种互斥的智能体。

一个复杂任务可以使用动态 DAG 作为外层结构，每个节点内部使用 ReAct；其中某些重复节点可以调用已验证的固定工作流。Planner 负责选择和组织这些执行方式。

## 4.1 Planner 的输入与输出

Planner 应当读取：

- 当前任务目标与验收标准；
- 已确认的硬性约束；
- 路由结果与可用能力；
- 当前工作记忆和执行进度；
- 预算、时间与资源限制；
- 相关历史经验和失败记录；
- 当前环境是否在线，以及可用的本地能力。

它应输出一个经过校验的 `PlanProposal`，包括：

- 计划目标；
- 执行模式；
- 节点与依赖；
- 节点输入输出契约；
- 所需能力与工具；
- 风险和权限要求；
- 成功条件；
- 失败恢复策略；
- 预算预估；
- 允许的重规划范围。

Planner 提出的计划只是候选，必须由任务控制器检查依赖、权限、预算和可执行性，之后才能成为生效计划。

# 五、如何决定 ReAct、固定 DAG 与动态 DAG？

这个选择不应该依靠一个固定的任务复杂度分数，而应该结合任务特征、环境不确定性和执行成本。

我建议从六个维度进行判断。

| 判断维度 | 更倾向短程 ReAct | 更倾向 DAG / 工作流 |
|---|---|---|
| 步骤数量 | 少，且依赖简单 | 多，且依赖关系明显 |
| 环境不确定性 | 需要逐步观察后决定 | 大部分步骤可以预先规划 |
| 并行机会 | 几乎没有 | 存在可并行节点 |
| 恢复需求 | 失败后重新观察即可 | 需要检查点、局部重试和补偿 |
| 重复频率 | 一次性临时任务 | 高频重复、流程相对稳定 |
| 验收方式 | 结果简单，容易直接核验 | 需要多阶段质量门禁 |

例如，用户说“帮我打开微信并进入某个聊天”，系统可能使用短程 ReAct；用户说“读取项目代码、分析架构、修改实现、运行测试、生成报告”，就更适合使用 DAG 编排。

但是，即使使用 DAG，节点内部仍然可以通过 ReAct 动态判断如何执行。因此，**DAG 管理任务依赖与生命周期，ReAct 管理局部的观察和行动决策。**

## 5.1 固定工作流与动态工作流如何共存？

建议引入三个层级：

- **已验证工作流**：具有稳定契约、通过评测并可重复执行。
- **参数化工作流**：主流程固定，但可以根据输入参数、条件分支和兼容能力选择不同路径。
- **动态计划**：由 Planner 根据当前任务和执行反馈生成，执行中允许在受控范围内调整。

一旦某个动态计划在多个任务中被证明稳定，可以提取为候选工作流。但必须经过整理、回放和边界测试，而不是直接把一次成功的执行轨迹复制成永久流程。

## 5.2 重规划不能破坏已经完成的工作

假设 AI 漫剧的剧本、角色设计和分镜都已通过验收，只有视频生成失败。

合理的做法是：

1. 保留已验收的上游产物；
2. 分析视频生成失败原因；
3. 判断是修复当前节点、替换生成服务，还是调整分镜；
4. 生成新的计划版本；
5. 检查新旧计划的依赖与兼容性；
6. 只重新执行受到影响的节点；
7. 重新验收最终产物。

不能因为一个节点失败，就默认从头运行全部流程。这样不仅浪费成本，还可能导致已经确认的内容发生不必要变化。

# 六、ReAct 与任务控制器：模型提出动作，系统决定是否执行

这里需要明确一个边界。

ReAct 可以根据观察结果提出下一步行动，但不能成为不受约束的执行循环。

例如，模型提出“再次点击登录按钮”，任务控制器应当检查：

- 当前界面是否仍然是登录页面；
- 是否已经登录成功；
- 上次点击是否已经生效；
- 当前动作是否存在重复副作用；
- 是否需要用户确认；
- 当前任务预算和循环次数是否允许继续。

因此，我建议每次 ReAct 循环都遵循统一的协议。

  {#each [
    ["Observe","获取当前环境状态、工作记忆和最近的执行证据。"],
    ["Decide","模型提出下一步动作、停止条件或需要澄清的问题。"],
    ["Validate","控制器校验权限、参数、预算、前置条件和重复执行风险。"],
    ["Act","通过统一工具网关执行已批准的动作。"],
    ["Verify","检查工具结果与实际状态，判断动作是否达到预期。"],
    ["Commit","持久化状态变化、执行证据、费用和未决问题。"],
    ["Continue / Stop","继续循环、等待、恢复、重规划或结束任务。"]

  {/each}

## 6.1 必须有明确的停止条件

ReAct 不能无限循环。

建议同时设置：

- 最大行动步数；
- 最大模型调用次数；
- 总 Token 与费用预算；
- 单节点超时；
- 任务总时限；
- 连续相同错误次数；
- 连续无进展次数；
- 最大重规划次数；
- 高风险动作的授权要求。

这些限制应由确定性控制器执行，而不是只在提示词中告诉模型“不要无限循环”。

当达到停止条件时，系统应该明确返回当前状态，例如“等待授权”“远端状态待核实”“预算不足”或“需要用户补充信息”，而不是为了让任务看起来成功而继续执行。

## 6.2 什么叫真正的进展？

系统还需要判断每一轮是否带来了有意义的状态变化。

例如，连续三次调用同一个工具、得到相同错误，不能被视为三次有效探索。

可以定义一组进展信号：

- 新的有效证据；
- 任务状态发生有意义变化；
- 一个节点通过验收；
- 阻塞原因得到消除；
- 计划被有效简化；
- 不确定性得到实质性降低。

如果连续多轮没有进展，控制器可以触发诊断，而不是继续增加模型调用。

# 七、验收器：必须独立判断任务是否真正完成

EvoAgent 不能只依赖执行智能体自己的判断。

如果 ReAct 说“完成了”，Planner 说“所有节点已执行”，都不代表用户目标已经实现。

建议建立统一的验收框架，将任务完成划分为四种状态：




      **PASS：通过验收**
      必要的验收条件均有充分证据支持，可以确认完成。






      **PARTIAL：部分完成**
      部分目标已完成，但仍有明确未完成项或未满足的条件。






      **INCONCLUSIVE：证据不足**
      当前证据无法证明成功或失败，需要进一步检查。






      **FAIL：未通过**
      存在明确失败证据，或必要的验收条件未满足。



这四种状态比简单的布尔值更适合复杂任务。

例如，云端视频生成请求超时，无法查询远端状态时，不能直接标记为 `FAIL`，也不能标记为 `PASS`。应该返回 `INCONCLUSIVE`，由恢复机制继续核查。

## 7.1 验收标准从哪里来？

建议优先级为：

1. 用户明确指定的验收条件；
2. 经过确认的项目要求；
3. 对应能力或工作流的标准验收契约；
4. 针对当前任务制定并经校验的补充条件。

如果验收标准本身有歧义，系统应当在必要时澄清，不能为了得到更高的任务成功率而偷偷降低标准。

例如，用户要求代码修改后全部测试通过。如果有测试失败，系统不能因为修改的目标函数看起来正确，就把任务标记为完全成功。

## 7.2 验收器也可能出错

因此，验收器需要独立评测，重点检查：

- 假成功率；
- 假失败率；
- 证据充分性；
- 对部分完成状态的识别能力；
- 对未知状态的处理能力；
- 不同专家和任务类型之间的一致性。

对于代码任务，尽量使用测试、静态分析和差异检查；对于手机操作，检查目标页面和实际状态；对于视频任务，检查产物存在性、时长、编码、音画同步和视觉质量。

大模型可以辅助语义验收，但重要结果不能只依赖执行模型对自身工作的文字总结。

# 八、多专家协作：不是让专家互相聊天，而是让他们共同完成一个任务

多个专家协作时，最容易出现三种问题：

- 两个专家重复做同一件事；
- 一个专家依赖另一个专家尚未验证的结果；
- 专家之间的结论冲突，却没有明确的裁决规则。

因此，建议建立统一的 `Agent Handoff Contract`（专家交接契约）。

每次交接至少明确：

- 交接的目标；
- 负责范围；
- 输入产物及其版本；
- 已确认事实与未验证假设；
- 当前验收要求；
- 必须遵守的约束；
- 交付物格式；
- 完成条件；
- 失败和升级处理方式。

例如，漫剧专家把分镜交给视频生成能力时，不能只传一句“请根据分镜生成视频”。

还应传递：

- 分镜版本；
- 角色参考素材；
- 每个镜头的时长和画面要求；
- 角色一致性标准；
- 允许使用的生成服务；
- 预算限制；
- 输出文件规格；
- 失败后允许的恢复路径。

这样，视频生成节点才能真正成为可管理、可追踪、可验收的任务节点。

## 8.1 多专家协作的调度方式

建议支持三种模式：

| 模式 | 适用情况 |
|---|---|
| 顺序交接 | 后续专家依赖前一专家的输出 |
| 并行协作 | 多个专家可以独立完成不同子任务 |
| 评审协作 | 一个专家产出结果，另一个独立检查或提出反例 |

但不建议所有任务都采用多个模型相互评审。只有当评审能显著提高质量、降低关键风险，并且成本合理时，才值得增加额外调用。

协作控制器还应设置最大参与专家数、最大交接次数和总预算上限，防止专家之间不断相互委派任务。

# 九、系统级故障归因：当多个组件同时参与时，怎么确定谁出了问题？

前面已经为工具、提示词、上下文和路由分别设计了诊断机制。现在需要把它们整合起来。

建议每个任务维护统一的 `Execution Trace`，将以下信息关联到同一条运行轨迹：

- 原始用户请求和目标版本；
- 路由决策及候选专家；
- 生效的 Plan 与 DAG 版本；
- 每次 ReAct 循环的观察和动作；
- 实际编译的上下文快照；
- 工具调用、参数、返回结果和证据；
- 工作记忆状态变化；
- 验收结果与诊断结论；
- 实际 Token、费用、延迟和重试次数。

这条轨迹不只是日志。它应该让系统能够重建当时发生了什么，并判断改进应该作用于哪个组件。

这里有一个重要限制：执行轨迹只能证明记录下来的事实，不能自动证明因果关系。

例如，某次任务在更换提示词后成功了，不代表提示词一定是唯一根因。可能同时发生了工具服务恢复、输入变化或环境更新。

因此，关键改进应该尽可能通过固定输入、固定环境、对照基线和重复测试来验证。

## 9.2 根因不确定时怎么办？

不要强行归因。

系统应该允许输出：

- 已确认根因；
- 高可信候选根因；
- 多个可能的促成因素；
- 证据不足，需要继续观察；
- 需要用户或开发者介入。

对于低风险、容易回滚的策略，可以允许在沙箱中并行验证多个假设；对于会修改工具代码、权限策略或生产工作流的高风险改动，则应要求更充分的证据。

# 十、系统级进化：优化整体，而不是只优化单个模块

现在进入这一轮最重要的设计。

EvoAgent 不应该让路由器、Planner、ReAct、工具、验收器分别追求自己的局部最优，而应该建立统一的系统级优化目标。

我建议使用一个多目标评估框架，至少同时考虑：

- 任务质量；
- 任务成功率；
- 运行稳定性；
- 端到端延迟；
- 每个成功任务的总成本；
- 失败恢复能力；
- 用户纠正与返工；
- 权限、安全和隐私风险。

这里不建议简单把所有指标加权成一个总分。因为某些约束不能通过其他指标抵消。

例如，任务成本降低 30%，不能抵消未经授权发送消息造成的安全问题。

因此，应该先建立硬性门禁，再在合格候选中进行多目标比较。

## 10.1 先区分四种改进类型

| 改进类型 | 例子 | 主要验证方式 |
|---|---|---|
| 局部改进 | 修复某个工具的参数校验 | 契约测试、专项回归 |
| 专家级改进 | 提升编程专家的代码修改质量 | 编程评测集、跨任务回归 |
| 协同改进 | 减少路由错误和不必要的专家交接 | 端到端回放、成本与质量比较 |
| 系统级改进 | 优化全局上下文策略和执行调度 | 多领域评测、资源与稳定性测试 |

改进范围越大，验证范围通常也越大。

例如，修改编程专家专用的提示词，主要需要编程专项测试和必要的共享内核回归；修改通用路由策略，则需要检查所有重要领域的路由和任务成功率。

## 10.2 防止局部优化破坏全局能力

建议为每个候选改进定义三个集合：

- **目标集合**：预期受益的任务；
- **保护集合**：不能明显退化的任务和安全场景；
- **探索集合**：尚未参与优化、用于发现意外副作用的测试案例。

例如，优化路由器以减少编程任务的错误分流时：

- 目标集合：复杂编程任务；
- 保护集合：旅游、日常聊天、手机操作和高风险任务；
- 探索集合：混合领域、含糊指令和新类型任务。

候选即使在目标集合中表现更好，只要导致保护集合出现不可接受的退化，就不应该直接发布。

还应保留一套长期固定的回归集，以及一套定期更新、用于发现新问题的探索集，避免系统只针对已经熟悉的测试案例优化。

# 十一、自动发布门禁：什么样的改进可以自动上线？

结合你此前确定的原则，EvoAgent 可以自动发布通过门禁的低风险改进，但不能把“评测分数更高”作为唯一条件。

建议建立五道门禁。

## 11.1 不同风险等级对应不同发布权限

| 改进类型 | 自动生成候选 | 自动评测 | 自动发布 |
|---|---|---|---|
| 低风险、兼容的上下文配置 | 允许 | 允许 | 满足门禁后允许 |
| 专家提示词与输出模板 | 允许 | 允许 | 通过专项及跨领域回归后，可按策略自动发布 |
| 路由与规划策略 | 允许 | 允许 | 需更广泛的跨领域测试和受控灰度 |
| 工具实现代码 | 允许生成候选 | 沙箱内允许 | 默认需要更严格的审批与构建验证 |
| 权限、安全内核与发布控制器 | 可提出修改建议 | 受控测试 | 禁止普通自动进化直接发布 |

这符合你希望高度自动化的方向，同时避免把所有变更都放在同一套权限下。

对工具实现代码，不是说永远不能自动发布，而是必须先明确可自动发布的变更范围、隔离构建环境、测试标准和紧急回滚机制。安全内核、权限边界和发布控制器则不应由普通的自进化循环自行解除保护。

## 11.2 灰度发布不等于随机让用户试错

对于 EvoAgent Android，可以按风险和任务类型选择灰度策略：

- 先在离线评测集和沙箱中验证；
- 再在影子模式下比较新旧决策；
- 对低风险任务逐步启用候选；
- 对关键指标设置自动停止和回滚条件；
- 确认稳定后，再扩大生效范围。

影子模式只能比较可以安全模拟或重复计算的决策。对于发送消息、支付、删除文件等有副作用的动作，不应为了对比新旧策略而重复执行真实操作。

此外，正式发布后必须保留清晰的版本归属。每个任务应继续使用它所绑定的兼容配置，或者在经过明确的安全迁移后升级，不能因为后台发布了新版本，就让运行中的任务突然换掉关键策略。

# 十二、统一运行轨迹与系统指标

为了把所有模块真正连接起来，我建议建立统一的 `Task Execution Trace` 和 `System Evaluation Record`。

每次任务都应能够回答：

- 用户提出了什么目标；
- 路由器为什么选择该专家；
- Planner 为什么选择该执行模式；
- 本次实际使用了哪些提示词、模型和工具版本；
- 上下文引擎加载了哪些信息；
- 哪些工具操作真正发生了；
- 哪些结果通过了独立验收；
- 任务失败时有哪些根因假设；
- 本次消耗了多少模型调用、Token、工具费用和时间；
- 哪个版本的改进带来了什么变化。

建议统一记录以下指标：

| 指标组 | 核心指标 |
|---|---|
| 路由 | 意图识别、专家选择、无效交接 |
| 规划 | 计划可执行性、重规划次数、计划偏差 |
| 执行 | 节点成功率、工具误用率、无进展循环 |
| 验收 | 假成功率、假失败率、证据充分性 |
| 稳定性 | 中断恢复率、重复副作用率、任务崩溃率 |
| 成本 | 单次任务成本、每个成功任务成本、重试成本 |
| 用户体验 | 纠正率、返工率、澄清负担 |
| 进化 | 候选通过率、发布后退化率、回滚率 |

这些指标需要统一任务口径。例如，“任务成功率”必须明确任务成功的判定条件、统计范围和失败任务是否包含中断及取消情况，否则不同版本之间的比较没有意义。

同时，运行日志与诊断记录也要遵守隐私和保留策略。不是所有原始模型输入、屏幕截图和用户文件都应该长期上传到服务端。

# 十四、从这里往下，还剩哪些关键问题？

经过这七轮，我们已经形成了一套相当完整的核心运行架构：

- 多专家与能力路由；
- Plan、ReAct、DAG 和工作流；
- 长期记忆、用户习惯、工作记忆；
- 上下文工程与提示词治理；
- 工具契约、专业技术能力与故障诊断；
- 验收、恢复、系统级评测和受控进化。

但还有三个必须深入的领域，才能把设计推进到真正可实现的全量工程架构。
