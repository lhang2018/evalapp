# EvoAgent 第二十专项：模型适配、多模型协同与智能成本治理

前面我们已经设计了专家系统、路由、Planner、ReAct、动态 DAG、记忆、上下文、工具契约、验收、恢复与进化治理。

现在要回答一个更深层的问题：

**EvoAgent 的智能究竟来自模型本身，还是来自模型与提示词、上下文、工具、工作流、记忆和反馈机制的组合？如果某个模型变强了，系统应该如何利用它；如果模型变弱、不可用或成本过高，又该如何保持稳定？**

我的核心判断是：

**EvoAgent 不应该围绕某一个模型构建，而应该围绕可验证的任务能力构建。模型只是能力实现的一种可替换资源。**

这意味着，不能把“使用了更强的模型”直接等同于“智能体能力提升”，也不能把某个模型的特定提示词技巧当作所有专家都适用的通用能力。

本专项建议定义为：

**Model Adaptation & Multi-Model Orchestration Engine，简称 MAMO。**

它负责模型能力评估、模型选择、调用升级、模型切换、适配策略管理和成本质量优化。

## 一、第一性原理：真正需要路由的是任务所需能力，而不只是模型

假设 EvoAgent 接到一个编程任务。

其中可能包含：

- 判断用户意图；
- 理解项目结构；
- 分析 AST；
- 制定修改计划；
- 生成补丁；
- 调用工具；
- 分析测试失败；
- 验证修改是否正确。

这些子任务对模型的要求完全不同。

意图分类可能只需要一个快速、低成本的模型；复杂故障分析可能需要更强的推理能力；AST 解析应该由确定性工具完成，而不是让大模型凭文本猜测语法结构；测试是否通过则应该以实际执行结果为依据。

因此，MAMO 不应该只回答：

“当前应该用哪个模型？”

它应该回答：

“当前任务的哪一部分需要什么能力？有哪些实现方式？哪种组合在质量、成本、延迟和风险之间最合适？”

这些因素存在交互关系，但不能混为一谈。

例如，一次代码任务成功，可能是模型推理更强，也可能是工具补全了模型的不足，或者是上下文准确地提供了关键文件。

如果系统不区分这些因素，就无法知道下一步究竟应该优化模型、提示词、上下文、工具还是工作流。

因此，**MAMO 必须与 OCAE 诊断系统协作，区分任务失败的原因，而不是把所有失败都归咎于模型。**

# 三、建立模型能力画像，而不是给每个模型一个总排名

我建议建立 `Model Capability Profile`（模型能力画像）。

每个模型都应该按照具体任务类型、工具环境、上下文规模和适配版本进行评估，而不是只记录一个笼统的“智能分数”。

## 3.1 模型能力画像包含什么？

| 维度 | 评估内容 |
|---|---|
| 任务理解 | 是否正确识别目标、约束和隐含条件 |
| 推理与规划 | 是否能形成有效计划，识别依赖和失败风险 |
| 代码能力 | 代码生成、调试、重构、结构化修改的实际表现 |
| 工具调用 | 参数正确率、协议遵循率、工具使用策略 |
| 长上下文 | 关键信息保留、跨段关联和约束遵循 |
| 结构化输出 | Schema 遵循率、格式错误率 |
| 多模态能力 | 对图像、视频、音频等输入的实际处理效果 |
| 纠错能力 | 能否根据真实反馈定位问题并修正 |
| 成本与延迟 | 实际调用费用、响应时间和重试开销 |
| 稳定性 | 多次执行的结果波动、超时率和失败率 |

但这张表仍然不够，因为同一个模型在不同场景中的表现可能有明显差异。

例如，模型 A 可能在短代码补全中表现很好，却在大型代码库重构时经常遗漏跨文件依赖。

所以，画像还必须绑定具体的评测条件。

## 3.2 画像必须带有适用范围

建议至少绑定：

- `model_id`：模型标识；
- `model_version`：实际模型版本或可识别的部署快照；
- `provider`：模型提供方；
- `task_type`：任务类别；
- `expert_id`：所属专家；
- `tool_environment`：工具与运行环境；
- `context_profile`：上下文长度和组装策略；
- `prompt_version`：使用的提示词版本；
- `adapter_version`：模型适配配置版本；
- `evaluation_dataset_version`：评测集版本；
- `evaluation_timestamp`：评测时间；
- `capability_metrics`：各项能力指标；
- `known_limitations`：已知局限。

这样，模型画像就不是一个永久有效的标签，而是有条件、有证据、有版本的评测结论。

例如，“模型 A 在编程任务中表现良好”不是一个足够精确的结论。

更有价值的结论是：

“模型 A 在指定版本的 Python 多文件修改评测集上，使用某版上下文策略和测试工具时，达到既定质量门槛，平均成本低于候选模型 B，但在大型重构任务中需要更强的回归验证。”

这才足以支持实际路由。

## 3.3 模型评测不能只用模型自己打分

建议以真实任务结果为主，结合自动化指标和必要的人工评测。

例如：

- 代码任务以补丁正确性、测试结果和变更范围为证据；
- 结构化输出以 Schema 校验结果为证据；
- 规划任务以依赖完整性、执行成功率和实际成本为证据；
- 工具调用以实际状态变化和后置条件为证据；
- 长上下文任务以关键约束保留和最终任务完成情况为证据。

模型可以解释自己为什么认为某个答案正确，但这种解释不能替代外部验证。

# 四、模型路由必须发生在多个层级

EvoAgent 不能只在用户发来消息时选择一次模型。

因为一个复杂任务可能包含多个不同性质的子任务，执行过程中也可能出现需要升级模型的情况。

我建议设计四级模型路由。


    <title size="lg">R1 · 任务级模型路由</title>
    根据整体任务类型、复杂度、风险、预算和专家能力，选择默认执行策略。
    例如：复杂编程任务选择编程专家，并为复杂诊断预留高能力模型预算。


    <title size="lg">R2 · 阶段级模型路由</title>
    针对规划、执行、诊断、验收等阶段选择合适模型或确定性工具。
    例如：规划阶段使用较强推理能力，代码解析阶段优先使用 AST 工具。


    <title size="lg">R3 · 节点级模型路由</title>
    为 DAG 中的具体节点选择模型、提示词版本和工具组合。
    例如：简单文件摘要使用低成本模型，复杂跨文件依赖分析使用更强模型。


    <title size="lg">R4 · 运行时升级路由</title>
    在观察到明确的困难、失败或质量风险时，决定是否重试、切换模型或升级推理能力。
    例如：低成本模型连续无法定位测试失败时，转入更强的诊断路径。


这四级路由不必每次都调用一个专门的路由模型。

大多数简单判断可以由规则和统计模型完成；只有任务复杂度难以判断、候选方案差异较大或需要语义理解时，才有必要调用更强模型辅助决策。

## 4.1 不要让路由本身成为成本黑洞

如果每次模型调用前，都先调用一个昂贵模型来决定应该调用哪个模型，那么路由系统本身就可能吞噬节省下来的成本。

因此建议采用分层决策：

1. 先通过任务类型、工具能力、权限和预算进行规则过滤；
2. 使用已有的能力画像和历史评测结果排序；
3. 只有在决策不确定、成本差异显著或风险较高时，才调用更强模型进行辅助判断；
4. 将路由决策和实际结果记录下来，用于后续校准。

这也符合你的成本原则：真正值得增加的成本应该用于提高任务质量，而不是用于无休止地分析如何选择模型。

# 五、动态升级模型：什么时候应该从便宜模型切换到更强模型？

这是 MAMO 最关键的运行时机制之一。

如果所有任务从一开始就使用最强模型，成本很容易膨胀；但如果始终坚持使用最低成本模型，又可能在复杂任务中反复失败。

我建议采用 **Progressive Escalation（渐进式能力升级）**，而不是简单的“失败就换模型”。

## 5.1 先区分四种不同的问题

| 观察到的问题 | 更合理的处理方式 |
|---|---|
| 输入格式错误 | 修正输入或适配层，不一定换模型 |
| 工具返回明确失败 | 检查工具状态、参数和前置条件 |
| 上下文缺失或冲突 | 重新检索、组装上下文或恢复任务状态 |
| 复杂推理持续失败 | 考虑升级模型、增加分析预算或拆分任务 |

这一步非常重要。

假设低成本模型连续三次无法修改代码，系统不能立即认定“模型不够强”。也可能是测试环境错误、关键文件未加载、工具契约不清楚，或者原计划本身不合理。

升级模型之前，应该先检查失败类型。

## 5.2 建立模型升级状态机

  {#each [
    ["NORMAL","当前模型正常执行，结果通过必要的验证。"],
    ["WARNING","发现低置信度、无进展、反复错误或质量风险。"],
    ["DIAGNOSING","检查上下文、工具、任务状态和失败证据。"],
    ["REPAIRING","先修复可确定的输入、工具或上下文问题。"],
    ["ESCALATION_CANDIDATE","仍存在明确的模型能力缺口，准备比较升级方案。"],
    ["ESCALATED","切换到更适合的模型或更强的推理策略。"],
    ["VERIFIED","验证升级后的结果是否真正改善。"],
    ["STOPPED","达到预算上限、缺乏可行方案或需要用户决策。"]
  ] as item}


        {item[0]}


        {item[1]}


    {#if item[0]!=="STOPPED"}

    {/if}
  {/each}

这个状态机不是要求每次失败都走完整流程，而是保证升级有依据、有预算、有验证结果。

## 5.3 升级必须考虑预期收益

假设当前模型完成某类任务的成功概率约为 70%，升级模型后预计可以达到 85%，但调用成本增加了 4 倍。

这并不意味着应该自动升级。

系统还需要考虑：

- 任务是否重要；
- 失败代价有多大；
- 当前预算还剩多少；
- 升级模型是否真的解决已识别的问题；
- 任务是否可以拆分；
- 是否存在低成本工具或局部修复方案。

可以用一个概念性的决策式表达：

\[
\text{升级净价值}
=
\text{预期质量收益}
-
\text{新增调用成本}
-
\text{新增延迟与风险}
\]

这不是一个可以直接通用计算的精确公式，而是要求系统在升级前明确比较预期收益与代价。

对于关键任务，提升成功率可能非常值得；对于低价值、可随时重试的小任务，升级可能不划算。

## 5.4 防止模型升级循环

建议为每个任务设置：

- 最大升级次数；
- 最大模型调用预算；
- 单节点重试上限；
- 升级后的最低质量验收条件；
- 允许使用的模型列表；
- 不可突破的任务总预算。

如果更强模型也无法解决问题，系统不能无限升级到更贵的模型，而应重新检查问题、采用不同工具、调整任务拆分方式，或停止并说明原因。

# 六、模型适配策略：提示词、上下文和工具使用技巧应该存在哪里？

这与你之前强调的专家隔离问题直接相关。

假设编程专家发现，模型 A 在处理多文件修改时，只要先获取符号引用关系，再生成补丁，成功率就会提高。

这个经验不能直接推广到旅游专家，也不能因为模型 A 使用这套策略有效，就认定模型 B 也会同样受益。

因此，我建议将模型适配策略设计成独立资产，而不是直接修改通用提示词。

## 6.1 适配策略的五个层级

  {#each [
    ["全局模型接口策略","统一请求、超时、错误处理、输出解析和供应商适配，不包含特定领域的行为技巧。"],
    ["模型家族适配策略","针对某类模型的上下文格式、结构化输出方式和工具调用差异。"],
    ["专家模型适配策略","针对编程、研究、手机操作等领域，规定模型如何使用该专家的工具与上下文。"],
    ["任务类型适配策略","针对调试、代码重构、数据分析、视觉检查等具体任务的执行方法。"],
    ["模型版本专属补偿","仅对特定版本已验证的局限进行补偿，并明确其失效条件。"]
  ] as item}

      <title size="md">{item[0]}</title>
      {item[1]}

    {#if item[0]!=="模型版本专属补偿"}

    {/if}
  {/each}

这里需要特别强调：

**模型适配策略是带有作用范围和版本的可治理资产，不是可以随意追加到系统提示词中的经验文本。**

## 6.2 适配策略必须绑定模型、任务和环境

建议每个策略记录：

- `adapter_id`；
- `adapter_version`；
- `model_id`；
- `model_version_range`；
- `expert_id`；
- `task_type`；
- `tool_environment`；
- `prompt_template_ref`；
- `context_policy_ref`；
- `evaluation_dataset_ref`；
- `known_limitations`；
- `rollback_version`。

例如，某个提示词补偿策略可能只适用于模型 A 的某个版本，在长上下文编程任务中有效。

如果模型升级后原有问题已经修复，该策略可能反而降低表现。因此，模型升级必须触发相关补偿策略的重新评估。

## 6.3 不要把所有成功经验都写进提示词

如果每次成功都向提示词中添加一句规则，最终可能出现：

- 提示词越来越长；
- 不同规则互相冲突；
- 模型执行成本上升；
- 不知道究竟是哪条规则有效；
- 旧规则无法安全撤回；
- 通用专家被某个特定任务的经验污染。

更合理的做法是先判断应该优化什么：

- 如果是稳定的操作顺序，优先考虑工作流；
- 如果是可重复使用的知识，考虑记忆；
- 如果是特定模型的行为补偿，考虑适配策略；
- 如果是确定性检查，优先考虑程序或工具；
- 如果是任务目标与依赖变化，考虑规划策略；
- 如果是执行失败原因不明，先进行诊断。

这样，模型适配系统就不会变成一个不断堆积提示词的系统。

# 七、多模型协同：多个模型不一定比一个模型更可靠

当我们引入多个模型时，很容易认为让它们相互讨论、互相检查，就能提高质量。

但这并不总是成立。

如果多个模型使用相似的训练数据、相同的上下文和相同的错误假设，它们可能产生高度一致但错误的结论。

例如，三个模型都认为某个工具返回成功就代表文件内容正确。即使它们互相确认，也不能替代实际读取文件和比较内容。

因此，MAMO 必须区分真正的独立验证与表面上的多模型一致。

## 7.1 四种多模型协作模式


    **模式 A：流水线协作**

    不同模型负责不同阶段。

    例如，低成本模型分类任务，强模型规划，确定性工具执行，验证器检查结果。

    优点：职责清晰，容易控制成本。



    **模式 B：升级协作**

    低成本模型先尝试，遇到明确困难后升级到更强模型。

    优点：适合任务难度不确定的情况，避免所有任务都支付最高成本。



    **模式 C：候选方案比较**

    在少数高价值决策中，生成多个候选方案，再通过统一标准比较。

    优点：可以探索不同解法；缺点是调用成本和决策延迟更高。



    **模式 D：独立验证**

    一个模型负责提出方案，另一个模型或确定性工具负责检查关键错误。

    优点：有机会降低共同错误，但前提是验证方法真正独立并且有效。


## 7.2 高风险任务不应只依赖模型投票

对于涉及重要文件修改、不可逆操作或关键交付物的任务，应当优先使用能够独立核验的证据。

例如：

- 代码任务使用实际测试和差异检查；
- 文件操作使用内容哈希和状态读取；
- 数据处理使用独立的数据完整性校验；
- 媒体制作使用元数据检查、音画同步检测和必要的视觉审查。

多模型可以辅助发现潜在问题，但不能通过简单多数票覆盖客观证据。

## 7.3 多模型协作必须设置退出条件

建议明确：

- 最大参与模型数量；
- 最大讨论轮数；
- 最大总调用成本；
- 必须产生的输出；
- 争议如何解决；
- 何时转入独立验证；
- 何时停止并请求用户决策。

如果多个模型连续几轮只是重复表达观点，却没有产生新证据或更好的候选方案，就应该停止协作，而不是继续消耗预算。

# 八、成本治理：如何真正控制智能体的长期成本？

你之前提出的原则是：真正有效的能力提升可以增加一些模型调用成本，但成本不能无限膨胀。

我建议把这条原则落实为一个独立的 **Quality–Cost Controller（质量与成本控制器）**。

它不是简单地选择最便宜的模型，而是管理整个任务的资源分配。

## 8.1 建立四级预算

| 预算层级 | 控制对象 |
|---|---|
| 任务总预算 | 整个任务允许消耗的费用、时间和模型调用量 |
| 阶段预算 | 规划、执行、诊断、验收等阶段的资源分配 |
| 节点预算 | 每个 DAG 节点的模型、工具、重试和恢复成本 |
| 单次调用预算 | 单次模型调用的输入输出限制、超时和费用上限 |

这四级预算必须共享同一套账本。

否则，Planner、ReAct、诊断器和验证器可能分别控制自己的成本，却让整个任务超支。

## 8.2 预算分配应该考虑不确定性

不建议一开始就把所有预算平均分配给每个节点。

例如，一个复杂编程任务可能有 10 个节点，其中大部分是简单的文件读取和测试执行，只有一个节点需要解决棘手的并发问题。

合理的策略是：

- 为常规节点分配基础预算；
- 为高不确定性节点预留额外预算；
- 为最终验收与必要恢复保留预算；
- 根据实际执行结果动态调整剩余资源；
- 禁止普通节点擅自挪用全局保留额度。

这样，系统既不会为每个简单步骤使用昂贵模型，也不会因为前期过度消耗而在关键诊断阶段没有资源。

## 8.3 评估的不是单次调用成本，而是成功交付成本

假设：

- 模型 A 每次调用成本较低，但经常需要重试；
- 模型 B 每次调用成本较高，但更容易一次完成。

仅比较单次调用价格，会得出错误结论。

更合理的指标是：

\[
\text{成功交付成本}
=
\frac{\text{任务总实际成本}}{\text{通过验收的任务数}}
\]

这个指标仍然需要结合任务质量、失败代价和延迟一起分析，但它比单纯比较每次模型调用价格更接近 EvoAgent 真正关心的目标。

例如，一个模型虽然便宜，但如果频繁产生昂贵的错误视频、重复修改文件或需要多次人工介入，其整体成本可能更高。

## 8.4 质量和成本不能互相掩盖

建议采用约束式优化，而不是单纯追求成本最低。

可以表达为：

\[
\min \text{Expected Total Cost}
\]

同时满足：

\[
\text{Quality} \geq Q_{\min}
\]

\[
\text{Risk} \leq R_{\max}
\]

\[
\text{Cost} \leq B_{\max}
\]

这里的 \(Q_{\min}\)、\(R_{\max}\) 和 \(B_{\max}\) 应当根据任务类型、用户授权和风险级别确定，而不是所有任务都使用同一个固定值。

对于高价值任务，系统可以在预算允许的情况下选择更强模型和更多验证；对于低风险任务，则可以使用较低成本的模型与较轻量的验收方式。

我建议模型适配系统采用与记忆治理类似的受控生命周期，但必须区分模型选择、提示词适配、上下文策略和执行工作流。

## 9.2 改进对象必须分开

同一个失败案例可能产生多个候选改进：

- 提示词需要明确输出结构；
- 上下文需要保留某个关键约束；
- 工具需要增加前置条件检查；
- 规划器需要补充一个依赖节点；
- 模型路由需要为特定任务选择更强模型。

这些候选不应该被打包成一次无法归因的大改动。

更合理的做法是逐步验证改进对象，必要时使用组合实验检查交互效果。

例如，单独更换模型可能没有改善，但模型与新的上下文策略组合后效果明显提升。系统应该能够识别这种交互，而不是简单地将功劳全部归给模型。

## 9.3 只允许证据支持的改进晋升

一次成功只能说明该方案在当前条件下有效，不能证明它适用于所有任务。

因此，模型适配候选必须记录：

- 适用专家；
- 任务类型；
- 模型版本；
- 提示词与上下文版本；
- 测试环境；
- 支持证据；
- 已知反例；
- 成本变化；
- 回滚方案。

只有通过对应范围的评测，才能将候选策略提升为稳定版本。

# 十、模型升级与模型更换：如何避免系统整体退化？

即使新模型在基准测试中更强，也不意味着它在 EvoAgent 的实际工作流中一定更好。

模型变化可能影响：

- 提示词遵循；
- 工具参数格式；
- JSON 或 Schema 输出；
- 上下文压缩效果；
- Planner 的任务拆分方式；
- ReAct 的循环次数；
- 错误诊断质量；
- 生成结果的风格和稳定性；
- 单任务成本与延迟。

因此，模型切换不能只修改一个 `model_id` 就直接全量发布。

## 10.1 建立模型迁移评测矩阵

建议对每次关键模型升级，检查以下组合：

| 评测范围 | 核心问题 |
|---|---|
| 各领域专家 | 新模型是否影响专家的实际任务质量？ |
| 工具调用 | 是否出现新的参数错误、协议错误或无效调用？ |
| 上下文压缩 | 是否更容易遗漏关键约束？ |
| 规划与 DAG | 是否产生更多无效节点或不合理依赖？ |
| ReAct | 是否出现无进展循环或过度探索？ |
| 失败恢复 | 是否正确识别错误并采取合适恢复策略？ |
| 成本与延迟 | 实际成功交付成本是否改善？ |
| 安全与权限 | 是否更容易提出或尝试越权操作？ |

不必每次更换模型都重新测试整个系统的所有可能组合。

可以根据模型变更影响、历史缺陷和关键依赖建立风险导向的回归测试集。但关键约束、权限和恢复保护集必须保留。

## 10.2 使用分阶段发布

建议按以下顺序推进：

1. 离线回放：在固定任务集上运行新模型；
2. 对照评测：比较旧模型与新模型的质量和成本；
3. 影子评估：在允许的情况下，对新模型的决策进行独立评估，但不执行可能产生副作用的动作；
4. 小范围启用：仅在指定专家或低风险任务中使用；
5. 持续监测：观察实际任务表现；
6. 扩大范围或回滚：根据预先定义的门槛决定。

如果新模型改变了工具调用行为，影子评估不能直接执行真实外部操作。应当通过模拟执行、只读环境或受控测试环境验证。

## 10.3 模型回滚不应该回滚任务事实

这是一个重要的工程边界。

假设新模型导致任务规划质量下降，系统决定切回旧模型。

这不意味着应该恢复到模型切换前的旧任务状态，也不意味着要丢弃新模型期间已经生成并验证有效的产物。

应该回滚的是模型路由与适配配置，而不是把已经确认的执行事实一并回滚。

任务状态仍然以权威状态库和执行证据为准。只有经过检查发现某些产物受到错误模型行为影响时，才需要让相关节点失效并重新执行。

# 十二、下一专项：自我诊断、因果归因与改进实验治理

到这里，我们已经覆盖了 EvoAgent 的几个关键执行层面：

- 专家系统与能力路由；
- 记忆和上下文工程；
- 长任务连续性；
- 动态 DAG 与 ReAct 协同；
- 工具执行契约与结果验证；
- 模型适配与成本治理。

但这些模块仍然需要一个更深层的系统来协调：**当任务失败或质量下降时，EvoAgent 如何知道真正的问题出在哪里？**

这是整个自进化系统能否持续改善的关键。

例如，一个代码任务失败了，可能是：

- 意图识别错了；
- 编程专家路由错了；
- 关键文件没有进入上下文；
- 上下文压缩丢失了接口约束；
- Planner 漏掉了依赖；
- ReAct 选择了错误工具；
- 工具执行失败；
- 模型能力不足；
- 验收器遗漏了缺陷；
- 记忆检索到了不适用的经验。

如果系统只是看到“任务失败”，然后把提示词改得更长、换一个更贵的模型，或者增加一次重试，它可能会增加成本，却没有真正解决问题。

下一专项建议定义为：

**Root Cause Analysis & Improvement Experiment Engine（根因分析与改进实验引擎，简称 RCAE）。**

重点研究：

1. 如何建立跨路由、专家、上下文、模型、工具和验收的统一故障证据链；
2. 如何区分症状、直接原因、根因和相关因素；
3. 如何避免把相关性误认为因果关系；
4. 如何判断问题属于局部案例、领域通用能力还是全局基础设施；
5. 如何识别多个故障同时发生时的主因与次因；
6. 如何设计能够区分不同根因假设的诊断实验；
7. 如何通过对照实验确定提示词、记忆、上下文、工具或模型改动是否真正有效；
8. 如何避免优化一个指标，却让其他能力退化；
9. 如何将诊断结论传递给正确的专家、模块和适配版本；
10. 如何建立可复现、可审计、可回滚的持续进化闭环。

这一步尤其重要，因为它决定 EvoAgent 是一个“失败后不断尝试修改自己的系统”，还是一个“能够用证据识别问题、定位责任边界、验证改进效果，并逐步提高可靠性和效率的系统”。

我建议下一轮从第一性原理开始，先把**故障证据、诊断假设、根因判定和改进实验**之间的边界彻底理清，再设计具体的诊断算法和治理机制。
