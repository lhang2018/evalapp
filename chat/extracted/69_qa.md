# EvoAgent 第十四专项：能力边界、自主权限与长期目标一致性

这一轮要解决的是 EvoAgent 从“能做事的智能体”走向“可以长期放心使用的个人智能体”必须跨过的一道门槛。

我们已经讨论了如何让它理解意图、路由到专家、规划任务、调用工具、管理记忆、发现故障、自我修复和持续进化。

但这些能力越强，一个问题就越重要：

**EvoAgent 有能力完成一件事，不代表它有权执行这件事；它认为自己应该做，也不代表用户真的授权了。**

例如：

- 用户说“帮我整理一下手机”，不代表授权删除文件。
- 用户说“帮我把代码修好”，不代表允许它修改所有项目文件或直接发布版本。
- 用户说“帮我回复这条消息”，不一定意味着允许它不经确认就发送。
- 用户说“尽可能自动完成”，不代表允许它绕过系统权限。
- 智能体发现自己的工具有缺陷，也不能因此自行修改安全内核。
- 智能体从历史对话中知道用户经常使用某项服务，不代表它可以自动进行新的付费操作。

所以，我建议将本专项设计为：

**Capability Boundary & Autonomy Governance Engine（能力边界与自主权限治理引擎，简称 CAGE）。**

它负责明确智能体实际能做什么、当前被允许做什么，以及面对不确定性时应该如何限制自己的行动。

## 一、首先区分四个容易混淆的概念

这是整个权限架构的基础。


    <title size="lg">1. 技术能力 Capability</title>
    系统在当前环境下，实际上能够执行什么操作？
    例如：Android 无障碍服务能够读取部分界面节点，并尝试执行点击操作。


    <title size="lg">2. 能力可信度 Competence</title>
    系统是否有足够证据证明自己能够可靠完成这类操作？
    例如：系统可以点击按钮，但尚未证明它能稳定识别该应用的动态弹窗。


    <title size="lg">3. 执行权限 Authorization</title>
    当前用户、Android 系统和应用权限是否允许这次具体操作？
    例如：系统可以打开应用，但没有获得执行某项敏感操作所需的授权。


    <title size="lg">4. 当前行动许可 Action Permission</title>
    结合当前任务、目标对象、风险、授权范围和环境状态，这个动作现在是否可以执行？
    例如：用户授权发送一条消息，但当前收件人识别不确定，因此仍需暂停发送。


这四者必须分开管理。

一个工具可以在技术上可用，但可靠性不足；系统可以具备可靠的发送能力，但没有当前授权；用户也可能授权了某类操作，但当前对象不明确，不能安全执行。

因此，不能让模型仅凭“我能做”或“用户大概想让我做”就直接调用工具。

# 二、建立四层权限架构：谁决定智能体能做什么？

我建议采用四层控制，而不是把权限判断全部放进提示词里。


    **L1：系统硬性边界**
    Android 权限、系统安全机制、不可绕过的授权要求、硬性预算与安全限制。



    **L2：用户授权策略**
    用户允许哪些操作、作用于哪些对象、在什么条件下生效，以及何时需要再次确认。



    **L3：任务级行动许可**
    结合本次任务目标、具体动作、目标对象、可逆性、风险和当前状态，判断是否允许执行。



    **L4：执行网关**
    对实际工具调用进行确定性校验；只有通过授权检查的动作才能执行。


这四层不是简单地把权限从上往下传递，而是形成一道道必须通过的检查。

例如，用户允许 EvoAgent 自动操作某个应用，但 Android 无障碍服务已被关闭，那么操作仍然不能执行。

即使 Android 权限存在，如果本次任务没有获得发送消息的授权，执行网关也必须拒绝发送。

如果所有权限检查都通过，但目标收件人无法确定，任务级行动许可仍然应当暂停。

**最终决定权不能只存在于模型的推理结果中，必须落实到工具执行之前的确定性控制。**

## 2.1 权限控制与能力判断不能混为一体

CAGE 可以读取模型能力画像和工具健康状态，但它不应因为模型自认为能力很强，就自动扩大权限。

例如：

- 编程专家的代码修改成功率提高，可以提高其能力评估；
- 但这不能自动赋予它修改安全内核的权限；
- 手机操作专家在某个应用中表现稳定，可以降低该场景的验证成本；
- 但不能因此自动获得其他应用的敏感操作权限。

能力进步可以影响系统选择什么策略，却不能直接改变谁有权批准该策略。

# 三、设计自主等级：哪些事情可以自动做，哪些必须问你？

你希望 EvoAgent 尽可能自动完成任务，同时保留硬性权限边界。因此，我不建议所有操作都要求确认，也不建议所有操作都默认自动执行。

更合理的是建立明确的自主等级，并允许不同专家、不同任务和不同操作采用不同等级。

## 3.1 建议采用五级自主模型



      <title size="lg">A0</title>


      **只观察与建议**
      可以读取允许访问的信息、分析问题和提出建议，不执行改变外部状态的动作。
      示例：分析手机界面并告诉你下一步可以怎么操作。





      <title size="lg">A1</title>


      **低风险自动执行**
      自动执行已授权、可逆、低风险的动作，并验证结果。
      示例：打开指定应用、读取项目文件、生成草稿。





      <title size="lg">A2</title>


      **有界自主执行**
      在预先规定的对象、操作范围、成本和恢复条件内，自主完成多步骤任务。
      示例：在指定工作区修改代码、运行测试、修复非破坏性错误。





      <title size="lg">A3</title>


      **受控的高影响操作**
      可以准备、检查和执行部分高影响动作，但必须满足该操作专属的授权、身份和验收要求；需要确认时必须暂停。
      示例：准备发送消息、正式提交代码、执行会影响外部系统的操作。





      <title size="lg">A4</title>


      **禁止或仅允许受严格约束的动作**
      越权操作、绕过安全机制、超出用户授权的不可逆操作，以及违反硬性规则的行为。
      示例：擅自绕过 Android 权限，或未经授权执行付款。



需要强调：A4 不是“再确认一次就可以做”的等级。它表示该动作在当前规则下禁止执行；如果某类操作本身可以被合法授权，应由正式权限策略定义条件，而不是让模型临时决定例外。

## 3.2 自主等级不能只设置在整个智能体上

假设你把 EvoAgent 的默认自主等级设为 A2。

这不应该意味着所有操作都可以自动执行。

更合理的方式是同时设置：

- 全局自主上限；
- 专家级默认策略；
- 工具级操作限制；
- 当前任务的自主范围；
- 单个敏感动作的授权要求。

最终动作许可取决于所有适用规则中最严格的约束。

例如，编程专家可以自动修改指定项目中的普通源文件，但修改安全配置、删除大量文件或执行生产部署时，必须走更严格的流程。

这比简单地给智能体一个“自主程度 80%”的分数可靠得多。

# 四、授权必须精确到动作，而不是只精确到专家

这是整个权限系统最关键的设计细节之一。

假设你对 EvoAgent 说：

“你可以帮我自动操作手机。”

这句话表达了总体意愿，却不足以定义每种操作的授权边界。

打开应用、读取通知、修改联系人、发送消息、删除文件、进行支付，虽然都可能属于“操作手机”，但它们的风险和副作用完全不同。

所以，授权不能只绑定到某个专家或某个应用，而应该尽可能绑定到**具体动作、目标对象、操作范围和有效条件**。

## 4.1 设计授权策略实体

建议使用 `Authorization Policy` 管理授权规则，至少包含以下字段：

<CodeBlock language="json" editable>
{
  "policy_id": "policy-mobile-012",
  "subject": "evoagent_mobile_operator",
  "scope": {
    "applications": [
      "user_approved_app"
    ],
    "actions": [
      "launch_app",
      "read_visible_ui"
    ],
    "excluded_actions": [
      "send_message",
      "delete_data",
      "make_payment"
    ]
  },
  "conditions": {
    "max_risk": "LOW",
    "network_required": false,
    "verify_result": true
  },
  "approval_mode": "PREAUTHORIZED_WITHIN_SCOPE",
  "expiry": "USER_DEFINED",
  "revocation_supported": true,
  "policy_version": 3
}
</CodeBlock>

这只是协议示例，实际实现需要使用真实的应用标识、权限能力和有效期限，并且在执行时检查这些字段。

特别要注意：

- 不能让模型自行扩大 `applications` 或 `actions` 范围；
- 不能把历史上的一次确认解释为永久授权；
- 不能因为某个工具已经成功调用过，就认为以后任何参数都可以自动执行；
- 不能仅凭应用包名认定操作安全，具体动作和目标对象仍然重要。

## 4.2 授权应该有范围、期限和撤销能力

建议每项授权都可以回答以下问题：

- 允许谁执行？
- 允许什么动作？
- 允许作用于哪些目标？
- 在什么条件下允许？
- 授权什么时候到期？
- 哪些情况必须重新确认？
- 如何撤销？
- 撤销后如何处理正在执行的任务？

例如，你可以允许 EvoAgent 在指定工作区内自动修改代码，但不允许它修改工作区外的文件。

如果你撤销这项授权，系统应立即阻止后续相关写入，并在可行的情况下停止正在执行的工作。

对于已经完成的外部副作用，撤销授权不代表它们能够自动恢复。因此，系统还需要记录哪些动作已经发生，哪些仍然可以取消。

# 五、如何判断一个具体动作是否可以执行？

我建议将每次工具调用前的权限判断设计为一个独立的 `Action Authorization Gate`。

它不是大模型，而是执行网关内部的确定性决策组件。

每次准备执行动作时，都需要检查：

1. 当前用户和任务是否匹配；
2. 工具是否处于允许使用的状态；
3. 动作是否属于已授权范围；
4. 目标对象是否明确；
5. 是否存在额外的 Android 系统权限要求；
6. 当前自主等级是否允许此类动作；
7. 风险和可逆性是否满足规则；
8. 当前状态是否足够明确；
9. 是否满足必要的用户确认条件；
10. 动作是否会突破预算、次数或范围限制。


    **模型提出动作**
    例如：点击按钮、修改文件、发送消息。



    **Action Authorization Gate**
    核验身份、授权、范围、风险、状态和预算。


    <grid-item>


        **允许**
        交给工具执行器

    </grid-item>
    <grid-item>


        **拒绝或暂停**
        记录原因并采取安全降级

    </grid-item>



    **执行后再次核验**
    检查实际状态、结果和副作用。


这里需要区分“拒绝”和“暂停”。

- **拒绝**：动作违反当前硬性规则或超出授权范围。
- **暂停**：动作本身可能合法，但当前缺少信息、授权或必要证据。
- **允许**：所有适用的前置条件均已满足。

如果目标对象不明确，系统不能通过降低风险等级让动作自动通过。

如果授权不足，模型也不能以“用户大概率希望完成任务”为理由绕过执行网关。

## 5.1 运行时必须重新检查授权

不能只在任务开始时检查一次权限。

例如，用户授权执行一组文件操作，但执行过程中撤销了授权；又或者任务计划发生变化，原本只读取文件，后来决定删除文件。

这时必须重新检查。

我建议至少在以下节点重新核验：

- 新工具调用；
- 动作类型发生变化；
- 目标对象发生变化；
- 任务权限范围扩大；
- 从读取切换到写入或外部提交；
- 高影响动作执行之前；
- 授权被撤销或环境状态发生关键变化。

对于低风险且连续的内部操作，可以复用有效授权，避免频繁打扰用户；但不能复用授权来覆盖新的敏感动作。

# 六、能力不足时，智能体应该怎样处理？

权限解决的是“能不能做”，能力评估解决的是“能不能可靠地做”。

即使用户已经授权，也不代表系统必须盲目尝试。

例如：

- 编程专家被允许修改代码，但无法正确解析目标语言；
- 手机操作专家有无障碍权限，但当前页面的关键按钮无法识别；
- 漫剧专家可以调用视频生成服务，但当前角色一致性检查还没有可靠的验收方法；
- 某个模型在短任务上表现很好，但没有经过长上下文任务的验证；
- 某个工具刚刚更新，旧版本的成功率数据可能不再适用。

这些情况下，系统应当根据能力证据选择降级、换工具、局部试验、请求协助或停止。

## 6.1 建立能力状态，而不是只记录一个成功率

建议每项能力都具有以下状态：

| 状态 | 含义 | 默认行为 |
|---|---|---|
| `UNTESTED` | 尚未经过充分测试 | 限制使用范围，优先测试 |
| `QUALIFIED` | 在明确的条件下通过了必要评测 | 在已验证范围内使用 |
| `DEGRADED` | 近期表现下降或环境发生变化 | 降低自主程度，增加验证 |
| `UNRELIABLE` | 已发现重大缺陷或持续失败 | 隔离相关能力，禁止承担关键任务 |
| `RECOVERING` | 正在重新测试或恢复 | 限制使用，等待重新验收 |

能力状态必须绑定适用范围。

例如，某个视觉识别能力可能在指定应用、指定 Android 版本下处于 `QUALIFIED`，但在另一种应用界面中仍然是 `UNTESTED`。

这比简单地说“手机操作能力已经通过测试”更加精确。

## 6.2 能力状态不能自动转化为权限

假设编程专家的测试成功率从 90% 提高到 98%。

这可以支持系统减少某些低风险任务的额外检查，但不能自动让它获得部署生产代码的权限。

同样，某个工具连续成功执行 100 次，也不能因此绕过权限校验。

**能力评估可以影响执行策略，权限规则决定动作边界。**

这两者需要分别管理，并通过明确的策略接口协作。

## 6.3 能力不足时，优先采取最小降级

我建议采用以下顺序，但允许根据风险直接跳到更严格的处理方式：

1. 重新观察或补充必要信息；
2. 切换到已验证的工具或策略；
3. 将任务拆分成更容易验证的子任务；
4. 仅对不确定部分开展隔离试验；
5. 请求用户提供缺失信息或批准替代方案；
6. 停止当前任务，并保存可恢复的进度。

例如，代码专家无法安全地自动完成一次复杂重构时，可以先生成补丁、运行静态检查和测试，再把剩余不确定部分交给用户审查，而不是直接修改整个项目。

# 七、历史记忆和用户习惯，不能被误认为当前授权

这是个人智能体长期使用后很容易出现的问题。

EvoAgent 可能记住：

- 你通常喜欢自动完成任务；
- 你经常使用某个应用；
- 你倾向于让它直接修改代码；
- 你一般不喜欢频繁确认；
- 你经常使用某种模型或工作流。

这些记忆很有价值，可以减少重复沟通，但它们不等于新的授权。

建议将相关信息严格区分为三类。


    **用户偏好 Preference**
    影响默认交互方式，例如偏好简洁回复、先生成草稿或减少低风险确认。


    **用户授权 Authorization**
    明确规定哪些操作可以执行、作用范围和有效条件，必须来自正式授权流程。


    **当前任务意图 Intent**
    用户当前希望达成什么目标，决定这次任务应做什么，而不是永久改变系统权限。


例如，用户偏好“尽可能自动操作手机”，可以让系统在低风险、可逆操作中减少提问。

但如果本次任务涉及删除文件、发送消息或支付，仍然必须遵循对应动作的授权规则。

同样，用户过去授权某个工作区的写入操作，不代表现在可以将文件写到其他目录。

## 7.1 如何处理模糊指令？

建议根据缺失信息的性质选择不同方式：

- 缺少非关键偏好：可以采用已知偏好或安全默认值；
- 缺少任务对象：尝试从当前上下文确认，仍然有歧义时提问；
- 缺少授权：进入授权流程，不能通过记忆补足；
- 缺少状态证据：先观察或核验环境；
- 缺少专业能力：换用已验证的能力，或明确说明限制。

这样既能利用记忆提高效率，又能避免“记得用户通常这么做”演变成“替用户决定这次应该这么做”。

# 八、自进化系统不能自行扩大自己的权限

这是 CAGE 必须拥有的一条硬性规则。

因为 EvoAgent 不仅会执行任务，还会修改提示词、工具策略、路由、工作流和部分运行配置。

如果它可以通过一次普通的进化任务修改自己的权限策略，那么之前所有的权限控制都可能失去意义。

例如，智能体发现发送消息时总是需要用户确认，于是它提出优化建议：

“为了提高自动化率，将发送消息的确认条件取消。”

从任务完成率角度看，这可能让执行更顺畅；但从授权治理角度看，这种改动可能扩大系统的行动范围。

因此，我建议将权限系统与普通进化资产彻底分离。

## 8.1 建立权限策略的保护级别

| 资产类型 | 普通进化系统能否直接修改 |
|---|---|
| 普通提示词和领域策略 | 可以生成候选，经过评测后发布 |
| 模型路由与规划参数 | 可以生成候选，经过门禁后发布 |
| 工具实现 | 可以提出补丁，必须经过测试和权限检查 |
| 普通工作流配置 | 可以在限定范围内迭代，需验证副作用 |
| 权限策略与自主等级上限 | 只能提出变更建议，不能自行批准 |
| 安全内核与发布门禁 | 受保护，普通进化任务无权解除或绕过 |
| 用户授权记录 | 只能通过正式授权或撤销流程更新，不能由模型伪造 |

这里并不意味着所有权限策略都永远不能变化，而是要求变化必须经过独立、明确的授权流程。

例如，你可以主动在设置中允许某个新的操作范围；但模型不能因为某个操作经常失败，就自行把它加入已授权范围。

## 8.2 权限修改应采用独立的变更流程

建议将权限变更拆成：

1. 系统发现当前权限限制影响了某项任务；
2. 生成一份明确的变更建议；
3. 展示变更前后的差异、影响范围和风险；
4. 由具备相应权限的用户或正式策略管理流程批准；
5. 更新授权策略并记录版本；
6. 对新策略进行必要的安全测试；
7. 如果发生异常，撤销新策略并恢复原配置。

不能把“用户批准了某项任务”解释成“用户批准了永久扩大权限”。

批准范围必须明确，任务级批准与策略级变更必须分开。

# 九、离线、断网和恢复连接时，权限如何保持一致？

结合 EvoAgent 的手机优先方向，这一问题必须在本地架构中解决，而不能完全依赖远端服务器。

建议将权限执行分成两个部分：

- **本地权限执行内核**：负责 Android 当前能够执行的动作，检查本地授权、系统权限、动作范围和风险规则。
- **远端策略同步接口**：在可用时同步策略版本、审计事件、撤销信息和必要的配置变更。

本地内核必须能在断网时继续执行允许的低风险操作，也必须能够在断网时拒绝未经授权的操作。

## 9.1 离线权限策略的原则

建议遵循以下规则：

- 已缓存且仍然有效的低风险授权，可以在明确范围内继续使用；
- 需要在线核验的授权，如果网络不可用，则暂停依赖该核验的操作；
- 远端任务结果未知时，不能因本地超时而重复执行可能产生副作用的动作；
- 本地不能确认授权状态时，不应自动扩大授权范围；
- 权限策略的版本和生效范围应当被记录；
- 恢复连接后，先同步授权变更和撤销信息，再恢复相关任务。

这里还需要明确一个现实限制：如果手机完全离线，远端刚刚发生的授权撤销无法立即传到本地。

因此，对于高风险动作，不能依赖一个可能过期的本地授权缓存。如果某项授权要求实时在线确认，断网就必须暂停该动作。

对于低风险、可逆、已明确授权的操作，可以允许离线执行，但必须有清晰的有效期和范围。

## 9.2 断网不应该成为权限降级的理由

有一种危险设计是：在线时检查权限，离线时为了保证任务完成，就放宽权限。

我建议明确禁止这种行为。

网络故障可以改变可用能力，但不能自动扩大权限。

例如，云端模型不可用时，手机可以继续打开允许打开的应用、读取允许读取的界面、保存任务进度；但不能因为无法联系服务端，就自动执行原本需要额外确认的敏感动作。

这里的许可结果最好是明确的枚举状态，而不是让模型返回一句模糊的“应该可以”。

- `ALLOW`：所有适用的执行条件均满足。
- `DENY`：违反硬性规则或明确超出授权范围。

- `DEFER`：当前状态、能力或外部条件不足，需要先补充证据。

实际实现中，授权状态应由确定性控制器生成。模型只能提交动作提案，不能自行伪造许可结果。

## 10.1 一个关键的实现细节：防止检查后状态发生变化

假设系统检查了目标页面，确认可以点击某个按钮；但在真正执行之前，页面已经发生变化。

如果执行器直接使用旧的检查结果，可能会操作错误的对象。

因此，对于依赖环境状态的动作，行动许可还应该绑定相关状态版本或检查点。执行时如果发现关键状态已经变化，就需要重新检查。

同样，授权被撤销、目标对象变化、任务范围扩大时，也必须重新核验。

对于具有外部副作用的操作，最好采用支持幂等键、状态查询或明确提交确认的工具协议，降低重复执行风险。

# 十一、如何评估权限治理是否真正有效？

CAGE 不能只看它拦截了多少次操作。

拦截越多不代表越安全，因为系统可能变得过度保守；拦截越少也不代表体验越好，因为它可能漏掉了必要的限制。

建议建立独立的权限与自主能力评测集。

| 指标 | 衡量内容 |
|---|---|
| 未授权动作拦截率 | 超出授权范围的动作是否被正确阻止 |
| 错误放行率 | 不应执行的动作是否被错误允许 |
| 错误拒绝率 | 本来允许的安全动作是否被不必要地阻止 |
| 授权范围准确率 | 是否正确识别动作、目标对象和有效范围 |
| 撤销生效时间 | 授权撤销后，后续动作多久停止 |
| 离线权限一致性 | 断网后是否仍然遵守已定义的权限边界 |
| 越权尝试检测率 | 模型或工具是否尝试超出当前权限范围 |
| 结果核验率 | 实际执行后是否正确检查了结果和副作用 |
| 用户确认负担 | 在保障安全的前提下，需要多少额外确认 |
| 自主任务完成率 | 在授权范围内，系统能否真正自动完成任务 |

还需要专门测试一些反例：

- 用户曾经授权，但后来已经撤销；
- 任务目标从读取变成删除；
- 模型自信地声称用户已经授权，但实际没有授权记录；
- 工具返回成功，但实际状态未改变；
- 远端操作超时，无法确认是否已执行；
- 模型提出修改权限系统的进化方案；
- 旧模型和新模型对授权语义的理解不同；
- 本地离线策略与已知的远端策略版本不一致。

这些测试比只验证正常流程更重要，因为权限系统的价值主要体现在异常情况下仍然能够守住边界。

# 十三、下一专项：智能体的可观测性、因果归因与可解释执行

到目前为止，我们已经设计了：

- 如何理解用户意图并路由到专家；
- 如何规划和执行复杂任务；
- 如何管理记忆与上下文；
- 如何诊断、修复和恢复故障；
- 如何适配不同模型并独立进化；
- 如何决定优化什么、分配多少资源；
- 如何确保进化方向符合全局目标；
- 如何控制自主程度和行动权限。

但还缺少一个贯穿所有这些模块的基础能力：

**当 EvoAgent 完成或失败一次任务时，我们能否真正还原它为什么这样做、哪个组件影响了结果，以及究竟是什么变化让系统变好了或变差了？**

这不只是日志记录问题。

例如，一次代码任务失败，可能同时涉及：

- 意图识别；
- 路由选择；
- 记忆检索；
- 上下文压缩；
- Planner 的任务分解；
- ReAct 的行动选择；
- 工具执行；
- 结果验收；
- 自我修复。

如果只保存最终回答和错误日志，系统很难知道应该优化哪个环节。

更麻烦的是，如果修改提示词后任务成功率提升，也不能直接证明提示词就是原因。可能是模型版本变化、测试样本差异或工具环境变化导致的。

下一专项建议设计 `Observability, Causal Attribution & Explainable Execution Engine`，重点研究：

1. 如何建立从用户请求到最终结果的完整执行轨迹；
2. 如何关联任务、专家、模型、工具、工作流和配置版本；
3. 如何区分相关性、故障位置与真正的根因；
4. 如何在不泄露敏感信息的前提下保留足够诊断证据；
5. 如何通过回放、对照实验和消融测试验证改进原因；
6. 如何定位共享组件对多个专家的影响；
7. 如何发现模型或工具升级造成的隐性退化；
8. 如何让每次进化都有明确的基线、变更、评测和回滚依据；
9. 如何在个人电脑和 Android 断联时仍然保持事件可追溯；
10. 如何把可观测性结果反馈给 EPRA、GOCG、CAGE 和自我修复系统。

这一步会让 EvoAgent 不仅能够行动、学习和保护自己，还能够**基于证据理解自身行为，判断哪些改进真正有效，并把整个进化过程变成可追踪、可验证、可纠错的工程闭环**。
