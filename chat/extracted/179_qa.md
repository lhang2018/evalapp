<WritingBlock id="52684" variant="document"># EvoAgent 专项设计 #96：端到端质量评测体系、真实任务基准与持续回归治理

**英文名称：** End-to-End Quality Evaluation, Real-Task Benchmarking & Continuous Regression Governance

**文档版本：** 1.0

**关联专项：** #75—#95

**设计状态：** 专项设计基线，待实施与验收。

## 一、专项目标

建立一套能够持续衡量 EvoAgent 的任务质量、执行效率、稳定性、成本和安全表现的统一评测体系，为所有进化候选提供可复现的质量证据。

本专项要回答五个核心问题：

1. 新版本是否真正提高了用户任务的完成质量？
2. 提升是否能够在不同任务、专家、设备和环境中复现？
3. 是否出现了局部提升、整体退化的情况？
4. 评测结果是否可信，能否避免评测器偏差与测试集过拟合？
5. 什么条件下可以自动发布、需要继续观察、必须拒绝或应当回滚？

最终建立以下闭环：

**真实任务与故障案例 → 基准构建 → 稳定版与候选版对照 → 多维质量评测 → 回归门禁 → 受控发布 → 真实运行监测 → 新案例进入评测集。**

本专项不是简单增加一个自动打分模块，而是让 EvoAgent 的进化从“感觉新版本更聪明”变成“有证据证明新版本在明确范围内更好”。

## 二、设计原则

### 2.1 任务质量优先

任何候选版本都不能单纯因为速度更快、成本更低或模型分数更高而被认定为更好。

如果一个版本减少了模型调用，但导致用户需要更多返工，就不能仅凭成本下降通过门禁。

如果一个版本更积极地完成任务，却增加了未经授权的操作，也不能认定为质量提升。

### 2.2 评测器与被评测对象分离

被测智能体不能独自决定自己的任务是否成功。

应尽可能使用独立、可复现的验证方式，例如：

- 程序构建和自动化测试；
- 文件、数据库或界面的实际状态检查；
- 工具契约测试；
- 任务特定的验收规则；
- 独立评审与抽样人工审核。

模型评审可以用于难以自动判断的开放式任务，但不能代替可直接执行的客观检查。

### 2.3 多维指标不能相互掩盖

系统必须同时检查质量、约束、安全、效率、稳定性和成本。

不能用某个维度的高分抵消另一个维度的硬性失败。

例如，代码生成质量得分再高，只要关键测试失败，就不能将其判定为完全通过。

### 2.4 共享内核与领域专家分别评测

每个专家都需要自己的专项评测集，同时需要一组跨领域的通用能力回归集。

这样可以避免代码专家的优化损害手机操作专家，也可以避免某个领域的特殊策略污染共享通用内核。

### 2.5 评测必须绑定实际版本

每次评测都应记录实际使用的模型、提示词、工具、路由策略、上下文策略、专家、工作流和环境版本。

无法确定实际运行组合的评测结果，不应作为正式发布证据。

## 三、评测体系总体架构

### 3.1 六层评测体系

| 层级 | 评测对象 | 主要目的 |
|---|---|---|
| L1：契约与单元测试 | 单个工具、解析器、数据结构、规则 | 检查局部功能正确性 |
| L2：组件评测 | 意图理解、路由、上下文、规划、验收器 | 定位具体能力变化 |
| L3：工作流评测 | 专家工作流、固定 DAG、灵活计划 | 验证多步骤执行质量 |
| L4：端到端任务评测 | 从用户请求到最终交付的完整过程 | 衡量实际任务完成质量 |
| L5：跨专家与跨环境回归 | 共享内核、多个专家、不同设备与网络状态 | 发现系统性退化 |
| L6：真实运行持续评测 | 经授权处理的实际运行案例和用户反馈 | 验证线上表现与真实价值 |

六层并非每次都必须全部执行。

局部工具修改可以先执行 L1 和相关 L2；共享内核、路由器、上下文策略或模型适配的重要变化，则需要执行更广泛的回归测试。

任何准备进入稳定版本的变更，都必须满足其风险等级对应的最低评测要求。

### 3.2 评测平台的逻辑组件

建议包括：

1. Benchmark Registry：评测基准注册表；
2. Dataset Manager：测试数据集版本管理；
3. Scenario Generator：受控场景与环境变化生成；
4. Evaluation Runner：稳定版与候选版执行器；
5. Evidence Collector：结果、事件和运行证据收集；
6. Evaluation Engine：指标计算与验收；
7. Regression Analyzer：差异分析与退化定位；
8. Release Gate：发布准入判断；
9. Production Feedback Collector：真实运行案例回收；
10. Evaluation Governance：评测集、评测器和基准自身的质量治理。

这些是逻辑组件，不要求分别部署为独立服务。

## 四、真实任务基准设计

### 4.1 基准必须来源于真实任务

评测基准不能只由容易回答的静态问题构成。

应覆盖真实使用中的完整任务，例如：

- 用户提供不完整需求，需要合理理解并完成；
- 任务需要读取文件、调用工具并交付成果；
- 工具调用失败，需要诊断与恢复；
- 任务需要多个专家协同；
- 网络中断后需要继续执行或恢复；
- 长期项目中需要遵守已经确认的约束；
- 任务结果必须通过实际测试才能判定成功；
- 系统需要发现潜在问题并提出建议，但不能擅自改变任务范围。

### 4.2 基准数据来源

建议使用四类来源。

**A. 人工设计的标准案例**

覆盖关键功能、边界条件、失败路径和高风险情景。

**B. 已确认结果的历史案例**

将已验证的真实任务转化为可重复评测的案例，保留必要的输入、环境约束、验收规则和版本信息。

**C. 经授权、隐私处理的运行案例**

从真实运行中发现反复出现的失败、返工、误路由和验收缺陷。

**D. 受控生成的对抗案例**

通过改变输入完整性、工具输出、网络状态、权限状态或环境版本，验证系统在变化条件下的表现。

历史案例不能未经处理就自动成为公开或跨用户共享的测试数据。数据的使用范围必须遵循既有隐私和权限策略。

### 4.3 任务类型覆盖

建议至少维护以下基准类别：

| 基准类别 | 重点验证内容 |
|---|---|
| 通用问答与信息整理 | 事实正确、相关性、表达与约束满足 |
| 需求理解与澄清 | 正确识别关键歧义，避免不必要追问 |
| 编程与软件工程 | 构建、测试、接口兼容、代码质量与回归 |
| 信息研究 | 证据质量、来源可靠性、结论与事实的一致性 |
| 手机操作 | 权限遵守、界面识别、操作结果和副作用验证 |
| 文件与数据处理 | 文件完整性、格式正确性、数据准确性 |
| AI 内容创作 | 内容要求、输出格式、质量与预算约束 |
| 工作流自动化 | 节点契约、依赖、失败恢复和端到端成功率 |
| 长期项目 | 历史约束保持、状态更新、任务连续性 |
| 主动帮助 | 建议的相关性、可操作性、实际价值和打扰成本 |
| 故障诊断与修复 | 根因判断、证据完整性、修复成功率和回归风险 |
| 离线与断联 | 本地可用性、事件完整性、重连同步与状态一致性 |

每类基准还应覆盖简单、普通、复杂、高影响等不同难度与风险等级。

### 4.4 单个评测案例的数据契约

建议建立版本化的 `Evaluation Case` 逻辑结构。

```json
{
  "case_id": "stable-id",
  "case_version": 1,
  "task_category": "coding",
  "difficulty": "complex",
  "risk_class": "medium",
  "input_ref": "controlled-input-reference",
  "environment_ref": "environment-version",
  "required_constraints": [],
  "expected_deliverables": [],
  "acceptance_contract_ref": "contract-id/version",
  "evaluation_methods": [],
  "failure_modes": [],
  "privacy_level": "internal",
  "dataset_partition": "release_gate",
  "case_status": "approved"
}
```

以上为设计示例，不是已经批准的正式 Schema。

案例必须包含足够的信息，保证在规定环境下可以重复执行和判断结果。

对于开放式任务，不要求存在唯一标准答案，但必须定义适当的评价维度、硬性约束和判定规则。

## 五、评测集分层与防止过拟合

### 5.1 五类评测集

| 评测集 | 用途 | 是否可以用于反复调优 |
|---|---|---|
| 开发集 | 诊断问题、尝试改进 | 可以 |
| 验证集 | 比较不同候选策略 | 可以，但需记录使用情况 |
| 固定回归集 | 检查已知能力是否退化 | 可以执行，不应无记录地反复改写 |
| 隐藏保留集 | 检验泛化能力，防止针对已知案例优化 | 严格限制访问 |
| 真实运行抽样集 | 检验生产表现 | 按隐私与数据治理规则使用 |

固定回归集与隐藏保留集承担不同职责，不能完全合并。

如果所有测试案例都被用于调优，系统可能逐渐学会应付测试，却没有真正提升对新任务的处理能力。

### 5.2 评测集版本管理

每次评测集变更都应记录：

- 新增、删除或修改的案例；
- 变更原因；
- 变更来源；
- 验收标准是否改变；
- 是否存在数据泄漏风险；
- 对历史评测结果的影响。

不能在候选版本失败后，直接修改验收标准让它通过。

如果发现旧的验收标准确实错误，应通过独立的基准治理流程修改，并保留旧版本及变更记录。

### 5.3 数据泄漏与记忆污染

如果某个专家在调优时已经接触隐藏案例的答案，该案例就不能再被视为完全独立的隐藏测试。

同样，如果某次真实任务的标准答案被直接写入长期记忆，后续再使用相同任务评测时，必须标记其可能受到记忆污染。

评测平台应能够记录案例使用历史，并在必要时轮换隐藏案例。

## 六、统一质量指标体系

### 6.1 任务成功率

任务成功率应根据正式验收标准计算，而不是根据执行器是否返回成功状态计算。

\[
\text{任务成功率}
=
\frac{\text{验收通过的任务数}}{\text{纳入评测的有效任务数}}
\]

对于存在部分完成、不同风险等级或不同任务类型的场景，应同时报告分层结果。

不应把未运行、被跳过或缺失关键证据的案例直接算作成功。

### 6.2 硬性约束满足率

统计任务是否遵守用户明确要求、必要权限、预算边界和其他硬性约束。

任何关键安全或授权违规都应单独报告，不能被总体平均分掩盖。

### 6.3 交付质量

根据任务类型分别评估：

- 正确性；
- 完整性；
- 相关性；
- 可用性；
- 可维护性；
- 证据充分性；
- 用户要求满足程度。

不能将所有任务统一压缩成一个没有解释力的总分。

### 6.4 效率与成本

至少测量：

- 端到端完成时延；
- 模型调用次数与费用；
- 工具调用次数；
- 重试与返工次数；
- 人工介入次数；
- 单位成功交付成本；
- 诊断与评测本身产生的额外成本。

成本应按照实际使用的模型和外部服务计量，不能只用调用次数近似代表真实成本。

### 6.5 稳定性与恢复能力

至少测量：

- 执行异常率；
- 超时率；
- 任务中断率；
- 失败恢复成功率；
- 重复执行造成的副作用；
- 离线缓存和同步完整性；
- 修复后回归率；
- 误报成功率。

### 6.6 主动帮助价值

针对主动发现问题、提供建议或推进长期目标的能力，应额外评估：

- 建议与当前目标的相关性；
- 建议是否基于真实证据；
- 是否提供了可操作的下一步；
- 是否避免重复建议；
- 是否产生了可验证的收益；
- 是否增加不必要的打扰；
- 是否越过用户授权或目标边界。

建议被用户采纳可以作为一种信号，但不能单独作为质量证明。用户不采纳建议，也不必然意味着建议没有价值。

## 七、稳定版与候选版的公平对照

### 7.1 对照原则

每次进化评测都应比较：

- 当前稳定版本；
- 待验证的候选版本。

对于可重复执行的案例，两者应使用相同的输入、环境约束和验收标准。

如果变更本身涉及环境或模型版本，则必须记录这些差异，避免把环境变化造成的结果误判为策略提升。

### 7.2 固定条件

对照实验应尽可能固定：

- 测试输入；
- 评测集版本；
- 工具和依赖版本；
- 执行权限；
- 预算限制；
- 网络与外部服务条件；
- 验收规则；
- 运行环境。

对随机性较强的模型任务，可以进行多次重复运行，并记录随机性、方差和运行次数。

### 7.3 配对比较

对每个案例，记录稳定版和候选版各自的结果。

例如：

| 案例 | 稳定版 | 候选版 | 判断 |
|---|---|---|---|
| A | 验收通过 | 验收通过 | 保持 |
| B | 验收通过 | 验收失败 | 回归 |
| C | 验收失败 | 验收通过 | 改进 |
| D | 验收失败 | 验收失败 | 未改善 |

这种方式能够帮助系统识别真正的改进与退化，而不是只比较两个版本的总体分数。

### 7.4 统计不确定性

对于样本量较小或运行结果波动较大的评测，不应将微小差异直接解释为真实提升。

应根据任务类型、样本量和随机性选择适当的统计方法，并报告样本数量、差异幅度与不确定性。

对于关键安全、权限和数据完整性测试，即使总体成功率很高，也不能用统计平均值替代必要的逐项验证。

## 八、独立评测与评测器治理

### 8.1 评测器分级

建议区分四类评测器。

**E1：确定性评测器**

用于构建、Schema、文件状态、明确规则、权限约束和其他能够客观验证的条件。

**E2：任务专用评测器**

用于代码质量、研究证据完整性、工作流输出等需要领域规则的任务。

**E3：模型辅助评审**

用于开放式写作、方案质量、建议相关性等难以完全自动化的内容。

**E4：人工抽样评审**

用于校验自动评测器的偏差、处理高影响争议案例，以及校准复杂任务的质量标准。

### 8.2 不同评测器之间的分歧

如果确定性测试通过，但模型评审认为结果质量较差，系统应保留这种分歧，而不是强行合并为一个分数。

如果模型评审认为成功，但实际文件缺失或测试失败，应以适用的客观验收条件为准。

当多个评测器产生冲突时，应根据事先定义的任务验收契约处理，并在必要时转入人工复核。

### 8.3 评测器自身也需要评测

评测器应具备独立测试集，覆盖：

- 明确的成功案例；
- 明确的失败案例；
- 边界案例；
- 不同格式与表达方式；
- 伪造的成功信号；
- 真实成功但表达不完美的案例；
- 与评测器自身版本相关的回归。

任何评测器的升级都可能改变候选版本的通过率，因此必须单独记录评测器版本，不能只记录被测智能体的版本。

## 九、跨专家回归与能力隔离

### 9.1 三层回归范围

建议每次变更至少识别三个影响范围：

**局部回归**

只测试被修改的工具、提示词、工作流或专家。

**共享依赖回归**

测试依赖被修改能力资产的所有相关组件和专家。

**全局保护回归**

测试受保护的共享通用内核、关键路由行为、权限策略和核心任务执行能力。

### 9.2 变更影响图

每个能力资产都应声明依赖关系。

当某项共享能力发生变化时，评测平台应根据依赖图选择相关回归集。

例如：

- 修改代码专家的 AST 分析工具，重点验证代码相关任务及其依赖；
- 修改共享上下文压缩策略，需要扩大到多个专家的长上下文任务；
- 修改统一路由策略，需要验证各专家的路由正确率和错误回退行为；
- 修改公共工具执行器，需要检查依赖该执行器的工作流；
- 修改授权系统，需要运行相关安全与权限回归。

不能只测试变更所在模块，而忽略其实际影响范围。

### 9.3 防止全局退化

每次发布都应分别检查：

- 目标专家的提升；
- 其他相关专家的变化；
- 共享通用内核的变化；
- 高风险任务的变化；
- 关键回归集的变化。

如果一个领域专家的收益伴随着其他专家的明显退化，必须进行明确的收益与风险评估，不能直接发布到所有专家。

## 十、自动发布门禁

### 10.1 门禁基本结构

候选版本必须经过以下检查：

1. 制品与依赖完整性；
2. 契约和单元测试；
3. 目标能力评测；
4. 相关专家回归；
5. 全局保护回归；
6. 安全、权限和数据完整性测试；
7. 成本与时延检查；
8. 统计不确定性分析；
9. 兼容性检查；
10. 发布与回滚准备检查。

具体检查范围取决于变更类型和风险等级。

### 10.2 发布判定

建议将候选版本分为四类结果：

| 结果 | 含义 | 后续处理 |
|---|---|---|
| `PASS` | 满足全部适用门禁 | 可以进入下一发布阶段 |
| `PASS_WITH_LIMITS` | 仅在明确限定范围内通过 | 限定范围发布或继续验证 |
| `HOLD` | 证据不足或结果不确定 | 补充评测，不进入稳定版本 |
| `REJECT` | 发生关键失败或明显回归 | 拒绝发布并记录原因 |

`PASS_WITH_LIMITS` 不能用于绕过安全门禁。任何限制都必须能够通过实际执行策略强制落实，而不只是写在报告中。

### 10.3 质量阈值

阈值应按任务类别、专家、风险等级和变更类型配置。

例如：

- 关键权限和安全测试必须全部通过；
- 关键工具契约测试不得出现未解决的失败；
- 核心验收指标必须达到对应任务类别的准入要求；
- 重要质量指标不能超过预先规定的退化容忍范围；
- 成本和时延必须满足对应的资源预算；
- 证据缺失时不能推定通过。

具体阈值应由基准数据、实际质量要求和运行成本校准，不应为所有专家设置一个脱离任务特征的统一数字。

### 10.4 自动发布边界

可以自动发布的对象应优先限定为：

- 变更范围明确；
- 风险较低；
- 可复现验证；
- 不改变安全边界；
- 具备可靠回滚能力；
- 已通过适用门禁的能力资产。

涉及共享核心内核、安全策略、授权机制、数据结构迁移或高影响外部行为的变更，应采用更严格的审批与发布流程。

## 十一、受控发布、监测与回滚

### 11.1 发布阶段

建议采用以下发布阶段：

1. 离线评测；
2. 隔离环境验证；
3. 影子评测或不影响用户结果的对照运行；
4. 限定范围的候选启用；
5. 稳定版本发布；
6. 发布后持续监测。

对于个人使用的 Android 或 Windows 环境，限定范围可以采用独立候选工作区、按任务启用或显式选择候选版本，不一定需要传统的大规模服务端灰度部署。

### 11.2 发布后监测

发布后应重点监测：

- 任务验收通过率；
- 关键错误率；
- 执行时延与成本；
- 失败恢复情况；
- 用户反馈与返工；
- 关键专家的表现；
- 新增的异常模式。

真实运行数据与离线基准结果不一致时，应进一步分析原因，而不是只相信离线测试。

### 11.3 回滚条件

出现以下情况时，应依据预先定义的规则暂停或回滚：

- 关键安全或授权问题；
- 核心契约发生不兼容；
- 重要任务类别显著退化；
- 成本超过批准上限；
- 关键工作流出现不可接受的失败；
- 数据完整性或状态一致性受到影响；
- 真实运行结果与发布准入条件明显不符。

回滚应恢复到已知可用的版本，同时保留导致回滚的证据，防止相同问题在下一轮进化中再次出现。

## 十二、评测结果的数据契约

### 12.1 Evaluation Run

每次评测应形成不可歧义的记录，建议包含：

```json
{
  "evaluation_run_id": "stable-id",
  "candidate_manifest_id": "candidate-runtime",
  "baseline_manifest_id": "stable-runtime",
  "evaluation_suite_ref": "suite-id/version",
  "dataset_version": "dataset-version",
  "evaluator_versions": [],
  "environment_digest": "sha256",
  "case_results_ref": "results-reference",
  "metric_summary_ref": "metrics-reference",
  "regression_summary_ref": "regression-reference",
  "gate_decision": "HOLD",
  "evidence_refs": [],
  "created_at": "RFC3339"
}
```

以上是设计示例，实际实现应使用正式的版本化 Schema。

### 12.2 单个案例结果

每个案例结果应关联：

- `evaluation_run_id`；
- `case_id` 与案例版本；
- 被测版本和运行环境；
- 任务是否真正执行；
- 原始执行结果的引用；
- 验收器结果；
- 失败分类；
- 时延与成本；
- 约束满足情况；
- 评测证据；
- 是否需要人工复核。

不得只保存一个总分而丢失失败原因与原始证据。

### 12.3 发布证据关联

正式发布清单应关联：

- 候选能力资产版本；
- 评测套件版本；
- 基准数据集版本；
- 评测器版本；
- 门禁判定；
- 兼容性声明；
- 发布范围；
- 回滚目标；
- 发布后监测要求。

这样才能在未来发生问题时，追溯某个版本为什么被允许发布。

## 十三、评测系统自身的持续进化

### 13.1 评测系统也会失效

评测系统可能出现：

- 测试覆盖不足；
- 评测器存在偏差；
- 案例过时；
- 测试数据泄漏；
- 隐藏集被过度使用；
- 任务难度分布不合理；
- 关键风险场景缺失；
- 某些专家的测试权重不足。

因此，评测体系不能被视为永远正确的最终裁判。

### 13.2 评测治理流程

当真实运行发现评测遗漏时，应执行：

1. 收集实际故障证据；
2. 判断是否属于现有基准未覆盖的场景；
3. 形成新的评测案例；
4. 确认验收标准；
5. 检查数据隐私和案例泄漏风险；
6. 将案例加入适当的评测集；
7. 验证候选版本在新案例上的表现；
8. 记录基准变更及其影响。

新增案例不能直接改变既有历史评测的判定结果，除非通过正式的基准版本变更流程重新评测。

### 13.3 防止指标投机

系统不得为了通过门禁而：

- 删除难度较高的案例；
- 降低验收标准；
- 隐瞒失败案例；
- 通过增加重试掩盖实际质量下降；
- 将未完成的任务标记为成功；
- 让被测模型直接修改评测器；
- 只报告有利的任务子集；
- 用平均分掩盖关键安全失败。

任何对评测数据、指标或阈值的修改，都必须留下可审查的变更记录。

## 十四、核心验收测试矩阵

| 测试 ID | 测试场景 | 通过条件 |
|---|---|---|
| EVAL-01 | 相同输入重复评测 | 结果能够关联到对应版本和环境 |
| EVAL-02 | 候选版改善部分案例 | 能识别改善案例及其幅度 |
| EVAL-03 | 候选版导致其他案例退化 | 能识别回归并阻止不合规发布 |
| EVAL-04 | 候选版速度提高但质量下降 | 不能仅凭速度提升通过 |
| EVAL-05 | 候选版成本下降但返工增加 | 能结合返工与成功交付成本判断 |
| EVAL-06 | 关键安全案例失败 | 触发强制门禁，不允许平均分抵消 |
| EVAL-07 | 评测器与实际状态冲突 | 以适用的独立证据核实结果 |
| EVAL-08 | 隐藏集存在数据泄漏 | 将相关案例标记为受污染并采取治理措施 |
| EVAL-09 | 新专家加入系统 | 建立对应的专家评测与相关全局回归 |
| EVAL-10 | 共享内核发生变更 | 执行跨专家保护回归 |
| EVAL-11 | 路由策略发生变更 | 检查各专家的路由与任务成功表现 |
| EVAL-12 | 模型版本发生变化 | 记录模型版本并执行相关对照评测 |
| EVAL-13 | 工具契约发生变化 | 执行契约测试及依赖工作流回归 |
| EVAL-14 | 评测样本量不足 | 输出不确定性并避免过度解读 |
| EVAL-15 | 评测集版本变化 | 保留旧版本并记录变更原因 |
| EVAL-16 | 候选版本缺少兼容声明 | 阻止进入稳定通道 |
| EVAL-17 | 评测结果证据不完整 | 不能直接判定正式通过 |
| EVAL-18 | 发布后出现严重退化 | 能够定位版本并按策略暂停或回滚 |
| EVAL-19 | 真实任务暴露新失败模式 | 能形成新的评测案例 |
| EVAL-20 | 主动建议数量增加但价值下降 | 不将建议数量增加视为质量提升 |
| EVAL-21 | 候选版本通过目标专家测试但全局回归失败 | 拒绝全局发布或严格限制发布范围 |
| EVAL-22 | 诊断器修改后自身判断变差 | 独立诊断评测能够识别退化 |
| EVAL-23 | 验收标准存在错误 | 通过独立基准治理流程修订 |
| EVAL-24 | 候选版本只在已知案例上提升 | 使用隐藏保留集检验泛化能力 |
| EVAL-25 | 个人设备离线执行 | 能在本地可用条件下完成适用评测，并记录环境限制 |
| EVAL-26 | 外部服务结果不稳定 | 识别外部波动，不将其直接归因于候选策略 |
| EVAL-27 | 回滚后需要再次评测 | 能够使用对应版本和基准证据复核 |
| EVAL-28 | 后台进化生成新候选 | 不得绕过评测与正式发布门禁 |

所有验收用例都必须有真实执行证据。本文件定义设计与验收要求，不代表功能已经实现。

## 十六、完成判定

- 评测体系覆盖从工具契约到端到端任务的主要层级；
- 真实任务基准能够覆盖核心专家与关键失败场景；
- 评测集具有明确的版本、来源和使用边界；
- 候选版本能够与稳定版本进行公平对照；
- 质量、约束、安全、成本和效率分别评估；
- 关键安全失败不会被总体平均分掩盖；
- 评测器具有独立验证机制；
- 共享内核与跨专家回归能够发现重要退化；
- 发布门禁与变更风险相匹配；
- 发布后的真实运行结果能够反馈到评测体系；
- 评测数据、指标和阈值的变更均可追溯；
- 评测结果能够关联实际运行版本与正式发布清单；
- 所有关键验收场景均有真实执行证据。

**最终目标：EvoAgent 每一次进化，都必须能够说明改了什么、为什么改、在哪些任务上改善、在哪些任务上退化、证据是否可靠，以及为什么允许进入稳定版本。真正的无限进化不是无限修改，而是能够持续发现问题、验证改进，并且不轻易丢失已经获得的能力。**</WritingBlock>

下一项重点包括：

1. 如何关联真实任务、执行版本、专家、工具和最终交付；
2. 如何识别成功率下降、异常增加、成本飙升和长期任务停滞；
3. 如何区分用户需求变化、环境波动、外部服务故障和能力退化；
4. 如何利用用户纠正、返工和反馈发现隐性质量问题；
5. 如何在不上传不必要敏感内容的情况下开展故障分析；
6. 如何处理 Android 离线日志、重连增量同步和重复事件；
7. 如何避免少量异常触发过度优化；
8. 如何将线上问题转化为 #95 的诊断案例和 #96 的回归测试；
9. 如何在发现重大问题时暂停候选版本、切换稳定版本或回滚；
10. 如何形成真正闭环的进化证据链。

这一步将把“发布前验证”与“发布后真实表现”连接起来，避免 EvoAgent 在测试环境中不断变好，却在用户实际使用中不知不觉退化。

完善了 EvoAgent 端到端评测与发布门禁体系
