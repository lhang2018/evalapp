# EvoAgent Android：全量设备边界与后续扩展路线

我的建议是：**以 Android 手机作为第一核心终端，把 EvoAgent 做成一个真正能理解意图、调用手机能力、完成复杂任务、验证执行结果，并从运行问题中持续改进的个人智能体。**

手机优先不意味着只能做手机操作。AI 漫剧制作、复杂工作流、编程辅助、资料研究等仍然属于 EvoAgent 的目标能力，只是优先通过手机完成交互和任务管理，再根据任务需要调用云端模型、外部生成服务或其他执行环境。

这里要先区分三件事：

- **设备边界**：EvoAgent 可以安装在哪里、控制什么、依赖什么。
- **能力边界**：哪些事情能在手机本地完成，哪些必须依赖云端或外部服务。
- **进化边界**：哪些改进可以下发到手机，哪些必须通过 Android 软件更新交付。

这三条边界必须一起确定，否则后续容易出现手机端、云端和进化系统互相耦合、反复重构的问题。

## 二、Android 手机内部，EvoAgent 到底由哪些部分组成？

建议将手机端划分为 7 个子系统。它们属于同一个 Android App 的内部模块，不是 7 个独立 App。




      **1. 交互与意图入口**
      语音、文字、任务历史、快捷入口、任务确认、执行进度。
      负责理解用户目标，不直接承担所有任务规划。






      **2. 本地运行时与路由**
      任务状态机、意图初判、ReAct 执行、本地能力选择、取消和恢复。
      决定当前任务在本地执行、交给云端，还是调用固定工作流。






      **3. Android 设备执行器**
      应用启动、系统 Intent、受授权的无障碍操作、界面识别、通知和系统能力适配。
      负责真正操作手机，并验证操作后的实际状态。






      **4. 本地记忆与上下文**
      用户偏好、任务历史索引、本地检查点、上下文缓存和离线记忆。
      与云端记忆协同，但不能把所有私人数据默认上传。






      **5. 本地日志与可靠同步**
      Room/SQLite、事件队列、版本清单、离线诊断包、断点续传。
      断网时仍然记录，重连后补传，必要时允许用户手动导出。






      **6. 能力包与版本管理**
      领域能力、工作流、模型适配配置、签名校验、激活、兼容性检查和回滚。
      使优化成果能有选择地更新，不必每次都重新安装 App。






      **7. 权限、安全与资源治理**
      权限状态、风险分级、预算、超时、速率限制、敏感操作确认和隐私控制。
      拥有独立于大模型的硬性约束，不能让模型自行解除。



## 三、手机究竟能做什么，不能做什么？

这是设备边界最重要的部分。

| 能力类别 | 手机本地可承担的工作 | 限制与依赖 |
|---|---|---|
| 应用操作 | 启动应用、调用公开 Intent、操作受授权界面 | 应用自身限制、系统版本、权限和界面变化 |
| 视觉理解 | 识别授权获取的屏幕截图、界面元素和状态 | 受截图权限、隐私内容及识别准确率限制 |
| 语音交互 | 录音、语音输入、播放反馈 | 语音识别和合成可能需要云端服务 |
| 通用任务 | 简单规则判断、任务状态管理、轻量处理 | 复杂推理通常使用云端模型 |
| 长流程任务 | 本地保存 DAG 状态、检查点、执行结果 | 生成、研究和远程工具可能依赖网络 |
| AI 漫剧制作 | 素材管理、任务编排、部分本地处理与 FFmpeg 合成 | 视频生成、配音等可能依赖外部服务；手机算力和存储有限 |
| 记忆功能 | 本地存储、检索、离线读取 | 跨设备共享和云端治理需要同步机制 |
| 自我改进 | 记录问题、分类失败、运行本地诊断 | 生产能力更新必须通过受控验证和发布流程 |

### 必须明确的权限边界

EvoAgent 不能承诺在 Android 上无条件控制所有应用。以下情况必须有明确的限制或备用路径：

- 锁屏、系统安全界面、受保护内容和其他禁止自动化的区域。
- 银行、支付、密码、授权确认等高风险操作。
- 需要特殊授权的截图、麦克风、无障碍和后台运行功能。
- 目标应用升级后，原有界面定位和操作流程失效。
- 系统杀死进程、设备重启、网络中断或外部 API 不可用。

对于高风险操作，必须根据风险要求用户确认或停止执行；不能仅凭模型判断就越权操作。

## 四、网络断开时，哪些功能必须继续可用？

手机优先战略要求 App 在没有服务器的情况下仍然有价值，但不代表离线时所有智能能力都能保持不变。




      **必须尽量保持本地可用**
      已批准的基础操作、本地任务记录、历史记录查看、日志采集、诊断包导出、离线检查点和现有能力包。






      **网络恢复后继续**
      云端模型调用、复杂任务规划、跨设备记忆同步、运行日志补传、能力包更新和进化结果接收。






      **不能假装离线也能完成**
      必须调用不可用的云端模型、远程视频生成服务或在线业务接口的任务，应暂停、等待或使用明确获准的替代方案。



## 五、后续扩展路径

手机优先不应导致架构封闭。我建议按下面的顺序扩展，而不是一开始就同时实现多个终端。


    **阶段 A：Android 核心能力完整化**

    建立本地运行时、ReAct 循环、工具注册、记忆、上下文治理、权限控制、任务验证、日志与离线同步。重点是把单个任务可靠地完成，而不是追求大量功能入口。


    **阶段 B：Android 复杂工作流**

    增加 DAG 编排、长任务状态管理、失败恢复、素材资产管理、成本控制和外部服务适配。以 AI 漫剧等任务验证复杂能力，但将具体制作流程作为独立能力包。


    **阶段 C：进化闭环**

    打通运行问题采集、根因分析、候选生成、独立评测、发布门禁、能力包分发和线上验证。允许经过授权的低风险改进自动发布。


    **阶段 D：跨设备能力复用**

    在 Android 核心稳定后，再把任务协议、能力契约、领域专家、工作流定义和版本体系抽象为可复用组件。


    **阶段 E：Windows 与其他终端适配**

    新终端分别实现设备执行器、权限模型、本地存储和界面。共享上层能力定义，不直接复用 Android 专属工具代码。


这里的阶段表示推荐实施顺序，不意味着必须等上一阶段所有功能全部完成才开始下一阶段。接口契约和数据模型应当从总体架构阶段就考虑跨终端兼容。

## 六、哪些能力可以共享，哪些必须隔离？

| 架构资产 | 未来能否共享 | 设计要求 |
|---|---|---|
| 意图分类与领域路由规则 | 可以 | 需要适配不同终端的能力清单 |
| ReAct、Planning 策略 | 可以 | 设备执行结果必须通过统一工具契约反馈 |
| 通用提示词与领域专家配置 | 可以 | 按模型、能力、版本及适用范围管理 |
| 记忆与上下文策略 | 可以 | 统一语义，区分本地数据与云端数据 |
| 工作流 DAG 定义 | 有条件共享 | 节点必须声明平台依赖、工具契约与权限 |
| Android 无障碍执行器 | 不直接共享 | 只能在符合条件的 Android 环境运行 |
| Windows 文件系统与桌面操作器 | 不直接共享 | 由 Windows 专属适配器实现 |
| 进化评测与发布机制 | 可以共享 | 每个终端仍须进行平台专属兼容性测试 |

这也能避免我们之前讨论过的问题：某个领域的一次失败，不应直接导致通用内核或其他领域专家被修改。所有改进都必须声明适用范围，并使用对应的评测集验证。

## 七、需要冻结的 Android 设备边界

我建议把以下约束写入正式的总体架构：

1. **第一正式终端是 Android 手机。** 不以 Windows、平板或可穿戴设备作为运行依赖。
2. **客户端与云端职责分离。** 本地执行、日志和离线能力不能依赖进化服务持续在线。
3. **系统权限与应用权限独立管理。** 无障碍、截图、麦克风和高风险操作都有单独授权及状态检查。
4. **任务执行、任务恢复与日志同步分离。** 同步失败不等于任务失败；日志也不能直接驱动任务重放。
5. **所有可更新能力都有版本和兼容性声明。** 配置、工作流、工具契约与原生 App 代码采用不同的更新方式。
6. **进化不能绕过发布门禁。** 低风险自动发布必须有预先定义的授权范围、质量与成本阈值、回滚机制。
7. **后续终端只通过稳定接口接入。** 不能为了扩展新设备而让 Android 专属代码污染通用智能体内核。

还有一个实施前需要确认的参数：Android 最低支持版本、目标 Android 版本、设备厂商适配范围和 Google 服务依赖策略。这些会影响无障碍、后台任务、语音、通知和兼容性测试，但不改变上述总体架构。

**最终结论：EvoAgent 应当先把 Android 手机打造为完整、可靠、能离线工作的个人智能体终端；云端承担重推理、跨任务治理与受控进化；其他设备未来通过独立适配器加入，而不是重新造一套智能体。**
