# EvoAgent 第五十专项：跨专家知识共享、能力资产与技能进化

本轮进入 EvoAgent 多专家架构的下一个核心问题：**智能体如何把一次任务中学到的东西，变成未来可以安全复用、持续改进的能力？**

此前我们已经设计了：

- 多专家系统与统一 Router；
- Plan、ReAct 与 DAG 的协同执行；
- 全局记忆、专家私有记忆和上下文压缩；
- 工具运行时、任务恢复与资源调度；
- 配置与版本治理；
- 因果诊断、质量验收、目标价值评估；
- 人机协作、授权和人工接管。

现在需要把这些能力连接起来。

例如，编程专家通过 AST 语法树分析，成功完成了一次大型代码重构。EvoAgent 能否把这次成功经历沉淀下来，让后续代码任务直接复用，而不是每次从头探索？

AI 漫剧专家跑通了一套分镜、配音、视频合成和质量验收流程。能否把它固化成可靠的工作流，并在后续任务中根据素材、模型和预算自动调整？

更进一步，某个专家发现了一种通用的需求澄清方法，其他专家能否学习？如果这条经验后来被证明存在缺陷，系统又如何防止它继续传播？

建议将本专项定义为：

**Cross-Expert Knowledge & Capability Evolution，简称 CEKCE。**

它负责将分散在专家、任务、工具、工作流和历史执行记录中的知识与能力，转化为具有明确适用范围、验证证据、版本、依赖和生命周期的可复用资产。

本专项的核心不是让所有专家共享一切，而是建立一种受治理的能力流通机制：

**经验可以被发现，能力可以被复用，改进可以被传播，但每次晋升、共享和执行都必须有明确的依据与边界。**

# 一、第一性原理：记住经验，不等于拥有能力

首先必须区分五种容易混淆的东西。

<box border radius="xl" padding={3} gap={3}>

    ["5. 专家策略 Policy","决定何时调用某项能力、采用什么参数、何时切换方案以及何时停止的决策规则。"]

这五种对象需要不同的治理方式。

一条知识可以被记忆系统保存，但未必已经经过验证；一段成功的执行记录可以成为经验，但不意味着每次都能复现；一个技能可以独立复用，但不一定适合所有专家；一个工作流可以稳定运行，却仍然依赖特定模型或工具版本；一条专家策略可以指导决策，但不应因为某次任务成功就自动成为全局规则。

因此，CEKCE 不能把所有历史记录简单地变成“技能”，也不能把所有成功案例直接写入共享记忆。

**必须建立从原始经验到可复用能力的晋升流程。**

## 1.1 能力进化的完整链路

建议统一采用以下链路：

- SELCIA 负责受控发布和改进候选的晋级。
- CEKCE 负责管理能力资产本身，以及它们如何被发现、复用、组合和演进。

不能因为检索到一项技能，就默认它可以执行。

# 三、能力分类：不是所有可复用资产都应该使用同一种格式

建议先定义统一能力资产分类体系，再决定每种资产的存储格式、执行方式和晋升条件。

| 类型 | 主要内容 | 是否可直接执行 |
|---|---|---|
| `KnowledgeAsset` | 事实、概念、规则、领域知识 | 否，通常用于推理和检索 |
| `ExperienceAsset` | 成功案例、失败案例、经验总结 | 否，需结合当前场景判断 |
| `SkillAsset` | 可复用的步骤、操作策略、专业算法 | 取决于实现形式和权限 |
| `WorkflowAsset` | 由多个技能和工具组成的编排流程 | 经过验证后可执行 |
| `PolicyAsset` | 选择、调度、停止和参数调整规则 | 可影响决策，必须严格治理 |
| `EvaluatorAsset` | 测试、质量检查和验收逻辑 | 可以运行，但需要评测器权限与隔离 |
| `ToolAdapterAsset` | 工具封装、接口适配与错误处理 | 可以调用工具，必须满足 TERSO 约束 |
| `ModelAdapterAsset` | 模型适配、输入输出格式转换与调用策略 | 可以参与推理调用，受模型和资源策略约束 |

还可以增加一种重要的资产：

**`FailurePatternAsset`：失败模式资产。**

它记录某类问题的触发条件、典型证据、已验证根因、修复方案和不适用场景。这样，同类错误再次出现时，系统可以直接参考已有诊断经验，而不是每次从头分析。

## 3.1 资产类型必须决定治理方式

例如，知识条目通常需要来源、时效性和可信度；工具适配器需要接口契约、权限声明和执行测试；工作流需要 DAG 定义、节点依赖、恢复策略和端到端验收；策略资产则需要历史回放、对照实验和明确的生效范围。

不能对所有资产统一采用“成功率超过 90% 就晋级”的规则。

有些知识资产根本不适合用任务成功率衡量；有些安全相关策略，即使平均成功率很高，也可能因为一项关键安全测试失败而必须拒绝发布。

## 3.2 一个资产可以引用另一个资产，但不能隐式复制其全部权力

例如，一个漫剧工作流可以引用视频合成技能、配音技能和 FFmpeg 工具适配器。

工作流本身不能因此获得比这些组件更宽泛的权限。

同样，一个知识条目可以指导专家选择某项技能，却不能直接授权它读取文件、联网或执行外部操作。

**能力描述的是“能做什么”，授权描述的是“现在允许做什么”。这两者必须分开。**

# 四、能力共享范围：全局共享不等于所有专家共用一切

这是多专家系统中最容易造成隐性污染的地方。

假设编程专家形成了一条经验：“复杂任务最好拆分成小步骤。”这条经验可能适用于其他专家，但如果系统把它直接变成所有任务的强制策略，就可能导致简单任务被过度拆解，增加成本和延迟。

因此，建议建立四级能力作用域，以及一个临时隔离层。

这四级是能力作用域，不是可信度等级。一个专家私有能力可以非常成熟，一个全局共享能力也可能存在缺陷。

## 4.1 能力可以从私有逐级晋升，但不能自动跨级传播

建议默认晋升路线：

`任务临时 → 专家私有 → 领域共享 → 全局共享`

但这不是所有能力必须经历的固定路线。

某些工具适配器天生只适用于一个专家，永远不需要晋升；某些通用 Schema 校验能力则可以直接作为基础设施开发并进入全局共享，但仍需经过适当测试。

关键在于每次晋升都必须有明确的适用范围和验证依据。

## 4.2 全局共享应当优先共享稳定接口，而不是内部策略

跨专家协作时，最适合共享的通常是：

- 明确的输入输出契约；
- 可复用的工具接口；
- 经过验证的基础技能；
- 标准化的数据格式；
- 质量检查与证据协议；
- 可组合的工作流节点。

最不适合未经验证直接共享的通常是：

- 专家内部提示词；
- 对特定任务形成的临时判断；
- 尚未验证的策略参数；
- 带有特定用户偏好的经验；
- 依赖私有上下文的结论。

这使系统能够共享真正可迁移的能力，而不是把所有专家变成同一个行为模式。

# 五、知识与记忆的边界：CEKCE 不取代 MEEG 和 CLEK

此前已经设计了全局记忆、专家记忆、任务记忆和上下文压缩。如果 CEKCE 再建立一套完全独立的记忆系统，就会造成重复存储、知识冲突和职责重叠。

建议明确以下边界。

| 系统 | 主要职责 |
|---|---|
| MEEG | 管理记忆生命周期、记忆作用域、更新、保留和冲突处理 |
| CLEK | 负责知识提取、关联、检索与知识组织 |
| ACMO | 负责当前任务的上下文构建、压缩与信息选择 |
| CEKCE / CIL | 管理经过治理的可复用能力资产，以及能力如何组合、发布和退役 |
| SOCDEA | 负责故障诊断、根因假设与因果验证 |
| UQEAG | 负责能力产物和执行结果的质量验收 |

例如，一次成功的代码重构记录可以先进入任务历史；CLEK 可以从中提取知识；MEEG 负责其记忆保留与作用域；CEKCE 则判断其中是否存在值得固化为技能的执行流程。

如果发现这次重构策略具有可复用价值，CEKCE 才创建技能候选。

**记忆负责保存经历，知识系统负责组织信息，能力系统负责将经过验证的信息转化为可复用的行动能力。**

这条边界可以避免所有记忆都变成技能，也避免技能仓库逐渐退化为一堆未经治理的聊天摘要。

# 六、能力资产模型：每项技能都必须有身份证和使用说明

建议建立统一的 `CapabilityManifest`，作为技能、工作流、工具适配器和评测器等能力资产的标准描述。

## 6.1 必需字段

| 字段 | 含义 |
|---|---|
| `capability_id` | 稳定的能力标识 |
| `capability_type` | 知识、技能、工作流、策略、评测器等 |
| `name` / `description` | 名称与能力描述 |
| `version` | 能力版本 |
| `owner_scope` | 所属全局、领域、专家或任务作用域 |
| `maintainer` | 维护者或责任模块 |
| `input_schema` | 输入契约 |
| `output_schema` | 输出契约 |
| `preconditions` | 执行前置条件 |
| `postconditions` | 执行后保证或检查条件 |
| `dependencies` | 依赖的工具、模型、其他能力和数据格式 |
| `permissions_required` | 所需权限声明 |
| `resource_profile` | 预期时间、内存、计算和费用需求 |
| `failure_modes` | 已知失败模式与处理策略 |
| `quality_evidence` | 关联的评测与验证证据 |
| `compatibility_range` | 适用的契约、环境和依赖版本 |
| `lifecycle_status` | 候选、试验、正式、冻结、退役等状态 |
| `content_digest` | 内容完整性摘要，用于识别实际资产版本 |
| `provenance` | 来源、创建过程、变更历史与证据引用 |

实际资产可以根据类型使用不同的扩展字段，但这些公共字段应该尽可能统一。

## 6.2 能力描述必须包含不适用场景

不能只写：

“这个技能可以自动重构 Python 代码。”

还应说明：

- 支持哪些 Python 版本；
- 是否依赖特定解析器；
- 支持哪些类型的 AST 变更；
- 是否保留注释、格式和类型信息；
- 对动态代码、反射和宏式生成的限制；
- 需要哪些测试；
- 在什么情况下必须回退到人工审查。

适用边界往往比能力宣传更重要，因为它决定了 Router 和专家能否正确选择能力。

## 6.3 必须区分接口版本与实现版本

例如，同一个 `CodeAnalysisSkill` 可以在不改变输入输出契约的情况下升级内部实现。

反过来，技能也可能保持同一套核心算法，却需要因为输入 Schema 发生不兼容变化而升级契约版本。

因此，建议分别管理：

- 能力实现版本；
- 输入输出契约版本；
- 依赖版本；
- 数据格式版本；
- 评测器版本。

这与 CGVCM 的版本治理保持一致，避免 CEKCE 自行发明一套互不兼容的版本体系。

# 七、能力发现与选择：怎样判断当前任务应该复用哪个技能？

即使拥有大量能力资产，如果系统不能准确发现和选择它们，资产库最终也会变成无人使用的仓库。

建议建立 `CapabilityDiscoveryEngine`，由专家在规划阶段提出能力需求，再从注册表中筛选适用候选。

## 7.1 能力检索采用多阶段流程

<box border radius="xl" padding={3} gap={2}>
  {#each [
    ["第一阶段：意图与能力需求识别","将当前任务转换为需要的能力类型、输入输出、约束和验收目标。"],

## 7.2 不能只根据语义相似度选择能力

假设用户要求“分析一个大型 Java 项目”。

语义检索可能找到一个名为“快速代码分析”的技能，但它实际只支持 Python。

如果系统只根据名称或描述相似度选择它，就会发生错误调用。

因此，候选排序必须建立在硬性适用条件过滤之后。

建议采用：

1. 先过滤不兼容、不授权或不满足前置条件的能力；
2. 再比较剩余能力的质量证据、适用范围和资源成本；
3. 对证据不足的候选采用保守策略；
4. 如果没有合格候选，允许系统组合基础能力，或者提出新的技能候选。

能力库不需要在每次任务中强行提供一个答案。

## 7.3 记录为什么选择某项能力

建议为关键能力调用生成 `CapabilitySelectionRecord`，记录：

- 当前任务需要什么能力；
- 哪些候选被考虑；
- 哪些候选因不兼容而被排除；
- 最终选择了什么；
- 选择依据是什么；
- 使用了哪个能力版本；
- 是否触发降级或替代方案。

这样，如果后续任务失败，SOCDEA 可以分析：究竟是能力本身存在缺陷，还是发现引擎选错了能力。

# 八、技能组合：从单个能力走向可组合的专业系统

真正有价值的能力资产不应只是独立技能的集合，而应该能够组成更复杂的任务流程。

例如，编程专家可以组合：

`需求解析 → AST 分析 → 变更规划 → AST 重写 → 格式化 → 静态检查 → 单元测试 → 回归验收`

漫剧专家可以组合：

`故事分析 → 角色设定 → 分镜生成 → 素材生成 → 配音 → 音画合成 → 质量检查 → 最终导出`

这些流程可以通过 DAG 组织，也可以在某些节点内使用 ReAct 或其他动态策略。

## 8.1 技能组合必须满足契约兼容

假设技能 A 输出的是原始文本，技能 B 需要的是结构化 JSON。

即使两项技能各自表现良好，也不能直接串联，除非存在经过验证的转换步骤。

因此，能力组合引擎需要检查：

- 输出与输入 Schema 是否兼容；
- 数据语义是否一致；
- 前置条件是否满足；
- 依赖版本是否兼容；
- 资源需求是否可以满足；
- 权限是否覆盖全部必要操作；
- 失败时是否有明确的恢复和补偿策略。

## 8.2 工作流必须声明节点级和端到端质量条件

一个工作流可以包含多个已经通过独立评测的技能，但它们组合后仍然可能失败。

例如：

- 单独的配音技能质量很好；
- 单独的视频合成技能也正常；
- 但合成时没有正确对齐配音时间轴。

因此，工作流需要自己的端到端验收集和恢复规则。

不能用所有子技能的单独成功率简单相乘或平均，就当作整个工作流的真实成功率；实际成功率还受到依赖关系、重试策略和节点交互的影响。

## 8.3 工作流成功后，应该沉淀什么？

不建议每次成功执行后都复制出一个全新工作流。

更合理的方式是：

- 保留稳定的工作流模板；
- 记录本次任务使用的参数和分支；
- 将新的有效改进提取为候选差异；
- 对候选差异进行回放和回归评测；
- 只有验证通过后，才更新正式模板或创建新版本。

这样既能复用成功经验，又能避免工作流库因细微差异不断膨胀。

# 九、能力晋升机制：从一次成功到正式可复用技能

这是 CEKCE 的核心治理闭环。

建议建立 `CapabilityPromotionPipeline`，将能力从原始候选逐步晋升为可复用资产。

## 9.1 能力生命周期

  {#each [

这些状态不是严格单向流水线。候选可以被拒绝，正式技能可以因安全缺陷直接冻结，已退役技能也可以在新环境下重新开发为新的能力版本。

## 9.2 晋升必须依据能力类型确定门槛

例如，工具适配器的晋升门槛可能包括：

- 接口契约测试；
- 错误处理；
- 超时与取消行为；
- 权限隔离；
- 资源限制；
- 失败恢复；
- 与当前执行环境的兼容性。

而一个通用知识条目的晋升门槛可能包括：

- 来源可靠性；
- 事实核验；
- 适用范围；
- 时效性；
- 与已有知识的冲突处理。

一个复杂工作流则需要端到端任务评测、节点失败注入、预算控制和恢复测试。

## 9.3 成功次数不能成为唯一晋升依据

某项技能可能连续成功十次，但这十次都来自非常相似的任务。

这只能证明它在有限场景中有良好表现，不能证明它适用于所有任务。

因此，晋升评测应考虑：

- 任务样本的多样性；
- 已知适用范围；
- 边界与异常场景；
- 与基线方案的比较；
- 失败案例与恢复表现；
- 关键保护指标；
- 评测证据的可信度。

对于高风险能力，还应要求独立评审或更严格的验证。

## 9.4 晋升范围必须与证据范围一致

如果一项技能只在某个专家、某种模型或某个操作系统上经过验证，就只能在对应范围内获得正式资格。

要把它晋升为领域共享或全局共享能力，需要额外的跨场景验证。

**不能让共享范围比验证证据覆盖的范围更大。**

# 十、能力冲突、重复与过期：如何避免技能库越长越乱？

随着 EvoAgent 长期运行，能力库会不断增长。如果缺少治理，最终可能出现大量相似技能、相互矛盾的知识和已经无法执行的旧工作流。

建议建立 `CapabilityLifecycleManager`，负责能力去重、冲突检测、依赖分析和退役管理。

## 10.1 先区分三类重复

| 类型 | 例子 | 处理策略 |
|---|---|---|
| 真正重复 | 两个技能实现完全相同的功能，输入输出也相同 | 比较质量、依赖和维护成本，考虑合并 |
| 互补能力 | 两个技能解决同类问题，但各自擅长不同场景 | 保留独立能力，由发现引擎选择 |
| 表面相似 | 两个技能名称相近，但行为、权限或前置条件不同 | 保留独立身份，明确区别与适用范围 |

不能仅凭名称、描述相似度或代码相似度就自动合并技能。

## 10.2 知识冲突必须保留来源与适用条件

例如，某条旧知识认为某个模型不支持特定功能，而新版本的模型已经支持。

系统不应该简单地删除旧记录，而应判断：

- 旧结论是否在当时成立；
- 新结论适用于哪个模型版本；
- 两条知识是否实际描述了不同条件；
- 旧技能是否仍被历史任务依赖；
- 是否需要更新适用范围或建立新版本。

很多所谓的知识冲突，实际上是条件或时间范围没有被正确表达。

## 10.3 过期能力必须能够自动失效

以下情况都可能导致能力失效：

- 工具 API 已经变化；
- 模型版本不再支持某种调用方式；
- 外部依赖被删除；
- 证书或授权已失效；
- 数据格式升级导致输入不兼容；
- 历史评测发现严重缺陷；
- 目标操作系统或硬件环境发生变化。

建议建立能力健康检查机制，定期验证关键依赖与契约。

如果能力已知不安全，应立即冻结相关版本，而不是等待下一次常规升级。

对于只是缺乏近期使用证据的能力，可以降低推荐优先级或安排重新验证，不应直接认定它已经失效。

## 10.4 退役不等于删除历史记录

退役的能力仍可能被旧任务、历史检查点和审计记录引用。

因此，系统需要保留必要的：

- 能力标识；
- 版本信息；
- 依赖摘要；
- 历史评测结果；
- 退役原因；
- 替代能力；
- 兼容性说明。

历史任务可以保留只读记录，但不能在当前环境不兼容或存在安全缺陷时，继续执行旧能力。

# 十一、跨专家传播：如何共享能力而不污染其他专家？

现在考虑一个更复杂的场景。

编程专家发现了一种更有效的任务分解方式，并在自己的评测集上取得明显改善。

系统是否应该立即把这个策略复制给漫剧专家、旅游专家和通用对话专家？

答案是：不应该。

首先，必须判断这个策略究竟属于哪一类能力：

- 通用的任务分解原则；
- 适用于代码工程的特定方法；
- 依赖某个模型的提示词技巧；
- 针对特定用户偏好的个性化策略；
- 仅在某类任务中偶然有效的经验。

不同类型的能力，传播范围完全不同。

## 11.1 建立受控传播流程

建议使用以下流程：

1. 发现候选能力；
2. 明确能力的来源和原始适用范围；
3. 判断是否存在跨专家复用价值；
4. 生成独立的候选版本；
5. 在目标专家的评测集上验证；
6. 检查是否影响原有能力和安全边界；
7. 通过独立评测后，才允许扩大共享范围；
8. 监测实际运行结果，必要时撤回传播。

传播能力不意味着复制整套专家配置。

例如，其他专家可以复用“先明确验收条件，再生成计划”的通用技能，但不必复制编程专家内部的全部提示词、模型参数和工具策略。

## 11.2 防止共享能力形成级联故障

如果一个有缺陷的全局技能被几十个专家依赖，它的影响范围可能远超原始问题。

因此，全局共享能力需要特别关注：

- 下游依赖数量；
- 影响范围；
- 兼容性变化；
- 回滚可行性；
- 是否存在替代能力；
- 是否可以分批发布。

对于关键共享能力，建议采用版本固定、受控灰度和明确的回滚机制。

如果发现问题，应能够冻结特定版本，并阻止新的任务继续选择它，而不是只能等待所有专家逐一修复。

## 11.3 能力传播不能传播用户的私人数据

某个用户的代码、对话、文件和任务记录，可能帮助专家发现有效方法。

但将其提炼为通用能力时，必须进行必要的数据最小化、脱敏与授权检查。

可以共享经过验证的通用算法或操作流程，不代表可以把原始项目文件、私人上下文或敏感数据直接复制到其他专家的知识空间。

# 十二、能力安全：技能库本身也是一个潜在的攻击面

这一点尤其重要。

如果 EvoAgent 允许系统从任务经验中自动生成可执行技能，那么技能资产就不只是知识数据，也可能包含程序、脚本、工具调用序列和外部依赖。

因此，技能库必须采用与工具运行时相衔接的安全治理。

## 12.1 能力资产必须具有可信来源

建议记录：

- 创建者或来源模块；
- 原始任务及其授权范围；
- 生成和修改过程；
- 审核与评测记录；
- 内容完整性摘要；
- 依赖来源；
- 当前维护者；
- 发布与撤销记录。

如果技能来自外部下载或第三方项目，还需要检查来源、许可证、完整性和依赖风险。

不能因为某项技能在语义上很适用，就直接运行其中的脚本。

## 12.2 将能力描述与可执行内容分开

能力的描述、元数据和实际可执行代码应分别管理。

这样，检索引擎可以读取技能的描述来判断是否适用，而不必执行技能本身。

只有在调用阶段通过契约、依赖、权限和资源检查后，执行器才可以运行相应内容。

对于代码类技能，建议优先在隔离环境中执行，并由 TERSO 控制文件访问、网络访问、进程创建和其他副作用。

## 12.3 技能不能自行扩大权限

例如，某个技能声明自己需要读取项目文件。

它可以申请相应权限，但不能在运行时自行修改权限声明，然后获得新的访问能力。

任何实质性权限扩展，都必须经过独立的授权与安全治理流程。

同样，技能更新不能通过修改自己的评测规则来降低晋升门槛，也不能自行批准自己的正式发布。

## 12.4 发现安全缺陷时，应支持快速冻结与撤销

如果一个正式技能被发现存在严重安全问题，系统应能够：

- 冻结该能力版本；
- 阻止新任务调用；
- 检查正在运行的实例；
- 根据风险决定暂停、终止或隔离；
- 保留审计证据；
- 评估依赖该技能的其他工作流；
- 选择安全替代版本；
- 在恢复前重新执行必要的验证。

这里需要区分冻结一个能力版本和删除全部相关历史数据。后者可能破坏审计和任务恢复能力，不应作为默认操作。

# 十三、能力与执行环境：同一个技能不一定能在所有设备运行

你的 EvoAgent 采用手机优先战略，后续可能在 Windows 电脑和微型 Linux 主机上扩展。

这意味着能力资产不仅需要判断“是否适用于任务”，还需要判断“当前设备能不能运行”。

例如：

- Android 上可以执行轻量文本分析，但不一定适合完整的本地视频合成；
- Windows 上可以运行某些桌面自动化工具，但 Linux 上可能没有相同的 GUI 环境；
- Linux 主机可能适合长期运行后台任务，但缺少某些专有应用；
- 同一套代码分析技能可能依赖不同平台的构建工具。

因此，建议在 `CapabilityManifest` 中增加设备与运行环境约束。

## 13.1 能力运行画像

每项能力至少应声明：

- 支持的操作系统与版本；
- CPU、内存和 GPU 等资源需求；
- 所需运行时和系统依赖；
- 是否需要网络；
- 是否需要图形界面；
- 是否需要外部模型或服务；
- 是否支持离线运行；
- 是否支持取消与检查点；
- 是否支持任务恢复；
- 是否能够跨设备执行；
- 资源不足时的降级方案。

这些信息应参与能力发现与调度，而不是等到执行失败后才发现设备不支持。

## 13.2 能力资产与执行实例分离

建议区分：

- **能力定义：** 描述技能的接口、逻辑、依赖和适用范围；
- **能力包：** 包含可部署的代码、配置、模型文件或必要资源；
- **能力实例：** 某台设备上已安装、配置并通过检查的具体运行实例。

例如，同一个 `VideoCompositionSkill` 可以有统一能力定义，但 Windows 和 Linux 使用不同的 FFmpeg 安装方式。

能力定义相同，不意味着部署包完全相同；部署包相同，也不意味着不同设备上的实例已经具备相同能力。

## 13.3 能力分发必须经过完整性和兼容性检查

跨设备分发时，建议执行：

1. 检查能力来源和内容完整性；
2. 验证设备与运行时兼容性；
3. 安装或解析依赖；
4. 检查权限和资源要求；
5. 执行必要的本地测试；
6. 注册本地能力实例；
7. 只有满足条件后才允许任务调用。

如果设备离线，系统可以使用本地已有的、经过验证的能力实例，但不能因为中心端发布了新版本，就默认远端实例已经升级。

# 十四、能力进化评测：怎样证明新技能比旧技能更好？

CEKCE 必须建立独立的能力评测机制，否则技能库很容易通过不断增加数量制造“进化”的假象。

建议建立 `CapabilityEvaluationSuite`，为每项重要能力维护专属评测集和质量指标。

## 14.1 评测至少覆盖五个方面

| 维度 | 核心问题 |
|---|---|
| 功能正确性 | 是否完成预期任务，是否满足输入输出契约？ |
| 适用范围 | 在哪些场景有效，在哪些场景会失败？ |
| 可靠性 | 异常、边界输入和依赖故障下表现如何？ |
| 效率 | 相比基线消耗多少时间、资源和费用？ |
| 安全与可恢复性 | 是否越权、产生未预期副作用，失败后能否安全恢复？ |

不同能力可以有不同的主指标，但必须保留适用的保护指标。

例如，AST 重构技能可以关注语义保持、测试通过率和代码变更范围；视频合成技能可以关注格式正确性、音画同步和合成时间。

## 14.2 比较必须使用适当的基线

候选技能可以与以下基线比较：

- 原有人工或程序化流程；
- 当前正式技能版本；
- 领域专家直接执行的方案；
- 不使用该技能的基础模型方案；
- 其他可替代技能。

这样可以判断技能究竟带来了增益，还是只是把原本就能完成的工作包装成一个新资产。

## 14.3 同时评测单项技能和组合工作流

一项技能单独表现优秀，不代表加入工作流后一定有收益。

因此建议同时维护：

- 技能级评测；
- 工作流级评测；
- 专家级回归评测；
- 跨专家共享后的目标领域评测。

如果某个技能在编程专家中提高了效率，却导致通用专家的回答变差，就不能因为它在原领域表现良好而直接全局共享。

## 14.4 评测失败也应成为能力资产

当技能失败时，系统应保留：

- 失败任务类别；
- 触发条件；
- 实际错误；
- 已尝试的恢复方法；
- 已确认和未确认的根因；
- 不适用场景；
- 是否需要冻结当前版本。

这些信息可以形成 `FailurePatternAsset`，帮助后续任务更早识别风险。

但未经验证的失败解释仍然是候选经验，不能直接升级为全局规则。

# 十五、与现有架构的协作边界

CEKCE 的职责是管理可复用能力资产，不应该重复建设其他专项已经承担的系统能力。

| 模块 | 职责边界 |
|---|---|
| Router | 选择专家与任务处理路径 |
| Planner / DAG | 规划任务和组织技能执行顺序 |
| MEEG / CLEK | 管理记忆与知识组织 |
| ACMO | 组织当前任务的上下文 |
| TERSO | 执行工具调用与副作用控制 |
| MTSRIC / ARCBG | 调度资源与执行预算限制 |
| CGVCM | 管理配置、版本、契约与兼容性 |
| SOCDEA | 诊断失败并验证根因 |
| UQEAG | 验收技能产物和最终结果 |
| GVAAG | 判断目标是否值得做，以及何时继续或停止 |
| HACCG | 管理用户授权、确认、接管与交互 |
| SELCIA | 管理候选改进的评测、发布、灰度和回滚 |
| CEKCE / CIL | 管理能力资产的注册、发现、组合、传播和生命周期 |

例如，一项代码分析技能失败时：

1. TERSO 记录实际执行情况；
2. SOCDEA 分析失败原因；
3. UQEAG 判断产物是否合格；
4. CEKCE 将可复用的修复方法整理为能力候选；
5. SELCIA 管理候选技能的验证与发布；
6. CGVCM 确保相关契约和依赖版本兼容。

这样，每个模块都承担清晰的职责，不会形成多个互相覆盖的“自进化控制器”。

# 十七、从架构落地角度，第一版应该先实现什么？

CEKCE 的设计范围很大，但第一版不应该一开始就实现自动技能发现、跨专家传播和自主合并。

对于你的个人部署方向，更合理的是先建立最小但完整的能力资产闭环。

    ["V0.2 · 执行记录转能力候选","从成功和失败任务中提取候选技能，但不自动发布。"],

这里的 V0.1～V1.0 是建议的实施里程碑，不是要求一次性开发完毕的版本承诺。

第一版最重要的验收标准不是“技能库里有多少技能”，而是：

1. 能够注册一项能力并明确它适用于什么场景；
2. 能够在任务中准确找到并调用它；
3. 能够记录该能力的实际版本、输入、输出和结果；
4. 能够判断复用是否成功；
5. 能够发现缺陷并阻止不合格版本继续传播；
6. 能够升级或回滚，而不破坏历史任务。

只要这条闭环跑通，后续的自动提取、自动组合和跨专家共享才有可靠的基础。

# 十八、下一专项：多专家协作、动态组队与跨专家任务交接

CEKCE 解决了能力如何沉淀和共享，但它还没有完全解决一个更复杂的问题：

**当一个任务同时需要多个专家时，EvoAgent 应该怎样组织它们协同工作？**

例如，制作一部 AI 漫剧可能同时需要：

- 通用专家理解用户目标；
- 编剧专家生成故事；
- 分镜专家规划镜头；
- 视觉专家生成素材；
- 配音专家处理声音；
- 视频工程专家完成合成；
- 质量专家检查最终产物。

这里的关键不再是单个专家如何完成任务，而是：

- 哪些工作适合交给多个专家并行执行？
- 哪些工作必须严格按顺序进行？
- 什么时候应该让一个专家把任务交给另一个专家？
- 如果两个专家给出互相冲突的结果，谁负责协调？
- 是否需要一个临时的协调专家？
- 如何防止多个专家重复劳动、互相覆盖或无限讨论？
- 如何在任务中途动态增加、移除或替换专家？
- 如何在某个专家失败时恢复整个协作流程？
- 如何控制跨专家通信成本、共享上下文和资源预算？
- 如何评价整个专家团队的表现，而不是只评价单个专家？

建议将下一专项定义为：

**Multi-Expert Orchestration & Dynamic Teaming，简称 MEODT。**

它将研究专家协作协议、动态组队、任务交接、共享上下文、冲突解决、并行执行、团队级验收与失败恢复。

本专项的核心原则是：

**多个专家的价值不在于数量，而在于能否形成有明确分工、共享必要信息、能够协调冲突、可以恢复并且整体可验收的协作系统。**

这将把 EvoAgent 从“多个专家可以独立工作”，进一步推进到“多个专家能够组成一个可治理、可动态调整的协作团队”。
