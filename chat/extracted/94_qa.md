# EvoAgent 第四十二专项：多任务调度、资源隔离与协同执行

本轮研究 EvoAgent 从“可靠地执行单个长期任务”走向“同时管理多个任务，并且让它们安全、高效地协同运行”。

结合此前确定的个人使用方向，EvoAgent 需要适配 Android 手机、Windows 个人电脑和微型 Linux 主机，也需要支持可选的云端模型与生成服务。不同设备的计算能力、后台运行限制、存储空间和网络条件差异很大，因此不能假设所有任务都能同时执行。

本专项建议定义为：

**Multi-Task Scheduling, Resource Isolation & Coordination，简称 MTSRIC。**

它负责任务排队、优先级调度、资源配额、并发控制、任务隔离、冲突检测、设备分配和资源不足时的协调处理。

核心目标不是最大化并发数量，而是：

**在有限资源和复杂依赖下，让正确的任务在正确的设备上，以可控的成本安全执行。**

## 一、第一性原理：任务并发不是越多越好

假设个人电脑同时运行：

- 大型代码项目的构建与测试；
- AI 漫剧的本地视频合成；
- 一个本地语言模型；
- 后台记忆整理；
- 多个等待远程生成服务的任务。

如果调度器只追求并发，可能导致内存不足、GPU 争抢、磁盘 I/O 堵塞，甚至让所有任务都变慢。

因此，需要同时优化四个目标：

1. **正确性：** 不破坏任务依赖、文件完整性、权限和验收要求。
2. **稳定性：** 避免资源过载、重复执行、死锁和任务相互干扰。
3. **效率：** 尽可能利用可用资源，减少无效等待。
4. **公平性与响应性：** 避免后台任务长期霸占资源，也避免低优先级任务永远无法执行。

这四个目标有时会互相冲突。例如，提高并行度可能缩短单个任务的等待时间，却增加系统内存压力。

所以，调度器不能只依据一个简单的优先级数字做决定。

# 二、总体架构：建立独立的多任务调度控制层

建议在已有 LTAR 任务生命周期管理之上增加 MTSRIC，而不是把资源调度直接塞进每个专家或 DAG 节点。


    <title size="md">任务入口与任务注册表</title>
    接收用户任务、后台任务、恢复任务和周期性任务，建立统一的任务身份与状态。





    <title size="md">MTSRIC 多任务调度器</title>
    负责优先级、资源预算、并发许可、任务依赖、资源预留、抢占和公平性。


    <grid-item>

        <title size="sm">资源管理器</title>
        CPU、GPU、内存、磁盘、网络和服务配额。

    </grid-item>
    <grid-item>

        <title size="sm">隔离与冲突管理器</title>
        工作目录、文件锁、产物依赖、数据库和外部副作用。

    </grid-item>





    <title size="md">设备与执行适配层</title>
    向 Android、Windows、Linux 主机及已授权的云端服务派发符合能力和权限要求的任务。





    <title size="md">LTAR 状态持久化与恢复</title>
    记录执行事件、检查点、资源消耗、任务迁移状态和异常恢复信息。


各模块的边界如下：

- **LTAR：** 决定任务处于什么生命周期状态，以及如何恢复。
- **MTSRIC：** 决定哪些任务可以在什么资源条件下执行。
- **ARCBG：** 决定单个任务或节点应投入多少推理和计算资源。
- **DAG 执行器：** 管理任务内部的依赖与节点执行顺序。
- **工具运行时：** 真正执行命令、代码、文件操作和外部调用。
- **SBAAG：** 管理权限、授权与危险操作的执行边界。

MTSRIC 可以阻止任务获得超出配额的执行资源，但不能代替工具运行时的安全隔离，也不能自行授予任务原本没有的权限。

# 三、统一任务调度：所有任务都进入同一套队列吗？

建议建立**统一任务注册表、多个逻辑队列、一个统一调度器**。

不建议让每种专家各自维护完全独立的调度系统，否则会发生资源冲突。例如，代码专家和视频专家可能都认为自己可以占用全部 GPU 内存。

## 3.1 建立五类逻辑队列

| 队列 | 典型任务 | 调度原则 |
|---|---|---|
| 交互任务 | 用户正在等待的简单问题或操作 | 优先保证响应延迟 |
| 前台执行任务 | 用户当前发起的代码、研究、创作任务 | 根据承诺时限和任务重要性调度 |
| 后台持续任务 | 记忆整理、索引更新、质量分析 | 利用剩余资源，避免干扰前台 |
| 恢复与维护任务 | 恢复核验、检查点修复、数据一致性检查 | 根据风险与恢复必要性确定优先级 |
| 等待与重试任务 | 等待网络、设备、模型或外部服务恢复 | 满足恢复条件后重新进入可调度状态 |

这些是逻辑队列，不意味着需要五套物理队列或五个独立服务。

统一调度器必须能够看到所有队列的资源需求，才能防止一个队列独占系统资源。

## 3.2 任务优先级不能只由创建时间决定

建议综合以下因素：

- 用户当前是否正在等待结果；
- 是否有明确的时间要求；
- 任务是否阻塞其他重要任务；
- 当前任务的风险与恢复紧迫性；
- 是否已经等待很长时间；
- 是否存在可用资源；
- 任务是否适合当前设备；
- 是否需要用户批准才能继续。

例如，一个正在执行的高成本视频生成任务，不应仅因为后台出现了一个新任务就被反复中断；但如果系统检测到内存不足，且用户发起了一个需要立即响应的简单请求，就应该优先保障交互响应。

建议采用**优先级等级 + 等待时间补偿 + 资源可行性检查**的组合策略。

等待时间补偿能够避免低优先级任务无限期饥饿，但不能让不满足权限或资源要求的任务绕过限制。

# 四、任务并发与资源治理：不仅要知道任务有多少，还要知道它们会消耗什么

一个系统同时运行三个任务，不一定比运行两个任务更重。三个轻量文本任务可能很便宜，而两个本地大模型和视频合成任务就可能耗尽内存。

因此，每个任务和执行节点都需要声明或估算资源需求。

## 4.1 建立资源需求描述

建议定义 `ResourceRequest`：

| 字段 | 示例 |
|---|---|
| `cpu_class` | 轻量、普通、重计算 |
| `memory_estimate` | 预计内存需求 |
| `gpu_requirements` | 是否需要 GPU、显存需求 |
| `disk_requirements` | 工作空间、临时文件与产物空间 |
| `network_requirements` | 是否需要联网、预期传输量 |
| `service_quota` | 模型或外部 API 并发配额 |
| `duration_estimate` | 预计执行时间 |
| `interruptibility` | 是否可暂停、可安全终止 |
| `resource_exclusivity` | 是否需要独占某个设备或资源 |
| `data_locality` | 必须访问哪些本地文件或数据 |

这些数据可以来自工具注册表、历史执行统计、模型配置和运行时监测。

如果任务没有准确的资源估算，可以采用保守估算、限制并发和运行时监控，而不是假设资源消耗很小。

## 4.2 建立全局资源预算

调度器需要维护当前设备的可用资源，而不只是累计任务声明的需求。

例如，设备可用内存会受到操作系统、其他应用、本地模型、缓存和文件处理的共同影响。

因此建议：

1. 获取当前设备资源状态；
2. 预留操作系统与基础服务所需资源；
3. 统计已运行任务的实际资源占用；
4. 为新任务估算资源需求；
5. 判断启动任务后是否仍有安全余量；
6. 执行期间持续监测；
7. 接近压力阈值时限制新任务、降低并发或暂停可中断任务。

**资源估算用于准入，实际监测用于纠偏。** 二者缺一不可。

## 4.3 不同资源使用不同的调度方式

- CPU：可以在安全范围内共享，并通过并发限制避免过载。
- GPU：可能需要独占、显存配额或严格的并发限制，具体取决于模型和运行时。
- 内存：必须考虑不可回收的工作集，不能仅依靠平均使用率。
- 磁盘：需要管理工作空间、临时文件、缓存和产物增长。
- 网络：需要限制并发连接、带宽与重试风暴。
- 外部 API：需要遵守服务端的速率、并发和费用限制。

这些资源不能简单相加为一个统一的“资源分数”。调度器应对每一种资源分别进行准入检查。

# 五、任务隔离：避免不同任务互相污染

多任务调度的另一个关键问题，是任务之间不能意外共享可变状态。

例如，两个代码任务同时修改同一个仓库，一个任务可能覆盖另一个任务的修改；视频任务的清理逻辑也可能删除其他任务仍在使用的临时素材。

建议建立四级隔离机制。


    <title size="md">1. 任务工作空间隔离</title>
    每个任务拥有明确的工作目录、临时文件命名空间和产物清单。清理操作只能处理本任务获准管理的文件。



    <title size="md">2. 可变资源隔离</title>
    通过文件锁、版本检查、独立数据库事务和资源租约，管理共享仓库、数据库与模型服务。



    <title size="md">3. 状态与记忆隔离</title>
    每个任务拥有独立的执行状态和上下文快照。共享记忆必须经过明确的访问范围与写入规则。



    <title size="md">4. 执行环境隔离</title>
    根据风险和平台能力使用独立进程、容器、受限目录、权限配置或其他沙箱机制。


并不是每个任务都必须使用容器。个人设备上的简单只读任务，可以使用较轻量的隔离；涉及不可信代码、敏感文件或高风险副作用的任务，则需要更严格的运行环境。

## 5.1 同一个项目的多个任务如何协作？

建议对共享代码仓库引入版本化工作空间。

例如：

- 任务 A 在自己的工作区修改登录模块；
- 任务 B 在自己的工作区修改支付模块；
- 两个任务基于同一个基础提交；
- 最终集成时检查文件冲突、接口兼容性和测试结果。

如果两个任务修改同一个文件，就不能只因为它们属于不同专家而认为彼此独立。

系统需要检测实际写入集合、依赖关系和版本变化，必要时暂停集成、重新基于最新版本执行，或请求人工处理冲突。

## 5.2 共享记忆不等于共享执行状态

多个任务可以读取同一条经过验证的项目知识，但不应直接修改彼此的执行状态。

例如，代码任务 A 发现了一个新的构建命令，可以将证据提交给项目知识层。任务 B 可以在授权范围内使用这条知识，但不能因此自动继承 A 的临时变量、未完成补丁或未经验证的诊断结论。

这与此前设计的 MEEG、ACMO 和多专家隔离原则一致。

# 六、DAG 内部并行与任务之间并行：两种并发必须统一协调

EvoAgent 的 DAG 可以让一个任务内部的多个节点并行执行，但系统也可能同时运行多个独立任务。

这形成两个层次：

- **任务内部并行：** 一个 DAG 中互不依赖的节点同时执行；
- **任务之间并行：** 多个用户任务同时运行。

如果两层分别决定并发度，就容易超出设备资源上限。

例如，三个用户任务各自认为可以启动两个 GPU 节点，最终可能同时启动六个 GPU 工作负载。

因此，建议采用全局资源准入机制。

## 6.1 节点启动前必须满足三个条件

一个 DAG 节点只有同时满足以下条件才能启动：

1. 依赖节点已经达到规定状态；
2. 资源管理器已批准所需资源；
3. 任务权限、数据访问和副作用约束均满足。

节点的局部计划不能绕过全局调度器。

如果一个节点需要等待 GPU 资源，它应进入资源等待状态，而不是持续重试启动。

## 6.2 优先并行执行真正独立的节点

假设 AI 漫剧 DAG 包含：

- 角色素材生成；
- 场景素材生成；
- 背景音乐准备；
- 分镜数据整理。

其中一些节点可能相互独立，可以并行；另一些节点需要前置产物，必须串行。

DAG 执行器应根据依赖关系确定可并行节点，MTSRIC 再根据当前资源状况决定实际启动哪些节点。

这意味着“依赖允许并行”不等于“资源允许并行”。

## 6.3 避免死锁与资源占用僵局

需要防范一种情况：

任务 A 占有部分资源，等待任务 B 释放另一项资源；任务 B 同时占有另一部分资源，又等待任务 A 释放资源。

建议：

- 尽可能采用资源预留或统一准入；
- 对需要多项资源的节点，尽量在启动前整体批准；
- 为锁设置持有期限和失效处理机制；
- 对长时间等待建立诊断；
- 对可以安全暂停的任务支持释放部分资源；
- 对不能安全释放的资源，禁止采用会导致死锁的抢占策略。

不能简单地对所有资源使用一个锁解决问题，因为这会显著降低并行效率。

# 七、抢占与公平性：高优先级任务能否打断低优先级任务？

建议将任务划分为三种抢占等级。

| 等级 | 行为 | 典型场景 |
|---|---|---|
| 可抢占 | 可以在安全检查点暂停并释放资源 | 大批量分析、后台索引、可重建的计算任务 |
| 条件抢占 | 需要完成当前安全阶段后暂停 | 文件转换、长时间测试、视频合成 |
| 不可直接抢占 | 必须等待操作完成或进入专门的取消流程 | 不支持中断的外部操作、可能产生不可逆副作用的操作 |

“不可直接抢占”不意味着任务永远不能停止，而是不能在不了解执行状态的情况下强行中断。

## 7.1 避免前台任务永远压制后台任务

如果每次用户发起新任务，都让后台任务立即停止，长期维护任务可能永远无法完成。

建议使用以下机制：

- 高优先级任务可以获得更快的资源准入；
- 低优先级任务在等待期间逐步提高调度权重；
- 后台任务使用可配置的资源上限；
- 在资源空闲窗口执行低优先级任务；
- 为必要的恢复与维护工作保留最低资源；
- 对长期等待任务设置告警或重新评估条件。

这能够在响应速度和长期任务进展之间建立平衡。

## 7.2 采用受控的资源借用

例如，视频任务预留了部分 GPU 资源，但当前正在等待云端生成服务返回结果。

系统可以将尚未实际使用的资源分配给其他任务，但需要明确：

- 借用资源是否能够及时收回；
- 原任务恢复时是否需要重新加载模型；
- 借用是否会产生明显的恢复成本；
- 当前任务是否有不可中断的资源需求。

对于本地大模型，卸载和重新加载可能很昂贵；对于等待网络的任务，则可能更适合释放本地资源。

调度器应根据真实的资源释放与恢复成本作出判断。

# 八、跨设备调度：不是所有任务都应该迁移

你的 EvoAgent 可能同时使用 Android 手机、Windows 电脑、微型 Linux 主机和可选云端服务。

这时需要建立 `DeviceCapabilityRegistry`，记录每个执行设备的能力和限制。

建议记录：

- 操作系统与架构；
- 可用 CPU、内存和 GPU；
- 已安装的模型与工具；
- 可访问的项目文件和存储；
- 网络连通性；
- 后台运行能力；
- 当前负载；
- 设备是否在线；
- 数据敏感性与执行权限；
- 任务迁移所需的产物和依赖。

## 8.1 设备选择应考虑五类因素

1. **能力匹配：** 设备是否具备运行所需工具和模型的能力？
2. **数据位置：** 文件是否已经在该设备上？
3. **资源状态：** 当前是否有足够的可用资源？
4. **执行成本：** 迁移数据和恢复环境需要多少时间？
5. **权限与隐私：** 任务数据是否允许离开当前设备？

例如，手机可以负责任务入口和轻量分析，个人电脑负责大型代码构建，微型 Linux 主机负责长期调度，云端负责已授权的生成服务。

但如果代码包含不允许外传的敏感数据，就不能仅因为云端模型更强而自动上传。

## 8.2 任务迁移需要明确的状态交接

建议迁移流程为：

1. 源设备请求迁移；
2. 在安全边界内暂停可迁移节点；
3. 持久化检查点与必要产物；
4. 目标设备核验能力、权限和资源；
5. 传输或验证必要数据；
6. 目标设备确认可以接管；
7. 更新权威调度状态；
8. 源设备释放执行权；
9. 目标设备恢复任务。

不能仅把任务状态从设备 A 改成设备 B，就认为迁移已经成功。

对于不支持迁移的节点，应保留在原设备执行，或者使用明确的替代工作流重新执行。

# 九、资源过载与故障隔离：一个任务失败不能拖垮整个系统

多任务系统必须防止局部故障演变为全局故障。

例如，某个视频生成服务连续失败，任务不断重试，可能占满网络连接、耗尽 API 配额，并让其他任务无法正常执行。

建议建立四种保护机制。

## 9.1 并发上限

对以下对象分别设置并发限制：

- 全局运行任务；
- 单个设备上的任务；
- 单个 DAG 内的并行节点；
- 单个模型实例；
- 单个外部服务；
- 特定工具类型；
- 特定资源密集型操作。

这些限制应根据设备能力和服务契约配置，并支持动态调整。

## 9.2 重试预算与熔断

如果某个外部服务持续失败，应暂停继续向它提交请求，而不是无限重试。

建议建立：

- 单操作最大重试次数；
- 指数退避与随机抖动；
- 服务级失败率监测；
- 熔断状态；
- 半开状态下的受控探测；
- 服务恢复后的逐步放量。

熔断只影响相应的故障服务或能力，不应默认阻止其他无关任务继续执行。

## 9.3 背压机制

当任务生产速度超过执行能力时，系统应该限制新的工作进入执行队列。

例如，视频任务持续生成大量待合成镜头，但本地磁盘和编码器已经接近容量上限。此时可以暂停新的素材下载或生成节点，先完成已有素材的处理。

背压机制可以避免积压无限增长，也能降低系统内存、磁盘和网络压力。

## 9.4 故障隔离与恢复

当某个任务发生异常时：

- 记录其错误和资源消耗；
- 限制其继续申请资源；
- 保留必要的诊断材料；
- 根据 LTAR 恢复规则处理节点状态；
- 允许无关任务继续运行；
- 必要时触发服务级熔断；
- 在恢复后逐步重新开放资源。

系统不能因为一个专家反复失败，就无限增加该专家的调用次数。

# 十、调度器如何知道自己做得好不好？

MTSRIC 需要独立评测，否则容易出现“并发数提高了，但任务完成更慢、失败更多”的情况。

建议至少跟踪以下指标：

| 指标 | 目的 |
|---|---|
| 任务完成率 | 判断调度是否支持任务成功交付 |
| 平均与高分位等待时间 | 判断任务是否长期排队 |
| 资源利用率 | 判断 CPU、GPU、内存和磁盘是否得到合理利用 |
| 资源超限事件 | 判断准入与资源监测是否有效 |
| 任务饥饿率 | 判断低优先级任务是否长期得不到执行 |
| 任务冲突率 | 判断文件、产物和共享状态是否发生冲突 |
| 并发执行失败率 | 判断增加并发是否降低了稳定性 |
| 迁移成功率 | 判断跨设备调度是否可靠 |
| 恢复与重试成本 | 判断故障是否导致过度资源消耗 |
| 任务总成本 | 判断调度是否在质量要求内提高效率 |

还需要增加几类专门的压力测试：

- 多个任务同时请求 GPU；
- 后台任务长时间占用磁盘；
- 前台任务持续到达；
- 外部 API 限流；
- 同一代码仓库被多个任务修改；
- 设备在任务迁移过程中断网；
- 任务取消时仍有节点正在运行；
- 高优先级任务与低优先级任务竞争内存。

评测时必须同时观察正确性、稳定性和效率，而不能只看资源利用率或并发数量。

# 十二、下一专项：工具执行运行时、沙箱与操作安全

到目前为止，我们已经设计了任务规划、专家协作、上下文、预算、主动感知、长期恢复和多任务调度。

但这些模块最终都需要调用工具来改变现实状态。

例如：

- 代码专家需要读写文件、运行测试和执行构建；
- 漫剧专家需要调用生成服务、下载素材和执行 FFmpeg；
- 手机操作专家需要与 Android 系统交互；
- 记忆系统需要读写数据库；
- 恢复管理器需要检查和修复任务状态。

如果工具执行层不可靠，上层再聪明也可能导致文件损坏、重复扣费、权限越界或任务状态不一致。

因此，下一专项建议定义为：

**Tool Execution Runtime & Sandboxed Operations，简称 TERSO。**

重点研究：

1. 如何建立统一的工具注册、发现、版本和能力契约；
2. 如何区分只读工具、可逆操作和不可逆操作；
3. 如何在执行前验证参数、权限和前置条件；
4. 如何为不同风险等级的工具选择合适的沙箱；
5. 如何管理进程、超时、取消、退出码和异常输出；
6. 如何限制文件访问、网络访问、系统命令和外部副作用；
7. 如何处理执行超时但实际操作已经成功的情况；
8. 如何为工具执行建立审计日志与结果证据；
9. 如何将工具调用与 LTAR 检查点、MTSRIC 资源配额和 SBAAG 授权机制连接；
10. 如何防止不可信文件、网页或工具输出诱导模型越权执行；
11. 如何对工具进行契约测试、故障注入和兼容性验证；
12. 如何在 Android、Windows、Linux 和可选云端环境中建立统一接口，同时保留各平台的安全边界。

这个专项的核心原则是：

**模型负责提出行动意图，调度器负责决定何时执行，授权机制负责判断是否允许，工具运行时负责安全执行，验收机制负责确认结果。**

只有把这几种职责分开，EvoAgent 才能在高度自动化的同时，保持可控、可审计和可恢复。
