# EvoAgent 第四十五专项：配置治理、版本兼容与系统变更管理

本轮解决 EvoAgent 在持续进化过程中一个容易被忽略、却会影响整个系统可靠性的核心问题：

**当各个专家、模型、工具、记忆系统、执行引擎和安全策略分别升级时，如何保证它们能够继续正确协作，并且在升级失败时安全恢复？**

此前的设计已经明确：EvoAgent 采用多专家架构、统一任务入口、独立进化控制器，以及任务状态持久化、资源调度、工具执行和安全治理。

这意味着系统不再是一个只需更新单个提示词的简单程序，而是一组拥有独立状态、接口、配置和生命周期的协作组件。

例如，编程专家升级了工具调用格式，但旧版任务检查点仍保存着原来的参数结构。如果系统没有兼容性治理，恢复旧任务时就可能失败，甚至错误执行。

又例如，新版记忆压缩器改变了上下文引用格式，但旧版专家仍然期待原来的数据结构。每个模块单独测试可能都通过，组合起来却会产生隐性故障。

本专项建议定义为：

**Configuration Governance, Version Compatibility & Change Management，简称 CGVCM。**

它负责配置所有权、版本治理、接口契约、依赖兼容、配置发布、状态迁移、跨设备版本协调和系统级变更验收。

## 一、第一性原理：模块可以独立进化，但系统行为不能失去控制

先明确三个重要概念。


    <title size="md">模块独立性</title>
    每个专家、工具、策略和服务拥有明确的职责、接口与生命周期，可以独立开发和评测。



    <title size="md">系统兼容性</title>
    模块升级后，依赖它的其他组件仍然能够正确理解其输入、输出、状态与行为约束。



    <title size="md">系统可恢复性</title>
    如果变更失败，系统能够识别影响范围、停止危险的后续执行，并恢复到经过验证的兼容状态。


这三者需要同时成立。

如果为了兼容而禁止所有模块升级，系统无法进化；如果允许每个模块随意变化，系统会不断积累隐性耦合；如果只允许发布、不设计回滚，系统就可能在一次失败升级后失去可靠运行能力。

因此，建议采用以下基本原则：

1. 每个模块拥有明确的配置和接口所有权。
2. 影响其他模块的变更必须声明兼容性。
3. 历史任务、记忆和检查点必须有明确的版本处理方式。
4. 安全策略和权限边界不能被普通配置升级绕过。
5. 新版本必须先经过独立评测，再进入受控发布。
6. 回滚不仅要恢复代码，还要考虑配置、状态和产物的兼容性。

**EvoAgent 应允许局部快速进化，同时对跨模块影响实行统一治理。**

# 二、建立统一配置治理体系：哪些配置归谁管理？

配置问题最容易出现在多个模块都认为自己拥有某项规则的情况。

例如：

- Router 希望提高某个专家的调用概率；
- ARCBG 希望降低该专家的资源消耗；
- 安全治理希望限制该专家的工具权限；
- 用户希望该专家优先处理某类任务。

如果这些规则散落在不同提示词和配置文件中，就很难判断最终行为由谁决定。

建议建立统一的 `ConfigRegistry`，但不要求所有配置都存储在同一个物理文件或数据库中。

统一的是配置身份、所有权、版本、优先级和变更流程。

## 2.1 配置按职责分类

| 配置类别 | 示例 | 主要所有者 |
|---|---|---|
| 系统基础配置 | 存储路径、服务地址、运行模式 | 系统运行时 |
| 专家配置 | 领域说明、工具偏好、专家评测集引用 | 对应专家的维护模块 |
| 模型配置 | 模型标识、上下文限制、参数和适配规则 | 模型注册与适配层 |
| 工具配置 | 输入输出 Schema、权限要求、超时与重试策略 | 工具注册与执行层 |
| 任务策略配置 | 规划方式、节点约束、验收条件 | Planner 与任务模板 |
| 资源配置 | 并发上限、资源配额、预算策略 | MTSRIC 与 ARCBG |
| 记忆配置 | 保留策略、命名空间、检索与压缩规则 | MEEG、CLEK 与记忆运行时 |
| 安全配置 | 授权边界、禁止操作、沙箱策略 | ASGTB 与 SBAAG 治理层 |
| 进化配置 | 候选评测、发布门槛、回滚规则 | 独立进化控制器与发布治理 |

配置所有权意味着谁负责定义、验证和维护规则，不代表该模块可以修改其他模块的受保护配置。

例如，Router 可以提出更改路由阈值的候选，但不能自行修改安全策略；进化控制器可以提交工具重试策略的改进建议，但不能直接扩大工具权限。

## 2.2 区分四类配置来源

建议为每次运行明确以下配置来源：

- **系统默认值：** 系统提供的基础行为；
- **用户偏好：** 用户明确设定的工作方式；
- **任务配置：** 当前任务特有的目标、约束与验收标准；
- **受保护策略：** 安全、授权、数据访问和强制执行边界。

不能简单地使用“最后写入者获胜”。

例如，用户偏好可以选择回答风格，却不能取消高风险操作的必要授权；任务配置可以要求更高的质量标准，却不能突破全局资源上限；专家配置可以建议工具，但不能跳过工具执行检查。

因此，需要为不同配置类别建立明确的优先级和合并规则。受保护策略具有不可被普通配置覆盖的约束力。

# 三、版本治理：不能只有一个全局版本号

EvoAgent 由多个独立演进的组件构成。如果只记录一个 `EvoAgent Version`，就无法解释某次失败究竟来自哪个组件的变化。

建议建立分层版本体系。

## 3.1 五类版本

  {#each [
    ["产品版本","表示某次对外发布的系统整体版本，便于用户识别与恢复。"],
    ["模块版本","表示 Router、记忆系统、Planner、工具运行时等独立组件的实现版本。"],
    ["契约版本","表示组件之间的数据结构、输入输出和行为约定的版本。"],
    ["策略版本","表示路由、预算、压缩、调度、安全和进化规则的版本。"],
    ["数据格式版本","表示任务状态、检查点、记忆记录、事件和产物元数据的存储格式。"]
  ] as item}

      <title size="md">{item[0]}</title>
      {item[1]}

    {#if item[0]!=="数据格式版本"}

    {/if}
  {/each}

这五类版本可以独立变化，但必须建立明确的依赖关系。

例如，产品版本可以固定某个经过验证的组件组合；策略版本可以更新而不改变数据格式；数据格式可以升级，但需要明确旧数据的读取、迁移和回滚方案。

## 3.2 建立系统运行清单 `RuntimeManifest`

每次任务运行都应该能够追溯其实际使用的关键版本。

建议清单至少记录：

- 系统版本；
- 关键模块版本；
- 工具契约版本；
- 模型标识与适配器版本；
- 路由与资源策略版本；
- 上下文构建与压缩策略版本；
- 记忆 Schema 版本；
- 任务 DAG 版本；
- 安全策略版本；
- 运行设备与执行环境；
- 关键依赖的版本或摘要；
- 必要的配置快照引用。

不需要把每一个普通配置都复制进每次模型调用，但必须能够还原影响执行行为的关键配置。

对动态变化的运行环境，还应记录任务实际使用的版本，而不是只记录系统启动时的版本。

## 3.3 版本号必须表达兼容性意图

建议采用语义化版本思想区分：

- **补丁变更：** 修复缺陷，预期不改变公开契约；
- **次版本变更：** 增加兼容能力；
- **主版本变更：** 存在不兼容的契约或行为变化。

但版本号本身不是兼容性证明。

即使工具只发布了补丁版本，也可能因缺陷修复改变边界行为；即使主版本号相同，也可能存在配置错误或外部依赖变化。

所以，系统还需要依赖声明、契约测试和实际兼容性验证。

# 四、接口契约与依赖图：让模块升级前知道会影响谁

建议建立统一的 `ContractRegistry`，保存模块对外提供的接口，以及它依赖的接口。

例如：

- Router 依赖专家注册表；
- Planner 依赖任务类型和工具能力描述；
- DAG 执行器依赖任务状态与工具执行协议；
- ACMO 依赖记忆检索和上下文数据格式；
- LTAR 依赖检查点与产物引用协议；
- MTSRIC 依赖资源需求和设备能力协议；
- TERSO 依赖工具契约与授权接口；
- ASGTB 依赖身份、授权和策略评估接口。

这张依赖图不仅用于启动系统，还用于评估变更影响。

## 4.1 每个接口必须定义什么？

建议接口契约至少包含：

1. 输入 Schema；
2. 输出 Schema；
3. 必填字段与可选字段；
4. 错误类型及处理方式；
5. 状态转换规则；
6. 权限和副作用要求；
7. 超时、取消与重试语义；
8. 版本兼容范围；
9. 数据语义与不变量；
10. 契约测试集。

特别需要定义语义，而不只是字段类型。

例如，旧版工具返回 `success=true`，新版仍然返回相同字段，但语义从“执行命令成功”变成“最终产物已通过验收”，这会造成隐性兼容问题。

## 4.2 变更前执行影响分析

当某个模块准备升级时，系统应分析：

- 哪些模块直接依赖它；
- 哪些模块间接依赖它；
- 哪些任务模板使用旧契约；
- 哪些未完成任务会受影响；
- 哪些历史检查点需要迁移；
- 哪些安全策略可能发生变化；
- 哪些测试必须重新运行。

例如，记忆 Schema 升级不仅影响记忆存储，还可能影响检索、上下文压缩、专家交接和任务恢复。

因此，不能只测试记忆模块自身。

**局部模块测试验证自身正确性；依赖图与集成测试验证系统组合后的正确性。**

# 五、数据 Schema 演进：历史任务不能因为升级就失去恢复能力

EvoAgent 会积累长期任务、检查点、记忆记录、工具执行事件和产物元数据。这些数据可能比某个模块的代码存活更久。

因此，数据格式升级需要独立治理。

## 5.1 建立 Schema 迁移流程

建议使用以下流程：

  {#each [
    ["1. 声明目标 Schema","定义新字段、语义变化、删除字段和兼容要求。"],
    ["2. 扫描旧数据","统计受影响的任务、检查点、记忆和事件格式。"],
    ["3. 定义迁移规则","明确字段转换、默认值、无法转换的数据和失败处理。"],
    ["4. 试运行迁移","在副本或隔离环境中迁移并检查结果。"],
    ["5. 验证语义等价","确认关键状态、引用、权限和历史事实没有被错误改变。"],
    ["6. 受控切换","发布新格式读写逻辑，并记录迁移版本和进度。"],
    ["7. 保留恢复路径","在确认新版本稳定前，保留必要的备份与旧数据恢复方案。"]
  ] as item}


        {item[0].split(".")[0]}


        **{item[0].slice(item[0].indexOf(" ") + 1)}**
        {item[1]}


    {#if item[0]!=="7. 保留恢复路径"}

    {/if}
  {/each}

## 5.2 不要在升级时直接覆盖所有历史数据

对于个人设备部署，建议优先采用可验证、可分批、可恢复的迁移方案。

例如，可以先让新版本读取旧 Schema，再将一部分数据迁移到新格式，验证成功后逐步扩大迁移范围。

如果旧版本不能读取新格式，则不能在未验证恢复方案的情况下直接切换唯一的权威数据。

对不可逆的语义变化，应保留原始数据或可重建的转换记录，而不是只保留转换后的结果。

## 5.3 历史任务需要区分继续执行与只读查看

并不是每个历史任务都需要迁移到最新版本。

建议区分：

- **只读历史任务：** 可以通过兼容读取器查看；
- **可恢复任务：** 必须满足恢复协议与关键依赖兼容；
- **可迁移任务：** 允许转换状态与依赖，并经过验证；
- **不可安全迁移任务：** 保留旧环境、只读访问、重新规划或请求用户处理。

例如，旧版任务检查点使用的工具契约已不再兼容时，系统可以保留历史记录，但不能直接恢复并执行旧请求。

# 六、配置合并与策略冲突：最终采用哪个值？

多层配置系统最容易出现的问题，不是配置缺失，而是多个配置同时有效，却没有明确的冲突解决规则。

例如：

- 用户希望任务尽快完成；
- ARCBG 为任务设置了费用上限；
- MTSRIC 限制 GPU 并发；
- 专家希望使用更大的模型；
- 安全策略禁止将项目文件发送到云端。

这些配置并不完全冲突，但需要明确哪些可以协商，哪些不能被覆盖。

## 6.1 建立四类配置合并规则

| 配置类型 | 合并原则 |
|---|---|
| 用户偏好 | 在不违反强制约束时尽可能满足 |
| 任务约束 | 任务范围内生效，不能违反更高层的硬约束 |
| 资源策略 | 可以动态分配，但不得超过已批准的上限 |
| 安全与授权策略 | 必须满足；普通配置不能覆盖 |

例如，用户要求“尽可能快”，系统可以增加并发，但仍需满足内存限制、API 配额、文件冲突和安全要求。

如果在这些限制下无法达到预期速度，系统应该报告限制或提出替代方案，而不是默默放宽约束。

## 6.2 区分硬约束与软偏好

建议在配置 Schema 中明确标记：

- `HARD_CONSTRAINT`：违反即拒绝、阻塞或重新规划；
- `SOFT_PREFERENCE`：可以在说明原因的情况下调整；
- `DEFAULT`：没有更具体规则时采用；
- `EXPERIMENTAL`：仅允许在指定的试验范围内使用。

例如，数据不能离开本地设备可能是硬约束；优先使用某个模型可能只是软偏好；默认超时则是可配置默认值。

不能把所有配置都变成同等权重的评分，然后让模型选择一个“总体最优”方案。

## 6.3 每次决策都要能解释配置来源

对于重要决策，建议记录：

- 最终生效的配置；
- 配置来源与版本；
- 被覆盖或未采用的配置；
- 冲突原因；
- 是否触发降级；
- 是否需要用户确认。

这样，当用户发现 EvoAgent 突然换了模型、减少了并发或拒绝了某项操作时，系统可以解释实际采用的规则，而不是只返回一个无法追溯的结果。

# 七、发布治理：不是所有改动都需要相同级别的审批

EvoAgent 的进化频率可能很高。如果每个小改动都走完整的人工审批，系统会非常迟缓；但如果所有改动都自动发布，就可能导致跨模块故障。

建议按变更影响建立四个发布等级。


    <title size="md">L0 · 低影响变更</title>
    例如不改变行为契约的文案修正、非关键日志字段调整。通过自动测试后可按策略发布。



    <title size="md">L1 · 单模块行为变更</title>
    例如某个专家的路由参数调整。需要模块级回放、对照评测和受控试运行。



    <title size="md">L2 · 跨模块或数据变更</title>
    例如修改工具契约、记忆 Schema 或任务状态协议。需要依赖分析、兼容性测试和明确的迁移与恢复方案。



    <title size="md">L3 · 安全、权限或权威状态变更</title>
    例如扩大权限、改变安全边界、修改关键授权机制。必须经过独立安全评测与适当的明确批准，不能由普通自进化流程自动放行。


这些等级是建议的治理分类，实际发布规则应结合影响范围、可逆性和风险进一步确定。

## 7.1 建立统一发布流水线

建议每个候选版本都经过：

1. 变更登记；
2. 依赖影响分析；
3. 契约与单元测试；
4. 历史任务回放；
5. 集成与端到端测试；
6. 安全和资源回归测试；
7. 候选版本签名或完整性验证；
8. 受控发布；
9. 运行监测；
10. 回滚或正式晋级。

对于低影响变更，可以简化流程；对于涉及授权、数据格式或长期任务状态的变更，不能跳过关键验证。

## 7.2 灰度发布不能让同一个任务混用不兼容策略

假设新版本只对 10% 的任务开放。

如果某个任务在执行中途从旧版本切换到新版本，就可能出现同一任务前半段使用旧工具契约、后半段使用新工具契约的问题。

建议为任务建立明确的版本策略：

- 默认固定关键版本；
- 允许无兼容性影响的更新；
- 发生必要迁移时，执行显式的版本转换；
- 对不兼容更新，优先在任务边界切换；
- 对必须立即生效的安全修复，执行独立的安全策略更新和必要的任务暂停。

安全策略需要能够及时收紧，但普通功能更新不应无条件打断所有正在运行的任务。

---

# 八、回滚治理：恢复代码不等于恢复系统

这是版本管理中最容易被低估的地方。

假设新版记忆系统已经把数据迁移到新格式，新版任务协调器也已经创建了新的检查点。随后发现新版存在缺陷，系统回滚到旧代码。

如果旧代码无法读取新数据，单纯切回旧版本并不能恢复服务。

同样，如果新版本已经执行了外部操作，回滚程序也不能自动撤销已经发生的外部副作用。

因此，建议建立 `ChangeRecoveryPlan`，明确每次重要变更的恢复策略。

## 8.1 回滚需要处理五个方面

| 恢复对象 | 需要解决的问题 |
|---|---|
| 代码与模块 | 能否切换到上一个经过验证的版本？ |
| 配置与策略 | 能否恢复兼容配置？安全策略是否需要保留最新限制？ |
| 数据格式 | 旧版本能否读取现有数据，还是需要反向迁移？ |
| 任务与检查点 | 正在执行的任务能否恢复，是否需要重建状态？ |
| 外部副作用 | 已发送、已发布、已扣费或已修改的数据如何核验与补偿？ |

其中，安全策略不能机械地随所有代码一起回滚。

如果新版本修复了一个重要安全漏洞，功能代码回滚时也不应自动重新启用已知不安全的权限配置。

因此，代码版本、数据版本和安全策略版本需要分别管理，再通过兼容性规则确定组合是否允许运行。

## 8.2 变更前就要设计恢复路径

不能等发布失败后才开始研究如何回滚。

对于高影响变更，应事先明确：

- 失败检测条件；
- 回滚触发门槛；
- 允许回滚到哪个版本；
- 数据是否可以逆向迁移；
- 哪些任务必须暂停；
- 哪些外部操作需要核验；
- 如何确认回滚后系统真正恢复。

如果某项数据迁移不可逆，就必须在执行迁移前明确备份、保留原始数据或其他恢复方案。

---

# 九、跨设备版本协调：手机、Windows 和 Linux 主机不能各自随意升级

你的部署方向是个人设备优先，因此版本治理不能假设所有设备始终在线，也不能要求所有设备在同一时刻完成升级。

建议建立 `DeploymentManifest`，描述每台设备当前的运行组合：

- 设备身份；
- 产品版本；
- 模块版本；
- 接口契约版本；
- 数据格式版本；
- 安全策略版本；
- 当前运行模式；
- 已知兼容范围；
- 待完成的迁移；
- 最近一次成功验证时间。

## 9.1 区分本地独立运行与协同运行

如果 Android 手机完全离线使用自己的本地能力，它可以暂时使用一套经过验证的本地运行组合。

但如果手机需要把任务提交给 Linux 主机执行，就必须验证双方的任务协议、工具契约、状态格式和授权规则是否兼容。

不要求所有设备拥有完全相同的版本，但要求它们在实际交互的接口上兼容。

## 9.2 建立升级协调流程

建议流程为：

1. 发布新的兼容性清单；
2. 设备检查是否满足升级前置条件；
3. 获取并验证目标版本；
4. 执行必要的数据备份与迁移；
5. 运行本地兼容性检查；
6. 与其他设备核验协作协议；
7. 在允许的范围内启用新版本；
8. 持续记录版本差异与异常；
9. 必要时暂停跨设备任务或回滚。

对于长期离线的设备，可以保留旧版本，但不能允许其在未经检查的情况下执行依赖新版本安全策略的高风险操作。

## 9.3 版本同步不等于配置同步

不同设备的硬件、工具和权限可能不同。

例如：

- Windows 电脑拥有本地代码构建环境；
- Linux 主机适合长期运行后台任务；
- Android 手机主要承担交互和轻量处理。

这些设备可以共享任务协议与部分通用策略，但不应该无条件复制所有本地路径、硬件配置和工具权限。

建议同步的是经过治理的配置与兼容性元数据，而不是把一台设备的全部配置原样覆盖到另一台设备。

# 十、让系统级变更本身也能自我进化

CGVCM 不应只是一个静态审批系统。它也需要利用运行数据发现配置和兼容性治理的问题。

例如，EvoAgent 可能发现：

- 某个模块频繁引发接口兼容问题；
- 某种数据迁移容易产生恢复失败；
- 某类配置冲突反复出现；
- 某个工具适配器的版本升级经常影响旧任务；
- 某种发布流程过于复杂，却没有提高实际安全性。

这些结果可以用来改进变更治理流程。

## 10.1 建立独立的变更质量评测

建议关注：

| 指标 | 目的 |
|---|---|
| 变更成功率 | 候选变更是否达到预期目标 |
| 回归缺陷率 | 新版本是否破坏原有能力 |
| 兼容性失败率 | 模块或设备之间是否出现契约不匹配 |
| 迁移成功率 | 历史任务、记忆和检查点能否安全升级 |
| 回滚成功率 | 失败变更是否能够恢复到有效状态 |
| 变更恢复时间 | 从发现问题到恢复正常运行需要多久 |
| 未预期行为变化 | 是否出现没有声明的路由、预算、权限或执行行为变化 |
| 发布治理成本 | 为确保变更安全投入了多少时间和资源 |

不能只以发布速度或回滚次数衡量治理质量。

回滚次数过少，可能意味着系统稳定，也可能意味着缺乏有效的故障检测；发布速度很快，也可能是因为跳过了必要测试。

## 10.2 通过历史任务回放验证行为变化

对于 Router、上下文压缩、预算分配、ReAct 停止策略等影响行为的模块，建议保留经过授权和脱敏处理的评测样本。

每次候选升级时，比较新旧版本在相同任务条件下的表现：

- 任务成功率；
- 关键事实与证据是否保留；
- 资源消耗；
- 工具选择；
- 权限边界；
- 失败恢复；
- 最终验收质量。

如果候选版本只在平均指标上提升，却在重要任务类别中出现明显退化，就不应直接全面发布。

对于涉及用户敏感数据的回放，需要执行相应的访问控制和数据最小化策略，不能为了评测而无限保留全部原始对话。

# 十二、下一专项：系统可观测性、因果诊断与进化效果归因

到这里，EvoAgent 已经设计了安全执行、权限治理、任务恢复、多任务调度，以及配置和版本管理。

但还有一个贯穿所有模块的核心问题：

**当系统表现变差时，如何知道究竟是哪一个模块、哪一次变更或哪一种交互导致了问题？**

例如，某次升级后，代码任务成功率从 85% 降到了 72%。

可能的原因包括：

- Router 把任务交给了不合适的专家；
- 上下文压缩丢失了关键约束；
- Planner 生成了不合理的 DAG；
- 新模型的工具调用能力发生变化；
- 预算策略过早停止了推理；
- 工具运行时出现兼容性问题；
- 测试集发生了变化；
- 任务难度分布与以前不同。

如果系统只观察最终成功率，就很容易把问题归咎于错误的模块，并通过修改另一个模块暂时掩盖症状。

这与你最初提出的自进化系统目标直接相关：不仅要发现运行中的问题，还要提升问题诊断能力，避免诊断能力和执行能力互相干扰。

下一专项建议定义为：

**System Observability, Causal Diagnosis & Evolution Attribution，简称 SOCDEA。**

重点研究：

1. 如何建立跨模块统一的运行事件与指标体系；
2. 如何关联用户任务、专家路由、上下文、工具调用和最终验收；
3. 如何区分相关性、时间先后与真正的因果关系；
4. 如何判断某次版本变更是否导致了质量退化；
5. 如何区分模型能力不足、上下文错误、工具故障和任务难度变化；
6. 如何设计能够区分不同根因的诊断实验；
7. 如何防止诊断器只根据自己的推测修改系统；
8. 如何建立独立的诊断评测集；
9. 如何量化自进化带来的质量、效率、稳定性与安全变化；
10. 如何通过对照实验、历史回放和受控发布验证改进效果；
11. 如何将诊断结论与 RCAE、EQEAG、SELCIA 和版本治理连接；
12. 如何避免为追求单一指标而牺牲整体任务质量。

本专项的核心原则是：

**运行失败只是观察结果，根因必须通过证据和可检验的假设来确定；改进是否有效，也必须通过独立评测，而不能由提出改进的模块自行宣布。**

完成这一专项后，EvoAgent 的自进化闭环就会更完整：不仅能够运行、恢复和升级，还能够更可靠地解释自己为什么变好、为什么变差，以及下一步应该改进什么。
