# EvoAgent 第三十五专项：多专家协作、任务分解与协同决策治理

这一轮进入 EvoAgent 的一个核心问题：**如何让多个专业智能体协同完成复杂任务，而不是简单地把多个专家拼接在一起。**

你之前已经明确，EvoAgent 采用统一任务入口、多层路由、共享通用内核、独立领域专家、任务 DAG、ReAct、Planner 和独立进化控制器。

现在要解决的是，这些机制在多专家协作时如何共同工作。

例如，用户提出：

“帮我制作一部 60 秒的动态视频漫剧，包括剧情、角色、分镜、画面、配音、视频合成和质量检查。”

这不是把任务简单路由给“漫剧专家”就结束了。

漫剧专家还需要判断哪些工作可以独立进行，哪些必须等待前置产物；什么时候调用图像、视频、配音和编程专家；如何保证角色一致性；生成失败后如何局部重做；最终由谁决定作品是否合格。

本专项建议定义为：

**Multi-Agent Collaboration & Task Decomposition Governance，简称 MACTDG。**

它负责协作策略、任务分解、专家分配、依赖管理、产物交接、冲突解决、协作成本控制与协作模式沉淀。

## 一、第一性原理：多个专家的价值来自互补，而不是数量

增加专家数量，并不必然提升任务质量。

如果三个专家使用相同的信息、采取相同的方法、给出相同的判断，那么它们之间的协作价值可能很低，反而会增加模型调用、上下文传递和协调成本。

反过来，如果一个任务需要不同领域的专业能力，合理的协作就可能显著提高质量。

因此，协作系统首先要判断：

- 单个专家是否已经足以完成任务；
- 任务是否包含不同的专业能力需求；
- 子任务之间是否存在依赖；
- 是否有必要让多个专家独立验证同一个结果；
- 协作成本是否值得；
- 最终结果能否通过明确的验收标准进行验证。

建议冻结一个原则：

**默认使用能够可靠完成任务的最小专家集合；只有在质量、能力覆盖、风险控制或效率方面存在明确收益时，才增加协作。**

这里的“最小”不是永远只用一个专家，而是避免为了体现多智能体架构而人为增加角色。

# 二、先区分五种协作模式

EvoAgent 不应该把所有多专家任务都处理成一种固定流程。

建议定义五种基础协作模式。


    <AsyncImage query="minimal editorial illustration one AI assistant working at a desk with notebook clean conceptual style" aspectRatio="3:4" maxWidth="92px"/>

      <title size="md">1. 单专家执行</title>
      一个专家负责任务，通用内核提供路由、上下文、工具和验收能力。适用于目标明确、领域单一的任务。




    <AsyncImage query="minimal editorial illustration three colleagues working independently on separate workstations conceptual design" aspectRatio="3:4" maxWidth="92px"/>

      <title size="md">2. 并行分工</title>
      多个专家处理相互独立的子任务，最后整合结果。适用于可并行的研究、素材准备和模块分析。




    <AsyncImage query="minimal editorial illustration interconnected workflow nodes arranged as a pipeline conceptual design" aspectRatio="3:4" maxWidth="92px"/>

      <title size="md">3. 依赖式流水线</title>
      一个专家的产物成为另一个专家的输入。适用于编剧、分镜、画面生成、配音与合成等有明确前置关系的工作。




    <AsyncImage query="minimal editorial illustration several experts discussing a document around a small table conceptual design" aspectRatio="3:4" maxWidth="92px"/>

      <title size="md">4. 多方审议与独立验证</title>
      不同专家对同一关键问题进行分析，再由有明确权限的决策者或规则引擎作出决定。适用于高风险判断和复杂质量验收。




    <AsyncImage query="minimal editorial illustration a person revising a project plan with feedback arrows conceptual design" aspectRatio="3:4" maxWidth="92px"/>

      <title size="md">5. 反馈式协作</title>
      执行专家先产出结果，评审专家发现问题，执行专家再有针对性地修复。适用于代码修复、视频质量提升和复杂交付物迭代。



这五种模式可以组合使用。

例如，一个视频制作任务可以采用流水线组织主流程，在独立阶段并行生成素材，再使用反馈式协作处理质量问题。

它们不是五种必须独立实现的智能体，而是五类可复用的协作策略。

# 三、任务分解：先理解目标，再决定如何拆分

任务分解是多专家协作的起点，也是最容易过度设计的环节。

如果用户只问“Python 中列表和元组有什么区别”，就没有必要构建复杂 DAG。

如果用户要求制作一部 60 秒视频漫剧，则可能需要多个阶段、多个专家、外部生成服务和多轮质量验收。

因此，建议采用两阶段分解。

## 3.1 第一阶段：建立任务目标模型

在创建子任务之前，Planner 需要先识别：

- 用户的最终目标；
- 必须满足的约束；
- 最终交付物；
- 验收标准；
- 可用资源与预算；
- 时间要求；
- 不允许发生的副作用；
- 当前已知条件和信息缺口。

这一步的产物不是执行计划，而是一个经过整理的目标模型。

例如，制作视频漫剧时，目标模型可能规定：

- 时长为 60 秒；
- 输出横屏 16:9 视频；
- 主要角色在各镜头中保持一致；
- 包含配音、背景音乐和字幕；
- 需要输出可播放的视频文件；
- 生成费用不能超过批准预算；
- 最终必须通过视频完整性与质量检查。

这些约束应当贯穿后续子任务，不能只存在于最初的聊天上下文里。

## 3.2 第二阶段：基于目标生成任务 DAG

Planner 根据目标模型决定哪些工作需要执行、哪些可以并行，以及哪些必须等待前置结果。

例如：


    **目标与验收标准确认**





    **剧情与角色设计**





    **分镜与镜头计划**


    <grid-item>


        **画面与素材生成**
        多个镜头可并行

    </grid-item>
    <grid-item>


        **配音与音频准备**
        可并行准备部分资源

    </grid-item>





    **视频合成与同步**





    **质量验收与定向返工**


这只是示例 DAG，不是固定工作流。

实际执行时，如果用户已经提供完整分镜，可以跳过剧情设计；如果某个视频生成工具能同时生成画面与运动，也可以合并部分节点；如果某个镜头失败，则可以只重做该镜头及其受影响的下游节点。

## 3.3 任务分解需要有停止条件

Planner 不应无限拆分任务。

建议在以下条件满足时停止继续分解：

- 子任务的目标已经明确；
- 输入和输出可以描述；
- 责任专家已经确定；
- 执行方式和验收条件已经足够清楚；
- 子任务规模适合当前执行器；
- 继续拆分的收益不足以抵消协调成本。

一个很重要的判断标准是：

**如果一个子任务可以直接执行、独立验收并清楚报告结果，就不一定需要继续拆分。**

# 四、动态任务 DAG：固定工作流与灵活规划如何结合

这里要特别强调：EvoAgent 不应该在“完全固定流程”和“完全自由规划”之间二选一。

建议采用三种执行模式。

| 模式 | 适用场景 | 规划方式 |
|---|---|---|
| 固化工作流 | 已验证、重复执行、输入输出稳定的任务 | 按已发布 DAG 执行，只允许声明过的分支 |
| 模板化工作流 | 任务结构大致稳定，但参数和部分步骤变化 | 从工作流模板生成实例 DAG |
| 动态规划 | 新任务、探索性任务、需求不明确或执行中出现新问题 | Planner 根据证据生成、调整或局部重建 DAG |

例如，第一次制作某类视频漫剧时，系统可能需要动态规划和大量探索。

当一个工作流已经经过多轮成功执行、质量验收和成本验证后，就可以沉淀为模板或固化工作流。

但固化并不意味着永远不能改变。如果模型能力、工具接口或用户需求发生变化，系统仍然可以提出新版本，并经过评测后发布。

## 4.1 允许局部重新规划，不要轻易推倒重来

假设一个视频任务已经完成剧情、角色、分镜和八个镜头中的七个，只剩一个镜头生成失败。

最合理的做法通常是：

1. 记录失败原因；
2. 判断失败是否影响其他镜头；
3. 保留已经通过验收的七个镜头；
4. 重新规划失败镜头的生成路径；
5. 验证新镜头与既有素材的兼容性；
6. 从受影响的合成节点继续执行。

只有当上游设计存在根本问题时，才应该扩大重规划范围。

这能显著降低重复成本，也有利于保留已经验证的工作成果。

# 五、专家分配：谁负责、谁协作、谁验收？

多专家系统最容易出现的误区，是给每个子任务都指定一个主专家，却忽略了协作责任和最终验收责任。

建议每个子任务至少明确以下角色。


    <title size="md">主责专家 · Owner</title>
    对该子任务的执行结果负责，组织所需工具和局部推理，并按契约提交产物。



    <title size="md">协作专家 · Contributor</title>
    提供特定领域的分析、素材或辅助结果，但不自动获得主任务的全部权限。



    <title size="md">验收者 · Verifier</title>
    依据明确的验收标准检查产物。关键场景下，应尽量与执行者分离，避免自我验证的偏差。



    <title size="md">任务协调器 · Coordinator</title>
    管理依赖、调度、状态、资源、重试和恢复，不代替专家作出所有领域判断。


并不是每个任务都需要四个不同的专家或进程。这里定义的是职责，而不是强制的智能体数量。

对于低风险的小任务，主责专家和验收者可以由同一个模块承担；对于重要交付物，则可以要求独立验收器或确定性检查工具。

## 5.1 专家分配应当综合考虑多种因素

建议路由和协作规划考虑：

- 专家能力是否覆盖任务要求；
- 过往同类任务的质量表现；
- 当前工具和模型是否可用；
- 执行成本与预期耗时；
- 专家是否需要特殊的领域技术；
- 输入数据是否适合交给该专家；
- 当前专家是否已经过载；
- 验收是否需要独立判断；
- 该任务是否属于已经验证的工作流。

不能只按专家的静态排名分配任务，也不能仅因为某专家名称与任务相似就认定它适合执行。

例如，代码专家不一定适合所有代码任务。涉及大型项目的 AST 分析、编译器诊断、数据库迁移和简单脚本编写，可能需要不同的能力组合。

## 5.2 先检查能力，再决定是否调用专家

建议使用能力注册表描述每个专家的实际能力，而不仅仅是自然语言介绍。

例如：

```json
{
  "expert_id": "code_expert",
  "capabilities": [
    "code_analysis",
    "ast_refactoring",
    "test_execution"
  ],
  "input_contracts": [
    "source_files",
    "project_manifest"
  ],
  "output_contracts": [
    "patch",
    "test_report"
  ],
  "supported_operations": [
    "read",
    "workspace_write",
    "run_tests"
  ]
}
```

这是示意结构。

真正的能力注册表还应记录工具依赖、能力版本、已验证的任务类型、资源需求、权限边界和质量评测结果。

能力声明表示“理论上支持什么”；评测结果则回答“在什么条件下，实际表现可靠”。

# 六、专家交接协议：不能只传一段聊天记录

多专家协作的质量，很大程度上取决于交接质量。

如果一个专家把全部聊天历史直接传给下一个专家，可能会导致上下文过长、无关信息过多、关键约束被淹没，以及不可信内容的来源丢失。

因此，建议建立统一的 `ExpertHandoff` 协议。

每次交接至少包含：

- 任务 ID 与子任务 ID；
- 当前主责专家与目标专家；
- 子任务目标；
- 输入产物引用；
- 必须遵守的约束；
- 已确认的事实；
- 尚未解决的问题；
- 输出契约；
- 验收标准；
- 预算和截止条件；
- 授权引用；
- 相关配置版本；
- 上游证据和不可信来源标记。

## 6.1 交接的核心是产物与约束，不是把思考过程全部复制过去

例如，分镜专家交给视频生成专家的内容应该是结构化的镜头计划，包括：

- 镜头 ID；
- 角色和场景引用；
- 画面描述；
- 运动要求；
- 镜头时长；
- 视觉风格约束；
- 输入素材引用；
- 预期输出规格；
- 验收标准。

不需要把分镜专家所有中间推理文本都传给视频生成专家。

但对于重要判断，应当保留可追溯的依据和必要的不确定性，不能为了压缩而丢掉关键约束。

## 6.2 交接前必须验证输入契约

如果上游专家没有提供必需的角色参考图，或者分镜时长总和不满足目标时长，视频生成专家不应该默默猜测缺失信息。

系统可以选择：

- 请求上游补齐；
- 使用经过批准的默认策略；
- 调整任务计划；
- 将节点置于等待状态。

具体选择取决于任务策略和风险，而不是由接收专家任意决定。

# 七、协作冲突治理：专家意见不同，不等于必须投票

多专家系统必然会遇到分歧。

例如：

- 编剧专家建议增加一个转折；
- 分镜专家认为这会导致节奏过快；
- 视频生成专家认为该镜头难以稳定生成；
- 成本治理模块认为新增镜头超出预算。

如果系统简单地采用多数票，就可能忽略最重要的硬约束。

建议把冲突分成四类。

| 冲突类型 | 例子 | 处理方式 |
|---|---|---|
| 事实冲突 | 两个专家对文件内容或执行结果判断不同 | 查询权威数据或独立验证 |
| 目标冲突 | 对剧情、设计或质量取舍意见不同 | 回到用户目标与验收标准 |
| 资源冲突 | 两个子任务争抢 GPU、预算或同一文件 | 由调度器和资源治理机制处理 |
| 权限冲突 | 某专家提出超出授权的操作 | 由 SBAAG 决定，不由专家投票 |

## 7.1 硬约束优先于偏好

例如，用户规定视频总时长不得超过 60 秒，那么专家不能仅凭“这样更有艺术性”就擅自将其扩展到 90 秒。

对于软约束，则可以比较质量、成本、速度和可维护性等因素，选择更符合整体目标的方案。

## 7.2 只有在有价值时才启动多方审议

对于简单的、可确定性验证的问题，不需要多个专家重复推理。

例如，视频分辨率是否为 1920×1080，可以直接通过媒体工具检查。

而对于剧情是否连贯、角色表达是否自然等主观质量问题，多个独立视角可能有价值，但仍应使用明确的评分标准，并保留分歧和置信度。

**多专家协作应优先增加独立信息，而不是重复生成相似意见。**

# 八、协作成本控制：什么时候多专家不值得？

每增加一个专家，就会增加一定的协调成本。

成本不仅包括模型调用费用，还包括：

- 上下文构建和传递；
- 专家启动与调度；
- 工具执行；
- 结果合并；
- 冲突解决；
- 重复验证；
- 失败重试；
- 额外的等待时间。

因此，协作规划需要判断新增专家带来的预期收益是否值得。

可以用一个简化的决策模型表示：

\[
U_{\text{collab}}
=
\Delta Q
+\lambda \Delta R
-\alpha \Delta C
-\beta \Delta T
\]

其中：

- \(\Delta Q\)：预期质量提升；
- \(\Delta R\)：风险降低或可靠性提升；
- \(\Delta C\)：额外成本；
- \(\Delta T\)：额外耗时；
- \(\lambda,\alpha,\beta\)：根据任务类型确定的权重。

这里的数值不应直接混用不同单位。工程实现时，应先将质量、风险、成本与耗时归一化或转化为明确的业务效用，再进行比较。

对于高风险任务，即使协作成本较高，独立验收仍然可能是必要的；对于低风险任务，增加多个专家进行重复分析可能毫无价值。

## 8.1 建立协作停止条件

建议至少设置以下限制：

- 最大专家数量；
- 最大任务分解深度；
- 最大协作轮数；
- 最大重试次数；
- 单任务预算；
- 总耗时限制；
- 最大并发；
- 最低可接受收益；
- 连续无进展的停止阈值。

当协作达到停止条件时，系统可以选择交付当前已验证的部分结果、请求用户决策、切换备用方案或明确报告失败。

不能因为一个专家认为“再找一个专家看看可能更好”，就无限增加协作层级。

## 8.2 协作效率必须可评测

建议跟踪：

- 单专家完成率；
- 多专家任务完成率；
- 每个合格交付物的总成本；
- 专家交接失败率；
- 重复劳动比例；
- 协作引入的等待时间；
- 多专家审议后的决策质量；
- 因协作导致的返工量；
- 任务分解深度与实际质量之间的关系。

只有通过真实任务数据比较，才能判断某种协作策略是否有效，而不是仅凭架构设计的复杂程度来评价。

# 九、故障与重新分配：某个专家失败，不应该让整个任务失去进度

假设视频生成专家连续失败，但剧情、分镜、角色素材和配音都已完成。

系统应当判断失败的影响范围，而不是立即重做整个任务。

建议将故障分为三种。


    <title size="md">局部故障</title>
    只影响单个子任务，其他产物仍然有效。保留已验收结果，仅重试或替换失败节点。



    <title size="md">能力故障</title>
    当前专家或工具无法完成任务。检查能力注册表，选择符合契约、权限和预算要求的替代专家或工具。



    <title size="md">上游设计故障</title>
    失败源于任务目标、输入规格或依赖设计本身。回到相关上游节点进行局部重新规划，并重新验证受影响的下游结果。


## 9.1 替代专家不能只看名称相似

如果主专家失败，备用专家需要满足：

- 输入输出契约兼容；
- 具有完成该任务所需的能力；
- 能够在当前授权范围内运行；
- 预算和资源要求可接受；
- 相关质量评测足以支持此次替换。

如果替代专家的输出规格不同，就需要显式适配或修改下游计划，而不是直接把它的产物塞给下一个节点。

## 9.2 重新分配前先核验执行状态

如果原专家的执行器已经超时，不能直接假设它停止了。

它可能仍在运行，甚至可能已经向外部服务提交了请求。

因此，重新分配之前应检查：

- 原执行器是否仍然活动；
- 是否持有有效资源租约；
- 是否已产生副作用；
- 是否存在未决外部操作；
- 结果是否已经提交；
- 是否可以安全重试。

这部分必须与 L3RG、TLCIG、TRCPG 和 SBAAG 协作。

## 10.1 工作流必须保留适用边界

一个工作流在某种模型、素材类型和设备上成功，不代表它在所有场景都适用。

因此，每个正式工作流至少需要描述：

- 适用的任务类型；
- 输入条件；
- 输出契约；
- 必要的能力和工具；
- 关键依赖；
- 成功与失败判据；
- 预算和资源范围；
- 已知限制；
- 评测数据和结果；
- 工作流版本；
- 回滚或退役条件。

例如，一个视频工作流如果依赖某个云端服务，就不能在服务离线时假装仍然能够完成相同任务。它应当明确声明该依赖，并定义等待、替代或降级路径。

## 10.2 区分工作流复用与专家能力进化

二者不是一回事。

- 工作流复用：让系统用已经验证过的方式组织任务。
- 专家能力进化：让某个专家在特定任务上表现得更好。
- 工具进化：改进执行接口、可靠性和性能。
- 路由进化：改进任务与能力之间的匹配。
- 质量治理：验证这些变化是否真正提升整体结果。

它们可以协作，但不能混为同一个优化过程。

一个工作流变得更快，并不一定意味着专家的推理能力提高了；一个专家的单项评测变好，也不一定意味着整体工作流更可靠。

# 十二、下一专项：自进化闭环与改进因果归因

多专家协作解决了“如何一起做事”，但它还没有完全解决你最初提出的核心目标：

**EvoAgent 如何从实际运行中发现自己的问题，找到真正有效的改进，并确认改进后系统确实变好了？**

这是自进化系统最重要、也最容易被设计得过于简单的部分。

例如，某个专家最近的任务成功率下降。

系统可能提出很多候选解释：

- 路由选择不准确；
- 上下文压缩丢失了关键约束；
- 模型版本发生变化；
- 工具接口退化；
- Planner 的分解策略不适合这类任务；
- 验收标准发生了变化；
- 近期任务本身变得更困难。

如果系统没有办法区分这些因素，就可能修改错误的模块，甚至因为一次偶然的成功而错误地认为改进有效。

下一专项建议定义为：

**Self-Evolution Loop & Causal Improvement Attribution，简称 SELCIA。**

重点研究：

1. 如何从运行证据中识别值得改进的问题；
2. 如何区分偶发错误、系统性缺陷和环境变化；
3. 如何为每个问题建立多个可验证的根因假设；
4. 如何决定改进应该作用于专家、路由、上下文、工具、工作流还是系统内核；
5. 如何生成范围明确、可回滚的候选改进；
6. 如何设计基线、对照组和回归评测；
7. 如何区分真实质量提升与任务难度、样本分布或模型变化造成的假象；
8. 如何衡量质量、成本、效率、稳定性与安全之间的综合变化；
9. 如何防止优化一个指标却损害其他重要能力；
10. 如何决定候选改进应继续测试、正式发布、暂缓还是回滚；
11. 如何让诊断能力与执行能力保持职责分离；
12. 如何将一次成功改进转化为长期可积累的系统知识，同时避免把偶然经验固化成错误规则。

这个专项会直接连接 RCAE、EQEAG、ODERI、MEEG 和独立进化控制器。

最终目标不是让 EvoAgent 频繁修改自己，而是建立一个可信的改进闭环：

**发现问题 → 建立假设 → 收集证据 → 生成候选 → 独立评测 → 受控发布 → 持续观察 → 必要时回滚。**

真正的无限进化，不是无限增加复杂度，也不是无限修改代码，而是让系统能够持续发现值得解决的问题，并以可验证、可归因、可回滚的方式逐步提升整体能力。

下一轮将正式进入 **SELCIA 自进化闭环专项**，从第一性原理开始，重点解决一个关键难题：如何证明系统变好是某项改进真正造成的，而不是偶然波动、任务难度变化或其他模块变化造成的。
