<WritingBlock id="58731" variant="document"># EvoAgent 专项设计 #87：故障根因诊断、因果归因与可验证修复治理

**英文名称：** Root Cause Analysis, Causal Attribution & Verified Repair Governance

**文档版本：** 1.0

**关联专项：** #75—#86

**设计状态：** 专项设计基线，待实施与验收。

## 一、专项目标

建立一套独立于正常任务执行链路的故障诊断与修复治理体系，使 EvoAgent 不仅能发现异常，还能逐步回答：

- 问题究竟发生在哪里？
- 哪些只是表面症状，哪些可能是根本原因？
- 是模型能力不足，还是提示词、上下文、规划、工具、环境或数据出了问题？
- 多个故障同时发生时，怎样确定它们之间的关系？
- 怎样验证某个原因确实导致了问题，而不是仅仅与问题同时出现？
- 如何区分临时恢复与真正修复？
- 如何避免修复一个问题，却引入更严重的新问题？
- 哪些故障经验可以复用，哪些只能适用于当前任务？
- 如何通过长期评测改进诊断能力，而不让错误诊断反过来污染系统？

**核心原则：异常检测负责发现现象，根因诊断负责提出并验证解释，修复控制器负责实施受控修复，独立验证器负责证明问题是否真正解决。**

诊断系统不能仅凭一次模型判断就修改稳定版能力，也不能把“尝试修复后任务成功”自动等同于“已经证明根因正确”。

## 二、核心架构：诊断与执行解耦

建议采用五个逻辑组件。

| 组件 | 职责 |
|---|---|
| Failure Evidence Collector | 收集故障现场、运行事件、输入输出、环境与版本证据 |
| Diagnostic Engine | 构建故障假设、分析竞争性解释并确定下一步验证 |
| Repair Planner | 根据证据提出候选修复及其影响范围 |
| Repair Controller | 检查权限、风险、预算、回滚能力并执行获准的修复 |
| Independent Verifier | 使用独立检查判断修复是否有效、是否引入回归 |

这些组件可以部署在同一个进程中，但必须保持逻辑职责分离和明确接口。

### 2.1 完整诊断闭环

```text id="87flow"
运行异常或质量退化
        ↓
冻结必要故障证据
        ↓
识别故障症状与影响范围
        ↓
生成多个可能的根因假设
        ↓
收集证据并排除竞争性解释
        ↓
选择低风险、信息价值高的验证实验
        ↓
形成候选修复方案
        ↓
检查权限、影响范围与回滚能力
        ↓
执行获准的修复
        ↓
独立验证修复效果与回归风险
        ↓
确认修复 / 恢复原状 / 继续诊断
        ↓
沉淀可复用经验并进入独立评测
```

其中，“生成根因假设”和“验证根因假设”是两个不同阶段，不能合并成模型的一次自由回答。

## 三、故障分类体系

诊断系统必须能够识别不同来源的故障，避免把所有问题都归因于模型能力不足。

建议建立以下一级故障类别。

### 3.1 模型与推理故障

- 对任务理解错误；
- 推理过程中遗漏必要条件；
- 输出不符合约束；
- 工具选择或参数生成错误；
- 模型能力与任务难度不匹配；
- 模型服务超时、拒绝或输出异常。

### 3.2 提示词与策略故障

- 指令存在冲突；
- 提示词缺少关键约束；
- 专家提示词不适用于当前任务；
- 提示词版本发生不兼容变化；
- 规则优先级不清晰；
- 诊断提示词将症状错误地解释为根因。

### 3.3 上下文与记忆故障

- 关键约束在上下文压缩时丢失；
- 历史信息过期或互相矛盾；
- 检索到无关知识；
- 专家之间发生记忆污染；
- 任务状态未正确恢复；
- 模型使用了未经确认的推断。

### 3.4 规划与调度故障

- 任务分解不合理；
- DAG 依赖关系错误；
- 计划遗漏必要步骤；
- 计划没有适应新的执行证据；
- 重规划过于频繁；
- 调度器重复执行已完成节点；
- 失败恢复范围过大或过小。

### 3.5 工具与接口故障

- 工具自身存在缺陷；
- 参数或 Schema 不匹配；
- 工具返回成功但未产生预期效果；
- 工具超时或返回不完整结果；
- 工具版本发生不兼容变化；
- 工具幂等性或副作用状态判断错误。

### 3.6 环境与依赖故障

- 网络、存储或资源不足；
- 权限发生变化；
- 依赖服务不可用；
- 操作系统或设备环境不兼容；
- 本地与云端状态不一致；
- 外部服务行为发生变化。

### 3.7 数据与知识故障

- 输入数据不完整或错误；
- 数据格式异常；
- 知识来源不可靠；
- 事实已经过期；
- 数据转换过程中丢失信息；
- 不同来源之间存在冲突。

### 3.8 监控与评测故障

- 正常任务被误判为失败；
- 真实故障未被发现；
- 验收规则不完整；
- 测试集无法代表真实任务；
- 评估器与被评估系统共享相同错误假设；
- 日志缺失导致错误归因。

### 3.9 组合故障

实际问题可能由多个因素共同造成。

例如，模型选择错误可能与上下文过长同时存在；工具参数问题也可能由提示词遗漏和 Schema 设计缺陷共同导致。

因此，故障分类不能强制每个问题只有一个根因。

诊断系统应允许记录主要原因、促成因素、触发条件和未解决的不确定性。

## 四、根因诊断记录与证据链

建议新增逻辑对象 `DiagnosticCase`，与现有任务、运行和事件记录关联。

### 4.1 诊断记录

建议包含：

- `diagnostic_case_id`：诊断案例标识；
- `task_id`：关联逻辑任务；
- `run_id`：发生故障的运行；
- `node_run_id`：关联节点，可为空；
- `symptom_refs`：异常信号与失败事件；
- `impact_scope`：影响范围；
- `failure_category`：故障类别；
- `hypothesis_refs`：根因假设集合；
- `evidence_refs`：支持或反驳假设的证据；
- `experiment_refs`：验证实验记录；
- `repair_refs`：候选修复和执行记录；
- `verification_refs`：独立验证结果；
- `diagnostic_status`：诊断状态；
- `runtime_manifest_id`：故障时的运行组件清单；
- `created_at`、`updated_at`：记录时间。

这些是建议的逻辑扩展，应与正式 Schema 统一，而不是假设现有接口已经全部实现。

### 4.2 证据类型

每项证据应区分：

- **直接证据：** 例如实际错误码、测试失败输出、外部系统状态；
- **对照证据：** 例如同一任务在不同工具版本下的表现；
- **关联证据：** 例如错误与某次版本更新同时出现；
- **推断证据：** 例如模型根据日志提出的解释；
- **反证：** 与当前根因假设不一致的事实；
- **缺失证据：** 当前无法获得但可能影响结论的信息。

关联证据不能自动升级为直接因果证据。

### 4.3 证据不可被候选修复覆盖

诊断开始时，应保留足够的原始故障证据，避免修复操作覆盖现场。

包括必要的：

- 原始错误和事件序列；
- 输入输出契约；
- 运行组件版本；
- 环境摘要；
- 已执行动作；
- 测试结果；
- 相关外部回执。

敏感内容仍须遵循数据最小化和权限规则。冻结证据不等于无限期保存全部原始数据。

## 五、根因假设生成与筛选

### 5.1 不允许只生成一个解释

对于有实际影响的故障，诊断系统应至少考虑一个主要解释和必要的竞争性解释。

例如，代码测试失败时，候选原因可能包括：

- 代码逻辑错误；
- 测试环境不完整；
- 测试用例本身存在缺陷；
- 依赖版本不匹配；
- 运行时配置错误。

不能因为第一眼看起来像代码问题，就立即修改代码。

### 5.2 假设记录

每个根因假设应记录：

- `hypothesis_id`；
- `statement`：假设内容；
- `category`：所属故障类别；
- `supporting_evidence_refs`；
- `contradicting_evidence_refs`；
- `predicted_observations`：如果假设成立，预期观察到什么；
- `alternative_hypothesis_refs`；
- `verification_method`；
- `estimated_test_cost`；
- `risk_if_wrong`；
- `status`：待验证、获得支持、被反驳或无法判定。

### 5.3 诊断结论等级

建议采用以下状态，而不是给出没有校准依据的精确概率：

| 状态 | 含义 |
|---|---|
| D0：未定位 | 只有症状，尚无可信根因假设 |
| D1：候选原因 | 已提出可能原因，但证据不足 |
| D2：证据支持 | 有证据支持，但仍存在重要替代解释 |
| D3：验证通过 | 通过具有区分能力的实验验证了该原因 |
| D4：修复确认 | 修复后故障不再出现，且相关回归检查通过 |
| D5：重复验证 | 在适用的独立测试或重复场景中再次验证成功 |

这些状态是诊断流程状态，不代表所有故障都必须达到 D5。

对于只能在特定环境复现的问题，系统可以给出有限范围的结论，但必须说明验证边界。

## 六、因果归因与验证实验

### 6.1 相关性不是因果性

如果某次提示词升级之后失败率上升，不能仅凭时间顺序就断言提示词升级导致了故障。

还可能存在：

- 模型版本同时变化；
- 输入任务难度变化；
- 工具服务发生故障；
- 运行环境变化；
- 评测集发生变化。

因此，根因诊断必须尽可能控制混杂因素。

### 6.2 验证方法

根据故障类型选择合适方法：

- 静态检查；
- 单元测试或契约测试；
- 重现失败案例；
- 对照运行；
- 输入与输出差异比较；
- 依赖版本检查；
- 受控参数变化；
- 隔离环境中的复现实验；
- 经过批准的 A/B 或影子评测。

不是每个问题都需要昂贵实验。

简单、可直接验证的故障应使用最小验证手段；影响范围大、修复风险高的问题则需要更严格的证据。

### 6.3 优先选择低风险、高信息价值的实验

验证实验应考虑：

- 能否区分竞争性假设；
- 是否会改变生产状态；
- 是否会产生外部副作用；
- 执行成本；
- 是否可重复；
- 是否能够回滚；
- 是否需要额外授权。

优先使用只读检查、测试环境、模拟工具和离线回放。

不能为了验证假设，就直接在生产环境中执行危险操作。

### 6.4 无法证明时应保留不确定性

有些故障可能无法完全复现，或证据已经不足。

此时可以报告：

- 最有支持的解释；
- 尚未排除的其他原因；
- 已经验证的事实；
- 仍缺少的证据；
- 建议的下一步调查。

不应为了给用户一个确定答案而编造根因。

## 七、修复方案治理

### 7.1 修复方案应明确影响范围

每个候选修复至少需要定义：

- 修复目标；
- 对应根因假设；
- 修改对象与版本；
- 预期改善；
- 可能引入的风险；
- 影响范围；
- 验证方案；
- 回滚条件；
- 预算与权限要求。

### 7.2 修复等级

**R1：任务内临时恢复**

例如，修正当前请求的参数，或重新执行一个失败的节点。

这类修复不应自动改变共享能力资产。

**R2：任务级策略调整**

例如，为当前任务更换一个适用工具或调整局部执行计划。

需要保留变更记录，并检查是否改变目标或授权。

**R3：能力资产修复**

例如，修复某个工具、提示词模板、工作流或专家配置。

需要版本化、测试和兼容性验证。

**R4：共享内核或诊断体系修复**

例如，修改通用规划器、上下文治理或根因诊断机制。

这类修改可能影响多个专家，必须使用更严格的独立评测、回归和发布门禁。

### 7.3 不允许诊断系统直接修改自身

诊断系统可以发现自己的判断错误，并提出改进候选，但不能仅凭自己的结论直接修改诊断策略并宣布修复成功。

必须由独立评测器、固定回归案例和必要的外部证据进行验证。

这样可以避免诊断系统通过修改判定规则，将原本的失败重新定义为成功。

## 八、独立修复验证

### 8.1 修复成功的必要条件

修复后应至少检查：

1. 原始故障是否能够重现；
2. 修复后的目标行为是否符合预期；
3. 相关回归测试是否通过；
4. 用户原始验收标准是否仍然满足；
5. 是否产生新的错误；
6. 是否引入成本、时延或稳定性退化；
7. 是否影响其他专家或共享能力；
8. 是否仍存在未验证的风险。

### 8.2 验证器必须与修复者保持必要独立性

修复者可以提供测试建议，但不能独自决定测试标准和最终结果。

例如：

- 代码生成器不应只依靠自己的解释证明代码正确；
- 工具开发者不应仅依靠工具返回的成功状态证明功能有效；
- 诊断模型不应通过修改自己的根因分类规则来证明判断准确；
- 工作流执行器不应只凭所有节点显示完成，就判定最终业务目标成功。

独立性可以通过不同的检查机制、固定验收契约、真实外部状态或独立测试器实现，不一定要求使用不同模型。

### 8.3 修复失败时的处理

如果修复没有解决问题：

- 保留原始故障和修复证据；
- 标记该修复假设未得到验证或已被反驳；
- 检查是否存在新的故障；
- 回滚不安全或退化的变更；
- 更新竞争性根因假设；
- 避免重复执行已经证明无效的修复。

失败的修复尝试也是有价值的诊断证据，不应被简单丢弃。

## 九、修复与稳定版隔离

### 9.1 四个状态层次

建议将故障处理分成：

- **生产稳定态：** 当前正在服务用户的能力版本；
- **诊断态：** 正在收集证据和验证根因；
- **候选修复态：** 已形成但尚未通过全部门禁的变更；
- **已验证发布态：** 经过正式验证并获得发布许可的版本。

不能因为候选修复在一个任务中成功，就立即替换稳定版。

### 9.2 自动修复的允许范围

可以考虑自动执行的低风险修复包括：

- 修正已经确认的无副作用参数错误；
- 在明确幂等的条件下重试临时失败；
- 在允许范围内重新运行失败的只读检查；
- 使用已经批准的兼容工具替代不可用工具；
- 修复可逆、局部且有明确验证规则的任务内问题。

是否允许自动执行，必须由风险分类、授权策略和具体修复契约决定，而不能仅根据“看起来简单”判断。

涉及共享能力变更、数据删除、外部副作用、权限扩大或不可逆影响时，应执行相应的更严格控制。

## 十、诊断知识沉淀与跨专家复用

### 10.1 故障经验资产

经过验证的故障经验可以沉淀为结构化资产，包含：

- 故障症状；
- 适用环境；
- 触发条件；
- 已验证根因；
- 反例与限制；
- 推荐诊断步骤；
- 修复方式；
- 验证条件；
- 已知副作用；
- 来源与证据；
- 适用的能力版本；
- 失效条件。

不能只保存一段“遇到这种错误就这样修”的自然语言描述，而忽略适用范围和验证依据。

### 10.2 共享与隔离

建议将经验分为：

- **通用故障知识：** 可被多个专家复用的基础错误模式；
- **领域故障知识：** 只对特定专家或技术栈有效的经验；
- **项目级故障知识：** 只适用于某个项目或环境的配置；
- **任务级诊断记录：** 当前任务的现场和临时判断。

只有经过验证、适用范围明确的经验，才能进入共享知识空间。

单个专家的经验不能未经评测就自动成为所有专家的通用规则。

### 10.3 经验复用前必须检查

- 当前错误是否真正相似；
- 环境和版本是否兼容；
- 原始修复是否通过验证；
- 是否存在反例；
- 是否会改变用户目标或权限；
- 是否可能造成新的副作用。

经验检索结果是诊断线索，不是必须执行的命令。

## 十一、根因诊断能力的独立进化

诊断系统本身需要建立专门的评测集。

### 11.1 评测数据

应包括：

- 已确认根因的历史故障；
- 多个根因同时存在的案例；
- 表面症状相同但根因不同的案例；
- 表面症状不同但根因相同的案例；
- 无法确定根因的案例；
- 修复成功与修复失败的对照案例；
- 错误日志、不完整证据和监控误报案例；
- 版本升级导致的兼容性问题；
- 诊断系统自身造成的错误归因。

### 11.2 评测指标

| 指标 | 目的 |
|---|---|
| 根因定位准确率 | 是否找到真实原因 |
| 假设覆盖率 | 是否考虑重要竞争性解释 |
| 错误归因率 | 是否将症状误判为根因 |
| 证据支持率 | 诊断结论是否有可追溯证据 |
| 实验区分能力 | 验证步骤能否区分竞争性假设 |
| 平均诊断成本 | 为定位问题消耗的资源 |
| 修复成功率 | 修复是否真正解决问题 |
| 回归引入率 | 修复是否导致其他问题 |
| 不必要修改率 | 是否在根因未明时过早修改系统 |
| 不确定性校准质量 | 是否能在证据不足时承认未知 |
| 根因复用收益 | 复用已验证经验是否改善结果 |
| 稳定版退化率 | 修复发布后是否影响正常任务 |

不能只用“诊断结论与最终标签一致率”评价系统，因为标签本身可能不完整或存在歧义。

### 11.3 进化流程

1. 收集经授权的故障案例；
2. 整理原始证据与最终结果；
3. 识别诊断错误类型；
4. 形成候选诊断策略或知识资产；
5. 使用独立评测集验证；
6. 检查误报、错误修复和回归风险；
7. 通过正式发布门禁；
8. 在受控范围内发布；
9. 持续监控实际效果；
10. 发现退化时回滚。

诊断系统不能通过删除困难案例、修改根因标签或降低验收标准来提高表面评测成绩。

## 十二、与整体架构的关系

| 模块 | 关系 |
|---|---|
| #80 根因诊断 | 本专项细化其证据、假设、验证和修复治理 |
| #81 知识治理 | 管理经过验证的故障知识资产 |
| #82 上下文治理 | 排查上下文丢失、冲突和污染 |
| #83 主动辅助 | 主动指出问题并提出修复建议 |
| #84 目标理解 | 判断故障是否源于目标或约束理解错误 |
| #85 动态执行 | 提供节点、计划和恢复状态 |
| #86 可观测性 | 提供异常信号、事件序列和执行证据 |
| #75—#79 进化治理 | 负责候选改进评测、收益验证、发布与回滚 |

需要特别区分三件事：

**发现故障**是观测能力；**解释故障**是诊断能力；**解决故障并证明解决有效**是修复与验证能力。

三者必须形成闭环，但不能因为其中一个环节成功，就推定另外两个环节也成功。

## 十五、完成判定

只有满足以下条件，才能认定本专项实施验收完成：

- 能够从运行事件追溯到具体任务、节点、工具与组件版本；
- 能够区分表面症状、根因假设和已验证根因；
- 对重要故障能够分析竞争性解释；
- 能够选择适当的验证实验；
- 不会将时间相关性直接当成因果证明；
- 修复操作具有明确影响范围、权限要求和回滚策略；
- 修复结果经过独立验证；
- 能够检测修复引入的回归和副作用；
- 经过验证的经验可以沉淀为有适用范围的知识资产；
- 诊断系统本身的错误也能够被记录和评测；
- 候选诊断与修复策略必须经过正式门禁才能影响稳定版；
- 所有关键验收用例均有真实执行证据。

**最终目标：让 EvoAgent 不仅能够发现异常，而且能够基于证据解释异常、验证根因、实施受控修复，并证明修复真正有效。对于暂时无法查明的问题，它也必须诚实地保留不确定性，而不是用一个看似合理的答案掩盖未知。**</WritingBlock>

## 下一项专项：#88

建议继续推进 **#88：故障经验治理、知识资产生命周期与跨专家迁移验证**。

#87 已经解决如何诊断和修复单次故障。下一步需要明确：当系统积累了大量历史问题、修复方案和经验后，如何判断哪些经验值得长期保存、哪些可以跨专家复用、哪些已经过期，以及如何防止错误经验不断传播。

这一步将重点解决四个问题：

1. **经验质量：** 如何区分已验证知识、临时技巧、模型猜测和过期经验。
2. **经验复用：** 如何判断当前问题是否真正适用某条历史经验。
3. **经验生命周期：** 如何创建、验证、发布、降级、废弃和回滚知识资产。
4. **跨专家迁移：** 编程专家中的成功经验，是否能迁移到其他领域，迁移前需要什么验证。

它将把一次次故障处理转化为长期积累的能力，同时避免“经验越多，错误传播越严重”。还有一个需要提前冻结的架构原则：**#87 和 #88 应当深化现有的根因诊断与知识治理能力，而不是再造两套平行系统。**

- #87 应优先扩展现有诊断模块，统一证据、根因假设、验证实验与修复记录。
- #88 应优先扩展现有知识资产生命周期，统一经验验证、适用范围、版本兼容和废弃机制。
- 两者都应复用统一事件、能力资产、版本管理和发布门禁，避免形成重复的数据模型、重复日志和互相冲突的治理规则。

这样才能让 EvoAgent 的专项设计逐步收敛成一个真正可实现、可测试、可维护的系统，而不是随着专项数量增加，架构本身越来越复杂。
