# 一、建立统一领域模型

EvoAgent 不能只围绕一个 `Agent` 对象设计数据库。因为一个真实任务可能包含多个专家、多个计划版本、几十个工具调用、若干记忆检索、多个生成产物，以及多轮评测和恢复。

建议将整个领域模型分为五个对象域。


    <title size="lg">A. 任务与执行域</title>
    Task、Goal、Constraint、Plan、PlanNode、Execution、Checkpoint、TaskResult
    回答：用户要什么、计划是什么、执行到哪里、最终结果是什么。


    <title size="lg">B. 能力与运行域</title>
    Expert、Capability、Tool、Workflow、ModelAdapter、RuntimeManifest
    回答：谁负责、有哪些技术、怎样调用、实际运行使用了哪些版本。


    <title size="lg">C. 记忆与上下文域</title>
    Memory、MemoryRelation、Evidence、ContextSnapshot、RetrievalRecord
    回答：什么信息值得保存、当前调用使用了什么信息、证据来自哪里。


    <title size="lg">D. 评测与进化域</title>
    Incident、Diagnosis、Experiment、Candidate、EvaluationRun、Release、Rollback
    回答：出了什么问题、为什么可能出错、改进是否有效、能否发布。


    <title size="lg">E. 治理与设备域</title>
    Device、PermissionGrant、BudgetLedger、SyncCursor、Policy、AuditEvent
    回答：在哪里运行、允许做什么、花费多少、设备离线后如何同步。


这些是逻辑对象域，不意味着要建立五个独立数据库。初期完全可以使用同一关系型数据库管理结构化数据，并用对象存储保存大型产物与原始证据，再按负载和可靠性要求逐步拆分。

## 1.1 核心实体之间的关系


    **Task**
    用户目标与约束



    **Plan / PlanVersion**
    一个任务可以有多个计划版本



    **PlanNode / Execution**
    每个节点可有多次执行尝试



    <grid-item>

        **Evidence**
        实际执行证据

    </grid-item>
    <grid-item>

        **Artifact**
        生成产物

    </grid-item>



    **Verification / TaskResult**
    根据验收契约确定完成情况


每次执行都需要关联当时的能力版本清单，而不是只关联一个专家名称。任务也应当可以引用相关记忆、上下文快照、预算账本和评测记录。

## 1.2 需要特别区分的五个概念

| 概念 | 含义 | 不应混淆成什么 |
|---|---|---|
| Task | 用户希望达成的目标 | 一次模型调用 |
| Plan | 为完成目标制定的执行方案 | 一段自然语言说明 |
| PlanNode | 计划中的一个逻辑步骤 | 一次实际执行 |
| Execution | 某个步骤的一次具体执行尝试 | 永远只有一次的操作 |
| Evidence | 能够支持或反驳某个结论的实际记录 | 模型自行生成的结论 |

例如，一个节点“运行测试”可以执行三次。第一次环境缺少依赖，第二次运行成功但有测试失败，第三次修复后全部通过。这三次尝试属于同一个逻辑节点，但必须分别保留执行记录，不能覆盖历史。

这会直接决定后续诊断器能否区分“原始故障”“恢复过程”和“最终结果”。

# 二、正式定义任务状态机

这是整个运行时最重要的规范之一。

不能让 Planner、ReAct、工作流引擎和验收器各自维护一套任务状态。我们需要一个由任务控制器负责校验和提交的状态机，所有模块通过受控命令推动状态转换。

## 2.1 任务的完整生命周期


    **CREATED**
    任务已创建



    **UNDERSTANDING → PLANNING**
    理解目标、确定约束与验收契约、生成计划



    **READY → RUNNING**
    前置条件满足，进入执行


    <grid-item>


        **WAITING**
        等待用户、工具或外部服务

    </grid-item>
    <grid-item>


        **REPLANNING**
        需要调整计划

    </grid-item>



    **VERIFYING**
    检查实际结果是否满足验收契约


    <grid-item>


        SUCCEEDED
        完整达标

    </grid-item>
    <grid-item>


        PARTIAL
        部分完成

    </grid-item>
    <grid-item>


        FAILED
        未完成

    </grid-item>

  取消、暂停、超时和安全停止也必须作为明确状态或受控终止原因处理。

这张图是生命周期概览，不是完整的状态转换表。真正的工程实现还需要定义每条边的触发条件、授权方、持久化顺序和失败处理。

## 2.2 不要把所有状态塞进一个字段

建议将状态拆成不同维度：

| 状态维度 | 示例 |
|---|---|
| 任务生命周期 | `RUNNING`、`WAITING`、`PAUSED`、`TERMINAL` |
| 执行结果 | `SUCCESS`、`PARTIAL`、`FAILURE`、`CANCELLED` |
| 计划状态 | `DRAFT`、`ACTIVE`、`SUPERSEDED` |
| 节点状态 | `PENDING`、`READY`、`RUNNING`、`RETRY_WAIT`、`COMPLETED`、`BLOCKED` |
| 验收状态 | `NOT_STARTED`、`PASS`、`FAIL`、`INCONCLUSIVE` |
| 同步状态 | `LOCAL_ONLY`、`PENDING_UPLOAD`、`ACKNOWLEDGED`、`CONFLICT` |

例如，任务可以处于 `WAITING`，等待用户确认；但它已经生成了部分产物。任务也可以处于终止状态，同时验收结果为 `INCONCLUSIVE`，表示执行已经停止，但缺少足够证据判断质量。

这样的分离可以防止状态组合变得含糊。

## 2.3 状态转换必须满足规则

我建议遵循以下约束：

- 任务控制器负责检查任务级状态转换是否合法。
- 计划控制器负责管理计划版本和节点依赖。
- 执行器只能报告执行结果，不能自行宣布整个任务成功。
- 验收器只能提交验收结论和证据，不能绕过权限规则。
- 用户取消任务后，控制器要停止后续调度，并尽力取消正在运行的操作。
- 对于无法确认是否执行成功的外部动作，必须进入状态核查，而不是直接重试。
- 任务进入终止状态后，不再原地恢复执行；如果需要继续，应创建新的恢复任务或明确的续执行实例，并保留原任务的关联关系。

这里还有一个重要设计：任务状态变更必须具有**版本号和并发控制**。例如手机与云端同时尝试更新一个任务时，不能简单地由最后写入者覆盖。

# 三、统一能力调用协议

现在定义专家、工具、技术能力和工作流如何与运行时交互。

我建议所有可执行能力通过统一的调用信封（Invocation Envelope）进入执行控制层。

## 3.1 调用请求的核心结构

<CodeBlock language="json" editable>
{
  "invocation_id": "inv-unique-id",
  "task_id": "task-unique-id",
  "plan_id": "plan-id",
  "node_id": "node-id",
  "capability_id": "python.ast_analysis",
  "capability_version": "3.0.0",
  "runtime_manifest_id": "manifest-id",
  "input_ref": "artifact-or-payload-ref",
  "deadline": "timestamp",
  "idempotency_key": "stable-operation-key",
  "requested_effect": "read_only",
  "authorization_context_ref": "auth-context-ref",
  "budget_reservation_ref": "budget-reservation-ref",
  "trace_id": "trace-id"
}
</CodeBlock>

这是协议设计示例。实际实现中，权限上下文、文件路径、用户数据和凭据需要使用受控引用，不能为了方便直接写入所有日志。

## 3.2 统一执行结果

<CodeBlock language="json" editable>
{
  "invocation_id": "inv-unique-id",
  "status": "SUCCEEDED",
  "output_ref": "artifact-result-ref",
  "error": null,
  "evidence_refs": [
    "evidence-ref-001"
  ],
  "side_effect_state": "NONE",
  "retry_advice": "DO_NOT_RETRY",
  "actual_cost": {
    "input_tokens": 0,
    "output_tokens": 0,
    "external_cost": 0
  },
  "started_at": "timestamp",
  "completed_at": "timestamp"
}
</CodeBlock>

同样，这是概念示例。真实协议还需要记录资源消耗单位、成本币种、部分执行情况和必要的环境元数据。

### 为什么要有 `side_effect_state`？

因为工具返回失败，不一定意味着没有产生副作用。

建议至少区分：

- `NONE`：确认没有副作用；
- `COMMITTED`：确认副作用已经发生；
- `PARTIAL`：确认只发生了部分副作用；
- `UNKNOWN`：无法确定实际状态。

当状态为 `UNKNOWN` 时，执行器应该优先查询真实状态或请求安全恢复，而不是盲目重试。

## 3.3 错误不能只有一段字符串

统一错误对象应包含：

- `error_code`：稳定的错误类别；
- `error_stage`：发生在规划、调用、执行、验收还是同步；
- `retryable`：是否允许重试；
- `retry_after`：建议等待时间；
- `evidence_refs`：支持诊断的证据；
- `side_effect_state`：副作用状态；
- `recovery_hint`：可供控制器使用的恢复建议。

其中，`recovery_hint` 只是建议，不能直接覆盖系统重试上限、权限规则或预算限制。

这样，ReAct 可以根据结构化反馈调整策略，而不需要依赖大模型从一段不规范的错误文本中猜测故障类型。

# 四、记忆与上下文的统一数据协议

前面已经确定记忆系统与上下文治理必须分离。现在进一步明确两者之间的数据边界。

## 4.1 记忆对象至少需要保存什么？

建议记忆不是单纯的 `key-value`，而是有来源、有适用范围、有可信度、有生命周期的对象。

<CodeBlock language="json" editable>
{
  "memory_id": "memory-unique-id",
  "namespace": {
    "scope": "project",
    "project_id": "project-id",
    "expert_id": "ai_drama"
  },
  "memory_type": "verified_constraint",
  "content_ref": "memory-content-ref",
  "source_refs": [
    "user-message-or-evidence-ref"
  ],
  "confidence": null,
  "verification_status": "USER_CONFIRMED",
  "valid_from": "timestamp",
  "valid_until": null,
  "status": "ACTIVE",
  "sensitivity": "PROJECT_PRIVATE",
  "created_at": "timestamp",
  "updated_at": "timestamp",
  "supersedes_memory_id": null
}
</CodeBlock>

这里不建议把所有记忆统一变成一个可由模型随意填写的置信度数字。用户明确确认的事实、工具实际观察到的状态、模型推断出的经验，应该有不同的证据类型和验证状态。

记忆系统还需要支持：

- 新记忆与旧记忆的冲突检测；
- 记忆失效和撤销；
- 来源追踪；
- 命名空间隔离；
- 用户可控的查看、纠正和删除；
- 记忆删除向索引、缓存和同步副本的传播。

## 4.2 上下文快照必须记录实际使用了什么

模型每次调用的上下文不一定需要永久保存完整原文，但必须有足够信息解释这次调用为什么得到当前结果。

建议记录：

- 使用的系统与专家指令版本；
- 输入消息及必要的受控引用；
- 检索到的记忆 ID；
- 选入上下文的证据引用；
- 压缩策略版本；
- 预算分配与截断记录；
- 模型适配器版本；
- 实际调用参数；
- 必要的输入摘要或内容哈希。

对于敏感数据，可以保存脱敏后的快照和受控的原始数据引用，而不是默认复制一份完整上下文到云端日志。

**记忆回答“系统保存了什么”，上下文快照回答“这次调用实际看到了什么”。** 两者之间需要有明确的引用关系，才能分析信息是否在检索、组装或压缩阶段丢失。

# 五、统一进化协议：把一次改进变成可审计的工程变更

这是 EvoAgent 自进化闭环的核心。

我们不能让系统只记录“修改了提示词，效果似乎变好”。每一次候选改进都应当是一份正式的变更对象。

## 5.1 候选变更需要包含什么？

<CodeBlock language="json" editable>
{
  "candidate_id": "candidate-unique-id",
  "target_component": "context_policy",
  "base_version": "context-v5",
  "candidate_version": "context-v6",
  "problem_refs": [
    "incident-ref-001"
  ],
  "hypothesis": "关键约束在压缩后被遗漏",
  "proposed_change_ref": "change-set-ref",
  "affected_capabilities": [
    "coding",
    "ai_drama"
  ],
  "evaluation_plan_ref": "evaluation-plan-ref",
  "budget_limit_ref": "budget-limit-ref",
  "risk_class": "controlled",
  "status": "PROPOSED"
}
</CodeBlock>

这份对象将问题、假设、改动、影响范围和评测计划绑定在一起。

在进入评测之前，系统必须能够回答：

- 要解决的具体问题是什么？
- 现有证据是否支持这个问题确实存在？
- 修改的目标组件是什么？
- 哪些专家、工具或工作流可能受影响？
- 预期改善哪些指标？
- 哪些指标不能退化？
- 实验最多花费多少资源？
- 失败后怎样恢复？

## 5.2 候选版本的发布状态

  {#each [
    ["PROPOSED","改进方案已生成，尚未验证。"],
    ["VALIDATED","方案结构、权限范围、依赖和基础契约检查通过。"],
    ["EVALUATING","正在运行专项测试、回归测试和成本评测。"],
    ["APPROVED","达到预先定义的质量与风险门槛。"],
    ["CANARY","在受控范围试运行，监控真实效果。"],
    ["ACTIVE","成为当前适用的稳定版本。"],
    ["REJECTED","评测未通过，保留原因但不发布。"],
    ["ROLLED_BACK","已发布版本出现退化，恢复到安全版本。"],
    ["RETIRED","不再接受新任务，保留历史追溯与迁移信息。"]
  ] as item}


        {item[0]}


        {item[1]}


  {/each}

这些状态并不要求每种候选都经过完全相同的流程。例如，实验性策略可以直接在隔离环境中评测；涉及安全边界或数据库迁移的变更，则必须满足额外的审批和恢复要求。

## 5.3 发布门禁必须在实验前定义

不能先看到结果，再临时决定什么叫通过。

建议每个实验预先定义：

1. 基线版本；
2. 固定评测集及独立保留集；
3. 目标指标与最小收益；
4. 不允许退化的指标；
5. 成本、延迟和资源上限；
6. 样本量与观察期；
7. 自动停止条件；
8. 回滚触发条件。

例如，优化上下文压缩时，不仅要求 Token 使用量下降，还要规定关键约束遗漏率不能超过阈值，任务质量不能显著下降，且总成本需要包括额外检索和压缩调用。

具体阈值不能现在凭空统一规定，应该由不同能力的风险、业务目标和基线表现决定。

# 六、把 Android 离线与云端进化纳入同一套协议

这一部分是前面设计与工程实现之间的关键桥梁。

EvoAgent 不是一个永远在线的云端 Agent。手机可能离线，云端可能不可用，任务可能在断联期间继续执行，也可能被系统中断。

因此，需要明确三个不同的机制。

## 6.1 任务同步、日志同步、版本同步必须分开

| 同步类型 | 解决的问题 | 冲突处理原则 |
|---|---|---|
| 任务状态同步 | 云端与设备对任务进度的认知如何保持一致 | 基于版本、事件顺序和合法状态转换合并 |
| 日志与证据同步 | 设备上的运行证据如何上传、去重与确认 | 采用稳定事件 ID、确认游标和重复上传去重 |
| 能力版本同步 | 手机何时获得新专家、工作流和策略 | 由发布系统分发经过门禁的版本清单 |

这三种同步不能共用一个简单的“最后更新时间”。

例如，日志上传失败时，设备可以继续把日志保存在本地；新版本下载失败时，设备仍然可以使用已有的稳定版本；任务状态冲突时，则需要根据任务所有权和合法状态转换判断如何合并。

## 6.2 离线执行应该遵循什么原则？

我建议明确以下规则：

- 本地已经具备全部能力、权限和必要数据的任务，可以按本地策略继续。
- 必须调用云端模型或外部 API 的步骤，应进入等待、降级或替代路径，而不是假装已经执行。
- 日志必须先持久化到本地，再尝试异步上传。
- 断联期间产生的日志应携带设备标识、事件 ID、任务 ID、版本清单和本地顺序信息。
- 重新联网后，先同步必要的任务状态和事件，再根据服务端确认结果继续执行。
- 旧版本设备不得因为重新联网就自动覆盖新版本配置或无条件迁移运行中的任务。
- 用户取消、权限撤销和安全停止等控制事件需要明确传播规则；对无法确认已执行的外部动作，必须先核实状态。

还有一点：本地日志可以记录事件顺序，但不同设备的时钟可能不一致，因此不能只靠时间戳判断全局先后顺序。跨设备任务需要额外的事件关联、版本控制和所有权规则。

# 七、现在形成一份正式的架构决策基线

我们已经把前面抽象的架构原则推进到了领域对象、状态机、能力协议、记忆协议和进化协议。

我建议将当前设计归纳为以下架构决策记录（ADR）。

  {#each [

## 八、下一步：定义数据库结构与核心接口

现在最合理的下一步，是把这套模型落到两个工程交付物上：

**交付物 A：EvoAgent 全量数据库与事件模型**

至少需要明确：

- 核心表及字段；
- 主键、外键和唯一约束；
- 任务与执行记录的关联关系；
- 记忆命名空间与证据引用；
- 运行版本清单；
- 预算账本；
- 评测与进化实验记录；
- 离线同步游标与去重规则；
- 索引、数据保留和迁移策略。

**交付物 B：EvoAgent 核心 API 与状态协议**

至少需要明确：

- 任务创建、查询、暂停、恢复、取消；
- 专家路由与能力发现；
- Plan 创建、修订和节点执行；
- 统一工具调用与错误返回；
- 记忆检索、写入和失效；
- 上下文组装与压缩；
- 验收与证据提交；
- 候选改进、评测、发布和回滚；
- 日志上传、确认和断点续传；
- 设备能力与版本同步。

我建议先完成**数据库与事件模型**，因为它会决定任务状态、日志关联、记忆、上下文和进化记录能否真正贯通；随后再根据这些实体定义 API 和状态机的精确语义。

这一步完成后，EvoAgent 的全量架构就会从概念层进入可以分工实施、编写测试和逐项验收的工程规范阶段。
