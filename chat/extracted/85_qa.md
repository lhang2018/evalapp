# EvoAgent 第三十三专项：可观测性、诊断证据与运行时智能

这一轮要解决一个核心问题：**当 EvoAgent 执行失败、效率下降或行为异常时，系统能否还原事实、定位原因，并为修复和进化提供可信证据？**

前面已经设计了多专家、Planner、ReAct、任务 DAG、工具治理、记忆与上下文、模型路由、质量评测、故障恢复和安全授权。

这些系统会产生大量运行信息。如果没有统一的可观测性设计，问题会逐渐累积：

- 任务失败了，却不知道是路由、上下文、模型还是工具的问题；
- 模型调用费用上升了，却无法定位是哪类任务导致；
- 任务恢复后，无法确认某个外部操作是否已经执行；
- 进化候选效果变差，却缺少改动前后的运行证据；
- 专家之间相互调用，日志各自独立，无法还原完整执行链；
- 日志很多，但真正需要诊断时，关键记录已经被清理。

本专项建议定义为：

**Observability, Diagnostic Evidence & Runtime Intelligence，简称 ODERI。**

它负责统一运行事件、任务追踪、指标、日志、审计关联、诊断证据、异常检测和运行时状态视图，为 RCAE、SHCRG、EQEAG 与进化控制器提供可信的数据基础。

## 一、第一性原理：系统必须能够区分发生了什么、为什么发生、如何证明

这三个问题不能混为一谈。


    <title size="md">第一层：运行事实</title>
    发生了什么？例如工具调用超时、文件写入完成、测试退出码为 1、外部请求状态未知。



    <title size="md">第二层：诊断假设</title>
    为什么可能发生？例如依赖版本不兼容、上下文缺少文件信息、模型选择不合适。



    <title size="md">第三层：验证证据</title>
    什么证据能够支持或否定假设？例如对照运行、工具输出、版本差异、可重复测试和实际状态核验。


例如，工具返回了超时错误，这是运行事实；“网络故障导致超时”只是诊断假设；重新检查网络、查询外部操作状态并确认结果，才可能形成更充分的证据。

ODERI 不应该直接把所有日志交给模型，然后让模型给出一个看似完整的解释。它需要先组织事实、关联上下文和保留证据来源，再由 RCAE 进行诊断。

**运行记录负责证明发生了什么；诊断模块负责解释原因；独立验证负责判断解释是否成立。**

# 二、建立统一事件模型：所有模块都使用同一套关联标识

EvoAgent 的执行链会经过多个模块：

用户请求 → Router → 专家 → Planner → DAG → ReAct → 工具 → 验收 → 记忆与经验处理。

如果每个模块都使用自己的任务编号、日志格式和时间戳，就很难把这些记录关联起来。

建议建立统一的事件信封 `RuntimeEvent`，让各模块以一致的方式记录重要状态变化。

## 2.1 每个事件应包含什么？

建议至少包括以下字段：

| 字段 | 用途 |
|---|---|
| `event_id` | 唯一事件标识，便于去重与追踪 |
| `event_type` | 事件类别，例如任务启动、工具失败、授权拒绝 |
| `occurred_at` | 事件实际发生时间 |
| `recorded_at` | 事件写入持久化存储的时间 |
| `task_id` | 所属任务 |
| `run_id` | 本次任务执行实例 |
| `trace_id` | 跨模块的完整执行追踪标识 |
| `span_id` | 当前执行步骤标识 |
| `parent_span_id` | 上游步骤标识 |
| `component_id` | 产生事件的模块或组件 |
| `component_version` | 产生事件时使用的组件版本 |
| `correlation_id` | 关联的外部请求、业务操作或恢复流程 |
| `severity` | 严重程度 |
| `payload_ref` | 详细证据或大型产物的引用 |
| `schema_version` | 事件结构版本 |

这些字段是建议的统一契约，不代表每条事件都必须填满所有字段。例如，启动事件可能没有父执行步骤；某些内部事件也不会涉及外部请求。

## 2.2 区分任务、运行和执行步骤

这三个 ID 尤其重要。

- `task_id`：表示用户要完成的任务，可以跨多次恢复持续存在。
- `run_id`：表示任务的一次执行尝试。恢复后可以创建新的运行实例。
- `trace_id`：表示一条关联的执行追踪，便于还原跨模块调用链。
- `span_id`：表示其中的一个具体步骤。

例如，同一个任务因为断电而恢复：

- `task_id` 保持不变；
- `run_id` 可以更新；
- 新旧运行之间通过恢复事件与检查点建立关联；
- 原始执行证据仍然保留。

这样既能追踪整个任务，又能分辨恢复前后究竟发生了什么。

## 2.3 事件不能只存在于内存中

关键事件应当及时持久化。

例如：

- 任务进入执行状态；
- 节点开始或完成；
- 工具执行产生副作用；
- 授权通过或拒绝；
- 任务取消；
- 检查点提交；
- 外部操作状态变更；
- 版本发布或回滚。

如果这些事件只写在进程内的缓冲区里，设备突然断电就可能丢失最关键的诊断信息。

但也不意味着每条调试信息都需要同步写入数据库。普通调试日志可以采用缓冲或批量写入；涉及状态、授权和外部副作用的关键事件，则应有明确的持久化保证。

# 三、统一可观测性数据：日志、指标、追踪和审计不能混为一谈

ODERI 需要管理多种运行数据，但每种数据回答的问题不同。


    <title size="md">1. Logs · 日志</title>
    记录具体发生的事情，例如异常消息、工具错误、模型接口错误和状态转换细节。



    <title size="md">2. Metrics · 指标</title>
    记录数量、比例、耗时和资源趋势，例如任务成功率、模型费用、队列长度、磁盘使用率和重试率。



    <title size="md">3. Traces · 执行追踪</title>
    还原一次任务经过了哪些模块、每个步骤花费多长时间、哪些步骤失败或等待。



    <title size="md">4. Audit Records · 审计记录</title>
    记录授权依据、关键配置变更、发布与回滚、安全拒绝和其他需要追责或核验的操作。



    <title size="md">5. Evidence Artifacts · 证据产物</title>
    保存测试报告、代码差异、工具原始输出、媒体检查结果和其他可供后续诊断验证的材料。


这五类数据可以关联，但不能相互替代。

例如，指标显示某个工具的失败率从 2% 上升到 15%，可以发现异常；追踪数据可以定位异常集中在哪些调用路径；日志能提供具体错误；证据产物则帮助判断究竟是工具缺陷、输入错误还是外部依赖问题。

审计记录还有额外的完整性与访问控制要求，不能为了方便诊断而与普通调试日志使用完全相同的保留和删除策略。

## 3.1 不是所有数据都应该高基数地进入指标系统

例如，把每个 `task_id`、文件路径、完整 URL 或用户输入都作为指标标签，会导致指标数量不断增长。

建议采用以下规则：

- 指标标签只使用有限的类别，例如专家类型、错误类型、模型类别；
- 任务 ID 和调用 ID 放在追踪或事件记录中；
- 详细路径、原始请求和大段工具输出放在受控证据存储中；
- 仪表盘通过任务 ID 或追踪 ID 查询具体执行记录。

这样既能保持长期统计的稳定性，又能在需要时下钻到具体任务。

# 四、建立端到端执行追踪：还原一次任务的完整生命周期

可观测性不能停留在“每个模块都有日志”。

它必须能够还原一项复杂任务的完整执行链。

例如，用户要求 EvoAgent 重构一个项目中的模块，完整追踪可能包括：

  {#each [
    ["用户请求","记录请求标识、任务目标版本与必要约束引用。"],
    ["专家路由","记录候选专家、路由结果、规则版本与选择依据。"],
    ["计划制定","记录 Planner 版本、计划版本、预算和验收标准。"],
    ["节点执行","记录 DAG 节点、依赖、输入产物、执行器与尝试次数。"],
    ["模型调用","记录模型版本、输入输出用量、耗时与调用状态。"],
    ["工具调用","记录工具版本、参数摘要、授权判定、结果和副作用状态。"],
    ["质量验收","记录测试、静态检查、验收结果与失败证据。"],
    ["最终交付","记录交付产物引用、最终状态和未解决问题。"]
  ] as item}


        {item[0].slice(0,2)}


        **{item[0]}**
        {item[1]}


    {#if item[0]!=="最终交付"}

    {/if}
  {/each}

这里不要求所有步骤都采用严格串行结构。实际任务 DAG 可能并行执行多个节点，因此追踪需要支持父子关系、并行分支、重试、等待和跨运行恢复。

## 4.1 每个关键决策都应能够追溯

对于模型路由，至少要能回答：

- 当时有哪些候选模型；
- 哪些候选因为能力或约束被过滤；
- 最终选择了哪个模型；
- 使用了哪个路由策略版本；
- 是否发生升级或回退；
- 最终任务质量如何。

对于上下文构建，则需要能够追溯：

- 本次调用使用了哪些信息来源；
- 使用了哪个上下文策略版本；
- 哪些关键事实被纳入；
- 使用了多少输入 Token；
- 是否触发压缩；
- 最终结果是否因信息遗漏而失败。

对于工具执行，则需要知道：

- 调用了哪个工具和版本；
- 执行前的授权结果；
- 实际输入与输出的证据引用；
- 是否产生外部副作用；
- 结果是否已经核验。

这些信息是后续诊断和进化归因的基础。

## 4.2 追踪数据需要控制体积

长任务可能产生数千次模型和工具调用。如果所有原始内容都直接塞进一个追踪记录，存储和查询成本会很高。

建议采用分层追踪：

- 任务级摘要记录总体状态、耗时、成本和关键异常；
- 节点级追踪记录依赖关系与执行结果；
- 调用级追踪记录模型、工具与授权信息；
- 原始输入输出保存在独立的受控证据存储中。

这样，普通查询可以快速查看任务概况，只有需要诊断时才读取大型原始产物。

# 五、可观测性与根因分析：给 RCAE 提供证据，而不是替它下结论

RCAE 的任务是诊断原因。ODERI 的任务是让诊断建立在完整、可追溯的数据之上。

建议建立标准化的诊断证据包 `Diagnostic Evidence Bundle`。

它可以包含：

- 任务与运行标识；
- 失败节点和前置依赖；
- 相关事件与执行追踪；
- 错误类型与原始错误引用；
- 模型、工具、专家和上下文策略版本；
- 相关配置变更；
- 预期结果与实际结果；
- 已尝试的恢复措施；
- 相关测试与验收证据；
- 尚未确认的外部操作状态；
- 数据完整性和证据缺失情况。

证据包不是将所有日志简单打包，而是围绕一个明确的故障问题进行关联与筛选。

## 5.1 诊断必须区分事实、假设与结论

例如，某个编程任务失败：

- 事实：测试退出码为 1；
- 事实：测试日志显示某个模块找不到符号；
- 事实：本次任务使用了新版本的代码分析工具；
- 假设：工具输出格式变化导致 Planner 生成了错误的修改计划；
- 验证方案：对同一输入分别使用旧工具与新工具运行，并比较计划和测试结果；
- 结论：只有在证据支持后，才能将原因归于工具升级。

如果缺少足够证据，诊断结果应标记为“原因未确定”，而不是强制输出一个单一根因。

## 5.2 证据缺失本身也需要被记录

例如，某次工具调用的原始输出已经因保留策略被清理。

系统不应该默默忽略这一事实，而应该告诉 RCAE：

- 该证据曾经存在；
- 当前已不可访问；
- 哪些摘要或相关记录仍然可用；
- 当前诊断的可信程度因此受到什么限制。

这可以避免系统将不完整日志误认为完整事实。

## 5.3 自动诊断必须受资源预算约束

如果每个普通工具错误都自动启动多模型根因分析，诊断成本可能超过任务本身。

建议根据故障严重性、重复次数、影响范围和恢复成本决定是否启动 RCAE：

- 瞬时、可恢复的小错误：优先使用规则和简要记录；
- 重复失败或任务无进展：生成结构化证据包；
- 跨模块故障或系统退化：启动更深入的诊断；
- 涉及权限、数据一致性或外部副作用的异常：优先保护状态并核验，不应只做文字分析。

# 六、运行指标与异常检测：从“发生故障”走向“提前发现退化”

ODERI 不能只在任务失败后收集日志，还应该帮助 EvoAgent 在问题扩大之前发现异常。

建议建立六类指标。

| 指标类别 | 典型指标 |
|---|---|
| 任务质量 | 通过率、失败率、返工率、恢复成功率 |
| 执行效率 | 任务耗时、节点耗时、排队时间、重试次数 |
| 模型成本 | 输入输出 Token、调用费用、升级次数、每个合格任务的总成本 |
| 工具健康 | 成功率、超时率、错误分布、外部依赖可用性 |
| 资源健康 | 内存、磁盘、CPU/GPU、队列长度、数据库延迟 |
| 安全与状态一致性 | 授权拒绝、异常副作用、状态冲突、未知外部操作数量 |

这里需要区分两种异常。

**即时异常**，例如数据库写入失败、磁盘空间不足、授权状态异常，需要快速触发保护措施。

**趋势异常**，例如某个专家的失败率持续上升、平均成本逐渐增加、任务耗时越来越长，可以通过滑动窗口、基线比较和趋势分析发现。

## 6.1 异常检测不应该依赖一个全局阈值

例如，代码编译任务可能通常只需几十秒，而视频生成任务可能需要数分钟甚至更久。

如果所有任务都采用同一个超时阈值，必然会产生大量误报或漏报。

建议按照以下维度建立基线：

- 专家类型；
- 任务类型；
- 模型与工具版本；
- 任务规模或难度；
- 本地与云端执行环境；
- 任务阶段；
- 正常情况下的耗时和资源分布。

阈值可以先使用明确的规则，再随着数据积累逐渐改进。对于样本量不足的类别，应标记为低置信度，不要假装已经拥有可靠基线。

## 6.2 告警必须关联可执行的处理策略

告警不应该只是显示一个红色状态。

例如：

- 磁盘空间接近临界值：启动受控清理，限制新的大型任务；
- 某模型服务持续不可用：熔断相关调用，尝试兼容的替代路径；
- 某工具错误率突然升高：降低调度优先级，必要时隔离工具版本；
- 任务队列持续积压：限制新任务并发，检查资源瓶颈；
- 授权或状态一致性异常：暂停相关副作用操作；
- 同类失败反复出现：生成 RCAE 诊断证据包。

实际处理动作应由对应的治理模块执行，ODERI 负责检测、关联和触发，不应该成为新的、拥有无限操作权限的控制器。

## 6.3 让 SHCRG 观察系统趋势，让 ODERI 提供运行证据

两者职责需要明确区分：

- ODERI 负责采集、关联、查询和整理运行事实；
- SHCRG 负责判断系统健康状态、趋势退化与风险等级；
- RCAE 负责分析故障根因；
- EQEAG 负责判断改进是否有效；
- 进化控制器负责管理候选方案与发布流程。

这样可以避免多个模块各自维护一套互相矛盾的健康指标。

# 七、隐私与日志治理：可观测性不能以泄漏个人数据为代价

对于你的个人智能体，这一点尤其重要。

EvoAgent 可能接触私人文件、代码仓库、聊天内容、账户信息和外部 API 凭据。完整记录所有模型输入输出，虽然方便诊断，却可能让日志变成另一个敏感数据仓库。

因此，建议把**可观测性完整性**与**原始内容保留**分开设计。

## 7.1 默认记录元数据，而不是无限复制原始内容

普通运行记录优先保留：

- 任务标识；
- 模块与版本；
- 输入输出摘要；
- 调用数量与耗时；
- 错误类别；
- 结果状态；
- 受控证据引用。

只有在确有必要、符合授权和保留策略时，才保存完整的原始输入输出。

例如，工具返回一个包含数万行代码的结果，普通日志可以记录文件引用、内容哈希、大小和解析摘要，而不必再复制一份完整代码。

## 7.2 对敏感字段进行结构化脱敏

建议对以下内容采用专门处理：

- API 密钥与访问令牌；
- 密码和会话凭据；
- 个人身份信息；
- 私人文件内容；
- 不必要的完整请求正文；
- 含敏感数据的 URL 参数；
- 外部服务返回的秘密字段。

脱敏应尽可能发生在数据进入普通日志之前，而不是依靠事后清理。

## 7.3 访问控制与删除策略也需要统一

不是所有模块都应该可以读取所有运行证据。

例如：

- 普通仪表盘只显示聚合指标；
- RCAE 读取与当前故障相关的必要证据；
- 安全审计模块读取授权与操作记录；
- 评测系统只读取允许用于评测的数据；
- 凭据管理模块不把秘密内容暴露给普通日志查询接口。

数据保留策略应兼顾诊断价值、隐私要求、存储空间和恢复需要。删除前需要确认该数据不是仍然需要的权威状态、检查点、审计证据或正式产物。

# 八、断网与离线运行：可观测性本身也必须能够恢复

前面已经讨论过 EvoAgent 在断网时如何继续运行，以及恢复联网后如何同步日志和状态。

ODERI 需要为此提供明确机制。

## 8.1 本地优先记录，恢复后再同步

对于个人设备，建议：

- 任务状态、关键事件和必要的审计记录优先保存在本地；
- 网络不可用时继续记录允许离线产生的事件；
- 事件具有稳定 ID 和本地序列信息；
- 恢复联网后按关联关系与版本进行同步；
- 同步端支持重复事件去重；
- 冲突时保留原始事实，交由对应的状态治理机制处理。

需要注意，**事件可以重复投递，但关键状态不能因此重复应用**。

因此，接收方应通过事件 ID、幂等键或状态版本识别重复记录。对于不同设备或不同来源产生的事件，还应保留来源和时间信息，而不是简单地按最后写入时间覆盖所有内容。

## 8.2 区分发生时间和记录时间

设备断网后，某个事件可能在上午发生，到下午恢复联网时才被上传。

如果只根据服务器接收时间排序，就可能错误还原事件顺序。

因此，应同时记录：

- 本地观察到的发生时间；
- 实际持久化时间；
- 上传或接收时间；
- 本地单调序列或其他可用的顺序信息。

不同设备的系统时钟可能不一致，所以跨设备事件的顺序不能只依赖墙上时钟；还需要结合任务依赖、事件序列和因果关联进行判断。

## 8.3 日志同步失败不能阻止本地安全运行

如果远端日志接收服务不可用，EvoAgent 不应因此丢失本地必要证据。

本地事件存储需要有明确的容量上限、优先级和保留策略。

当空间不足时，系统应优先保护权威状态、关键审计和恢复证据，并限制非必要的详细调试日志。若连关键状态都无法可靠持久化，则应进入受控降级，而不是继续执行可能产生不可恢复副作用的操作。

# 九、统一运行状态视图：让用户知道系统现在到底在做什么

可观测性最终还需要服务于使用者。

对于个人 EvoAgent，不一定需要复杂的运维大屏，但应该有一个清晰的运行状态界面或命令入口，能够回答以下问题：

- 当前有哪些任务正在执行？
- 哪些任务在等待模型、工具、网络或用户确认？
- 每个任务已经执行到哪个阶段？
- 哪些工具或模型目前不可用？
- 当前成本、磁盘与资源使用情况如何？
- 最近发生了哪些异常？
- 是否有任务处于恢复中或状态未知？
- 哪些候选进化版本正在评测？
- 当前稳定版本是什么？
- 最近一次发布或回滚是否成功？

## 9.1 按角色呈现不同视图

虽然这是一个个人系统，但仍然可以区分几种逻辑视图：


    **任务视图**

    显示任务状态、执行步骤、产物、预算、失败原因和恢复进度。



    **系统健康视图**

    显示模型、工具、数据库、资源、队列和存储的健康状态。



    **诊断视图**

    显示故障证据、诊断假设、已完成检查、缺失证据和建议的验证步骤。



    **进化视图**

    显示候选版本、评测结果、质量变化、成本变化、发布状态和回滚记录。


这些视图应当从同一套权威事件与指标中构建，避免每个界面各自维护不同的状态副本。

## 9.2 诊断报告应该给出证据，不只是结论

例如：

**问题：编程任务连续失败。**

- 失败节点：测试执行；
- 失败次数：3；
- 主要错误：找不到符号；
- 相关变更：代码分析工具版本升级；
- 已核验事实：测试输入相同，工具输出结构发生变化；
- 当前假设：新工具输出与 Planner 预期 Schema 不兼容；
- 尚缺证据：尚未完成旧版本与新版本的对照运行；
- 建议下一步：在隔离工作区进行版本对照测试。

这比直接显示“根因是工具升级”更可信，也更便于后续评测系统验证。

# 十、与其他专项的协作边界

ODERI 是运行证据的基础设施，但不应该接管其他模块的全部职责。

| SIEC | 统一事件、关联标识和状态变化证据 | 系统间事件与状态关联 |
| SHCRG | 运行指标、趋势与异常数据 | 健康判断、风险分级和退化治理 |
| RCAE | 故障轨迹、相关版本、证据包 | 根因分析、假设生成与验证方案 |
| EQEAG | 实验运行数据、任务追踪和版本关联 | 质量评测、对照实验和发布资格 |
| L3RG | 中断、恢复、数据一致性和资源证据 | 系统生命周期、检查点与恢复 |
| SBAAG | 授权判定、拒绝事件和操作记录 | 权限策略、安全门禁和行动治理 |
| CERG | 上下文构建、压缩、检索与 Token 数据 | 上下文质量和预算策略 |
| MRCRG | 模型选择、升级、回退与实际用量 | 模型路由与推理资源分配 |
| TRCPG | 工具调用、错误、执行结果和版本 | 工具契约、运行时治理与插件管理 |

核心原则是：**ODERI 负责提供可追溯的运行事实，不负责替所有模块做决策。**

# 十二、下一专项：系统集成、协议治理与跨模块一致性

到目前为止，我们已经分别设计了 EvoAgent 的专家、任务编排、工具、记忆、上下文、模型路由、评测、恢复、安全与可观测性。

但随着这些专项逐渐完善，会出现一个新的架构风险：

**每个模块单独设计得很好，并不意味着它们组合起来就一定可靠。**

例如：

- Planner 使用一种任务状态格式，恢复系统使用另一种；
- 工具运行时认为调用已经成功，但 DAG 节点仍然处于运行中；
- 记忆系统保存了新版本经验，上下文缓存却仍然使用旧版本；
- 安全模块撤销了授权，但后台执行器仍然持有旧权限；
- 进化控制器发布了新策略，正在执行的长任务却意外切换到新配置；
- 日志系统记录了事件，但任务状态库没有完成相应更新。

这些问题不一定来自任何单个模块的算法缺陷，而可能来自模块之间缺少明确的协议、状态所有权和一致性规则。

因此，下一专项建议定义为：

**System Integration, Protocol Governance & Cross-Module Consistency，简称 SIPG。**

重点研究：

1. 如何建立统一的模块接口和数据契约；
2. 如何明确每类数据的唯一权威来源；
3. 如何管理任务状态、事件、工具结果和记忆之间的一致性；
4. 如何设计跨模块调用、事件投递、重试与幂等协议；
5. 如何处理模块版本不兼容和接口演进；
6. 如何保证任务在不同模块之间传递时不丢失目标、约束、预算与权限；
7. 如何防止共享状态被多个模块无序修改；
8. 如何让长任务绑定明确的配置快照，而不被意外升级影响；
9. 如何建立统一错误模型、取消语义和恢复协议；
10. 如何验证各模块组合后的整体行为，而不仅是单元测试结果；
11. 如何让插件和领域能力包在统一契约下接入系统；
12. 如何在个人设备资源有限的情况下实现可靠的模块协作，而不必引入过度复杂的分布式架构。

这一专项很重要，因为 EvoAgent 的复杂度不只来自模块数量，更来自它们之间的交互关系。

我们的目标不是让所有模块都依赖一个巨大的中心控制器，而是建立明确的接口、状态所有权、协议和验证机制，让每个模块能够独立演进，同时保证整个系统不会因为局部变化而失去一致性。

**下一轮将从第一性原理出发，研究模块边界、状态所有权与跨模块协议，进一步确定 EvoAgent 的统一运行契约。**
