# EvoAgent 第三十四专项：系统集成、协议治理与跨模块一致性

这一轮要解决的是 EvoAgent 从一组设计完善的模块，真正成为一个整体系统时最容易出现的问题：**模块各自正确，组合之后却不一定正确。**

你之前已经明确了 EvoAgent 的核心方向：

- 统一任务入口与多层路由；
- 共享通用内核与独立领域专家；
- Planner、ReAct 与任务 DAG 协同；
- 记忆、上下文和专业能力独立治理；
- 模型路由与工具运行时统一管理；
- RCAE 负责根因分析，进化控制器负责改进；
- EQEAG 负责独立评测；
- L3RG 负责长期运行与故障恢复；
- SBAAG 负责安全授权；
- ODERI 负责可观测性。

现在的问题是，这些模块如何使用同一套运行规则协作，又不互相越权或产生状态冲突。

本专项建议定义为：

**System Integration, Protocol Governance & Cross-Module Consistency，简称 SIPG。**

它负责统一接口契约、数据所有权、模块通信、状态转换、事件交付、版本兼容、跨模块事务边界与集成验证。

## 一、第一性原理：先明确谁有权决定一件事，再设计模块如何通信

假设 EvoAgent 正在执行一个复杂编程任务。

- Planner 认为某个节点已经完成；
- 工具运行时认为工具调用成功；
- 验收器发现结果不符合要求；
- DAG 调度器准备启动下一个节点；
- 恢复系统同时检测到该节点存在未提交的检查点。

如果没有明确的状态所有权，每个模块都可能修改任务状态，最终产生互相矛盾的结论。

因此，SIPG 的第一原则是：

**每一种权威状态都必须有明确的所有者；其他模块只能通过定义好的命令或事件请求改变它。**

这不意味着所有数据都必须存储在一个数据库中，也不意味着必须建立一个庞大的中心服务。它意味着，任何关键状态都不能出现两个彼此独立、都自认为最终权威的写入者。

# 三、明确状态所有权：谁是最终权威？

建议为 EvoAgent 建立一张全局状态所有权表。

| 状态或数据 | 权威所有者 | 其他模块的职责 |
|---|---|---|
| 用户请求与任务身份 | 任务入口与任务注册模块 | 提供请求或引用任务 |
| 任务生命周期与 DAG 节点状态 | TLCIG | 请求状态变更、订阅任务事件 |
| 实际工具执行结果 | 工具运行时及其执行记录 | 引用结果，不能自行伪造工具成功 |
| 模型能力与可用性 | 模型注册表及健康状态机制 | 查询能力、报告调用结果 |
| 当前有效授权 | SBAAG | 请求授权、执行前核验 |
| 上下文构建结果 | CERG | 消费已构建的上下文及其版本信息 |
| 持久化记忆与经验 | MEEG | 提交候选记忆或经验，遵守验证与版本规则 |
| 运行事实与执行追踪 | ODERI | 产生事件、查询证据，不随意改写历史事实 |
| 健康状态与风险等级 | SHCRG | 接收指标和事件，提供健康判定 |
| 进化候选与发布资格 | 进化控制器及 EQEAG | 提交候选、评测结果与发布请求 |
| 正式配置与版本引用 | 配置及发布治理模块 | 读取固定版本或请求正式切换 |

这张表定义的是逻辑所有权，不是部署拓扑。

例如，任务状态和执行事件可以存储在同一个 SQLite 数据库中，但任务状态仍然由 TLCIG 的状态转换逻辑管理，ODERI 不能仅凭一条日志就把失败任务改成成功。

同样，工具返回成功不等于任务成功。工具运行时只对实际工具调用负责，任务是否完成仍然需要由任务协调与验收流程决定。

## 4.1 统一的调用结果不能只有 `success: true`

建议统一使用带有明确语义的结果对象，例如：

```json
{
  "contract_version": "1.0",
  "operation_id": "op-123",
  "status": "SUCCEEDED",
  "result_ref": "artifact-456",
  "error": null,
  "side_effect_state": "CONFIRMED",
  "retryable": false
}
```

这是示意结构，不是要求所有模块使用完全相同的字段。

关键在于结果必须区分：

- 操作已经成功；
- 操作已经明确失败；
- 操作仍在执行；
- 操作被取消；
- 操作状态未知；
- 操作成功，但副作用尚未核验。

例如，网络请求超时不能自动解释为操作失败。服务器可能已经接收请求，只是响应没有到达本地。

如果接口只返回 `success: false`，上层很可能会直接重试，导致重复付费、重复提交或重复修改文件。

## 4.2 错误分类必须跨模块统一

建议定义统一错误类别，并允许模块附加领域专属错误码。

| 错误类别 | 含义 | 默认处理方向 |
|---|---|---|
| `VALIDATION_ERROR` | 输入或输出不符合契约 | 修正数据，不盲目重试 |
| `AUTHORIZATION_ERROR` | 缺少或超出授权 | 请求授权或停止操作 |
| `CAPABILITY_ERROR` | 当前模型或工具不支持所需能力 | 重新路由或调整计划 |
| `TRANSIENT_ERROR` | 短暂故障 | 有界重试 |
| `TIMEOUT_UNKNOWN` | 超时，操作结果不确定 | 先核验，再决定是否重试 |
| `VERSION_INCOMPATIBLE` | 接口或数据版本不兼容 | 协商版本、适配或拒绝执行 |
| `RESOURCE_EXHAUSTED` | 内存、磁盘、预算或并发资源不足 | 降级、排队或停止 |
| `STATE_CONFLICT` | 当前状态与请求不兼容 | 重新读取权威状态 |
| `INTEGRITY_ERROR` | 数据完整性或关键证据校验失败 | 隔离并进入恢复流程 |
| `INTERNAL_ERROR` | 未分类的内部错误 | 保留证据并按策略升级诊断 |

这套分类应该用于任务、工具、模型、记忆、上下文和评测模块，而不是让每个模块各自发明一套完全不同的错误语义。

# 五、命令与事件：必须分清“想做什么”和“已经发生什么”

这是跨模块一致性的核心。

例如，Planner 希望启动某个 DAG 节点，这是一条命令；任务协调器接受请求并将节点状态更新为运行中，才是已经发生的状态变化。

建议统一区分两类消息。

## 5.1 命令：请求系统执行动作

命令通常具有明确的目标与执行条件，例如：

- `CreateTask`
- `StartNode`
- `CancelTask`
- `RequestAuthorization`
- `ExecuteTool`
- `PublishCandidate`
- `CreateCheckpoint`

命令需要经过负责该状态或操作的模块验证。命令被发送，不代表命令已成功执行。

## 5.2 事件：记录已经发生的事实

事件则描述系统确认发生了什么，例如：

- `TaskCreated`
- `NodeStarted`
- `AuthorizationGranted`
- `ToolExecutionCompleted`
- `CheckpointCommitted`
- `CandidateEvaluated`
- `ReleaseRolledBack`

事件应该由掌握相应事实的模块产生。

例如，任务协调器可以产生 `NodeCompleted` 事件，但前提是节点已经通过规定的完成条件。模型自己在文本中说“任务完成”，不能直接成为权威事件。

## 5.3 事件消费者必须支持重复投递

在本地系统中，即使不使用消息队列服务，也可能因为进程重启、事务重试或同步失败而重复处理事件。

因此，每个事件应有稳定的 `event_id`，消费者应根据业务语义实现幂等处理。

但要注意：去重不能简单地把所有相同内容的事件删除。两次合法的工具调用可能具有完全相同的输入，却代表两次不同的操作。

正确做法是区分：

- 事件身份；
- 业务操作身份；
- 执行尝试身份；
- 幂等键；
- 事件来源。

这些标识各有用途，不能互相替代。

# 六、跨模块事务：不要假设整个 EvoAgent 能使用一个大事务

EvoAgent 的一次复杂任务可能同时涉及：

- SQLite 任务数据库；
- 本地文件系统；
- 模型 API；
- 工具执行器；
- 外部生成服务；
- 记忆存储；
- 事件记录。

这些资源无法天然参与同一个原子事务。

例如，任务节点需要生成代码文件、运行测试、保存测试报告，并更新任务状态。即使数据库事务完全可靠，也不能自动保证文件写入、子进程执行和数据库更新同时成功或同时回滚。

建议采用“局部事务 + 显式操作状态 + 恢复核验”的设计。

## 6.1 以文件产物提交为例

建议流程如下：

  {#each [
    ["1. 准备产物","在受控临时位置生成文件，并验证内容和预期路径。"],
    ["2. 完整性检查","计算必要的内容哈希，检查文件大小、格式与约束。"],
    ["3. 原子提交产物","在支持原子重命名的同一文件系统内，将文件提交到正式产物位置。"],
    ["4. 提交权威记录","在数据库事务中登记产物引用、状态和相关事件。"],
    ["5. 完成核验","确认数据库引用的文件存在且完整，节点才进入可验收状态。"]
  ] as item}


        {item[0].split(".")[0]}


        **{item[0].slice(item[0].indexOf(" ") + 1)}**
        {item[1]}


    {#if item[0]!=="5. 完成核验"}

    {/if}
  {/each}

这只是建议的基本流程。实际实现需要处理每一步崩溃的情况。

例如，文件已经提交，但数据库事务未完成，恢复程序就应通过操作记录、文件哈希和提交标识判断它是有效产物、孤儿文件还是未完成操作，而不是盲目删除或覆盖。

## 6.2 外部操作使用 Saga 式恢复思路

对于无法参与本地事务的外部操作，可以使用 Saga 式的步骤记录与补偿策略。

例如，视频生成工作流：

1. 预留任务预算；
2. 向外部服务提交生成请求；
3. 保存外部任务 ID；
4. 查询生成状态；
5. 下载产物；
6. 本地验收；
7. 提交最终任务结果。

如果中间步骤失败，应根据当前状态决定是重试、查询、等待、补偿还是人工介入。

但补偿操作不一定能够真正撤销原操作。例如，已经产生的云端费用不能靠删除本地任务记录消除。

因此，系统必须明确记录哪些步骤可以补偿、哪些只能核验，以及哪些副作用不可逆。

# 七、统一任务状态协议：Planner、DAG、ReAct 与工具运行时如何协同

前面已经讨论过专家、Plan、ReAct 和任务 DAG 的关系。SIPG 需要把这些概念转化成统一的运行协议。

建议明确：

- **专家**负责领域判断与专业策略；
- **Planner**负责提出或调整计划；
- **DAG 调度器**负责依赖关系、节点调度与执行资格；
- **ReAct 循环**负责局部观察、推理和下一步行动；
- **工具运行时**负责实际执行工具调用；
- **验收器**负责验证产物是否满足要求；
- **任务协调器**负责权威任务状态与生命周期。

这些模块不能互相替代。

## 7.1 统一节点生命周期

建议一个 DAG 节点采用如下状态：

  {#each [
    ["PENDING","等待依赖或调度条件满足"],
    ["READY","依赖满足，可以申请执行"],
    ["RUNNING","执行器已获得执行资格"],
    ["WAITING","等待外部结果、用户授权或资源恢复"],
    ["VERIFYING","结果已产生，正在核验"],
    ["SUCCEEDED","满足完成条件并提交了有效结果"],
    ["FAILED","已经确定失败，且不再自动重试"],
    ["CANCELLED","节点已取消"],
    ["NEEDS_RECONCILIATION","实际执行状态与权威记录不一致，需要核验"]
  ] as item}


        {item[0]}


        {item[1]}


    {#if item[0]!=="NEEDS_RECONCILIATION"}

    {/if}
  {/each}

这是建议的统一状态集合。正式实现时，可以根据节点类型增加状态细节，但不能破坏基础语义。

特别需要区分：

- 工具调用成功；
- 节点执行完成；
- 节点验收通过；
- 整个任务完成。

例如，代码生成工具已经成功写入文件，但测试还没有运行，这个节点可能已经完成执行，却尚未完成验收。

如果系统把这些状态都叫作 `SUCCESS`，就会在复杂工作流中产生大量歧义。

## 7.2 状态转换必须有明确的守卫条件

例如，`RUNNING → SUCCEEDED` 不应由任意模块直接设置。

它至少需要满足：

- 执行结果已提交；
- 必要产物已经登记；
- 节点完成条件已经满足；
- 不存在未解决的关键副作用状态；
- 当前任务与节点状态版本匹配；
- 对应的完成事件已经按要求持久化。

而 `RUNNING → NEEDS_RECONCILIATION` 则适用于执行器异常退出、结果记录缺失或外部操作状态未知等情况。

这能防止系统仅凭某个模块的局部判断就跳过关键验证步骤。

## 7.3 ReAct 循环只能在节点授权范围内行动

ReAct 可以根据观察动态调整下一步行动，但其工具调用仍必须受到：

- 当前任务目标；
- 节点输入输出契约；
- 可用工具能力；
- 授权范围；
- 预算限制；
- 停止条件；
- 当前节点状态；

的约束。

如果 ReAct 发现原计划不可行，可以请求 Planner 重新规划，但不能自行绕过 DAG 调度器、创建未授权的外部操作或修改权威任务状态。

这就是灵活推理与可靠流程编排之间的边界。

# 八、配置与版本快照：长任务不能被后台进化意外改变

EvoAgent 会持续进化，模型路由、专家策略、上下文策略和工具版本都可能更新。

但一个已经开始执行的长任务，不应该因为后台发布了新版本，就在执行过程中自动混用新旧配置。

建议为每次任务运行建立不可变的 `ExecutionManifest`，记录本次执行使用的配置快照。

至少包括：

- 任务目标和约束版本；
- 专家策略版本；
- Planner 与 DAG 版本；
- ReAct 执行策略版本；
- 模型路由策略版本；
- 模型和适配器版本；
- 工具与能力包版本；
- 上下文策略版本；
- 记忆快照或必要的记忆引用；
- 验收规则版本；
- 预算和授权策略引用；
- 运行环境与关键依赖版本。

## 8.1 运行中升级采用显式切换

建议区分三种操作：

- **新任务采用新版本：** 默认推荐方式；
- **当前任务继续使用旧快照：** 保障执行语义稳定；
- **当前任务迁移到新版本：** 必须执行兼容性检查、状态迁移与重新验收。

对于长时间等待的任务，旧模型或工具可能已经不可用。此时可以提出迁移方案，但应当记录变更原因、影响范围与重新验证要求。

## 8.2 不要冻结所有数据，只冻结决定执行语义的关键版本

如果每次任务都复制全部模型文件、工具文件和记忆数据，会造成严重的存储浪费。

更合理的方式是使用不可变版本引用与内容哈希。

对于体积很大的模型或工具包，可以保存版本 ID、来源和校验信息，而不重复复制文件。

对于记忆系统，则可以冻结任务开始时的必要快照，或记录可重现的检索结果与来源版本。具体采用哪种方式，取决于任务对可重复性的要求。

# 九、模块版本与接口演进：允许进化，但不能破坏契约

EvoAgent 的模块会持续迭代，因此接口不能只设计一次。

建议区分三种版本：

- **契约版本：** 输入输出、错误语义和状态转换规则；
- **实现版本：** 模块代码或策略的具体版本；
- **数据版本：** 持久化结构、事件 Schema、检查点和产物格式。

三者变化速度不同，不能混成一个版本号。

## 9.1 契约变更分级

| 变更类型 | 示例 | 建议处理 |
|---|---|---|
| 兼容性新增 | 增加可选字段 | 保持旧调用可用，验证默认行为 |
| 语义修正 | 修正错误码含义 | 评估所有消费者的行为变化 |
| 破坏性变更 | 删除必填字段、改变状态语义 | 新契约版本、适配或受控迁移 |
| 数据迁移 | 修改检查点格式 | 提供迁移器、回滚方案和兼容性测试 |
| 能力变化 | 工具不再支持某种操作 | 更新能力声明，阻止不兼容任务继续执行 |

不能因为两个模块使用相同的 JSON 结构，就认为它们一定兼容。

真正的兼容性还涉及字段含义、默认值、错误处理、幂等性、权限要求和状态转换。

## 9.2 使用适配器，而不是到处写兼容分支

如果某个旧工具仍在被长期任务使用，而新版本采用了不同接口，可以在边界提供版本适配器。

这样，内部模块仍然使用统一契约，而适配器负责转换旧格式、检查能力差异和映射错误。

适配器本身也需要版本管理与测试，不能成为绕过安全或一致性规则的隐蔽通道。

## 9.3 过期接口必须有明确的退役流程

建议一个接口从旧版本迁移到新版本时，经历：

1. 发布新契约；
2. 提供适配器或迁移工具；
3. 检测仍在使用旧接口的模块；
4. 迁移并运行集成测试；
5. 确认没有活动任务依赖旧契约；
6. 正式停止旧接口；
7. 保留必要的恢复兼容路径。

对于个人设备系统，不必建设复杂的服务注册中心，但仍然需要保留接口版本清单和依赖关系。

# 十、跨模块集成测试：单元测试通过，不等于系统正确

这是 SIPG 必须建立的另一项能力。

每个模块的单元测试，只能验证它在特定输入下的局部行为。跨模块问题通常出现在状态转换、失败恢复、版本差异和并发交互中。

建议建立五类集成测试。

  {#each [
    ["1. 契约集成测试","验证模块输入输出、错误映射、版本兼容与权限要求是否一致。"],
    ["2. 工作流集成测试","验证 Router、专家、Planner、DAG、ReAct、工具和验收器之间的完整执行语义。"],
    ["3. 故障注入测试","模拟超时、断网、进程退出、事件重复投递和数据库事务中断。"],
    ["4. 并发与竞态测试","验证取消与完成同时发生、多个节点竞争资源、授权撤销与工具调用并发等场景。"],
    ["5. 版本组合测试","验证稳定版本与候选版本、旧检查点与新运行时、不同工具和模型适配器组合是否兼容。"]
  ] as item}

      <title size="md">{item[0]}</title>
      {item[1]}

    {#if item[0]!=="5. 版本组合测试"}

    {/if}
  {/each}

## 10.1 建立跨模块不变量

不变量比单个用例更有价值，因为它们描述系统在各种执行路径下都必须满足的条件。

建议至少定义以下不变量：

1. 未获授权的操作不得进入实际执行阶段。
2. 未完成必要验收的节点不得被标记为最终成功。
3. 任务终态不能被普通事件重复投递随意覆盖。
4. 同一个业务操作的重试不得无依据地产生重复副作用。
5. 子任务权限不得超过父任务与系统策略共同允许的范围。
6. 任务执行快照必须明确标识实际使用的配置版本。
7. 事件缺失或延迟不能被自动解释为对应操作从未发生。
8. 无法确认的外部操作必须保留未知状态，直至核验或进入明确的人工处理流程。
9. 关键状态变化必须有可追溯的事件或持久化记录。
10. 候选进化不能绕过独立评测与发布治理直接覆盖稳定版本。
11. 权威状态存储无法保证可靠提交时，禁止继续执行依赖该持久化保证的高风险操作。
12. 同一节点的并发执行必须通过租约、版本检查或其他机制防止不受控的重复写入。

这些不变量应当转化成自动化测试，而不仅仅是文档中的原则。

## 10.2 对关键状态机采用属性测试

例如，随机生成任务状态转换序列，检查是否会出现：

- 已取消的任务被普通事件改回运行中；
- 未验收的节点直接进入成功状态；
- 任务已经终止，却仍然启动新的副作用操作；
- 恢复过程同时创建两个有效执行器；
- 旧版本执行器在失去租约后继续写入结果。

对于状态机和并发协调机制，可以采用属性测试、模型检查或基于状态转移的随机测试。具体技术应根据实现语言和工具链选择，不需要为了采用某种测试框架而改变整个系统架构。

# 十一、个人设备部署：统一协议不等于拆分微服务

这是结合你此前明确的个人设备战略，特别需要强调的一点。

SIPG 研究的是逻辑模块如何协作，不是要求每个模块都部署成一个独立服务器。

对于个人电脑、Mini PC 或微型 Linux 主机，我建议采用：

**模块化单体为主、少量独立执行进程为辅、统一协议贯穿所有边界。**


    **EvoAgent Core**
    任务协调、路由、Planner、DAG、记忆、上下文、模型路由、授权和配置治理。



    **Shared Contracts**
    统一数据结构、错误模型、事件类型、状态转换与版本规则。



    <grid-item>

        **Local Storage**
        SQLite、事件记录、检查点、索引与产物引用。

    </grid-item>
    <grid-item>

        **Execution Workers**
        受限代码执行、媒体处理、外部工具与独立子进程。

    </grid-item>



    **External Adapters**
    云端模型、搜索、媒体生成和其他外部服务的适配与状态核验。


这是一种逻辑部署示意，不要求固定的进程数量。

## 11.1 为什么核心模块优先采用模块化单体？

对于个人设备，它有几个实际优势：

- 部署和升级简单；
- 数据库事务边界更容易管理；
- 调试时更容易还原调用链；
- 不需要维护额外的服务发现、网络通信和分布式一致性基础设施；
- 资源消耗更可控。

但模块化单体不代表所有代码都可以互相访问内部状态。模块之间仍然应该通过公开接口协作，不能直接修改其他模块的私有数据结构。

## 11.2 哪些组件值得独立进程运行？

以下场景更适合采用独立进程或隔离执行器：

- 运行用户代码或不可信代码；
- 容易崩溃或消耗大量内存的工具；
- FFmpeg 等媒体处理任务；
- 需要独立资源限制的模型或推理进程；
- 需要与主程序隔离权限的外部插件。

这些边界能够提高故障隔离能力，也有助于落实 SBAAG 的实际权限约束。

## 11.3 如果以后接入独立服务器怎么办？

只要模块契约、事件模型、状态所有权和幂等协议设计得当，未来就可以把部分组件迁移到远端。

但不能认为只要把函数调用改成 HTTP，就完成了分布式化。

远端部署还需要处理网络分区、认证、事件投递、重复请求、远程任务状态、数据同步和版本协商。

因此，当前最有价值的投资是先定义清楚逻辑边界和协议，而不是提前建设一套复杂的微服务基础设施。

# 十三、下一专项：多专家协作、任务分解与协同决策治理

我们已经设计了专家独立运行、任务 DAG、Planner、ReAct 和统一模块契约。

接下来还需要深入解决一个问题：

**当多个专家都能解决任务的一部分时，系统如何判断该由谁做、做多少、何时协作，以及如何防止专家之间重复劳动、相互矛盾或无限转交任务？**

例如，一个复杂的 AI 漫剧制作任务可能同时需要：

- 编剧专家；
- 分镜专家；
- 图像生成专家；
- 视频生成专家；
- 配音专家；
- 编程与媒体处理专家；
- 质量验收专家。

这不是简单地将任务路由给一个专家就能解决的。系统需要决定任务如何分解、依赖如何建立、专家如何交换产物、意见冲突如何解决，以及在哪个阶段停止继续细分任务。

下一专项建议定义为：

**Multi-Agent Collaboration & Task Decomposition Governance，简称 MACTDG。**

重点研究：

1. 如何判断一个任务是否需要多个专家，而不是单专家即可完成；
2. 如何决定任务分解粒度，避免过度拆分和过度耦合；
3. 如何根据依赖关系构建任务 DAG，而不是预先规定所有固定流程；
4. 如何为每个子任务选择负责专家与协作专家；
5. 如何让专家共享必要上下文，同时保持领域记忆与权限隔离；
6. 如何定义专家交接协议、产物契约和验收责任；
7. 如何处理专家意见冲突、重复工作和互相推诿；
8. 如何限制递归分解深度、协作次数、预算与总耗时；
9. 如何判断协作带来的收益是否超过额外成本；
10. 如何在某个专家失败、离线或能力不足时重新分配任务；
11. 如何避免多专家相互强化同一个错误结论；
12. 如何将成功的协作模式沉淀为可评测、可版本化的工作流，而不是仅仅记住一次成功的聊天过程。

这一专项会进一步把你最初设想的“多个领域专家组成一个可持续进化的智能体”落到真正的协同执行机制上。

关键目标是：**不是让专家越多越好，而是让每个专家在正确的任务边界内发挥作用，并让整体协作产生单个专家难以达到的效果。**
