# EvoAgent 第五十七专项：知识资产、技能生命周期与能力复用治理

<text color="secondary" size="sm">KCLG · Knowledge & Capability Lifecycle Governance</text>

前面我们已经讨论了 EvoAgent 如何执行任务、组织专家、管理记忆、发现故障、恢复运行、优化资源，以及独立评估自己的改进。

现在进入一个决定系统能否长期成长的关键问题：

**智能体每完成一次任务，到底应该留下什么？这些经验怎样变成可复用的能力，又怎样避免错误经验、过期技能和重复资产不断污染系统？**

这是一个比简单的“记忆系统”更大的问题。

假设 EvoAgent 成功完成了一次复杂的代码重构。

它可能留下：

- 用户对代码风格的偏好；
- 项目当前使用的技术栈；
- 一次任务的执行记录；
- 某个错误的根因分析；
- 一种有效的 AST 分析方法；
- 一套通过测试的代码重构工作流；
- 一个可复用的代码分析技能；
- 一组用于防止同类错误再次出现的回归测试。

这些东西都来自同一次任务，但它们不是同一种资产。

如果全部放进一个共享记忆库，系统很容易把一次偶然成功误认为通用规律，把某个项目的特殊约束误认为所有项目的规则，甚至让未经验证的执行结果直接变成正式技能。

因此，KCLG 的任务不是简单地增加存储，而是建立一套完整的**知识与能力资产治理体系**。

它需要回答：

1. 一次执行完成后，哪些信息应该保留？
2. 哪些经验可以沉淀为技能，哪些只能作为案例？
3. 如何判断新技能应该创建、扩展现有技能，还是直接复用已有能力？
4. 如何验证一次成功是否具有可复用性？
5. 如何防止错误经验进入全局知识库？
6. 如何管理技能的版本、依赖、适用范围与兼容性？
7. 如何淘汰已经过时、重复或低价值的能力？
8. 如何让领域专家共享有价值的经验，同时保持各自的专业边界？
9. 如何让记忆、技能、工作流和评测案例之间形成可追溯的关联？
10. 如何让 EvoAgent 在长期运行后能力越来越强，而不是资产越来越多、系统越来越混乱？

本专项的核心原则是：

**执行经验不等于知识，知识不等于技能，技能不等于经过验证的能力；每一次升级，都必须经过与其风险和适用范围相匹配的验证。**

# 一、第一性原理：不是所有成功都值得学习

先看三个场景。

<box border radius="xl" padding={3} gap={3}>
  <box gap={1}>
    <title size="md">场景 A：偶然成功</title>
    <text color="secondary" size="sm">智能体尝试了五种方法，第五种碰巧成功，但无法解释原因，也没有可靠测试。</text>
    <text>合理处理：保留执行记录和待验证假设，不直接升级为正式技能。</text>
  </box>
  <divider color="subtle"/>
  <box gap={1}>
    <title size="md">场景 B：可复现的方法</title>
    <text color="secondary" size="sm">智能体通过 AST 分析定位代码问题，方法可以在多个相似项目中复现，并且通过独立测试。</text>
    <text>合理处理：建立候选技能，明确适用条件，经过评测后再正式发布。</text>
  </box>
  <divider color="subtle"/>
  <box gap={1}>
    <title size="md">场景 C：项目专属经验</title>
    <text color="secondary" size="sm">某个项目的构建流程必须使用特定版本的依赖和特殊配置。</text>
    <text>合理处理：保存到该项目的知识与能力命名空间，不能直接推广为全局默认规则。</text>
  </box>
</box>

这三个场景的关键区别，不是有没有成功，而是证据强度、可复现性和适用范围不同。

## 1.1 建立四个核心区分

| 概念 | 定义 | 典型例子 |
|---|---|---|
| 记忆 Memory | 为未来任务保留有用的信息 | 用户偏好、项目背景、历史决策 |
| 知识 Knowledge | 有来源、适用范围和可信状态的信息 | API 文档、经过核验的技术事实 |
| 技能 Skill | 可调用、具有明确输入输出契约的操作能力 | AST 分析器、代码格式检查器 |
| 工作流 Workflow | 将多个步骤、依赖和验收规则组织成可执行流程 | 代码修改、测试、审查与发布流程 |

还需要第五种资产：**评测案例 Evaluation Case**。

它负责记录任务输入、预期行为、验证条件和实际结果，用于检验知识、技能或工作流是否真正有效。

这五类资产之间可以相互关联，但不能混为一谈。

例如，一个失败案例可以形成知识假设，也可以成为回归测试；只有当解决方法被明确实现、具有稳定契约并通过相应验证后，才适合升级为技能。

## 1.2 为什么不能直接把所有历史对话变成长期记忆？

因为历史对话可能包含：

- 临时假设；
- 错误结论；
- 已经失效的需求；
- 用户后来推翻的决策；
- 某个任务的特殊条件；
- 外部文件中未经验证的指令；
- 与当前任务无关的细节。

如果系统将所有内容一视同仁地保存并检索，记忆越多，未必越聪明，反而可能增加冲突、噪声和错误引用。

因此，KCLG 需要在资产产生、验证、晋升、使用、更新和退役的每个阶段进行治理。

它不是新的领域专家，也不负责执行所有技能，而是治理资产的身份、来源、版本、验证状态、依赖关系与生命周期转换。

这样可以避免建立一个包揽所有事情的“超级知识智能体”。

# 三、资产分类与命名空间：什么应该共享，什么不应该共享？

这是整个 KCLG 最重要的设计之一。

EvoAgent 具有通用智能体、编程专家、漫剧专家、研究专家等多个领域能力。它们需要共享部分知识，但不能把所有经验混在一起。

建议采用**全局共享、领域共享、项目专属、任务临时**四级资产命名空间。

## 3.1 四级命名空间

    ["G1 · 领域共享","编程、漫剧、研究、数据分析等领域的专业方法、技能、工作流和评测集。"],
    ["G2 · 项目专属","特定代码仓库、某个漫剧项目、某个长期研究项目的配置、约束与专属资产。"],
    ["G3 · 任务临时","当前任务的草稿、中间结果、临时假设、待验证产物和短期执行状态。"]

    <box gap={1}>

      <text color="secondary" size="sm">{item[1]}</text>
    </box>

      <divider color="subtle"/>
    {/if}

这里的命名空间表示资产的适用和共享范围，不代表四个完全独立的数据库。底层可以共用存储、索引与元数据服务，但必须在逻辑上隔离。

## 3.2 资产不能因为来自通用智能体就自动成为全局资产

例如，通用智能体帮助用户修改一个 Python 项目，发现了一个有效的构建命令。

这条命令可能只适用于：

- 某个项目；
- 某个操作系统；
- 某个依赖版本；
- 某个特定的运行环境。

因此，默认应先将其保存在项目专属范围。

当系统有证据表明某个方法具有更广泛的适用性时，可以申请晋升到领域共享层；只有当它确实跨领域通用，并通过相应的验证时，才考虑进入全局共享层。

**共享范围的扩大必须是显式、可追溯的治理动作，而不是记忆系统自动推断的结果。**

## 3.3 全局通用能力与领域专业能力可以共享什么？

建议允许跨领域共享以下资产：

- 通用的任务状态机；
- 可靠的重试和恢复机制；
- 通用文件处理与结构化数据工具；
- 通用的产物完整性验证；
- 经过验证的工具调用契约；
- 通用安全和授权约束；
- 通用的评测与诊断框架。

但以下内容默认保持领域隔离：

- 领域专用的质量标准；
- 特定项目的业务规则；
- 代码仓库的结构与技术决策；
- 角色、场景与素材的一致性约束；
- 用户对特定项目的私有信息；
- 仅在某种模型或工具版本下有效的优化策略。

这种设计既避免重复建设，也防止一个领域的经验污染另一个领域。

# 四、资产来源与可信度：经验进入知识库前必须经过什么？

KCLG 需要解决一个根本问题：系统如何知道某条知识或某个技能值得信任？

答案不是给所有资产打一个简单的“可信度 90 分”，而是保存可验证的来源、证据、适用范围与验证状态。

## 4.1 建立统一的来源记录

建议每项资产都能够关联以下信息：

| 字段 | 含义 |
|---|---|
| `asset_id` | 稳定的资产标识 |
| `asset_type` | 记忆、知识、技能、工作流或评测案例 |
| `origin_type` | 用户输入、外部来源、执行产物、诊断结果或人工创建 |
| `origin_ref` | 原始来源或事件引用 |
| `created_by` | 创建者或产生该资产的组件 |
| `created_at` | 创建时间 |
| `scope` | 全局、领域、项目或任务范围 |
| `validation_status` | 未验证、验证中、已通过、失败或已过期 |
| `evidence_refs` | 支持该资产的测试、执行记录或来源引用 |
| `version` | 当前资产版本 |
| `dependencies` | 该资产依赖的其他资产 |
| `expiry_policy` | 过期检查、复核条件或失效规则 |

不要求所有资产都有相同的字段内容，但应具有统一的身份和来源模型。

## 4.2 区分四种不同状态

建议不要将所有知识统一标记为“可信”或“不可信”，而是至少区分：

- **已记录：** 系统知道这条信息存在，但尚未验证；
- **已核验：** 相关事实或来源已经过适当检查；
- **已复现：** 某个方法在规定条件下可以重复得到预期结果；
- **已批准复用：** 资产已满足对应范围和风险级别的复用要求。

这几个状态不是所有资产都必须依次经历的固定流水线。

例如，用户明确表达的个人偏好可以作为“用户已声明”的事实记录，不需要通过外部实验来验证用户是否真的表达过该偏好。但系统仍然需要记录其适用范围、时间和是否后来被用户修改。

相反，一个声称能够修复复杂代码缺陷的技能，需要通过适当的功能测试、回归测试和安全检查，才能被批准在正式任务中复用。

## 4.3 一次成功不等于可复用

建议根据资产类型决定验证方式。

- 事实知识：检查来源与证据；
- 用户偏好：记录原始表达和适用范围；
- 诊断假设：保留为假设，直到有证据支持；
- 技能：验证输入输出契约、功能与边界行为；
- 工作流：验证端到端完成能力、恢复路径和成本；
- 评测案例：验证输入、预期结果与测试方法本身是否有效。

例如，某个视频生成提示词一次生成了效果不错的角色，不代表它在不同镜头、不同模型版本和不同场景下都能保持角色一致性。

合理的处理方式是保存成功案例和生成配置，随后通过一组代表性测试评估其适用范围，而不是立即将它升级成全局通用技能。

## 4.4 外部内容不能直接成为系统规则

外部文档、网页、代码仓库和工具输出都可能包含错误信息或恶意指令。

因此：

- 外部文档可以成为知识候选；
- 工具输出可以成为执行证据；
- 模型生成内容可以成为改进候选；
- 用户明确提供的项目规则可以成为项目约束。

但这些来源都不能仅凭“被写入知识库”就获得修改全局规则、授权策略或发布门槛的权限。

这部分必须继续受 TSEG 和受保护治理流程约束。

# 五、能力复用决策：应该复用、扩展，还是新建？

这是 KCLG 与 CEKCE / CIL 最直接的交叉点。

如果每次遇到新任务都创建新技能，能力库会快速膨胀；如果所有任务都强行复用现有技能，又可能形成复杂、脆弱、难以维护的万能技能。

因此，建议建立 `Capability Reuse Decision Engine`。

## 5.1 先判断任务需要的是什么能力

例如，用户要求分析一个 Python 项目中的函数依赖。

系统首先应识别任务契约：

- 输入是什么；
- 输出需要什么结构；
- 使用哪种语言或文件格式；
- 是否需要精确的语法结构；
- 是否需要跨文件符号解析；
- 是否需要执行代码；
- 结果怎样验收。

随后，再搜索现有能力资产，而不是仅凭任务名称寻找相似技能。

两个都叫“代码分析”的技能，实际输入输出、依赖和可靠性可能完全不同。

## 5.2 建立四种复用决策

<box border radius="xl" padding={3} gap={3}>
  {#each [
    ["A · 直接复用","已有技能的输入输出契约、能力范围、版本和环境均满足当前任务要求。"],
    ["B · 参数化复用","能力本身已经适用，只需调整明确支持的参数或配置。"],
    ["C · 扩展现有能力","已有技能覆盖大部分需求，但需要增加一个经过评估的新能力分支或适配器。"],
    ["D · 创建新能力","现有技能无法满足关键契约，或扩展会使原技能的职责、风险与维护复杂度明显恶化。"]
  ] as item}
    <box gap={1}>
      <title size="md">{item[0]}</title>
      <text color="secondary" size="sm">{item[1]}</text>
    </box>
    {#if item[0]!=="D · 创建新能力"}
      <divider color="subtle"/>
    {/if}
  {/each}
</box>

## 5.3 复用决策不能只看语义相似度

建议综合考虑：

- 输入输出契约是否匹配；
- 能力覆盖度；
- 环境和版本兼容性；
- 质量评测表现；
- 安全权限范围；
- 依赖与维护成本；
- 当前任务的风险；
- 扩展后对现有调用方的影响。

例如，AST 分析技能和正则表达式搜索技能都可能用于“查找函数”，但它们在语法正确性、跨文件解析能力和运行成本上存在差异。

如果任务要求精确识别函数定义、嵌套结构和符号引用，不能仅因为现有文本搜索技能名称相似就复用它。

## 5.4 创建新技能之前必须先做重复检查

建议按以下顺序执行：

1. 搜索已有能力及其别名；
2. 检查功能契约和测试覆盖；
3. 判断现有能力能否通过参数配置完成任务；
4. 评估扩展现有能力的成本与风险；
5. 比较新建能力的长期维护成本；
6. 形成决策记录；
7. 只有确认有必要时才创建新资产。

这样可以减少同一能力被不同专家反复实现的问题。

## 5.5 复用本身也需要评测

系统不能仅以“减少了多少技能数量”衡量复用效果。

更重要的是：

- 复用后任务是否仍然合格；
- 是否降低重复实现；
- 是否增加不必要的依赖；
- 是否扩大了权限范围；
- 是否让技能更难维护；
- 是否产生新的回归风险。

一个高度通用的技能如果需要大量特殊分支才能处理所有任务，可能比多个职责清晰的小技能更难维护。

因此，复用决策的目标是提高整体能力资产的可维护性和可靠性，而不是追求技能数量最少。

# 六、技能生命周期：从一次成功到正式能力

建议建立统一的 `CapabilityLifecycleStateMachine`。

每项正式能力都应该具有明确的生命周期状态，并且只有满足条件的状态转换才允许发生。

## 6.1 建议的生命周期

<box border radius="xl" padding={3} gap={2}>
  {#each [
    ["DISCOVERED · 已发现","系统识别到一个可能有价值的能力或改进机会。"],
    ["CANDIDATE · 候选","已经形成初步实现、配置或明确的改进方案。"],
    ["VALIDATING · 验证中","正在检查契约、功能、兼容性、安全性和质量表现。"],
    ["APPROVED · 已批准","满足对应范围和风险级别的发布要求。"],
    ["ACTIVE · 正式使用","能力已注册，可由符合条件的任务调用。"],
    ["DEGRADED · 表现退化","出现质量、兼容性或可靠性问题，需要限制使用或重新评估。"],
    ["DEPRECATED · 已弃用","不再推荐用于新任务，但可能暂时保留对旧工作流的兼容。"],
    ["RETIRED · 已退役","正式停止使用，保留必要的审计、历史引用和恢复信息。"]
  ] as item}
    <box gap={1}>
      <title size="md">{item[0]}</title>
      <text color="secondary" size="sm">{item[1]}</text>
    </box>
    {#if item[0]!=="RETIRED · 已退役"}
      <divider color="subtle"/>
    {/if}
  {/each}
</box>

这是一套概念状态集合，不意味着所有资产都必须经历全部状态。例如，普通记忆不需要经过技能发布流程；而正式可执行技能必须满足相应的验证与授权要求。

## 6.2 每次状态转换都必须有条件

例如，候选技能进入验证阶段前，应具备：

- 明确的能力契约；
- 输入输出定义；
- 依赖声明；
- 基本测试；
- 适用范围；
- 风险分类；
- 版本标识。

从验证中进入批准状态，则需要通过与其用途匹配的质量、安全和可靠性门槛。

如果技能验证失败，不能直接把它标记为正式使用。可以退回候选阶段继续修改，也可以终止该候选。

如果正式技能出现严重安全问题，则可以立即冻结或撤销其调用资格，而不必等待完整的普通弃用流程。

## 6.3 退化与退役必须有明确原因

技能不应因为“很久没有调用”就自动被删除。

长期未使用可能意味着：

- 该技能已经没有价值；
- 相关任务最近没有出现；
- 它是低频但关键的恢复能力；
- 它是某个旧项目仍然需要的依赖；
- 它的发现机制出了问题。

因此，退役决策应结合调用量、维护成本、质量表现、依赖关系和业务重要性。

对于历史任务仍然引用的技能，退役前应明确：

- 是否存在替代能力；
- 是否需要迁移旧工作流；
- 是否保留兼容适配器；
- 是否需要冻结原版本；
- 是否仍然可以从归档中恢复。

## 6.4 正式能力应采用不可变版本

建议正式发布的技能版本具有不可变的版本标识和内容摘要。

如果需要修改代码、提示词、依赖或关键配置，应生成新版本，而不是原地覆盖旧版本。

这样才能回答：

- 某个历史任务究竟使用了哪个版本？
- 为什么该版本当时通过评测？
- 新版本引入了什么变化？
- 哪些工作流依赖旧版本？
- 如果新版本发生退化，应该回滚到哪个已验证版本？

对于本地个人部署，这些信息可以使用 Git、文件内容摘要和本地数据库实现，不需要一开始就搭建复杂的企业级制品平台。

# 七、技能依赖图：防止一次升级破坏整个能力网络

随着 EvoAgent 的能力增加，技能之间会逐渐形成依赖关系。

例如：

`Python AST 分析器 → 代码依赖分析技能 → 重构工作流 → 编程专家`

如果 AST 分析器升级后改变了输出 Schema，下游代码依赖分析技能可能无法继续工作。

如果系统只测试新 AST 分析器自身，却不检查依赖它的工作流，就可能在正式任务中产生故障。

因此，建议建立 `Capability Dependency Graph`。

## 7.1 每项能力必须声明依赖

依赖声明至少包括：

- 被依赖资产的 ID；
- 兼容版本范围；
- 输入输出契约版本；
- 必要的运行环境；
- 权限需求；
- 可选依赖；
- 替代能力；
- 对应的兼容性测试。

依赖关系不只是“技能 A 调用了技能 B”。

还需要记录技能 A 是否依赖技能 B 的某个具体行为、输出字段或质量保证。

## 7.2 变更时执行影响分析

当一个技能发生变化时，KCLG 应根据依赖图确定：

1. 哪些直接依赖可能受到影响；
2. 哪些工作流需要重新验证；
3. 哪些专家的能力声明需要更新；
4. 哪些评测案例需要重新运行；
5. 哪些历史版本仍然需要保留；
6. 是否存在可以安全迁移的下游资产。

如果只是文档中的非关键描述发生变化，不一定需要重跑所有下游测试。

如果是输入输出契约、权限或执行行为发生变化，则需要更严格的影响分析。

## 7.3 工作流升级与技能升级必须分开管理

一个工作流可以引用特定版本的技能，也可以引用一个受控的兼容版本范围。

两种方式各有用途：

- 固定版本有利于复现历史任务；
- 兼容范围有利于安全地接收经过验证的更新。

但不能让一个历史工作流无条件自动使用所有最新技能。

建议在工作流发布时，明确其依赖策略与兼容性要求。对于高风险或高成本任务，应优先采用更严格的版本锁定和变更验证。

# 八、知识、记忆与技能之间的升级关系

前面已经区分了记忆、知识、技能、工作流和评测案例。现在需要进一步定义它们如何相互转化。

建议建立一套**受控资产晋升流程**，但不要把它设计成单向流水线。

## 8.1 从执行结果到长期资产

以一次复杂代码修复为例：

    ["执行事件","GECO 保存工具调用、文件差异、测试结果和执行版本。"],

    ["诊断假设","SOCDEA 分析原因，提出可验证的修复或改进解释。"],
    ["候选知识或技能","将有潜力的方法整理为知识条目、脚本、技能或工作流。"],
    ["独立评测","QEEG 使用相应测试集验证有效性、适用范围与边界行为。"],
    ["批准复用","KCLG 登记版本、来源、依赖和适用范围，并进入受控资产库。"],

  ] as item}
    <box gap={1}>
      <title size="md">{item[0]}</title>
      <text color="secondary" size="sm">{item[1]}</text>
    </box>

    {/if}
  {/each}

这里需要注意，成功案例不一定要形成技能。

有些经验适合变成文档或知识条目；有些适合变成测试用例；有些只适合留在项目记忆中；只有确实需要重复执行、具备稳定契约的操作方法，才值得实现为正式技能。

## 8.2 知识可以保持为知识，不必强行技能化

例如，某项技术的兼容性限制可能只需要被检索和引用，不需要实现成一个新的技能。

如果为了让每条知识都“可执行”而不断创建工具，系统反而会增加维护成本和权限面。

相反，一些已经被频繁验证的操作步骤可以逐步固化为工作流，使其执行过程更稳定、可观测、可恢复。

## 8.3 晋升范围必须与证据范围一致

假设某个技能只在 Windows 11、某个 Python 版本和一个特定仓库中通过了测试。

它不能仅凭一次成功就被声明为适用于 Android、Linux 和所有 Python 项目的通用技能。

资产的适用范围应该随着测试覆盖和真实使用证据逐步扩大，而不是由创建者随意填写。

## 8.4 失败案例的长期价值可能高于成功案例

成功结果有时难以解释，失败却可能暴露明确的边界条件。

例如：

- 某个 AST 分析器在特定语法结构下失效；
- 某个工作流在磁盘写满后无法恢复；
- 某个上下文压缩策略丢失了用户约束；
- 某个模型切换策略在断网后反复调用远程服务。

这些失败案例可以成为长期回归资产，防止相同问题在不同技能、不同模型或不同版本中反复出现。

但失败本身也不是通用知识。必须先记录条件和证据，再判断其适用范围。

# 九、去重与资产整理：能力库不能无限膨胀

长期运行的 EvoAgent 会积累大量相似资产。

例如：

- `python-function-finder`
- `python-symbol-search`
- `ast-function-locator`
- `code-function-detector`

它们名称不同，但可能具有相同功能；也可能只是名字相似，实际契约不同。

因此，KCLG 需要建立 `Asset Deduplication Engine`。

## 9.1 分三步判断重复

**第一步：发现候选重复项。**

可以使用名称、标签、描述、输入输出 Schema、依赖关系和内容摘要检索相似资产。

**第二步：比较实际能力。**

检查它们的功能覆盖、测试结果、权限范围、运行环境、性能和适用条件。

**第三步：决定如何治理。**

可能的结果包括：

- 保留一项正式能力，其他资产改为别名；
- 将重复实现合并到同一能力下；
- 保留不同实现，由统一接口根据环境选择；
- 发现原本相似的资产其实用途不同，继续独立维护；
- 将已经过时的资产迁移并退役。

## 9.2 不能只凭名称或向量相似度自动合并

两个技能的描述可能很相似，但其中一个只能分析 Python，另一个支持多语言符号解析。

如果仅根据语义相似度合并，可能破坏原有能力边界。

因此，自动化去重可以负责发现候选、提供比较证据和提出建议；正式合并则需要验证兼容性与下游影响。

## 9.3 建立资产维护价值指标

建议跟踪：

- 使用频率；
- 任务成功率；
- 维护成本；
- 依赖数量；
- 与其他资产的功能重叠；
- 失败和退化记录；
- 替代能力是否存在；
- 当前适用范围；
- 长期复用收益。

这些指标可以帮助发现值得整合的资产，但不应简单用调用次数决定生死。

一个很少被调用、却能在关键恢复场景中发挥作用的技能，仍然可能具有很高的价值。

# 十、长期知识治理：过期、冲突、隐私与遗忘

资产越多，越容易出现信息冲突。

例如，项目记忆中记录某个 API 的旧用法，而新版本文档已经改变；或者用户先后提出了不同的偏好；又或者某个工作流引用了已经被撤销授权的工具。

因此，KCLG 需要对资产的有效性进行持续治理。

## 10.1 建立不同的过期策略

不是所有资产都应该按照固定时间自动过期。

建议根据资产类型选择策略：

- **时间型：** 一段时间后重新核验，例如易变的外部服务信息；
- **版本型：** 依赖版本变化时触发复核，例如工具 API 契约；
- **事件型：** 项目配置、用户目标或授权发生变化时重新检查；
- **使用型：** 真实运行中持续出现失败或性能退化时重新评估；
- **长期稳定型：** 对低变化的通用知识，保留并在必要时核验。

过期不一定意味着删除。通常应先降低可用状态、触发核验，或者限制其适用范围。

## 10.2 冲突信息必须保留来源与时间

如果系统发现两条知识相互矛盾，不应简单地选择最近写入的一条。

需要比较：

- 来源可靠性；
- 适用范围；
- 版本和时间；
- 是否存在明确的取代关系；
- 是否来自用户的最新明确决定；
- 是否需要重新核验。

例如，用户对某个项目的最新明确决策可以取代旧项目约束；但用户的一次随口猜测，不应该自动覆盖已经核验的技术事实。

## 10.3 用户偏好与客观知识需要分离

用户可能喜欢某种代码风格、回答方式或工作流程。

这些偏好可以帮助 EvoAgent 个性化，但不能自动变成全局技术规则。

例如，用户偏好少写测试，可以作为个性化偏好被记录；但系统仍然需要根据任务风险和验收契约执行必要测试。

同样，用户可能对某项技术有自己的判断。系统可以记录用户的观点，但不能因此将其自动升级为已经验证的客观事实。

## 10.4 隐私与删除要求必须传播到相关资产

某条信息可能不仅存在于记忆条目中，还可能被引用进摘要、索引、技能配置或评测案例。

因此，资产治理需要支持来源追踪与关联查找。

当用户要求删除或限制某项信息时，系统应根据适用规则处理原始来源及相关派生资产，并明确说明无法确认完成的部分。

不应仅删除一个索引条目，就宣称所有派生副本都已经消失。

对于涉及敏感数据的资产，还应控制访问权限、日志暴露和跨领域复用范围。

---

# 十一、资产治理的指标：怎样知道知识库真正变好了？

KCLG 不能只统计技能总数、知识条目数量或记忆容量。

这些数字容易增长，却不一定代表系统能力提高。

建议建立 `AssetGovernanceMetrics`。

| 指标 | 衡量内容 |
|---|---|
| 能力复用率 | 在适用且经过验证的情况下，任务复用了现有能力的比例 |
| 重复资产率 | 经核验存在实质功能重复的资产比例 |
| 候选晋升通过率 | 候选资产通过相应独立验证的比例 |
| 资产回归率 | 新版本导致已有任务或依赖失效的比例 |
| 依赖完整性 | 正式能力的依赖是否存在、兼容且满足要求 |
| 过期资产命中率 | 实际任务使用到的资产中，已过期或不适用的比例 |
| 技能维护成本 | 更新、修复和兼容处理所需的资源 |
| 复用收益 | 相比重新实现，复用能力节省的成本与时间 |
| 资产退役质量 | 退役后是否造成工作流中断或能力缺失 |
| 经验复现率 | 被沉淀为方法的经验在规定条件下能够复现的比例 |
| 来源可追溯率 | 正式资产中能够找到必要来源和验证证据的比例 |
| 跨任务迁移表现 | 能力在声明的不同适用场景中是否仍然合格 |

这些指标应按资产类型和领域分别统计。

例如，用户偏好记忆不适合使用“技能复用率”评价；低频恢复技能也不能仅凭调用频率被判定为低价值。

## 11.1 评价资产的净收益

一个新技能可能减少重复劳动，但同时增加依赖、维护成本和故障风险。

因此，是否保留或扩展它，应比较：

- 节省的执行时间；
- 节省的重复实现成本；
- 对任务质量的影响；
- 维护与兼容成本；
- 额外资源消耗；
- 引入的故障与安全风险。

如果资产没有带来可验证的收益，且增加了系统复杂度，就应该考虑合并、简化或退役。

## 11.2 不要用一个总分管理所有资产

资产治理的目标不应该是找到一个万能的“资产价值分”。

更合理的做法是先满足安全、质量、来源和兼容性门槛，再根据使用场景比较维护成本和收益。

正式能力即使暂时不常用，只要仍然满足关键用途，也可以继续保留。

## 13.1 第一版必须通过的端到端验收测试

建议使用前面讨论过的 AST 代码分析能力作为第一个完整案例。

1. 编程专家发现任务需要 AST 分析能力。
2. KCLG 查询现有技能，判断是否已有符合契约的实现。
3. 如果没有，则创建候选技能，并明确支持的语言、版本和适用范围。
4. 对候选技能运行结构正确性、边界条件和回归测试。
5. 通过 QEEG 验收后，登记正式版本及其依赖。
6. 将该技能接入代码分析工作流。
7. 当技能契约发生变化时，识别受影响的工作流和专家。
8. 运行必要的兼容性与回归测试。
9. 如果新版本发生退化，恢复到经过验证的版本。
10. 如果发现另一个功能重复的技能，执行影响分析后决定合并、保留或退役。

这条链路跑通后，EvoAgent 才真正拥有了能力资产的生命周期治理，而不只是一个不断增长的技能目录。

# 十四、下一专项：自主目标管理、长期任务与智能体主动性

到目前为止，我们已经讨论了大量关于智能体如何执行、如何评测、如何恢复、如何优化和如何积累能力的问题。

但还有一个更深层的问题尚未解决：

**EvoAgent 在没有用户持续发出指令的情况下，应该主动做什么？它怎样判断什么值得做、什么时候应该继续，以及什么时候必须停止？**

这不是简单的定时任务问题。

例如，用户要求 EvoAgent 持续改进自己的编程能力。系统可能发现一个可以修复的缺陷，于是提出修复候选。但接下来还存在很多决策：

- 现在应该修复这个缺陷，还是先完成用户正在等待的任务？
- 应该继续分析更多问题，还是已经有足够证据开始实施？
- 是否值得为了一个很少发生的错误投入大量资源？
- 用户暂时没有新指令时，哪些后台工作仍然有价值？
- 如果一个任务长期没有进展，系统应该继续尝试还是主动停止？
- 如果系统发现了一个潜在改进机会，它有权直接执行吗？
- 如何防止智能体为了追求自己的优化目标，不断产生更多任务、调用更多模型，甚至无休止地修改自己？

因此，建议下一专项定义为：

**Autonomous Goal & Initiative Governance，简称 AGIG。**

它将重点研究：

1. 如何区分用户目标、系统维护目标、领域目标和临时子目标；
2. 如何把长期目标分解成有边界、可验证的任务；
3. 如何判断某个潜在改进是否值得投入资源；
4. 如何为自主任务分配优先级、预算和截止条件；
5. 如何在用户前台任务与后台主动任务之间进行协调；
6. 如何区分建议、准备、执行和需要用户批准的动作；
7. 如何防止智能体不断创建子任务，形成无限递归；
8. 如何判断继续探索的预期收益是否已经低于成本；
9. 如何管理等待条件、依赖关系和长期任务状态；
10. 如何在没有网络、模型不可用或资源不足时暂停自主任务；
11. 如何防止自主目标覆盖用户的明确意图与安全边界；
12. 如何将主动性与 QEEG、RERA、APRO 和 KCLG 结合，使系统既能主动发现机会，又不会盲目行动；
13. 如何评估主动任务是否真正创造了价值，而不是仅仅增加了活动数量；
14. 如何让用户设置主动程度、审批范围、安静时段和资源限制；
15. 如何保证自主任务可以解释、取消、恢复和审计。

这个专项与此前的自进化控制器、任务调度器和后台进化机制紧密相关，但需要单独定义目标与主动性的治理规则。

它的核心原则是：

**自主性不是无限制地采取行动，而是在明确的目标、授权、资源和停止条件内，主动选择有价值的下一步。**

完成 AGIG 后，EvoAgent 的整体设计将进一步覆盖从用户目标形成、任务执行、质量验证、经验沉淀，到自主发现下一步改进机会的完整循环。

届时，我们就可以进一步检查整个架构是否存在重复模块、职责缺口、接口冲突或过度复杂化的问题，并开始将这些专项整合成一份可冻结、可实施、可持续演进的完整架构基线。
