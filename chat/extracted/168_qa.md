**英文名称：** Adaptive Task Decomposition, Dynamic Planning & Multi-Workflow Orchestration

**文档版本：** 1.0

**所属体系：** EvoAgent 自进化智能体专项设计集

**关联专项：** #75—#84

**设计状态：** 专项设计基线，待实施与验收。

## 一、专项目标

建立统一的任务执行与编排机制，使 EvoAgent 能够根据目标、任务复杂度、确定性、风险、预算和实际执行结果，动态选择执行方式，并在遇到新情况时进行有约束的计划调整。

本专项需要解决：

1. 什么任务可以直接执行，什么任务需要 Plan，什么任务适合固定 DAG？
2. 如何将复杂目标拆分为可独立验证的子任务？
3. 如何识别任务依赖、并行机会、关键路径和阻塞条件？
4. 如何在执行过程中根据实际观察调整计划？
5. 如何结合 ReAct、Plan、DAG 和成熟工作流，而不是让它们彼此竞争？
6. 如何让多个领域专家协同工作，同时避免重复劳动和结果冲突？
7. 当某个子任务失败时，如何局部恢复，而不是重新执行整个任务？
8. 如何在质量、时延、成本和稳定性之间进行有约束的优化？
9. 如何防止计划反复变化、任务无限扩张和无进展循环？
10. 如何确保动态规划不绕过安全策略、用户授权和结果验收？
11. 如何将成功的动态执行路径沉淀为可复用的稳定工作流？
12. 如何持续评估和优化任务分解、规划及调度能力？

**核心原则：目标与约束相对稳定，执行计划可以动态调整；每次调整都必须有依据、可追溯，并且不能降低最终验收标准。**

## 二、总体架构

### 2.1 执行引擎的逻辑组成

建议将执行引擎划分为以下逻辑组件：

| 组件 | 核心职责 |
|---|---|
| Task Classifier | 判断任务类型、复杂度、确定性与风险 |
| Execution Mode Selector | 选择直接执行、动态计划、固定工作流或混合执行 |
| Task Decomposer | 将复杂目标分解为子任务 |
| Plan Manager | 维护计划版本、调整记录和当前执行策略 |
| DAG Scheduler | 管理依赖关系、并行调度、阻塞与节点状态 |
| ReAct Executor | 根据观察、行动和反馈推进当前执行步骤 |
| Expert Coordinator | 分配领域专家、协调输入输出与共享成果 |
| Recovery Controller | 管理重试、局部恢复、补偿和失败升级 |
| Result Verifier | 独立验证子任务和最终任务是否达标 |
| Budget Controller | 管理时间、模型调用、工具成本与重试预算 |

这些是逻辑职责，不要求部署成十个独立服务。第一版可以在一个运行进程内实现，但接口和职责应当能够独立测试。

### 2.2 整体执行流程

```text
用户目标与任务契约
        ↓
任务类型、风险和约束分析
        ↓
选择执行模式
        ↓
检索成熟工作流与可复用能力
        ↓
生成初始计划
        ↓
检查依赖、权限、预算和验收条件
        ↓
执行就绪节点
        ↓
ReAct 观察与行动
        ↓
验证节点结果
        ↓
更新任务状态与依赖图
        ↓
是否需要重新规划？
    ┌───┴────┐
    否       是
    ↓        ↓
继续执行   受控调整计划
    └───┬────┘
        ↓
最终结果独立验收
        ↓
交付结果与记录执行证据
        ↓
评估是否值得固化为工作流
```

重新规划不是默认发生的动作。只有新证据、阻塞、失败、目标变更或收益明显的替代路径，才应触发计划调整。

## 三、执行模式选择

EvoAgent 不应该为所有任务采用同一种执行方式。

### 3.1 四种基本模式

| 模式 | 适用场景 | 特点 |
|---|---|---|
| M1：直接执行 | 简单、明确、低风险任务 | 最少规划开销 |
| M2：动态 Plan + ReAct | 开放式、存在不确定性的任务 | 边执行边观察和调整 |
| M3：固定 DAG 工作流 | 重复发生、步骤与验收明确的任务 | 稳定、可重复、易测试 |
| M4：混合编排 | 同时包含成熟流程与未知问题的复杂任务 | 固定流程与动态规划结合 |

例如：

- 翻译一段文字：通常采用 M1。
- 调查一个未知代码故障：通常采用 M2。
- 重复执行已经验证的媒体合成流程：优先采用 M3。
- 制作一部 AI 漫剧：可采用 M4，将脚本处理、素材登记、合成和验收组织为工作流，对失败镜头、角色一致性异常等不确定环节采用动态规划。

### 3.2 模式选择不能只看任务领域

同样是编程任务，解释一个函数与重构一个大型项目的执行模式应当不同。

模式选择应考虑：

- 目标是否明确；
- 步骤是否已知；
- 依赖是否确定；
- 是否需要外部工具；
- 失败是否容易恢复；
- 是否存在不可逆副作用；
- 是否需要多个专家；
- 结果是否具有明确的自动验收方式；
- 预算是否允许探索。

### 3.3 优先复用成熟工作流

如果存在已经验证、版本兼容且满足当前任务约束的工作流，系统应优先考虑复用，而不是每次都重新规划。

但是，复用前仍需检查输入契约、依赖版本、适用范围和风险条件。

如果当前任务超出工作流的已验证范围，可以：

1. 直接拒绝不适用的部分；
2. 使用成熟工作流处理确定性部分；
3. 将未知部分交给动态计划；
4. 在结果满足验收标准后，评估是否扩展工作流。

不能因为某个工作流过去成功过，就假定它适用于所有相似任务。

## 四、Plan、ReAct、DAG 与工作流的关系

这是本专项最重要的架构决策。

四者不是相互替代的四种智能体，而是解决不同层次的问题。

### 4.1 Plan：决定怎样实现目标

Plan 是当前任务的执行策略。

它负责：

- 将目标分解为子目标；
- 决定先做什么、后做什么；
- 识别不确定性和风险；
- 选择工具与专家；
- 判断何时需要重新规划；
- 确定完成条件。

Plan 可以是高层策略，不必包含每一次工具调用的细节。

### 4.2 DAG：规定依赖和调度约束

DAG 表达任务之间的先后依赖和并行关系。

例如：

```text
需求分析
   ↓
脚本生成
   ↓
分镜设计
   ↓
角色设定
   ↓
镜头生成
   ↓
视频合成
   ↓
质量验收
```

如果部分镜头彼此独立，可以并行生成；如果角色设定发生重大变化，则相关镜头需要重新检查。

DAG 不负责判断用户的真实目标，也不应独立决定任务成功。

### 4.3 ReAct：推进具体执行步骤

ReAct 负责在当前执行范围内循环：

**观察 → 判断下一步行动 → 调用工具或执行操作 → 观察结果 → 更新状态。**

例如，代码节点运行测试失败，ReAct 可以读取错误、检查代码、尝试修复并再次运行测试。

但如果问题已经超出当前节点的处理范围，例如原计划依赖的库不可用，ReAct 应将事实反馈给 Plan Manager，而不是无限地在当前节点内尝试。

### 4.4 工作流：固化已经验证的执行能力

工作流是具有明确输入、输出、依赖、验收与恢复规则的可复用资产。

成熟工作流可以包含：

- 固定 DAG；
- 带条件分支的节点；
- 受控的动态计划节点；
- ReAct 执行节点；
- 独立验收节点；
- 失败恢复和补偿节点。

因此，工作流并不等于完全固定的流程，它可以在明确边界内包含动态能力。

### 4.5 最终关系

| 层次 | 主要问题 |
|---|---|
| 用户目标与验收契约 | 最终必须实现什么 |
| Plan | 采用什么策略实现目标 |
| DAG | 哪些任务依赖哪些任务，哪些可以并行 |
| 工作流 | 哪些执行模式已经固化并可复用 |
| ReAct | 当前步骤如何根据实际观察推进 |
| Result Verifier | 如何证明结果达到标准 |

这些层次必须共享必要状态，但不能互相越权。

## 五、动态任务分解

### 5.1 子任务必须具有明确边界

复杂任务不能只拆成一串自然语言步骤。

每个子任务至少应明确：

- `node_id`：稳定的逻辑节点标识；
- `objective`：节点目标；
- `input_refs`：输入引用；
- `output_contract`：预期输出结构；
- `dependency_refs`：前置依赖；
- `assigned_expert_ref`：负责的专家或执行器；
- `required_tools`：必要工具；
- `acceptance_criteria`：节点验收条件；
- `risk_class`：节点风险；
- `budget_ref`：节点预算；
- `retry_policy_ref`：重试规则；
- `recovery_policy_ref`：恢复规则；
- `side_effect_policy_ref`：副作用控制规则。

以上是建议的逻辑扩展，应与现有 `node_run_id`、Task、Workflow 和工具契约映射。

### 5.2 拆分质量标准

一个合格的子任务应满足：

1. 目标明确；
2. 输入可识别；
3. 输出可验证；
4. 依赖关系明确；
5. 失败影响范围可判断；
6. 执行权限和预算可控制；
7. 可以独立记录结果；
8. 必要时可以独立重试或恢复。

如果两个子任务的输出高度耦合，拆分后反而需要频繁同步，就不应该为了增加并行度而强行拆分。

### 5.3 分解深度动态调整

简单任务不需要被拆成大量微小节点。

任务复杂度增加时，可以逐步分解；如果子任务本身仍然复杂，再进一步分解。

建议采用分层分解：

- 顶层：用户目标；
- 中层：主要交付目标或工作阶段；
- 底层：可执行、可验证的操作节点。

每一层都需要保留与父目标的关联。

### 5.4 停止分解条件

满足以下条件时，应停止继续细分：

- 当前节点可以安全执行；
- 输入输出契约足够明确；
- 执行成本低于继续拆分的收益；
- 进一步分解无法显著改善可验证性；
- 节点已有经过验证的工作流可以直接调用。

否则，过度分解会增加调度开销、状态同步成本和故障面。

## 六、计划版本与受控重新规划

动态规划最大的风险之一，是系统在执行过程中不断改变计划，导致任务迟迟不能完成。

因此，计划必须具有明确的版本、触发条件和变更规则。

### 6.1 计划版本

建议采用以下逻辑对象：

- `plan_id`：逻辑计划标识；
- `plan_revision`：计划修订号；
- `parent_revision`：上一修订号；
- `trigger_event_refs`：触发变更的事件；
- `change_summary`：变更内容；
- `affected_node_refs`：受影响节点；
- `preserved_node_refs`：保留的节点；
- `invalidated_output_refs`：失效输出；
- `acceptance_contract_ref`：原有验收契约；
- `budget_impact`：预算变化；
- `authorization_impact`：授权变化；
- `verification_requirements`：变更后必须重新执行的验证。

计划变更应形成新的修订记录，不得覆盖历史版本。

### 6.2 重新规划触发条件

允许触发重新规划的典型情况：

- 必要工具不可用；
- 子任务输出不满足契约；
- 新发现与原假设冲突；
- 依赖项失败或发生变化；
- 任务预算不足；
- 当前方案持续没有进展；
- 发现更可靠且收益明确的执行路径；
- 用户明确修改目标；
- 关键风险发生变化。

仅仅因为模型想到了另一种可能方案，不足以自动触发整个计划重写。

### 6.3 计划变更分级

**P1：局部调整**

例如，调整一个节点的参数或增加一个验证步骤。

在不改变目标、授权和关键验收标准的前提下，可以自动进行。

**P2：局部重构**

例如，替换一个不可用工具，或者重新安排一组依赖节点。

需要重新检查受影响节点、依赖和预算。

**P3：任务级重规划**

例如，原方案无法完成用户目标，需要改变整体执行路径。

必须保留原目标与验收契约，并重新检查成本、时限和执行风险。

**P4：目标或授权变更**

例如，计划调整将扩大交付范围、产生新的外部副作用，或改变用户明确要求。

不能把它当作普通的计划优化；必须进入目标变更或授权流程。

### 6.4 防止反复重规划

建议设置：

- 单次任务的重规划预算；
- 连续无进展的检测条件；
- 同一失败原因的重复检测；
- 计划修订之间的收益比较；
- 重新规划后的最小执行周期；
- 任务级停止与升级规则。

如果反复重规划没有产生可验证的进展，应停止循环，保留当前状态，并向用户说明阻塞原因和可行选项。

## 七、DAG 调度与并行执行

### 7.1 就绪节点调度

只有满足以下条件的节点，才可以进入就绪队列：

- 必需依赖已完成并通过必要验证；
- 输入契约满足要求；
- 工具与执行环境可用；
- 预算仍然有效；
- 权限与授权条件满足；
- 不存在尚未解决的关键阻塞。

就绪不代表必须立即并行执行。调度器还应考虑资源、成本和副作用冲突。

### 7.2 并行执行条件

两个节点可以并行执行，前提是：

- 不存在直接或间接依赖；
- 不会竞争同一不可安全共享的资源；
- 不会产生相互冲突的外部副作用；
- 输出合并方式明确；
- 并行执行不会破坏一致性；
- 资源预算足够。

例如，多个独立镜头的素材生成可以并行；但对同一个文件的并发修改，通常需要串行化或通过明确的合并协议处理。

### 7.3 关键路径与收益判断

调度器可以识别关键路径、可并行节点和潜在瓶颈。

但是，更多并行不一定更快，也不一定更便宜。

需要比较：

- 预计执行时延；
- 模型与工具并发限制；
- 失败后的重做成本；
- 输出合并成本；
- 资源竞争风险；
- 对最终质量的影响。

对于成本较高、容易失败或高度耦合的节点，可以选择串行执行。

### 7.4 节点状态机

建议统一采用以下逻辑状态：

`PENDING → READY → RUNNING → VERIFYING → SUCCEEDED`

异常路径包括：

- `BLOCKED`：依赖或资源阻塞；
- `FAILED`：节点执行失败；
- `RETRYING`：正在执行允许的重试；
- `RECOVERING`：正在执行恢复；
- `SKIPPED`：经规则允许而跳过；
- `CANCELLED`：已取消；
- `NEEDS_USER`：需要用户确认或补充信息。

节点失败不能自动导致所有节点失败。

调度器应根据依赖关系、失败传播规则和任务验收要求，决定哪些节点停止、哪些可以继续、哪些需要重新执行。

## 八、多专家与多工作流协同

### 8.1 协同模式

建议支持三种基本模式。

**模式 A：单专家执行**

适用于一个专家可以完整处理的任务。

**模式 B：主协调器分配子任务**

由主协调器拆分任务，并将明确的子任务交给领域专家。

**模式 C：多专家协同分析**

多个专家对不同维度进行分析，再由协调器统一比较、消除冲突和形成最终交付。

不应为了体现多智能体能力，让简单任务也调用多个专家。

### 8.2 专家任务契约

每个被调用的专家应接收明确的任务包：

- 子目标；
- 输入引用；
- 输出契约；
- 相关约束；
- 可用工具；
- 预算；
- 验收标准；
- 允许的副作用；
- 需要回传的证据。

专家只应在分配范围内自主执行。

如果发现子任务目标不合理，可以提出问题或建议，但不能静默扩大自身任务范围。

### 8.3 专家之间如何交换成果

默认采用显式交付物和引用传递，而不是把所有专家的完整对话相互复制。

例如：

- 编程专家输出代码差异、测试结果和依赖说明；
- 规划专家输出结构化计划；
- 资料检索专家输出来源和经过核验的事实；
- 漫剧专家输出素材引用、镜头状态和合成约束。

这样可以减少上下文污染，避免不同专家因为看到大量无关对话而降低判断质量。

### 8.4 冲突处理

当多个专家给出互相矛盾的结论时：

1. 明确矛盾发生在哪个事实或决策上；
2. 比较证据质量和适用范围；
3. 检查是否因为各自假设不同而产生分歧；
4. 必要时进行补充验证；
5. 无法消除冲突时保留不确定性；
6. 由有权决策的协调器按照任务目标、验收契约和风险策略作出处理。

不能简单通过多数投票决定事实真伪。

### 8.5 防止多专家放大错误

一个专家的错误结论可能被多个下游专家当成已知事实。

因此，跨专家传递的关键内容必须标记：

- 已确认事实；
- 未验证假设；
- 评估意见；
- 输出版本；
- 证据引用；
- 适用范围。

下游专家不得把上游专家的推断自动提升为已验证事实。

## 九、失败恢复与局部重执行

### 9.1 失败首先定位到节点

当任务失败时，应先判断：

- 是单个节点失败；
- 是节点输出不符合契约；
- 是依赖状态错误；
- 是执行环境故障；
- 是计划本身存在缺陷；
- 还是最终验收规则未满足。

恢复策略应由故障类型决定，而不是统一重跑整个任务。

### 9.2 局部恢复策略

| 故障类型 | 推荐处理 |
|---|---|
| 临时网络异常 | 在预算与重试策略允许时重试 |
| 工具参数错误 | 修正参数并重新验证 |
| 节点输出格式错误 | 修复或重新生成该节点输出 |
| 上游产物发生变化 | 重新评估受影响的下游节点 |
| 外部依赖不可用 | 等待、替代或安全降级 |
| 计划缺陷 | 创建新计划修订 |
| 结果验收失败 | 定位失败条件，决定局部修复或重新规划 |
| 外部副作用状态未知 | 先对账，不得盲目重复执行 |

### 9.3 缓存与结果复用

已完成节点的结果可以复用，但必须检查：

- 输入是否相同；
- 相关依赖是否变化；
- 产物版本是否有效；
- 工具或模型变更是否影响结果；
- 输出是否仍满足当前验收条件；
- 结果是否允许在当前任务中复用。

不能仅凭节点名称相同就复用旧结果。

### 9.4 外部副作用与幂等性

对于发送消息、提交订单、删除文件等具有外部副作用的操作，重试前必须检查执行状态和幂等语义。

如果执行结果未知，应先使用 Side-effect Ledger 和外部回执进行对账。

不能为了恢复任务而重复执行可能产生重复副作用的操作。

## 十、质量、成本、时延与预算治理

### 10.1 质量是硬约束，不是可以随意折价的指标

调度器可以优化成本和时延，但不能让较低成本抵消未达到的必要验收条件。

建议分两阶段决策：

第一阶段，筛选满足安全、权限和最低质量要求的可行方案。

第二阶段，在可行方案中比较成本、时延、资源消耗和预期收益。

如果没有方案能够满足必要条件，应明确报告限制，而不是自动降低标准。

### 10.2 预算分层

建议将预算分成：

- 任务总预算；
- 规划与重规划预算；
- 子任务预算；
- 专家调用预算；
- 工具调用预算；
- 恢复预算；
- 最终验收预算。

预算消耗应可追溯到具体任务、运行、节点和资产版本。

### 10.3 预算不足时的处理

预算不足时，系统应按以下顺序处理：

1. 停止可选的额外探索；
2. 避免重复执行已完成的有效节点；
3. 复用符合条件的已有产物；
4. 调整并行度和模型选择；
5. 提供满足当前约束的低成本替代方案；
6. 如果无法完成必要验收，暂停并说明缺口。

不能为了在预算内结束任务而虚报成功。

## 十一、计划质量评估与工作流固化

本专项不仅负责执行，还要让系统能够逐步学会更好的任务分解和规划方式。

### 11.1 规划质量指标

建议跟踪：

- 计划执行成功率；
- 子任务分解有效率；
- 依赖关系正确率；
- 计划修订后的收益；
- 无进展循环发生率；
- 不必要重规划率；
- 失败后的局部恢复成功率；
- 节点结果复用有效率；
- 多专家协同收益；
- 任务总时延；
- 任务总成本；
- 最终验收通过率。

所有指标都应按任务类型、风险和执行模式分别统计。

### 11.2 何时固化为工作流

当同类任务反复出现，且执行路径已经经过足够验证时，可以考虑将其固化为工作流。

需要检查：

- 输入条件是否稳定；
- 步骤与依赖是否明确；
- 输出契约是否清晰；
- 失败模式是否已知；
- 恢复策略是否经过验证；
- 验收标准是否可靠；
- 不同环境下的兼容性是否明确；
- 固化后是否比动态规划更稳定或更经济。

### 11.3 固化不是冻结一切

成熟工作流可以包含受控的动态节点。

例如，漫剧制作工作流可以固定脚本、分镜、素材管理、配音、合成和验收的整体结构，但允许某个失败镜头进入动态恢复流程。

因此，固化的是经过验证的结构、契约和边界，而不是要求所有任务必须经历完全相同的每一步。

### 11.4 工作流自身也需要独立进化

工作流变更必须经过版本管理、回归测试和收益对照。

不能因为一次动态执行成功，就自动将整条轨迹发布为稳定工作流。

一次成功轨迹只能作为候选；还需要验证可重复性、异常恢复能力和适用范围。

## 十二、与无限优化闭环的结合

执行引擎的优化目标是提高真实任务的完成能力，而不是追求更复杂的计划或更多的子任务。

完整闭环：

1. 正常执行用户任务；
2. 记录计划、节点、工具调用和验收结果；
3. 识别规划错误、依赖错误、恢复失败和无进展循环；
4. 使用 #80 分析根因；
5. 使用 #81 沉淀经过验证的故障模式；
6. 使用 #82 检查上下文是否影响计划质量；
7. 生成规划器、调度器或工作流的改进候选；
8. 在独立评测集上对比基线；
9. 验证质量、时延、成本和稳定性；
10. 通过 #75—#79 的适用治理流程；
11. 受控发布；
12. 观察真实任务结果并在退化时回滚。

需要严格区分：

- 当前任务的计划调整；
- 稳定工作流的版本变更；
- 规划器或调度器自身的能力升级。

三者具有不同风险和生命周期，不能共用一个无约束的自动修改入口。

## 十三、核心验收测试矩阵

| 测试 ID | 场景 | 通过条件 |
|---|---|---|
| PLAN-01 | 简单、明确的低风险任务 | 直接执行，不产生不必要的复杂计划 |
| PLAN-02 | 开放式未知任务 | 能生成合理的动态计划 |
| PLAN-03 | 已验证的重复任务 | 优先复用适用的稳定工作流 |

| PLAN-24 | 重规划改变了节点依赖 | 重新验证受影响的下游节点 |
| PLAN-25 | 恢复操作可能重复外部副作用 | 依据幂等性和状态对账执行安全恢复 |

所有测试必须通过真实执行记录确认。本文件定义设计要求和验收标准，不代表实现已经完成。

## 十五、完成判定

只有满足以下条件，才能认定本专项实施验收完成：

- 系统能够根据任务特点选择合理的执行模式；
- 复杂任务可以分解为具有明确输入、输出和验收条件的子任务；
- DAG 调度遵守依赖、资源、权限和预算约束；
- ReAct、Plan、DAG 与工作流具有清晰的职责边界；
- 计划变更具有版本、依据和影响范围记录；
- 能够对失败节点执行安全的局部恢复；
- 多专家协同具有明确的任务契约和结果验证机制；
- 系统能够检测无进展循环和不必要重规划；
- 外部副作用状态未知时不会盲目重试；
- 动态调整不会降低用户原有验收标准；
- 成熟工作流经过独立验证后才能固化；
- 规划与调度改进经过独立评测和正式发布门禁；
- 所有关键验收场景均有真实执行证据。

**最终目标：让 EvoAgent 能够针对不同任务选择最合适的执行方式，在不确定环境中灵活调整，在确定性流程中保持稳定，在复杂任务中有效协同，并且始终以用户目标和可验证的最终结果作为执行依据。**</WritingBlock>

## 下一项专项：#86

建议继续推进 **#86：任务执行可观测性、过程质量监控与实时纠偏治理**。

#85 解决了任务应该怎样规划、调度和恢复。接下来需要进一步解决：智能体在执行过程中，如何及时知道自己正在变好还是变差、是否偏离目标，以及是否应该继续、暂停、纠偏或重新规划。

#86 将重点设计：

1. **过程质量监控：** 不只检查最终结果，还检查执行中间状态是否异常。
2. **目标偏离检测：** 识别计划虽然仍在推进、实际却已经偏离用户目标的情况。
3. **执行进度真实性：** 区分真实进展、重复尝试和表面上忙碌但没有产出的循环。
4. **实时纠偏策略：** 决定什么时候继续、重试、调整计划、切换专家或请求用户确认。
5. **监控与执行解耦：** 监控系统不能因为自身异常而破坏正在正常运行的任务。
6. **质量信号与自进化衔接：** 将执行过程中的问题变成可靠证据，供后续诊断、评测和优化使用。

这一步会把 EvoAgent 从“能够规划和执行”推进到“能够持续判断自己的执行是否仍然正确，并在问题扩大前采取适当措施”。
