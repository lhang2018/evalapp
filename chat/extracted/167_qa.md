举几个典型场景：

- 用户说“帮我优化这段代码”，真正目标可能是修复 Bug、提高性能、降低维护成本，也可能是让代码更容易扩展。不同目标对应不同的优化方式。

- 用户提出一个看起来合理的方案，但智能体发现它无法实现用户最终目标。这时，机械执行反而是不负责任的。

不过，深层理解也存在另一种风险：智能体过度揣测用户意图，擅自替用户改变目标，甚至把自己的偏好当成用户的真实需求。

因此，#84 要建立的不是一个简单的意图分类器，而是一套完整的**目标理解、约束识别、意图置信判断、任务规划、结果验收和主动纠偏机制**。

核心原则是：理解要深入，但不能自作主张；执行要灵活，但不能偏离用户目标；发现更好的路径，应当主动提出，而不是默默替用户改变目标。

现有正式数据契约已经提供了这一专项的基础：`Task` 记录用户目标、约束和验收契约，`Goal` 支持显式、长期、派生、维护和机会型目标，并关联成功标准、授权和预算。<FileCite ref_id="turn24file0"/><FileCite ref_id="turn24file1"/> 因此，#84 应在现有契约上补充目标理解与决策机制，而不是另建一套任务系统。

<WritingBlock id="68421" variant="document"># EvoAgent 专项设计 #84：用户意图深层理解、真实目标识别与任务完成效果治理

**英文名称：** Deep Intent Understanding, Goal Inference & Task Outcome Governance

**文档版本：** 1.0

**关联专项：** #75—#83

**设计状态：** 专项设计基线，待实施与验收。

## 一、专项目标

建立统一的目标理解与任务决策机制，使 EvoAgent 能够从用户的自然语言、上下文、明确约束和实际任务状态中，理解用户希望实现的结果，并据此选择合理的执行方式。

本专项解决以下问题：

1. 如何区分用户的字面指令、直接目标和更深层的实际需求？
2. 如何理解用户没有明确表达、但可以从上下文合理推断的需求？
3. 如何判断哪些信息可以合理推断，哪些必须向用户确认？
4. 当用户描述的执行方法并不能实现其目标时，智能体应如何处理？
5. 当存在更好的方案时，如何主动提出建议，同时保留用户的决策权？
6. 如何处理用户目标之间的冲突、信息缺失和不断变化的要求？
7. 如何将模糊目标转化为可执行计划和可验证的验收标准？
8. 如何判断任务是否真正解决了用户的问题，而不只是完成了表面动作？
9. 如何从用户反馈和任务结果中改进目标理解能力？
10. 如何确保更深入的理解不会降低任务执行质量、效率和稳定性？

**核心原则：理解用户想要什么，不等于猜测用户想要什么；优化实现路径，不等于擅自改变用户目标；完成任务，不等于真正解决问题。**

## 二、目标理解的基本模型

EvoAgent 必须同时理解四个不同层次。

### 2.1 四层目标模型

| 层次 | 名称 | 需要回答的问题 |
|---|---|---|
| G1 | 字面指令 | 用户明确要求执行什么？ |
| G2 | 直接目标 | 用户希望通过这个任务得到什么结果？ |
| G3 | 目的与约束 | 用户为什么需要这个结果？有哪些不可忽略的限制？ |
| G4 | 潜在改进机会 | 有没有能够更好实现用户目标的替代方案或额外价值？ |

例如，用户说：“帮我优化这个程序。”

- G1：对程序进行优化。
- G2：获得更好的程序。
- G3：可能涉及正确性、运行效率、可维护性、兼容性和成本。
- G4：可能发现根本问题不在代码效率，而在算法复杂度、数据结构或架构设计。

这里需要特别注意：G3 中的具体目标不能仅凭“优化”两个字就被确定。G4 中的机会也不能自动替代 G1 和 G2。

智能体应当区分已经确认的目标与仍然存在的不确定性。

### 2.2 目标与方法分离

用户提出的操作方法，不一定是实现目标的最佳方法。

例如：

用户要求：“增加更多模型调用，提升回答质量。”

智能体应分析：

- 当前质量问题是否确实由模型能力不足导致；
- 是否存在上下文丢失、工具错误或评测缺陷；
- 是否可以通过更好的规划、验证或知识检索解决问题；
- 增加模型调用是否值得其成本。

如果存在更可靠的方法，智能体应主动提出，并说明差异。

但是，除非用户授权范围允许，智能体不能把自己的替代方案直接当作已经获得批准的新目标。

### 2.3 目标理解不等于无限追问

如果用户的意图已经足够明确，智能体应直接执行，不应为了完善目标模型而反复要求用户补充信息。

例如，用户要求将一段文字翻译成英文，且没有其他特殊限制时，通常无需先进行一轮复杂的需求分析。

只有当不确定性可能实质影响正确性、成本、风险或最终交付时，才需要进一步澄清。

## 三、目标理解的数据契约

本专项优先复用正式 `Task` 和 `Goal` 契约。

建议在现有 `Task` 数据及相关引用对象中，增加或关联以下逻辑信息。

### 3.1 目标理解记录

- `intent_record_id`：目标理解记录标识；
- `task_id`：关联的逻辑任务；
- `explicit_objective`：用户明确提出的目标；
- `interpreted_objective`：系统对直接目标的解释；
- `inferred_goals`：推断出的潜在目标；
- `constraints`：明确约束与必要的隐含约束；
- `assumption_refs`：尚未确认的假设；
- `ambiguity_refs`：需要处理的歧义；
- `alternative_plan_refs`：可能的替代实现路径；
- `acceptance_contract_ref`：正式验收契约；
- `authorization_ref`：适用的授权规则；
- `confidence_assessment`：目标理解的可信度评估；
- `user_confirmation_refs`：关键目标或约束的确认记录；
- `revision_history_refs`：目标理解的变更历史。

这些是建议的逻辑扩展，不代表现有接口已经全部实现。落地前应与已有 Schema 统一。

### 3.2 明确区分事实、推断与假设

每个重要的目标要素应标记来源：

- `EXPLICIT`：用户明确表达；
- `CONTEXT_SUPPORTED`：由已有上下文和证据支持；
- `INFERRED`：合理推断，但用户尚未确认；
- `UNKNOWN`：目前无法确定；
- `SUPERSEDED`：已被后续明确要求替代。

例如：

用户明确要求“成本尽量低”，这是明确约束。

系统根据用户过去的任务推断“可能希望尽快交付”，则属于推断。

如果当前没有足够证据判断交付期限，应保持未知，而不是自行编造一个截止时间。

### 3.3 目标记录必须可追溯

每个关键目标应尽可能关联：

- 来源消息或任务事件；
- 相关项目决策；
- 用户确认记录；
- 适用的验收标准；
- 后续变更原因。

这样，当用户后续说“我不是这个意思”时，系统可以定位误解发生在哪里，而不是只修改最终答案。

## 四、目标理解的执行流程

建议将目标理解设计为以下流程。

```text
接收用户输入
      ↓
识别明确指令与任务类型
      ↓
提取目标、约束与期望产物
      ↓
读取相关会话、项目与任务状态
      ↓
识别歧义、缺失信息和目标冲突
      ↓
评估推断依据与不确定性
      ↓
判断是否需要澄清
      ↓
建立任务契约与验收标准
      ↓
规划并执行任务
      ↓
验证实际结果
      ↓
判断是否真正满足用户目标
      ↓
交付结果、提出有价值的后续建议
```

这条流程不要求每个任务都执行全部步骤。

简单、低风险、目标明确的任务可以直接进入执行；复杂任务、长期任务和高风险任务则需要更完整的目标建模与验证。

## 五、意图理解与路由的关系

意图识别和专家路由需要协同，但不能完全混为一体。

### 5.1 意图理解负责判断目标

例如，用户提出一个代码问题，系统应理解用户究竟是想：

- 解释代码；
- 修复 Bug；
- 优化性能；
- 设计架构；
- 实现功能；
- 审查安全问题；
- 建立自动化开发工作流。

这些任务可能都属于编程领域，但执行策略、所需工具和验收标准明显不同。

### 5.2 路由负责选择能力

在目标理解完成初步分类后，路由器根据任务要求、风险和可用能力，选择适用的专家、工具与工作流。

不能因为识别到“编程”关键词，就固定调用编程专家的某个工作流。

同样，任务涉及多个领域时，也不应强制只选择一个专家。

### 5.3 允许目标理解与路由迭代

执行过程中可能发现新的事实，使最初的目标解释需要调整。

例如，用户要求提高程序运行速度，但诊断发现程序实际问题是数据库连接失败。

系统可以更新任务计划，将故障排查作为必要步骤，但应保留用户原始目标，并记录计划调整的原因。

如果调整会改变交付范围、成本或用户要求的结果，应主动说明；如果涉及关键目标变更，则应取得必要确认。

## 六、真实需求推断机制

### 6.1 推断依据

推断应优先依赖：

1. 当前用户明确表达；
2. 当前任务中的上下文和限制；
3. 用户已确认的项目决策；
4. 与当前任务直接相关的历史信息；
5. 已验证的领域知识；
6. 有充分依据的常见任务规律。

越靠后的信息，越不能直接覆盖当前明确指令。

### 6.2 推断强度

建议采用四级逻辑状态：

| 状态 | 含义 | 处理方式 |
|---|---|---|
| I1：明确 | 用户已明确表达 | 直接纳入任务契约 |
| I2：高度支持 | 多项相关证据支持同一解释 | 可以作为执行依据，但保留来源 |
| I3：合理可能 | 存在可信解释，但仍有其他可能 | 用于准备建议或可逆计划 |
| I4：未知 | 缺乏足够依据 | 不作为既定目标使用 |

这些状态是决策辅助分类，不是未经校准的概率值。

高风险决策不能只依靠模型输出的主观置信度。需要结合可核验的证据、错误后果和授权要求。

### 6.3 不要过度推断

系统不得因为某个目标常见，就认定当前用户一定具有该目标。

例如：

- 不能因为用户要求优化代码，就默认允许重写整个项目；
- 不能因为用户要求规划旅行，就默认允许预订酒店；
- 不能因为用户讨论工作流，就默认允许访问所有历史文件；
- 不能因为用户希望提高效率，就默认允许增加成本；
- 不能因为用户希望智能体自主，就默认允许执行所有不可逆操作。

合理推断可以帮助准备方案，但不能凭空创造授权。

## 七、歧义与澄清决策

### 7.1 是否询问用户的判断标准

需要综合考虑：

- 不确定性有多大；
- 不同解释会导致多大结果差异；
- 错误选择是否容易撤销；
- 任务是否存在安全风险；
- 用户补充信息的成本；
- 是否存在合理且低风险的默认方案。

### 7.2 三种处理方式

**方式 A：直接执行。**

适用于目标清晰、影响较小、错误容易修正的任务。

**方式 B：说明假设后继续。**

适用于存在轻微歧义，但可以选择合理默认方案且不会造成明显损失的任务。

例如：“我先按保持现有接口兼容、优先修复正确性来优化。”

**方式 C：先询问关键问题。**

适用于不同解释会显著改变交付结果、预算、风险或不可逆动作的任务。

例如，用户要求清理项目文件，但没有说明哪些文件可以删除，系统应先确认删除范围或使用安全的预览模式。

### 7.3 澄清问题必须有价值

不要把所有未知信息都转化为用户需要回答的问题。

优先询问那些会实质改变决策的信息，并尽可能一次解决最关键的歧义。

如果可以通过只读检查、测试或低成本调查消除不确定性，应优先使用这些手段，而不是把所有分析工作推回给用户。

## 八、目标冲突与决策治理

用户可能同时提出多个互相制约的目标。

例如：

- 最高质量；
- 最低成本；
- 最快交付；
- 完全本地运行；
- 高度自主；
- 绝不产生外部副作用。

这些目标未必能够同时达到最优。

### 8.1 冲突分类

建议识别：

- 直接矛盾；
- 资源冲突；
- 时间冲突；
- 风险与收益冲突；
- 用户新旧要求冲突；
- 当前要求与历史决策冲突；
- 任务目标与执行方法冲突。

### 8.2 解决规则

1. 不可违反的安全与权限边界优先；
2. 用户当前明确且合法的任务要求优先于一般历史偏好；
3. 当前任务的核心目标优先于可选的额外优化；
4. 对可以兼容的目标，寻找共同满足的方案；
5. 对无法兼容的目标，说明冲突与取舍；
6. 对重大、不可逆的目标取舍，要求必要确认；
7. 对不影响用户目标的内部执行选择，允许智能体自主决定。

### 8.3 不要擅自把目标变成单一分数

如果用户要求“高质量、低成本、稳定”，系统不能仅靠一个加权分数，让成本改善抵消严重质量退化。

应先满足硬性约束，再在可行方案中比较效率、成本和其他软目标。

这与 #78 的收益归因和 #79 的退化治理保持一致。

## 九、从真实目标到可验收的任务契约

理解目标的最终目的，是让任务可以正确执行和验收。

### 9.1 目标转化结构

每个复杂任务应尽可能形成：

- `objective`：需要实现的结果；
- `constraints`：不能违反的限制；
- `deliverables`：需要交付的产物；
- `acceptance_criteria`：验收条件；
- `assumptions`：当前采用的假设；
- `dependencies`：必要的前置条件；
- `risk_class`：任务风险；
- `budget_ref`：预算约束；
- `authorization_ref`：授权范围；
- `success_evidence`：证明任务成功的证据。

### 9.2 目标不能只描述动作

例如，“调用代码工具”“打开手机应用”“生成视频”都只是动作，不代表用户目标已经实现。

真正的验收应关注结果：

- 代码是否满足要求并通过适用测试；
- 手机操作是否达成预期状态；
- 视频是否生成、可播放并满足验收标准；
- 工作流是否可以重复运行；
- 文档是否覆盖用户要求的范围。

### 9.3 用户目标可以分层验收

复杂任务可能包含多个交付目标。

应分别记录：

- 已完成；
- 部分完成；
- 被阻塞；
- 需要用户确认；
- 未完成；
- 验收未通过。

不能将“执行流程已经跑完”直接等同于“用户目标已经达成”。

## 十、目标变化与任务连续性

用户可能在执行过程中修改目标。

例如，最初要求优化速度，后来又明确要求保持接口不变。

系统应：

1. 记录新的明确要求；
2. 分析对现有计划的影响；
3. 更新任务契约与验收标准；
4. 检查已完成步骤是否仍然有效；
5. 必要时重新规划；
6. 保留历史决策与变更原因；
7. 避免把旧要求与新要求混合成相互矛盾的执行指令。

### 10.1 新旧目标冲突

当用户明确修改目标时，应以新的合法要求为准，并评估已经产生的副作用。

但如果新要求可能导致数据丢失、破坏现有成果或产生重大外部影响，系统应说明后果，并执行必要的确认与安全检查。

### 10.2 长期目标与当前任务

长期目标可以帮助智能体发现更好的路径，但不能无限制地扩大当前任务。

例如，用户的长期目标是建立自主编程智能体，而当前任务只是修复某个测试。

系统可以在修复过程中指出对整体架构有价值的发现，但不应擅自将当前任务扩大为整个架构重构。

## 十一、任务完成后的效果评价

任务验收不仅要判断动作是否完成，还要评估用户真正关心的结果。

### 11.1 四类完成证据

**A. 产物证据**

文件、代码、文档、视频或其他交付物是否存在，格式是否正确。

**B. 功能证据**

产物是否能够实现目标，例如测试通过、流程可运行或结果符合要求。

**C. 约束证据**

用户提出的必要限制是否得到满足。

**D. 结果证据**

任务是否实际解决了问题，是否仍有重要缺口、风险或未完成事项。

### 11.2 防止虚假完成

以下情况不能直接判定任务成功：

- 模型声称已经完成，但没有实际执行证据；
- 工具返回成功，但最终状态不符合要求；
- 文件已生成，但内容不完整；
- 测试通过，但关键验收条件未覆盖；
- 任务步骤完成，但用户的核心目标仍未实现。

如果无法完整验证，应明确说明已经验证的部分与尚未验证的部分。

## 十二、主动建议与目标理解的结合

本专项与 #83 紧密相关。

目标理解不仅帮助智能体执行当前任务，也为主动发现提供依据。

### 12.1 主动发现的三类机会

- **目标缺口：** 当前方案不能充分实现用户目标。
- **实现机会：** 有更好的路径可以达到相同目标。
- **额外价值：** 存在与当前目标密切相关、但不属于必要交付范围的改进机会。

### 12.2 建议的表达方式

有价值的主动建议应说明：

1. 发现了什么；
2. 为什么认为它重要；
3. 有什么证据；
4. 有哪些可行方案；
5. 各方案有什么代价；
6. 是否影响当前任务；
7. 哪些动作需要用户决定。

如果问题明确且建议成本很低，可以简洁提出，不必每次都生成完整报告。

### 12.3 不要混淆必要纠偏与可选增值

如果当前方案无法完成用户目标，纠正方案属于主任务的一部分。

如果当前任务已经可以成功完成，而另有一项值得考虑的长期改进，则属于可选增值。

系统应区分这两类事项，避免把必要工作推迟到用户决定之后，也避免将可选优化强行塞进当前任务。

## 十三、目标理解能力的独立进化

目标理解本身也必须经过评测和迭代。

### 13.1 典型失败模式

- 只理解关键词，忽略真实目标；
- 过度推断用户意图；
- 忽略明确约束；
- 把执行方法误认为最终目标；
- 询问太多无关问题；
- 关键歧义未解决就贸然执行；
- 发现更优方案后擅自替换目标；
- 任务完成后只检查工具调用是否成功；
- 混淆历史偏好与当前明确要求；
- 误将主动建议扩大为自动执行授权。

### 13.2 评测指标

建议重点跟踪：

| 指标 | 评估目的 |
|---|---|
| 目标识别准确率 | 是否正确理解用户直接目标 |
| 约束提取召回率 | 是否遗漏重要约束 |
| 目标误推断率 | 是否将猜测误当成用户需求 |
| 澄清决策准确率 | 是否在真正需要时提问 |
| 无效澄清率 | 是否询问了可以直接解决的问题 |
| 目标偏离率 | 执行过程中是否偏离原目标 |
| 验收契约有效率 | 验收标准是否能够检验真实目标 |
| 虚假完成率 | 是否在目标未达成时声称成功 |
| 主动纠偏收益 | 纠偏是否实际提高结果质量 |
| 目标理解带来的任务改善 | 相较基线是否提高完成质量 |
| 目标分析成本 | 为理解目标额外消耗的资源 |

指标应按任务类型、复杂度、风险等级和专家分别分析。

### 13.3 独立评测与修复流程

目标理解改进应经过：

1. 建立真实案例和失败案例；
2. 生成候选目标理解策略；
3. 使用固定评测集比较候选与基线；
4. 验证约束提取和澄清决策；
5. 检查目标偏离与虚假完成风险；
6. 通过 #75—#79 的适用治理流程；
7. 受控发布并观察实际效果。

候选模型不得通过修改评测答案或降低验收要求来证明自己的目标理解能力更好。

## 十四、与整体自进化架构的关系

| 模块 | 与本专项的关系 |
|---|---|
| 统一任务入口 | 接收用户表达并形成初步任务表示 |
| 目标理解引擎 | 建立目标、约束、假设与歧义模型 |
| 多层路由 | 根据任务目标选择专家和能力 |
| 共享通用内核 | 提供任务状态、规划、验证和上下文治理 |
| 领域专家 | 补充专业目标解释与领域验收标准 |
| #80 根因诊断 | 分析执行失败与目标理解错误 |
| #81 知识治理 | 沉淀经过验证的目标理解经验 |
| #82 上下文治理 | 保留目标、约束和执行状态 |
| #83 主动辅助 | 根据目标识别遗漏、风险和改进机会 |
| #78 收益归因 | 验证目标理解改进是否带来真实收益 |
| #79 发布后治理 | 监测目标理解策略上线后的实际表现 |

完整流程是：

**理解目标 → 明确约束 → 选择执行路径 → 完成任务 → 验收结果 → 识别差距 → 主动纠偏 → 沉淀经验 → 独立验证改进。**

| GOAL-19 | 目标理解策略发生版本变化 | 可追踪、评测和回滚 |

## 十七、完成判定

只有满足以下条件，才能认定本专项实施验收完成：

- 能够区分字面指令、直接目标、推断目标和未知事项；
- 明确约束能够进入可追踪的任务契约；
- 不会将未经确认的猜测当作确定目标；
- 能够合理决定直接执行、说明假设或请求澄清；
- 发现更优方案时能够主动提出意见；
- 不会擅自替换用户目标或扩大授权；
- 能够将复杂目标转换为可验证的验收标准；
- 能够区分动作完成与真实目标达成；
- 目标理解策略能够独立评测、版本化和回滚；
- 所有关键验收用例都有真实执行证据。

**最终目标：让 EvoAgent 不只是听懂用户说了什么，而是尽可能准确地理解用户想实现什么，并以可靠、透明、可验证的方式帮助用户达成目标。它可以提出更好的路径，可以主动纠正明显问题，但必须始终尊重用户的真实目标、明确约束和决策权。**</WritingBlock>

## 下一项专项：#85

建议继续推进 **#85：动态任务分解、执行计划自适应与多工作流协同治理**。

#84 解决的是“究竟应该完成什么”。#85 将解决“怎样以最合适的执行路径完成它”。

重点包括：

- 如何判断任务适合直接执行、固定 DAG，还是动态 Plan；
- 如何根据实时观察调整计划，而不是机械执行最初的步骤；
- 如何在多个专家之间分配子任务；
- 如何识别任务依赖、并行机会和关键路径；
- 如何在执行失败时局部恢复，而不是重做整个任务；
- 如何在质量、时间和预算之间作出有约束的选择；
- 如何保证动态调整不会绕过验收标准、权限边界和回归治理。

这一步将把目标理解真正连接到执行引擎，进一步提升 EvoAgent 在复杂任务中的实际完成能力。
