# 一、先冻结一条总原则：所有模块必须围绕同一个任务事实运行

我认为，EvoAgent 最容易出现的架构风险，不是某个模块不够先进，而是不同模块对同一件事拥有不同的理解。

例如：

- Planner 认为任务已经完成；
- ReAct 认为还需要再执行一次；
- 工具返回成功；
- 验收器发现结果不合格；
- 记忆系统却把任务记为成功；
- 进化系统最终又把它当作一次成功案例。

如果没有统一的状态模型，这种情况完全可能发生。

因此，我建议正式确立：

> **统一任务事实源（Task of Record）+ 模块独立决策 + 统一状态转换 + 独立验收。**

这里的“统一事实源”不代表所有数据都塞进一张数据库表，而是指任务的权威状态、状态变化规则和证据引用必须有明确的归属，其他模块不能各自维护互相矛盾的最终结论。

## 1.1 任务的权威状态应该是什么？


    **Task Record**
    任务 ID、目标、约束、当前状态、计划版本、预算、结果引用


    <grid-item>


        **计划状态**
        当前计划、节点依赖、重规划历史

    </grid-item>
    <grid-item>


        **执行状态**
        工具调用、重试、外部副作用、检查点

    </grid-item>
    <grid-item>


        **验收状态**
        验收规则、验证证据、未满足条件

    </grid-item>
    <grid-item>


        **数据与资产引用**
        记忆、上下文快照、日志、产物和版本

    </grid-item>


每个子系统都可以拥有自己的内部状态，但任务的最终状态必须通过明确的规则归并，而不是任由任意一个模块宣布成功。

例如：

- 工具成功，只能证明工具报告成功；
- 节点完成，只能证明该节点满足自身的完成条件；
- DAG 执行结束，只能证明编排已终止；
- 只有任务验收契约满足要求，任务才能被标记为完全成功。

如果只完成了一部分，应当明确记录部分成功，而不是用一个布尔值掩盖实际情况。

# 二、第二个关键决策：统一能力契约，而不是统一所有专家的实现

我们已经决定，不同专家可以拥有不同的提示词、记忆、技术引擎和规划策略。但如果每个专家都用自己的方式调用工具、保存状态和报告错误，最终仍然会形成多个彼此不兼容的系统。

解决方法不是把所有专家做成一模一样，而是让它们遵守统一的**能力契约（Capability Contract）**。

## 2.1 所有能力都应该声明什么？

无论它是一个 AST 分析器、一个旅游路线算法、一个 FFmpeg 合成器，还是一个可以调用 ReAct 的专家，都应声明：

| 契约内容 | 必须回答的问题 |
|---|---|
| 能力身份 | 它是什么，属于哪个领域，当前版本是什么？ |
| 输入与输出 | 接收什么数据，返回什么结果？ |
| 前置条件 | 执行前需要哪些资源、权限和环境？ |
| 执行语义 | 是只读、可修改、可重复执行，还是会产生外部副作用？ |
| 失败语义 | 可能返回哪些错误，哪些错误可恢复？ |
| 资源需求 | 需要什么模型、工具、网络、内存或 GPU 资源？ |
| 验收方式 | 如何判断该能力正确完成了自己的工作？ |
| 兼容性 | 支持哪些模型、设备、依赖和协议版本？ |
| 安全边界 | 哪些操作允许，哪些操作必须拒绝或申请授权？ |
| 进化策略 | 可以修改哪些部分，必须通过哪些测试？ |

这使系统能够把专业能力当作可组合资产，而不是把它们写死在某个专家的提示词里。

## 2.2 还需要区分四种完全不同的能力






      **工具能力**
      完成一个明确动作。例如读取文件、运行测试、查询路线、合成视频。








      **专业技术能力**
      使用专门算法或技术解决问题。例如 AST、类型检查、约束求解和角色一致性检测。








      **专家能力**
      理解领域目标，选择技术，规划任务并对领域结果负责。








      **工作流能力**
      把多个工具、技术能力和专家节点组织成可重复执行、可验证、可恢复的流程。



这四种能力可以互相组合，但不能混为一谈。

例如，Python AST 是专业技术能力，读取代码文件是工具能力，编程专家负责判断怎样重构，重构工作流则定义读取、分析、修改、测试和验收的步骤。

这套区分将直接决定未来增加新专家、新技术和新工作流时，究竟需要新增配置、实现一个组件，还是修改共享运行时。

# 三、第三个关键决策：ReAct 不是系统的最高控制者

这点需要正式冻结。

我们前面已经确定 ReAct 负责观察、判断、行动和验证。但如果允许 ReAct 无限制地决定所有事情，系统就可能在循环中自行扩大权限、突破预算、修改目标，甚至不断修改自己的执行策略。

因此，我建议明确区分三个控制层。


    <title size="lg">第一层：不可被模型覆盖的系统约束</title>
    权限、用户授权、数据边界、硬性预算、紧急停止、发布门禁和安全规则。



    <title size="lg">第二层：任务控制器</title>
    任务状态、执行调度、超时、重试上限、计划修订、取消和恢复。



    <title size="lg">第三层：智能决策层</title>
    专家推理、ReAct、模型规划、工具选择、动态策略与候选方案生成。


这里的箭头表示约束和控制关系，不是说上层必须由一个独立服务器实现。

### 为什么要这样设计？

假设编程专家连续三次修复失败，决定再调用一次更强的模型。

- 专家可以提出这个方案；
- ReAct 可以分析是否值得尝试；
- 预算控制器检查剩余预算；
- 任务控制器检查重试次数；
- 系统约束检查是否允许访问相关资源。

只有通过这些检查，下一次调用才能执行。

同样，进化系统可以提出修改安全策略的候选方案，但不能仅凭候选评测结果就直接修改自身的硬性权限边界。

**模型负责提出和选择方案，确定性控制层负责执行授权、预算、状态转换和不可绕过的约束。**

## 3.1 还需要明确谁有权修改什么

建议建立变更权限矩阵：

| 修改对象 | 自动候选生成 | 自动发布 |
|---|---|---|
| 专家提示词、低风险策略 | 允许 | 满足门禁且在授权范围内时允许 |
| 记忆检索、上下文压缩策略 | 允许 | 满足专项及跨专家回归门禁时允许 |
| 普通工作流节点与参数 | 允许 | 经过兼容性和安全验证后允许 |
| 工具实现、依赖和执行环境 | 允许提出候选 | 根据风险等级决定，涉及高风险执行时需加强审批 |
| 路由决策策略 | 允许 | 满足路由专项与全局回归门禁时允许 |
| 数据库结构和数据迁移 | 允许提出方案 | 需要迁移测试、备份与明确恢复策略 |
| 安全内核、权限边界、发布机制 | 可以提出建议 | 不允许普通自进化流程直接自动覆盖 |

这样既保留了你希望的高自主性，又不会让“自主进化”变成没有边界的自我修改。

# 四、第四个关键决策：进化系统必须建立完整的证据链

我们之前讨论过日志、自动评测和根因分析。现在要把它们连接起来。

我建议每次值得分析的异常都形成一条**问题证据链**，而不是只保留一条错误日志。

完整链路应该是：

  {#each [
    ["1. 事件","发生了什么？记录实际输入、输出、状态变化和异常。"],
    ["2. 影响","影响了哪个任务、节点、用户目标或系统指标？"],
    ["3. 候选根因","可能涉及哪些组件，支持证据和反证分别是什么？"],
    ["4. 诊断实验","如何区分工具故障、规划错误、记忆问题或模型能力问题？"],
    ["5. 候选改进","具体修改什么，预期改善什么，可能影响哪些其他能力？"],
    ["6. 独立评测","是否改善目标指标，是否引入回归或增加不可接受的成本？"],
    ["7. 发布观察","新版本在真实任务中是否仍然有效？"],
    ["8. 结果归档","保留成功、失败、回滚原因和后续待验证问题。"]
  ] as item}





        **{item[0]}**
        {item[1]}


  {/each}

这里还有一个关键细节：**每条失败记录必须能够追溯到当时运行的组件版本和实际证据。**

否则，几天后系统升级了模型、工具和上下文策略，即使重新执行同一个任务，也未必能复现原来的故障。

## 4.1 诊断不能只依赖事后总结

例如，某个手机操作任务失败，模型总结说“按钮识别错误”。

但真实原因可能是：

- 截图已经过期；
- 无障碍节点树为空；
- 当前界面发生了跳转；
- 点击坐标计算有误；
- 点击实际成功，但结果页面加载较慢；
- 目标 App 的权限状态发生了变化。

这些原因需要不同的修复。

所以问题诊断器应该输出：

- 可能根因及置信程度；
- 支持与反对每个根因的证据；
- 尚缺少哪些信息；
- 建议执行什么验证；
- 若暂时无法确定，如何安全降级。

如果证据不足，允许记录为“根因未确定”。**不允许为了完成诊断而强行生成一个看似合理的原因。**

## 4.2 还需要建立修复效果的因果验证

如果一次失败发生后，系统同时修改了提示词、工具、压缩策略和模型配置，结果有所改善，就很难知道究竟哪项改动起了作用。

因此，对于可分离的问题，应尽量一次验证一个主要假设，或者采用明确设计的对照实验。

当然，真实系统中有些问题必须联合修复，不能机械要求每次只改一个组件。但无论如何，都要记录改动组合、基线、候选和实验结论。

这会让 EvoAgent 的进化从“尝试各种修改，看起来有效就留下”，逐渐转变为有证据支持的工程优化。

# 五、第五个关键决策：版本不能只按模型或 Git 分支管理

之前我们讨论过模型适配档案和 Git 分支。这里需要进一步明确：EvoAgent 的运行行为由很多组件共同决定，单独记录一个模型版本或者一个 Git commit 远远不够。

例如，同一个模型可能搭配：

- 不同的专家提示词；
- 不同的上下文压缩策略；
- 不同的记忆检索配置；
- 不同的路由策略；
- 不同版本的专业技术工具；
- 不同的工作流；
- 不同的验收规则。

它们组合起来才构成实际运行的能力。

## 5.1 引入运行版本清单

建议每次任务运行都关联一份不可变的 `Runtime Manifest`，记录本次运行实际使用的组件组合。

  <title size="lg">Runtime Manifest 示例</title>
  以下为逻辑结构示例，不代表已经实现的数据库格式。
  <CodeBlock language="json" editable>
{
  "manifest_version": "1",
  "runtime_id": "runtime-profile-001",
  "model_adapter_version": "model-adapter-v3",
  "router_policy_version": "router-v5",
  "expert_versions": {
    "coding": "coding-v8"
  },
  "memory_policy_version": "memory-v3",
  "context_policy_version": "context-v6",
  "react_runtime_version": "react-v4",
  "workflow_engine_version": "workflow-v2",
  "tool_versions": {
    "python_ast": "ast-v3",
    "test_runner": "test-runner-v2"
  },
  "evaluation_policy_version": "eval-v4"
}
</CodeBlock>
  实际清单还需要包含可追溯的模型标识、配置摘要、依赖锁定信息、安全策略版本及必要的内容哈希。

这份清单的作用是回答：

- 这次任务究竟使用了哪些版本？
- 某个错误是否只在特定组件组合中出现？
- 升级一个工具后，哪些运行结果需要重新验证？
- 某个稳定版本是否能够恢复？
- 哪些任务受到一次进化发布的影响？

这里有一个重要区别：**版本清单保证可追溯，不保证完全可复现。** 云端模型可能发生服务端变化，外部网站可能改变内容，随机生成和非确定性工具也可能导致结果不同。因此，还需要记录必要的输入引用、环境信息和外部状态，并区分“版本可追溯”“任务可恢复”和“执行可复现”三个目标。

## 5.2 不要为每个专家复制一套完整分支

Git 分支适合管理源代码变更，但不是所有配置和运行结果都适合放在 Git 中。

建议将不同类型的资产分开管理：

| 资产类型 | 推荐的管理方式 |
|---|---|
| 核心运行时代码、工具实现 | Git 分支、提交、标签 |
| 专家提示词与策略配置 | 版本化配置资产 |
| 模型适配档案 | 模型配置仓库与评测记录 |
| 记忆和任务状态 | 数据库、事件记录和备份 |
| 工作流定义 | 版本化工作流资产 |
| 评测集与评测结果 | 数据版本与实验记录 |
| 运行日志和原始证据 | 日志存储、对象存储和索引 |
| 生产版本清单 | 发布系统维护的不可变版本记录 |

这样，旅游专家的提示词改进不会导致编程专家的整个源代码分支被复制；如果它修改了共享路由器，系统才根据依赖图要求对其他专家进行回归测试。

## 5.3 版本兼容性必须有明确策略

假设手机离线一周，重新联网后发现服务器已经发布了新版工作流。

不能简单地让手机自动把旧任务切换到新版本，因为旧任务的状态结构、节点语义和工具依赖可能发生变化。

建议区分：

- 新任务默认使用哪个稳定版本；
- 运行中的任务是否固定原版本；
- 原版本不可用时，是否允许安全迁移；
- 数据库和协议是否向后兼容；
- 哪些升级需要重新执行验收；
- 什么时候允许淘汰旧版本。

对于正在执行的任务，默认应当固定运行版本；只有经过兼容性验证、明确允许迁移的任务，才可以切换版本继续执行。

# 六、第六个关键决策：架构本身也必须有变更治理

现在我们已经拥有大量模块和设计原则。如果以后每次讨论都可以随意修改核心架构，项目仍然会回到功能不断变化、工程反复重做的状态。

所以，架构冻结不应该意味着“以后不能改”，而应该意味着：

**明确哪些是稳定契约，哪些是可替换实现，哪些变更需要重新评审。**

## 6.1 建立四类架构决策






      **A 类：核心不变量**
      例如权限边界不能被模型绕过、任务状态必须可追溯、自动发布必须经过门禁。这些只能通过正式的高等级架构变更修改。








      **B 类：稳定接口契约**
      例如能力调用协议、任务状态语义、日志关联规则。实现可以替换，但必须保持兼容或提供明确迁移方案。








      **C 类：可进化策略**
      例如提示词、路由排序、压缩策略、规划深度和低风险重试策略。可以在规定范围内自动实验和发布。








      **D 类：实验性实现**
      例如新的记忆检索算法、新的路由分类器或新的工作流生成方法。先在实验环境中验证，成熟后再纳入稳定契约。



这四类不是永久不变的标签。一个实验性组件可以成熟为稳定实现；一个原本低风险的策略，如果开始影响权限或外部副作用，就需要升级其变更等级。

## 6.2 每次架构变更都要回答六个问题

1. 现有设计具体在哪个场景中失败？
2. 有哪些证据证明问题来自架构，而不只是实现缺陷？
3. 修改会影响哪些模块、数据、任务和版本？
4. 是否有更小范围的修复方案？
5. 需要哪些测试、迁移、灰度和回滚措施？
6. 什么证据足以证明这次变更值得接受？

这可以避免为了一个局部问题重做整个系统，也能避免因为短期实现方便而破坏未来扩展能力。

# 七、把这些决策整合成一份真正可冻结的基线

经过这一轮，我们可以把 EvoAgent 的架构原则收敛为以下 12 项。它们比具体使用哪个框架、数据库或模型更重要，因为技术选型可以调整，而核心职责和状态契约一旦设计混乱，后续成本会很高。

## 八、接下来应该怎么推进？

我不建议现在马上进入编码，也不建议继续无目标地增加更多模块。接下来应该完成一轮更偏工程落地的设计审查。

我建议按以下顺序推进：

  **统一领域模型与数据字典。** 定义 Task、Plan、DAG Node、Execution、Evidence、Memory、Context Snapshot、Capability、Expert、Artifact、Evaluation、Release 等核心实体，以及它们的关联关系。
  **定义统一状态机。** 明确任务从创建、规划、执行、等待、暂停、失败、部分成功、验收和终止的全部状态，以及每种状态允许的转换。
  **定义能力接口和错误协议。** 明确专家如何调用专业技术，ReAct 如何执行工具，工具失败如何分类，验收器如何返回证据。
  **定义进化实验与发布协议。** 明确候选如何创建、评测如何独立运行、依赖如何分析、灰度如何执行，以及回滚如何保证数据和任务状态一致。
  **最后冻结技术选型与部署边界。** 再根据 Android 本地执行、云端模型 API、数据持久化、专业技术运行环境和资源预算，确定工程目录、服务边界和实际技术栈。

其中，第一步最重要。因为只要任务、状态、能力和证据的数据模型确定，专家路由、记忆、上下文、ReAct、DAG、专业技术和进化系统就能围绕同一套契约实现。

**我的判断是：EvoAgent 目前最缺少的不是新的智能体功能，而是把已有架构收敛成统一的领域模型、状态机、能力契约和进化协议。**

完成这四项之后，才算真正具备架构冻结的基础。后续无论增加编程专家、旅游专家、AI 漫剧能力，还是更换大语言模型，都应该优先通过新增或替换能力组件完成，而不是反复重做整个系统。
