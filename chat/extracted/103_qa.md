# EvoAgent 第五十一专项：多专家协作、动态组队与跨专家任务交接

本轮研究 EvoAgent 从“拥有多个独立专家”，走向“多个专家能够协同完成复杂任务”的核心架构。

此前已经设计了多专家系统、统一 Router、Plan、ReAct、DAG、能力资产 CEKCE、质量验收 UQEAG、目标价值评估 GVAAG、人机协作 HACCG，以及故障诊断、版本治理和任务恢复机制。

但这些设计还留下一个关键问题：

**当一个任务需要多个专家共同完成时，究竟由谁组织它们？它们如何分工、通信、处理冲突，并最终对整体结果负责？**

例如，AI 漫剧制作任务可能需要编剧、分镜、视觉生成、配音、视频合成和质量评测等能力。如果每个专家只是独立接收一段指令，系统很容易出现：

- 前一个专家输出的格式不符合后一个专家的要求；
- 多个专家重复分析相同问题，浪费模型调用和计算资源；
- 一个专家修改了方案，其他专家仍然使用旧版本；
- 专家之间给出相互矛盾的结论，却没有明确的裁决机制；
- 某个关键专家失败，导致整个任务无法继续；
- 每个专家都认为自己完成了工作，但没有任何模块对最终产物负责；
- 专家数量越多，通信成本越高，整体质量反而下降。

因此，建议将本专项定义为：

**Multi-Expert Orchestration & Dynamic Teaming，简称 MEODT。**

它负责多专家团队的组建、分工、协作协议、信息共享、冲突解决、动态调整、交接、故障恢复与团队级质量验收。

本专项最重要的原则是：

**不是所有复杂任务都需要多个专家。只有当专业分工、并行执行或独立审查所带来的收益，大于协调成本和新增风险时，才应该组建专家团队。**

# 一、第一性原理：专家数量不等于协作能力

先区分三个概念。

- **专家能力：** 某个专家擅长完成什么工作。
- **任务编排：** 整个任务应该分解成哪些步骤、有哪些依赖关系。
- **团队协作：** 多个专家如何共同执行这些步骤，交换必要信息，并对整体结果形成一致判断。

这三者不能互相替代。

一个编程专家可以调用 AST 分析、测试和静态检查等多个技能，但不一定需要组成多个独立专家。反过来，一个复杂的代码重构任务也可能需要代码分析专家、架构专家和独立审查专家协作。

同样，DAG 可以描述任务节点之间的依赖关系，却不能单独解决专家之间的责任归属、通信冲突、共享上下文和协作失败问题。

但协作也有代价：

- 专家之间需要传递信息；
- 不同专家可能采用不同的假设；
- 输出格式和质量标准可能不一致；
- 并行执行可能产生额外资源消耗；
- 团队协调本身也可能失败。

因此，团队是否值得组建，应该由 GVAAG 结合任务价值、成本、风险与成功概率评估，而不是由任务复杂度单独决定。

## 1.2 建立协作收益判断

可以用一个简化模型辅助判断：

\[
\Delta V_{\text{team}}
=
B_{\text{specialization}}
+B_{\text{parallelism}}
+B_{\text{verification}}
-C_{\text{coordination}}
-C_{\text{resources}}
-R_{\text{interaction}}
\]

其中：

- \(B_{\text{specialization}}\)：专业互补带来的收益；
- \(B_{\text{parallelism}}\)：并行执行带来的收益；
- \(B_{\text{verification}}\)：独立审查带来的收益；
- \(C_{\text{coordination}}\)：协调、通信和交接成本；
- \(C_{\text{resources}}\)：新增模型调用、计算和外部服务成本；
- \(R_{\text{interaction}}\)：协作产生的冲突、错误传播和副作用风险。

这不是精确的数学定律，而是一个决策框架。

对于简单任务，一个专家通常就足够。对于需要多个专业领域、可以并行处理且结果需要独立审查的任务，多专家团队可能具有明显优势。

**默认从最小团队开始，只在有证据表明需要时增加专家。**

## 2.1 协调器不等于一个必须存在的“总指挥模型”

MEODT 的协调器可以由不同实现组成：

- 一个规则与状态机驱动的协调服务；
- 一个负责复杂任务分解的协调智能体；
- 一个基于 DAG 的确定性编排器；
- 或者由上述几种机制组合而成。

简单任务可以完全使用确定性编排，不需要额外调用协调模型。

复杂任务则可以由协调智能体提出方案，但最终的任务依赖、授权、预算和状态变更仍然需要由可验证的控制逻辑执行。

这能够避免团队中出现一个新的万能智能体，导致所有决策再次集中到一个难以审计的模型里。

## 3.2 如何选择协作模式？

建议由协调器按照以下顺序判断：

1. 单个专家能否在合理成本内完成任务？
2. 是否存在真正独立的子任务？
3. 是否存在必须由不同专业能力承担的阶段？
4. 是否需要独立评审来降低关键错误风险？
5. 是否有足够的资源支持并行？
6. 多专家带来的收益是否超过协调成本？
7. 失败时是否能够安全恢复或替换专家？

如果没有明确的协作收益，就使用单专家模式。

如果只是需要调用多个工具，不应该为了体现多专家架构而强行拆成多个智能体。

# 四、专家角色模型：谁负责执行，谁负责协调，谁负责验收？

在团队中，领域专家和团队角色不是同一回事。

例如，编程专家可以在一个任务中负责实施，在另一个任务中负责审查。协调器也可以是一个独立的轻量服务，而不是一个领域专家。

建议把团队成员定义为具有明确角色的 `TeamMember`。

## 4.1 建议的团队角色

| 角色 | 主要职责 |
|---|---|
| `COORDINATOR` | 组织团队、分配任务、跟踪依赖和处理交接 |
| `SPECIALIST` | 提供领域知识与专业产物 |
| `EXECUTOR` | 在授权范围内执行具体操作 |
| `RESEARCHER` | 搜集信息、验证来源、提出候选方案 |
| `REVIEWER` | 独立检查产物、假设和证据 |
| `INTEGRATOR` | 合并不同专家的输出，解决格式与接口问题 |
| `OBSERVER` | 观察进度、成本、风险与异常，不直接修改目标产物 |

这些角色可以由不同的智能体实例承担，也可以由一个专家在不同阶段切换角色。

但对高风险任务，应避免同一个执行实例同时负责实施、独立评审和最终批准，以降低自我验证的偏差。

## 4.2 团队成员需要明确责任边界

建议每个成员都具有：

- `member_id`：团队内唯一标识；
- `expert_id`：所属专家；
- `role`：当前团队角色；
- `owned_tasks`：负责的任务；
- `input_contract`：接收信息的格式；
- `output_contract`：交付产物的格式；
- `allowed_resources`：允许访问的资源；
- `budget_quota`：资源配额；
- `completion_criteria`：完成条件；
- `failure_policy`：失败时的处理策略；
- `reporting_policy`：需要汇报哪些事件。

这使得协调器可以准确判断某个成员是否完成任务，以及其结果能否进入下一个节点。

## 4.3 责任不能因为多人协作而消失

多专家系统容易出现一个问题：每个专家都完成了自己的局部任务，但整个项目没有人对最终结果负责。

建议采用明确的责任模型：

- 每个子任务有唯一的责任主体；
- 每个共享产物有明确的所有者；
- 每个团队有唯一的整体协调责任主体；
- 最终交付必须经过 UQEAG 的团队级验收；
- 涉及用户授权或重大副作用的操作，仍由独立治理规则决定是否需要用户批准。

整体责任主体负责保证协作闭环，但不能代替实际的质量验收。

# 五、与 Planner、DAG、ReAct 的关系：不能把架构混成一团

这是多专家架构必须明确的边界。

| 组件 | 回答的问题 |
|---|---|
| GVAAG | 这项任务是否值得做？是否获得授权？ |
| Router | 哪个专家或处理路径最适合？ |
| MEODT | 是否需要多个专家？团队如何分工与协作？ |
| Planner | 应该采取什么计划？ |
| DAG | 任务之间有哪些依赖、并行和汇合关系？ |
| ReAct | 当前执行步骤如何根据观察结果动态调整？ |
| TERSO | 工具如何被安全、可靠地执行？ |
| UQEAG | 任务产物是否达到验收标准？ |
| LTAR | 任务状态如何持久化、暂停、恢复和终止？ |

这里有一条重要原则：

**团队协作不替代 DAG，DAG 也不替代团队协调。**

DAG 描述任务节点及依赖；MEODT 管理专家如何承担这些节点、如何通信、何时交接，以及发生冲突时由谁处理。

例如，一个 DAG 节点可以分配给编程专家执行，而另一个节点分配给审查专家验证。两个专家的交接和责任由 MEODT 管理，节点之间的执行依赖由 DAG 管理。

对于动态任务，协调器可以请求修改 DAG，但必须经过明确的计划变更、预算检查和授权检查，不能直接在执行过程中任意增加任务。

---

# 六、团队协作协议：专家之间应该交换什么信息？

这是决定多专家系统是否稳定的关键。

如果专家之间只传递自然语言对话，系统会很难确定某个结论究竟是事实、假设、建议，还是已经验证的结果。

例如，编程专家说：

“这个重构方案应该没有问题。”

对于后续专家来说，这句话缺少关键信息：它基于什么代码版本？运行过哪些测试？哪些行为尚未验证？是否存在已知风险？

因此，建议建立统一的 `TeamMessageProtocol` 和 `WorkPackageContract`。

## 6.1 任务交接不能只传递一段提示词

每个子任务应通过结构化工作包进行交接。

| 字段 | 作用 |
|---|---|
| `work_package_id` | 工作包唯一标识 |
| `team_id` | 所属团队 |
| `task_id` | 关联的主任务 |
| `goal_ref` | 上级目标与验收契约 |
| `assigned_member` | 当前责任成员 |
| `input_artifacts` | 输入产物及版本 |
| `required_outputs` | 必须交付的结果 |
| `constraints` | 范围、预算、时间和禁止事项 |
| `dependencies` | 前置工作与依赖 |
| `completion_criteria` | 明确的完成条件 |
| `evidence_requirements` | 必须提供的证据 |
| `handoff_status` | 当前交接状态 |

这样，下游专家不需要重新阅读全部历史对话，就能知道自己接收的工作是什么。

## 6.2 统一团队消息类型

建议至少定义以下消息类型：

- `TASK_ASSIGNMENT`：分派任务；
- `STATUS_UPDATE`：汇报进度；
- `ARTIFACT_READY`：通知产物已经生成；
- `HANDOFF_REQUEST`：请求交接；
- `BLOCKER_REPORTED`：报告阻塞；
- `EVIDENCE_SUBMITTED`：提交验证证据；
- `CONFLICT_RAISED`：提出结论或产物冲突；
- `REPLAN_REQUEST`：请求重新规划；
- `BUDGET_WARNING`：资源消耗达到预警阈值；
- `TASK_COMPLETED`：报告子任务完成；
- `TASK_FAILED`：报告任务失败。

消息应有唯一标识、来源、目标、关联任务、时间和版本信息。

重要的状态变更必须持久化，不能只存在于某个模型的临时对话上下文中。

## 6.3 消息与产物分离

专家可以在消息中说明某个结果已经生成，但实际产物应保存在可引用、可版本化的存储中。

例如，消息可以引用：

- 代码差异；
- 研究报告；
- 分镜清单；
- 视频文件；
- 测试报告；
- 验收证据。

消息负责通知和解释，产物负责保存实际内容。

这样可以减少重复传输大型文件，也能避免多个专家各自持有内容略有不同的副本。

---

# 七、共享上下文：团队应该共享多少信息？

多专家协作并不意味着所有专家共享完整对话、全部记忆和全部工具输出。

共享太少，会导致专家缺少必要背景；共享太多，则会增加成本、信息噪声、隐私暴露和上下文冲突。

建议将团队上下文分成四层。

<box border radius="xl" padding={3} gap={3}>
  <box gap={1}>
    <title size="md">T0 · 团队公共上下文</title>
    <text color="secondary" size="sm">主目标、任务约束、验收契约、团队分工、当前版本、共同决策和关键风险。</text>
  </box>
  <divider color="subtle"/>
  <box gap={1}>
    <title size="md">T1 · 任务相关上下文</title>
    <text color="secondary" size="sm">某个工作包的输入、必要历史、依赖产物、相关证据和局部决策。</text>
  </box>
  <divider color="subtle"/>
  <box gap={1}>
    <title size="md">T2 · 专家私有上下文</title>
    <text color="secondary" size="sm">专家自己的领域推理、专属记忆、内部策略与不需要向团队传播的细节。</text>
  </box>
  <divider color="subtle"/>
  <box gap={1}>
    <title size="md">T3 · 证据与产物存储</title>
    <text color="secondary" size="sm">完整日志、文件、测试报告、引用来源、版本化产物和必要的审计记录，按需检索。</text>
  </box>
</box>

## 7.1 公共上下文只保留对协作有用的信息

团队公共上下文不应该成为所有专家输出的拼接集合。

它应优先包含：

- 当前有效的目标和约束；
- 每个成员的职责；
- 已经确认的关键事实；
- 已经批准的方案；
- 尚未解决的冲突；
- 关键产物的版本；
- 当前风险和资源状态。

冗长的推理过程、重复的工具日志和与当前任务无关的记忆，应保存在相应的私有上下文或证据存储中。

## 7.2 上下文压缩必须保留协作关键状态

如果 ACMO 对团队上下文进行压缩，必须保留：

- 未完成工作；
- 关键决策及其依据；
- 产物版本；
- 依赖关系；
- 未解决的分歧；
- 用户的有效约束；
- 当前授权状态；
- 预算与截止条件。

不能只保留一段自然语言摘要，然后丢失哪些结论已经验证、哪些只是猜测。

## 7.3 共享上下文不能自动扩大权限

专家能够看到某个文件，不代表它有权修改该文件。

专家收到其他成员的工具调用记录，也不代表它获得了执行相同操作的授权。

因此，团队上下文和能力资产必须与独立的权限检查机制分离。

---

# 八、产物所有权与并发冲突：谁可以修改什么？

这是多专家并行执行时非常容易出现的问题。

例如，两个专家同时修改同一个代码模块；或者一个专家正在更新分镜，另一个专家仍然依据旧分镜生成素材。

如果没有明确的产物所有权与版本协议，团队可能产生相互覆盖、重复工作和难以追溯的结果。

建议建立 `ArtifactOwnershipPolicy`。

## 8.1 默认采用单一写入者

对于同一份共享产物，建议默认只有一个责任主体能够提交正式修改。

其他专家可以：

- 读取当前版本；
- 提交修改建议；
- 生成独立分支；
- 在隔离环境中进行候选修改。

但正式合并应经过明确的版本检查与集成流程。

例如，两个代码专家可以分别生成不同的补丁，但不能无协调地同时覆盖同一份工作目录。

## 8.2 使用版本校验防止陈旧输入

每个工作包都应声明输入产物的版本。

如果下游专家开始工作后，上游产物已经更新，系统应判断：

- 新版本是否与原版本兼容；
- 当前工作是否依赖已经变化的内容；
- 是否需要重新运行相关步骤；
- 原有输出是否仍然有效。

不能简单地把最新产物覆盖到所有专家的输入中，却不检查依赖关系。

## 8.3 集成专家不能替代质量验收

集成专家负责合并产物、解决格式与接口冲突，并形成候选的最终结果。

但它不应因为成功合并所有文件，就直接宣称整体任务合格。

最终产物仍然需要经过 UQEAG 的团队级验收；高风险或关键任务还可以增加独立审查。

---

# 九、专家冲突：多个专家给出不同结论时怎么办？

多专家协作不能假定所有专家都会达成一致。

它们可能因为知识不同、输入版本不同、目标权重不同，或者评测方法不同而产生分歧。

例如：

- 架构专家建议拆分服务，成本专家认为当前项目不值得增加服务；
- 编程专家认为代码修改完成，审查专家发现回归风险；
- 视觉专家建议重新生成角色素材，视频工程专家认为可以通过后期处理解决；
- 两个研究专家引用了不同时间的资料，得出相互矛盾的结论。

如果系统仅采用多数投票，可能会选择一个错误的方案；如果总是听从主管智能体，也可能放大主管本身的判断偏差。

建议建立 `ConflictResolutionEngine`。

## 9.1 首先区分四种冲突

| 冲突类型 | 示例 | 处理方法 |
|---|---|---|
| 事实冲突 | 两个专家对同一事实给出不同结论 | 核对来源、时间和证据 |
| 方案冲突 | 两种实现路径都可行 | 比较成本、风险、收益与约束 |
| 产物冲突 | 两个专家修改了同一文件或数据 | 依据所有权、版本和集成规则解决 |
| 目标冲突 | 某个专家的方案违反用户的原始约束 | 回到有效目标与授权，不以投票覆盖 |

这四类冲突不能采用同一种解决方式。

## 9.2 建议的冲突处理流程

<box border radius="xl" padding={3} gap={2}>
  {#each [
    ["1. 检测冲突","识别互相矛盾的结论、产物版本或执行约束。"],
    ["2. 统一比较条件","检查专家是否使用了相同目标、输入版本和验收标准。"],
    ["3. 收集证据","要求相关专家提供来源、测试结果、成本估计和适用边界。"],
    ["4. 判断是否可消解","通过补充调查、重新运行测试或合并方案解决。"],
    ["5. 按冲突类型裁决","事实问题优先核验；方案问题按目标与约束比较；权限问题交给安全治理。"],
    ["6. 记录决策与异议","保留最终选择、依据、未解决的不确定性和后续验证条件。"]
  ] as item}
    <box gap={1}>
      <title size="md">{item[0]}</title>
      <text color="secondary" size="sm">{item[1]}</text>
    </box>
    {#if item[0]!=="6. 记录决策与异议"}
      <divider color="subtle"/>
    {/if}
  {/each}
</box>

## 9.3 不要让多数投票替代证据

三个专家重复同一个来源，并不等于有三份独立证据。

同一个基础模型在三个不同角色提示下给出相同答案，也不意味着得到了真正独立的验证。

对于事实性或高风险结论，应优先检查证据来源和验证方式的独立性，而不是简单统计专家数量。

对于方案选择，则可以综合比较各自的预期收益、成本、风险和适用条件。

## 9.4 重大冲突应允许升级到用户

当存在多个合理方案，但它们在成本、产品方向或用户偏好上有实质性差异时，系统应通过 HACCG 向用户展示关键差异，而不是无限组织专家讨论。

如果冲突涉及强制安全约束，协调器也不能通过团队投票改变规则。

**专家可以对方案提出异议，但不能通过协商创造新的权限。**

# 十、动态组队：什么时候增加、替换或移除专家？

静态团队容易理解，但复杂任务可能在执行过程中不断出现新问题。

例如，编程专家最初判断只是局部代码修改，后来发现问题来自数据库事务设计，需要架构专家加入；又或者某个外部模型服务不可用，需要替换相关执行专家。

因此，MEODT 需要支持动态组队，但必须避免团队规模不断膨胀。

建议建立 `TeamReconfigurationPolicy`。

## 10.1 允许动态调整的触发条件

- 发现现有团队缺少必要的专业能力；
- 某个专家反复无法完成任务；
- 任务目标发生实质性变化；
- 新证据改变了任务分解方式；
- 当前团队资源不足；
- 某个阶段需要独立审查；
- 某个专家不再有未完成工作；
- 继续保留某个成员的协调成本已经超过其预期收益。

## 10.2 增加专家前必须回答三个问题

1. 新专家是否拥有当前团队缺少的能力？
2. 它是否能够利用已有产物和契约，而不需要重复整个任务？
3. 增加它是否会产生足够的预期收益，抵消上下文、通信和执行成本？

如果新专家只是重复现有专家已经完成的工作，而且没有独立验证或替代价值，就不应该加入。

## 10.3 专家退出不能丢失责任

当一个成员退出团队时，必须处理：

- 未完成的工作包；
- 尚未提交的产物；
- 正在运行的工具；
- 已占用的资源；
- 需要交接的决策与证据；
- 其他成员对它的依赖。

协调器应将任务重新分配、保留为待办，或者明确终止，而不是直接删除成员记录。

## 10.4 动态组队必须受预算约束

建议为每个团队设置：

- 最大并发成员数；
- 最大模型调用量；
- 总预算上限；
- 每个成员的资源配额；
- 最大重规划次数；
- 最大冲突处理轮数；
- 最大返工次数。

具体数值应根据任务类型和设备能力配置，而不是在全局硬编码一个适用于所有场景的数字。

对于个人电脑或微型 Linux 主机，还应考虑内存、GPU、并发模型调用和后台任务对前台交互的影响。

---

# 十一、专家失败与团队恢复：一个成员失败，不应该让整个任务失去进度

多专家系统必须能够处理局部失败。

例如，漫剧制作中的配音专家暂时无法访问外部服务，但分镜、视觉素材和故事脚本都已完成。如果整个任务因此重新开始，就会浪费大量资源。

建议建立 `TeamRecoveryManager`，与 LTAR、TERSO、SOCDEA 和 UQEAG 协作。

## 11.1 将失败分为五类

| 失败类型 | 典型情况 | 默认处理 |
|---|---|---|
| 成员执行失败 | 某专家输出格式错误 | 修复或有限重试 |
| 能力不可用 | 所需工具或模型不可用 | 使用兼容替代能力或等待 |
| 交接失败 | 输入产物缺失、版本不匹配 | 重新核验契约和依赖 |
| 协作失败 | 冲突无法解决、责任不明确 | 暂停相关节点，升级协调 |
| 团队级失败 | 关键目标无法达成、预算耗尽 | 诊断、调整范围、请求用户决策或终止 |

这些失败需要不同的恢复策略，不能全部交给一个无限重试循环。

## 11.2 从检查点恢复，而不是从头重做

团队需要保存：

- 已完成工作包；
- 当前产物版本；
- 已验证的证据；
- 未完成的依赖；
- 当前团队成员与角色；
- 资源消耗；
- 尚未解决的冲突；
- 当前有效的目标、授权和预算。

恢复时，协调器应判断哪些节点仍然有效，哪些需要重新执行。

如果只是在替换配音专家，而脚本和画面素材没有变化，就不应该无条件重新生成所有视觉素材。

如果上游分镜发生变化，则依赖它的素材生成和合成步骤可能需要重新执行。

## 11.3 替代专家必须满足契约兼容

不能仅因为两个专家都属于“编程专家”就认为它们可以互换。

替代成员需要满足：

- 工作包输入输出契约；
- 必要的专业能力；
- 所需工具和权限；
- 当前运行环境；
- 质量验收要求；
- 剩余预算与时间约束。

如果替代专家的输出格式不同，需要通过经过验证的适配器进行转换，而不是直接将其结果交给下游。

## 11.4 局部恢复不能绕过最终验收

即使所有失败节点都已经重新运行，最终结果仍可能不合格。

因此，团队恢复完成后，应根据受影响的产物和依赖关系执行必要的回归验证，并由 UQEAG 决定是否通过。

---

# 十二、团队级质量评测：评价协作结果，而不是成员数量

多专家系统最容易出现的错误之一，是把“所有成员都完成任务”当成“团队完成任务”。

实际上，团队可能发生：

- 子任务之间不兼容；
- 关键要求无人负责；
- 多个成员重复工作；
- 产物整合失败；
- 冲突被隐藏；
- 最终结果缺少必要证据。

因此，建议建立 `TeamEvaluationProfile`。

## 12.1 团队质量的六个维度

| 维度 | 评估内容 |
|---|---|
| 目标完成度 | 整体交付是否满足主任务要求 |
| 协作正确性 | 工作包、依赖、交接和产物版本是否正确 |
| 专业质量 | 各领域产物是否达到相应的验收标准 |
| 协作效率 | 相比单专家基线，是否减少时间或提高质量 |
| 资源效率 | 新增协调和并行执行的成本是否合理 |
| 故障恢复能力 | 成员失败、工具异常和任务变更后能否恢复 |

其中，最终交付质量仍由 UQEAG 的验收契约决定。团队评测不能取代最终验收，也不能通过多个成员的平均分掩盖某个关键子任务的严重缺陷。

## 12.2 团队评测应当与单专家基线比较

对于适合比较的任务，建议在评测集上对照：

- 单专家执行；
- 多专家顺序交接；
- 多专家并行执行；
- 多专家加独立评审。

比较质量、延迟、成本、失败率和恢复表现。

如果多专家模式并没有稳定的质量或效率优势，就应考虑简化团队拓扑。

## 12.3 评测团队协作是否真正减少了错误

不能只统计专家数量、通信次数和子任务完成率。

更重要的是：

- 是否发现了单专家容易遗漏的问题；
- 是否减少了重复劳动；
- 是否降低了接口错误；
- 是否缩短了关键路径；
- 是否提升了最终产物质量；
- 是否增加了新的错误传播路径。

团队协作的价值应通过结果证明，而不是通过系统结构的复杂程度证明。

# 十三、与现有架构的集成关系

MEODT 必须与前面设计的系统模块形成稳定的职责边界。

| 模块 | 协作关系 |
|---|---|
| Router | 选择领域专家或初始处理路径 |
| GVAAG | 决定目标是否值得执行，以及组队的预期价值 |
| CEKCE / CIL | 提供可复用的专家能力、技能和工作流 |
| Planner / DAG | 规划子任务、依赖关系和执行顺序 |
| ReAct | 处理成员内部的动态执行与观察 |
| TERSO | 执行工具调用和控制副作用 |
| MTSRIC / ARCBG | 管理团队并发、资源配额和总预算 |
| ACMO / MEEG / CLEK | 提供上下文、记忆与知识检索 |
| UQEAG | 验收团队产物和整体交付结果 |
| LTAR | 持久化团队任务、检查点、暂停与恢复状态 |
| SOCDEA | 诊断协作失败、交接错误和无效重复工作 |
| HACCG | 处理用户确认、目标变更、暂停、取消和人工接管 |
| CGVCM | 管理团队协议、契约和依赖版本 |
| SELCIA | 管理经过验证的团队策略改进及受控发布 |

需要特别明确：

**MEODT 负责组织专家协作，不负责自行决定所有专家的目标、权限、资源和验收标准。**

这些职责仍由相应的治理模块承担。

# 十六、下一专项：全局事件总线、运行可观测性与因果追踪

多专家协作解决了多个专家如何共同完成任务的问题，但也让系统的运行链路变得更加复杂。

当一个任务涉及 Router、多个专家、DAG、工具、记忆、质量验收和进化控制器时，如果最终结果失败，系统必须能够回答：

- 用户的原始请求是什么？
- 为什么选择了这个专家和这条执行路径？
- 哪些决策改变了任务方向？
- 哪个专家产生了问题，问题又如何传播到其他节点？
- 哪些工具实际执行了操作？
- 任务为什么暂停、恢复或重新规划？
- 哪个版本的能力、模型和配置参与了执行？
- 这次失败究竟来自执行、协作、评测还是治理？
- 手机与主机断联期间发生了什么，恢复连接后如何还原完整过程？

如果没有统一的事件与追踪体系，SOCDEA 很难进行可靠的根因诊断，UQEAG 也难以判断验收证据是否可信，CEKCE 更无法准确判断一项能力是否真的进步。

因此，下一专项建议定义为：

**Global Event & Causal Observability，简称 GECO。**

重点研究：

1. 如何建立跨模块统一事件模型与事件总线；
2. 如何关联用户请求、目标、任务、DAG 节点、专家、工具和产物；
3. 如何区分事件、状态、日志、指标、追踪与因果关系；
4. 如何重建一次任务的完整执行时间线；
5. 如何在多专家并行、重试和跨设备执行中保持事件关联；
6. 如何在断网、崩溃和重复消息情况下保证事件可靠记录；
7. 如何利用事件数据支持 SOCDEA 的根因分析；
8. 如何向 UQEAG 提供可追溯的验收证据；
9. 如何评估 Router、专家、工作流和技能的真实运行表现；
10. 如何在个人电脑或微型 Linux 主机的有限资源下控制日志存储和追踪开销；
11. 如何管理日志脱敏、敏感信息访问和审计权限；
12. 如何利用历史事件回放复现故障，而不重复执行真实外部副作用。

本专项的核心原则是：

**系统不仅要知道最终发生了什么，还要能够重建关键决策、实际执行、状态变化与结果之间的关系，并明确哪些因果结论已经得到验证、哪些仍然只是推测。**

这将为 EvoAgent 的任务恢复、质量评测、根因诊断、能力进化和多专家协作建立统一的运行事实基础。
