# EvoAgent 第五十五专项：自适应性能、资源调度与成本优化

<text color="secondary" size="sm">APRO · Adaptive Performance & Resource Optimization</text>

前面已经完成了可靠性专项 RERA 的架构设计。现在进入 APRO，解决 EvoAgent 在个人设备上长期运行时的性能与资源问题。

你的部署方向有一个很重要的特点：**以个人电脑、Android 手机和微型 Linux 主机为核心，不假设存在一台始终在线、资源无限的中央服务器。**

因此，EvoAgent 不能简单照搬大型云端智能体的架构。它必须学会根据设备能力、任务难度、质量要求和当前负载，动态决定该使用什么模型、多少个专家、怎样执行 DAG，以及哪些工作应当延迟。

APRO 的目标不是单纯减少 Token，也不是让所有任务尽可能快，而是：

**在满足任务质量、安全、可靠性和用户授权要求的前提下，尽量用更少的时间、计算资源和金钱完成任务。**

例如，同样是代码任务：

- 修改一个变量名，不需要启动多个专家；
- 重构一个复杂模块，可能需要 AST 分析、测试专家和独立代码审查；
- 生成 60 秒动态漫剧，可能需要大量云端生成预算和本地视频合成资源；
- 手机正在发热或内存不足时，不应该强行运行多个本地模型；
- 服务器断网时，应优先选择本地可执行的能力，而不是反复请求已经不可用的服务。

这些场景不能依靠一套固定的模型选择规则解决。它们需要一个能够感知资源、预测成本、控制并发并从实际执行结果中学习的系统。

# 一、第一性原理：优化整个任务，而不是孤立的模块

APRO 首先要避免五种常见的优化误区。

1. **模型越强越好。** 更强的模型可能提高单次推理质量，却不一定提高整个任务的成功率。
2. **并行越多越快。** 多专家并行可能增加协调成本、内存占用和重复工作。
3. **上下文越短越省钱。** 过度压缩可能丢失约束，导致返工成本超过节省的 Token。
4. **缓存越多越高效。** 过期缓存可能使系统使用错误的技能版本、旧代码或失效的任务状态。
5. **本地运行一定更便宜。** 本地模型可能耗时更长、占用更多内存，也可能使其他任务无法运行。

真正的优化对象应该是整个任务的最终交付成本。

## 1.1 建立统一的任务效用模型

可以把一次任务的综合表现表示为：

\[
J =
w_q Q +
w_r R +
w_t T +
w_c C +
w_m M +
w_e E
\]

其中：

- \(Q\)：任务质量；
- \(R\)：可靠性与恢复表现；
- \(T\)：完成时间；
- \(C\)：实际费用；
- \(M\)：内存及其他资源占用；
- \(E\)：能耗或设备负载。

这里需要注意，质量和可靠性通常是越高越好，而时间、成本、资源占用通常是越低越好。因此，实现时不能直接对这些原始数值做简单加权求和，而应先进行归一化，并明确各项的优化方向。

更重要的是，**安全、授权和必要的质量验收应当作为硬约束，而不是可以被其他收益抵消的普通评分项。**

例如，不能因为某个策略降低了 50% 的成本，就允许它绕过必要的安全检查。

实际调度可以采用两阶段决策：

1. 先过滤掉违反安全、质量、授权和硬资源限制的方案；
2. 再在剩余方案中比较延迟、费用、资源消耗和预期收益。

## 1.2 区分三种优化目标

    ["交付型任务","优先保证最终产物质量、可验证性与合理成本。适用于代码修改、文档制作和视频生成。"],
    ["后台型任务","优先控制资源占用、运行预算与对前台任务的影响。适用于评测、索引、记忆整理和进化实验。"]

例如，后台进化任务即使能够更快完成，也不应该抢占用户正在使用的本地模型所需的全部内存。

建议建立六个核心组件。

这些组件通过统一的资源预算、任务状态和事件协议协作，不需要成为六个独立的 AI 智能体。

第一版更适合采用确定性调度逻辑和简单的历史统计。随着数据积累，再逐步引入更复杂的预测与自适应策略。

## 2.1 与已有模块的关系

- Router 决定应该由哪个专家处理请求。
- Planner 决定任务应该分解成哪些节点。
- APRO 决定这些节点使用什么资源、何时执行、在哪里执行，以及是否需要降低并行度。
- TERSO 负责落实工具执行与资源限制。
- RERA 负责故障、重试、恢复和安全停止。
- GECO 记录实际资源消耗与执行结果。
- SELCIA 负责评测和发布经过验证的调度改进。

因此，APRO 不应该取代 Router 或 Planner。

**Router 解决能力匹配，Planner 解决任务分解，APRO 解决资源约束下的执行优化。**

# 三、统一资源模型：系统必须知道自己还能做什么

如果 APRO 不知道设备当前的资源状况，就只能根据静态配置猜测。

因此，建议建立 `ResourceSnapshot` 和 `ResourceBudget` 两类数据结构。

## 3.1 ResourceSnapshot：当前资源快照

至少应包含：

| 资源类别 | 关键数据 |
|---|---|
| CPU | 可用核心数、负载、任务队列 |
| 内存 | 可用内存、进程占用、模型驻留占用 |
| GPU / NPU | 是否可用、显存或共享内存、当前任务占用 |
| 磁盘 | 剩余空间、读写压力、临时文件占用 |
| 网络 | 可用性、延迟、带宽估计 |
| 模型运行时 | 已加载模型、加载耗时、并发限制 |
| 外部费用 | 已使用预算、待确认费用、剩余预算 |
| 设备状态 | 电池、温度、系统资源压力与运行限制 |

并不是所有平台都能提供这些指标。例如，Android 应用可能无法直接获取完整的 GPU 占用或精确的系统级资源信息。

因此，资源快照应当支持 `available`、`estimated` 和 `unknown` 等状态。不能把无法观测的资源当成无限可用。

## 3.2 ResourceBudget：预算不是单一的金额

建议将预算分成以下几个维度：

- **时间预算**：任务允许运行多久；
- **计算预算**：允许消耗多少 CPU、GPU 时间或推理资源；
- **Token 预算**：模型输入和输出的允许范围；
- **费用预算**：允许产生多少外部服务费用；
- **内存预算**：任务可以占用多少内存；
- **并发预算**：允许同时运行多少节点、专家和模型请求；
- **重试预算**：失败后还能进行多少次尝试；
- **返工预算**：质量不达标时允许多少轮修改。

这些预算需要相互关联。

例如，任务虽然还有 Token 额度，但如果剩余时间不足以完成最终验收，就不应该继续生成大量中间分析。

同样，一个任务可能还有费用额度，但当前设备内存不足，此时应该等待、降级或迁移，而不是继续启动本地模型。

## 3.3 预算采用分层继承与受控分配

建议采用以下层级：

<box border radius="xl" padding={3} gap={2}>
  <box background="surface-secondary" radius="md" padding={3}>
    **系统预算**

    <text color="secondary" size="sm">整台设备的资源安全上限、并发限制与全局费用限制。</text>
  </box>
  <box padding={{left:3}} gap={2}>
    <box border radius="md" padding={3}>
      **任务预算**

      <text color="secondary" size="sm">由用户目标、截止时间、质量要求与授权决定。</text>
    </box>
    <box padding={{left:3}} gap={2}>
      <box border radius="md" padding={3}>
        **DAG 节点预算**

        <text color="secondary" size="sm">为分析、生成、测试、合成等节点分配资源。</text>
      </box>
      <box padding={{left:3}}>
        <box border radius="md" padding={3}>
          **工具与模型调用预算**

          <text color="secondary" size="sm">限制单次操作的超时、Token、费用和并发。</text>
        </box>
      </box>
    </box>
  </box>
</box>

下层预算不能突破上层剩余额度。

同时，应区分“预留预算”和“实际消耗”。如果多个节点并行运行，每个节点都把整个任务的剩余额度当作自己可用的预算，就会出现预算超支。

因此，APRO 应通过原子化预留、执行后结算和失败释放等机制管理资源。

# 四、动态模型选择：什么时候需要最强模型？

这是 APRO 最重要的能力之一。

EvoAgent 可能接入本地模型、远程模型以及不同价格、延迟和能力水平的模型适配器。不能简单规定所有任务都使用同一个模型，也不能只根据模型名称或参数规模选择。

建议建立 `Model Selection Policy`。

## 4.1 先定义任务所需的能力

每个任务在进入模型调度前，应尽可能明确：

- 任务类型；
- 所需能力；
- 难度与不确定性；
- 质量验收要求；
- 输入与输出规模；
- 是否需要工具调用；
- 是否涉及高风险操作；
- 可接受的延迟；
- 可接受的费用；
- 可用模型与执行环境。

这些信息可以由 Router、Planner、历史统计和任务契约共同提供，不应完全依赖模型自己给出的难度评分。

## 4.2 建立候选模型能力表

建议为每个模型适配器维护一个动态的 `ModelCapabilityProfile`。

| 属性 | 用途 |
|---|---|
| 任务能力表现 | 在编程、推理、摘要等任务上的历史验收表现 |
| 上下文容量 | 支持的输入长度与输出限制 |
| 工具支持 | 是否支持所需的工具调用或结构化输出 |
| 平均延迟 | 相似任务的历史执行耗时 |
| 费用 | 输入、输出或其他计费方式 |
| 资源需求 | 内存、GPU、CPU 与模型加载成本 |
| 可靠性 | 超时率、失败率、恢复表现 |
| 适用限制 | 隐私、联网、部署与授权要求 |

模型能力数据应按任务类型分组，并随着实际评测持续更新。

不能因为某个模型在通用问答中表现很好，就默认它在代码修复、复杂规划或结构化输出上同样优秀。

## 4.3 采用逐级升级策略

一个可实施的初始策略是：

<box border radius="xl" padding={3} gap={3}>
  {#each [
    ["第一级：低成本尝试","使用已验证、成本较低且满足任务最低要求的模型或规则能力。"],
    ["第二级：验证输出","使用测试、Schema 校验、静态分析或其他独立方法检查结果。"],
    ["第三级：针对性升级","如果证据显示结果不合格或问题复杂度超出当前能力，则切换更适合的模型或专业技能。"],
    ["第四级：高能力处理","对复杂、歧义较大或高返工成本的任务，使用更强模型与必要的专家协作。"],
    ["第五级：终止或请求协助","如果预算耗尽、权限不足或无法验证结果，则暂停并说明限制，而不是无限升级。"]
  ] as item}
    <box gap={1}>
      <title size="md">{item[0]}</title>
      <text color="secondary" size="sm">{item[1]}</text>
    </box>
    {#if item[0]!=="第五级：终止或请求协助"}
      <divider color="subtle"/>

这不是强制所有任务都从最低级开始。对于复杂代码迁移、高风险数据处理或明确要求高质量的任务，可以直接选择经过验证的高能力路径。

逐级升级只是默认优化策略，不应增加不必要的尝试次数。

## 4.4 比较总成本，而不是单次调用价格

假设两个模型处理同一类代码任务：

- 模型 A 单次调用成本较低，但经常需要返工；
- 模型 B 单次调用成本较高，但更容易一次通过测试。

如果只比较单次 Token 费用，可能会错误选择模型 A。

更合理的比较是：

\[
C_{\text{effective}}
=
C_{\text{inference}}
+
C_{\text{tools}}
+
C_{\text{rework}}
+
C_{\text{recovery}}
\]

其中包括推理成本、工具成本、返工成本和恢复成本。

实际决策还需要考虑任务失败造成的时间损失，以及质量要求是否已经满足。

例如，模型 A 虽然便宜，但如果它的输出无法通过测试，就不应该仅凭成本优势被选中。

## 4.5 模型切换不能丢失关键上下文

从本地模型切换到远程模型，或者从一个模型适配器切换到另一个模型时，系统必须重新构建经过验证的任务上下文。

不能只把最近几轮聊天内容直接复制过去。

建议传递：

- 当前任务目标；
- 经过验证的需求与约束；
- 相关产物和版本；
- 已经执行的操作；
- 已知失败及其证据；
- 剩余预算；
- 仍然有效的授权范围；
- 当前节点的验收条件。

这与 ACMO、MEEG 和 CLEK 的上下文设计直接相关。APRO 决定上下文使用多少资源，而记忆与上下文模块负责确保传递的信息仍然准确、完整且适用。

# 五、多专家与 DAG 并行：并行不是越多越好

EvoAgent 采用多专家架构，但专家数量增加后，资源开销并不是线性增长。

多个专家可能各自加载模型、检索记忆、重复分析同一问题，还可能需要额外的协调与结果整合。

因此，APRO 必须根据任务结构和设备资源动态决定并行度。

## 5.1 建立 DAG 的资源感知调度

Planner 负责生成任务 DAG，APRO 负责在 DAG 的依赖约束下调度可执行节点。

每个节点至少应声明：

- 依赖节点；
- 预计执行时间；
- 预计内存与计算需求；
- 预计费用；
- 是否可并行；
- 是否具有外部副作用；
- 是否允许取消；
- 失败后的恢复策略。

APRO 根据当前资源情况选择可运行节点，而不是简单地将所有已解锁节点同时启动。

## 5.2 区分三类并行任务

| 类型 | 处理策略 |
|---|---|
| 高度独立的任务 | 资源充足时优先并行执行 |
| 有共享模型或资源竞争的任务 | 根据模型驻留、内存与队列情况调整并发 |
| 存在冲突或强依赖的任务 | 按依赖顺序执行，或通过明确的隔离与合并机制控制冲突 |

例如，两个专家分别分析两个互不相关的代码模块，可能适合并行。

但两个专家同时修改同一个文件，可能造成冲突，增加合并和回归测试成本。

即使 CPU 足够空闲，也不意味着同时修改同一个文件是更好的方案。

## 5.3 估算并行收益

假设任务有多个可并行节点。

理想情况下，关键路径决定最低执行时间；但真实运行还会受到模型加载、资源竞争、任务启动和结果合并的影响。

因此，APRO 应比较：

- 串行执行的预计时间；
- 并行执行的预计时间；
- 并行额外消耗的资源；
- 任务失败或冲突的概率；
- 合并与验收所需的额外成本。

只有预期收益足够大时，才增加并行度。

## 5.4 专家团队规模应当动态调整

建议将团队规模分为三种模式：

- **单专家模式：** 适用于目标明确、依赖简单的任务；
- **小团队模式：** 适用于需要专业分工或独立验证的任务；
- **多专家模式：** 适用于复杂、可分解且并行收益明确的任务。

APRO 不应仅凭任务字数或表面复杂度增加专家。

更有价值的判断是：新增专家是否能够提供独立的专业能力、减少关键路径耗时，或者提高验证质量。

如果多个专家只是重复回答同一个问题，就应减少冗余调用。

# 六、记忆与上下文优化：省下的 Token 不能靠返工还回去

这一部分与此前讨论的 ACMO、MEEG、CLEK 和各领域专家直接相关。

APRO 不能把上下文压缩当作一个全局统一的“缩短文本”任务。它需要根据任务阶段、专家职责和信息的重要性，决定哪些内容应该加载、哪些内容可以摘要、哪些内容必须保留原始证据。

## 6.1 建立分层上下文预算

建议把上下文分成五个逻辑层：

<box border radius="xl" padding={3} gap={3}>
  {#each [
    ["L0 · 全局控制上下文","当前系统规则、授权边界、用户当前目标及必要的安全约束。"],
    ["L1 · 任务上下文","当前任务契约、验收标准、计划版本、预算和关键依赖。"],
    ["L2 · 专家上下文","当前专家的领域知识、工具使用约束、专业方法与相关历史经验。"],
    ["L3 · 当前执行上下文","当前节点输入、相关产物、近期结果、错误证据和待解决问题。"],
    ["L4 · 按需读取内容","完整文件、历史对话、详细日志、长文档和其他大型资料。"]
  ] as item}
    <box gap={1}>
      <title size="md">{item[0]}</title>
      <text color="secondary" size="sm">{item[1]}</text>
    </box>
    {#if item[0]!=="L4 · 按需读取内容"}
      <divider color="subtle"/>
    {/if}
  {/each}
</box>

这里的层级是逻辑分层，不代表每次请求都必须把前四层完整复制到模型上下文中。

系统应按任务需要选择内容，并确保不可省略的授权与验收约束在压缩和模型切换后仍然有效。

## 6.2 压缩应保留什么？

建议为上下文压缩建立独立的 `ContextRetentionPolicy`。

高优先级信息包括：

- 用户明确提出的约束；
- 当前有效的授权；
- 已验证的事实与证据引用；
- 已完成的操作及其实际结果；
- 尚未解决的问题；
- 任务依赖和版本信息；
- 不可逆操作的状态；
- 失败原因及已尝试过的方法；
- 最终验收条件。

可压缩的信息包括重复解释、已经解决且不再影响当前任务的讨论，以及能够通过稳定引用重新读取的长文档。

但对于代码任务，不应只保留“修改了某个函数”的摘要，而忽略实际代码版本、测试结果和变更差异。

对于漫剧任务，也不能只保留“角色素材已生成”，而不保存角色版本、素材引用和质量验收状态。

## 6.3 全局压缩与专家专用压缩应当分开

建议保留两种能力：

- **全局上下文治理：** 统一管理 token 预算、保留规则、隐私限制和任务连续性。
- **领域专用压缩器：** 由不同专家针对特定内容使用适合的结构化表示。

例如：

- 编程专家可以保留 AST 结构、符号引用、代码差异和测试证据；
- 漫剧专家可以保留角色 ID、场景 ID、分镜关系、时间线和素材版本；
- 研究专家可以保留论点、来源、证据强度与待验证假设；
- 数据分析专家可以保留数据 Schema、筛选条件、转换步骤和统计结果。

这也回答了此前的一个重要问题：上下文压缩不应该只有一个通用算法，也不应该让每个专家各自发明一套互不兼容的记忆系统。

**全局模块负责统一治理，领域模块负责专业表达。**

## 6.4 缓存必须具备失效机制

缓存可以减少重复推理、重复读取和重复生成，但需要明确缓存的适用条件。

建议将缓存键与以下信息关联：

- 输入内容摘要；
- 任务或节点类型；
- 模型与技能版本；
- 关键配置；
- 数据依赖版本；
- 权限和隐私范围；
- 必要的运行环境信息。

如果代码文件发生变化，基于旧代码生成的分析缓存可能失效；如果技能版本升级，旧版本的执行结果也不应自动成为新版本正确性的证据。

缓存只是一种性能优化，不是可信事实的替代品。

# 七、本地、远程与跨设备调度：根据任务选择执行位置

EvoAgent 的部署路线不是单一云端系统，而是个人设备优先。

因此，APRO 需要建立 `Execution Placement Policy`，决定任务应该在手机、个人电脑、微型 Linux 主机还是外部服务中执行。

## 7.1 建立执行位置的选择维度

| 维度 | 需要考虑的问题 |
|---|---|
| 能力匹配 | 该设备是否具备所需模型、工具与运行环境？ |
| 资源条件 | 当前内存、计算能力和磁盘空间是否足够？ |
| 网络条件 | 是否需要联网？网络延迟和稳定性如何？ |
| 隐私要求 | 任务数据是否允许离开本地设备？ |
| 执行成本 | 远程调用费用是否值得？ |
| 恢复能力 | 任务中断后能否恢复，产物能否可靠同步？ |
| 用户体验 | 是否会影响当前前台操作、电池或设备温度？ |

不能只根据设备算力选择执行位置。

例如，本地 Linux 主机可能有足够的计算能力，但如果某个任务涉及不能离开手机的私有数据，就不能为了速度自动把数据发送到远程服务。

## 7.2 建立三种执行模式

<box border radius="xl" padding={3} gap={3}>
  {#each [
    ["Local-first · 本地优先","优先使用本地工具、规则能力与适合的本地模型，适用于隐私要求高、网络不稳定或成本敏感的任务。"],
    ["Hybrid · 混合执行","本地负责数据准备、权限控制和产物处理，远程服务负责经授权的高成本或高能力生成。"],
    ["Remote-assisted · 远程辅助","在满足授权、隐私、费用和网络要求时，使用远程模型或设备完成特定步骤，本地保留任务治理与结果验收能力。"]
  ] as item}
    <box gap={1}>
      <title size="md">{item[0]}</title>
      <text color="secondary" size="sm">{item[1]}</text>
    </box>
    {#if item[0]!=="Remote-assisted · 远程辅助"}
      <divider color="subtle"/>
    {/if}
  {/each}
</box>

这些是任务级执行策略，不是要求整个 EvoAgent 永远固定在其中一种模式。

同一任务的不同节点可以采用不同执行位置，但每次跨设备或跨信任边界的数据传输，都必须重新检查授权和数据使用范围。

## 7.3 断网时需要明确降级策略

如果外部模型不可用，APRO 可以：

1. 选择经过验证且能够完成该步骤的本地模型；
2. 使用确定性工具或规则能力完成不需要模型的步骤；
3. 暂停依赖外部服务的节点，继续执行独立节点；
4. 保存检查点，等待网络恢复；
5. 在预算或质量要求无法满足时，明确请求用户决策。

不能为了让任务看起来持续运行，就用明显不具备相应能力的本地模型生成未经验证的结果。

## 7.4 Android 必须考虑设备状态

手机资源调度和桌面电脑不同。

除了内存、CPU 和网络，APRO 还应考虑：

- 电池电量与充电状态；
- 设备温度与系统热限制；
- 后台执行限制；
- 用户是否正在进行前台交互；
- 模型驻留对其他应用的影响。

如果手机正在发热，可以暂停非必要的本地模型推理，延后后台索引和进化评测。

但是，设备降温或资源释放不能通过跳过关键状态保存、授权检查或安全停止流程来实现。

# 八、成本控制：不只是 Token，更要关注返工和外部费用

EvoAgent 未来可能接入代码执行、云端视频生成、语音合成、文件处理和其他第三方服务。

这些服务的费用结构差异很大。单纯统计模型 Token，无法反映整个任务的真实成本。

## 8.1 建立统一的 Cost Ledger

建议建立 `CostLedger`，至少记录：

- 任务与节点 ID；
- 模型或服务名称；
- 调用次数；
- 输入与输出 Token；
- 实际或估算费用；
- 费用确认状态；
- 重试与返工产生的费用；
- 任务预算；
- 剩余额度；
- 成本对应的产物与验收结果。

对于按量计费但账单延迟返回的外部服务，应区分已确认费用与估算费用。

APRO 不应将尚未确认的费用视为零。

## 8.2 预算分配应根据任务结构决定

例如，一个 AI 漫剧任务可以将预算划分为：

- 剧本与分镜；
- 角色和场景素材；
- 视频片段生成；
- 配音与音频处理；
- 本地合成；
- 质量验收；
- 必要的返工预留。

具体比例应根据服务定价、历史成功率和用户质量要求动态估算，而不是硬编码一个适用于所有任务的固定比例。

如果前面的角色素材质量不达标，系统就不应该继续投入大量视频生成费用。

## 8.3 采用阶段性投入策略

对于高成本生成任务，建议在阶段边界进行质量门控：

1. 先生成低成本的候选内容；
2. 验证结构、时长、角色和基础质量；
3. 只有满足条件后，才进入更昂贵的生成阶段；
4. 保留必要的返工预算；
5. 如果关键约束持续不满足，暂停并请求用户确认。

这能避免错误的上游输入持续放大后续费用。

## 8.4 评价成本时必须结合产出质量

一个成本很低但最终不能交付的任务，不应被评为优化成功。

建议同时比较：

- 每个验收通过任务的平均成本；
- 每个合格产物的平均成本；
- 返工成本；
- 失败任务的沉没成本；
- 资源占用与耗时；
- 质量是否达到用户要求。

这使 APRO 优化的是“合格交付的成本”，而不是单纯的调用价格。

# 九、前台、后台与进化任务：资源优先级必须统一

EvoAgent 不仅需要执行用户任务，还可能在后台进行记忆整理、技能评测、工作流分析和进化实验。

如果这些任务各自独立调度，就可能发生资源争抢。

例如，用户正在让编程专家修改代码，后台 SELCIA 同时启动多个候选模型评测，导致本地模型被卸载、内存压力上升，前台任务响应变慢。

因此，建议 APRO 建立统一的 `WorkloadPriorityManager`。

## 9.1 建立五类工作负载

| 工作负载 | 默认优先级 | 调度原则 |
|---|---|---|
| 安全控制与关键状态持久化 | 最高 | 保证必要的授权撤销、状态记录与安全停止能力 |
| 用户前台交互 | 高 | 优先保证响应性和当前任务连续性 |
| 正在执行的关键任务 | 中高 | 尽量减少中断，保护已投入的计算与工作进度 |
| 普通后台维护 | 中低 | 在资源充足时执行，可暂停和恢复 |
| 进化实验与批量评测 | 低 | 使用剩余资源，必要时主动让出资源 |

这是一套建议的默认优先级，不是所有任务都必须采用完全相同的固定顺序。

例如，用户明确启动的大规模视频生成任务可能需要持续占用资源；而后台安全更新或授权撤销相关操作则不应被普通用户任务阻塞。

## 9.2 防止优先级反转

如果高优先级任务依赖某个低优先级任务持有的资源，就可能出现优先级反转。

例如，前台任务需要加载模型，但后台任务占用了大部分内存。

APRO 可以在必要时暂停后台任务、释放非必要缓存，或者限制其继续申请资源。

同时，关键任务也不能无限制地抢占所有资源，否则可能导致其他必要的系统维护永远无法完成。

## 9.3 后台任务必须可暂停、可恢复

建议后台进化和批量评测任务具备：

- 明确的检查点；
- 可释放的模型与内存资源；
- 可暂停的工作单元；
- 恢复后的版本核验；
- 独立的预算；
- 对前台资源压力的响应机制。

当资源不足时，系统应优先暂停可恢复的后台任务，而不是让所有任务一起进入不可控状态。

# 十、性能分析与自适应优化：不要凭感觉调参

APRO 还需要解决一个长期问题：系统怎样知道真正的瓶颈在哪里？

例如，任务响应慢，原因可能是：

- Router 多次调用模型；
- 模型加载时间过长；
- DAG 并行度不足；
- 工具执行等待外部服务；
- 上下文过长；
- 磁盘 I/O 成为瓶颈；
- 多专家重复工作；
- 返工次数过多。

如果没有明确的性能证据，系统很容易优化错方向。

## 10.1 建立端到端耗时分解

建议为每个任务追踪以下耗时：

\[
T_{\text{total}}
=
T_{\text{queue}}
+
T_{\text{routing}}
+
T_{\text{planning}}
+
T_{\text{execution}}
+
T_{\text{waiting}}
+
T_{\text{validation}}
\]

这只是便于诊断的概念分解。对于并行 DAG，端到端耗时不能简单地把所有节点耗时相加，而应结合关键路径和实际等待关系分析。

例如，如果模型推理只占总耗时的 20%，即使把推理速度提升一倍，整个任务的耗时也不会减少一半。

因此，APRO 应优先识别关键路径上的主要瓶颈。

## 10.2 采用分层优化策略

建议按以下顺序进行优化：

1. **消除无效工作。** 减少重复推理、无效重试和冗余专家调用。
2. **优化任务结构。** 改善 DAG 分解、依赖关系和数据传递。
3. **优化上下文。** 减少无关内容，复用可验证的中间结果。
4. **优化调度。** 调整并行度、优先级、模型驻留和资源分配。
5. **优化单次执行。** 在前面几项完成后，再优化模型选择、推理参数和底层性能。

这样可以避免用更快的模型掩盖糟糕的工作流设计。

## 10.3 建立策略实验机制

对于模型选择、并行度、上下文压缩和缓存策略，APRO 可以提出不同候选方案，并在隔离环境中比较。

实验应固定或记录：

- 任务样本；
- 模型与技能版本；
- 质量验收条件；
- 资源环境；
- 费用统计口径；
- 测试数据；
- 失败与恢复规则。

如果实验环境与真实运行环境差异较大，系统不能直接把实验结果视为生产环境中的确定收益。

## 10.4 优化策略必须可回滚

例如，APRO 学到“增加专家数量可以提高复杂代码任务的成功率”。

这条经验可能只在特定模型、设备和任务分布下成立。

因此，策略发布后应继续监控：

- 实际成功率；
- 端到端耗时；
- 返工率；
- 费用；
- 设备资源压力；
- 不同任务类型的表现。

一旦出现明显退化，就应恢复到经过验证的稳定策略，而不是让错误的自适应规则持续影响后续任务。

# 十一、APRO 与自进化的边界：调度器不能为了省资源破坏质量

APRO 本身也会成为进化对象。

系统可能发现某个路由策略浪费了很多 Token，或者某个专家团队经常产生重复结果，于是提出优化方案。

但资源优化很容易出现“局部指标改善、整体质量下降”的情况。

例如：

- 减少独立代码审查，降低成本，却增加缺陷漏检；
- 缩短上下文，降低 Token 消耗，却导致需求约束丢失；
- 减少回归测试，加快交付，却提高回归风险；
- 降低检查点频率，减少磁盘写入，却增加崩溃后的重做成本；
- 将所有任务切换到本地模型，降低外部费用，却导致任务无法在截止时间前完成。

因此，APRO 必须接受三个不可突破的原则。

**第一，安全与授权是硬约束。** 资源不足不能成为绕过 TSEG 的理由。

**第二，任务验收标准不能由优化器自行降低。** UQEAG 的必要质量要求不能因为成本压力而自动消失。

**第三，调度策略的进化必须独立评测。** 优化器不能只依据自己生成的预测值宣称成功，必须比较实际结果。

建议将 APRO 的策略发布纳入 SELCIA，并要求 GECO 持续记录策略版本、实际资源消耗、质量结果和退化信号。

## 13.1 第一版的验收标准

建议使用三种不同的任务验证 APRO：

- 一个简单聊天任务；
- 一个包含分析、修改和测试的代码任务；
- 一个包含多个生成与合成阶段的漫剧任务。

系统应当能够：

1. 记录任务执行前的资源状态；
2. 选择符合质量要求的模型和能力；
3. 在资源不足时限制并发或延后后台任务；
4. 记录每个节点的实际耗时与成本；
5. 识别重复推理、无效重试和高成本返工；
6. 保持上下文压缩后的任务约束和证据完整；
7. 在模型切换或断网后维持有效的任务状态；
8. 比较优化前后的质量、耗时、费用和资源占用；
9. 在优化策略造成退化时回滚；
10. 证明资源优化没有绕过安全、可靠性和最终验收要求。

只有这些指标能够可靠测量，后续的自适应调度才有可信的学习基础。

# 十四、下一专项：质量工程、评测体系与结果可信度

到这里，我们已经系统讨论了多个核心领域：

- 多专家与协作机制；
- Router、Plan、ReAct 与任务 DAG；
- 记忆、上下文与领域专用能力；
- GECO 全局观测与因果证据；
- TSEG 安全与进化治理；
- RERA 可靠性与恢复保证；
- APRO 性能、资源与成本优化。

但这些系统还存在一个共同问题：

**我们如何知道 EvoAgent 真正变得更好了，而不是仅仅变得更快、更便宜、更复杂，或者更擅长让自己看起来成功？**

这需要下一专项解决。

建议将其定义为：

**Quality Engineering & Evaluation Governance，简称 QEEG。**

它将重点研究：

1. 如何为不同专家、任务类型和工作流定义可执行的质量契约；
2. 如何区分任务完成、产物合格、用户满意和长期效果；
3. 如何为代码、文档、漫剧、研究与自动化任务建立不同的评测方法；
4. 如何组合确定性测试、规则检查、模型评审与人工验收；
5. 如何减少模型评审自身的偏差；
6. 如何建立固定回归集、动态测试集和困难案例集；
7. 如何评价 Router 是否选择了正确的专家；
8. 如何评价 Planner 的分解方式是否合理；
9. 如何评价记忆和上下文压缩是否丢失关键信息；
10. 如何衡量多专家协作带来的真实增益；
11. 如何区分随机波动、任务难度变化和真正的能力提升；
12. 如何防止智能体通过修改评测器、降低标准或隐藏失败来制造虚假的进步；
13. 如何让用户反馈转化为有证据的改进方向；
14. 如何建立跨版本、跨模型、跨设备的可比较评测体系；
15. 如何将质量门槛接入 SELCIA，使所有重要改进都必须证明自己的收益。

这一专项尤其重要，因为它将成为所有自进化模块共同依赖的“进步判定体系”。

APRO 可以提出更高效的调度方案，RERA 可以提出更可靠的恢复方案，CEKCE 可以提出更好的技能，SOCDEA 可以提出根因修复方案。

但最终都需要回答同一个问题：

**改进之后，系统是否在真实任务上变得更好？**

而且，这个结论必须有独立证据支持，不能仅由提出改进的模块自己宣布。

这就是 QEEG 的核心使命：让 EvoAgent 的持续进化从“不断修改自己”，转变为“持续提出假设、独立验证收益，并只保留真正有效的改进”。
