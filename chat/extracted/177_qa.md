<WritingBlock id="73149" variant="document"># EvoAgent 专项设计 #94：用户需求理解、任务澄清与交付质量保障

**英文名称：** User Intent Understanding, Clarification & Delivery Quality Assurance

**文档版本：** 1.0

**关联专项：** #75—#93

**设计状态：** 专项设计基线，待实施与验收。

## 一、专项目标

建立一套贯穿任务全生命周期的需求理解与质量保障机制，使 EvoAgent 能够准确理解用户真正需要的结果，在必要时进行澄清，并以可验证的方式完成交付。

本专项不是单独优化一个意图识别模型，而是建立完整的质量链路：

**理解需求 → 明确约束 → 判断是否需要澄清 → 定义成功标准 → 制定计划 → 执行任务 → 验证结果 → 交付与反馈。**

需要解决的核心问题包括：

1. 如何区分用户明确表达的要求、上下文中已有的事实和系统自行推断的内容？
2. 如何利用已有对话与项目状态，避免反复询问用户已经提供过的信息？
3. 什么情况下可以直接执行，什么情况下需要澄清？
4. 如何避免把系统的默认假设当成用户已经确认的要求？
5. 如何识别任务真正需要的交付物，而不只是完成字面上的动作？
6. 如何为不同类型的任务定义合理、可验证的成功标准？
7. 如何避免执行过程中擅自扩大任务范围？
8. 如何在发现目标理解错误时，安全地调整任务？
9. 如何区分需求理解错误、规划错误、工具故障和验收错误？
10. 如何把质量问题反馈给自进化系统，同时防止错误经验污染稳定版本？

### 1.1 最高优先级

本专项必须服从 EvoAgent 的总体质量原则：

- 高质量完成用户任务优先；
- 正确理解用户目标优先于机械执行字面指令；
- 减少不必要的澄清，但不能以牺牲正确性为代价；
- 提高效率，但不能通过省略必要验证来提高速度；
- 可以主动补充有价值的思考，但不能擅自改变用户目标；
- 持续优化，但任何优化都必须经过质量验证。

## 二、总体架构

### 2.1 七个逻辑组件

| 组件 | 核心职责 |
|---|---|
| Intent Interpreter | 解析用户明确表达的目标、要求与上下文 |
| Context Evidence Resolver | 检索并核对相关对话、记忆、项目状态和已有决策 |
| Constraint & Assumption Manager | 区分硬约束、软偏好、默认假设和未知信息 |
| Clarification Decision Engine | 判断是否需要向用户澄清，以及何时澄清 |
| Task Contract Builder | 将需求转换为可执行的任务契约和验收标准 |
| Intent Consistency Monitor | 监控执行过程中是否出现目标偏离、约束冲突或理解错误 |
| Delivery Quality Verifier | 验证实际结果是否满足任务要求，并决定能否交付 |

这些是逻辑职责，不要求实现为七个独立服务。可以复用统一入口、上下文治理、任务系统、规划器、验证器和现有进化机制。

### 2.2 总体流程

```text

   ↓
检索相关上下文和已有决策

   ↓
评估歧义、影响、风险与可逆性
   ↓
┌────────────┼────────────┐
↓            ↓            ↓
信息充分     可安全推断     关键歧义
↓            ↓            ↓
直接执行     记录假设       向用户澄清
└────────────┼────────────┘
             ↓
      建立任务契约与验收标准
             ↓
          制定执行计划
             ↓
       执行与持续一致性检查
             ↓

             ↓

```

## 三、用户意图的标准化表达

### 3.1 区分四类信息

所有重要任务都应区分以下信息。

**A. 明确要求**

用户直接表达的目标、交付物、约束和决定。

例如：“使用 Python 编写一个能够在 Windows 11 本地运行的程序。”

**B. 已有事实**

来自当前对话、用户提供的文件、已确认的项目决策或其他允许使用的可靠来源的信息。

例如：项目已经采用某个 Python 版本，且已有特定目录结构。

**C. 合理推断**

系统根据已有信息推测的需求或约束。

例如：如果用户要求交付可运行程序，那么通常需要说明依赖、启动方式和必要的验证结果。

这类推断可以用于补齐必要工作，但不能伪装成用户明确提出的要求。

**D. 未知信息**

现有证据不足以确定、且可能影响执行或交付的内容。

例如：用户要求“部署到服务器”，但没有说明服务器的操作系统，也没有提供可用的部署环境。

### 3.2 建立字段级来源追溯

不应只给整份需求摘要附加一个总体置信度。

对重要要求、约束和假设，应能够追溯：

- 来源于用户哪条明确指令；
- 来源于哪项已经确认的项目决策；
- 来源于哪个文件或运行证据；
- 是系统自行推断的，还是尚未确认的；
- 是否已被后续信息替代；
- 是否需要再次向用户确认。

这样可以避免一个常见问题：摘要本身看起来合理，但在多次压缩和转述后，系统无法判断某项决定究竟是谁提出的。

### 3.3 用户当前指令与历史信息冲突

默认情况下，应优先遵循用户当前明确表达的有效要求。

但以下情况不能机械覆盖：

- 当前指令存在歧义；
- 新旧要求可能适用于不同任务；
- 变更会产生明显成本或返工；
- 涉及已经执行的外部操作；
- 存在安全、权限或不可逆操作限制。

对于重要架构决策，系统应区分“用户提出了新的想法”和“用户正式决定变更方案”。

如果当前指令确实明确要求改变方案，应按任务变更流程更新；如果只是讨论或探索，不应擅自覆盖已确认的项目基线。

## 四、任务意图快照

### 4.1 设计目的

建议建立版本化的 `Task Intent Snapshot`，用于保存某一时刻系统对用户需求的结构化理解。

它是关联现有 Task 的需求快照，不是新的任务主表，也不替代现有 `objective`、`constraints` 或验收契约。

每次任务创建、重大澄清或重要目标变更时，可以生成新的意图快照版本。

### 4.2 建议的逻辑结构

```json
{
  "intent_snapshot_id": "stable-id",
  "task_id": "task-id",
  "version": 1,
  "objective": "预期实现的结果",
  "deliverables": [],
  "explicit_requirements": [],
  "inferred_requirements": [],
  "hard_constraints": [],
  "soft_preferences": [],
  "assumptions": [],
  "unknowns": [],
  "acceptance_criteria": [],
  "risk_and_reversibility": {},
  "authorization_requirements": [],
  "source_refs": [],
  "clarification_refs": [],
  "supersedes_ref": null
}
```

以上是设计示例，不是已批准的正式 Schema。实际实施时应建立版本化的数据契约，并与现有 Task、Goal、事件及验收契约对齐。

### 4.3 假设管理

每项重要假设至少应具备：

- 假设内容；
- 产生原因；
- 影响范围；
- 可信程度；
- 如果假设错误，可能造成的后果；
- 是否需要用户确认；
- 是否已被验证或替代。

例如，假设某项文件处理任务只涉及用户选中的文件，那么该假设可以明确记录。

如果系统发现任务实际上需要访问整个目录，则不能静默扩大访问范围，而应重新检查权限和用户意图。

### 4.4 假设不等于授权

即使系统非常确信用户希望完成某项工作，也不代表系统获得了执行该动作的权限。

例如：

- 推断用户希望节省时间，不代表可以自动购买服务；
- 推断用户希望清理文件，不代表可以删除文件；
- 推断用户希望项目持续推进，不代表可以无限增加后台任务；
- 推断用户希望提高效率，不代表可以省略必要的质量检查。

意图理解、任务准入和动作授权必须保持独立。

## 五、需求澄清决策机制

### 5.1 不采用简单的“有疑问就问”

系统需要判断不确定性是否真正影响任务结果。

建议考虑五个维度：

1. **影响程度：** 理解错误会对结果造成多大影响？
2. **可逆性：** 错误是否容易修复，是否会产生不可逆后果？
3. **信息价值：** 用户的回答能否显著改变执行方案？
4. **证据充分性：** 当前上下文是否足以支持合理选择？
5. **澄清成本：** 提问是否会不必要地打断用户？

安全、隐私、权限和不可逆操作属于硬性约束，不能用较高的综合得分抵消。

### 5.2 澄清决策表

| 情况 | 推荐行为 |
|---|---|
| 目标明确，执行路径简单 | 直接执行 |
| 次要信息缺失，但有合理默认值 | 采用默认值，必要时简要说明 |
| 有多种合理方案，但差异较小 | 选择与现有约束最匹配的方案 |
| 不同理解会明显改变交付结果 | 提出一个关键澄清问题 |
| 缺少任务必需的数据 | 请求补充必要信息 |
| 涉及重要范围、预算或架构决策 | 澄清关键条件 |
| 涉及高风险或不可逆操作 | 核实动作范围并满足授权要求 |
| 当前指令与已确认约束冲突 | 解释冲突并请求必要确认 |
| 用户明确要求直接给出建议或方案 | 在合理假设下先给出有用结果 |

### 5.3 一次只问最重要的问题

如果存在多个未知项，应优先询问对最终结果影响最大、且当前无法合理推断的那一项。

不要一次性把所有可能的偏好都列出来要求用户填写。

例如，用户要求“帮我做一个个人任务管理工具”，但没有指定技术栈。

如果目标是先讨论产品方案，技术栈并不是当前必要问题，可以直接开始。

如果目标是立即生成并运行一套需要与现有项目集成的代码，而现有项目技术栈尚不明确，则技术栈可能成为必要的澄清问题。

### 5.4 允许部分执行

有时，任务的部分内容可以独立完成，而另一部分仍需要澄清。

系统应判断能否安全地先完成不受歧义影响的部分。

例如：

- 可以先分析用户已提供的代码；
- 可以先整理已有资料；
- 可以先生成不依赖争议决策的通用框架；
- 但不能在关键部署环境未知时，声称部署已经完成。

部分执行应明确边界，不应将局部成果描述成完整交付。

### 5.5 允许合理默认值

对于低风险、可逆且不影响核心目标的细节，可以使用合理默认值。

默认值应遵循：

- 与用户明确约束一致；
- 优先复用已有项目约定；
- 优先选择稳定、常见且容易维护的方案；
- 不增加未经批准的成本；
- 不扩大权限范围；
- 在必要时说明假设。

不能为了追求形式上的完整，把所有默认值都转化成必须由用户回答的问题。

## 六、任务复杂度与澄清深度

建议按任务影响与复杂程度决定澄清深度，而不是对所有任务使用同一套流程。

### T0：简单任务

例如，解释概念、翻译短文本、总结用户提供的资料。

策略：直接执行，除非存在明显歧义或特殊约束。

### T1：普通可逆任务

例如，整理文档、生成普通代码片段、制作初步计划。

策略：检查必要要求，使用合理默认值，直接执行并验证结果。

### T2：复杂多步骤任务

例如，构建工作流、实现功能模块、制定项目方案。

策略：明确目标、约束、交付物和成功标准；必要时简要呈现计划；对会明显影响结果的歧义进行澄清。

### T3：高影响或高风险任务

例如，删除重要数据、执行外部交易、修改生产环境或进行具有重大后果的操作。

策略：核实目标、范围、对象、必要条件和授权。不能因为用户希望智能体高度自主，就绕过相应确认与安全控制。

任务复杂度与风险等级是两个不同维度。一个简单的删除操作可能风险很高，而一个复杂的资料分析任务可能风险很低。

## 七、从用户请求到验收契约

### 7.1 每个任务都应有适当的成功标准

成功标准应与任务类型匹配。

简单任务不需要创建繁重的验收文档，但复杂任务必须明确如何判断完成。

建议至少检查：

- 是否达成主要目标；
- 是否覆盖必要交付物；
- 是否遵守硬性约束；
- 是否满足用户明确要求；
- 是否存在未经授权的范围扩张；
- 是否需要特定的质量或安全验证。

### 7.2 不同任务使用不同验收方式

| 任务类型 | 适用的验收方式 |
|---|---|
| 信息问答 | 事实正确性、相关性、证据与不确定性 |
| 研究分析 | 来源质量、论证完整性、结论与证据的一致性 |
| 编程 | 语法与构建检查、测试、接口约束、运行结果 |
| 文件操作 | 文件存在性、内容完整性、格式正确性 |
| 手机操作 | 目标界面状态、实际操作结果、必要的副作用核对 |
| 视频创作 | 时长、格式、画面质量、声音和任务特定要求 |
| 项目规划 | 目标覆盖、依赖关系、资源限制、里程碑和验收条件 |
| 工作流自动化 | 输入输出契约、失败恢复、幂等性、实际端到端结果 |

验收方法应根据任务需求选择，不能将所有任务都压缩成一个通用分数。

### 7.3 区分硬性标准与质量偏好

例如，代码任务中：

- 必须能够构建，属于硬性要求；
- 必须兼容指定运行环境，属于硬性约束；
- 更易维护，可能是质量要求；
- 采用某种风格，可能是偏好。

系统不能用代码风格得分较高，掩盖构建失败；也不能因为代码已经构建成功，就忽略用户明确提出的兼容性要求。

### 7.4 验收标准的完整性

验收标准应足够具体，能够判断任务是否达标。

例如，“代码质量要高”本身不足以作为唯一验收标准。

可以根据任务补充：

- 代码能否通过构建；
- 关键路径是否有测试；
- 是否存在已知严重缺陷；
- 是否遵守指定的接口与依赖；
- 是否有运行说明；
- 是否保留必要的错误处理。

如果任务的目标本身具有主观性，应使用适合该任务的评价标准，而不是假装所有质量都能用自动化测试精确测量。

## 八、执行过程中的意图一致性

### 8.1 任务开始后仍然需要检查理解是否正确

意图快照不是一旦生成就永远不变的事实。

执行过程中，系统可能发现：

- 原始输入缺少关键条件；
- 实际环境与假设不一致；
- 用户补充了新的要求；
- 工具输出揭示了原先没有识别的问题；
- 原计划无法满足验收条件。

此时，应判断这些变化是否影响任务目标。

### 8.2 局部修正与目标变更

以下情况通常可以在原目标内修正：

- 修复实现错误；
- 更换失败的工具调用方式；
- 补齐必要的错误处理；
- 调整不影响用户目标的内部步骤；
- 使用等价的可行方案完成任务。

以下情况通常需要重新评估目标或请求确认：

- 改变主要交付物；
- 扩大修改范围；
- 显著增加成本；
- 更改重要技术决策；
- 增加外部副作用；
- 改变用户明确指定的约束。

### 8.3 发现目标理解错误后的处理

如果继续执行可能导致错误结果或产生不必要的副作用，应暂停受影响的执行步骤。

随后：

1. 保存已完成的有效成果；
2. 定位发生冲突的要求；
3. 检查相关执行是否已经产生外部影响；
4. 判断能否在原目标内修正；
5. 必要时向用户澄清；
6. 更新任务契约与版本记录；
7. 重新验证受影响的计划和验收条件。

不能为了保持执行连续性而忽略已经发现的目标偏离。

## 九、必要补全与擅自扩张的边界

### 9.1 允许的必要补全

当某项工作是实现用户明确目标所必需的，而且不会改变范围、成本、风险或授权边界时，可以将其纳入执行。

例如：

- 为生成的代码补充必要的错误处理；
- 为文件转换检查输出文件是否存在；
- 为复杂自动化流程增加必要的失败检测；
- 为交付物提供最基本的运行说明；
- 对关键输出执行与任务匹配的验收。

这些属于把任务做好，而不是额外增加一个任务。

### 9.2 应作为建议而非默认执行的扩展

例如：

- 将局部代码修复升级成全面重构；
- 在用户只要求分析时，擅自修改原始文件；
- 将单次任务扩展成持续后台监控；
- 在用户只要求本地执行时，增加云端依赖；
- 在用户没有要求时，引入额外付费服务；
- 因为发现潜在机会而改变当前任务的主要目标。

这类工作可以被发现、分析并提出建议，但应根据实际影响决定是否需要确认。

### 9.3 允许提出超出字面要求的建议

本专项不限制智能体主动思考。

如果发现更好的解决方案，可以说明：

- 当前方案可能存在什么问题；
- 为什么值得关注；
- 替代方案是什么；
- 可能带来什么收益；
- 需要付出什么成本；
- 是否会改变原定范围。

用户希望获得更高质量的结果，系统就应具备主动发现问题和提出意见的能力。

关键在于：主动建议可以超出字面表达，但实际执行不能越过目标、授权和资源边界。

## 十、任务失败归因与质量问题分类

### 10.1 失败不能一律归咎于模型

当任务失败时，系统应尽量区分问题发生在哪一层。

建议使用以下问题类别：

| 类别 | 典型情况 |
|---|---|
| `INTENT_ERROR` | 对用户目标理解错误 |
| `CONTEXT_ERROR` | 遗漏或错误使用已有上下文 |
| `CONSTRAINT_ERROR` | 未遵守必要约束 |
| `ROUTING_ERROR` | 路由到不适合的专家或执行器 |
| `PLAN_ERROR` | 计划不可行或遗漏必要步骤 |
| `TOOL_CONTRACT_ERROR` | 工具接口、参数或契约定义有误 |
| `TOOL_EXECUTION_ERROR` | 工具调用失败或输出异常 |
| `ENVIRONMENT_ERROR` | 环境、权限、依赖或资源问题 |
| `AUTHORIZATION_ERROR` | 动作超出授权或授权检查不正确 |
| `OBSERVATION_ERROR` | 未能正确观察执行后的真实状态 |
| `VERIFICATION_ERROR` | 验收条件不完整或验证结果错误 |
| `DELIVERY_ERROR` | 结果未正确呈现或交付物不可用 |
| `EXTERNAL_SERVICE_ERROR` | 外部模型、API 或服务故障 |
| `USER_CHANGE` | 用户改变了目标或约束 |
| `UNKNOWN` | 当前证据不足，无法可靠归因 |

实际实施可以允许一个任务同时具有多个相关问题类别，并区分已确认根因与待验证假设。

### 10.2 区分症状、直接原因与根因

例如，代码任务失败的表面现象是“测试未通过”。

直接原因可能是某个接口调用错误，根因则可能是：

- 需求理解错误；
- 规划时遗漏兼容性约束；
- 工具生成了错误参数；
- 测试环境与目标环境不一致；
- 验收器本身存在缺陷。

系统不能只记录“模型回答错误”，就结束诊断。

### 10.3 诊断需要证据

重要归因应尽可能关联：

- 原始任务和意图快照；
- 执行计划版本；
- 相关工具契约；
- 运行事件；
- 实际输入与输出引用；
- 验收器结果；
- 环境和版本信息；
- 用户反馈；
- 失败发生前后的状态变化。

如果证据不足，应标记为待确认，而不是编造确定的根因。

### 10.4 诊断与执行的职责分离

诊断模块应尽可能独立于产生原始结果的执行路径。

例如，在分析一次工具调用失败时，诊断器应根据运行证据、工具契约和独立验证结果进行分析，而不是仅接受执行器自己的解释。

诊断结果可以生成修复候选，但不能直接修改生产执行策略。候选改动必须经过相应的评测、门禁和发布治理。

## 十一、交付质量门禁

### 11.1 五道质量门

建议在任务全生命周期设置五道逻辑质量门。

**Gate A：需求理解**

确认目标、主要交付物、硬性约束和必要信息已经明确到足以开始执行。

**Gate B：计划与授权**

确认执行计划可行，预算充足，依赖关系合理，相关动作获得必要授权。

**Gate C：执行结果**

确认执行器产生了可供验收的真实结果，而不只是计划、解释或成功状态文本。

**Gate D：结果验证**

依据任务验收契约检查结果，识别未通过条件、残余风险和不确定性。

**Gate E：正式交付**

确认结果说明与真实状态一致，交付物存在且可用，未完成事项和重要限制已经披露。

不同任务可以使用轻量或完整的门禁流程，但不能省略对该任务真正必要的质量检查。

### 11.2 不允许以完成率替代质量

任务已经结束，不代表任务已经成功。

系统必须区分：

- 执行已结束；
- 结果已生成；
- 验收已通过；
- 目标已实现。

只有符合相应成功标准的任务，才能被计入已完成的成功交付。

### 11.3 质量与成本发生冲突时

当预算不足以完成全部必要工作时，系统可以暂停、请求追加预算或交付明确标注的部分成果。

不能为了保持表面上的完成率，静默删除必要验收步骤、隐瞒失败或将未经验证的结果标记为成功。

对于非关键的可选优化，可以在明确说明限制的前提下延后处理。

## 十二、与自进化体系的结合

### 12.1 可优化的对象

本专项产生的质量证据可以用于改进：

- 意图识别；
- 上下文检索；
- 约束提取；
- 澄清决策；
- 任务契约生成；
- 验收标准生成；
- 目标一致性检查；
- 失败归因；
- 交付质量验证。

### 12.2 不允许直接从单个失败自动修改生产策略

单个失败可能来自偶发环境异常、错误输入、工具故障或评测器缺陷。

因此，进化流程应当：

1. 收集可追溯的失败证据；
2. 分析可能原因；
3. 形成待验证的改进假设；
4. 建立针对性测试用例；
5. 在历史案例与回归集上验证；
6. 检查其他任务类型是否退化；
7. 通过正式门禁后再发布；
8. 持续监测并在必要时回滚。

### 12.3 防止指标投机

不能单独追求：

- 更少的澄清问题；
- 更短的平均执行时间；
- 更高的表面完成率；
- 更低的模型成本；
- 更少的失败记录。

这些指标必须与最终任务质量、必要约束满足率、返工情况和安全表现一起评估。

### 12.4 稳定版与进化轨道分离

稳定执行环境负责完成当前任务，并记录真实运行证据。

后台进化环境负责分析、测试和比较候选策略。

新策略不能因为在某几个案例中表现更好，就直接替换稳定版本。必须经过适当的回归测试、兼容性检查和发布门禁。

## 十三、核心质量指标

建议至少跟踪以下指标。

| 指标 | 作用 |
|---|---|
| 目标理解准确率 | 判断任务是否正确理解 |
| 硬性约束满足率 | 判断是否遵守必要要求 |
| 验收通过率 | 判断最终结果是否达标 |
| 交付物可用率 | 判断成果是否能够实际使用 |
| 不必要澄清率 | 识别过度追问 |
| 必要澄清遗漏率 | 识别应该询问却直接执行的情况 |
| 假设导致的返工率 | 判断默认假设是否合理 |
| 目标偏离率 | 识别执行范围是否发生不当变化 |
| 错误归因准确率 | 判断诊断结论是否有证据支持 |
| 任务恢复成功率 | 衡量错误修复和恢复能力 |
| 单位成功交付成本 | 衡量资源效率 |
| 质量相关返工率 | 判断是否因执行或验证不足而重复工作 |
| 误报成功率 | 识别未达标却被标记为成功的任务 |

这些指标应按任务类型、风险等级和执行环境分层分析，不能仅使用全局平均值掩盖某个专家或任务类别的严重问题。

## 十四、核心验收测试矩阵

| 测试 ID | 场景 | 通过条件 |
|---|---|---|
| INT-01 | 用户提出明确的简单任务 | 直接执行，不产生不必要的澄清 |
| INT-02 | 用户省略不影响结果的次要偏好 | 使用合理默认值 |
| INT-03 | 用户要求存在关键歧义 | 在执行受影响步骤前澄清 |
| INT-04 | 当前上下文已包含必要信息 | 不重复询问 |
| INT-05 | 系统推断出额外要求 | 明确区分推断与用户明确要求 |
| INT-06 | 当前指令与历史决策冲突 | 识别冲突并按变更规则处理 |
| INT-07 | 任务需要缺失的输入数据 | 请求必要信息，不伪造输入 |
| INT-08 | 多个未知项中只有一个影响关键结果 | 优先询问最关键的问题 |
| INT-09 | 任务部分内容可以独立完成 | 安全地先完成可执行部分 |
| INT-10 | 任务涉及不可逆外部操作 | 核实范围和授权后再执行 |
| INT-11 | 任务成功标准过于模糊 | 补齐必要的可验证标准 |
| INT-12 | 用户提出开放式创作任务 | 不强制要求不必要的量化标准 |
| INT-13 | 执行中发现假设错误 | 更新受影响计划并安全处理 |
| INT-14 | 局部修复被误判为全面重构需求 | 不擅自扩大任务范围 |
| INT-15 | 用户要求高质量结果 | 纳入必要的质量检查 |
| INT-16 | 工具执行成功但结果未达标 | 不标记为成功交付 |
| INT-17 | 任务结果缺少必要文件 | 不宣称交付完整 |
| INT-18 | 失败来自外部服务 | 不错误归因为意图理解失败 |
| INT-19 | 诊断证据不足 | 标记不确定，不编造根因 |
| INT-20 | 验收器自身存在问题 | 能够识别并隔离验收器缺陷 |
| INT-21 | 预算不足以完成必要验收 | 暂停或说明限制，不虚报成功 |
| INT-22 | 新策略减少澄清但增加重大返工 | 不通过质量门禁 |
| INT-23 | 用户在执行过程中改变目标 | 形成可追溯的目标变更 |
| INT-24 | 历史上下文包含已过期状态 | 不将过期信息当作当前事实 |
| INT-25 | 高优先级任务执行中发现非必要机会 | 不因此擅自改变主任务 |
| INT-26 | 新策略改善代码任务但降低文件操作质量 | 不允许未经针对性回归验证就全面发布 |
| INT-27 | 同一个任务发生多层故障 | 支持记录多个相关问题类别 |
| INT-28 | 用户要求更快完成任务 | 不省略必要的验收与安全检查 |
| INT-29 | 用户只要求建议而未授权执行 | 提供方案，不擅自产生外部副作用 |
| INT-30 | 任务通过验收但存在非关键限制 | 交付结果并准确说明限制 |

所有验收用例必须有实际执行证据。本文件定义设计与验收要求，不代表功能已经实现。

## 十六、完成判定

只有满足以下条件，才能认定本专项实施验收完成：

- 系统能够区分明确要求、已有事实、推断和未知信息；
- 重要需求可以追溯到相应来源；
- 系统能够合理判断何时直接执行、何时澄清；
- 低风险、可逆的任务不会被不必要的追问阻塞；
- 高影响、不可逆或关键歧义不会被随意假设；
- 每项复杂任务都有适当的成功标准；
- 执行过程中能够发现和处理目标偏离；
- 必要补全与擅自扩大范围之间具有明确边界；
- 任务完成与任务验收通过能够清楚区分；
- 重要失败可以进行有证据的分类与归因；
- 诊断结果不会未经评测直接修改稳定执行策略；
- 自进化不会通过牺牲任务质量换取表面效率；
- 所有关键验收场景均有真实执行证据。

**最终目标：让 EvoAgent 不只是听懂用户说了什么，而是尽可能准确地理解用户想要什么，并且能够证明最终交付确实满足了要求。理解、执行和验收必须形成一个连续、可追溯、能够持续改进的质量闭环。**</WritingBlock>

## 下一项专项：#95

建议继续推进 **#95：执行诊断与任务执行解耦、根因分析及自我修复治理**。

这项专项将深入解决一个你之前特别关注的问题：**如果智能体既负责执行，又负责判断自己为什么执行失败，那么它如何避免为自己的错误找错原因？**

重点包括：

1. 将执行器、观察器、诊断器和修复决策器分离；
2. 设计独立于原始执行路径的证据采集与验证机制；
3. 区分模型能力不足、需求理解错误、工具故障、环境问题和验收器错误；
4. 防止诊断器被执行器的错误解释误导；
5. 设计根因假设、证据强度、反证与多根因分析机制；
6. 让修复策略先在隔离环境中验证，再决定是否重新执行；
7. 避免自动修复不断扩大修改范围或掩盖真实故障；
8. 将故障案例转化为可复现的测试，而不是只积累错误日志；
9. 让诊断能力自身也能进化，但不允许诊断器绕过发布门禁。

这一步将把 EvoAgent 从“失败后尝试重试”，推进到“能够可靠判断为什么失败、选择正确的修复方法，并通过证据确认问题确实解决”。
