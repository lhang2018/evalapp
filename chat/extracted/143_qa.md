融合两类智能

我认为，真正把 EvoAgent 做成产品的关键，就在这里：**主动智能负责发现“还能为用户做什么”，无限优化负责让它越来越擅长发现、判断和完成这些事情。**

这两者不应该是两个独立功能，也不能简单地把主动智能接入现有自进化系统。我们需要重新设计它们之间的关系，让用户价值成为整个进化系统的共同目标。

我建议将 EvoAgent 的总体机制升级为：**双闭环、一条统一证据链、三类优化对象。**

两条闭环的分工非常明确：

- **用户价值闭环是产品运行机制。** 它要持续帮助用户完成任务、发现机会、减少重复劳动。
- **系统进化闭环是能力改善机制。** 它要利用真实证据，改善执行、判断、主动性和稳定性。

它们会相互促进，但不能混为一体。

例如，主动智能发现某个新机会后，不应该立即修改自己的策略、提高自主权限，或者把未经验证的判断写入长期通用规则。它可以先完成允许的行为，再将结果交给独立的进化控制器评估。

这保留了我们之前确定的稳定运行与后台进化分离的架构原则。<MemoryCite />

# 二、真正的进化对象，不只是任务执行能力

此前我们主要优化执行质量、工具调用、路由、记忆、工作流和稳定性。

现在，主动智能加入后，优化对象需要扩大，但不是无限制地增加模块。

我建议分成三大类。

这里有一个关键结论：

**无限优化不再只是优化“怎么完成任务”，还要优化“应该帮助用户做什么、何时帮助、帮助到什么程度”。**

但主动智能不能凌驾于任务执行之上。用户明确交办的高优先级任务，始终优先于可选的主动建议。

# 三、怎样知道主动帮助有没有变好？

这是整个设计最难的地方。

执行任务相对容易验证。例如，代码测试是否通过、文件是否生成、目标状态是否达成。

但主动帮助具有更大的不确定性。

假设系统向用户提出了十条建议：

- 用户接受了八条；
- 用户忽略了两条。

这不能直接证明系统很聪明。八条建议可能只是用户原本就打算做的事情，也可能给用户增加了大量负担。

所以，我们不能用建议数量、消息数量或者点击率来驱动进化。

建议建立一套专门的主动智能质量指标。

| 指标 | 要回答的问题 |
|---|---|
| 机会发现准确性 | 系统发现的事情是否确实存在？ |
| 机会相关性 | 这件事是否与用户当前目标有关？ |
| 增量价值 | 与不提供这项帮助相比，用户是否获得了额外收益？ |
| 建议采纳与使用 | 用户是否采用了建议，是否实际使用了准备好的成果？ |
| 误报率 | 系统是否经常推测出不存在或不重要的需求？ |
| 打扰成本 | 主动提醒是否打断用户、增加认知负担？ |
| 上下文时效性 | 系统是否错误地把过去的事情当作当前任务？ |
| 执行兑现率 | 系统提出的主动帮助是否真正完成并通过验收？ |
| 单位价值成本 | 为用户创造的实际收益需要多少额外计算和工具成本？ |

其中最重要的是**增量价值**。

可以用下面的概念式理解：

\[
\text{增量价值}
=
\text{提供主动帮助后的用户收益}
-
\text{不提供该帮助时的用户收益}
\]

实际收益可以体现为节省的时间、减少的错误、提高的成果质量、避免的遗漏等。真实系统需要通过合适的对照、用户反馈和可观察结果估计它，而不是假装能够精确测量每一项主观价值。

而且，用户没有采纳建议，并不必然代表建议错误；用户采纳了，也不必然代表建议创造了价值。因此需要结合任务结果、用户反馈和具体情境进行判断。

# 四、无限优化应该怎样作用于主动智能？

这里建议增加一个重要的内部机制：**主动策略的独立评测与进化**。

例如，EvoAgent 当前有三种候选策略：

- 策略 A：只在用户完成复杂任务后提供建议。
- 策略 B：在项目出现明确遗漏时提供建议。
- 策略 C：定期整理项目进展，并推荐下一步行动。

系统不能直接认定 C 最先进，所以 C 最好。

它应该先检查不同策略的适用范围，再通过历史任务回放、模拟、受控试验和必要的用户反馈，判断哪种策略在什么情况下更有效。

可能最终发现：

- 简单查询不需要主动建议；
- 长期项目适合阶段性整理；
- 高风险任务适合主动检查遗漏；
- 重复性任务适合建议建立工作流；
- 用户正在忙于明确任务时，不适合插入额外建议。

最终进化出来的不是一个对所有场景都采用同样行为的策略，而是一套**能够根据任务类型、用户授权、上下文和风险选择适当主动程度的策略体系**。

这比不断增加提示词、让模型自由发挥更可靠。

## 建议的主动策略进化流程

<CodeBlock language="mermaid" editable={false}>flowchart TD
    A["收集主动帮助的运行证据"] --> B["分析有效帮助与无效帮助"]
    B --> C["发现策略缺陷"]
    C --> D["生成候选策略"]

这样，主动智能自身也能够持续改善。

它不仅会学习哪些任务执行方式更好，还会逐渐学会哪些时候应该主动、哪些时候应该安静，以及哪些类型的帮助真正值得用户接受。

# 五、个人化进化和全局进化，必须分开

这是另一个不能忽略的问题。

假设某个用户喜欢系统在完成报告后，自动准备下一步行动清单。

另一个用户只希望系统完成指定任务，不需要额外建议。

如果 EvoAgent 将第一个用户的偏好直接升级为全局策略，第二个用户的体验就可能变差。

因此，建议建立三个层次：

| 层次 | 优化内容 | 作用范围 |
|---|---|---|
| 个人偏好层 | 主动频率、建议风格、确认习惯、允许的自动化范围 | 当前用户 |
| 专家与场景层 | 编程、资料整理、手机操作等场景的有效主动策略 | 指定专家或任务类型 |
| 全局能力层 | 通用机会发现、结果验证、安全约束、评测方法 | 经过验证后适用的系统范围 |

三者之间可以传递经过治理的经验，但不能直接混用。

个人偏好可以影响这个用户看到什么、什么时候看到，但不能绕过全局安全规则。

专家级策略可以提升某个领域的表现，但必须检查是否影响共享内核和其他专家。

全局改进则必须有更充分的跨场景证据，不能因为一个用户的一次反馈就自动推广。

# 六、建立统一的优先级规则，防止主动智能抢占主任务

我建议将所有任务和主动机会放进统一的任务优先级治理机制。

优先级不是简单的数字排名，而是先满足硬约束，再比较价值。

有些主动帮助可以在后台准备，不必立即打断用户；有些可以等到主任务完成后再展示；只有真正紧迫且有充分依据的事项，才应按照用户设置和相应策略及时提醒。

此外，主动智能不能无限消耗模型调用、工具调用和后台资源。应当设置独立的主动分析预算、频率上限和停止条件，避免系统为了持续进化而不断产生没有实际价值的活动。

# 七、最终架构应该增加什么？

我建议在现有 EvoAgent 架构中正式加入一个横跨产品运行和后台进化的能力域：

**主动智能与自进化协同控制体系。**

它不是取代已有的通用内核、领域专家或独立进化控制器，而是把它们连接起来。

主要包含：

1. **用户状态理解：** 汇总授权范围内的近期对话、项目进度、决策和待解决问题。
2. **机会发现：** 识别遗漏、下一步工作、相关资料和重复劳动。
3. **主动行为策略：** 决定保持安静、提供建议、准备成果或执行任务。
4. **价值与风险评估：** 评估实际收益、时机、打扰成本和风险。
5. **主动效果评测：** 验证帮助是否真正有效，而不只看用户是否点击。
6. **主动策略进化：** 通过隔离实验和发布门禁持续优化机会发现与主动行为。
7. **个性化策略管理：** 在个人偏好、专家策略和全局能力之间建立清晰边界。
8. **统一证据链：** 将任务结果、主动帮助效果、成本、用户反馈与版本变更关联起来。
9. **稳定运行与后台进化隔离：** 确保实验不会未经验证就改变用户正在使用的系统。
10. **用户控制中心：** 允许用户调整主动程度、数据范围、提醒频率和授权边界。

这套体系应当与前面设计的质量评测体系 AEVC 协同工作，而不是重新建立一套重复的评测基础设施。

## 最后，最关键的战略判断

EvoAgent 的无限进化不应该追求“系统变得越来越复杂”，也不应该追求“系统每天做越来越多的事情”。

真正值得追求的是：

- 同样的任务，完成得越来越好；
- 同样的成本，创造更多实际价值；
- 同样的错误，越来越少重复发生；
- 同样的上下文，能够发现更重要的机会；
- 同样的自主权限，能够做出更合理的判断；
- 随着长期使用，用户需要投入的指导和纠错越来越少。

因此，我建议把 EvoAgent 的长期进化目标正式定义为：

**在不突破安全、隐私、授权和资源边界的前提下，持续提高系统为用户创造的可验证价值，并降低用户为获得这些价值所付出的时间、精力和管理成本。**

这使得“无限优化”不再只是内部工程目标，而是围绕用户价值展开的持续改进机制。

下一步最值得做的，是把这套关系落实为正式的《EvoAgent 主动智能与自进化协同架构设计》，明确组件边界、数据流、策略进化接口、评测指标和发布门禁，再与原有 PRD、架构设计及各专项建立追踪关系。
