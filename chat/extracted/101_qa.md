# EvoAgent 第四十九专项：人机协作、用户控制权与可接管性

本轮继续设计 EvoAgent 的人机协作体系，重点不是增加聊天界面或通知功能，而是解决一个更深层的架构问题：

**当智能体能够长期运行、自主规划、调用工具、修改项目并持续进化时，如何让用户始终保有对目标、授权、资源和关键结果的控制权，同时又不必事事亲自监督？**

此前已经设计了目标价值评估与自主性治理（GVAAG）。它负责判断系统应该做什么、是否值得做、允许自主到什么程度，以及什么时候应该停止。

本专项 HACCG 则负责将这些规则落实到真实的人机交互中：什么时候通知用户、什么时候需要批准、如何处理用户改变主意、如何暂停或取消任务，以及如何在发生异常时把控制权交还给用户。

## 一、第一性原理：用户不应该成为系统的实时调度器

传统工具需要用户一步步操作。自主智能体则应该承担更多规划、执行和恢复工作。

但这不意味着用户应该失去控制权。

一个好的个人智能体应当做到：

- **日常操作少打扰：** 不需要用户确认每一次内部计算和低风险步骤。
- **关键决策可理解：** 用户能够知道系统正在追求什么目标、准备做什么，以及为什么。
- **重要操作可控制：** 涉及重大副作用、权限变化或超出原授权范围的操作时，必须执行适当的确认流程。
- **任务状态可接管：** 用户可以暂停、取消、调整目标，或接管未完成的工作。
- **错误发生后可恢复：** 系统能够保存状态、解释失败，并提供明确的继续、修复或放弃选项。

这里最重要的区别是：

**减少用户操作次数，不等于减少用户控制权；提高自主性，也不等于把更多决策隐藏起来。**

这个控制平面需要满足两个架构要求。

第一，所有设备上的用户操作都应经过统一的任务控制协议，不能因为 Android 和 Linux 主机各自实现了一套控制逻辑，就出现一端显示已取消、另一端仍继续执行的情况。

第二，**交互层不能直接绕过任务、安全与授权机制修改底层状态**。用户点击“取消”后，HACCG 应向任务控制器发出正式的取消请求，由 LTAR、TERSO 等模块执行相应的安全停止和状态处理。

# 三、交互策略：哪些事情需要告诉用户？

这是 HACCG 的第一个关键设计。

如果系统把所有内部步骤都推送给用户，用户很快就会关闭通知；如果系统只在最终失败时才告知用户，又可能让用户失去干预机会。

建议建立五类交互动作。

<box border radius="xl" padding={3} gap={3}>
  {#each [
    ["I0 · 静默执行","低风险、可逆、已授权且处于任务范围内的操作，只记录必要的运行事件。"],
    ["I1 · 状态通知","任务开始、阶段完成、长时间等待或重要进展时，提供简洁的状态更新，不要求用户回复。"],
    ["I2 · 建议征询","存在多个合理方案，但系统可以先完成低风险调查；向用户提供选择，必要时允许继续安全的独立工作。"],
    ["I3 · 必须确认","即将执行超出既有授权的操作，或涉及预先规定必须人工批准的重大副作用时，暂停相关操作并等待明确批准。"],
    ["I4 · 安全阻断","发现越权、授权失效或违反强制安全策略时，阻止相关操作；不能通过普通的用户确认按钮绕过安全边界。"]
  ] as item}

      <title size="md">{item[0]}</title>

这些是交互策略等级，不是 TERSO 的操作风险等级，也不是 GVAAG 的自主性等级。

同一项操作是否需要确认，应综合判断操作风险、用户授权、任务范围和当前状态。

例如，编程专家在用户指定的项目中修改一个局部文件，可以属于静默执行；但将代码推送到公共仓库，即使技术上只是一条命令，也可能需要单独确认。

## 3.1 不要让每个模块各自决定是否打扰用户

Router、Planner、专家和工具运行时都可能发现需要用户参与的情况。

但它们不应各自直接弹出互不协调的确认窗口。

建议由统一的 `InteractionPolicyEngine` 接收各模块的交互请求，进行合并、排序和去重。

例如，某个代码任务连续发现三个问题：

- 测试覆盖不足；
- 项目依赖较旧；
- 一个无关模块存在潜在技术债。

系统可以把这些问题合并为一条有重点的进度更新，而不是连续发送三条通知。

但如果其中一项操作确实需要在执行前获得批准，就不能因为合并通知而将它隐藏在普通的进度消息里。

## 3.2 打扰策略不能覆盖必须确认的要求

系统可以根据用户偏好减少普通通知、合并进度消息、降低低价值提醒频率。

但它不能因为用户开启了“免打扰”，就自动批准本来需要人工批准的操作。

免打扰影响的是通知方式和时机，而不是授权规则本身。

# 四、授权与确认：用户究竟批准了什么？

这是整个人机控制体系中最需要精确设计的部分。

假设系统向用户询问：

“是否允许我继续？”

这个问题本身就不合格，因为用户不知道“继续”具体意味着什么。

系统可能只是继续运行测试，也可能准备修改文件、安装依赖、上传代码或部署服务。不同操作的影响完全不同。

因此，建议建立独立的 `ApprovalRecord` 和 `AuthorizationScope`，将确认请求与实际授权范围分离管理。

## 4.1 每次重要确认都要说明六件事

    ["影响什么","列出涉及的文件、项目、设备、外部服务或其他资源。"],

确认界面不需要展示所有底层技术细节，但必须让用户理解决策的实际含义。

## 4.2 授权应当具有明确边界

建议一个授权记录至少包含：

| 字段 | 作用 |
|---|---|
| `approval_id` | 确认记录标识 |
| `subject` | 获得授权的智能体或任务 |
| `action_scope` | 允许执行的操作类型 |
| `resource_scope` | 允许访问或修改的资源范围 |
| `task_scope` | 授权适用的目标和任务 |
| `budget_limit` | 允许使用的预算上限 |
| `valid_from` / `expires_at` | 授权生效和过期时间 |
| `conditions` | 执行前必须满足的条件 |
| `revocation_policy` | 如何撤销授权 |
| `approval_evidence` | 用户批准的记录与范围摘要 |
| `status` | 待批准、有效、已撤销、已过期或已使用等状态 |

并不是所有授权都需要限制到一个单独的工具调用。

用户可以提前批准某个项目在指定范围内运行测试、修复测试失败并执行回归验证。

但这个授权不能自动扩展到其他项目、上传私人代码、部署到生产环境或修改全局安全策略。

## 4.3 一次确认不等于永久授权

建议区分三种授权模式：

- **单次授权：** 只允许指定的一次操作。
- **任务级授权：** 允许在某个目标和明确范围内执行一组操作。
- **持续授权：** 在限定的任务类别、资源、预算与期限内允许反复执行。

持续授权必须能够被检查、过期和撤销。

如果任务目标、资源范围或风险发生实质性变化，系统需要重新判断原授权是否仍然适用，而不是简单地沿用以前的批准。

## 4.4 确认不能成为绕过安全边界的万能按钮

必须区分两种情况：

- 用户有权决定的事项，例如项目修改方案、预算偏好和可选功能；
- 受强制安全规则、访问权限或其他约束限制的事项。

前者可以通过授权或确认处理；后者不能仅凭用户点击“我同意”就自动放行。

同样，系统也不能通过拆分操作规避确认。例如，一次性上传整个项目需要确认，就不能把上传拆成一百个小文件后当作无需确认的普通操作。

**确认的依据应当是实际影响与授权范围，而不是单条命令看起来有多简单。**

# 五、任务控制协议：暂停、恢复、取消和接管必须有明确语义

在长期任务中，“停止”不是一个简单的布尔值。

如果系统正在编译代码、生成视频、写入文件或调用远程 API，用户按下暂停或取消后，系统需要知道当前操作是否能够立即中断，以及已经发生的副作用如何处理。

建议建立统一的 `TaskControlProtocol`。

## 5.1 定义五种控制操作

| 操作 | 含义 |
|---|---|
| `PAUSE` | 请求任务进入安全暂停状态，保留可恢复的进度 |
| `RESUME` | 在重新检查状态、依赖与授权后继续任务 |
| `CANCEL` | 请求终止任务，不再启动新的普通工作步骤 |
| `CHANGE_GOAL` | 修改目标、范围或约束，触发影响分析与必要的重新规划 |
| `TAKEOVER` | 将后续关键决策或具体操作交给用户，或切换到人工控制模式 |

这些操作不能只改变 UI 上的任务状态。

它们必须与 LTAR 的生命周期状态、DAG 执行器、TERSO 工具运行时以及必要的安全检查协同工作。

## 5.2 暂停与取消的区别

**暂停**意味着系统预计稍后继续。

因此，暂停时需要：

- 停止启动新的非必要步骤；
- 处理中断请求与正在运行的子任务；
- 保存可靠的检查点；
- 记录未完成节点和外部操作状态；
- 释放不再需要的资源；
- 保留恢复所需的状态与依赖信息。

**取消**意味着不再继续当前任务的正常执行路径。

但取消不等于自动撤销已经发生的事情。

例如：

- 已修改的本地文件可能需要保留为未提交变更；
- 已经发送的外部请求可能无法撤回；
- 正在进行的远程任务可能只能请求取消，不能保证即时终止；
- 已产生的费用不能仅凭取消任务而自动退回。

因此，取消操作需要返回实际处理结果，而不是一律显示“已撤销全部操作”。

## 5.3 建立正式的控制状态机

这是一组建议的控制状态，而不是任务生命周期全部状态的替代品。执行失败、验收失败、等待外部依赖等情况，仍然需要由 LTAR 的完整状态机管理。

还要注意，`PAUSE_REQUESTED` 和 `CANCEL_REQUESTED` 都不是最终状态。系统必须等待执行器报告实际停止情况，并核验关键副作用。

## 5.4 控制请求需要幂等与顺序规则

手机可能重复发送取消请求，设备也可能在网络断开后重传命令。

因此，控制协议需要支持：

- 唯一的 `control_request_id`；
- 重复请求去重；
- 任务版本或状态版本校验；
- 控制命令的确认回执；
- 过期命令拒绝执行；
- 冲突请求的明确处理规则。

例如，用户先点击暂停，随后又点击取消。系统应依据明确的状态转换规则处理，不应该因为消息到达顺序不同而意外恢复任务。

# 六、用户中途改变要求：不能简单地覆盖原始目标

真实工作中，用户经常在任务执行期间改变主意。

例如：

- “先不用追求最高质量，控制一下成本。”
- “不要改这个模块了，换一种实现方式。”
- “原计划是生成一分钟的视频，现在缩短到三十秒。”
- “暂停当前优化，我想先看一下已经完成的部分。”
- “这个项目的代码不能上传到任何云服务。”

这些变化对任务的影响并不相同。有些只改变偏好，有些需要重新规划，有些则必须立即阻止相关操作。

建议建立 `GoalChangeManager`，负责解析变更、计算影响，并协调目标版本、任务计划、授权和验收契约。

## 6.1 每次实质性变更都应生成新版本

不建议直接覆盖原始目标。

例如：

- `goal_version = 1`：原始目标；
- `goal_version = 2`：用户修改后的目标；
- `plan_version = 3`：根据新目标重新生成的计划；
- `contract_version = 2`：更新后的验收契约。

这些版本不必同步递增，但应保留各自的变更记录及依赖关系。

这样系统才能回答：原本计划做什么、用户何时修改了要求、哪些步骤已经完成、哪些步骤因新目标而失效。

## 6.2 按变更影响决定如何处理

建议将目标变更分为四类。

  <box gap={1}>
    <title size="md">C4 · 关键约束变化</title>
    <text color="secondary" size="sm">例如禁止上传项目代码、停止某类外部操作。应立即阻止可能违反新约束的后续动作，并处理在途操作。</text>
  </box>
</box>

## 6.3 新要求与旧任务冲突时，优先保护当前有效约束

例如，用户要求“从现在开始，项目文件不得上传到云端”。

系统不能等到整个任务重新规划完成后才应用这项要求。

它应该先阻止尚未开始的相关上传操作，向在途执行器发送停止请求，核验哪些数据已经发出，然后再调整任务计划。

与此同时，也不能假定所有在途请求都可以立即撤销。系统需要准确报告已停止、正在停止、无法撤回和状态未知的操作。

## 6.4 变更后重新验收，不意味着所有工作都要重做

如果用户只是调整报告的排版，已完成的事实核验可能仍然有效。

如果用户更改了视频时长，某些镜头和配音素材可能还能复用，但时间轴与合成结果需要重新检查。

如果用户更改了代码的核心行为要求，相关测试、代码和依赖它们的产物可能需要重新执行。

因此，`GoalChangeManager` 应结合 DAG 依赖图和 UQEAG 证据有效性规则，只让受影响的部分失效，而不是无条件重做全部工作。

# 七、人工接管：让用户真正接管任务，而不是只能聊天指挥

对于个人智能体，用户有时并不希望取消整个任务，只是希望亲自处理某个关键步骤。

例如：

- 系统已经完成代码修改，用户想亲自审查并决定是否合并；
- 视频素材已生成，用户想手动调整时间轴；
- 旅游方案已规划好，用户想自己确认最终预订；
- 系统遇到无法自动处理的界面，用户想接手完成操作。

建议建立 `HumanTakeoverSession`。

## 7.1 接管需要明确交接什么

至少应包括：

- 当前目标及版本；
- 已完成工作；
- 未完成工作；
- 当前状态与检查点；
- 已产生的副作用；
- 待处理问题；
- 可操作资源；
- 当前授权范围；
- 接管期间禁止自动执行的操作；
- 恢复智能体控制所需的条件。

用户接管期间，系统不应继续修改同一资源，除非已经明确采用了允许并行协作的机制。

例如，用户正在手动编辑一个文件时，智能体不能继续自动覆盖该文件的内容。

## 7.2 人工接管后，智能体如何恢复？

建议采用显式交接流程：

1. 保存任务检查点；
2. 标记资源的控制权；
3. 将当前状态与未完成工作展示给用户；
4. 用户完成人工操作；
5. 系统读取实际变化并核验；
6. 检查版本差异与依赖；
7. 重新确认任务目标与授权仍然有效；
8. 更新计划并恢复执行。

对于用户手动修改过的文件，系统应先识别差异并保留用户修改，不能简单地用旧检查点覆盖当前状态。

## 7.3 人工接管不应要求用户理解所有内部细节

用户通常只需要知道：

- 当前做到哪一步；
- 哪个问题需要自己处理；
- 哪些操作已经完成；
- 接下来可以做什么；
- 接管后智能体会不会继续自动操作。

内部 DAG、日志和版本细节可以按需展开，但不能成为用户接管任务的必要前提。

# 八、进度展示：让用户知道进展，而不是被日志淹没

对于个人设备优先的 EvoAgent，主要入口是 Android，但实际工作可能发生在手机本地、Windows 电脑或 Linux 主机上。

用户需要一个统一的任务视图，了解所有设备正在做什么，而不是分别打开不同设备查看日志。

建议建立 `TaskProgressView`，统一展示任务目标、状态、阶段进度、下一步、风险和资源使用情况。

## 8.1 进度至少分成四层

<box border radius="xl" padding={3} gap={3}>
  <box gap={1}>
    <title size="md">第一层：一句话状态</title>
    <text color="secondary" size="sm">例如：“代码修改已完成，正在运行回归测试。”适合手机通知与任务列表。</text>
  </box>
  <divider color="subtle"/>
  <box gap={1}>
    <title size="md">第二层：阶段进度</title>
    <text color="secondary" size="sm">展示已完成阶段、当前阶段、待处理阶段和阻塞原因。进度应来自真实状态，而不是模型猜测。</text>
  </box>
  <divider color="subtle"/>
  <box gap={1}>
    <title size="md">第三层：关键决策</title>
    <text color="secondary" size="sm">解释为何选择当前方案、为何更换工具、为何暂停或请求用户确认。</text>
  </box>
  <divider color="subtle"/>
  <box gap={1}>
    <title size="md">第四层：完整审计与运行轨迹</title>
    <text color="secondary" size="sm">查看节点状态、工具调用、版本、错误证据、授权记录和验收结果。</text>
  </box>
</box>

这四层应当共享同一份任务状态数据。不能让简洁的进度界面显示“已完成”，而底层任务状态仍处于等待或未验证状态。

## 8.2 进度百分比必须有真实依据

复杂任务中，“完成了 80%”经常只是主观估计。

如果 DAG 有十个节点，也不能简单地认为完成八个节点就代表整个任务完成了 80%，因为最后的集成、验收和发布可能是最关键的工作。

建议优先展示：

- 已完成的阶段；
- 剩余的必要阶段；
- 正在等待的依赖；
- 已知阻塞项；
- 预算消耗；
- 验收状态。

如果确实需要百分比，应使用已定义的进度计算规则，并明确它是工作量估计还是实际完成比例。

## 8.3 进度通知应当具有信息价值

不必每次工具调用都通知用户。

更适合通知的事件包括：

- 关键阶段完成；
- 预计成本或时间发生重大变化；
- 出现需要用户决策的问题；
- 长时间任务进入等待状态；
- 任务已经达到验收标准；
- 发生重要失败或安全阻断。

对于频繁发生但没有新信息的事件，可以在本地保留完整记录，只向用户呈现摘要。

# 九、手机优先与多设备控制：断联后仍然知道谁在执行

这是 EvoAgent 现有部署方向下必须落实的设计。

Android 负责主要交互，Windows 电脑和 Linux 主机可能承担较重的执行工作。设备之间可能断联，任务也可能在后台继续运行。

因此，控制权不能只保存在某个设备的内存里。

## 9.1 建立统一的控制请求协议

建议所有控制请求都包含：

- `control_request_id`；
- `task_id`；
- `target_device_id`；
- `control_action`；
- `expected_task_version`；
- `requested_by`；
- `created_at`；
- `expires_at`；
- `authorization_ref`；
- `request_status`。

这样 Android 可以向 Linux 主机发送暂停请求，Linux 主机可以返回实际执行状态；即使请求重传，也能通过标识避免重复处理。

## 9.2 区分命令已发送、已接收和已生效

例如，手机显示用户已经取消任务，但网络恰好中断。

这时只能说明手机已经发出取消请求，不能宣称远程任务已停止。

建议区分以下状态：

- 请求尚未发送；
- 请求已发送；
- 目标设备已接收；
- 目标设备正在处理；
- 目标设备确认已生效；
- 请求超时或结果未知。

如果设备离线，系统应明确展示控制请求仍在等待确认。

对于涉及高风险操作的任务，失去控制连接后是否继续执行，应由事先定义的任务策略决定；不能统一假设所有任务都应继续，也不能假设所有任务都能安全立即停止。

## 9.3 授权撤销必须有跨设备语义

假设用户撤销了某个远程执行权限。

系统需要将撤销事件持久化，并尽快传播到相关设备，同时检查是否仍有在途操作。

在撤销尚未得到远程确认时，控制界面应显示实际状态，而不是把“已发出撤销请求”当作“所有设备都已停止使用权限”。

对于无法联网的设备，可以在本地执行已经配置的安全限制，并在恢复连接后核验状态。

## 9.4 离线操作恢复后需要对账

设备重新连接后，应同步：

- 控制请求及其处理结果；
- 任务状态变更；
- 授权变化；
- 已执行的操作；
- 未完成的操作；
- 产物与检查点；
- 尚未确认的外部副作用。

如果手机显示任务已暂停，而主机记录任务已完成，系统不能简单地用最后到达的消息覆盖另一个状态。

需要根据权威状态版本、事件顺序和实际执行证据进行对账，并在存在冲突时保留证据、暂停有风险的后续操作。

# 十、确认与授权界面的防误导设计

用户控制权不只取决于系统是否提供按钮，还取决于用户是否理解按钮的含义。

如果系统使用模糊措辞、隐藏副作用，或者让“批准”成为最醒目的默认选项，用户可能在没有真正理解的情况下授权。

因此，HACCG 应建立统一的 `ApprovalUXPolicy`。

## 10.1 确认界面必须满足四个条件

1. **操作明确：** 让用户知道具体要执行什么。
2. **影响可见：** 展示主要资源、外部影响、成本与风险。
3. **选择对等：** 允许批准、拒绝、修改方案或稍后决定。
4. **结果可追溯：** 批准后能够查看授权范围、执行结果和撤销方式。

不应该用“为了完成任务，请点击继续”来隐藏本来需要用户判断的实质性选择。

## 10.2 不同操作使用不同的确认粒度

例如：

- 普通低风险操作可以通过已有的任务级授权完成；
- 新增外部服务、扩大资源访问范围，需要针对变化重新确认；
- 高影响、不可逆操作，需要展示具体操作和后果；
- 不允许的操作必须明确阻断，而不是提供一个看似可以覆盖安全规则的按钮。

## 10.3 确认超时不能默认等于批准

如果用户没有回复，系统应依据操作类型和既定策略决定如何处理。

例如：

- 普通可选优化：可以等待或跳过；
- 必须确认的外部操作：保持阻塞；
- 可能造成损害的持续执行：根据预先定义的安全策略暂停相关工作；
- 用户尚未批准的权限扩展：不得自动生效。

对于已过期的确认请求，即使用户随后点击了旧通知，也需要检查请求是否仍然有效。

如果任务目标、资源范围或操作内容已经变化，原确认不能直接复用。

---

# 十一、用户反馈与长期偏好：学习交互习惯，但不能过度推断

EvoAgent 需要逐渐理解用户希望怎样协作。

例如，用户可能偏好：

- 普通任务少通知；
- 重要决策主动说明理由；
- 代码任务尽量自主完成；
- 修改关键文件前先展示差异；
- 长期任务每天汇报一次进展。

这些偏好有助于降低交互成本，但需要与授权和安全规则分离。

## 11.1 将交互偏好分为三类

| 类型 | 示例 | 处理方式 |
|---|---|---|
| 显式偏好 | “普通进度不用通知我” | 在适用范围内保存并执行 |
| 情境性偏好 | 当前正在处理紧急任务，希望减少打扰 | 仅在当前情境内应用 |
| 推断性偏好 | 用户多次忽略普通进度通知 | 作为候选偏好，不自动扩大权限 |

系统不能因为用户长期没有回复通知，就推断用户已经授权所有相关操作。

也不能因为用户过去允许某个项目自动运行，就认为所有未来项目都获得了同样授权。

## 11.2 偏好更新应当可解释和可撤销

建议将用户偏好记录为独立的 `InteractionPreference`，包含适用范围、来源、更新时间和置信依据。

例如：

“普通进度通知偏好：合并为阶段摘要；来源：用户明确要求；适用范围：所有普通任务；安全确认不受影响。”

这样用户可以理解系统为什么采用某种交互方式，并在需要时修改。

## 11.3 反馈不应直接修改安全策略

用户可以要求系统少打扰、提高自主执行程度或改变进度报告频率。

但这些偏好不能自动改变强制权限、数据隔离规则或必须执行的安全检查。

HACCG 应当把交互偏好交给偏好与记忆系统管理，把授权变更交给独立的安全治理流程处理。

---

# 十二、评测体系：怎样判断人机协作真的变好了？

HACCG 本身也需要独立评测。

如果用户点击次数减少了，但误批准的操作增多，那么交互优化并不成功。

建议从六个维度进行评测。

| 维度 | 评测指标 |
|---|---|
| 交互效率 | 每个任务所需的用户操作次数、确认次数、无效打扰次数 |
| 理解程度 | 用户是否正确理解目标、风险、授权范围与当前状态 |
| 控制能力 | 暂停、取消、目标变更和接管是否按预期生效 |
| 授权正确性 | 未授权操作率、过期确认误用率、范围外执行率 |
| 恢复质量 | 断联后控制状态对账准确率、人工接管后的恢复成功率 |
| 用户体验 | 用户满意度、关键问题解决时间、反复解释次数 |

其中，授权正确性和关键控制可靠性属于不可随意抵消的保护指标。

不能为了减少确认次数，而让原本需要确认的操作静默执行。

## 12.1 建立专门的交互故障测试集

建议测试以下场景：

- 用户在任务执行期间改变目标；
- 手机与主机断联时发出取消请求；
- 旧的确认通知在任务变化后被点击；
- 两个设备同时请求暂停与恢复；
- 用户撤销授权，但远程操作已经开始；
- 用户接管文件后，智能体试图继续修改；
- 用户要求停止任务，但远程工具无法立即中断；
- 长期任务等待确认期间，预算或授权到期；
- 进度界面显示完成，但底层任务尚未验收；
- 多个模块同时产生通知，需要合并或区分优先级。

这些测试不只检查界面显示，还应验证任务状态、授权记录、在途操作和最终副作用。

## 12.2 交互系统不能自己证明自己有效

例如，HACCG 新版把确认界面改得更简洁，用户平均点击时间下降了。

这并不能直接证明体验提高，因为用户也可能只是更快地点击了不理解的按钮。

需要同时评估用户对操作内容的理解、授权准确性、任务完成质量和错误恢复情况。

# 十四、下一专项：跨专家知识共享、能力资产与技能进化

到目前为止，我们已经设计了目标决策、自主性治理、人机协作、质量验收和因果诊断。

但多专家架构还有一个长期问题：

**当不同专家在执行任务时不断积累经验、工具用法、工作流和解决方案，哪些知识应该共享，哪些应该隔离，哪些能够沉淀成可复用能力，又如何判断这些能力真的可靠？**

例如：

- 编程专家解决了一个 AST 代码重构问题，能否让其他编程任务复用？
- 漫剧专家跑通了一套分镜、配音与视频合成流程，能否固化成稳定工作流？
- 通用专家发现了一种有效的需求澄清方式，能否共享给旅游和编程专家？
- 某个专家总结出一条经验，但它只在特定模型版本下有效，系统如何防止其他专家错误复用？
- 两个专家分别形成了相似的能力，系统应该合并、保留独立版本，还是让它们竞争评测？
- 某项技能长期没有使用，或者依赖的工具已经失效，系统如何识别并淘汰它？

建议下一专项定义为：

**Cross-Expert Knowledge & Capability Evolution，简称 CEKCE。**

重点研究：

1. 如何建立统一的能力注册表和技能依赖图；
2. 如何区分事实知识、经验记忆、工具能力、工作流与可执行技能；
3. 如何定义全局共享、领域共享、专家私有和任务临时知识的边界；
4. 如何将成功任务转化为经过验证的可复用能力；
5. 如何对技能进行版本管理、兼容性检查、评测和回滚；
6. 如何防止错误经验在多个专家之间传播；
7. 如何处理重复技能、冲突知识和过期能力；
8. 如何让一个专家借鉴其他专家的能力，而不直接污染自己的核心策略；
9. 如何判断一项技能应该升级、拆分、合并、冻结或淘汰；
10. 如何建立能力发现、复用、验证与反馈闭环；
11. 如何将 AST、代码分析、视频合成、浏览器操作等专业技术沉淀为可组合的能力包；
12. 如何让技能资产在 Android、Windows 和 Linux 设备之间安全分发，并处理不同设备的依赖差异。

本专项的核心原则是：

**经验可以共享，但未经验证的经验不能直接成为全局规则；技能可以复用，但每次复用都必须满足适用条件、依赖要求和安全边界。**

这会把 EvoAgent 从“拥有多个专家的智能体”，进一步推进为“能够积累、验证、组合、传播和淘汰能力的智能体系统”。
