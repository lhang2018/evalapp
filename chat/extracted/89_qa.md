# EvoAgent 第三十七专项：能力学习、经验沉淀与长期知识演化

这一轮要解决的是：**EvoAgent 完成任务之后，究竟应该学到什么、保存什么、复用什么，以及如何防止错误经验污染未来的任务。**

前面已经建立了自进化闭环 SELCIA：发现问题、分析根因、生成候选、独立评测、受控发布、持续监测。

现在进入下一个层次：即使一次任务成功完成，系统也不应该只留下聊天记录和最终产物，而应该判断这次经历是否产生了值得长期保留的知识。

例如，EvoAgent 完成了一次大型代码重构，发现：

- 使用 AST 分析比纯文本替换更适合该类代码；
- 修改后必须运行特定测试；
- 某个工具在特定项目结构下存在兼容性问题；
- 用户偏好先给出计划，再执行大规模修改；
- 一组任务可以沉淀为可复用的工作流。

这些内容不能全部塞进同一个记忆库，更不能全部自动升级为通用规则。

本专项建议定义为：

**Capability Learning, Experience Consolidation & Long-Term Knowledge Evolution，简称 CLEK。**

它负责经验分类、知识沉淀、适用范围、验证晋升、冲突解决、过期检测和长期能力演化。

## 一、第一性原理：记住一件事，不等于学会一项能力

首先要区分四个层次。


    <title size="md">第一层：经历记录</title>
    发生过什么？例如某次代码重构失败，原因可能是符号引用没有同步修改。



    <title size="md">第二层：经验提炼</title>
    从经历中发现了什么规律？例如重构前需要分析符号引用与依赖关系。



    <title size="md">第三层：可复用策略</title>
    如何把规律变成可以执行的策略？例如先构建 AST 与符号引用图，再生成修改计划。



    <title size="md">第四层：经过验证的能力</title>
    在明确的适用范围内，经过独立评测，能够稳定完成目标的工具、规则、工作流或专家能力。


这四层之间不能自动跳跃。

一次失败可以产生一个值得调查的经验，但不能直接证明一条通用规则；一次成功可以提供有价值的样本，但不能证明某个策略适用于所有相似任务。

**CLEK 的目标不是让系统记住更多，而是让有价值的经验逐步成为可靠、可验证、可复用的能力。**

# 二、建立统一的知识类型：不同信息必须进入不同位置

EvoAgent 需要的不是一个无限扩大的记忆库，而是一套有边界的知识体系。

建议将长期知识分为八类。

| 知识类型 | 示例 | 主要存储与管理位置 |
|---|---|---|
| 事实知识 | 某个工具支持哪些参数 | 工具注册表、权威文档与证据引用 |
| 用户偏好 | 用户倾向先确认方案再执行 | 用户偏好记忆 |
| 项目知识 | 当前代码仓库使用的框架与目录结构 | 项目记忆与项目索引 |
| 任务经验 | 某次任务失败的原因及有效修复方式 | 经验库 |
| 领域知识 | AST、视频编码、旅游规划等专业知识 | 对应专家的知识空间 |
| 程序化策略 | 某种经过验证的执行步骤 | 专家策略或工作流库 |
| 工具与能力 | 一个可调用的 AST 分析器或视频质检工具 | 能力注册表与工具运行时 |
| 系统规则 | 权限约束、状态一致性和发布门槛 | 受保护的共享内核与治理配置 |

这些知识之间可以互相引用，但不应该随意互相覆盖。

例如，用户偏好“希望尽量快速完成任务”，不能覆盖代码重构的正确性门槛；某次项目经验也不能直接变成所有项目通用的默认规则。

## 2.1 先判断知识属于谁

每条候选经验至少要回答：

- 它针对当前任务、当前项目、某个专家还是整个系统？
- 它描述的是事实、偏好、假设还是经过验证的规则？
- 它适用于什么条件？
- 有哪些证据支持它？
- 什么情况下它可能失效？
- 它是否涉及敏感信息？
- 是否允许被其他专家检索或复用？

如果这些问题还没有明确答案，经验可以暂时保留在局部经验区，但不应该直接晋升到共享内核。

# 三、经验如何产生：不要只从失败中学习

如果 EvoAgent 只在失败时学习，就会错过大量有价值的成功经验。

但如果它对每次成功都进行完整的经验提炼，又会产生巨大的计算与存储成本。

建议设置四种经验来源。


    <title size="md">1. 失败驱动学习</title>
    从失败、返工、超时、异常恢复和验收不通过中发现问题，形成候选经验。



    <title size="md">2. 成功驱动学习</title>
    从高质量完成、低成本执行和成功恢复中识别值得复用的策略。



    <title size="md">3. 重复模式学习</title>
    在多次任务中发现相同问题、相同解决路径或稳定出现的依赖关系。



    <title size="md">4. 外部知识学习</title>
    从工具文档、技术规范、用户提供的资料和经过核验的外部信息中补充知识。


不同来源需要不同的验证方式。

一次成功的任务可以证明“这次执行成功了”，但不一定证明使用的策略是成功的原因。重复任务、对照实验和独立验证可以进一步提高可信度。

外部文档能够支持某个事实，但不代表文档中的所有建议都适合 EvoAgent 的实际环境。

## 3.1 引入经验价值筛选

建议只有满足一定价值条件的经历，才进入深入提炼流程。

可以考虑：

- 是否影响任务质量；
- 是否反复出现；
- 是否产生较大成本；
- 是否能迁移到其他任务；
- 是否能被清晰表达；
- 是否具有可验证的适用条件；
- 是否值得长期保存。

例如，一次无关紧要的临时网络超时，可能只需要保留运行日志；一种在多个项目中反复出现、且有明确修复方法的依赖解析问题，则更值得形成长期经验。

# 四、建立经验生命周期：从观察到晋升，再到退役

建议每条候选经验都拥有明确的生命周期，而不是一经写入就永久生效。

  {#each [
    ["OBSERVED · 已观察","记录原始事实、结果和证据引用。"],
    ["EXTRACTED · 已提炼","形成明确的经验描述、适用条件与失效条件。"],
    ["CANDIDATE · 待验证","准备将经验用于新任务，但仍视为候选知识。"],
    ["VALIDATED · 已验证","通过相应的测试、对照或证据核验。"],
    ["PROMOTED · 已晋升","进入对应的项目记忆、专家策略或正式能力目录。"],
    ["MONITORED · 持续监测","继续观察真实使用效果、适用范围和退化情况。"],
    ["DEPRECATED · 已弃用","因版本变化、证据不足或策略失效而停止默认使用。"]
  ] as item}


        {item[0]}


        {item[1]}


    {#if item[0]!=="DEPRECATED · 已弃用"}

    {/if}
  {/each}

这条生命周期允许分支，而不是只能顺序向前。

例如，某条经验可能在验证阶段被否定；某个已晋升的工作流也可能因为工具升级而退役；某条经验可能只在特定项目中有效，因此不需要进入通用专家知识。

还应当区分“停止使用”和“物理删除”。为了审计、回滚或解释历史决策，系统可能仍然需要保留已弃用知识的版本记录，但必须遵守敏感数据的保留与删除规则。

## 4.1 晋升不应该只有一个统一门槛

不同知识的晋升成本不同。

- 用户明确表达的稳定偏好，可以在确认适用范围后直接进入用户偏好记忆。
- 某次任务的失败事实，可以直接写入任务记录，但不能直接晋升为通用规则。
- 一条项目特有的修复经验，可以在项目内试用。
- 一个跨项目的专家策略，需要更广泛的验证。
- 共享内核规则、安全策略或核心执行机制，需要经过独立评测和受控发布。

**晋升门槛应由知识的影响范围、错误代价和可验证程度决定。**

# 五、让每条经验都能回答：什么时候适用，什么时候不适用？

长期记忆最危险的问题之一，是系统记住了结论，却忘记了结论成立的条件。

例如：

> 经验：使用 AST 重构代码比文本替换更可靠。

这句话有一定道理，但并不是所有代码修改都需要 AST。修改一个简单配置字符串时，使用 AST 可能反而增加成本。

更合理的经验应该包含：

- **适用场景：** 需要重命名符号、修改结构化语法或追踪代码引用的任务；
- **前置条件：** 对应语言存在可靠的解析器，目标代码能够被正确解析；
- **推荐策略：** 优先使用 AST 或符号分析；
- **例外条件：** 非语法文件、格式损坏的代码、简单文本数据；
- **失败信号：** 解析失败、符号解析不完整或修改后语法检查失败；
- **验证方式：** 语法检查、类型检查、测试及差异审查；
- **证据来源：** 相关任务运行记录和对照测试；
- **有效版本：** 适用的语言、解析器和工具版本。

这样，系统才能在未来根据实际条件判断是否应用经验，而不是盲目执行一条脱离上下文的规则。

## 5.1 建立统一的经验 Schema

建议定义 `ExperienceRecord`，至少包含：

| 字段 | 作用 |
|---|---|
| `experience_id` | 稳定的经验标识 |
| `knowledge_type` | 事实、偏好、任务经验、策略等 |
| `scope` | 任务、项目、专家或共享范围 |
| `claim` | 经验的核心结论 |
| `preconditions` | 生效前必须满足的条件 |
| `exceptions` | 已知不适用的情况 |
| `evidence_refs` | 支持结论的运行记录、测试和资料 |
| `counter_evidence_refs` | 反例或反证 |
| `confidence_status` | 当前证据状态，不只依赖主观置信度 |
| `validation_status` | 待验证、已验证、已否定等 |
| `version_constraints` | 适用的模型、工具或规则版本 |
| `created_at` / `updated_at` | 创建与更新时间 |
| `review_condition` | 需要重新核验的条件 |
| `supersedes` | 被替代的旧经验引用 |

这是建议的逻辑结构。正式实现时，可以根据不同知识类型扩展专属字段。

重要的是，经验不仅保存“结论”，还保存它的来源、适用范围、验证状态和失效条件。

# 六、知识冲突治理：新经验不能直接覆盖旧经验

随着 EvoAgent 长期运行，冲突是必然的。

例如：

- 旧经验认为使用模型 A 的代码质量更高；
- 新实验发现模型 B 在特定项目中更好；
- 用户偏好快速交付，但当前任务要求高可靠性；
- 两个专家分别提出不同的工作流；
- 一条经验基于旧版本工具，另一条基于新版本工具。

如果系统只采用最新记录，就可能丢失仍然有效的旧知识。

建议把冲突分成五类。

| 冲突类型 | 处理策略 |
|---|---|
| 事实冲突 | 查询权威来源，核对时间、版本和证据 |
| 适用范围冲突 | 缩小知识范围，分别保留不同条件下的规则 |
| 用户偏好冲突 | 根据用户当前明确要求、适用场景和偏好优先级处理 |
| 策略效果冲突 | 使用分层评测和对照实验比较实际效果 |
| 安全规则冲突 | 交由受保护的安全治理机制处理，普通经验不得覆盖 |

## 6.1 很多冲突不需要选出唯一赢家

例如，模型 A 在短代码生成任务中更便宜，而模型 B 在大型仓库分析任务中表现更好。

正确做法不是简单删除其中一个经验，而是把它们分别绑定到适用任务范围。

同样，AST 分析适用于结构化代码修改，文本替换适用于简单、可确定性验证的文本变更。两者可以共存。

**经验冲突的解决方式，往往是明确边界，而不是强制统一结论。**

## 6.2 安全规则不属于普通经验库

用户偏好、领域经验和工作流可以通过验证逐渐改进。

但权限边界、秘密信息保护、危险操作授权和关键状态一致性不能由普通经验学习过程自行修改。

例如，系统不能因为某次跳过授权后任务完成得更快，就把“跳过授权”沉淀成优化策略。

这类规则必须由 SBAAG 与受保护的系统治理机制管理。

# 七、从经验到能力：知识如何真正改变系统行为？

这是 CLEK 最核心的工程问题。

如果系统只是保存经验，却没有明确机制让未来任务使用这些经验，那么所谓学习只是在不断积累数据。

建议建立四条明确的转化路径。


    <title size="md">路径 A：经验 → 检索知识</title>
    把已核验的事实、项目经验和专业规则存入可检索知识库，由上下文系统在适用时引用。



    <title size="md">路径 B：经验 → 专家策略</title>
    将反复验证的决策规则转化为专家的结构化策略、检查清单或决策条件。



    <title size="md">路径 C：经验 → 工作流</title>
    将稳定重复的执行步骤转化为有输入输出契约、依赖、验收和恢复机制的 DAG 模板。



    <title size="md">路径 D：经验 → 工具或正式能力</title>
    当经验需要确定性执行、结构化分析或高频复用时，考虑实现专用工具、算法或能力包，并进行独立评测。


例如，代码专家多次发现“修改函数签名后遗漏调用方”这一问题。

最初可以将它记录为经验；之后把它转化为专家的重构检查清单；如果需要更可靠的自动执行，就可以实现基于 AST 和符号引用的检查工具；最终再把工具、检查步骤和验收规则组合成可复用的重构工作流。

这是一条从经历到正式能力的路径，而不是要求每次经验都走到最后一步。

## 7.1 什么时候应该实现工具，而不是继续优化提示词？

建议在以下条件满足时考虑工具化：

- 同类操作反复出现；
- 结果可以通过明确规则验证；
- 纯模型推理经常遗漏细节；
- 错误代价较高；
- 有成熟的算法或库可用；
- 工具的维护成本低于长期重复推理成本。

例如，语法树分析、哈希校验、媒体时长检查、文件格式验证和数据库完整性检查，都更适合由确定性工具承担。

专家负责决定什么时候调用工具、如何解释结果；工具负责完成可验证的具体操作。

# 八、记忆系统如何使用这些经验：检索不等于自动注入

CLEK 与记忆系统、上下文系统之间必须有明确边界。

- CLEK 负责判断知识是否值得沉淀、是否可信、应该属于哪里；
- MEEG 负责管理持久化记忆、知识版本与经验生命周期；
- CERG 负责根据当前任务检索、筛选、压缩和组织上下文；
- 专家负责在当前任务中应用知识；
- EQEAG 负责评测应用知识后是否真的改善了结果。

也就是说，经验进入长期存储，不代表它应该出现在每次模型调用的上下文中。

## 8.1 根据当前任务检索，而不是加载所有历史

假设用户要求编写一个简单的 Python 文件处理脚本。

上下文系统不应该加载所有代码专家经验，更不应该把漫剧制作、旅游规划和历史项目的全部记录塞进提示词。

合理的检索过程应该是：

1. 识别当前任务类型；
2. 确定相关知识空间；
3. 按任务条件检索候选经验；
4. 检查版本、适用条件和可信状态；
5. 排除冲突、过期或未验证的知识；
6. 按重要性与上下文预算排序；
7. 只注入当前任务真正需要的信息。

## 8.2 检索必须考虑知识的可信程度

建议至少区分：

- 已核验事实；
- 经过评测的正式策略；
- 适用范围明确的项目经验；
- 尚未充分验证的候选经验；
- 已过期或已被否定的知识。

普通任务默认优先使用可信、适用且版本兼容的知识。

候选经验可以用于受控实验，但不应该在没有标记的情况下伪装成正式规则。

## 8.3 知识必须能够退出上下文

即使一条经验已经晋升，也不应该永久占据上下文。

当当前任务不再适用、版本不兼容、用户约束发生变化或经验被撤销时，CERG 应停止注入相关知识。

这要求记忆系统与上下文系统共享稳定的知识 ID 和版本引用，而不是只传递一段无法追踪来源的文本。

# 九、用户习惯与通用知识必须分开演化

你之前特别关注过通用智能体如何学习用户习惯，同时又不影响代码、旅游等不同专家的独立性。

CLEK 在这里需要明确一个原则：

**用户偏好可以跨任务复用，但必须保留作用范围；用户偏好不是专业事实，更不能覆盖任务的硬约束。**

例如：

- 用户偏好先讨论方案，再开始执行；
- 用户偏好回答简洁，但技术设计需要完整说明；
- 用户倾向先使用本地资源，必要时才调用云服务；
- 用户希望复杂任务提供阶段性进度。

这些偏好可能影响通用交互层、任务规划和不同专家的工作方式。

但不能简单地把它们复制到每个专家的长期知识中，导致后续无法统一更新。

建议建立分层偏好模型：

| 层级 | 示例 | 应用规则 |
|---|---|---|
| 全局偏好 | 默认使用中文沟通 | 除非当前任务或用户要求另有规定 |
| 工作方式偏好 | 重大执行前先确认计划 | 在适用任务中生效 |
| 领域偏好 | 代码修改优先保留现有架构 | 只作用于相关领域 |
| 项目偏好 | 当前项目使用指定框架 | 只在该项目中生效 |
| 当前任务指令 | 本次任务直接执行，不必先讨论方案 | 对本次任务的具体行为起作用，但仍受安全规则约束 |

当前任务的明确指令可能覆盖一般偏好，但不能覆盖安全、权限和其他不可违反的系统约束。

此外，系统应支持用户查看、更正和撤销可编辑的偏好记录。对于错误推断的习惯，应该允许直接纠正，而不是让系统无限次重复学习同一个错误。

# 十、知识过期与失效检测：长期记忆不能成为历史包袱

有些知识具有长期价值，有些知识只在特定版本或时间段内有效。

例如：

- 某个工具的参数格式会随着版本升级而改变；
- 某个云端服务的 API 可能被废弃；
- 项目结构会发生变化；
- 用户的工作偏好可能更新；
- 某个优化策略在新模型上不再有效。

因此，CLEK 需要建立知识有效性治理。

## 10.1 过期不一定意味着知识本身错误

如果旧版工具使用某个参数，而新版工具改用了另一种参数，这不意味着旧经验在当时就是错误的。

它可能只是失去了当前适用性。

建议将知识失效原因区分为：

- 事实被新证据否定；
- 依赖版本发生变化；
- 适用环境发生变化；
- 实验发现收益不再成立；
- 用户明确修正了偏好；
- 原始证据无法继续验证；
- 经验长期未使用，需要重新核验。

这些情况应采用不同处理方式。

## 10.2 不要仅凭时间自动删除所有旧知识

某些知识变化很快，例如服务 API；某些知识相对稳定，例如算法原理；某些知识需要等到特定条件触发才值得重新核验。

因此，建议采用基于有效条件的复核：

- 工具或模型版本发生变化时，重新检查相关知识；
- 某项策略的效果持续退化时，触发复评；
- 新证据与现有知识冲突时，启动冲突治理；
- 某个知识长期未使用且维护成本较高时，考虑降级或归档；
- 用户明确修改偏好时，更新对应的权威记录。

对已经失效的知识，应停止默认使用并保留必要的历史关联；对于包含敏感数据且用户要求删除的内容，则需要遵守相应的数据删除流程，而不是以“保留历史”为由无限保留。

# 十一、让知识学习本身也可以被评测

CLEK 不能只评估“记忆里新增了多少条知识”，而应该评估这些知识是否让未来任务变得更好。

建议建立四组指标。

| 指标类别 | 典型指标 |
|---|---|
| 知识质量 | 事实准确率、证据完整度、过期率、冲突率 |
| 检索质量 | 相关知识命中率、无关知识注入率、关键经验遗漏率 |
| 应用效果 | 使用经验后的成功率、返工率、工具调用次数和任务成本 |
| 治理质量 | 错误经验晋升率、失效知识使用率、回滚成功率、错误知识影响范围 |

其中，最值得关注的指标之一是**错误经验的影响范围**。

一条错误的项目经验只影响一个项目，和一条错误的通用规则污染所有专家，后果完全不同。

因此，知识晋升时必须同时考虑可信程度与传播范围。

## 11.1 使用对照实验评估经验的价值

假设某条新的代码重构经验已经通过验证。

可以在适当的测试任务上比较：

- A 组：使用稳定版本的代码专家策略；
- B 组：使用新策略，并允许检索该条经验；
- 其他模型、工具、验收标准与预算尽可能保持一致。

比较结果时，不仅看任务成功率，也看返工、耗时、成本和其他任务类别是否受到影响。

如果加入这条经验后没有改善，可能是经验不够准确、检索时机不对、上下文组织方式不合适，或者该经验本来就没有额外价值。

这时不应该为了让知识晋升成功而放宽评测标准。

## 11.2 区分知识质量和检索质量

即使一条经验本身完全正确，如果上下文系统在错误的任务中频繁注入它，也可能降低整体表现。

因此：

- 经验内容错误，属于知识质量问题；
- 经验正确但检索不到，属于检索问题；
- 经验正确但检索范围过宽，属于适用范围治理问题；
- 经验正确且被正确检索，但执行效果不佳，可能属于策略应用或执行能力问题。

这种分层能够避免系统把所有问题都归咎于记忆系统。

# 十三、下一专项：自适应上下文与记忆协同优化

CLEK 解决了经验如何产生、验证和沉淀，但还有一个关键问题：

**当 EvoAgent 已经积累大量知识后，如何在每一次任务中，恰好提供需要的知识，而不是越记越多、越用越乱？**

这直接连接你之前反复关注的记忆系统、上下文压缩、上下文设计和多专家隔离。

建议下一专项定义为：

**Adaptive Context & Memory Orchestration，简称 ACMO。**

重点研究：

1. 如何根据任务类型动态构建上下文，而不是使用固定提示词模板；
2. 如何在用户偏好、项目知识、专家知识、任务历史和工具结果之间分配上下文预算；
3. 如何区分必须保留的硬约束与可以压缩的普通信息；
4. 如何判断一条记忆是否真正有助于当前任务；
5. 如何识别上下文中的冲突、过期信息和重复信息；
6. 如何根据任务阶段动态调整上下文，而不是一次构建后始终不变；
7. 如何让多个专家共享必要事实，同时保护各自的领域记忆；
8. 如何在压缩时保留来源、版本、不确定性和关键依赖；
9. 如何判断模型是否因为上下文遗漏而失败；
10. 如何根据历史任务结果改进检索、排序、压缩和信息保留策略；
11. 如何测量上下文质量，而不仅仅是 Token 数量；
12. 如何避免上下文优化与专家能力优化互相干扰，导致无法判断改进究竟来自哪里。

这一专项的核心不是追求更长的上下文，也不是追求更激进的压缩，而是：

**让每一次模型调用都获得完成当前任务所需的最小充分信息，并且不丢失任何不可忽略的约束。**

完成 ACMO 后，我们就能把知识沉淀、上下文构建、专家执行和自进化评测连接成一个更加完整的系统闭环。

下一轮将从第一性原理开始，设计 EvoAgent 的动态上下文构建、分层记忆检索、压缩保真与质量评测机制。
