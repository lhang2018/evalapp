# 一、我认为最值得继续探讨的 12 个问题






      **01. 多专家之间，究竟如何划分能力边界？**

      最高优先级

      我们已经确定旅游、编程、漫剧等专家独立进化，但还没定义：什么属于专家私有能力，什么属于共享能力，什么应该由多个专家共同完成？

      例如，代码调试能力属于编程专家，但工具故障诊断是否应该是共享能力？如果两个专家各自发展出不同的恢复策略，谁来判断哪一个更好？








      **02. 路由错误以后，系统如何纠正自己？**

      意图路由不是一次判断就永远正确。如果用户说“帮我开发一个旅游 App”，系统可能只选择编程专家，也可能需要编程、旅游业务和手机部署能力。

      我们还需要设计路由置信度、任务中途重新路由、专家切换、任务交接和失败恢复机制。更重要的是，如何区分路由错了和专家本身能力不足？








      **03. 不同专家的能力如何共享和迁移？**

      我们已经说过，局部经验需要验证后才能成为通用能力，但还没有设计迁移协议。

      一个专家总结出的经验，怎样证明能迁移到另一个专家？是共享提示词、共享工具、共享工作流，还是提炼成独立算法？如何避免把某个领域有效的技巧错误推广到全局？








      **04. 如何知道问题的真正根因？**

      我们已经区分了单次错误、场景问题、子能力缺陷和通用机制缺陷，但仍缺少完整的因果诊断方法。

      如果模型、提示词、记忆、工具和上下文同时存在问题，如何设计实验找出主要原因？当证据不足时，系统是否允许暂时不修复，而不是强行给出一个根因？








      **05. 如何证明智能体真的进化了？**

      测试集可能被反复使用，智能体可能逐渐记住测试答案，甚至出现评测规则被候选版本间接影响的问题。

      我们需要明确训练与评测数据隔离、隐藏测试集、跨任务泛化、长期回归和独立验收机制，否则系统可能只是越来越会应付自己的测试。









        **06. 记忆和知识到底归谁所有？**

        用户偏好、个人事实、项目知识、专家经验、工具知识和系统经验之间的边界还没有完全明确。

        哪些可以跨专家共享？哪些只能留在设备上？用户要求删除某条记忆后，备份、向量索引、派生摘要和已生成的经验应该如何处理？










        **07. 智能体拥有多大的实际行动权？**

        在手机上，它可能打开 App、读取界面、修改文件、发送消息或提交订单。

        哪些操作可以自动执行，哪些需要确认？如何处理不可逆动作、误操作、重复执行和用户中途撤销？权限边界如何避免被提示词或工作流绕过？










        **08. 长任务怎样保证状态正确？**

        AI 漫剧制作、复杂编程和手机自动化都可能运行很久，中间遇到断网、进程被杀、工具超时或用户改变需求。

        如何保存检查点、恢复现场、避免重复副作用，并在用户修改目标后判断哪些已完成步骤仍然有效？










        **09. 工作流如何升级而不破坏历史任务？**

        我们讨论了将成功任务固化为 DAG，但还没解决工作流升级、依赖变化、旧任务恢复和历史版本兼容。

        如果某个工具接口变了，过去发布的工作流还能运行吗？一个流程中的部分节点升级后，如何确认整个流程仍然有效？










        **10. 多个任务同时运行时，如何分配资源？**

        之前主要讨论单个任务的成本。现实中可能同时存在多个任务、多个专家和大量后台评测。

        哪些任务优先？怎样防止一个复杂任务耗尽预算？任务执行与进化实验竞争资源时，谁优先？










        **11. Android 的真实运行限制如何处理？**

        后台运行、无障碍服务、系统权限、厂商省电策略、断网、低显存云端模型选择、应用更新，都可能影响可靠性。

        哪些功能必须在线，哪些能离线运行？服务端不可用时，手机端如何降级，而不是让整个智能体失效？










        **12. 系统怎样长期维护和演进？**

        模型可能下线，API 可能涨价，工具可能停止服务，新的模型也可能改变原有策略的效果。

        如何管理依赖、模型适配、版本生命周期、故障降级、成本变化和安全更新？如何避免能力资产只对某个模型或某个工具版本有效？




以上 12 个方面都值得深入讨论，但优先级并不完全相同。我的判断是，前五项决定 EvoAgent 能不能正确进化；第六至第九项决定它能不能安全、可靠地长期执行任务；第十至第十二项决定它能不能在真实设备和长期运行环境中持续工作。

# 二、还有四个容易被忽略、但会决定产品上限的问题

除了上面 12 个技术与架构问题，我认为还有四个更深层的设计盲区。

## 13. 智能体如何知道自己“不擅长什么”？

我们已经讨论了发现失败，但这还不够。

一个成熟的 EvoAgent 不应该非要等任务失败之后才发现能力不足。它应该逐步建立一份动态的**能力画像**：

- 哪类任务成功率高。
- 哪些环境或条件下容易失败。
- 哪些任务虽然能完成，但成本特别高。
- 哪些能力只是偶尔成功，还没有足够证据证明稳定。
- 哪些能力依赖特定模型、工具或版本。

这份画像不能只由大模型自评生成，而应由历史执行证据、评测结果和环境信息共同维护。

例如，系统可能已经很擅长普通代码生成，但在复杂并发错误的定位上仍然不稳定。它就应该在这类任务上提高验证强度，而不是笼统地给自己贴上“编程能力很强”的标签。

## 14. 多个专家意见冲突时，谁说了算？

假设旅游专家认为应该调整行程，预算规划能力认为这样会超出预算，用户又要求不改变住宿。

这不是简单选择一个最擅长的专家就能解决的。

我们需要一个统一的**约束协调与决策机制**，区分：

- 用户明确规定的硬约束。
- 用户表达的软偏好。
- 专家提出的建议。
- 工具返回的客观事实。
- 系统自身的资源和安全限制。

专家可以提出不同方案，但不能各自覆盖其他专家的结论，更不能覆盖用户的硬性约束。协调器应判断方案是否可行、哪些条件冲突，以及何时需要向用户澄清。

## 15. 用户的需求改变时，智能体如何管理变化？

长任务不是一开始规划完就永远不变。

例如，用户已经完成漫剧的角色设计和分镜，突然要求把视频时长从 60 秒改成 30 秒。

智能体需要判断哪些资产可以继续复用，哪些任务需要重新执行，哪些工作流节点可以跳过，哪些结果已经过期。

这需要建立**任务变更管理机制**，记录目标版本、约束变更、受影响节点和需要重新验收的结果，而不是每次都从头开始，也不能盲目继续旧计划。

## 16. 用户如何理解和控制自己的智能体？

EvoAgent 越自主，用户就越需要知道它在做什么、花了多少钱、使用了哪些权限，以及为什么选择某个方案。

因此，产品层还应设计：

- 当前任务状态与进度。
- 关键决策及其理由。
- 成本预算与实际消耗。
- 正在使用的专家、模型和工作流版本。
- 需要用户确认的动作。
- 任务暂停、取消、恢复和撤销。
- 进化更新说明及版本回滚入口。

这些不只是界面功能，也是建立用户信任、控制风险和让长期自主运行真正可用的必要条件。

# 三、我建议再增加一个总机制：EvoAgent 的“设计决策与风险登记册”

我们已经有总体架构方向，但后续很容易出现一个问题：随着新想法不断加入，之前讨论过的原则可能被遗忘，不同模块也可能作出互相矛盾的决定。

因此，我建议除了代码仓库和技术文档，还要维护一份机器可读、可追踪的设计决策登记册。

每个重要决策至少记录：

| 字段 | 内容 |
|---|---|
| 决策编号 | 例如 `ADR-001` |
| 设计问题 | 当前要解决什么问题 |
| 可选方案 | 考虑过哪些替代方案 |
| 选择结果 | 最终采用什么方案 |
| 选择理由 | 为什么这样选择 |
| 影响范围 | 哪些模块、专家、数据和版本会受到影响 |
| 风险与限制 | 可能出现什么问题 |
| 验收方式 | 怎样证明设计有效 |
| 状态 | 待讨论、已采纳、实验中、已验证、已废弃 |

这样，未来如果要更换模型、增加新的专家，或者调整记忆系统，我们就可以追踪这项变化会影响哪些既有决策，而不是重新从零讨论整个项目。

# 四、哪些问题应该先讨论？

我不建议 16 个问题同时展开。它们之间有明显的依赖关系，应该按架构风险和先后顺序推进。



      <title size="lg">01</title>


      **能力边界、所有权与依赖图**

      先明确什么属于通用内核、什么属于领域专家、什么属于任务工作流，以及共享能力如何晋级。否则后面的路由、进化和回归测试都没有稳定基础。





      <title size="lg">02</title>


      **统一任务协议与状态管理**

      明确所有专家如何接收任务、调用工具、共享必要结果、交接工作、处理中断和恢复。它决定多专家协作是否真正可运行。





      <title size="lg">03</title>


      **诊断、评测与进化有效性**

      明确如何证明问题属于哪个层级，如何判断改进有效，以及如何保护其他能力不退化。这决定 EvoAgent 能否真正进化，而不是反复修改自己。





      <title size="lg">04</title>


      **记忆、隐私和能力迁移**

      明确记忆的所有权、共享范围、更新与删除规则，以及经验如何从专家私有能力晋级为共享能力。





      <title size="lg">05</title>


      **安全、成本与长期运行**

      明确权限、预算、并发调度、断网恢复、版本兼容、故障降级和发布回滚机制。



## 五、我的判断：目前最大的风险不是缺少功能，而是模块之间的关系还没有定型

我们已经考虑了很多重要能力，但接下来真正需要解决的是：

- 一个问题如何在多个模块之间传播？
- 一个模块的改进如何影响其他专家？
- 一条记忆如何变成技能，再变成工作流或共享能力？
- 一个任务如何从动态执行转化为稳定流程？
- 一项局部改进如何证明不会损害通用能力？
- 一次模型升级如何保留既有资产，同时避免错误迁移？
- 一个长期任务如何在需求变化、工具故障和预算限制下继续可靠完成？

这些问题的答案决定了整个系统能否形成真正的闭环。

**我建议下一轮优先深入第一个问题：EvoAgent 的能力所有权、能力依赖图与共享机制。**

因为这会决定通用内核、领域专家、技能、记忆、工具和工作流究竟如何组织，也是后面实现路由、独立进化和回归保护的基础。

我们应该先把这张关系图和规则设计清楚，再逐步深入其他层面，而不是继续单独增加模块。
