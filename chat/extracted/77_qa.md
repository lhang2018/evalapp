# EvoAgent 第二十二专项：记忆进化与经验治理

这一轮我们要解决 EvoAgent 自进化体系中的一个根本问题：

**智能体在运行过程中不断积累经验，但哪些经验应该记住、记在哪里、何时生效、何时升级，以及什么时候应该遗忘或撤销？**

这件事看似属于记忆系统，实际上决定了整个系统能否长期进化。

如果 EvoAgent 每次成功都增加一条规则，它会越来越臃肿；如果每次失败都修改提示词，它会越来越不稳定；如果某个专家学到的经验直接进入全局记忆，还可能破坏其他专家原本可靠的行为。

所以，我们不能把“记忆越来越多”当作“智能越来越强”。

本专项建议定义为：

**Memory Evolution & Experience Governance Engine，简称 MEEG。**

它与前面设计的记忆系统、上下文引擎、RCAE 根因分析引擎和进化治理系统协同，负责经验的分类、提取、验证、存储、检索、晋升、降级、冲突处理和撤销。

## 一、第一性原理：记忆不是事实仓库，经验也不是规则

首先必须区分六种不同的信息。

  {#each [
    ["事实 Fact","已经确认的客观信息，例如某个文件当前的内容、某次测试的实际结果。"],
    ["状态 State","某个任务或流程当前进行到哪里，例如哪些节点已完成、哪些操作仍未确认。"],
    ["偏好 Preference","用户明确表达或在获得适当依据后推断出的长期偏好，例如偏好的输出格式。"],
    ["经验 Experience","从一次或多次执行中观察到的有效做法、失败模式或环境规律。"],
    ["假设 Hypothesis","尚未被充分验证的解释，例如某种上下文组织方式可能提高代码修改成功率。"],
    ["规则 Policy","经过明确治理后，对特定范围内的行为形成的稳定约束或执行策略。"]
  ] as item}

      <title size="md">{item[0]}</title>
      {item[1]}

    {#if item[0]!=="规则 Policy"}

这六类信息不能混为一谈。

例如，一次任务中模型先分析 AST 再修改代码，最终测试通过。

这能证明该次任务采用了这种顺序，并且得到了成功结果；但它还不能证明“所有代码修改都必须先分析 AST”。

正确的做法是把它记录为一条带有适用条件的候选经验，再通过其他案例验证。

同样，一次失败也不能直接形成“这个模型不适合编程”的规则。

**经验可以来自单次观察，但稳定规则必须经过与其影响范围相匹配的验证。**

# 二、建立经验生命周期：从观察到稳定能力

我建议每条经验都拥有明确的生命周期，而不是直接写入长期记忆。

  {#each [
    ["OBSERVED","观察到一个结果或行为，保留原始证据。"],
    ["CANDIDATE","提取候选经验，明确适用范围、支持证据与反例。"],
    ["UNDER_TEST","在受控环境中验证，比较现有策略与候选策略。"],
    ["VALIDATED","获得足够证据支持，但仍只在明确范围内成立。"],

    ["DEPRECATED","适用条件变化或证据过时，不再作为默认策略。"],

这里的 `VALIDATED` 与 `PROMOTED` 必须区分。

一条经验可能已经通过某类编程任务的评测，但只适合存入编程专家的特定任务策略，不应该进入全局共享规则。

例如：

- “对于某类 Python 重构，先分析符号引用有助于减少遗漏”可以进入编程专家的策略库；
- “所有专家都必须先执行符号引用分析”则没有充分依据；
- “当前项目使用 Python 3.12”属于项目环境事实，不需要通过经验晋升流程才能记录；
- “用户希望代码修改前先给出计划”属于用户偏好或明确指令，应该进入对应的用户偏好或任务约束机制，而不是当成模型从成功案例中学出的规律。

经验治理需要判断的不只是“这条信息是否有用”，还包括“它应该以什么形式生效，以及对谁生效”。

# 三、经验应该存在哪里？建立分层记忆与策略资产体系

这是 MEEG 最重要的设计决策之一。

我建议不要把所有信息都存入一个统一的向量数据库，然后依靠语义相似度决定是否使用。

因为“内容相似”不等于“应该共享”，“检索相关”也不等于“当前适用”。

EvoAgent 应该采用**分层记忆、独立命名空间、统一检索接口、分级治理**的架构。

## 3.1 七类记忆与策略资产

  {#each [
    ["M1 · 工作记忆","当前对话、当前决策所需信息、短期中间结果。任务结束后按需清理。"],
    ["M2 · 任务记忆","任务目标、节点状态、执行轨迹、产物、失败与恢复记录。用于恢复和追溯。"],
    ["M3 · 用户记忆","用户明确的长期偏好、已确认的工作习惯和个性化要求。"],
    ["M4 · 项目记忆","特定项目的架构、文件关系、环境、技术约束和历史决策。"],
    ["M5 · 专家记忆","某个领域内经过筛选的知识、失败模式、有效方法和适用条件。"],
    ["M6 · 全局共享记忆","经过严格验证、确实跨领域适用的基础经验和通用约束。"],
    ["M7 · 策略资产库","正式管理的提示词、上下文策略、工作流、模型适配、工具契约与验证规则。"]

需要强调，M7 与记忆并不完全相同。

记忆主要回答“系统知道什么、经历过什么、哪些经验可能有用”；策略资产则定义“系统应该如何执行”。

例如：

- “上次 AST 修改遗漏了装饰器”是任务经验；
- “在特定 Python 重构任务中必须检查装饰器兼容性”可以成为领域策略；
- 实现这一检查的代码属于工具；
- 规定何时执行检查、失败后如何处理的流程属于工作流；
- 验证检查是否有效的测试集属于评测资产。

它们可以相互引用，但不应该混成同一种对象。

## 3.2 共享不等于复制到全局

我建议采用“独立存储、分层检索、显式引用”的方式。

例如，编程专家形成了一条经过验证的经验，旅游专家不需要看到它的全部内容。只有当某项经验被证明适用于共享基础设施时，才将其提升到全局共享范围。

某些通用原则可以跨领域复用，例如：

- 工具执行结果必须核验；
- 未确认的外部操作不能直接重复执行；
- 任务预算不能被局部循环绕过；
- 用户明确提出的硬性约束不能被历史偏好覆盖。

这些更适合成为共享的系统策略或治理规则，而不是依靠语义检索偶然找到的一段记忆。

**全局共享应当是一种经过审批的适用范围，而不是所有专家默认都能读取的公共记忆池。**

# 四、经验晋升：什么情况下才有资格成为长期能力？

不能规定“成功一次就记住”，也不能简单规定“成功十次就升级”。

因为十次相似的重复执行，可能都来自同一个项目、同一个环境和同一个错误假设。

经验晋升必须同时考虑证据质量、适用范围、风险和实际收益。

## 4.1 建立五个晋升门槛

| 门槛 | 必须回答的问题 |
|---|---|
| 证据可信 | 结果是否真实发生，是否有可追溯的执行证据？ |
| 原因可解释 | 为什么这条经验有效？是否存在其他可能解释？ |
| 范围明确 | 它适用于哪些任务、专家、模型、工具和环境？ |
| 效果可复现 | 在代表性案例与反例中，是否能重复获得预期效果？ |
| 风险可控 | 是否会损害其他任务、增加不合理成本或违反用户约束？ |

不是每种记忆都必须通过全部五项门槛。

用户明确表达的偏好，不需要通过实验来证明其真实性；但它是否适用于当前任务，仍需要根据用户当前指令和作用范围判断。

一次任务的真实执行事实，可以直接进入任务记忆；但要把这次执行总结成通用规则，就需要更严格的验证。

## 4.2 根据经验类型采用不同的晋升路径


    **事实与状态**

    通过来源、版本、完整性和状态核验确认后即可保存，不需要证明其普遍性。

    例如：某次测试在指定环境中失败，记录测试命令、版本和实际输出。



    **用户偏好**

    以用户明确表达为优先；推断出的偏好应保留较低确定性，并允许用户修正。

    例如：用户明确要求代码修改前先说明计划。



    **局部经验**

    在相同项目、任务或环境中复现后，可以作为局部提示或恢复建议。

    例如：当前项目的某个生成工具需要特定参数。



    **领域策略**

    需要在该领域的代表性任务和边界案例中验证，并检查相关指标是否退化。

    例如：特定代码重构类型在修改前执行符号引用分析。



    **全局规则**

    需要更广泛的跨领域证据、明确的规则来源和更严格的治理门禁。

    例如：不能仅凭模型的成功回复，就把外部操作标记为已验证完成。


## 4.3 晋升范围必须逐级扩大

建议允许以下路径：

任务经验 → 项目经验 → 领域候选经验 → 领域稳定策略 → 全局候选规则 → 全局正式规则。

但这不是一条必须走完的升级阶梯。

绝大多数经验永远停留在项目或领域层就足够了。只有真正具备跨领域价值的原则，才有必要进入全局共享范围。

而且，某条经验在领域内验证通过，并不意味着它已经获得进入全局层的资格。

# 五、经验如何检索？不能只看语义相似度

假设编程专家检索到一条历史经验：

“遇到测试失败时，先重装依赖。”

这条经验可能来自一个特殊项目。当时失败确实是依赖损坏导致的。

但如果当前失败是业务逻辑错误，照搬这条经验不仅无效，还可能破坏环境。

因此，记忆检索不能只问“这段内容和当前问题像不像”，还必须问“这条经验在当前条件下是否适用”。

## 5.1 建立五阶段检索流程

  {#each [
    ["01","权限与命名空间过滤","只检索当前任务、专家和用户有权使用的记忆。"],
    ["02","语义与关键词召回","寻找与当前目标、错误类型、工具和环境相关的候选经验。"],
    ["03","适用性过滤","检查领域、任务类型、模型版本、工具版本、前置条件与有效期限。"],
    ["04","可信度与价值排序","考虑证据质量、验证状态、历史效果、成本和反例。"],
    ["05","冲突检查与上下文装配","检查是否与当前指令、硬性约束或其他有效策略冲突，再决定如何使用。"]
  ] as item}


        {item[0]}


        **{item[1]}**
        {item[2]}


    {#if item[0]!=="05"}

    {/if}
  {/each}

注意：即使一条经验在语义检索中排名第一，也可能因为不满足前置条件而被排除。

例如，某个修复策略只适用于旧版本工具，而当前工具版本已经升级，那么它可以作为历史参考，但不应自动作为默认执行方案。

## 5.2 记忆应该提供来源，而不是只提供结论

每条被使用的经验都应该尽可能保留：

- 来源任务或证据引用；
- 验证状态；
- 适用范围；
- 适用前提；
- 失败反例；
- 创建与最近验证时间；
- 对应策略或工具版本；
- 是否存在替代经验。

这样，专家就可以根据经验的可信程度和当前任务的匹配程度决定如何使用它。

对于低可信度的经验，系统可以将其作为一个待验证假设，而不是直接当作执行规则。

## 5.3 经验不能覆盖当前用户指令

例如，长期用户记忆表明用户通常偏好低成本方案，但用户这次明确要求最高质量。

当前任务就应该遵守本次明确要求，而不是让历史偏好自动降低质量等级。

同样，领域经验不能覆盖系统级安全约束，旧的项目记忆也不能覆盖已经确认的新项目状态。

建议采用明确的权威顺序：

1. 系统安全与平台约束；
2. 当前任务中有效的明确指令和授权；
3. 已验证的权威任务状态与项目事实；
4. 当前有效的正式策略；
5. 经过验证且适用的领域经验；
6. 未验证的候选经验和历史假设。

这不是说所有信息都能简单排序。发生冲突时，还需要检查信息的作用范围和有效版本。但至少不能让“检索到了某条经验”成为覆盖当前约束的理由。

# 六、经验过期与遗忘：旧经验何时应该失效？

经验不会永远有效。

模型可能升级，工具可能改变，项目环境可能更新，用户偏好也可能变化。

因此，MEEG 不应该只负责记住，还必须负责识别失效和控制撤销。

## 6.1 不同类型的记忆采用不同的失效机制

| 信息类型 | 建议失效机制 |
|---|---|
| 临时工作记忆 | 任务阶段结束或上下文不再需要时清理 |
| 任务状态 | 以任务状态机和保留策略为准，不能因时间过去就随意删除未决状态 |
| 项目事实 | 文件、依赖、配置或项目版本发生变化时重新核验 |
| 用户偏好 | 用户明确修改时更新；长期未使用不应自动视为错误 |
| 工具经验 | 工具版本、API 或运行环境发生实质变化时重新验证 |
| 模型适配策略 | 模型版本、提示词、上下文策略变化时重新评估 |
| 领域经验 | 出现反例、效果退化或适用条件变化时降级或重新测试 |
| 全局规则 | 规则来源或安全要求变化时进入正式变更流程 |

这里需要区分两种情况：

- **过期：** 过去可能正确，但现在不再适用；
- **错误：** 经过进一步证据发现，过去的结论本身就不成立。

前者可以标记为 `DEPRECATED`，后者则可能需要 `REVOKED`。

## 6.2 撤销经验必须追踪依赖

假设一条错误经验已经被用于：

- 编程专家提示词；
- 某个工作流模板；
- 一条模型适配策略；
- 多条其他经验的推导；
- 记忆检索缓存。

这时仅仅删除原始经验是不够的。

系统必须维护经验到策略、工作流和其他经验之间的引用关系。

一旦原始经验被撤销，就需要识别哪些下游资产依赖它，并决定：

- 立即停止使用；
- 重新评测；
- 恢复到旧版本；
- 重新生成候选策略；
- 或者仅移除其中一条不成立的推导。

这与前面设计的产物依赖图类似，但管理对象从任务产物变成了知识与策略依赖。

## 6.3 不要因为使用频率低就删除重要规则

高频使用不等于高价值，低频使用也不等于无价值。

例如，某项安全规则可能很少触发，但一旦触发就能防止严重错误。

因此，记忆清理应考虑：

- 当前有效性；
- 证据质量；
- 是否仍被其他资产引用；
- 重新获取成本；
- 失效风险；
- 隐私与保留要求；
- 是否属于不可随意删除的审计记录。

对于可以重新检索的普通知识，可以使用较短保留策略；对于任务状态、重要决策和关键诊断证据，则需要根据审计与恢复需求保留。

# 七、经验冲突：当两条经验都曾经有效，应该怎么办？

这在长期进化系统中一定会发生。

例如：

- 经验 A：代码修改前先进行完整分析，可以减少遗漏。
- 经验 B：简单代码修改应直接执行，避免额外分析成本。

这两条经验并不一定互相矛盾，它们可能适用于不同复杂度的任务。

如果系统只是根据时间戳保留最新经验，或者根据出现次数最多的经验做决定，就可能破坏原本有效的行为。

  {/each}

## 7.2 用条件化经验替代简单的全局规则

例如，最终可以形成：

- 对简单、低风险、局部代码修改，优先采用轻量分析；
- 对跨文件重构、复杂依赖和高风险变更，先执行结构分析；
- 当模型或工具的能力不足以满足最低验收标准时，自动升级到更强的分析路径。

这比“总是完整分析”或者“永远直接修改”更符合实际任务需求。

## 7.3 规则冲突必须有明确的处理权

建议将冲突解决分为三个层级：

- 普通经验冲突：由检索与适用性规则解决；
- 专家策略冲突：由对应专家的策略治理流程处理；
- 全局规则或安全约束冲突：由更高层的治理机制处理，不能通过模型投票或自动统计覆盖。

如果证据不足，系统应保留冲突状态，而不是悄悄选中其中一条经验。

# 八、记忆进化必须区分“学到了什么”与“改变了什么”

这是我认为最重要的设计边界之一。

记忆系统负责保存知识和经验；真正改变智能体行为的，可以是提示词、上下文策略、工作流、工具、模型适配或路由规则。

如果把所有经验都塞入记忆，再期待模型每次推理时自行选择是否遵守，就很难保证行为稳定性。

## 8.1 建立经验到执行策略的转换机制

例如，RCAE 发现某类代码修改经常遗漏调用方。

经过实验，确认在特定跨文件重构任务中，先进行符号引用分析能稳定降低遗漏率。

这时，MEEG 不应该只把结论写入一条长期记忆。

更合理的转换是：

1. 保留原始失败案例与实验结果；
2. 将经过验证的结论登记为编程领域经验；
3. 生成候选策略，规定适用任务和前置条件；
4. 将策略集成到编程专家的工作流或节点契约；
5. 运行相关回归测试；
6. 通过发布门禁后启用；
7. 持续监测效果并保留回滚版本。

这样，经验不仅被记住，而且以明确、可验证、可回滚的方式改变了系统行为。

## 8.2 不同类型的经验应该进入不同执行资产

| 经验结论 | 优先转化方向 |
|---|---|
| 某个稳定执行顺序有效 | 工作流模板 |
| 某类输入经常被误解 | 提示词或任务输入契约 |
| 某些信息经常在压缩中丢失 | 上下文保留策略 |
| 某类错误需要特殊诊断步骤 | 故障诊断策略 |
| 某工具经常返回不完整结果 | 工具契约与验证器 |
| 某模型在特定任务中表现较差 | 模型路由或适配策略 |
| 某知识只对当前项目有效 | 项目记忆 |
| 某项事实会频繁变化 | 权威状态查询，而不是长期记忆 |
| 某种经验尚未验证 | 候选经验库，不直接改变生产行为 |

这能减少提示词膨胀、记忆污染和策略冲突。

# 十二、下一专项：安全、权限与自主进化边界

到这里，我们已经讨论了自我诊断、根因归因、改进实验和经验晋升。

但这套系统越能自主诊断、修改策略和沉淀经验，就越需要明确一条边界：

**EvoAgent 可以自主改进自己的能力，但不能因为它认为某项改进有益，就自动扩大自己的权限、突破用户约束或绕过发布门禁。**

下一专项建议设计：

**Autonomy, Security & Evolution Governance Engine（自主性、安全与进化治理引擎，简称 ASEGE）。**

重点研究：

1. 如何划分只读、可逆修改、外部副作用和不可逆操作的风险等级；
2. 哪些行为可以完全自动执行，哪些必须经过用户确认；
3. 如何隔离用户记忆、项目数据、工具凭据和不同专家的权限；
4. 如何防止网页、文件、工具输出和记忆中的恶意指令影响控制系统；
5. 如何限制自我修改范围，防止候选改进绕过自身的安全检查；
6. 如何对提示词、工作流、工具和模型路由设置不同的发布门槛；
7. 如何在离线环境中维持权限检查、日志和安全恢复能力；
8. 如何实现可撤销授权、操作审计和失败后的安全收尾；
9. 如何评估自主程度提升是否真的带来了收益，而非仅增加风险；
10. 如何让安全机制自身也能被评测和改进，但不能被普通进化流程自行解除。

这一步不是给 EvoAgent 增加一个简单的安全模块，而是要明确整个系统的自主边界：哪些能力可以自我优化，哪些规则只能在受控流程中修改，以及在证据不足、权限不明或状态未知时，系统应该如何安全地停止。

完成这项设计后，EvoAgent 的持续进化就不仅有能力提升闭环，也有与之匹配的权限和风险控制闭环。
