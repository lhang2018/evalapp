# EvoAgent 深度设计第三轮：局部经验如何进化成通用能力？

这一轮我们要解决 EvoAgent 最核心、也最容易设计错的问题之一：

**当一个领域专家发现了一种有效方法，系统如何判断它只是这个领域的技巧，还是可以推广到其他领域的通用能力？**

这决定了 EvoAgent 最终会走向两个完全不同的结果：

- 如果过度隔离，每个专家都从头积累经验，系统会形成许多重复、孤立的能力。
- 如果过度共享，一个领域里的偶然成功就可能污染其他专家，甚至导致整个系统退化。

我们要找的是第三条路：**经验可以自由发现，但共享必须经过验证；知识可以传播，但传播范围由证据决定。**

## 一、先从第一性原理重新定义“经验”

假设编程专家在修复一个 Python 异步任务时，发现先检查事件循环状态，再修改任务取消逻辑，能够解决某类问题。

系统记录下来的内容可能有四种完全不同的形态：


    <title size="lg">第一层：事件</title>
    这一次任务失败了，后来通过修改取消逻辑解决。

    它只证明某件事发生过，不证明方法具有普遍价值。



    <title size="lg">第二层：经验假设</title>
    在某些异步任务中，失败可能与取消状态没有得到正确处理有关。

    这是待验证的解释，必须保留不确定性。



    <title size="lg">第三层：领域知识</title>
    在已验证的 Python 运行环境与任务条件下，某种取消状态检查策略可以降低特定错误的发生率。

    它已经具有明确的适用范围，可以进入编程专家的能力库。



    <title size="lg">第四层：候选通用原则</title>
    对于具有可重复副作用的任务，在重试前确认上一步的实际状态，可以减少重复执行风险。

    这个原则可能适用于编程、手机操作和复杂工作流，但仍需要跨领域验证。


注意，第四层并不是简单地把 Python 代码复制到手机操作专家中。

真正有迁移价值的，可能是更抽象的原理：**重试前确认实际状态**。不同领域可以采用不同实现，但共享同一个经过验证的原则。

这揭示了一个重要区别：

**经验迁移的对象不一定是原始解决方案，而可能是解决方案背后的机制、约束或判断规则。**

因此，EvoAgent 不应该只有“经验存储库”，还需要能够把经验抽象成候选原则、验证其适用条件，并在不同领域中寻找反例的学习机制。

# 二、经验晋级不能只看成功次数，要判断为什么成功

这是整个迁移机制最关键的一点。

假设编程专家采用某个提示词后，连续 20 次任务成功。能不能把这份提示词直接推广到所有专家？

不能。

因为这 20 次成功可能有不同解释：

- 提示词确实改善了推理。
- 20 个任务其实非常相似。
- 测试案例过于简单。
- 模型本来就能完成这些任务，提示词没有带来实际提升。
- 这批任务恰好使用了某个特定模型或工具版本。
- 评测器没有发现隐藏错误。

因此，经验晋级至少需要回答五个问题。

| 判断问题 | 要获得的证据 |
|---|---|
| 这次成功是真的吗？ | 独立验收结果，而非模型自评 |
| 方法是否真的带来改善？ | 与原有方法的对照实验 |
| 为什么它可能有效？ | 有证据支持的机制假设及适用条件 |
| 在什么范围内有效？ | 不同任务、环境和边界条件的测试 |
| 是否值得共享？ | 迁移收益、额外成本和潜在副作用 |

我建议把**可解释的作用机制、可描述的适用条件、可验证的结果**作为经验晋级的三个核心要求。

这里的“可解释”不是要求模型提供一段听起来合理的理由，而是要求提出一个能够被实验检验的假设。

例如：

> 假设在可能产生重复副作用的操作中，重试前先确认上一步是否已经生效，能够减少重复执行。

这条假设可以通过故意注入超时、响应丢失和重复请求来测试。如果测试结果不支持它，就不应仅凭模型生成的解释把它升级为共享原则。

## 三、我建议建立五级经验晋级体系

我们前面已经讨论过能力成熟度。这次需要进一步区分：**经验的成熟度**和**经验的共享范围**不是同一个东西。

我建议将经验的生命周期设计为以下五级。



      <title size="lg">E0</title>


      **原始事件**

      保存任务输入、执行轨迹、工具返回、失败结果和环境信息。

      权限：仅作为证据，不自动改变稳定能力。





      <title size="lg">E1</title>


      **候选经验**

      从一个或多个事件中提炼问题模式、解决方案假设、适用条件和反例。

      权限：可以用于诊断建议或隔离实验，不作为已验证事实。





      <title size="lg">E2</title>


      **领域验证经验**

      在特定专家、任务类别和环境下，通过对照测试或重复验证。

      权限：可以进入对应领域的候选知识库或策略库。





      <title size="lg">E3</title>


      **跨领域迁移候选**

      提炼出更抽象的机制，并在其他相关领域测试，验证迁移收益与副作用。

      权限：可以申请进入共享能力候选库，但不能直接覆盖现有通用策略。





      <title size="lg">E4</title>


      **已批准的共享经验**

      通过规定的跨领域评测、兼容性检查和发布门禁，成为共享能力、规则或工具的正式版本。

      权限：可以被符合适用条件的专家采用，并继续接受运行监测。



这不是要求每一条经验都必须走完整的五级晋级。

许多经验只在 E1 就已经很有价值，例如一个任务的特殊注意事项；某些专业知识可以长期停留在 E2，因为它们本来就只适用于一个领域。

只有具备明确迁移价值的经验，才值得投入资源晋级为共享能力。

**不晋级不代表失败。保留在正确的局部范围，本身就是一种成功的知识管理。**

# 四、经验迁移有四种不同形式，不能一律当成“共享记忆”

这是我认为需要补充的重要设计。

经验从一个专家迁移到另一个专家时，不一定要迁移同一种资产。我们至少要区分四种形式。


    <title size="lg">1. 事实与知识迁移</title>
    例如某个 API 的参数要求、某项工具的已知限制。

    迁移条件：来源可靠、版本明确、适用范围清楚，并且接收方有使用该知识的需要。



    <title size="lg">2. 策略与原则迁移</title>
    例如“遇到不确定的工具结果时，先查询实际状态，再决定是否重试”。

    迁移条件：作用机制具有跨领域适用性，并经过目标领域的反例与边界测试。



    <title size="lg">3. 工具与组件迁移</title>
    例如把经过验证的幂等请求封装、JSON 参数校验器或检查点机制提供给其他专家。

    迁移条件：接口契约、权限、依赖和兼容性明确；目标环境通过契约测试。



    <title size="lg">4. 工作流与技能迁移</title>
    例如将编程任务中的“执行—检查—修复—复测”模式提炼成可复用流程。

    迁移条件：任务结构相似、节点输入输出兼容，并且目标领域拥有自己的验收规则。


为什么要拆开？

因为一个领域有效的完整工作流，通常不能原样复制到另一个领域；但其中某个工具校验器、状态管理方法或恢复原则可能非常适合共享。

因此，EvoAgent 的经验提炼器应该能够把一个成功案例拆解为多个候选资产，而不是只生成一段长记忆。

例如，一次编程任务的成功执行轨迹，可以分别产生：

- 一条 Python 专用知识。
- 一条关于任务恢复的候选原则。
- 一个可复用的工具调用校验器。
- 一组新的回归测试。
- 一份只适用于该项目的工作流。

这些资产分别进入不同的生命周期，避免把领域知识、通用原则和工程实现混成一团。

# 五、如何判断一个经验能不能迁移到另一个领域？

我建议建立一个明确的**迁移验证流程**，而不是由进化智能体主观决定。

假设编程专家发现了一条候选原则：

“工具调用超时后，不要立即重复执行，应先检查原操作的真实状态。”

系统希望把它推广给手机操作专家。

完整流程应该如下：

<CodeBlock language="mermaid" editable={false}>flowchart TD
    A[编程专家提出候选经验] --> B[提炼作用机制与适用条件]
    B --> C[寻找目标领域的对应问题]
    C --> D{是否存在可验证的迁移假设}
    D -->|否| E[保留为领域经验]
    D -->|是| F[构造目标领域测试案例]
    F --> G[对比原策略与候选策略]
    G --> H[测试成功率、成本和副作用]
    H --> I{是否达到迁移门槛}
    I -->|否| J[拒绝或限制适用范围]
    I -->|是| K[生成共享能力候选]
    K --> L[独立验收与兼容性测试]
    L --> M{发布门禁}
    M -->|通过| N[批准共享版本]
    M -->|失败| O[保留旧版并记录原因]</CodeBlock>

这里最关键的是：**目标领域必须有自己的验证证据。**

编程任务里，重复执行可能导致数据库写入或测试副作用；手机操作里，重复执行可能导致重复提交表单或发送消息。二者的具体风险不同，但都可能需要先确认状态。

如果目标领域的操作无法安全地查询状态，那么这条原则就不能机械地应用。系统可能需要改用其他恢复机制，或者在不确定时停止并请求用户确认。

所以，共享的应该是经过验证的机制与约束，而不是不加条件的命令。

## 六、迁移实验不能只看目标领域的成功率

一条经验在目标领域提高了成功率，仍然不代表它值得共享。

至少需要比较五类指标：

| 指标 | 要回答的问题 |
|---|---|
| 目标收益 | 目标任务是否真正改善？ |
| 迁移稳定性 | 不同任务和环境下是否都有效？ |
| 副作用 | 是否让其他重要行为退化？ |
| 成本变化 | 是否增加了过多模型调用、执行时间或工具费用？ |
| 安全影响 | 是否产生新的重复执行、权限或数据风险？ |

例如，新增一次状态检查，可能会降低重复提交的概率，但同时增加一次工具调用和一定延迟。

如果它应用于不可逆的高风险操作，这个成本可能非常值得；如果应用于纯本地、无副作用的查询任务，则可能没有必要。

因此，共享经验不能只附带一个“推荐使用”的标记，而应当包含适用条件、预期收益、已知副作用和不适用情形。

# 七、共享能力不能只有“全局开启”和“完全隔离”两种状态

我认为这是能力迁移设计中一个特别重要的改进点。

一项经验经过跨领域验证后，也不一定要立即应用于所有专家。我们应该支持按适用范围分批推广。

例如，一种新的恢复策略已经在编程和手机操作领域得到验证，但还没有在 AI 漫剧制作中测试。

它可以先成为：

- 编程专家的正式能力。
- 手机操作专家的正式能力。
- 漫剧专家的可选实验能力。
- 通用内核中尚未启用的共享候选。

这比一次性全局发布安全得多。

我建议共享策略支持以下状态：

这意味着，共享能力也可以具有渐进式的发布过程。

但这里需要一个重要限制：权限、安全和预算规则不能因为普通能力迁移而被放宽。普通共享策略只能在受保护的系统约束之内运行。

## 八、经验迁移后，源专家与目标专家如何保持独立？

假设编程专家把一个恢复原则推广给手机操作专家。

后续手机操作专家发现，这个原则在某些界面操作中并不适用。

正确的做法不是要求两个专家必须继续使用相同策略，也不是立刻撤销编程专家的能力。

而是：

1. 记录目标专家的失败案例。
2. 确认是经验的适用范围定义有误，还是目标实现有问题。
3. 如果问题只在手机操作领域，就限制该领域的启用条件。
4. 如果发现共享原则本身存在缺陷，再修订共享资产并重新评测其他使用方。
5. 保留源专家和目标专家的独立版本，避免一次迁移失败引发无关回归。

这引出一个重要架构原则：

**共享的是有版本、有范围、有契约的资产，而不是把所有专家绑在同一份可变策略上。**

共享资产更新时，使用方可以锁定旧版本，主动申请升级，并在自己的评测集上验证兼容性。

这与软件依赖管理很像，但 EvoAgent 还需要增加能力收益、适用条件、运行证据和跨领域副作用等信息。

# 九、这套迁移机制最终需要哪些数据？

为了让前面讨论的机制可落地，我建议增加一个独立的 `experience_transfer` 领域，而不是把迁移逻辑塞进普通记忆检索。

核心数据可以分成四类。

| 数据对象 | 主要字段 |
|---|---|
| 经验候选 | 来源任务、来源专家、问题模式、候选原则、置信度、适用条件、反例 |
| 迁移假设 | 源领域、目标领域、作用机制、预期收益、风险和不适用范围 |
| 迁移实验 | 基线版本、候选版本、测试集、运行环境、质量、成本与副作用 |
| 迁移发布 | 批准范围、共享资产版本、启用条件、依赖方、回滚目标 |

这些记录应当与能力图谱关联。

例如，某条候选原则最初来自编程专家，后来在手机操作专家中通过测试。系统应能追踪它的来源、验证证据和目标领域的实际收益。

但不能因为它被批准共享，就把源专家的全部私有记忆一并共享出去。**共享经验与共享原始数据必须是两件事。**

如果原始轨迹包含用户文件、项目代码或敏感信息，系统应优先使用经过授权、脱敏和必要性审查的测试材料。不能为了证明迁移有效，就默认把所有领域的数据汇集到一个共享记忆库。

# 十、我认为还需要防止一个更隐蔽的问题：经验迁移造成“认知污染”

假设编程专家在某个模型上发现，使用更详细的规划提示词能够改善任务结果。它把这项经验推广给其他专家。

但真实原因可能是该模型在旅游任务中已经足够强，额外规划反而会造成冗长回答、增加调用成本，甚至让它错过用户真正关心的约束。

这种情况说明，迁移经验时必须区分三个层次：

- **机制层经验：** 为什么某种方法可能有效。
- **策略层实现：** 在具体模型、任务和环境中如何实现该方法。
- **运行层配置：** 何时启用、使用多大强度、何时停止。

机制可以具有较强的可迁移性，但策略和配置未必能够直接迁移。

例如，“复杂任务需要验证关键约束”可以成为共享原则；“每个任务都多调用两次模型”则不应成为全局规则。

因此，我建议 EvoAgent 采用一个分离设计：

**共享原则与验证契约，领域专家独立选择具体策略和执行强度。**

只有当某个具体实现也经过目标领域验证后，才允许共享该实现。这样可以避免把在一个领域有效的技巧，错误地升级为所有领域必须遵循的固定做法。

## 十二、下一轮我建议继续讨论什么？

现在我们已经初步建立了能力资产模型、所有权机制和经验迁移机制，但还有一个根本问题没有真正解决：

**当多个专家、多个候选版本和多个改进方向同时存在时，EvoAgent 应该如何决定先优化什么？**

例如：

- 编程专家的成功率提升了，但调用成本很高。
- 旅游专家的稳定性存在问题，但只影响少量复杂任务。
- 一个共享上下文组件可能同时影响四个专家。
- 一个新的模型适配方案有潜力，但需要昂贵的回归测试。
- 一项记忆策略改进可能提高长期任务质量，但短期测试效果不明显。

系统不能简单选择失败次数最多的模块，也不能只挑最容易取得短期分数提升的改进。

我认为下一轮应该研究 **EvoAgent 的进化决策与资源分配机制**，回答四个问题：

1. 如何衡量一项能力当前的真实短板和改进价值？
2. 如何比较局部改进、共享能力改进和基础设施改进？
3. 如何在质量收益、成本、风险、时延和验证成本之间做决策？
4. 如何决定继续实验、扩大测试、发布、暂停还是放弃？

这会把前面所有设计真正连起来：能力图谱告诉系统可以改什么，经验迁移机制告诉系统可以共享什么，而进化决策机制则负责判断**现在最值得改什么，以及值得投入多少资源**。
