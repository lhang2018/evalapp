# EvoAgent 第十一专项：模型适配、能力迁移与多模型独立进化

这一轮回到你最初提出的核心目标：

**让 EvoAgent 在当前大语言模型、当前设备和当前任务环境中不断变强；当模型发生变化时，能够保存已经验证的成果，从新的分支继续优化，而不是重新从零开始，也不把旧模型的缺陷带到新模型上。**

这里有一个非常关键的设计问题。

假设你现在使用模型 A，经过长期优化后，已经获得了较好的通用任务规划、编程工具调用、上下文管理和故障恢复能力。后来你换成模型 B。

如果直接把模型 A 的全部提示词、经验、路由策略和 ReAct 参数复制过去，可能出现以下情况：

- 模型 B 不需要那么长的提示词，导致成本上升；
- 模型 B 的工具调用格式不同，导致执行失败；
- 模型 B 更擅长规划，却被旧策略限制；
- 模型 B 对上下文的处理方式不同，旧压缩策略反而丢失关键信息；
- 模型 A 的错误补偿规则被保留下来，降低模型 B 的表现；
- 模型 B 在某些任务上更好，但在另一些任务上更差。

所以，模型切换绝不能等同于简单替换 API 地址。

我建议把这个专项定义为 **Model Adaptation & Evolution System（模型适配与进化系统）**，让模型适配成为 EvoAgent 的一等能力。

## 一、首先确立一个架构原则：智能体不是模型，模型也不是智能体

EvoAgent 的整体能力由多个部分共同构成：

- 基础模型的理解、推理与生成能力；
- 提示词与指令策略；
- 路由、规划和 ReAct 控制；
- 上下文组装、压缩和记忆检索；
- 工具契约与专业技术能力；
- 工作流与任务状态管理；
- 结果验收和自我修复；
- 用户偏好与经验系统；
- 当前设备、权限和运行环境。

因此，模型只是智能体能力的一部分。

更换模型时，系统需要判断哪些组件可以直接复用，哪些需要重新校准，哪些必须隔离，哪些需要重新开发。


    **EvoAgent 稳定内核**
    任务状态、权限边界、工具契约、验收标准、预算控制和版本管理



    **模型适配层**
    统一调用协议、能力声明、上下文适配、工具调用映射与错误归一化


    <grid-item>

        **模型 A 适配分支**
        独立提示词、路由参数、上下文策略和评测记录

    </grid-item>
    <grid-item>

        **模型 B 适配分支**
        独立提示词、路由参数、上下文策略和评测记录

    </grid-item>


    **共享的已验证能力**
    领域知识、工具契约、工作流、验收规则和可迁移经验


这里需要注意：共享内核不代表所有组件都必须共用一份配置。真正的设计原则是**统一契约、明确作用域、独立版本、受控共享**。

# 二、建立四类资产，决定模型切换时如何处理

我建议把 EvoAgent 中与智能相关的资产分成四类。这比简单地把全部文件复制到一个新 Git 分支里更可靠。

## 2.1 A 类：模型无关的稳定资产

这些资产原则上不应依赖某个模型的行为。

例如：

- 工具输入输出契约；
- Android 权限边界；
- 任务状态机；
- 工作流 DAG 定义；
- 代码测试与媒体验收规则；
- 任务 ID、事件 ID 和检查点协议；
- 用户授权记录；
- 预算硬限制；
- 文件恢复与副作用核验机制。

更换模型时，通常可以直接复用，但仍要验证新模型是否能正确遵守这些契约。

尤其是权限和预算限制，不能依赖模型提示词保证，必须由确定性控制器执行。

## 2.2 B 类：跨模型可迁移的知识与经验

这些资产可能适用于多个模型，但需要检查适用条件。

例如：

- 用户明确表达的工作习惯；
- 当前项目的架构与业务约束；
- Python 代码重构的通用验收方法；
- 远端任务超时后的安全核查原则；
- 已验证的漫剧工作流；
- 工具故障的真实复现案例；
- 经过验证的领域知识。

这类资产应尽可能与模型版本解耦。

但需要保留来源和适用范围。例如，“模型 A 经常漏掉某个工具参数，所以提示词必须重复提醒”不是通用知识；真正可以迁移的，可能是“工具参数应通过 Schema 校验，缺少必填字段时禁止执行”。

## 2.3 C 类：模型相关的适配资产

这些资产应该按模型或模型能力配置独立管理。

例如：

- 系统提示词与角色指令；
- ReAct 的输出格式与循环策略；
- 工具调用提示模板；
- 规划深度和反思策略；
- 上下文压缩阈值；
- 结构化输出适配；
- 模型特定的错误恢复规则；
- 置信度校准数据；
- 针对该模型优化过的路由参数。

这些资产不能因为在模型 A 上有效，就假设在模型 B 上也有效。

## 2.4 D 类：模型与环境共同依赖的资产

这类最容易被忽略。

例如：

- 模型 A 在某种 Android 操作场景下的最佳视觉提示词；
- 模型 B 在特定项目规模下的上下文截断策略；
- 某个模型配合特定工具版本时的成功率；
- 模型在低网络质量或有限资源条件下的降级策略。

它们不只依赖模型，还依赖工具版本、设备、操作系统、上下文长度和外部服务。

建议给这类资产同时绑定模型、环境和依赖版本。环境变化时，相关适配也可能需要重新验证。

# 三、模型适配不能只靠 Git 分支，还要建立完整的适配快照

你提出的“把适配好的模型存档，从新的分支继续优化”方向是对的，但仅靠 Git 分支还不够。

Git 能管理文本配置、代码和部分工作流定义，却不能自动保存所有外部依赖、评测数据、远端模型行为和运行结果。

因此，我建议引入一个正式实体：`Model Adaptation Snapshot`，即模型适配快照。

它代表一套可以被明确识别、复现、比较和回滚的智能体配置。

## 3.1 快照包含什么？

这是概念示例。正式快照还应包含配置内容哈希、代码提交、依赖锁定文件、模型参数、数据集版本、适用环境、许可证信息、发布门禁结果以及回滚引用。

如果模型供应商无法提供可固定的模型权重或精确修订版本，系统应明确标记该快照为“外部模型版本不可完全锁定”。即使配置和提示词完全相同，供应商更新模型后，行为也可能变化。

## 3.2 为什么需要快照？

它能够回答：

- 当前稳定版本使用了哪个模型？
- 该模型对应哪些提示词和上下文策略？
- 哪个版本的工具和工作流与它配套？
- 这套配置在哪些任务集上通过了评测？
- 最近一次改进改变了什么？
- 如果出现退化，可以恢复到哪个已验证版本？

这样，EvoAgent 的进化历史就不是一堆难以追溯的配置修改，而是具有明确父子关系的版本链。

# 四、多模型分支：独立进化，但不重复造轮子

我建议采用“共享稳定内核 + 模型独立适配分支 + 跨模型候选晋升”的模式。

这比让所有模型共享一套不断变化的提示词更安全，也比完全分裂成互不相干的多个智能体更高效。

## 4.1 推荐的版本结构


    **Core Stable**
    权限、任务状态、工具契约、验收协议、预算与恢复机制



    <grid-item>

        <title size="md">Model A Branch</title>
        稳定版
        A 专属提示词、规划参数、上下文策略、评测结果。

        继续优化 A，不受 B 的实验直接影响。

    </grid-item>
    <grid-item>

        <title size="md">Model B Branch</title>
        实验版
        从通用资产与迁移基线开始，重新校准 B 的适配策略。

        独立评测，逐步晋升为稳定版。

    </grid-item>



    **Cross-Model Candidate Exchange**
    候选改进 → 兼容性检查 → 跨模型评测 → 选择性合并


## 4.2 一个重要细节：不要把 Git 合并当成能力迁移

假设模型 A 的提示词从 V12 改成 V13，在编程任务上提升了 5%。

这个改动不应自动合并到模型 B 的提示词中，因为 B 可能不需要相同的提示，也可能因为指令冲突而表现更差。

正确的处理方式是：

1. 记录改动针对什么问题；
2. 保存原始失败案例与评测结果；
3. 将可复用的根因或设计原则提炼出来；
4. 在模型 B 分支生成一个新的候选方案；
5. 在 B 的独立评测集上验证；
6. 只有通过门禁后，才将候选合入 B 分支。

真正共享的是经过验证的知识、工具改进和适用原则，而不是盲目复制所有配置。

同样，模型 B 发现的通用工具缺陷，可以修复在共享工具层；但 B 专属的提示词优化，不应自动改变 A 的稳定版本。

## 4.3 如何处理共享内核升级？

假设共享工具执行网关从 V4 升级到 V5。

两个模型分支都可以收到升级候选，但分别验证：

- 工具调用协议是否兼容；
- 模型输出是否仍然能够被正确解析；
- 任务状态是否保持一致；
- 旧工作流是否仍然可用；
- 各自的回归集是否通过。

共享内核的安全修复可能需要强制升级，但普通性能优化不应自动打破所有模型分支的稳定性。

# 五、切换模型时的迁移流程

这是整个专项的核心执行流程。

模型切换不应该直接把流量从 A 指向 B，而应该经历一次有明确证据的迁移。

  {#each [
    ["M1：冻结源快照","保存模型 A 的配置、代码、依赖、评测结果和已知限制。"],
    ["M2：创建迁移分支","继承模型无关的内核、工具契约、知识和经验；隔离模型专属适配资产。"],
    ["M3：能力探测","测试模型 B 的结构化输出、工具调用、规划、上下文遵循和异常处理。"],
    ["M4：生成适配候选","为模型 B 调整提示词、上下文策略、ReAct 参数与模型适配器。"],
    ["M5：独立评测","在统一任务集与 B 专属测试集上比较质量、成本、延迟和稳定性。"],
    ["M6：受控试运行","在不影响正式任务的条件下进行影子测试或低风险灰度。"],
    ["M7：建立稳定快照","通过门禁后发布 B 的独立稳定版本，保留 A 的稳定快照。"],
    ["M8：持续校准","监控新模型表现、外部版本变化和能力退化，必要时回滚。"]
  ] as item}


        {item[0].split("：")[0]}


        **{item[0].split("：")[1]}**
        {item[1]}


  {/each}

## 5.1 能力探测应该测什么？

不能只用几个问答题判断模型是否适合 EvoAgent。

至少应测试：

- 是否能正确输出工具调用参数；
- 是否遵守结构化输出契约；
- 是否能够在观察后修正计划；
- 是否能区分工具请求被接受与任务真正完成；
- 是否会在上下文压缩后丢失硬性约束；
- 是否能够根据错误结果进行有效恢复；
- 是否会在证据不足时错误宣称成功；
- 是否能够在预算限制内完成任务；
- 是否能处理多轮任务状态和长任务检查点。

这些测试应尽量使用真实的 EvoAgent 执行接口，而不是只测试模型的裸文本回答。

## 5.2 迁移后哪些内容需要重新验证？

即使工具契约和工作流本身没有改变，新的模型也可能改变整体执行表现。

例如，旧模型需要详细的分步规划提示词，新模型却更擅长根据状态动态规划。旧策略迁移过去后，可能导致过度规划、重复调用和成本上升。

所以，迁移评测既要检查单个模型能力，也要检查它与上下文、ReAct、工具和验收器组合后的端到端表现。

# 六、最难的部分：如何判断一条经验到底能不能跨模型迁移？

这是 EvoAgent 自进化系统需要特别重视的问题。

经验不应该只有“通用”和“模型专属”两个标签。我建议采用四种迁移状态。

| 状态 | 含义 | 处理方式 |
|---|---|---|
| `PORTABLE` | 原理和适用条件不依赖具体模型 | 可以复用，但仍需检查当前任务是否满足条件 |
| `CALIBRATION_REQUIRED` | 原理可复用，但参数或阈值依赖模型 | 继承原理，在新模型上重新校准 |
| `MODEL_SPECIFIC` | 与某个模型的特定行为强相关 | 保留在原模型分支，不直接迁移 |
| `UNVERIFIED` | 证据不足，无法判断迁移性 | 只作为实验候选，不作为稳定策略 |

## 6.1 举一个具体例子

假设模型 A 经常忘记在调用文件工具时传递 `workspace_id`。

系统积累了一条经验：

> 每次调用文件工具前，都在提示词中重复强调必须传递 `workspace_id`。

这条经验可能只是在补偿模型 A 的行为缺陷。

真正应该提炼的通用原则是：

> 所有文件操作必须经过确定性参数校验，缺少必填字段时禁止执行。

这样就把模型相关的补偿措施，转化成模型无关的工程约束。

但不是所有问题都能这么处理。

例如，模型 A 和 B 对长上下文的处理方式不同，某种压缩策略在 A 上效果很好，在 B 上可能需要重新校准压缩比例、保留规则和摘要结构。这种经验应当继承设计原则，但不能直接复制参数。

## 6.2 迁移证据应该来自哪里？

建议综合使用：

- 相同输入下的跨模型回放；
- 新模型的独立评测集；
- 不同任务复杂度的测试；
- 错误类型和恢复行为；
- 成本与延迟；
- 经验应用后的反例；
- 长期任务中的稳定性。

不能因为某条经验在 A 上成功了 100 次，就认为它在 B 上也有同样的效果。

经验的来源模型、验证模型和适用环境都应当被明确记录。

# 七、多模型运行时：怎样决定一个任务交给哪个模型？

当 EvoAgent 支持多个模型后，下一步不是让所有任务都使用最强模型，而是建立一个模型调度器。

它应该综合任务需求、能力画像、成本、延迟和风险，选择适合的模型。

例如：

- 简单意图分类可以使用低成本模型；
- 复杂代码架构分析可以使用推理能力更强的模型；
- 工具调用密集型任务可以优先选择经过验证、工具调用可靠的模型；
- 涉及本地隐私的任务可以使用本地模型或不上传敏感数据的方案；
- 云端模型不可用时，可以使用经过批准的离线能力处理有限任务。

## 7.1 调度器不能只按模型价格排序

假设模型 A 每次调用成本低，但复杂任务成功率较低，需要反复重试；模型 B 单次调用较贵，却能一次完成。

只比较单次调用费用会得到错误的调度结果。

建议重点比较：

\[
\text{每次成功任务的总成本}
=
\frac{\text{任务期间全部模型、工具和恢复成本}}
{\text{验收通过的任务数}}
\]

实际系统还应考虑任务时限、隐私、延迟、失败后果和用户等待成本。对于某些任务，最低费用并不是最优目标。

## 7.2 建立模型能力画像

模型调度器应该使用经过实际评测的能力画像，而不是依赖模型供应商的宣传或模型自评。

每个模型可以分别记录：

- 意图识别准确率；
- 工具参数有效率；
- 规划质量；
- 长任务完成率；
- 上下文约束保留率；
- 结果验收通过率；
- 故障恢复成功率；
- 平均成本和延迟；
- 在不同复杂度任务上的表现；
- 已知的能力限制。

这些指标应当关联模型版本和适配快照。

如果供应商悄悄更新了底层模型，即使 API 名称没有变化，EvoAgent 也应该通过持续评测检测表现变化，而不是默认原有能力画像永远有效。

## 7.3 不要让模型调度器产生无限升级循环

一个常见陷阱是：低成本模型不确定，就升级到更强模型；更强模型仍不确定，就再升级；不断调用直到预算耗尽。

建议建立明确的升级策略：

1. 先判断当前缺少的是知识、状态证据还是推理能力；
2. 如果缺少事实，优先检索或调用工具，而不是升级模型；
3. 如果确实需要更强推理能力，检查升级的预期收益；
4. 限制升级次数和额外成本；
5. 如果仍无法解决，返回部分完成、证据不足或需要人工介入的状态。

模型越强不意味着所有问题都能解决。缺少实际环境信息时，更强模型同样可能产生错误结论。

---

# 八、模型适配的评测体系

如果没有独立评测，所谓“模型适配成功”就只是主观感觉。

建议建立四层评测。


    **第一层：模型接口能力**
    测试请求格式、结构化输出、工具调用、超时、错误码和流式响应处理。


    **第二层：组件能力**
    分别测试路由、规划、上下文压缩、记忆检索、ReAct、诊断和验收策略。


    **第三层：端到端能力**
    使用真实工具和工作流，测试复杂任务完成率、恢复能力、延迟和实际费用。


    **第四层：迁移与回归**
    检查新模型是否继承了通用能力、保留了约束，并且没有让其他领域或既有稳定任务退化。


## 8.1 建立统一的跨模型任务集

建议维护一套相对稳定的基准任务集，包含：

- 通用问答和信息整理；
- 多轮对话与用户偏好；
- 工具调用与结果验证；
- Android 应用操作；
- 编程、代码修改和测试；
- 复杂任务规划与 DAG 执行；
- 长上下文和记忆检索；
- 故障诊断与恢复；
- 不确定情况下的澄清与停止；
- 成本受限任务。

同时保留各领域的专属评测集，避免统一基准掩盖局部能力差异。

跨模型比较时，应尽量固定任务输入、工具版本、验收规则和环境条件。对于具有随机性的任务，需要足够的重复测试，并记录实际调用参数和结果。

## 8.2 不能只看平均分

例如，模型 B 在简单任务上的表现显著提升，但在文件操作和手机操作任务中更容易误判成功。

如果只看平均分，模型 B 可能看起来更好，但在实际个人助手场景中却更危险。

因此，评测应该同时设置：

- 整体质量目标；
- 领域最低门槛；
- 高风险任务硬性门槛；
- 成本和延迟限制；
- 关键故障率限制；
- 迁移后保护集合。

任何不可接受的安全退化，都不能由其他任务上的得分提升来抵消。

## 8.3 新模型是否需要完全重新优化？

不需要。

更合理的是先继承稳定内核和可迁移资产，再通过评测定位新模型真正需要调整的部分。

例如：

- 工具契约没有问题，就不需要重写工具系统；
- 用户记忆仍然有效，就不需要重建全部用户偏好；
- 新模型的工具调用已经稳定，就不必机械地增加更多工具提示；
- 只有上下文压缩导致关键信息丢失时，才重点优化压缩策略；
- 只有复杂规划表现退化时，才针对 Planner 和 ReAct 做专项实验。

这样能够减少迁移成本，避免为了适配新模型而无差别重构整个智能体。

# 九、版本回滚与稳定性保护

模型 A 已经长期稳定运行，而模型 B 正在实验时，两个版本必须互不污染。

我建议为每个适配分支维护独立的：

- 稳定快照；
- 实验候选；
- 评测结果；
- 依赖清单；
- 运行监控；
- 回滚目标。

例如：



      **Model A**
      稳定
      snapshot-A12


      **Model B**
      实验
      candidate-B04



  B 的实验失败时，回滚到 B 自己的上一个稳定快照。如果 B 尚无稳定版本，则退回到明确配置的已验证基线或模型 A 的兼容版本。

不能假设模型 A 的快照一定能够无条件替代 B 的快照。两者可能使用不同的工具协议、上下文格式或模型参数，因此回滚目标必须提前验证兼容性。

## 9.1 模型供应商更新时怎么办？

如果供应商在不改变公开模型名称的情况下更新了底层模型，EvoAgent 应将它视为潜在的环境变化。

建议：

1. 定期运行关键评测；
2. 检测工具调用、成功率、成本和延迟变化；
3. 对异常变化生成诊断事件；
4. 如果可固定旧模型版本，则切回已验证版本；
5. 如果无法固定，则隔离相关适配并重新校准；
6. 在确认表现稳定之前，不自动晋升新快照。

这能够保护长期积累的适配成果，避免外部模型更新悄悄破坏已经稳定的智能体。

# 十一、下一专项：进化优先级与全局资源调度

到目前为止，我们已经讨论了智能体如何执行任务、积累经验、修复故障、管理不确定性，以及适配不同模型。

但还有一个关键问题尚未彻底解决：

**当 EvoAgent 同时发现几十个可以改进的问题时，它应该先优化什么？**

例如：

- 路由器有一些分类错误；
- 编程专家在少数复杂任务中失败；
- 上下文压缩导致部分约束丢失；
- 某个工具存在偶发故障；
- 一个模型的成本比另一个模型高；
- 漫剧工作流在某个环节经常返工；
- 自我诊断器有时会误归因。

如果系统同时优化所有问题，会消耗大量模型调用和评测资源，还可能让多个改进互相影响。

我建议下一轮设计 **Evolution Prioritization & Resource Allocation Engine（进化优先级与资源调度引擎）**，重点研究：

1. 如何判断一个问题是否值得优化；
2. 如何估计问题对真实任务成功率的影响；
3. 如何区分高频小问题和低频高损失问题；
4. 如何计算改进的预期收益、实施成本和回归风险；
5. 如何在通用能力与领域专家之间分配优化资源；
6. 如何决定该投入模型调用、工程修复、工具优化还是评测建设；
7. 如何限制持续优化带来的成本膨胀；
8. 如何避免系统反复优化同一个问题，却忽略真正的瓶颈；
9. 如何判断某项改进已经达到收益递减点；
10. 如何建立全局优化计划，让系统在有限资源下持续提升整体能力。

这一步会把 EvoAgent 从“能够不断发现和修复问题”，推进到“**能够判断哪些问题最值得解决，并把有限资源投入最有价值的改进**”。
