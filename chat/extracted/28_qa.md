# EvoAgent 深度设计第七轮：如何在变化的环境中保持稳定，并持续进化？

这一轮，我们要解决一个比模型切换更广泛的问题：

**EvoAgent 长期运行时，如何分辨究竟是环境变了、工具坏了、模型退化了，还是智能体自身的能力确实存在缺陷？**

这是决定系统能否长期稳定运行的关键。

想象几个场景：

- 昨天还能正常调用的工具，今天开始返回不同格式的数据。
- 云端模型没有更换名称，但回答风格或工具调用行为发生了变化。
- Android 系统升级后，无障碍节点树的结构发生改变。
- 一个工作流之前一直成功，今天却因为外部服务超时而失败。
- 智能体连续几次遗漏用户约束，于是进化控制器准备修改通用提示词。
- 某个工具偶尔失效，但智能体错误地把它诊断为自己的规划能力不足。

这些情况的共同点是：**系统观察到了行为变化，但变化不一定发生在智能体自身。**

如果没有正确的诊断机制，EvoAgent 可能陷入两种相反的错误：

1. 把环境问题当成能力问题，反复修改提示词、规划和记忆，越改越不稳定。
2. 把能力问题当成环境问题，长期依赖重试、降级或换模型掩盖真实缺陷。

因此，我建议在现有进化架构中增加一个独立的核心子系统：

**环境与能力健康诊断器（Environment & Capability Health Monitor）。**

它负责识别变化、提出竞争性根因假设、收集证据，并决定应该恢复、适配、修复还是启动进化流程。

## 一、第一性原理：先区分“系统状态变化”和“系统能力变化”

这两个概念看起来接近，但对架构的影响完全不同。


    <title size="lg">环境状态变化</title>
    外部条件发生了变化，智能体自身的实现可能完全没有变化。

    例如，网络中断、API 限流、应用页面改版、模型服务端升级、权限被撤销。



    <title size="lg">系统能力变化</title>
    智能体在给定任务和环境条件下，实际完成任务的表现发生变化。

    例如，指令遵循率下降、错误恢复失效、记忆检索错误增加、结果验收遗漏。



    <title size="lg">二者之间的关系</title>
    环境变化可能导致能力表现下降，但不能直接证明智能体内部实现存在缺陷；反过来，环境看似正常，也不代表智能体内部一定没有问题。


我们需要把观察到的现象、可能的根因和最终确认的原因分开存储。

例如，一次手机操作失败，最初只能记录：

> 目标页面未打开，操作未完成。

这时不能立即得出“手机操作能力下降”的结论。

接下来还需要检查：

- 应用是否已经启动？
- 系统是否弹出了权限窗口？
- 无障碍服务是否仍然有效？
- 目标应用是否更改了界面？
- 操作指令是否发送成功？
- 视觉识别是否识别错了控件？
- 执行后的状态验证是否正常工作？

只有在收集到足够证据后，系统才应该选择具体的修复路径。

**所以，健康诊断器的第一项职责不是修复问题，而是防止系统在尚未理解问题之前就开始修改自己。**

# 二、我建议建立四类故障归因，而不是让模型直接猜根因

EvoAgent 应该首先把异常分配到不同的诊断范围，再通过证据逐步缩小范围。






      **A 类：外部环境异常**

      网络、服务可用性、API 限流、系统权限、第三方应用变化等。

      优先动作：检查状态、等待、切换到兼容路径或安全降级，而不是立即进化提示词。








      **B 类：工具或接口异常**

      工具返回格式变化、参数校验失败、执行器崩溃、结果状态不可信、接口契约不兼容等。

      优先动作：验证工具契约、检查调用与返回、修复适配器或恢复工具服务。








      **C 类：智能体实现缺陷**

      提示词遗漏约束、规划错误、上下文压缩丢失信息、记忆检索错误、ReAct 状态转换不正确等。

      优先动作：定位具体能力或组件，创建受控候选，并运行相关回归测试。








      **D 类：交互性或复合故障**

      例如模型更新后更容易生成某种参数，而工具适配器恰好无法处理这种参数；或者新系统界面与旧的操作策略发生冲突。

      优先动作：分析多个组件之间的交互，不要强行将问题归到单一组件。



这四类不是互斥的最终标签。一场故障可能同时包含外部原因和内部缺陷。

例如，工具服务发生超时属于环境异常；智能体超时后不检查状态就重复提交，则是内部恢复策略缺陷。

我们应该允许一个故障关联多个根因，并记录每个根因的证据强度。

另外，第一版不必追求每次都准确识别根因。更重要的是：**当根因不确定时，系统能够限制影响、保留证据，并避免做出破坏性修改。**

# 三、如何知道环境已经变化了？

不能只靠用户投诉，也不能只靠失败日志。

因为某些变化在任务失败之前就可以发现，而另一些变化只有通过实际任务表现才能发现。

我建议建立三个层次的变化检测。

## 3.1 第一层：契约变化检测

这是最直接、也最可靠的一类。

例如：

- API 返回字段从字符串变成对象。
- 工具不再接受某个参数。
- 模型服务返回新的错误类型。
- Android 无障碍节点缺失关键属性。
- 工作流所依赖的程序版本发生变化。

这些变化可以通过接口契约测试、版本信息、结构校验和健康检查发现。

系统应当在关键操作前检查必要的依赖是否满足要求，而不是每次都等待任务失败。

## 3.2 第二层：运行行为漂移检测

有些变化不会导致接口直接报错，却会逐渐改变实际表现。

例如：

- 模型的工具调用成功率下降。
- 相同类型任务的平均调用次数增加。
- 上下文压缩后的关键约束遗漏率上升。
- 某类手机界面的控件识别准确率下降。
- 同一工作流的失败恢复次数持续增加。

这些指标需要按照能力、模型版本、工具版本、任务类型和环境分组统计。

例如，不能只统计整个系统的工具调用失败率，还要分别统计：

- 模型 A 与模型 B 的工具调用失败率。
- 不同工具版本的参数校验失败率。
- 编程任务和手机操作任务中的重试率。
- 网络正常和网络不稳定时的恢复表现。

否则，系统可能把一个领域的局部异常误判为全局能力退化。

## 3.3 第三层：任务分布变化检测

还有一种更隐蔽的变化：工具、模型和代码都没有变，但用户开始提出不同类型的任务。

例如，编程专家原来主要处理简单函数，后来开始处理多模块工程；手机操作专家原来只负责打开应用，后来开始执行跨应用流程。

即使内部实现完全相同，成功率也可能下降。

这不一定是退化，而可能是任务难度和分布发生变化。

因此，健康诊断器必须记录任务类别、难度特征和适用范围。发现表现变化后，应先检查新旧任务分布是否可比，再判断是否存在真实能力退化。

**没有任务分布信息的成功率趋势，很容易产生错误结论。**

# 四、系统发现异常后，应该如何决定下一步？

我建议采用一个“先止损、再诊断、后修复”的运行时状态机。

这与后台进化流程不同。运行时首先要保证当前任务安全，而不是立即开始实验。

<CodeBlock language="mermaid" editable={false}>flowchart TD
    A[检测到异常或行为漂移] --> B[检查权限、任务状态与安全风险]
    B --> C{是否存在紧急风险}
    C -->|是| D[停止危险操作并保护状态]
    C -->|否| E[收集工具、模型、环境与任务证据]
    D --> E
    E --> F[生成多个根因假设]
    F --> G[执行低风险诊断检查]
    G --> H{是否有足够证据}
    H -->|否| I[安全降级、暂停或请求协助]
    H -->|是| J{问题属于哪一类}
    J -->|环境| K[恢复依赖或切换兼容路径]
    J -->|工具| L[修复适配器或工具契约]
    J -->|内部能力| M[提交进化候选]
    J -->|复合故障| N[分解交互因素并隔离实验]
    K --> O[重新验证任务状态]
    L --> O
    M --> P[离线评测与发布门禁]
    N --> P
    O --> Q[更新健康状态与运行证据]
    P --> Q</CodeBlock>

这里有一个重要区别：

- **运行时恢复**：让当前任务安全地继续、降级或停止。
- **后台进化**：通过独立实验改变未来任务的表现。

例如，手机操作过程中发现无障碍服务失效，运行时应该停止依赖该服务的操作并提示用户恢复权限，而不是一边操作手机，一边修改无障碍策略。

又例如，代码工具突然返回异常数据，当前任务应该进入安全恢复路径；后台则可以记录异常，分析是否需要更新工具适配器。

这两条路径应当共享证据，但不应共享未经验证的变更。

# 五、环境适应不应该等同于“自动修改自己”

这是我想特别强调的架构原则。

当环境变化时，系统有很多种适应方式。直接修改提示词和 Harness，只是其中一种，而且往往不是第一选择。

我建议把运行时适应分为五个层级。



      <title size="lg">L0</title>


      **重新确认状态**

      重新检查当前任务、工具结果和外部环境，避免基于过时状态继续操作。





      <title size="lg">L1</title>


      **调整当前任务策略**

      在既有权限和预算范围内，重新规划、调整重试方式或选择已经批准的兼容路径。





      <title size="lg">L2</title>


      **切换已验证配置**

      例如切换到经过测试的备用模型、工具适配器或工作流版本。






        <title size="lg">L3</title>


        **创建新的候选实现**

        如果现有策略无法解决问题，才创建隔离候选，修改提示词、上下文、Planning、工具策略或其他组件。







        <title size="lg">L4</title>


        **修改受保护基础设施**

        涉及权限模型、核心状态机、发布门禁和硬预算控制的变化，必须走专门的高风险变更流程。




系统应优先选择满足安全和任务要求、且变更范围最小的适应方式。

但这并不意味着永远优先使用最低层级。如果发生了严重的安全风险，正确动作可能是直接停止操作；如果备用工具也不可靠，就不能为了追求任务完成率而强行切换。

**适应的目标是恢复正确、稳定的任务执行，而不是保证任务无论如何都继续。**

# 六、如何防止健康诊断器自己误判？

我们之前已经讨论过，进化系统可能把相关性误认为因果关系。现在到了真实运行环境中，这个问题更加突出。

假设编程专家最近的成功率从 90% 降到 82%。

系统可能提出三种解释：

- 模型服务行为发生了变化。
- 工具调用成功率下降。
- 最近的任务更复杂了。

如果直接选择其中一个原因并开始修改，就有可能走错方向。

因此，我建议健康诊断器采用**竞争性假设 + 证据更新**的机制。

例如：

| 根因假设 | 支持证据 | 反对证据 | 下一步检查 |
|---|---|---|---|
| 模型行为漂移 | 工具调用格式错误增加 | 模型版本标识没有变化 | 运行固定探针任务 |
| 工具接口异常 | 参数校验错误增加 | 工具健康检查正常 | 使用已知有效参数直接测试 |
| 任务难度增加 | 最近复杂任务比例上升 | 同类任务仍可能退化 | 按任务类别重新计算成功率 |
| 上下文策略退化 | 关键约束遗漏增加 | 尚无独立复现 | 比较原始输入与压缩后上下文 |

系统不需要一开始就确定唯一根因，而是根据证据逐步更新判断。

## 6.1 使用固定探针任务

可以为模型、工具和关键组件建立一组低成本的健康检查任务。

例如：

- 模型是否能按照约定格式调用工具。
- 上下文组装器是否保留用户明确提出的约束。
- 工具适配器是否正确处理已知输入和异常返回。
- 记忆检索是否能找到指定的测试记忆。
- ReAct 状态机是否能在工具失败后进入正确的恢复状态。

这些探针应当尽量确定性强、成本低，并避免对真实用户数据和外部系统产生副作用。

如果固定探针失败，而对应的环境和依赖检查也出现异常，就能缩小诊断范围。

但探针通过只能说明某些基础行为仍然正常，不能证明所有复杂任务都正常。因此，它们不能替代完整的能力回归测试。

## 6.2 比较变化前后的相同任务

如果怀疑模型行为发生变化，可以使用同一组固定任务，在不同时间、不同模型快照或不同配置下运行。

如果怀疑工具变化，可以在隔离环境中对比旧版与新版工具适配器。

如果怀疑上下文压缩策略，可以固定输入和模型配置，只替换上下文策略。

这种方法能够减少无关因素的干扰。

## 6.3 明确诊断置信度

我建议每项根因假设都记录：

- 支持证据。
- 反对证据。
- 尚未验证的条件。
- 当前判断的不确定性。
- 下一项最有价值的诊断实验。

不要让模型仅凭语言表达给出“95% 确信”之类的数字。置信度应该尽可能根据历史诊断准确率、实验结果或适当的统计方法进行校准。

当系统无法可靠区分原因时，应当选择风险更低的措施：保持旧版本、限制受影响功能、继续收集证据，或者请求用户介入。

# 七、环境变化必须进入能力图谱，但不能被当成能力版本

这一点需要与前面设计的版本体系衔接。

我建议给每次运行增加一个独立的环境快照引用。

例如：

```text
Task Run
├── capability_version
├── implementation_version
├── model_profile_version
├── tool_contract_version
├── runtime_environment_version
├── memory_policy_version
├── workflow_version
└── release_manifest_id
```

这并不意味着每次任务都要把所有环境信息复制一份。可以保存不可变的版本引用和必要的运行时摘要，再通过引用还原完整配置。

这样，当任务失败时，系统能够追溯当时的实际组合，而不是只知道“编程专家 v7 失败了”。

同时，我建议新增三类资产。

| 资产 | 职责 |
|---|---|
| `environment_profiles` | 描述模型服务、工具、系统、权限和运行环境 |
| `health_observations` | 保存探针结果、行为漂移指标和异常证据 |
| `diagnostic_cases` | 保存根因假设、诊断实验、判断依据和处理结果 |

还可以增加 `environment_change_events`，记录模型 API 更新、工具版本变化、权限变化和外部依赖异常等事件。

这些数据要与能力图谱关联，但不能直接修改能力成熟度。

例如，某工具在一次 API 更新后失效，系统可以将其标记为环境兼容性异常；只有进一步证实当前工具适配器确实需要修改，才创建相应的实现候选。

**环境健康状态、能力健康状态和发布成熟度必须分开管理。**

一个版本可能在原环境中非常成熟，但在新环境中暂时不兼容；这不意味着旧版本失去价值，只意味着它的适用范围需要被明确限定。

# 八、运行时健康监测应该关注哪些指标？

我不建议只记录成功率、失败率和模型费用。EvoAgent 需要能从不同层次观察自身运行。


    <title size="lg">系统与环境健康</title>
    API 可用率、网络错误、限流频率、工具服务状态、权限有效性、依赖版本变化。



    <title size="lg">Harness 运行健康</title>
    ReAct 循环异常退出、状态转换错误、工具调用参数校验失败、上下文超限、检查点恢复失败。



    <title size="lg">能力质量</title>
    任务成功率、关键约束遗漏率、结果验收失败率、重复执行率、人工干预率、不同任务难度下的表现。



    <title size="lg">资源效率</title>
    每个成功任务的模型成本、工具费用、调用次数、执行时长、重试成本，以及失败任务的资源浪费。



    <title size="lg">进化系统健康</title>
    诊断准确率、错误归因率、候选通过率、回归缺陷率、发布后回滚率、单位改进收益和实验预算消耗。


这些指标还需要具备明确的统计窗口、分组方式、阈值来源和处理动作。

例如，工具失败率连续升高，可以触发诊断；但不应该只因为一个短时间窗口中的随机波动，就立即认定系统退化。

对于关键安全事件，则不需要等待统计趋势。一次明确的权限越界或危险操作尝试，就可能足以触发即时停止。

因此，健康监测需要同时支持两种机制：

- **趋势检测：** 识别缓慢、持续或统计上显著的行为漂移。
- **事件触发：** 对权限违规、数据损坏、不可逆操作风险等立即响应。

## 九、一个具体案例：手机操作失败后，EvoAgent 应该怎样处理？

假设用户让 EvoAgent 打开某个 App，进入指定页面并完成一个操作。

任务失败后，系统记录了以下现象：

- 应用启动成功。
- 页面识别结果与预期不一致。
- 点击操作已发送。
- 目标状态没有出现。

正确的处理流程不是立即修改手机操作专家的提示词，而是：

  确认当前应用、页面和任务状态，避免重复点击。
  检查无障碍服务是否有效，必要时确认视觉识别结果是否与当前屏幕一致。
  检查目标控件是否存在、是否可点击，以及系统是否弹出了权限窗口或其他覆盖层。
  通过只读检查或安全测试判断，失败是否来自界面变化、工具适配器、操作策略或执行后的状态验证。
  如果只是页面结构变化，优先更新页面适配策略；如果是工具返回不准确，优先修复工具接口；只有证据指向规划或识别策略时，才创建能力改进候选。
  在安全环境中验证修复效果，再决定是否发布到手机操作专家的稳定版本。

这里有一个重要原则：**失败恢复与能力进化应该使用同一套证据，但拥有不同的决策权限。**

运行时负责当前任务的安全和恢复；进化系统负责经过验证的长期改进。前者不能因为想完成任务而绕过权限，后者不能因为发现失败就直接修改稳定版本。

# 十、V0.1 应该怎样落地？

我建议先实现最小的环境健康与诊断闭环，而不是一开始就建设复杂的异常检测平台。



      <title size="md">01</title>


      **统一运行事件**

      每次任务记录模型、工具、能力实现、工作流、环境版本和任务结果。





      <title size="md">02</title>


      **依赖健康检查**

      为模型 API、工具适配器、记忆检索和关键运行时组件提供健康检查与契约测试。





      <title size="md">03</title>


      **规则化异常分类**

      先识别明确的网络错误、限流、参数错误、接口不兼容、权限失效和结果验收失败。





      <title size="md">04</title>


      **竞争性根因诊断**

      对无法直接分类的异常，生成多个假设，选择低成本、低风险的诊断实验。





      <title size="md">05</title>


      **运行时恢复与进化分流**

      运行时采取经过批准的恢复动作；需要改变长期能力时，提交候选进入独立评测与发布流程。





      <title size="md">06</title>


      **健康状态与版本关联**

      记录异常发生时的环境快照、根因证据、处理动作和后续表现，为下一次诊断提供依据。



第一版验收可以很具体：人为模拟一次 API 超时、一次工具返回格式错误、一次上下文约束遗漏和一次权限失效，检查系统是否能够正确区分故障类型、避免危险重试、保留完整证据，并把需要长期修复的问题送入进化流程。

如果这四类案例都能按预期处理，就已经具备了环境与能力健康诊断的基本骨架。

# 十一、这一轮形成的架构结论

到这里，EvoAgent 的长期运行机制已经可以分成三个互相协作的系统：

- **运行时控制系统：** 完成任务、管理状态、执行工具、验证结果，并在异常时安全恢复。
- **健康诊断系统：** 检测环境变化、能力退化和依赖异常，收集证据并判断可能的根因。
- **后台进化系统：** 根据诊断结果提出候选、安排实验、评测改进、批准发布并监测长期收益。

它们共享统一的事件和证据体系，但不能互相取代职责。

尤其要保护稳定运行轨道：后台进化可以持续探索和提出修改，却不能直接把未经验证的候选注入正在执行的任务。

**我们追求的不是一个不断修改自己的智能体，而是一个能在环境变化时保持安全、在问题出现时正确诊断、在证据充分时持续改进的智能体。**

## 下一轮：我们应该深入“记忆系统”，还是“运行时控制系统”？

从目前的设计进度看，我建议下一轮优先研究 **EvoAgent 的记忆系统与上下文治理**。

原因是，记忆、上下文和 ReAct 规划几乎贯穿所有任务，也很容易成为跨领域的共同故障源：

- 记住了错误经验，可能反复犯同一种错误。
- 没有记住关键约束，可能导致任务失败。
- 检索了无关记忆，可能污染当前判断。
- 上下文压缩过度，可能丢失重要信息。
- 历史记忆与当前事实冲突，可能让模型继续使用过时信息。
- 模型切换后，原来的记忆组织和检索策略可能不再有效。

我们需要进一步区分长期知识、用户偏好、项目状态、任务检查点、运行经验和待验证假设，并决定它们分别如何存储、检索、更新、过期、隔离和参与进化。

这会把此前讨论的能力图谱、环境诊断、模型适配和独立进化机制进一步连接起来。
