**专项编号：** #77

**英文名称：** Regression Test Selection, Coverage Traceability & Evidence Governance

**文档版本：** 1.0

**所属体系：** EvoAgent 自进化智能体专项设计集

**关联专项：** #75 MTRC-CCR；#76 依赖图与变更影响传播治理

**设计状态：** 专项设计基线，实施与验收状态待实际验证

## 一、专项目标

建立统一的回归测试与证据治理体系，让 EvoAgent 每次修改模型配置、提示词、工具、专家、工作流、上下文策略或共享内核时，都能够确定：

1. 哪些测试必须执行；
2. 哪些测试可以根据可靠证据复用历史结果；
3. 测试是否真正覆盖了本次变更的影响范围；
4. 测试结果是否可信、可复现；
5. 新版本相对于稳定版本究竟改善了什么；
6. 哪些质量退化必须阻止发布；
7. 如何把真实运行中发现的故障转化为长期有效的回归案例。

本专项不以测试数量最少为目标，而是追求：

**在不削弱必要质量与安全门槛的前提下，用尽可能少的冗余测试，获得足以支持发布决策的验证证据。**

## 二、与 #75、#76 的关系

三项专项形成完整的验证链路。

| 专项 | 核心问题 | 产出 |
|---|---|---|
| #75 兼容性治理 | 当前组件组合是否兼容 | 兼容性判定和契约证据 |
| #76 变更影响治理 | 本次变更影响哪些资产 | 影响闭包、传播路径和候选测试范围 |
| #77 回归与证据治理 | 应执行哪些测试，结果是否足以支持发布 | 测试计划、覆盖记录、结果证据和验证报告 |

完整流程：

`变更事件 → #76 影响分析 → #75 兼容性检查 → #77 测试选择与执行 → 独立评测门禁 → 发布控制器`

这里的先后关系是逻辑依赖，不要求所有检查串行执行。对于互不依赖的检查，可以并行运行；但所有必需检查都完成之前，不能形成最终的发布通过结论。

本专项也不替代 Evaluation Gate Controller。它负责组织和记录验证证据，独立门禁负责依据不可由候选版本修改的规则作出准入判断。

## 三、测试体系分类

EvoAgent 需要覆盖从单个工具到完整用户任务的多个层级。

### 3.1 测试类型

| 类型 | 验证对象 | 示例 |
|---|---|---|
| 契约测试 | 接口与 Schema | 工具输入输出符合正式契约 |
| 单元测试 | 单个函数或模块 | 任务状态转换正确 |
| 组件集成测试 | 多个组件组合 | 模型适配器与工具网关协同 |
| 工作流测试 | DAG 与执行流程 | 失败节点能够安全恢复 |
| 专家回归测试 | 领域能力 | 编程专家正确识别代码问题 |
| 系统端到端测试 | 完整用户任务 | 从自然语言输入到真实成果交付 |
| 安全与权限测试 | 动作准入和边界 | 未授权的高风险动作被阻止 |
| 故障恢复测试 | 中断与异常 | 重启后任务状态正确恢复 |
| 兼容性测试 | 版本与环境组合 | App/Core/工具版本匹配 |
| 性能与成本测试 | 资源和效率 | 时延、调用次数和成本符合限制 |
| 对抗性测试 | 恶意或异常输入 | 越权指令、异常工具输出不会突破边界 |
| 隐藏回归测试 | 未公开的关键案例 | 防止候选只针对已知测试过拟合 |

测试可以覆盖多个类别，但每个测试必须有明确的主要用途、适用对象和验收断言。

### 3.2 两套测试集合

必须区分：

**强制测试集：** 包含关键安全、权限、数据完整性、任务状态机、副作用、预算和发布控制等必要测试。正式发布不能通过减少测试选择范围绕过这些检查。

**增量测试集：** 根据 #76 的影响分析，选择本次变更直接或间接影响的测试。

每次正式发布的实际测试范围是两者的合并，并补充由风险评估决定的测试。

## 四、统一测试用例契约

### 4.1 测试用例的基本结构

每个正式测试用例至少需要定义：

- `test_id`：稳定的测试标识；
- `version`：测试定义版本；
- `test_type`：测试类型；
- `target_refs`：被测资产及其版本；
- `dependency_refs`：相关依赖；
- `preconditions`：执行前置条件；
- `fixture_refs`：测试输入与数据引用；
- `assertions`：明确的通过条件；
- `risk_class`：相关风险等级；
- `timeout_seconds`：最长执行时间；
- `budget_ref`：测试资源预算；
- `environment_constraints`：适用环境；
- `privacy_level`：数据敏感级别；
- `determinism_policy`：可复现性要求；
- `evidence_requirements`：需要保存的证据；
- `owner_or_namespace`：责任域或所属专家。

这些字段是建议的逻辑契约。正式实现时应与现有评测集资产和数据 Schema 统一，避免重复定义同一字段。

### 4.2 测试断言必须具体

以下断言不充分：

- “回答看起来不错”；
- “任务基本完成”；
- “没有发现明显问题”。

应尽量转换为可以验证的条件，例如：

- 预期文件确实存在并可打开；
- 必需章节全部存在；
- 指定工具调用参数符合 Schema；
- 未授权时不存在外部副作用；
- 取消后没有新增受保护动作；
- 任务恢复后没有重复提交非幂等操作；
- 指定代码测试通过；
- 质量评分达到已批准的阈值。

对于无法完全自动判断的语义质量，可以采用结构化评分、独立模型评审、人工复核或多种证据组合，但必须记录评判方法及其局限。

## 五、测试覆盖追踪模型

仅统计测试数量或代码覆盖率，无法证明 EvoAgent 的任务能力得到了充分验证。

### 5.1 五层覆盖关系

每次正式变更都应能够建立以下关联：

1. **需求覆盖：** 本次变更影响哪些需求和验收条件？
2. **资产覆盖：** 哪些模型、工具、专家、工作流或共享内核组件受到影响？
3. **依赖覆盖：** 哪些直接与传递依赖已被检查？
4. **行为覆盖：** 哪些正常路径、异常路径、恢复路径和安全边界已被测试？
5. **证据覆盖：** 每个必需检查是否具有有效的实际执行结果？

例如，代码工具的输出 Schema 发生变化：

- 需求覆盖：代码分析结果仍需准确、结构合法；
- 资产覆盖：代码工具、分析工作流、编程专家；
- 依赖覆盖：工具适配器和相关工作流；
- 行为覆盖：正常解析、异常输入、工具超时、恢复执行；
- 证据覆盖：工具契约测试、工作流集成测试、领域回归测试的实际结果。

### 5.2 覆盖矩阵

系统需要维护“资产—测试”“依赖边—测试”“需求—断言”之间的显式关联。

| 被测对象 | 必要测试 | 覆盖状态 |
|---|---|---|
| 代码工具 | 输入输出契约测试 | 必须有有效证据 |
| 代码分析工作流 | 节点集成和恢复测试 | 必须有有效证据 |
| 编程专家 | 领域任务回归集 | 必须达到批准门槛 |
| 共享任务内核 | 状态机、预算、取消、安全测试 | 强制覆盖 |
| 发布控制器 | 门禁、签名、回滚测试 | 强制覆盖 |

每个覆盖项至少应标记为：

- 已覆盖且证据有效；
- 已执行但失败；
- 未执行；
- 不适用且有依据；
- 证据过期；
- 无法判定。

“不适用”必须有明确理由，不能作为规避测试的默认选项。

### 5.3 覆盖率的使用限制

代码行覆盖率、分支覆盖率和路径覆盖率可以帮助发现遗漏，但不能直接等价于任务成功率或产品质量。

建议分别统计：

- 必需测试执行覆盖率；
- 受影响资产覆盖率；
- 关键依赖边覆盖率；
- 必需验收断言覆盖率；
- 故障恢复场景覆盖率；
- 安全边界覆盖率；
- 端到端任务类型覆盖率。

这些指标应分别报告，不能合并成一个看似精确的综合百分比来掩盖缺失项。

## 六、回归测试选择算法

### 6.1 测试选择的输入

测试选择器接收：

- `change_id`；
- 变更前后的资产引用；
- #76 输出的影响分析报告；
- #75 输出的兼容性约束；
- 当前候选版本的 `Runtime Manifest`；
- 适用的测试集版本；
- 强制测试规则；
- 风险等级；
- 可用资源预算。

如果关键输入缺失，应将结果标记为不完整，而不是自动缩小测试范围。

### 6.2 测试集合计算

可以采用以下逻辑模型：

\[
T_{\text{required}} =
T_{\text{core}}
\cup T_{\text{direct}}
\cup T_{\text{transitive}}
\cup T_{\text{risk}}
\cup T_{\text{release}}
\]

其中：

- \(T_{\text{core}}\)：强制核心回归测试；
- \(T_{\text{direct}}\)：直接受影响资产的测试；
- \(T_{\text{transitive}}\)：传递受影响资产的测试；
- \(T_{\text{risk}}\)：根据风险增加的专项测试；
- \(T_{\text{release}}\)：当前发布渠道要求的测试。

计算后可以去重和优化执行顺序，但不能删除任何仍然必需的测试。

### 6.3 选择与排序

在所有必需测试确定后，系统可以根据以下因素排序：

1. 能够尽早发现严重故障的测试；
2. 运行成本低、诊断价值高的测试；
3. 关键接口和安全边界测试；
4. 直接受影响组件的集成测试；
5. 领域专家和完整工作流测试；
6. 完整端到端测试；
7. 资源消耗较高的压力测试和扩展评测。

排序只能改变执行顺序，不能把必需测试变成可选测试。

### 6.4 测试结果复用

历史测试结果只有满足以下条件，才能作为有效的复用证据：

- 被测资产版本匹配；
- 相关依赖版本匹配；
- 测试定义和断言版本匹配；
- 运行环境符合要求；
- 测试数据和配置符合当前条件；
- 结果仍在有效期内；
- 本次变更没有触发强制重新验证规则。

例如，模型配置、工具版本或执行适配器发生变化时，不能因为之前某个相似任务通过了测试，就直接宣称当前组合通过。

复用的是经过验证的证据，不是对新版本的未经验证的推断。

## 七、测试执行与结果状态

### 7.1 统一测试结果

建议采用以下结果状态：

| 状态 | 含义 | 是否可以满足必需测试 |
|---|---|---|
| `PASSED` | 所有规定断言通过 | 可以，前提是证据有效 |
| `FAILED` | 至少一个必要断言失败 | 不可以 |
| `BLOCKED` | 前置条件无法满足 | 不可以 |
| `NOT_RUN` | 尚未执行 | 不可以 |
| `FLAKY` | 多次执行结果不稳定 | 不可以直接视为通过 |
| `INVALID` | 测试本身或环境存在问题 | 不可以 |
| `INCONCLUSIVE` | 现有证据不足以判断 | 不可以 |
| `NOT_APPLICABLE` | 有依据地确认不适用 | 仅在规则允许且记录理由时适用 |

测试基础设施故障不能被解释为被测能力通过。

如果测试本身存在缺陷，应先修复或替换测试，再重新执行。修复测试定义必须产生新的可追踪版本。

### 7.2 不稳定测试处理

对于偶发失败的测试：

1. 记录每次运行的结果和环境；
2. 区分产品故障、环境故障与测试本身的不稳定；
3. 进行受限次数的复测；
4. 保留首次失败证据；
5. 必要时隔离该测试并启动修复流程；
6. 对涉及安全和数据完整性的测试，不得通过简单的重试成功就消除首次失败。

对于核心安全测试，不能仅因为重试后通过，就忽略首次失败所揭示的潜在风险。

### 7.3 测试执行资源治理

每个测试集应明确超时、并发、预算和停止条件。

如果预算不足以完成全部必需测试，候选版本应保持未验证状态，不能通过自动删除测试来取得通过结论。

系统可以暂停非关键的扩展实验，但必须优先保障正式发布所需的测试。

## 八、测试证据治理

### 8.1 什么才算有效证据

一次测试的执行状态不等于一份可信证据。

有效证据至少需要回答：

- 测试了什么；
- 使用哪个版本；
- 在什么环境下运行；
- 使用什么输入和配置；
- 实际执行了哪些断言；
- 得到了什么结果；
- 是否存在失败、跳过或警告；
- 结果由哪个测试器或评测器产生；
- 是否可以定位对应的日志和产物。

### 8.2 测试证据记录

建议为每次测试执行建立独立记录，包含：

- `test_run_id`；
- `test_id` 与测试定义版本；
- `change_id`；
- 被测资产及版本；
- `runtime_manifest_id`；
- 测试集引用及版本；
- 环境摘要；
- 输入数据引用；
- 随机种子或随机性策略；
- 执行开始和结束时间；
- 结果状态；
- 各项断言结果；
- 日志与产物引用；
- 时延和资源成本；
- 评测器版本；
- 失败原因；
- 证据完整性信息。

以上字段是本专项的逻辑扩展建议，实施时应与现有事件、资产和评测契约统一。

### 8.3 证据完整性

正式测试证据应关联不可变版本和可校验的内容摘要。

对于重要发布证据，可以增加签名、受控存储和权限隔离。

系统必须能够区分：

- 真实执行产生的结果；
- 模拟或 Mock 环境产生的结果；
- 人工审核产生的结果；
- 模型生成的分析结论。

Mock 测试可以用于验证协议和控制流，但不能替代真实供应商或真实设备能力的验证。

### 8.4 隐私与数据治理

测试数据应采用最小必要原则。

真实用户任务产生的失败案例，在进入回归集之前，需要检查授权、隐私等级、敏感数据和必要的脱敏要求。

测试证据不应默认保存完整的原始对话、文件或设备截图。可以使用受控引用、脱敏输入、摘要和可复现的合成样本替代不必要的原始数据。

## 九、质量基线与版本比较

### 9.1 比较对象

候选版本应当与明确指定的稳定基线比较，而不是与任意历史结果比较。

报告需要明确：

- 稳定基线的资产版本；
- 候选版本的资产版本；
- 测试集版本；
- 环境差异；
- 数据集差异；
- 运行次数；
- 质量、成本和时延的比较结果。

如果候选版本和稳定版本使用不同的模型或环境，应明确区分由环境变化和由代码或策略变化造成的影响。

### 9.2 不能只看平均分

假设一个候选版本提高了平均回答质量，但导致高风险动作的权限检查失效。

即使整体平均分提高，该版本仍然不能发布。

因此，门禁至少应分别检查：

- 核心任务成功率；
- 关键质量指标；
- 严重错误和安全违规；
- 恢复成功率；
- 兼容性；
- 成本和时延；
- 必需测试覆盖；
- 证据完整性。

关键安全失败不能被其他指标的改善抵消。

### 9.3 统计可靠性

对于具有随机性的模型任务，应设置适当的重复运行次数，并根据任务类型和样本规模判断结果的可靠程度。

不能将少量样本的微小提升直接宣称为稳定进步。

正式报告应区分：

- 观察到的提升；
- 统计上有足够证据支持的提升；
- 尚无法确定的变化；
- 明确退化。

## 十、失败案例转化为回归测试

这是 EvoAgent 持续进化的重要闭环。

### 10.1 从故障到测试

```text
真实任务失败
    ↓
保存必要的运行证据
    ↓
独立诊断故障原因
    ↓
形成失败案例候选
    ↓
脱敏与授权检查
    ↓
设计可复现输入和断言
    ↓
人工或自动审核测试质量
    ↓
加入候选回归集
    ↓
验证新测试能够识别目标故障
    ↓
纳入正式评测或隐藏回归集
```

不能把每一次失败直接加入正式测试集，否则会产生大量重复、低价值或不可复现的测试。

### 10.2 测试质量要求

每个新增回归案例必须说明：

- 它针对什么故障；
- 故障在什么条件下出现；
- 什么结果代表再次出现同类问题；
- 什么结果代表问题得到修复；
- 是否会误报正常行为；
- 该案例适用于哪些资产与版本。

### 10.3 防止测试过拟合

对于关键领域和高风险行为，可以维护受保护的隐藏回归集。

候选优化器可以获取必要的失败类别和评测反馈，但不应拥有修改隐藏测试、删除失败记录或调整发布阈值的权限。

一次成功的轨迹可以成为新的测试素材，但不能直接证明该行为已经形成可靠能力。

## 十一、独立发布门禁

### 11.1 门禁输入

发布门禁需要接收：

- 变更影响报告；
- 兼容性判定；
- 必需测试计划；
- 实际测试结果；
- 测试覆盖报告；
- 证据完整性检查；
- 与稳定基线的对比报告；
- 风险和回滚信息。

### 11.2 发布判定

建议将候选结果分为：

- `PASS`：所有必要门槛满足；
- `FAIL`：发现明确的门槛失败；
- `BLOCKED`：存在未满足的前置条件；
- `INCONCLUSIVE`：证据不足以作出可靠判断。

只有 `PASS` 才允许进入正式晋级流程。

其他状态均不能被解释为发布通过。

### 11.3 门禁不可被候选修改

候选版本不得自行：

- 删除必需测试；
- 降低安全阈值；
- 修改隐藏回归集；
- 伪造测试结果；
- 将失败状态改成通过；
- 更换基线以掩盖退化；
- 在证据缺失时强制晋级。

测试集维护、评测规则变更和发布审批必须具有独立的权限边界与审计记录。

## 十二、测试报告与可观测性

每次候选验证结束后，系统应生成统一的评测报告。

报告至少包括：

1. 候选版本与稳定基线；
2. 本次变更摘要；
3. 影响资产与传播路径；
4. 计划执行的测试及其状态；
5. 未执行或不适用的测试及原因；
6. 必需覆盖率；
7. 失败案例和严重程度；
8. 质量、成本、时延比较；
9. 兼容性与安全结论；
10. 证据完整性；
11. 发布建议；
12. 回滚目标。

报告应当同时服务于技术诊断和产品治理，但不应把未经验证的内部推断展示为已确认的故障原因。

## 十三、核心验收测试矩阵

| 测试 ID | 场景 | 通过条件 |
|---|---|---|
| EVAL-01 | 修改单个工具 | 自动选出直接契约与集成测试 |
| EVAL-02 | 修改被多个专家共享的工具 | 覆盖所有相关专家和工作流 |
| EVAL-03 | 共享内核发生变更 | 必需核心回归集不能被省略 |
| EVAL-04 | 存在旧版本测试结果 | 不把不匹配的旧证据作为新版本通过依据 |
| EVAL-05 | 必需测试失败 | 门禁拒绝晋级 |
| EVAL-06 | 必需测试未执行 | 候选保持未验证状态 |
| EVAL-07 | 测试环境异常 | 结果标记为阻塞或无效，而非通过 |
| EVAL-08 | 测试出现偶发失败 | 保留失败证据并进入不稳定性处理 |
| EVAL-09 | 候选平均分提高但存在严重安全失败 | 仍然拒绝晋级 |
| EVAL-10 | 新增失败案例 | 能够追溯到原始故障和正式断言 |
| EVAL-11 | 候选尝试修改评测阈值 | 修改被权限边界阻止 |
| EVAL-12 | 测试证据缺失 | 不能形成完整的发布通过报告 |
| EVAL-13 | Mock 测试通过但真实能力未验证 | 不宣称真实环境能力已通过 |
| EVAL-14 | 运行结果来自不同环境 | 报告环境差异并限制不恰当的直接比较 |
| EVAL-15 | 预算不足 | 停止扩展实验，不删除必需测试 |
| EVAL-16 | 评测通过后发布失败 | 稳定版本保持不变，保留完整诊断记录 |
| EVAL-17 | 发布后发生质量退化 | 触发监控、暂停或回滚策略 |
| EVAL-18 | 隐藏回归测试发现退化 | 候选不得晋级 |

所有用例都必须在实际测试环境中执行并保存结果。本文中的验收矩阵是待执行规范，不代表测试已经通过。

## 十四、性能、成本与执行效率

测试治理必须本身可控，不能因为不断扩展回归集而使进化成本无限增长。

建议采用以下措施：

- 先执行高诊断价值的轻量测试；
- 根据 #76 的影响范围进行增量测试；
- 并行执行相互独立的测试；
- 复用满足版本和环境条件的有效证据；
- 对长时间运行的测试设置明确超时；
- 为每次候选评测设置资源预算；
- 将扩展探索实验与正式发布测试分离；
- 保留核心安全测试的固定执行要求。

当资源不足时，系统可以延迟非必要探索实验，但不能通过缩小强制测试范围来制造发布通过结果。

## 十五、实施交付清单

本专项需要形成以下正式交付物：

1. 统一测试用例契约；
2. 测试集分类与生命周期规范；
3. 资产、依赖、需求和测试的覆盖关联表；
4. 增量回归测试选择算法；
5. 测试执行与状态管理规范；
6. 测试证据记录和完整性校验规范；
7. 稳定基线与候选版本对比报告；
8. 失败案例转回归测试的流程；
9. 独立发布门禁规则；
10. 核心验收测试矩阵；
11. 测试预算与执行效率治理；
12. 与 #75、#76、Evaluation Gate Controller 和 Release Controller 的接口映射。

## 十六、完成判定

只有满足以下条件，才能认为 #77 的实施验收完成：

- 所有正式能力都有可追踪的必要测试；
- 变更影响分析能够映射到实际测试集合；
- 测试选择不会跳过强制安全和核心回归集；
- 测试结果与实际资产版本、运行环境和测试定义关联；
- 不稳定、阻塞和无效结果不会被当作通过；
- 关键发布证据能够复现或独立核验；
- 新增失败案例能够经过审核进入回归体系；
- 候选不能修改自己的发布门槛；
- 发布报告能够解释质量、成本、兼容性和安全结论；
- 所有正式验收测试均有真实执行记录。

**最终目标：让 EvoAgent 每次进化都不仅能够说明“改了什么”，还能够证明“测了什么、覆盖了什么、改善了什么，以及为什么允许发布”。**</WritingBlock>

## 下一步：专项 #78

建议继续推进 **#78：候选改进对照实验与收益归因治理**。

#77 解决“测试是否充分、证据是否可信”；#78 将进一步解决一个更难的问题：

**即使候选版本通过所有测试，我们如何证明它确实比稳定版本更好？**

例如，某次提示词优化让回答速度提升了 15%，但任务成功率下降了 3%；另一次工具优化只提高了少数任务的质量，却让成本大幅上升。系统需要在统一基线、可控实验和多维指标下，区分真实收益、随机波动、环境变化和副作用，避免把“测试通过”误认为“进化成功”。

这将把 #75—#78 串成完整的治理链路：兼容性、影响分析、回归证据，再到真实收益验证。
