# EvoAgent 第二十八专项：上下文工程与推理治理

这一轮要深入研究 EvoAgent 的核心问题之一：**如何让模型在每个决策时刻，获得恰好足够、真正相关、可信且不会互相冲突的信息。**

前面已经设计了记忆系统、上下文压缩、专家系统、Planner、ReAct、任务 DAG、工具运行时和经验进化。现在需要把它们连接起来。

这里有一个重要判断：

**上下文不是记忆的简单拼接，也不是聊天历史的压缩版。上下文是一份针对当前决策构建的、受预算约束的执行信息视图。**

同一条信息，在不同任务、不同专家和不同执行阶段，可能具有完全不同的价值。

例如，一个编程任务在制定计划时，需要项目架构、用户约束和修改目标；执行具体代码编辑时，需要目标文件、相关符号、当前节点输入和修改约束；验证阶段，则需要测试结果、预期行为和验收标准。

如果每个阶段都注入全部历史，不仅浪费 Token，还可能让真正重要的信息被大量无关内容淹没。

本专项建议定义为：

**Context Engineering & Reasoning Governance，简称 CERG。**

它负责上下文构建、信息排序、压缩、预算分配、阶段切换、推理证据管理和上下文质量评测。

## 一、第一性原理：模型的上下文是工作台，不是仓库

我们可以把 EvoAgent 的信息体系分成三个层次。


    <title size="md">第一层：持久知识与历史</title>
    记忆、项目文档、历史任务、工具结果、经验库、正式策略和审计记录。它们可以长期存在，但不应该全部进入每次模型调用。



    <title size="md">第二层：任务工作状态</title>
    当前目标、已确认事实、任务 DAG、节点状态、待解决问题、预算、约束、验收标准和恢复检查点。



    <title size="md">第三层：本次决策上下文</title>
    针对当前模型调用，从规则、任务状态、记忆和工具结果中选出的最小充分信息，以及当前需要完成的具体决策。


三层之间的关系是：

- 持久知识提供可检索的信息；
- 任务工作状态提供当前执行事实；
- 上下文构建器决定本次调用实际需要看到什么。

这三个层次不能混淆。

例如，记忆库里保存了 100 条编程经验，不意味着编程专家每次调用模型都应该看到这 100 条。它应该先识别当前任务，再检索和筛选真正适用的经验。

同样，聊天历史中出现过某个结论，不意味着该结论已经被验证。上下文系统必须保留信息的来源和可信状态，不能把历史文字自动升级为事实。

# 二、建立上下文信息分类：模型到底需要哪些信息？

建议将上下文划分为九类，每一类拥有不同的优先级、来源和更新规则。

| 类别 | 内容示例 | 主要处理方式 |
|---|---|---|
| C1 · 安全与授权 | 权限边界、禁止操作、有效授权 | 由受控策略注入，不能被普通记忆覆盖 |
| C2 · 当前用户目标 | 当前请求、明确约束、成功标准 | 保留原始依据与当前有效解释 |
| C3 · 任务状态 | 当前节点、依赖、已完成步骤、剩余预算 | 从权威状态源获取 |
| C4 · 项目与环境事实 | 文件结构、依赖版本、配置、运行环境 | 按需查询并注明版本或时间 |
| C5 · 领域知识与经验 | 专家知识、经过验证的策略、候选经验 | 按任务匹配度与证据质量检索 |
| C6 · 工具能力与结果 | 可用工具 Schema、实际输出、错误信息 | 只提供当前决策需要的部分 |
| C7 · 历史交互与决策 | 已确认的讨论、用户反馈、历史选择 | 经过摘要、来源核验和时效过滤 |
| C8 · 计划与中间产物 | 当前计划、局部分析、候选方案 | 按阶段维护，避免无条件累积 |
| C9 · 验收与恢复信息 | 验收标准、失败原因、检查点、未决状态 | 在验证和恢复阶段重点保留 |

这九类不是九段必须固定出现的提示词。它们是上下文引擎内部的信息分类。

实际组装时，某次调用可能只需要其中四五类；另一种调用可能需要更多。

最重要的是，**信息是否进入上下文，应该由当前任务和决策需求决定，而不是由它是否曾经出现在历史记录中决定。**

# 三、动态上下文构建：每次模型调用都应该重新判断需要什么

我建议建立一个独立的 **Context Builder（上下文构建器）**。

它不直接保存所有记忆，也不负责决定任务目标。它根据当前调用的类型、任务状态和预算，从多个信息源构建一份有明确结构的上下文。

这里有一个细节：上下文构建不是每次都要重新进行昂贵的全量检索。

## 3.2 不同决策类型使用不同上下文模板


    **意图理解上下文**

    当前用户表达、必要的对话上下文、相关用户偏好、候选意图和歧义信息。



    **计划制定上下文**

    任务目标、硬性约束、环境事实、可用能力、预算、依赖关系和验收标准。



    **工具执行上下文**

    当前节点指令、必要输入、工具契约、权限边界、预期输出和失败处理条件。



    **故障诊断上下文**

    失败证据、执行轨迹、实际与预期结果、最近相关变更、已尝试方案和未证实的假设。



    **验收上下文**

    用户目标、可验证验收条件、实际产物、测试结果和未解决的问题。



    **任务恢复上下文**

    权威任务状态、检查点、已发生的副作用、外部操作状态、剩余预算和下一安全动作。


这比让所有调用共享同一个巨大提示词更容易控制成本，也更容易进行针对性评测。

# 四、上下文压缩：不是缩短文字，而是保护决策所需的信息

你之前专门问过上下文压缩是不是全局公用的。这里需要进一步明确。

我的建议是：

**上下文压缩的基础机制可以全局复用，但压缩策略、保留规则和验收标准必须支持按专家、任务类型和执行阶段配置。**

原因是不同任务丢失信息的代价完全不同。

- 编程任务可能不能丢失文件路径、函数签名、错误栈和依赖关系。
- 漫剧任务可能不能丢失角色设定、镜头约束、素材版本和音画同步要求。
- 研究任务可能不能丢失来源、证据、时间和不确定性。
- 手机操作任务可能不能丢失当前页面状态、已执行动作和用户授权边界。
- 任务恢复不能丢失已经发生的副作用、外部操作状态和检查点。

因此，不能采用一个统一的“保留最近 N 条消息”规则解决所有场景。

## 4.1 建立四级压缩机制


    <title size="md">L0 · 原始记录保留</title>
    原始对话、工具结果、执行事件和关键证据按各自的保留策略存储。压缩上下文不能替代这些记录。



    <title size="md">L1 · 局部摘要</title>
    对某一阶段、工具输出或对话片段进行摘要，保留重要事实、结论、未决问题和证据引用。



    <title size="md">L2 · 任务状态压缩</title>
    将长任务整理为当前目标、硬约束、已完成事项、剩余工作、风险、检查点和下一步。



    <title size="md">L3 · 决策专用上下文</title>
    针对当前模型调用，从原始记录、摘要和权威状态中重建最小充分上下文。


这里的 L0–L3 是逻辑层次，不代表四份内容必须重复保存。

原始记录负责可追溯，摘要负责降低读取成本，任务状态负责恢复执行，决策上下文负责当前推理。

## 4.2 压缩时哪些信息不能轻易丢失？

建议定义一组通用的“关键事实保护规则”：

1. 用户明确的目标与硬性约束；
2. 有效的权限与预算边界；
3. 已核验的任务和节点状态；
4. 已发生或结果未知的外部副作用；
5. 关键错误信息与验收证据；
6. 未解决的矛盾和不确定性；
7. 重要产物、版本和来源引用；
8. 当前检查点与可恢复条件。

这些信息应当结构化保留，而不是仅希望模型在摘要中“尽量记住”。

例如，任务取消后外部视频生成状态仍未知，这个状态不能在摘要中被简化为“视频生成失败”。前者意味着需要对账，后者可能导致系统错误地重复提交生成请求。

## 4.3 压缩结果必须经过验证

建议在压缩后执行一组检查：

- 目标是否保留；
- 硬约束是否完整；
- 已完成和未完成事项是否区分；
- 事实与假设是否混淆；
- 失败证据是否仍可追溯；
- 关键数字、路径、版本是否改变；
- 是否错误地把未知状态变成确定结论；
- 是否产生新的矛盾。

对于高风险恢复任务，关键状态应直接从权威状态库重新读取，不应只依赖模型生成的摘要。

**摘要是导航材料，不是权威状态的替代品。**

# 五、Token 预算：如何控制成本，而不是靠无限增加上下文解决问题？

这与你之前强调的要求直接相关：真正提升能力很重要，可以适当增加模型调用成本，但成本不能无限膨胀。

上下文系统必须将 Token 视为一种受预算约束的资源，而不是越多越好。

## 5.1 建立多级预算

我建议同时设置四级预算。

| 预算层级 | 控制内容 |
|---|---|
| 全局预算 | 系统在指定周期内允许用于推理、诊断、评测和进化的总资源 |
| 任务预算 | 单个任务允许使用的模型调用量、费用和时间 |
| 阶段预算 | 规划、执行、诊断、验收等阶段的资源分配 |
| 单次调用预算 | 本次输入 Token、预留输出 Token、模型上下文限制和费用 |

预算应由统一的资源与预算管理机制管理。上下文引擎负责在预算内组织信息，但不能自行提高任务预算。

## 5.2 按决策价值分配上下文

假设一次模型调用有 12,000 Token 的输入预算，这不意味着系统应该尽量填满它。

更合理的做法是先确保必须保留的信息完整，再为其他信息分配剩余空间。



      **安全、授权与硬约束**
      最高优先级

    确保当前决策不越过任务约束与权限边界。




      **当前目标与权威状态**
      必需信息

    保证模型知道要做什么、已经完成什么，以及哪些事项仍未解决。




      **当前决策所需证据**
      按需分配

    提供相关文件、工具结果、诊断证据和领域知识。




      **历史背景与补充知识**
      剩余预算

    只在能够改善当前决策时加入，避免无关历史挤占有效证据。


这里不建议预先为每一类固定分配百分比。任务复杂度、模型能力、上下文窗口和决策风险差异很大，固定比例容易造成某类信息不足、另一类信息浪费。

## 5.3 超预算时应该怎样降级？

我建议采用明确的降级顺序：

1. 删除重复的历史说明；
2. 用可追溯的摘要替代低价值原文；
3. 只保留当前节点需要的工具输出；
4. 将大型日志、代码和媒体信息放在外部产物中，按需读取；
5. 缩小候选经验的检索范围；
6. 将复杂任务拆成多个具有明确输入输出的阶段；
7. 必要时切换到经过验证的低成本策略；
8. 如果关键约束、证据或安全信息仍无法完整保留，就暂停、重新规划或请求用户决定。

最后一步很重要：不能为了满足 Token 预算而删除必要约束，然后假装任务仍然可以安全执行。

## 5.4 什么时候值得调用更强模型？

上下文预算与模型路由应该协作。

对于简单、低风险、结构明确的任务，轻量模型加上可靠工具可能已经足够。

对于复杂诊断、跨文件重构、长期规划或互相冲突的证据，可以考虑使用更强模型。

但模型升级应该基于任务难度、错误风险、预期收益和剩余预算，而不是因为上下文很长就自动升级。

有时真正的解决办法是改善上下文质量，而不是增加模型推理成本。

# 六、上下文与专家架构：共享引擎，但不共享全部策略

这一点与你之前确定的多专家设计完全一致。

EvoAgent 的通用内核应该提供统一的上下文基础设施，但领域专家应当能够定义自己的信息需求和压缩策略。

## 6.1 全局共享什么？

建议共享以下机制：

- Token 计量；
- 上下文构建接口；
- 来源与可信度标记；
- 预算检查；
- 版本和快照记录；
- 通用去重机制；
- 结构化摘要框架；
- 不可信内容标记；
- 压缩前后差异检查；
- 基础上下文质量评测接口。

这些是基础设施，不需要每个专家重新实现。

## 6.2 专家独立配置什么？


    **编程专家**

    优先保留代码路径、符号关系、接口契约、错误栈、依赖版本、修改范围和测试结果。



    **旅游专家**

    优先保留用户当前约束、日期、地点、预算、交通条件、预约状态和信息时效。



    **漫剧专家**

    优先保留角色设定、分镜关系、素材版本、镜头时长、配音状态、生成预算和验收标准。



    **手机操作专家**

    优先保留当前设备与页面状态、已执行动作、授权范围、操作结果和恢复条件。



    **研究专家**

    优先保留来源、发布日期、原始证据、结论依据、矛盾信息和不确定性。


这些是各领域的上下文策略示例，不是所有任务都必须使用的固定模板。

## 6.3 专家可以优化自己的上下文策略吗？

可以，但必须通过受控进化流程。

例如，编程专家发现保留调用关系摘要比重复注入所有源代码更有效，可以提出候选策略。

然后通过代表性任务比较：

- 验收通过率；
- 关键事实遗漏率；
- Token 消耗；
- 推理延迟；
- 失败恢复成功率；
- 跨任务退化。

只有候选策略在适用范围内获得足够证据，才允许发布。

即使某个专家的策略经过验证，也不应该直接修改全局上下文引擎。全局引擎的改动需要更广泛的跨专家回归测试。

# 七、上下文与 Planner、ReAct、DAG 的关系

这几个概念必须明确分工，否则容易出现重复规划、重复记忆和重复压缩。

## 7.1 Planner：负责计划，不负责无限保存历史

Planner 需要获得足够的信息来确定：

- 任务目标；
- 约束；
- 子任务划分；
- 依赖关系；
- 所需能力；
- 验收标准；
- 风险与预算。

Planner 产生的计划应当以结构化任务资产保存，而不是每次重新从聊天历史中生成。

当任务状态变化时，可以对计划进行局部修订，并记录修改原因与版本。

## 7.2 DAG：负责执行状态和依赖关系

DAG 节点应当定义明确的输入、输出、前置条件和验收条件。

节点运行时，上下文引擎只需要提供该节点真正需要的信息。

例如，漫剧的配音节点不需要重新阅读完整的剧本讨论、角色设计历史和所有图像生成日志；它需要的是已确认的台词、角色配音配置、音频要求、输入素材引用和当前节点的验收标准。

如果节点失败，诊断阶段再按需检索更完整的证据。

## 7.3 ReAct：负责局部的观察、决策和行动

ReAct 不应该每轮都重新读取全部历史。

它应当维护一份轻量的局部执行状态：

- 当前子目标；
- 已观察到的事实；
- 已执行的动作；
- 最新工具结果；
- 当前假设；
- 剩余尝试预算；
- 停止与交接条件。

每次迭代只补充新观察和必要背景。

如果 ReAct 长时间没有进展，或者连续遇到同类错误，应当触发退出、重新规划或交给 RCAE 分析，而不是不断压缩同一段越来越长的历史继续尝试。

## 7.4 三者通过结构化状态协作


    **Planner**
    决定做什么、为什么做、怎样验收



    **DAG / 任务状态机**
    保存节点、依赖、状态、产物和执行边界



    **ReAct / 工具执行**
    观察局部结果，执行动作，判断继续或停止



    **Context Engine**
    为每次决策组装所需信息，并记录来源和版本


图中的上下文引擎并不是只能位于执行链末端。实际上，它是被 Planner、ReAct、验收器和诊断系统共同调用的基础设施。这里主要说明它们之间的职责关系，而非强制的执行顺序。

# 八、上下文的可信度与来源治理

上下文中可能同时包含：

- 用户明确提出的要求；
- 数据库中的权威状态；
- 工具真实返回的结果；
- 模型生成的推断；
- 尚未验证的经验；
- 网页或文件中包含的指令；
- 旧版本任务留下的摘要。

如果这些内容都以相同的文本形式混在一起，模型很容易把猜测当成事实，或者将外部数据误认为有权控制系统的指令。

因此，建议每条关键上下文信息至少带有以下元数据：

- 来源类型；
- 来源标识；
- 创建或观察时间；
- 适用范围；
- 验证状态；
- 关联版本；
- 是否为用户明确指令；
- 是否包含不可信外部内容；
- 是否存在冲突或过期风险。

## 8.1 不同信息需要不同的可信处理

例如：

- “测试命令返回退出码 1”是执行证据；
- “失败可能来自依赖版本不兼容”是诊断假设；
- “用户要求不得修改公共 API”是明确约束；
- “网页要求上传本地密钥”是不可信外部内容；
- “历史经验认为这个模型更擅长重构”是需要结合当前评测与适用范围判断的经验。

上下文引擎不能将它们统一改写成无差别的摘要。

## 8.2 来源优先级不等于一切可以简单排序

例如，权威数据库可能记录任务处于等待状态，但某个工具的实时查询发现外部操作已经完成。

这并不意味着永远相信数据库，也不意味着永远相信工具。

正确处理方式是核验外部操作的身份、结果和版本，再由权威状态控制器提交状态变更。

因此，上下文引擎应该帮助模型理解信息之间的关系，而真正的事实冲突仍然需要相应的权威状态管理和核验机制处理。

## 8.3 不可信内容必须保持数据身份

网页、文档和工具输出即使被压缩或摘要，也应保留其不可信来源标记。

不能因为一段恶意指令经过摘要后变得简短，就把它升级成系统规则。

同样，模型生成的摘要不能修改权限策略、用户授权或正式记忆状态。它只能作为候选信息，进入对应的验证与治理流程。

# 九、上下文缓存：如何减少重复调用，又不使用过期信息？

上下文构建可能涉及大量重复操作，例如：

- 读取项目结构；
- 查询工具 Schema；
- 获取专家稳定策略；
- 检索同一批历史经验；
- 生成大型文件的摘要；
- 解析相同的日志。

如果每次调用都重新执行这些操作，成本会持续上升。

但如果缓存失效管理不当，又可能导致模型使用旧文件、旧权限、旧策略或错误任务状态。

因此，我建议采用分层缓存。

| 缓存对象 | 建议策略 |
|---|---|
| 工具 Schema 与稳定配置 | 绑定版本，版本变化时失效 |
| 项目结构摘要 | 绑定文件版本或内容哈希，相关文件变化时重建 |
| 检索结果 | 绑定查询条件、命名空间、索引版本与适用范围 |
| 历史记录摘要 | 保留来源引用与摘要版本，原始记录仍可追溯 |
| 任务状态 | 以权威状态源为准，不能只依赖长期缓存 |
| 权限与授权 | 执行前核验当前有效状态，不依赖可能过期的上下文副本 |
| 外部服务状态 | 根据时效要求重新查询，必要时进行对账 |

缓存的目标是避免重复计算，而不是取代真实状态。

另外，模型服务端可能具有自己的提示词前缀缓存或 Token 缓存机制。EvoAgent 可以在不改变正确性的前提下优化请求前缀和复用策略，但不能假定所有模型、供应商或本地推理引擎都支持相同的缓存能力。

# 十、如何评估上下文策略是否真的有效？

这是 CERG 能否参与自进化的关键。

上下文策略不能只靠模型自己说“现在信息更充分了”来判断，也不能因为 Token 减少就认定优化成功。

我建议从五个维度评估。

## 10.1 必须采用对照实验

例如，编程专家有两种上下文策略：

- 策略 A：注入最近 30 条对话和完整工具日志；
- 策略 B：注入当前任务状态、相关代码片段、关键证据和必要历史摘要。

不能仅仅因为策略 B 的 Token 少了 40%，就认为它更好。

需要在相同或可比较的任务集上评估：

- 最终任务质量是否保持；
- 关键约束是否更少遗漏；
- 工具调用是否更加准确；
- 失败后是否更容易恢复；
- 总成本是否真正下降。

最好同时测试简单任务、复杂任务、边界案例和故障恢复场景。

## 10.2 区分上下文问题与模型能力问题

假设编程专家没有发现一个关键依赖关系，可能有多种原因：

1. 上下文根本没有包含该信息；
2. 检索系统没有找到相关文件；
3. 压缩时错误地删除了依赖信息；
4. 信息存在，但组织方式不清晰；
5. 模型看到了信息，却没有正确推理；
6. 工具本身没有提供完整证据。

如果直接归因于模型推理能力不足，就可能通过升级模型增加成本，却没有解决真正的问题。

因此，评测应该记录上下文构建过程，并在失败后能够回溯：必要信息是否存在、来源是否正确、压缩是否丢失、模型是否使用了它。

## 10.3 上下文改进也要通过受控发布

建议采用以下流程：

1. 从真实失败或成本异常中提出上下文改进假设；
2. 选择具有代表性的任务集；
3. 固定其他主要变量；
4. 比较候选策略和稳定策略；
5. 检查质量、遗漏率、成本和恢复效果；
6. 通过治理门槛后在指定专家或任务类型中灰度发布；
7. 持续监测并保留回滚版本。

如果一个改进只对编程任务有效，就先发布到编程专家，而不是直接推广到所有专家。

如果它降低 Token，却显著增加恢复失败率，则不应该仅凭成本收益通过发布。

# 十二、下一专项：模型路由、模型协作与推理成本治理

上下文工程解决了“给模型什么信息”，但还有一个紧密相关的问题：

**面对不同难度、不同风险、不同成本的任务，EvoAgent 应该调用哪个模型，调用几次，是否需要多个模型协作，以及什么时候应该停止继续推理？**

这与之前讨论的专家路由不同。

专家路由决定由哪个领域专家负责；模型路由决定这个专家在具体阶段使用什么模型和推理资源。

例如，同一个编程专家：

- 理解一个简单需求，可能只需要低成本模型；
- 规划跨文件重构，可能需要更强的推理能力；
- 运行 AST 分析、静态检查和测试时，可能不需要调用模型；
- 遇到难以解释的故障时，可以升级模型进行根因分析；
- 验收高风险修改时，需要独立的验证机制，而不是让生成答案的模型简单地自我确认。

因此，模型路由不能只是根据任务名称选择模型，也不能把所有困难任务都交给最贵的模型。

下一专项建议定义为：

**Model Routing, Collaboration & Reasoning Budget Governance，简称 MRCRG。**

重点研究：

1. 如何区分专家路由、任务路由、工具路由和模型路由；
2. 如何根据任务难度、风险、上下文规模和历史表现选择模型；
3. 如何判断当前模型已经足够，避免不必要的模型升级；
4. 如何设计低成本模型到高能力模型的逐级升级机制；
5. 如何决定哪些任务应该使用模型推理，哪些应交给确定性工具；
6. 如何判断多模型协作是否真的比单模型更有价值；
7. 如何防止多个模型互相重复推理、重复检查，却没有增加有效证据；
8. 如何管理输入 Token、输出 Token、调用次数、延迟和总任务预算；
9. 如何评估模型路由的准确性，并通过真实任务结果持续改进；
10. 如何在本地模型、云端模型和离线环境之间进行受控切换；
11. 如何处理模型版本升级、服务限流、故障和输出格式不兼容；
12. 如何为诊断、执行、验收和进化任务设置不同的模型策略。

这一专项将把 EvoAgent 的智能资源分配补齐：不仅知道应该由哪个专家处理任务，还知道该专家在每个执行阶段应当调用什么能力、使用多少推理资源，以及何时继续、升级或停止。

核心目标仍然是你最初强调的方向：**真正提高任务质量、执行效率和稳定性，同时让成本增长始终受到明确控制。**
