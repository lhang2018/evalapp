## 一、专项目标

建立一套统一的任务调度与自主执行治理体系，使 EvoAgent 能够在完成当前用户任务的同时，有选择地推进长期目标、执行已授权的维护工作，并处理经过评估的主动帮助机会。

系统需要回答：

1. 多个任务同时存在时，应该先做什么？
2. 用户当前明确要求的任务与后台长期目标冲突时，如何仲裁？
3. 如何判断一个主动发现的机会值得执行，还是只需要提供建议？
4. 如何避免主动任务不断创建子任务，最终陷入无限扩张？
5. 如何限制模型调用成本、并发数量、运行时间和外部服务消耗？
6. 后台任务遇到故障、断网、设备关机或权限变化时，如何安全恢复？
7. 如何避免同一个任务在手机、电脑和服务器上重复执行？
8. 如何判断任务真正推进了长期目标，而不是只生成更多计划？
9. 如何暂停、取消、恢复和审计自主执行？
10. 如何在提高自主程度的同时，始终保证任务质量、效率、稳定性和用户控制权？

本专项的核心原则是：

**自主性不是让系统尽可能多地执行任务，而是让系统能够正确选择值得执行的任务，并在有限资源、明确授权和可验证结果的约束下把它们完成。**

## 二、总体架构

### 2.1 六个逻辑组件

| 组件 | 核心职责 |
|---|---|
| Goal Orchestrator | 管理长期目标、目标依赖、阶段进展和完成条件 |
| Task Admission Controller | 判断新任务是否值得进入调度系统 |
| Priority Scheduler | 在当前任务、长期目标、维护任务和主动机会之间进行优先级仲裁 |
| Resource & Budget Manager | 管理预算、并发、运行时间和设备资源 |
| Execution Coordinator | 将获准任务分配给适合的设备和执行器 |
| Completion & Progress Verifier | 验证实际结果、目标进展和停止条件 |

这些是逻辑职责，可以复用现有共享内核、DAG 调度器、执行控制器、预算系统和验证器，不要求新增六个独立服务。

### 2.2 总体流程

```text
用户任务 / 已批准计划 / 主动发现的机会
                    ↓
              目标关联与去重
                    ↓
              任务准入检查
                    ↓
        目标、授权、预算、风险校验
                    ↓
              优先级仲裁
                    ↓
              依赖关系检查
                    ↓
              资源与设备分配
                    ↓
              执行与运行监控
                    ↓
              验收与进展验证
                    ↓
      完成 / 暂停 / 恢复 / 失败 / 取消
                    ↓
         更新 Goal 与用户可见状态
                    ↓
             评估实际价值
```

新任务并不必然进入执行队列。系统可以拒绝、合并、延后或仅向用户提出候选任务。

## 三、统一目标与任务管理

### 3.1 复用现有 Goal 与 Task

现有正式契约已经区分长期目标与具体任务，并为任务提供 `origin`、`goal_id`、验收契约、风险等级、授权引用、预算引用、执行状态和幂等键。

本专项应复用这些字段，不重新定义第二套目标和任务身份。

目标与任务的关系如下：

- 一个 Goal 可以关联多个 Task；
- 一个 Task 可以推进一个主要 Goal；
- 一个 Goal 可以包含多个阶段和依赖任务；
- 一个 Task 失败，不代表整个 Goal 失败；
- 一个 Goal 暂停，不意味着已经完成的 Task 需要重新执行；
- 一个任务成功，只有在其结果确实满足目标条件时，才应计入长期目标进展。

### 3.2 目标与任务分离

例如，长期目标是“完成 EvoAgent Android 个人智能体”。

该目标可以分解为：

- 完成权限管理；
- 实现语音输入；
- 完成工具调用；
- 实现状态验证；
- 完成离线恢复；
- 通过端到端测试。

每个子任务有自己的验收条件、预算、依赖关系和失败恢复策略。

不能将“生成了六份设计文档”直接视为“六个模块已经实现”，也不能将“代码已经生成”视为“功能已经通过验收”。

### 3.3 任务来源

复用现有 `Task.origin`：

- `user`：用户明确要求的任务；
- `scheduled`：经过授权的定时任务；
- `derived`：从已有目标推导出的任务；
- `opportunity`：由主动帮助系统发现的机会。

任务来源决定默认准入规则，但不直接决定任务是否有权执行。

例如，`derived` 任务即使与长期目标高度相关，也必须检查其必要性、预算、授权和风险。

### 3.4 调度器状态与 Task 状态分离

现有 Task 契约已经定义正式任务状态。调度器还需要维护队列状态、资源等待原因、执行租约和重排原因。

建议通过独立的调度记录或经过版本化的 Schema 扩展实现，不要随意向正式 Task 状态枚举中添加值，也不要将调度状态混入任务完成状态。

这样可以区分：

- 任务尚未执行；
- 任务正在等待资源；
- 任务因为依赖未满足而被阻塞；
- 任务等待用户授权；
- 任务执行完成但仍需验收。

## 四、任务准入控制

这是防止自主系统无限扩张的第一道门。

### 4.1 任务准入的八项检查

每个新任务进入执行队列之前，都应检查：

1. **目标价值：** 它是否推进一个明确的用户目标，或带来足够明确的收益？
2. **必要性：** 是否已经有其他任务覆盖相同工作？
3. **证据充分性：** 创建任务的依据是否可靠？
4. **授权：** 当前是否允许执行该任务？
5. **风险：** 是否存在不可接受的安全或副作用风险？
6. **预算：** 是否有足够资源完成并验收？
7. **依赖：** 必要条件是否已经满足，或者有可行的等待策略？
8. **停止条件：** 是否能明确判断何时完成、何时停止？

如果任务没有明确目标、预算或停止条件，不应直接进入自主执行状态。

### 4.2 准入结果

建议采用以下结果：

- `ACCEPT`：允许进入调度队列；
- `ACCEPT_WITH_LIMITS`：仅允许在指定范围内执行；
- `DEFER`：暂缓，等待条件满足；
- `PROPOSE`：只向用户提出建议；
- `MERGE`：合并到已有任务；
- `REJECT`：拒绝创建；
- `REQUIRE_APPROVAL`：需要用户确认。

这些是调度器内部的决策结果，不应与正式 Task 状态混为一谈。

### 4.3 主动机会的默认准入规则

对 `opportunity` 类型任务，默认采取更严格的准入策略：

- 发现问题，可以记录；
- 有价值的建议，可以展示；
- 低风险、只读的资料整理，可以在授权范围内执行；
- 可逆的本地准备工作，可以根据既定策略执行；
- 会改变项目范围、增加明显成本或产生外部副作用的工作，必须经过相应授权。

不得仅仅因为系统发现某项工作“可能有用”，就自动创建一连串实际执行任务。

## 五、优先级仲裁

### 5.1 先检查硬性约束，再比较优先级

任务调度不能只依靠一个综合分数。

以下情况属于硬性约束：

- 当前动作不符合安全或权限要求；
- 必要依赖不可用；
- 预算不足；
- 关键验收条件缺失；
- 任务与其他执行发生不可接受的冲突；
- 任务已经取消或过期；
- 同一个非幂等动作仍存在未解决的执行状态。

硬性条件不满足时，即使任务非常紧急，也不能直接越过检查。

### 5.2 建议的优先级顺序

通过硬性检查后，建议采用以下默认调度原则：

1. 必要的安全控制与风险处置；
2. 用户当前明确要求、正在等待交付的任务；
3. 已授权且具有明确时效要求的任务；
4. 已批准的长期目标关键任务；
5. 经过授权的维护任务；
6. 低风险主动准备任务；
7. 非紧急的探索与机会任务。

这是一套默认规则，不是无条件的固定排序。例如，具有明确期限的任务可能需要优先于普通的当前任务等待队列，但不能因此破坏正在执行的关键操作或安全约束。

### 5.3 优先级评估维度

调度器可以进一步考虑：

- 截止时间；
- 不完成的预期损失；
- 对长期目标的贡献；
- 任务是否为其他任务的关键依赖；
- 当前证据的充分程度；
- 执行成本；
- 失败风险；
- 用户等待时间；
- 延后执行是否会造成额外成本。

建议先进行硬性过滤，再进行多维比较，而不是直接把所有因素混成一个难以解释的数字。

### 5.4 防止低优先级任务永久饥饿

如果调度器永远优先执行新到达的高优先级任务，维护任务和长期目标可能长期得不到推进。

因此，应支持：

- 等待时间增长后的有限优先级提升；
- 长期目标的最低资源保障；
- 任务截止时间预警；
- 对过期机会进行自动失效处理；
- 在不影响当前任务的情况下利用空闲资源。

但优先级提升不能突破预算、授权和安全门槛。

## 六、长期目标推进与 DAG 协同

### 6.1 目标不是任务清单的简单集合

长期目标需要有明确的成功标准和阶段性里程碑。

例如，AI 漫剧能力包的目标不能只是“完成脚本、分镜、配音和合成任务”，还应包括：

- 是否生成了有效素材；
- 是否保持角色一致性；
- 最终视频是否满足格式与时长要求；
- 是否通过质量验收；
- 失败时是否能够恢复；
- 成本是否在预算范围内。

目标进展应以已验证成果为依据。

### 6.2 固定 DAG 与动态规划协同

对于稳定、可重复的工作流，优先使用已经验证的 DAG 模板。

对于开放任务，允许动态规划与局部重规划。

调度器负责：

- 检查节点依赖是否满足；
- 识别可执行节点；
- 为可执行节点分配资源；
- 处理依赖等待；
- 根据实际执行证据更新计划；
- 识别无法继续推进的目标。

它不应重新实现 Plan 或 ReAct，而应调用现有规划和执行机制。

### 6.3 只在必要时重新规划

当出现以下情况时，可以触发局部或任务级重规划：

- 关键依赖失效；
- 连续失败表明当前路径不可行；
- 目标条件发生合法变化；
- 预算发生变化；
- 新证据改变了可行方案；
- 现有计划无法满足验收标准。

不能因为后台调度器发现了一个新机会，就自动改变正在执行的主任务计划。

## 七、防止无限任务扩张

这是本专项最重要的治理要求之一。

### 7.1 建立任务生成预算

每个自动生成的任务必须具有：

- 父任务或关联目标；
- 创建原因；
- 预期收益；
- 验收条件；
- 最大资源预算；
- 最大执行时间或截止条件；
- 最大重试次数；
- 允许的子任务生成范围；
- 停止条件。

这些约束应与现有 Goal、Task、Budget 和授权机制关联。

### 7.2 任务生成必须有上限

建议为系统设置以下可配置限制：

- 单个父任务允许创建的活动子任务数量；
- 单个 Goal 同时运行的任务数量；
- 全局主动机会任务数量；
- 单个目标的累计探索预算；
- 自动生成任务的最大依赖深度；
- 单个任务的最大重试与恢复次数；
- 同一失败模式允许自动尝试的修复次数。

初始安全配置可以采用保守策略：主动机会任务默认不自动递归生成下一代机会任务；如需扩展任务树，应先完成当前任务验收，或经过单独的准入决策。

具体数值应通过真实负载和评测确定，不应在缺乏运行证据时直接固定为全局常量。

### 7.3 任务去重与合并

新任务创建前，应检查：

- 是否已经存在目标相同的任务；
- 是否有任务正在处理相同问题；
- 是否已有经过验证的成果可以直接复用；
- 是否存在相同的待办或维护任务；
- 是否属于之前已经拒绝或取消的重复机会。

对于真正相同的任务，应复用现有任务标识或通过正式机制合并；对于目标相同但验收要求不同的任务，则应保留各自的任务契约。

### 7.4 停止条件

任何自主任务至少应具备以下停止条件之一，并明确具体适用规则：

- 已满足验收契约；
- 已达到预算上限；
- 已超过截止时间；
- 已达到无进展阈值；
- 关键依赖不可用；
- 需要额外授权；
- 风险超过允许范围；
- 用户取消目标；
- 继续执行的预期收益不足以抵消成本；
- 当前任务已被更新的合法目标替代。

当任务停止时，应记录停止原因与当前状态，而不是继续生成新任务来绕开停止规则。

## 八、预算与资源管理

### 8.1 预算层次

建议建立四级预算：

| 层级 | 作用 |
|---|---|
| 全局运行预算 | 控制整个智能体在一个预算周期内的资源消耗 |
| Goal 预算 | 限制单个长期目标的累计投入 |
| Task 预算 | 限制单个任务的执行与恢复成本 |
| Run 预算 | 限制一次具体执行尝试的消耗 |

Run 预算不能绕过 Task 预算，多个 Task 也不能通过分拆来绕过 Goal 或全局预算。

### 8.2 预算内容

预算不应只限制模型 token，还应覆盖：

- 模型 API 费用；
- 工具调用费用；
- 外部生成服务费用；
- CPU 与内存资源；
- GPU 使用时间；
- 存储与带宽；
- 执行时长；
- 重试与恢复开销；
- 后台任务占用；
- 数据同步成本。

### 8.3 主任务资源保障

资源管理器应保留主任务所需的执行能力。

当系统处于高负载时：

1. 暂停非必要的主动机会任务；
2. 降低可选后台任务的并发；
3. 将低优先级工作延后；
4. 在质量不受影响的前提下选择更经济的执行方案；
5. 保留必要的验收和安全检查资源。

不能为了让后台目标持续推进，而导致当前用户任务无法完成。

### 8.4 预算耗尽后的行为

预算达到上限时，系统不能自动扩大预算。

可以选择：

- 停止可选探索；
- 采用已验证的低成本方案；
- 保存当前进度；
- 等待预算周期重置；
- 请求用户批准额外预算；
- 在仍然可行时交付已完成部分，并说明剩余限制。

必要的安全检查与结果验收不能因为预算紧张而被静默跳过。

## 九、并发与资源仲裁

### 9.1 按资源类型控制并发

不同任务消耗的资源不同。

例如：

- 代码分析可能主要消耗模型调用和 CPU；
- 视频生成可能大量消耗外部服务费用；
- FFmpeg 合成可能占用本地 CPU 和磁盘；
- Android UI 操作可能独占前台交互能力；
- 后台知识整理可能主要消耗存储和检索资源。

调度器应支持按资源类型设置并发上限，而不是只限制同时运行的任务数量。

### 9.2 任务间的资源冲突

当多个任务需要同一个独占资源时，应使用明确的资源租约或锁机制。

例如，两个任务不能同时对同一手机界面执行互相冲突的点击操作；两个任务也不能无协调地修改同一个项目工作区。

对共享文件、数据库和外部系统的写入，应根据风险和并发能力选择适当的互斥、版本检查或事务机制。

### 9.3 公平性与隔离

调度器应避免某个高消耗任务长期占用所有资源。

建议支持：

- 每个 Goal 的并发上限；
- 每个专家的资源配额；
- 高优先级任务的资源预留；
- 后台任务的可抢占与可暂停性；
- 长时间任务的定期状态检查；
- 资源不足时的有序降级。

抢占只能发生在支持安全暂停或恢复的执行点。不能在不可逆操作执行到一半时直接强制中断并假定状态安全。

## 十、后台执行的安全治理

### 10.1 按动作风险控制自主程度

自主程度必须绑定具体动作，而不是只给整个智能体设置一个全局的“自主级别”。

建议采用以下执行分级：

| 等级 | 允许范围 | 默认控制 |
|---|---|---|
| A0 | 观察、分析、提出建议 | 不产生外部副作用 |
| A1 | 只读检查、资料整理、计划生成 | 限定数据访问范围 |
| A2 | 已授权的可逆本地操作 | 检查范围、备份与恢复条件 |
| A3 | 已明确授权的特定外部操作 | 检查动作级授权、幂等性与结果回执 |
| A4 | 高风险、不可逆或权限敏感操作 | 按策略要求显式确认，不因任务自动生成而放行 |

这不是说所有 A3 操作都需要每次重新询问用户。如果用户已经针对具体动作、范围和条件授予有效授权，可以在授权范围内执行。

但授权必须可追溯，不能自动扩展到不同对象或更高风险动作。

### 10.2 自动任务不自动获得执行权限

系统通过准入检查，只代表任务可以进入调度流程，不代表任务中的每个动作都已经获准。

每次执行前仍须检查：

- 当前授权是否有效；
- 工具权限是否满足；
- 实际动作是否超出授权摘要；
- 目标对象是否发生变化；
- 风险等级是否变化；
- 是否存在未解决的外部副作用状态。

### 10.3 外部副作用与幂等性

调度器必须复用现有 `Side-effect Ledger` 和工具契约。

如果某项操作可能重复产生外部副作用，恢复前应确认原操作是否已经发生。

当 `safe_to_repeat=unknown` 时，不能因为任务租约过期或设备重新连接，就直接重新提交操作。

必须先对账、确认实际状态，或请求必要的人工介入。

## 十一、跨设备调度与离线恢复

### 11.1 设备不是简单的任务副本

EvoAgent 的 Android 端、Windows 电脑和后续个人服务器具有不同的能力边界。

建议按能力分配任务：

- Android：语音交互、手机 UI 操作、设备权限相关任务；
- Windows：本地代码项目、文件处理、桌面软件操作、FFmpeg 合成；
- 个人 Linux 主机：适合其环境的后台调度、日志汇聚、评测与持续运行任务；
- 云端服务：需要网络的模型调用和外部生成服务。

实际执行位置必须由能力声明、授权、数据位置、资源和当前在线状态共同决定，不能仅凭任务类型固定分配。

### 11.2 单一执行所有权

一个 Task 在同一时刻应只有一个有效的执行所有者。

建议采用带过期时间的执行租约，并在每次所有权变更时使用递增的 fencing token 或等效机制，防止旧设备在租约失效后继续写入状态。

设备切换时，应：

1. 检查旧执行者的租约；
2. 确认已提交的外部副作用；
3. 恢复已持久化的任务状态；
4. 验证新设备的能力和权限；
5. 建立新的执行租约；
6. 从安全恢复点继续执行。

不能只因为某设备离线，就认定它上一次执行一定失败。

### 11.3 断网与重连

离线期间：

- 只执行允许离线的任务；
- 使用本地可用的工具与知识；
- 保留任务状态、事件和必要的副作用记录；
- 禁止依赖不可用云服务的任务伪装成功；
- 避免多个设备各自执行同一个任务。

恢复连接后：

- 根据正式同步回执确认已持久化的事件；
- 合并可安全合并的状态更新；
- 解决版本冲突；
- 对账未知的外部副作用；
- 重新检查预算和授权；
- 再决定是否恢复执行。

HTTP 请求成功或网络连接恢复本身，都不能被视为任务状态已经安全同步。

## 十二、暂停、恢复、取消与失败处理

### 12.1 暂停

任务可以因为预算不足、资源冲突、用户要求、依赖不可用或风险变化而暂停。

暂停时应保存：

- 当前目标和验收契约；
- 已完成节点；
- 未完成节点；
- 运行组件版本；
- 必要上下文与证据；
- 外部副作用状态；
- 恢复前置条件。

### 12.2 恢复

恢复前应重新验证：

- 任务是否仍然有效；
- 用户目标是否发生变化；
- 预算是否仍然可用；
- 依赖是否恢复；
- 组件版本是否兼容；
- 当前授权是否仍然有效；
- 是否需要重新执行部分验收。

恢复不是从上次模型输出的最后一句继续生成，而是从经过验证的执行状态恢复。

### 12.3 取消

取消任务后，系统应阻止后续未获准动作，并处理已经开始的操作。

对于已经产生的外部副作用，取消并不意味着可以自动撤销。例如，已经发送的消息或已经提交的外部请求可能无法真正撤回。

系统必须区分取消后续工作、停止正在执行的安全步骤，以及尝试补偿已经产生的副作用。

### 12.4 失败

失败任务应保存失败原因、执行证据和恢复建议。

只有在仍有明确价值、预算充足且恢复策略有效时，才允许自动重试。

不能为了追求长期目标的完成率而无限重试，也不能将持续失败的任务不断拆分成新任务以规避原来的停止条件。

## 十三、目标进展与用户可见反馈

### 13.1 进展必须由证据支撑

系统应区分：

- 已完成并通过验收；
- 已执行但尚未验收；
- 正在执行；
- 等待依赖；
- 等待用户确认；
- 已暂停；
- 已失败；
- 已取消；
- 已过期。

用户应能够了解任务实际处于什么状态，而不是只看到“智能体正在努力完成”。

### 13.2 长期目标进度

建议根据可验证的里程碑汇总目标进展。

不能简单地使用已完成 Task 数量除以总 Task 数量计算进度，因为不同任务的价值和依赖关系可能差异很大。

如果没有足够依据估算百分比，应展示已经完成的里程碑、当前阻塞和下一步，而不是给出虚假的精确进度。

### 13.3 主动反馈频率

用户不需要接收每个后台事件的通知。

建议只在以下情况提供用户可见反馈：

- 关键里程碑完成；
- 出现影响目标的重大阻塞；
- 需要用户决定或授权；
- 预算即将达到上限；
- 任务已经完成并通过验收；
- 预期目标发生重大变化；
- 需要用户处理不可自动恢复的问题。

其他运行信息可以保留在任务详情和日志中。

## 十四、与无限优化体系的结合

### 14.1 可以优化什么

调度与自主执行能力可以独立改进：

- 任务准入准确率；
- 优先级仲裁策略；
- 资源分配策略；
- 设备选择策略；
- 后台任务暂停与恢复；
- 依赖调度；
- 任务去重；
- 预算分配；
- 停止条件；
- 长期目标进展判断。

### 14.2 不能只优化任务完成数量

调度器如果只追求完成任务数量，可能通过拆分任务、缩短验收或生成更多低价值工作来提高表面指标。

应综合评估：

- 用户目标达成率；
- 最终验收通过率；
- 单位资源带来的实际价值；
- 无效任务比例；
- 主动任务造成的干扰；
- 重复执行与重复副作用；
- 任务恢复成功率；
- 预算超限率；
- 长期目标推进效率；
- 用户需要介入的频率。

### 14.3 进化闭环

```text
采集调度与执行证据
          ↓
识别无效任务、资源浪费和优先级错误
          ↓
提出候选调度策略
          ↓
在历史任务与固定测试集上回放
          ↓
评估质量、成本、时延和安全影响
          ↓
通过正式进化门禁
          ↓
受控发布
          ↓
监测实际目标达成效果
          ↓
必要时回滚
```

调度策略的优化不能绕过现有的发布治理，也不能修改正在运行任务的安全约束。

## 十七、完成判定

只有满足以下条件，才能认定本专项实施验收完成：

- 所有自主任务均有明确目标、验收条件、预算和停止策略；
- 新任务经过准入检查后才能进入执行队列；
- 当前用户任务的必要资源得到保障；
- 长期目标与具体任务具有可追溯的关联；
- 自动任务生成受到明确限制；
- 预算、并发和资源分配具有可验证的边界；
- 跨设备执行具有单一所有权和安全恢复机制；
- 未知外部副作用状态不会触发盲目重试；
- 任务完成状态以真实验收结果为依据；
- 暂停、恢复、取消和失败均能保留必要的执行证据；
- 主动任务不能绕过授权或扩大用户目标；
- 调度策略的改进必须通过独立评测与发布门禁；
- 所有关键验收场景均有真实执行证据。

**最终目标：让 EvoAgent 能够主动发现值得做的事情，也能够有纪律地选择哪些事情应该做、何时做、在哪里做、花多少资源做，以及什么时候应该停止。真正成熟的自主智能体，不是永远忙碌的智能体，而是能够持续推进用户目标，同时守住质量、成本、授权和稳定性边界的智能体。**</WritingBlock>
