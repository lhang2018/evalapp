<WritingBlock id="71462" variant="document"># EvoAgent 用户任务端到端流程与交互状态规范

**文档编号：** EA-UX-008  
**版本：** 1.0  
**文档类型：** 用户体验流程、任务交互规则与技术契约映射  
**适用范围：** EvoAgent Android 首发产品及后续扩展终端

## 一、设计目标

本文件将产品功能转化为可实施的端到端交互流程，覆盖四类核心情境：

- F01：快速问答与连续对话；
- F02：多步骤任务的规划、执行、验收和交付；
- F03：用户改变目标、任务失败、取消和恢复；
- F04：主动整理近期工作并提供有价值的帮助。

四种情境共用统一的任务执行内核，但不必采用完全相同的处理流程。

核心原则是：**简单任务尽可能直接完成，复杂任务可靠地完成，异常任务可控地恢复，主动帮助始终服从核心任务。**

## 二、统一任务处理流程

### 2.1 全局流程

用户输入进入统一入口后，系统按照以下顺序处理：

1. 解析用户目标、约束和上下文；
2. 判断任务复杂度、风险和能力需求；
3. 确定是否需要澄清；
4. 判断是否存在适用的稳定工作流；
5. 选择专家、工具和执行策略；
6. 检查权限、依赖、预算和停止条件；
7. 执行任务并保存关键状态；
8. 对结果进行独立验收；
9. 交付成果或进入恢复流程；
10. 记录必要的运行证据；
11. 在有价值且不影响主任务时，考虑额外帮助。

现有架构中的职责保持不变：Router 负责选择候选路径，Planner 负责规划，DAG Runtime 管理节点执行，ReAct 负责受约束的局部循环，Action Guard 控制动作准入，Evaluator 独立检查结果。<FileCite ref_id="turn16file3"/>

### 2.2 任务路径选择

| 任务类型 | 推荐路径 | 用户体验 |
|---|---|---|
| 简单问答 | 直接回答 | 不展示复杂执行流程 |
| 需要资料或工具的问答 | 检索或工具增强 | 展示必要的来源与限制 |
| 重复且可验收的工作 | 稳定工作流 | 快速执行，减少重复规划 |
| 主流程确定、局部存在不确定性 | 混合工作流 | 仅对不确定步骤进行动态规划 |
| 没有适用工作流的复杂任务 | 受限动态规划 | 展示关键计划和真实进度 |
| 高风险或需要额外权限的任务 | 授权与审批流程 | 在受保护动作之前请求必要确认 |
| 用户主动整理近期工作 | 独立主动分析任务 | 使用授权数据，提供摘要与可选建议 |

系统不应把所有输入都升级成复杂任务，也不能因为用户使用了简短的自然语言，就忽略其实际目标的复杂度。

## 三、F01：快速问答与连续对话

### 3.1 用户场景

用户打开 EvoAgent，询问一个问题，随后继续追问、纠正或要求进一步处理。

例如：

> 用户：什么是 AST？  
> EvoAgent：解释 AST 的基本概念。  
> 用户：结合代码智能体，讲讲它能解决什么问题。  
> EvoAgent：在保留前文上下文的基础上，解释 AST 在代码分析、重构和静态检查中的作用。

### 3.2 交互步骤

| 步骤 | 系统行为 | 用户看到什么 |
|---|---|---|
| F01-01 | 接收输入，关联当前会话 | 输入内容 |
| F01-02 | 判断是否属于简单问答 | 无额外操作 |
| F01-03 | 检查是否需要实时资料或工具 | 必要时说明来源 |
| F01-04 | 生成回答并检查基本一致性 | 直接回答 |
| F01-05 | 保留必要的会话上下文 | 可以继续追问 |

### 3.3 规则

**规则 A：不强制启动复杂任务。**

如果问题能够直接回答，不需要创建复杂计划、展示内部专家切换或调用多余工具。

**规则 B：上下文相关，但不无限继承。**

后续回答只应继承与当前问题相关的信息。用户明确纠正前文后，后续回答应采用纠正后的信息。

**规则 C：复杂问题可以自然升级。**

如果用户接着要求研究资料、生成文件或执行操作，系统可以从对话进入正式任务流程，并复用已有上下文。

**规则 D：不把生成的回答当成外部操作证据。**

例如，回答“文件已经保存”之前，必须确认文件确实生成并可访问。

### 3.4 验收条件

- 简单问题不会无故启动复杂工作流。
- 连续追问能够正确继承必要上下文。
- 用户纠正信息后，后续回答不会持续使用已知错误。
- 需要外部证据的问题不会仅依靠模型自述。
- 从问答升级到任务时，不会无故丢失已确认要求。

## 四、F02：多步骤任务执行

### 4.1 用户场景

用户说：

> 帮我研究一个主题，整理相关资料，形成一份结构清晰、结论有依据的报告，并检查完成质量。

用户不需要自行选择研究专家、检索工具、文档生成器和验收器。

### 4.2 阶段一：理解与任务契约

系统提取：

- 最终目标；
- 交付物类型；
- 内容范围；
- 质量要求；
- 已提供资料；
- 时间与成本约束；
- 必要的权限；
- 验收条件。

如果缺少非关键细节，系统可以采用合理的默认值。如果缺少的条件会显著改变任务结果或风险，则应询问用户。

任务进入正式执行前，应形成可检查的任务契约。

### 4.3 阶段二：规划与准入

系统先判断是否存在适用的稳定工作流。

如果存在，优先复用；如果只有部分步骤可复用，则采用混合规划；只有在没有适用路径时，才使用受限动态规划。

执行前检查：

- 相关工具是否已注册；
- 所需能力版本是否兼容；
- 网络和外部服务是否可用；
- 预算是否足够；
- 是否存在必须事先确认的动作；
- 是否定义了任务停止条件和验收规则。

如果任务无法在当前环境中完成，应提前说明依赖或限制，而不是等到耗尽预算后才告知用户。

### 4.4 阶段三：执行与进度展示

任务执行期间，界面显示真实阶段，例如：

1. 正在整理资料；
2. 已完成资料收集；
3. 正在分析证据；
4. 正在生成报告；
5. 正在检查报告；
6. 已完成交付。

系统不应展示未经计算的虚假进度百分比。

执行中的关键变化应写入运行记录。每个步骤都要能区分尚未开始、正在运行、等待、已完成、失败和取消。

用户可以在执行过程中：

- 补充约束；
- 查看必要的中间成果；
- 处理授权请求；
- 取消任务；
- 在支持的情况下暂停后继续。

### 4.5 阶段四：独立验收

报告生成后，验收器根据任务契约检查：

- 文件是否存在且可打开；
- 报告结构是否符合要求；
- 必要章节是否齐全；
- 关键结论是否有来源支撑；
- 重要事实是否存在明显矛盾；
- 是否满足用户明确提出的约束。

验收器应与生成过程在逻辑上分离，不能仅因为生成器声称完成，就直接判定成功。

如果部分验收项失败，系统应决定能否安全修复。可以修复的，继续处理相关步骤；无法修复的，明确报告未通过的项目。

### 4.6 阶段五：交付

用户最终看到：

- 报告文件；
- 简明结论；
- 验收摘要；
- 尚未解决的问题；
- 适当的后续建议。

如果文件生成成功但内容验收未通过，不能显示为全部完成。

### 4.7 验收条件

- 用户只需描述目标，无需手动组织技术组件。
- 计划、执行和验收使用同一套目标与约束。
- 工具失败不会无条件触发无限重试。
- 预算耗尽时停止新增调用。
- 真实产物通过相应验收后才能标记成功。
- 失败或部分完成时，已经产生的可用成果不会无故丢失。

## 五、F03：用户改变目标、任务失败与恢复

这是多步骤智能体最容易出现状态错误的环节，必须单独设计。

### 5.1 用户改变目标时的处理

用户可能在任务执行中提出不同类型的变更。

| 变更类型 | 示例 | 系统处理 |
|---|---|---|
| 补充信息 | “报告还要包含成本分析” | 更新约束，评估受影响步骤 |
| 调整优先级 | “先完成结论部分” | 重新排序可执行节点 |
| 修改交付格式 | “改成表格形式” | 重新评估相关产物与验收规则 |
| 改变核心目标 | “不要做报告，改成演示文稿” | 重新建立目标与计划，评估复用价值 |
| 扩大权限范围 | “再帮我发送给其他人” | 重新执行权限检查，必要时单独审批 |
| 取消任务 | “先停下来” | 进入取消流程，处理在途动作 |

### 5.2 任务变更规则

**规则 A：不抹除已发生的事实。**

已完成的工作、已经产生的外部副作用和历史运行记录必须保留。改变目标不意味着之前的动作从未发生。

**规则 B：只重做受影响的步骤。**

系统应根据依赖关系判断哪些结果仍然有效，哪些需要重新计算。

**规则 C：变更后重新验收。**

交付格式或任务目标发生变化时，应更新相关验收条件，不能沿用已经不适用的验收结论。

**规则 D：授权不随任务扩张。**

新增动作超出原授权范围时，必须重新经过动作准入检查。

### 5.3 任务失败时的决策流程

1. 识别失败发生在哪个步骤。
2. 判断失败属于模型、工具、网络、权限、资源、状态还是验收问题。
3. 检查是否存在尚未确认的外部副作用。
4. 评估安全恢复路径。
5. 在预算、重试次数和停止条件允许时执行恢复。
6. 恢复失败后，停止无效尝试并保留成果。
7. 向用户说明当前状态和可选择的后续操作。

系统不得将所有失败统一处理为“重新调用模型”。

### 5.4 中断后的恢复

当 App 退出、设备重启或网络中断时，恢复前需要核对：

- 当前任务状态；
- 最近的有效检查点；
- 已完成节点；
- 正在执行或状态未知的节点；
- 已提交的外部动作；
- 当前运行绑定的配置版本；
- 剩余预算。

如果外部操作状态未知，先通过可用的查询或对账方式确认，不应直接重复提交。

### 5.5 取消与恢复的状态规范

| 当前状态 | 用户操作 | 预期行为 |
|---|---|---|
| `running` | 取消 | 阻止新增非必要动作，处理在途操作 |
| `waiting_approval` | 拒绝 | 不执行受保护动作，提供替代路径 |
| `waiting` | 继续 | 检查等待条件是否已经满足 |
| `recovering` | 再次取消 | 停止可取消的恢复步骤 |
| `verifying` | 修改目标 | 判断现有验收结果是否仍适用 |
| `needs_user` | 补充信息 | 更新任务契约并重新评估计划 |
| `failed` | 重新执行 | 创建可追踪的新运行记录 |
| `cancelled` | 再次启动 | 按明确的重启规则创建新运行，不覆盖旧记录 |

以上是用户交互规则。具体内部状态名称和转换应以现有 Task of Record 状态契约为准。

### 5.6 验收条件

- 变更目标后不会丢失历史执行记录。
- 不受变更影响的有效结果可以复用。
- 需要重新授权的动作不会沿用过期授权。
- 取消后不会盲目重放外部操作。
- 重启后能够恢复真实状态或明确报告无法确认。
- 失败任务重新执行后，历史失败记录仍然可追溯。

## 六、F04：主动整理近期工作与机会发现

主动智能应当围绕用户真实的工作状态运行，而不是随机生成建议。

### 6.1 触发方式

主动整理分为两种：

**用户主动触发：** 用户说“整理一下最近的工作”“看看当前项目还有什么没处理”。

**用户预先授权的主动触发：** 用户设置了定期项目整理、明确的待办提醒或其他具体的主动任务。

系统不能因为具备读取能力，就默认主动分析全部对话、通知和文件。

### 6.2 主动分析流程

#### 第一步：确认分析范围

明确本次允许使用的来源，例如当前项目、指定会话、用户明确选择的文件或已授权的数据源。

#### 第二步：建立证据集合

系统收集必要的事实，并保留来源关联。

需要区分：

- 用户明确说过的内容；
- 有记录支持的任务状态；
- 系统根据现有证据得出的推断；
- 尚未确认的信息。

#### 第三步：整理当前状态

输出：

- 已完成事项；
- 进行中的工作；
- 被阻塞的任务；
- 尚未解决的问题；
- 已确认的重要约束；
- 可能需要关注的时间节点。

不能把过时任务状态当作当前事实。存在冲突时，应标记为待确认。

#### 第四步：发现潜在机会

例如：

- 某个项目存在尚未解决的依赖；
- 一项工作缺少必要的验收步骤；
- 一组重复任务可能适合保存为工作流；
- 用户已经具备完成下一阶段工作的必要材料。

每项机会都应评估相关性、潜在收益、证据可信度、时效性、执行成本和干扰程度。

#### 第五步：筛选并交付建议

只向用户展示经过筛选的高价值建议。

建议格式应当简洁：

**发现了什么 → 为什么值得关注 → 可以怎么做 → 需要什么权限或成本。**

如果没有足够有价值的建议，允许不输出额外建议。

### 6.3 主动任务的资源隔离

主动分析使用独立的队列和预算。

系统必须遵守以下规则：

1. 核心任务运行期间，不得为了主动分析抢占必要的执行资源。
2. 资源不足时，先暂停主动分析。
3. 主动分析不得修改正在运行的核心任务状态。
4. 用户关闭主动帮助后，不再启动新的非必要主动任务。
5. 已经生成的建议不等于用户授权执行建议。
6. 任何外部操作都必须经过相应的权限、风险和预算检查。
7. 主动任务应有完成条件、最大运行范围和无进展停止策略。

### 6.4 验收条件

- 摘要中的关键事实能够追溯到授权来源。
- 系统能够区分事实、推断和未知信息。
- 无依据或低价值建议能够被过滤。
- 主动分析失败不会影响核心任务。
- 关闭主动帮助后，核心执行和必要的安全提示仍正常工作。
- 主动建议不会自动变成未经授权的外部动作。

## 七、用户界面状态与内部状态的对应关系

用户需要清晰的状态，而不需要了解每个内部状态码。

| 用户界面 | 内部状态或条件 | 允许的下一步 |
|---|---|---|
| 正在理解 | 任务解析与分类中 | 继续处理或请求澄清 |
| 需要补充信息 | `needs_user` 或明确的澄清等待 | 用户补充、取消 |
| 正在执行 | `running` | 查看进度、补充约束、取消 |
| 等待授权 | `waiting_approval` | 批准、拒绝、取消 |
| 正在恢复 | `recovering` | 查看恢复进度、取消可取消步骤 |
| 正在验收 | `verifying` | 等待验收或处理验收失败 |
| 已完成 | `succeeded` 且验收证据满足要求 | 查看成果、继续讨论 |
| 部分完成 | 有效成果存在，但部分目标未满足 | 查看缺口、继续或结束 |
| 未完成 | `failed`、`cancelled` 或其他终止条件 | 查看原因、重新运行或结束 |

实际实现时，用户界面还应区分等待网络、等待外部服务和等待用户决策等原因，避免把所有等待统一显示成“执行中”。

**重要规则：** 页面状态必须来自任务记录和事件，不得仅依据模型返回的自然语言推断。

### 8.1 标识与状态的使用规则

- `task_id` 标识逻辑任务；
- `run_id` 标识一次具体执行；
- `node_run_id` 标识 DAG 节点执行；
- `approval_id` 关联具体授权；
- `runtime_manifest_id` 关联本次运行使用的不可变组件组合；
- `event_id` 用于事件的稳定识别与幂等同步。

这些标识不是 UI 装饰字段，而是保证用户看到的进度、历史、恢复和验收结果能够对应真实执行记录的基础。<FileCite ref_id="turn16file0"/>
