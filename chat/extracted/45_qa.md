## 用户

用户说话后。怎么路由到对应的专家系统呢，路由本身准不准，目前有考虑评估手段。或者跟智能体一样迭代升级手段吗

## ChatGPT

这个问题非常关键。**EvoAgent 的路由器本身也必须是一个可评测、可诊断、可迭代的系统，而不能只写一段提示词，让大模型猜应该调用哪个专家。**

而且路由错误可能比普通回答错误影响更大：它会让后续整个任务进入错误的专家、使用错误的工具和记忆，甚至导致本来正确的能力被误判为有问题。

我建议把路由设计成 EvoAgent 的独立核心子系统，称为 **智能路由与路由进化系统（Routing & Routing Evolution）**。它既参与每一次用户请求，也接受独立的质量评估和持续优化。

## 一、用户说话后，究竟怎么路由？

不是简单的：

`用户说话 → 大模型判断领域 → 调用专家`

而是采用多阶段路由。先理解任务，再判断专家和能力是否匹配，最后根据执行过程动态调整。



    **1. 用户输入**
    语音或文字 → 语音转写、上下文整理



    **2. 任务理解层**
    识别目标、约束、实体、风险、是否多步骤，以及用户真正想完成的结果。



    **3. 候选路由层**
    根据专家描述、能力清单、历史评测和当前环境，召回一个或多个候选专家。



    **4. 路由决策层**
    综合任务匹配度、置信度、风险、能力可用性、成本与任务复杂度，决定选谁。


    <grid-item>


        **匹配明确**
        进入对应专家

    </grid-item>
    <grid-item>


        **复杂或模糊**
        进一步判断或拆分任务

    </grid-item>



    **5. 执行反馈与路由验证**
    检查专家是否具备能力、执行是否有效，必要时重新路由并记录原因


这里有个重要原则：**意图识别、专家选择、工具选择和执行成功判断，是四个不同的问题。**

例如，用户说“帮我修一下这个 Python 项目”。

- 意图识别：用户想修复代码。
- 专家路由：选择编程专家。
- 工具选择：决定是否使用代码读取、终端、测试工具。
- 执行验证：运行测试、检查改动，判断是否真的修好。

如果测试失败，不能直接推断路由错误；也可能是代码分析错误、工具故障或原始需求不完整。

## 二、路由究竟用什么技术？不能只靠一个大模型

我建议采用 **规则约束 + 候选召回 + 模型判别 + 置信度校准 + 执行反馈** 的混合架构。






      **第一层：规则与硬约束**
      过滤不支持的任务、检查权限、设备能力、工具可用性和禁止操作。
      优点：可预测、可测试。不能靠模型置信度绕过硬约束。








      **第二层：候选专家召回**
      利用专家能力描述、任务分类、关键词、语义检索及能力注册表，筛选可能合适的专家。
      优点：不必让模型每次从全部专家中盲选，也便于新增专家。








      **第三层：模型辅助判别**
      对候选专家进行比较，分析任务目标、约束、所需能力、歧义和跨领域依赖。
      优点：处理自然语言的模糊表达和复杂组合任务。








      **第四层：决策与置信度校准**
      判断是否足以选择单个专家，是否需要多个专家协作，或是否应追问用户。
      置信度必须通过历史标注数据校准，不能直接相信模型自报的 95%。



### 路由结果不应只有一个专家名称

建议统一输出结构化的 `RoutingDecision`，例如：

```json
{
  "task_type": "code_debugging",
  "candidates": [
    {"expert_id": "coding", "score": 0.93},
    {"expert_id": "general", "score": 0.46}
  ],
  "selected_experts": ["coding"],
  "decision": "single_expert",
  "reason_codes": [
    "CODE_ARTIFACT_DETECTED",
    "DEBUGGING_INTENT"
  ],
  "required_capabilities": [
    "read_project",
    "run_tests"
  ],
  "fallback_policy": "ask_or_replan"
}
```

这些分数只是格式示例，不是经过实测的准确率。生产系统中的分数必须有明确含义，并通过校准和离线测试验证。

路由结果还需要关联 `routing_policy_version`、模型版本、候选专家清单、耗时和成本。否则以后即使发现路由准确率下降，也很难知道是模型换了、专家变多了，还是决策策略发生了变化。

## 三、怎么评估路由到底准不准？

这是你提出的问题中最重要的部分。

我的建议是建立一套独立的**路由评测体系**，不能只看用户是否满意，也不能把任务最终失败率直接当作路由错误率。

首先建立一份专门的路由评测集，覆盖日常任务、边界案例、模糊意图、跨领域任务、新增专家以及工具不可用等情况。

例如：

| 用户输入 | 正确的路由行为 | 重点检查 |
|---|---|---|
| “帮我规划东京三日游” | 旅游专家 | 是否正确识别旅游意图 |
| “帮我修复这个 Python 项目的测试错误” | 编程专家 | 是否识别代码调试任务 |
| “把这段故事做成 60 秒 AI 漫剧” | 漫剧专家 | 是否选择复杂工作流能力 |
| “打开微信，找到某个人发来的文件” | 手机操作专家，必要时结合文件处理能力 | 是否区分手机操作与文件理解 |
| “帮我研究某个问题，再写成 Python 脚本分析” | 多专家协作或先规划再分派 | 是否正确处理跨领域任务 |
| “帮我把这件事处理好” | 结合上下文判断，必要时追问 | 是否避免无依据地强行路由 |

这些只是初始样例。真正的评测集还要覆盖不同说法、长对话上下文、口语转写错误、否定表达、任务修改，以及模型和专家版本变化。

### 需要监控哪些指标？


    **1. Top-1 路由准确率**

    首选专家是否属于标注的正确路由。适用于单专家任务。



    **2. Top-K 候选召回率**

    正确专家是否出现在前 K 个候选中。可以判断错误发生在候选召回还是最终决策。



    **3. 错误路由率与高风险错误率**

    统计误选专家、遗漏必要专家，以及错误路由导致高风险动作的比例。



    **4. 拒绝与追问质量**

    该追问时是否追问，该直接执行时是否不必要地打断用户。



    **5. 路由成本与时延**

    每次路由额外消耗的模型调用、Token、费用和等待时间。



    **6. 路由对最终任务的贡献**

    正确路由是否真的改善任务成功率、恢复率和整体成本，而不是只优化分类准确率。


还应监控**置信度校准**：例如，系统声称置信度约为 0.8 的任务，长期来看是否真的有约 80% 符合相应的正确性定义。对跨领域任务，正确答案可能是多个专家的组合，不能机械地用单标签准确率衡量。

评测数据也要区分：人工确认的正确路由、规则可判定的任务，以及尚无明确答案的案例。用户最终完成任务，不一定代表路由正确；任务失败，也不一定代表路由错误。

## 四、路由本身怎么迭代升级？

我建议让路由器拥有独立的进化轨道，但它不能绕过 EvoAgent 的统一进化控制器、评测门禁和发布系统。

它的进化流程应该是：


    **① 采集路由证据**
    输入摘要、候选专家、决策结果、置信度、用户纠正、最终任务验收



    **② 路由错误诊断**
    区分意图理解错误、候选遗漏、排序错误、能力注册错误与置信度失准



    **③ 生成局部候选**
    修改分类规则、专家描述、候选召回、判别提示词或决策阈值



    **④ 独立评测与对比**
    在固定测试集、困难案例、回归集和成本预算下比较基线与候选



    **⑤ 灰度发布与线上验证**
    有限流量试运行，监控错误率、任务成功率、成本和回滚条件


### 路由可以优化哪些东西？

| 可优化对象 | 示例 | 影响范围 |
|---|---|---|
| 专家能力描述 | 明确编程专家负责调试、测试和重构 | 主要影响对应专家的候选召回 |
| 路由规则 | 增加特定意图的识别条件 | 影响匹配规则覆盖的任务 |
| 候选召回策略 | 调整语义检索、关键词和候选数量 | 可能影响多个领域 |
| 判别提示词 | 改善模糊表达和多领域任务判断 | 影响使用该判别器的任务 |
| 决策阈值 | 调整自动选择、追问和拒绝的边界 | 影响错误路由与交互效率 |
| 模型及路由模型 | 更换判别模型或增加专用分类器 | 需要评估准确率、时延和费用 |
| 专家注册信息 | 更新可用工具、版本、平台与能力契约 | 影响路由可行性判断 |

**不是每次路由失败都要升级模型。** 很多问题只需要修正专家的能力描述、工具注册信息或一条明确的路由规则。只有证据显示问题具有广泛性、简单改进无效时，才考虑更复杂的方案。

而且，路由器自身也可能出错。它可能把工具故障判断为专家不匹配，把用户表达含糊判断为模型能力不足，甚至错误地把自己的历史决策当成训练标签。因此，诊断结果要保留证据和不确定性，不能让路由器完全依靠自己的判断给自己打分。

## 五、怎样保证路由升级不会破坏其他专家？

我建议采用三道门禁。




      **第一道：离线评测门禁**
      候选必须在固定评测集上达到路由质量要求，并检查困难案例、边界案例和高风险误路由。





      **第二道：跨专家回归门禁**
      即使改动只针对旅游路由，也要验证其他专家的召回率、误路由率、成本与时延是否发生不可接受的退化。





      **第三道：线上灰度与回滚**
      新路由先在受控范围运行，持续比较基线；出现明显退化时自动停止推广或回滚。



路由策略也应该有独立版本，例如：

- `routing_policy_version`
- `routing_classifier_version`
- `expert_registry_version`
- `routing_eval_suite_version`

这样，当路由质量下降时，可以判断是判别器换了、专家注册信息变化了，还是路由规则升级导致的，而不是盲目修改整个智能体。

## 六、路由本身要不要成为一个独立专家？

我的建议是：**路由是独立的核心子系统，但不必一开始就把它实现成一个完整的通用专家智能体。**

原因是路由器与领域专家的目标不同。

- 领域专家负责完成某一类任务。
- 路由器负责选择合适的执行者。
- 进化控制器负责优化路由与专家的策略。
- 评测门禁负责判断这些改进是否真的有效。

如果把路由器完全当成普通专家，它可能调用不必要的工具、消耗过多 Token，甚至通过自我反思不断重新选择专家，导致循环路由和成本膨胀。

更合理的方式是：路由器采用可组合的判断流程，必要时才调用模型辅助判别；决策次数、候选数量和预算都有硬性上限。

## 七、我建议增加的架构模块

在此前的 EvoAgent 架构上，正式增加一个一级逻辑模块：

**智能路由与路由进化系统**，包含以下子模块：

1. 意图理解与任务分类器。
2. 专家能力注册表和能力发现。
3. 候选专家召回与排序。
4. 路由决策、置信度校准和追问策略。
5. 路由日志、归因分析与错误案例库。
6. 独立路由评测集与回归测试。
7. 路由候选实验、版本管理与灰度发布。
8. 跨专家影响分析与自动回滚。

它和前面讨论的 8 个服务不是简单的第 9 台服务器。初期可以把它作为任务编排服务内部的独立模块，路由评测与候选发布则复用统一的进化、评测和发布基础设施。只有当负载、可靠性或团队边界需要时，再考虑独立部署。

另外，路由评测结果还应成为专家系统进化的重要输入：如果某个专家经常收到不适合自己的任务，应先检查路由，而不是让该专家不断优化自己的提示词来弥补错误输入。

## 八、最终应达到什么状态？

我建议将路由的目标定义为：

**路由不是追求每次都必须选出一个专家，而是在质量、成本、风险和任务完成率之间，持续选择当前最合适的执行路径。**

这意味着它必须能够：

- 正确选择单个专家。
- 在复杂任务中选择多个专家或建立任务 DAG。
- 对模糊请求合理追问，而不是强行猜测。
- 发现当前没有合适专家时，拒绝错误分派或进入受控通用路径。
- 区分路由失败、工具失败、专家执行失败和验收失败。
- 在模型更换、专家增加、能力包升级后重新评测。
- 自动优化低风险路由策略，同时保留基线、成本上限、独立门禁和回滚能力。

还有一个重要的工程原则：**新专家加入时，必须同时提供能力声明、适用范围、禁用条件、路由测试案例和版本兼容信息。** 否则，专家数量越多，路由未必越准确，反而可能增加候选混淆。

这样，路由器本身就不再是静态的入口代码，而是 EvoAgent 中一个有独立评测、独立版本和受控进化能力的核心系统。
