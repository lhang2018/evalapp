# EvoAgent 第五十八专项：自主目标管理、长期任务与智能体主动性治理

<text color="secondary" size="sm">AGIG · Autonomous Goal & Initiative Governance</text>

前面已经讨论了 EvoAgent 如何执行任务、评估质量、管理知识资产，以及通过 RERA 和 APRO 实现可靠性与资源优化。

现在要解决更深一层的问题：

**当用户没有持续发出指令时，EvoAgent 如何判断自己下一步应该做什么？**

这决定了 EvoAgent 究竟只是一个等待命令的工具，还是一个能够长期推进目标、发现问题、主动提出改进，同时又始终受用户控制的个人智能体。

例如，你让 EvoAgent 持续改进自己的编程能力。

系统可能发现：

- 某个代码技能经常失败；
- 某个工作流存在重复调用；
- 一个回归测试覆盖不足；
- 某种模型切换策略造成大量返工；
- 一项新能力可能提高复杂任务的成功率。

发现这些问题之后，系统并不能一律立即行动。

它还需要判断：

- 这个问题是否值得现在解决？
- 是否会影响正在进行的用户任务？
- 应该先收集证据，还是直接修改？
- 是否有权限执行修改？
- 需要多少计算资源和时间？
- 如果改进失败，能否恢复？
- 如果没有足够证据，应该继续探索还是停止？
- 如果用户一直没有新指令，系统是否应该无限寻找改进机会？

因此，AGIG 不是一个简单的计划器，也不是定时任务系统，而是一个负责管理**目标、主动性、授权、优先级、持续推进与停止条件**的治理层。

---

# 一、第一性原理：智能体不能把“继续做事”当成目标

首先明确一个重要原则：

**EvoAgent 的目标不是最大化自己的活动量、任务数量、模型调用量或自我修改次数，而是在用户授权范围内创造可验证的价值。**

如果系统把“持续改进自己”理解为必须不断产生新改进，它就可能陷入无休止的循环：

1. 发现一个可以改进的问题；
2. 创建一个改进任务；
3. 改进后发现新的问题；
4. 创建更多任务；
5. 不断消耗资源；
6. 即使收益已经很小，也继续寻找改进机会。

这并不是无限进化，而是缺少停止机制。

## 1.1 将目标价值与行动成本分开

可以用一个概念模型描述某个主动任务的净价值：

\[
V_{\text{net}} =
V_{\text{expected}}
-
C_{\text{execution}}
-
C_{\text{opportunity}}
-
R_{\text{expected}}
\]

其中：

- \(V_{\text{expected}}\)：预期收益；
- \(C_{\text{execution}}\)：执行成本；
- \(C_{\text{opportunity}}\)：占用资源而延误其他任务的机会成本；
- \(R_{\text{expected}}\)：失败、回归或其他风险的预期损失。

这是用于比较候选行动的决策模型，不是可以直接精确计算所有价值的公式。

实际实现时，应该根据任务类型使用适当的估算方法，并记录不确定性。

例如，一个低频代码缺陷可能只影响极少数任务。即使它可以修复，也未必值得立即启动复杂的重构。

相反，如果一个故障正在造成重复付费调用，或者威胁用户数据完整性，即使修复成本较高，也可能应当优先处理。

## 1.2 主动性必须有边界

AGIG 需要区分三件事：

- **可以发现什么：** 系统可以从运行数据、失败案例和已有知识中发现潜在问题。
- **可以准备什么：** 系统可以分析问题、生成候选方案、运行授权范围内的测试。
- **可以执行什么：** 系统只能执行当前授权策略允许的操作。

发现问题不代表拥有修改权限，提出改进方案也不代表可以直接发布。

尤其对于自主编程、工作流修改、外部服务调用和能力晋升，必须分别判断授权和风险。

## 1.3 没有新任务，不等于必须创造新任务

AGIG 应允许系统进入真正的空闲状态。

如果当前没有值得执行的主动任务，可以：

- 等待用户输入；
- 等待一个已经定义的外部条件；
- 执行必要的低成本维护；
- 在预算允许时运行已批准的评测；
- 什么都不做。

**能够在没有价值时停止，是自主智能体成熟度的一部分。**

## 2.1 AGIG 与现有模块的边界

| 模块 | 核心职责 |
|---|---|
| AGIG | 管理目标、主动性、授权边界、优先级与停止条件 |
| Router | 选择适合的专家与能力 |
| Planner | 将已批准的目标分解成可执行计划 |
| ReAct | 根据执行观察动态选择下一步行动 |
| DAG 执行器 | 执行任务依赖与节点调度 |
| APRO | 在资源约束下安排执行位置、模型、并发和预算 |
| RERA | 处理故障、重试、恢复与安全停止 |
| QEEG | 验证任务结果与改进收益 |
| TSEG | 保护安全、权限和治理边界 |
| GECO | 记录目标执行、决策、操作与结果证据 |
| KCLG | 管理由执行结果产生的知识、技能与工作流资产 |
| SELCIA | 对经过验证的改进进行受控发布和回滚 |
| HACCG | 向用户展示进展、风险、待审批事项与停止原因 |

其中最重要的区别是：

**AGIG 决定为什么做、是否值得做、是否可以做；Planner 决定怎样做；执行系统负责真正去做。**

# 三、目标分类：不同目标不能采用同一种治理规则

EvoAgent 可能同时拥有多个目标，但它们的来源、时效和权限不同。

建议建立 `GoalType`，至少分成五类。

## 3.1 五类目标

<box border radius="xl" padding={3} gap={3}>
  {#each [
    ["G1 · 用户显式目标","用户直接提出的任务或长期要求，例如开发一个软件、完成一个项目。"],

    ["G3 · 任务派生子目标","为了完成当前目标，由 Planner 分解出来的分析、测试、修复等子目标。"],
    ["G4 · 系统维护目标","维持必要的运行可靠性、数据完整性、存储健康与安全状态。"],
    ["G5 · 主动发现的机会目标","系统根据证据提出的改进候选，例如减少无效调用、修复重复出现的缺陷。"]
  ] as item}
    <box gap={1}>
      <title size="md">{item[0]}</title>
      <text color="secondary" size="sm">{item[1]}</text>

    {#if item[0]!=="G5 · 主动发现的机会目标"}
      <divider color="subtle"/>

这五类目标的治理方式不应完全相同。

用户显式目标通常具有明确的任务意图；系统维护目标则必须受到严格的操作范围约束；主动发现的机会目标往往还需要经过价值评估和授权检查。

## 3.2 子目标不能自动扩大原始目标

例如，用户要求修复一个代码缺陷。

Planner 可以生成：

- 复现缺陷；
- 定位根因；
- 修改代码；
- 运行测试；
- 检查回归。

这些都是合理的派生子目标。

但如果系统进一步发现整个项目架构可以重写，就不能把“架构重写”自动视为原始任务的一部分。

它可以提出建议，但这属于范围扩张，应根据影响、授权和预算规则单独判断。

## 3.3 目标必须具有明确的所有者与有效期

建议每个目标至少记录：

- `goal_id`：稳定标识；
- `goal_type`：目标类别；
- `origin`：用户、任务分解、维护规则或主动发现；
- `owner_scope`：目标所属的用户、项目或系统范围；
- `parent_goal_id`：父目标；
- `success_criteria`：成功条件；
- `authorization_ref`：授权依据；
- `priority`：当前优先级；
- `budget_ref`：资源预算；
- `deadline`：可选的截止条件；
- `expiry_policy`：目标失效条件；
- `status`：当前状态；
- `created_at` / `updated_at`：生命周期时间；
- `evidence_refs`：支持目标的证据。

一个长期目标可以持续存在，但它派生出来的每个具体任务都应该有自己的预算、停止条件和执行状态。

# 四、自主程度分级：不是只有“自动”与“手动”两种模式

这是 AGIG 最重要的设计之一。

如果系统所有操作都需要用户确认，它很难真正自主推进任务；如果系统可以自行修改代码、发布技能、调用付费服务和调整治理规则，又会产生过大的风险。

因此，建议采用**按操作类型、风险等级和授权范围组合决定自主程度**，而不是只设置一个全局的“自主性开关”。

## 4.1 建立五级自主执行模式

<box border radius="xl" padding={3} gap={3}>
  {#each [
    ["A0 · 仅建议","可以发现问题、分析原因、提出计划，但不执行有实际影响的变更。"],
    ["A1 · 受控准备","可以读取授权范围内的数据、生成方案、准备补丁和运行无副作用的分析。"],
    ["A2 · 沙箱自主","可以在隔离环境中修改文件、执行测试、生成候选技能和评测结果。"],
    ["A3 · 授权范围内自主执行","可以在明确授权的项目、工具和预算范围内完成操作，并执行必要验收。"],
    ["A4 · 长期目标自主推进","可以持续管理获批目标、安排子任务、等待条件、恢复执行和提出后续改进，但不能突破授权与治理边界。"]
  ] as item}
    <box gap={1}>
      <title size="md">{item[0]}</title>
      <text color="secondary" size="sm">{item[1]}</text>
    </box>
    {#if item[0]!=="A4 · 长期目标自主推进"}
      <divider color="subtle"/>
    {/if}
  {/each}
</box>

这里的 A4 不代表系统拥有无限权限。

即使用户授权长期自主推进，系统仍然不能自行修改权限规则、突破资源上限，或者将一个低风险任务扩展为未经批准的高风险操作。

## 4.2 自主等级必须与操作风险共同判断

例如，同一个 A3 系统可以：

- 在指定代码仓库内修改文件；
- 自动运行单元测试；
- 生成新的技能候选；
- 在授权预算内调用指定模型。

但它不一定可以：

- 将代码推送到公开仓库；
- 删除用户原始文件；
- 购买新的付费服务；
- 发布未经评测的技能；
- 修改全局安全策略。

因此，真正的授权判断应该是一个组合：

\[
\text{Decision}
=
f(\text{Goal},\text{Action},\text{Scope},
\text{Risk},\text{Budget},\text{Approval})
\]

自主等级只是其中一个输入，不是通行证。

## 4.3 建立按动作分类的审批矩阵

| 动作 | 默认建议 |
|---|---|
| 读取授权范围内的项目文件 | 可自动执行 |
| 生成计划、分析报告和补丁候选 | 可自动执行 |
| 在隔离环境运行测试 | 可自动执行，但受资源限制 |
| 修改授权范围内的工作区文件 | 根据用户设置与操作风险决定 |
| 修改正式共享技能 | 必须经过独立验证与受控发布 |
| 修改全局安全、权限或晋升规则 | 不允许由普通自进化流程自行批准 |
| 产生超出授权的费用 | 需要额外授权 |
| 删除重要数据、公开发布或不可逆外部操作 | 根据风险和授权要求进行明确审批 |

这个矩阵应该是可配置的策略，而不是硬编码到各个专家里面。

# 五、目标价值评估：系统如何判断什么值得主动做？

主动机会通常很多，资源却有限。

例如，EvoAgent 在一次代码任务后可能发现：

- 一条错误日志可以优化；
- 一个技能可以减少 Token；
- 一组测试可以补充；
- 一个缓存策略可以调整；
- 一个专家提示词可以改进；
- 一个长期存在的架构缺陷需要重构。

AGIG 必须决定先处理什么。

## 5.1 建立目标价值评估模型

建议将候选目标的价值拆成六个维度：

| 维度 | 评估问题 |
|---|---|
| 预期收益 | 完成后能减少多少错误、时间、费用或维护负担？ |
| 证据强度 | 是否有真实失败记录、稳定指标或明确用户需求？ |
| 紧迫程度 | 是否存在截止时间、持续损失或正在发生的故障？ |
| 影响范围 | 影响一个任务、一个领域，还是多个专家与工作流？ |
| 执行成本 | 需要多少计算、费用、开发工作和测试时间？ |
| 风险与不确定性 | 修复是否可能破坏已有能力，收益估计是否可靠？ |

不要直接将六项分数机械相加。不同任务可能需要不同的风险策略，而且证据不足时不能仅凭较高的预期收益就允许高风险操作。

## 5.2 区分紧急程度与长期价值

例如：

- 正在导致文件损坏的问题，紧急程度很高；
- 一个长期降低代码质量的设计缺陷，可能长期价值很高；
- 一个偶尔出现的低影响格式问题，优先级可能很低；
- 用户正在等待的任务，即使没有系统维护价值，也可能具有更高的当前优先级。

因此，AGIG 应同时管理：

- **紧急队列：** 正在发生的故障、截止时间和关键依赖；
- **用户目标队列：** 当前任务与获批的长期项目；
- **改进机会队列：** 经过证据支持的主动改进；
- **维护队列：** 低紧迫度的整理、评测与维护任务。

这些队列共享全局资源调度，但不能仅凭一个统一分数决定所有任务的先后顺序。

## 5.3 预期收益必须与成功概率关联

假设某项改进预计每个月可以节省 10 小时，但系统对这个估计只有很低的信心。

另一项改进预计每个月节省 4 小时，但有明确日志和可复现的基准测试支持。

第二项改进可能更值得优先执行。

建议采用类似的估算：

\[
V_{\text{expected}}
=
P(\text{success}) \cdot V_{\text{benefit}}
\]

然后再考虑执行成本、机会成本和失败风险。

这不是要求系统精确预测概率，而是要求它明确区分“证据支持的收益”与“未经验证的乐观估计”。

## 5.4 允许目标进入观察状态

不是所有问题都值得立即修复。

对于低频、低影响、证据不足的问题，可以先：

- 收集更多运行证据；
- 建立监测指标；
- 等待下一次相似任务；
- 在未来有空闲资源时运行测试；
- 暂时不采取行动。

这使系统不必在每次发现问题时立即生成复杂改进任务。

# 六、长期任务管理：如何持续推进而不丢失方向？

AGIG 必须支持跨多个执行周期的长期目标。

例如，用户要求 EvoAgent 在未来几周内持续改善编程工作流。

这个目标可能需要多轮执行、等待、测试、失败恢复和用户决策。

不能把它简单实现为一个永不结束的 ReAct 循环。

## 6.1 建立长期目标状态机

建议采用以下状态：

  {#each [

    ["REVIEW · 待评估","已产生候选结果，需要验收或用户决策。"],
    ["COMPLETED · 已完成","所有必要的成功条件均已满足。"],
    ["CANCELLED · 已取消","用户或有效治理流程取消了目标。"],
    ["EXPIRED · 已失效","目标超过有效期，或其前提已经不再成立。"]
  ] as item}
    <box gap={1}>
      <title size="md">{item[0]}</title>
      <text color="secondary" size="sm">{item[1]}</text>
    </box>
    {#if item[0]!=="EXPIRED · 已失效"}
      <divider color="subtle"/>
    {/if}
  {/each}
</box>

这些状态用于描述目标本身，与单个 DAG 节点的执行状态不同。

一个长期目标可以处于 `RUNNING`，但其中某个子任务处于 `WAITING`；整个目标也可能因为关键子任务被阻塞而暂时停止推进。

## 6.2 每次恢复都要重新检查目标是否仍然有效

假设 EvoAgent 开始优化一个模型调用策略，执行到一半后被暂停。

几天后恢复时，系统不能直接从旧检查点继续运行，而应该检查：

- 用户目标是否已经改变；
- 原问题是否仍然存在；
- 依赖的模型和工具是否更新；
- 授权是否仍然有效；
- 预算是否仍然充足；
- 候选改进是否已被其他版本解决；
- 旧计划是否仍然满足当前质量契约。

如果目标已经失去价值，系统应当停止或重新规划，而不是为了完成旧计划继续消耗资源。

## 6.3 长期目标必须有明确的阶段验收

例如，一个长期编程能力改进目标可以分成：

1. 收集真实失败案例；
2. 验证根因；
3. 提出修复候选；
4. 完成独立评测；
5. 受控发布；
6. 观察实际效果；
7. 决定继续、回滚或关闭目标。

每个阶段都应有自己的完成条件。

如果第一阶段没有发现足够证据，系统可以结束本轮探索，而不必强行进入后续阶段。

## 6.4 长期目标不意味着永久执行

任何长期目标都应该有明确的退出条件，例如：

- 达到目标指标；
- 达到预算上限；
- 超过截止时间；
- 连续多轮没有有效进展；
- 关键前提失效；
- 风险超过允许范围；
- 需要用户做出新的决定。

长期目标可以持续存在，但具体执行周期必须有边界。

# 七、停止机制：如何判断应该继续、暂停还是结束？

这是 AGIG 最关键的安全设计之一。

许多智能体可以创建任务，却没有清晰的停止逻辑。它们会反复分析、重复尝试、不断创建子目标，或者在已经得到足够结果后继续调用模型。

建议建立独立的 `GoalStopController`，负责识别终止条件、无进展循环和资源耗尽。

## 7.1 建立六种停止原因

| 停止原因 | 处理方式 |
|---|---|
| `SUCCESS` | 目标已达到验收标准，正常结束 |
| `NO_VALUE` | 预期收益不足以抵消执行成本，结束或归档 |
| `BUDGET_EXHAUSTED` | 预算耗尽，停止执行并报告结果 |
| `AUTHORIZATION_REQUIRED` | 需要额外权限或用户批准，暂停等待 |
| `BLOCKED` | 关键依赖无法满足，暂停或等待条件变化 |
| `NO_PROGRESS` | 多轮执行没有产生有效进展，停止当前策略并诊断 |

另外，还应支持用户取消、目标过期、安全中止和系统关闭等终止条件。

停止不是一种失败。对于证据不足、预算耗尽或授权缺失的任务，及时停止可能是最正确的决策。

## 7.2 无进展检测不能只看文本有没有变化

例如，ReAct 每轮都生成了不同的分析文本，但始终重复调用同一个失败工具。

从文本表面看，系统一直在工作；从任务状态看，却没有任何有效进展。

因此，建议用结构化状态判断进展：

- 是否新增有效证据；
- 是否排除了某个根因；
- 是否完成了一个可验收子目标；
- 是否产生了有效产物；
- 是否减少了剩余不确定性；
- 是否推进了关键依赖；
- 是否发现了必须改变策略的新事实。

如果连续多轮没有有效进展，AGIG 应要求系统调整策略、缩小目标、暂停或结束。

具体阈值应按任务类型配置，不能对所有任务固定使用相同轮数。

## 7.3 防止“为了证明自己有用而继续工作”

假设系统已经修复了一个问题，所有必要测试均通过，用户目标也已完成。

此时，智能体可能继续发现一些非必要的代码优化机会。

这些机会可以记录为候选，但不能自动延长已经完成的任务。

建议将以下两件事分开：

- 当前目标是否已经完成；
- 是否还存在其他值得开展的目标。

完成一个目标后，系统可以提出新的改进建议，但必须重新经过目标价值评估、授权检查和预算分配。

## 7.4 目标取消必须向下传播

如果用户取消一个长期目标，AGIG 需要：

1. 阻止创建新的派生任务；
2. 取消尚未启动的子任务；
3. 通知可取消的运行中任务；
4. 对不可中断的操作采取安全收尾策略；
5. 释放未使用的资源预留；
6. 保存必要的状态和审计记录；
7. 检查等待中的定时任务和条件监控是否仍然有效。

需要注意，取消请求不意味着可以随意终止正在修改文件、提交事务或执行外部副作用的操作。相关操作仍须遵循 RERA 的安全恢复和状态对账规则。

# 八、无限递归与目标膨胀：如何防止智能体不断创造子任务？

EvoAgent 的目标分解、专家协作和自进化机制都可能产生新任务。

例如：

`优化编程能力 → 优化代码技能 → 优化 AST 分析器 → 优化 AST 分析器的评测器 → 优化评测器的优化策略……`

如果没有治理，系统可能把任何潜在改进都视为必须继续推进的目标。

## 8.1 建立目标图，而不是无限嵌套计划

建议使用 `Goal Graph` 管理目标及其依赖关系。

每个目标需要明确：

- 父目标；
- 预期结果；
- 子目标集合；
- 允许的递归深度；
- 任务总预算；
- 截止条件；
- 终止条件；
- 是否允许派生新目标；
- 哪些派生目标需要重新审批。

这可以让系统识别目标之间的关系，避免同一个问题通过不同路径被重复创建。

## 8.2 子目标必须证明其必要性

一个子目标只有在以下条件成立时，才应进入正式执行队列：

- 它确实有助于父目标；
- 它不违反父目标的授权范围；
- 它有明确的完成条件；
- 它具有独立价值或不可替代的必要性；
- 它的成本和风险可以接受；
- 它没有被已有任务或资产覆盖。

如果某个子目标只是“也许还能进一步优化”，但没有明确收益和验证方法，就应作为候选记录，而不是自动启动。

## 8.3 设置多层预算和递归限制

建议同时设置：

- 最大目标分解深度；
- 单个目标的子任务数量上限；
- 单次主动发现的候选数量上限；
- 每轮主动探索预算；
- 每个长期目标的累计预算；
- 每日或每周后台资源上限；
- 同类失败或无进展循环的终止阈值。

这些限制不是为了禁止复杂任务，而是为了保证复杂度与任务价值相匹配。

对于确实需要深度分解的任务，可以由 Planner 在预算范围内提出扩展申请，但不能通过创建更多子目标绕过父目标的资源限制。

## 8.4 防止循环依赖与重复目标

Goal Graph 应支持：

- 检测循环依赖；
- 识别语义重复的目标；
- 合并相同目标的并行请求；
- 将子目标关联到已有长期目标；
- 识别已经完成但再次被创建的目标；
- 对已经失效的父目标阻止继续派生。

需要注意，两个语义相似的目标未必完全相同。自动去重可以提出合并候选，但仍需比较验收条件、授权和范围。

## 8.5 对自我改进目标设置特殊约束

当目标涉及 EvoAgent 自身的模型选择、技能、工作流或进化机制时，必须更加谨慎。

例如：

- 优化一个领域技能，可以作为普通能力改进候选；
- 修改全局任务路由规则，需要评估对所有专家的影响；
- 修改 QEEG 的验收标准，可能影响整个进化系统的可信度；
- 修改 TSEG 的安全规则，不能由普通自进化任务自行批准。

因此，建议将“修改治理机制本身”作为独立的高风险目标类别，并要求独立评测和受保护的审批路径。

# 九、主动发现机制：系统应该从哪里寻找下一步机会？

AGIG 不能只等待系统其他模块递交任务，还需要定义机会发现的来源和触发方式。

建议建立 `OpportunityDetector`，但它主要负责发现和整理候选，而不是直接执行所有改进。

## 9.1 五类机会来源

机会也可以来自用户明确表达的长期目标，例如“持续改善代码生成质量”。

但机会发现必须依赖真实证据和明确目标，不能仅仅因为系统有空闲资源，就不断创建新的优化项目。

## 9.2 机会候选必须具有证据

建议每个 `OpportunityRecord` 至少包含：

- 问题描述；
- 来源事件或指标；
- 影响范围；
- 初步根因假设；
- 预期收益；
- 估计成本；
- 风险与不确定性；
- 建议行动；
- 建议验证方法；
- 是否需要用户批准；
- 失效或重新评估条件。

如果缺少可靠证据，可以先创建观察任务，而不是直接创建修复任务。

例如，单次响应变慢可能来自网络抖动，不应立即修改模型调度器。系统可以先收集更多数据，判断问题是否重复发生。

## 9.3 机会合并与优先级管理

多个模块可能发现同一个问题。

例如，GECO 发现代码任务耗时增加，APRO 发现模型调用次数增加，QEEG 发现某些任务的返工率上升。

它们可能指向同一个根因：某个技能升级后，输出质量下降，导致重复调用。

AGIG 应将这些线索关联到同一机会记录，避免分别创建三个独立的优化项目。

但在根因尚未确认前，这些记录应保持为相关证据，而不是直接认定它们一定由同一个问题造成。

# 十、授权与审批：怎样让系统主动行动，但不越权？

AGIG 必须与 TSEG 紧密协作。

这里最重要的设计不是让用户每次都审批，而是让用户能够预先定义一个明确的自主执行范围。

## 10.1 建立授权范围模型

建议每项长期目标都关联一个 `AutonomyPolicy`，明确：

- 允许访问的项目与数据；
- 允许使用的工具；
- 允许修改的文件或资源范围；
- 允许调用的模型与外部服务；
- 费用与计算预算；
- 允许执行的操作类型；
- 必须人工确认的动作；
- 授权的有效期；
- 撤销与紧急停止规则。

授权必须具体到可以检查的范围。

例如，“可以自主优化编程能力”过于宽泛。更合理的授权可以是：允许在指定工作区创建候选技能、运行测试、生成评测报告，但正式发布共享技能仍须经过受控晋升流程。

## 10.2 审批不能被无限拆分绕过

假设一个操作需要用户批准，智能体不能通过将其拆成多个看似低风险的子任务来绕过审批。

例如，用户没有授权公开发布代码，系统不能通过“创建公开仓库”“上传文件”“发布版本”三个独立子任务，间接完成未经授权的发布。

因此，授权检查需要考虑：

- 当前动作；
- 动作组合后的实际效果；
- 父目标与整体任务；
- 可能产生的外部副作用；
- 已经使用的授权额度；
- 是否改变了数据或信任边界。

## 10.3 审批请求应该说明具体影响

当系统需要用户批准时，不应只问“是否允许继续”。

建议展示：

- 目标是什么；
- 为什么需要这一步；
- 将执行哪些操作；
- 会修改哪些文件或资源；
- 预计费用与时间；
- 可能的风险；
- 有什么替代方案；
- 如果拒绝，任务将怎样处理。

这能让用户做出有信息依据的决策，而不是反复确认抽象的权限请求。

## 10.4 授权变化必须立即影响运行中的目标

如果用户撤销了某个工具的使用权限，所有依赖该工具且尚未完成的目标都需要重新评估。

系统应阻止新调用，并对运行中的操作采取适当的安全收尾策略。

授权不能只在任务创建时检查一次，而应在执行关键动作之前重新确认。

# 十一、与 APRO 的协作：前台任务、后台任务和主动改进怎样竞争资源？

AGIG 负责决定某个目标是否值得推进，APRO 负责安排它如何使用资源。

两者不能各自维护一套互不兼容的优先级系统。

## 11.1 建立统一工作负载队列

建议把工作负载分为：

- 用户当前交互；
- 用户明确委托的执行任务；
- 已获批的长期目标；
- 必要的系统维护；
- 主动发现的改进候选；
- 后台评测与进化实验。

每个工作负载都应有资源预算、优先级、截止条件和可暂停性。

## 11.2 主动任务应采用剩余资源策略

对于个人电脑、手机和微型 Linux 主机，建议默认采用：

- 前台交互优先；
- 必要的安全和状态持久化不被普通任务阻塞；
- 已获批且接近关键里程碑的任务优先于低价值探索；
- 后台维护在资源允许时执行；
- 主动改进和批量评测优先使用剩余资源。

但“剩余资源策略”不意味着所有后台任务都必须等待前台完全空闲。如果一个重要的长期目标有明确期限，系统可以根据预先设定的调度政策分配资源。

## 11.3 任务暂停后必须保留恢复条件

当资源不足时，系统可以暂停主动任务。

恢复时应重新检查：

- 目标是否仍然有效；
- 当前授权是否有效；
- 预算是否仍有余额；
- 依赖和产物是否仍然兼容；
- 是否有更高优先级任务；
- 是否需要重新规划。

如果用户正在使用本地模型，后台评测任务可以释放模型资源，而不是为了维持自身运行影响用户体验。

## 11.4 防止后台任务永远得不到执行

如果所有后台任务都采用低优先级，它们可能长期被前台任务压制。

对于确实需要持续推进的长期目标，可以使用受控的资源配额或公平调度机制。

但这种机制应有上限，并且不能突破安全控制、用户明确优先级和设备资源约束。

# 十二、结果反馈：主动行动之后，怎样知道是否值得？

主动任务完成后，AGIG 不应该只记录“任务结束”。

它需要知道：

- 原始问题是否解决；
- 预期收益是否兑现；
- 是否引入了新问题；
- 实际成本是否超出预期；
- 是否值得继续推进类似任务；
- 是否应该将经验沉淀为知识或技能。

## 12.1 建立主动任务结果记录

建议建立 `GoalOutcomeRecord`，至少包含：

| 字段 | 作用 |
|---|---|
| `goal_id` | 关联目标 |
| `completion_status` | 成功、失败、取消、阻塞或未能确认 |
| `acceptance_evidence` | 支持完成结论的证据 |
| `actual_cost` | 实际时间、费用与资源消耗 |
| `expected_benefit` | 执行前预估的收益 |
| `observed_benefit` | 执行后可观察的实际收益 |
| `regression_results` | 相关回归测试和质量检查结果 |
| `side_effects` | 实际产生的副作用 |
| `follow_up_needed` | 是否需要继续观察或后续行动 |
| `decision_record` | 为什么继续、停止、回滚或归档 |

结果记录应由真实执行证据和独立验收共同支持，不能只依赖智能体对自己表现的描述。

## 12.2 区分任务完成与目标价值实现

例如，系统完成了一个缓存优化任务，代码已经合并，测试也通过了。

这说明技术交付可能已经完成，但不一定证明实际运行成本已经降低。

要证明收益，还需要观察：

- 缓存命中率是否改善；
- 总任务耗时是否降低；
- 内存占用是否增加；
- 是否产生更多过期结果；
- 真实任务的失败率是否变化。

因此，某些目标可以在“实现完成”后进入观察阶段，等有足够证据后再关闭。

## 12.3 结果反馈必须回流到正确的模块

- GECO 接收实际执行事件；
- QEEG 评估目标是否达到质量要求；
- APRO 更新成本与性能估计；
- RERA 更新故障和恢复证据；
- KCLG 判断是否需要沉淀新的知识、技能或评测案例；
- AGIG 更新目标状态、后续优先级与停止条件；
- SELCIA 决定是否发布经过验证的改进。

这种分工能够避免 AGIG 直接修改其他模块的内部策略，保持整个架构的职责边界。

# 十三、AGIG 的关键数据结构与接口

进入工程实施前，建议先确定以下核心对象。

## 13.1 `GoalRecord`

表示一个用户目标、系统维护目标或经过评估的主动目标。

主要包含：

- 目标 ID 与类型；
- 目标来源和所属范围；
- 成功条件；
- 父目标与子目标；
- 当前状态；
- 授权引用；
- 预算引用；
- 截止与失效条件；
- 依赖关系；
- 结果与证据引用。

## 13.2 `OpportunityRecord`

表示系统发现的潜在改进机会。

主要包含：

- 问题描述；
- 证据来源；
- 影响范围；
- 初步根因假设；
- 预期收益；
- 执行成本；
- 风险与不确定性；
- 建议行动；
- 建议验证方式；
- 是否需要审批；
- 是否与已有机会重复。

## 13.3 `AutonomyPolicy`

定义某类目标或操作允许的自主执行范围。

主要包含：

- 允许的操作类型；
- 可访问的数据范围；
- 可使用的工具；
- 费用与计算预算；
- 必须审批的动作；
- 有效期；
- 撤销条件；
- 安全停止策略。

## 13.4 `GoalExecutionPlan`

表示一个已获准目标的执行安排。

主要包含：

- 目标与计划版本；
- 子任务 DAG；
- 优先级；
- 资源预算；
- 执行位置；
- 等待条件；
- 检查点；
- 重规划条件；
- 停止条件；
- 验收契约。

## 13.5 `GoalOutcomeRecord`

表示目标执行后的结果与实际收益。

主要包含：

- 完成状态；
- 验收证据；
- 实际成本；
- 预期与实际收益；
- 失败与副作用；
- 后续观察要求；
- 停止、回滚或继续推进的依据。

这五个对象构成 AGIG 的核心数据契约。实际工程中还需要定义持久化结构、事件协议、状态转换校验与并发控制。

## 15.1 第一版必须通过的端到端验收测试

建议使用一个明确的长期目标：改善 EvoAgent 的代码修复工作流。

1. 用户授权系统在指定工作区内持续分析代码修复失败。
2. AGIG 创建长期目标，明确成功条件、预算、允许操作和停止条件。
3. GECO 收集真实失败案例，QEEG 识别可验证的质量问题。
4. AGIG 将证据整理为改进机会，并评估优先级。
5. 系统在授权范围内生成候选修复方案。
6. QEEG 在隔离环境中评测候选方案。
7. 如果方案通过验证，提交给 SELCIA 走受控发布流程。
8. 如果预算不足或出现无进展，AGIG 暂停并说明原因。
9. 如果用户撤销授权，系统阻止新的相关操作并安全处理正在运行的任务。
10. 运行一段时间后，系统根据真实结果判断改进是否有效，以及是否值得继续推进。

验收标准不只是“系统能够持续工作”，而是：

**系统能够主动发现有价值的工作，合理分配资源，在授权范围内推进，并在目标完成、收益不足、风险升高或条件不再成立时正确停止。**

# 十六、下一专项：全系统架构一致性审计与设计冻结

到这里，EvoAgent 已经连续完成了多个专项的设计。现在有必要暂时改变推进方式。

之前的工作主要是不断发现新问题、补充模块、深化专项。这样能够扩大设计覆盖面，但也会带来一个风险：**每个专项单独看起来都合理，组合起来却可能出现职责重叠、接口不一致、状态重复、治理链条过长等问题。**

例如：

- GECO 和 QEEG 都需要保存证据，它们分别保存什么？
- AGIG、Planner 和 APRO 都会影响任务执行顺序，谁拥有最终调度权？
- KCLG、CEKCE 和 CIL 都涉及能力资产，注册、治理和调用的边界在哪里？
- RERA、DAG 执行器和 AGIG 都能暂停任务，三者如何协作？
- SELCIA 负责发布改进，QEEG 负责评测，TSEG 负责安全门槛，谁最终批准一个版本进入正式运行？
- 用户记忆、项目知识、技能经验和任务上下文之间，是否存在重复存储与相互污染？
- 如果设备离线，哪些模块必须继续工作，哪些可以延迟？

这些问题不是继续增加新模块就能解决的，而是需要一次全系统审计。

## 16.2 设计冻结不等于停止进化

设计冻结的含义是：在一个明确的版本范围内，固定核心职责、关键接口、状态模型和安全边界。

后续仍然可以新增技能、专家、工作流、评测器和优化策略，但不应因为每次发现一个新需求，就重新设计整个系统。

对于 EvoAgent，我建议将核心架构和可进化能力分开治理：

- **稳定内核：** 任务身份、权限、状态持久化、事件、预算、恢复和发布治理；
- **可进化层：** 专家、技能、模型路由、工作流、领域评测和优化策略；
- **实验层：** 尚未验证的候选技能、候选策略和新能力。

稳定内核负责约束进化，可进化层负责持续提高能力，实验层负责探索新方案。

这样才能避免系统在持续改进自己的同时，把自身的基础运行机制也变成随时可能失效的实验品。

**下一步建议正式进入全系统架构一致性审计，而不是继续无限增加专项。** 审计完成后，我们再根据依赖关系和实施价值确定 V0.1 的工程边界，把已经讨论的大量设计收敛为一套职责清晰、接口统一、能够在个人电脑或微型 Linux 主机上逐步实现的 EvoAgent 架构。
