**专项编号：** #76  
**专项名称：** Dependency Graph & Change Impact Propagation Governance  
**中文名称：** 依赖图与变更影响传播治理  
**版本：** 1.0  
**所属体系：** EvoAgent 自进化智能体专项设计集  
**关联专项：** #75 MTRC-CCR 模型、工具与运行时兼容性治理  
**设计性质：** 正式专项设计提案，待纳入现有专项基线

## 一、专项目标

建立一套统一的依赖关系与变更影响治理机制，使 EvoAgent 在模型、工具、专家、工作流、共享内核、数据契约、评测规则或运行环境发生变化时，能够回答六个问题：

1. 哪些能力直接受到影响？
2. 哪些其他能力可能受到间接影响？
3. 哪些测试必须重新执行？
4. 哪些稳定能力可以继续运行？
5. 哪些能力必须暂时禁止新任务使用？
6. 哪些变更可以安全发布，哪些必须阻止或回滚？

本专项不是单纯维护一张依赖关系图，而是将依赖关系与兼容性检查、回归测试、版本发布、运行隔离和用户可见能力状态关联起来。

**核心目标：用可验证的依赖关系确定影响范围，以风险决定验证强度，以测试证据决定是否允许发布。**

## 二、与 #75 的职责边界

两个专项相互依赖，但不能合并为一个职责不清的模块。

| 比较维度 | #75 MTRC-CCR | #76 依赖图与变更影响传播 |
|---|---|---|
| 核心问题 | 当前组件组合是否兼容 | 发生变更后哪些对象受到影响 |
| 输入 | 具体组件版本、兼容性声明、运行环境 | 变更对象、变更内容、依赖图 |
| 主要计算 | 兼容性判定 | 影响范围与传播路径 |
| 测试职责 | 提供兼容性测试要求和证据 | 决定哪些相关测试需要执行 |
| 发布职责 | 提供兼容性证据 | 汇总影响范围，阻止遗漏验证 |
| 运行职责 | 识别不兼容组合 | 识别受影响能力并协调暂停、降级或恢复 |

举例来说：

一个工具的输出 Schema 发生变化。

- #76 找出所有依赖该工具的工作流、专家和能力包。
- #75 检查新 Schema 与这些依赖的具体版本是否兼容。
- 独立评测控制器决定必要的回归测试是否通过。
- 发布控制器决定候选版本是否可以晋级。
- 运行时控制器负责执行任务准入、停止和恢复规则。

任何单个模块都不能独立完成整个决策链。

## 三、依赖图的统一数据模型

### 3.1 节点类型

依赖图复用现有能力资产注册表和数据契约，不建立第二套独立的资产身份体系。

| 节点类型 | 示例 | 需要追踪的内容 |
|---|---|---|
| `model_profile` | 模型档案 | 模型能力、适配器、限制 |
| `tool` | 文件读取工具 | 输入输出契约、权限、副作用 |
| `skill` | 代码分析技能 | 执行要求、依赖工具 |
| `workflow` | 报告生成流程 | DAG 节点、执行顺序、验收 |
| `expert` | 编程专家 | 专用工具、记忆策略、评测集 |
| `capability_pack` | AI 漫剧能力包 | 多项能力及其依赖 |
| `runtime_adapter` | Native 或其他运行时适配器 | 运行协议和执行行为 |
| `interface_schema` | 工具输入输出契约 | Schema 版本、兼容规则 |
| `evaluation_suite` | 回归评测集 | 测试范围、版本和门禁 |
| `context_policy` | 上下文治理策略 | 压缩、保留和来源规则 |
| `router_policy` | 路由策略 | 候选选择和回退规则 |
| `core_component` | 受保护共享内核组件 | 全局依赖与保护级别 |
| `release_manifest` | 发布清单 | 发布资产、版本和回滚目标 |

其中，`runtime_adapter`、`interface_schema`、`context_policy`、`router_policy` 和 `core_component` 可以作为依赖图的逻辑节点或现有组件的关联对象。它们不必全部成为新的独立资产类型。

### 3.2 节点身份

每个正式资产应当通过稳定的资产标识和不可变版本进行定位。

例如：

- `asset_id = code-expert`
- `version = 1.2.0`

同一资产的两个版本是不同的图节点。

如果只用 `code-expert` 作为节点标识，就无法准确回答某个历史任务实际依赖的是哪个版本。

因此，依赖图的正式节点身份应当对应：

`asset_id + version`

对于非资产类节点，则使用现有契约标识、版本和内容摘要等字段建立稳定身份。

### 3.3 依赖边的方向

统一采用以下约定：

**消费者指向提供者。**

例如：

`编程专家 → 代码分析工作流 → AST 工具`

表示编程专家依赖代码分析工作流，而工作流依赖 AST 工具。

这样，当 AST 工具发生变更时，系统只需沿着依赖边的反方向查找消费者，就能得到可能受影响的能力。

禁止不同模块各自采用不同的依赖方向，否则变更传播结果将不可预测。

## 四、依赖边的类型与语义

并不是所有依赖都具有相同的影响程度。

### 4.1 六种主要依赖类型

| 类型 | 含义 | 示例 |
|---|---|---|
| `required_runtime` | 执行时必须存在 | 工作流依赖文件读取工具 |
| `interface_contract` | 依赖特定接口或 Schema | 工具调用依赖输入 Schema |
| `capability_requirement` | 需要某种能力 | 视觉任务需要图像理解 |
| `data_contract` | 依赖数据结构或语义 | 任务状态依赖事件 Schema |
| `quality_gate` | 依赖评测或验收规则 | 专家发布必须通过领域回归集 |
| `optional_fallback` | 可选依赖，失效后允许降级 | 云端服务不可用时使用受限离线能力 |

每条依赖边至少应记录：

- 消费者与提供者的版本引用；
- 依赖类型；
- 是否为必需依赖；
- 版本与能力约束；
- 影响级别；
- 降级策略引用；
- 依赖声明来源；
- 验证证据引用。

不应将所有依赖简单存成一个无语义的 ID 列表。现有 `dependency_refs` 可以继续作为依赖引用来源，但依赖类型、约束和验证结果需要有明确的结构化表达。

### 4.2 必需依赖与可选依赖

如果专家依赖某个必需工具，工具不兼容时，专家相关执行路径必须阻止新任务进入。

如果依赖是可选增强能力，则可以在满足以下条件时继续运行：

- 降级路径已经明确声明；
- 降级后的任务仍满足用户的必要要求；
- 权限和安全边界没有被扩大；
- 最终结果仍经过适用的验收。

如果用户要求实时资料，而系统仅能提供离线资料，就不能把降级结果宣称为完整的实时研究成果。

## 五、变更事件模型

依赖图不能只在发布时更新，还必须接收所有会改变能力行为或兼容性的变更事件。

### 5.1 变更类型

| 变更类别 | 示例 | 默认影响判断 |
|---|---|---|
| 实现变更 | 修复工具内部错误 | 需要评估行为与回归影响 |
| 接口变更 | 修改 Schema | 检查直接接口消费者及其传递依赖 |
| 能力变更 | 模型新增或失去工具调用能力 | 检查能力需求匹配 |
| 策略变更 | 修改 Router Policy | 检查路由结果与专家分布 |
| 数据变更 | 修改事件或记忆 Schema | 检查读写方、迁移和恢复 |
| 运行时变更 | 升级 Runtime Adapter | 检查所有相关执行路径 |
| 权限变更 | 调整工具所需权限 | 检查准入规则和授权路径 |
| 评测变更 | 修改验收规则 | 检查门禁、历史可比性和发布流程 |
| 资源变更 | 调整预算或超时策略 | 检查受影响任务的可完成性 |
| 退役变更 | 停用某个工具版本 | 检查活跃依赖和恢复路径 |

### 5.2 变更记录

每次变更应形成一个可追踪的变更记录，至少包含：

- `change_id`；
- 变更对象及其旧、新版本；
- 变更类别；
- 变更内容摘要；
- 变更来源；
- 变更原因；
- 关联候选版本；
- 风险等级；
- 依赖图快照或摘要；
- 影响分析结果；
- 必须执行的测试；
- 最终发布或拒绝结论。

`change_id` 是本专项建议新增的逻辑标识，实施时应沿用现有事件和资产版本体系。

### 5.3 变更内容不能只靠版本号判断

同一个版本号变化可能代表完全不同的风险。

例如：

- 修改内部日志格式；
- 改变工具输出字段的含义；
- 修改权限检查路径；
- 更换模型供应商；
- 调整共享内核的任务状态转换。

系统应尽可能结合 Schema 差异、配置差异、代码变更摘要、依赖声明和测试结果确定影响，而不是仅凭版本号增加了一个小版本或大版本作出结论。

## 六、影响传播算法

### 6.1 影响分析流程

```text
收到变更事件
    ↓
确定变更对象与版本
    ↓
读取对应依赖图版本
    ↓
检查直接消费者
    ↓
递归分析传递消费者
    ↓
合并依赖类型与风险信息
    ↓
确定受影响资产集合
    ↓
生成候选回归测试集合
    ↓
检查保护级别与硬性门禁
    ↓
形成影响分析报告
```

### 6.2 影响传播规则

当节点 B 发生变化时，系统沿反向依赖寻找直接依赖 B 的消费者，然后继续查找这些消费者的消费者。

例如：

`AST 工具 → 代码分析工作流 → 编程专家 → 编程能力包`

如果 AST 工具发生接口变更：

- 代码分析工作流是直接受影响对象；
- 编程专家是传递受影响对象；
- 编程能力包也可能受影响；
- 其他不依赖这条链路的旅游专家，不应仅因 AST 工具变更而自动被判定为受影响。

注意：以上是按反向依赖关系描述传播路径，正式图中的边方向仍采用消费者指向提供者的约定。

### 6.3 影响范围分级

建议将影响对象分为四级。

| 级别 | 定义 | 处理策略 |
|---|---|---|
| I0：直接影响 | 变更对象及其直接契约消费者 | 必须验证 |
| I1：传递影响 | 通过依赖链受到影响的消费者 | 根据依赖类型与风险确定验证范围 |
| I2：潜在影响 | 存在间接关联，但尚未证实会发生行为变化 | 检查证据，必要时执行针对性测试 |
| I3：无影响证据 | 依赖图和契约证明不存在相关依赖 | 可以排除本次变更的专项回归 |

I3 不能用于绕过全局强制回归集。

例如，某项修改与安全规则无关，并不意味着发布时可以跳过所有核心安全测试。

### 6.4 影响分析必须具备闭包性质

如果 A 依赖 B，B 依赖 C，那么 C 发生相关变更时，系统不能只检查 B 而遗漏 A。

依赖图应当计算完整的传递影响闭包，并保留传播路径，便于解释为什么某个资产被纳入测试范围。

如果路径中存在可选依赖，则应结合其降级声明判断，而不是无条件阻断全部消费者。

### 6.5 循环依赖处理

正式能力依赖图应尽量采用无循环的执行依赖结构。

如果发现循环依赖：

- 不得无限递归传播；
- 应记录具体的循环路径；
- 对新候选资产，默认拒绝进入稳定通道，直到依赖关系得到解决或被显式建模；
- 对历史资产，进入兼容性检查和影响评估流程；
- 如果循环来自合法的协作关系，应将其建模为明确的组合单元，而不是隐藏循环。

传播算法必须维护访问集合，并对同一节点去重。

## 七、如何决定需要重跑哪些测试

影响分析的价值，不只是列出受影响对象，而是找出最小且充分的测试集合。

### 7.1 测试映射

每个资产应声明其适用的测试集合，并明确测试覆盖的能力、接口和依赖范围。

例如：

- AST 工具：输入输出契约测试、代码解析正确性测试；
- 代码分析工作流：节点集成测试、失败恢复测试；
- 编程专家：代码任务成功率与安全回归测试；
- 共享内核：任务状态、预算、取消和恢复的核心测试；
- 发布流程：兼容性、签名、回滚和健康检查测试。

测试与资产之间应存在显式关联，不能只依靠文件名称或人工记忆确定。

### 7.2 测试选择规则

变更发生后，测试集合由四部分构成：

\[
T_{\text{required}} =
T_{\text{direct}}
\cup T_{\text{transitive}}
\cup T_{\text{risk}}
\cup T_{\text{core}}
\]

其中：

- \(T_{\text{direct}}\)：直接受影响资产的测试；
- \(T_{\text{transitive}}\)：传递受影响资产的测试；
- \(T_{\text{risk}}\)：根据风险增加的针对性测试；
- \(T_{\text{core}}\)：每次正式发布都必须执行的核心回归集。

最终测试集合必须去重，但不能因为某项测试在多个类别中重复出现，就将其删除出必要的执行范围。

### 7.3 测试选择示例

假设修改了一个代码分析工具：

1. 必须执行该工具的契约测试；
2. 执行直接依赖它的工作流集成测试；
3. 执行受到影响的编程专家回归测试；
4. 执行必要的共享内核和工具调用安全测试；
5. 执行固定的核心安全回归集；
6. 根据变更类型决定是否需要全量测试。

如果变更触及共享内核、权限、任务状态机或发布门禁等关键区域，应扩大测试范围，必要时执行完整系统回归。

### 7.4 测试结果复用

历史测试结果可以复用，但必须满足：

- 被测试资产版本一致；
- 相关依赖版本一致；
- 环境条件符合要求；
- 测试定义和门禁版本一致；
- 结果仍在有效期内；
- 不存在要求强制重新验证的变更。

不允许将旧版本的通过结果直接作为新版本的兼容性证据。

## 八、变更风险评估与准入

影响范围大，不一定意味着变更风险最高；影响范围小，也不意味着变更安全。

因此，风险评估应同时考虑：

- 受影响资产数量；
- 影响路径的深度；
- 组件的重要程度；
- 是否触及共享内核；
- 是否触及权限和安全规则；
- 是否改变数据 Schema；
- 是否影响正在运行的任务；
- 兼容性证据是否充分；
- 回滚是否可行。

### 8.1 关键保护级别

建议为资产增加或关联以下保护级别：

- `protected_core`：共享内核与关键控制机制；
- `shared_critical`：被多个专家共享的关键能力；
- `domain_critical`：特定领域不可缺少的能力；
- `domain_optional`：可选领域能力；
- `experimental`：实验资产。

保护级别应与现有资产命名空间和生命周期分开管理，不能把命名空间直接当作风险等级。

### 8.2 高风险变更规则

涉及以下内容时，应默认进入严格评审：

- 全局权限策略；
- Action Guard；
- Task of Record；
- 任务状态机；
- 副作用账本；
- 预算强制执行；
- 评测门禁；
- 发布控制器；
- 数据完整性；
- 安全相关工具契约。

这些变更必须执行相应的核心回归测试，并获得独立的门禁结论。

### 8.3 低风险变更规则

低风险变更也必须有证据。

只有当依赖分析完整、变更范围明确、必需测试通过、发布和回滚条件满足时，才可以进入受控自动准入范围。

“改动文件少”“只改了提示词”或“没有改接口”都不能单独作为低风险的充分证据。

## 九、正在运行的任务如何处理

依赖图变更不能直接改写已经启动的任务。

### 9.1 普通兼容性变更

任务运行绑定的 `Runtime Manifest` 保持不变。

新版本仅影响后续任务或经过明确迁移流程的恢复任务。已有运行不应因为某个候选资产发布，就在执行中静默切换到新组件。

### 9.2 发现严重安全缺陷

如果新发现的缺陷使当前组件继续运行存在严重安全风险，则安全撤销策略优先于普通版本固定策略。

系统应：

1. 识别所有受影响的运行；
2. 阻止新增的危险动作；
3. 根据动作可取消性停止或隔离执行；
4. 对已提交的外部副作用进行状态核对；
5. 保存必要的运行证据；
6. 通知用户相关任务已被暂停或受限；
7. 仅在修复并重新验证后恢复。

版本固定是为了保证可复现性，不是要求系统继续执行已经确认不安全的动作。

### 9.3 旧版本恢复

恢复旧版本时，必须检查旧版本是否仍满足当前的安全、权限和运行环境要求。

如果旧版本已经被撤销或存在不可接受的安全缺陷，就不能仅因为它是历史稳定版本而恢复。

## 十、变更影响报告

每次影响分析都应形成可追溯报告。

建议字段包括：

- `change_id`；
- 变更对象及版本；
- 图快照或图摘要版本；
- 直接影响资产；
- 传递影响资产；
- 传播路径；
- 影响级别；
- 受影响的运行和任务模板；
- 必须执行的测试集合；
- 可复用的有效测试证据；
- 需要暂停或限制的能力；
- 兼容性判定结果；
- 未解决的风险；
- 发布建议；
- 回滚目标；
- 最终审批和发布结果。

报告必须说明为什么某个资产被纳入或排除。

不能只输出一份无解释的资产 ID 列表。

## 十一、与用户产品的连接

依赖图和影响传播不应只存在于后台管理界面。

它需要决定用户能否继续使用某项能力，以及遇到问题时系统如何解释。

### 11.1 能力可用状态

当某个可选工具升级失败时，系统可以只限制依赖该工具的功能，而不影响其他无关专家。

当共享内核发生严重问题时，则需要根据实际影响范围暂停更广泛的能力。

### 11.2 任务启动前

系统应当根据当前批准的资产组合检查必要依赖。

如果某项能力暂时不可用，用户应看到明确原因和替代路径，而不是先启动任务，再在执行中暴露可预见的依赖缺失。

### 11.3 后台进化期间

候选版本及其影响分析不会直接改变稳定产品。

只有经过兼容性检查、必要回归测试和发布门禁后，才能按批准策略更新稳定能力。

### 11.4 产品验收

- 无关专家不因无关变更被无依据地全部禁用；
- 必需依赖失效时，不会继续承诺完整能力；
- 用户任务不会被候选版本无约束地切换；
- 重要功能降级有明确说明；
- 严重安全问题能够触发及时的能力限制；
- 已验证的无影响结论可以用于减少不必要的回归成本。

## 十二、与其他专项的接口关系

| 专项或模块 | #76 的交互方式 |

| 统一事件与诊断体系 | 接收变更事件和运行时故障证据 |

| Evaluation Gate Controller | 判断必需证据是否满足准入条件 |

## 十三、验收测试矩阵

| 测试 ID | 场景 | 通过标准 |
|---|---|---|
| DEP-01 | 单个工具发生变更 | 找到全部直接消费者 |
| DEP-02 | 存在三层以上依赖 | 找到完整传递影响闭包 |
| DEP-03 | 存在可选依赖 | 根据明确的降级策略判断影响 |
| DEP-04 | 存在循环依赖 | 终止传播并输出具体循环路径 |
| DEP-05 | 共享内核发生变更 | 扩大影响分析和必要回归范围 |
| DEP-06 | 无关领域专家没有依赖该变更 | 不被无依据地纳入专项影响集合 |
| DEP-07 | 测试结果来自旧版本 | 不被当作新版本的有效证据 |
| DEP-08 | 候选只通过单元测试 | 仍执行必要的组合和风险测试 |
| DEP-09 | 必需测试未执行 | 不允许正式晋级 |
| DEP-10 | 严重安全缺陷影响在途任务 | 触发适用的安全停止或限制策略 |
| DEP-11 | 普通候选发布失败 | 稳定版本和无关能力不受影响 |
| DEP-12 | 影响分析发现不完整依赖声明 | 标记不确定性并要求补充验证 |
| DEP-13 | 回滚目标已失效 | 不得宣称具备有效回滚保障 |
| DEP-14 | 变更报告生成 | 每项纳入和排除结论可追溯 |
| DEP-15 | 重复接收同一变更事件 | 不重复创建相互冲突的变更记录 |
| DEP-16 | 依赖图与资产注册表不一致 | 阻止依赖该不一致信息的关键发布 |

### 系统级验收要求

1. 影响传播能够在有限时间内终止。
2. 同一图版本、同一变更输入和同一规则版本能够产生可解释的一致结果。
3. 所有关键依赖都能追溯到资产或正式契约。
4. 未知依赖不能被默认为不存在。
5. 必要回归测试不能因优化测试选择算法而被省略。
6. 影响分析失败时，关键发布不得默认放行。
7. 任何测试未执行的结果必须明确标记为未验证。

## 十四、性能与成本治理

依赖图规模会随专家、工具、工作流和版本持续增长。因此需要避免每次小改动都扫描和测试整个系统。

建议采用以下机制：

- 按资产版本保存依赖图快照；
- 对未发生变化的依赖子图复用有效计算结果；
- 对新增或修改的依赖执行局部重算；
- 缓存变更影响结果，但严格绑定图版本与规则版本；
- 只对受影响的测试集合执行增量回归；
- 对共享内核、安全规则和其他关键路径保留强制回归集；
- 对依赖缺失、声明不完整或证据过期的情况采用保守策略。

效率优化不能降低门禁强度。

如果系统无法证明某个依赖不存在，就不能仅为了减少测试成本而将其视为不存在。

## 十五、核心监控指标

| 指标 | 说明 |
|---|---|
| 影响识别召回率 | 实际受影响资产中被成功识别的比例 |
| 影响识别精确率 | 被判定受影响的资产中确实相关的比例 |
| 依赖声明完整率 | 正式资产中依赖声明完整的比例 |
| 必要测试覆盖率 | 必须执行的测试中实际执行的比例 |
| 影响分析耗时 | 从变更输入到报告生成的时间 |
| 增量测试节省量 | 相对于规定基线减少的测试资源 |
| 发布后依赖故障率 | 发布后由依赖问题导致的故障比例 |
| 回滚触发率 | 因变更造成退化而回滚的比例 |
| 未知依赖阻塞率 | 因依赖证据缺失而无法判定的比例 |

指标应按资产类型、变更类别、影响级别和发布版本分别分析。

不能单纯追求更少的测试、更低的阻塞率或更少的回滚。真正目标是减少不必要的验证成本，同时不增加遗漏故障的风险。

## 十六、实施顺序

### 阶段 1：依赖声明标准化

梳理现有 `dependency_refs` 和兼容性字段，统一依赖方向、依赖类型、版本约束和必要性声明。

### 阶段 2：依赖图与传播引擎

建立版本化依赖图、反向索引、传递闭包计算、循环检测和影响报告。

### 阶段 3：测试关联

将资产、依赖边和回归测试集建立正式关联，实现必要测试的自动选择与去重。

### 阶段 4：接入进化和发布控制

让候选变更自动生成影响分析报告，并由独立评测门禁和发布控制器作出最终决策。

### 阶段 5：接入用户能力状态

将受影响范围转换为可理解的能力状态、任务准入条件和恢复提示。

## 十七、完成判定

本专项设计完成的条件是：

1. 统一的资产依赖图能够表达直接和传递依赖。
2. 变更事件能够产生可追溯的影响分析报告。
3. 影响传播可以识别循环、缺失依赖和不确定性。
4. 测试选择能够覆盖直接影响、传递影响、风险测试和核心回归集。
5. 无关能力能够在有证据的情况下避免不必要的停用。
6. 严重安全变更能够触发适当的运行限制。
7. 候选版本不会因影响分析或测试选择失败而绕过发布门禁。
8. 用户可见能力状态能够反映实际依赖情况。
9. 所有正式结论都有对应的版本、图快照、测试证据和发布记录。
10. 关键验收用例已通过真实测试，而不是仅完成文档编写。

**最终结论：#76 使 EvoAgent 能够在持续进化中准确控制变更的影响范围。它既防止一个局部修改悄然破坏其他专家，也避免每次优化都迫使整个系统停摆。通过依赖图、增量验证和独立发布门禁，系统可以在保持核心质量与稳定性的前提下持续扩展能力。**</WritingBlock>

## 下一项专项

按照当前连续设计序列，下一项建议推进 **#77：回归测试选择、覆盖追踪与测试证据治理**。

#76 解决“哪些资产受到影响”，#77 则进一步解决“如何证明这些资产经过了充分测试”。两者需要形成闭环：影响分析产生测试范围，测试执行产生证据，独立门禁根据证据决定是否允许发布。

这一专项还需要重点处理一个自进化系统特有的问题：随着专家、工具和工作流不断增加，测试集也会持续增长。系统必须在不牺牲核心安全覆盖的前提下，减少冗余测试、发现覆盖盲区，并确保每次质量提升都有可信的对比基线。
