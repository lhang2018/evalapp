# EvoAgent 第十八专项：任务编排、动态 DAG 与 ReAct 协同治理

这一轮我们要把前面设计的专家系统、Planner、ReAct、记忆、上下文、工具、验收、自我修复和长任务状态机真正连接起来。

核心问题不是“用哪一种规划方式最好”，而是：

**面对不同复杂度、不同确定性、不同风险的任务，EvoAgent 应该由谁决定做什么、谁负责执行、谁判断结果、谁有权修改计划，以及失败后由谁决定如何恢复？**

如果这些职责没有明确边界，就很容易出现以下问题：

- Planner 反复重写计划，任务迟迟无法执行；
- ReAct 为了完成当前步骤，绕过了 DAG 的前置条件；
- 专家智能体自行修改全局任务目标；
- 失败后每一层都尝试重试，造成重复调用和成本膨胀；
- 一个节点失败，整个工作流被迫从头执行；
- 固定工作流遇到异常时缺乏调整能力；
- 动态规划虽然灵活，却无法稳定复现和验收。

因此，我建议将本专项定义为：

**Task Orchestration & Dynamic DAG Governance Engine，简称 TODG。**

它负责统一任务规划、依赖管理、执行控制、动态调整、失败恢复和资源治理。

## 一、第一性原理：规划、执行与控制是三种不同的职责

先明确一个核心判断：Planner、ReAct 和 DAG 并不是三个互相竞争的智能体，它们处在不同的抽象层次。


    <title size="lg">Planner：决定如何完成目标</title>
    将目标拆解成任务、依赖、验收条件和资源计划，并在必要时提出计划变更。


    <title size="lg">DAG：表达任务之间的依赖关系</title>
    描述哪些节点必须先完成、哪些节点可以并行、哪些结果是后续步骤的输入。


    <title size="lg">ReAct：处理执行过程中的局部决策</title>
    观察当前状态、选择工具、执行动作、分析结果，并决定当前节点的下一步行动。


    <title size="lg">任务控制器：维护全局正确性</title>
    控制状态迁移、权限、预算、依赖、重试、恢复和最终验收。


这四个部分不能相互替代。

例如，Planner 可以提出“先生成角色设定，再生成分镜，最后合成视频”的计划，但不能自行宣布视频已经生成。

DAG 可以表达“分镜依赖角色设定”，但不能独立判断某个工具调用是否应该重试。

ReAct 可以在生成分镜时发现角色素材不完整，并提出补充素材的建议，但不能未经控制器批准就修改全局预算或绕过依赖约束。

任务控制器则负责将这些提议转换成合法、可执行、可恢复的任务状态。

**规划器提出方案，执行器执行动作，状态机维护事实，治理层决定哪些变化可以被接受。**

# 二、先确定统一控制架构

我建议 EvoAgent 采用“分层控制、单一任务状态权威、局部自治、全局约束”的架构。

这里的“单一权威”指每个任务的状态和计划都有唯一的权威管理者，并不是所有智能都集中在一个模型里。

## 2.1 完整控制链


    **用户目标与有效约束**
    原始目标、阶段目标、授权、预算、验收要求



    **任务控制器 Task Controller**
    持有权威任务状态，判断当前阶段和可执行动作



    <grid-item>

        **Planner**
        生成或修改计划

    </grid-item>
    <grid-item>

        **DAG Engine**
        校验依赖与节点状态

    </grid-item>



    **调度器 Scheduler**
    选择就绪节点、分配资源、控制并发与预算



    <grid-item>

        **专家执行器**
        领域能力、专用工具和专业验收

    </grid-item>
    <grid-item>

        **ReAct Runtime**
        节点内的观察、行动与反馈循环

    </grid-item>



    **工具执行网关与验收器**
    授权检查、真实执行、结果验证、证据记录



    **状态更新与恢复控制**
    提交结果、更新检查点、继续执行或进入恢复流程


这不是一个严格线性的调用链。执行过程中，控制器可能多次调用 Planner，节点内部可能运行多个 ReAct 循环，多个 DAG 节点也可能并行执行。

但无论如何，所有正式的任务状态变化都必须回到权威任务控制器。

## 2.2 为什么不能让 Planner 直接控制所有工具？

因为规划和执行的可信要求不同。

Planner 可能生成错误的依赖关系、忽略资源限制，或者误判某个节点已经满足前置条件。

如果 Planner 既能生成计划，又能直接执行全部工具，还能随意修改任务状态，那么规划错误就可能直接变成执行错误。

因此，Planner 输出的应该是一个**计划提案**，由控制器和 DAG Engine 校验后再正式接受。

同理，ReAct 可以提出临时行动，但工具网关仍然必须执行授权检查；专家可以提出局部恢复方案，但不能跳过全局预算、依赖和验收规则。

# 三、任务应该如何选择固定工作流、动态 DAG 和 ReAct？

这是本专项最重要的决策之一。

我不建议把任务简单划分成“固定流程任务”和“智能体任务”。现实中的复杂任务往往同时需要固定流程和动态决策。

例如，代码修改可能有稳定的基本流程：

读取项目、理解需求、修改代码、运行测试、检查差异。

但具体修改过程可能需要反复搜索代码、读取文件、运行测试、根据错误修复问题。这部分就更适合 ReAct。

所以，正确的设计不是三选一，而是根据不同层级选择合适的控制方式。

## 3.1 四种编排模式




      **模式 A：固定工作流**

    适合步骤、依赖和验收标准高度确定的任务。
    例如：固定格式的数据导入、标准文件转换、已有模板的重复生成。
    特点：成本低、可复现性高、执行边界清晰。





      **模式 B：动态 DAG**

    适合需要拆解、并行、动态增加依赖和条件分支的复杂任务。
    例如：多模块代码重构、漫剧多素材制作、跨工具数据分析。
    特点：能表达复杂依赖，同时保持节点级状态与恢复能力。





      **模式 C：ReAct 局部循环**

    适合当前状态不完全确定、下一步行动需要根据观察动态选择的节点。
    例如：定位测试失败、探索未知界面、调试接口异常。
    特点：灵活，但必须受节点目标、行动预算和权限约束。





      **模式 D：受控人工确认**

    适合风险较高、目标存在歧义或缺少必要授权的任务阶段。
    例如：不可逆删除、超出预算的操作、存在多个互相冲突的用户要求。
    特点：暂停相关动作，等待确认或补充信息，而不是让模型自行猜测。


同一项任务可以组合这些模式。

例如，代码任务可以由固定工作流管理准备、测试和交付；由动态 DAG 管理多个模块；每个模块内部再用 ReAct 完成定位与修复；涉及超出授权范围的操作时进入人工确认。

## 3.2 模式选择应该考虑哪些因素？

建议使用任务特征，而不是只根据用户意图标签来决定编排方式。

| 判断因素 | 更倾向固定工作流 | 更倾向动态 DAG 或 ReAct |
|---|---|---|
| 流程确定性 | 高 | 低或中等 |
| 前置依赖 | 稳定、可预定义 | 可能动态发现 |
| 环境可预测性 | 高 | 低 |
| 中途探索需求 | 少 | 多 |
| 并行处理需求 | 固定并行结构 | 动态依赖和并行 |
| 错误处理 | 已有成熟恢复路径 | 需要观察后决定 |
| 结果验收 | 明确、稳定 | 需要动态补充证据 |

风险并不决定是否采用 DAG 或 ReAct，而是决定需要多严格的授权、验收、日志和恢复门禁。

**低风险任务可以更灵活，高风险任务可以同样使用动态规划，但必须收紧可执行动作和变更权限。**

# 四、Planner 应该什么时候规划，什么时候重新规划？

如果每次行动前都调用 Planner，成本会很高；如果只在任务开始时规划一次，又很难应对未知情况。

因此，我建议采用两级规划机制。

## 4.1 初始规划与局部重规划


    **全局规划 Global Planning**
    建立总体目标、阶段、主要 DAG、资源预算、关键依赖和验收标准。
    一般在任务开始、目标发生重大变化或全局计划失效时执行。


    **局部规划 Local Planning**
    针对某个节点或阶段，决定具体步骤、工具调用、局部依赖和恢复方式。
    一般在进入新节点、发现未知情况或当前节点执行受阻时执行。


例如，编程任务的全局规划确定：

1. 分析项目；
2. 修改两个相关模块；
3. 运行测试；
4. 检查回归；
5. 交付修改结果。

在第一个模块中，ReAct 发现实际接口与预期不同。此时可能只需要局部调整该模块的执行策略，不必重新规划整个项目。

但如果发现两个模块的接口设计存在根本冲突，原来的依赖关系已经不成立，就可能需要修改 DAG，甚至重新制定阶段计划。

## 4.2 建立计划变更触发器

建议只有出现以下情况时，才触发相应级别的重规划：

- 原计划所依赖的关键假设被证伪；
- 发现了未预期的必要子任务；
- 关键节点失败且已有恢复路径不适用；
- 输入、输出或接口发生实质变化；
- 用户明确修改目标；
- 预算、时间或工具能力发生变化；
- 发现任务无法满足原定验收标准；
- 任务执行结果表明当前计划的预期收益明显不足。

相反，以下情况通常不需要全局重规划：

- 某个节点内出现可局部修复的参数错误；
- 一次可安全重试的临时读取失败；
- 某个步骤需要额外读取一个文件，但整体依赖关系没有改变；
- 当前节点可以在原有目标和预算内完成局部调整。

## 4.3 重规划必须有成本

每次重规划都应记录：

- 触发原因；
- 原计划版本；
- 新计划提案；
- 预计收益；
- 额外调用成本；
- 已完成节点是否受到影响；
- 哪些产物需要重新生成；
- 是否改变用户可见的交付范围。

如果新计划没有明确收益，或者收益不足以覆盖新增成本，就不应自动接受。

同时，系统应该设置重规划预算，例如每个任务允许多少次全局重规划、多少次局部规划调用。超过限制后，优先选择已验证的恢复方案，必要时暂停并请求用户决策。

这能避免智能体陷入“不断思考如何更好完成任务，却始终没有真正完成任务”的循环。

# 五、动态 DAG：如何安全地修改执行计划？

DAG 的价值在于表达任务依赖，但真实任务往往无法在开始时确定所有节点。

因此，EvoAgent 需要允许 DAG 在执行过程中演化。

不过，动态修改不能意味着 Planner 可以随意删除节点、改变依赖或重置任务状态。

我建议采用“计划提案—结构校验—影响分析—提交新版本”的机制。

## 5.1 DAG 节点必须有明确的契约

每个节点至少应该定义：

- `node_id`：稳定的节点标识；
- `goal`：节点要实现的结果；
- `inputs`：所需输入及其版本；
- `outputs`：预期产物；
- `dependencies`：前置节点；
- `acceptance_criteria`：完成条件；
- `tool_policy`：可使用的工具范围；
- `budget_limit`：该节点的资源上限；
- `retry_policy`：重试条件和次数；
- `recovery_policy`：失败后的处理方式；
- `idempotency_policy`：是否能够安全重复执行。

这些字段让节点不仅是一个任务名称，而是一个可调度、可验证、可恢复的执行单元。

## 5.2 动态变更应该分为四类

| 变更类型 | 示例 | 建议处理方式 |
|---|---|---|
| 增加节点 | 发现需要新增静态分析步骤 | 检查输入、输出、依赖和预算后加入新版本 |
| 修改节点 | 调整视频编码参数 | 检查已产生的产物是否失效 |
| 修改依赖 | 新发现某个素材必须先经过校验 | 重新检查拓扑关系和下游节点 |
| 删除或跳过节点 | 发现某个可选分析步骤不再必要 | 验证其是否影响硬性约束和最终验收 |

## 5.3 计划变更需要通过哪些门禁？

建议按照以下顺序执行：

1. Planner 生成 `Plan Change Proposal`。
2. 验证目标与硬性约束没有被违反。
3. 验证 DAG 没有循环依赖。
4. 检查新增依赖是否已经满足。
5. 分析哪些已完成节点仍然有效。
6. 识别受影响的下游节点与产物。
7. 计算新增成本、时间和预算风险。
8. 检查所需工具和权限是否可用。
9. 提交新计划版本并保存检查点。
10. 由调度器按新版本继续执行。

对于无风险、纯内部、可逆的局部调整，可以通过预先定义的策略自动批准；对于扩大外部副作用、突破预算或改变用户交付范围的变更，则必须经过相应的治理门禁。

## 5.4 已完成节点不能因为重规划而自动失效

例如，漫剧中的角色素材已经生成并通过验收。

之后，Planner 发现需要增加一个背景生成节点。

这不应该导致所有角色素材重新生成。

只有当新的计划改变了已完成产物的输入条件、格式要求或验收标准时，系统才应该重新评估其有效性。

建议建立 `Artifact Dependency Graph`（产物依赖图），让每个产物关联：

- 来源节点；
- 输入产物版本；
- 工具与配置版本；
- 内容哈希；
- 验收报告；
- 下游引用。

这样，重规划后只需要使真正受影响的节点失效，而不是重新执行整个任务。

# 六、ReAct 的行动范围：可以灵活，但不能越界

ReAct 的优势是能够根据观察结果动态调整行动。

但如果没有明确边界，ReAct 可能在一个局部节点内不断探索，最后偏离原始任务目标。

例如，编程专家正在修复一个测试失败，发现了另一处代码风格问题，于是开始重构整个项目。

从局部角度看，这可能是一个有价值的改进；从任务角度看，它却可能增加成本、扩大变更范围并引入新缺陷。

因此，我建议为每个 ReAct 循环设置一个 `Action Envelope`（行动边界）。

## 6.1 行动边界包含什么？

- 当前节点目标；
- 允许读取和修改的对象范围；
- 可使用的工具；
- 禁止的操作；
- 最大循环次数；
- 最大模型调用次数；
- token 和费用预算；
- 时间限制；
- 允许的局部计划调整范围；
- 必须暂停并请求确认的条件。

ReAct 每次提出行动后，都必须检查它是否仍然处于这个边界内。

## 6.2 ReAct 何时应该停止？

建议在以下情况之一出现时退出当前循环：

- 当前节点已达到验收标准；
- 需要的证据已经收集完毕；
- 达到行动次数或成本上限；
- 遇到不可恢复的错误；
- 需要超出当前权限范围的动作；
- 发现原始目标或前置条件存在歧义；
- 需要修改全局 DAG；
- 连续多次行动没有带来有效进展。

退出不代表整个任务必须结束。

控制器可以决定标记节点成功、进入恢复、触发局部重规划、等待外部依赖，或者请求用户决策。

## 6.3 需要避免重复推理与重复恢复

同一个问题可能被多个模块同时发现。

例如：

- ReAct 认为工具失败需要重试；
- 专家智能体提出重新执行节点；
- Planner 提出重建整个阶段；
- 自我修复系统提出切换模型。

如果这些模块各自行动，就可能同时产生多次重复执行。

因此，建议为每个失败事件创建唯一的 `Recovery Case`，由恢复控制器统一管理。

其他模块只能提交恢复提案，不能各自独立启动恢复动作。

这样，恢复过程才有唯一的状态、预算和责任主体。

# 七、失败之后究竟应该重试、局部恢复还是重新规划？

这是动态执行系统必须解决的核心问题。

我建议将失败恢复分成四种主要策略，而不是统一使用重试。




      **策略 A：直接重试**

    适用于已确认可重试的瞬时故障，例如临时网络错误、限流或短暂资源不足。
    前提：重试不会产生不可控的重复副作用，或者已具备幂等保护。





      **策略 B：节点内修复**

    适用于目标仍然明确、问题局限在当前节点的情况。
    例如修正参数、补充输入、重新读取文件或修复代码后再次验证。





      **策略 C：局部重规划**

    适用于当前节点的执行路径失效，但全局目标和主要 DAG 仍然有效的情况。
    例如更换工具、增加一个必要的分析节点或调整局部依赖。





      **策略 D：全局重规划**

    适用于原计划的关键假设不成立、任务目标变化或整体方案无法达到验收标准的情况。
    需要重新检查预算、依赖、已完成产物和用户目标。


## 7.1 恢复策略应该由证据驱动

例如，某个 API 调用超时：

- 如果服务端明确返回限流，并给出可重试条件，可以延迟后重试；
- 如果请求已提交但结果未知，应该先核查外部状态；
- 如果参数错误，应该修复参数，而不是重复相同请求；
- 如果 API 已经不再提供所需能力，则可能需要替换工具或调整计划；
- 如果没有任何可行工具满足任务要求，则应停止相关执行并说明限制。

这里不应该让模型单凭错误文本自由决定所有恢复动作。

恢复控制器需要结合错误分类、工具契约、幂等性、当前状态、预算和历史恢复结果，选择允许的策略。

## 7.2 恢复也必须经过验收

一次恢复动作成功执行，不代表原问题已经解决。

例如，代码修复工具成功写入文件，但测试仍然失败。

恢复控制器应该要求原节点重新满足验收条件，必要时触发下游回归检查。

同样，视频重新生成成功，只能证明生成完成；仍然需要检查时长、素材引用、音画同步和质量要求。

**恢复的成功标准是任务重新具备可靠的前进条件，而不是某个工具返回成功。**

# 八、多个专家如何协同，而不互相争夺控制权？

EvoAgent 采用多专家架构之后，任务编排必须处理一个新问题：

不同专家可以对同一任务提出建议，但不能同时拥有修改整个任务计划的权力。

例如，漫剧任务中：

- 编剧专家建议修改故事；
- 分镜专家发现镜头数量不足；
- 视频生成专家发现某些镜头无法生成；
- 配音专家发现台词时长超出镜头时长；
- 合成专家发现音画时间轴冲突。

这些建议都可能合理，但它们之间存在依赖关系。

如果每个专家都直接修改 DAG，就可能产生冲突、循环依赖和重复工作。

## 8.1 建立三种不同的权限

| 权限层级 | 谁可以执行 | 典型行为 |
|---|---|---|
| 节点执行权 | 当前节点的执行专家 | 完成节点内任务、调用授权工具、提交结果 |
| 局部提案权 | 当前专家、ReAct、诊断器 | 提议补充节点、调整参数、修改局部计划 |
| 全局计划提交权 | 任务控制器与计划治理流程 | 接受 DAG 变更、修改关键依赖、更新全局预算与阶段目标 |

专家可以提交结构化建议，但全局计划只能由权威控制器接受并提交。

## 8.2 为每个专家定义输入输出契约

例如，分镜专家的输出不应该只是一段自然语言，而应当包含：

- 镜头列表；
- 镜头时长；
- 角色引用；
- 场景与素材依赖；
- 必须生成的资产；
- 验收条件；
- 未解决的问题；
- 已知风险。

视频生成专家接收的是经过验证的镜头定义和素材引用，返回生成结果、实际时长、资产位置及质量检查结果。

这样，上游专家修改了镜头时长时，系统就可以识别哪些下游视频和配音节点需要重新执行。

## 8.3 并行专家需要明确同步点

多个专家可以并行处理互不依赖的任务，但涉及共享产物或关键接口时，必须建立同步点。

例如：

- 编剧专家与角色设计专家可以在初期并行工作；
- 分镜生成需要依赖已确定的故事结构与角色设定；
- 视频生成依赖已验收的镜头定义；
- 最终合成依赖已确认的视频、音频和字幕资产。

如果上游内容在并行执行期间发生变化，下游节点不能继续盲目使用旧版本。

应当通过输入版本和产物依赖关系判断节点是否需要暂停或重新验收。

## 8.4 冲突由控制器处理，而不是让专家自行投票

假设配音专家建议将某句台词缩短，而编剧专家坚持保留原文。

这不是简单的模型投票问题。

系统应该检查：

- 用户是否明确要求台词原文不可修改；
- 当前镜头时长是否属于硬性约束；
- 是否存在延长镜头或调整节奏的替代方案；
- 不同方案的成本和质量影响；
- 哪些选择需要用户确认。

如果涉及用户明确设定的创作要求，就不能让专家通过内部投票擅自改变用户目标。

# 九、预算与调度：避免局部优化导致全局成本膨胀

你之前特别强调过：真正的能力提升可以接受一定成本增加，但成本不能无限膨胀。

任务编排必须把这个原则落实到执行控制中。

建议采用三级预算体系。


    **任务总预算**
    整个任务允许消耗的费用、时间、模型调用量和资源上限。
    任务控制器负责保证不会因为局部重试而突破总预算。


    **阶段预算**
    某个阶段可以使用的资源，例如素材生成、代码修改或质量验收。
    用于控制各阶段之间的资源分配。


    **节点与循环预算**
    单个节点、Planner 调用、ReAct 循环、工具重试和恢复过程的上限。
    用于防止局部循环无限消耗资源。


## 9.1 预算必须统一核算

如果 Planner、ReAct、专家和自我修复系统各自维护独立的调用额度，就可能出现每个模块都认为自己没有超预算，但整个任务已经超支的情况。

因此，建议建立统一的 `Budget Ledger`，记录：

- 模型调用费用；
- 输入和输出 token；
- 外部生成服务费用；
- 工具执行时间；
- CPU、内存和其他本地资源；
- 重试与恢复产生的额外成本；
- 已预留但尚未实际消耗的预算。

节点开始前可以预留资源；执行后根据实际消耗结算；取消节点时释放尚未使用的预留额度。

对于无法提前精确计费的外部工具，应当使用保守估算并在执行后对账。

## 9.2 不要把所有剩余预算都交给失败节点

例如，整个任务预算为 100 个单位，其中 80 个单位已经消耗，剩余 20 个单位。

某个节点失败后，不应该因为它“还有机会修复”就无限次调用模型，直到剩余预算耗尽。

恢复控制器应当比较：

- 预计修复收益；
- 成功概率；
- 额外费用；
- 剩余任务的必要成本；
- 最终验收是否仍然可实现。

必要时，系统可以选择低成本恢复策略、暂停并等待用户决策，或者明确报告任务无法在剩余预算内完成。

## 9.3 预算耗尽时应该如何处理？

建议设置清晰的动作：

- 停止启动新的非必要节点；
- 不再接受超出预算的普通重试；
- 保存任务状态与检查点；
- 核实已经提交的外部操作；
- 保留必要的验收和安全收尾资源；
- 向用户报告已完成部分、剩余工作和继续执行的预计成本；
- 如果需要增加预算，必须走明确的授权流程。

这样，成本控制才是系统级约束，而不是模型提示词中的一句“请节约成本”。

# 十、将成功任务沉淀为稳定工作流

这与我们最初讨论的“如何把跑通的任务做成工作流”直接相关。

我建议不要把一次成功的执行轨迹直接录制成固定流程。因为一次成功可能包含偶然因素、无必要的步骤，甚至包含在其他环境中不适用的操作。

更可靠的做法是：从成功轨迹中提取可复用结构，再经过验证，形成可发布的工作流模板。

## 10.2 哪些部分应该固定，哪些部分应该动态？

建议将工作流分成三个部分：

- **稳定骨架：** 必须执行的节点、关键依赖、硬性验收和安全检查。
- **可配置部分：** 用户参数、模型选择、工具实现、预算与质量等级。
- **动态扩展部分：** 在执行时根据观察结果增加的诊断节点、恢复节点或可选分支。

例如，一个编程工作流可以固定“修改后必须运行相关测试”这一验收要求，但允许执行器根据实际错误动态增加代码搜索、静态分析或依赖检查步骤。

这样，EvoAgent 既能积累稳定、可复用的工作流，又不会因为工作流固定而失去应对未知问题的能力。

## 10.3 不要把工作流模板与运行实例混为一谈

建议区分：

- `Workflow Template`：经过验证的可复用流程定义；
- `Workflow Version`：某一版具体的节点结构与策略；
- `Workflow Run`：某次任务实际运行的实例；
- `Workflow Trace`：实例的执行证据；
- `Workflow Evaluation`：该版本在评测集和真实任务中的表现。

每次运行都应该绑定明确的模板版本。

如果后续模板升级，不应修改正在执行的任务所引用的旧版本。当前任务需要迁移到新版本时，应经过明确的兼容性检查和迁移流程。

# 十一、任务编排的完整控制算法

为了让上述设计真正可实施，我建议将任务控制器实现为一个事件驱动的状态机，而不是一个无限运行的模型循环。

下面是其逻辑流程。

<CodeBlock language="python" editable>
def advance_task(task_id):
    task = load_authoritative_task(task_id)

    if task.is_terminal:
        return task.status

    reconcile_unresolved_operations(task)

    validate_objectives_constraints_and_budget(task)

    if task.requires_user_approval:
        return pause_for_approval(task)

    if task.has_unresolved_recovery_case:
        proposal = recovery_controller.propose(task)
        decision = recovery_gate.validate(proposal, task)

        if not decision.allowed:
            return pause_or_fail_safely(task, decision)

        apply_recovery_proposal(task, proposal)

    if task.plan_is_invalid:
        proposal = planner.propose_plan_change(task)
        decision = plan_gate.validate(proposal, task)

        if not decision.allowed:
            return pause_or_fail_safely(task, decision)

        commit_new_plan_version(task, proposal)

    ready_nodes = dag_engine.get_ready_nodes(task)

    if not ready_nodes:
        if dag_engine.has_unresolved_dependencies(task):
            return diagnose_blocked_task(task)

        return verify_final_deliverables(task)

    node = scheduler.select_node(ready_nodes, task.budget)

    context = context_engine.build_for_node(task, node)

    action = expert_runtime.propose_next_action(node, context)

    decision = execution_gate.validate(
        task=task,
        node=node,
        action=action,
        budget=task.budget,
        authorization=task.authorization
    )

    if not decision.allowed:
        return handle_execution_denial(task, node, decision)

    result = executor.run(action)

    persist_execution_evidence(task, node, action, result)

    node_result = verifier.evaluate(node, result)

    commit_node_state_and_checkpoint(task, node, node_result)

    return task.status
</CodeBlock>

这段代码是控制逻辑示意，不是可直接运行的实现。实际系统还需要处理并发锁、事务边界、崩溃恢复、幂等性和异步外部操作。

但它明确了一个重要原则：

**模型提出动作，程序验证动作，执行器执行动作，验收器检查结果，状态机提交状态。**

模型不应同时承担全部职责。

## 11.1 任务控制器不需要每次都调用大模型

控制器的大部分工作应该由确定性代码完成：

- 检查节点依赖；
- 更新状态；
- 核算预算；
- 检查权限；
- 判断是否超时；
- 验证版本；
- 处理幂等键；
- 恢复检查点；
- 校验 DAG 结构。

只有在需要理解复杂输入、生成计划、分析未知错误或比较替代方案时，才调用相应的模型能力。

这样既能降低成本，也能提高状态管理与执行恢复的可靠性。

# 十二、如何评估整个编排系统？

TODG 的评测不能只看任务成功率，因为系统可能通过无限重试取得成功，也可能因为过度保守而很少失败。

建议建立四组指标。

## 12.1 计划质量

- 计划一次通过率；
- 必要节点遗漏率；
- 无效依赖率；
- 计划变更次数；
- 重规划后目标偏离率；
- 已完成产物的无效重做率。

## 12.2 执行质量

- 节点完成率；
- 节点验收通过率；
- 工具调用成功率；
- 无进展循环发生率；
- 恢复后任务完成率；
- 重复副作用率。

## 12.3 资源效率

- 每项成功任务的模型调用成本；
- 每个节点的平均执行成本；
- 重试与恢复成本占比；
- 预算超限率；
- 计划调整的额外成本；
- 已验收产物复用率。

## 12.4 稳定性与治理

- 非法 DAG 变更拦截率；
- 未授权动作拦截率；
- 中断恢复后的状态一致率；
- 取消请求生效率；
- 失败后正确停止率；
- 最终验收误判率。

这些指标应该按任务类型、专家、模型版本和工作流版本分层统计。

例如，编程专家在多文件重构中的表现，不能与简单问答的成功率混合计算，否则简单任务的高成功率可能掩盖复杂任务中的严重缺陷。

## 12.5 必须建立对照测试

对于一次编排策略改进，至少要比较：

- 当前稳定策略；
- 新候选策略；
- 代表性正常任务；
- 复杂任务；
- 失败与恢复任务；
- 高成本或长时间任务；
- 约束与权限边界测试。

如果新策略提高了成功率，却明显增加重复副作用、预算超限或恢复失败，那么它不应该因为单一指标改善就自动发布。

# 十四、下一专项：工具执行协议、能力契约与结果真实性

到这里，我们已经把智能体的高层控制链连接起来了。

但仍有一个重要问题没有彻底解决：

**如果模型、Planner、ReAct 和专家都可以提出行动，那么系统如何保证工具真正执行了正确的动作，并且返回的结果足以证明任务目标已经达成？**

这是智能体从“会思考”走向“可靠执行”的关键边界。

例如：

- 文件工具返回写入成功，但内容实际上不完整；
- 浏览器工具报告点击成功，却没有触发预期页面变化；
- 视频生成服务返回任务 ID，但生成任务最终失败；
- 编程工具修改了文件，却破坏了其他模块；
- 工具接口升级后，旧的参数校验不再有效；
- 模型认为工具返回的内容可信，但实际内容可能不完整或包含错误信息；
- 两个专家分别调用同一工具，却对工具的副作用和状态产生不同理解。

下一专项建议设计 **Tool Execution Contract & Capability Verification Engine（工具执行契约与能力验证引擎，简称 TECV）**，重点讨论：

1. 工具能力如何描述，包括输入、输出、前置条件和副作用；
2. 如何区分模型提出的工具请求、工具接受的请求、真实执行结果和最终验收；
3. 如何为不同工具定义幂等性、重试、取消、超时和恢复协议；
4. 如何验证工具返回的结果，而不是盲目信任工具报告；
5. 如何检测工具版本升级造成的行为变化；
6. 如何为不同专家建立专用工具能力包；
7. 如何评估工具的成功率、可靠性、成本与适用范围；
8. 如何让工具故障诊断反馈给自我修复与进化系统；
9. 如何防止模型或工具绕过权限、预算和任务状态控制；
10. 如何将经过验证的工具调用模式沉淀为稳定工作流。

这一步完成后，EvoAgent 的整体控制链才会更加完整：上层负责理解目标、规划和协调，下层负责执行真实动作，中间通过明确的契约、权限、证据和验收机制连接起来。

而且，这个专项也会直接决定未来编程专家如何使用 AST、手机操作专家如何使用 Android 原生接口，以及漫剧专家如何协调生成服务、素材数据库和 FFmpeg 合成，而不会把这些领域专用能力混成一套模糊的通用工具机制。
