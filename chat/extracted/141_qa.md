**文档版本：** 产品设计基线 1.0  
**产品方向：** Android 优先的个人通用智能体  
**设计原则：** 用户价值优先、真实任务驱动、能力渐进开放、可靠执行、持续进化

## 一、产品愿景

EvoAgent 是一个能够理解个人目标、调用适当能力、执行多步骤任务、交付真实结果，并通过经过验证的经验持续改善的个人智能体。

用户不需要了解背后的专家系统、工作流引擎、模型路由或进化控制器，只需要用自然语言表达自己想完成的事情。

系统负责理解、规划、执行、验证、恢复和交付；遇到不确定事项或需要授权的操作时，再与用户协作。

### 1.1 产品价值

1. **降低操作成本：** 减少用户在多个应用、工具和信息源之间反复切换的时间。
2. **提高任务完成能力：** 不只回答问题，还能够在权限和工具允许的范围内实际执行。
3. **减少重复劳动：** 把验证有效的方法保存为可重复运行的工作流。
4. **提高结果可信度：** 提供可检查的交付物、执行状态和验证证据。
5. **持续改善体验：** 根据真实任务中的错误、用户反馈和评测结果改善能力。
6. **保持用户控制权：** 用户能够查看、纠正、暂停、取消和授权关键操作。

### 1.2 产品成功的最终判断

EvoAgent 的成功不能以专家数量、工具数量、代码行数、进化次数或文档数量衡量。

核心判断是：

- 用户是否愿意把真实任务交给它。
- 它是否能够稳定地完成任务。
- 它是否能交付用户真正需要的结果。
- 它是否比原有工作方式节省时间或提高质量。
- 用户是否愿意持续使用并逐渐扩大授权范围。

## 二、目标用户与需求

### 2.1 首要用户

首发面向希望通过一个个人智能体处理多种日常任务的个人用户，而不是面向需要管理大量员工、复杂组织权限或企业级工作流的团队。

用户不必具备 AI、编程或自动化技术知识。

### 2.2 核心需求

- 用文字或语音直接表达目标。
- 不必手动选择专家、模型或工具。
- 简单任务快速完成，复杂任务自动分解。
- 在关键节点能够确认、调整或停止。
- 结果以文件、整理后的信息、实际操作结果或其他明确产物交付。
- 任务失败时能够知道原因、恢复进度或选择其他方案。
- 重复任务不必每次从头解释。
- 重要记忆、权限和成本由用户控制。

### 2.3 产品不应该要求用户做什么

- 不要求用户手动挑选领域专家。
- 不要求用户学习 ReAct、DAG 或 Harness。
- 不要求用户理解后台服务如何拆分。
- 不要求用户通过反复调试提示词才能完成普通任务。
- 不要求用户为了使用基本能力先搭建复杂服务器。
- 不允许把模拟执行、未验证结果或尚未完成的步骤包装成成功交付。

## 三、产品功能结构

### 3.1 对话模式

用于交流、解释、分析、构思和内容创作。

特点：
- 可以连续对话并保留必要上下文。
- 可以使用用户允许的记忆和个人偏好。
- 不把每次对话都强行转成复杂执行任务。
- 当用户需要真实操作或文件交付时，可以自然转入任务执行。

### 3.2 任务执行模式

用于需要多个步骤、工具调用、文件操作或实际状态变化的目标。

基本能力：
- 解析任务目标与约束。
- 必要时向用户澄清。
- 生成执行计划。
- 展示执行状态和关键进展。
- 在需要时请求权限或确认。
- 处理失败、重试、恢复和取消。
- 验证交付结果。
- 展示已完成、部分完成、失败和待确认事项。

### 3.3 工作流模式

用于重复性任务。

用户可以：
- 从经过验证的任务中创建工作流。
- 查看并修改工作流的输入、步骤和验收规则。
- 设置允许使用的工具、权限与预算。
- 再次运行并查看每次结果。
- 在工作流升级后查看变化与兼容性说明。
- 回退到先前稳定版本。

工作流的创建、保存、编辑、升级和回滚是独立的产品能力，不应仅仅作为后台技术模块存在。

### 3.4 能力与设置

用户可以查看和管理：
- 可用能力及其适用范围。
- 模型与成本策略。
- 记忆和个人偏好。
- 文件、网络及设备权限。
- 数据保留、同步和诊断导出。
- 版本更新和已启用的工作流。

普通用户使用时不必直接管理专家路由；高级用户可以在适当的设置页面查看更详细的信息。

### 3.5 任务历史与成果

每个任务都应有可追溯的记录，包括：
- 原始目标与约束。
- 执行状态和时间。
- 关键操作及授权记录。
- 实际产物与保存位置。
- 验收结果及证据。
- 失败原因、恢复记录和后续建议。
- 使用的能力版本与必要的成本信息。

历史记录必须区分日志、恢复检查点和实际副作用记录，不能仅靠一份聊天记录恢复所有任务。

## 四、首批用户任务场景

以下场景用于建立产品能力边界。它们是候选场景，不代表相关功能已经实现。

### 场景 A：信息搜索与整理

用户提出目标，例如：“帮我比较几种方案，并整理成一份报告。”

期望交付：
- 有来源依据的信息。
- 明确的比较维度。
- 结论与不确定事项。
- 可以保存或继续编辑的报告。

验收要求：
- 关键事实能够追溯来源。
- 不得将猜测包装成已核实事实。
- 报告满足用户指定的结构和范围。

### 场景 B：文档与文件处理

用户提供文件或指定可访问的资料，要求整理、归纳、转换或生成文档。

期望交付：
- 实际生成的文件。
- 清晰的输出位置。
- 对输入资料的处理说明。
- 对缺失信息和处理错误的提示。

验收要求：
- 文件真实存在并能够打开。
- 内容符合指定格式和要求。
- 不得声称处理了实际无法访问的文件。

### 场景 C：手机操作

用户提出目标，例如打开某个应用、找到指定功能或执行经过授权的操作。

期望交付：
- 实际执行结果。
- 关键状态变化的验证证据。
- 失败时的原因和可恢复路径。

验收要求：
- 只有在具备相应原生接口、无障碍能力或其他有效工具时才执行。
- 涉及发送消息、删除内容、付款等高影响操作时，遵守相应授权要求。
- 不能仅凭点击动作发出成功信号，必须验证最终状态。

### 场景 D：重复性任务

用户多次执行同一类资料整理、报告生成或其他任务，希望以后自动完成。

期望交付：
- 可保存的工作流。
- 可调整的输入参数。
- 明确的适用条件和依赖。
- 每次运行的独立记录与结果。

验收要求：
- 不能因为一次运行成功就直接把轨迹升级为稳定工作流。
- 重复运行时需要验证结果。
- 工作流变更必须有版本记录和失败回退能力。

### 场景 E：编程与技术任务

用户要求分析、修改或测试代码。

期望交付：
- 对问题的定位与解释。
- 实际代码修改或明确的修改方案。
- 测试、静态分析或其他适用验证结果。
- 未解决问题与回滚方法。

验收要求：
- 有真实项目访问权限才能声称修改了项目。
- 根据任务使用 AST、LSP、测试框架等专业工具。
- 不能把代码生成成功等同于代码正确。

### 场景 F：复杂内容制作

以 AI 漫剧为例，用户希望制作一段 30～60 秒的动态视频。

期望交付：
- 脚本、分镜和素材。
- 实际生成的画面、配音与合成视频。
- 视频文件及质量检查结果。
- 成本、失败镜头和降级处理记录。

验收要求：
- 明确哪些环节使用真实生成服务。
- 检查视频是否真实生成、时长是否符合要求。
- 不得将模拟服务结果当作真实视频交付。

## 五、统一的用户任务旅程

所有执行型任务遵循统一的用户体验：

1. **提出目标：** 用户通过文字、语音或文件输入需求。
2. **理解目标：** 系统识别意图、约束、交付物和验收条件。
3. **必要澄清：** 只有影响执行正确性的重要信息缺失时才提问。
4. **制定方案：** 选择稳定工作流、混合执行路径或动态规划。
5. **检查权限与预算：** 确认工具、风险、成本和执行边界。
6. **执行任务：** 展示必要进展，保存关键状态，处理失败。
7. **验证结果：** 根据任务类型检查实际产物、外部状态或其他证据。
8. **交付成果：** 展示结果、保存位置、验收状态和未完成事项。
9. **反馈与复用：** 用户可以纠正结果、保存有效工作流或反馈问题。
10. **后台改善：** 系统对可复用经验进行独立评估，合格后再进入稳定能力。

简单对话不必经过全部步骤。执行复杂度应由任务决定，而不是由系统架构强制决定。

## 六、用户界面与导航

首发应用建议包含以下主要入口：

1. **首页：** 对话输入、语音输入、附件入口和最近任务。
2. **任务中心：** 运行中、待确认、已完成、失败和可恢复任务。
3. **工作流：** 已保存流程、运行记录、编辑与版本管理。
4. **成果：** 任务生成的文件和其他可交付产物。
5. **我的设置：** 记忆、权限、模型、成本、隐私、同步和更新。

任务详情页统一展示：
- 目标与验收标准。
- 当前状态和执行进度。
- 关键步骤与等待用户处理的事项。
- 暂停、继续、取消等可用操作。
- 产物、验证结果和错误信息。

后台诊断和进化实验室可以作为高级功能，但不应挤占普通用户的主要交互空间。

## 七、功能优先级

### P0：首发不可缺少

- 文字输入与基本语音交互。
- 对话与任务执行的基本区分。
- 任务状态、历史、取消和必要的授权确认。
- 基础任务规划与受控工具调用。
- 结果验证与真实产物交付。
- 基本错误处理、预算控制和运行记录。
- 本地状态保存与基本离线能力。
- 权限、隐私和数据导出。
- 能够展示真实执行结果的可运行 Android 应用。

### P1：形成明显的个人助理价值

- 稳定工作流的保存与重复执行。
- 文档处理和结构化成果交付。
- 更可靠的信息检索与来源追踪。
- 多步骤任务恢复。
- 用户偏好和分层记忆。
- 更丰富的手机操作能力。
- 用户可理解的成本和质量反馈。

### P2：扩展专业能力

- 编程专家及专业代码分析工具。
- AI 漫剧制作能力包。
- 更复杂的跨工具工作流。
- 多设备协同。
- 高级诊断、独立评测和后台进化管理。

优先级不是按技术难度划分，而是按首发价值、使用频率、可靠性、实施成本与风险共同决定。若某项 P2 能力被证明是目标用户的高频刚需，可以调整顺序。

## 八、产品级验收与衡量

建立统一指标：

- 可信任务完成率。
- 首次验收通过率。
- 用户纠正率。
- 任务平均耗时及实际节省时间。
- 重复工作流成功率。
- 失败恢复成功率。
- 单次成功任务的平均成本。
- 应用稳定性和任务状态恢复率。
- 权限违规、隐私泄露和其他关键安全事件。

每项能力上线前必须具有：
1. 明确的目标用户和使用场景。
2. 明确的输入、输出和验收条件。
3. 可重复的代表性测试。
4. 失败、超时、取消和恢复测试。
5. 实际成本和依赖说明。
6. 权限及隐私边界。
7. 版本管理与回滚方案。

具体数值门槛应在建立代表性测试集并获得真实基线后确定，不得用未经验证的指标宣称产品成熟。

## 九、产品路线图

### 阶段一：建立可用产品

目标：用户可以提出目标、执行一批明确范围内的任务，并得到真实、可验证的结果。

主要交付：Android 基本应用、任务执行与状态管理、工具治理、成果展示、权限控制、基础恢复能力。

验收重点：端到端任务是否真实完成，而不是模块是否单独运行。

### 阶段二：建立可重复的个人工作方式

目标：用户能够保存、复用和调整常见任务流程。

主要交付：工作流中心、基础记忆、文件成果管理、任务恢复和质量反馈。

验收重点：重复运行是否稳定，是否减少用户的重复指导。

### 阶段三：扩展领域专业能力

目标：将通用能力与领域专业工具结合。

主要交付：编程、手机操作、复杂内容制作等独立能力包。

验收重点：每个能力包有独立的验收集、成本、依赖、权限和回滚策略。

### 阶段四：建立受控进化闭环

目标：系统能够从真实失败中发现改进机会，并证明改进有效。

主要交付：问题诊断、独立评测、候选实验、稳定版本发布、收益监测和回滚。

验收重点：改进能够提高真实任务质量，而不会破坏已有稳定能力。

### 阶段五：扩大设备与自主范围

目标：在可靠性和用户价值得到验证后，扩展跨设备能力与更高自主程度。

主要交付：桌面端、可选个人宿主、更多设备接口和受控主动任务。

验收重点：扩展不破坏统一任务记录、权限控制、结果验证和恢复机制。

## 十、产品与技术的追踪关系

| 用户可见能力 | 后台支撑能力 | 产品验收证据 |
|---|---|---|
| 对话与任务入口 | 意图识别、路由、上下文治理 | 正确理解目标与约束 |
| 任务执行 | Planner、ReAct、DAG、工具网关 | 真实任务完成与状态记录 |
| 结果交付 | 产物管理、独立验收器 | 文件、外部状态或其他结果证据 |
| 工作流中心 | 工作流资产、版本与依赖管理 | 可重复运行、可修改、可回滚 |
| 个人记忆 | 分层记忆、来源追踪、压缩策略 | 可查看、可纠正、跨领域隔离 |
| 失败恢复 | 检查点、幂等处理、副作用账本 | 不重复执行危险动作并能恢复 |
| 后台进化 | 问题诊断、独立评测、发布控制器 | 有基线、有对照、有回滚的收益证据 |
| 离线与同步 | 本地状态、事件队列、同步协调 | 断网后可保存并在恢复连接后同步 |
| 权限与成本控制 | Action Guard、预算和策略控制 | 未授权动作被阻止、超预算及时停止 |

## 十一、产品设计的长期原则

1. 用户价值优先于技术复杂度。
2. 真实执行优先于模拟成功。
3. 结果验收优先于模型自我判断。
4. 稳定复用优先于每次重新探索。
5. 专家和工作流对用户透明，但必要的执行信息必须可检查。
6. 通用内核与领域能力独立演进。
7. 后台进化不能直接绕过稳定版门禁。
8. 用户始终保有必要的授权、停止、纠正与恢复权。
9. 不以无限自主替代明确的目标、预算和停止条件。
10. 每个新增专项都必须说明对应的用户需求、产品能力和验收价值。

**最终原则：EvoAgent 的进化能力必须服务于一个真正可用的个人智能体。只有当用户能够持续获得更好的任务结果，进化才具有产品意义。**</WritingBlock>

## 接下来怎么做

这份总纲先建立了产品方向，但还没有完成产品设计。下一步最值得做的，是把抽象场景变成可实施、可验收的具体任务，而不是继续增加架构章节。

我建议下一份交付是 **《EvoAgent 首发核心场景与端到端验收设计》**，逐项定义用户输入、界面交互、执行步骤、真实依赖、输出产物、异常恢复和验收用例。这样就能开始判断：哪些能力现有技术设计已经覆盖，哪些缺少实现，哪些功能目前不值得投入。
