## 一、产品功能设计原则

EvoAgent 面向用户提供的是一套完成工作的产品，而不是一组需要用户自行组合的智能体、工具和工作流。

产品的核心体验是：

**用户提出目标 → 系统理解并执行 → 用户查看真实进展 → 系统验证结果 → 交付成果 → 在合适的时候提供额外帮助。**

内部仍然采用统一任务入口、受保护的共享内核、独立领域专家、能力依赖图和独立进化控制器。用户界面不应直接暴露这些架构细节。<FileCite ref="turn15file1"/>

每项用户功能必须明确六件事：

1. 用户为什么需要它；
2. 用户在哪里、怎样使用它；
3. 系统实际执行什么；
4. 用户最终得到什么；
5. 出错时系统如何处理；
6. 如何验证这项功能真正有效。

## 三、模块一：统一任务入口

### 功能 UX-01：自然语言任务输入

**用户价值：** 不需要先判断该使用哪个专家、工具或工作流。

用户可以直接输入：

- “帮我研究一下这个问题，整理成一份报告。”
- “继续上次没完成的项目。”
- “帮我分析这个代码库中的问题。”
- “看看最近的工作还有什么重要事项没处理。”
- “把这段内容整理得更清晰。”

系统自动判断这是普通问答、需要执行的任务、任务延续还是主动帮助请求。

**交互要求：**

- 输入框始终是主要入口；
- 不要求用户先选择专家；
- 支持必要的文件附件；
- 支持在已有对话中补充目标和约束；
- 支持取消、修改和重新提交；
- 只有缺失信息会显著影响结果时，才优先要求澄清。

**验收条件：** 用户使用自然语言表达不同类型的目标时，系统能够建立正确的任务类型，并保留用户明确提出的约束。

### 功能 UX-02：语音入口

用户可以通过语音表达目标，转写后进入与文字输入相同的任务处理路径。

系统应区分“语音识别完成”和“任务执行完成”。对于重要目标或可能产生外部影响的操作，不能仅凭语音转写结果直接执行高风险动作。

语音识别能力、语音播报能力及其离线支持范围，应根据实际接入的组件分别声明。

### 功能 UX-03：自动任务分类与路由

系统在后台判断任务属于哪类工作，并选择适当的专家、工具或工作流。

用户默认不需要理解路由过程。但在长任务、领域切换或能力受限时，可以查看简洁的执行说明。

如果路由不正确，用户可以直接纠正，例如：

“这个不是旅游规划，我要研究的是旅游行业的软件架构。”

系统应重新理解任务，而不是要求用户自行查找并切换内部专家。

**验收条件：** 路由错误可以被发现、纠正和记录；低置信度或能力不匹配时可以澄清或安全回退。

## 四、模块二：聊天与工作模式

### 功能 UX-04：聊天模式

适用于日常提问、概念解释、讨论和轻量分析。

系统应优先直接回答，不强制创建复杂的多步骤任务。

对于需要实时资料、外部工具或专业分析的问题，应根据实际能力调用相应服务，并明确来源和限制。

### 功能 UX-05：工作模式

适用于需要多步骤执行或产生正式成果的任务。

进入工作模式后，用户可以看到：

- 任务目标；
- 关键约束；
- 简明执行计划；
- 当前阶段；
- 需要用户处理的事项；
- 最终成果及验收状态。

用户不需要阅读全部内部日志才能了解进度。

### 功能 UX-06：模式自动转换

聊天与工作不是两个互不相通的系统。

例如，用户先讨论一个问题，随后说：“把刚才的分析整理成报告。”

系统应复用相关上下文，建立正式任务，并明确最终交付要求。

当任务结束后，用户也可以继续讨论成果、要求修改或开展下一项工作。

**验收条件：** 模式转换不会丢失已确认约束，也不会无故重新执行已完成的步骤。

## 五、模块三：任务工作区

### 功能 UX-07：任务计划

系统根据任务复杂度决定是否展示计划。

简单任务不需要展示计划。复杂任务应先形成可理解的步骤，并在执行中根据实际结果调整。

计划至少包含：

- 主要步骤；
- 关键依赖；
- 验收目标；
- 可能需要用户确认的事项。

用户可以纠正目标、补充约束或要求调整计划。

### 功能 UX-08：任务状态与进度

任务状态必须反映真实执行情况。

| 用户可见状态 | 说明 |
|---|---|
| 理解中 | 正在解析目标与约束 |
| 执行中 | 实际工作正在进行 |
| 等待你确认 | 存在需要用户处理的授权或决策 |
| 暂停中 | 当前没有继续推进 |
| 恢复中 | 正在恢复或核对任务状态 |
| 验收中 | 正在检查产物和结果 |
| 已完成 | 达到约定的完成标准 |
| 部分完成 | 有可用成果，但仍有未完成事项 |
| 未完成 | 未达到目标或执行受到阻塞 |

状态不能只由模型生成的文字决定，必须与实际任务记录一致。

### 功能 UX-09：任务控制

用户可以根据任务状态执行相应操作：

- 暂停；
- 继续；
- 取消；
- 补充要求；
- 查看中间成果；
- 重新执行失败的部分。

取消任务后，系统应停止新增动作，并处理已经提交的外部操作。取消不意味着可以假定已经产生的外部副作用自动撤销。

### 功能 UX-10：异常恢复

系统应当能够解释失败发生在哪一步，以及是否有安全恢复路径。

例如，工具超时后，系统应先判断操作是否可能已经生效，再决定是否重试。

如果无法安全恢复，系统应暂停相关操作，保留已完成成果，并请求用户决定下一步。

**验收条件：** 任务中断、工具失败、预算耗尽和应用重启等情况下，状态与实际结果保持一致。

## 六、模块四：结果与成果管理

### 功能 UX-11：结果验收

结果验收是任务执行的组成部分，不是可选的装饰功能。

不同任务应使用不同的验收方法：

- 文档：检查文件、格式、结构和内容；
- 研究：检查来源、关键事实和结论；
- 编程：检查代码变更、测试结果和构建情况；
- 手机操作：检查实际界面或外部状态；
- 视频制作：检查文件可播放性、时长及约定的质量指标。

用户可以查看验收摘要，但不必默认查看全部技术细节。

### 功能 UX-12：成果交付

成果页面应优先展示用户可以直接使用的结果。

支持的产物类型取决于已开放能力，包括文本、文档、表格、代码变更、研究报告及媒体文件等。

每项成果应具备：

- 清晰的名称；
- 可访问的实际产物；
- 必要的版本或生成时间；
- 验收状态；
- 需要说明的限制。

没有生成真实文件时，不能显示虚假的下载入口。

### 功能 UX-13：成果继续编辑

用户可以在已有成果基础上提出修改要求。

系统应尽可能复用已有材料和执行结果，只重做受影响的部分。

例如，用户要求修改报告中的一个章节，不应默认重新执行整个研究流程。

**验收条件：** 局部修改能够保留未受影响的内容，并重新执行必要的相关验收。

## 七、模块五：项目、记忆与连续工作

### 功能 UX-14：任务历史

用户可以查看历史任务，按时间、项目和状态进行查找。

历史记录应区分：

- 已完成；
- 部分完成；
- 失败；
- 已取消；
- 等待处理。

用户可以打开成果、继续任务或查看必要的执行摘要。

### 功能 UX-15：项目空间

项目空间用于持续推进同一目标下的多项任务。

每个项目包含：

- 项目目标；
- 已确认的关键约束；
- 重要决策；
- 关联任务；
- 相关资料与成果；
- 待解决问题；
- 下一步计划。

系统可以建议将相关任务归入同一项目，但应允许用户纠正错误归类。

### 功能 UX-16：跨会话任务延续

当用户要求“继续上次的工作”时，系统应恢复必要的任务状态、约束和成果，而不是仅依靠聊天历史猜测。

如果存在多个合理的目标候选，应先询问用户。

### 功能 UX-17：用户记忆管理

记忆系统需要服务于任务完成，而不是无限积累信息。

用户应能了解和控制：

- 哪些信息被作为长期偏好使用；
- 哪些内容仅属于当前会话或项目；
- 如何纠正过时或错误信息；
- 哪些信息不希望继续用于个性化；
- 哪些数据源允许参与分析。

长期记忆、领域记忆和任务上下文应保持适当隔离，不能因为一个领域的错误信息影响其他领域。

## 八、模块六：主动帮助

主动帮助是 EvoAgent 的差异化价值，但不能干扰核心任务执行。

### 功能 UX-18：当前任务增益

当用户交办任务时，系统除了完成主要目标，还可以发现明显遗漏、风险或更好的方案。

例如，生成报告时发现关键证据不足，系统应优先处理会影响报告正确性的缺口。对于不影响主要结果的额外增强，可以在交付后提出。

### 功能 UX-19：近期工作整理

用户可以主动要求：

“结合最近的对话和项目，帮我整理一下当前正在推进的事情。”

系统在授权的数据范围内，整理：

- 已完成的工作；
- 当前重点；
- 尚未解决的问题；
- 重要的约束与决定；
- 值得关注的下一步。

结果必须区分已确认事实与推断，不得假定自己可以读取所有应用和全部历史信息。

### 功能 UX-20：机会发现与建议

系统可以发现与当前目标相关的额外机会，例如：

- 一个任务其实已经具备保存为工作流的条件；
- 某个项目存在明显的未完成依赖；
- 用户的研究材料可以进一步转化为执行计划；
- 某个已发现的问题有更低成本的解决方案。

每条建议必须说明提出理由、潜在收益和所需操作。

### 功能 UX-21：主动程度控制

用户可以选择主动帮助的强度：

| 级别 | 行为 |
|---|---|
| 关闭 | 不生成额外的主动建议，但保留核心执行所需的风险提示 |
| 低 | 主要在当前任务完成后提出高价值建议 |
| 标准 | 在授权范围内整理项目和待处理事项，并提供适量建议 |
| 高 | 更积极地发现机会、提出跟进建议；仍受资源、权限和非干扰规则约束 |

这些级别是产品策略，不是对自主执行权限的自动授权。

主动帮助使用独立预算。资源紧张或核心任务不稳定时，主动帮助应优先暂停。

## 九、模块七：能力与信任中心

### 功能 UX-22：能力状态展示

用户不必了解所有内部专家，但需要知道当前能否完成某项工作。

建议为能力提供以下状态：

- 可用；
- 需要授权；
- 依赖外部服务；
- 实验中；
- 暂不可用；
- 未开放。

例如，AI 漫剧能力可能已经具备脚本和合成流程，但如果视频生成服务尚未配置，产品就应明确说明依赖，而不是显示为完整可用。

### 功能 UX-23：权限与审批

用户可以查看已授予的权限、对应能力及其用途。

审批请求必须绑定具体动作及必要的参数摘要。授权不应自动扩展到其他动作或更广泛的数据范围。

### 功能 UX-24：隐私与数据控制

用户能够了解任务数据的来源、处理范围、同步状态和保留策略。

需要上传的数据应符合授权与数据最小化原则。用户拒绝可选的数据访问权限后，系统应尽可能提供不依赖该权限的替代路径。

### 功能 UX-25：成本与资源控制

用户能够设置或查看与实际能力相对应的预算和资源限制。

任务达到预算上限时，系统应停止新增调用，保留已有成果，并说明继续执行需要什么条件。

不能为了节省成本跳过必要的安全检查和结果验收。

## 十、模块八：持续进化的用户体验

### 功能 UX-26：问题反馈

用户可以标记：

- 结果错误；
- 任务没完成；
- 路由不合适；
- 工具执行失败；
- 结果质量不足；
- 主动建议不相关。

反馈应关联对应任务与运行版本，以便诊断系统找到相关证据。

### 功能 UX-27：改进效果说明

后台完成经过验证的改进后，可以用简洁的方式向用户说明：

- 改进了什么；
- 解决了哪类问题；
- 有什么证据支持；
- 是否影响当前任务或需要用户操作。

不需要把所有内部实验和模型推理细节暴露给用户。

### 功能 UX-28：稳定版本与更新控制

用户正在执行的任务应绑定明确的运行版本。后台更新不能任意改变当前任务的关键执行组件。

新版本需要通过质量、安全、兼容性和成本门禁；发生退化时应能暂停发布或回滚。

用户看到的应当是更可靠的服务，而不是频繁且不可预测的系统变化。

## 十一、产品功能的开放顺序

完整产品目标不变，但不同功能需要不同的开放条件。

| 产品层级 | 功能范围 | 开放依据 |
|---|---|---|
| 基础任务 | 统一入口、问答、任务执行、状态、验收、交付 | 真实任务链通过验收 |
| 连续工作 | 历史、项目、记忆、暂停恢复、工作流复用 | 状态一致性和回归测试通过 |
| 领域能力 | 编程、旅游、手机操作、AI 漫剧等 | 对应专家具有独立评测和安全边界 |
| 主动帮助 | 任务增益、工作整理、机会发现 | 相关性、用户收益和非干扰测试通过 |
| 持续进化 | 候选改进、独立评测、受控发布、回滚 | 进化与发布闭环通过验证 |

## 十三、产品层的统一验收规则

每项用户功能至少要有：

1. 一个真实使用场景；
2. 明确的用户输入；
3. 预期的系统行为；
4. 可观察的输出；
5. 失败与恢复规则；
6. 对应的专项设计；
7. 可重复执行的验收用例；
8. 发布前的开放条件。

如果某项功能只有界面而没有真实执行能力，应标记为演示或实验功能。如果有真实执行能力但缺少结果验证，应限制开放范围。只有实际完成验收后，才能作为正式可用功能开放。
