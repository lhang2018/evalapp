## 一、第一性原理：我们最终想优化的对象是什么？

先看一个具体例子。

用户让 EvoAgent 修复一个 Python 程序中的异步任务错误。

智能体失败了。

我们可能会说：

- Python 编程能力有问题。
- 异步编程能力有问题。
- 规划能力有问题。
- 工具使用能力有问题。
- 记忆中没有相关经验。
- 模型本身不擅长这个任务。

但这些结论并不等价。

假如真正原因是代码执行工具使用了错误的 Python 版本，那么即使我们重写编程提示词、升级模型、调整 Planning，也可能毫无帮助。

反过来，如果智能体在 Python、Kotlin 和 JavaScript 中都反复遗漏用户明确提出的约束，那么问题可能根本不在编程领域，而在共享的指令遵循机制。

这说明：

**一次任务失败，不是某项能力缺陷的直接证明。它只是关于系统内部可能存在问题的一条证据。**

我们需要把三个概念彻底分开。


    <title size="lg">任务结果</title>
    某次任务成功或失败，是我们观察到的现象。



    <title size="lg">能力</title>
    系统在一定条件下稳定完成某类任务的潜在能力，是我们需要通过多种证据估计的对象。



    <title size="lg">能力实现机制</title>
    模型、提示词、记忆、工具、规划策略、工作流及环境共同构成的实现方式。


这里还有一个容易被忽略的事实：

同一项能力可能由多个机制共同实现；同一个机制也可能参与多个不同能力。

因此，能力不是一个简单的代码文件，也不一定对应一个独立智能体。

**这是我们设计 EvoAgent 的第一个基础原则：能力、实现能力的组件、具体任务表现，必须是三个可以分别追踪的对象。**

## 二、能力不是树，而应该是多维网络

我们之前提出过能力层级：

通用能力 → 领域能力 → 子能力 → 具体任务。

这个结构有用，但单靠树形结构是不够的。

为什么？

因为现实中的能力有三种关系。

### 1. 层级关系：能力可以逐层细分

例如：

- 编程
  - 代码理解
  - 代码生成
  - 调试
  - 测试
  - 重构

而调试还可以继续细分成异常定位、并发问题分析、内存问题诊断等。

### 2. 依赖关系：一项能力可能依赖其他能力

例如，代码调试依赖：

- 问题理解
- 代码阅读
- 工具调用
- 假设验证
- 错误定位
- 结果验收

所以，调试不是一个孤立的能力模块。

### 3. 交叉关系：相同能力可以服务于不同领域

例如：

- 工具故障诊断可以用于编程、旅游和手机操作。
- 长任务状态管理可以用于编程、漫剧制作和复杂研究。
- 约束检查可以用于代码生成、行程规划和文件整理。

如果强行把每项能力放进唯一的领域目录，就会出现重复实现；如果把所有能力都放进通用层，又会导致通用内核越来越庞大、难以隔离。

因此，我提出第一个架构假设：

**EvoAgent 的能力结构应该是一个多维能力图谱，而不是简单的树形目录。**


    **通用能力节点**
    指令遵循、规划、记忆检索、工具诊断、结果验证



    <grid-item>

        **编程能力**
        生成、调试、测试

    </grid-item>
    <grid-item>

        **旅游能力**
        规划、查询、预订

    </grid-item>
    <grid-item>

        **漫剧能力**
        分镜、生成、合成

    </grid-item>
    <grid-item>

        **手机操作能力**
        识别、交互、验证

    </grid-item>

  领域能力可以依赖共享能力，也可以组合其他领域能力；共享能力的变化需要分析所有依赖方。

这张图不是说所有领域能力都应该共享同一个实现，而是说它们可以依赖同一类经过验证的能力契约。

例如，多个专家都可以使用统一的“工具调用可靠性”接口，但编程专家和手机操作专家仍然可以拥有不同的具体工具策略。

这让我们既能复用能力，又不必让所有专家共享同一份易变配置。

## 三、能力究竟应该属于谁？我认为要分清四种“所有权”

这里可能是整个问题中最值得深入的地方。

我们通常会说“这个能力属于编程专家”，但这句话其实可能表达四种不同意思。






      **1. 能力定义权**

      谁定义这项能力要完成什么、适用什么条件、怎样才算成功？

      例如，编程专家定义“代码修复”需要通过哪些测试；共享验证机制定义所有任务都必须遵守的基本验收协议。








      **2. 实现控制权**

      谁可以修改这项能力的提示词、策略、工具配置和工作流？

      编程专家可以独立修改自己的代码生成策略，但不能因此直接修改旅游专家的行程规划提示词。








      **3. 验收决定权**

      谁决定改进是否有效？

      候选改动的提出者不应拥有最终验收权。验收必须依据独立测试、硬性约束和真实运行证据。









        **4. 共享与迁移决定权**

        谁决定一项局部能力可以推广到其他领域？

        编程专家发现的经验可以提出共享申请，但不能仅凭自己领域内的成功，就直接修改所有专家的通用策略。




这四种权力不应该默认归于同一个组件。

尤其是验收权和共享决定权，需要比普通执行策略更严格的隔离。

我会进一步提出一条原则：

**每项可进化能力都应该有明确的负责人、可修改范围、依赖对象、验收规则和共享晋级规则。**

这里的“负责人”是系统中的逻辑所有者，不一定是人，也不一定是独立 Agent。

这比单纯给每个专家分配一个目录更重要。目录只能隔离文件，权限和依赖规则才能真正隔离进化影响。

## 四、一个更深的问题：我们到底应该共享“能力”，还是共享“能力的实现”？

我的答案是：**优先共享能力契约和经过验证的经验，不默认共享易变的实现。**

这是我认为能显著降低 EvoAgent 架构风险的设计。

假设旅游专家和编程专家都需要“失败恢复”。

我们可以有三种方案：


    <title size="lg">方案 A：完全各自实现</title>
    旅游专家自己处理失败，编程专家自己处理失败。

    优点：隔离强。缺点：重复建设，难以积累通用经验。



    <title size="lg">方案 B：共享一个完整的恢复策略</title>
    所有专家使用同一套重试、重新规划和恢复逻辑。

    优点：复用高。缺点：一个策略改动可能同时破坏所有领域。



    <title size="lg">方案 C：共享契约，策略可独立实现</title>
    所有专家遵守统一的失败恢复接口和安全约束，但可以拥有不同的恢复策略；成熟的通用策略经过验证后，才可被其他专家采用。

    推荐
    兼顾复用、隔离和可进化性。


例如，统一恢复契约可以要求：

- 识别当前步骤和失败类型。
- 检查是否允许重试。
- 避免重复执行不可幂等的操作。
- 确认任务当前真实状态。
- 在预算和权限限制内恢复，或者安全停止。

但是，具体如何恢复仍由领域策略决定。

编程专家可能优先运行测试、检查日志、定位代码并修复；旅游专家可能重新查询交通和住宿信息；手机操作专家可能重新识别屏幕、确认按钮状态。

它们遵守相同的安全契约，但不需要采用相同的策略。

这给出一个重要结论：

**通用能力应该首先表现为稳定的接口、约束、验证方法和可迁移的原则，而不是所有领域强制共用同一份提示词、记忆和策略代码。**

当然，也有一些真正适合共享的实现，例如预算计量、事件追踪、权限检查和版本校验。这些实现本身通常有明确、可测试的行为契约，应该优先做成稳定的基础服务。

## 五、我建议将能力资产拆成五个对象

如果要让 EvoAgent 真正具备长期进化能力，就不能只把一个专家当作一个整体版本管理。

我们需要更细的资产模型。

| 对象 | 表示什么 | 示例 |
|---|---|---|
| 能力定义 | 要完成什么、适用范围和成功条件 | Python 异步错误诊断 |
| 能力契约 | 输入、输出、前置条件、后置条件和约束 | 输入代码与错误日志，输出可验证的修复方案 |
| 能力实现 | 实际执行所需的策略和组件 | Prompt、工具、模型配置、记忆策略、工作流 |
| 能力证据 | 证明能力有效的测试与运行结果 | 测试集、成功率、失败案例、成本和兼容性记录 |
| 能力发布版本 | 哪些实现与证据共同构成一个可用版本 | `python-async-debug-v3` |

为什么要这样拆？

因为能力的定义不应该随着某次实现变化而随意改变。

例如，“修复 Python 异步错误”这项能力的目标仍然是正确修复问题，并通过适当测试。今天它由模型 A 和某份提示词实现，明天可能改用模型 B、另一套工具或不同的工作流。

只要契约仍然成立，我们就可以替换实现，而不必重新定义整个能力。

反过来，如果我们发现原有验收标准不完整，例如只检查代码能运行，却不检查任务取消后的资源泄漏，那么这属于能力契约的改进。它可能影响多个实现，因此需要更广泛的测试。

这让能力定义、实现改动和验收标准改动不再混为一谈。

## 六、能力不能只看“属于哪一层”，还要看它的成熟度和适用范围

这是另一个值得重新思考的地方。

一项能力即使被称为“通用能力”，也不代表它已经足够成熟，能够安全地供所有专家使用。

例如，EvoAgent 在编程领域发现一种新的上下文压缩策略，能提高代码调试成功率。但它尚未在旅游、漫剧或手机操作任务上测试过。

这时，正确的处理不是立即把它升级为通用策略，而是记录：

- 它在哪些任务和模型上有效。
- 已经验证了哪些环境。
- 哪些任务尚未验证。
- 是否存在已知反例。
- 当前效果和成本改善有多大。
- 哪些其他组件可能受到影响。

我建议为能力资产增加独立的成熟度状态：

  {#each [{n:"M0",t:"观察中",d:"只有问题线索、候选想法或未经验证的经验。不能作为稳定能力自动推广。"},{n:"M1",t:"局部验证",d:"在明确的任务和环境范围内可重复成功，可以在对应专家的受控范围内使用。"},{n:"M2",t:"领域稳定",d:"经过代表性回归测试和真实运行验证，可以进入该领域专家的稳定能力库。"},{n:"M3",t:"跨领域验证",d:"在多个相关领域中验证了适用性和副作用，才有资格申请共享能力。"},{n:"M4",t:"长期稳定",d:"经过持续运行、模型或环境变化测试，并具备版本兼容、监测与回滚机制。"}] as m}


        <title size="md">{m.n}</title>


        **{m.t}**
        {m.d}


    {#if m.n !== "M4"}{/if}
  {/each}

这些状态不能简单理解为能力的绝对等级。某项专用能力即使只在一个领域使用，也可能已经非常成熟；它不需要为了成为 M4 而强行推广给其他专家。

成熟度回答的是“我们对它的可靠性有多少证据”，而不是“它有多通用”。

**通用性和成熟度应该是两个独立维度。**

这一点很重要，否则系统可能因为某项能力成熟，就错误地认为它应该被所有专家共享。

## 七、当一个专家想改进能力时，系统应该如何决定修改范围？

现在我们可以把前面讨论的原则组合成一个更严格的决策过程。

假设编程专家发现代码调试任务表现不佳。

<CodeBlock language="mermaid" editable={false}>flowchart TD
    A[发现能力缺陷线索] --> B[定位关联能力与实现组件]
    B --> C[检查根因证据与适用范围]
    C --> D{是否有足够证据}
    D -->|否| E[补充诊断或保持现状]
    D -->|是| F[提出最小范围候选改动]
    F --> G[检查依赖图与潜在影响方]
    G --> H[选择分层回归测试]
    H --> I[评估质量、成本、安全与副作用]
    I --> J{是否通过独立门禁}
    J -->|否| K[拒绝候选并记录原因]
    J -->|是| L[发布到获准范围]
    L --> M[观察实际运行结果]
    M --> N[更新能力证据与成熟度]</CodeBlock>

这里的核心不是要求每次只修改一个文件，而是要求每次进化都有清晰的范围声明。

例如：

- 修改 Python 异步技能，只影响编程专家的特定子能力。
- 修改编程专家的全局提示词，需要测试该专家的主要任务。
- 修改共享上下文组件，需要测试所有依赖它的关键能力。
- 修改核心权限系统，需要运行安全与权限相关的全局验证。

这样，测试范围就不再依赖开发者临时判断，而是由能力依赖图、组件所有权和变更类型共同决定。

但依赖图也不可能预先描述所有隐性影响，所以我们仍然需要运行监测和发布回滚机制。

# 八、头脑风暴：我们还有没有比“专家架构”更好的方案？

我想再挑战一下我们自己的方案。

目前的方向是“共享内核 + 多领域专家 + 独立进化”。它很合理，但并不意味着所有能力都必须按照专家的方式组织。

我认为至少存在三种可行架构。


    <title size="lg">方案 A：完整专家隔离</title>
    每个领域拥有自己的 Agent、提示词、记忆、工具和工作流，只共享基础设施。

    优势：隔离强，进化风险小。缺点：重复建设，跨领域能力难以复用。



    <title size="lg">方案 B：共享通用内核 + 领域专家</title>
    领域专家共享统一运行时，拥有独立策略、记忆命名空间、工具和评测集。

    优势：平衡复用与隔离，工程复杂度适中。缺点：共享内核仍可能成为共同故障源。



    <title size="lg">方案 C：能力图谱驱动的动态组合</title>
    不把所有能力固定绑定到某个专家，而是把经过验证的能力封装为可组合资产，根据任务动态组合执行链。

    优势：组合灵活、跨领域迁移潜力大。缺点：能力契约、依赖管理、调度和验证更加复杂。


我的推荐是：**采用方案 B 作为基础架构，逐步引入方案 C 的能力图谱和动态组合机制。**

不建议第一版就构建完全动态的能力网络，因为那会增加过多的调度和验证复杂度。先让专家隔离、统一协议和版本管理真正跑通，再逐步开放能力的动态组合。

## 九、进一步推导：真正需要隔离的，究竟是什么？

我认为不是“智能体”本身，而是五种可能发生变化的东西：

1. **策略隔离**：提示词、Planning、路由和恢复策略。
2. **状态隔离**：任务状态、项目记忆、临时上下文和用户数据。
3. **工具隔离**：可用工具、权限、调用预算和运行环境。
4. **评测隔离**：不同能力使用适合自己的验收标准和回归集。
5. **进化隔离**：候选改动只能在获准范围内生效，不能直接覆盖其他专家的稳定配置。

因此，专家只是组织这些隔离边界的一种方式。

一个专家可以调用其他专家，也可以组合共享能力；但它不能因为调用了某项共享能力，就获得修改该能力实现的权限。

这就让“谁可以使用能力”和“谁可以修改能力”成为两个不同的问题。

这是我们之前的专家路由设计中，应该进一步明确的部分。

# 十、我认为这轮头脑风暴得出了五个重要结论






      **结论一：能力是一张图，而不是一个树形目录。**

      它同时存在层级、依赖和交叉复用关系。








      **结论二：能力所有权必须拆分。**

      定义、实现、验收和共享晋级不应由同一个执行智能体完全控制。








      **结论三：优先共享契约与验证过的经验，不默认共享易变实现。**

      这能在复用通用能力的同时，避免策略改动造成大范围回归。








      **结论四：能力成熟度与通用性是两个不同维度。**

      一项能力可以在单个领域非常稳定，但尚不适合跨领域推广。








      **结论五：每次进化都必须声明影响范围。**

      影响范围决定测试范围、发布权限和回滚策略，而不是由模型随意决定。



## 十一、下一步还值得深挖的三个问题

现在我们已经开始触及 EvoAgent 最核心的底层设计。下一轮，我建议继续研究三个更具体的问题：

- **能力图谱如何落到数据库和工程目录中？** 怎样表示能力、实现、依赖、证据、版本和所有权，而不是只画一张架构图？
- **通用能力怎样从领域专家中产生？** 什么条件下允许经验从编程迁移到旅游或手机操作？怎样验证迁移有效而不是误用？
- **进化控制器如何决定改什么、测什么、花多少钱？** 如何把问题诊断、影响分析、评测覆盖和预算控制统一成一个可执行的决策流程？

我认为我们不需要现在就把所有问题拍板。更好的方法是先形成明确的设计假设，再通过架构推导和工程实验逐步验证。

**如果只选一个最值得先深挖的方向，我会选“能力图谱的数据模型与所有权机制”。** 因为它会决定未来所有专家如何组织、如何共享、如何独立进化，以及如何避免局部改进破坏整个系统。
