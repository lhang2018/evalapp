# EvoAgent 第四十七专项：统一质量评测、结果验收与质量进化

本轮研究 EvoAgent 的另一个核心问题：**系统怎样判断自己交付的结果是否真正满足用户需求，并且如何持续提高交付质量？**

前面已经设计了多专家架构、统一任务入口、Router、Plan、ReAct、DAG、记忆与上下文、长期任务恢复、工具运行时、安全治理、版本管理，以及 SOCDEA 因果诊断系统。

这些模块解决了任务如何规划、如何执行、如何恢复，以及出了问题如何查找原因。

但即使所有模块都正常运行，最终交付物仍然可能不合格。

例如：

- 代码成功编译，却没有实现用户要求的业务规则；
- 漫剧视频成功生成，却出现角色不一致、音画不同步；
- 旅游行程包含真实景点，却没有考虑交通时间和营业时间；
- 手机操作返回成功，却没有确认目标界面状态真的改变；
- 长篇研究报告结构完整，却遗漏了关键反例；
- 任务所有 DAG 节点都标记为完成，但最终产物仍然不符合要求。

因此，建议将本专项定义为：

**Unified Quality Evaluation & Acceptance Governance，简称 UQEAG。**

它负责统一质量模型、任务验收契约、领域评测器、证据管理、质量门禁、缺陷归因与质量进化。

需要特别区分：本专项中的 UQEAG 是新建议的架构模块名称；此前对 EQEAG 等模块的具体边界，仍应在最终全量架构中统一整理，避免不同模块承担重复职责。

## 一、第一性原理：完成任务，不等于交付合格

建议把任务结果分成四个独立维度。


    <title size="md">1. 执行完成度</title>
    计划中的操作执行到了什么程度？哪些节点完成、失败、跳过或仍在等待？



    <title size="md">2. 结果正确性</title>
    交付物是否符合事实、逻辑、程序、格式与任务约束？



    <title size="md">3. 结果适用性</title>
    结果是否适合实际使用，是否满足用户目标、资源条件和场景限制？



    <title size="md">4. 证据充分性</title>
    系统是否有足够证据支持上述判断？哪些部分尚未验证？


这四个维度不能互相替代。

一个任务可以执行完成，但结果不正确；结果可能碰巧正确，但没有足够证据证明；结果可能满足技术要求，却不适合用户的实际使用场景。

因此，不能把 DAG 完成率、工具成功率或模型自评分直接当作最终质量分数。

**UQEAG 的职责不是让系统看起来完成了任务，而是建立能够证明交付物达到要求的验收机制。**

# 二、总体架构：建立独立于执行过程的质量控制层

建议 UQEAG 横跨所有专家和任务类型，但不取代领域专家自己的专业评测能力。


    <title size="md">用户目标与任务约束</title>
    明确用户要什么、哪些条件不可违反、哪些质量指标可以权衡。





    <title size="md">验收契约生成器</title>
    将自然语言需求转换为可检查的条件、证据要求和未验证项。





    <grid-item>

        <title size="sm">通用评测器</title>
        完整性、约束遵守、可追溯性、资源与稳定性。

    </grid-item>
    <grid-item>

        <title size="sm">领域评测器</title>
        代码测试、视频质量、行程可行性、界面状态验证等。

    </grid-item>





    <title size="md">质量门禁与验收决策</title>
    结合硬性条件、质量阈值、证据充分性和用户授权，决定通过、部分通过、返工或阻塞。





    <title size="md">缺陷归因与质量进化</title>
    将失败项关联到 SOCDEA，形成经过验证的改进候选，再交由版本与进化治理流程管理。


其中有三个重要边界：

- **领域专家负责专业判断与生成结果。**
- **UQEAG 负责验收契约、质量证据和通过条件。**
- **SOCDEA 负责分析质量失败的可能原因，并通过独立验证确认根因。**

评测器可以由规则、测试程序、专业模型和人工共同组成。并不是所有质量问题都适合交给同一个模型评分。

# 三、验收契约：在执行之前定义什么叫完成

这是整个质量体系最重要的设计。

如果系统在任务完成后才决定怎样评分，就容易出现标准漂移：结果不好时放宽标准，结果不错时又宣称所有要求都已满足。

建议建立 `AcceptanceContract`，在任务规划阶段生成，并在执行前完成必要的确认。

## 3.1 验收契约的核心字段

| 字段 | 含义 |
|---|---|
| `contract_id` | 验收契约唯一标识 |
| `task_id` | 所属任务 |
| `requirements` | 用户提出的要求及其关联标识 |
| `hard_constraints` | 不可违反的硬性条件 |
| `quality_dimensions` | 需要评估的质量维度 |
| `acceptance_criteria` | 每项要求对应的通过条件 |
| `verification_method` | 采用的验证方式 |
| `evidence_requirements` | 需要保留的证据 |
| `thresholds` | 适用的质量阈值 |
| `priority_weights` | 可权衡指标的优先级或权重 |
| `uncertainty_policy` | 无法充分验证时如何处理 |
| `contract_version` | 验收标准的版本 |
| `approval_status` | 是否需要用户确认以及确认状态 |

这些字段不一定全部由用户手动填写。普通任务可以由系统自动生成默认契约，复杂任务则可以在规划阶段向用户澄清关键条件。

## 3.2 把自然语言要求转换成可验证条件

例如，用户要求：

“重构代码，保持现有功能不变，并提高可维护性。”

系统不能仅将它转换成“代码质量达到 90 分”。

更合理的做法是拆解为：

- 现有自动化测试必须通过；
- 已明确列出的外部接口行为不得改变；
- 代码结构与重复逻辑需要进行具体检查；
- 新增行为必须有相应测试；
- 未验证的兼容性风险必须列出；
- 维护性改进需要结合可解释的证据进行评估。

其中，“现有测试全部通过”是可程序化验证的条件；“可维护性提高”则可能需要多个证据来源，不能仅凭一个模型分数判断。

## 3.3 区分硬性条件和可权衡指标

建议明确区分：

- **硬性条件：** 不满足时不能判定完整通过；
- **质量指标：** 在硬性条件满足后进行比较；
- **偏好指标：** 在不违反硬性条件时尽可能优化；
- **未知项：** 当前缺乏足够证据，不能作出确定判断。

例如，用户要求视频时长为 30～60 秒，那么时长超出范围就属于明确的不合格条件，不能通过提高画质得分抵消。

如果用户更重视画质而不是速度，则可以调整质量与效率之间的权重，但不能因此取消必须满足的交付格式。

**硬性条件不能被加权平均掩盖。**

# 四、质量评测采用多层结构，而不是一个万能评分器

建议将质量评测分成五层。

  {#each [
    ["Q0 · 结构与完整性","文件是否存在、格式是否正确、必需字段是否齐全、产物是否可以读取。"],
    ["Q1 · 约束符合性","用户要求、权限限制、资源上限和任务硬约束是否得到遵守。"],
    ["Q2 · 功能与事实正确性","代码行为、计算结果、引用事实、状态变化和领域规则是否正确。"],
    ["Q3 · 专业质量与适用性","结果是否达到该领域的质量要求，能否实际使用。"],
    ["Q4 · 用户目标与整体价值","交付物是否解决了真实问题，是否满足重要偏好和整体使用场景。"]
  ] as item}

      <title size="md">{item[0]}</title>
      {item[1]}

    {#if item[0]!=="Q4 · 用户目标与整体价值"}

    {/if}
  {/each}

前几层通常更容易自动验证；越往后，越需要领域判断、用户反馈或实际使用证据。

这不意味着 Q4 一定比 Q0 更重要，而是它们回答的问题不同。

例如，文件格式错误属于结构性缺陷，即使内容非常优秀也无法直接交付；而文件格式正确，只能说明交付物具备基本结构，不能证明内容质量合格。

## 4.1 质量评测结果必须保留分项

建议每个结果都保留：

- 各项验收条件的状态；
- 证据引用；
- 质量分项；
- 关键缺陷；
- 未验证事项；
- 评测器版本；
- 最终判定依据。

不建议只存一个总分。

一个报告即使总体得分较高，也可能存在一个关键事实错误；一个视频即使画面质量很好，也可能存在严重的音画不同步。

## 4.2 评测器必须知道自己的适用边界

例如：

- 静态代码分析可以发现某些代码问题，但不能证明所有业务行为正确；
- 自动化测试可以验证已覆盖的行为，但不能证明未测试的场景没有缺陷；
- 模型评审可以比较文案或画面的某些质量特征，但不能代替所有客观检查；
- 用户满意度可以反映使用体验，但不能单独证明事实准确或安全合规。

因此，每个评测器都应声明自己能够验证什么、不能验证什么，以及结果的不确定性。

# 五、通用质量模型：不同专家使用同一套治理语言

虽然各领域的质量指标不同，但可以建立一套通用的质量维度，供所有专家复用。

| 维度 | 核心问题 |
|---|---|
| 正确性 | 结果是否正确？ |
| 完整性 | 重要要求是否遗漏？ |
| 约束遵守 | 是否违反用户明确要求或系统硬约束？ |
| 一致性 | 各部分是否互相矛盾？ |
| 可验证性 | 是否有足够证据支持结果？ |
| 可用性 | 用户是否能按预期使用交付物？ |
| 鲁棒性 | 输入变化、边界情况和异常条件下表现如何？ |
| 效率 | 是否在合理时间与资源成本内完成？ |
| 可维护性 | 结果是否便于后续理解、修改和扩展？ |
| 安全性 | 是否存在越权、泄漏或其他不可接受的风险？ |

并不是每个任务都需要全部维度。

例如，简单事实查询可以重点关注正确性、证据与时效性；代码重构需要更重视行为正确性、可维护性和回归风险；视频生成则需要专门的视听质量维度。

通用模型负责提供统一的治理框架，领域专家负责定义适合具体任务的指标。

# 六、领域质量包：专业知识不能被全局平均掉

建议建立 `QualityPack`，作为可注册、可版本化的领域质量评测能力包。

每个质量包包含：

- 适用任务类型；
- 领域质量维度；
- 评测器及版本；
- 硬性验收规则；
- 质量阈值；
- 必需证据；
- 已知局限；
- 参考评测集；
- 适用工具与模型；
- 回归测试规则。

例如，编程专家可以使用代码质量包，AI 漫剧专家使用视频质量包，旅游专家使用行程可行性质量包。

这些质量包可以独立进化，但必须遵循 UQEAG 的统一契约与发布治理。

## 6.1 编程质量包

  <title size="md">核心验收维度</title>



      **功能正确性**

      测试结果、接口行为、边界条件和需求覆盖。





      **变更完整性**

      预期文件差异、依赖变化、接口兼容和构建结果。





      **安全与质量**

      静态分析、权限边界、秘密信息暴露和必要的安全测试。





      **可维护性**

      结构清晰度、重复逻辑、复杂度和可理解性。



代码任务不能仅因测试全部通过就直接宣称完全正确，还需要说明测试覆盖的范围和未验证的风险。

## 6.2 AI 漫剧质量包

建议包含：

- 角色一致性；
- 场景与分镜匹配；
- 画面质量；
- 运动连贯性；
- 配音与角色匹配；
- 音画同步；
- 时长与格式；
- 叙事完整性；
- 预算与素材来源合规性。

其中，时长、格式、音轨和文件可读取性通常可以程序化验证；角色一致性、叙事连贯性和整体观感则可能需要专门的模型评审与人工抽检。

## 6.3 旅游规划质量包

建议包含：

- 景点与服务信息的真实性；
- 营业时间与出行日期的匹配；
- 交通时间与路线可行性；
- 用户预算约束；
- 用户偏好匹配；
- 行程强度与休息安排；
- 信息时效性；
- 预订状态是否经过实际确认。

尤其需要区分“推荐了一个景点”和“已经确认景点在指定日期开放”，也要区分“建议预订”与“已经成功预订”。

## 6.4 通用对话质量包

建议关注：

- 是否正确理解用户意图；
- 事实是否可靠；
- 是否遵循当前对话约束；
- 是否正确利用必要的上下文；
- 是否明确区分事实与推测；
- 是否遗漏重要条件；
- 是否给出适当的下一步建议；
- 是否存在不必要的冗长或偏题。

对于需要当前信息的回答，质量评测还应考虑信息时效性和来源可靠性。

# 七、证据体系：每个质量结论都应该知道依据是什么

UQEAG 不能只返回“通过”或“未通过”，还必须保存能够支持判断的证据。

建议建立 `QualityEvidence`，将验收结论与具体产物、测试、测量结果和来源关联起来。

## 7.1 证据分类

| 证据类型 | 示例 |
|---|---|
| 结构证据 | 文件存在、Schema 校验通过、视频可读取 |
| 执行证据 | 命令退出码、工具执行结果、任务状态变化 |
| 测试证据 | 单元测试、集成测试、回归测试报告 |
| 事实证据 | 可核查的来源、数据记录、外部状态查询 |
| 测量证据 | 视频时长、资源消耗、响应时间、误差范围 |
| 评审证据 | 领域模型评审、人工检查、用户反馈 |
| 过程证据 | 使用的配置版本、工具版本、任务轨迹和验收过程 |

不同证据支持的结论范围不同。

例如，视频文件的时长测量可以支持“视频时长在指定范围内”，却不能支持“故事节奏令人满意”。

## 7.2 证据必须关联版本

假设代码测试报告显示全部测试通过，但测试是在旧版代码上生成的，那么它不能直接证明新版代码通过了测试。

因此，证据需要关联：

- 产物版本或内容哈希；
- 输入数据版本；
- 测试集版本；
- 评测器版本；
- 工具与运行环境；
- 生成时间；
- 对应的验收契约。

当产物发生变化时，系统必须判断哪些旧证据仍然有效。

这与 LTAR 的产物依赖模型和 CGVCM 的版本治理直接相连。

## 7.3 建立证据充分性规则

建议将证据状态分为：

- `SUFFICIENT`：满足当前验收规则；
- `INSUFFICIENT`：缺少必要证据；
- `CONTRADICTORY`：不同证据之间存在冲突；
- `STALE`：证据已过期或对应的产物版本发生变化；
- `INVALID`：证据来源或生成过程不符合要求。

如果证据不足，系统应明确标记为未验证，而不是默认通过。

如果证据冲突，系统应进入冲突处理流程；如果证据过期，应重新验证相关条件，而不是盲目重复全部任务。

# 八、质量门禁：决定任务通过、返工还是阻塞

建议建立统一的 `QualityGate`，在关键节点和最终交付时执行验收。

质量门禁可以放在不同层级：

- DAG 节点完成后；
- 一组相关节点汇合后；
- 关键产物生成后；
- 最终交付前；
- 长期任务恢复后；
- 工具或模型版本发生变化后。

不是所有节点都需要昂贵的完整评测。轻量的结构检查可以频繁执行，昂贵的专业评审则可以集中在关键节点。

## 8.1 统一验收状态

建议定义以下状态：

| 状态 | 含义 |
|---|---|
| `PASS` | 所有适用的必要条件均满足，证据充分 |
| `PASS_WITH_WARNINGS` | 满足交付条件，但存在已披露的非阻断问题 |
| `PARTIAL_PASS` | 部分要求满足，部分要求未完成或未验证 |
| `REWORK_REQUIRED` | 存在可修复的质量缺陷，需要返工 |
| `BLOCKED` | 因依赖、权限、资源或外部条件无法继续验收 |
| `INCONCLUSIVE` | 当前证据不足以作出可靠判定 |
| `FAIL` | 已确认不满足必要验收条件 |

这些状态必须有明确的转换规则。

例如，`INCONCLUSIVE` 不能自动变成 `PASS`；`BLOCKED` 不能被当作执行失败，也不应被当作成功；`PARTIAL_PASS` 必须明确说明已完成和未完成的范围。

## 8.2 质量门禁与任务状态机分离

质量门禁负责给出验收结论，LTAR 负责管理任务生命周期。

例如：

- DAG 所有节点完成，但最终验收失败：任务可以进入返工流程；
- 部分产物合格，部分产物未完成：任务可以进入部分完成状态；
- 结果未知且无法核验：任务不应被错误标记为已完成；
- 用户决定接受某项已知缺陷：系统应记录明确的验收例外，而不是伪造质量通过结果。

这样可以避免把执行状态和质量状态混成一个字段。

## 8.3 返工必须针对缺陷，而不是无限重复生成

如果视频因为音画不同步而未通过验收，系统应定位到相关音轨、时间轴或合成节点，而不是默认重做全部素材。

如果代码只在某个边界条件上失败，应优先修复相关逻辑并重新执行必要的回归测试。

返工过程需要受到预算、次数和风险限制；反复未通过时，应转入 SOCDEA 诊断流程，而不是无限重试。

# 九、质量优化与刷分防护：不要让评测器变成新的目标漏洞

自进化系统会逐渐学习哪些行为更容易获得高分。

如果评测器存在漏洞，系统可能学会优化分数，却没有真正改善结果。

例如：

- 代码任务通过删除失败测试来提高测试通过率；
- 研究报告减少关键事实，只保留容易验证的内容；
- 漫剧系统通过降低复杂度来减少画面缺陷，却损害叙事质量；
- 规划系统通过缩短任务范围来提高完成率，却遗漏用户需求；
- 预算优化器过早终止推理，从而降低成本但损害正确性。

这类问题不能只靠增加一个更高的总分门槛解决。

## 9.1 建立独立评测与隐藏回归集

建议区分：

- **开发评测集：** 用于快速调试；
- **固定回归集：** 用于比较长期趋势；
- **隐藏评测集：** 降低针对已知测试样本过度优化的风险；
- **对抗评测集：** 检测评测器漏洞和异常策略；
- **真实使用反馈集：** 观察实际场景下的质量表现。

隐藏评测集需要受控访问，避免优化模块通过直接读取全部答案来针对性刷分。

## 9.2 对关键指标设置不可抵消的保护条件

例如：

- 关键事实错误率不得超过规定上限；
- 安全违规不得通过其他质量分数抵消；
- 重要用户约束不得被忽略；
- 必需的测试不能被候选修改随意删除；
- 结果不可验证时不能默认通过。

即使综合得分提高，只要关键保护条件被违反，就不应直接发布。

## 9.3 评测器本身也要接受审计

建议记录评测器的：

- 版本与配置；
- 输入产物版本；
- 判定结果；
- 证据引用；
- 已知局限；
- 误判情况；
- 校准结果；
- 变更历史。

如果评测器升级后通过率大幅提高，系统必须区分这是因为产物质量真的变好了，还是因为评测标准变宽松了。

# 十、用户反馈：如何让系统学会用户真正重视什么？

质量不能完全由开发者预先定义。

用户可能对同一个任务有不同的偏好。例如，编程用户可能更重视可维护性，而不是最短代码；漫剧创作者可能更重视角色一致性，而不是单帧画面精度；旅行规划用户可能更重视舒适程度，而不是每天访问更多景点。

因此，UQEAG 需要将用户反馈纳入质量进化，但不能把一次反馈直接当作普遍规律。

## 10.1 区分三种反馈

| 反馈类型 | 示例 | 建议用途 |
|---|---|---|
| 明确偏好 | “以后优先保证代码可维护性” | 更新适用范围明确的用户偏好 |
| 单次验收反馈 | “这次视频配音不自然” | 修复当前任务或形成候选改进案例 |
| 长期行为信号 | 用户反复修改同一类结果 | 作为潜在偏好或质量缺陷的证据 |

长期行为信号只是证据，不是自动授权。系统应结合上下文判断，必要时向用户确认，避免把偶然行为误认为长期偏好。

## 10.2 反馈必须关联具体质量维度

用户说“不满意”，不足以直接告诉系统该如何改进。

建议尽可能将反馈关联到：

- 哪个交付物；
- 哪项验收条件；
- 哪个质量维度；
- 哪个执行版本；
- 哪个具体缺陷；
- 用户期望的改进方向。

但不能为了结构化而强迫用户填写复杂表单。普通对话中，系统可以自然地询问一个最关键的澄清问题，或者先提出可选的改进方向。

## 10.3 用户偏好不应污染客观质量标准

用户可以决定优先追求速度还是画质，可以决定代码风格，也可以选择更保守或更有创意的方案。

但偏好不能让系统把错误事实判定为正确，也不能自动豁免必要的安全检查。

因此，建议把质量规则拆成：

- 客观正确性；
- 强制约束；
- 用户偏好；
- 领域质量判断；
- 可接受的权衡范围。

用户偏好主要影响可权衡指标，而不是任意改变全部验收条件。

# 十一、与其他专项的集成：让质量成为全系统共同遵循的契约

UQEAG 必须连接此前设计的核心模块，但不应该接管它们的全部职责。

| 模块 | 与 UQEAG 的关系 |
|---|---|
| Router | 路由质量由独立评测集和实际任务结果验证 |
| Planner / DAG | 节点级和最终验收条件成为计划约束 |
| ACMO / MEEG | 检查上下文与记忆是否保留必要要求 |
| LTAR | 恢复后重新核验受影响的产物与验收证据 |
| MTSRIC | 质量检查需要遵守资源预算与优先级策略 |
| TERSO | 提供执行证据、工具结果和产物引用 |
| ASGTB | 质量评测不能覆盖授权、安全和隐私约束 |
| CGVCM | 管理验收契约、评测器与质量包的版本兼容 |
| SOCDEA | 分析质量缺陷的根因，并验证改进效果 |
| SELCIA | 管理质量改进候选、灰度发布和回滚 |

特别需要注意：UQEAG 可以指出某个任务未通过验收，但不应直接自行修改 Router、工具权限或安全策略来提高通过率。

它应该将缺陷和证据交给相应模块与治理流程处理。

## 11.1 建立质量反馈闭环

# 十三、下一专项：任务价值决策、目标分解与自主性边界

质量体系解决了“结果好不好”，因果诊断解决了“为什么好或不好”。但还有一个更上游的问题：

**EvoAgent 如何决定应该做什么、值得投入多少资源，以及何时应该停止？**

例如：

- 用户提出一个目标，但没有给出具体执行步骤；
- 一个复杂任务需要数小时计算，成功概率却不高；
- 系统发现了可以改进的地方，但用户并没有要求改进；
- 一个任务已经达到合格标准，继续优化可能只会增加成本；
- 系统发现另一个相关问题，但解决它会扩大原任务的范围；
- 多个用户任务同时存在，系统需要判断哪个更值得优先执行。

如果没有统一的价值决策机制，EvoAgent 可能陷入两种极端：要么只执行明确指令，缺乏主动性；要么不断发现新问题、扩大任务范围，最终消耗大量资源，却没有更好地完成用户真正需要的事情。

下一专项建议定义为：

**Goal Value Assessment & Autonomy Governance，简称 GVAAG。**

重点研究：

1. 如何从用户意图中提取目标、约束和成功条件；
2. 如何区分明确指令、合理推断与系统主动提出的目标；
3. 如何评估任务价值、成功概率、成本、风险和机会成本；
4. 如何决定应该直接执行、先澄清、提出方案还是拒绝执行；
5. 如何限制任务范围不断扩张；
6. 如何决定何时继续优化、何时满足于合格结果、何时停止；
7. 如何在多个任务之间分配注意力和资源；
8. 如何管理系统主动发现的问题与用户当前目标之间的关系；
9. 如何让自主程度根据授权、风险和可逆性动态变化；
10. 如何防止系统通过自行创造目标来证明自己的存在价值；
11. 如何评估主动行动是否真正为用户带来了收益；
12. 如何将价值判断与质量验收、资源预算、安全治理和进化控制器连接。

本专项的核心原则是：

**自主性不是无限增加行动数量，而是在明确的目标、授权和资源边界内，选择最值得做的事情，并知道什么时候不应该继续做。**

这将补齐 EvoAgent 从“能够完成任务”到“能够自主选择任务、合理分配资源并控制行动边界”的关键一环。
