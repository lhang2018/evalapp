# EvoAgent 第五专项：提示词与指令治理系统全量设计

这一轮要解决一个看似简单、实际影响整个智能体的问题：**EvoAgent 的提示词到底由谁管理，哪些部分可以优化，哪些部分绝对不能被随意修改，以及如何保证某个专家的优化不会破坏其他专家。**

我们前面已经设计了：

- 多专家路由与独立领域能力；
- Plan、DAG、ReAct 与任务状态管理；
- 长期记忆、用户习惯和工作记忆；
- 上下文组装、预算分配、压缩与恢复；
- 运行日志、故障诊断、自动评测和版本进化。

现在必须将提示词放回这些系统的整体关系中，而不是把它当成一个独立的文本文件。

我的核心建议是：

**提示词不是一个大字符串，而是一套有层级、有权限、有依赖、有版本、有测试、有发布门禁的指令资产。**

而且，不是所有提示词都应该采用相同的优化方式。有些是稳定的控制规则，有些是领域策略，有些只是可以实验的表达方式。它们必须分开管理。

# 一、首先区分五类容易混淆的东西


    <title size="lg">1. 系统与安全策略</title>
    规定权限、信任边界、安全停止、数据隔离和不可绕过的约束。
    受保护


    <title size="lg">2. 通用智能体策略</title>
    规定通用任务理解、澄清、规划、行动选择、结果核验与沟通原则。
    受控优化


    <title size="lg">3. 领域专家策略</title>
    规定编程、旅游、AI 漫剧、手机操作等领域的专业知识组织和执行策略。
    独立进化


    <title size="lg">4. 阶段与任务策略</title>
    针对 Planner、ReAct、验收器、诊断器和具体任务动态选择的指令。
    按需加载


    <title size="lg">5. 工具与模型协议</title>
    工具参数、调用格式、模型适配、输出结构和错误处理规范。
    契约管理


这些类别有交叉，但它们的修改权限和评测标准不同。

例如，编程专家可以优化“如何分析一个复杂重构任务”的策略，但不能通过修改自己的提示词，取消文件写入权限检查。

同样，模型适配层可以调整某个模型需要的工具调用格式，但不能擅自改变用户的任务目标或专家的业务验收标准。

还要特别强调：**提示词里的安全声明不等于真正的安全控制。** 文件访问、支付、发送消息、权限校验和预算限制，必须由执行器与策略引擎提供确定性约束，不能只依赖模型是否遵守提示词。

# 二、建立统一的指令分层与组合机制

我建议采用“受保护内核 + 通用策略 + 专家策略 + 阶段策略 + 任务上下文”的分层体系。

但有一点需要避免：不要简单地把五段提示词按顺序拼起来，就认为完成了指令治理。真正的系统还需要依赖解析、冲突检查、权限校验和最终编译。


    **A. 受保护的控制与安全策略**
    权限边界、可信度规则、停止条件、数据隔离



    **B. 通用智能体策略**
    意图理解、任务拆解、澄清、规划与结果核验



    <grid-item>

        **C1. 领域专家策略**
        专业知识与领域方法

    </grid-item>
    <grid-item>

        **C2. 阶段执行策略**
        Planner、ReAct、验收、诊断

    </grid-item>



    **D. 当前任务与个性化信息**
    目标、约束、相关记忆、任务状态和证据



    **指令编译与模型适配**
    冲突检查、格式转换、预算控制、最终请求构建


这张图表示逻辑上的职责关系，并不意味着所有模型 API 都能将每层作为独立的 system/developer 消息传入。不同模型支持的消息角色和工具协议不同，最终需要由模型适配器编译成目标模型实际支持的请求格式。

## 2.1 受保护内核究竟保护什么？

建议将以下内容作为受保护策略资产：

- 权限和授权检查；
- 外部工具与不可信内容的信任边界；
- 用户数据和专家命名空间隔离；
- 任务取消、安全停止与人工介入规则；
- 不允许绕过的预算上限；
- 高风险操作的审批要求；
- 运行日志与证据的完整性要求；
- 发布、回滚和版本兼容规则。

这些内容应由独立的策略引擎和权限系统执行，提示词仅负责帮助模型理解和遵循相关规则。

**受保护不等于永远不能升级。** 未来确实可能需要修改安全策略，但应当走专门的变更审批、兼容性测试和发布流程，不能由普通的自动进化任务自行改写。

# 三、提示词资产要有独立的数据模型

不能把全部提示词存进数据库的一张 `prompts` 表，然后只记录文本和更新时间。

建议为提示词建立以下核心实体。

| 实体 | 作用 |
|---|---|
| `InstructionAsset` | 提示词、策略说明、工具指令等资产的身份和类型 |
| `InstructionVersion` | 某个资产的不可变版本及其内容哈希 |
| `InstructionDependency` | 资产之间的依赖、继承和兼容关系 |
| `InstructionPolicy` | 修改权限、风险等级和发布要求 |
| `InstructionBundle` | 某个专家或阶段使用的一组指令版本 |
| `CompiledPrompt` | 针对某次模型调用编译出的最终指令结构 |
| `PromptEvaluation` | 版本在指定评测集上的结果 |
| `PromptCandidate` | 由诊断或实验产生的候选改进 |
| `PromptRelease` | 发布范围、生效版本、灰度状态和回滚信息 |

其中，`InstructionBundle` 尤其重要。

因为一次运行实际使用的不是某一个提示词，而是一组相互依赖的资产。例如，编程专家可能使用：

- 通用智能体策略 V8；
- 编程专家策略 V12；
- ReAct 执行策略 V4；
- 工具调用协议 V3；
- 当前模型适配策略 V6。

这些版本组合在一起，才构成真正的运行配置。

如果只记录“编程专家提示词版本 V12”，当任务失败时，我们仍然无法确定它当时使用了什么通用策略、工具规范和模型适配版本。

## 3.1 每个提示词资产还应记录什么？

至少包括：

- 唯一 ID 与资产类型；
- 资产所属范围；
- 当前稳定版本；
- 内容哈希；
- 父版本；
- 依赖项；
- 允许修改的主体；
- 风险等级；
- 适用模型与任务类型；
- 评测集与验收契约；
- 创建原因和变更记录；
- 发布状态与回滚目标。

内容哈希可以帮助识别版本是否发生变化，但不能单独证明内容正确，也不能代替访问控制和发布审批。

# 四、最重要的设计：哪些部分允许自动进化？

这直接决定 EvoAgent 能不能在长期运行中不断变好，同时避免自我破坏。

我建议把提示词及其相关策略划分为四个进化等级。






      **P0：受保护策略**
      禁止普通自动修改
      权限、数据隔离、安全门禁、强制授权和回滚控制。任何修改都需要专门的受控流程。








      **P1：通用核心策略**
      严格评测
      通用意图理解、规划原则、上下文规则和通用结果核验。候选可以自动生成，但必须经过跨专家回归与严格门禁。








      **P2：领域专家策略**
      独立进化
      编程、漫剧、旅游等专家的专业提示词与任务方法。以各自领域的评测集为主，同时执行共享内核兼容性测试。








      **P3：实验性策略**
      沙箱验证
      候选表达方式、示例顺序、输出模板、检索提示和低风险协作策略。允许高频实验，但不能绕过预算、权限与回归门禁。



这里要区分两个权限：

- 允许模型提出和修改候选；
- 允许候选进入正式运行环境。

前者可以高度自动化，后者必须受风险等级、评测结果和发布策略约束。

## 4.1 提示词改进不一定是改提示词

当智能体回答错误时，进化系统不能默认通过修改提示词解决。

例如，编程专家没有正确完成代码修改，可能是：

- 意图识别错误；
- Planner 拆解任务错误；
- 上下文丢失了关键约束；
- 工具参数定义错误；
- AST 分析能力不足；
- 工具实际执行失败；
- 验收器判断错误；
- 提示词确实存在歧义。

如果问题来自工具实现，却通过增加一段“请仔细检查工具结果”的提示词掩盖问题，表面上可能有所改善，实际根因仍然存在。

所以，每个提示词候选都必须关联一个明确的故障假设和证据。只有诊断结果支持“提示词或指令编排是问题来源”时，才优先修改相应资产。

# 五、提示词版本、Git 分支和运行版本必须协同

之前我们讨论过：当一个模型适配好了，就应该保存为稳定版本，换模型后从新的分支继续优化。

这套原则同样适用于提示词。

建议采用三层版本管理：


    **第一层：资产版本**
    单个提示词、工具描述、阶段策略的不可变版本。


    **第二层：运行配置清单**
    锁定某次运行实际使用的所有资产、模型适配器、工具协议与策略版本。


    **第三层：发布版本与 Git 历史**
    记录候选分支、评测结果、批准记录、正式发布和回滚历史。


例如：

│   ├── safety-policy/
│   ├── general-agent/
│   └── context-policy/
├── experts/

## 5.1 模型切换时，应该分支什么？

假设当前稳定配置适配模型 A。切换到模型 B 时，不应该把全部专家策略重新复制一份，再独立发展成两套无法同步的系统。

建议分离：

- 与模型无关的通用任务规则；
- 领域专家的专业策略；
- 模型相关的消息格式、工具调用和采样配置；
- 需要针对模型行为优化的提示词变体；
- 模型特定的评测基线。

可以共享同一份领域策略资产，同时让不同模型适配配置引用它们。

只有经过实验证明某项策略在不同模型上需要不同实现时，才建立模型特定的覆盖版本。这样既能保存模型 A 的最佳配置，也不会让模型 B 的优化无条件覆盖模型 A 的稳定版本。

另外，Git 分支并不等于运行时版本。正式运行必须绑定不可变的版本清单，不能只记录一个可能继续变化的分支名。

# 六、指令冲突：不能只依靠提示词顺序解决

多个提示词资产组合时，可能出现冲突。

例如：

- 通用策略要求先确认用户目标；
- 某个专家策略要求尽快执行；
- 用户习惯偏好自动完成；
- 当前任务涉及删除文件，需要明确授权。

如果简单地将四段文本拼起来，让模型自行判断，结果可能不稳定。

因此，EvoAgent 应该建立**指令冲突检测与执行约束机制**。

## 6.1 冲突分为四类

| 冲突类型 | 示例 | 处理方式 |
|---|---|---|
| 权限冲突 | 专家要求执行，但权限不足 | 执行控制器拒绝或等待授权 |
| 任务冲突 | 历史偏好与当前明确要求不一致 | 根据适用范围和当前任务规则解决 |
| 规则冲突 | 通用策略与专家策略给出不同执行方法 | 根据策略契约确定职责和优先级 |
| 版本冲突 | 新提示词依赖旧工具协议 | 编译前检查依赖兼容性 |

不是所有冲突都应该交给大模型处理。

权限冲突必须由确定性策略决定；版本冲突必须由依赖检查解决；只有确实存在语义歧义、且没有明确规则可以判断时，才考虑由模型分析或向用户澄清。

## 6.2 建立指令契约

每个提示词资产除了文本内容，还应该声明：

- 自己负责解决什么问题；
- 哪些事情不属于自己的职责；
- 依赖哪些其他策略和工具；
- 可以修改哪些内容；
- 发生冲突时应当如何处理；
- 需要输出什么结构；
- 通过什么评测证明有效。

例如，ReAct 策略可以负责提出下一步动作，但不能自行宣布一个未经过验收的任务已经成功；诊断器可以提出根因假设，但不能直接修改稳定运行配置。

这种职责划分可以显著减少各个提示词之间的重复规则与相互矛盾。

# 七、提示词编译器：真正送进模型之前，还要做一次检查

我建议建立一个独立的 `Instruction Compiler`。

它的工作不只是拼接文本，而是将资产、依赖、当前任务和模型能力转化为一个可执行的请求配置。

编译过程可以分成六步：

  {#each [
    ["1. 解析资产","加载当前稳定版本及其依赖。"],
    ["2. 检查权限","确认当前调用可以使用哪些策略、记忆和工具。"],
    ["3. 检查兼容性","验证模型协议、工具契约和输出格式是否匹配。"],
    ["4. 处理冲突","检测规则冲突、重复指令和不兼容的策略组合。"],
    ["5. 生成请求","结合上下文视图和预算，构建模型实际支持的消息结构。"],
    ["6. 生成快照","记录最终请求结构、版本清单和必要的完整性信息。"]
  ] as item}





        **{item[0]}**
        {item[1]}


  {/each}

编译器还应支持静态检查。例如：

- 是否引用了不存在的工具；
- 是否遗漏必要的输出 Schema；
- 是否存在不满足依赖要求的版本；
- 是否超出上下文预算；
- 是否尝试加载未授权的专家资产；
- 是否存在重复或互相矛盾的硬性约束。

需要明确的是，静态检查不能证明提示词在语义上一定正确。因此，编译成功只是候选可以进入评测的前提，不代表它已经可以发布。

# 八、提示词如何自动优化？建立独立的实验闭环

现在进入自进化的核心部分。

我建议提示词进化采用以下流程：


    **发现问题**
    来自运行日志、用户纠正、验收失败或专项测试



    **诊断根因**
    确认问题是否属于提示词或指令编排



    **生成候选版本**
    提出改动假设、预期收益和可能的副作用



    **离线评测与回归**
    固定测试集、对照基线、检查安全和成本



    **影子测试与受控试运行**
    在不影响正式任务或限定范围内验证实际效果



    **发布、监控与回滚**
    只有满足门禁的版本才能成为稳定配置


## 8.1 每次候选改动必须先提出假设

例如：

> 问题：编程专家在修改代码时，经常遗漏兼容性要求。

候选假设可能是：

> 在执行计划中显式列出兼容性约束，并在修改后增加针对性检查，可以减少兼容性遗漏。

然后设计实验：

- 基线：当前稳定提示词；
- 候选：增加约束提取与修改后检查；
- 主指标：兼容性要求满足率；
- 保护指标：测试通过率、误修改率、延迟和 Token 成本；
- 回归范围：编程专家专项测试、通用任务测试和权限测试；
- 发布条件：主指标达到预设改善要求，保护指标没有不可接受的退化。

这比让一个模型“把提示词写得更好”，然后根据几条示例判断效果要可靠得多。

## 8.2 自动评测不能只依赖另一个大模型打分

可以结合：

- 确定性测试；
- 结构化输出验证；
- 代码测试与静态检查；
- 工具执行结果；
- 独立模型评审；
- 人工抽样审查；
- 真实任务中的成功率、返工率和成本。

不同任务使用不同评测方法。例如，编程任务可以运行测试，漫剧任务可以检查时长、分辨率和音画同步，手机操作任务可以验证目标界面或实际状态。

大模型评审可以提供辅助证据，但不能成为唯一的质量门禁。

# 九、成本控制：提示词进化不能无限增加模型调用

你之前明确提出，真正的能力提升可以接受适度成本增长，但不能让成本无限膨胀。这个原则必须落实到提示词优化流程中。

因为某个候选可能通过增加多轮自检、额外规划和反思，获得更高的任务成功率，但成本和延迟也可能成倍增长。

因此，每个候选必须同时评估四个维度：

- **质量**：是否真正提高任务完成质量？
- **稳定性**：是否减少失败和结果波动？
- **效率**：是否减少返工、延迟或不必要的步骤？
- **成本**：每次任务及每个成功任务的总成本增加了多少？

建议为每次实验设置预算上限，包括候选生成、评测调用、重试和灰度运行的成本。

同时，优化器应该优先尝试低成本方案：

1. 修正歧义或重复的指令；
2. 调整信息顺序和输出结构；
3. 改善上下文选择；
4. 优化工具使用策略；
5. 只有前面的方法不足时，再考虑增加模型调用、引入更昂贵的模型或增加验证步骤。

这里不能把 Token 数量作为唯一成本指标。还需要考虑模型价格、工具调用费用、失败重试、延迟和人工介入成本。

## 9.1 建立质量与成本的共同门禁

可以采用以下策略：

| 结果 | 决策 |
|---|---|
| 质量提升，成本基本不变 | 优先接受候选 |
| 质量提升，成本适度增加 | 根据预先设定的收益门槛决定 |
| 成本降低，质量不退化 | 优先接受候选 |
| 平均质量提升，但安全指标退化 | 拒绝候选 |
| 只改善少数任务，却显著损害其他专家 | 限定适用范围或拒绝 |
| 证据不足，无法判断是否改善 | 继续实验，不发布为稳定版本 |

这意味着进化系统不是追求“最强的单次回答”，而是寻找在质量、稳定性、效率和成本约束下更优的策略。

# 十、Android 端、服务端和模型供应商之间怎么分工？

结合 EvoAgent 的手机优先战略，我建议明确以下职责。


    **Android App：稳定执行与本地保护**
    加载已批准的指令包、执行本地任务、记录运行版本、采集日志、实施权限检查、离线保存状态，并在兼容性允许时继续使用已有稳定版本。


    **服务端：实验、评测与发布治理**
    汇总授权上传的运行证据、诊断问题、生成候选、执行评测、管理版本、控制灰度发布与回滚。


    **模型供应商：推理与模型能力**
    提供模型推理、工具调用等能力。模型可以帮助提出优化建议，但不直接拥有 EvoAgent 的发布权限。


这里还有一个重要边界：提示词更新不一定需要更新整个 Android App。

如果变化只是经过批准的提示词、专家策略或上下文配置，可以通过签名的版本化配置包分发；如果变化涉及本地执行器、权限控制、数据库结构或原生代码，则可能需要应用更新或专门的迁移流程。

而且，离线设备不应因为收到一个新配置，就自动覆盖仍有未完成任务依赖的旧版本。它必须检查兼容性，并保留可回滚的稳定配置。

# 十一、这一轮建议冻结的架构决策

  {#each [
    "提示词被视为具有身份、版本、依赖和发布状态的正式工程资产。",
    "区分受保护策略、通用核心策略、领域专家策略和实验性策略。",

# 十二、下一步：设计工具与专业能力治理系统

我建议接下来不要急着进入代码实现，而是先深入设计 **EvoAgent 工具与能力系统**。

原因是，我们已经讨论过一个特别关键的问题：如果工具本身就有问题，智能体可能识别错误、调用错误，或者根据错误结果继续推理。单纯优化提示词并不能解决这些问题。

下一轮需要明确：

1. 工具、专业技术能力、领域专家和工作流之间的边界；
2. 如何描述工具的输入输出契约、前置条件、权限和副作用；
3. 如何区分工具自身故障、模型误用工具、参数错误和环境问题；
4. 如何通过契约测试、运行时校验和故障注入验证工具可靠性；
5. 如何为编程场景增加 AST、静态分析、测试运行器等专业能力；
6. 如何让多个专家复用经过验证的能力，而不共享彼此的错误经验；
7. 工具升级后如何兼容旧任务、评测新版本并安全回滚；
8. 如何将工具故障诊断与提示词进化分离，避免优化错方向。

这一步完成后，EvoAgent 才能真正区分：**是模型没做好、提示词没设计好、上下文丢失了信息、工具实现有缺陷，还是工作流本身不合理。**

只有具备这种故障归因能力，自进化系统才能针对真正的问题改进，而不是遇到任何失败都去修改提示词。
