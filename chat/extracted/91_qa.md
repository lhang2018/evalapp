# EvoAgent 第三十九专项：自适应推理深度、模型调用与计算预算治理

本轮进入 EvoAgent 的资源调度与推理控制层，解决一个关键问题：

**面对不同任务，EvoAgent 如何决定投入多少思考、调用多少次模型、使用哪些专家、运行哪些工具，以及什么时候应该停止？**

这不是简单的模型选择问题，而是一个贯穿整个智能体的动态决策问题。

例如，同样是编程任务：

- 修改一个简单的配置值，可能只需要一次模型调用和一次校验。
- 修改多个模块的接口，可能需要规划、代码分析、实施和回归测试。
- 修复一个反复出现但原因不明的故障，可能需要多轮证据收集、根因分析和对照实验。
- 修改支付、权限或数据迁移逻辑，即使代码量很少，也可能需要更严格的验证。

因此，不能仅凭任务长度决定推理深度，也不能把所有任务都交给最强模型、执行最多轮次。

本专项建议定义为：

**Adaptive Reasoning & Compute Budget Governance，简称 ARCBG。**

它负责任务难度评估、推理策略选择、模型与专家调度、预算分配、停止条件、资源降级和效果评测。

## 一、第一性原理：资源投入应由预期收益和风险决定

EvoAgent 每增加一次模型调用、专家协作或工具执行，都可能获得更多信息，但也会增加成本、延迟和出错机会。

所以系统真正需要回答的不是“还能不能继续思考”，而是：

**再投入一单位资源，是否有足够大的机会改善最终结果？**


    <title size="md">任务需求</title>
    目标复杂度、信息缺口、任务依赖、失败影响和验收要求。





    <title size="md">资源与策略决策器</title>
    选择模型、推理方式、专家数量、工具调用、验证深度和预算。





    <title size="md">执行与观察</title>
    运行模型、专家、工具和工作流，收集结果、成本、耗时及进展证据。





    <title size="md">继续、切换、停止或恢复</title>
    根据实际进展动态调整资源，而不是机械执行预先设定的调用次数。


这里有一个重要边界：资源调度器可以决定投入多少计算资源，但不能擅自降低用户的硬性要求或绕过安全约束。

如果预算不足以满足必要的验收要求，系统应该明确说明限制、请求追加预算、提供安全的部分结果，或停止任务，而不是将不合格的结果标记为成功。

# 二、首先判断任务需要哪一种执行模式

建议 EvoAgent 先判断任务的执行结构，再决定模型和预算，而不是所有任务都进入 Planner 或 ReAct 循环。

| 执行模式 | 典型场景 | 资源策略 |
|---|---|---|
| 直接回答 | 简单解释、翻译、明确事实处理 | 一次或少量模型调用 |
| 工具增强 | 需要计算、查询文件、执行代码或核验事实 | 选择必要工具并验证结果 |
| 轻量规划 | 多步骤但依赖简单的任务 | 生成简短计划，按步骤执行 |
| ReAct 循环 | 需要根据工具观察动态调整下一步 | 逐轮判断是否产生有效进展 |
| Planner + DAG | 多阶段、存在依赖或可并行的复杂任务 | 显式管理依赖、预算和节点状态 |
| 多专家协作 | 需要不同领域能力或独立审议 | 仅在互补价值足够时增加专家 |
| 诊断与实验 | 根因不明、现有策略持续失败 | 投入证据收集、对照实验与独立评测 |

这些模式不是互相排斥的。

例如，复杂编程任务可以先通过 Planner 生成 DAG，再由某个节点运行 ReAct 循环；如果出现反复失败，则切换到根因诊断流程。

**选择正确的执行结构，往往比单纯增加推理轮数更重要。**

# 三、任务难度评估：不能只看任务有多长

建议建立独立的 `TaskDifficultyEstimator`，在执行前评估任务的资源需求，并在执行过程中根据实际表现不断修正。

它不应该只依靠模型给出的一个“难度分数”，而应综合多个可观察因素。

## 3.1 六个核心评估维度

    ["D2 · 不确定性","目标、输入、环境或解决方案中有多少尚未确定的部分。"],
    ["D3 · 失败代价","错误是否会造成数据损坏、重大返工、财务损失或不可逆副作用。"],
    ["D4 · 验证难度","结果能否通过测试、计算、规则检查或权威来源直接验证。"],
    ["D5 · 能力缺口","当前专家、模型、工具和已有工作流是否具备足够的能力。"],
    ["D6 · 资源需求","预期 Token、执行时间、外部调用费用、内存和并发需求。"]

      {item[1]}

    {#if item[0]!=="D6 · 资源需求"}

    {/if}
  {/each}

这六个维度不应被简单地压缩成一个万能分数。

例如，任务可能很简单，但失败代价极高；也可能很复杂，但可以通过确定性测试充分验证。两者需要不同的资源策略。

## 3.2 采用分层决策，而不是完全依赖评分

建议采用三步判断：

1. **硬约束检查：** 是否需要独立验收、明确授权或特定安全流程？
2. **执行结构判断：** 是否需要工具、规划、DAG 或多专家协作？
3. **资源规模估计：** 根据复杂度、不确定性、历史表现和资源限制，决定初始预算。

这样，风险不会被一个较低的平均难度分数掩盖。

例如，涉及不可逆文件操作的任务，即使只包含一步，也可能必须先核验目标、检查授权并准备恢复方案。

## 3.3 采用动态难度，而不是一次评估后不再改变

任务开始时的难度只是预测。

执行过程中，系统可能发现：

- 原本以为是简单修改，实际存在复杂依赖；
- 原本需要多个专家的问题，实际上已有成熟工作流；
- 工具返回的证据足够明确，可以提前结束；
- 连续多轮失败说明原计划可能不成立；
- 外部服务不可用，需要切换策略。

因此，难度评估需要在关键事件发生后更新，例如节点失败、预算接近上限、发现新依赖或验证结果与预期不符时。

但不能每次出现轻微波动就重新规划整个任务。应设置明确的触发条件，防止调度器本身产生大量开销。

# 四、推理深度控制：什么时候继续思考，什么时候转向执行？

这里需要区分三种不同的资源消耗：

- 模型内部的推理计算；
- 多轮模型调用与 ReAct 循环；
- 外部工具、专家和工作流执行。

它们不能完全互相替代。

例如，模型继续推理可能无法获得当前文件的真实内容；此时调用文件工具更有价值。反过来，如果工具已经返回明确结果，再调用多个专家重复分析也可能没有意义。

## 4.1 建立四种资源动作

建议每轮决策后，从以下动作中选择：




      **继续推理**
      仍存在可通过分析当前证据解决的重要问题，且预期收益高于成本。






      **获取新信息或执行工具**
      当前缺少事实、运行结果或外部状态，继续纯推理无法弥补信息缺口。






      **切换策略或重新规划**
      当前路径反复失败、出现新依赖，或已有证据表明原方案不再合适。






      **停止并验收**
      目标已达到、必要证据齐全，或者继续投入已没有足够价值。



注意，“停止”不总是意味着任务成功。系统还需要区分成功完成、部分完成、等待外部条件、预算耗尽和失败终止。

## 4.2 衡量有效进展，而不是统计思考轮数

每轮执行后，系统应该检查是否产生了实际进展：

- 是否解决了一个明确问题；
- 是否获得了新的有效证据；
- 是否减少了关键不确定性；
- 是否完成了一个经过验收的节点；
- 是否排除了某个根因假设；
- 是否降低了后续任务的风险。

如果连续几轮只是在重复相似的解释、反复调用同一工具，或生成无法验证的新计划，就应考虑停止、切换策略或进入诊断。

**轮数多不代表思考充分；产生可验证的新信息和有效结果，才是继续投入资源的理由。**

# 五、模型选择：不是永远选最强，而是选择满足任务要求的最低充分成本方案

EvoAgent 可以接入多个模型，也可以同时使用本地模型和云端模型。因此，需要一个统一的模型路由策略。

建议将模型选择与专家路由分开：

- 专家路由决定由哪个领域能力负责；
- 模型路由决定该专家使用哪个模型；
- 资源调度器决定调用次数、预算与执行策略。

三者协作，但不应混成一个不可解释的黑盒决策。

## 5.1 建立模型能力注册表

每个模型至少应记录：

- 支持的输入与输出类型；
- 上下文窗口与最大输出限制；
- 代码、推理、视觉、工具调用等能力评测；
- 实际延迟与可用性；
- 费用或本地资源消耗；
- 工具调用和结构化输出支持；
- 数据处理与部署限制；
- 已验证的适用任务；
- 失败率与降级路径。

不能仅依靠模型名称或供应商宣传来判断模型是否适合某个任务。

## 5.2 采用分级调用策略

建议将模型使用分为三个逻辑级别。

| 级别 | 适用场景 | 典型策略 |
|---|---|---|
| L1 · 轻量 | 简单问答、分类、格式整理、确定性辅助任务 | 优先选择低成本、低延迟方案 |
| L2 · 标准 | 多步骤分析、一般编程、需要工具配合的任务 | 使用满足任务质量要求的主力模型 |
| L3 · 高能力 | 复杂规划、疑难诊断、关键架构决策、困难代码问题 | 使用经过相应任务评测的高能力模型，并配置必要验证 |

这些是调度级别，不是固定绑定三个具体模型。

例如，某个经过验证的本地模型可能足以完成简单代码任务；某个云端模型可能在复杂推理上更有优势。但是否选择它们，应根据当前可用性、质量证据、费用和数据约束决定。

## 5.3 什么时候应该升级模型？

建议在以下情况考虑升级：

- 当前模型连续出现相同类型的失败；
- 任务需要当前模型不具备的能力；
- 关键问题在合理的工具使用后仍然无法解决；
- 独立验收发现实质性缺陷；
- 当前任务的风险和质量要求高于现有模型已验证的能力范围。

升级之前，先判断失败究竟来自模型能力、信息缺失、工具问题还是错误的任务分解。

如果文件工具根本没有读取到关键文件，换成更强的模型也未必能解决问题。

## 5.4 什么时候应该降级？

本地优先或离线模式下，云端模型可能不可用；预算也可能不足以继续使用高成本模型。

这时可以：

- 切换到满足当前任务要求的本地模型；
- 采用更小的子任务；
- 使用确定性工具替代部分模型推理；
- 暂停需要云端能力的节点；
- 交付已验收的部分结果。

但是，降级必须显式记录，并重新检查当前任务是否仍然满足必要的质量与安全要求。

不能因为系统切换到了低能力模型，就自动放宽验收标准。

# 六、预算治理：每个任务都必须知道自己还能花多少资源

建议建立统一的 `TaskBudget`，由任务协调器管理。

预算至少包括：

| 预算类型 | 作用 |
|---|---|
| Token 预算 | 限制累计输入与输出 Token |
| 费用预算 | 限制模型及外部服务费用 |
| 时间预算 | 限制任务总耗时或阶段耗时 |
| 调用预算 | 限制模型调用、工具调用和重试次数 |
| 并发预算 | 限制同时运行的专家、工具与任务节点 |
| 本地资源预算 | 限制内存、CPU、GPU 和磁盘等资源使用 |
| 副作用预算 | 控制文件修改、外部请求及其他需授权操作的范围 |

其中，副作用预算并不替代授权机制。即使任务还有充足的预算，也不意味着系统可以执行未授权操作。

## 6.1 预算需要分层管理

建议同时存在三个层级：

- **全局预算：** 当前运行环境能够使用的资源上限；
- **任务预算：** 单个用户任务的总资源限制；
- **节点预算：** 单个 DAG 节点或 ReAct 阶段允许使用的资源。

例如，视频制作任务的总预算是 100 个成本单位，可以把其中一部分分配给素材生成、另一部分分配给视频合成和质量检查，并保留一定的故障恢复预算。

这不是要求预算必须在开始时固定分配。实际执行中可以动态调整，但任何调整都必须遵守全局上限和用户批准的约束。

## 6.2 不要把预算一次性平均分给所有节点

有些节点非常便宜，有些节点是昂贵的外部生成任务。

建议采用“初始估算 + 按需申请 + 阶段性再分配”的模式：

1. Planner 估算节点的资源需求；
2. 调度器为当前可执行节点分配预算；
3. 节点执行后报告实际消耗；
4. 系统根据结果、剩余工作和失败风险重新分配；
5. 超过节点预算时，暂停并决定重试、调整或终止。

对于并行节点，应先保留其他必要节点的预算，避免某个失败节点通过反复重试耗尽整个任务资源。

## 6.3 预留故障恢复资源

预算不能全部消耗在正常路径上。

建议为需要可靠交付的任务保留恢复额度，用于：

- 关键工具重试；
- 局部重新规划；
- 失败节点替换；
- 必要的独立验收；
- 最终产物修复。

恢复额度的比例应根据历史失败率、任务类型和风险确定，而不是对所有任务使用统一固定值。

如果恢复预算没有使用，可以释放给最终验收或其他有价值的步骤。

# 七、停止条件：避免无限推理与无意义重试

自适应推理必须有明确的停止机制。

建议建立统一的 `StopController`，由它综合判断任务是否完成、是否继续投入资源、是否需要等待，以及是否应该停止执行。

## 7.1 六类停止条件

  {#each [
    ["目标完成","必要交付物已经产生，并且通过对应的验收标准。"],
    ["证据充分","当前决策所需的事实与验证结果已经足够，不需要继续重复确认。"],
    ["边际收益不足","继续推理或调用工具的预期收益低于成本，且没有必须完成的验证。"],
    ["预算耗尽","达到资源上限，需要停止、申请追加预算或交付部分结果。"],
    ["等待外部条件","依赖的服务、用户确认、文件或设备当前不可用。"],
    ["风险或状态不明","无法确认操作是否已执行、授权是否有效或状态是否一致时，暂停危险操作并进入核验或恢复流程。"]
  ] as item}

      <title size="md">{item[0]}</title>
      {item[1]}

    {#if item[0]!=="风险或状态不明"}

    {/if}
  {/each}

这六类条件对应不同的结束状态，不能全部记为 `SUCCESS`。

## 7.2 为 ReAct 循环增加无进展检测

建议为每轮 ReAct 记录：

- 当前目标；
- 最近一次有效观察；
- 已尝试的动作；
- 已排除的方案；
- 是否产生新的证据；
- 是否出现重复动作；
- 剩余预算；
- 下一步动作的预期价值。

如果多轮执行没有产生有效进展，系统可以采取以下策略：

1. 停止重复相同动作；
2. 检查工具输入和返回结果；
3. 调整搜索或执行策略；
4. 请求更合适的专家；
5. 进入 RCAE 根因分析；
6. 在预算和安全边界内终止任务。

建议将“连续无进展次数”作为可配置参数，而不是所有任务都使用同一个固定数字。

对于确定性工具失败，可以更快触发切换；对于复杂探索任务，可以允许有限的不同策略尝试。

## 7.3 完成必须由验收决定，而不是由模型自我宣告

模型说“已经完成”，只是一项声明。

任务是否真正完成，应由相应的验收机制判断。

例如：

- 代码修改需要检查差异、运行必要测试；
- 视频制作需要检查文件可播放性、时长和必要的视听要求；
- 文件操作需要核实目标状态；
- 研究任务需要检查关键结论是否有足够证据。

如果验收失败，系统可以继续执行修复；如果验收无法进行，则应该标记为待验收或受限完成，而不是假装通过。

# 八、离线与故障降级：资源不足时，系统如何继续工作？

EvoAgent 采用个人设备优先的方向，因此 ARCBG 必须考虑本地设备、微型 Linux 主机和可选云端服务之间的资源差异。

建议建立明确的能力降级矩阵。

| 故障或限制 | 优先处理方式 | 不应做的事 |
|---|---|---|
| 云端模型不可用 | 切换到经过验证的本地模型，或暂停依赖云端的节点 | 假装本地模型具有相同能力 |
| 本地内存不足 | 降低并发、缩小任务批次、释放缓存 | 不受控制地反复重试 |
| GPU 不可用 | 使用兼容的 CPU 路径、其他模型或等待恢复 | 继续提交无法运行的任务 |
| 外部生成服务离线 | 保留已完成产物，等待恢复或选择兼容替代服务 | 丢弃已验收成果 |
| 任务预算不足 | 重新规划、申请追加预算或交付部分结果 | 自动扩大用户授权预算 |
| 网络断开 | 使用本地可用能力，记录待执行任务与状态 | 假设未确认的远程操作已经失败 |
| 关键状态无法确认 | 暂停相关副作用，恢复连接后核验 | 重复提交可能产生重复副作用的操作 |

这里有一个重要原则：

**降级可以降低服务范围，但不能静默降低结果可信度。**

例如，云端视频生成服务离线时，本地设备可能仍然可以完成素材管理、字幕准备和 FFmpeg 合成，但不能因此声称尚未生成的视频镜头已经完成。

## 8.1 恢复后要核对状态，不只是继续执行

网络恢复后，任务协调器需要核验：

- 哪些节点已经完成；
- 哪些节点正在执行；
- 哪些外部操作结果尚不确定；
- 哪些产物已经持久化；
- 哪些任务可以安全重试；
- 当前模型和工具版本是否发生变化；
- 之前的上下文快照是否仍然有效。

然后再恢复调度。

这需要与此前设计的离线日志同步、断点恢复、幂等和任务状态治理机制协同，不能由模型自己判断整个任务是否已经执行过。

# 九、让预算分配也能自我进化，但不能让系统随意放大资源消耗

当 EvoAgent 积累足够的运行数据后，可以逐步学习不同任务的实际资源需求。

例如，系统发现：

- 简单代码问答通常不需要多个专家；
- 某类大型仓库任务在首次调用后立即生成代码，返工率明显较高；
- 某种视频生成任务需要为失败镜头预留恢复预算；
- 某个轻量模型在特定任务上的质量已足够，使用更昂贵模型没有明显收益。

这些结果可以用于改进预算策略。

但应遵循以下流程：

1. 记录真实任务的预算、策略与验收结果；
2. 按任务类型和难度分析资源消耗；
3. 提出新的预算分配策略；
4. 在历史任务回放或隔离环境中评测；
5. 比较质量、成本、耗时与失败恢复表现；
6. 通过受控试运行后再发布；
7. 持续观察是否发生质量退化。

**系统可以学习如何更有效地使用已批准的资源，但不能因为预测收益较高，就自行突破用户设定的预算上限。**

## 9.1 分别评测四种能力

为了避免诊断与执行再次耦合，建议将以下能力分别评测：

- **难度判断：** 是否正确识别任务复杂度、风险和不确定性；
- **资源预测：** 是否合理估计 Token、时间、费用和工具调用；
- **策略选择：** 是否选对模型、专家、执行结构和验证方式；
- **停止判断：** 是否既避免过早结束，也避免无意义的继续执行。

如果系统在复杂任务上频繁预算不足，原因可能是难度预测错误，也可能是工具实际成本发生变化，或者任务分解策略过于乐观。

不能只增加预算就宣布问题已经解决。

# 十一、下一专项：主动感知、信息获取与不确定性治理

前面已经设计了任务规划、专家协作、上下文构建和计算预算。但还有一个更基础的问题没有完全解决：

**当 EvoAgent 不知道某件事时，它应该如何发现自己不知道、决定去哪里获取信息，以及判断获取到的信息是否足以支持行动？**

例如，用户说：“帮我修复项目中的性能问题。”

此时系统可能不知道：

- 性能瓶颈究竟在哪里；
- 是否有足够的运行日志；
- 是否需要先运行性能分析工具；
- 是否应该读取更多代码；
- 是否需要用户补充目标性能指标；
- 是否已经有足够证据直接开始修改。

如果系统过早行动，可能修错方向；如果不停地搜索、提问和调用工具，又会浪费资源。

下一专项建议定义为：

**Active Perception, Information Acquisition & Uncertainty Governance，简称 APIUG。**

重点研究：

1. 如何识别当前任务中的信息缺口；
2. 如何区分事实未知、目标不明确、能力不足和环境不可用；
3. 如何决定直接执行、读取文件、调用工具、检索资料或询问用户；
4. 如何判断一条信息的来源是否可信、是否过时；
5. 如何衡量不同信息获取动作的预期价值；
6. 如何选择最有价值的下一项观察或实验；
7. 如何在多个冲突来源之间建立证据链；
8. 如何决定现有证据是否足以支持执行；
9. 如何避免反复搜索已经知道的内容；
10. 如何在信息不足时安全地暂停或请求澄清；
11. 如何将新观察更新到任务状态和上下文，而不污染长期记忆；
12. 如何评测主动感知是否真正减少了错误、返工和无效资源消耗。

这个专项会连接 ACMO、ARCBG、RCAE、ODERI、Planner、ReAct 和工具运行时。

最终目标是：

**让 EvoAgent 不仅会利用已有信息，还会主动判断自己缺少什么、以最低合理成本获取关键证据，并在证据不足时知道何时不应该贸然行动。**

下一轮将从第一性原理开始，设计 EvoAgent 的不确定性模型、信息获取策略、证据可信度体系与主动观察闭环。
