# EvoAgent 第六专项：工具、专业能力与工作流治理系统全量设计

这一轮，我们解决 EvoAgent 自进化架构中另一个容易被低估的问题：**智能体能否正确判断自己需要什么能力、正确调用它、确认它是否可靠，并在能力本身出现问题时找到真正的根因。**

前面已经设计了提示词治理、上下文工程、记忆、任务状态、ReAct 和多专家架构。现在需要把这些模块与真正执行工作的工具连接起来。

例如，编程专家修改代码失败，可能有很多原因：

- 模型没有正确理解需求；
- Planner 把任务拆错了；
- 上下文漏掉了兼容性约束；
- 模型调用工具时参数错误；
- 工具接口定义与真实实现不一致；
- AST 分析器有缺陷；
- 编译环境缺少依赖；
- 测试本身不可靠；
- 验收器错误地判定成功。

如果 EvoAgent 只记录“任务失败”，然后让服务端修改提示词，它就可能不断优化错误的对象。

因此，这一专项的核心目标是建立一套**能力可描述、调用可约束、结果可验证、故障可归因、版本可追溯、升级可回滚**的工具与能力基础设施。

# 一、首先统一六个概念

这些概念必须分清，否则后续数据库、接口和进化系统都会混乱。


    <title size="lg">1. 工具 Tool</title>
    一个可以被调用的具体执行接口。
    例如：读取文件、启动 Android 应用、运行测试、生成图像、查询云端任务状态。


    <title size="lg">2. 专业技术能力 Skill</title>
    完成某类问题所需的算法、知识、工具组合和验证方法。
    例如：Python AST 重构、角色一致性检查、Android 界面状态识别。


    <title size="lg">3. 领域专家 Expert</title>
    理解某个领域目标，选择策略、专业能力和工具，并对领域结果负责。
    例如：编程专家、AI 漫剧专家、手机操作专家。


    <title size="lg">4. 工作流 Workflow</title>
    把经过验证的多个步骤编排成可重复、可恢复的执行过程。
    例如：剧本 → 角色 → 分镜 → 视频 → 配音 → 合成 → 验收。


    <title size="lg">5. 模型适配器 Model Adapter</title>
    把统一的模型调用协议转换成具体供应商或模型支持的请求格式。
    例如：工具调用格式、结构化输出、模型能力差异和错误码映射。


    <title size="lg">6. 运行环境 Runtime</title>
    实际执行工具和工作流的设备、进程、依赖、权限与资源环境。
    例如：Android 本地执行环境、云端容器、Python 沙箱、FFmpeg 运行环境。


它们之间的关系可以概括为：

- 专家决定当前任务需要什么专业能力。
- 专业能力决定应该采用哪些算法、工具和验证步骤。
- 工作流将多个能力按依赖关系组织起来。
- 工具执行具体操作。
- 运行环境提供真实的执行条件。
- 模型适配器负责模型交互，不负责替工具证明其结果正确。

**工具是能力的执行入口，但工具本身不等于完整能力。**

例如，能够调用 Python 解释器，不代表具备可靠的代码修改能力。真正的代码修改能力还需要理解项目结构、分析语法树、规划修改、运行测试、检查差异并验证结果。

# 二、建立统一能力注册中心

EvoAgent 需要一个统一的 Capability Registry（能力注册中心），让路由器、Planner、专家和工作流引擎知道当前有哪些能力可以使用，以及它们适用于什么条件。

但它不能只是一个工具名称列表。

一个能力注册项至少应该回答十个问题：

1. 它能解决什么问题？
2. 哪些任务适合使用它？
3. 哪些情况不适合使用它？
4. 需要什么输入和前置条件？
5. 输出什么结果？
6. 会产生什么副作用？
7. 需要哪些权限？
8. 运行成本和资源需求是什么？
9. 如何验证结果正确？
10. 当前哪个版本经过了哪些测试？

这是注册协议的示例。正式实现还应记录能力来源、依赖版本、运行环境约束、许可证、超时策略、兼容性范围、故障历史和发布清单。

这里的 `cost_class` 只能用于初步筛选，不能替代实际成本核算。真正调度时，还应考虑当前资源占用、预计执行时间、外部 API 费用和剩余预算。

## 2.2 能力发现与执行权限分开

注册中心回答的是“有哪些能力、哪些可能适用”。

它不应该直接决定“当前任务可以执行哪些动作”。

例如，系统注册了文件删除工具，不意味着编程专家可以随意删除用户文件。实际执行仍需要检查：

- 当前任务是否确实需要删除；
- 目标文件是否属于授权范围；
- 当前用户是否授予相应权限；
- 删除是否可恢复；
- 是否需要用户确认；
- 当前运行环境是否允许该操作。

能力发现与权限判定必须是两个独立步骤。

## 2.3 能力可以有多个实现

这对手机优先和云端优先架构都很重要。

同一种逻辑能力可能有多个实现：

| 能力 | 实现 A | 实现 B |
|---|---|---|
| 图像识别 | Android 本地视觉模型 | 云端视觉 API |
| 语音转写 | 本地语音识别 | 云端语音识别 |
| 代码分析 | 本地 AST 工具 | 云端代码分析服务 |
| 视频合成 | 手机端 FFmpeg | 云端视频处理服务 |
| 界面识别 | Android 无障碍节点 | 屏幕视觉识别 |

因此，专家应该依赖稳定的能力契约，而不是把具体供应商、设备或工具实现写死在自己的提示词中。

调度器可以根据准确率、延迟、成本、隐私、网络状态和可用资源选择实现，但不能为了节省成本而违反任务质量或权限要求。

# 三、统一工具契约：调用之前，先明确什么叫正确调用

工具最常见的问题之一，是接口看起来能调用，但输入输出的含义不清楚。

例如，一个名为 `open_app` 的工具，究竟表示：

- 已经发出了启动请求；
- Android 已经接受启动请求；
- 目标应用已经进入前台；
- 目标页面已经成功打开；
- 用户可以开始下一步操作。

这五个结果完全不同。

如果工具只返回 `{"success": true}`，ReAct 可能把“启动请求已提交”误判为“任务已经完成”。

所以，我建议每个工具都必须声明输入契约、输出契约、前置条件、后置条件、失败语义和副作用。

## 3.1 工具契约至少包括哪些部分？

| 契约部分 | 需要明确的内容 |
|---|---|
| 输入契约 | 必填字段、类型、范围、格式和业务约束 |
| 前置条件 | 权限、登录状态、文件存在、网络可用等 |
| 执行语义 | 工具实际承诺执行到哪一步 |
| 输出契约 | 返回值结构、状态含义、证据和错误类型 |
| 后置条件 | 调用结束后必须成立的可验证条件 |
| 副作用 | 文件修改、应用启动、费用产生、消息发送等 |
| 幂等语义 | 相同请求重复执行会怎样 |
| 超时语义 | 超时代表失败、未知，还是仍在后台执行 |
| 恢复语义 | 能否查询状态、重试、取消或补偿 |
| 版本兼容 | 输入输出是否兼容旧调用方 |

特别是“超时语义”和“幂等语义”，它们直接决定任务能否安全恢复。

## 3.2 用 Android 应用启动举例

假设工具的输入是：

```json
{
  "package_name": "com.example.app",
  "launch_mode": "foreground"
}
```

不能简单地把返回结果定义成：

```json
{
  "success": true
}
```

更合理的是区分：

```json
{
  "request_status": "ACCEPTED",
  "observed_state": "UNKNOWN",
  "package_name": "com.example.app",
  "evidence_refs": [],
  "error": null
}
```

随后由界面状态观察器确认应用是否真正进入前台。

如果应用启动失败，则返回明确的错误类别，例如：

- `APP_NOT_INSTALLED`
- `LAUNCH_NOT_ALLOWED`
- `ACTIVITY_NOT_FOUND`
- `APP_START_TIMEOUT`
- `FOREGROUND_NOT_CONFIRMED`

这里的重点不是错误码一定采用这些名字，而是必须让不同故障拥有不同的语义，避免 ReAct 只能根据自然语言错误信息猜测发生了什么。

## 3.3 工具输出不能自动等于事实

工具返回值也可能错误。

因此，建议区分三个层次：

1. **工具自报结果**：工具声称自己执行了什么。
2. **运行证据**：日志、文件、系统状态或远端任务状态。
3. **独立验证结论**：根据证据和验收规则判断结果是否符合预期。

并非每个工具都需要独立调用第二个工具来验证，但对高风险操作和关键任务结果，应当尽可能获得与执行声明相独立的证据。

例如，文件写入工具返回成功后，可以通过读取文件、校验哈希或检查目标内容验证；云端视频生成返回成功后，可以查询远端任务状态并检查实际产物。

# 四、工具调用控制器：所有执行统一经过一个受控入口

我不建议让每个专家直接调用底层工具。否则，不同专家可能各自实现权限检查、重试、日志和错误处理，最终很难保证行为一致。

建议引入统一的 `Tool Execution Gateway`。


    **专家 / ReAct / 工作流节点**
    提出工具调用请求



    **工具执行网关**
    参数校验、权限检查、预算预留、幂等控制



    <grid-item>

        **本地执行器**
        Android / 桌面 / 沙箱

    </grid-item>
    <grid-item>

        **远端执行器**
        API / 云端任务 / 服务

    </grid-item>



    **结果核验与执行账本**
    记录结果、证据、副作用、费用与错误



    **统一执行结果**
    返回 ReAct、工作流引擎和任务控制器


这个网关负责确保工具调用遵守统一的执行规则，但不需要把所有工具实现都放在一个进程或一台服务器中。

## 4.1 调用协议需要具备哪些机制？

建议每次调用至少关联：

- `invocation_id`：唯一调用标识；
- `task_id`、`node_id`：任务与节点关联；
- `capability_id` 和 `tool_version`：实际使用的能力与工具版本；
- `idempotency_key`：识别同一逻辑操作的重复请求；
- `authorization_context`：授权检查的受控引用；
- `budget_reservation_id`：预算预留记录；
- `trace_id`：贯穿模型、工具和任务日志的关联 ID；
- `input_ref`、`output_ref`：必要的输入输出引用；
- `side_effect_state`：副作用状态；
- `evidence_refs`：支持执行结论的证据。

这样，工具故障可以关联到具体任务、模型调用、专家版本和上下文快照，而不是只留下一个孤立的错误日志。

## 4.2 重试机制不能一刀切

我建议至少将重试分为四类：

| 类别 | 示例 | 默认处理 |
|---|---|---|
| 安全重试 | 读取文件时发生暂时性网络错误 | 在预算和次数限制内重试 |
| 核查后重试 | 云端任务请求超时 | 先查询原请求状态 |
| 修正后重试 | 参数格式错误 | 修正参数并重新校验 |
| 禁止自动重试 | 已发送消息、已支付、权限被拒绝 | 停止或进入受控恢复流程 |

实际规则必须由工具契约和风险策略共同决定。

即使一个工具声明为幂等，也需要确认幂等键的作用范围、保存期限以及供应商是否真正支持该语义，不能仅凭配置中的一个布尔值就认为重复执行绝对安全。

# 五、专业技术能力：为什么不能只依赖通用大模型？

你之前特别提到，编程可能需要 AST 语法树和专门的优化技术，其他场景也会有类似需求。

这正是能力系统需要解决的问题。

通用大模型负责理解、推理和策略选择，但在很多场景中，可靠性来自专业算法、确定性工具和领域验证，而不只是更好的提示词。

我建议把专业能力拆成三类。

## 5.1 第一类：确定性技术能力

适合有明确输入、明确规则、可验证输出的问题。


    <AsyncImage query="abstract syntax tree programming language code visualization" aspectRatio="4:3" maxWidth="112px"/>

      **编程：AST 与静态分析**
      解析语法树、符号引用、类型检查、代码差异分析、编译和测试。模型负责提出修改方案，确定性工具负责检查结构与行为。




    <AsyncImage query="FFmpeg video editing timeline waveform audio tracks" aspectRatio="4:3" maxWidth="112px"/>

      **AI 漫剧：媒体处理**
      FFmpeg 合成、时长检查、分辨率检查、音画同步、帧率与音频格式校验。




    <AsyncImage query="Android accessibility UI hierarchy tree mobile app interface inspection" aspectRatio="4:3" maxWidth="112px"/>

      **手机操作：界面状态验证**
      无障碍节点读取、应用包名核验、页面状态检测、操作前后状态比对。



这类能力的优势是结果通常更容易验证。但确定性工具也可能存在实现缺陷、环境依赖问题和版本兼容问题，因此仍然需要测试与运行时校验。

## 5.2 第二类：模型辅助的专业能力

例如：

- 复杂代码架构理解；
- 视频分镜设计；
- 角色外观一致性判断；
- 复杂网页结构理解；
- 语音对话意图识别。

这类能力需要模型进行语义判断，但应当尽可能用确定性工具、领域规则或独立评测约束结果。

例如，角色一致性不能只靠模型说“角色看起来一致”。可以结合角色参考图、视觉相似度、关键特征检查和人工抽样验收。

## 5.3 第三类：复合型能力

很多真正有价值的能力都属于这一类。

例如，可靠的代码重构能力可能由以下部分组成：

1. 模型理解修改目标；
2. AST 工具分析代码结构；
3. Planner 生成修改计划；
4. 受控补丁工具实施修改；
5. 编译器检查语法和类型；
6. 测试运行器验证行为；
7. 验收器检查目标和回归结果。

这才是一项完整的专业能力，而不是一个单独的工具或提示词。

## 5.4 AST 代码重构的完整执行示例

    ["执行受控修改","通过补丁工具修改目标代码，保留原始差异。"],

这里不应该强制每一次代码修改都使用 AST。例如，修改一个简单的文档字符串，可能不需要复杂的语法树重构流程。

专业能力应该根据任务风险、代码结构、修改范围和验收要求决定使用哪些技术，而不是为了体现专业性而增加不必要的步骤。

# 六、工具故障归因：智能体怎样知道究竟是谁出了问题？

这是本专项最核心的设计。

我们不能只使用一个 `failure_reason` 字段，让模型自行填写“工具失败”或“提示词不够好”。

建议建立独立的故障诊断器（Failure Diagnosis Engine），并明确区分**观察事实、根因假设、验证实验和最终结论**。

## 6.1 故障分类树


    **任务或节点未达到预期结果**



    <grid-item>

        **理解与决策**
        意图识别、规划、推理、上下文、提示词

    </grid-item>
    <grid-item>

        **执行与环境**
        工具、参数、依赖、网络、权限、资源

    </grid-item>


    **结果与验收**
    目标不清、验收标准错误、证据不足、验证器缺陷


    **系统与协同**
    状态不一致、重复执行、版本不兼容、同步失败、预算耗尽


一个故障可能有多个原因。例如，模型生成了错误参数，而工具又没有正确校验参数，这可能同时包含调用策略缺陷和工具契约缺陷。

因此，诊断器不应强行选择唯一根因，而应支持：

- 主要根因；
- 次要促成因素；
- 尚未排除的假设；
- 已经排除的假设；
- 支持与反对每个假设的证据；
- 根因结论的验证状态。

## 6.2 一个具体案例

假设编程专家尝试修改代码，但最终测试失败。

诊断器不应该直接增加一句“修改代码后一定要仔细检查”。

而应该按证据逐步判断：

| 检查点 | 观察结果 | 可能结论 |
|---|---|---|
| 用户目标解析 | 兼容性约束已正确提取 | 初步排除目标遗漏 |
| 上下文快照 | 兼容性约束实际进入模型请求 | 初步排除上下文遗漏 |
| 工具参数校验 | 参数符合工具 Schema | 排除明显的参数格式错误 |
| AST 分析结果 | 目标符号引用关系解析错误 | 怀疑专业能力缺陷 |
| 测试环境 | 依赖版本与基线一致 | 降低环境不一致的可能性 |
| 修复工具问题后重测 | 相同案例恢复通过 | 支持工具缺陷假设 |

这里的关键是“初步排除”和“支持假设”，而不是仅凭一条日志就断言根因已经确定。

## 6.3 根因诊断必须有自己的评测集

诊断器本身也可能判断错误。

因此，应该建立包含已知故障的诊断测试集，例如：

- 工具返回错误但实际操作成功；
- 工具没有执行成功却返回成功；
- 模型参数错误；
- 上下文遗漏约束；
- 测试环境异常；
- 工作流依赖关系错误；
- 日志缺失或时间顺序不完整。

对于这些测试案例，系统应检查诊断准确率、误归因率、证据覆盖率和错误修复成本。

特别要关注**错误归因导致的二次损害**：如果工具存在缺陷，系统却不断修改提示词，最终可能让提示词越来越复杂、成本越来越高，工具缺陷仍然存在。

# 七、工具可靠性工程：如何证明一个工具可以被使用？

工具注册完成，不等于工具已经可靠。

我建议每个工具根据风险等级建立独立的质量契约，至少包含五类测试。

## 7.1 五层测试体系

| 测试层 | 验证内容 | 示例 |
|---|---|---|
| 契约测试 | 输入输出与 Schema 是否一致 | 缺少必填参数时是否明确拒绝 |
| 单元测试 | 工具内部逻辑是否正确 | AST 节点转换是否保持语义 |
| 集成测试 | 工具与环境、依赖和服务是否兼容 | FFmpeg 是否能读取目标编码格式 |
| 故障注入 | 异常条件下能否安全处理 | 网络超时、磁盘满、进程中断 |
| 端到端测试 | 工具在真实任务链路中是否达成目标 | 修改代码后测试通过且无意外差异 |

高风险工具还需要额外的权限测试、并发测试、重复调用测试和安全边界测试。

## 7.2 工具必须有独立的验收契约

例如，文件修改工具的契约不能只是“成功写入文件”。

它可以规定：

- 目标路径必须位于授权工作区；
- 修改前必须保存原始版本或具备恢复方式；
- 返回值必须包含实际修改文件清单；
- 必须能核对修改前后的差异；
- 未经授权不得修改其他文件；
- 发生部分写入时必须返回明确状态；
- 发生不确定结果时必须支持核查。

这样，工具质量不再依赖模型是否在提示词里记住了所有注意事项。

## 7.3 工具故障要区分两个指标

这是一个重要的评测设计。

**工具自身可靠性**衡量：在合法输入、满足前置条件的情况下，工具是否按契约工作。

**工具使用可靠性**衡量：整个智能体是否能够选择合适的工具、生成正确参数、理解返回结果，并在必要时完成恢复。

两者不能混为一个成功率。

例如，某个工具在合法输入下成功率达到 99.9%，但模型经常给它传入错误参数，那么整体任务成功率仍然可能很低。此时主要问题可能在调用策略或参数生成，而不是工具内部实现。

反过来，模型参数完全正确，但工具经常超时或返回错误，问题就应该优先交给工具可靠性工程处理。

# 八、工作流治理：从一次跑通到可重复执行的能力

你之前特别关心：一个复杂任务跑通之后，怎样把它固化成稳定的工作流，以后还可以持续迭代。

这次我们把它与能力系统正式连接起来。

建议工作流不是一段由模型生成后直接执行的任意代码，而是一个具有版本、节点契约、依赖、恢复策略和验收条件的正式资产。

## 8.1 工作流节点必须定义什么？

每个节点至少需要：

- 输入输出契约；
- 前置条件；
- 使用的能力与工具版本；
- 成功与失败判定；
- 超时与重试策略；
- 副作用与幂等语义；
- 验收要求；
- 检查点与恢复策略；
- 预算限制；
- 允许的重规划范围。

例如，AI 漫剧工作流中的“生成视频”节点，不应只规定“调用视频生成 API”。

它还应规定：

1. 输入分镜和角色素材必须已通过验证；
2. 生成请求必须关联稳定的幂等键或远端任务 ID；
3. 超时后优先查询原任务；
4. 生成结果必须检查实际文件和媒体元数据；
5. 失败时只允许在预算和次数限制内重试；
6. 生成成功后将产物写入不可变的资产版本；
7. 下游合成节点只能使用通过验收的产物。

## 8.2 工作流如何从成功任务中产生？

我建议采用以下晋升流程：

  {#each [
    ["运行时轨迹","记录实际执行过的节点、输入输出、失败和恢复。"],
    ["候选流程提取","识别可重复的步骤、依赖关系和条件分支。"],
    ["人工或自动整理","移除临时操作，明确节点契约、输入输出和恢复逻辑。"],
    ["回放测试","使用保存的输入和可复现环境重放关键路径。"],
    ["边界测试","验证失败、异常输入、权限限制和部分成功情况。"],
    ["成本与质量评测","检查成功率、延迟、成本和产物质量。"],
    ["发布为工作流版本","通过门禁后，进入可复用能力目录。"]
  ] as item}





        **{item[0]}**
        {item[1]}


  {/each}

必须注意：一次成功运行只能产生候选工作流，不能自动证明它已经适合复用。可能只是某次输入恰好简单、环境恰好正常，或者用户在执行过程中手动修正了多个关键步骤。

工作流需要通过回放、边界和恢复测试，才能成为稳定资产。

## 8.3 固化不等于永久固定

即使工作流已经稳定，也不意味着永远不能改变。

建议区分：

- **稳定工作流**：具有明确契约、通过测试并可重复执行；
- **实验分支**：尝试替换节点、优化依赖或调整执行策略；
- **运行时动态决策**：在预先允许的范围内选择分支或能力实现；
- **正式升级**：通过评测后发布新版本。

例如，漫剧工作流可以保持整体 DAG 稳定，同时允许“视频生成”节点在两个兼容服务之间选择。但切换服务不能破坏输入输出契约，也不能绕过质量、成本和权限检查。

# 九、工具、能力与工作流怎样独立进化？

这是 EvoAgent 与普通自动化平台的根本区别之一。

普通工作流平台通常依赖开发者人工修复故障；EvoAgent 则希望能够从运行证据中发现问题，提出改进方案，验证改进效果，并在通过门禁后自动发布低风险变更。

但必须强调：**进化系统应当根据根因选择改进对象，而不是遇到失败就自动修改工具或工作流。**

## 9.1 建立统一的候选改进协议

一项改进可以针对不同组件：

- 工具实现；
- 工具参数契约；
- 专业技术能力；
- 工作流节点或依赖；
- 专家策略；
- 提示词；
- 模型适配器；
- 诊断器自身。

每个候选都需要记录：

  "target_id": "python.ast_refactor",

## 9.2 不同组件需要不同的进化方式

| 改进对象 | 典型方式 | 主要门禁 |
|---|---|---|
| 提示词 | 候选生成、对照评测 | 任务质量、成本、跨专家回归 |
| 工具参数契约 | Schema 修改、契约测试 | 调用方兼容性、错误处理 |
| 工具实现 | 代码修改、构建、测试 | 单元测试、安全测试、集成测试 |
| 专业能力 | 替换算法或组合方式 | 领域专项评测、边界条件 |
| 工作流 | 调整 DAG、节点策略 | 回放、恢复、幂等和端到端验收 |
| 模型适配器 | 调整请求和响应映射 | 协议兼容、工具调用和错误映射 |
| 诊断器 | 改进根因分类或证据规则 | 已知故障集、误归因率 |

工具实现和原生执行器的代码变更风险通常高于提示词模板调整。因此，不能给它们使用完全相同的自动发布权限。

## 9.3 共享能力改进如何避免污染所有专家？

假设编程专家发现一个通用工具参数验证器的缺陷。

修复候选可以被提交到共享能力仓库，但需要：

1. 在原始失败案例上验证修复；
2. 在该工具的完整契约测试集上验证；
3. 检查其他调用方是否兼容；
4. 在关键专家的回归集上运行测试；
5. 评估成本、延迟和资源变化；
6. 发布独立的能力版本；
7. 由各专家的兼容性策略决定何时升级。

这比直接修改所有专家提示词安全得多。

同样，某个专家的失败经验不能自动变成全局规则。共享的是经过验证、明确适用范围的能力和改进，不是未经筛选的结论。

# 十、Android 本地执行与云端工具如何统一？

EvoAgent 采用手机优先战略，因此工具系统必须从一开始就支持本地和云端两种执行环境，而不是先假设所有工具都运行在服务器上。

建议定义统一的能力契约，再通过不同执行器实现。


    **统一能力注册中心**
    能力 ID、输入输出契约、权限、版本与验收规则



    **能力调度器**
    依据任务需求、网络、隐私、成本和设备资源选择实现


    <grid-item>


        **Android 执行器**
        应用启动、无障碍操作、本地文件、离线能力、媒体合成。

        权限由 Android 系统和本地策略共同约束。

    </grid-item>
    <grid-item>


        **云端执行器**
        大模型 API、云端生成、复杂计算、远端任务与共享评测。

        通过服务端身份、授权、预算和审计机制约束。

    </grid-item>


    **统一结果协议**
    执行状态、证据、成本、副作用、错误与恢复建议


## 10.1 调度不能只考虑谁更快或更便宜

例如，处理私人文件时，即使云端 OCR 更快，也不一定应该把文件上传到云端。

调度器至少应考虑：

- 当前任务是否允许联网；
- 数据是否允许离开设备；
- 本地能力是否足够；
- 云端能力是否可用；
- 质量差异是否影响验收；
- 延迟和费用是否符合预算；
- 本地设备资源是否充足；
- 当前任务能否在断网时继续；
- 选择的实现是否兼容当前工作流版本。

当网络中断时，如果某项任务只能由云端执行，系统应等待、暂停或采用经过批准的替代能力，而不是静默降低质量并宣称任务完成。

## 10.2 工具升级不能要求所有手机同时升级

能力契约应当尽可能向后兼容。

例如，某个工具从 V2 升级到 V3：

- 如果输入输出兼容，旧工作流可以继续使用 V2，也可以在验证后升级到 V3；
- 如果返回状态的语义发生变化，必须增加版本兼容处理；
- 如果旧任务正在运行，应继续使用其锁定的兼容版本，或者经过明确的迁移流程；
- 如果新版本修复了安全漏洞，系统应根据风险策略决定是否禁止旧版本继续运行。

Android 设备可能长时间离线，因此需要支持版本清单缓存、兼容性检查、增量下载、签名校验和安全回滚。对于无法安全回滚的数据库迁移或权限变更，则需要采用专门的迁移与恢复方案。

# 十一、工具与能力系统的质量指标

为了让它真正进入自进化闭环，必须建立独立的质量评价体系。

| 指标 | 含义 |
|---|---|
| 契约符合率 | 工具是否遵守输入输出和状态语义 |
| 工具执行成功率 | 满足前置条件的调用中，有多少按契约完成 |
| 调用选择准确率 | 智能体是否选用了适当的能力 |
| 参数有效率 | 调用请求是否满足参数契约 |
| 结果核验通过率 | 返回结果是否获得必要证据支持 |
| 故障归因准确率 | 诊断器是否找到真正的问题来源 |
| 重复副作用率 | 恢复和重试是否造成重复操作 |
| 恢复成功率 | 发生故障后是否能够安全继续 |
| 端到端任务成功率 | 能力在真实任务中是否达成用户目标 |
| 单次成功任务成本 | 完成一个验收通过的任务实际消耗多少资源 |

其中，工具成功率不能代替端到端任务成功率。

例如，工具调用成功率很高，但如果专家经常选错工具，整个智能体仍然表现不佳。反过来，某个专业能力即使需要更多步骤，只要能够显著提高关键任务的正确率并满足成本约束，也可能更值得采用。

## 11.1 建立能力等级，但不要只用一个总分

建议将能力的质量状态分成：

- `EXPERIMENTAL`：实验性，尚未证明稳定；
- `VALIDATED`：通过契约和专项测试；
- `STABLE`：通过目标场景的质量、稳定性与恢复门禁；
- `DEPRECATED`：不再建议新任务使用；
- `QUARANTINED`：出现重大异常，暂时禁止正常调度；
- `RETIRED`：停止使用，但保留必要的历史引用。

一个能力可以在 Python 代码分析方面是 `STABLE`，但在某种特殊语法或旧运行环境中仍不适用。因此，状态还应关联适用范围、版本和环境条件，不能把单一的全局质量标签理解为无条件可靠。

# 十三、接下来还需要设计哪些关键系统？

到这里，我们已经把以下内容连接起来：

- 用户习惯与个性化；
- 长期记忆和工作记忆；
- 上下文组装、压缩与恢复；
- 提示词和指令治理；
- 工具、专业技术能力与工作流；
- 运行日志、故障诊断、自动评测和进化。

但还有一个不能遗漏的关键问题：**如何保证路由器、Planner、ReAct、工具、验收器和诊断器协同工作，而不是各自优化却让整体系统退化？**

我建议下一轮深入设计 EvoAgent 的**路由、规划、执行与验收协同控制系统**。

重点包括：

1. 用户意图如何映射到通用能力和领域专家；
2. 如何判断应该使用单个专家、多个专家还是固定工作流；
3. 路由错误与专家执行错误如何区分；
4. Planner 如何决定采用固定 DAG、动态 DAG 或短程 ReAct；
5. 执行过程中何时继续、重试、暂停或重规划；
6. 验收器如何独立判断结果是否真正完成；
7. 多专家协作时如何传递任务状态、记忆和证据；
8. 当多个组件都提出改进时，如何判断先优化哪个问题；
9. 如何防止局部优化损害整体成功率、稳定性和成本；
10. 如何通过统一的运行轨迹、对照评测和发布门禁实现系统级进化。

这将把前面各个子系统进一步连接成一个真正完整的运行架构。
