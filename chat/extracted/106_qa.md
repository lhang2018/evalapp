# EvoAgent 第五十四专项：可靠性工程、故障注入与恢复保证

<text color="secondary" size="sm">RERA · Reliability Engineering & Recovery Assurance</text>

前面已经完成了几个重要的基础设计：

- MEODT：多专家协作与动态组队；
- GECO：全局事件、运行追踪与因果证据；
- TSEG：安全边界、信任体系与自进化治理。

现在要解决的是一个更贴近实际运行的问题：

**当 EvoAgent 长时间运行、执行复杂任务、调用外部工具，甚至在任务中途遭遇断电、崩溃或断网时，怎样保证它不会丢失关键进度、重复执行危险操作，或者在恢复过程中制造新的故障？**

这里有一个重要区别。

普通应用的可靠性，主要关注程序是否崩溃、数据是否丢失、服务是否可用。

EvoAgent 的可靠性还必须考虑智能体自身的行为：它可能错误地判断任务已经完成，可能无限重试，可能恢复一个已经失效的计划，也可能在上游结果变化后继续使用旧的下游产物。

因此，RERA 不应只是增加异常捕获、重试和日志，而应建立一套完整的**任务可靠性状态机、故障分类、恢复协议、故障注入测试和可靠性评测体系**。

## 一、第一性原理：失败不可避免，但失控可以被限制

设想一个真实的 AI 漫剧制作任务。

编剧、分镜、视觉生成已经完成，配音服务也已返回结果。此时 Linux 主机突然断电。

重新启动后，系统面临几个问题：

- 哪些工作已经真正完成？
- 哪些产物已经写入磁盘？
- 哪些产物虽然生成了，但尚未记录完成事件？
- 视频合成是否已经启动？
- 如果外部服务已经扣费，但本地没有收到响应，是否应该再次调用？
- 当前工作流使用的角色设定是否已经发生变化？
- 哪些任务可以直接恢复，哪些必须重新执行？
- 如果关键状态无法确认，应该继续、等待还是终止？

如果系统只保存一个“任务进度 70%”的数值，这些问题都无法可靠回答。

因此，RERA 的第一条原则是：

**恢复必须依据可验证的状态和产物，而不能仅依赖模型记忆、进度百分比或上一次的自然语言总结。**

### 1.1 将可靠性分为六个维度

这六个维度需要分别评测。

例如，一个任务最终成功了，不代表它的恢复机制可靠；它可能只是因为故障恰好没有影响最终产物。

同样，恢复成功也不代表没有发生重复扣费、数据泄露或未经授权的外部操作。

### 1.2 可靠性不能只看成功率

假设两个版本的编程专家都完成了 95% 的任务。

- 版本 A 在失败时能够准确报告问题，并从检查点恢复。
- 版本 B 在失败时会反复执行修改命令，偶尔覆盖用户文件，还可能误报任务完成。

它们的表面成功率相同，但工程可靠性显然不同。

因此，RERA 必须同时评价正常执行和异常路径，尤其要关注失败后的行为。

# 三、故障分类：不同故障必须采用不同处理策略

很多智能体系统把所有异常都当作“再试一次”。

这是不可靠的。

例如，模型服务暂时超时，可能适合有限重试；但如果一个付费 API 请求已经提交，响应却丢失，再次发送可能产生第二笔费用。

因此，建议建立统一的 `FailureTaxonomy`。

| 故障类型 | 典型场景 | 默认处理策略 |
|---|---|---|
| 暂时性故障 | 网络短暂中断、服务限流 | 有界重试、退避等待 |
| 永久性故障 | 配置错误、缺失依赖、权限不足 | 停止重试，修复配置或请求人工介入 |
| 结果未知 | 请求已发出但响应丢失 | 查询实际状态或执行对账，不盲目重试 |
| 数据与契约故障 | 输出格式错误、输入版本不匹配 | 校验、修复或重新生成 |
| 状态一致性故障 | 事件与实际产物不一致 | 暂停相关节点，进行状态对账 |
| 资源故障 | 内存不足、磁盘写满、CPU 过载 | 限流、释放资源、降级或暂停 |
| 依赖故障 | 上游产物变化、技能版本失效 | 重新评估受影响的下游节点 |
| 安全故障 | 越权、授权撤销、安全校验失败 | 阻断相关操作，执行安全响应 |
| 智能体决策故障 | 错误规划、循环、重复劳动 | 停止当前策略，诊断并有限重规划 |
| 质量故障 | 最终产物不满足验收要求 | 返工、局部重跑或终止交付 |

这里的“默认处理”是建议策略，不是所有场景的绝对规则。最终行为还需要结合任务风险、操作可逆性、授权范围和剩余预算决定。

## 3.1 区分三种最重要的执行结果

对任何可能产生副作用的操作，系统都应能够区分：

- `SUCCEEDED`：执行成功，并且结果已经得到必要的核验；
- `FAILED`：有证据表明操作失败，且实际影响已知；
- `UNKNOWN`：无法确定操作是否成功或产生了什么影响。

`UNKNOWN` 不是普通失败。

例如，调用外部视频生成服务时，连接在提交请求后断开。服务可能已经接受请求并开始生成视频，也可能根本没有收到请求。

此时不能直接认定失败并再次调用。

应该先尝试使用请求 ID、服务端任务 ID 或其他可用证据查询状态。如果服务不支持状态查询，则需要根据费用风险和操作策略决定等待、人工确认或在明确接受重复风险后重试。

**未知状态必须成为系统的一等状态，而不是被强行归类为失败。**

# 四、重试机制：防止智能体陷入无限循环

重试是必要能力，但无约束的重试会造成一系列问题：

- 模型调用费用持续增加；
- 同一个工具被反复调用；
- 多个专家同时重试同一个失败节点；
- 失败原因没有改变，结果却不断重复；
- 自动恢复与人工取消相互冲突；
- 上游失败引发整个 DAG 的重试风暴。

建议建立 `RetryController`，统一管理重试次数、等待策略、故障分类和任务级预算。

## 4.1 重试必须满足准入条件

每次重试前，至少检查：

1. 该故障是否属于允许重试的类型？
2. 前一次操作是否已经产生副作用？
3. 重试是否具有幂等保障？
4. 当前授权是否仍然有效？
5. 是否仍有足够的时间、资源和费用预算？
6. 前一次失败的原因是否可能已经改变？
7. 是否需要先执行状态核验或补偿操作？

如果关键条件不满足，系统应暂停或终止，而不是为了追求任务完成率继续尝试。

## 4.2 采用分层重试预算

建议同时设置四种限制：

| 预算层级 | 限制对象 | 防止的问题 |
|---|---|---|
| 操作级 | 单个工具调用 | 同一操作无限重试 |
| 节点级 | 单个 DAG 节点 | 某个子任务持续失败 |
| 任务级 | 整个任务 | 多个节点共同消耗过多资源 |
| 系统级 | 同时运行的所有任务 | 故障期间产生重试风暴 |

预算需要相互约束。

例如，某个工具还有一次重试额度，并不意味着任务已经达到费用上限后仍然允许重试。

## 4.3 使用退避与抖动

对于网络中断、限流等暂时性故障，可以使用指数退避。

\[
d_n=\min(d_{\max},d_0\cdot 2^n)
\]

其中 \(d_0\) 为初始等待时间，\(d_{\max}\) 为等待上限。

如果多个任务可能同时重试，还可以增加随机抖动，避免所有请求在同一时刻再次冲击故障服务。

但退避不是通用解决方案。

权限不足、输入契约错误、无效配置和安全阻断等故障，通常不应通过反复重试来解决。

## 4.4 重规划也必须受限制

智能体可能认为当前方案失败，于是重新规划；新方案再次失败，又重新规划。这样就会出现不断改变策略却始终无法完成任务的循环。

建议分别设置：

- 最大普通重试次数；
- 最大重规划次数；
- 最大连续无进展次数；
- 最大返工轮数；
- 最大总执行时间；
- 最大任务成本。

当同一问题连续出现、方案没有实质变化，或者连续多轮没有产生新的有效证据时，应触发熔断或转入诊断，而不是继续重复执行。

## 4.5 重试必须记录原因

每次重试都应在 GECO 中记录：

- 前一次失败事件；
- 当前故障分类；
- 重试理由；
- 采用的等待策略；
- 是否进行了状态核验；
- 使用的预算；
- 重试后的结果；
- 是否产生了新的副作用。

这样，SOCDEA 才能判断重试是否真的提高了成功概率，还是只增加了成本。

# 五、幂等性与副作用：恢复机制最容易出错的地方

这是 RERA 最值得优先实现的部分。

假设一个工具调用已经成功修改文件，但进程在记录成功事件前崩溃。系统重启后发现没有成功记录，于是再次执行同一个修改。

如果工具操作是简单覆盖，也许结果没有变化；如果它是追加内容、提交代码、发送消息或创建付费任务，就可能造成重复副作用。

## 5.1 建立操作级幂等协议

建议为每个重要操作生成唯一的 `operation_id`。

执行器至少应维护：

- 操作标识；
- 请求内容摘要；
- 目标资源；
- 当前执行状态；
- 已知的副作用；
- 结果引用；
- 是否允许安全重试；
- 实际核验结果。

当相同操作被重复请求时，执行器应先查询已有状态，而不是默认再次执行。

对于支持幂等键的外部 API，应使用稳定的操作标识；对于不支持幂等的服务，则必须设计状态查询、人工确认或明确接受重复风险的策略。

**不能仅依赖客户端生成一个 ID，就宣称外部操作已经实现幂等。** 真正的幂等保障还取决于执行器和目标系统如何处理重复请求。

## 5.2 区分四种操作阶段

建议使用以下状态：

<box border radius="xl" padding={3} gap={2}>
  {#each [
    ["PREPARED","操作已准备，尚无执行成功证据。"],
    ["IN_FLIGHT","操作已提交或正在执行，最终结果尚未确认。"],
    ["EFFECT_VERIFIED","实际效果已通过执行器回执或状态核验得到确认。"],
    ["FAILED_OR_UNKNOWN","操作失败，或结果仍然未知；需要依据证据继续处理。"]
  ] as item}
    <box gap={1}>
      <title size="md">{item[0]}</title>
      <text color="secondary" size="sm">{item[1]}</text>
    </box>
    {#if item[0]!=="FAILED_OR_UNKNOWN"}
      <divider color="subtle"/>
    {/if}
  {/each}
</box>

这里的 `FAILED_OR_UNKNOWN` 在正式实现时建议拆分为两个独立状态，避免混淆。上面的分组只是展示概念。

操作成功的判定标准应根据工具类型决定。例如：

- 文件修改：核验目标文件内容或版本；
- 代码提交：核验提交标识与远端状态；
- 付费 API：核验请求 ID、任务状态或服务端账单记录；
- 外部消息：核验服务端接受状态，不能把“请求发送成功”直接等同于“对方已经收到”。

## 5.3 对不可逆操作采用更严格策略

以下操作尤其需要谨慎：

- 发送外部消息；
- 创建付费生成任务；
- 提交或发布代码；
- 修改外部系统状态；
- 删除文件或数据；
- 执行金融或其他高影响操作。

如果系统无法确认第一次操作是否成功，就不应自动再次执行不可逆操作。

优先查询真实状态；无法查询时，暂停相关步骤并向用户说明不确定性。

## 5.4 补偿操作不等于真正回滚

有些操作无法完全撤销。

例如，已经发送的消息无法保证被对方撤回；已经发生的 API 费用可能无法退还；已经发布的代码可能已经被其他系统拉取。

因此，RERA 需要区分：

- **回滚：** 将系统状态恢复到先前版本；
- **补偿：** 通过另一项操作降低先前操作造成的影响；
- **停止：** 阻止后续副作用继续发生；
- **对账：** 查明当前真实状态。

系统不应承诺所有副作用都能够回滚。

# 六、检查点与恢复：从“保存进度”升级为“保存可恢复状态”

检查点不是简单地保存任务百分比，也不应该只是保存模型的对话摘要。

建议建立 `RecoveryCheckpoint`，保存足以判断任务能否继续执行的关键状态。

## 6.1 检查点至少需要保存什么？

| 数据类别 | 必要内容 |
|---|---|
| 任务状态 | 任务 ID、当前状态、生命周期版本 |
| 计划状态 | DAG 版本、节点状态、依赖关系 |
| 产物状态 | 产物 ID、版本、校验摘要、存储引用 |
| 执行状态 | 正在运行的操作、已确认结果、未知结果 |
| 授权状态 | 授权引用、有效期、相关撤销状态 |
| 团队状态 | 成员、职责、未完成工作包与交接情况 |
| 资源状态 | 已消耗预算、剩余额度、截止条件 |
| 版本状态 | 专家、技能、工具、模型适配器与配置版本 |
| 恢复信息 | 最近一次有效检查点、待对账操作和已知故障 |

完整日志、视频文件和大型产物不需要全部复制进检查点，可以通过版本化引用访问。

但这些引用必须仍然有效，并且相关产物必须能够被找到和验证。

## 6.2 检查点必须有明确的一致性边界

例如，某个 DAG 节点同时修改了三个文件，并更新了数据库中的任务状态。

如果检查点只记录了两个文件的更新，就可能产生一个无法继续执行的中间状态。

因此，建议优先在明确的安全边界创建检查点，例如：

- 一个节点完成并且产物已验证；
- 一组相关文件完成原子提交；
- 外部操作状态已经核验；
- 一次计划变更已经提交；
- 一次团队交接已经完成。

对于无法原子提交的跨资源操作，应记录操作阶段，并在恢复时执行对账或补偿。

## 6.3 恢复前先执行一致性检查

恢复流程建议采用以下顺序：

<box border radius="xl" padding={3} gap={2}>
  {#each [
    ["1. 加载最近的有效检查点","验证检查点版本、完整性和引用是否存在。"],
    ["2. 读取检查点之后的事件","重建期间发生的状态变更与已知操作结果。"],
    ["3. 对账真实执行状态","检查文件、进程、外部服务任务和未确认操作。"],
    ["4. 验证依赖与授权","检查产物版本、计划依赖、技能兼容性和当前有效权限。"],
    ["5. 计算恢复边界","决定哪些节点可以继续，哪些需要重跑、隔离或人工确认。"],
    ["6. 恢复执行","仅启动已满足条件的节点，并继续记录操作结果。"],
    ["7. 验收恢复后的结果","根据受影响范围执行回归验证和最终质量验收。"]
  ] as item}
    <box gap={1}>
      <title size="md">{item[0]}</title>
      <text color="secondary" size="sm">{item[1]}</text>
    </box>
    {#if item[0]!=="7. 验收恢复后的结果"}
      <divider color="subtle"/>
    {/if}
  {/each}
</box>

恢复过程中，如果发现状态无法确认，系统应保留未知状态并暂停相关操作。

不能为了让任务继续而擅自假定某个操作成功或失败。

## 6.4 检查点恢复必须考虑版本兼容性

假设一个任务暂停了一周，期间某个技能已经升级，原来的 DAG 也发生了变化。

系统不能不加检查地使用最新技能继续执行旧计划。

建议在恢复时检查：

- 原技能版本是否仍然可用；
- 是否存在已知安全缺陷；
- 旧计划是否兼容当前工作流版本；
- 原产物是否仍然满足下游契约；
- 是否需要使用原版本、迁移状态或重新规划。

对于无法安全迁移的任务，可以继续使用受保护的兼容版本，也可以暂停并请求用户决策。

# 七、DAG 恢复：不是从失败节点简单地重新开始

对于复杂工作流，恢复机制必须理解任务之间的依赖关系。

例如，AI 漫剧工作流包含：

`故事脚本 → 分镜 → 角色素材 → 视频片段 → 配音与合成 → 最终验收`

如果最终视频合成失败，而所有上游产物都经过验证，系统可以只重新执行合成节点。

但如果故事脚本发生变化，依赖它的分镜、部分角色素材、视频片段和最终合成结果可能都需要重新生成或验证。

因此，RERA 必须与 DAG 编排器建立 `Dependency Invalidation` 机制。

## 7.1 区分三种下游节点

| 类型 | 处理原则 |
|---|---|
| 完全不受影响 | 输入、契约与依赖均未变化，可以保留已验证结果 |
| 需要重新验证 | 输入变化可能影响结果，但尚不能确定是否必须重跑 |
| 必须重新执行 | 关键输入已改变，原结果不再满足有效性条件 |

不能简单地将所有下游节点全部重跑，也不能因为某个节点过去执行成功就永久信任其结果。

## 7.2 使用产物血缘判断影响范围

GECO 应记录产物与输入、工具、技能版本之间的关联。

当某个输入发生变化时，RERA 根据血缘关系找到受影响节点，再结合契约与变化类型判断是否需要重新执行。

例如，配音文件重新生成，通常不需要重新编写故事脚本；但如果角色台词发生变化，就可能需要重新配音、重新合成，并重新验证字幕和时长。

## 7.3 恢复必须考虑计划变更

如果 SOCDEA 诊断发现原 DAG 的分解方式本身存在缺陷，恢复过程可能需要重新规划。

但新的计划必须：

- 保留原始目标和有效约束；
- 明确变更原因；
- 记录新旧计划版本；
- 检查受影响的产物和节点；
- 重新检查授权与预算；
- 通过必要的治理检查。

计划变更不能覆盖历史记录，否则系统将无法解释原计划为什么失败，也无法准确评价 Planner 的表现。

# 八、降级运行：资源不足时，不一定要完全停止

个人电脑和微型 Linux 主机的计算资源有限。系统可能同时运行本地模型、工具执行、数据库和后台进化任务。

如果资源不足，EvoAgent 不应只有“继续运行”或“整个系统崩溃”两种状态。

建议建立 `DegradedOperationPolicy`。

## 8.1 设计四种运行模式

<box border radius="xl" padding={3} gap={3}>
  {#each [
    ["NORMAL · 正常运行","允许在资源预算内执行任务、并行工作流和后台评测。"],
    ["CONSTRAINED · 受限运行","降低并发、暂停非必要后台任务、限制模型调用并优先保障前台任务。"],
    ["RECOVERY · 恢复模式","停止非必要新任务，优先处理未确认操作、关键状态对账和检查点恢复。"],
    ["SAFE_STOP · 安全停止","停止可能产生新副作用的操作，保存可保存的状态，并等待资源恢复或人工介入。"]
  ] as item}
    <box gap={1}>
      <title size="md">{item[0]}</title>
      <text color="secondary" size="sm">{item[1]}</text>
    </box>
    {#if item[0]!=="SAFE_STOP · 安全停止"}
      <divider color="subtle"/>
    {/if}
  {/each}
</box>

系统可以根据磁盘剩余空间、内存压力、执行失败率、任务积压和关键组件健康状态切换模式。

具体阈值需要通过目标设备的实际测试确定，不能仅凭一组固定数字适用于所有电脑。

## 8.2 建立任务优先级

建议优先保障：

1. 安全控制、授权撤销和必要的执行停止；
2. 正在进行的关键状态持久化与故障对账；
3. 用户当前明确要求的前台任务；
4. 已开始且可安全完成的工作流；
5. 普通后台任务；
6. 进化实验、批量评测和非紧急优化。

例如，当内存不足时，可以先暂停后台技能评测，而不是让任务恢复机制和安全控制也因资源竞争而失效。

## 8.3 磁盘写满必须有专门策略

磁盘写满会同时影响事件记录、检查点、产物生成和状态恢复。

因此，建议预留关键状态存储空间，并对大型调试日志和临时产物设置独立配额。

系统不能在磁盘写满后继续宣称所有操作都具备完整的审计和恢复保障。

如果无法持久化关键状态，应根据操作风险暂停可能产生副作用的工作，释放可清理空间后再恢复。

## 8.4 降级不等于绕过质量要求

资源不足时，可以选择：

- 减少并行度；
- 暂停非关键专家；
- 使用经过验证的低成本模型或能力；
- 缩小允许处理的批次；
- 将任务暂停，等待设备资源恢复。

但不能因为资源不足就降低必要的安全门槛，或者把未经验证的结果直接当成合格产物。

# 九、故障注入：主动制造故障，才能验证恢复能力

仅靠正常运行测试，很难证明系统真的具备可靠恢复能力。

很多缺陷只会在特定时机出现，例如：

- 工具操作已经成功，但成功事件尚未写入；
- 产物已经保存，但任务状态尚未提交；
- 用户撤销授权时，设备正好断网；
- 两个专家同时提交产物；
- 检查点创建过程中进程崩溃；
- 任务恢复时，旧技能版本已经被禁用。

因此，建议建立 `Fault Injection Framework`，在可控环境中主动注入故障。

## 9.1 第一版必须测试的故障场景

| 故障注入 | 需要验证的结果 |
|---|---|
| 工具执行前崩溃 | 操作没有被误判为已经成功 |
| 工具执行后、记录前崩溃 | 系统能够通过对账识别实际效果 |
| 重复发送同一操作请求 | 幂等机制能够阻止不必要的重复副作用 |
| 模型服务超时 | 任务按策略重试、暂停或切换，不进入无限循环 |
| 磁盘写满 | 关键状态受到保护，危险操作能够安全停止 |
| 网络中断 | 本地事件可以保存，恢复后能够同步和对账 |
| 检查点损坏 | 系统拒绝不可信检查点，尝试其他有效恢复路径 |
| 上游产物版本变化 | 下游节点被正确保留、重新验证或重跑 |
| 授权撤销 | 相关执行被阻止，未知状态被明确标记 |
| 多专家并发修改 | 冲突被发现，不发生静默覆盖 |
| 进化候选引入回归 | 版本不能绕过质量和安全发布门槛 |
| 恢复过程再次崩溃 | 可以从最新有效检查点重新恢复，不无限重复副作用 |

## 9.2 故障注入必须在隔离环境进行

不能为了测试恢复机制而在真实用户项目中随意删除文件、断开关键存储或重复调用付费 API。

建议使用模拟工具、测试文件、虚拟外部服务和独立任务数据库构建故障注入环境。

对于确实需要验证真实系统行为的测试，应明确操作范围、测试数据和回滚方法。

## 9.3 测试应覆盖不同故障发生时机

同一种故障在不同阶段发生，可能导致完全不同的结果。

例如，工具调用过程中的崩溃至少可以分为：

1. 调用尚未发出；
2. 调用已发出但未被确认；
3. 远端已经执行；
4. 返回结果已经收到；
5. 结果尚未持久化；
6. 结果已经持久化但任务状态尚未更新。

因此，故障注入应覆盖关键状态转换之间的中断点，而不是只测试“进程崩溃一次”。

# 十、可靠性指标：如何判断系统真正变得更可靠？

RERA 需要把可靠性变成可测量、可比较的工程目标。

建议建立 `ReliabilityMetricCatalog`，与 GECO 的事件和指标体系统一。

## 10.1 核心指标

| 指标 | 含义 |
|---|---|
| 任务成功率 | 满足最终验收契约的任务占比 |
| 首次执行成功率 | 不依赖重试与恢复即完成的任务占比 |
| 恢复成功率 | 发生符合统计口径的故障后，最终成功恢复的任务占比 |
| 状态对账成功率 | 恢复时能够核实实际状态并解决不一致的操作占比 |
| 重复副作用率 | 非预期重复产生外部影响的操作占比 |
| 检查点恢复耗时 | 从开始恢复到达到可安全继续状态的耗时 |
| 平均恢复时间 | 在明确的故障统计口径下，从故障发生到恢复的平均时间 |
| 任务超时率 | 超过规定时间预算的任务占比 |
| 资源故障率 | 因内存、磁盘、CPU 或其他资源限制而中断的任务占比 |
| 故障重试收益 | 重试后新增成功数、额外成本与无效重试数量 |
| 恢复后回归率 | 恢复后重新验收发现缺陷的任务占比 |
| 关键事件缺失率 | 关键运行事件未被可靠记录的比例 |

这里需要特别注意指标的统计口径。

例如，恢复成功率不能只统计“成功恢复的任务”，还必须明确哪些故障进入分母、哪些任务被取消，以及哪些任务因证据不足而无法判定。

## 10.2 为不同任务定义可靠性目标

并不是所有任务都需要相同的可靠性要求。

- 普通聊天任务可以优先保证响应及时与上下文连续；
- 代码修改任务需要重点保证文件安全、测试证据与恢复正确性；
- AI 漫剧任务需要重点保证大型产物不丢失、生成费用可追踪和阶段性恢复；
- 外部系统操作需要重点保证授权、幂等和副作用核验；
- 自进化任务则必须重点保证版本可追溯、安全回归和可靠回滚。

因此，建议按任务类型定义可靠性配置，而不是为所有任务硬编码一套相同策略。

## 10.3 不要通过降低标准制造更高成功率

如果某个版本把原本需要通过的测试删除，任务成功率可能上升，但系统并没有变得更可靠。

因此，RERA 的可靠性指标必须与 UQEAG 的固定验收契约、TSEG 的安全门槛以及 GECO 的真实事件证据关联。

任何影响成功率定义、恢复判定和测试标准的变更，都需要独立记录与审核。

# 十一、可靠性与自进化：把恢复能力本身纳入进化闭环

RERA 不只是给系统增加恢复机制，它还应该让 EvoAgent 能够逐步发现恢复机制自身的问题。

例如，系统发现：

- 某类任务的重试经常无效；
- 某个工具适配器无法区分超时和真正失败；
- 某种检查点无法恢复并行任务；
- 某个技能版本经常造成下游节点失效；
- 某个工作流恢复时会重复生成付费视频。

这些问题都可以成为可靠性改进候选。

建议建立以下闭环：

<box border radius="xl" padding={3} gap={2}>
  {#each [
    ["1. GECO 记录实际故障","收集执行事件、状态差异、产物版本与资源消耗。"],
    ["2. SOCDEA 形成根因假设","区分执行缺陷、计划缺陷、恢复缺陷和环境问题。"],
    ["3. RERA 生成修复候选","修改重试策略、恢复状态机、检查点协议或依赖失效规则。"],
    ["4. 隔离环境进行故障注入","使用相同故障场景验证候选方案。"],
    ["5. UQEAG 与安全评测验收","验证功能、数据一致性、授权边界和副作用控制。"],
    ["6. SELCIA 受控发布","进行版本比较、灰度或受限部署，必要时回滚。"],
    ["7. GECO 持续观测","验证真实运行中是否改善，是否出现新的失败模式。"]
  ] as item}
    <box gap={1}>
      <title size="md">{item[0]}</title>
      <text color="secondary" size="sm">{item[1]}</text>
    </box>
    {#if item[0]!=="7. GECO 持续观测"}
      <divider color="subtle"/>
    {/if}
  {/each}
</box>

关键要求是：**发现故障的机制、修复故障的机制，以及证明修复有效的机制，不能完全依赖同一个未经独立验证的判断。**

例如，SOCDEA 认为某个重试策略有问题，可以提出修改建议；但候选策略是否有效，仍然需要通过独立故障场景和固定评测集验证。

## 11.1 建立可靠性回归集

每次可靠性改进，都应保留一组能够重现原始问题的测试案例。

如果系统修复了“工具超时导致重复调用”的问题，未来修改 TERSO、RetryController 或相关技能时，就必须重新运行这个案例。

这样可以避免同一类故障不断重复出现，或者一个版本修复了旧问题，却引入新的恢复缺陷。

## 11.2 评价改进的净收益

可靠性改进也可能产生代价。

例如，增加更频繁的检查点能够降低崩溃后的重做量，但会增加磁盘写入和存储占用。

因此，改进评估应同时比较：

- 故障恢复成功率；
- 恢复耗时；
- 任务总成本；
- 资源开销；
- 重复副作用；
- 运行复杂度；
- 新增故障模式。

如果一项改进只让某个指标变好，却显著损害其他关键指标，就不能简单地认定它是全局进步。

# 十二、与现有架构的集成边界

| 模块 | 在可靠性体系中的职责 |
|---|---|
| GECO | 记录事件、追踪、产物血缘和实际操作证据 |
| LTAR | 维护任务生命周期、检查点和恢复状态 |
| RERA | 管理故障分类、重试、熔断、降级与恢复决策 |
| TERSO | 执行工具操作、控制副作用并提供结果核验 |
| SOCDEA | 分析故障根因并提出改进假设 |
| UQEAG | 验证恢复后的产物是否满足最终验收要求 |
| MEODT | 重新分配失败工作包、替换专家并协调团队恢复 |
| Planner / DAG | 维护任务依赖、节点状态和受控重规划 |
| CEKCE / CIL | 提供可替换的能力与工作流版本 |
| TSEG / APE | 保证恢复、替换和重试不会突破安全边界 |
| SELCIA | 管理可靠性改进的独立评测、发布和回滚 |
| MTSRIC / ARCBG | 控制恢复期间的资源消耗、并发和预算 |
| HACCG | 展示任务不确定性，支持用户暂停、取消和人工接管 |

其中，RERA 应作为跨模块的可靠性策略层，而不是接管其他模块的全部职责。

# 十三、架构决策记录 ADR-761～ADR-780

以下建议纳入 EvoAgent 全量架构，作为 RERA 的治理基线。

## 14.1 第一版必须通过的端到端测试

建议用一个真实的代码修复任务完成验收：

1. 创建任务，生成 DAG 并执行代码分析。
2. 修改代码并运行测试。
3. 在关键状态转换之间模拟进程崩溃。
4. 重启系统，加载检查点并读取后续事件。
5. 对账文件、工具操作和测试结果的实际状态。
6. 仅恢复尚未完成且满足执行条件的节点。
7. 验证没有重复修改、重复提交或丢失产物。
8. 重新运行必要的回归测试。
9. 由 UQEAG 根据真实证据判定最终结果。
10. 由 GECO 保留完整的故障、恢复和验收轨迹。

**核心验收标准不是“崩溃后程序能重新启动”，而是“重新启动后，系统能够准确判断哪些工作已完成、哪些状态未知、哪些工作可以安全继续”。**

这才是复杂智能体真正需要的可靠性。

# 十五、下一专项：性能工程、资源调度与成本优化

完成 RERA 后，EvoAgent 已经具备了任务执行、专家协作、运行观测、安全治理和故障恢复的基本架构。

但还有一个与个人部署密切相关的问题尚未系统解决：

**当 EvoAgent 同时拥有多个专家、模型适配器、记忆系统、工作流和后台进化任务时，怎样在有限的 CPU、内存、GPU、磁盘和网络资源下，让整个系统既足够聪明，又不会拖垮用户设备？**

这不是简单的“减少模型调用”。

例如：

- Router 过于复杂，可能每次聊天都调用多个模型，导致响应变慢；
- 记忆检索过度，可能每次任务都加载大量无关内容；
- 多专家并行执行，可能同时占满内存；
- 后台进化任务可能与用户的前台任务争抢 GPU；
- 为了提高恢复能力而频繁创建检查点，可能产生大量磁盘写入；
- 过度压缩上下文，可能减少 Token 消耗，却增加返工率；
- 为了节省成本而切换低能力模型，可能使任务成功率下降，最终花费更多。

因此，建议下一专项定义为：

**Adaptive Performance & Resource Optimization，简称 APRO。**

重点研究：

1. 如何建立模型、工具、专家、任务和设备的统一资源预算；
2. 如何动态选择模型，而不是所有任务都使用最高成本模型；
3. 如何在响应质量、延迟、Token、内存和外部费用之间进行权衡；
4. 如何根据任务依赖和设备负载调整 DAG 并行度；
5. 如何控制专家数量，避免协调成本超过协作收益；
6. 如何决定记忆检索、上下文压缩和缓存的使用策略；
7. 如何管理模型预热、驻留、卸载与后台任务；
8. 如何在 Android、Windows 和微型 Linux 主机之间分配执行任务；
9. 如何根据任务价值和截止条件分配计算资源；
10. 如何优化检查点频率、事件存储和产物缓存；
11. 如何识别无效模型调用、重复推理、无进展循环和高成本返工；
12. 如何通过性能剖析发现真正的瓶颈，而不是凭感觉优化；
13. 如何将性能改进纳入 SELCIA 的独立评测和回归体系；
14. 如何保证资源优化不能绕过 TSEG 的安全门槛和 UQEAG 的质量要求。

本专项的核心原则是：

**优化的目标不是让每个模块单独运行得最快，而是让整个 EvoAgent 在满足质量、安全与可靠性要求的前提下，用合理的资源成本完成用户真正需要的任务。**

这将把 EvoAgent 从“能够执行、能够恢复、能够自我改进的系统”，进一步推进到“能够根据任务价值、运行环境和资源约束，自适应地选择最合适执行策略的个人智能体”。
