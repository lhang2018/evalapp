从资深产品经理的角度，我会先暂停继续堆技术模块，重新审视整个项目的产品定位。

你现在已经提出了 ReAct 循环、上下文治理、Harness 工程、提示词工程、运行日志、自动评测、Git 分支、模型适配，以及刚刚发现的工具自身故障问题。这些方向都正确，但它们还属于技术能力清单，不等于一个完整的产品定义。

EvoAgent 真正要解决的问题，不是让 AI 能够修改自己，而是让 AI 系统在长期运行中，能够持续提高完成任务的能力，同时知道自己的能力边界、识别自身故障，并且不因错误的自我优化而退化。

我会把它定义为：

EvoAgent 是一个能够持续运行、持续评估、持续修复和持续进化的智能体操作系统。它把模型、工具、上下文、执行流程和评测机制视为一个可管理、可验证、可回滚的整体，并针对特定模型、任务和环境积累长期有效的能力资产。

它不是另一个简单的 Agent 框架，也不是一个只会自动修改提示词的工具，更不是让大模型无限制地修改自身代码。

它应该是一个让智能体从“能运行”，逐渐成长为“能可靠地完成任务、发现问题、修复问题，并证明自己变得更好”的产品。

## 一、先确定产品最终应该是什么样

我建议将 EvoAgent 定位为一个具有五项核心能力的系统。

1. 能够完成任务的智能体运行平台

不仅能够对话，还能规划任务、调用工具、处理上下文、管理状态、应对失败，并在明确的验收条件下完成任务。

2. 能够发现问题的运行监控平台

持续记录运行轨迹，发现工具错误、模型行为变化、上下文损失、质量下降、成本异常和任务失败。

3. 能够验证改进的进化实验平台

将每个问题转化为可测试的改进假设，通过基线对比、回归测试和隔离实验，判断是否真的改善了能力。

4. 能够积累长期资产的版本平台

将经过验证的提示词、Harness 策略、工具实现、评测集和模型适配配置保存为可追溯版本，支持继承、分支和回滚。

5. 能够自我保护的可靠性平台

独立验证工具和评测器的可靠性，在证据不足、依赖异常或安全门禁失效时，停止自动发布而不是盲目进化。

这五项能力共同组成产品。缺少其中任何一项，都会限制系统最终能达到的自主程度。

例如，只有任务执行而没有观测，系统无法积累可靠经验；只有日志而没有评测，系统不知道如何改进；只有自动修改而没有独立验证，系统可能越改越差；只有优化而没有版本资产，换模型时又要从头开始。

## 二、产品的北极星：不是进化次数，而是可靠完成任务的能力

这是我认为整个项目最需要确立的一条原则。

假设 EvoAgent 一天自动修改了 100 次提示词，生成了 50 个分支，进行了 200 次实验。表面上，它非常活跃。

但如果任务成功率没有提高，工具故障没有减少，成本越来越高，系统还经常需要人工救火，那么这些进化都没有产品价值。

所以，我建议把北极星指标定义为：

可信自主完成率（Verified Autonomous Completion Rate）

它衡量的是：在预先定义的任务集合中，智能体在授权范围内、不需要人工介入，并且通过独立验收的任务比例。

可信自主完成率=自主完成且通过独立验收的任务数符合评测条件的任务总数\text{可信自主完成率} = \frac{\text{自主完成且通过独立验收的任务数}} {\text{符合评测条件的任务总数}}可信自主完成率=符合评测条件的任务总数自主完成且通过独立验收的任务数​
这个指标要与成本、延迟、安全性一起看。否则，系统可能通过无限重试或耗费大量 Token 来提高成功率。

我会为 EvoAgent 建立一个产品级指标体系。

## 产品成功指标

任务质量

核心
可信自主完成率、首次成功率、任务验收通过率、回归失败率。

故障恢复能力

可靠性
故障检测准确性、根因定位准确率、工具故障隔离时间、恢复成功率、重复故障率。

进化有效性

学习效率
有效改进率、改进带来的任务收益、退化率、回滚率、从发现问题到验证修复的时间。

经济效率

成本
单个成功任务的平均成本、平均耗时、每次有效改进的实验成本、人工干预时长。

未经授权操作次数、门禁绕过次数、敏感信息泄露事件、回滚有效性。严重安全事件不能用其他指标的提升抵消。

在第一版里，不需要立即拥有完美的指标系统，但要确保这些指标未来能从数据中计算出来。

还有一个重要区别：进化引擎本身也应该被评估。它不但要看 Agent 是否变好，还要看自己提出的修复是否有效、诊断是否正确，以及是否浪费了大量实验资源。

## 三、真正的产品核心：一条可信的自进化流水线

如果让我选择 EvoAgent 最值得长期投资的核心，我不会选择某一种提示词技术，也不会选择某个特定模型。

我会选择这条流水线：

Observe · 观测

知道系统发生了什么

Verify · 验证

确认工具、数据和评测结果是否可信

Diagnose · 诊断

判断故障属于模型、Agent、工具、环境还是评测器

Experiment · 实验

提出修复方案，在隔离环境验证效果

Promote · 晋级

通过门禁才发布，失败则拒绝并保留证据

Learn · 积累

沉淀可复用的能力、失败案例和模型适配资产

形成闭环，但每一步都可以拒绝不可信的输入，并保留完整审计记录。

这条流水线有一个特别重要的产品设计：每个阶段都可以独立失败，而且失败不能被下一阶段掩盖。

比如：

-
工具验证失败，就不能拿它的结果证明提示词优化成功。

-
评测器不可信，就不能发布候选版本。

-
候选版本通过离线测试，但生产环境表现退化，就应该自动回滚。

-
模型更换后，旧模型的经验未经验证，不能直接被视为新模型的最佳实践。

这会让 EvoAgent 不只是一个“自我修改器”，而是一个能够控制自身演化质量的系统。

## 五、不要从“通用智能体”开始，而要从一个可验证的产品切入口开始

你最终想让 EvoAgent 适用于通用任务，甚至具备自主编程能力。这是合理的长期方向，但从产品交付角度，第一版不应试图同时解决所有任务。

通用能力是长期目标，第一阶段则要选择一个能够反复测试、能衡量结果、又能覆盖核心工程问题的任务集合。

我建议采用“通用底座 + 分阶段能力包”的路线。

## 阶段 1

通用任务与工具可靠性

计算、文件读取、结构化信息整理、API 调用、任务规划、错误恢复。建立可重复评测集和可靠的工具契约。

目标：证明运行、观测、诊断和评测闭环成立。

## 阶段 2

自主编程与代码修复

读取代码库、修改代码、运行测试、诊断错误、创建 Git 分支、提交候选补丁。

目标：让每个代码修复都可测试、可回滚、可复现。

## 阶段 3

Harness 与工具自主修复

让系统能够修改工具实现、路由规则、上下文治理和恢复策略，在隔离环境中验证修复。

目标：不仅改善任务表现，还能修复自身的工程缺陷。

## 阶段 4

多模型、多任务进化

跨模型能力继承、独立适配档案、实验预算调度、不同任务类型的专属策略。

目标：把进化经验变成可迁移、可验证的长期资产。

我为什么建议把自主编程作为第二阶段？

因为代码天然具有相对明确的验证方式：单元测试、集成测试、类型检查、静态分析、构建结果和 Git 差异。它们能帮助你验证自进化机制是否真的有效。

但不要把测试通过等同于绝对正确。代码可能存在测试未覆盖的漏洞，测试本身也可能有缺陷。因此，编程能力的自主发布仍需要独立门禁和权限约束。

## 六、EvoAgent 应该具备自己的“能力资产库”

你之前特别强调：一个模型适配好了，就应该归档；更换模型时，从新分支继续优化。

我认为这个要求不应该仅仅作为 Git 分支管理功能，而应该升级为一个独立的产品模块：Agent Capability Registry（智能体能力资产库）。

每个稳定档案不仅保存代码和配置，还应保存：

-
模型及适配器信息。

-
Agent Core 版本与工具依赖。

-
系统提示词和策略配置。

-
上下文治理规则和记忆策略。

-
工具版本、接口契约及健康基线。

-
评测集版本、评测器版本与结果。

-
成功案例、失败案例和适用范围。

-
进化历史、发布记录、回滚记录。

-
环境指纹、已知限制和安全约束。

这样，每个档案就不再只是一个 Git commit，而是一份有适用范围、有质量证据、有明确依赖的智能体能力快照。

### 关键的产品规则

可以继承

通用工具契约、与模型无关的修复、独立测试方法、经过验证的任务案例和安全规则。

必须重新验证

模型专属提示词、工具调用策略、上下文裁剪参数、推理参数和依赖模型行为的优化。

禁止无条件继承

未经验证的修复、被隔离工具的成功记录、过期的环境假设、评测器失效时产生的优化结论。

从长期竞争力看，这个能力资产库很可能比某一代模型的具体表现更重要。模型可以被替换，但积累下来的高质量测试、故障模式、验证方法和经过证明的工程策略，可以长期为系统创造价值。

## 七、从产品经理角度，重新规划 V0.1 到 V1.0

我会把开发路线从“开发多少个模块”，改成“每个版本证明什么产品能力”。

| 版本 | 核心交付 | 必须证明的事情 |
|---|---|---|
| V0.1 | Agent Runtime、工具调用、日志、SQLite、Git、基础评测 | 系统可以稳定运行，失败可追溯 |
| V0.2 | 工具注册表、独立工具测试、健康监控、熔断和故障归因 | 能区分工具故障与 Agent 故障 |
| V0.3 | 候选生成、隔离实验、自动回归、变更报告 | 能够证明一次改进是否有效 |
| V0.4 | 模型档案、能力资产库、分支继承、版本回滚 | 更换模型不会丢失历史成果或盲目继承旧策略 |
| V0.5 | 白名单自动发布、生产监控、自动回滚、预算与权限管理 | 低风险改进可以受控自主发布 |
| V1.0 | 多任务能力包、工具与 Harness 修复、多模型进化调度 | 形成稳定、可持续、可扩展的自进化产品 |

这条路线有一个重要区别：V0.2 的工具可靠性不能被当作可有可无的附加功能。由于你已经意识到工具自身可能出错，我会把它列为 V0.1 之后最优先的升级，而不是先做更复杂的自动改代码能力。

### V1.0 的产品验收标准

在进入 V1.0 前，我希望 EvoAgent 至少通过以下验收：

1.
一组固定的代表性任务能够持续运行，并具有可信的质量基线。

2.
每次任务运行都可以追踪到模型、配置、工具和版本。

3.
能够发现常见工具故障，并在不确定时停止依赖相关结果。

4.
能够针对明确的问题生成候选修复并进行隔离测试。

5.
每次自动发布都具备可审计的评测证据。

6.
任何自动晋级都不会覆盖历史稳定版本，且回滚经过实际测试。

7.
模型切换后，系统能够建立新基线并重新验证模型相关策略。

8.
质量提升不是靠无限增加成本、降低安全要求或针对固定测试集过拟合实现的。

具体的成功率门槛、成本上限和样本规模，应该在获得第一批真实运行数据后制定，而不是在没有基线的情况下随意设定一个漂亮的百分比。

## 八、这个项目最大的产品风险是什么？

我会重点防范五个风险。

风险 1：错误自我强化

工具或评测器出错，却让系统误以为优化成功。应对：独立工具验证、可信基线、评测器测试和发布门禁。

风险 2：局部优化导致整体退化

一个任务成功率提高，其他任务却开始失败。应对：固定回归集、分任务指标、影子运行和自动回滚。

风险 3：进化成本失控

重复实验、多个模型互相评审，最终成本高于改善带来的收益。应对：实验预算、问题优先级和收益成本分析。

风险 4：版本资产失去可信度

不同模型、工具版本和评测基线混在一起，导致无法复现。应对：不可变版本标识、依赖清单和实验报告。

风险 5：自主权超过验证能力

系统能够修改核心代码，但没有足够可靠的测试和恢复机制。应对：分级权限、隔离执行、独立门禁和紧急停止。

这五个风险中，最值得提前投资的是第一个：错误自我强化。因为其他问题通常会产生明显异常，而错误的自我评估可能让系统在表面指标持续改善的情况下，逐渐失去真实可靠性。

## 九、如果由我负责这个产品，我会这样分配开发精力

在第一阶段，我会把资源集中在四件事情上：

## 01

先让运行结果可信

ReAct、工具契约、事件日志、异常处理、运行回放。

## 02

再让问题可以被定位

工具健康检查、故障分类、独立评测、根因证据。

## 03

然后让改进可以被证明

基线对照、隔离实验、质量与成本比较、晋级和回滚。

## 04

最后才扩大自主权

从配置自动调整，逐步发展到工具修复、Harness 改进和自主编程。

不要让项目过早陷入复杂多智能体协作、庞大知识库、自动修改所有代码或者炫酷控制台的开发。这些功能可以后续增加，但它们无法替代可信的运行、评测和发布机制。

## 十、我的最终产品判断

我认为，EvoAgent 最值得做成的产品，不是一个永远不停止运行、永远不断修改自己的 AI，而是一个具有以下能力的系统：

-
它能够完成任务。

-
它能够知道任务为什么失败。

-
它能够检查自己依赖的工具和评测系统。

-
它能够提出并验证修复方案。

-
它能够证明一次改进比旧版本更好。

-
它能够积累跨任务、跨版本、跨模型的有效经验。

-
它能够在无法确认结果可信时停止自动晋级。

-
它能够随着能力增强，逐步扩大自主范围，而不失去控制。

让每一次运行都成为改进的证据，让每一次改进都成为经过验证的能力，让每一次模型切换都成为新一轮进化的起点。

我建议接下来的工作不再只是继续添加模块，而是先形成一份正式的《EvoAgent 产品需求文档（PRD）》，明确产品目标、用户工作流、模块边界、功能优先级、数据模型、版本规则、验收标准和风险控制。随后以这份 PRD 为基准迭代工程，避免技术架构越做越大，却无法判断产品究竟是否在变好。
