# EvoAgent 第十七专项：上下文工程与长任务连续性引擎

这一轮继续深入 EvoAgent 的智能内核。

前面我们已经区分了历史记录、长期记忆、经验和策略，也明确了专家隔离、跨专家知识共享、记忆可信度与上下文压缩的基本原则。

现在要解决更贴近执行的问题：

**当一个任务很长、涉及多个专家、几十个工具调用，甚至中途断网、切换模型、重启应用时，EvoAgent 如何确保自己没有忘记目标、没有丢失关键约束，也不会把尚未完成的工作误认为已经完成？**

这不是单纯的上下文窗口问题。

即使模型拥有很大的上下文窗口，如果任务状态、工具结果、记忆来源和恢复检查点没有正确管理，智能体仍然会迷失方向。

反过来，即使模型上下文有限，只要任务状态保存得当、信息选择合理、执行能够恢复，智能体也可以可靠地完成很长的工作。

我建议将本专项定义为：

**Context Engineering & Long-Running Task Continuity Engine，简称 CLTC。**

它负责将任务目标、运行状态、必要记忆、执行证据和模型上下文组织成一个可持续推进、可中断恢复、可验证的任务系统。

## 一、第一性原理：上下文不是记忆库，也不是任务状态数据库

首先必须把四个容易混淆的概念分开。

  {#each [
    ["任务状态 Task State","机器可读取的当前事实：哪些步骤完成、哪些等待、哪些失败、哪些结果尚未确认。"],
    ["长期记忆 Long-term Memory","未来任务可能需要的知识、用户偏好、历史经验和经过验证的操作方法。"],
    ["执行证据 Execution Evidence","证明某项动作发生过、工具返回过什么、验收是否通过的可追溯记录。"],
    ["模型上下文 Model Context","本轮推理真正需要看到的信息，包括目标、相关约束、必要状态、证据摘要和可用工具。"]
  ] as item}



        **{item[0]}**
        {item[1]}


  {/each}

它们之间的关系应该是：

- 任务状态保存“现在实际处于什么状态”；
- 执行证据说明“为什么可以认为处于这个状态”；
- 长期记忆提供“以前学到的哪些知识可能有帮助”；
- 模型上下文只装入“本轮决策需要使用的内容”。

例如，一项视频生成任务的状态数据库记录某个镜头已经生成，文件路径和内容哈希也已保存；执行证据记录生成服务返回的任务 ID 与最终文件验收结果。

此时，模型不需要反复看到整个生成历史，只需要知道这个镜头已经验收通过、文件在哪里、哪些后续节点依赖它。

**关键原则：不能依靠模型记住全部历史来维持任务连续性。任务连续性必须由外部持久化状态保证。**

# 二、建立五层上下文架构

我建议 CLTC 采用五层逻辑架构。它们可以共享存储和代码基础设施，但职责必须分开。


    <title size="lg">L1 · 目标与约束层</title>
    保存原始用户目标、明确约束、授权范围、验收标准、预算上限和禁止事项。
    核心要求：不能被普通摘要静默改写。


    <title size="lg">L2 · 持久化任务状态层</title>
    保存 DAG、节点状态、依赖、当前检查点、重试计数、资源占用和待处理动作。
    核心要求：状态变化需要明确、可验证、可恢复。


    <title size="lg">L3 · 执行证据层</title>
    关联工具结果、文件版本、模型调用摘要、验收报告、错误记录和状态转换依据。
    核心要求：区分动作已尝试、结果已观察和结果已验收。


    <title size="lg">L4 · 上下文组装层</title>
    根据当前节点、专家、模型能力、风险和 token 预算选择需要的信息。
    核心要求：按需加载，而不是把所有历史一并塞进上下文。


    <title size="lg">L5 · 推理与行动层</title>
    由专家、Planner、ReAct 和工具接口根据当前上下文提出下一步动作。
    核心要求：推理结果必须经过状态、权限和执行门禁检查。


这里有一个关键的架构决定：

**上下文组装层不应该成为事实的唯一来源。**

它是一个面向模型的视图，而不是权威数据库。

如果摘要说某个步骤已完成，但任务状态库和执行证据显示该步骤仍在等待外部结果，就必须以经过验证的状态记录为准，并将摘要视为过期信息。

# 三、目标、约束和任务状态必须分开保存

长任务最容易出现的问题之一，是随着对话推进，原始目标逐渐被新指令、临时决定和模型摘要覆盖。

例如，用户最初要求：

> 制作一部 45 秒的动态视频漫剧，角色形象保持一致，总预算不超过指定额度，最后必须检查音画同步。

任务进行到一半时，用户又提出“先把前 15 秒做出来看看”。

这是一项阶段性要求，不意味着原来的 45 秒总目标、角色一致性要求和总预算自动失效。

因此，CLTC 应当把任务目标拆成三个层次。

## 3.1 原始目标、当前阶段目标和执行计划


    **原始目标 Original Objective**
    用户希望最终实现什么，以及明确提出的全局限制。
    除非发生明确的目标变更，否则持续有效。


    **阶段目标 Phase Objective**
    当前阶段需要交付什么中间成果。
    例如：先交付 15 秒样片，供用户确认角色和风格。


    **执行计划 Execution Plan**
    当前准备采用的 DAG、节点顺序、工具和恢复策略。
    可以根据执行结果修改，但必须继续满足有效的目标与约束。


这三个层次不能合并成一段不断改写的摘要。

否则模型可能因为最新阶段目标只提到 15 秒，就把总时长误解为 15 秒；也可能因为某个执行计划发生变化，就丢失原始验收要求。

## 3.2 目标变更必须形成明确的变更记录

建议将目标变更设计成独立的 `Objective Revision`：

- 原始目标版本；
- 新目标版本；
- 用户明确提出的变更；
- 被修改、被保留和被取消的约束；
- 变更影响的任务节点；
- 是否需要重新规划；
- 是否需要重新评估预算；
- 是否需要用户确认。

例如，用户明确说“不要做 45 秒了，改成 15 秒”，系统才能把总时长目标正式修改为 15 秒。

如果只是说“先做 15 秒给我看”，系统应该建立一个阶段目标，不应覆盖总目标。

## 3.3 约束需要结构化，而不是只放在提示词中

建议将任务约束分为：

- 质量约束；
- 预算约束；
- 时间约束；
- 工具与环境约束；
- 文件和数据范围约束；
- 用户授权约束；
- 验收约束；
- 禁止事项。

其中，硬性约束应保存在独立的结构化记录中，模型上下文只是它们的呈现形式。

如果上下文压缩器把“预算不超过 100 元”压缩成“尽量节约成本”，这不是无害的摘要，而是约束丢失。

# 四、长任务必须有持久化状态机

接下来解决一个关键问题：一个任务究竟在什么状态下才算完成？

不能仅依赖模型回答“我已经完成了”。

对于长任务，我建议采用显式状态机，并区分任务状态、节点状态和外部操作状态。

## 4.1 任务级状态

  {#each [
    ["CREATED","任务已创建，尚未开始执行。"],
    ["READY","任务约束、预算和执行计划已准备好。"],
    ["RUNNING","至少一个执行节点正在运行。"],
    ["WAITING","等待用户、外部服务、设备或其他依赖。"],
    ["PAUSED","因用户要求、资源限制或可恢复异常暂停。"],
    ["RECOVERING","正在核实状态、恢复节点或重新规划。"],
    ["VERIFYING","执行步骤已基本完成，正在验证最终交付。"],
    ["COMPLETED","最终验收标准已满足，并且有对应证据。"],
    ["FAILED","任务无法继续完成，且没有可行的自动恢复方案。"],
    ["CANCELLED","任务已取消，相关运行和后续动作已停止或进入安全收尾。"]
  ] as item}


        {item[0]}


        {item[1]}


  {/each}

这是一组建议的任务级状态，并不意味着每个任务都必须依次经过所有状态。

例如，简单任务可能从 `READY` 直接进入 `RUNNING`，最后进入 `VERIFYING` 和 `COMPLETED`。

## 4.2 节点级状态

DAG 中的每个节点还需要独立状态：

- `BLOCKED`：依赖尚未满足；
- `READY`：可以执行；
- `RUNNING`：执行中；
- `WAITING_EXTERNAL`：等待外部结果；
- `SUCCEEDED`：执行结果已通过该节点的验收条件；
- `FAILED`：执行失败；
- `RETRY_PENDING`：允许重试，等待调度；
- `SKIPPED`：经过明确的策略决定跳过；
- `CANCELLED`：已取消；
- `NEEDS_RECONCILIATION`：结果不确定，需要核对真实状态。

特别注意，`SUCCEEDED` 必须有明确的定义。

例如，一个视频生成 API 返回了任务 ID，只能证明生成请求已被接受，不能证明视频文件已经生成，更不能证明视频质量验收已经通过。

## 4.3 状态变更必须通过合法转换

建议由任务引擎管理状态迁移，不允许 Planner 或模型直接把任意节点改成成功。

例如：

- `READY → RUNNING`：执行器已取得执行权；
- `RUNNING → WAITING_EXTERNAL`：外部操作已提交，等待结果；
- `WAITING_EXTERNAL → NEEDS_RECONCILIATION`：等待超时，实际结果未知；
- `NEEDS_RECONCILIATION → SUCCEEDED`：通过外部状态核查与验收确认成功；
- `RUNNING → FAILED`：符合失败条件，并记录失败证据。

这能防止模型因为摘要中写着“已完成”，就直接跳过尚未完成的节点。

# 五、检查点与断点恢复：不能把“重新开始”当作默认恢复策略

对于几十个节点的 DAG，如果中途断网、进程崩溃或模型调用超时，直接重新执行整个任务可能会重复花钱、覆盖文件，甚至重复触发外部副作用。

因此，CLTC 必须与工作流引擎协作，建立持久化检查点。

## 5.1 检查点保存什么？

一个有效检查点至少需要记录：

| 类别 | 必须保存的内容 |
|---|---|
| 任务身份 | `task_id`、任务版本和目标版本 |
| 当前状态 | 任务状态、节点状态和已完成依赖 |
| 执行进度 | 已完成步骤、待执行步骤、当前执行尝试 |
| 产物清单 | 文件路径、版本、内容哈希和验收状态 |
| 外部操作 | 外部任务 ID、请求幂等键、操作状态与查询方式 |
| 资源信息 | 已使用预算、剩余预算、重试次数和时间限制 |
| 运行版本 | 专家配置、工具版本、模型适配版本 |
| 恢复信息 | 最近的可信检查点、未决操作和恢复策略 |

检查点不需要保存全部模型上下文。

相反，应该优先保存可以重建上下文的结构化状态和证据引用。这样即使模型换了、上下文窗口不同，任务仍然可以恢复。

## 5.2 检查点何时创建？

建议至少在以下节点创建检查点：

- 一个具有实际副作用的操作开始之前；
- 重要外部操作已提交之后；
- DAG 节点完成并通过验收之后；
- 大型文件或素材生成完成之后；
- 任务阶段切换时；
- 用户暂停或取消任务时；
- 执行计划发生重大变化时。

对于高成本或难以重现的节点，可以提高检查点频率；对于低成本、无副作用的内部步骤，则不必每一步都持久化完整快照。

## 5.3 必须区分执行一次与结果确认

这是断点恢复最重要的规则。

假设 EvoAgent 调用云端视频生成服务，服务已经收到请求，但手机断网，系统没有收到结果。

此时有三种可能：

1. 请求根本没有到达服务端；
2. 请求已经执行，结果尚未返回；
3. 请求已完成，但返回消息丢失。

如果系统直接重试，可能重复生成视频并再次收费。

正确的恢复顺序应当是：

1. 查找原操作的幂等键和外部任务 ID；
2. 如果服务支持，先查询原任务状态；
3. 如果已完成，恢复结果引用；
4. 如果仍在运行，继续等待；
5. 如果明确失败，按策略决定是否重试；
6. 如果无法确定状态，则保持 `NEEDS_RECONCILIATION`，不要假定失败。

对于不支持幂等请求或状态查询的外部服务，系统必须显式标记这种限制，并采取保守的恢复策略。

**超时不等于失败，进程崩溃不等于操作没有发生。**

## 5.4 文件产物也必须具备幂等性

例如，漫剧制作流程中的视频合成节点不应该每次恢复时都随意覆盖同一个文件。

建议采用：

- 稳定的节点产物 ID；
- 明确的输入版本；
- 内容哈希；
- 临时输出文件；
- 验收成功后原子提交；
- 已验收产物的复用规则。

如果输入素材没有变化、工具版本和合成参数也满足复用条件，就可以复用已验收产物，避免重复计算。

但如果角色素材、分镜或音轨发生变化，系统必须识别依赖失效，只重做受影响的节点，而不是错误地复用旧结果。

# 六、上下文组装：每次推理究竟应该看到什么？

现在进入模型上下文设计本身。

我不建议把上下文构造成一段不断增长的对话，而建议将它视为一个有预算、可重建、有明确来源的工作视图。

## 6.1 统一上下文包

建议定义 `Context Package`，每次模型调用之前由上下文引擎生成。

<CodeBlock language="json" editable>
{

  "task_id": "task-884",
  "task_revision": 7,
  "target_node_id": "render-final-video",
  "objective": {
    "summary": "Render and validate the final video",
    "constraints_ref": "constraints-v3",
    "acceptance_ref": "acceptance-v5"
  },
  "current_state": {

      "storyboard",
      "voiceover",
      "scene_generation"
    ],

  },

这是一个概念示例。实际上下文包还需要记录组装器版本、所用模型的实际限制、信息优先级和来源完整性状态。

其中最重要的不是这些字段本身，而是三个原则：

- 上下文必须能够从持久化状态重建；
- 重要信息必须能追溯到来源；
- 被省略的信息必须在必要时可以重新获取。

模型看到的是上下文包渲染后的内容，而不是直接拥有修改任务状态的权限。

## 6.2 上下文选择应该按优先级进行

建议采用以下顺序：

1. 当前任务的硬性约束与有效授权；
2. 当前节点的目标和验收条件；
3. 当前节点的输入、依赖和真实状态；
4. 尚未解决的问题和关键不确定性；
5. 必要的历史决策与证据；
6. 与当前任务相关的有效记忆；
7. 其他有助于推理的历史信息。

这不是说高优先级内容一定要以固定文本顺序出现，而是说，在预算不足时，系统不能先丢掉硬性约束，却保留大量无关的历史对话。

如果连最低必要上下文都无法装入模型输入窗口，系统应当拆分任务、改用适配的模型或采用结构化工具，而不是继续压缩到关键约束无法辨认。

# 七、上下文压缩：不能只看节省了多少 Token

上下文压缩通常很容易被错误地定义为“在尽可能少的 token 里保留尽可能多的信息”。

对于 EvoAgent，这个目标不够准确。

更合理的目标是：

**在满足任务正确性、约束完整性和可追溯性要求的前提下，以合理成本提供完成当前决策所需的最少信息。**

## 7.1 不同信息采用不同压缩策略

| 信息类型 | 建议策略 |
|---|---|
| 原始目标与硬性约束 | 结构化保存，压缩后必须能验证语义完整性 |
| 用户当前明确指令 | 保留原始语义和变更关系，不得由历史摘要覆盖 |
| 任务节点状态 | 使用结构化状态，不通过自然语言摘要推断 |
| 工具返回的大型结果 | 保存原始结果引用，提取当前决策需要的字段 |
| 代码、配置和技术文档 | 优先使用结构化提取、AST、符号索引或按需读取 |
| 视觉与视频素材 | 保存资产 ID、版本、元数据和验收结果，按需加载素材 |
| 历史对话 | 生成有来源的摘要，保留必要的原文引用 |
| 失败诊断与经验 | 保留证据、假设状态、适用范围和反例 |
| 模型自由生成的中间内容 | 可以压缩或丢弃，但不能把未经验证的内容升级为事实 |

## 7.2 全局压缩引擎与领域策略如何分工？

建议继续采用共享基础设施、领域独立策略的架构。

全局上下文引擎负责：

- token 预算；
- 消息格式与上下文包；
- 结构化信息装配；
- 压缩接口；
- 来源引用；
- 截断检测；
- 约束完整性检查；
- 上下文版本与重建。

领域专家负责定义：

- 哪些信息是该领域的关键约束；
- 哪些字段必须完整保留；
- 哪些结果需要引用原文；
- 哪些历史内容可以重新检索；
- 哪些压缩错误会导致严重退化。

模型适配层则负责调整不同模型的提示词组织、上下文长度和输入格式。

这样可以共享工程能力，同时避免用一套通用摘要规则损害编程、手机操作或漫剧制作等不同场景。

## 7.3 压缩后必须有完整性校验

我建议将关键约束单独保留，并在压缩后进行确定性核验。

例如，原始约束是：

- 总时长 45 秒；
- 预算不得超过指定上限；
- 角色外观保持一致；
- 最终必须完成音画同步检查。

压缩后，系统需要验证这四项约束仍然存在，并且没有被改变含义。

如果某项约束无法验证，系统应标记为上下文不完整，重新装配或检索原始内容。

不能让模型仅仅回答“我认为约束都保留了”，就认为压缩通过。

## 7.4 上下文压缩也必须有成本收益判断

更复杂的压缩器可能减少 token，但自身也会产生模型调用和处理延迟。

因此，评估应该比较：

- 输入 token 减少量；
- 压缩所需调用成本；
- 上下文组装延迟；
- 关键约束保留率；
- 任务成功率；
- 返工率；
- 错误恢复成本。

如果一项压缩策略只能节省少量 token，却需要额外调用一个昂贵模型，而且增加了约束丢失风险，就没有理由默认对所有任务启用。

# 八、任务恢复时，模型和上下文发生变化怎么办？

这是长任务设计中一个非常重要的边界。

假设 EvoAgent 开始时使用模型 A，运行到一半时手机断网；恢复后，模型 A 不可用，系统只能使用模型 B。

这时不能简单地把原始对话和摘要直接交给模型 B，然后继续。

因为不同模型可能对提示词结构、工具调用格式、上下文压缩方式和规划策略有不同要求。

我建议将恢复分为三个阶段。

## 8.1 第一阶段：恢复事实状态

先恢复：

- 当前任务与目标版本；
- 已验收节点和产物；
- 未决外部操作；
- 当前预算与剩余资源；
- 有效授权和约束；
- 任务依赖及失败节点。

这个阶段尽可能不依赖大模型推理。

## 8.2 第二阶段：重新组装模型上下文

根据当前模型和适配策略，重新生成上下文包。

例如：

- 旧模型使用的提示词格式不再直接沿用；
- 当前模型无法使用原来的工具协议时，重新生成兼容的工具描述；
- 旧上下文摘要与持久化状态冲突时，以经过验证的状态为准；
- 记忆中依赖旧模型的补偿规则，需要检查是否仍然适用。

## 8.3 第三阶段：重新评估是否能够继续

如果只是模型切换，可以在原任务约束下继续。

但如果模型切换影响了关键能力，或者新模型无法满足当前任务的最低能力要求，就应该暂停相关节点、采用已验证的替代策略，或者请求用户确认。

**模型可以变化，任务事实不能随模型一起改变。**

这也意味着，长任务的持续性不能依赖某个特定模型记住过去的对话。真正的连续性来自持久化状态、可追溯证据和可重建的上下文。

# 九、跨设备同步：手机与个人电脑必须有明确的状态所有权

结合 EvoAgent 的手机优先架构，任务可能在 Android 上发起，在个人电脑或 Mini PC 上执行复杂工作，再将结果返回手机。

如果没有明确的状态所有权，就可能出现：

- 手机认为节点已经完成，电脑却认为还在执行；
- 电脑更新了任务目标，手机仍然使用旧约束；
- 两边同时恢复同一个任务，重复执行外部操作；
- 离线期间双方都修改了同一份任务状态；
- 任务结果已生成，但手机一直没有收到完成通知。

因此，不能只同步对话历史，而必须同步任务状态、版本和事件。

## 9.1 建议的状态所有权模型

对于单个任务，在任意时刻应有一个明确的协调者负责推进其状态机。

例如：

- 手机本地任务：Android 任务引擎是协调者；
- 电脑执行的长任务：个人电脑上的任务引擎是协调者；
- 手机负责展示、补充指令和接收结果，但不应与电脑同时独立推进同一组节点。

协调者可以转移，但必须有明确的租约、版本或所有权转移记录，避免两个执行器同时认为自己拥有推进权限。

这并不意味着任务协调者拥有全部数据访问权。文件权限、工具权限和用户授权仍然由独立的权限系统控制。

## 9.2 使用版本号检测过期状态

建议每次重要状态变更都增加任务修订号，例如：

- `task_revision`：任务整体修订版本；
- `state_version`：状态记录版本；
- `plan_version`：当前 DAG 版本；
- `context_package_id`：当前上下文快照；
- `checkpoint_id`：最近一个可信检查点。

当手机恢复连接并提交一项修改时，电脑应当检查该修改基于哪个版本。

如果基础版本已经过期，不能直接覆盖最新状态，而应当进行冲突解决。

例如，用户在手机上取消了一个任务，而电脑离线期间仍然在运行。重新连接后，电脑不能因为本地仍然显示 `RUNNING`，就忽略取消请求并继续启动新的节点。

系统需要根据任务状态、已经发生的外部副作用和取消规则执行安全收尾。

## 9.3 不要把事件同步当成状态同步

事件同步解决的是“发生过什么”。

状态同步解决的是“当前权威状态是什么”。

两者相关，但并不等价。

建议采用：

- 事件日志：保留可追溯的变化历史；
- 状态快照：快速恢复当前任务；
- 修订号：检测并发修改；
- 协调者租约：防止重复推进；
- 检查点：恢复执行进度；
- 对账流程：发现事件与状态不一致时重新核验。

这样，即使设备离线很久，也能够在恢复连接后通过事件、版本和检查点重建一致的任务状态。

# 十一、如何评估上下文与长任务连续性？

上下文系统不能只通过 token 节省量评估。它必须证明任务在压缩、恢复、模型切换和跨设备同步后仍然正确。

建议建立以下评测指标。

| 指标 | 需要回答的问题 |
|---|---|
| 约束保留率 | 压缩和恢复后，关键约束是否完整且语义一致？ |
| 状态重建准确率 | 从检查点和事件恢复后，节点状态是否与真实执行状态一致？ |
| 恢复成功率 | 中断后能否在不重复执行危险动作的前提下继续任务？ |
| 重复副作用率 | 是否重复发送、删除、支付或重复生成昂贵产物？ |
| 产物复用率 | 能否正确复用未失效的已验收产物？ |
| 任务目标漂移率 | 长任务执行中是否偏离用户原始目标？ |
| 上下文组装成本 | 每次决策需要多少 token、耗时和额外模型调用？ |
| 上下文相关性 | 被加载的信息是否对当前节点决策有实际帮助？ |
| 预算一致性 | 恢复后是否正确计算已使用与剩余预算？ |
| 跨设备状态一致率 | 手机与个人电脑恢复连接后，权威任务状态是否一致？ |
| 未决操作对账率 | 超时或崩溃后的外部操作是否得到明确核实？ |
| 最终验收正确率 | 是否只有真正满足验收条件的任务才被标记为完成？ |

其中，约束保留率不能只依靠模型自评。应当通过结构化约束比对、针对性测试和必要的人工抽检来验证。

对于恢复能力，也不能只测试普通进程重启。还应模拟网络中断、外部请求已提交但结果丢失、文件写入中断、模型切换和并发修改等情况。

## 11.1 建立专门的故障注入测试

我建议至少包含以下测试：

- 在工具执行前崩溃；
- 在外部操作提交后崩溃；
- 在结果返回但尚未保存状态时崩溃；
- 在节点完成后、检查点写入前崩溃；
- 上下文压缩时故意移除一项关键约束；
- 在任务中途切换模型；
- 手机与个人电脑同时尝试推进任务；
- 恢复时发现外部任务已完成，但本地状态仍为等待；
- 用户取消任务后，设备恢复连接；
- 预算已接近上限时触发恢复和重试。

这些测试能检验系统是否真正具备连续性，而不是仅仅在正常流程中运行顺利。

# 十三、下一专项：任务编排、动态 DAG 与 ReAct 的协同治理

现在，我们已经分别讨论了记忆、上下文、持久化状态和长任务恢复。

但这些设计最终都要服务于一个实际问题：

**EvoAgent 面对复杂任务时，究竟由谁决定下一步做什么？由谁决定任务应该拆成哪些节点？什么时候使用固定工作流，什么时候动态规划，又什么时候应该让 ReAct 临场调整？**

这不是简单地在 Planner、ReAct 和 DAG 之间三选一。

一个复杂任务可能需要：

- 用 Planner 制定初始方案；
- 用 DAG 表达依赖和并行关系；
- 用 ReAct 执行单个节点内的动态工具调用；
- 用验收器判断节点结果；
- 用恢复控制器处理失败；
- 用任务治理层批准计划变更；
- 用长任务引擎持久化状态并恢复执行。

如果这些模块之间没有明确的控制权边界，就可能出现多个规划器反复改计划、ReAct 绕过工作流依赖、失败后重复执行已完成节点，或者局部智能体不断重试却耗尽整个任务预算。

下一专项建议设计 **Task Orchestration & Dynamic DAG Governance Engine（任务编排与动态 DAG 治理引擎）**，重点研究：

1. 专家智能体、Planner、ReAct、DAG 和任务执行器各自的职责；
2. 如何区分固定工作流、动态计划和临时行动策略；
3. 哪些节点可以并行、哪些必须串行，以及依赖如何验证；
4. 如何在执行过程中动态修改 DAG，而不破坏已完成节点和原始目标；
5. 如何决定重试、重新规划、局部回滚还是全局恢复；
6. 如何避免多个专家同时修改计划造成冲突；
7. 如何让失败诊断真正改变后续执行策略，而不是只生成更多重试；
8. 如何协调模型调用预算、任务时间预算和外部工具成本；
9. 如何把成功跑通的任务沉淀为稳定工作流，同时保留必要的动态分支；
10. 如何评估计划质量、执行效率、恢复效果和最终任务完成质量。

这一步会把前面设计的智能模块连接到统一的执行控制体系中，明确 EvoAgent 如何从理解目标走到稳定交付结果，同时保留处理未知情况的灵活性。
