# EvoAgent 第三十专项：评测体系、质量基准与进化效果归因

这一轮要解决自进化系统最关键的治理问题之一：

**EvoAgent 怎样证明一次改进确实让系统变强了，而不是只让某项指标变好看？**

前面已经设计了多专家架构、工具运行时、记忆与上下文、模型路由、RCAE 根因分析，以及 SHCRG 健康治理。它们都会不断提出改进建议。

但是，如果没有独立、可信的评测体系，每个模块都可能用自己的指标证明自己成功：

- 模型路由说调用费用下降了；
- 上下文引擎说 Token 消耗减少了；
- 编程专家说代码生成速度提高了；
- 工作流引擎说任务完成率提高了；
- 进化控制器说候选策略已经通过测试。

这些结论可能都是真的，但仍然不能证明 EvoAgent 的整体任务质量提高了。

例如，代码生成速度提高了 30%，但回归缺陷增加了；模型费用下降了 20%，但任务失败后的恢复成本翻倍；单个专家变强了，却让共享工具的其他使用者受到影响。

因此，本专项建议定义为：

**Evaluation, Quality Benchmark & Evolution Attribution Governance，简称 EQEAG。**

它负责评测基准、质量门槛、对照实验、进化效果归因、跨模块回归、发布资格和回滚证据。

## 一、第一性原理：进化必须以可验证的任务结果为依据

我建议首先明确一个基本原则：

**任何模块都可以提出改进，但没有任何模块可以单方面宣布自己的改进有效。**

例如：

- RCAE 可以提出故障根因假设，但不能仅凭诊断报告认定问题已经解决；
- MRCRG 可以提出更便宜的模型路由策略，但不能仅凭 Token 减少认定优化成功；
- CERG 可以提出新的上下文压缩策略，但必须验证关键事实是否被遗漏；
- 工具治理系统可以报告新工具的能力，但必须通过独立测试验证；
- 进化控制器可以创建候选版本，但不能绕过发布门槛直接修改生产配置。

评测系统应该独立于被评测的候选策略，拥有自己的基准、判定规则、版本记录和结果存档。

这里的“独立”主要是逻辑和治理上的独立，不意味着必须部署独立服务器。对于你的个人设备战略，一个本地进程内的独立评测模块就可以承担这项职责。

# 二、建立四层评测体系

EvoAgent 不应该只用一个总分衡量所有能力。我建议建立四层评测体系。


    <title size="md">L1 · 组件评测</title>
    评估模型适配器、工具、记忆检索、上下文压缩器、路由器等单个组件是否符合契约。



    <title size="md">L2 · 能力评测</title>
    评估编程、研究、旅游、漫剧制作等领域能力在代表性任务上的实际表现。



    <title size="md">L3 · 端到端任务评测</title>
    评估从用户请求、意图识别、计划、工具执行到最终验收的完整任务链。



    <title size="md">L4 · 系统级进化评测</title>
    评估改进对整体质量、成本、延迟、稳定性、恢复能力及其他专家的影响。


这四层需要逐级关联，但不能互相替代。

例如，AST 工具通过全部组件测试，只能说明它在测试范围内满足工具契约；这并不自动证明编程专家完成复杂重构的能力提高了。

同样，某个专家的任务成功率上升，也不能直接证明全局模型路由的改进有效，因为这可能是专家策略、上下文或工具版本变化造成的。

## 2.1 建立评测对象的统一身份

每次评测都应该明确被测对象，包括：

- 组件或专家 ID；
- 当前稳定版本；
- 候选版本；
- 相关模型版本；
- 工具与能力包版本；
- 上下文策略版本；
- 任务和工作流版本；
- 评测基准版本；
- 评测配置与资源预算。

这样才能判断一次成绩变化究竟由什么变化引起。

如果同时修改了模型路由、上下文策略和工具版本，最终成绩提高了，也很难知道具体是哪项改动起了作用。

因此，在能够控制变量时，应尽量分离改动；如果确实需要联合优化，就要明确把它作为一个整体候选方案评测，而不是随意归因给某个组件。

# 三、评测基准：不能只保留一套固定题库

如果 EvoAgent 长期只针对同一批测试任务进行优化，就容易逐渐适应这些题目，却无法处理真实世界中的新情况。

因此，我建议将评测数据分成六类。

| 评测集 | 主要用途 | 是否适合反复用于开发 |
|---|---|---|
| 契约测试集 | 检查组件输入输出和基本行为 | 适合 |
| 开发评测集 | 发现问题、比较候选方案 | 适合，但需要防止过拟合 |
| 固定回归集 | 检查已知能力是否退化 | 适合持续运行，但不能是唯一标准 |
| 隐藏验证集 | 检验候选方案对未直接参与优化的任务的表现 | 应限制直接访问 |
| 真实任务评测集 | 衡量实际使用中的质量和成本 | 按隐私规则采集并持续抽样 |
| 故障与边界案例集 | 检查超时、断网、权限不足、冲突和恢复能力 | 适合持续扩充 |

## 3.1 为什么隐藏验证集很重要？

假设 EvoAgent 的编程专家在 200 个开发任务上表现不好，于是进化控制器不断修改提示词、模型选择和上下文策略，直到这 200 个任务全部通过。

此时，它可能确实找到了更好的通用策略，也可能只是逐渐针对这 200 个任务进行了过拟合。

隐藏验证集可以提供额外证据：候选策略是否也能解决没有直接参与优化的相似任务？

但隐藏验证集也不能永远保持不变。如果某个固定集合长期被用于反复决策，它最终也可能被间接过拟合。因此需要定期补充新的案例、记录使用历史，并保留未公开的测试样本。

## 3.2 真实任务如何转化为评测案例？

真实任务往往涉及个人文件、私有项目、用户偏好和外部服务，不能直接无差别地复制到评测集。

建议采用受控流程：

1. 识别任务类型和失败模式；
2. 判断是否允许将相关数据用于评测；
3. 尽量抽取必要的最小信息；
4. 对敏感内容进行适当脱敏或使用合成案例替代；
5. 保存任务来源与授权范围；
6. 明确预期结果和可验证的验收条件；
7. 将案例归入相应的评测集。

尤其对于个人电脑上的代码、聊天历史和本地文件，评测系统不应该默认把它们上传到云端，也不应该因为它们出现在运行日志里，就自动将其纳入外部模型评测。

## 4.1 质量门槛必须高于优化收益

例如，一个候选版本的结果是：

- 任务通过率提高；
- 模型成本下降；
- 平均耗时缩短；
- 但未经授权的文件修改次数从 0 增加到 1。

这种候选版本不应该因为综合得分提高而发布。

对于安全、权限和关键任务约束，应采用硬性门槛，而不是允许其他指标补偿其退化。

同理，编程专家不能通过降低测试覆盖要求来提升表面成功率，漫剧专家不能通过缩短目标时长来提高生成成功率，模型路由也不能通过把困难任务排除在统计范围之外来改善结果。

**评测必须固定任务目标与验收标准，优化不能反过来随意修改判定规则。**

## 4.2 不同专家需要不同的专业指标

通用指标可以共享，但领域质量指标必须专业化。

例如：

- 编程：测试通过率、回归缺陷、修改范围、接口兼容性；
- 研究：事实准确性、来源可靠性、引用完整性、时效性；
- 漫剧：时长、角色一致性、音画同步、素材与预算约束；
- 手机操作：操作成功率、状态确认、越权行为、错误恢复；
- 旅游：约束满足率、信息时效、行程可执行性、预约状态准确性。

这些指标需要有可操作的判定方式。不能把所有领域都交给同一个模型评分器，再将它的分数当成绝对真值。

对于难以完全自动化的主观质量指标，可以采用明确的评分标准、人工抽样复核和一致性评估。

# 五、对照实验：如何证明改进确实有效？

这是自进化系统必须具备的核心能力。

假设 EvoAgent 要优化编程专家的上下文策略：

- 稳定版本 A：注入较多历史消息；
- 候选版本 B：注入结构化任务状态和相关证据。

最简单的实验方式，是让两种策略在相同或可比较的任务上运行，然后比较最终结果。

但为了让结果可信，需要进一步控制变量。

## 5.2 必须考虑模型的随机性

对于生成式模型，同一个任务多次运行可能得到不同结果。

如果只让稳定版本运行一次、候选版本运行一次，就可能把随机波动误认为改进。

建议根据任务成本和风险选择适当方法：

- 对确定性工具，优先使用可重复的契约与回归测试；
- 对随机性较高的生成任务，使用多次试验或合适的成对比较；
- 对成本高昂的长任务，先通过低成本代表性案例筛选候选，再进行完整端到端验证；
- 对样本量不足的实验，明确标记结果不确定，不要过早宣布成功。

对于样本量较小的个人系统，没有必要为了追求复杂的统计显著性而进行大量昂贵实验。但也不能把少数几个成功案例当作可靠的普遍证据。

## 5.3 固定随机种子并不能解决所有问题

部分本地模型和工具支持固定随机种子，这有助于提高可重复性。

但不同硬件、模型版本、供应商服务端实现和并行执行方式仍可能造成差异。

因此，版本记录、环境记录、重复试验和验收证据仍然不可缺少。

# 六、进化效果归因：出了问题，到底是谁导致的？

这一点尤其重要，因为 EvoAgent 是一个包含多个相互影响模块的系统。

假设某次发布后，编程任务的成功率下降了 8%。

可能原因包括：

- 模型供应商更新了模型；
- 模型路由选择了不同模型；
- 上下文压缩丢失了关键代码信息；
- AST 工具升级后改变了输出格式；
- 编程专家策略发生变化；
- 评测环境或任务难度变化；
- 多个因素共同造成退化。

如果系统只能看到“成功率下降”，却不能追溯相关版本与执行证据，就无法可靠地修复问题。

## 6.1 建立进化关联链

每次候选改进都应该拥有一条可追溯的关联链：

  {#each [
    ["问题记录","问题首次出现的时间、任务类型、影响范围和证据。"],
    ["根因假设","RCAE 提出的候选原因、证据强度和待验证问题。"],
    ["改进提案","明确的变更范围、预期收益、潜在副作用和回滚方式。"],
    ["候选版本","代码、配置、提示词、模型策略或能力包的不可变版本引用。"],
    ["实验记录","评测集、环境、基线、候选结果、资源消耗和失败样本。"],
    ["发布记录","审批结果、发布范围、时间、版本与生效条件。"],
    ["线上结果","真实任务质量、成本变化、异常事件和持续收益。"],
    ["最终结论","保留、回滚、继续观察或重新提出改进假设。"]
  ] as item}


        {item[0]}


        {item[1]}


    {#if item[0]!=="最终结论"}

    {/if}
  {/each}

这条关联链应由 SIEC 提供统一的事件关联和版本追踪能力，由 RCAE 提供诊断证据，由 EQEAG 负责评测与效果判定，再由 SIEC、发布治理和相关运行时共同记录最终状态。

这些是职责分工，不代表需要部署八个独立服务。

## 6.2 归因需要分层进行

建议按以下顺序排查：

1. 评测数据和验收标准是否发生变化；
2. 模型、工具、配置和执行环境是否发生变化；
3. 退化是否集中在某个专家或任务类型；
4. 退化是否与某次具体变更存在明确关联；
5. 是否可以通过回滚或受控对照实验验证；
6. 如果存在多个变化，是否需要进一步分离变量。

不能仅凭“时间上发生在发布之后”就认定某项变更是根因。

当多个因素同时变化，无法可靠确定唯一原因时，应明确记录“原因尚未确定”，而不是为了形成完整报告强行选出一个原因。

## 6.3 允许一个优化被判定为失败

进化系统应该能够接受以下结论：

- 假设不成立；
- 收益不足以抵消成本；
- 改善只存在于特定任务类型；
- 评测证据不足；
- 其他专家发生退化；
- 候选方案存在无法接受的风险；
- 暂时无法确定真正原因。

这并不是进化失败，而是避免系统把无效改变发布到生产环境的重要机制。

# 七、跨专家回归：共享内核的修改尤其需要谨慎

你之前反复强调过一个核心设计目标：优化通用智能体，不能意外影响编程专家、旅游专家或其他领域专家。

EQEAG 必须将这个要求转化为具体的评测规则。

## 7.1 不同改动需要不同范围的回归测试

| 改动类型 | 建议回归范围 |
|---|---|
| 单个专家的提示词或策略 | 该专家的开发集、固定回归集和关键端到端任务 |
| 工具实现升级 | 工具契约、依赖该工具的能力包与代表性工作流 |
| 全局上下文引擎修改 | 所有主要专家、长任务、压缩与恢复场景 |
| 模型路由策略修改 | 各主要任务类型、不同难度层级和预算边界 |
| 记忆系统或压缩策略修改 | 检索、冲突处理、跨任务隔离和恢复测试 |
| 权限、安全或任务状态机修改 | 所有相关权限边界、状态转换、取消和故障恢复测试 |
| 评测器或验收规则修改 | 评测器自身的校准测试，以及使用它的所有发布门槛 |

这张表是最低限度的测试范围建议。实际回归集合应当由组件依赖图、变更影响分析和历史故障记录共同决定。

## 7.2 建立依赖影响图

如果全局上下文引擎被修改，系统应当能够查询哪些专家、工具、工作流和验收器依赖它。

然后根据影响范围自动选择必要的回归集。

这可以避免两个极端：

- 每次改动都运行全部测试，导致成本过高；
- 只测试直接修改的组件，漏掉跨模块回归。

## 7.3 共享内核的发布门槛应更高

单个专家的优化可以在该专家的范围内灰度发布。

但涉及共享内核的改动，例如任务状态机、权限系统、上下文基础机制和统一工具执行网关，应当经过更广泛的回归测试。

如果某个候选版本提高了编程专家的成绩，却降低了研究专家的引用准确性，就不能仅凭编程任务的收益将其直接推广到全局。

# 八、发布治理：从候选策略到生产版本

建议将进化版本划分为五个阶段。



      阶段 1
      <title size="md">候选创建</title>

    保存变更内容、来源问题、适用范围、预期收益、风险与回滚方案。




      阶段 2
      <title size="md">离线评测</title>

    运行契约、质量、边界、恢复和跨专家回归测试，淘汰不合格候选。




      阶段 3
      <title size="md">受控试运行</title>

    在隔离工作区或明确授权的低风险任务中观察候选表现，不直接影响稳定生产状态。




      阶段 4
      <title size="md">灰度发布</title>

    仅在经过批准的专家、任务类型或流量范围内启用，并持续比较稳定版本与候选版本。




      阶段 5
      <title size="md">正式发布或回滚</title>

    满足质量门槛且没有不可接受的退化后，才将候选晋升为稳定版本；否则停止推广或恢复原版本。


对于个人使用的 EvoAgent，这些阶段不必全部依靠复杂的自动化部署平台实现。可以先由本地进化控制器管理版本、运行测试和生成发布报告，再根据风险决定是否需要用户批准。

但即使是个人系统，也不建议允许候选策略直接覆盖稳定版本而没有可恢复的历史记录。

## 8.1 不同变更应采用不同的审批级别

例如：

- 低风险、纯内部格式调整：通过契约和回归测试后可以自动发布；
- 专家提示词和工具选择策略：需要对应领域的评测结果；
- 全局上下文、记忆或模型路由变化：需要跨专家回归；
- 权限、安全和高风险副作用相关改动：需要更严格的审核与授权；
- 评测器或验收规则本身的修改：需要独立验证，不能由被评测的候选自行放宽门槛。

自动化程度可以逐步提高，但发布资格必须由预先定义的治理规则决定。

# 九、回滚不是简单切回旧版本

如果候选版本发布后出现退化，系统需要恢复的不只是一个配置文件。

例如，一次上下文策略升级可能同时影响：

- 专家策略版本；
- 任务执行配置；
- 缓存内容；
- 记忆索引；
- 工作流快照；
- 已经生成的产物；
- 正在执行的任务。

因此，回滚必须考虑运行状态与数据兼容性。

## 9.1 建立回滚前检查

建议确认：

- 上一个稳定版本是否仍然可用；
- 数据格式是否兼容旧版本；
- 正在执行的任务是否绑定旧配置；
- 是否有任务已经产生外部副作用；
- 是否需要重建缓存或重新索引；
- 是否存在必须迁移的数据；
- 是否需要暂停新的任务调度。

对于已经启动的长任务，不应在未检查兼容性的情况下，直接切换其执行语义。

## 9.2 回滚之后仍要保留失败证据

回滚后应当继续保留：

- 候选版本；
- 失败任务样本；
- 退化指标；
- 触发回滚的事件；
- 回滚操作记录；
- 已知原因和未解决假设。

否则，系统可能在下一轮进化中再次提出相同改动，却不知道之前已经失败过。

## 9.3 回滚不等于删除候选

候选可以被标记为拒绝、隔离或需要重新设计，但不应该因为失败就丢失其诊断与实验记录。

这些数据可以帮助 RCAE 识别重复故障模式，也可以防止进化控制器反复尝试已经证实无效的方案。

# 十、评测系统自身也必须被评测

这是容易被忽略、但非常重要的一点。

如果 EvoAgent 的验收器本身不可靠，那么整个进化闭环都会建立在错误判断上。

例如：

- 代码验收器没有运行测试，却把任务判定为成功；
- 研究验收器只检查引用格式，不检查来源是否支持结论；
- 漫剧验收器检查了文件存在，却没有检查实际视频内容；
- 模型评分器偏好冗长答案，导致策略通过增加无关内容获得更高分；
- 发布门槛计算错误，将失败任务排除在分母之外。

因此，评测器也需要自己的基准。

## 10.1 为评测器建立已知结果集

建议为每个重要验收器准备一组具有已知正确判定的案例：

- 明确合格的结果；
- 明确不合格的结果；
- 临界案例；
- 格式正确但语义错误的结果；
- 缺少证据的结果；
- 结果未知或无法判断的案例。

然后评估验收器的误判率、漏判率和不确定情况的处理能力。

## 10.2 不同类型的验收器具有不同的可信边界

优先使用可重复的确定性验证：

- 文件是否存在、哈希是否匹配；
- 测试是否实际运行、退出码和结果如何；
- 视频时长、分辨率、音轨是否满足约束；
- 工具输出是否符合 Schema；
- 外部操作是否得到可核验的确认。

对于语义正确性、研究质量、角色一致性等较难完全确定性验证的内容，可以组合使用规则、独立模型审查和人工抽样。

但模型评分不能自动成为绝对真值，尤其不能让同一个生成模型仅凭自我判断就完成高风险任务的最终验收。

## 10.3 评测标准修改需要独立治理

如果某项改进没有通过测试，系统不能简单修改测试规则让它通过。

如果确实发现旧的评测标准存在缺陷，应当：

1. 记录缺陷证据；
2. 提出评测标准修订方案；
3. 使用独立案例验证新标准；
4. 评估新旧标准对历史结果的影响；
5. 版本化保存标准变更；
6. 重新评估相关候选。

这样可以防止评测系统逐渐变成“为进化结果背书”的工具。

# 十一、个人设备上的实现建议

考虑到你的 EvoAgent 主要运行在个人电脑、Mini PC 或微型 Linux 系统上，我不建议为了评测治理单独搭建大型分布式评测平台。

建议采用本地优先的轻量架构。


    **Evolution Controller**
    提出候选、管理改进流程与发布申请



    **EQEAG Evaluation Engine**
    评测编排、基准管理、结果比较、质量门槛与发布资格判断



    <grid-item>

        **Benchmark Store**
        固定回归集、开发集、隐藏验证集、真实任务案例

    </grid-item>
    <grid-item>

        **Experiment Store**
        候选版本、实验参数、运行结果、失败证据与统计摘要

    </grid-item>



    **Isolated Evaluation Runner**
    在受控工作区运行测试、模拟任务与候选方案



    **Decision & Release Gate**
    发布、继续观察、拒绝、隔离或回滚


这里同样是逻辑架构，不需要每个方框都成为独立进程。

## 11.1 建议使用本地数据库和不可变版本记录

可以使用 SQLite 等本地数据库存储：

- 评测任务；
- 基准集元数据；
- 实验记录；
- 指标结果；
- 发布资格；
- 变更与回滚历史。

大型日志、代码、图片和视频仍然放在文件系统或产物存储中，通过稳定引用关联到实验记录。

如果候选涉及代码修改，应在独立工作区中运行，避免候选代码直接修改正在使用的评测器或基准数据。

## 11.2 评测任务本身也应该可恢复

例如，运行 100 个端到端任务时，设备突然关机。

恢复后，系统应该知道：

- 哪些测试已完成；
- 哪些测试尚未开始；
- 哪些测试正在执行；
- 哪些外部操作状态未知；
- 哪些结果已经写入数据库；
- 哪些结果需要重新核验。

评测运行器可以复用之前设计的任务生命周期、资源调度和恢复机制。

但需要注意：评测重试不能默认意味着安全地重复执行。对于会产生费用或外部副作用的测试，应使用隔离环境、模拟工具或具有明确幂等性的操作。

## 11.3 先保证证据完整，再追求评测自动化

初期不需要让系统自动决定所有发布事项。

优先确保每次实验都能回答：

- 测试的是什么版本？
- 使用了什么基准？
- 通过了哪些检查？
- 哪些指标改善或退化？
- 是否存在样本不足？
- 是否影响其他专家？
- 是否可以安全回滚？

这些基础能力建立之后，再逐步提高自动发布的比例。

# 十三、下一专项：长期运行、故障恢复与系统韧性治理

现在，我们已经为 EvoAgent 设计了能力扩展、任务执行、记忆与上下文、模型路由、根因诊断、质量评测和受控进化。

接下来还有一个基础问题需要深入：

**当 EvoAgent 连续运行几天、几周甚至几个月，遇到断电、磁盘空间不足、数据库损坏、模型服务异常、任务堆积、配置升级失败或部分数据不一致时，怎样保证系统能够恢复，而不是越运行越不稳定？**

这与你之前明确的本地设备战略直接相关。

个人电脑或 Mini PC 的资源有限，网络和外部模型服务也可能不稳定。如果系统只能在一切正常时表现良好，却不能处理长期运行中的各种故障，就无法真正成为可靠的个人智能体。

下一专项建议定义为：

**Long-running Reliability & Resilience Governance，简称 L3RG。**

重点研究：

1. 如何设计系统启动、关闭、重启和异常退出的完整生命周期；
2. 如何处理数据库事务中断、日志损坏和状态不一致；
3. 如何实现任务检查点、恢复扫描与外部操作对账；
4. 如何管理磁盘空间、缓存、日志和产物保留；
5. 如何防止内存泄漏、后台任务堆积和资源耗尽；
6. 如何处理模型服务故障、限流、网络断连和长时间不可用；
7. 如何确保断网期间的任务、日志和事件在恢复连接后正确同步；
8. 如何处理系统升级中断、配置回滚和数据库迁移失败；
9. 如何区分可自动恢复的故障、需要隔离的故障和必须请求用户介入的故障；
10. 如何通过故障注入、恢复演练和长期稳定性测试验证系统；
11. 如何避免恢复过程重复执行外部副作用；
12. 如何在资源有限的设备上确定可靠性、成本和性能之间的合理平衡。

这一专项的目标不是让系统永远不出故障，而是让 EvoAgent **能够发现故障、保存必要证据、限制故障影响、恢复可恢复状态，并在无法安全恢复时明确停止，而不是继续以错误状态运行。**
