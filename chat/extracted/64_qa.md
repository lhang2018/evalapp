# EvoAgent 第九专项：自我诊断、自我修复与故障恢复系统

这一轮我们继续深入智能体本身的智能机制，暂时不展开服务器部署和分布式基础设施。

前面已经设计了经验学习系统和能力自我模型。现在要解决更直接的问题：

**当 EvoAgent 正在执行任务时发现自己出了问题，它如何判断问题在哪里、选择正确的修复方法、验证修复效果，并决定是否将这次修复沉淀为长期改进？**

这与普通的重试机制有本质区别。

普通重试是：失败了，再试一次。

自我修复是：发现异常，分析原因，选择修复策略，验证是否有效，并决定是否需要改变后续执行方式。

例如，EvoAgent 让手机自动打开某个应用，结果没有进入目标页面。

一个简单智能体可能不断重复点击。

一个具备自我修复能力的智能体应该依次判断：

- 应用是否真的启动了？
- 当前页面是否与预期不同？
- 是点击坐标错误，还是界面布局变化？
- 是无障碍节点识别失败，还是权限不足？
- 是网络请求没有完成，还是页面仍在加载？
- 是否需要重新观察界面、改用另一种定位方式，或者暂停任务？

**核心原则：先诊断，再修复；先验证，再恢复；只有找到可复用的证据，才考虑长期进化。**

# 一、自我修复系统必须与执行系统分离

我建议为 EvoAgent 建立独立的 `Self-Repair Engine`，而不是把所有恢复逻辑塞进 ReAct 循环。

原因很简单：执行智能体的目标是完成当前任务，而诊断器的目标是判断当前执行为什么没有达到预期。这两个目标有关联，但不能完全合并。

如果执行模型既负责做事，又负责判断自己的行为是否正确，它可能会为已经失败的方案不断寻找理由。

因此，系统应该有三个相互协作但职责不同的部分：


    **执行智能体**
    理解目标、制定计划、调用工具、完成当前任务。



    **异常检测与诊断器**
    识别异常、重建事实、提出根因假设、评估证据。



    **自我修复控制器**
    选择修复动作，检查风险与预算，批准或拒绝恢复方案。



    **恢复执行与独立验收**
    执行修复，检查实际状态，确认成功、部分恢复或仍然失败。


这里的诊断器可以调用模型辅助分析，但关键事实应来自实际执行轨迹、工具结果和可验证状态。

修复控制器则负责决定哪些动作可以自动执行，哪些必须等待用户授权，哪些必须停止。

# 二、第一步：系统如何发现自己正在出问题？

如果只在最终任务失败后才启动诊断，很多问题已经造成了额外成本，甚至产生不可逆副作用。

所以，自我修复系统需要同时识别两种情况：

- **结果异常：** 已经明确失败，例如工具返回错误、测试未通过。
- **过程异常：** 任务暂时还没失败，但执行轨迹显示出明显风险，例如连续重复操作、成本异常增长、状态没有进展。

我建议建立五类异常检测机制。

| 异常类型 | 识别依据 | 示例 |
|---|---|---|
| 结果异常 | 预期结果与实际结果不一致 | 文件修改后测试失败 |
| 状态异常 | 实际环境状态与任务状态冲突 | 任务记录显示应用已打开，但系统实际没有打开 |
| 行为异常 | 出现重复、循环或无效动作 | 连续三次点击同一个无响应按钮 |
| 资源异常 | 预算、延迟、内存或调用次数超出限制 | 模型调用成本持续增加 |
| 可信度异常 | 关键结论缺乏证据，或证据相互矛盾 | 模型声称操作成功，但没有状态验证 |

这些异常不应该全部依赖大模型判断。

例如，超时、预算超限、重复调用、状态字段缺失等情况，可以由确定性规则检测。复杂的语义异常、意图偏差和疑似推理错误，才需要模型辅助诊断。

## 2.1 一个关键设计：预期状态与实际状态必须分开保存

假设手机操作智能体执行“打开某个应用”。

它可能记录了：

- 计划状态：应用已启动；
- 工具状态：启动请求已提交；
- 实际观察：当前前台仍然是桌面；
- 验收状态：目标未达成。

如果只维护一个 `success=true/false` 字段，这些信息就会被混在一起。

建议将任务状态拆分为：

- `desired_state`：希望达到的状态；
- `predicted_state`：模型认为当前应该是什么状态；
- `observed_state`：实际观察到的状态；
- `verified_state`：经过验收确认的状态；
- `execution_status`：当前执行生命周期状态。

这样，系统可以检测到模型判断、工具返回和实际环境之间的差异，而不是盲目相信其中某一个。

## 2.2 检测到异常后，不要立即启动昂贵诊断

我建议采用分级触发：

- 轻微异常：执行一次低成本状态检查；
- 可恢复错误：调用工具契约规定的恢复机制；
- 重复异常：启动根因诊断；
- 高风险异常：立即暂停相关动作并检查安全状态；
- 重大异常：隔离相关能力或版本，阻止继续调用。

例如，普通的文件读取失败可能只需要检查路径和权限；如果一个工具连续返回与实际状态不符的成功结果，就应该提高警惕，暂停依赖该工具的后续关键操作。

# 三、第二步：诊断器如何找到真正的根因？

这是整个自修复系统最难、也最有价值的部分。

我建议把根因分析拆成四个层次，而不是让模型直接回答“为什么失败”。


    **D1：现象确认**
    发生了什么？是否确实偏离预期？有没有足够证据确认异常？


    **D2：故障定位**
    问题最早出现在哪个环节：理解、规划、上下文、工具、环境、状态管理还是验收？


    **D3：根因假设**
    列出可能原因、支持证据、反证、未验证条件及其相对可信程度。


    **D4：根因验证**
    通过安全的状态检查、回放、对照实验或局部测试，判断哪种解释最符合事实。


## 3.1 必须区分故障位置与根本原因

例如，任务在验收阶段失败，并不意味着验收器就是根因。

可能是：

- 上游工具真的没有完成操作；
- 工具完成了，但没有返回必要证据；
- 任务状态没有及时更新；
- 验收器读取了过期数据；
- 验收规则本身写错了。

“失败在哪个环节被发现”和“哪个组件导致了失败”是两个不同问题。

系统应先定位首次出现的异常，再分析原因。这样才能避免只修补最后暴露问题的模块。

## 3.2 诊断器应输出结构化报告

例如：

<CodeBlock language="json" editable>
{
  "incident_id": "incident-0214",
  "observed_failure": "目标应用未进入前台",
  "first_divergence": "post_launch_verification",
  "hypotheses": [
    {
      "cause": "launch_request_rejected",
      "supporting_evidence": [
        "launch_result_code"
      ],
      "status": "SUPPORTED"
    },
    {
      "cause": "foreground_detection_stale",
      "supporting_evidence": [],
      "status": "UNTESTED"
    }
  ],
  "root_cause_status": "UNCONFIRMED",
  "recommended_check": "refresh_foreground_state",
  "risk_class": "LOW",
  "repair_budget": {
    "max_actions": 2,
    "max_model_calls": 1
  }
}
</CodeBlock>

这是结构示例。真实系统需要引用实际存在的事件 ID、工具结果和状态快照，不能让模型随意编造证据编号。

这里最重要的字段是 `root_cause_status`。如果原因还没有确认，修复控制器就不应该把某个假设当成事实，更不能据此自动修改共享工具或通用提示词。

## 3.3 不确定时，优先做最便宜的鉴别实验

例如，诊断器怀疑是界面识别错误，也怀疑应用启动失败。

最便宜的检查可能是重新读取当前前台应用信息。如果读取结果已经表明目标应用根本没有启动，就没必要先调用昂贵的视觉模型分析整张屏幕。

建议诊断器选择能够最大程度区分候选原因、同时风险和成本最低的检查。

但不能为了节省成本而跳过必要的安全核验。对于可能产生不可逆副作用的操作，应先确保当前状态明确，再决定是否继续。

# 四、第三步：建立分级自我修复策略

我不建议让智能体遇到错误后直接自由发挥，尝试任何它想到的修复方法。

更可靠的方式是建立一个**从低风险、低成本到高风险、高成本的修复阶梯**。

  {#each [
    ["R0","重新观察","刷新环境状态、重新读取工具结果、确认异常是否仍然存在。"],
    ["R1","修正输入","纠正参数、补全缺失字段、重新检索相关上下文。"],
    ["R2","安全重试","仅在确认重试安全、满足工具契约和预算限制时重试。"],
    ["R3","切换方法","更换定位方式、工具实现或经过验证的替代策略。"],
    ["R4","局部重规划","保留已验收产物，只重新执行受到影响的任务节点。"],
    ["R5","升级诊断","使用更强的诊断能力、扩大证据范围或进行隔离实验。"],
    ["R6","暂停并求助","等待用户授权、请求缺失信息，或停止不安全的执行。"]
  ] as item}


        {item[0]}


        **{item[1]}**
        {item[2]}


  {/each}

这是一个推荐的修复阶梯，不是要求每次严格从 R0 走到 R6。

如果检测到权限错误，系统不应该先不断重试；如果发现工具可能重复提交了支付请求，也不能通过再次调用来验证。控制器应根据故障类型、风险和证据，直接选择最合适的安全路径。

## 4.1 不同故障类型对应不同的修复策略

| 故障 | 合理的修复方向 | 不应该做的事 |
|---|---|---|
| 参数格式错误 | 按契约修正并重新校验 | 不断使用相同错误参数重试 |
| 短暂网络故障 | 检查状态，再按契约重试 | 盲目重复提交有副作用的请求 |
| 上下文遗漏 | 恢复缺失约束，重新编译请求 | 无差别增加所有提示词长度 |
| 路由错误 | 重新评估任务与能力匹配 | 让原专家无限尝试不擅长的任务 |
| 工具实现缺陷 | 隔离工具，进入测试与修复流程 | 通过提示词掩盖工具缺陷 |
| 工作流依赖错误 | 调整受影响的 DAG 节点和依赖 | 无条件从头重跑整个任务 |
| 验收器误判 | 核查证据与验收规则 | 为提高成功率直接放宽标准 |
| 权限不足 | 请求授权或停止 | 自动寻找绕过权限的方法 |

这张表体现了一个核心思想：修复动作必须针对故障类型，而不是统一使用“多想一遍”或“换个提示词”。

## 4.2 自我修复要有明确的预算

你之前强调过，能力可以提升，成本也可以适度增加，但不能无限增长。

因此，每次自我修复都应拥有独立的预算，包括：

- 最大诊断模型调用次数；
- 最大修复尝试次数；
- 最大额外 Token；
- 最大额外费用；
- 最大恢复时长；
- 最大允许副作用风险。

当预算耗尽时，系统应暂停并给出当前已知事实、未解决的问题和建议下一步，而不是继续调用模型直到偶然成功。

更重要的是，**预算耗尽不代表任务已经失败，也不代表任务已经成功**。如果外部状态尚不明确，应保持 `INCONCLUSIVE` 或等待状态。

# 五、第四步：修复成功后，怎样证明问题真的解决了？

修复动作执行成功，并不等于原始问题已经解决。

例如：

- 重新点击按钮成功，不代表目标业务操作已经完成；
- 修复代码并成功保存，不代表代码通过测试；
- 重启应用成功，不代表原来的异常不再出现；
- 修改提示词后一次回答正确，不代表策略整体改善。

因此，修复控制器必须在修复前明确成功条件，并在修复后使用独立证据重新验收。

## 5.1 建立修复前后的对照

每次修复都应记录：

- 原始异常；
- 修复前的实际状态；
- 修复动作及其依据；
- 修复后的实际状态；
- 原始验收条件是否满足；
- 是否引入新的异常；
- 实际成本；
- 是否需要继续观察。

例如，代码修改失败后，系统不仅要检查新代码是否成功写入，还需要重新运行相关测试、检查代码差异，并确认没有意外修改其他文件。

对于间歇性故障，一次成功可能不足以证明问题已解决。应根据故障性质进行重复测试或在后续任务中持续观察。

## 5.2 不能用降低验收标准来制造修复成功

这是自修复系统必须具备的硬性规则。

假设任务要求所有测试通过，而系统修复三次后仍有测试失败。它不能为了结束任务而自动把验收条件改成“主要功能可用”。

如果用户明确允许降级方案，系统可以提出一个新的任务目标，并在需要时征求用户确认；否则，应保留原始验收标准，并如实报告未完成的部分。

# 六、自我修复与自我进化：必须是两个独立闭环

这是本专项最重要的架构决策之一。

假设 EvoAgent 今天遇到一个网页按钮定位失败的问题。

它可能有两种处理方式：

**当前任务的修复闭环：**

重新观察页面，发现按钮位置发生变化，改用无障碍节点定位，完成当前任务并通过验收。

**长期系统的进化闭环：**

将此次故障作为候选经验，收集其他页面的类似案例，验证无障碍节点定位在相应场景中是否更可靠，再决定是否修改手机操作专家的默认策略。

第一件事是让当前任务恢复正常；第二件事是让未来任务减少类似问题。

两者可以共享证据，但不能互相替代。


    **运行时自我修复**
    异常 → 诊断 → 修复 → 验收 → 恢复当前任务



    **经验沉淀接口**
    保存经过脱敏的故障记录、根因证据和修复结果



    **后台进化闭环**
    跨任务分析 → 生成候选 → 评测 → 发布或拒绝


这里的箭头代表受控的数据流，而不是运行时修复可以直接修改后台稳定版本。

## 6.1 为什么不能让运行时直接修改自己？

因为当前任务中的局部信息往往不足以支持全局修改。

例如，某个应用的按钮位置变了，运行时切换定位方法可能是正确的；但如果直接将“所有手机操作都优先使用视觉识别”写进全局策略，反而可能降低稳定性、增加延迟和模型成本。

所以，我建议：

- 运行时可以执行已经批准的恢复策略；
- 运行时可以生成经验与改进候选；
- 后台进化系统负责验证跨任务效果；
- 只有通过发布门禁的候选才能成为新的稳定策略。

对于低风险且可逆的运行参数调整，可以允许在当前任务范围内自动生效，但必须有明确的适用范围、预算和恢复方式。

## 6.2 修复经验什么时候应该升级？

建议采用以下规则：

- 一次偶发错误：记录事件，通常不需要修改系统；
- 重复出现的相似故障：分析是否存在稳定的故障模式；
- 根因明确且可复现：生成针对性改进候选；
- 改进通过专项测试：允许在对应范围内试运行；
- 改进通过跨场景回归：考虑晋升为稳定策略；
- 发布后出现退化：停止扩大范围，并回滚或重新诊断。

这让自我修复与自我进化形成闭环，但又不会因为一次偶然成功而不断修改整个系统。

# 七、诊断器自身出错怎么办？

这是一个必须继续往下追问的问题。

如果执行智能体可能出错，工具可能出错，那么诊断器也一定可能出错。

例如，诊断器认为某次失败是上下文遗漏，于是增加了提示词；但真实原因是工具返回了错误状态。后续任务成本变高，问题却没有解决。

如果系统没有评估诊断器自身的机制，它就可能持续沿着错误方向优化。

我建议建立三项保护机制。

## 7.1 证据与结论分离

诊断器必须明确区分：

- 已观测事实；
- 推测原因；
- 支持证据；
- 反对证据；
- 未验证的条件；
- 最终诊断状态。

它不能通过一段流畅的解释，就把一个假设升级为已确认根因。

## 7.2 关键诊断使用独立验证

对于低风险问题，可以直接执行廉价检查；对于涉及工具实现、共享提示词、安全策略或大量任务的改动，必须进行独立验证。

例如，怀疑 AST 工具有缺陷时，应当用能够复现问题的最小代码样例进行测试，而不是只让另一个大模型评价原工具是否可靠。

## 7.3 建立诊断回归集

每次诊断策略升级，都应该在已知故障案例上测试：

- 是否能识别真正的故障类别；
- 是否会把工具问题误判成提示词问题；
- 是否会把环境问题误判成模型问题；
- 是否能够识别多个共同根因；
- 是否会在证据不足时承认不确定；
- 是否会提出超出权限的修复动作。

建议重点监控误归因率和错误修复成本，而不仅是诊断器自报的置信度。

# 八、Android 端的自我修复需要特别设计

结合 EvoAgent 的手机优先方向，自我修复不能只考虑云端模型任务，还必须处理 Android 环境中的实际异常。

例如：

- 目标应用被系统关闭；
- 无障碍服务被用户关闭；
- 应用页面发生变化；
- 权限弹窗阻止操作；
- 网络断开；
- 系统回收后台进程；
- 当前任务状态与实际界面不一致；
- 服务端已经收到任务，但手机没有收到确认。

这些问题不一定需要重新调用大模型。

我建议将手机自修复分成三层。


    **第一层：本地确定性恢复**
    重新读取界面状态、检查权限、查询应用前台状态、恢复本地任务检查点、检测重复动作。
    目标：以最低成本解决可以确定性处理的问题。


    **第二层：智能策略恢复**
    重新识别界面、调整操作路径、选择替代工具、局部重规划或请求云端模型辅助诊断。
    目标：处理需要语义理解或动态决策的异常。


    **第三层：受控人工介入**
    权限不足、状态无法确认、可能造成不可逆副作用、恢复预算耗尽或安全风险无法排除时暂停。
    目标：避免为了自动完成而越过安全边界。


## 8.1 断网时应该怎么办？

如果 Android 与个人电脑或 Mini PC 失去连接，本地执行轨道仍然可以：

- 保存任务状态和必要日志；
- 运行已批准的本地恢复策略；
- 对能够离线验证的任务继续处理；
- 将需要云端能力的节点标记为等待或阻塞；
- 保存待同步的事件；
- 恢复连接后继续上传诊断证据。

但断网时不能假装远端操作已经成功。

如果手机无法确认云端任务是否执行，正确状态是“结果待核实”，而不是简单地再次提交同一个请求。

## 8.2 哪些修复动作可以完全自动化？

建议按风险划分：

| 风险等级 | 示例 | 默认策略 |
|---|---|---|
| 低风险、可逆 | 重新读取界面、修正无害参数、恢复本地检查点 | 可以自动执行 |
| 中风险、可控 | 替换工具实现、重新生成非最终产物 | 需要额外校验和预算限制 |
| 高风险、有副作用 | 删除文件、发送消息、支付、提交正式发布 | 根据权限与授权要求执行，必要时必须确认 |
| 状态不确定 | 无法确认远端操作是否完成 | 先核查，不盲目重试 |

风险不应该只由工具名称决定，而应结合当前参数、目标对象、实际副作用和可恢复程度来评估。

例如，读取文件通常是低风险操作，但读取包含敏感信息的文件仍然需要权限检查；生成视频通常可以重试，但如果每次调用都会产生费用，就需要预算和任务状态核查。

# 九、自我修复系统的核心状态机

为了防止恢复逻辑散落在各个专家中，我建议建立统一的修复状态机。


    **NORMAL**
    正常执行



    **DETECTED**
    检测到异常，记录事件并暂停受影响的动作



    **DIAGNOSING**
    收集证据，分析根因与风险



    **REPAIR_APPROVED**
    修复策略通过权限、风险和预算检查



    **REPAIRING**
    执行修复并记录实际状态变化



    **VERIFYING**
    使用原始验收标准核查修复结果


    <grid-item>


        **RECOVERED**
        恢复原任务或继续剩余节点

    </grid-item>
    <grid-item>


        **ESCALATED**
        停止、等待或请求进一步介入

    </grid-item>


还需要支持 `ROLLING_BACK` 和 `QUARANTINED` 等状态：

- `ROLLING_BACK`：撤销已知可逆的部分变更，恢复到安全检查点。
- `QUARANTINED`：将疑似有缺陷的工具或策略暂时移出正常调度。

这些状态的转移应由确定性控制器管理。模型可以提出恢复建议，但不能绕过状态机直接把任务标记为已恢复。

尤其需要注意，回滚不是万能的。发送消息、外部支付、已经被第三方获取的文件等操作，可能无法真正撤销。因此，系统必须区分“回滚本地状态”和“补偿外部副作用”。

# 十、如何评估自我修复是否真的变强？

我建议建立独立的自我修复评测集，而不是只看任务成功率。

| 指标 | 说明 |
|---|---|
| 异常检测召回率 | 真实异常中，有多少被检测到 |
| 误报率 | 正常执行中，有多少被错误判定为异常 |
| 根因归因准确率 | 是否正确定位故障来源 |
| 修复成功率 | 修复后是否真正满足原始验收标准 |
| 误修复率 | 是否修改了本来正常的组件或策略 |
| 平均恢复时间 | 从发现异常到恢复或安全停止的时间 |
| 恢复成本 | 额外模型调用、Token、工具费用和时间 |
| 重复副作用率 | 修复或重试是否造成重复外部操作 |
| 安全停止准确率 | 应当停止时是否及时停止 |
| 复发率 | 同类问题在修复后是否再次出现 |

这里有一个容易忽略的指标：**修复成功率必须结合修复成本来看。**

如果一种修复方法能够让成功率提升 2%，却让每次任务平均多调用十次大模型，那么它未必值得默认启用。

同样，如果某种快速恢复策略能解决 90% 的普通故障，但在少数高风险操作中可能造成重复提交，就需要把它限定在安全的适用范围，而不是简单以平均成功率决定是否发布。

建议每次自修复策略升级都同时评估质量、成本、恢复时间和安全指标。

# 十二、下一专项：不确定性判断与主动决策系统

自我修复完成后，我建议继续研究另一个更深层的智能问题：

**EvoAgent 怎样判断自己到底知道多少、什么时候应该相信当前判断、什么时候应该继续探索、什么时候应该问你，以及什么时候应该停止？**

这与普通的模型置信度不同。

一个模型可能对错误答案非常自信；一个任务也可能没有明显错误，却缺少足够证据证明成功。

下一专项建议设计 `Uncertainty & Active Decision Engine`，重点包括：

1. 区分模型信心、证据充分性、环境不确定性和执行风险；
2. 判断何时可以直接执行，何时需要检索、验证或澄清；
3. 决定是否值得增加一次模型调用或使用更强的模型；
4. 判断何时继续探索的预期收益已经低于成本；
5. 防止系统因为过度谨慎而频繁打断用户；
6. 防止系统因为过度自信而错误执行；
7. 将不确定性纳入路由、规划、ReAct、验收和自我修复；
8. 通过实际结果校准判断，而不是依赖模型自报置信度。

这一步很重要，因为真正成熟的个人智能体，不是永远自信地执行，也不是遇到一点不确定就问用户，而是**知道何时可以放心行动、何时必须验证、何时值得继续投入，以及何时应该停止**。
