## 一、先统一产品定位：EvoAgent 到底是什么？

我建议将 EvoAgent 定义为：

> **一个以目标完成为核心、以工作流为可复用执行资产、以可验证的持续改进为后台能力的个人通用智能体系统。**

它既不是单纯的聊天助手，也不是单纯的工作流引擎，更不是一个为了不断修改自己而存在的自进化实验项目。

它的价值在于：用户只需要描述目标，系统就能根据自身能力选择合适的执行方式；任务成功后积累可复用的流程经验；运行失败时能够诊断、恢复和记录；经过验证的改进再进入稳定版本。

这四个支柱应该成为所有后续功能的判断标准。

例如，AI 漫剧不是一个新的核心系统，而是“完成任务”和“积累可复用能力”的具体场景。Android 无障碍操作不是产品的全部，而是其中一种工具能力。ReAct 不是产品本身，而是完成部分复杂任务的一种执行策略。

这样才能避免每次想到一个新场景，就重新设计整个系统。

## 二、把过去讨论过的功能重新归位

先把已经讨论过的内容重新分层。这样可以判断哪些必须保留，哪些应该成为插件，哪些不应该在第一版开发。

| 已讨论的功能 | 在新架构中的位置 | 产品决策 |
|---|---|---|
| ReAct 循环 | Agent Runtime | 保留，作为可配置执行策略 |
| 上下文治理 | Context Manager | 保留，按任务管理上下文和历史 |
| Harness 工程 | Runtime 基础设施 | 保留，负责执行约束、工具接口、状态和错误处理 |
| 提示词工程 | Prompt / Policy Registry | 保留，支持版本化和评测 |
| 意图识别 | Intent Router | 保留，负责选择任务类型和执行路径 |
| Android 应用操作 | Mobile Tool Adapters | 独立能力包，逐步开放 |
| 工作流固化 | Workflow Compiler | 提升为核心模块 |
| 工作流执行 | Workflow Runtime | 提升为核心模块 |
| 运行日志与故障诊断 | Observability & Diagnostics | 核心基础设施 |
| 自动评测 | Evaluation Engine | 核心基础设施 |
| 自进化 | Evolution Engine | 独立后台系统 |
| 模型适配与切换 | Model Profile Registry | 核心平台能力 |
| AI 漫剧 | Comic Studio Capability | 第一个复杂任务验证案例 |
| 自主编程 | Coding Capability | 后续能力包，不是第一版必做 |
| 自动发布 | Release Controller | 仅允许通过门禁的限定改进 |

这里有一个需要特别强调的调整：**工作流系统不应该只是进化系统的一个附属功能，它应该成为 EvoAgent 最重要的长期资产之一。**

因为提示词可以重写，模型可以更换，工具可以替换，但经过长期运行、验证、修复和积累的工作流，才真正代表系统已经学会如何稳定完成某一类任务。

同时，不能把所有成功都固化。临时任务、低频任务和无法稳定验收的任务，可以继续由动态规划处理。工作流应当在具有足够复用价值时才晋级。

模型 API、数据库、对象存储、Git、FFmpeg、Android 系统接口等，不必再各自成为新的顶层架构。它们是被上述各层使用的基础设施或外部能力。

### 为什么要分成这五层？

因为它们的变化速度和稳定性要求不同：

- 手机交互界面可以持续改善，但不能破坏任务状态。
- Agent Runtime 应尽量稳定，不能因为一个任务表现不好就自动修改安全机制。
- 工作流可以独立于核心代码升级。
- 评测系统应尽量独立验证候选版本，避免候选版本自行修改评测标准。
- 进化平台可以频繁实验，但它的实验结果不能直接影响稳定运行中的任务。

这正好对应你最初提出的要求：稳定的智能体长期服务，后台独立进化；更换模型时保留原来的适配成果，从新的分支继续优化。

## 四、EvoAgent 的核心运行逻辑应该是什么？

我建议把系统的完整闭环正式定义为：

**目标 → 执行策略选择 → 任务执行 → 结果验收 → 经验沉淀 → 问题分析 → 改进实验 → 版本发布。**

其中必须有三条不同的执行路径。

    <title size="md">路径 A：已有稳定工作流</title>
    用户目标匹配成功的工作流后，先检查适用条件，再直接调用指定版本。

    <text color="secondary" size="sm">目标是提高稳定性、速度和复用率，而不是每次重新规划。</text>
  </box>
  <box border radius="lg" padding={3} gap={1}>
    <title size="md">路径 B：已知能力，但没有稳定工作流</title>
    Agent 使用 ReAct 和受控工具完成任务，记录完整轨迹，验证结果，并判断是否值得提炼成候选工作流。

    <text color="secondary" size="sm">目标是积累新能力，而不是强制所有任务都固化。</text>
  </box>
  <box border radius="lg" padding={3} gap={1}>
    <title size="md">路径 C：工具或系统发生故障</title>
    进入诊断与恢复流程，区分模型判断错误、工具执行失败、环境变化、网络异常和验收失败。

    <text color="secondary" size="sm">目标是恢复安全运行，并生成有证据的问题记录。</text>
  </box>
</box>

这三条路径最终都要经过统一的结果验收和事件记录。

一个任务完成后，系统不能仅凭模型说“已完成”就将其判定为成功。应根据任务类型定义验收标准，例如：

- 手机操作：目标应用是否打开，目标状态是否出现。
- 视频制作：文件是否存在、能否播放、时长是否正确、音画是否符合要求。
- 编程：测试是否通过，功能是否满足验收条件。
- 文档整理：输出是否完整，格式和内容是否满足要求。

这会成为后续工作流固化和进化评估的共同基础。

## 五、工作流才是系统长期积累的核心资产

这里我建议把几个容易混淆的概念明确分开。

| 资产 | 它保存什么 | 示例 |
|---|---|---|
| Tool | 单一操作能力 | 调用 TTS、打开 Android 应用、执行 FFmpeg |
| Skill | 某类任务的知识和方法 | 分镜设计规则、字幕校验方法 |
| Workflow | 多个步骤的执行关系和条件 | 漫剧制作 DAG |
| Model Profile | 某个模型及任务类型的适配配置 | 模型、提示词、上下文预算和参数 |
| Evaluation Suite | 判断结果好坏的标准和测试集 | 镜头一致性回归集 |
| Run Trace | 某次实际执行的证据 | 工具调用、耗时、错误和验收结果 |
| Release | 已批准的版本组合 | Workflow v1.2 + Model Profile v3 |

它们不能相互替代。

例如，一条 AI 漫剧工作流可以使用同一套流程，但根据不同任务调用不同模型配置。更换视频模型后，工作流本身可能不需要修改，只需要重新验证视频生成节点的适配情况。

反过来，如果发现字幕处理顺序存在结构性问题，即使不更换模型，也可能需要升级工作流版本。

## 六、独立进化系统应该进化什么，又不能进化什么？

这部分必须重新定边界。否则，“无限进化”很容易变成系统不断修改自己，却没有可靠证据证明它变好了。

我建议按风险和可验证程度分级开放。

| 进化对象 | 允许的改进方式 | 初期自主程度 |
|---|---|---|
| 提示词与上下文策略 | 对比实验、回归评测、版本化发布 | 可自动测试，限定范围内可自动发布 |
| 工作流参数 | 调整重试、并发、预算和超时策略 | 低风险改进通过门禁后自动发布 |
| 工作流结构 | 增删节点、修改依赖和分支 | 必须运行独立回归与失败注入测试 |
| 工具适配器 | 优化调用、错误处理和超时恢复 | 先在隔离环境测试，严格审核后发布 |
| 模型适配 | 比较模型、提示词和上下文预算 | 建立新档案并独立评测，不覆盖旧档案 |
| Agent Runtime | 修改 ReAct、状态机或上下文内核 | 暂不自动发布 |
| 权限与安全机制 | 修改授权边界、发布门禁和安全策略 | 禁止自主放宽 |
| 评测规则 | 增加测试和更好的验收指标 | 可以提案，但不能为了让候选通过而删除失败测试 |

特别是工具故障，必须独立诊断。

假设智能体调用一个视频生成工具失败了，系统需要判断：

- 是模型生成了错误参数？
- 是工具适配器错误地构造了请求？
- 是供应商 API 改版？
- 是网络超时？
- 是额度不足？
- 还是工具成功返回了结果，但下游验收失败？

如果不区分这些原因，进化系统就可能错误地修改提示词，导致问题越来越复杂。

所以我建议把“工具健康检查”和“工具契约测试”作为独立子系统。工具升级或模型切换时，先验证工具本身，再验证 Agent 如何使用它。

## 七、模型更换时，怎样保留之前积累的能力？

你的原始要求是：某个模型适配稳定后要存档，未来更换模型时，从新分支继续迭代。

这应该被正式定义为 **Model Profile Registry + Compatibility Evaluation**，而不是简单记录一个模型名称。

每份模型适配档案应包含：

- 供应商、模型标识和可确认的模型版本。
- 系统提示词、任务提示词和上下文治理策略。
- 工具调用格式、结构化输出 Schema 和兼容性配置。
- 采样参数、超时、重试和 Token 预算。
- 对应的工作流版本与工具依赖。
- 测试集、评测结果、成本、延迟和失败类型。
- 创建时间、发布状态、哈希和回滚关系。

切换模型时，流程应该是：

<CodeBlock language="text" editable={false}>Stable Model Profile A
        |
        +---- Archive A
        |
        +---- Create Candidate Profile B
                         |
                         v
              Compatibility Evaluation
                         |
                         v
                Workflow Regression
                         |
                         v
                Cost / Latency / Quality
                         |
                 +-------+-------+
                 |               |
              Pass             Fail
                 |               |

          Promote B          Keep A Stable
          Preserve A         Record Failure</CodeBlock>

这里需要特别注意：**模型档案可以复用，但模型行为不能假定完全兼容。**

同一套提示词在两个模型上可能产生不同的工具调用、结构化输出和推理行为。因此，更换模型时要重新运行兼容性测试。旧档案应当保留，不要因为新模型通过一次测试，就删除原来的适配成果。

## 八、产品应该怎样分阶段交付？

我不建议同时开发 Android 操作、复杂内容制作、自主编程和自动进化。它们的复杂度都很高，过早并行会让你无法判断问题究竟出在哪一层。

更合理的路线是先建立一个完整的最小闭环，再逐步扩展能力。

## 十、怎么判断 EvoAgent 真的在进化？

这是产品层面最重要的指标设计。不能用“代码改了多少次”“工作流增加了多少条”或者“提示词优化了多少次”来证明系统在进化。

我建议以任务结果为中心，建立以下指标：

| 指标 | 衡量什么 |
|---|---|
| 任务成功率 | 是否真正交付满足要求的结果 |
| 首次成功率 | 是否无需返工就能完成 |
| 恢复成功率 | 发生错误后能否安全恢复 |
| 单任务成本 | 完成一个任务的平均费用 |
| 端到端耗时 | 从接收目标到交付结果的时间 |
| 工具故障率 | 失败有多少来自工具或外部服务 |
| 工作流复用率 | 有多少适用任务可以直接调用稳定流程 |
| 回归缺陷率 | 新版本是否破坏原本已经成功的能力 |
| 自动发布回滚率 | 自动晋级的改进有多少在发布后出现退化 |

这些指标要按任务类型分别统计。AI 漫剧、手机操作和软件开发的成功标准不同，不能用一个综合分数掩盖某一类任务的退化。

进化的真正含义是：在任务质量不降低、安全边界不放宽的前提下，让相同类型的任务越来越稳定、越来越高效，或者在相同成本下取得更好的结果。

## 十一、最终建议：重新设计，但只重构真正需要稳定的部分

我建议现在正式停止继续叠加功能，进入一次架构收敛阶段。

保留之前讨论中已经有价值的技术方向：ReAct、上下文治理、Harness、工具适配、运行日志、自动评测、Git 隔离、模型档案和 Android 执行端。

真正需要重新设计的是它们之间的关系：

- 把工作流从附属模块提升为核心能力平台。
- 把进化系统与日常执行内核彻底分离。
- 把模型、工具、工作流和评测集分别进行版本管理。
- 把结果验收与问题归因放在所有任务的统一闭环中。
- 把 Android 和 AI 漫剧放在可插拔能力层，而不是放进核心执行引擎。
- 把自动发布限制在有明确测试证据和回滚能力的范围内。

**我认为，EvoAgent 的第一版不应该以“做出一个能做所有事情的智能体”为目标，而应该以“做出一个能够可靠完成任务、沉淀工作流、并用证据改善自身的完整系统”为目标。**

前者很容易让项目陷入不断扩展功能的循环；后者会让每一个新功能都建立在已经验证过的基础设施之上。

下一步最有价值的交付物，不是继续写某个单独的能力模块，而是先形成一份正式的 **《EvoAgent 产品需求文档 PRD + 总体技术架构设计 TAD + V0.1 验收标准》**，将产品边界、模块职责、数据模型、核心接口、进化门禁和开发路线一次性统一。然后以这份基线为依据，进入可运行工程的实现阶段。
