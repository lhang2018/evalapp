## 一、项目当前阶段

EvoAgent 已经形成正式的总体架构与 PRD、实施路线与验收规范、核心接口与数据契约。既有设计确定了 Android 优先、八个逻辑服务、四个受保护控制器，以及 A—H 阶段的总体实施路线。<FileCite ref="turn15file1"/><FileCite ref="turn15file5"/><FileCite ref="turn15file3"/>

因此，后续工作不再以重新设计基础架构或重新安排初始开发为目标，而是聚焦两条工作线。

### 工作线 A：剩余专项设计

目标：完成原计划中的专项设计，进一步明确各专项的职责、接口、策略、边界、异常处理、评测与验收。

要求：
- 沿用现有编号、术语和架构基线。
- 已完成的专项不重复设计。
- 专项之间的依赖和冲突必须明确。
- 新专项不得随意改变共享内核、安全边界和已冻结的数据契约。
- 发现原设计存在问题时，先记录差异和影响，再提出有依据的修订方案。

### 工作线 B：面向最终用户的产品重设计

目标：从用户的实际需求出发，重新梳理产品定位、交互入口、任务体验、功能边界、主动帮助和长期使用方式。

要求：
- 以用户能够完成的任务组织产品，而不是以技术模块组织页面。
- 明确每项功能给用户带来的实际价值。
- 明确用户如何开始、执行、查看、纠正和结束任务。
- 明确产品功能与现有技术专项的对应关系。
- 不因产品交互调整而重复建设已经具备的底层能力。

两条工作线可以并行，但必须通过统一的需求和验收映射保持一致。

## 二、两条工作线的协同关系

| 维度 | 专项设计线 | 用户产品重设计线 |
|---|---|---|
| 核心问题 | 系统如何可靠地实现能力 | 用户如何使用能力并获得价值 |
| 主要产出 | 技术专项设计、接口与策略规范 | 产品需求、用户流程、页面与交互规则 |
| 评价标准 | 完整性、一致性、安全性、可验证性 | 可理解性、任务完成率、效率、信任与满意度 |
| 依赖关系 | 受总体架构和既有契约约束 | 依赖已确认的能力边界，同时可以提出新需求 |
| 变更方式 | 通过专项差异分析与兼容性评审 | 通过用户价值、影响范围和产品验收评审 |
| 最终交付 | 可实施、可验证的技术设计 | 用户能理解、能操作、能获得真实成果的产品 |

**关键原则：产品需求可以推动技术专项完善，但不能仅凭一个新的交互想法就推翻已经完成的基础架构。**

如果产品需要的能力已经存在，就复用；如果能力只完成了设计，就明确后续实现要求；如果确实缺少必要能力，才新增专项或修订已有专项。

## 三、用户功能与技术专项映射矩阵

后续所有用户侧功能都应当关联对应的技术能力族。

| 用户侧功能 | 对应的技术能力族 | 必须明确的验收结果 |
|---|---|---|
| 文字与语音入口 | 交互、意图识别、输入适配 | 用户输入能够形成正确的任务目标 |
| 自然语言完成任务 | 任务契约、规划、执行引擎 | 任务能够按照约束执行并交付 |
| 任务进度与控制 | 状态机、事件、检查点、取消恢复 | 页面状态与实际执行一致 |
| 自动选择专家 | 路由、能力注册、依赖图 | 能选择适用能力，并在不确定时回退 |
| 复杂任务执行 | Planner、ReAct、DAG Runtime | 任务步骤可调度、可恢复、可验收 |
| 文件与成果交付 | 产物管理、验收器、结果索引 | 实际成果存在且符合要求 |
| 长期项目与记忆 | 记忆命名空间、上下文治理 | 重要信息得到保留，过时信息可纠正 |
| 重复任务复用 | 工作流资产、版本与兼容性 | 工作流可重复运行且通过评测 |
| 主动帮助 | 目标治理、机会评估、资源调度 | 建议有价值、可关闭且不干扰主任务 |
| 后台持续进化 | 诊断、独立评测、发布门禁 | 改进有证据，退化可以阻断和回滚 |
| Android 离线使用 | 本地状态、事件队列、同步和恢复 | 断网与重连后状态可恢复、事件不重复 |
| 用户信任与安全 | 权限、审批、副作用账本、审计 | 未授权动作被阻止，关键操作可追溯 |

这张矩阵是两条工作线之间的总索引，不替代各专项的详细设计。

## 四、用户产品重设计已经形成的阶段成果

此前的连续设计已经覆盖以下内容：

1. 产品定位与用户价值；
2. 核心用户任务与任务验收矩阵；
3. 产品能力覆盖与缺口台账；
4. 首发产品的信息架构与完整用户旅程；
5. 首发范围冻结与发布门禁。

接下来不再重复编写这些文档的概念性内容，而是把它们整合为一份统一的产品需求体系，并继续补齐具体交互规则、功能细节和验收关联。

需要特别保留的产品约束：

- 核心任务执行质量、效率和稳定性优先。
- 主动智能只在有价值且合适的时机发挥作用。
- 后台进化不得破坏当前稳定执行。
- 用户可以控制权限、主动程度和任务停止。
- 产品必须清楚区分已实现、已验证、依赖外部服务和未开放能力。

## 五、每个剩余专项的统一设计标准

为避免剩余专项之间出现重复、冲突或无法实施的问题，后续每份专项设计都应当具备以下内容。

### 5.1 目标与边界

- 专项要解决什么问题；
- 为什么现有能力不足以解决；
- 影响哪些用户功能；
- 哪些职责属于其他专项；
- 哪些行为明确禁止。

### 5.2 架构与数据

- 模块职责；
- 输入与输出；
- 依赖的接口和数据契约；
- 状态转换；
- 关键事件；
- 版本和兼容性要求。

### 5.3 执行与异常

- 正常执行路径；
- 超时、错误和中断；
- 重试与恢复条件；
- 权限和资源边界；
- 停止条件；
- 与其他模块交互时的失败隔离。

### 5.4 评测与验收

- 正常场景测试；
- 边界和异常场景测试；
- 回归测试；
- 安全与兼容性测试；
- 量化指标；
- 通过与拒绝条件；
- 发布、降级和回滚要求。

### 5.5 产品关联

每份专项必须说明：
- 它支持哪些用户功能；
- 用户能够感受到什么改善；
- 对用户界面有哪些要求；
- 哪些失败需要向用户解释；
- 如何证明该专项带来了预期价值。

没有明确用户价值的技术专项，仍可因安全、稳定性或维护需要存在，但必须说明其工程必要性。

## 六、后续推进顺序

### 第一阶段：统一两条工作线的总索引

建立产品功能、专项设计、接口契约和验收用例之间的关联。

目的不是重新审核所有代码，而是确保已有设计可追踪，后续新增内容不重复、不冲突。

### 第二阶段：继续用户侧产品重设计

重点完成统一产品需求体系，明确各项功能的用户操作、系统行为、状态展示、权限边界和验收条件。

### 第三阶段：沿原有编号继续剩余专项设计

按既定清单逐项推进，每完成一份就更新依赖和关联关系。

不重新从基础架构开始，也不重新编号已经完成的专项。

### 第四阶段：处理专项与产品需求之间的差异

当产品需求与既有专项出现不一致时，先分类：

- 产品层表达问题：修改产品交互；
- 既有能力可复用：补齐映射；
- 设计细节缺失：完善专项；
- 接口契约冲突：提出兼容性修订；
- 基础架构确有缺陷：形成明确的变更理由和影响分析。

### 第五阶段：形成完整、可交付的设计体系

最终形成相互关联的产品 PRD、专项设计集、接口与数据契约、验收矩阵和发布规范。

它们共同构成完整的项目基线，而不是一批彼此独立的文档。

## 七、项目进度的统一记录方式

每轮工作只需明确记录：

| 项目 | 记录内容 |
|---|---|
| 本轮推进内容 | 产品功能或专项编号 |
| 完成成果 | 新增或修订的具体设计 |
| 与已有设计的关系 | 复用、补充、修订或替代 |
| 依赖和影响 | 关联模块、接口及其他专项 |
| 未解决问题 | 仍需要决策或证据的问题 |
| 下一步 | 原有序列中的下一项工作 |

这样既能持续推进大量专项设计，又能避免反复解释项目背景和重复完成已经交付的工作。

## 八、执行约束

从现在开始：

- 不重新启动已经完成的基础架构设计。
- 不把代码上传或代码审核作为设计工作的前置条件。
- 不反复重写已经形成的产品定位和首发原则。
- 不把新增文档数量作为唯一进度指标。
- 不擅自把产品设计目标当作已实现功能。
- 不让专项设计脱离用户价值、系统边界和验收要求。
- 不因产品重设计而无依据地扩大核心系统的职责。

**最终目标：在保留既有基础设计与开发成果的前提下，完成剩余专项设计，并把它们整合成一套面向真实用户、具有明确功能和可验证价值的 EvoAgent 产品体系。**</WritingBlock>
