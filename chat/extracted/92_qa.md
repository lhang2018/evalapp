# EvoAgent 第四十专项：主动感知、信息获取与不确定性治理

本轮解决 EvoAgent 从“根据已有信息执行任务”走向“主动发现信息缺口、寻找证据、判断何时足以行动”的关键问题。

前面已经建立了多个基础模块：

- Router：判断由哪个专家处理任务；
- Planner、ReAct 与 DAG：决定任务如何分解和执行；
- MEEG、CLEK：管理记忆、经验和长期知识；
- ACMO：决定当前模型调用需要哪些上下文；
- ARCBG：管理推理深度、模型选择和资源预算；
- RCAE、EQEAG、SELCIA：分析失败、独立评测并管理改进。

现在需要把这些能力连接起来。

例如，用户说：

“帮我找出这个项目为什么运行越来越慢，并修复它。”

EvoAgent 不能直接假设问题出在数据库，也不能一开始就读取所有文件或调用所有专家。它需要判断当前证据是否充分、下一步观察什么最有价值、何时开始修复，以及如何证明问题真正得到解决。

本专项建议定义为：

**Active Perception, Information Acquisition & Uncertainty Governance，简称 APIUG。**

它负责信息缺口识别、主动观察、信息获取策略、证据可信度、行动门槛和不确定性治理。

## 一、第一性原理：不知道，并不可怕；不知道自己不知道，才危险

一个可靠的智能体必须区分四种状态：


    <title size="md">1. 已知且有证据</title>
    例如，性能分析报告显示某个函数占用了 65% 的执行时间，且报告对应当前代码版本。



    <title size="md">2. 已知但证据不足</title>
    例如，模型怀疑数据库查询过慢，但尚未获取查询计划或运行指标。



    <title size="md">3. 明确存在信息缺口</title>
    例如，不知道性能下降从哪个版本开始，也没有历史基线。



    <title size="md">4. 当前无法确认</title>
    例如，性能分析工具无法运行、远程设备离线，或现有证据相互矛盾。


这四种状态对应不同的行动。

- 已知且有证据：可以进入下一步决策，但仍需满足任务的验收要求。
- 已知但证据不足：优先获取能够验证或反驳该判断的信息。
- 明确存在信息缺口：规划有针对性的信息获取动作。
- 当前无法确认：缩小任务范围、请求必要信息、等待恢复或明确报告限制。

**APIUG 的目标不是让系统永远消除不确定性，而是让它知道哪些不确定性可以接受，哪些必须先解决。**

# 二、建立统一的不确定性模型

建议不要只让模型输出一个“我有 80% 把握”的数字。

这种主观置信度容易受表达方式影响，也未必经过校准。更可靠的做法是记录不确定性的具体来源、影响和可验证条件。

## 2.1 六种不确定性

| 类型 | 典型问题 | 首选处理方向 |
|---|---|---|
| 目标不确定性 | 用户究竟想要什么结果？ | 澄清需求、确认验收标准 |
| 事实不确定性 | 实际发生了什么？ | 查询文件、日志、权威来源 |
| 因果不确定性 | 为什么出现这个问题？ | 对照实验、诊断、反证 |
| 能力不确定性 | 当前模型、专家或工具能否完成？ | 能力评测、最小验证任务 |
| 环境不确定性 | 设备、服务、依赖是否可用？ | 环境检查、状态探测 |
| 结果不确定性 | 当前产物是否正确、完整？ | 测试、独立验收、运行验证 |

这六类问题不能全部通过增加模型推理来解决。

如果目标不明确，继续推理可能只是猜测用户意图；如果缺少事实，工具调用可能更有价值；如果因果关系不清楚，就需要设计能够区分不同原因的实验。

## 2.2 将不确定性与任务状态关联

建议建立 `UncertaintyRecord`，记录：

- `uncertainty_id`：唯一标识；
- `task_id`：关联任务；
- `uncertainty_type`：不确定性类别；
- `question`：尚未解决的具体问题；
- `current_hypotheses`：候选解释；
- `supporting_evidence`：支持证据；
- `contradicting_evidence`：反证；
- `impact_if_wrong`：判断错误的影响；
- `resolution_options`：可能的信息获取方式；
- `resolution_status`：未解决、调查中、已解决、可接受或无法确认。

这个对象用于表达“系统还需要知道什么”，而不是替代任务规划、运行日志或长期记忆。

例如，代码专家可以记录“数据库查询是否为主要瓶颈”这一不确定性，并关联性能日志、查询计划和后续实验。其他专家无需重新猜测问题，可以直接读取当前状态与证据。

# 三、主动感知：智能体下一步应该观察什么？

传统工作流往往预先规定步骤：先读取文件，再运行测试，最后生成报告。

主动感知则要求 EvoAgent 根据当前观察结果，动态决定下一步获取什么信息。

例如，性能问题可能有多个候选原因：

- 数据库查询变慢；
- CPU 密集计算增加；
- 缓存命中率下降；
- 网络请求阻塞；
- 最近的代码修改引入退化。

此时，最合理的下一步不一定是继续阅读代码，而可能是获取一次性能采样，因为它能够同时区分多个候选原因。

## 3.1 建立观察动作目录

建议将信息获取能力统一注册为 `ObservationAction`。

| 动作类型 | 示例 | 主要作用 |
|---|---|---|
| 直接读取 | 文件、配置、历史记录 | 获取已有事实 |
| 状态探测 | 服务健康检查、设备状态 | 确认当前环境 |
| 结构化分析 | AST 分析、依赖图、数据库查询计划 | 获取结构性证据 |
| 运行测量 | 性能分析、基准测试、资源监控 | 观察实际行为 |
| 外部检索 | 官方文档、API 规范、版本信息 | 获取外部事实 |
| 受控实验 | 对比不同参数、执行隔离测试 | 区分候选原因 |
| 用户澄清 | 询问目标、范围或偏好 | 消除无法从外部获取的歧义 |
| 独立验证 | 测试、产物检查、交叉核验 | 判断结果是否可信 |

每种观察动作都应定义输入、输出、成本、权限、执行风险、超时策略和可验证程度。

这样，模型可以选择观察方式，但不需要自行发明工具接口，也不能绕过工具运行时的权限控制。

## 3.2 根据观察结果动态分支

例如：


    **发现性能退化**

    现有证据不足以确定根因。





    **获取性能采样与历史基线**





    <grid-item>

        CPU 计算占主导
        分析热点函数与调用路径。

    </grid-item>
    <grid-item>

        数据库等待占主导
        分析查询计划、锁与等待时间。

    </grid-item>





    **验证根因假设，再决定是否修改代码**
    如果证据仍不充分，则选择下一项能够区分候选原因的观察或实验。


这里的分支只是示例，不意味着所有性能问题都能被一次采样准确定位。

关键在于：任务 DAG 可以保留总体目标、硬约束和验收节点，而内部观察步骤可以根据真实结果动态生成或调整。

**DAG 负责依赖与状态约束，主动感知负责决定下一步需要获取什么信息。二者不是替代关系。**

# 四、信息价值评估：哪一次观察最值得执行？

主动感知不能演变成无限调查。系统需要判断下一项观察是否值得花费资源。

建议引入“预期信息价值”，将候选观察动作按其决策价值进行比较。

## 4.1 评估四个方面

对于一个候选观察动作，至少评估：

1. **区分能力：** 它能否区分当前的重要假设？
2. **决策影响：** 结果是否可能改变下一步行动？
3. **可靠程度：** 该动作能否产生可信、可复现的证据？
4. **执行成本与风险：** 需要多少时间、Token、费用和副作用？

可以用简化的价值模型：

\[
VOI(a)=
\mathbb{E}[\text{决策损失减少}\mid a]
-
\text{成本}(a)
-
\text{风险}(a)
\]

这里的 \(VOI\) 表示信息价值。公式用于指导候选动作排序，不代表系统总能精确计算这些数值。

例如：

- 读取现有日志，成本低且可能快速定位问题；
- 运行完整压力测试，可能产生更强证据，但耗时更长；
- 让三个专家重复阅读相同日志，可能成本很高，却几乎不增加信息。

在其他条件相近时，应优先选择能够以较低成本减少关键不确定性的动作。

## 4.2 观察结果可能改变决策时，信息价值才更高

假设系统已经确认某个函数占用了绝大部分执行时间。

如果无论查询数据库还是检查网络，都会继续优化这个函数，那么再做这些观察的价值可能很低。

反之，如果不同观察结果会导致完全不同的修复方案，就值得进一步调查。

这能防止系统陷入“为了更确定而不断收集信息”的循环。

## 4.3 风险约束不能被平均信息价值抵消

某项检查可能成本较高，但如果它是高风险操作的必要验收步骤，就不能因为估算信息收益低而跳过。

因此，APIUG 的动作选择必须同时满足：

- 预期价值约束；
- 任务硬约束；
- 安全与授权要求；
- 时间与资源预算。

信息价值用于选择可选动作，不能取代必要的安全检查。

# 五、证据治理：信息获取之后，如何判断它是否可信？

主动获取的信息并不天然可靠。

文件可能过期，日志可能对应旧版本，外部资料可能已经失效，模型生成的解释也可能存在错误。

建议建立统一的 `EvidenceRecord`，让系统在使用信息时能够回答：它来自哪里、支持什么结论、适用于哪个版本，以及是否有反证。

## 5.1 证据的六个关键属性

| 属性 | 含义 |
|---|---|
| 来源 | 文件、工具、用户、外部文档或模型假设 |
| 时间与版本 | 证据何时产生，对应哪个系统状态 |
| 直接性 | 是实际测量，还是间接推断 |
| 可复现性 | 是否能够重新获取或验证 |
| 适用范围 | 能支持哪些任务、环境与结论 |
| 冲突情况 | 是否存在相反证据或尚未解释的差异 |

例如，“服务响应变慢”可以由用户报告提出，也可以由性能监控证实。

用户报告足以触发调查，但不能单独证明具体根因。性能监控则可能支持延迟确实增加，但仍未必能够证明是哪个组件导致的。

## 5.2 区分观察事实与根因假设

建议在所有诊断与上下文记录中严格区分：

- **Observation：** 实际观察到的现象；
- **Evidence：** 支持某个判断的证据；
- **Hypothesis：** 对原因的解释；
- **Conclusion：** 在当前证据下能够支持的结论；
- **Unknown：** 仍未解决的问题。

例如：

- 观察：请求耗时从 200 ms 增加到 900 ms；
- 证据：性能采样显示数据库等待时间明显增加；
- 假设：某次索引变更导致查询计划退化；
- 验证：对比变更前后的查询计划；
- 结论：只有在证据足够时，才能把索引变更认定为主要原因。

这样可以避免模型把“可能是数据库问题”在多轮摘要之后逐渐变成“数据库问题已经确认”。

## 5.3 冲突证据不能简单取平均

如果日志显示服务正常，但用户反馈操作失败，系统不应直接认为双方各有一半正确。

更合理的做法是检查：

- 是否观察的是不同时间段；
- 是否来自不同设备或实例；
- 是否存在局部故障；
- 是否有日志采集缺失；
- 两者是否衡量了不同的指标。

很多证据冲突最终可以通过明确时间、对象和测量范围来解决，而不是强制选择一个来源。

# 六、什么时候应该询问用户，而不是继续猜测？

这是主动感知与通用智能体交互之间的关键接口。

EvoAgent 不应该遇到任何未知信息都询问用户，否则会让用户承担本来可以自动完成的调查工作。

也不应该为了保持自动化，就在关键需求不明确时擅自做出不可逆的决定。

建议将信息缺口分为三类。


    <title size="md">A 类：可以自行获取</title>
    例如项目路径、工具版本、文件结构、运行日志。优先使用已有权限的工具获取，不必询问用户。



    <title size="md">B 类：可以采用可逆的默认值</title>
    例如报告的默认排版、临时文件命名、低风险任务的展示方式。使用合理默认值，并在必要时说明。



    <title size="md">C 类：必须澄清或授权</title>
    例如相互冲突的硬性要求、无法推断的关键业务目标、未经授权的高风险操作。停止相关决策，提出具体问题或请求授权。


## 6.1 询问问题也需要价值判断

一个好的澄清问题应当：

- 直接针对会改变执行方案的信息；
- 尽可能一次解决关键歧义；
- 提供清晰、容易回答的选项；
- 避免询问系统可以自行可靠获取的信息；
- 不重复询问用户已经明确提供的条件。

例如，“你希望优化什么？”通常过于宽泛。

如果现有证据显示主要瓶颈可能涉及响应延迟或内存占用，系统可以先进行低成本测量，再询问用户是否有必须满足的延迟目标或内存上限。

这样既降低了用户负担，也提高了决策质量。

## 6.2 用户沉默不等于授权

如果任务涉及删除数据、覆盖文件、对外发送信息或其他需要明确授权的操作，系统不能把用户未回复理解为同意。

可以继续执行不依赖该授权的安全子任务，但必须将需要授权的步骤保留为阻塞节点。

这与之前的 SBAAG 安全授权机制保持一致。

# 七、与 Planner、ReAct 和 DAG 的关系：固定骨架，动态观察

主动感知不能成为一个独立于任务执行系统的平行智能体，否则容易出现多个模块各自规划、重复调用工具的问题。

建议明确以下职责：

| 模块 | 职责 |
|---|---|
| Planner | 生成任务计划、目标和依赖结构 |
| DAG 执行器 | 管理节点状态、依赖、并行和恢复 |
| ReAct 控制器 | 在局部执行循环中根据观察调整行动 |
| APIUG | 识别信息缺口，选择高价值观察和验证动作 |
| ACMO | 将必要的观察结果组织进当前模型上下文 |
| ARCBG | 为信息获取和后续推理分配资源 |
| RCAE | 分析失败原因和证据链 |
| EQEAG | 验证新的观察策略是否提高了任务表现 |

一个合理的执行过程是：

1. Planner 确定总体目标与必要验收条件；
2. DAG 执行器启动当前可执行节点；
3. APIUG 判断节点所需的信息是否充分；
4. 若不足，选择合适的观察动作；
5. ACMO 将新证据组织为下一次调用的上下文；
6. ReAct 根据观察决定继续、切换工具或请求重新规划；
7. 节点完成后，由相应的验收机制检查结果；
8. 运行证据进入 ODERI，必要时由 RCAE 分析异常。

**APIUG 不应该重新发明一套任务规划器。它应当为现有规划与执行体系提供更好的信息决策能力。**

# 八、主动感知必须有边界：避免无限探索

主动感知最容易出现的问题，是系统不断发现新的未知信息，最终永远无法完成任务。

例如，调查一个程序的性能时，可以不断深入操作系统、数据库、网络、编译器乃至硬件层。技术上总能找到更多值得研究的问题，但用户未必需要这些调查。

因此，APIUG 需要明确的停止条件。

## 8.1 六种合理的停止状态

- `SUFFICIENT`：现有证据已经足以支持当前决策；
- `RESOLVED`：目标不确定性已得到解决；
- `ACCEPTABLE`：仍有不确定性，但其风险在任务允许范围内；
- `BUDGET_EXHAUSTED`：达到预算上限；
- `BLOCKED`：缺少必要授权、输入或外部条件；
- `UNRESOLVED`：经过合理调查仍无法确认。

这些状态应当与任务执行状态分开管理。

例如，一个性能根因可以是 `UNRESOLVED`，但任务仍然可以交付一份已验证的诊断报告。反过来，根因已经找到，也不代表代码修复和回归测试已经完成。

## 8.2 建立观察次数与重复动作限制

建议按任务类别配置：

- 单次观察的超时限制；
- 相同观察动作的重复次数；
- 连续无新证据的停止门槛；
- 调查阶段预算；
- 最大依赖展开深度；
- 必须升级到人工判断的条件。

这些限制不是为了让系统机械地停止，而是防止它重复进行没有新增价值的调查。

如果连续几轮获取的证据没有改变假设排序或后续决策，系统就应该重新评估信息获取策略。

## 8.3 不确定性可以被接受，但必须记录

不是所有未知信息都值得消除。

例如，一份研究报告可以明确说明某项结论尚未被验证，而不必为了追求绝对确定而无限搜索。

但是，对于影响安全、数据完整性或关键验收结果的不确定性，系统可能必须继续验证或暂停执行。

因此，是否允许带着不确定性继续，应该由任务风险和验收规则决定，而不是由模型主观判断。

# 九、让主动感知本身也能持续进化

APIUG 不仅要执行信息获取策略，还需要判断这些策略是否有效。

例如，系统可能发现：

- 先检查项目状态比直接搜索代码更快；
- 某类故障通过日志与性能采样即可定位，不需要多个专家；
- 某个外部资料源经常过期；
- 某种诊断流程会反复收集相同证据；
- 某些澄清问题可以由低风险的自动探测替代。

这些发现可以成为改进候选，但不能直接变成新的全局规则。

## 9.1 建立主动感知评测指标

建议至少评估以下维度：

| 指标 | 评价什么 |
|---|---|
| 信息缺口识别率 | 是否识别出会影响任务决策的关键未知项 |
| 观察动作有效率 | 执行的观察是否产生新的、可用的信息 |
| 关键假设区分能力 | 观察是否能够排除或支持候选原因 |
| 证据可靠性 | 获取的信息是否准确、适用且可追溯 |
| 过度调查率 | 是否收集了大量不会改变决策的信息 |
| 用户澄清效率 | 是否以较少问题解决关键歧义 |
| 诊断返工率 | 是否因过早下结论而重复调查 |
| 信息获取成本 | 为解决关键未知项消耗了多少时间、费用和资源 |

不能只用“调查次数减少”作为优化目标，因为少调查可能意味着漏掉关键证据。

同样，不能只用“信息缺口识别率提高”作为目标，因为系统可能把大量无关未知项都标记出来。

## 9.2 用对照实验验证新的观察策略

例如，针对同类性能故障，可以比较：

- 稳定策略：按照现有诊断流程获取信息；
- 候选策略：先选择预期信息价值最高的观察动作；
- 验收：比较根因识别质量、修复成功率、调查成本和错误结论率。

测试时需要尽量控制任务难度、工具版本和验收规则。

对于复杂问题，还应检查策略是否在某些任务类别中退化，不能仅根据平均调查时间缩短就批准发布。

这与 SELCIA 的候选评测和发布治理机制一致。

# 十一、下一专项：长期任务自治、执行恢复与跨会话连续性

到这里，我们已经分别设计了任务规划、专家能力、长期知识、上下文、资源预算和主动感知。

接下来需要研究一个把它们真正连接起来的问题：

**当一个任务持续数小时、数天甚至更久，中间发生应用关闭、设备重启、网络断开、工具失败或用户切换任务时，EvoAgent 如何准确恢复，而不是从头开始或错误地重复执行？**

这对于你选择的个人电脑、Android 手机和微型 Linux 主机部署方向尤其重要。

例如，AI 漫剧制作任务可能已经完成剧本、角色设定和部分镜头生成，但随后云端服务断开。如果系统只保存聊天记录，恢复后就可能重新生成已完成的镜头、重复扣费，或者把旧版分镜与新版素材混合。

下一专项建议定义为：

**Long-Horizon Task Autonomy & Recovery，简称 LTAR。**

重点研究：

1. 如何把长期任务的权威状态持久化；
2. 如何区分任务状态、模型上下文、记忆和执行日志；
3. 如何实现检查点、断点恢复和跨会话继续执行；
4. 如何处理任务暂停、取消、超时和用户中断；
5. 如何防止恢复时重复执行有副作用的操作；
6. 如何管理部分成功、部分失败和结果未知的节点；
7. 如何在工具或模型版本变化后判断原任务能否继续；
8. 如何恢复 DAG、ReAct 循环与多专家协作的中间状态；
9. 如何在 Android、本地电脑和微型 Linux 主机之间处理设备能力差异；
10. 如何让离线任务安全排队，并在连接恢复后继续；
11. 如何验证恢复后的任务状态与实际文件、工具和外部服务一致；
12. 如何在任务恢复后继续使用正确的记忆、上下文和资源预算。

本专项的核心原则是：

**恢复任务时，优先恢复可验证的执行状态，而不是仅凭历史聊天重新猜测发生了什么。**

完成 LTAR 后，EvoAgent 的长任务执行、异常恢复和跨会话连续性就会有更明确的架构基础。
