## 二、智能体自身的能力层面

这一层关注智能体本身由什么组成，以及这些组成部分是否能够被独立改进。

| 设计维度 | 已考虑的细节 | 设计重点 |
|---|---|---|
| 意图理解 | 意图分类、目标解析、约束提取、完成条件识别 | 不把用户表面指令直接当成完整任务规格 |
| 推理与决策 | 大语言模型调用、提示词、ReAct、Planning、重新规划 | 区分通用推理能力和特定任务策略 |
| 上下文治理 | 历史摘要、信息优先级、Token 预算、关键事实保留 | 防止上下文丢失、污染和无效膨胀 |
| 记忆系统 | 工作、情景、语义、程序、偏好及失败经验记忆 | 管理写入、检索、更新、冲突、过期与遗忘 |
| 工具系统 | 工具注册、调用契约、参数构造、健康检查、错误分类 | 区分 Agent 不会使用工具和工具自身存在故障 |
| Harness | 状态机、超时、重试、幂等、检查点、取消、权限控制 | 把执行可靠性从模型自由发挥中分离出来 |
| 技能系统 | 可复用知识、工具使用方法、任务技能和能力包 | 形成可以独立版本化的任务能力 |
| 工作流系统 | DAG、依赖、条件分支、并行、恢复、版本发布 | 把成功任务转化为可重复执行的稳定流程 |
| 结果验证 | 工具结果检查、最终交付验收、质量判断 | 不能仅凭模型宣称完成就认定成功 |
| 模型适配 | 模型档案、提示词组合、参数、工具调用兼容性 | 切换模型时保留旧配置并重新评测 |

这里最重要的架构共识，是不能把上述能力混成一个不可拆解的“智能体大脑”。

例如，记忆负责保存和检索信息，上下文治理负责选择当前任务需要的信息，Planning 负责决定如何完成任务，Harness 负责约束执行，结果验证负责判断任务是否真的完成。

它们需要协同，但每个模块应该有明确职责、输入输出和评测方法。

# 三、进化机制：智能体如何真正改进自己？

这是 EvoAgent 区别于普通 Agent 的核心，也是我们目前讨论最深入的部分。

  <title size="lg">已考虑的进化闭环</title>

    **执行任务**
    获取真实运行结果



    **观察与记录**
    轨迹、错误、工具结果、记忆使用、耗时、成本、验收证据



    **诊断与归因**
    判断问题属于任务、场景、子能力还是通用机制



    **生成改进假设**
    选择最小有效修改范围



    **隔离实验与评测**
    比较新旧版本，测试目标能力和受影响的其他能力



    **发布、拒绝或回滚**
    只有证据充分、满足门禁的改进才能进入稳定版本


我们已经考虑了以下关键问题：

1. **优化对象不止提示词。** 还包括 Harness、记忆、上下文、ReAct、Planning、工具路由、工作流、结果验证和模型适配。
2. **局部问题不等于通用能力缺陷。** 要判断错误的作用范围，优先修复最小有效范围。
3. **诊断与执行分离。** 执行智能体可以提供问题线索，但不能单凭自己的判断认定根因。
4. **评测与发布分离。** 候选版本不能自行修改评测规则或批准自己发布。
5. **通用能力需要保护。** 改进某项子能力时，要测试相关能力是否退化。
6. **进化允许失败。** 证据不足、改进无效或回归风险过高时，保留原版本。
7. **进化本身也有成本。** 实验、回归测试、多模型比较不能无限制运行。

## 四、问题归因与能力边界

这是你特别强调、也必须落实到系统设计里的一个方面。

我们已经提出五层问题范围：

| 层级 | 问题范围 | 示例 |
|---|---|---|
| L1 | 单次执行错误 | 一行代码写错、某个参数拼写错误 |
| L2 | 特定场景或环境 | 某个 Android 版本、某个框架版本不兼容 |
| L3 | 领域子能力 | Python 异步编程能力反复出现缺陷 |
| L4 | 通用能力 | 不同领域中反复遗漏用户明确约束 |
| L5 | 共享基础机制 | 上下文压缩反复删除关键约束，影响多个领域 |

同时考虑了四级证据：

- E0：单次观察。
- E1：能够重复复现。
- E2：多个独立案例呈现同类问题。
- E3：跨场景证据支持存在共同原因。

这是一套问题分类和证据框架，不是自动判定真相的算法。系统仍然需要结合因果假设、对照实验和实际测试。

尤其是编程能力，我们已经明确：某一种写法错误，不意味着整个编程能力失效；某个语言或框架的问题，也不应直接触发全局提示词改写。

## 五、记忆、学习和经验积累

这部分我们也已经从“保存历史记录”扩展到完整的记忆生命周期设计。

| 方面 | 已考虑的设计 |
|---|---|
| 记忆分类 | 工作记忆、情景记忆、语义记忆、程序记忆、用户偏好、失败经验 |
| 记忆写入 | 识别哪些信息值得保存，区分事实、推测与临时事件 |
| 记忆检索 | 根据任务选择相关信息，而不是加载全部历史 |
| 记忆更新 | 处理新旧冲突、过期事实和版本变化 |
| 记忆遗忘 | 降权、淘汰或标记失效信息，避免长期污染 |
| 记忆评测 | 准确性、召回质量、实际使用收益、污染率 |
| 经验提炼 | 将已验证经验转化为技能、工作流、工具知识或回归案例 |

我们也区分了三个容易混淆的概念：

- **记忆：** 保存什么。
- **上下文治理：** 当前任务使用什么。
- **学习与进化：** 根据证据改变什么。

但具体的记忆数据结构、检索算法、冲突处理策略、保留期限和遗忘规则，仍然需要进入详细设计阶段。

# 六、能力与成本联合优化

你提出了另一个非常重要的要求：不能为了省钱而牺牲真正重要的能力，也不能因为追求更好的表现而让成本无限增长。

我们已经考虑了两部分。

### 6.1 任务执行成本

- 根据任务复杂度、风险和不确定性选择执行强度。
- 简单任务使用轻量路径，复杂任务按需启用更深入的规划、验证和诊断。
- 评估额外模型调用是否带来值得的质量提升。
- 控制单次调用、单任务、每日或每月的预算。
- 将模型、工具、视频生成、存储、网络和其他服务费用纳入总成本。

### 6.2 自进化成本

- 使用低成本测试先筛选候选版本。
- 对有潜力的候选运行更完整的回归测试。
- 将更昂贵的评测用于高风险或高价值改进。
- 对实验设置预算、并发、时限和终止条件。
- 不允许进化系统自行突破硬性资源上限。

我们也明确了：能力完整不等于每次调用所有能力；成本优化不等于一味选择最便宜的模型。

不过，具体的成本分配算法、任务风险定价、收益预测、预算预留和资源竞争策略，还没有最终定型。

后续应当建立按任务类型、能力类别、模型版本和环境条件划分的评测集，并为关键指标设置最低门槛。

## 十一、我认为接下来最重要的工作

现在不宜继续无限增加模块名称，而应该将已有设计收敛成一个统一的、可执行的架构规范。

我建议按下面的顺序推进：

1. **建立完整的能力地图。** 明确通用能力、领域能力、任务能力和具体执行案例之间的关系。
2. **建立统一的运行数据模型。** 让任务、记忆、工具调用、工作流、模型配置、错误和评测结果能够关联追踪。
3. **建立问题归因和影响范围模型。** 让系统判断问题应该归属于单次执行、特定环境、子能力还是共享机制。
4. **建立能力—成本联合优化机制。** 明确预算、资源分配、边际收益判断和停止条件。
5. **建立独立进化与发布体系。** 通过隔离实验、分层回归、兼容性测试和回滚保护稳定版。
6. **实现最小闭环并用真实任务验证。** 先证明系统能发现问题、提出合理改进、验证改进效果，再逐步扩大自主程度。

我的最终判断是：**我们已经充分讨论了 EvoAgent 的主要设计方向，但还没有完成所有工程细节的定型。** 接下来最重要的不是继续堆叠功能，而是把各个维度之间的依赖、数据流、控制流和验证机制真正统一起来。

尤其要防止三个问题：局部错误引发全局改动、进化模块无法证明自己的改进有效、能力提升导致成本无限膨胀。

只要这三个问题被纳入核心架构，并且每个子系统都能独立观测、评测、版本化和受控升级，EvoAgent 才具备逐步实现真正自进化的工程基础。
