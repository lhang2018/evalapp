#95 的设计重点不是让智能体失败后更努力地重试，而是让它建立一套独立、可验证的故障诊断与修复机制。

这里必须区分三个角色：

- **执行器：** 负责完成任务，并产生真实的运行证据。
- **诊断器：** 负责判断发生了什么、可能为什么发生，以及哪些解释有证据支持。
- **修复控制器：** 负责判断是否值得修复、允许怎样修复，以及如何验证修复没有引入新问题。

这三个角色不能因为使用了同一个模型，就被当成同一个可信来源。执行器声称“工具出错”，不等于工具真的出错；诊断器认为“修改提示词就能解决”，也不等于根因已经找到。

因此，EvoAgent 应建立一条独立的证据链：**先保存事实，再提出根因假设，随后验证假设，最后才允许实施修复。** 对于低风险、可逆且有充分证据的故障，可以自动恢复；涉及核心内核、权限、安全策略或高风险外部操作的修复，则必须经过更严格的门禁。

EvoAgent 的现有正式数据契约已经提供了实施基础：运行事件通过 `task_id`、`run_id` 和 `runtime_manifest_id` 关联任务、执行尝试和实际运行版本；错误对象包含 `error_code`、`correlation_id`、`related_event_id` 和 `safe_to_repeat` 等字段；能力资产则具备版本、评测证据与回滚引用。<FileCite ref_id="turn35file0"/><FileCite ref_id="turn35file1"/>

**英文名称：** Execution-Diagnosis Decoupling, Root Cause Analysis & Self-Repair Governance

**文档版本：** 1.0

**关联专项：** #75—#94

**设计状态：** 专项设计基线，待实施与验收。

## 一、专项目标

建立一套能够独立分析执行故障、验证根因假设、选择合理修复策略，并通过实际证据确认修复效果的诊断与自我修复体系。

本专项要解决的不是简单的重试问题，而是以下深层问题：

1. 执行器能否可靠判断自己是否执行失败？
2. 执行器的错误解释是否会误导诊断器？
3. 如何区分任务理解错误、规划错误、工具故障和环境问题？
4. 如何判断一次失败究竟由什么引起，是否存在多个共同原因？
5. 如何防止系统把相关性误判为因果关系？
6. 如何证明修复真正解决了问题，而不是暂时绕过症状？
7. 如何防止自动修复扩大任务范围、破坏已有功能或引入新的风险？
8. 如何让诊断能力自身持续改进，同时防止错误诊断策略污染稳定版本？
9. 如何将失败案例转化为可复现的测试与可复用经验？
10. 如何在 Android、Windows 和个人服务器环境中统一诊断与修复治理？

**核心原则：执行器负责产生结果，诊断器负责建立有证据支持的解释，修复控制器负责限制行动并验证效果。任何角色的自我判断都不能替代独立验证。**

## 二、总体架构

### 2.1 六个逻辑组件

| 组件 | 核心职责 |
|---|---|
| Failure Detector | 发现执行异常、验收失败、目标偏离与无进展 |
| Evidence Collector | 收集运行事件、工具回执、环境状态和验证证据 |
| Diagnostic Engine | 生成根因假设、比较证据并判断原因是否得到确认 |
| Repair Planner | 生成修复候选、评估影响、成本和可逆性 |
| Repair Execution Controller | 在授权和隔离条件下实施获准的修复 |
| Independent Repair Verifier | 验证修复效果、检查回归并决定是否允许交付 |

这些是逻辑职责，不要求实现为六个独立服务。可以复用现有的任务执行内核、事件系统、工具契约、验收器、预算管理器和进化治理系统。

但在职责、数据流和权限上，必须保证诊断与修复不会直接绕过原有执行治理。

### 2.2 总体流程

```text id="c95flow"
任务执行 / 运行异常 / 验收失败
                ↓
           发现故障事件
                ↓
         保存并关联原始证据
                ↓
         确定失败现象与影响范围
                ↓
         生成多个根因候选
                ↓
         收集支持证据与反证
                ↓
         评估根因及不确定性
                ↓
         选择修复、恢复或停止策略
                ↓
         检查权限、预算和风险
                ↓
         隔离环境中实施修复
                ↓
         独立验收与回归测试
                ↓
    ┌───────────┼───────────┐
    ↓           ↓           ↓
 验证通过     验证失败     证据不足
    ↓           ↓           ↓
受控发布     回滚或停止   继续诊断或求助
    └───────────┼───────────┘
                ↓
       记录根因、修复与最终证据
                ↓
          进入独立进化评测
```

如果故障影响正在执行的任务，系统可以先采取安全降级或暂停措施，再继续诊断，不必为了完成全部诊断而让风险持续扩大。

## 三、执行与诊断的职责隔离

### 3.1 执行器的职责

执行器负责：

- 接收已经批准的任务契约；
- 按照计划调用工具；
- 记录实际输入与输出；
- 保存工具回执和运行事件；
- 报告异常与当前状态；
- 按授权范围执行获准的恢复动作。

执行器可以报告自己观察到的问题，也可以提出初步原因。

但它的解释只能视为诊断输入，不能自动成为正式根因结论。

例如，执行器报告“API 参数错误”，诊断器仍需检查实际请求、工具输入 Schema、服务端响应和相关版本信息。

### 3.2 诊断器的职责

诊断器负责：

- 读取允许访问的运行证据；
- 重建故障发生前后的事件顺序；
- 比较任务契约、计划、工具契约和实际行为；
- 提出多个可能的根因；
- 查找支持证据和反证；
- 判断是否需要进一步测试；
- 输出诊断结论及其证据强度。

诊断器不应直接修改生产提示词、工具参数、核心代码或权限策略。

诊断输出是一个供修复控制器评估的候选结果，而不是执行命令。

### 3.3 修复控制器的职责

修复控制器负责判断：

- 当前是否值得修复；
- 是否应先尝试已验证的恢复策略；
- 是否需要隔离执行；
- 是否需要用户授权；
- 是否需要修改代码、配置、提示词或工作流；
- 应使用哪些验收和回归测试；
- 修复失败时如何停止或回滚。

修复控制器不得因为诊断器给出了高置信度结论，就跳过必要的风险与权限检查。

### 3.4 三个角色能否使用同一个模型

可以使用同一个基础模型，但必须隔离其任务上下文、权限和决策接口。

如果条件允许，可以采用不同模型或不同执行环境进行交叉验证，但不应假定更换模型就必然带来独立判断。

真正的独立性来自：

- 原始证据可以独立读取；
- 诊断结果与执行器的自我解释分离；
- 关键判断有可验证的测试；
- 诊断器无法直接修改生产执行策略；
- 修复结果由独立验收流程确认。

对于高影响故障，不能仅凭同一模型重复分析几次，就认定获得了独立证据。

## 四、故障检测与影响分级

### 4.1 故障来源

Failure Detector 应综合以下信号：

- 工具返回明确错误；
- 执行超时或无进展；
- 输出违反 Schema；
- 验收器检查失败；
- 实际状态与预期状态不一致；
- 任务违反硬性约束；
- 外部副作用状态不明；
- 预算或权限检查失败；
- 用户报告结果不正确；
- 关键运行事件缺失或顺序冲突。

模型自报失败只是其中一种信号，不能成为唯一的故障发现方式。

### 4.2 故障影响分级

建议采用以下逻辑等级：

| 等级 | 影响 | 默认处理 |
|---|---|---|
| D0 | 无实际故障，只有可忽略的波动 | 记录或忽略 |
| D1 | 局部、低风险、可逆的执行问题 | 允许采用已验证的恢复策略 |
| D2 | 任务质量下降、需要实质性修复 | 诊断并在受控条件下验证 |
| D3 | 影响多个任务、重要数据或稳定版本 | 限制影响范围，强化审核 |
| D4 | 安全、权限或重大外部副作用风险 | 立即采取安全控制，停止未经授权的动作 |

等级应依据实际影响、可逆性、作用范围和潜在后果确定，而不是仅根据错误消息中的严重程度判断。

### 4.3 故障不等于任务失败

一次工具调用失败可能通过安全恢复成功解决，不一定导致整个任务失败。

反过来，工具调用全部返回成功，也可能因为最终结果不符合目标而导致任务验收失败。

因此，故障事件、执行状态和任务最终结果必须分开记录。

## 五、证据采集与可信度治理

### 5.1 证据优先级

建议按证据类型区分可靠性，而不是仅凭叙述是否合理决定可信度。

通常应优先考虑：

1. 可复现的实际状态与独立验证结果；
2. 工具或外部系统的有效回执；
3. 与任务关联的原始运行事件；
4. 可核对的输入、输出及版本信息；
5. 独立生成的测试结果；
6. 执行器或模型提供的解释；
7. 尚未验证的推测。

不同故障类型的最佳证据可能不同。例如，工具 Schema 问题需要检查契约和实际参数，而目标理解错误则需要回到用户原始要求及确认记录。

### 5.2 最小证据包

每个重要故障应形成可追溯的证据包，至少包括：

- `task_id`；
- `run_id`；
- 相关 `node_run_id`（如适用）；
- `runtime_manifest_id`；
- 相关事件引用；
- 错误对象引用；
- 任务契约与验收契约版本；
- 工具契约版本；
- 实际观察到的状态；
- 已尝试的恢复操作；
- 现有外部副作用状态；
- 隐私分级与访问范围。

不要求把所有原始数据复制到一个大型诊断对象中。可以使用引用关联已有证据，避免重复存储敏感内容。

### 5.3 证据完整性

诊断器需要识别证据缺失、时间顺序不确定和版本不匹配等问题。

例如：

- 关键工具回执未同步；
- 运行日志只记录了错误消息，没有保存实际输入；
- 任务恢复后使用了不同版本的工具；
- 外部操作已经提交，但确认状态尚未返回。

此时应降低结论的确定程度，必要时先补齐证据或执行状态对账。

### 5.4 隐私与数据最小化

诊断不意味着可以无限收集运行数据。

应优先使用结构化事件、必要的输入输出摘要和证据引用。

对敏感文件、私人对话、凭据和受限数据，必须遵循既定权限和保留策略。不能因为故障分析需要上下文，就自动上传全部原始数据到云端。

## 六、根因分析机制

### 6.1 区分四个层次

诊断器必须区分：

- **现象：** 发生了什么。
- **直接原因：** 哪个具体条件直接导致失败。
- **根因：** 为什么该条件会出现，哪个上游机制存在缺陷。
- **促成因素：** 哪些条件让问题更容易出现或扩大。

例如：

- 现象：代码测试失败。
- 直接原因：某个函数调用了不存在的接口。
- 根因候选：上下文中使用了过期接口定义，或者代码生成未遵循当前依赖版本。
- 促成因素：测试集未覆盖该接口变更。

如果证据只能确认直接原因，就应如实报告，不必强行推断更深层根因。

### 6.2 多根因分析

一个故障可以由多个原因共同引起。

例如，工具调用失败可能同时涉及：

- 需求解析遗漏必要参数；
- 工具契约缺少输入校验；
- 执行器未处理服务端错误；
- 验收器没有检测失败结果。

诊断器应允许记录多个相关原因，并区分主要原因、次要原因和待验证因素。

不能为了让报告简洁，就强行选择唯一根因。

### 6.3 根因假设

每个根因候选应包含：

- 假设描述；
- 支持证据；
- 反证；
- 适用范围；
- 当前证据强度；
- 可以验证该假设的测试；
- 如果假设成立，预期会观察到什么；
- 如果假设不成立，预期会观察到什么。

建议使用定性证据等级：

- `unverified`：尚未验证；
- `weak`：只有有限支持；
- `supported`：存在多项相互一致的证据；
- `confirmed`：通过足够的直接证据或可复现验证确认；
- `rejected`：关键证据与该假设冲突。

这些是诊断结果等级，不应被误认为经过校准的概率。

### 6.4 反证与可证伪性

诊断器不能只寻找支持自己初始判断的证据。

例如，初步判断是“工具版本不兼容”，就应检查：

- 实际运行版本是否确实不兼容；
- 在相同版本下能否复现；
- 换成兼容版本后是否恢复；
- 是否存在与版本无关的输入错误；
- 失败是否只在某个特定环境出现。

如果反证表明初始假设不成立，应更新诊断，而不是不断修改假设来维护最初的判断。

### 6.5 因果确认

相关性并不等于因果关系。

例如，升级模型后任务成功率下降，不能直接证明模型升级导致问题。同期可能还发生了提示词变化、工具版本变化或评测集变化。

对于重要问题，应尽可能通过以下方式验证：

- 在隔离环境中复现；
- 固定其他变量后比较；
- 对比变更前后的版本；
- 执行针对性测试；
- 使用能够区分不同根因的实验。

无法确认时，可以采用经过验证的临时缓解措施，但必须保留根因未确认的状态。

## 七、故障分类体系

建议将根因分类分为以下层次。

| 类别 | 典型问题 |
|---|---|
| `INTENT` | 目标理解错误、需求歧义处理错误 |
| `CONTEXT` | 上下文遗漏、错误摘要、过期记忆 |
| `ROUTING` | 专家选择或能力路由错误 |
| `PLANNING` | 计划不可行、依赖遗漏、步骤顺序错误 |
| `MODEL` | 模型能力不足、输出不符合要求 |
| `PROMPT` | 提示词冲突、约束表达不清 |
| `TOOL_CONTRACT` | 输入输出契约错误、Schema 不匹配 |
| `TOOL_RUNTIME` | 工具执行异常、超时、输出错误 |
| `ENVIRONMENT` | 权限、依赖、设备或运行环境问题 |
| `EXTERNAL_SERVICE` | API 故障、限流、外部服务异常 |
| `OBSERVATION` | 未正确识别执行后的实际状态 |
| `VERIFICATION` | 验收器缺陷、测试覆盖不足 |
| `AUTHORIZATION` | 授权判断错误或动作超出范围 |
| `RESOURCE` | 预算不足、并发冲突、资源耗尽 |
| `SYNC_STATE` | 事件丢失、状态冲突、同步确认缺失 |
| `UNKNOWN` | 证据不足，暂时无法确定 |

实际记录应区分故障发生层、直接原因、根因和影响范围，避免仅靠一个分类标签代替完整分析。

## 八、修复策略与自主等级

### 8.1 修复分级

建议采用五级修复策略。

**R0：安全停止与状态核实**

适用于权限不明确、外部副作用状态未知、关键数据不完整等情况。

动作包括暂停、对账、保留证据和等待确认。该级别不要求立即找到根因。

**R1：已验证的恢复动作**

适用于可重复、可逆且风险较低的恢复操作，例如对确认可以安全重试的只读请求进行有限重试，或者恢复一个已知的临时连接问题。

**R2：局部任务修复**

适用于任务范围内的可逆修正，例如修正一个已明确的参数、重新生成一个失败的非关键节点，或者在不改变目标的情况下更换已批准的执行路径。

**R3：能力资产候选修复**

适用于提示词、工具配置、工作流、模型配置或代码存在可复现缺陷的情况。

所有变更必须先进入隔离环境，形成候选版本，并通过相应的测试和发布门禁。

**R4：核心、安全与重大变更**

适用于共享内核、权限策略、关键数据结构、跨专家行为或高风险外部动作的修复。

应采用严格的评审、回归测试、授权和发布控制。不能仅凭自动诊断就直接修改生产安全边界。

### 8.2 自动修复的准入条件

只有同时满足适用条件，才允许自动修复：

- 根因有足够证据支持；
- 修复方式属于已批准的策略范围；
- 操作风险在自动执行阈值内；
- 预算足够；
- 目标与授权没有发生变化；
- 有明确的成功判据；
- 修复可被隔离、验证或安全回滚；
- 不会绕过外部副作用检查。

缺少任何必要条件时，应降低自主等级，转为诊断、等待或请求确认。

### 8.3 重试不是万能修复

系统必须区分：

- 临时故障；
- 确定性错误；
- 不可重复操作；
- 需要改变输入或执行路径的问题；
- 需要用户介入的问题。

对于确定性错误，重复相同操作通常没有价值。

对于外部副作用状态未知的操作，不能仅因为任务超时就直接重试。必须先依据现有 `Side-effect Ledger` 和外部回执完成状态核实。

### 8.4 自动修复范围不能无限扩大

当一个修复方案失败时，不允许自动将修复范围无限扩大。

例如：

- 局部参数修正失败，不意味着可以自动重写整个工具；
- 工作流修复失败，不意味着可以直接修改共享内核；
- 专家输出质量下降，不意味着可以任意更换全局模型；
- 验收器失败，不意味着可以降低验收标准以获得通过。

扩大修复范围需要重新诊断、评估影响，并满足相应的准入条件。

## 九、修复沙箱与验证机制

### 9.1 隔离环境

候选修复应优先在隔离环境中执行。

隔离环境应尽可能具备：

- 独立工作区或分支；
- 固定的输入与测试数据；
- 明确的工具和模型版本；
- 受控的网络与文件访问；
- 独立预算；
- 可清理的临时状态；
- 可追溯的运行记录。

高风险修复不能直接在用户的生产环境中试错。

### 9.2 修复前后对照

修复验证至少应回答：

1. 原故障是否能够复现？
2. 修复后原故障是否消失？
3. 目标验收条件是否通过？
4. 是否引入新的错误？
5. 其他相关功能是否退化？
6. 成本和执行时延是否出现明显恶化？
7. 是否改变了权限、数据或外部副作用行为？
8. 是否仍然满足原始任务约束？

如果原故障无法复现，不能简单地把后续一次成功归因于修复有效。

### 9.3 独立验收器

对于重要修复，验证机制应尽量使用不同于修复生成路径的证据。

例如：

- 代码修复使用构建与测试工具验证；
- 文件修复检查实际文件内容和格式；
- 手机操作修复检查目标界面的实际状态；
- 工作流修复使用端到端任务进行验证；
- 工具契约修复使用独立的契约测试；
- 诊断策略修复使用固定故障案例集评测。

如果只能由同一个模型判断自己的修复是否正确，验证强度应相应降低。

### 9.4 发布与回滚

修复候选只有通过适用门禁后，才能进入正式发布流程。

发布前应明确：

- 变更内容；
- 受影响的能力资产；
- 测试与评测证据；
- 兼容性要求；
- 发布范围；
- 监控指标；
- 回滚目标；
- 失败后的恢复策略。

发布后如果出现质量退化，应能够识别对应版本并按既定策略回滚。

## 十、修复状态机

建议建立独立的修复流程状态机，不修改正式 Task 的状态枚举。

```text id="repairstates"
detected
   ↓
evidence_collected
   ↓
diagnosing
   ↓
hypothesis_review
   ↓
repair_proposed
   ↓
admission_check
   ├──→ rejected
   ├──→ waiting_approval
   └──→ sandbox_running
                ↓
           verification
                ├──→ verification_failed
                ├──→ rollback_required
                └──→ ready_for_release
                              ↓
                        release_gate
                         ├──→ rejected
                         └──→ released
                                  ↓
                            post_release_monitoring
                                  ↓
                            completed / rolled_back
```

其中：

- `detected`：已经发现故障；
- `evidence_collected`：已有足够的初始证据；
- `diagnosing`：正在生成与验证根因假设；
- `hypothesis_review`：评估诊断结论及其不确定性；
- `repair_proposed`：形成修复候选；
- `admission_check`：检查修复准入条件；
- `waiting_approval`：等待必要授权；
- `sandbox_running`：在隔离环境中实施修复；
- `verification`：执行修复验证；
- `ready_for_release`：验证通过，等待正式发布；
- `released`：已通过门禁并发布；
- `post_release_monitoring`：监控实际效果；
- `completed`：修复流程完成；
- `verification_failed`：修复验证失败；
- `rollback_required`：需要回滚；
- `rolled_back`：已回滚；
- `rejected`：修复候选被拒绝。

这些状态是修复流程的设计建议，实际实现应使用独立的、版本化的修复记录，并保持与正式任务状态的关联。

## 十一、诊断器自身的质量治理

### 11.1 诊断器也会犯错

诊断器可能出现：

- 忽略关键证据；
- 过度相信执行器的解释；
- 只寻找支持初始假设的材料；
- 把相关性当作因果关系；
- 错误估计修复收益；
- 误判问题影响范围；
- 在证据不足时过早结束分析。

因此，诊断器必须拥有自己的评测集和质量指标，不能被当作天然可靠的裁判。

### 11.2 独立诊断评测集

建议建立覆盖以下场景的固定测试集：

- 根因已知的可复现故障；
- 存在多个相似根因的故障；
- 原始日志缺失；
- 执行器给出错误解释；
- 验收器本身存在缺陷；
- 工具与环境同时异常；
- 证据不足、无法确定根因；
- 修复看似成功但实际未解决问题；
- 修复解决旧问题但引入回归；
- 需要停止而非修复的高风险情况。

评测集应包含真实故障案例和经过控制的合成案例，并明确区分测试标签与实际运行中的未知根因。

### 11.3 诊断器的发布门禁

诊断策略升级前，应检查：

- 根因分类是否准确；
- 证据引用是否完整；
- 错误自信是否增加；
- 不必要修复是否增加；
- 高风险故障是否被正确升级；
- 修复成功率是否提高；
- 是否出现其他任务类别的退化；
- 额外诊断成本是否合理。

任何可能降低安全控制或扩大自动修复权限的改动，都不能仅凭平均诊断准确率提高就获得发布资格。

### 11.4 稳定版与后台进化分离

稳定版负责执行任务、记录故障并调用已经批准的恢复策略。

后台进化轨道负责分析失败案例、改进诊断方法、生成修复候选和执行回归评测。

后台进化不得直接改写生产诊断规则或执行权限。候选版本必须经过正式门禁、受控发布和可回滚验证。

## 十二、故障经验沉淀与复用

### 12.1 不要把每条错误日志都变成长期知识

只有经过适当验证的案例，才适合沉淀为可复用的故障经验。

建议区分：

- 原始故障证据；
- 待验证的根因假设；
- 已确认的故障案例；
- 已验证的恢复策略；
- 已通过评测的修复知识；
- 已正式发布的能力资产。

不同状态的知识不能互相替代。

### 12.2 可复用故障案例

每个已验证案例应记录：

- 触发条件；
- 适用环境；
- 可复现输入；
- 故障现象；
- 已确认根因；
- 被否定的假设；
- 修复方式；
- 验收与回归结果；
- 适用版本；
- 不适用条件；
- 风险与限制。

如果无法安全保存原始输入，可以保存经过脱敏的最小复现材料或受控引用。

### 12.3 专家之间的知识共享

不同专家可以复用已经验证的通用故障模式，但不能将所有领域的修复策略无差别共享。

例如：

- 通用的超时诊断方法可以共享；
- 代码 AST 修复经验应归属代码专家的相关能力资产；
- Android UI 恢复策略应考虑具体系统版本、权限与界面状态；
- 视频生成服务的参数修复应关联对应的服务版本。

共享经验应声明适用范围、依赖和验证证据。

## 十四、核心验收测试矩阵

| 测试 ID | 场景 | 通过条件 |
|---|---|---|
| RCA-01 | 执行器报告工具错误 | 诊断器仍独立核对工具回执和契约 |
| RCA-02 | 执行器给出错误的根因解释 | 不直接将该解释认定为根因 |
| RCA-03 | 日志缺少关键事件 | 明确降低结论确定性或补充证据 |
| RCA-04 | 存在两个相似根因 | 能提出并区分多个候选 |
| RCA-05 | 发现支持初始判断的证据 | 同时检查关键反证 |
| RCA-06 | 根因无法确认 | 保留未知状态，不编造确定结论 |
| RCA-07 | 一次失败存在多个共同原因 | 支持记录多根因及其关联 |
| RCA-08 | 临时网络故障 | 使用受限的已验证恢复策略 |
| RCA-09 | 确定性参数错误 | 不无限重复相同请求 |
| RCA-10 | 外部副作用状态未知 | 先对账，再决定是否恢复 |
| RCA-11 | 局部修复失败 | 不自动无限扩大修复范围 |
| RCA-12 | 候选修复引入回归 | 阻止发布或执行回滚 |
| RCA-13 | 验收器本身有缺陷 | 能够识别验收问题，不盲目相信验收结果 |
| RCA-14 | 修复改变共享内核 | 进入更严格的发布门禁 |
| RCA-15 | 修复需要超出原授权范围 | 停止并请求必要确认 |
| RCA-16 | 预算耗尽 | 停止可选诊断或修复，不擅自扩预算 |
| RCA-17 | 任务可通过安全降级继续 | 不必等待全部根因分析结束才采取必要措施 |
| RCA-18 | 新修复策略在其他专家上退化 | 不允许无差别发布 |
| RCA-19 | 相同故障再次出现 | 能关联历史案例，但仍核对当前证据 |
| RCA-20 | 诊断器过度自信 | 评测能识别无证据支持的结论 |
| RCA-21 | 修复后原故障不再复现 | 不仅凭一次成功就断言修复有效 |
| RCA-22 | 修复通过单元测试但端到端失败 | 不允许标记为完整修复成功 |
| RCA-23 | 不同运行版本发生同类故障 | 能比较版本差异与环境因素 |
| RCA-24 | 后台进化生成修复候选 | 不得绕过正式发布门禁 |
| RCA-25 | 修复已发布后出现质量退化 | 能定位版本并按策略回滚 |
| RCA-26 | 故障证据包含敏感信息 | 遵循数据访问、脱敏与保留策略 |
| RCA-27 | 诊断过程本身失败 | 记录诊断失败，不将其误标为根因已确认 |
| RCA-28 | 高风险故障需要立即停止 | 优先实施安全控制，而不是继续自动试错 |

所有测试均须在真实或受控环境中提供执行证据。本文件定义设计与验收要求，不代表相应功能已经实现。

## 十六、完成判定

只有满足以下条件，才能认定本专项实施验收完成：

- 执行器不能直接决定自己的故障根因；
- 诊断器能够关联真实运行证据和版本信息；
- 根因结论能够区分已确认、待验证与未知；
- 诊断过程支持反证和多根因分析；
- 修复动作受到独立的授权、预算和风险检查；
- 高风险和不可逆操作不会因自动修复而绕过控制；
- 候选修复能够在隔离环境中验证；
- 修复结果必须通过适用的独立验收；
- 回归失败能够阻止发布或触发回滚；
- 诊断策略和修复策略都有独立评测；
- 已验证的故障经验能够安全地复用；
- 后台进化不能直接修改稳定执行策略；
- 所有关键验收场景均有真实执行证据。

**最终目标：让 EvoAgent 从“遇到问题就重试”进化为“知道发生了什么、清楚哪些原因尚未确认、能够选择有证据支持的修复方法，并通过实际结果验证修复是否有效”的智能体。诊断能力本身也必须接受验证、约束和持续改进，不能成为另一个不受控制的错误来源。**</WritingBlock>

## 下一项专项：#96

建议继续推进 **#96：端到端质量评测体系、真实任务基准与持续回归治理**。

#95 解决了如何分析和修复单个故障，但还需要回答一个更大的问题：**怎样证明 EvoAgent 整体上真的在变好，而不是只修好了几个案例，却让其他能力退化？**

下一项应重点设计：

1. 如何构建覆盖通用任务、编程、手机操作、信息研究和工作流自动化的真实任务基准；
2. 如何区分任务完成率、验收通过率、用户目标达成率与表面执行成功率；
3. 如何设计固定回归集、动态故障集和真实用户任务抽样；
4. 如何在模型、提示词、工具、路由、上下文策略变化后进行对照评测；
5. 如何衡量质量、效率、稳定性、成本与主动帮助价值；
6. 如何发现某个专家的改进损害了共享内核或其他专家；
7. 如何确定自动发布门槛、灰度范围和回滚条件；
8. 如何避免评测器与被评测系统共享同一缺陷；
9. 如何判断一个改进是真正可泛化的提升，而不是针对测试集过拟合；
10. 如何将所有评测证据与正式版本、运行环境和能力资产关联。

这将把 #94 的任务质量保障与 #95 的诊断修复机制进一步连接起来，形成一个更完整的进化闭环：**不只知道哪里失败、怎样修复，还能持续证明每一次改进是否真正提高了整体任务质量。**
