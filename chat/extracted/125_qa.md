## ChatGPT

你发现的是 EvoAgent 自进化架构里一个非常关键的缺口：**如果智能体使用的工具本身有问题，那么进化系统可能不仅发现不了问题，还会被这个有问题的工具误导，最终越优化越差。**

例如，Agent 有一个网页搜索工具。它搜索结果不完整，却返回 `success=true`。Agent 以为自己拿到了完整信息，于是修改提示词、上下文策略，甚至模型适配方式。可是，真正的问题始终在搜索工具本身。

更危险的是，如果负责诊断问题的模型也依赖这个工具，它可能会用错误的数据诊断错误，形成一个自我强化的错误循环。

所以，原先的 EvoAgent 还需要增加一个关键系统：

# 工具可信度与自我诊断层（Tool Integrity & Self-Diagnosis）

它不能只是让 Agent 反思“刚才是不是用错了工具”，而是要让系统具备独立检查工具、识别工具故障、区分故障来源、隔离异常工具，以及验证修复效果的能力。

## 一、先把故障来源分清楚

EvoAgent 不能把所有失败都归因于 Agent 自身。至少需要区分下面六类问题。

| 故障类型 | 例子 | 应该优先检查什么 |
|---|---|---|
| 工具自身故障 | 搜索服务返回错误、计算器算错 | 工具健康检查、独立测试 |
| 工具接口故障 | 参数格式错误、返回字段缺失 | 输入输出契约、Schema 校验 |
| 工具语义故障 | 返回成功，但实际只搜索了一页 | 结果完整性、业务规则验证 |
| 工具选择故障 | 应该查数据库，却调用网页搜索 | 工具路由策略、任务与工具匹配 |
| 工具使用故障 | 工具正确，但 Agent 参数填错 | 参数来源、调用轨迹、重试记录 |
| 工具与环境故障 | API 限流、网络中断、凭据失效 | 环境检查、超时、服务状态 |

还有第七种：**评估系统自身故障**。比如，评测器只检查返回文本是否包含某个词，却没有检查结果是否正确。这种情况下，工具和 Agent 都可能有问题，而评测系统仍然判定通过。

因此，进化系统需要先定位故障，再决定修改哪个模块。

对于搜索、研究等没有唯一标准答案的任务，则需要使用多种证据，并允许系统给出“无法确定”，而不是强行判断工具正确或错误。

## 三、工具也必须有自己的测试集和版本

这是进一步防止系统盲目进化的核心。

你不能只给 Agent 建立评测集，还要给每个工具建立独立的质量基线。

例如，计算器工具：

- 输入 `17 * 19`，期望结果必须是 `323`。
- 输入 `1 / 0`，必须返回受控错误，不能导致整个进程崩溃。
- 输入超长表达式，必须按预算规则拒绝。
- 输入不支持的语法，必须明确报错，不能猜一个答案。

网页搜索工具则需要另一种测试：

- 服务不可用时，是否正确报告失败？
- 搜索结果是否包含必要字段？
- 请求是否超时？
- 是否把空结果伪装成成功？
- 如果声明返回 10 条结果，实际是否确实满足约定？

这里要区分两种不同的测试。

<box gap={2}>
  <row align="start" gap={3}>
    <box background="surface-secondary" radius="lg" size="48px" align="center" justify="center">
      <icon name="test-tube" size="xl"/>
    </box>
    <box flex="1" gap={1}>
      **工具单元测试**

      <text color="secondary" size="sm">验证工具自身的逻辑、边界条件、参数和输出契约。适合每次代码变更后运行。</text>
    </box>
  </row>
  <row align="start" gap={3}>

    </box>
    <box flex="1" gap={1}>
      **工具集成测试**

      <text color="secondary" size="sm">验证 Agent 能否选对工具、传入正确参数、理解返回结果，并在工具故障时正确恢复。</text>
    </box>
  </row>
</box>

这两种测试必须分开。如果计算器的单元测试失败，就不应先去调整 Agent 的提示词；如果计算器本身正常，但 Agent 总是传错参数，才应该优先优化工具选择或调用策略。

## 四、增加工具故障的独立数据库

原来的 `runs`、`events`、`issues` 和 `experiments` 四张表仍然保留，但我建议至少新增三张表。

| 表 | 关键字段 | 作用 |
|---|---|---|
| `tool_registry` | `tool_id`、`version`、`schema_hash`、`enabled`、`risk_level` | 保存工具身份、版本、契约和启用状态 |
| `tool_health` | `tool_id`、`checked_at`、`success_rate`、`latency_ms`、`error_rate` | 保存健康检查与运行统计 |
| `tool_test_runs` | `tool_id`、`test_suite_version`、`passed`、`failure_details` | 保存工具独立测试结果 |

另外，`issues` 应增加 `suspected_component`、`confidence` 和 `evidence_refs` 字段，明确问题可能属于哪个模块，以及判断依据是什么。

例如：

<CodeBlock language="json" editable={false}>{
  "issue_id": "iss_001",
  "suspected_component": "tool:search",
  "category": "semantic_contract_violation",
  "confidence": 0.94,
  "evidence_refs": [
    "run_123:event_008",
    "tool_test_search_017"
  ],
  "status": "quarantined"
}</CodeBlock>

这里的 `0.94` 只是示意数据，不代表系统可以仅凭模型主观判断就获得如此高的可信度。实际置信度应该来自可验证的规则、测试结果和历史统计。

还有一个容易忽略的问题：工具的健康度应按版本记录。不能因为搜索工具 V1 运行正常，就认定刚升级的 V2 也正常。

## 五、出现故障后，系统如何自行处理？

我建议为工具建立五种运行状态。

<box border radius="xl" padding={3} gap={2}>
  {#each [{state:"HEALTHY",color:"#16A34A",desc:"工具正常，可以按策略使用。"},{state:"SUSPECT",color:"#D97706",desc:"发现异常迹象，增加验证并降低信任度。"},{state:"QUARANTINED",color:"#DC2626",desc:"停止普通任务调用，保留诊断和隔离测试能力。"},{state:"RECOVERING",color:"#2563EB",desc:"候选修复已通过部分测试，进入受限试运行。"},{state:"HEALTHY",color:"#16A34A",desc:"完成规定的验证和观察期后，恢复正常使用。"}] as item,i}
    <row align="start" gap={3}>
      <box background={item.color} radius="md" padding={2} minWidth="118px" align="center">
        <text color="#FFFFFF" weight="medium" size="sm">{item.state}</text>
      </box>
      <box flex="1" padding={{top:2,bottom:2}}>
        <text size="sm">{item.desc}</text>
      </box>
    </row>
    {#if i<4}
      <box padding={{left:3}}>
        <icon name="arrow-down" size="sm" color="secondary"/>
      </box>
    {/if}
  {/each}
</box>

实际实现时，状态转换需要有明确规则。例如：

- 一次网络超时不应立即永久禁用工具。
- 连续超时或错误率超过阈值时，可以进入 `SUSPECT`。
- 确认存在严重错误、数据污染或权限风险时，进入 `QUARANTINED`。
- 修复版本通过工具测试、集成测试和安全测试后，才能进入 `RECOVERING`。
- 观察期通过后才能恢复正常。

恢复机制也必须区分工具类型。对于只读搜索工具，可以尝试备用服务；对于发送邮件、删除文件、付款等有副作用的工具，不能因为超时就盲目重试，因为第一次操作可能已经成功。

**熔断器保护的是系统整体，而不是只保护工具本身。**

如果一个工具持续返回错误，Agent 应该能够暂停调用、使用经过授权的替代方案，或者向用户说明任务暂时无法可靠完成。

## 六、最重要的：让进化引擎先排查自己，再决定修改谁

我建议将原来的进化流程改成下面这套故障诊断流程。

<box border radius="xl" padding={3} gap={2}>
  <box background="surface-secondary" radius="lg" padding={3} align="center">
    **检测到任务失败或结果异常**
  </box>
  <box align="center"><icon name="arrow-down" color="secondary"/></box>
  <box border radius="lg" padding={3} align="center">
    **第一步：验证工具本身**
    <text color="secondary" size="sm">契约检查、独立测试、健康状态、结果一致性</text>
  </box>
  <box align="center"><icon name="arrow-down" color="secondary"/></box>
  <box border radius="lg" padding={3} align="center">
    **第二步：验证工具调用链**
    <text color="secondary" size="sm">工具选对了吗？参数对吗？结果被正确解析了吗？</text>
  </box>
  <box align="center"><icon name="arrow-down" color="secondary"/></box>
  <box border radius="lg" padding={3} align="center">
    **第三步：验证 Agent 运行机制**
    <text color="secondary" size="sm">ReAct 状态、上下文、提示词、重试和停止条件</text>
  </box>
  <box align="center"><icon name="arrow-down" color="secondary"/></box>
  <box border radius="lg" padding={3} align="center">
    **第四步：验证评测系统**
    <text color="secondary" size="sm">评测器是否正确？测试是否覆盖了实际故障？</text>
  </box>
  <box align="center"><icon name="arrow-down" color="secondary"/></box>
  <box background="surface-secondary" radius="lg" padding={3} align="center">
    **确定故障范围 → 生成修复提案 → 独立验证 → 决定是否发布**
  </box>
</box>

如果多个环节同时异常，系统应该允许记录多个根因，而不是强制选出一个原因。证据不足时，也应进入“待诊断”状态，不自动修改生产配置。

### 一个关键的发布规则

假设进化引擎发现工具存在故障，同时又提出了一个新的提示词方案。

这时应当遵守：

1. 先隔离或确认工具故障。
2. 冻结依赖该工具的相关质量评测。
3. 修复工具或切换到已验证的替代工具。
4. 重新建立可信的评测基线。
5. 再测试提示词和 Harness 的改进。
6. 只有评测环境可信时，才允许相关优化晋级。

否则，系统可能会利用一个有问题的工具制造出虚假的高分，然后把错误的改进永久保存到稳定分支中。

## 七、我建议把 EvoAgent 的架构升级为 V0.2

在原来的 V0.1 上，增加一个独立的 **Tool Reliability Engine（工具可靠性引擎）**，并将它放在进化引擎之前。

V0.2 应当优先交付这五项能力：

- [ ] 工具注册表：记录工具版本、Schema、权限和健康状态。
- [ ] 独立工具测试：每个工具有自己的正向、负向和边界测试。
- [ ] 结果验证器：校验输出契约，并为关键结果提供独立核验。
- [ ] 熔断与隔离：异常工具停止参与普通任务，避免污染后续执行。
- [ ] 故障归因门禁：工具或评测系统状态不可信时，禁止依赖这些结果自动发布改进。

后续再让 Agent 自动生成工具修复代码，在隔离分支中运行测试、进行安全审查和集成验证。工具修复和 Agent 自身优化应使用同一套实验平台，但使用不同的权限等级与发布门槛。

**最终目标不是让 EvoAgent 永远相信自己，而是让它能够验证自己所依赖的每一个关键组件，并在无法验证时主动降低自主程度。**

这会使整个系统从“能够反思的 Agent”，真正进化为一个具有故障检测、隔离、恢复和自我验证能力的工程系统。
