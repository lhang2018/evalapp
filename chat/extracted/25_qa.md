# EvoAgent 深度设计第四轮：智能体应该如何决定“先优化什么”？

这一轮，我们要设计 EvoAgent 的进化决策中枢。

前面几轮已经建立了几个基础：

- 能力不是简单的树，而是包含依赖关系的能力图谱。
- 能力定义、实现、证据和发布版本需要分别管理。
- 专家可以独立进化，共享能力必须经过验证才能推广。
- 每次改动都必须考虑影响范围、回归测试、成本和回滚。

但这些原则还没有回答一个关键问题：

**当系统发现十个问题、提出二十个改进方案，却只有有限的模型调用额度、时间和预算时，它究竟应该先做什么？**

这不是简单的任务优先级排序，而是一个持续决策问题。

如果决策机制设计得不好，EvoAgent 可能会：

- 不断修复容易修复、但价值很低的问题。
- 忽略发生概率低、但后果严重的缺陷。
- 反复优化某个专家，却让其他专家长期停滞。
- 为了提高成功率，不断增加模型调用和验证成本。
- 花费大量预算测试收益微乎其微的改动。
- 只优化容易被量化的指标，忽略真实任务质量。

所以，这一轮的目标不是设计一个“改进排行榜”，而是设计一个能够在质量、成本、风险和长期价值之间做出合理选择的**进化决策系统**。

## 一、第一性原理：进化的目标到底是什么？

先提出一个可能有争议的判断：

**EvoAgent 不应该以“让自己越来越强”作为直接优化目标，因为“强”没有可操作的定义，而且不同能力之间存在冲突。**

我们需要把目标落到真实任务上。

例如：

- 用户让它完成代码修改，代码必须正确，不能只是看起来合理。
- 用户让它操作手机，关键操作必须真实完成，而不是只生成操作计划。
- 用户让它制作漫剧，结果需要符合质量要求、预算和时长限制。
- 用户让它规划旅行，行程需要满足约束，信息也要足够可靠。

因此，EvoAgent 的首要目标应当是：

**在给定的任务、环境、权限和资源约束下，提高真实任务的成功交付能力。**

这里的“成功交付”至少包含五个部分：






      **任务质量**

      是否达成目标，是否满足用户的硬性约束，结果是否经过适当验证。








      **可靠性与安全性**

      是否稳定完成，是否出现未经授权的操作，是否能正确处理失败。








      **资源效率**

      在达到质量要求的前提下，控制模型费用、工具费用、延迟和实验开销。








      **长期能力收益**

      改进是否能重复产生收益，是否能迁移到相关任务，是否减少未来的失败和维护成本。



这五个目标不应该全部压缩成一个可以任意补偿的总分。

例如，不能因为成本降低了 30%，就允许未经授权的手机操作增加；也不能因为平均成功率提高，就忽略高风险任务的严重失败。

因此，我建议采用两层决策：

1. **硬约束层：** 权限、安全、最低质量、硬预算和用户明确约束，不允许通过其他指标的改善来抵消违规。
2. **优化层：** 在满足硬约束的候选方案之间，比较质量收益、可靠性、成本、延迟和长期价值。

这比简单地让一个模型生成“综合评分”更可靠，也更容易工程化。

# 二、不要直接给“问题”排序，而要给“可执行的改进方案”排序

假设系统发现了三个问题：

| 问题 | 初步现象 |
|---|---|
| A | 编程专家偶尔生成错误代码 |
| B | 旅游专家的行程规划成本偏高 |
| C | 共享上下文组件偶尔丢失用户约束 |

如果只按失败次数排序，A 可能排第一。

但我们还不知道：

- A 是模型能力不足、提示词问题，还是测试环境问题？
- B 能否通过缓存、轻量模型或减少重复查询解决？
- C 的发生频率虽然低，但是否会导致多个专家同时出错？
- 哪个问题最容易修复？
- 哪个问题修复后能带来最大的长期收益？
- 哪个问题值得投入更多预算来诊断？

因此，决策对象不应该只是一个问题，而应该是一个完整的**改进候选方案**。

一个候选方案至少要包含：

- 它试图解决的缺陷。
- 对缺陷根因的假设。
- 准备修改的能力或组件。
- 预期收益和适用范围。
- 可能影响的其他专家。
- 实现成本和验证成本。
- 预期模型调用费用与延迟变化。
- 失败风险和回滚方案。
- 用什么测试判断它是否成功。

例如，C 不应该只是“改进上下文管理”，而应该形成可验证的方案：

> 修改上下文压缩组件，在压缩前识别必须保留的用户硬约束；通过编程、旅游和漫剧的约束保留测试，验证关键约束遗漏率是否下降，同时检查上下文长度、成本和其他信息丢失情况。

这就把一个模糊的优化想法变成了可以评估的工程候选。

**问题发现系统负责指出哪里可能有问题，进化决策系统负责判断值不值得改，候选实现负责提出如何改，独立评测系统负责验证改得是否有效。**

这四个职责不应该混在一个大模型提示词里。

# 三、如何计算一个改进方案的价值？

我建议不要一开始就设计复杂的强化学习算法。V0.1 可以先采用可解释的期望收益模型，再逐步引入更好的统计估计。

一个改进方案的价值，可以从五个方面估计。

## 3.1 预期质量收益

这项改进预计能让多少真实任务受益？

不仅要看失败率，还要看任务量、缺陷严重性和成功后的实际价值。

例如：

- 修复一个高频的工具调用问题，可能影响大量任务。
- 修复一个罕见的高风险缺陷，发生概率虽低，但预期损失可能很大。
- 优化一个很少使用的格式化技能，即使容易成功，整体价值也可能有限。

我们可以先估算：

\[
\text{预期收益}
=
\text{适用任务量}
\times
\text{每次任务的预期改善}
\]

但这个公式只是起点。不同任务的价值不同，严重失败也不能只用平均值来衡量，因此实际系统应当按任务类型和风险等级分别估计。

## 3.2 预期资源成本

需要统计的不只是一次改动的成本，还包括：

- 诊断成本。
- 候选生成成本。
- 测试与回归成本。
- 发布后的额外运行成本。
- 长期维护成本。

例如，某个方案每次任务能节省少量模型调用，但需要非常昂贵的维护和评测。它未必值得采用。

## 3.3 预期风险

一个改动可能解决目标缺陷，却破坏其他能力。

因此，风险估计必须结合能力依赖图：

- 修改一个专家的局部提示词，通常影响范围较小。
- 修改共享上下文组件，可能影响所有依赖它的专家。
- 修改权限、预算或发布门禁，风险更高，需要独立的审批和验证机制。

需要强调的是，风险不能只看受影响专家的数量。一个低频但涉及权限边界的缺陷，可能比多个专家的轻微质量波动更重要。

## 3.4 不确定性

系统可能认为某项改进很有价值，但实际上缺乏证据。

例如，某个提示词在三个相似案例中有效，不足以证明它能改善整个编程专家。

因此，我们应当分别记录：

- 预期收益。
- 估计的不确定性。
- 现有证据的覆盖范围。
- 还需要哪些实验才能降低不确定性。

不能把模型给出的一个高置信度数字，直接当成可靠的概率估计。

## 3.5 长期价值

有些改进短期收益不明显，却能降低未来大量任务的失败成本。

例如：

- 增加结构化任务检查点。
- 改善工具错误分类。
- 建立可靠的结果验收器。
- 优化模型适配和兼容性测试。
- 改善可复现性与故障定位。

这些基础设施改进可能不会立即提高某个任务的成功率，但会让未来诊断和恢复更加便宜、更可靠。

所以，进化系统必须同时考虑短期任务收益和长期基础设施价值。

# 四、进化优先级不能只用一个分数决定

我建议采用“硬门槛 + 多目标排序 + 不确定性探索”的三阶段决策机制。

## 第一阶段：硬门槛筛选

以下候选应当直接拒绝、暂停或要求进一步诊断：

- 会突破系统权限边界。
- 会绕过硬预算上限。
- 无法安全回滚，却可能破坏稳定版本。
- 缺少必要的复现证据或验收方式。
- 存在不可接受的隐私、安全或数据损坏风险。

对于涉及安全和权限的高风险改动，不能因为预计收益高就自动放行。

## 第二阶段：多目标排序

通过硬门槛的候选，再根据预期收益、风险、成本和长期价值排序。

可以先使用下面这个概念模型：

\[
V(a)=
\frac{
B_q(a)+B_r(a)+B_l(a)-R(a)
}{
C_d(a)+C_i(a)+C_v(a)+C_m(a)
}
\]

其中：

- \(B_q\)：预期任务质量收益。
- \(B_r\)：可靠性与风险降低收益。
- \(B_l\)：长期能力收益。
- \(R\)：未被硬门槛排除的剩余风险。
- \(C_d\)：诊断成本。
- \(C_i\)：实现成本。
- \(C_v\)：验证成本。
- \(C_m\)：长期维护成本。

这个公式的作用是明确思考维度，不应直接把不同单位的原始数值相加。实际实现时，应先将收益和风险转换成一致的价值尺度，或采用多目标 Pareto 排序，避免用任意权重制造虚假的精确性。

例如，质量、延迟、费用和安全风险可以保留为独立指标。一个候选如果在所有指标上都不比另一个好，就可以被淘汰；如果各有优劣，则根据任务类型、用户约束和资源预算决定。

## 第三阶段：保留探索机会

如果系统永远只选择当前估计收益最高的候选，它可能一直重复优化已知问题，而错过更重要的新问题。

因此，还需要一部分资源用于探索：

- 验证根因不明确但可能影响较大的问题。
- 测试可能带来跨领域收益的新方法。
- 评估尚未充分验证的模型或工具。
- 检查长期没有覆盖的专家和能力。

但探索也要有预算，不能成为无限实验的借口。

# 五、系统应该如何分配有限的进化预算？

这里要区分两种完全不同的预算：

1. **运行预算：** 用来完成用户任务。
2. **进化预算：** 用来诊断问题、生成候选、评测、实验和发布改进。

两者应该独立核算。

否则，一个复杂的进化实验可能占用过多模型调用，导致正在运行的用户任务无法及时完成。

我建议建立三层预算。




      **第一层：硬性资源上限**

    单次实验、单个候选、每日或每月的费用与计算资源上限。任何进化策略都不能绕过。





      **第二层：进化周期预算**

    为诊断、局部修复、共享能力改进、基础设施和探索分配预算。具体比例由实际收益与资源情况调整，而不是永久固定。





      **第三层：候选实验预算**

    每个候选在开始前获得预算额度、最大实验次数、停止条件和回退方案。未证明价值时，不自动无限追加预算。


预算分配还应该考虑共享收益。

例如，改进共享上下文组件可能同时帮助四个专家；但这不代表它一定优先于某个专家的局部问题。如果共享组件改动风险大、测试昂贵，或者证据很弱，局部修复可能仍然更划算。

反过来，如果四个专家都在遭遇相同的约束遗漏问题，那么修复共享根因可能比给四个专家分别加提示词更有长期价值。

**预算应该跟着预期边际收益和风险走，而不是简单平均分给每个专家。**

# 六、进化系统什么时候应该继续、停止或放弃？

这部分很容易被忽略，但它直接决定系统是否会陷入无限自我优化。

我建议每个候选方案都有明确的实验状态机。

<CodeBlock language="mermaid" editable={false}>flowchart TD
    A[提出改进候选] --> B[检查硬门槛与预算]
    B --> C{是否值得实验}
    C -->|否| X[拒绝或归档]
    C -->|是| D[运行低成本初筛]
    D --> E{是否有改善信号}
    E -->|否| F[停止实验并记录]
    E -->|是| G[运行目标回归测试]
    G --> H{证据是否充分}
    H -->|否| I{是否值得继续取证}
    I -->|否| X
    I -->|是| J[增加有限预算]
    J --> G
    H -->|是| K[运行影响范围测试]
    K --> L{是否通过发布门禁}
    L -->|否| F
    L -->|是| M[受控发布]
    M --> N[观察真实运行结果]
    N --> O{是否出现退化}
    O -->|是| P[停止扩散并回滚]
    O -->|否| Q[积累证据与更新能力画像]</CodeBlock>

这里需要明确几个规则。

### 1. 没有改善信号时，不能无限尝试

如果一个候选经过预先定义的低成本测试后，没有任何有意义的改善信号，就应该停止或重新检查假设，而不是不断调整参数直到碰巧通过。

### 2. 证据不足不等于一定失败

如果初步结果有希望，但样本太少，可以增加测试。不过，继续测试必须具有明确的信息价值，且不能突破预算。

### 3. 改进收益不明确时，允许不发布

EvoAgent 不必每次诊断后都修改自己。

有时最合理的结果是：“问题已定位，但现有证据不足以支持自动修复。”

这不是进化失败，而是避免低质量改动进入稳定版本。

### 4. 发布后仍然需要监测

离线测试通过不代表在真实环境里永远有效。

模型版本、工具行为、任务分布和用户需求都可能变化。发布后要持续监测关键指标，一旦出现显著退化，就停止进一步推广，必要时回滚。

# 七、怎样避免系统只优化容易量化的指标？

这是一个比公式更深的问题。

如果 EvoAgent 只追求成功率，它可能通过缩小任务范围来提高分数；如果只追求低成本，它可能少做必要验证；如果只追求任务速度，它可能跳过重要步骤。

因此，进化决策必须区分：

- **不可违反的约束：** 用户硬性要求、安全权限、数据完整性、必要的结果验收。
- **需要达到的最低标准：** 任务质量、可靠性和必要的兼容性。
- **可以优化的目标：** 费用、延迟、冗余调用、维护成本和长期收益。

只有在硬约束和最低标准得到满足后，才比较可以优化的目标。

此外，评测不能只看平均值。至少要同时关注：

- 总体成功率。
- 重要任务类别的成功率。
- 高风险失败。
- 最差表现的关键任务分组。
- 成本与延迟分布。
- 回归缺陷率。
- 新任务和未见案例上的表现。

例如，一个候选让总体成功率从 90% 上升到 92%，但使高风险手机操作的错误率明显上升，就不能因为总分提高而自动发布。

**任何综合评分都不能代替关键约束和分组门槛。**

# 八、进化决策中枢应该由哪些模块组成？

现在可以把它整理成一套独立的工程系统，而不是一个让大模型自由决定“接下来改什么”的提示词。


    <title size="lg">1. 问题与机会登记器</title>
    收集运行失败、成本异常、质量退化、重复人工干预和潜在改进机会。



    <title size="lg">2. 根因与影响分析器</title>
    关联能力图谱、依赖版本和历史证据，识别可能的根因、影响范围及不确定性。



    <title size="lg">3. 改进候选生成器</title>
    为问题生成可验证的方案，声明预期收益、修改范围、测试计划、成本和回滚策略。



    <title size="lg">4. 进化决策器</title>
    执行硬门槛检查、多目标排序、预算分配和有限探索，选择最值得实验的候选。



    <title size="lg">5. 实验与独立评测器</title>
    在隔离环境中比较基线与候选，执行分层回归、成本评估和副作用检查。



    <title size="lg">6. 发布与收益监测器</title>
    管理批准、分批发布、运行观测、停止推广、回滚和长期收益追踪。


其中有一条必须坚持的架构规则：

**候选生成器可以提出改动，但不能自行决定自己的改动通过了验收；进化决策器可以安排实验，但不能绕过系统硬约束；发布器只能发布已经获得授权的版本。**

这三个职责必须分离。

## 九、V0.1 不应该一开始就实现复杂的智能优化算法

我建议采用三个阶段。

| 阶段 | 实现方式 | 验收目标 |
|---|---|---|
| V0.1：可控进化 | 规则门槛、可解释排序、固定预算、人工批准高风险变更 | 系统能从问题记录中提出候选，并完成一次可复现的评测与发布决策 |
| V0.2：证据驱动 | 增加收益估计、置信区间、历史实验对比、自动选择回归集 | 能够减少无效实验，合理调整测试投入 |
| V0.3+：自适应调度 | 基于历史实验学习不同改进策略的收益，动态调整探索和预算 | 在质量、安全门槛不退化的前提下，提高长期进化效率 |

第一版的重点不是让系统“聪明地决定一切”，而是让每个决定可解释、可追踪、可拒绝、可复现。

我们甚至可以先不允许它自动修改任何代码，而只允许它：

1. 发现问题。
2. 提出改进候选。
3. 估算成本和影响范围。
4. 自动运行隔离测试。
5. 根据门槛给出发布建议。

等这条链路可靠以后，再逐步开放低风险候选的自动发布权限。

# 十、这一轮的核心结论

我们现在已经有了三个相互连接的机制：

- **能力图谱：** 确定系统拥有哪些能力、它们依赖什么，以及改动可能影响谁。
- **经验迁移机制：** 判断一项经验是否只属于某个专家，还是具备跨领域复用价值。
- **进化决策机制：** 决定当前最值得改什么、投入多少资源、需要什么证据，以及何时停止。

这三个机制共同构成 EvoAgent 的进化中枢。

我还想强调一个容易被忽略的原则：**最好的进化系统，不是修改次数最多的系统，而是在有限资源下，能够持续找到值得解决的问题，并用证据证明改进有效的系统。**

## 下一轮最值得深入的问题

我建议接下来研究一个更底层的难题：**EvoAgent 如何构建可靠的评测与因果诊断系统？**

因为目前所有进化决策都依赖一个前提：系统能够判断一次改进究竟有没有产生真实收益。

如果评测器本身不可靠，系统就可能奖励错误的改动；如果根因诊断把相关性误认为因果关系，进化系统就会不断修错方向。

下一轮我们可以重点探讨：

1. 如何设计真实任务评测集，防止候选版本对测试集过拟合。
2. 如何通过对照实验区分模型、提示词、记忆、工具和上下文的影响。
3. 如何处理样本量不足、随机波动和不确定性。
4. 如何让评测器独立于候选实现，避免自我评估造成偏差。
5. 如何把评测结果转化为能力图谱中的长期证据，并影响后续进化决策。

这一步完成后，EvoAgent 的“发现问题—决定优化—执行实验—判断收益”才会真正闭环。
