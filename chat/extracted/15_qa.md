# 一、先完整拆解：一个智能体究竟由什么组成？

我建议把 EvoAgent 拆成 **12 个核心子系统、3 个贯穿全系统的基础平台、1 个独立进化中枢**。

  <title size="lg">EvoAgent 完整能力地图</title>



      **01 · 交互与意图理解**

    语音识别、自然语言理解、意图分类、约束提取、目标澄清、完成条件识别。




      **02 · 推理与决策**

    模型调用、提示词、ReAct、Planning、任务分解、重新规划、停止条件、模型路由。




      **03 · 记忆与知识**

    工作记忆、情景记忆、语义记忆、程序记忆、用户偏好、知识检索、遗忘和记忆更新。




      **04 · 上下文治理**

      **05 · 工具与环境交互**

    工具注册、API 适配、Android 原生接口、无障碍操作、视觉识别、工具健康和权限管理。




      **06 · 技能与工作流**

      **09 · 观察、诊断与故障恢复**

    运行轨迹、错误分类、因果假设、根因分析、故障定位、恢复策略和异常检测。




      **10 · 学习与经验提炼**

    从成功与失败中提取经验、更新技能、生成工作流候选、积累回归案例、迁移已有知识。




      **11 · 评测与实验**

    基准测试、对照实验、失败注入、消融实验、统计置信度、回归检测和发布门禁。




      **12 · 自身配置与版本管理**

    提示词版本、模型档案、上下文策略、规划策略、Harness 版本、依赖清单、发布与回滚。

      事件日志、指标、追踪、数据库、资产存储、数据脱敏与审计。





      **B. 安全与治理平台**

      权限、隐私、风险等级、用户授权、版本签名和发布约束。





      **C. 端云协同平台**

      Android 稳定运行、云端深度分析、离线能力、同步、配置分发和兼容性检查。





      **独立进化中枢（Evolution Controller）**

    决定哪些问题值得改、应该修改哪个子系统、如何设计实验、如何评估改进，以及何时拒绝、发布或回滚。


这张地图是产品级的完整能力划分，不意味着第一版就需要实现 12 个独立服务。很多子系统最初可以是同一个 Python 后端中的模块，等职责和负载明确后再拆分。

还要注意，**记忆、上下文、学习不是同一个模块**：

- 记忆负责保存什么信息。
- 上下文治理负责当前任务应该取用哪些信息。
- 学习负责从新证据中提炼什么值得改变。
- 进化中枢负责决定改变是否有效，以及能否发布。

这四者必须协作，但不能混成一个无限增长的“智能体大脑”。

# 二、最重要的遗漏：记忆系统本身也必须能够进化

你专门提到记忆，我认为这是整个架构中最值得单独设计的部分之一。

如果 EvoAgent 只记录运行日志，却没有把有价值的信息变成可检索、可更新、可纠错的长期记忆，它就会不断重复犯错。

反过来，如果它把所有聊天、错误和执行结果全部存成永久记忆，又会导致记忆污染、检索混乱、上下文膨胀，甚至把一次错误当成长期事实。

所以我们需要的不只是 Memory Store，而是完整的 **Memory Lifecycle（记忆生命周期管理）**。

## 2.1 记忆至少应该有六类

| 记忆类型 | 保存什么 | 如何改进 |
|---|---|---|
| 工作记忆 | 当前任务目标、约束、待办事项、临时状态 | 优化状态更新、压缩和丢失检测 |
| 情景记忆 | 某次任务如何执行、发生了什么、最终结果如何 | 优化事件摘要、检索和经验提取 |
| 语义记忆 | 已验证的事实、规则、概念和环境知识 | 优化事实核验、冲突解决和过期检测 |
| 程序记忆 | 已验证的技能、工具使用方法、工作流和恢复策略 | 优化技能提炼、流程版本化和复用 |
| 用户偏好记忆 | 用户明确表达的偏好、长期设置和授权范围 | 优化偏好提取、适用范围和冲突处理 |
| 失败经验记忆 | 哪些方法失败、失败条件、原因证据和有效修复方式 | 优化故障检索、相似案例匹配和反例测试 |

这六类记忆是逻辑上的分类，不一定需要六个独立数据库。

其中有两个必须特别注意的区别：

**第一，记录失败不等于学会避免失败。**

例如，记忆中保存了“调用工具 X 失败”。这只是一条事件。真正有用的失败经验还应该记录：

- 当时的输入和环境是什么。
- 工具返回了什么错误。
- 根因是否已确认，还是仅有推测。
- 哪些修复方案被尝试过。
- 哪些方案经过测试有效。
- 这个经验适用于哪些版本和条件。
- 哪些相似情形不应该套用该经验。

**第二，记忆越多不代表智能体越聪明。**

系统需要学会何时检索、什么时候不使用旧记忆、如何识别冲突，以及什么时候应当放弃过时经验。

## 2.2 记忆进化的完整闭环

<CodeBlock language="mermaid" editable={false}>flowchart TD
    A[任务执行与环境观察] --> B[生成候选记忆]
    B --> C[分类与来源标注]
    C --> D[验证事实、置信度与适用范围]
    D --> E{是否值得保存}
    E -->|否| F[丢弃或仅保留短期事件]
    E -->|是| G[写入对应记忆库]
    G --> H[检索与使用反馈]
    H --> I[评估记忆是否帮助任务]
    I --> J[更新、降权、标记过期或保留]
    J --> K[回归测试记忆策略]
    K --> L[发布新的记忆策略]
    L --> H</CodeBlock>

这意味着，EvoAgent 不仅要学习“做事的方法”，还要学习**什么值得记住、记多久、在什么情况下使用，以及什么时候不再相信它**。

例如：

- 用户明确要求“以后优先使用某种输出格式”，可以进入待确认或已确认的偏好记忆。
- 某次视频生成失败，通常先作为情景记忆记录。
- 多次验证发现某个 API 版本不接受某参数，才有理由形成有版本和适用范围的工具知识。
- 某个工作流经过多次独立验收后，可以晋级为程序记忆中的稳定能力。
- 旧模型上形成的经验，在新模型上需要重新验证后，才能升级为新模型的适配知识。

用户明确表达的长期偏好与高影响授权，不应仅仅因为统计结果发生变化就被自动覆盖。记忆系统可以提出修改建议，但需要尊重用户的控制权。

## 2.3 记忆系统本身优化什么？

至少要有四类独立指标：

- **记忆准确性：** 保存的信息是否真实、来源是否清楚、是否过期。
- **记忆召回质量：** 相关任务能否检索到真正有用的信息。
- **记忆使用收益：** 使用记忆后，任务质量是否改善、成本是否下降。
- **记忆污染率：** 错误、矛盾、无关或不应长期保存的信息是否进入了长期记忆。

如果服务端发现记忆检索经常召回无关内容，可以先优化检索策略；如果发现事实本身已经过期，就应更新知识，而不是不断调整检索算法。

这也再次说明，诊断必须能够区分问题发生在哪一个子系统。

# 三、给每一个子系统建立“可进化清单”

这一步是整个项目从概念设计进入工程设计的关键。

我们不能只说“所有模块都可以优化”，而应该明确每个模块：

1. 哪些对象能够改变。
2. 通过什么证据判断需要改变。
3. 用什么方法验证。
4. 哪些变化允许自动发布。
5. 失败后怎样回滚。

我建议建立下面这张总表，作为 EvoAgent 后续开发时的进化注册表。

| 子系统 | 可优化对象 | 主要评测证据 |
|---|---|---|
| 意图理解 | 分类策略、提示词、约束提取器 | 意图准确率、关键约束遗漏率 |
| 推理与决策 | Prompt、规划策略、ReAct 参数、停止策略 | 任务成功率、无效步骤率、成本 |
| 记忆系统 | 写入规则、记忆分类、检索、更新与遗忘策略 | 召回质量、记忆使用收益、污染率 |
| 上下文治理 | 摘要策略、优先级、检索预算、压缩策略 | 关键信息保留率、Token 成本 |
| 工具系统 | 适配器、参数构造、工具路由、健康检测 | 契约通过率、工具故障率、恢复率 |
| 技能与工作流 | 技能定义、DAG、条件、恢复分支 | 工作流成功率、复用率、执行耗时 |
| Harness | 超时、重试、幂等、检查点、调度策略 | 故障恢复率、重复执行率、稳定性 |
| 质量验证 | 验收规则、结果验证器、质量检查 | 漏检率、误报率、独立验收通过率 |
| 诊断系统 | 错误分类、根因假设、故障关联规则 | 根因判断准确性、修复建议有效率 |
| 学习系统 | 经验提炼、泛化判断、技能晋级规则 | 新任务迁移效果、错误经验率 |
| 评测系统 | 测试集覆盖、边界案例、统计方法 | 回归检出率、漏测率、评测可复现性 |
| 配置与模型适配 | 模型档案、提示词版本、参数组合 | 模型兼容性、质量、成本、延迟 |
| 安全与权限 | 风险检测覆盖、授权流程、审计能力 | 未授权动作数、策略违规率 |
| 端云协同 | 同步、离线策略、更新分批与回滚 | 更新失败率、离线成功率、版本一致性 |

有一个细节必须明确：**评测系统本身也会有缺陷，因此不能只依赖单一评测分数。**

比如，某个新 Planning 策略让任务完成率提高了，但代价是增加了大量不必要的工具调用。系统必须同时看质量、成本、时延和风险指标，而不是只优化其中一个数字。

此外，安全机制不是普通的优化目标。我们可以改进检测能力、降低误报、增强审计，但不能让进化系统为了提高任务成功率而放宽硬性授权边界。

## 进化不应该一次改动整个智能体

假设一次任务失败，诊断结果认为问题来自记忆检索。

正确的改进流程应该是：

- 锁定当前稳定版本。
- 复制一份候选配置。
- 只修改记忆检索策略。
- 在相同的测试集上运行新旧版本。
- 检查记忆召回质量、任务成功率、成本以及其他任务的回归情况。
- 达到门禁要求后，再把新策略纳入发布清单。

如果同时修改提示词、记忆、上下文、Planning 和 Harness，即使结果变好了，也很难知道究竟是什么产生了效果；如果结果变差，更难确定应该撤销哪项修改。

因此，我建议进化系统默认采用**单因素优先、组合实验补充**的方式。对于组件之间存在明显交互的情况，再设计组合实验，避免把复杂的相互作用误判为某个模块的单独贡献。

# 四、谁来进化这些模块？不能让智能体自己给自己打分

我建议把 EvoAgent 内部划分成四个职责不同的角色。它们可以由不同的模型、程序模块或隔离任务实现，不一定是四个独立的大模型。






      **角色 A：执行智能体**

      负责理解目标、使用记忆、规划和执行任务。它可以报告自己遇到的问题，但不能仅凭自身判断就认定问题根因。








      **角色 B：诊断智能体**

      分析轨迹、工具日志、记忆命中、上下文变化和结果验收证据，提出根因假设，并说明证据与不确定性。








      **角色 C：进化与实验智能体**

      选择可改进对象，生成候选配置或代码分支，设计测试，比较新旧版本。它负责提出和验证改进，而不是直接把改动发布到稳定环境。








      **角色 D：独立验收与发布控制器**

      执行固定的质量、安全、兼容性和成本门禁，检查候选版本是否符合要求，并控制发布、停止扩散或回滚。



尤其要避免一个循环漏洞：进化智能体修改了评测规则，随后又用修改后的规则证明自己通过了测试。

候选版本可以提出新增测试，但不能单方面删除原有失败案例、修改硬性门禁或批准自己的发布。最终验收应由权限独立、规则受控的发布控制器执行。

# 五、手机端和服务端分别负责什么？

对你计划中的 EvoAgent Mobile，我建议采用下面的部署分工。

| 能力 | Android 端 | 服务端 |
|---|---|---|
| ReAct 与 Planning | 执行当前生效策略；支持基本离线任务 | 深度规划实验、策略比较 |
| 记忆 | 本地工作状态、允许离线使用的记忆 | 授权同步后的跨任务记忆、复杂检索与评估 |
| 上下文治理 | 按当前策略组装上下文 | 优化候选策略并进行回归测试 |
| Harness | 执行控制、权限、检查点、取消 | 候选代码构建、复杂故障复现 |
| 工具系统 | 手机原生能力、无障碍操作、网络工具调用 | 云端工具、外部 API、工具适配测试 |
| 工作流 | 执行已发布的适用流程 | 编译候选流程、版本验证 |
| 诊断 | 收集本地事件、进行有限诊断 | 深度根因分析、跨任务统计 |
| 学习与进化 | 记录经验、使用已发布策略 | 生成候选、实验、验收和发布 |
| 模型与配置 | 使用兼容的当前版本 | 维护模型档案和候选发布清单 |

这并不意味着所有记忆都应该上传云端。敏感记忆可以只保留在设备上；上传范围应由用户授权、数据分类和隐私策略决定。

同样，云端生成的新版本也不能直接覆盖手机上的运行配置。应先验证设备能力、模型兼容性、工具版本与依赖，再在安全检查点切换。

如果新版出现问题，手机端应能回到最近的兼容稳定版。对于涉及原生代码的更新，还需要独立的软件签名、安装和回滚机制。

# 六、最终形成一套真正完整的自进化闭环

我建议把 EvoAgent 的完整闭环正式定义为：

<CodeBlock language="mermaid" editable={false}>flowchart TD
    A[用户目标] --> B[意图理解与任务规划]
    B --> C[记忆检索与上下文组装]
    C --> D[Harness 控制下的执行]
    D --> E[工具交互与工作流运行]
    E --> F[独立结果验收]
    F --> G[任务结果与运行证据]
    G --> H[记忆更新与经验提炼]
    G --> I[问题诊断与根因假设]
    H --> J[进化候选]
    I --> J
    J --> K[隔离实验与回归评测]
    K --> L{独立门禁}
    L -->|通过| M[版本发布与端云分发]
    L -->|失败| N[拒绝、记录与重新诊断]
    M --> O[运行监测与回滚]
    O --> A</CodeBlock>

这张图里有两个不同的学习方向：

- **任务经验学习：** 让系统学会更好地完成任务，例如积累工具用法、稳定工作流和用户偏好。
- **智能体自身进化：** 改进系统完成任务的方法，例如优化记忆检索、上下文管理、ReAct、Planning、Harness 和诊断策略。

两者相互促进，但必须分开评测。

如果工作流变好了，说明某类任务能力有所提升；如果记忆系统能把有效经验迁移到未见过的任务，才进一步说明它的泛化能力有所改善。如果新模型上的提示词和 Planning 策略经过对照实验后表现更好，才有证据说相应的智能体配置获得了提升。

**这就是我们真正要构建的系统：不仅能够积累任务能力，还能够持续改进承载这些能力的整个智能体。**

## 七、我建议接下来正式冻结的设计原则

为了避免项目继续因为新增概念而反复重构，我建议把以下内容确定为 EvoAgent 的架构基线：

1. **完整纳入可进化对象。** 不仅有提示词、Harness、ReAct 和 Planning，还包括记忆、上下文、工具认知、技能、工作流、诊断、学习和模型适配。
2. **每个子系统都必须可观测、可评测、可版本化。** 没有对应指标和回归测试的模块，不应直接进入自动进化。
3. **任务执行、记忆学习和自身进化职责分离。** 它们可以共享数据，但不能互相替代。
4. **稳定运行与候选进化严格隔离。** 只有通过独立门禁的版本才能进入稳定环境。
5. **允许拒绝改进。** 证据不足、效果不明确或存在回归风险时，维持原版本就是正确的决定。
6. **模型、工具、记忆策略和工作流分别管理版本。** 每次运行都能追溯实际使用的配置组合。
7. **以长期任务表现衡量进化。** 关注成功率、恢复能力、记忆收益、跨任务迁移、成本、时延和安全性，而不是系统修改了多少次自己。

我还想补充一个最终边界：我们可以把上述系统设计成高度自主、能够持续改进的智能体，但不能预先保证它会达到某种“完美状态”。不同模型、工具、环境和任务都可能发生变化。EvoAgent 真正应该达到的成熟状态，是能够知道自己的能力边界、用证据评估自身、可靠地积累经验，并在不确定时安全地停止，而不是宣称自己已经完美。

**下一步应该交付的核心设计文档，不再只是 PRD 和普通技术架构，而应该是《EvoAgent 完整自进化架构规范》：逐一规定这 12 个子系统的内部职责、接口、记忆模型、可进化对象、评测指标、端云边界和版本发布机制。** 这份规范应该成为以后增加手机操作、AI 漫剧、编程和其他能力包时共同遵循的底层设计依据。
