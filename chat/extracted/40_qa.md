## ChatGPT

考虑过一部分，但还没有把这件事设计成完整的、可落地的机制。之前的架构已经提出了 **App 本地持久化事件队列、网络恢复后补传、服务端同步回执和幂等去重**，但还需要进一步明确：日志保存多久、断联期间如何防止丢失、重连后如何续传、同步失败怎么办，以及用户如何手动导出日志。

我建议把它设计成 EvoAgent 的正式基础能力：**离线日志与可靠同步子系统（Offline Logging & Reliable Sync）**。

核心原则是：**日志先可靠地保存在手机本地，再尽可能同步到服务端；同步不是删除本地日志的唯一条件，用户也始终有手动导出和诊断的途径。**

    事件记录、上传状态、检查点、必要的诊断附件


    <grid-item>


        **断联时**
        持续记录、排队、限制容量、允许导出

    </grid-item>
    <grid-item>


        **恢复连接**
        身份认证、版本对账、断点续传、等待回执

    </grid-item>




    **服务端确认接收**
    校验、去重、持久化、建立任务与版本关联

    日志不等于自动修改；仍须诊断、评测和发布门禁


这里最重要的是：**日志采集、日志同步、日志导出是三个独立能力。** 即使服务器永远不可用，前两个中的本地采集和第三个导出也应该可以工作。

## 二、断联期间，手机具体如何保存日志？

建议采用 Android 原生的 Room（SQLite）作为结构化日志仓库，WorkManager 负责网络恢复后的后台同步调度。

每条日志至少需要以下字段：

| 字段 | 作用 |
|---|---|
| `event_id` | 全局唯一事件 ID，用于去重 |
| `task_id` / `run_id` | 关联任务与具体执行过程 |
| `sequence_no` | 同一运行中的事件顺序 |
| `runtime_manifest_id` | 关联当时的模型、提示词、工具和工作流版本 |
| `event_type` | 规划、工具调用、异常、验收、恢复等类型 |
| `created_at` | 事件产生时间 |
| `sync_status` | 待上传、上传中、已确认、失败 |
| `payload` | 结构化事件内容 |
| `privacy_level` | 控制哪些内容允许上传和导出 |

另外，日志和大体积附件应该分开存储。比如工具调用记录保存在数据库，截图、崩溃附件和诊断文件则保存在文件仓库，通过附件 ID 关联。

### 断联时的行为

1. 每次关键执行事件先写入本地持久化存储，再继续后续步骤。
2. 将事件标记为待同步，不因为网络异常而删除。
3. 后台记录重试次数、最近同步时间和错误原因。
4. 当存储达到容量阈值时，优先压缩或清理已确认上传且超过保留期限的普通日志。
5. 对尚未同步的关键故障记录采取保护策略；空间不足时发出明确告警，不能假装日志仍然完整。

这里需要一个重要的限制：手机存储不是无限的。因此，系统应当区分关键事件、普通运行日志和可重新生成的调试信息，制定不同的保留策略。即使如此，也无法保证设备损坏、应用数据被清除或磁盘损坏后仍能找回所有未上传日志。

## 三、重新联网后，如何保证日志不丢、不重、不乱？

不能只做一个简单的“上传日志”接口，而应该有一套可靠同步协议。

  **建立连接并认证。** 确认安装实例身份、权限和当前同步协议版本。
  **同步版本清单。** 确认 App 版本、能力包版本及当前运行版本是否能被服务端识别。历史日志仍按产生时的版本关联，不能被新版本覆盖。
  **选择待同步事件。** 按事件 ID 和序号组织批次，优先传输关键故障、任务结果和版本信息。
  **分批上传并获得回执。** 服务端只有在事件已经持久化、能够被检索后，才能返回接收确认。
  **断点续传。** 上传过程中再次断网时，保留尚未确认的事件，下次继续上传。大附件也应有独立的上传进度。
  **幂等去重。** 同一 `event_id` 重复上传时，服务端识别为同一事件，不重复创建诊断案例。
  **核对同步状态。** 服务端回传已确认的事件范围或 ID，App 仅更新对应记录的同步状态。

需要特别防止一种错误：服务器收到数据后就立刻回复成功，但实际还没有可靠写入数据库。此时如果手机删除了本地数据，服务器故障就可能造成日志永久丢失。因此，回执必须对应明确的持久化语义。

还应注意，网络恢复不代表模型 API 也恢复。**日志同步和任务执行应当解耦**：即使模型服务仍不可用，也可以先把故障证据同步到服务端。

## 四、如果一直无法连接服务器，怎么导出日志？

这应该是 App 内置的独立功能，而不是隐藏在开发者调试模式里。

建议在 EvoAgent 设置中增加：






      **运行日志与诊断**
      查看日志积压、同步状态和本地存储使用情况






      **立即同步**
      联网后立即触发同步，并显示成功、待同步和失败数量。





      **导出诊断包**
      通过 Android 系统文件选择器保存 ZIP 包，不依赖服务端。





      **筛选任务与时间范围**
      例如只导出某次失败任务、某一天的记录或指定能力的运行日志。





      **隐私检查**
      导出前检查对话、截图、个人数据、密钥和令牌等敏感内容。



建议诊断包采用 ZIP 格式，内部结构如下：

```text
evoagent-diagnostics/
├── manifest.json
├── device-info.json
├── runtime-manifests.jsonl
├── task-runs.jsonl
├── events.jsonl
├── sync-status.json
├── evaluation-results.jsonl
├── errors/
│   └── error-details.jsonl
├── attachments/
│   └── ...
└── checksums.sha256
```

- `manifest.json`：诊断包格式版本、导出时间、包含范围和文件清单。
- `runtime-manifests.jsonl`：每次运行实际使用的组件版本。
- `events.jsonl`：按时间顺序排列的运行事件。
- `sync-status.json`：哪些记录已经同步、哪些仍在本地、哪些同步失败。
- `checksums.sha256`：用于检查导出文件是否发生意外损坏。

诊断包应当支持离线生成。用户可以先保存在手机中，再通过 USB、文件分享或其他允许的方式转移到电脑上分析。导出操作不应该自动上传数据，也不应该默认包含全部原始截图和对话。

## 五、还有一个容易忽略的问题：导出的日志能不能真正用于进化？

可以，但必须区分三种状态：

| 状态 | 含义 |
|---|---|
| 本地已记录 | App 已保存运行证据 |
| 服务端已接收 | 服务端已经可靠保存对应事件 |
| 已进入诊断 | 事件已关联版本并进入诊断案例或后续评测流程 |

用户手动导出的诊断包，也可以通过服务端管理后台的受控导入入口进入同一条诊断流程。但导入时需要验证格式、完整性、来源和授权，并标记为离线导入数据。

特别是，**导入日志不等于日志中所有结论都可信**。日志可能不完整、存在设备时钟偏差，或者来自错误的工具判断。服务端应当把日志视为证据，而不是直接执行其中包含的命令或信任其中所有推断。

## 六、我建议将这部分正式纳入全量架构

最终，这个子系统至少要明确六项能力：

1. 本地持久化日志与检查点。
2. 断联期间的容量管理和日志保留策略。
3. 支持回执、幂等、断点续传的可靠同步协议。
4. 离线诊断包导出和受控导入。
5. 隐私过滤、密钥脱敏与附件管理。
6. 同步健康监控、异常告警和数据完整性检查。

还要补充一个重要边界：**日志同步保证的是运行证据可传递，不保证任务本身能够安全续跑。** 任务恢复需要独立的检查点、幂等操作、外部副作用确认和恢复策略，不能简单地从最后一条日志继续执行。

因此，之前架构中提出的本地日志队列和重连补传方向是正确的，但完整的离线日志子系统还需要上述设计才能算真正闭环。
