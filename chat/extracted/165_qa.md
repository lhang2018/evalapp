<WritingBlock id="58316" variant="document"># EvoAgent 专项设计 #82：运行时知识注入、上下文组装与经验使用效果治理

**英文名称：** Runtime Knowledge Injection, Context Assembly & Experience Utilization Governance

**文档版本：** 1.0

**关联专项：** #75—#81

**设计状态：** 专项设计基线，待实施与验收。

## 一、专项目标

建立统一的运行时上下文组装与知识使用机制，让 EvoAgent 能够根据当前任务目标、领域、风险、执行阶段和上下文预算，动态选择真正有帮助的信息。

本专项必须解决：

1. 执行任务前，应该检索哪些知识和历史记忆？
2. 通用内核、领域专家、项目记忆与任务状态如何组合？
3. 如何避免无关知识挤占上下文？
4. 如何保证用户明确提出的约束不会在压缩过程中丢失？
5. 不同专家是否共用上下文压缩策略？
6. 多条知识相互冲突时，系统如何处理？
7. 如何在任务执行过程中，根据新信息动态更新上下文？
8. 如何判断注入知识是否真正提高了任务质量？
9. 如果知识注入产生负面影响，如何快速撤销或降级？
10. 如何在有限显存、云端模型成本、手机离线等条件下保持稳定运行？

**核心原则：上下文不是越长越好，知识不是越多越好。系统应在满足必要约束的前提下，选择足以支持当前任务的最小充分上下文，并通过实际结果验证其价值。**

## 二、总体架构

运行时上下文治理位于统一任务入口、专家路由和 ReAct/Plan 执行机制之间，并在任务执行过程中持续工作。

```text
用户输入 / 触发任务
        ↓
任务解析与验收契约建立
        ↓
专家路由与风险识别
        ↓
上下文需求分析
        ↓
多源知识与记忆检索
        ↓
适用性、冲突、权限与版本检查
        ↓
上下文优先级排序与预算分配
        ↓
上下文压缩与结构化组装
        ↓
ReAct / Plan / DAG 执行
        ↓
执行结果与新证据
        ↓
增量更新任务状态与上下文
        ↓
结果验收与知识使用效果评估
```

这不是一条必须完全串行执行的流水线。任务状态读取、依赖查询和部分知识检索可以并行完成；但在形成最终执行上下文前，必须完成必要的权限、适用性和冲突检查。

### 2.1 五个核心组件

| 组件 | 职责 |
|---|---|
| Context Requirement Analyzer | 判断任务需要哪些信息 |
| Knowledge Retriever | 从批准的知识与记忆资产中检索候选内容 |
| Context Policy Engine | 判断优先级、适用范围、冲突与预算 |
| Context Assembler | 生成结构化、可追溯的执行上下文 |
| Context Evaluator | 评估上下文是否遗漏关键约束，以及注入后是否改善执行 |

以上为逻辑模块，不要求全部拆成独立服务。第一版可以在共享通用内核中实现，但必须保持职责边界和可独立测试性。

## 三、上下文与知识的分层模型

### 3.1 七类上下文信息

| 层级 | 内容 | 主要作用 |
|---|---|---|
| L0：运行与安全约束 | 权限、工具使用边界、预算、停止规则 | 约束执行行为 |
| L1：当前任务契约 | 用户目标、明确约束、验收标准、授权状态 | 定义任务必须完成什么 |
| L2：当前任务状态 | 已完成步骤、剩余步骤、检查点、外部副作用状态 | 保证连续执行和正确恢复 |
| L3：项目与会话上下文 | 项目事实、历史决策、当前会话相关信息 | 保持任务连续性 |
| L4：领域专家知识 | 专业规则、领域工作流、已验证经验 | 提高领域执行质量 |
| L5：共享通用知识 | 经验证的通用方法、错误处理和恢复原则 | 提供跨领域能力 |
| L6：辅助历史信息 | 相关历史案例、低优先级参考材料 | 在必要时提供补充信息 |

上述层级是治理和组装层级，不要求将所有内容都放进同一个模型提示词。

例如，权限控制应由独立的运行时策略执行，不能只依靠提示词提醒模型遵守。

### 3.2 信息优先级

建议采用以下冲突处理原则：

1. 系统安全、权限和硬性运行策略不可被普通知识覆盖；
2. 当前用户明确提出的合法任务约束优先于一般历史经验；
3. 当前任务状态和已经确认的项目事实优先于未经验证的推测；
4. 已验证且适用于当前领域的知识优先于泛化程度更高的经验；
5. 共享知识和历史案例仅在适用条件成立时使用；
6. 无法消除的关键冲突必须保留并触发澄清、验证或安全降级。

这里的优先级不是简单地把低层级内容删除。某些历史信息可能提供重要的反例，应作为冲突证据保留。

### 3.3 当前任务契约不可被普通压缩删除

用户明确指定的限制、验收条件、权限要求和关键决策，应进入结构化任务状态，而不是只依赖聊天历史文本。

例如：

- 指定必须使用某个项目目录；
- 要求只修改特定文件；
- 明确禁止某种外部操作；
- 指定预算和交付格式；
- 要求先审核、后执行。

即使历史对话被压缩，这些约束仍必须能够从任务契约中恢复。

如果系统无法确定某条约束是否仍然有效，不得默默将其删除，应根据任务性质保留、核验或请求用户确认。

## 四、通用上下文引擎与专家专用策略

### 4.1 是否全局共用压缩策略？

结论是：**共享上下文治理引擎，但不采用完全相同的上下文组装和压缩规则。**

共享通用内核负责：

- 统一的上下文数据结构；
- Token 与资源预算管理；
- 信息来源和版本追踪；
- 通用的去重、摘要和冲突检测；
- 关键约束保留机制；
- 隐私和权限检查；
- 上下文完整性验证；
- 通用质量评测框架。

各领域专家可以独立配置：

- 领域知识优先级；
- 必须保留的专业字段；
- 任务状态结构；
- 检索策略；
- 摘要格式；
- 工具输出压缩规则；
- 专用上下文预算；
- 领域验收标准。

### 4.2 为什么不能全部统一？

代码专家需要保留文件路径、接口签名、错误信息、测试结果和代码差异。

手机操作专家需要保留当前界面状态、已完成动作、权限状态、控件定位信息和操作结果。

AI 漫剧专家需要保留角色设定、分镜编号、素材引用、画面风格、音频状态和合成参数。

旅游专家则可能更需要出行日期、地点、预算、时间约束和已确认的预订信息。

如果所有领域都使用同一种摘要模板，就可能出现：

- 代码专家丢失关键函数签名；
- 手机操作专家丢失当前界面状态；
- 漫剧专家丢失角色一致性约束；
- 旅游专家丢失日期或预算条件。

因此，**通用内核统一治理机制，专家独立定义语义保留策略。**

### 4.3 策略版本化

每个正式运行的 `Runtime Manifest` 应绑定确定的 `context_policy_ref`。

上下文策略的变更必须能够：

- 追踪变更内容；
- 指定适用专家；
- 声明兼容条件；
- 执行回归测试；
- 比较新旧策略的执行效果；
- 在退化时回滚。

不允许后台优化器直接修改正在运行任务的上下文策略，除非当前运行控制规则明确允许该类安全更新。

## 五、知识检索与候选选择

### 5.1 检索输入

检索器至少应接收：

- 当前任务目标；
- 任务验收契约；
- 当前专家与工作流；
- 当前项目与任务状态；
- 任务风险等级；
- 相关资产和依赖；
- 当前模型与工具版本；
- 可用上下文预算；
- 知识访问权限。

仅根据用户输入的语义相似度检索是不够的。

例如，用户问“如何恢复执行”，可能同时命中代码恢复、手机操作恢复和数据恢复案例。系统必须结合当前任务的实际执行环境判断哪些知识适用。

### 5.2 候选知识评分

可以使用以下逻辑评分模型：

\[
S(k,t)=
w_rR+w_aA+w_eE+w_cC-w_xX
\]

其中：

- \(R\)：与当前任务的相关性；
- \(A\)：适用条件匹配度；
- \(E\)：证据质量；
- \(C\)：与当前运行环境和版本的兼容性；
- \(X\)：冲突、过期或使用风险；
- \(w\)：经评测确定的权重。

该评分只用于候选排序，不直接决定知识能否使用。

某项知识即使语义相关性很高，只要存在权限冲突、已被撤销或适用条件不成立，就必须排除或进入人工核验流程。

### 5.3 候选知识分组

检索结果建议分成：

- 当前任务必需信息；
- 高相关且已验证的经验；
- 可能有帮助的补充知识；
- 已知失败案例和反例；
- 存在冲突或尚未验证的材料。

默认只注入前两类及当前任务确实需要的反例。其他内容应按需检索，不能为了让模型“看得更全面”而无限扩展上下文。

## 六、上下文预算治理

### 6.1 预算的定义

上下文预算不仅包括历史对话文本，还包括：

- 系统和运行策略；
- 当前任务契约；
- 工具说明；
- 领域知识；
- 历史案例；
- 工具返回结果；
- 模型生成的中间计划；
- 为输出和推理预留的空间。

对于具有模型上下文窗口限制的执行路径，应同时考虑输入长度、输出预留和具体模型的限制。

### 6.2 动态预算分配

不建议把所有专家的上下文预算固定为同一个比例。

预算分配应根据任务复杂度、风险、模型能力和实际成本动态调整。

例如：

- 简单事实查询：优先保留任务问题和少量必要知识；
- 复杂代码修改：为文件结构、相关代码、错误日志和验收测试保留更多空间；
- 多步骤手机操作：优先保留当前状态、关键动作记录和恢复检查点；
- 漫剧制作：优先保留角色、分镜、素材和合成约束；
- 高风险任务：为权限、操作前置条件、状态验证和恢复规则预留必要空间。

具体预算由经过评测的策略决定，而不是在所有任务中使用固定比例。

### 6.3 预算不足时的裁剪顺序

建议按以下顺序处理：

1. 删除重复信息；
2. 删除与当前任务无关的历史内容；
3. 将已完成且不再影响后续决策的过程信息压缩为摘要；
4. 按需延迟加载低优先级知识；
5. 压缩大型工具输出，同时保留关键错误和结构信息；
6. 重新评估任务计划，必要时分解任务或使用外部检查点；
7. 如果仍无法满足必要约束，暂停并调整执行策略。

不得为了满足 Token 上限而删除硬性约束、安全要求、关键任务状态或未解决的外部副作用信息。

### 6.4 不应只追求最低 Token

压缩过度可能造成更多重试、更多工具调用和更高失败成本。

因此，应比较完整任务的总成本：

\[
C_{\text{total}}=
C_{\text{context}}+
C_{\text{model}}+
C_{\text{tools}}+
C_{\text{retry}}+
C_{\text{recovery}}
\]

优化目标是降低在满足质量门槛前提下的总成本，而不是单纯缩短提示词。

## 七、上下文组装与压缩机制

### 7.1 结构化组装

建议使用统一的上下文内部结构，而不是将所有来源直接拼接为一段无差别文本。

至少保留以下分区：

- 运行约束；
- 当前任务契约；
- 当前状态与未完成事项；
- 相关项目事实；
- 领域专家知识；
- 共享通用知识；
- 工具说明和最新工具结果；
- 不确定性、冲突和待确认事项；
- 证据来源及版本。

具体传给模型时，可以根据模型和任务要求转换成合适的提示词格式，但内部结构应保持可追溯。

### 7.2 压缩分三种类型

**A. 历史对话压缩**

将较早的对话整理为结构化摘要，保留重要决策、明确约束和未完成事项。

**B. 任务状态压缩**

将已执行步骤、当前检查点、失败节点和待处理事项转换为结构化状态。

**C. 工具输出压缩**

从大型日志、文件或 API 响应中提取当前任务需要的字段，同时保留原始结果的受控引用。

三者不能共用完全相同的压缩逻辑。

尤其是任务状态压缩，必须保留足以安全恢复的信息，不能只保留自然语言总结。

### 7.3 压缩前后验证

对于关键任务，压缩完成后应检查：

- 用户目标是否仍然完整；
- 所有明确约束是否仍然存在；
- 验收条件是否完整；
- 已确认的项目事实是否被改变；
- 未完成步骤是否被保留；
- 工具副作用状态是否明确；
- 不确定事项是否仍被标记为不确定；
- 关键知识来源是否可追溯。

如果发现重要信息丢失，应恢复原始引用或重新构建上下文，而不是继续执行。

### 7.4 原始证据不可被摘要取代

摘要可以帮助模型理解历史，但不能替代需要核验的原始证据。

例如，摘要写着“测试已经通过”，在涉及关键发布决策时仍应能够追溯到实际测试结果和对应版本。

同样，摘要写着“文件已修改”，也不能代替文件状态、变更记录和验收结果。

## 八、执行过程中的增量上下文更新

上下文不是任务开始时构建一次就永远不变。

ReAct、Plan 和 DAG 执行过程中，会不断产生新的观察、结果和约束。

### 8.1 更新触发条件

- 新工具调用产生重要结果；
- 当前计划发生变化；
- 用户补充或修改任务约束；
- 新发现与历史假设冲突；
- 某个工作流节点失败；
- 任务进入恢复阶段；
- 外部副作用状态发生变化；
- 发现某条知识不适用；
- 当前预算不足以支持原计划。

### 8.2 更新规则

每次更新应区分：

- 新事实；
- 新假设；
- 被证伪的旧假设；
- 已完成步骤；
- 新增约束；
- 待确认事项；
- 已发生的外部副作用；
- 尚未完成的验收条件。

新工具输出不能无条件覆盖已确认事实。

如果两个来源互相冲突，系统应保留冲突信息，并根据证据质量、时间、来源可信度和任务风险进行核验。

### 8.3 上下文更新与执行控制

普通上下文更新可以在任务执行期间进行。

涉及任务目标、授权边界、安全策略或不可逆操作的变更，则必须经过相应的控制流程。

例如，工具调用超时后，系统可以更新故障信息，但不能因为摘要中写着“可能失败”就直接再次提交一个非幂等操作。

## 九、知识注入安全与冲突治理

### 9.1 知识是参考数据，不是更高权限的指令

知识库内容、历史对话、工具输出和外部文件中都可能包含错误信息或恶意指令。

运行时必须区分：

- 系统级规则；
- 用户任务指令；
- 经授权的工具操作；
- 知识资产中的事实和建议；
- 不可信外部内容。

检索到的经验不能自行改变权限、绕过审批或修改用户当前任务的目标。

### 9.2 过期知识

如果知识依赖的模型、工具或工作流版本已变化，应检查其兼容性。

对于已撤销、已废弃或不符合当前版本条件的知识，禁止直接作为已验证经验注入。

如果只是存在版本差异但尚未证明失效，可以将其作为待核验参考，而不能赋予与当前有效知识相同的权重。

### 9.3 冲突处理

当多个知识给出不同建议时：

1. 检查各自适用条件；
2. 检查版本和证据；
3. 判断是否存在领域差异；
4. 检查是否涉及权限或安全约束；
5. 尝试通过确定性检查或受控实验消除冲突；
6. 无法确定时保留冲突并采取保守策略。

对于影响任务质量但风险较低的冲突，可以选择成本较低的验证方案。

对于涉及外部副作用或高风险操作的冲突，必须在执行前解决必要的不确定性。

## 十、上下文治理与专家路由的关系

路由器与上下文组装器不能相互循环依赖。

建议采用两阶段机制：

**第一阶段：路由前的轻量上下文分析。**

使用当前用户输入、必要的会话状态和轻量检索，判断任务类型、候选专家和初步风险。

**第二阶段：路由后的领域上下文组装。**

确定专家后，检索对应的领域知识、项目记忆、工具说明和工作流状态。

如果执行过程中出现证据表明最初路由错误，可以申请重新路由，但必须保留已有任务状态和重要约束，并明确跨专家切换时哪些上下文允许迁移。

不能为了提高路由准确率，先把所有专家的全部知识都塞进路由模型。

## 十一、上下文效果的独立评测

### 11.1 必须比较不同上下文策略

对于关键上下文改进，至少比较：

- 基线策略；
- 候选策略；
- 在适用场景下不注入可选知识的对照策略。

对照实验用于判断额外知识是否真正提供了增量价值。

如果候选策略注入更多知识，但任务成功率没有改善，甚至增加了时延和成本，就不应仅凭检索命中率提高而认为优化成功。

### 11.2 核心评测指标

| 指标 | 目的 |
|---|---|
| 任务成功率 | 判断整体执行效果 |
| 关键约束保留率 | 检查压缩是否丢失重要要求 |
| 上下文冲突率 | 衡量注入内容之间的冲突 |
| 知识适用性准确率 | 衡量被注入知识是否适用 |
| 无关知识注入率 | 衡量上下文污染程度 |
| 证据可追溯率 | 衡量关键事实是否能够追溯来源 |
| 上下文构建时延 | 衡量组装过程是否拖慢任务 |
| 总任务成本 | 衡量模型、工具、重试和恢复的整体开销 |
| 恢复成功率 | 衡量上下文是否支持正确恢复 |
| 压缩后状态一致率 | 衡量压缩后的任务状态是否与原状态一致 |

关键约束保留率应针对明确标记为必须保留的约束计算。不能用一个平均分掩盖单条关键约束丢失。

### 11.3 评测场景

至少覆盖：

- 简单任务与复杂任务；
- 多轮对话；
- 长任务和任务恢复；
- 工具输出较大的任务；
- 具有多个专家候选的任务；
- 知识冲突任务；
- 模型与工具版本变化；
- 断联与重新连接；
- 高风险任务；
- 不同专家之间的知识迁移。

### 11.4 上下文优化必须通过正式门禁

候选上下文策略需要经过 #75—#79 的适用治理流程。

如果策略改变了知识资产的使用方式、压缩逻辑或专家间的信息流，还必须验证相关依赖与数据契约。

候选策略不得通过删除困难样本、降低约束保留要求或缩小评测范围来制造改善。

## 十二、运行时降级与恢复

上下文系统自身也可能发生故障，例如知识服务不可用、检索结果异常、压缩器超时或上下文预算计算错误。

### 12.1 故障处理策略

| 故障 | 处理策略 |
|---|---|
| 可选知识服务不可用 | 使用已有有效上下文继续，或跳过可选知识 |
| 领域知识检索失败 | 在任务允许时使用专家的已批准基础能力 |
| 上下文预算不足 | 重新压缩、分阶段加载或调整计划 |
| 关键约束缺失 | 停止受影响执行路径并重建上下文 |
| 发现知识已撤销 | 移除相关知识并检查依赖 |
| 压缩结果验证失败 | 恢复原始引用或重新构建 |
| 任务状态与摘要冲突 | 以可核验的任务状态和运行证据为准 |
| 高风险信息存在冲突 | 暂停相关动作并进入核验或授权流程 |

### 12.2 降级不能破坏安全

当知识服务不可用时，系统可以减少辅助知识使用，但不能同时丢失核心权限规则、预算控制和必要的任务状态。

如果当前任务必须依赖某个关键领域知识才能安全执行，而系统无法获取该知识，就应暂停相应动作，而不是假设自己仍然具备足够能力。

### 12.3 离线策略

Android 端可以缓存当前任务必需的信息和经过批准的低风险知识。

服务端恢复后，再同步知识使用事件和评测证据。

客户端不得在离线期间自动把未经验证的知识提升为共享知识或修改全局上下文策略。

## 十三、与无限优化闭环的结合

本专项的运行时治理与后台进化必须分离。

**用户任务执行闭环：**

1. 解析目标和约束；
2. 选择专家；
3. 组装必要上下文；
4. 执行任务；
5. 更新状态和上下文；
6. 验收结果；
7. 交付成果。

**后台上下文进化闭环：**

1. 收集必要的上下文使用证据；
2. 识别上下文遗漏、知识误用和压缩问题；
3. 形成候选策略；
4. 在固定任务集上对照测试；
5. 评估质量、时延和成本；
6. 通过独立门禁；
7. 受控发布；
8. 监测实际效果；
9. 发现退化时降级或回滚。

后台进化不能为了收集更多数据而阻塞用户任务，也不能让候选上下文策略未经验证地改变稳定版本。

## 十六、完成判定

本专项只有在以下条件全部得到验证后，才能认定实施验收完成：

- 通用上下文治理机制与专家专用策略能够协同工作；
- 用户明确提出的必要约束不会因普通压缩而丢失；
- 关键知识具备来源、版本与适用条件；
- 上下文预算不足时能够安全降级；
- 知识冲突和过期知识能够被识别；
- 任务状态可以在长任务和恢复流程中可靠重建；
- 知识注入效果可以通过对照实验评估；
- 候选策略不能绕过独立评测和发布门禁；
- 后台进化不会无约束地改变稳定任务；
- 所有关键验收场景均有实际执行证据。

**最终目标：让 EvoAgent 只在真正需要时使用真正有帮助的知识，以最合适的方式保留任务状态和约束，并通过可验证的上下文治理提高执行质量、效率与稳定性。知识系统应当成为执行能力的放大器，而不是执行链路上的额外负担。**</WritingBlock>

## 下一项专项：#83

建议继续推进 **#83：任务执行过程中的主动辅助、机会识别与自主性边界治理**。

前面已经讨论过，你希望 EvoAgent 不只是被动等待指令，还能适度整理近期对话、理解当前工作状态、主动提供相关资料，并发现用户没有明确提出但确实有价值的便利。

#83 将把这项用户侧能力正式接入现有架构，重点解决：

- 如何判断什么时候值得主动帮助；
- 如何区分真正有价值的机会与无关打扰；
- 如何将主动发现转化为可选建议，而不是擅自执行；
- 如何利用近期对话和项目状态，同时保护隐私；
- 如何限制主动分析的成本与频率；
- 如何评估主动辅助是否真正提高了用户的任务完成效果；
- 如何保证主动辅助不会影响正在执行的任务。

这里需要继续坚持已经确定的最高优先级：**主动性是额外价值，不能与任务执行质量竞争资源，更不能为了表现得聪明而打扰用户或擅自改变任务目标。**
