# EvoAgent 第四十四专项：安全治理、信任边界与自主权限进化

本轮研究 EvoAgent 如何在自主能力不断增强的同时，保持权限可控、行为可审计、风险可限制，并且不允许自进化过程悄悄扩大自身权力。

前面已经设计了工具运行时 TERSO、任务调度 MTSRIC、长期恢复 LTAR、主动感知 APIUG，以及专家系统、记忆系统和独立进化控制器。

这些能力组合起来后，EvoAgent 已经不再只是一个回答问题的聊天机器人，而是一个能够规划任务、调用工具、修改文件、管理长期工作并改进自身策略的执行系统。

这会带来一个根本问题：

**谁来约束智能体的行动？如果智能体本身也在进化，约束它的规则由谁管理？**

建议将本专项定义为：

**Agent Security Governance & Trust Boundaries，简称 ASGTB。**

它不是单一的安全过滤器，而是一套贯穿身份、授权、工具执行、记忆访问、设备协作和进化发布的治理体系。

## 一、第一性原理：能力、权限与信任是三件不同的事

首先必须明确三个概念。


    <title size="md">能力 Capability</title>
    系统技术上能够完成什么。例如，某个工具可以修改文件，某个模型能够生成 Shell 命令。



    <title size="md">权限 Permission</title>
    系统在当前身份、任务、资源和授权范围内被允许做什么。



    <title size="md">信任 Trust</title>
    系统对某个主体、组件或证据的可靠程度作出的判断，包括来源、完整性、历史表现与适用范围。


这三者不能互相替代。

- 模型能够生成删除文件的命令，不代表它有权删除文件。
- 专家过去 100 次执行成功，不代表它自动获得更广泛的权限。
- 一个工具经过签名验证，只能说明其来源或完整性满足相应验证条件，不代表它的行为必然安全。
- 一条记忆经过验证，也不意味着它可以覆盖当前任务的授权边界。

**EvoAgent 可以通过进化扩大能力，但权限的变化必须经过独立的授权治理；信任判断只能影响风险评估，不能代替权限检查。**

# 二、建立统一的身份体系：每次操作究竟代表谁？

在多专家、多工具、多设备和长期任务环境中，不能只用“当前智能体”作为所有操作的身份。

例如，代码专家调用文件工具，视频专家调用云端生成服务，恢复管理器重新提交某个请求。它们可能共享同一个用户，但任务目标、可访问资源和授权范围完全不同。

建议建立以下身份层级。

  {#each [
    ["用户身份","代表真正发起任务或批准操作的用户。"],
    ["任务身份","代表一次具有明确目标、约束和授权范围的任务。"],
    ["专家身份","代表负责特定领域工作的逻辑执行主体。"],
    ["工具身份","代表实际执行操作的工具或服务实例。"],
    ["设备身份","代表执行环境及其受信任程度。"],
    ["进化控制器身份","代表提出、评估和发布系统改进的独立治理主体。"]
  ] as item}

      <title size="md">{item[0]}</title>
      {item[1]}

    {#if item[0]!=="进化控制器身份"}

    {/if}
  {/each}

这些身份应当通过明确的关联关系连接，而不是彼此混同。

例如：

- 用户发起任务；
- 任务由代码专家负责；
- 代码专家请求调用文件修改工具；
- 工具在 Windows 设备的受限工作空间内执行；
- SBAAG 判断该操作是否符合当前授权；
- TERSO 记录实际执行结果；
- LTAR 更新任务状态。

每个环节都应能追溯到具体身份和操作关联 ID。

## 2.1 身份不能仅由模型文本声明

如果模型在工具参数中写入“我是管理员”或“用户已经授权”，系统不能据此改变其权限。

身份必须来自可信的运行时身份上下文、授权记录或经过验证的凭证。

同样，工具返回的文本、外部网页和导入的记忆不能自行创建更高权限的身份。

## 2.2 权限继承必须有明确规则

建议遵循最小权限原则：

- 任务只能使用用户实际授权的权限；
- 专家只能使用任务允许的权限子集；
- 工具只能执行注册契约允许的操作；
- 设备只能访问本身被允许访问的资源；
- 进化控制器只能修改其被明确授权管理的策略与候选版本。

权限可以被进一步限制，但不能仅因为下游主体需要方便，就自动扩大上游授权。

# 三、统一授权模型：权限不是一个开关，而是一组有边界的许可

建议建立 `AuthorizationPolicy` 与 `AuthorizationGrant` 两个核心对象。

前者定义规则，后者记录一次具体授权。

例如，“允许代码专家修改项目”过于宽泛。更合适的授权应该明确：

- 哪个任务可以修改哪个项目；
- 哪些目录允许读写；
- 是否允许删除文件；
- 是否允许联网安装依赖；
- 是否允许访问环境变量或凭据；
- 授权何时失效；
- 哪些操作仍然需要单独确认。

## 3.1 授权记录建议包含的字段

| 字段 | 作用 |
|---|---|
| `grant_id` | 授权记录的唯一标识 |
| `subject_id` | 被授权的主体 |
| `task_scope` | 授权适用的任务范围 |
| `resource_scope` | 可以访问的资源范围 |
| `allowed_actions` | 允许执行的操作 |
| `constraints` | 金额、文件范围、网络目标等限制 |
| `approval_source` | 授权来源及审批记录 |
| `issued_at` | 授权产生时间 |
| `expires_at` | 可选的失效时间 |
| `revocation_status` | 是否已撤销 |
| `policy_version` | 授权所依据的策略版本 |

授权可以按一次操作、一个任务、一段时间或一组受限操作生效，但不能默认无限期有效。

例如，用户允许某个任务修改一个指定项目，并不意味着该任务可以修改用户主目录下的所有文件。

## 3.2 区分四种授权范围


    <title size="md">单次操作授权</title>
    适用于特定的高影响操作，例如覆盖指定文件或发布指定内容。



    <title size="md">任务级授权</title>
    允许某个任务在规定的项目、目录和操作范围内工作。



    <title size="md">能力级授权</title>
    允许使用某类受限能力，例如在隔离环境中运行测试。



    <title size="md">长期授权策略</title>
    用于定义可重复使用的规则，但仍须受当前任务、设备、资源和风险限制。


长期授权并不意味着每次都不需要重新检查。

如果操作目标变化、风险等级提高、设备不可信或授权条件已经失效，就必须重新判断。

## 3.3 授权决策采用明确的合取条件

建议一次操作只有同时满足以下条件，才能进入执行阶段：

\[
\begin{aligned}
Permit ={}& IdentityValid \\
&\land PolicyAllows \\
&\land GrantValid \\
&\land ScopeMatches \\
&\land PreconditionsMet
\end{aligned}
\]

这是一种治理规则，而不是某个模型的置信度计算。

如果任意一个必要条件不成立，系统就应拒绝、暂停或请求补充授权。

尤其不能通过专家切换、重试、改用其他模型或重新规划来绕过拒绝结果。

# 四、自主权限进化：系统可以改进策略，但不能给自己升权

这是 EvoAgent 最重要的安全设计之一。

随着使用时间增加，系统可能发现某些权限配置过于保守，导致频繁询问用户；也可能发现某些权限过宽，增加了风险。

它可以分析这些问题并提出改进建议，但不能直接修改自己的权限边界。

## 4.1 建立权限策略的独立生命周期

建议采用以下流程：

  {#each [
    ["1. 发现问题","记录权限拒绝、重复审批、越权尝试和操作失败等事件。"],
    ["2. 形成改进候选","提出更清晰的资源范围、授权期限或审批规则。"],
    ["3. 安全影响分析","评估候选规则是否扩大访问范围、提高副作用或削弱现有保护。"],
    ["4. 独立验证","在隔离测试环境中验证允许与拒绝行为是否符合预期。"],
    ["5. 授权批准","涉及权限扩大时，由具备授权权力的主体明确批准。"],
    ["6. 版本化发布","通过受控发布流程启用策略，并保留旧版本。"],
    ["7. 持续监测与回滚","检查误放行、误拒绝和异常行为，必要时回滚。"]

        {item[0].split(".")[0]}


        **{item[0].slice(item[0].indexOf(" ") + 1)}**
        {item[1]}

  {/each}

## 4.2 权限扩大与权限收紧必须区别处理

权限收紧通常可以由受控治理流程提出并实施，例如：

- 缩小工具可访问的目录；
- 缩短授权有效期；
- 禁止某类外部网络访问；
- 提高某类操作的审批要求。

权限扩大则需要更严格的批准流程。

例如，系统发现某个代码任务经常因为无法写入项目目录而失败，可以提出一个更精确的工作空间授权方案，但不能直接把文件系统访问范围从项目目录扩大到整个磁盘。

**历史成功率、评测分数和执行效率都不能自动构成升权依据。**

## 4.3 防止权限治理被自进化控制器间接绕过

即使进化控制器没有直接修改授权记录，它也可能通过修改工具注册表、调度策略或执行器配置，间接获得更大权限。

因此，需要将安全关键配置统一纳入受保护的策略边界。

至少应保护：

- 身份验证规则；
- 授权与审批策略；
- 禁止操作清单；
- 工具权限声明；
- 沙箱约束；
- 设备信任规则；
- 安全审计要求；
- 权限策略的发布和回滚机制。

修改这些配置的权限应由独立治理机制控制，而不是由普通专家或进化候选自行决定。

# 五、信任边界：数据可以被利用，但不能自动获得控制权

EvoAgent 会接触大量不同来源的信息：

- 用户直接输入；
- 本地文件与代码仓库；
- 网页和外部文档；
- 工具返回结果；
- 专家生成的诊断报告；
- 长期记忆；
- 其他设备同步的任务事件；
- 模型生成的计划与摘要。

这些内容的可信程度不同。

更重要的是，即使一段内容完全真实，也不代表它有权指挥系统执行操作。

例如，项目 README 中的安装说明可以作为技术资料，但其中要求上传凭据的命令仍然需要独立的安全检查。

## 5.1 建立四类信任边界

| 边界 | 核心问题 | 治理方式 |
|---|---|---|
| 指令边界 | 谁能改变系统目标或授权？ | 明确指令来源与优先级 |
| 数据边界 | 哪些内容可以被读取、使用或外传？ | 数据分类、访问控制和最小化传递 |
| 执行边界 | 哪些主体可以产生实际副作用？ | 授权、沙箱、资源约束和执行审计 |
| 状态边界 | 哪些来源可以改变权威任务状态？ | 版本检查、合法状态转换和事件核验 |

建议明确：外部内容、工具输出和记忆默认都是信息来源，而不是更高优先级的指令来源。

如果用户授权系统阅读某个网页，不代表用户授权网页中的指令修改任务目标。

如果模型从日志中发现一条命令，也不代表该命令可以直接执行。

如果另一台设备上传了任务事件，也不代表它有权覆盖当前任务的权威状态。

## 5.2 对抗提示注入需要运行时保护

提示注入不能只依靠模型识别恶意措辞来防御。

建议组合使用：

1. 明确区分可信指令与不可信数据；
2. 对工具返回的内容保留来源标记；
3. 限制每个工具的权限与数据访问范围；
4. 对敏感操作重新进行授权和参数检查；
5. 对外部数据传输实施独立控制；
6. 对涉及秘密信息的操作使用专门的凭据访问机制；
7. 通过对抗测试验证系统是否会越权。

即使恶意文本成功影响了模型判断，也不应该因此自动获得文件访问权、网络访问权或系统管理权限。

## 5.3 信任不是永久标签

某个工具过去表现良好，并不代表它未来永远可信。

工具版本升级、依赖变化、签名验证失败、行为异常或运行环境改变，都可能影响信任判断。

建议将信任记录关联到具体的工具版本、设备、环境和时间范围。

当关键条件变化时，系统应重新验证，而不是永久沿用旧的信任结论。

# 六、秘密信息治理：记忆、上下文和工具都不能随意接触凭据

随着 EvoAgent 能够运行代码、访问 API 和管理长期任务，系统可能接触到：

- API 密钥；
- 访问令牌；
- SSH 密钥；
- 数据库凭据；
- 用户文件中的敏感信息；
- 外部服务的临时授权。

建议建立独立的 `SecretAccessManager`，避免将所有凭据直接放入模型上下文或长期记忆。

## 6.1 凭据访问采用最小化机制

- 尽量使用操作系统提供的安全凭据存储；
- 通过受限工具按需获取必要凭据；
- 不将秘密值写入普通日志；
- 避免把完整凭据注入通用模型上下文；
- 限制凭据可用于哪些服务、操作和时间范围；
- 对凭据访问建立独立审计；
- 支持失效、撤销和轮换；
- 发生泄漏风险时触发相应的处置流程。

对于个人电脑部署，具体机制可以根据 Windows、Linux 和 Android 平台能力分别实现，但上层接口应保持一致。

## 6.2 脱敏不能只依赖模型

如果工具输出包含 API 密钥，系统不能只要求模型“不要泄漏”。

应在日志记录、上下文构建、文件导出和跨设备同步等环节设置相应的数据过滤与访问规则。

脱敏本身也不能成为随意修改证据的理由。需要保留原始敏感数据时，应将其放在受控存储中，并让审计记录能够引用该数据，而不是把秘密值直接复制到普通日志。

# 七、专家隔离与共享记忆：知识共享不等于权限共享

EvoAgent 采用多个领域专家，例如通用对话、编程、旅游、AI 漫剧制作和手机操作。

这些专家需要共享某些通用能力，但不能因此共享全部数据访问权。

建议将记忆与权限分成两条独立链路。


    <title size="md">知识链路</title>
    经过验证的经验、项目知识、用户偏好和可复用的技术方案，可以在符合访问策略时共享。



    <title size="md">权限链路</title>
    每次实际操作仍然根据任务身份、资源范围、授权记录和工具契约独立判定。


例如，旅游专家可以读取用户明确允许共享的旅行偏好，但不能因此访问代码项目中的秘密文件。

编程专家可以学习某个项目的构建经验，但不能仅凭这条记忆访问另一项目的凭据。

同样，用户的长期偏好可以影响默认工作方式，但不能改变安全授权规则。

**记忆决定系统知道什么；授权决定系统可以做什么。**

## 7.1 跨专家交接需要数据范围检查

当一个任务从通用专家交给编程专家时，不能无条件复制全部聊天历史、全部记忆和所有工具输出。

建议根据当前子任务生成最小必要的交接上下文：

- 任务目标；
- 相关约束；
- 必要的证据引用；
- 当前节点状态；
- 允许访问的数据范围；
- 尚未解决的问题。

如果某个专家需要额外数据或权限，应通过明确的访问请求处理，而不是自动继承其他专家的全部能力。

# 八、跨设备信任：任务迁移后，权限不能跟着文件无限扩散

此前 LTAR 和 MTSRIC 已经设计了跨设备任务恢复与调度。

ASGTB 需要进一步回答：当任务从 Android 手机迁移到 Windows 电脑，或者从个人电脑迁移到微型 Linux 主机时，哪些授权可以继续有效？

答案不能是“只要任务状态同步成功，权限就自动继承”。

## 8.1 区分任务状态迁移与授权迁移

任务迁移可以携带：

- 任务目标与约束；
- 已完成节点；
- 产物引用；
- 必要上下文；
- 执行日志引用；
- 未决操作状态。

但设备权限需要在目标设备上重新检查。

例如，手机被允许访问某个本地文件，并不意味着 Linux 主机也自动获得访问权限；Windows 上已经批准的本地 Shell 操作，也不代表云端执行环境可以运行相同命令。

## 8.2 建立设备信任评估

建议记录：

- 设备身份及注册状态；
- 系统版本与关键安全配置；
- 可用的身份验证方式；
- 当前网络与连接状态；
- 可访问的数据范围；
- 可运行的工具及其版本；
- 当前设备是否允许执行高风险操作。

对于个人自托管部署，不一定需要复杂的企业级设备管理系统，但至少要有明确的设备注册、身份验证、权限范围和撤销机制。

## 8.3 设备离线与重新连接的安全规则

离线期间，设备只能继续执行其已经获得授权、且符合离线策略的操作。

重新连接后：

- 核验设备身份；
- 同步授权撤销与策略版本；
- 对过期授权进行失效处理；
- 对离线期间的操作事件进行对账；
- 对结果未知的外部操作进行核验；
- 在必要的策略同步完成前，限制高风险操作。

如果设备离线期间的授权可能已经被撤销，而系统无法确认当前授权状态，就不应允许它继续执行依赖该授权的高风险操作。

这也是为什么权限版本和任务状态版本必须分别管理：任务状态更新并不等于授权仍然有效。

# 九、审计与追责：必须能够还原一次操作为什么发生

EvoAgent 的安全审计不能只记录“工具调用失败”或“用户批准了操作”。

系统需要能够回答：

- 是哪个任务提出了操作？
- 哪个专家生成了行动意图？
- 当时使用了什么工具版本？
- 操作依据是什么证据？
- 使用了哪份授权记录？
- 当时采用哪个安全策略版本？
- 操作实际访问了什么资源？
- 执行产生了什么副作用？
- 最终结果如何核验？
- 如果操作失败，是否触发了恢复或补偿？

## 9.1 建立不可随意改写的审计事件链

建议记录以下事件类型：

- `AUTHORIZATION_GRANTED`
- `AUTHORIZATION_DENIED`
- `AUTHORIZATION_REVOKED`
- `TOOL_EXECUTION_REQUESTED`
- `TOOL_EXECUTION_STARTED`
- `TOOL_EXECUTION_COMPLETED`
- `TOOL_EXECUTION_REJECTED`
- `POLICY_VERSION_CHANGED`
- `DEVICE_TRUST_CHANGED`
- `SECRET_ACCESS_RECORDED`
- `SECURITY_INCIDENT_DETECTED`
- `RECOVERY_ACTION_TAKEN`

每个事件关联任务、主体、设备、工具执行和适用策略版本。

对个人使用的系统，可以从本地追加式审计日志、权限受控的存储和定期校验开始。更高要求的部署可以进一步使用哈希链、数字签名或独立备份增强篡改检测。

需要注意：哈希链可以帮助发现部分修改，却不能单独保证日志一定完整，也不能阻止拥有底层存储全部控制权的攻击者重写整条链。审计保护必须与访问控制、备份和可信执行环境的实际能力相匹配。

## 9.2 审计记录不应泄漏秘密

日志需要保留足够的诊断信息，但不能把完整密码、API 密钥或敏感文件内容复制进去。

建议记录：

- 访问了哪个凭据引用；
- 使用凭据的工具和操作；
- 授权是否通过；
- 结果是否成功；
- 是否触发泄漏风险。

而不是默认记录凭据本身。

## 9.3 安全事件必须能触发限制与恢复

当系统检测到越权尝试、异常网络访问、工具版本不可信或权限状态冲突时，应能够：

1. 阻止相关操作继续执行；
2. 隔离对应任务或工具；
3. 保留必要的审计证据；
4. 撤销或暂停受影响的授权；
5. 检查是否存在已产生的副作用；
6. 通过恢复机制核验系统状态；
7. 在问题解决后经过验证再恢复服务。

不能只生成一份安全告警报告，然后让原任务继续按照原计划执行。

# 十、如何让安全治理本身接受评测？

ASGTB 不能只统计拦截了多少次操作。

拦截数量多，可能意味着防护有效，也可能意味着策略配置错误，导致大量正常操作被拒绝。

同样，用户审批次数减少，可能是自动化改进，也可能是系统悄悄扩大了权限。

因此，建议从四个维度评测安全治理。

## 10.1 安全性

- 越权操作拦截率；
- 未授权数据访问事件；
- 权限提升尝试的发现率；
- 提示注入导致的越权执行率；
- 敏感信息泄漏事件；
- 未授权副作用发生率。

## 10.2 正确性

- 合法操作误拒绝率；
- 授权范围判断准确率；
- 权限撤销生效时间；
- 工具与策略版本匹配正确率；
- 跨设备授权一致性；
- 审计链完整性。

## 10.3 可用性

- 正常任务的授权等待时间；
- 不必要的重复审批次数；
- 受控降级后的任务完成率；
- 安全事件后的恢复时间；
- 用户能够理解并有效修改授权范围的程度。

## 10.4 自进化安全

- 权限扩大候选的正确识别率；
- 未经批准的策略修改拦截率；
- 安全策略更新后的回归缺陷率；
- 候选策略引入的误放行与误拒绝变化；
- 策略回滚是否能够恢复到经过验证的版本。

## 10.5 建立安全对抗测试集

建议持续测试以下场景：

- 网页试图诱导模型泄漏本地凭据；
- 项目 README 要求执行超出授权范围的命令；
- 一个专家试图读取另一个专家的私有数据；
- 工具输出伪造“用户已授权”的声明；
- 离线设备仍然使用已撤销的权限；
- 自进化候选试图修改安全规则；
- 同一个授权被用于不同的项目或设备；
- 工具版本变化后继续使用旧的信任结论；
- 恢复任务时重新执行未经确认的外部副作用；
- 低风险操作在目标变化后实际变成高风险操作。

每个测试都应定义预期允许、预期拒绝、必须记录的审计事件和恢复要求。

安全评测结果应进入 SELCIA 的发布门槛。关键安全测试失败时，不能仅凭平均任务成功率提高就批准新策略。

# 十二、下一专项：配置治理、版本兼容与系统变更管理

经过本轮设计，EvoAgent 已经拥有多专家、多任务、长期记忆、工具执行、安全授权和自进化等大量子系统。

现在出现一个新的系统级问题：

**当这些模块分别升级、调整配置或改变数据结构时，如何保证整个系统仍然兼容，而不是某个模块优化成功，却导致其他模块退化？**

例如：

- 新版上下文压缩器改变了记忆引用格式；
- 新版 Router 改变了专家选择规则；
- 新版工具契约修改了参数结构；
- 新版任务状态机增加了节点状态；
- 新版预算策略改变了资源分配；
- 新版安全策略收紧了某项权限；
- 新版恢复逻辑无法读取旧检查点。

每个局部改动可能都合理，但如果缺少系统级变更治理，最终会产生兼容性问题、状态迁移失败、隐性行为变化和难以定位的回归故障。

下一专项建议定义为：

**Configuration Governance, Version Compatibility & Change Management，简称 CGVCM。**

重点研究：

1. 如何建立全局配置注册表与配置所有权；
2. 如何区分静态配置、运行时策略和学习产生的候选参数；
3. 如何管理专家、模型、工具、记忆 Schema 和任务 DAG 的版本；
4. 如何定义模块间接口契约和兼容性要求；
5. 如何安全升级长期任务状态与历史检查点；
6. 如何处理模型、工具和外部服务的版本变化；
7. 如何对跨模块改动进行依赖分析和影响评估；
8. 如何支持配置灰度发布、版本固定、回滚与恢复；
9. 如何避免不同设备长期运行不同版本而产生状态冲突；
10. 如何管理默认配置、用户偏好、任务配置和安全策略之间的优先级；
11. 如何让自进化控制器提出配置改进，同时防止它绕过受保护的治理规则；
12. 如何通过兼容性测试、回放测试、故障注入和端到端验收保证变更质量。

本专项的核心原则是：

**每个模块可以独立进化，但每次影响系统行为的变更，都必须有明确的版本、兼容性契约、影响范围和恢复路径。**

这将帮助 EvoAgent 从一组可以工作的智能模块，逐步成为一个能够长期升级、持续进化而又不轻易破坏已有能力的完整系统。
