它解决两个方向的问题：

- **上行：** App 在真实使用中发现的问题，如何带着足够的上下文和版本信息传到服务端，让服务端准确诊断。
- **下行：** 服务端优化出来的成果，如何找到正确的 App、正确的领域、正确的组件，并经过验证后生效，而不是一股脑地更新整个 App。

最重要的是，**服务端优化不等于每次都要发布一个新的 Android 安装包**。很多优化只需要更新配置、提示词、路由策略或工作流；只有涉及原生代码、权限机制、底层执行器等变更时，才可能需要 App 软件更新。

# 一、先确定整体设计：双向同步，而不是简单上传日志、下载更新



    **Android App：稳定执行端**
    执行任务、记录证据、本地恢复、应用已批准的更新



    双向同步协议
    事件上传、版本对账、策略下发、结果回传



    **服务端：诊断与进化中心**
    汇总证据、定位问题、生成候选、评测、发布和回滚




    **受控发布与反馈闭环**
    版本清单 → 兼容性验证 → App 应用 → 真实运行监测 → 继续改进或回滚


这里有一个重要设计：App 和服务端不是直接互相修改对方的数据，而是通过统一的协议与版本资产协作。

- App 不直接修改服务端生产环境。
- 服务端不直接修改 App 正在执行的任务。
- App 上传的是运行证据，而不是直接要求服务端修改某段提示词。
- 服务端下发的是具有明确版本、适用范围和验证状态的更新。
- App 必须验证更新是否适用，才能将其激活。

# 二、App 的运行日志究竟如何与服务端关联？

核心不是只上传一份日志文件，而是为每次执行建立一条完整的**任务追溯链**。

## 2.1 每个任务都记录自己的版本身份

假设你在手机上说：

“帮我打开某个应用，进入指定页面，然后完成一项操作。”

App 执行时，应该同时记录以下信息。

| 记录类别 | 记录内容 |
|---|---|
| 任务身份 | `task_id`、`run_id` |
| 设备身份 | 匿名化的 `device_id`、安装实例标识 |
| 任务能力 | 通用专家、手机操作专家等 |
| 模型身份 | 模型标识、模型适配版本 |
| 策略身份 | 提示词版本、Planning、ReAct 策略版本 |
| 执行组件 | Harness、工具适配器版本 |
| 工作流 | 工作流 ID 与版本 |
| 环境信息 | Android 版本、App 版本、相关权限状态 |
| 执行证据 | 工具调用、关键状态变化、错误码 |
| 验收结果 | 是否达到目标，以及依据 |
| 资源消耗 | 调用次数、耗时、费用（可获取时） |

这样，服务端收到“手机操作失败”时，就能知道这次失败发生在哪个版本组合上。

例如，问题可能来自：

- 手机操作专家的策略有缺陷。
- 无障碍工具适配器的版本不兼容。
- Android 页面发生了变化。
- 模型更新后改变了工具调用方式。
- 上下文没有保留用户的关键约束。

没有版本追溯信息，这些原因很容易混在一起。

## 2.2 每条事件都关联到任务和执行版本

建议采用如下逻辑结构：

```text
Task
 └── TaskRun
      ├── RuntimeManifest
      │    ├── AppVersion
      │    ├── ModelProfileVersion
      │    ├── PromptVersion
      │    ├── HarnessVersion
      │    ├── ToolVersions
      │    └── WorkflowVersion
      │
      ├── RuntimeEvents
      ├── Checkpoints
      ├── Artifacts
      └── EvaluationResult
```

其中，`RuntimeManifest` 是关键。

它记录一次运行实际使用的版本组合。即使后续更新了提示词或工作流，也不会覆盖旧任务的历史版本信息。

服务端收到日志后，可以通过 `run_id` 找到该次运行，通过 `RuntimeManifest` 还原相关组件版本，再关联诊断案例和进化候选。

**这才是日志能够真正驱动进化的前提。**

## 2.3 日志如何上传？

建议采用本地持久化事件队列，而不是任务结束后才统一上传。

  App 运行时产生事件，先写入本地持久化队列。
  事件附带唯一 ID、任务 ID、运行 ID 和版本清单引用。
  网络可用时，按批次上传允许共享的事件。
  服务端确认接收后，App 标记对应事件已同步。
  如果上传失败，事件继续保存在本地，之后重试。

这样，即使 App 崩溃、手机断网或服务端暂时不可用，已经落盘的关键事件也不会因为进程退出而直接丢失。

同步接口应具备幂等性，重复上传同一事件不能重复创建进化任务。

此外，不建议默认上传所有原始对话、屏幕截图和文件内容。应先上传必要的结构化事件，敏感诊断材料则根据授权、必要性和隐私策略处理。

# 三、服务端优化后，究竟怎样影响 App？

这里必须区分不同的更新类型。它们不应该使用同一种分发机制。






      **类型 A：策略与配置更新**
      无需安装新 APK
      例如模型路由参数、已批准的重试策略、非关键提示词配置、预算参数。
      通过版本化配置包下发。App 校验后激活，支持回滚。








      **类型 B：领域能力与工作流更新**
      通常无需安装新 APK
      例如手机操作专家的流程、旅游规划工作流、AI 漫剧 DAG、经过验证的工具调用模板。
      通过能力包或工作流包下发。前提是当前 App 已有兼容的执行器和工具接口。








      **类型 C：模型适配更新**
      例如切换模型 API、调整模型专用提示词、工具调用适配参数。
      更新模型档案、适配器配置和路由规则。涉及新的原生执行能力时，不能仅靠配置解决。








      **类型 D：客户端代码更新**
      需要 App 软件更新
      例如修改原生 Android 执行器、数据库底层实现、无障碍适配代码或核心状态机。
      需要构建、测试、签名并通过受控的软件分发机制安装更新。



这里的关键区别是：**服务端能够改进智能体的行为，不代表服务端可以凭空赋予旧 App 不具备的底层能力。**

例如，服务端可以优化手机操作专家的控件定位策略，但如果新方案需要一个旧 App 尚未实现的 Android 原生接口，就必须先升级客户端执行器。

# 四、必须增加一个核心机制：版本清单与能力包分发

我建议新增两个正式架构模块：

- `Evolution Sync Service`：负责 App 与服务端的双向同步。
- `Release & Capability Delivery Service`：负责能力包、配置包、模型适配和客户端制品的版本分发。

这两个模块与进化控制器分开，避免候选生成、评测和生产发布混成一个流程。

## 4.1 服务端发布什么？

每次发布都生成一份机器可读的发布清单。例如：

```json
{
  "release_id": "release-2026-0042",
  "release_channel": "stable",
  "target": {
    "platform": "android",
    "capability_id": "mobile_operator"
  },
  "base_release": "release-2026-0038",
  "components": [
    {
      "type": "policy_bundle",
      "id": "mobile_operator_policy",
      "version": "2.4.1"
    },
    {
      "type": "workflow_bundle",
      "id": "app_navigation",
      "version": "1.8.0"
    }
  ],
  "compatibility": {
    "minimum_app_version": "1.0.0",
    "required_tool_contracts": ["android_accessibility.v2"]
  },
  "evaluation": {
    "status": "passed",
    "report_id": "eval-2026-0192"
  },
  "rollback_release": "release-2026-0038"
}
```

以上只是说明数据结构的示例，不代表已经创建了真实发布版本。

正式清单还应包含制品摘要、签名、发布范围、启用策略、预算与安全策略版本，以及必要的依赖信息。

## 4.2 App 如何判断更新适不适合自己？

App 收到清单后，依次检查：

1. 目标平台和能力是否匹配。
2. 当前版本是否满足最低兼容要求。
3. 所需工具契约是否存在。
4. 制品签名与完整性是否有效。
5. 发布版本是否已被授权。
6. 本地是否有足够存储空间和可用资源。
7. 更新是否与正在运行的任务冲突。
8. 是否存在有效的回滚目标。

任何必要检查失败，都不应该激活该版本。

## 4.3 App 如何应用更新？

推荐采用**双版本槽位或等价的原子切换机制**。

```text
当前稳定版本 A
       |
下载候选版本 B
       |
完整性与兼容性验证
       |
在隔离环境执行必要测试
       |
准备激活 B
       |
在安全边界切换版本引用
       |
运行健康检查与任务监测
       |
  ┌────┴────┐
  |         |
  正常      异常
  |         |
正式保留 B  恢复 A
```

这适用于可以独立版本化的策略和能力包。对于 Android 原生代码更新，则必须使用符合平台要求的应用更新机制，不能把普通配置热更新当成 APK 热替换。

另外，切换时应避免中途更换正在运行任务所使用的组件。任务默认固定使用启动时记录的版本清单，后续任务才使用新版本；只有明确支持安全迁移的任务才允许切换。

# 五、完整闭环：从一次失败到 App 真正变好

假设手机操作专家在某个 App 页面连续识别错控件。


    **App 发现问题**

    操作后的页面状态与预期不符，验收器判定失败。App 记录屏幕状态引用、工具调用、错误类别和当前版本清单。


    **日志关联到服务端**

    事件通过同步协议上传，服务端根据任务 ID、运行 ID、组件版本和环境信息建立诊断案例。


    **服务端诊断根因**

    通过证据判断是页面变化、无障碍节点读取异常、模型定位策略不合适，还是执行后缺少状态验证。无法确认时保留多个假设。


    **建立局部候选**

    如果问题来自手机操作专家的策略，只修改对应能力包；如果是工具实现问题，则建立工具适配器候选。不能默认修改通用内核。


    **自动评测**

    使用固定页面案例、不同布局、异常页面和失败恢复场景，对比旧版本和新版本，同时评估误操作风险、时延与模型成本。


    **发布门禁**

    候选通过兼容性、质量、成本和安全检查后，生成签名发布清单。低风险更新可按授权自动发布。


    **App 接收更新**

    App 校验目标能力、版本依赖、签名和回滚信息，再在合适的时机启用新版本。


    **真实运行验证**

    后续任务继续采集结果。如果实际成功率改善且没有出现不可接受的回归，保留新版本；否则停止推广或回滚。


这才构成真正的闭环：

**运行问题 → 版本化证据 → 根因诊断 → 局部改进 → 隔离评测 → 受控发布 → App 应用 → 线上验证 → 再次进化。**

# 六、服务端离线、手机离线时怎么处理？

两种离线场景必须分别设计。

| 场景 | App 的行为 | 服务端恢复后的行为 |
|---|---|---|
| 进化服务离线 | 继续使用当前稳定版本执行任务 | 上传积压事件，恢复诊断与进化 |
| 网络完全中断 | 执行允许离线的本地任务，保存检查点 | 重连后同步事件和状态 |
| 模型 API 不可用 | 使用已批准的备用模型或本地路径，否则安全停止 | 根据错误证据判断是否需要修复 |
| 更新服务不可用 | 保留现有稳定版本，不等待更新 | 恢复版本对账和更新分发 |
| 更新包校验失败 | 拒绝更新，继续使用稳定版本 | 记录发布故障，重新检查制品 |
| 新版本运行异常 | 按适用策略停止推广或回滚 | 分析线上证据，创建后续候选 |

还需要补充一个容易遗漏的规则：服务端可能在 App 离线期间发布多个版本。App 恢复联网时，不应盲目逐个安装所有历史版本，而应进行**版本对账**，选择一个与当前环境兼容、经过授权且具备明确迁移路径的目标版本。

# 七、我建议正式补充的核心数据表

在前面的全量架构基础上，至少补充或明确以下实体。

| 实体 | 作用 |
|---|---|
| `device_installations` | 设备安装实例与同步状态 |
| `runtime_manifests` | 每次任务实际使用的组件版本组合 |
| `runtime_events` | App 运行事件 |
| `sync_batches` | 事件同步批次 |
| `sync_receipts` | 服务端接收确认 |
| `evolution_cases` | 从运行问题建立的诊断案例 |
| `evolution_candidates` | 进化候选及其基线 |
| `evaluation_runs` | 候选测试与评测结果 |
| `release_manifests` | 正式发布清单 |
| `release_artifacts` | 策略包、能力包和客户端制品 |
| `device_release_states` | 各安装实例的目标版本与当前版本 |
| `deployment_records` | 发布与启用记录 |
| `rollback_records` | 回滚原因与恢复结果 |

这些是逻辑实体，实际可以根据事务边界合并或拆分为物理表。

# 八、最后确定四条架构规则

我建议把以下规则直接加入 EvoAgent 的正式架构约束。

**规则一：每次运行都必须能够追溯到版本组合。**

否则，服务端即使发现了问题，也可能无法确定该问题由哪个组件或环境引起。

**规则二：每项进化成果必须声明适用范围和兼容条件。**

一个旅游专家的提示词改进不能自动影响编程专家；一个新模型适配不能默认适用于旧模型；一个新工作流不能要求旧 App 调用不存在的接口。

**规则三：所有更新必须经过验证、授权和可恢复的激活流程。**

服务端生成了候选不代表候选可以发布；发布成功也不代表 App 已成功应用；App 应用了更新也不代表真实任务质量已经改善。

**规则四：App 既是执行端，也是进化证据的采集端，但不是无限制的自修改端。**

App 可以在授权范围内调整已批准的策略、记录问题、恢复任务和接收更新；对核心执行器的代码修改则必须经过隔离构建、测试、签名和受控软件更新。

最终，这套机制应当被视为 EvoAgent 的基础设施，而不是后续附加的一个同步功能。只有把上行证据链、下行发布链和版本反馈链连接起来，服务端的进化才会真正改善手机上的智能体，而不是停留在服务端生成了一份更好的提示词或代码。
