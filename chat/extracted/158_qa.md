<WritingBlock id="73518" variant="document"># MTRC-CCR 模型、工具与运行时兼容性治理专项设计

**专项编号：** #75  
**专项名称：** MTRC-CCR（Model–Tool–Runtime Compatibility Governance）  
**版本：** 1.0  
**所属体系：** EvoAgent 专项设计集  
**设计类型：** 能力契约、兼容性判定、依赖治理、运行准入与升级控制

## 一、专项目标

MTRC-CCR 的核心职责是：在能力注册、任务启动、运行时依赖变化和候选版本发布等关键节点，判断当前组件组合是否满足执行要求。

需要治理的对象包括：

- 模型及模型配置；
- 模型网关和运行时适配器；
- 工具及其适配器；
- 领域专家；
- 工作流与 DAG 节点；
- Router、Planner 和 Context Policy；
- 数据 Schema 与接口协议；
- Android App、共享内核及运行环境；
- 评测集、验收器和发布配置。

本专项不负责替代模型网关、工具网关、任务编排器或发布控制器。它提供兼容性声明、判定结果、依赖关系和准入依据，由既有模块执行相应的允许、拒绝、降级或回滚操作。

### 1.1 必须解决的实际问题

1. 模型升级后，原有工具调用格式是否仍然有效？
2. 工具接口变更后，哪些专家和工作流会受到影响？
3. 某个工作流依赖视觉能力，但当前模型不支持图像输入时，如何阻止错误执行？
4. Android App 升级后，旧工作流和旧任务状态是否仍然兼容？
5. 某个工具在联网环境可用，断网后是否应当被标记为不可用？
6. 候选专家通过自身测试，但与共享内核组合后发生退化，如何阻止发布？
7. 一个任务开始后，如果模型配置或工具版本升级，如何确保当前任务不被无约束地切换到新版本？
8. 当兼容性信息缺失或无法验证时，系统应该如何处理？

## 二、设计边界与架构关系

### 2.1 兼容性治理不等于能力选择

系统中存在三个不同问题，必须分开处理。

| 问题 | 负责机制 | 输出 |
|---|---|---|
| 选择哪个专家、模型或工作流 | Router、Planner、能力匹配 | 候选执行路径 |
| 候选组件是否能正确协同 | MTRC-CCR | 兼容性判定 |
| 该动作是否允许执行 | Action Guard、权限与预算策略 | 允许、拒绝或等待授权 |

路由评分高，不代表组件兼容。

工具健康检查通过，也不代表工具与当前模型、工作流及权限策略兼容。

兼容性通过，同样不代表高风险动作已经获得授权。

三者必须分别成立。

### 2.2 系统职责

MTRC-CCR 提供五项核心能力：

1. **兼容性声明：** 每个能力资产明确支持的接口、版本、平台、依赖和限制。
2. **依赖解析：** 从工作流、专家和工具构建完整的依赖关系。
3. **兼容性判定：** 判断组件之间是否满足接口和运行要求。
4. **组合验证：** 对真实组件组合执行契约测试和必要的集成评测。
5. **变更影响分析：** 组件升级时，识别受影响的专家、工作流和运行任务。

本专项遵循已有分层架构，不改变共享内核、安全控制器和独立进化控制器的权责。

## 三、兼容性模型

兼容性不能用单个布尔值完全表达。系统需要分别检查静态契约、能力需求、运行环境和实际健康状态。

### 3.1 四个兼容性维度

**A. 接口兼容性**

检查输入输出 Schema、API 版本、协议版本、错误格式和必要字段。

**B. 能力兼容性**

检查模型和工具是否具备工作流所需的能力，例如：

- 文本输入；
- 图像理解；
- 结构化输出；
- 工具调用；
- 流式响应；
- 代码执行；
- 文件读写；
- 指定的上下文容量或输出长度。

能力声明必须以供应商实际支持情况、适配器契约测试或可复现的验证证据为依据。

**C. 环境兼容性**

检查 Android 版本、App/Core 版本、运行时适配器、网络条件、系统权限、存储能力和必要的外部服务。

**D. 运行与资源兼容性**

检查超时、并发、预算、调用限制、离线能力、幂等语义以及运行时是否能够满足工作流的执行要求。

### 3.2 判定状态

| 状态 | 含义 | 默认处理 |
|---|---|---|
| `COMPATIBLE` | 必需的兼容性条件已验证满足 | 允许进入后续权限与预算检查 |
| `COMPATIBLE_DEGRADED` | 可以执行，但某些非必需能力不可用 | 仅在任务允许降级时执行 |
| `INCOMPATIBLE` | 存在已确认的硬性冲突 | 拒绝该组合 |
| `UNKNOWN` | 缺少证据，无法确认兼容性 | 根据风险和策略阻止或进入受控验证 |
| `QUARANTINED` | 发现异常或可信度不足，需要隔离 | 不得进入稳定执行通道 |

必须注意：

- `COMPATIBLE` 不等于工具当前健康；
- `UNKNOWN` 不等于不兼容，但不能被自动解释为兼容；
- 高风险动作所依赖的关键组件处于 `UNKNOWN` 时，不得执行相关动作；
- `COMPATIBLE_DEGRADED` 不能静默绕过用户明确要求的必要能力。

## 四、兼容性契约设计

### 4.1 设计原则

兼容性声明是能力资产的一部分，随资产版本一起管理。

资产身份仍使用已有的 `asset_id + version`。契约不能仅依靠显示名称或“最新版”等可变标签进行关联。

每份声明必须能够说明：

- 资产自身是什么；
- 它依赖什么；
- 它需要什么；
- 它支持什么；
- 哪些情况不受支持；
- 兼容性证据来自哪里；
- 发生不兼容时如何处理。

### 4.2 建议的兼容性声明结构

以下是对既有 `Capability Asset.compatibility` 字段的扩展建议，不是对已存在接口的强制重命名。

```json
{
  "contract_version": "1.0",
  "asset_ref": {
    "asset_id": "example-workflow",
    "version": "1.2.0"
  },
  "compatibility": {
    "supported_runtime_adapters": [
      {
        "name": "native",
        "version_range": "1.x"
      }
    ],
    "required_capabilities": [
      "text_input",
      "structured_output",
      "tool_calling"
    ],
    "required_interfaces": [
      {
        "interface_id": "tool-gateway",
        "schema_version": "1.0"
      }
    ],
    "platform_constraints": {
      "minimum_app_version": "1.0.0",
      "minimum_core_version": "1.0.0",
      "supported_platforms": [
        "android"
      ]
    },
    "network": {
      "requires_network": true,
      "offline_fallback_allowed": false
    },
    "permissions_required": [],
    "resource_requirements": {
      "max_runtime_seconds": 300,
      "budget_class": "standard"
    },
    "contract_tests": [
      "contract-suite-1"
    ],
    "evaluation_suite_ref": "evaluation-suite/1.0",
    "fallback_policy_ref": null
  }
}
```

以上仅为结构示例。实际使用时，应根据现有 Schema 的字段定义进行兼容扩展，不得直接用示例替换正式数据契约。

其中 `version_range` 只是示例语法；实际版本范围的解析规则必须统一定义，不能让不同模块各自解释。

### 4.3 模型配置的额外要求

模型兼容性不能仅检查模型名称。

至少需要检查：

- 输入模态；
- 工具调用格式；
- 结构化输出能力；
- 上下文和输出长度限制；
- 流式响应行为；
- 超时和供应商限制；
- 适配器的错误处理与重试语义；
- 任务所要求的质量和成本条件。

对于供应商宣称支持但尚未验证的能力，应保留证据等级，不得直接视为经过测试的兼容能力。

### 4.4 工具的额外要求

工具契约必须与现有 `Tool Contract` 保持一致，并检查：

- `input_schema` 和 `output_schema`；
- 工具版本；
- 所需权限；
- 风险等级；
- 超时；
- 幂等语义；
- 网络与离线要求；
- 成本模型；
- 健康检查和契约测试。

如果工具将一个字段由必填改为可选，可能属于兼容变更；如果改变了字段语义、删除了必要字段或改变副作用行为，则必须根据依赖方的实际要求重新判定。

不能仅凭版本号变化决定是否兼容。

## 五、依赖解析与兼容性判定算法

### 5.1 依赖图

MTRC-CCR 应复用既有能力依赖图，而不是再建立一套彼此独立的依赖数据库。

例如：

`任务 → 专家 → 工作流 → 工具 → 工具适配器 → 运行时`

同时还可能依赖：

`任务 → 模型档案 → 模型网关 → 供应商接口`

以及：

`工作流 → Context Policy → 数据 Schema → 验收器`

依赖关系必须支持版本固定、依赖类型、必要性和约束声明。

### 5.2 判定流程

**步骤 1：解析不可变资产引用。**

读取任务计划需要使用的专家、模型、工作流、工具和适配器的准确版本。

**步骤 2：递归解析依赖。**

获取所有必要的直接和间接依赖，检查缺失引用、循环依赖和已退役资产。

**步骤 3：执行静态契约检查。**

验证接口、Schema、版本范围、能力需求和平台约束。

**步骤 4：检查权限和环境前置条件。**

确认当前运行环境满足任务需要的权限、网络和系统条件。这里检查的是前置条件，不代替 Action Guard 对具体动作的最终决策。

**步骤 5：检查资源条件。**

确认任务的时限、预算和调用限制能够满足相关能力的最低要求。

**步骤 6：执行必要的健康与契约测试。**

在适当阶段运行工具健康检查、适配器契约测试或集成测试。

**步骤 7：形成判定报告。**

输出判定状态、失败原因、受影响依赖、可行替代方案和证据引用。

**步骤 8：确定准入结果。**

兼容性判定通过后，仍需经过任务权限、风险和预算检查。

**步骤 9：固定运行版本。**

任务启动后，绑定不可变 `Runtime Manifest`，记录本次执行实际使用的组件组合。

### 5.3 判定优先级

判定应遵循以下优先级：

1. 安全、权限和数据完整性硬约束；
2. 必需接口和能力约束；
3. 环境与版本约束；
4. 资源和执行约束；
5. 可选能力与性能偏好。

任何高优先级硬约束失败，都不能被低优先级性能优势抵消。

## 六、三层兼容性检查机制

不应在每次用户输入时都运行完整集成测试，也不能只在发布时检查一次。

### 第一层：注册时验证

适用于新模型档案、工具、工作流、专家或适配器进入资产库时。

检查内容：

- 声明完整性；
- Schema 合法性；
- 依赖引用有效性；
- 版本范围是否合法；
- 必需契约测试是否存在；
- 资产生命周期是否允许进入验证。

缺少必要声明的资产不得直接进入稳定通道。

### 第二层：任务启动前验证

适用于每次任务建立实际执行路径时。

检查内容：

- 计划中的资产版本是否存在；
- 必需依赖是否满足；
- 当前环境是否符合要求；
- 必要的权限和网络条件是否可用；
- 预算是否足够；
- 是否存在已知的兼容性故障。

这层检查应尽量轻量，并复用可信的静态验证结果。

### 第三层：发布前组合验证

适用于模型、工具、专家、工作流、运行时或关键策略准备升级时。

检查内容：

- 直接依赖和传递依赖；
- 组合契约测试；
- 领域专用回归测试；
- 核心安全回归集；
- 质量、成本和时延对比；
- 兼容性退化；
- 回滚目标是否有效。

这一层的测试结果应关联候选版本和具体的依赖组合，不能把某个组件单独通过测试，直接解释为所有组合都兼容。

## 七、版本固定与运行时变更治理

### 7.1 运行版本固定

每次任务运行必须绑定一个不可变 `Runtime Manifest`，记录实际使用的模型档案、Router/Planner、Context Policy、专家、工作流、工具版本、运行时适配器及相关环境信息。

同一任务的运行不能仅依靠一个可变的“当前版本”标签来恢复。

### 7.2 运行期间的升级规则

默认禁止无约束地热切换关键组件。

如果任务执行中出现模型不可用、工具版本失效或兼容性故障，系统应当：

1. 停止受影响的新动作；
2. 检查当前步骤和外部副作用状态；
3. 判断能否使用原版本继续；
4. 如果需要替换组件，验证替代组合；
5. 在必要时创建新的运行记录，并关联原运行；
6. 重新执行受影响步骤；
7. 对最终结果重新验收。

替换模型或工具不一定要求创建新的逻辑任务，但必须保证运行版本变化和恢复过程可追溯。

### 7.3 兼容性降级

降级只允许发生在明确声明为可选的能力上。

例如，工作流允许无网络时使用本地资料完成部分分析，则可以切换到明确支持离线的路径。

但如果任务明确要求实时检索，而系统没有可用的联网能力，就不能把离线摘要伪装成完整的实时研究结果。

## 八、能力生命周期与兼容性状态

兼容性状态和资产生命周期是两个不同概念。

资产生命周期沿用现有状态：

`draft → candidate → validating → approved → active`

此外还包括 `degraded`、`deprecated` 和 `retired` 等状态。

MTRC-CCR 不自行替代这些生命周期，而是提供进入相应状态的兼容性证据。

例如：

- 新工具声明完整，进入 `candidate`；
- 契约测试通过，进入进一步验证；
- 组合测试通过后，才可能获得批准；
- 发布后发现接口行为变化，可以将资产标记为 `degraded`；
- 不再支持的版本可以被弃用或退役。

关键规则：一个资产在独立测试中通过，不代表所有依赖它的组合都可以自动升级。

## 九、异常处理与用户可见行为

### 9.1 典型故障

| 故障 | 内部处理 | 用户体验 |
|---|---|---|
| 模型不支持必要模态 | 判定不兼容，寻找受支持路径 | 说明当前能力不足或提供替代方案 |
| 工具 Schema 不匹配 | 阻止调用，记录契约错误 | 说明任务的相关步骤暂不可用 |
| 运行时版本过旧 | 阻止不兼容组合启动 | 提示需要更新或切换受支持能力 |
| 外部服务不可用 | 结合网络和降级策略处理 | 显示等待、部分完成或受限状态 |
| 兼容性信息缺失 | 标记 `UNKNOWN` | 不宣称能力已得到验证 |
| 运行中发生版本故障 | 停止受影响动作并检查状态 | 显示恢复进度或需要用户处理 |
| 新版本回归失败 | 阻止候选晋级 | 用户继续使用稳定版本 |
| 依赖被退役 | 阻止新任务使用旧依赖 | 说明能力暂不可用及可能的迁移路径 |

### 9.2 统一错误对象

沿用现有错误契约，错误信息至少包含：

- `error_code`；
- `message`；
- `retryable`；
- `correlation_id`；
- `related_event_id`；
- `required_action`；
- `safe_to_repeat`。

其中，`safe_to_repeat` 为 `unknown` 时，必须先对账或人工确认，不能直接重试。

建议为兼容性治理增加标准化错误类别，例如：

- `COMPAT_ASSET_MISSING`；
- `COMPAT_SCHEMA_MISMATCH`；
- `COMPAT_CAPABILITY_MISSING`；
- `COMPAT_RUNTIME_UNSUPPORTED`；
- `COMPAT_ENVIRONMENT_UNAVAILABLE`；
- `COMPAT_DECLARATION_MISSING`；
- `COMPAT_DEPENDENCY_RETIRED`。

这些是建议的错误类别，最终名称应遵循现有错误码命名规范。

## 十、与独立进化及发布控制器的关系

MTRC-CCR 必须成为候选改进进入稳定版本前的必要检查之一。

### 10.1 候选改进流程

1. 产生候选资产；
2. 解析受影响的依赖图；
3. 检查直接依赖和传递依赖；
4. 运行必要的契约与集成测试；
5. 运行质量、安全、成本和兼容性评测；
6. 形成独立判定报告；
7. 由 Evaluation Gate Controller 作出准入判断；
8. 由 Release Controller 决定发布、灰度或拒绝；
9. 发布后观察健康状态；
10. 发现退化时暂停或回滚。

MTRC-CCR 提供证据，但不能自行批准自己的候选版本。

### 10.2 变更影响分析

当某个工具版本升级时，应自动识别：

- 直接使用该工具的工作流；
- 依赖这些工作流的专家；
- 使用这些专家的任务模板；
- 需要重新执行的回归测试；
- 可能受到影响的运行环境。

这样可以避免每次小改动都重测整个系统，同时确保关键安全集和共享内核回归集不会被跳过。

## 十一、数据与接口设计

本专项优先扩展既有数据契约，而不是新建重复的数据实体。

建议定义以下逻辑接口：

| 接口 | 职责 | 主要输出 |
|---|---|---|
| `resolve_dependencies` | 解析资产依赖 | 有序依赖图及缺失项 |
| `validate_compatibility` | 执行静态契约检查 | 兼容性判定及原因 |
| `preflight_task` | 任务启动前检查 | 准入建议与阻塞项 |
| `check_runtime_manifest` | 验证运行版本与实际组件 | 一致性结果 |
| `analyze_change_impact` | 评估候选变更的影响范围 | 受影响资产和测试集 |
| `evaluate_compatibility_candidate` | 汇总组合测试结果 | 候选兼容性证据 |
| `mark_asset_degraded` | 记录运行中发现的兼容性退化 | 退化事件与受影响引用 |

这些是逻辑接口名称，不代表已有代码中的函数名。实际实现时应复用原有服务边界和数据契约。

### 11.1 兼容性判定报告

每份正式报告至少包含：

- 判定报告 ID；
- 资产引用及不可变版本；
- 依赖图摘要；
- 运行环境摘要；
- 兼容性状态；
- 不满足的约束；
- 已执行测试及结果；
- 证据引用；
- 降级或替代建议；
- 关联的 `Runtime Manifest`；
- 判定策略版本；
- 生成时间。

报告必须可追溯，但不应默认包含不必要的原始对话、敏感文件内容或其他高敏感数据。

## 十二、验收测试矩阵

### 12.1 基础兼容性测试

| 测试 ID | 场景 | 预期结果 |
|---|---|---|
| MTRC-01 | 所有必需依赖均满足 | 判定通过 |
| MTRC-02 | 必需工具不存在 | 拒绝组合 |
| MTRC-03 | 输入 Schema 不匹配 | 阻止调用 |
| MTRC-04 | 必要的模型能力缺失 | 拒绝或使用明确批准的替代路径 |
| MTRC-05 | 工具接口版本不受支持 | 阻止相关工作流进入稳定执行 |
| MTRC-06 | 兼容性声明缺失 | 标记未知，不能直接进入稳定通道 |
| MTRC-07 | 依赖存在循环或无效引用 | 拒绝激活 |
| MTRC-08 | 依赖已经退役 | 阻止新任务使用该依赖 |

### 12.2 运行时与恢复测试

| 测试 ID | 场景 | 预期结果 |
|---|---|---|
| MTRC-09 | 运行期间组件版本发生变化 | 当前运行不被静默切换 |
| MTRC-10 | 外部服务中断 | 按明确的降级策略处理 |
| MTRC-11 | 任务恢复时旧版本不可用 | 检查迁移或替代方案，不盲目继续 |
| MTRC-12 | 工具副作用状态未知 | 先对账，不直接重放 |
| MTRC-13 | 替代模型接管失败步骤 | 重新验证能力并重新验收 |
| MTRC-14 | App/Core 版本不兼容 | 阻止不兼容组件组合激活 |

### 12.3 进化与发布测试

| 测试 ID | 场景 | 预期结果 |
|---|---|---|
| MTRC-15 | 候选工具通过单测但集成测试失败 | 不批准候选 |
| MTRC-16 | 候选模型提高速度但质量退化 | 根据独立门禁拒绝晋级 |
| MTRC-17 | 依赖变更影响多个专家 | 自动识别相关回归范围 |
| MTRC-18 | 兼容性证据过期或失效 | 重新验证或限制使用 |
| MTRC-19 | 新版本发布后健康检查失败 | 暂停或回滚 |
| MTRC-20 | 兼容性检查自身发生故障 | 不得默认放行关键动作 |

### 12.4 核心验收原则

- 所有关键契约测试必须通过；
- 已知的硬性不兼容不能被放行；
- 兼容性声明缺失不能被解释为默认兼容；
- 关键安全回归集始终执行；
- 评测失败不能被平均分或非关键指标提升抵消；
- 所有正式判定必须关联可追溯的测试和版本证据。

本专项不预先声称任何测试已经通过。只有真实运行并保存结果后，才可以将对应测试标记为通过。

## 十三、性能与效率要求

兼容性治理本身不能成为新的性能瓶颈。

建议采取以下策略：

1. 对不可变资产版本缓存静态契约验证结果；
2. 对依赖图计算结果建立版本关联；
3. 只对受变更影响的依赖子图重新验证；
4. 任务启动时执行轻量检查；
5. 完整集成测试放在注册、候选验证和发布阶段；
6. 对健康状态和动态能力设置合理的有效期；
7. 在网络不可用时，不把过期健康信息当作实时健康证明；
8. 将兼容性检查的时延纳入端到端任务成本。

缓存结果只能复用与相同资产版本、契约版本和相关环境条件匹配的证据，不能因版本相似而直接复用。

## 十四、监控与持续优化指标

建议采集以下指标：

| 指标 | 目的 |
|---|---|
| 兼容性检查耗时 | 控制任务启动开销 |
| 兼容性阻塞率 | 发现依赖声明或环境问题 |
| 运行时兼容性故障率 | 衡量静态检查的有效性 |
| 兼容性误放行率 | 发现漏检的关键冲突 |
| 兼容性误拒绝率 | 发现过度保守的判定 |
| 变更影响分析准确率 | 衡量依赖图的完整性 |
| 候选版本兼容性退化率 | 监控进化过程的风险 |
| 回滚触发率 | 识别发布质量问题 |
| 检查缓存命中率 | 衡量效率优化效果 |

这些指标必须按任务类型、资产类型、版本和运行环境分组分析，不能只看全局平均值。

对于误放行等安全相关指标，应结合明确的严重程度、测试覆盖和实际故障证据判断，不得仅凭某个统计值认定系统绝对安全。

## 十六、完成判定

MTRC-CCR 设计完成，必须满足以下条件：

1. 模型、工具、专家、工作流和运行时具有一致的兼容性声明规则。
2. 依赖能够递归解析，并识别缺失、退役和冲突。
3. 系统能够区分兼容、不兼容、未知和降级状态。
4. 任务启动前能够检查必要的兼容性条件。
5. 运行中关键组件版本保持可追溯。
6. 候选版本发布前能够执行组合验证和变更影响分析。
7. 不兼容的候选不能进入稳定通道。
8. 运行中发生兼容性故障时，系统能够安全停止或进入受控恢复。
9. 用户界面能够准确展示相关能力的可用状态。
10. 测试、判定报告和版本证据能够关联到统一任务与运行记录。

**最终目标：让 EvoAgent 的模型、工具、专家和工作流可以独立升级，但只有经过兼容性验证的组合才能进入稳定执行；让能力扩展不再依赖人工猜测和事后排错，而是依赖明确契约、自动检查和可追溯证据。**

## 本专项与用户产品的直接关联

这份设计不仅是后台治理，它会直接影响用户能否使用某项能力。

例如，用户打开编程任务时，系统应当判断当前代码工具、模型能力和运行环境是否满足要求；如果某个组件不兼容，界面显示明确的受限状态，而不是先让用户等待，再以工具错误结束。

同样，当后台准备升级某个专家时，系统需要先检查依赖与兼容性，再进入质量评测和发布门禁。这样才能让用户侧产品持续增加能力，而不破坏已经稳定的任务流程。
