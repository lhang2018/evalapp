## 一、先从第一性原理重新定义 EvoAgent

EvoAgent 的最终目标不是拥有越来越多的专家，也不是无限增加提示词、工具或模型调用。

它应该是一个能够：

- 理解用户真正想达成的目标；
- 选择合适的专家、专业技术和执行路径；
- 利用记忆与上下文维持任务连续性；
- 在真实环境中执行并验证结果；
- 识别失败究竟来自哪里；
- 将可重复的问题转化为可验证的改进；
- 在质量、稳定性、延迟、成本和安全之间做出合理权衡；
- 在模型、设备、工具和外部环境变化后，仍然保持可靠运行。

否则，它可能越来越擅长执行错误的策略，却越来越相信自己的策略是正确的。

这条链路至少还有六类需要专门设计的问题。

### 1. 用户意图会在执行过程中变化

例如，用户先说“帮我写一个程序”，随后补充“不能改原有接口”，最后又说“最好不增加依赖”。

系统必须知道：

- 哪些要求是新增约束；
- 哪些要求覆盖了旧要求；
- 哪些旧决策需要重新验证；
- 哪些已经执行的步骤需要撤销或重做；
- 哪些要求相互矛盾，需要用户裁决。

这需要一个**目标与约束管理系统**，而不是仅仅把所有对话拼接到上下文中。

### 2. 用户没有提供完整信息时，系统怎么决定？

不能所有问题都追问，也不能所有问题都自行猜测。

需要一个决策策略，根据错误代价、信息缺失程度、任务可逆性和用户等待成本，选择：

- 直接执行；
- 采用明确标注的合理默认值；
- 先做可逆的探索；
- 向用户追问；
- 暂停并说明阻塞原因。

### 3. 任务成功的定义可能是多维的

例如，生成一个视频并不等于任务完成。

可能还要求时长正确、声音清晰、角色一致、成本没有超限、文件能正常播放、产物保存成功。

所以需要**任务验收契约**，将目标拆成可检验的条件，而不能只靠模型回答“已经完成”。

### 4. 系统必须区分完成、部分完成和无法完成

例如，旅游行程已经规划完成，但酒店预订失败。

不能把整个任务简单标记为成功或失败，而应分别记录：

- 已完成的子目标；
- 未完成的子目标；
- 阻塞原因；
- 是否存在替代方案；
- 用户下一步需要做什么。

### 5. 任务需要有明确的终止条件

智能体可能反复搜索、不断修改计划、重试同一个工具，或者为了追求更好的结果无限优化。

因此需要明确停止条件：质量已达标、预算耗尽、收益不足、达到迭代上限、风险不可接受，或者用户取消。

### 6. 任务结果应该成为可复用资产

成功完成的任务可能产生代码、视频、研究报告、工作流、配置、素材或操作记录。

需要明确这些产物的所有权、版本、依赖、存储位置、可复用范围和有效期限。

这部分我们之前提到了工作流固化，但还没有完整覆盖**任务产物与长期项目资产管理**。

# 三、第二层：专家系统之外，还有哪些能力组织方式？

我们已经确定采用统一入口、多领域专家和共享基础设施。但如果继续递归，专家之间还存在更复杂的关系。

## 3.1 专家不仅有领域，还可能有不同职责

除了旅游、编程、AI 漫剧、手机操作等领域专家，还可能需要以下逻辑角色：

| 角色 | 主要职责 | 是否必须独立成为专家 |
|---|---|---|
| 任务规划器 | 目标分解、依赖和计划生成 | 不一定，可作为独立模块 |
| 路由器 | 专家选择、候选召回、路由评测 | 建议独立子系统 |
| 执行专家 | 负责具体领域任务 | 是，按领域组织 |
| 审查器 | 检查结果、寻找遗漏和错误 | 可共享，也可按领域定制 |
| 验收器 | 根据契约判定是否达标 | 建议与执行决策保持逻辑隔离 |
| 故障诊断器 | 区分规划、模型、工具和环境问题 | 建议独立诊断能力 |
| 进化控制器 | 管理候选、评测、发布与回滚 | 必须与普通执行逻辑隔离 |

这里还有一个没有完全讨论的问题：**执行者和审查者是否应该使用相同的模型、相同的提示词和相同的证据？**

如果完全相同，可能发生共同盲点。比如模型生成了一个错误方案，又用同样的假设来验证自己，最终仍然判定通过。

合理的方式不是强制所有任务使用第二个大模型，而是按风险选择独立验证手段：

- 代码使用测试、类型检查和静态分析；
- 视频使用文件校验、音画检测和抽样检查；
- 手机操作使用实际界面状态确认；
- 需要主观判断的内容，再使用独立模型或人工评审。

这样既能减少共同错误，也能避免无意义地增加模型调用成本。

## 3.2 专家之间还需要能力协商

例如，编程专家发现自己需要操作手机来验证应用行为。

它不应该直接突破自身权限去操作 Android，而应向手机操作能力提出结构化请求，并明确：

- 需要什么能力；
- 为什么需要；
- 预期输入输出；
- 需要什么权限；
- 执行失败时如何返回；
- 这次调用是否产生外部副作用。

这需要统一的**专家协作协议**。

此外，还要考虑专家冲突。例如：

- 编程专家希望修改文件；
- 安全策略禁止某类修改；
- 成本治理器认为剩余预算不足；
- 任务规划器认为修改会影响其他任务。

最终决策不能简单由最后发言的专家决定，而应通过统一的策略、权限和任务约束系统裁决。

## 3.3 专家能力还需要组合与继承规则

新增一个“前端开发专家”时，它可能复用编程专家的代码分析能力、测试工具、上下文治理和基础记忆接口。

但不应直接复制整个编程专家，然后长期维护两套重复实现。

因此需要区分：

- **专家配置**：专业指令、领域策略、评测集；
- **能力组件**：AST、测试、检索、图像分析等；
- **工作流模板**：可重复的任务编排；
- **共享内核**：安全、记忆、上下文和运行时。

专家应当组合这些资产，而不是将它们全部复制到自身内部。

# 四、第三层：记忆系统和上下文治理，还缺少哪些问题？

我们已经确定记忆与上下文是核心能力，也讨论了分层压缩和专家定制。但如果把它们作为长期运行的基础设施，还需要进一步考虑以下场景。

## 4.1 记忆不只是存储和检索

记忆系统至少需要处理八类问题：

    ["时效与失效","价格、行程、软件版本等信息什么时候过期？"],

举例：用户之前要求旅行预算控制在一定范围内，后来明确更改了预算。

这不应被处理成两条永远同时有效的记忆，而应记录新的有效约束、适用任务、修改时间和必要的历史信息。

再例如，编程专家发现某个解决方案有效。它不应该立刻把这条经验提升成通用规则。还需要知道它在哪个语言版本、框架版本和项目环境中有效，以及是否有独立验证证据。

## 4.2 记忆之间需要建立关系，而不是全部扁平化

建议至少支持以下关系：

- 事实与事实之间的冲突；
- 经验与适用条件之间的关系；
- 项目与任务之间的从属关系；
- 记忆与原始证据之间的引用关系；
- 规则与例外之间的关系；
- 记忆与专家、模型、工具版本之间的关联。

在必要时，可以采用关系数据库、全文检索、向量检索或图结构。**不应该为了使用某种新技术而把所有记忆都做成向量数据库。** 不同数据结构解决的问题不同。

## 4.3 上下文治理还要解决动态信息优先级

上下文不能只按最近消息、语义相似度或固定顺序选择信息。

同一条信息对不同阶段的价值不同。

例如，编程任务在定位错误时，最近的错误栈很重要；修改代码时，相关函数、接口契约和历史失败尝试更重要；验收时，测试结果和原始需求又更重要。

因此需要**阶段感知的上下文组装**：

- 识别当前任务状态；
- 判断当前步骤的目标；
- 检索适用记忆与证据；
- 保留硬性约束和未完成事项；
- 分配 Token 预算；
- 检查遗漏；
- 生成本次模型调用所需上下文。

同时必须处理上下文中的不可信内容。网页、文件、代码注释和工具返回可能包含恶意指令。它们应该被视为待分析的数据，而不是自动成为系统指令。

## 4.4 还需要防止记忆和上下文的反馈污染

这是一个容易被忽略的递归问题：

1. 专家做出了错误判断。
2. 系统把这次判断写入记忆。
3. 下一次上下文检索再次提供该错误经验。
4. 专家更倾向于重复同样的错误。
5. 进化系统观察到错误频繁发生，却错误地认为这是经过验证的惯例。

因此，记忆写入与经验固化必须有独立的可信度门槛。失败案例可以被保存用于诊断，但不应直接成为成功经验；未经验证的模型推断也不能自动升级成高可信度规则。

# 五、第四层：工具、环境和执行过程，还有哪些盲区？

我们已经讨论过工具本身可能有问题，这是对的。但工具故障并不是单一类别。

## 5.1 必须区分工具的不同故障

| 故障类别 | 示例 | 应优先检查什么 |
|---|---|---|
| 工具不可用 | API 超时、服务下线 | 网络、服务健康状态、依赖 |
| 输入错误 | 参数缺失、格式不合法 | 输入契约、调用参数、上游输出 |
| 工具实现错误 | 返回结果不符合规范 | 工具版本、实现和回归测试 |
| 环境不兼容 | Python 版本、Android 系统变化 | 环境检测、兼容性声明 |
| 结果不可信 | 返回成功但实际未完成 | 独立验证、证据一致性 |
| 权限不足 | 无障碍未授权、文件不可访问 | 权限状态、授权流程 |
| 外部状态变化 | 页面布局改变、资源被删除 | 重新观察、更新前置条件 |
| 部分执行 | 操作已生效但响应丢失 | 幂等键、状态查询和恢复策略 |

一个尤其重要的问题是：**工具调用超时，不代表工具没有执行。**

例如，智能体请求发布一条内容，服务器已经成功发布，但响应丢失。如果系统直接重试，就可能重复发布。

所以工具契约应支持幂等性、执行状态查询、可重试性声明，以及必要时的补偿操作。

## 5.2 工具与环境也要版本化

工具不是永远稳定的。一个工具即使接口不变，其底层依赖、行为、输出质量或权限要求也可能变化。

建议每次执行都记录：

- 工具 ID 和版本；
- 输入契约版本；
- 执行环境和依赖版本；
- 关键输入的摘要或受控引用；
- 原始返回结果和错误类型；
- 重试次数、耗时和资源消耗；
- 验证结果；
- 是否存在外部副作用。

工具升级后，应该重新运行相关能力的测试集，并评估依赖它的工作流和专家。

## 5.3 专业技术能力还需要沙箱与资源隔离

对于编程专家，运行用户代码可能产生文件删除、网络访问、资源耗尽等风险。

对于漫剧专家，批量生成或处理媒体可能消耗大量存储、内存和算力。

因此需要按能力定义：

- 运行权限；
- 文件系统边界；
- 网络访问范围；
- CPU、内存、GPU 和磁盘配额；
- 超时与进程终止策略；
- 依赖安装权限；
- 结果目录与临时目录；
- 清理和恢复规则。

尤其是云端执行用户代码时，不能把“模型认为代码安全”当成沙箱替代品。

## 5.4 系统还需要一个环境能力探测机制

在真正执行之前，EvoAgent 应知道当前环境是否具备所需能力。

例如：

- 当前 Android 版本是否支持目标操作；
- 无障碍服务是否已授权；
- 本地是否安装所需程序；
- Python 版本是否满足要求；
- 网络 API 是否可用；
- 当前模型是否支持所需的图像输入；
- 可用 GPU 显存是否足够；
- 剩余存储和任务预算是否满足需求。

这应形成**环境与能力探测系统**。它不仅供路由使用，也应在计划生成、任务启动和故障恢复时被调用。

# 六、第五层：Plan、DAG、ReAct 和工作流，还有哪些复杂情况？

我们已经厘清专家、计划、执行循环和工作流的职责，但长任务还需要更强的状态管理能力。

## 6.1 计划必须有版本与变更记录

假设一项任务最初有 10 个节点，执行到第 6 个节点时发现前提不成立，需要重新规划。

系统必须知道：

- 原计划是什么；
- 哪些节点已经成功；
- 哪些节点正在执行；
- 哪些节点的结果仍然有效；
- 哪些节点需要重新运行；
- 哪些外部副作用无法直接撤销；
- 新计划与旧计划之间发生了什么变化。

因此，计划不能只是模型返回的一段文本。对于复杂任务，它应该是版本化、可持久化的结构化对象。

## 6.2 DAG 还需要处理动态分支与循环

严格来说，DAG 本身不能包含环，但真实任务可能需要重复检查、重试或迭代优化。

合理的设计是：

- 用 DAG 表达一次计划的依赖关系；
- 用有限次数的循环节点或外层状态机表达迭代；
- 每次迭代保留输入、输出、失败原因和预算；
- 超过上限后转入替代方案、人工确认或停止。

这样既能表达复杂执行过程，又能保持依赖关系可分析。

## 6.3 长任务还需要持久化状态和断点恢复

例如，一部 60 秒漫剧制作了半小时后，手机重启或云端生成服务断开。

EvoAgent 不应该重新生成全部素材，而应能够恢复：

- 已完成节点及其产物；
- 未完成节点及其输入；
- 当前计划版本；
- 已消耗预算；
- 外部服务的任务 ID；
- 可继续执行的检查点；
- 需要重新验证的过期结果。

这要求任务状态和日志分开存储。日志用于观察与诊断，任务状态用于决定如何继续执行，不能拿日志简单重放所有动作。

## 6.4 失败恢复不能只有重试

建议为每类失败定义恢复策略：

- 重试：适用于可重试的瞬时故障；
- 替换工具：适用于特定工具不可用；
- 调整参数：适用于可诊断的输入问题；
- 重新规划：适用于原计划前提不成立；
- 回滚：适用于可逆且有明确回滚操作的改动；
- 补偿操作：适用于无法真正撤销的外部副作用；
- 请求用户确认：适用于高风险或关键信息缺失；
- 安全停止：适用于无法保证结果或权限的情况。

另外，重试必须有上限、退避策略和成本预算，不能无限循环。

# 七、第六层：自进化系统本身，还有哪些深层问题？

这一层是 EvoAgent 与普通智能体最大的区别，也是架构风险最高的地方。

## 7.1 问题发现不等于根因诊断

一条失败记录只能说明发生了什么，不一定能说明为什么发生。

例如，编程任务失败可能是：

- 路由选错了专家；
- 记忆召回了过期信息；
- 上下文遗漏了关键接口；
- Planner 漏掉了测试步骤；
- ReAct 过早结束；
- AST 工具解析失败；
- 测试环境不一致；
- 验收器判断错误。

因此，诊断器需要输出多个候选根因、支持证据、反证、置信度和下一步验证建议，而不是强行选择一个原因。

必要时应设计受控的诊断实验，分别更换组件或重放可复现的输入，比较结果变化。

## 7.2 系统可能错误地优化了指标

假设我们希望提升任务成功率。

系统可能通过：

- 只接受简单任务；
- 过度追问用户；
- 对失败任务直接报告成功；
- 反复调用昂贵模型；
- 删除困难评测案例；
- 放宽验收标准。

让表面指标变好，但真实用户体验变差。

因此，每个优化目标都需要配套的反指标和约束。例如：

| 优化目标 | 必须同时检查的约束 |
|---|---|
| 提高任务成功率 | 任务难度、误报成功率、风险事件 |
| 降低 Token 成本 | 结果质量、信息遗漏、恢复率 |
| 减少执行时间 | 超时率、错误率、验证完整性 |
| 提高自动完成比例 | 错误副作用、用户干预成本 |
| 提高记忆命中率 | 记忆准确率、过期信息和冲突率 |
| 提高路由准确率 | 追问率、拒绝率、跨领域任务成功率 |

## 7.3 评测集也可能被污染

如果系统把生产失败案例不断加入测试集，再针对这些案例反复优化，就可能逐渐过拟合已知问题。

还可能发生：

- 训练、调优和最终测试数据重叠；
- 模型生成的错误标签被当作真值；
- 只测试常见场景而遗漏边界条件；
- 评测标准随着候选版本一起变化；
- 某些专家的测试集长期得不到更新。

建议将数据分为开发集、验证集、保留回归集和真实环境监控集，并管理评测集的版本、来源、标注质量与泄漏情况。对于高风险能力，还应保留独立于候选生成流程的验收测试。

## 7.4 自进化必须有独立的发布权限

不能让一个正在优化自己的智能体同时：

1. 诊断自己的问题；
2. 修改自己的代码或配置；
3. 修改评测标准；
4. 宣布自己通过测试；
5. 直接覆盖生产版本。

这会形成自我认证的闭环。

更安全的方式是将候选生成、独立评测、发布审批和生产运行分开。低风险配置可以在预先授权的门禁下自动发布；涉及安全内核、权限边界、数据迁移或原生执行器的改动，需要更严格的审查。

## 7.5 进化收益必须考虑长期成本

某个策略可能让成功率提高一点，却让每个任务的平均成本翻倍。

因此，进化系统需要评估的不只是单次调用费用，还包括：

- 每个成功任务的总成本；
- 失败与重试的额外成本；
- 记忆检索和上下文压缩成本；
- 评测和候选实验成本；
- 外部服务费用；
- 本地资源消耗；
- 用户等待时间；
- 回滚和事故处理成本。

建议为每个任务、每个专家和每次进化实验设置独立预算，并由共享预算治理器实施硬限制。

## 7.6 进化还需要冷却期和稳定性判定

刚发布的版本不应因为短期表现波动就不断被新版本替换。

可以设置：

- 最小样本量；
- 最短观察期；
- 最低收益门槛；
- 置信区间或不确定性要求；
- 版本冷却期；
- 回滚触发阈值；
- 连续失败次数限制。

这样能够减少频繁迭代、版本振荡和成本失控。

# 八、第七层：Android 设备、云端和离线运行，还有哪些未覆盖的场景？

这是 EvoAgent 手机优先战略中特别容易被低估的一层。

## 8.1 Android 系统可能随时打断任务

需要考虑：

- App 进入后台后被系统限制；
- 进程被杀死或设备重启；
- 用户切换应用；
- 无障碍服务被关闭；
- 系统权限被撤销；
- 手机进入省电模式；
- 内存不足、磁盘空间不足；
- 系统升级或目标应用升级；
- 通知、麦克风、截图权限发生变化。

因此，任务状态不能只存在于内存里。需要持久化检查点，并且在恢复时重新检查权限、环境和外部状态。

还要明确一个现实边界：Android 的后台执行机制并不能保证任意任务永久运行。长期任务需要采用符合系统规则的后台执行方案，并根据任务类型使用适当的前台服务、WorkManager 或用户可见的持续任务机制。

## 8.2 云端断联不只影响模型调用

断联时可能同时失去：

- 云端模型；
- 远程工具；
- 任务编排服务；
- 记忆同步；
- 日志上传；
- 版本更新；
- 外部媒体生成服务。

所以不能只设置一个“网络不可用”的统一错误状态，而应记录各依赖的独立可用性。

例如，云端模型不可用，但本地已经生成的 FFmpeg 合成任务仍然可以继续；日志上传失败，也不应阻止一个已经获得授权的本地任务执行。

## 8.3 设备与云端需要有明确的权威数据边界

这是此前讨论过日志同步，但还应扩大到所有关键数据。

| 数据类别 | 建议的权威来源 |
|---|---|
| 当前设备权限与环境状态 | 设备本地 |
| 本地任务检查点 | 设备本地，按策略同步必要摘要 |
| 云端任务执行状态 | 对应任务执行服务 |
| 用户通用偏好 | 按数据类型指定权威副本与冲突规则 |
| 专家、工具和工作流发布版本 | 版本发布系统 |
| 原始设备运行日志 | 设备本地采集，云端接收已授权副本 |
| 进化候选与评测结果 | 进化与评测系统 |
| 外部任务的真实状态 | 外部服务查询结果或可验证的实际状态 |

不能采用“谁最后上传，谁就覆盖”的通用同步策略。不同数据需要不同的冲突解决方式。

## 8.4 跨设备未来扩展还要考虑任务所有权

虽然目前手机优先，但未来可能出现 Android 发起任务、云端执行、Windows 继续处理的情况。

这时需要：

- 任务归属与执行租约；
- 任务状态同步；
- 设备能力声明；
- 产物访问权限；
- 重复执行防护；
- 设备离线后的所有权转移；
- 用户取消任务时的跨端传播。

这也是为什么我们应当现在就定义统一任务协议，而不是等 Windows 版本开发时再补。

# 九、第八层：安全、隐私、信任与权限，还有哪些遗漏？

这部分不能只是增加一个安全专家或安全提示词，而应该作为所有组件必须遵守的系统约束。

## 9.1 提示词注入与不可信内容

智能体可能读取网页、邮件、代码仓库、文档或应用界面。其中可能包含诱导智能体泄露数据、执行危险工具或改变系统行为的内容。

系统必须区分：

- 系统级约束；
- 用户授权的任务指令；
- 专家配置；
- 外部数据；
- 工具返回；
- 模型生成的推断。

外部内容不能自动获得更高的指令优先级。检索到的内容即使与任务高度相关，也不代表它有权修改系统规则。

## 9.2 权限必须按动作和风险管理

不能只为某个专家授予一个宽泛的“可以操作手机”或“可以使用文件系统”的权限。

更合理的是针对具体动作检查：

- 谁发起了请求；
- 操作对象是什么；
- 是否涉及敏感数据；
- 是否会产生外部副作用；
- 是否可撤销；
- 是否需要用户确认；
- 当前授权是否仍然有效。

特别是支付、删除重要文件、发送消息、发布内容和修改系统设置等操作，不能仅凭模型置信度决定是否执行。

## 9.3 日志本身也可能泄露隐私

运行日志可能包含：

- 对话内容；
- 文件路径；
- 个人信息；
- 屏幕截图；
- 访问令牌；
- API 响应；
- 代码和业务数据。

所以需要日志脱敏、字段分级、加密存储、访问控制、保留期限、导出确认和删除策略。

默认不应把所有原始对话、截图和文件直接上传云端。诊断任务应尽可能只上传必要的结构化证据或经过脱敏的引用。

## 9.4 自动进化必须防止权限升级

如果进化系统能够修改提示词、工具注册表、工作流和策略，就可能意外扩大某个专家的权限。

所以权限范围应由独立安全策略控制，候选改进只能在已授权范围内变更。

例如，优化后的手机操作专家可以提高界面定位准确率，但不能因此自动获得支付权限；编程专家可以改善测试策略，但不能因为测试失败就自动开放任意网络访问。

## 9.5 必须支持撤销、暂停和紧急停止

用户应该能够：

- 取消当前任务；
- 暂停所有自动操作；
- 禁止某个专家调用特定工具；
- 关闭自动发布；
- 撤销或回滚某个能力版本；
- 清除指定记忆或停止同步；
- 查看当前正在执行的任务和权限状态。

这些控制应由运行时和安全内核实现，而不是依赖模型自觉遵守。

# 十一、还有三个长期演进问题，值得提前纳入架构

这些问题未必在第一阶段就能完全解决，但如果不提前预留设计空间，后面很容易推倒重来。

## 11.1 模型变化与模型能力漂移

我们已经讨论过切换模型时保存旧版本适配档案，但还需要考虑同一模型本身也可能变化。

例如，模型提供商更新模型版本、API 行为、上下文窗口、工具调用格式或速率限制。

因此，模型适配档案不应只记录模型名称，还应包括：

- 模型的准确版本或可识别的供应商标识；
- 调用参数和工具调用协议；
- 已验证的能力范围；
- 路由、压缩、规划和生成策略版本；
- 专项评测结果；
- 成本、时延和失败率；
- 回退模型及兼容性要求。

切换模型后，需要重新验证受影响的能力，不能仅凭模型名称或基准测试成绩就认定旧配置仍然适用。

## 11.2 能力依赖图与影响分析

这是一个非常值得正式增加的基础设施。

假设我们准备升级上下文压缩引擎。系统应该能回答：

- 哪些专家使用它？
- 哪些模型配置依赖它？
- 哪些工作流会受到影响？
- 哪些评测集需要重跑？
- 哪些设备版本兼容？
- 哪些历史候选版本需要重新验证？

建议建立**能力依赖图（Capability Dependency Graph）**，连接专家、技术能力、工具、工作流、模型配置、评测集和发布版本。

这样，进化系统在修改某个组件前，就能计算潜在影响范围，而不是只测试触发问题的那个任务。

## 11.3 长期经验固化与能力淘汰

我们讨论了成功工作流固化，但还没有完整讨论能力退役。

一个曾经有效的工作流可能因为 API 下线、模型变化、依赖漏洞、业务规则变化或更好的方案出现而不再适用。

因此需要：

- 能力健康度监测；
- 使用频率与收益统计；
- 过期依赖检测；
- 兼容性验证；
- 版本淘汰与迁移；
- 历史产物可追溯；
- 必要时恢复旧版本。

进化不是只增加新能力，也包括清理过时能力、合并重复实现、淘汰低收益策略，避免系统无限膨胀。

# 十二、递归遍历最后一层：容易被忽视的特殊场景

前面讨论的是主要架构。这里再从真实使用场景出发，寻找那些正常流程无法覆盖的问题。

| 特殊场景 | 可能发生的问题 | 需要的设计 |
|---|---|---|
| 用户表达自相矛盾 | 同时要求最低成本和最高质量，且不允许增加时间 | 目标冲突检测、权衡策略与必要的追问 |
| 任务中途改变目标 | 已完成步骤不再适用 | 计划修订、结果有效性检查、必要的补偿 |
| 多个任务同时运行 | 一个任务修改另一个任务正在使用的文件 | 资源锁、任务隔离、并发冲突检测 |
| 两个专家给出冲突建议 | 无法确定采用哪一个方案 | 证据比较、约束优先级与冲突裁决 |
| 工具成功但结果错误 | 返回码正常，实际产物不合格 | 独立验收与真实状态检查 |
| 工具失败但已产生副作用 | 重试导致重复操作 | 幂等控制、状态查询与补偿策略 |
| 外部数据过期 | 使用旧价格、旧文档或旧接口 | 时效标记、来源验证与重新获取 |
| 长任务跨越多个版本 | 恢复任务时配置已升级 | 版本快照、兼容性检查和迁移策略 |
| 新专家没有足够样本 | 路由器不知道它是否可靠 | 冷启动策略、受控试用与最低能力验证 |
| 用户纠正系统 | 纠正可能只适用于当前任务 | 判断是局部约束还是长期偏好，再决定是否记忆 |
| 评测指标短期波动 | 系统频繁发布、回滚 | 样本量门槛、观察期与稳定性策略 |
| 所有工具都不可用 | ReAct 继续循环 | 能力缺失识别、停止条件和用户告知 |
| 设备存储即将耗尽 | 日志、缓存和任务产物无法继续保存 | 分级保留、清理策略和任务安全停止 |
| 本地时钟错误 | 任务超时、缓存过期判断错误 | 可靠时间源、单调时钟和时间不确定性处理 |
| 用户取消任务 | 云端仍继续生成、产生费用 | 取消传播、任务终止状态和费用停止机制 |
| 更新后出现退化 | 新版本覆盖了旧版本的稳定行为 | 灰度、回滚、版本钉住和线上回归监控 |
| 同一问题反复出现 | 每次都重新诊断、重复花费 | 故障案例库、相似问题检索和已知修复复用 |
| 专家数量不断增加 | 路由成本与选择错误上升 | 专家合并、能力去重、淘汰与注册表治理 |
| 模型或工具被恶意内容诱导 | 执行未经授权的动作 | 指令隔离、权限检查和安全策略 |
| 用户删除数据但云端仍保留 | 本地与服务端数据不一致 | 删除传播、同步确认和备份生命周期治理 |

这张表还可以继续扩充，但其中有一个共同规律：

**不能只设计正常执行路径，还必须设计中断、冲突、恢复、撤销、升级和退役路径。**

## 十三、我们还没有充分讨论的一个根本问题：什么叫“进化成功”？

这是我认为最值得深入的一个问题。

假设 EvoAgent 在某个测试集上的任务成功率从 80% 提高到了 85%。

这是否意味着它真的进化了？

不一定。

因为可能存在以下情况：

- 测试集太简单；
- 评测标准被放宽；
- 调用次数从 2 次增加到 8 次；
- 高风险错误增加了；
- 对新场景的泛化能力下降；
- 记忆检索开始依赖特定历史案例；
- 成功率提升只发生在一个专家上，却让其他专家退化。

因此，我们需要把“进化成功”定义成一个多维判断，而不是单一分数。

  <title size="lg">EvoAgent 进化验收的五个维度</title>
  {#each [
    ["任务质量","结果正确、完整，满足用户目标与验收契约。"],
    ["可靠性","失败可检测、可恢复，重复执行行为稳定。"],
    ["泛化能力","在未见过的任务、环境和输入上没有明显退化。"],
    ["资源效率","质量提升相对于模型调用、延迟和计算资源的成本合理。"],
    ["安全与可控性","不扩大未授权权限，不破坏隐私、硬性约束和回滚能力。"]

  {/each}

我建议采用**带硬约束的多目标优化**，而不是简单地把所有指标加权成一个总分。

例如，某个候选版本即使显著提高了任务成功率，只要它突破了权限边界，或让高风险错误超过上限，就必须拒绝发布。

另外，质量提升和成本提升之间应该建立明确的决策规则。允许某些重要任务花费更多模型调用来提高成功率，但不允许成本无限膨胀。每种专家、任务等级和风险等级都可以有不同预算与收益门槛。

# 十五、现在最重要的不是继续无限增加模块，而是找出架构中的关键依赖关系

经过这次梳理，我认为有五个问题应该优先解决，因为它们会影响几乎所有其他模块。






      <title size="md">优先级 1：统一任务契约与状态模型</title>
      基础依赖
      明确任务目标、约束、计划、执行状态、验收结果、取消、恢复和产物引用。否则，专家、DAG、ReAct、日志和云端同步会各自维护一套状态。








      <title size="md">优先级 2：统一能力契约与依赖图</title>
      扩展基础
      将专家、工具、专业技术、工作流和模型配置组织成可组合、可发现、可版本化的能力资产，避免新增一个领域就重写核心代码。








      <title size="md">优先级 3：独立验收与故障归因</title>
      质量基础
      将“执行了什么”“工具报告什么”“实际结果如何”“为什么失败”分开记录，防止错误结果被当成成功经验。








      <title size="md">优先级 4：统一版本、评测与发布门禁</title>
      进化基础
      让专家、模型配置、压缩策略、工具和工作流能够独立迭代，同时计算跨组件影响、控制成本并支持回滚。








      <title size="md">优先级 5：设备离线与可靠恢复</title>
      运行基础
      确保 Android 端在断网、进程重启、权限变化和版本升级时，能够正确保存状态、恢复任务、同步日志并避免重复副作用。



## 十六、我的最终判断：还需要补充什么，才能让架构真正完整？

经过这次递归审查，我认为主要方向已经覆盖得比较全面，但仍有一些内容需要通过正式设计来冻结，不能仅凭模块名称就认为已经解决。

最值得继续细化的是：

1. **统一数据模型**：任务、事件、记忆、上下文快照、工具调用、产物和版本之间的关联关系。
2. **统一能力协议**：专家如何声明能力，工具如何声明错误，工作流如何调用能力，以及跨设备如何保持兼容。
3. **统一状态机**：任务执行、取消、重试、恢复、部分成功和终止的精确语义。
4. **统一评测标准**：如何证明一个组件真的变好，如何判断改进收益足以抵消成本。
5. **统一进化权限模型**：哪些对象可以自动修改，哪些必须人工批准，哪些永远不能被进化系统修改。
6. **统一运行与恢复机制**：设备、云端和外部服务在各种中断情况下，如何保证状态一致、避免重复操作。
7. **统一长期治理机制**：如何淘汰旧能力、迁移数据、应对依赖漏洞和模型变化，避免系统随着进化不断膨胀。

我不建议此时继续无止境地增加新的逻辑模块。下一步更有价值的是将这些内容整合成一套正式的**《EvoAgent 全量架构设计基线与关键决策清单》**，明确哪些决定已经确定、哪些仍有多个可选方案、每项决策依赖什么证据，以及变更时需要重新评测哪些组件。

这样我们就能从“不断想到新功能”，转向“形成一套边界清晰、能够实现、能够验证、能够长期演进的完整系统设计”。
