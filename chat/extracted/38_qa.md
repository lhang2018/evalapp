## 用户

那当前有几个服务端了呢，他们怎么协同的呢

## ChatGPT

结合我们前面确定的 EvoAgent 全量架构，**服务端不能简单地越拆越多，而应该按职责划分逻辑服务，再根据实际规模决定是否独立部署。**

目前设计中，已经出现了模型服务、稳定任务服务、进化服务、同步服务、版本分发服务等不同职责。它们不是五套各自独立的智能体，也不是每个模块都必须单独买一台服务器。

我建议采用一个明确的方案：**一个统一的服务端平台，划分多个逻辑服务，内部协同；稳定执行与进化实验隔离；通过统一的任务、事件和版本协议连接 Android App。**

这样既能支持未来扩展，也避免一开始就陷入复杂的微服务治理。

这里有三个需要特别说明的地方：

- **模型网关服务不等于大语言模型本身。** 真正的模型可以由外部云端 API 提供商运行，EvoAgent 的模型网关负责调用和管理。
- **能力与工具服务不代表所有工具都必须放在云端。** Android 原生接口、无障碍操作等能力仍然在手机上执行，云端保存能力定义、版本和可远程执行的工具。
- **数据库、消息队列和 Git 仓库是基础设施，不计入上述 8 个逻辑服务。**

# 二、这 8 个服务怎么协同？

可以理解为两条相互连接的业务链：一条负责完成用户任务，一条负责让未来任务做得更好。

## 2.1 第一条链：完成任务




      **① App 提交任务**
      提交用户目标、必要约束和当前能力信息。






      **② 任务编排服务**
      识别意图、选择领域专家，决定使用 ReAct 还是工作流。






      **③ 模型网关 + 记忆与上下文**
      准备必要上下文，选择合适模型，产生下一步行动建议。






      **④ 能力与工具执行**
      调用云端工具或让 App 执行手机操作，记录实际结果。






      **⑤ 验证与返回**
      验证目标是否达成，必要时恢复、重试或请求用户协助。



这里并不是每个任务都必须经过全部服务。

例如，打开手机上的一个应用，如果本地就能通过 Android 原生接口完成，可以直接在 App 端执行，不必为此调用云端模型。

而一个复杂的 AI 漫剧制作任务，则可能需要云端规划、多个生成工具、工作流编排和长时间的任务状态管理。

**路由和执行模式应该由任务需要决定，而不是固定经过所有模块。**

## 2.2 第二条链：让系统越来越好




      **① App 产生运行证据**
      记录失败、耗时、工具结果、验收结论和版本清单。






      **② 同步与观测服务**
      去重、归档、关联任务和运行版本，形成可追溯证据。






      **③ 进化与诊断服务**
      分析根因，判断该修改模型适配、工具、提示词、记忆还是工作流。






      **④ 评测与发布门禁**
      比较基线与候选，检查质量、成本、兼容性和安全。






      **⑤ 版本分发服务**
      发布签名制品和版本清单，向适用的 App 分发更新。




    **⑥ App 验证更新效果**
    继续收集真实运行指标，判断新版本是否值得保留或需要回滚。


两条链之间有一个关键隔离：进化服务不会直接改写正在执行任务的运行状态。它只生成候选并经过评测、发布和兼容性检查，才可能影响 App 的后续任务。

# 三、这 8 个服务需要分别部署吗？

**不需要一开始就部署成 8 个独立的微服务。** 我建议采用“逻辑服务先分开，物理部署按需要拆分”的策略。

| 部署单元 | 包含的逻辑服务 | 部署原则 |
|---|---|---|
| 稳定任务后端 | 1、2、3、4 | 优先保证可用性和任务执行稳定 |
| 进化控制后端 | 5、6、7 | 与正式任务执行隔离，控制实验资源 |
| 版本分发后端 | 8 | 独立管理制品、发布状态和回滚 |
| 外部模型服务 | 模型提供商 API | 由网关统一接入，可切换提供商 |
| 共享基础设施 | 数据库、对象存储、Git、队列等 | 根据可靠性和负载分别部署 |

这是一个**建议的部署边界**，不是必须采用的唯一方案。比如在资源有限时，任务编排、记忆与上下文、能力注册可以先作为同一后端应用中的独立模块；进化实验执行器则应保持隔离，避免候选代码影响生产任务。

未来负载增大时，再把高负载模块独立扩容。

# 四、它们如何避免互相干扰？

这比服务数量更重要。

1. **统一身份。** 每次任务有 `task_id` 和 `run_id`，每次运行关联不可变的 `runtime_manifest`。
2. **统一契约。** 服务之间通过明确的 API、事件格式和版本协议协作，不随意共享可变内部状态。
3. **统一权限。** 任务服务、进化服务和发布服务拥有不同权限，进化服务不能直接覆盖生产版本。
4. **统一预算。** 正式任务和候选实验使用独立预算池。
5. **统一版本治理。** 提示词、模型适配、工作流和工具都有独立版本；发布时再组成一个完整的运行版本清单。
6. **独立故障域。** 进化服务不可用时，不应影响已经批准的稳定能力；模型服务不可用时，App 根据本地能力和备用路径决定继续或安全停止。

# 五、我认为还需要特别明确的一点

8 个逻辑服务并不意味着 8 个服务都应该拥有独立的决策权。

真正需要有明确权威边界的是以下四个控制器：

- **运行时控制器：** 决定当前任务可以做什么。
- **进化控制器：** 决定研究和验证什么改进。
- **评测门禁控制器：** 判断候选是否满足发布条件。
- **发布控制器：** 决定哪些经过批准的版本可以下发、激活或回滚。

它们之间有严格的权限边界。尤其是进化控制器，不能自行认定自己生成的改进是正确的，再直接发布到 App。

**最终建议：先冻结 8 个逻辑服务的职责与接口，而不是冻结 8 台服务器的部署方式。** 这样既能保持完整架构，也能根据未来的使用规模灵活部署，不必因为服务拆分方式变化而推翻整个 EvoAgent 架构。
