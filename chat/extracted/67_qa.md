# EvoAgent 第十二专项：进化优先级与全局资源调度引擎

这一轮要解决的，不是智能体如何发现问题，而是一个更接近“自主进化大脑”的问题：

**EvoAgent 同时发现很多问题时，怎样决定先改什么、投入多少资源、改到什么程度，以及什么时候应该停止优化？**

你之前明确过几个重要原则：

- 通用能力与领域专家要分开优化，避免局部改进污染其他能力。
- 提示词、Harness、上下文、记忆、ReAct、Planner、工具和工作流都可能成为改进对象。
- 能力真正提升后，可以接受一定的模型调用成本增加，但成本不能无限膨胀。
- 经验需要验证，不能因为一次任务失败就修改整个智能体。
- 不同模型要能独立进化，同时保留已经验证的稳定版本。
- EvoAgent 是个人使用系统，运行资源有限，不应该为了优化而建立庞大、昂贵的后台系统。

这些原则共同决定了：进化系统不能只是一条“发现问题 → 修改配置 → 测试”的流水线。它还需要一个负责分配有限资源、选择最有价值改进的决策层。

我建议把它设计为 `Evolution Prioritization & Resource Allocation Engine`，简称 **EPRA（进化优先级与资源调度引擎）**。

## 一、先明确：什么才算一次有价值的进化？

假设 EvoAgent 在一周内发现了以下问题：

- 100 次任务中，路由器有 8 次选错专家；
- 编程专家有 2 次复杂重构失败；
- 上下文压缩有 1 次丢失关键约束；
- 漫剧生成工作流有 5 次重复调用，增加了费用；
- 某个工具偶尔返回错误状态；
- 当前模型调用成本比预期高 20%。

不能简单地按照出现次数排序。

因为一次错误的权限判断，可能比几十次无害的格式错误更严重；一个低频但会导致数据损坏的工具缺陷，也可能比一个高频但只影响回答风格的问题更值得优先处理。

因此，我建议从第一性原理出发：

**进化的目标不是消灭最多的错误，而是在安全和资源约束下，最大程度地提高未来任务的综合表现。**

这里的综合表现至少包括：

- 任务质量与成功率；
- 稳定性和可恢复性；
- 用户体验与返工负担；
- 运行延迟；
- 每个成功任务的总成本；
- 权限、安全与隐私；
- 长期维护成本。

有些目标可以权衡，有些则是硬性约束。例如，降低成本不能抵消违反权限边界的风险。

# 二、第一层决策：哪些问题必须优先处理？

进化系统首先要区分“必须处理的问题”和“可以优化的问题”。

这是因为不能让一个统一的收益分数决定所有事情。

## 2.1 建立四级优先级






      <title size="lg">P0：安全与完整性事件</title>
      例如未经授权的操作、重复支付风险、错误报告高风险任务成功、工具可能破坏用户数据。
      **处理原则：** 先限制风险、暂停相关动作或隔离问题组件，再诊断。不能因为成本高而推迟必要的保护措施。








      <title size="lg">P1：核心能力与系统稳定性问题</title>
      例如共享工具存在普遍缺陷、任务恢复经常失败、关键上下文被持续丢失、路由大面积错误。
      **处理原则：** 优先修复影响面大、复现明确或造成明显任务损失的问题。








      <title size="lg">P2：质量、效率与成本优化</title>
      例如减少不必要的模型调用、降低重复生成、改善复杂任务规划、减少用户返工。
      **处理原则：** 在满足安全和稳定性要求后，按预期净收益排序。








      <title size="lg">P3：探索性改进</title>
      例如尝试新的规划策略、新的模型路由方式、潜在的跨领域经验迁移。
      **处理原则：** 使用有限的实验预算探索，不挤占必要的故障修复资源。



这四级不是单纯的分数排名，而是不同的处理策略。

例如，一个高风险问题可能没有明确根因，但仍然应该立即限制相关动作。它不需要先证明“修复收益最高”，才获得处理资源。

反过来，一个高频但影响极小的问题，不一定需要立刻投入大量模型调用进行深度诊断。

## 2.2 P0 不等于立即自动修改代码

发现高风险问题后，最优先的动作通常是降低风险，而不是立刻尝试修改工具。

例如，工具返回结果与实际状态持续不一致时，系统可以先将它标记为不可信，停止让它承担关键验收任务，再在隔离环境中分析原因。

这比让自进化系统在生产环境中直接改写工具实现更安全。

# 三、第二层决策：如何估算一项改进真正值多少钱？

确定优先级等级后，系统还需要对候选改进进行量化比较。

我建议为每个候选建立统一的 `Improvement Candidate` 记录。

## 3.1 候选改进的完整信息

每项候选至少需要包含：

| 字段 | 要回答的问题 |
|---|---|
| 问题描述 | 具体发生了什么？ |
| 影响范围 | 影响多少任务、哪些专家和哪些模型？ |
| 根因状态 | 已确认、较可信、多个假设还是未知？ |
| 预期收益 | 改进后哪些指标会提高或降低？ |
| 证据强度 | 收益估计基于多少真实案例和测试？ |
| 改进成本 | 开发、模型调用、评测和维护需要多少资源？ |
| 回归风险 | 会不会影响其他领域或共享组件？ |
| 可逆性 | 失败后能否安全回滚？ |
| 适用范围 | 当前项目、某个专家、某个模型还是全局？ |
| 停止条件 | 什么结果意味着不值得继续？ |

其中最重要的是区分**问题严重程度、证据强度和修复成本**。

严重的问题不一定容易修；修复容易的问题也不一定值得优先修；有很高预期收益但证据极弱的方案，可能值得先做低成本实验，而不是直接发布。

## 3.2 建立预期净收益模型

对于可以合理估算的改进，可以使用一个简化框架：

\[
\text{预期净收益}
=
\text{预期任务损失减少}
+
\text{预期质量与效率收益}
-
\text{实施成本}
-
\text{验证成本}
-
\text{维护成本}
-
\text{预期回归损失}
\]

这里的各项需要在明确的评估周期内衡量，避免把不同时间范围的收益混在一起。

例如，一项改进可能增加一次模型调用，但减少后续三次失败重试。如果它确实降低了每个成功任务的总成本，那么增加单次调用并不意味着整体变贵。

反过来，一项改进即使提高了任务成功率，如果导致每个任务都额外调用大量模型，也需要判断收益是否足以抵消成本。

安全和权限仍然是独立门槛，不能通过这条公式抵消。

## 3.3 不要让一个公式假装自己无所不知

真实场景下，收益和回归风险往往不能精确估算。

所以我建议每个候选同时保存：

- 预期收益区间；
- 估计依据；
- 关键假设；
- 置信程度；
- 最坏可接受结果；
- 哪个实验可以最快验证关键假设。

例如，“优化上下文压缩预计减少 15% 的模型费用”只能是实验假设，不能直接作为事实写进系统。

如果不确定性很大，系统应优先比较实验成本，而不是只比较理论收益。

# 四、第三层决策：先修根因，还是先做实验？

这一步决定 EvoAgent 会不会把资源浪费在错误方向上。

假设发现编程专家的任务成功率下降，有四种可能：

1. 路由器把复杂任务交给了不合适的模型；
2. 上下文压缩丢失了项目约束；
3. 工具调用返回了错误状态；
4. 编程专家的提示词确实存在缺陷。

如果根因尚未确定，直接优化提示词可能只是碰巧改善部分案例，甚至会掩盖真正的工具故障。

因此，进化系统需要在“立即修复”和“先诊断”之间进行选择。

## 4.1 建立诊断投入策略

| 情况 | 推荐策略 |
|---|---|
| 根因明确，修复小且可逆 | 直接生成修复候选，进入专项测试 |
| 根因基本明确，但影响范围不确定 | 先做局部修复实验，再检查保护集合 |
| 存在多个根因假设 | 先选择最有区分力的低成本诊断实验 |
| 影响面大，但复现困难 | 先增加观测、构造最小复现案例 |
| 安全风险高、原因未知 | 先隔离或降级相关能力，再深入诊断 |
| 预期收益很小，诊断成本很高 | 暂缓或归档，除非风险等级要求立即处理 |

## 4.2 用信息价值决定是否继续调查

例如，某个工具最近发生了 10 次失败。

系统可以先检查：

- 是否集中在同一工具版本；
- 是否都发生在网络超时后；
- 是否来自同一模型；
- 是否都使用了某类参数；
- 是否发生在同一工作流节点。

如果这几个低成本检查就能排除大多数假设，就不需要立刻启动昂贵的大模型诊断。

只有在关键原因仍然不明确、且不同原因会导致不同修复方案时，才值得投入更多诊断资源。

这让进化系统不仅知道“哪个问题值得修”，也知道“现在是否值得花钱查清楚”。

# 五、第四层决策：全局资源应该怎样分配？

这里需要把个人使用的现实约束纳入架构。

EvoAgent 可能运行在 Android 手机上，后台分析则交给个人电脑或 Mini PC。它不应该为了追求理论上的最优，把每一条日志都交给大型模型分析。

我建议将资源预算拆成四个池。


    **预算池 A：运行时可靠性**
    用于必要的任务验证、故障恢复、安全检查和关键状态核验。优先保障，不能被普通进化实验随意挤占。


    **预算池 B：已知问题修复**
    用于修复已复现的工具缺陷、路由问题、上下文错误和工作流故障。


    **预算池 C：性能与成本优化**
    用于降低成功任务成本、缩短执行时间、减少返工和改善用户体验。


    **预算池 D：探索性实验**
    用于尝试新的模型、规划策略、经验迁移和潜在能力提升。


这里不建议现在就给四个池设定固定百分比。

个人电脑的可用资源、模型 API 预算、当前故障数量和用户使用频率都会变化。固定比例可能在某些时期浪费资源，在另一些时期又不足以修复关键问题。

更合理的方式是：

- 先满足运行时可靠性和安全所需的最低资源；
- 再为已知问题修复分配资源；
- 根据实际收益决定性能优化投入；
- 在资源允许时开展探索性实验；
- 如果出现高优先级故障，允许重新分配非必要实验预算。

## 5.1 预算必须同时包含硬上限和软目标

建议支持：

- 每日和每月模型费用上限；
- 单个进化实验费用上限；
- 每轮诊断的最大调用次数；
- 最大并发实验数；
- 最大本地 CPU、内存和磁盘占用；
- 最大后台运行时间；
- 正式任务的最低资源保障；
- 进化实验对手机前台体验的影响限制。

其中，硬上限由确定性控制器执行。模型不能通过声称“再多调用一次就能成功”，自行突破预算。

## 5.2 离线时也能做有价值的进化工作

当网络断开或云端模型不可用时，个人电脑仍然可以进行一部分低成本工作：

- 汇总已有的结构化事件；
- 统计工具错误频率；
- 发现重复调用和无进展循环；
- 运行本地测试；
- 重放已有的脱敏案例；
- 检查经验库中的冲突和过期记录；
- 对比本地代码与稳定版本的差异。

但是，没有模型或必要证据时，系统不应假装完成了复杂的语义诊断。

可以将候选问题排队，等待恢复网络后再进行更深入的分析。

# 六、第五层决策：通用能力、专家能力和工具能力，谁先优化？

这是你之前特别强调的问题：一个领域出现错误，并不意味着通用智能体整体有问题。

所以，进化系统必须同时考虑改进的**影响范围**与**收益范围**。

## 6.1 建立四种改进作用域

| 作用域 | 典型改进 | 回归要求 |
|---|---|---|
| 单次任务 | 调整本次计划、补充上下文 | 当前任务重新验收 |
| 专家级 | 优化编程专家、旅游专家或漫剧专家 | 领域专项测试及共享接口测试 |
| 共享组件级 | 修复工具网关、上下文引擎、路由器 | 所有受影响专家的相关回归测试 |
| 全局内核级 | 修改权限、安全、任务状态和发布控制 | 最严格的兼容性、安全和恢复测试 |

一个候选不应该因为潜在收益较高，就自动获得更大的修改权限。

例如，编程专家的提示词优化，默认应该留在编程专家分支。只有当根因分析表明问题来自共享上下文引擎时，才应考虑共享组件改进。

## 6.2 评估收益时要计算实际影响面

假设路由器在编程任务中出现 10% 的错误，但编程任务只占全部任务的 5%。

同时，旅游专家有 4% 的失败率，但旅游任务占全部任务的 40%。

如果两类失败的严重程度相近，那么旅游专家的改进可能带来更大的整体收益。

但如果编程错误会破坏文件，而旅游错误只是推荐不够准确，风险调整后的优先级又可能反过来。

因此，候选排序应考虑：

- 任务发生频率；
- 失败概率；
- 失败严重程度；
- 可修复程度；
- 改进覆盖范围；
- 实施和验证成本；
- 其他领域的潜在退化。

不能只根据某个专家的局部成功率判断全局价值。

## 6.3 避免把不同专家的差异抹平

不同专家本来就应该具有不同的策略。

编程专家需要考虑 AST、测试、依赖和代码差异；手机操作专家需要关注界面状态、无障碍节点和操作副作用；漫剧专家需要关注角色一致性、媒体生成、音画同步和预算。

全局优化器应当负责分配资源、治理共享组件和比较整体效果，而不是强制所有专家使用相同的提示词、规划深度和验收方法。

# 七、第六层决策：如何判断一个优化值得继续，还是应该停止？

自进化系统很容易陷入另一个问题：一项改进已经产生收益，但系统不断追加优化，最后新增成本大于新增收益。

因此，我建议每项进化任务都具有明确的停止规则。

## 7.1 四种停止条件

  {#each [
    ["收益已足够","候选达到目标指标，并且没有必要继续投入更多资源。"],
    ["收益递减","追加实验带来的预期改善越来越小，已不足以覆盖成本。"],
    ["证据不足","多轮实验无法证明候选优于基线，或者结果受随机因素影响过大。"],
    ["风险或预算触顶","达到成本、时间、资源或安全限制，必须暂停、回滚或重新评估。"]
  ] as item}



        **{item[0]}**
        {item[1]}


  {/each}

## 7.2 不要把“没有明显提升”直接当成失败

某个实验可能没有提升成功率，却减少了 20% 的模型费用；也可能提升了质量，但让延迟大幅增加。

所以，候选的停止判断应该回到它最初的目标。

例如：

- 目标是减少工具误用，就重点看工具误用率和相关任务质量；
- 目标是降低成本，就比较每个成功任务的总费用；
- 目标是提升安全性，就看高风险错误率和保护性停止是否有效；
- 目标是改善跨模型迁移，就看新模型上的表现，而不是只看源模型。

同时保留整体保护指标，防止为了一个目标导致其他关键指标退化。

## 7.3 采用“最小有效改进”原则

我建议 EvoAgent 优先选择能够解决问题的最小改动。

例如，路由器把一个新任务类型错误地分配给旅游专家。

如果根因只是缺少一条明确的意图判定规则，就不应该立即重写整个路由架构。

先修正局部规则、补充评测案例，再检查是否还有更深层的架构缺陷。

只有当多个局部修复都失败，或证据表明系统结构本身不适合当前任务时，才扩大改动范围。

这样能降低回归风险，也更容易确认究竟是什么变化带来了改善。

# 八、进化优先级引擎的实际工作流程

将前面的设计汇总起来，EPRA 的完整流程可以是：

  {#each [
    ["01","收集问题","从任务失败、用户纠正、工具异常、成本变化和评测结果中形成候选。"],
    ["02","分类与分级","判断是安全事件、核心能力缺陷、效率问题还是探索机会。"],

## 8.1 让进化引擎也学习自己的资源分配效果

这里还可以进一步形成一个闭环。

EPRA 不仅要判断哪些问题值得修，还要记录自己的判断是否准确。

例如：

- 预计修复一个工具缺陷可以改善 100 个任务，实际只改善了 10 个；
- 预计一次上下文优化收益有限，实际却显著减少了重试；
- 花费大量预算优化提示词，但真正根因是工具参数契约；
- 某个低频问题虽然出现不多，却造成了很高的恢复成本。

这些结果可以用来校准后续的优先级预测。

但要避免让调度器陷入自我强化：如果它总是优先优化容易测量的成本问题，就可能忽略难以量化的可靠性和安全问题。

因此，必须保留硬性安全约束、必要的探索预算，以及独立评测对优化结果的监督。

# 十、下一专项：自进化系统的目标函数与长期能力治理

我们已经设计了进化系统如何发现问题、学习经验、修复故障、适配模型，并选择优先改进的对象。

但还有一个更根本的问题：

**如果 EvoAgent 的各个模块都在优化自己的指标，怎样保证它们最终共同朝着用户真正需要的方向进化？**

例如：

- 路由器为了提高分类准确率，增加更多模型调用；
- Planner 为了减少失败，生成越来越长的计划；
- 验收器为了避免假成功，频繁要求更多检查；
- 上下文系统为了避免信息丢失，不断增加输入长度；
- 自我修复系统为了提高恢复率，增加更多重试；
- 进化引擎为了提升质量，不断扩大测试规模。

每个模块看起来都在变好，但整体系统可能越来越慢、越来越贵，用户体验反而下降。

这意味着我们还需要一个更高层的治理机制，负责判断：

1. EvoAgent 的长期目标究竟是什么；
2. 质量、稳定性、成本、速度和自主程度如何共同衡量；
3. 哪些指标是硬性约束，哪些允许权衡；
4. 如何识别局部最优导致的全局退化；
5. 如何防止系统通过降低验收标准、改变统计口径来制造进步；
6. 如何处理不同专家之间的目标冲突；
7. 如何判断一次进化究竟改善了用户体验，还是只改善了内部指标；
8. 如何防止自进化目标偏离用户明确的需求与授权；
9. 如何维护长期稳定能力，同时允许必要的架构升级；
10. 如何判断 EvoAgent 已经足够好，暂时不值得继续投入优化资源。

我建议下一轮设计 **Global Objective & Capability Governance Engine（全局目标与能力治理引擎）**。

它将决定 EvoAgent 不只是持续变化，而是持续朝着正确的方向变化。
