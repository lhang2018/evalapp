# 第一章 产品概述

## 1.1 产品定义

EvoAgent 是一个能够理解用户意图、规划并执行任务、调用工具、管理记忆、验证执行结果、诊断运行问题，并通过持续评测改进自身能力的个人智能体系统。

EvoAgent 不以单纯增加功能数量为最终目标，而是追求在明确的任务范围、运行环境、模型能力、权限约束和资源预算下，持续提升任务完成质量、稳定性、执行效率和成本效益。

与普通对话式 AI 不同，EvoAgent 不仅要回答问题，还要能够：

1. 理解用户真正想完成的任务。
2. 判断任务需要哪些能力、工具和执行流程。
3. 将复杂目标分解为可以执行和验收的步骤。
4. 在执行过程中观察状态、调用工具、处理异常。
5. 通过独立的验收机制判断任务是否真正完成。
6. 记录执行轨迹、失败原因、恢复过程和结果质量。
7. 从运行证据中识别可以改进的问题。
8. 对候选改进进行隔离实验、自动评测和风险审查。
9. 将通过门禁的低风险改进发布到适用范围内。
10. 在模型、工具或环境变化后重新验证能力，并保留历史稳定版本。
11. 在网络或服务端不可用时，继续执行允许离线完成的任务。
12. 随着任务积累，逐渐形成可复用的专业能力和稳定工作流。

## 1.2 产品愿景

打造一个能够长期陪伴用户、逐步理解用户需求、稳定完成复杂任务，并通过证据驱动持续改善执行质量的个人智能体平台。

最终形成以下能力：

- 用户只需要表达目标，不必事先了解工具和工作流。
- 智能体能够根据任务自动选择合适的领域专家、模型和工具。
- 简单任务可以快速完成，复杂任务可以规划、分解和持续执行。
- 已经验证有效的工作流程可以沉淀为稳定能力资产。
- 运行中遇到的问题能够被系统化记录、诊断和改进。
- 不同领域的能力可以独立进化，避免相互污染。
- 模型切换后能够继承适用资产，而不是从零开始。
- 稳定运行与后台进化相互独立，避免实验破坏正式版本。
- 进化过程受到安全、质量、成本和发布权限的共同约束。

## 1.3 核心产品理念

### 理念一：任务完成优先于模型输出

模型生成了答案、调用了工具或执行了操作，不代表任务已经完成。

系统必须根据任务类型设置验收标准，尽可能通过工具结果、状态检查、测试结果或其他独立证据验证完成情况。

### 理念二：运行稳定与后台进化分离

正在执行任务的稳定版本，不直接接受未经验证的提示词、策略、工具代码或工作流修改。

所有长期改进均应经过候选生成、评测、门禁和受控发布。

### 理念三：局部问题不等于整体能力缺陷

某个代码写法错误，不代表整个编程能力存在缺陷；某个旅游任务失败，也不代表通用规划能力必然退化。

系统必须根据任务、领域、组件、模型、工具和环境等维度定位问题，限制改进影响范围。

### 理念四：所有重要改进都应有证据

不能仅因为模型认为新方案更好，就自动认定优化成功。

每项重要改进都需要明确目标、基线、评测方法、成本变化、风险和回滚方案。

### 理念五：质量提升必须受到成本约束

EvoAgent 追求质量、稳定性和效率的综合改善，不允许通过无限增加模型调用、重试次数和实验预算来换取表面上的成功率提升。

### 理念六：安全边界高于自主程度

智能体可以高度自动化地完成任务，但不能绕过系统权限、用户授权、硬预算和高风险操作约束。

### 理念七：能力资产与模型版本解耦

模型可以替换，领域能力、任务定义、工作流、工具契约、评测集和记忆资产应尽可能独立管理。

模型切换后，系统应继承兼容资产，并重新验证受影响的行为。

# 第二章 产品目标与成功标准

## 2.1 产品目标

### G1：建立通用任务执行能力

支持自然语言输入、意图识别、任务分类、规划、工具调用、结果验证、失败恢复和任务总结。

### G2：建立多领域专家体系

支持通用任务、编程、旅游、AI 漫剧制作、手机操作等领域能力，并允许未来扩展新领域。

### G3：建立可观测的运行系统

能够追溯任务使用的模型、提示词、工具、工作流、记忆策略、环境版本、执行轨迹和结果。

### G4：建立证据驱动的进化闭环

实现问题发现、根因诊断、候选生成、独立评测、成本评估、发布门禁和回滚。

### G5：建立稳定的模型迁移机制

支持多个模型适配档案、独立实验分支、跨模型能力验证和稳定版本保留。

### G6：建立离线可用能力

在服务端离线或网络中断时，允许手机端继续完成可离线任务、恢复部分任务并保存待同步问题。

### G7：形成可复用工作流资产

将经过验证的复杂任务流程沉淀为有版本、有输入输出契约、有恢复能力、有验收标准的工作流。

### G8：支持 Android 个人智能体交互

提供专属 App 和语音双入口，并通过受控的原生接口、无障碍服务和视觉识别能力完成手机操作。

## 2.2 产品成功指标

以下为首期建议验收目标，具体阈值应在建立基线、评测集和测试环境后，经产品、研发、测试共同确认。

| 指标 | 定义 | 首期验收方向 |
|---|---|---|
| 任务成功率 | 满足任务验收标准的任务占比 | 建立固定基准集，按任务类别统计 |
| 结果验证覆盖率 | 已执行独立结果验证的任务占比 | 对支持验收的任务实现完整验证 |
| 工具调用正确率 | 参数合法且调用结果符合契约的比例 | 建立契约测试与异常测试 |
| 失败可诊断率 | 具有足够证据并能归入有效诊断类别的失败比例 | 覆盖常见环境、工具和执行异常 |
| 失败恢复成功率 | 在允许恢复的故障中，恢复后任务最终通过验收的比例 | 通过故障注入测试建立基线 |
| 关键约束保留率 | 上下文处理后仍完整保留的关键约束比例 | 硬约束不得因普通压缩而丢失 |
| 记忆有效性 | 记忆检索结果在当前任务中的正确性与适用性 | 分别评测写入、召回、过期和冲突处理 |
| 进化收益 | 候选版本相对基线的真实质量或效率改善 | 必须同时检查成本和回归 |
| 进化回归率 | 新版本导致既有能力退化的比例 | 建立跨领域回归测试 |
| 单任务成本 | 成功完成任务的模型、工具及其他可计量成本 | 按任务类型、模型和版本统计 |
| 发布后回滚率 | 发布后因质量、稳定性或安全问题回滚的比例 | 持续监控 |
| 离线数据保全率 | 离线期间应保留的关键事件和检查点成功持久化的比例 | 通过断网、重启和容量测试验证 |
| 版本可追溯率 | 能够还原执行版本组合的任务占比 | 所有正式任务均记录必要版本引用 |

不得通过降低任务难度、减少失败样本或忽略高风险任务来人为提高指标。

成功率必须结合任务难度、任务类型、评测范围和样本量解释，不得只用一个全局数字代表全部能力。

# 第三章 用户与使用场景

## 3.1 目标用户

### 普通个人用户

希望通过自然语言或语音完成信息查询、应用操作、日常事务和跨步骤任务。

### 复杂任务用户

希望完成编程、资料整理、内容制作、流程自动化等需要多步执行和结果验收的任务。

### 高级使用者

希望管理领域专家、模型适配、工作流、任务历史、运行日志、预算和自动化策略。

### 系统维护者

负责查看诊断结果、审核高风险改动、管理发布策略、排查系统问题和维护基础设施。

## 3.2 核心用户场景

### 场景 A：自然语言完成手机操作

用户说：“打开某个 App，找到指定功能，完成某项操作。”

系统识别意图、定位目标应用、选择操作方式、执行动作并验证结果。

若遇到权限弹窗、界面变化或执行失败，系统先重新观察和诊断，不盲目重复操作。

### 场景 B：复杂任务自动执行

用户提出一个需要多个步骤的目标。

系统判断是否适合使用现有工作流；如果没有合适流程，则进行任务分解、工具选择、执行和验收。

任务结束后，记录关键执行证据。

### 场景 C：重复任务固化为工作流

某个任务经过多次成功执行后，系统识别可复用步骤，形成候选工作流，补充输入输出契约、异常处理和验收规则。

通过回归测试后，才能发布为稳定工作流。

### 场景 D：运行问题驱动能力改进

某类任务反复失败。

系统分析问题是否来自模型、工具、上下文、记忆、规划或环境，再生成对应候选并进行评测。

### 场景 E：切换大语言模型

管理员或进化系统引入新模型。

系统创建独立适配档案，复用兼容资产，运行必要的兼容性和领域回归测试，满足门槛后生成新发布组合。

### 场景 F：服务端离线

手机端继续运行本地已有能力，保存故障记录和检查点；网络恢复后同步允许共享的事件。

### 场景 G：复杂 AI 漫剧制作

用户提出 30～60 秒动态视频漫剧需求。

系统建立制作任务 DAG，管理剧本、角色、分镜、视频生成、配音、合成、质量验收和预算，并将跑通的流程沉淀为可复用能力包。

# 第四章 产品总体架构

## 4.1 总体架构

EvoAgent 采用双端协同、双轨运行、分层能力的产品架构。

### 手机端：稳定执行轨道

主要负责：

- 专属 App 与语音交互。
- 本地意图识别和任务分类的基础能力。
- 任务状态与检查点管理。
- ReAct 执行运行时。
- 已安装的领域专家和工作流。

- 本地权限、预算和安全控制。
- 日志与异常事件采集。
- 离线任务执行与待同步事件队列。
- 已批准更新的验证、安装、启用和回滚。

### 服务端：进化与验证轨道

主要负责：

- 运行事件接收和分析。
- 根因诊断与影响范围评估。
- 能力依赖图管理。
- 候选改进生成。
- 模型适配与模型比较。
- 评测任务调度。
- 隔离实验环境。
- Git 分支与版本管理。
- 成本收益分析。
- 发布门禁和签名发布包。
- 发布后质量监测。
- 跨任务、跨版本的进化证据管理。

服务端是主要进化中心，但不能成为手机端正常运行的强制依赖。

## 4.2 稳定运行轨道与进化轨道的关系

两条轨道共享版本清单、运行事件和评测证据，但拥有不同的执行权限。

稳定运行轨道负责当前任务的正确、安全执行。

进化轨道负责改变未来任务的实现方式。

进化轨道不能直接修改正在运行的稳定配置。候选版本必须在独立环境中完成验证后，才能申请发布。

# 第五章 统一任务入口与意图识别

## 5.1 功能目标

用户无需提前选择具体专家或工具，只需表达目标，系统就能够判断任务意图、复杂度、风险、领域和执行需求。

## 5.2 输入方式

- 文本输入。
- 语音输入。
- App 内快捷操作。
- 已授权的系统事件或自动化触发。
- 已有任务的继续、恢复和重试请求。

## 5.3 意图识别结果

每个任务至少形成以下结构化信息：

- 用户目标。
- 任务类别。
- 领域标签。
- 预估复杂度。
- 是否需要调用工具。
- 是否需要规划或工作流。
- 是否依赖在线服务。
- 可能的副作用。
- 所需权限。
- 验收条件。
- 预算和时延约束。
- 识别置信度及不确定性。

## 5.4 路由策略

路由器综合任务意图、专家能力、工具可用性、模型适配情况、成本预算、当前环境和安全要求选择执行路径。

优先级建议：

1. 安全与权限约束。
2. 任务类型与能力匹配。
3. 工具和环境可用性。
4. 质量要求。
5. 成本与时延。
6. 用户偏好和历史表现。

当路由置信度不足、任务含义不明确或不同解释会导致不同副作用时，系统应当先询问用户，而不是盲目执行。

## 5.5 验收标准

- 常见意图能够正确路由到对应能力。
- 不支持的任务能明确说明限制。
- 低置信度任务能够进入澄清流程。
- 高风险操作不会因意图识别结果而绕过授权。
- 路由决策可以追溯，且不把单次误判直接固化为永久规则。

# 第六章 领域专家与能力隔离

## 6.1 设计目标

不同领域具有独立的提示词、记忆命名空间、工具集合、工作流、评测集和模型适配配置。

领域专家可以共享经过批准的通用内核，但不能直接修改其他专家的私有策略。

## 6.2 首批领域能力

### 通用任务专家

负责一般问答、信息整理、简单任务规划、跨领域任务分发和无法明确归属的任务。

### 编程专家

负责代码理解、项目分析、代码生成、调试、测试、错误修复和开发工作流。

### 旅游专家

负责旅行信息整理、行程规划、地点推荐、交通与预算规划等任务。

### AI 漫剧专家

负责剧本、角色、分镜、生成素材、视频、配音、合成、质量验收和制作流程管理。

### 手机操作专家

负责 App 启动、页面识别、控件定位、操作执行、状态验证和异常恢复。

以上是领域规划，并不意味着所有领域都必须在 V0.1 完整实现。

## 6.3 能力依赖图

系统应当维护能力与组件之间的依赖关系。

例如：

编程专家依赖通用 ReAct 引擎、代码工具、编程记忆策略、编程评测集和代码修复工作流。

当代码工具适配器变化时，系统只需首先评估直接依赖它的能力，再根据依赖关系决定是否扩大回归范围。

共享内核的改动则必须评估所有受影响专家。

## 6.4 能力独立发布

每个领域专家应具有：

- 独立版本。
- 独立配置。
- 独立记忆命名空间。
- 独立评测集。
- 独立质量指标。
- 独立发布记录。
- 明确的共享依赖清单。

# 第七章 Planning、ReAct 与工作流编排

## 7.1 职责划分

### Planning 引擎

负责理解目标、分解子任务、建立依赖关系、估算资源、制定验收条件，以及在必要时调整计划。

### ReAct 执行引擎

负责在当前步骤中观察状态、选择行动、调用工具、读取结果、判断下一步并在局部范围内修正执行策略。

### 工作流引擎

负责执行已固化的 DAG，管理节点状态、条件分支、并行任务、检查点、重试和恢复。

### 运行时控制器

负责执行权限、硬预算、任务状态一致性、循环上限、终止条件、副作用保护和最终执行控制。

模型可以提出行动建议，但不能绕过运行时控制器。

## 7.2 任务执行流程

1. 接收用户目标。
2. 识别意图和任务风险。
3. 路由到合适的专家。
4. 检查是否存在匹配的已验证工作流。
5. 选择直接执行、ReAct 或 Planning + DAG 路径。
6. 建立任务状态和验收标准。
7. 在预算和权限约束内执行。
8. 对关键步骤进行状态检查。
9. 处理异常并在必要时恢复。
10. 通过独立验收判断结果。
11. 保存结果、事件、检查点和必要记忆。
12. 向用户反馈真实完成状态。

## 7.3 任务状态机

建议至少包含：

- CREATED：已创建。
- CLASSIFYING：意图识别中。
- PLANNING：规划中。
- READY：准备执行。
- RUNNING：执行中。
- WAITING_USER：等待用户输入或授权。
- WAITING_DEPENDENCY：等待外部依赖。
- RECOVERING：异常恢复中。
- VERIFYING：结果验收中。
- SUCCEEDED：验收成功。
- FAILED：任务失败。
- CANCELLED：用户或系统取消。
- SUSPENDED：安全暂停。

状态转换必须由运行时控制器管理，并保存关键状态变更记录。

## 7.4 循环与终止控制

系统应限制：

- 最大模型调用次数。
- 最大工具调用次数。
- 最大执行时长。
- 最大重试次数。
- 最大任务费用。
- 最大并发任务数。
- 允许的副作用操作范围。

当任务无法继续、预算耗尽或出现高风险状态时，系统应安全停止或请求用户介入。

## 7.5 工作流固化

将成功执行的任务转化为候选工作流时，必须提取：

- 输入参数。
- 任务前置条件。
- 节点定义。
- 节点依赖关系。
- 工具契约。
- 条件分支。
- 重试和恢复策略。
- 产物定义。
- 验收条件。
- 资源预算。
- 适用环境。
- 版本依赖。

工作流通过固定案例、异常案例、恢复案例和成本评测后，才能进入稳定工作流库。

# 第八章 工具系统与故障处理

## 8.1 工具管理

每个工具必须注册：

- 工具 ID 与版本。
- 输入输出 Schema。
- 权限要求。
- 副作用等级。
- 超时与重试策略。
- 幂等性支持。
- 错误分类。
- 健康检查方式。
- 适用模型或环境限制。
- 测试与兼容性记录。

## 8.2 工具调用过程

调用前验证参数和权限；调用时记录状态；调用后验证返回格式与业务结果。

工具返回成功，不等于业务目标一定完成。

例如，点击操作成功发送，不代表页面已经进入目标状态。
