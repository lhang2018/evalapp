## 一、为什么要进行产品重构

EvoAgent 已经积累了路由、专家系统、ReAct、Plan、工作流、记忆、工具治理、评测、日志和自进化等设计。

但技术模块丰富不等于产品已经成立。

一个真正可用的个人智能体，必须能够回答六个问题：

1. 用户为什么需要它，而不是直接使用普通聊天助手？
2. 用户能够交给它哪些真实任务？
3. 用户从哪里发起任务，如何知道任务正在进行？
4. 系统如何证明任务真正完成，而不是仅仅生成一段看似合理的回答？
5. 当任务失败时，用户如何恢复、纠正或接管？
6. 使用时间越长，系统究竟在哪些方面变得更好？

因此，产品重构不再以增加技术专项为主要进度指标，而是以**可交付的用户价值、端到端任务完成能力和可验证的改进效果**为核心。

## 二、产品定义与价值主张

### 2.1 一句话定义

EvoAgent 是一款以手机为主要入口的个人智能体。用户通过文字或语音表达目标，EvoAgent 理解任务、规划步骤、调用获得授权的能力、验证执行结果并交付成果，同时根据实际运行证据持续改善自身。

### 2.2 用户购买的不是技术模块，而是六种价值

| 用户价值 | 用户能够感受到的结果 |
|---|---|
| 少操心 | 不需要把复杂任务拆成大量指令逐条告诉智能体 |
| 真正完成 | 不只提供建议，还能在权限允许的范围内执行并交付 |
| 结果可靠 | 能检查文件、数据、执行状态或其他可验证结果 |
| 连续工作 | 能延续相关任务的上下文，避免重复解释 |
| 主动帮助 | 在有明确价值时发现遗漏、风险或更好的解决办法 |
| 持续变好 | 常见任务越来越稳定，失败更少，恢复更快，资源使用更合理 |

### 2.3 产品成功的定义

EvoAgent 的成功不以智能体数量、提示词数量、代码行数或专项设计数量衡量。

核心判断是：

- 用户需要的任务是否完成；
- 完成质量是否符合要求；
- 结果是否有证据支持；
- 用户为完成任务付出的时间和操作是否减少；
- 系统是否能识别并恢复失败；
- 长期使用后，真实任务的质量、效率和稳定性是否持续改善。

“无限进化”意味着持续、可验证且受预算和权限约束的改进，而不是无限制修改自己或无限制调用资源。

## 三、目标用户与产品边界

### 3.1 首要用户

首要目标是个人用户，而不是企业团队或多租户组织。

产品需要适应个人日常使用中的多种任务：提问、资料研究、文件创作、复杂任务执行、手机操作、个人事务安排和领域专业工作。

### 3.2 终端战略

- **首发终端：** Android 手机。
- **主要交互：** 专属 App、文字输入和语音输入。
- **运行策略：** 云端优先，保留基本离线能力。
- **扩展终端：** Windows 桌面、平板及个人自有服务器。
- **设计要求：** 任务记录、权限策略、能力契约和进化版本应尽可能跨终端复用，不要求所有设备首发时都实现相同能力。

### 3.3 首发边界

首发不承诺所有专家、所有应用操作和所有复杂创作能力均已成熟。

产品必须区分：

1. 已经可执行并通过验收的能力；
2. 可以调用外部服务、但依赖条件的能力；
3. 只能提供建议或生成计划的能力；
4. 尚未实现的能力。

界面不能把“已识别用户意图”显示成“已经具备执行能力”，也不能把模拟执行结果当成真实执行成果。

## 四、用户可见的三种工作模式

EvoAgent 不应把用户暴露在复杂的技术模块中。用户主要通过三种模式使用产品。

### 4.1 聊天模式：快速理解与回答

适用于提问、解释、讨论、方案比较和轻量级建议。

用户体验要求：

- 尽可能直接回答；
- 结合获得授权的相关上下文；
- 复杂问题可以提出更好的解决方案；
- 不为了展示自主性而强行启动任务流程；
- 用户明确要求执行时，可以转入工作模式。

### 4.2 工作模式：围绕目标完成任务

适用于研究报告、文件制作、复杂分析、编程和多步骤操作。

用户体验要求：

- 用户只需描述目标和重要约束；
- 系统负责合理分解任务；
- 只有关键歧义才打断用户澄清；
- 展示当前状态、必要的执行摘要和需要用户决策的事项；
- 支持暂停、取消、恢复和查看中间产物；
- 交付前进行与任务类型相适应的验收。

工作模式的核心是“把事情办完”，而不是让用户一直盯着智能体的每一步。

### 4.3 主动帮助模式：发现有价值的下一步

适用于整理近期任务、发现遗漏、提供相关资料、提醒风险、跟进待办和提出更好的处理方式。

主动帮助必须满足：

- 有明确的用户价值；
- 信息来源在用户授权范围内；
- 不干扰正在进行的主任务；
- 不把推测包装成事实；
- 不因追求主动性而频繁打扰用户；
- 默认提出建议，而不是自动执行高风险动作。

主动帮助是增强功能，不是取代任务执行的第二套主系统。

## 五、用户任务蓝图

产品应以任务类型组织能力，而不是先要求用户选择某个专家。

### 5.1 首批核心任务

| 任务类型 | 用户输入示例 | 预期交付 |
|---|---|---|
| 问答与解释 | “帮我弄明白这个概念” | 准确、易理解的回答，必要时附依据 |
| 资料研究 | “研究一下这个问题，给我一份有依据的报告” | 资料、结论、来源、分歧和待确认事项 |
| 文件创作 | “把这些材料整理成一份正式文档” | 可打开、可编辑、结构完整的文件 |
| 多步骤工作 | “完成这件事，过程中遇到问题自己处理” | 任务计划、进度、异常恢复和最终成果 |
| 手机辅助 | “打开指定应用，找到这个功能并完成操作” | 经授权的实际操作、执行证据和结果说明 |
| 任务跟进 | “继续上次没完成的事情” | 恢复相关上下文，明确未完成项并继续执行 |
| 主动建议 | “结合最近的工作，看看还有什么值得处理” | 有依据、可选择、优先级清楚的建议 |

这些是产品目标与验收场景，不代表每项能力已经在当前工程中全部实现。

### 5.2 任务完成的标准流程

**理解目标 → 确认关键约束 → 规划 → 执行 → 验收 → 交付 → 记录改进证据**

具体要求如下：

**第一步：理解目标**

识别用户想要的最终结果、必要输入、截止时间、成本限制和风险边界。

**第二步：判断是否需要澄清**

只有当缺失信息会显著影响结果、安全性或成本时，才优先询问。低风险且合理的默认值可以直接采用，并在必要时说明。

**第三步：规划执行**

优先采用已验证的工作流。重复性强的任务使用稳定流程；局部存在不确定性的任务采用混合规划；没有适用流程时才进行受限动态规划。

**第四步：执行与恢复**

跟踪实际执行状态。遇到错误时，判断是否可以安全重试、替换步骤、调整计划或降级完成。无法确认外部操作是否成功时，先核对状态，不盲目重复执行。

**第五步：独立验收**

根据任务选择证据，例如文件是否生成、测试是否通过、数据是否满足约束、外部操作是否成功，或者是否需要用户确认。

**第六步：交付**

明确说明：

- 完成了什么；
- 产物在哪里；
- 哪些验收项已经通过；
- 哪些部分尚未完成；
- 是否存在风险、假设或需要用户决定的事项。

**第七步：改进**

记录必要的运行证据，供后续诊断和评测使用。不能把一次成功直接认定为永久改进，也不能把失败直接认定为路由错误。

## 六、产品信息架构

建议采用以下用户可见的信息结构。

### 6.1 首页

提供统一的任务入口，支持文字、语音、继续最近任务和查看待处理事项。

首页应突出用户可以做什么，而不是展示大量智能体内部状态。

### 6.2 对话与任务工作区

同一个入口既支持普通对话，也支持长任务。

任务进入工作模式后，应提供：

- 目标和约束；
- 当前进度与状态；
- 简明执行计划；
- 需要审批的动作；
- 已生成的中间产物；
- 验收结果；
- 暂停、取消和恢复操作。

### 6.3 任务历史与成果库

用户能够按任务查看历史、重新打开产物、继续未完成任务和追溯结果。

任务历史应区分成功、部分完成、失败、取消和等待用户操作，不能只显示一串聊天记录。

### 6.4 主动建议中心

集中展示经过筛选的机会，例如待跟进事项、相关资料、风险提示和效率改进建议。

每条建议应说明：

- 为什么现在提出；
- 依据是什么；
- 能带来什么价值；
- 需要用户做什么；
- 是否可以忽略或关闭。

### 6.5 能力与信任设置

用户能够查看能力状态、模型与资源使用策略、授权范围、记忆设置、数据保留选项和主动帮助频率。

用户应当能够限制某些能力，而不必关闭整个智能体。

## 七、主动帮助与主任务的隔离机制

这是产品的重要差异化能力，但必须服从主任务优先原则。

### 7.1 四类主动帮助

1. **当前任务增益：** 在完成当前任务时，发现遗漏的约束、缺失资料或更优方案。
2. **近期对话整理：** 在授权范围内整理近期讨论的结论、未解决问题和下一步。
3. **个人事务跟进：** 对用户明确建立的待办、计划和长期目标提供提醒或跟进。
4. **机会型帮助：** 发现与当前目标相关、能够节省时间或降低风险的额外机会。

### 7.2 建议筛选规则

每个机会都应评估：

- 与用户当前目标的相关性；
- 潜在收益；
- 判断依据的可信程度；
- 是否具有时效性；
- 是否重复；
- 执行成本；
- 对主任务的干扰程度。

只有综合价值足够高时才向用户展示。紧急风险可以采用更及时的提示方式，但普通建议不应频繁打断用户。

### 7.3 严格隔离

主动帮助使用独立的任务队列和资源预算。

- 主任务运行期间，主动帮助不能抢占关键执行资源。
- 主任务的运行版本和执行状态不能被主动帮助修改。
- 主动帮助不能扩大原有授权。
- 需要外部操作时，按照该操作本身的权限规则处理。
- 如果资源紧张、网络异常或主任务不稳定，主动帮助优先暂停。
- 后台分析失败，不得导致主任务失败。

对近期对话、通知、文件和其他应用信息的分析，仅能使用用户明确授权或产品合法提供的相关数据源。不能默认将手机上的全部信息视为可读取。

## 八、无限优化如何真正改善用户体验

自进化不是独立于产品价值的功能。它必须围绕真实任务建立闭环。

### 8.1 运行中的安全调整

在任务允许的范围内，可以执行有边界的恢复动作，例如重新规划、切换兼容工具或对可安全重试的操作进行重试。

调整必须服从任务预算、权限和停止条件，不能无限循环。

### 8.2 后台改进候选

任务结束后，系统可以从运行证据中发现问题，例如：

- 路由错误；
- 工具参数错误；
- 计划不完整；
- 上下文丢失；
- 验收标准不充分；
- 重试策略不合理；
- 延迟或成本异常。

诊断系统提出根因假设，候选改进进入独立评测。执行系统不能因为自己认为某种解释正确，就直接修改生产策略。

### 8.3 稳定能力升级

候选改进只有在独立质量评测、安全检查、兼容性检查和资源门禁通过后，才可以进入审批、灰度、发布或回滚流程。

每次任务应固定其运行配置。任务执行期间不应因后台发布而突然切换关键组件版本。

### 8.4 用户真正能感受到的进化

长期优化至少应带来以下变化：

- 同类任务一次完成率提高；
- 错误路由减少；
- 失败后恢复成功率提高；
- 不必要的澄清和重复操作减少；
- 单次成功任务的平均时间与成本下降；
- 交付结果更符合用户要求；
- 主动建议更加相关、准确，且更少打扰；
- 用户不需要反复纠正已经明确的偏好。

如果技术指标提高，却没有带来任务质量或效率的真实改善，就不能把它认定为有效进化。

## 九、能力开放与产品优先级

### 第一层：基础可用

首先保证统一入口、自然语言理解、任务状态、权限检查、受控执行、结果验收、产物交付、取消恢复和失败说明。

这是其他能力成立的基础。

### 第二层：个人效率

加入相关记忆、任务延续、资料研究、文档创作、稳定工作流和经过筛选的主动建议。

重点是减少重复劳动，让用户可以放心把多步骤工作交给智能体。

### 第三层：领域专家

逐步接入编程、旅游、AI 漫剧、手机操作等领域能力。

每个领域独立维护能力范围、工作流、工具、记忆策略、验收方式和评测集。某个领域失败，不应破坏通用内核或其他专家。

### 第四层：受限自主运行

在明确授权、可停止、有预算、有日志、有恢复策略的前提下，支持定时任务、待办跟进和长期目标。

更高自主性必须建立在已验证的任务能力之上，而不是反过来要求用户承担未经验证的风险。

## 十、产品验收与成功指标

指标必须从用户结果出发，并按领域和任务难度分层统计。

| 指标类别 | 核心指标 | 评价目的 |
|---|---|---|
| 任务质量 | 验收通过率、用户返工率 | 是否真正满足要求 |
| 完成能力 | 端到端完成率、首次完成率 | 是否能独立完成工作 |
| 可靠性 | 失败恢复率、重复副作用事件 | 是否稳定、可恢复 |
| 路由质量 | 领域准确率、能力覆盖率、错误路由代价 | 是否把任务交给正确能力 |
| 效率 | 完成时间、人工介入次数 | 是否真正减少用户负担 |
| 成本 | 单次成功任务成本、重试成本 | 是否高效使用资源 |
| 主动帮助 | 建议采纳率、有效收益、误打扰率 | 是否值得主动提供帮助 |
| 信任与安全 | 未授权动作、严重安全事件、状态不可追溯事件 | 是否可控、可审计 |
| 持续进化 | 候选收益、回归率、发布后表现 | 优化是否产生长期收益 |

具体阈值应在建立基线、明确任务分布和收集可靠评测数据后确定。不能为了达到某个指标而降低任务难度、缩小评测集或把未完成任务算作成功。

**硬性验收原则：** 未授权的高风险操作必须被阻止；未验证的结果不得宣称已经验证；后台优化不得破坏稳定执行。

## 十一、明确的非目标

产品重构期间不以以下事项作为优先目标：

- 不以增加专家数量作为首要进度；
- 不以增加技术专项数量代替用户功能交付；
- 不在没有可靠执行与验收能力时追求完全自主；
- 不允许智能体自行修改生产权限、安全规则或发布门禁；
- 不默认扫描用户所有应用、对话和文件；
- 不把主动建议变成频繁通知；
- 不要求每种领域能力都在首发时完成；
- 不以模型自评或模拟结果代替真实验收。

## 十二、接下来的产品推进顺序

下一阶段按照以下顺序推进：

**第一步：冻结核心用户场景。**  
把首批任务具体化，明确输入、执行行为、产物、验收证据、异常恢复和用户介入条件。

**第二步：建立用户任务验收矩阵。**  
每个场景都必须有可重复的测试案例和清晰的完成标准。

**第三步：建立能力覆盖矩阵。**  
将产品场景对应到现有专家、工具、工作流和执行能力，标明已实现、部分实现、依赖外部服务和未实现。

**第四步：形成用户可见的交互流程。**  
明确首页、聊天模式、工作模式、主动建议、任务历史、审批和成果展示之间的关系。

**第五步：以真实代码为依据安排实施。**  
优先补齐能够影响端到端任务质量的缺口，不为增加模块而增加模块。

**第六步：建立用户价值与进化收益的共同验收体系。**  
每一项重要改进都要说明解决了哪个用户问题、通过什么证据证明有效，以及如何避免回归。

---

**最终产品原则：EvoAgent 的技术能力越强，用户就越不需要操心技术细节；它的自主性越高，执行边界、结果证据和可恢复性就越必须清晰。**</WritingBlock>

接下来把总纲落到可以真正判定“做出来没有”的标准上。产品不能只说“支持资料研究”或“支持手机操作”，而必须说明具体场景中什么算成功、失败后怎么办，以及用什么证据验收。

## 第二份基线：首批核心用户任务场景与验收矩阵

<WritingBlock id="59317" variant="document"># EvoAgent 首批核心用户任务场景与验收矩阵

**版本：** 产品重构基线 1.0  
**目的：** 将产品目标转换成用户场景、可见交付物和可重复验收条件。

## 一、首批任务范围

优先建设以下任务，不以新增技术模块为交付目标。

| 编号 | 用户任务 | 优先级 | 主要验收对象 |
|---|---|---|---|
| T01 | 普通提问与连续对话 | P0 | 回答质量、上下文一致性 |
| T02 | 资料研究与报告整理 | P0 | 来源、结论、完整性 |
| T03 | 创建和整理文件 | P0 | 文件可用性、内容质量 |
| T04 | 多步骤任务执行 | P0 | 端到端完成、恢复能力 |
| T05 | 暂停、恢复与继续任务 | P0 | 状态一致性、进度保留 |
| T06 | Android 基础受控操作 | P0（限定范围） | 授权、实际状态、操作结果 |
| T07 | 近期对话整理与主动建议 | P1 | 相关性、可信度、低打扰 |
| T08 | 从失败中改进执行能力 | P0（后台质量保障） | 改进证据、回归控制 |
| T09 | 离线使用与恢复同步 | P1 | 数据完整性、状态对账 |
| T10 | 编程、旅游、AI 漫剧等领域任务 | 分领域开放 | 领域专用验收标准 |

P0 代表首批产品成立所必需的能力；P1 代表在基础任务可靠后开放的能力。Android 基础操作属于首发方向，但具体操作范围必须以已实现的适配能力和授权范围为准。

## 二、各任务的验收定义

### T01：普通提问与连续对话

**用户场景：** 用户询问一个问题，随后补充条件、纠正回答或引用前文继续讨论。

**通过条件：**
- 回答覆盖用户实际问题，而非只匹配关键词。
- 对事实、推断和不确定内容作出适当区分。
- 后续回答能正确继承相关上下文。
- 用户纠正信息后，后续处理使用纠正后的内容。
- 需要关键输入时能够澄清，不编造缺失信息。

**失败处理：** 明确说明不确定之处，允许用户纠正，并避免将错误结论写入长期记忆。

**验收证据：** 标准问答集、上下文连续性案例、纠错案例和事实核验结果。

### T02：资料研究与报告整理

**用户场景：** 用户提出一个研究问题，要求收集资料、分析并生成报告。

**通过条件：**
- 报告回答原始问题并满足指定范围。
- 重要事实能够追溯到来源。
- 对存在争议或相互矛盾的信息进行说明。
- 区分来源事实、分析判断和待验证假设。
- 交付内容符合约定的结构和格式。

**失败处理：** 来源不足时缩小结论范围，说明缺口，不以推测补齐证据。

**验收证据：** 来源覆盖检查、关键事实抽查、结构检查和独立质量评审。

### T03：创建和整理文件

**用户场景：** 用户要求把材料整理成一份正式文档，或生成其他指定格式的文件。

**通过条件：**
- 文件实际存在且能够正常打开。
- 文件类型、名称和内容结构符合要求。
- 核心内容完整，没有明显遗漏或重复。
- 文件中的数字、引用和关键结论经过适当检查。
- 用户能够明确找到最终交付物。

**失败处理：** 生成失败时保留可恢复的中间结果，说明失败原因，不将不存在的文件声明为已交付。

**验收证据：** 文件存在性、格式解析、结构检查、内容检查及交付路径。

### T04：多步骤任务执行

**用户场景：** 用户提出一个需要多个步骤的目标，例如研究资料、分析结果并生成报告。

**通过条件：**
- 系统理解最终目标和重要约束。
- 计划包含实现目标所需的关键步骤。
- 各步骤状态可追踪，依赖关系正确。
- 局部失败不会无条件导致整个任务失控。
- 重试不会重复产生不可逆的外部副作用。
- 最终产物通过预先定义的验收标准。

**失败处理：** 在预算和权限允许范围内恢复；无法恢复时交付已完成部分，并明确剩余工作。

**验收证据：** 任务记录、步骤结果、恢复记录、预算使用情况和最终验收报告。

### T05：暂停、恢复与继续任务

**用户场景：** 用户在任务执行过程中退出 App，网络中断，或主动要求稍后继续。

**通过条件：**
- 系统能识别哪些步骤已完成、哪些尚未完成。
- 恢复时能重建任务所需的关键上下文。
- 恢复前核对不确定的外部操作状态。
- 不把旧计划误认为当前有效计划。
- 用户能够查看恢复进度，并在必要时取消任务。

**失败处理：** 状态无法确认时暂停相关操作并请求核对，而不是盲目重新执行。

**验收证据：** 进程中断恢复、断网恢复、任务重复提交和副作用对账测试。

### T06：Android 基础受控操作

**用户场景：** 用户要求打开指定应用、定位某个功能或执行已支持的手机操作。

**通过条件：**
- 所需系统权限已经获得。
- 操作目标在当前支持范围内。
- 高风险或不可逆动作遵循单独的授权规则。
- 执行后检查实际界面或状态，而不是只依据模型的完成声明。
- 遇到界面变化、权限撤销或目标不明确时停止危险操作。

**失败处理：** 允许安全恢复的步骤可以有限重试；状态不明或目标不符时停止并向用户说明。

**验收证据：** 授权记录、操作前后状态、执行结果、异常日志和副作用对账。

### T07：近期对话整理与主动建议

**用户场景：** 用户希望智能体整理近期讨论，分析当前正在推进的事情，并提出有用的下一步。

**通过条件：**
- 仅使用授权范围内的对话和其他信息源。
- 区分已确认事实、推断和未知信息。
- 正确归纳已完成事项、未解决问题和重要约束。
- 建议与当前目标相关，并说明提出理由。
- 能够跳过低价值、重复或缺乏证据的建议。
- 不因生成建议而干扰正在执行的主任务。
- 未经授权不直接执行建议中的高风险动作。

**交付形式：** 一份简洁的进展摘要、待解决问题和按价值排序的下一步建议。

**失败处理：** 信息不足时明确说明依据不足，不虚构用户的当前状况。

**验收证据：** 经审核的摘要与事实对照、建议相关性评估、误打扰率和用户采纳反馈。

### T08：从失败中改进执行能力

**用户场景：** 相似任务反复出现工具错误、执行失败、质量不足或不必要的重试。

**通过条件：**
- 能将问题关联到具体任务和运行版本。
- 能区分路由、模型、工具、计划、权限、环境和验收问题。
- 根因只是待验证假设时，不将其直接认定为事实。
- 改进候选必须通过独立评测和回归门禁。
- 未通过的候选不能改变稳定版本。
- 发布后的回退条件明确，且能够恢复已知稳定版本。

**失败处理：** 无法确定根因时保留诊断记录，不为了表现出“持续进化”而随意修改系统。

**验收证据：** 基线与候选对比、回归集结果、成本和时延变化、审批记录及发布后表现。

### T09：离线使用与恢复同步

**用户场景：** 手机断网后继续进行可离线任务，恢复网络后同步记录。

**通过条件：**
- 已有任务和本地记录不会因断网而无故丢失。
- 不依赖网络的能力可以在明确范围内继续工作。
- 联网后能够识别已同步和待同步记录。
- 重复同步不会重复创建任务或外部副作用。
- 冲突或同步失败有可见状态和恢复方式。

**验收证据：** 断网、重连、重复上传、进程重启和同步冲突测试。

### T10：领域专家任务

**用户场景：** 用户提出编程、旅游、AI 漫剧等领域任务。

**通过条件：**
- 系统识别目标所需的领域能力。
- 只调用当前已注册、兼容且获准使用的能力。
- 使用对应领域的验收方法。
- 不支持的能力明确告知用户，不伪装成已经执行。
- 某个专家的失败不会污染其他专家或共享内核。

**验收证据：** 领域专用测试集、约束满足情况、执行产物和独立评测报告。

## 三、统一任务状态的用户体验规范

系统内部可以有细粒度状态机，但用户界面只需要呈现清楚、可行动的状态：

| 用户可见状态 | 用户应当理解的含义 |
|---|---|
| 理解中 | 系统正在确定目标与约束 |
| 需要补充 | 缺少关键输入，等待用户回答 |
| 执行中 | 任务正在进行 |
| 等待授权 | 有一个需要用户决定的操作 |
| 暂停中 | 任务已停止推进，可查看原因 |
| 恢复中 | 系统正在恢复任务状态或核对外部结果 |
| 验收中 | 正在检查成果是否满足要求 |
| 已完成 | 已达到约定的完成标准 |
| 部分完成 | 部分成果可用，但仍有未完成项 |
| 未完成 | 任务未达到完成标准，需要查看原因或决定下一步 |

状态必须反映真实情况，不能只根据模型输出的自然语言判断任务是否成功。

## 四、首批端到端验收流程

每个 P0 场景至少覆盖以下测试：

1. **正常路径：** 输入有效，任务顺利完成。
2. **信息缺失：** 系统能合理澄清，不擅自假设关键条件。
3. **工具失败：** 错误可识别，恢复策略有效。
4. **权限拒绝：** 未获授权的动作不会执行。
5. **超时与预算耗尽：** 系统停止新增调用并说明状态。
6. **取消与恢复：** 任务状态正确，不产生重复副作用。
7. **验收失败：** 不把未达标的产物声明为成功。
8. **回归检查：** 新版本不能破坏原有已通过案例。

每项测试都必须保存实际结果。没有执行的测试标记为“未测试”，不能用设计说明替代测试证据。

## 五、如何决定一项能力是否可以对用户开放

能力开放前必须回答：

- 用户能通过什么入口使用它？
- 支持的输入和输出是什么？
- 依赖哪些工具、权限或外部服务？
- 哪些情况属于不支持范围？
- 怎样判断执行成功？
- 失败后如何停止、恢复或交接给用户？
- 会消耗多少时间和资源？
- 是否有可重复的评测案例？
- 升级后如何回滚？

这些问题没有明确答案时，可以保留为内部实验能力，但不应宣传为成熟的自主执行能力。

## 六、后续工作

在上述矩阵基础上，下一项工作是建立 **EvoAgent 产品能力覆盖与缺口台账**。

它将逐一对应现有工程，标记每个场景所需的入口、专家、工作流、工具、验收器和用户界面能力，并区分“已有实现”“部分实现”“仅有设计”“尚未实现”。

后续实施顺序应由影响用户任务完成质量的缺口决定，而不是由技术模块数量决定。
</WritingBlock>

## 接下来推进什么

产品重构现在已经有两份基线：一份定义产品应该为用户创造什么价值，另一份定义首批任务怎样验收。

下一步我会继续做 **第三份：EvoAgent 产品能力覆盖与缺口台账**，重点是把目标与现有工程对应起来：

- 哪些用户功能已经有代码实现；
- 哪些只有接口或设计，还不能真正使用；
- 哪些依赖外部服务或 Android 系统权限；
- 哪些缺口会直接影响任务完成质量；
- 哪些改进应优先实施，哪些可以延后。

我会把“设计完成”“代码存在”“测试通过”“端到端可用”严格区分，避免再次出现技术设计越来越完整、用户却无法真正使用的情况。

产品重构与代码审核可以并行。下一阶段的核心交付不是更多专项，而是让 EvoAgent 从一套具备进化机制的工程，逐步变成一个**用户愿意持续使用、能够放心交办任务、并且确实越用越可靠的个人智能体**。<MemoryCite />
