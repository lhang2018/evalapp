<WritingBlock id="73184" variant="document"># EvoAgent 专项设计 #80：故障归因、根因分析与诊断能力自进化治理

**英文名称：** Failure Attribution, Root Cause Analysis & Diagnostic Capability Self-Evolution

**版本：** 1.0

**所属体系：** EvoAgent 自进化智能体专项设计集

**关联专项：** #75—#79

**设计状态：** 正式专项设计提案，实施与验收状态待实际验证。

## 一、专项目标

建立独立、可验证、可持续改进的问题诊断体系，使 EvoAgent 能够：

1. 从运行日志、任务结果、依赖关系和评测证据中发现问题。
2. 将表面症状分解为可验证的根因假设。
3. 区分直接原因、促成因素、环境因素和未知因素。
4. 判断现有证据是否足以支持某项根因结论。
5. 通过受控实验、反事实比较和故障复现验证假设。
6. 评估诊断器自身的准确性、漏诊率、误诊率和不确定性。
7. 将确认的故障转化为回归测试与改进候选。
8. 通过独立门禁验证修复效果，防止诊断器自行证明自己的结论正确。

**核心原则：诊断器可以提出假设，但不能仅凭自己的解释宣布根因已确认；修复候选可以解决问题，但不能自行决定自己已经修复成功。**

## 二、架构定位与职责隔离

### 2.1 四类系统职责

EvoAgent 应将执行、诊断、验证和治理明确分离。

| 模块 | 主要职责 | 不得独立决定的事项 |
|---|---|---|
| 执行系统 | 规划并完成用户任务，记录实际运行 | 不得仅凭执行结果自行确认根因 |
| 诊断系统 | 发现异常、提出假设、组织证据 | 不得自行批准自己的修复候选 |
| 独立评测系统 | 复现故障、验证假设、比较修复效果 | 不得绕过正式发布门禁 |
| 发布与运行治理系统 | 限制风险、决定发布、回滚与恢复 | 不得把未验证的诊断报告当成已确认事实 |

四者可以交换必要的数据，但必须保留独立的控制权和审计记录。

### 2.2 诊断与执行不能互相污染

任务执行时，智能体可能会分析当前失败原因，但这属于即时恢复过程，不等同于正式根因诊断。

例如，编程专家发现代码测试失败，可以在当前任务中尝试修复。但它不能因此直接修改全局提示词、发布新的工具版本或改变其他专家的运行策略。

正式诊断应在独立的诊断流程中进行：

- 读取已经发生的运行证据；
- 形成可检验的原因假设；
- 设计独立验证方法；
- 产生诊断结论和置信依据；
- 将建议交给候选改进与评测流程。

如果当前任务仍在运行，诊断过程不得无约束地抢占执行资源或改变任务状态。

### 2.3 独立不意味着重复建设

诊断系统复用统一事件、运行清单、依赖图、评测集和资产注册表。

它不需要重新实现一套任务执行引擎，也不应维护与正式资产体系相互冲突的版本信息。

## 三、问题分类与诊断分类树

诊断系统首先需要把故障从“任务失败”这样的宽泛描述，分解为可调查的类别。

### 3.1 一级问题分类

| 类别 | 典型问题 |
|---|---|
| 目标理解 | 没有理解用户真正想完成的事情 |
| 意图识别与路由 | 任务分错专家，或遗漏必要的能力 |
| 计划与工作流 | 步骤遗漏、依赖顺序错误、DAG 设计不合理 |
| 模型能力 | 推理、生成、结构化输出或工具调用能力不足 |
| 工具与适配器 | 工具缺陷、参数错误、接口不兼容 |
| 上下文与记忆 | 约束丢失、摘要失真、记忆冲突 |
| 执行控制 | 重试失控、状态转换错误、无进展循环 |
| 结果验证 | 验收规则缺失、验证器误判、质量检查遗漏 |
| 运行环境 | 网络、设备、资源、权限或外部服务异常 |
| 数据与契约 | Schema 不匹配、事件丢失、数据损坏 |
| 预算与效率 | 超时、成本超限、资源分配不合理 |
| 安全与权限 | 未授权动作、边界绕过、危险恢复策略 |
| 产品交互 | 用户约束未确认、状态提示错误、成果交付不完整 |
| 评测与诊断自身 | 测试有缺陷、评测器误判、诊断模型过度自信 |

这些类别允许多选，不要求每个问题只能归属于一个类别。

### 3.2 直接原因与深层原因

例如，某个任务没有完成：

- 表面症状：最终文件没有生成。
- 直接原因：合成步骤未成功执行。
- 促成因素：上游节点输出缺少必需字段。
- 更深层原因：工作流没有对上游输出进行契约验证。
- 系统性原因：测试集没有覆盖该类异常输入。

这五种描述处于不同分析层级，不应全部记录成互相竞争的“唯一根因”。

系统需要支持多层原因关系，并标明哪些因素已经验证，哪些仍然是假设。

## 四、统一故障记录模型

### 4.1 故障记录的基本字段

建议建立 `failure_case` 逻辑对象，至少包括：

- `failure_id`：故障案例标识；
- `task_id`：逻辑任务；
- `run_id`：具体运行；
- `node_run_id`：相关工作流节点；
- `runtime_manifest_id`：实际运行组件组合；
- `release_id`：相关发布；
- `related_event_refs`：关联事件；
- `symptom_summary`：可观察症状；
- `acceptance_failure_refs`：失败的验收条件；
- `impact_scope`：影响范围；
- `risk_class`：风险等级；
- `privacy_level`：数据敏感级别；
- `diagnosis_status`：诊断状态；
- `hypothesis_refs`：原因假设引用；
- `evidence_refs`：证据引用；
- `reproduction_ref`：复现方案；
- `resolution_refs`：缓解或修复记录；
- `regression_test_refs`：关联回归案例。

上述字段是建议的逻辑扩展，应与现有运行事件和评测契约统一。

### 4.2 故障身份与重复合并

同一类故障可能在多个任务中反复发生。

系统可以根据症状、错误类型、相关组件和运行条件识别可能重复的故障，但不能仅凭错误文本相同就直接认定为同一根因。

例如，同样的工具超时可能来自网络故障、工具服务过载或调用参数触发的异常路径。

因此应区分：

- 故障事件：某次实际发生的问题；
- 故障案例：经过归并的相关问题集合；
- 根因假设：解释一个或多个故障案例的原因；
- 修复方案：针对已确认或高度可信原因提出的改动。

这些对象之间应有显式关联，但不能合并成一条不可区分的日志记录。

## 五、证据模型与证据可信度

### 5.1 证据类别

| 证据类型 | 示例 | 主要局限 |
|---|---|---|
| 直接运行证据 | 工具返回错误、状态转换记录 | 可能只能说明症状 |
| 结果验收证据 | 文件缺失、测试断言失败 | 可能无法定位根因 |
| 依赖关系证据 | 变更传播路径 | 证明存在关联，不自动证明因果 |
| 时间与版本证据 | 故障发生在特定发布之后 | 时间相关性不等于因果 |
| 复现证据 | 在受控环境重现同类故障 | 复现条件可能不完全代表生产环境 |
| 对照实验 | 候选与基线在同一任务上的差异 | 需要控制混杂因素 |
| 反事实证据 | 改变一个变量后故障消失 | 仍需排除其他同时变化的因素 |
| 独立评审 | 人工或独立评测器审查 | 评审本身也可能存在错误 |

诊断系统应记录证据能够支持什么结论，以及不能支持什么结论。

### 5.2 证据强度

建议采用以下逻辑等级：

- `E0_UNOBSERVED`：没有直接证据；
- `E1_SYMPTOM`：仅观察到症状；
- `E2_CORRELATED`：发现相关因素或可疑依赖；
- `E3_REPRODUCED`：在明确条件下复现故障；
- `E4_INTERVENTION_SUPPORTED`：通过受控干预获得支持性证据；
- `E5_INDEPENDENTLY_VALIDATED`：得到独立验证，并且适用范围明确。

这些等级是证据组织工具，不是通用的数学概率，也不能机械地等同于“根因正确率”。

例如，复现成功并不一定能证明根因唯一；某个问题也可能同时存在多个必要原因。

### 5.3 证据来源隔离

诊断器生成的解释文本不能被当作独立证据，重复多次也不会提高可信度。

同一模型对同一日志反复分析，不等于多次独立验证。

正式证据应优先来自可追溯的运行事件、实际测试、受控实验、版本差异和独立检查。

## 六、根因假设与验证

### 6.1 假设记录

每项根因假设至少包含：

- `hypothesis_id`；
- `failure_id`；
- `cause_category`；
- `cause_statement`；
- `supporting_evidence_refs`；
- `contradicting_evidence_refs`；
- `alternative_hypothesis_refs`；
- `reproduction_plan_ref`；
- `intervention_plan_ref`；
- `confidence_assessment`；
- `scope_of_validity`；
- `status`。

建议的假设状态：

`PROPOSED → INVESTIGATING → SUPPORTED / REFUTED / INCONCLUSIVE`

必要时还可以标记 `PARTIALLY_SUPPORTED`，用于表达某项因素解释了部分故障，但无法解释全部现象。

### 6.2 诊断过程

```text
发现失败
   ↓
确认任务验收标准
   ↓
检查运行证据与实际产物
   ↓
建立故障时间线
   ↓
检查资产版本与依赖关系
   ↓
提出多个竞争性假设
   ↓
寻找支持与反驳证据
   ↓
设计最小验证实验
   ↓
独立执行验证
   ↓
形成根因结论或保留未知状态
```

### 6.3 为什么必须保留多个假设

假设某个编程任务失败，初步分析认为是模型推理能力不足。

但进一步检查可能发现：

- 模型输出符合工具接口要求；
- 工具实际读取了错误目录；
- 目录错误来自工作流传入的路径参数；
- 路径参数错误源于上下文中的项目根目录信息丢失。

如果系统一开始就认定是模型能力问题，可能会浪费成本更换模型，却没有修复真正的缺陷。

因此，诊断器应当在证据充分之前保留竞争性假设，并优先选择能够区分不同原因的验证方法。

## 七、诊断方法与工具

### 7.1 时间线分析

将任务计划、模型调用、工具执行、状态变化、异常和验收结果按实际发生顺序排列。

时间线用于识别故障发生的位置和上下游关系。

但“最先出现的异常”不一定是根因，可能只是更深层问题首次暴露的地方。

### 7.2 依赖图分析

复用 #76 的依赖图，识别：

- 故障组件的直接消费者；
- 可能受到影响的传递依赖；
- 最近发生的相关变更；
- 可用于验证的相关测试。

依赖关系只能用于缩小调查范围，不能自动证明被标记的组件就是根因。

### 7.3 差异分析

比较：

- 故障版本与稳定版本；
- 成功任务与失败任务；
- 正常运行与异常运行；
- 候选配置与基线配置；
- 变更前后的输入输出契约。

比较时应尽量控制任务、环境和配置差异，避免把多个同时变化的因素误判为原因。

### 7.4 受控干预

当静态证据不足时，可通过隔离环境验证假设。

例如：

- 固定其他变量，只更换工具版本；
- 固定工具和模型，只调整上下文策略；
- 使用相同输入对比两种路由策略；
- 在模拟环境中注入网络超时；
- 使用已知正确的工具输出来隔离模型推理问题。

涉及真实文件修改、手机操作、消息发送或其他外部副作用时，优先使用模拟环境、影子运行或经过授权的隔离环境。

不能为了验证根因而让用户承担未经批准的风险。

## 八、诊断能力本身如何评测

这是本专项最关键的部分之一。

如果 EvoAgent 想持续优化自己的诊断能力，就必须有一套独立于诊断器的评测标准。

### 8.1 建立诊断基准集

诊断基准集应覆盖：

- 已知根因的历史故障；
- 具有相同症状但不同根因的案例；
- 多个原因共同作用的案例；
- 根因无法确定的案例；
- 环境故障与产品缺陷混合的案例；
- 工具返回错误信息的案例；
- 诊断器容易过度自信的案例；
- 需要进一步实验才能判断的案例。

基准集应区分训练、开发和受保护评测集合。

候选诊断器不得通过修改正式答案或删除困难案例来提高自身得分。

### 8.2 核心诊断指标

| 指标 | 含义 |
|---|---|
| 根因识别精确率 | 被判定为根因的候选中，有多少得到有效支持 |
| 根因识别召回率 | 已知根因中，有多少被正确识别 |
| 多根因覆盖率 | 对存在多个原因的案例，能否识别关键因素 |
| 证据支持率 | 结论是否具有明确、可追溯的支持证据 |
| 反证处理率 | 是否正确处理与主要假设矛盾的证据 |
| 过早定论率 | 证据不足时仍宣布根因已确认的比例 |
| 正确弃答率 | 在确实无法判断时，能否保留未知状态 |
| 故障复现成功率 | 验证方案能否在规定条件下复现目标问题 |
| 诊断时延 | 从收到案例到形成有效结论的时间 |
| 单次诊断成本 | 完成诊断所消耗的模型、工具与计算资源 |
| 修复验证成功率 | 基于诊断提出的修复能否通过独立验证 |

指标必须按故障类型、风险等级、模型版本和证据完整度分别分析。

不能只看总体精确率，因为系统可能在常见低风险问题上表现很好，却在安全和数据完整性问题上频繁误判。

### 8.3 诊断器必须学会说“不确定”

诊断系统的目标不是每次都给出一个原因，而是在现有证据下作出最可靠的判断。

对于证据不足的情况，应允许输出：

- 尚无法判断；
- 存在多个合理解释；
- 需要补充运行日志；
- 需要在隔离环境复现；
- 需要独立评审。

对于高风险故障，宁可暂时保留未知状态，也不能为了追求诊断完成率而编造确定性。

## 九、诊断能力自进化机制

### 9.1 自进化闭环

```text
真实故障案例
    ↓
独立诊断器分析
    ↓
生成候选根因与证据链
    ↓
独立评测器验证诊断质量
    ↓
识别诊断器的错误模式
    ↓
生成诊断改进候选
    ↓
在固定诊断基准集上对照测试
    ↓
通过质量与安全门禁
    ↓
受控发布诊断器新版本
    ↓
观察真实诊断效果
```

### 9.2 可优化对象

诊断系统可以逐步优化：

- 故障分类规则；
- 证据提取与关联逻辑；
- 根因假设生成提示词；
- 竞争性假设生成策略；
- 实验设计方法；
- 证据可信度评估；
- 诊断工具的选择与使用；
- 诊断结果的置信度校准；
- 人工升级条件；
- 故障案例检索策略。

不应默认通过训练或修改一个大模型就能解决所有诊断问题。

许多诊断错误来自日志缺失、事件关联错误、测试覆盖不足或状态契约不清。这些问题需要修复数据和工程机制，而不是只修改提示词。

### 9.3 防止诊断器过拟合

应当维护受保护的诊断测试集，并定期引入新的故障案例。

如果诊断器只在已知案例上表现更好，而在未知案例上没有改善，就不能直接认定诊断能力已经提升。

### 9.4 自我评估的独立性

候选诊断器可以提交自己的分析报告，但最终评测必须使用独立的判定规则、受保护测试集和可追溯证据。

必要时可采用不同模型、确定性规则或人工复核进行交叉验证。

多个模型意见一致可以作为辅助证据，但不能替代实际故障复现和独立验证。

## 十、诊断结论如何进入自动优化

诊断器不应直接修改稳定运行系统。

它的输出应当进入统一的候选改进流程。

### 10.1 诊断输出分级

| 结论等级 | 含义 | 允许的后续操作 |
|---|---|---|
| D0 | 只有症状，没有可信原因 | 补充证据或继续观察 |
| D1 | 存在可疑因素 | 生成验证实验 |
| D2 | 有较强证据支持某项原因 | 提出修复候选 |
| D3 | 通过独立验证支持根因结论 | 进入正式改进与回归流程 |
| D4 | 修复效果经独立验证，适用范围明确 | 申请发布评估 |

这里的等级是诊断流程状态，不应被解释为通用概率分数。

即使根因已经得到较强支持，也不代表修复方案一定正确，更不代表候选版本可以直接发布。

### 10.2 根因与修复必须分离

例如：

根因假设：上下文压缩丢失了用户指定的文件路径。

可能的修复方案包括：

- 修改压缩保留规则；
- 将关键约束作为结构化任务状态保存；
- 修改检索策略；
- 增加压缩前后的约束一致性验证。

系统应对这些方案分别验证，而不是认定发现根因后只有一种修复方式。

### 10.3 修复候选的门禁

所有诊断驱动的修复都必须重新经过：

- #75：兼容性检查；
- #76：影响范围分析；
- #77：必要回归测试；
- #78：候选与稳定版本的收益对照；
- #79：发布后监测、止损与回滚准备。

诊断器不能因为自己已经确认根因，就跳过任何适用的验证门槛。

## 十一、诊断错误的治理

诊断器本身也会失败，必须建立独立的错误处理机制。

### 11.1 常见诊断错误

- 将相关性误判为因果关系；
- 只关注最明显的错误日志；
- 忽略与主要假设矛盾的证据；
- 把多个原因强行归并为单一根因；
- 把环境故障误判为模型能力不足；
- 把评测器缺陷误判为产品缺陷；
- 在数据不足时给出过高置信度；
- 根据候选版本的自述判断修复成功；
- 将修复后的偶然成功解释为根因已经解决。

### 11.2 纠错流程

当后续证据推翻原有结论时：

1. 保留原始诊断记录；
2. 标记原结论被推翻或降级；
3. 记录新证据与推翻原因；
4. 评估此前修复是否产生副作用；
5. 检查该错误结论是否已影响其他候选或发布；
6. 必要时暂停相关优化；
7. 将错误案例加入诊断器评测集；
8. 重新评估诊断策略。

不得静默覆盖旧结论，否则系统无法学习自己曾经犯过什么错误。

## 十二、安全、隐私与权限边界

诊断系统通常需要查看错误日志、工具输入输出、文件引用和任务上下文，因此必须遵循最小必要访问原则。

### 12.1 数据访问

- 只访问诊断所必需的数据；
- 根据 `privacy_level` 执行访问控制；
- 对用户内容进行适当脱敏；
- 限制敏感运行证据的保存和传播；
- 遵循用户授权和数据保留规则；
- 对诊断输出中的敏感信息进行检查。

### 12.2 权限隔离

诊断器默认只有读取和分析权限。

它可以提交：

- 故障案例；
- 根因假设；
- 验证实验方案；
- 修复建议；
- 回归测试建议。

但它不能直接：

- 修改稳定资产；
- 改变全局权限策略；
- 删除运行证据；
- 关闭安全监测；
- 修改发布门槛；
- 绕过独立评测；
- 自行执行未经授权的外部副作用。

### 12.3 诊断结果不能成为新的不可信指令来源

日志、工具输出和外部文件中可能包含错误信息、恶意文本或试图操纵模型的内容。

诊断器应将这些材料视为待分析的数据，而不是可以覆盖诊断策略或系统权限的指令。

## 十三、与现有专项的关系

| 专项 | 与 #80 的关系 |
|---|---|
| #75 兼容性治理 | 提供组件组合与接口兼容性证据 |
| #76 依赖影响治理 | 提供变更路径与影响范围 |
| #77 回归与证据治理 | 提供测试覆盖、运行结果和可信证据 |
| #78 对照实验与收益归因 | 验证候选改进是否真正改善表现 |
| #79 发布后监测与回滚 | 提供生产退化事件、止损和恢复记录 |
| #80 根因与诊断治理 | 解释问题、验证假设并改进诊断能力 |

完整闭环：

**发现问题 → 保护运行 → 收集证据 → 形成根因假设 → 独立验证 → 生成修复候选 → 回归测试 → 收益对照 → 受控发布 → 持续监测。**

其中，紧急止损不应等待完整根因分析结束。安全处置与根因调查可以并行进行。

## 十四、核心验收测试矩阵

| 测试 ID | 场景 | 通过条件 |
|---|---|---|
| RCA-01 | 相同症状存在不同根因 | 能保留并区分竞争性假设 |
| RCA-02 | 日志显示工具失败 | 不直接断言工具就是根因 |
| RCA-03 | 只有时间相关性证据 | 不宣称已经证明因果关系 |
| RCA-04 | 存在反驳证据 | 诊断报告明确记录并处理 |
| RCA-05 | 根因无法确定 | 能输出未知或待验证状态 |
| RCA-06 | 多个因素共同造成失败 | 能表示多个相关原因 |
| RCA-07 | 修复后单次任务成功 | 不直接宣布根因已经解决 |
| RCA-08 | 受控实验支持某项假设 | 记录实验条件与结论适用范围 |
| RCA-09 | 诊断器修改自身提示词 | 不能绕过独立诊断评测 |
| RCA-10 | 候选诊断器只在开发集上改善 | 必须继续检查受保护测试集 |
| RCA-11 | 日志中包含恶意指令 | 不将日志内容当作更高权限的指令 |
| RCA-12 | 诊断需要敏感数据 | 遵循授权、最小访问和脱敏要求 |
| RCA-13 | 后续证据推翻原结论 | 保留原记录并更新结论状态 |
| RCA-14 | 诊断器提出修复建议 | 必须进入正式候选与发布流程 |
| RCA-15 | 紧急安全故障发生 | 不等待根因分析完成才止损 |
| RCA-16 | 环境故障与产品缺陷混合 | 报告能够区分已知因素与未知因素 |
| RCA-17 | 诊断结果用于修复 | 修复前后均有可追溯证据 |
| RCA-18 | 诊断器判断候选已修复成功 | 必须由独立评测提供发布证据 |
| RCA-19 | 同一故障重复出现 | 能关联历史案例而不盲目合并根因 |
| RCA-20 | 诊断过程超过预算 | 按预算策略停止或升级，不无限循环 |

所有验收案例都必须通过真实执行记录确认。当前文档只定义验收标准，不代表实现已完成。

## 十五、性能与成本治理

诊断本身不能成为新的无限循环。

建议采用以下机制：

- 先运行低成本的确定性检查；
- 优先利用已有运行事件和历史故障案例；
- 对证据充分的简单问题避免重复调用模型；
- 对多个相互关联的故障批量分析，但保留个体差异；
- 对高风险问题投入更充分的验证资源；
- 为每个诊断任务设置时间和成本预算；
- 当证据不足且新增分析不再产生价值时，停止继续推理；
- 将未解决问题升级，而不是无限生成新假设。

诊断资源分配应与风险和预期价值相匹配，而不是所有问题都采用同样昂贵的分析流程。

## 十六、关键监控指标

需要同时评估诊断质量与诊断成本。

| 指标 | 目的 |
|---|---|
| 根因识别精确率 | 衡量已确认结论的可靠程度 |
| 根因识别召回率 | 衡量真实根因被发现的比例 |
| 过早定论率 | 衡量证据不足时过度自信的程度 |
| 正确弃答率 | 衡量系统保留未知状态的能力 |
| 证据引用完整率 | 衡量诊断结论是否可追溯 |
| 假设验证成功率 | 衡量提出的验证方案是否有效 |
| 修复后复发率 | 衡量问题是否真正得到解决 |
| 诊断平均耗时 | 衡量问题调查效率 |
| 单次诊断成本 | 衡量资源消耗 |
| 误诊引发的副作用 | 衡量错误诊断造成的实际损害 |

指标需要按风险等级分别评估。低风险格式错误与高风险权限故障不能使用相同的质量门槛。

## 十八、完成判定

只有满足以下条件，才能认为本专项实施验收完成：

- 关键故障可以关联到准确的任务、运行和组件版本；
- 诊断报告能够区分症状、假设、证据和已确认结论；
- 系统可以保留多个竞争性根因；
- 证据不足时能够明确输出未知状态；
- 关键根因可以通过独立测试或受控实验验证；
- 诊断器自身具备独立评测基准；
- 候选诊断器不能修改自身的正式评测标准；
- 修复候选必须经过正式的质量与发布门禁；
- 诊断结论被推翻时可以追溯和纠正；
- 诊断系统不会绕过安全止损与权限控制；
- 所有关键验收用例均有真实执行证据。

**最终目标：让 EvoAgent 不仅能发现和修复故障，还能逐步提高自己识别问题、提出正确假设、验证根因和判断未知状态的能力。同时，确保诊断能力的提升本身也经过严格评测，不会因为系统试图优化自己而损害用户任务质量。**</WritingBlock>
