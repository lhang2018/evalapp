# EvoAgent 第二十六专项：任务生命周期、并发与隔离治理

这一轮我们解决 EvoAgent 从“能可靠执行单个任务”走向“能长期、稳定地管理多个任务”时必然遇到的问题。

你设计的 EvoAgent 不只是聊天机器人。它可能同时运行编程、研究、漫剧制作、手机操作等任务，还会执行长时间 DAG、调用外部模型、积累记忆、恢复失败任务，并在后台进行受控进化。

如果没有统一的任务生命周期和并发治理，就会出现：

- 两个任务同时修改同一份文件；
- 一个任务取消了，后台工具却继续执行；
- 两个专家争抢同一份 GPU 或模型调用预算；
- 某个任务的临时记忆污染另一个任务；
- 新版本发布后，正在执行的旧任务突然改变行为；
- 断网恢复后，同一个外部操作被重复提交；
- 低优先级的后台评测挤占了用户当前任务的资源。

本专项建议定义为：

**Task Lifecycle, Concurrency & Isolation Governance，简称 TLCIG。**

它负责任务状态机、任务隔离、资源调度、并发控制、取消与恢复、任务优先级和跨任务冲突治理。

## 一、第一性原理：任务不是一个请求，而是一个有状态、有资源、有副作用的执行实体

在 EvoAgent 中，一个用户请求可能变成一个复杂任务。

例如，“制作一段 60 秒动态视频漫剧”可能包含：

- 需求分析；
- 剧本生成；
- 角色与场景设计；
- 分镜规划；
- 多次图像和视频生成；
- 配音；
- 媒体合成；
- 质量验收；
- 失败恢复；
- 最终交付。

这个任务可能持续几十分钟，也可能因外部服务不可用而暂停数小时。

因此，不能把 HTTP 请求是否返回、模型是否回答完毕，当成整个任务的生命周期。

**任务必须是能够独立识别、持久化、暂停、恢复、取消、审计和最终结算的执行实体。**

建议每个任务至少具有以下属性：

- 唯一 `task_id`；
- 原始目标与约束；
- 当前生命周期状态；
- 任务所属专家；
- 任务 DAG 与节点状态；
- 执行配置快照；
- 权限与预算；
- 资源占用情况；
- 输入、输出和产物引用；
- 取消、暂停与恢复信息；
- 当前执行租约；
- 任务优先级；
- 最终验收结果。

任务的所有权、状态和配置都必须持久化，不能只存在于某个模型调用的内存里。

# 二、任务生命周期：明确每个状态意味着什么

我建议采用显式任务状态机，而不是通过几个布尔字段拼凑任务状态。

  {#each [
    ["CREATED","任务已登记，尚未进入执行队列。"],
    ["QUEUED","等待调度器分配资源。"],
    ["READY","依赖、授权和必要资源已满足，可以启动。"],
    ["RUNNING","任务正在执行一个或多个节点。"],
    ["WAITING","等待外部服务、用户输入、授权或其他依赖。"],
    ["PAUSING","正在停止新的调度，并处理正在执行的节点。"],
    ["PAUSED","任务已进入可恢复的暂停状态。"],
    ["CANCEL_REQUESTED","已收到取消请求，正在协调停止操作。"],
    ["CANCELLED","取消已完成，剩余操作已停止或进入明确的安全处置状态。"],
    ["SUCCEEDED","所有必要步骤和最终验收均已通过。"],
    ["FAILED","任务无法按当前策略完成，且没有可继续的自动恢复路径。"],
    ["RECOVERY_REQUIRED","状态不一致、外部结果未知或恢复条件尚未满足，需要先核验。"]
  ] as item}


        {item[0]}


        {item[1]}


    {#if item[0]!=="RECOVERY_REQUIRED"}

    {/if}
  {/each}

这里需要特别注意：`WAITING` 不等于 `PAUSED`。

- `WAITING` 表示任务仍然有效，但在等待某个条件。
- `PAUSED` 表示执行被有意暂停，等待恢复指令或调度条件。
- `CANCEL_REQUESTED` 表示取消已经提出，但副作用和后台执行尚未全部核实。
- `RECOVERY_REQUIRED` 表示系统暂时无法确认安全的下一步，需要先完成对账。

这几个状态不能混用，否则容易在断网、取消和重启后产生重复执行。

## 2.1 终态必须有明确含义

建议 `SUCCEEDED`、`FAILED` 和 `CANCELLED` 是逻辑上的终态，但终态记录仍然可以关联后续的审计、清理和补偿事件。

例如，任务取消后发现外部视频生成仍在继续，不应该悄悄把原任务重新改回运行中。应当记录外部操作的后续状态，并根据策略决定是否继续监测、取消外部任务或清理产物。

如果原任务需要继续执行，应通过明确的恢复或新任务机制处理，而不是任意修改终态。

## 2.2 状态转换必须经过权威控制器

建议由 Task Lifecycle Manager 统一检查：

- 当前状态是否允许目标转换；
- 是否满足必要前置条件；
- 是否存在仍在执行的关键操作；
- 是否需要先核验外部状态；
- 当前授权是否仍有效；
- 状态版本是否与发起转换时一致。

这样，Planner、专家或工具不能直接将任务改成 `SUCCEEDED`，也不能绕过取消流程把任务强行恢复为 `RUNNING`。

# 三、任务隔离：不同任务不能共享一切

这是多任务系统最容易出现隐性错误的地方。

两个任务可能属于同一个专家、同一个项目，甚至使用同一套工具，但它们仍然需要拥有独立的执行状态。

建议采用四层隔离模型。


    <title size="md">L1 · 任务执行隔离</title>
    每个任务拥有独立的运行状态、DAG、节点状态、执行尝试、取消令牌和任务预算。



    <title size="md">L2 · 上下文与记忆隔离</title>
    每个任务拥有独立的工作记忆和上下文包；共享用户、项目和专家记忆必须通过明确的检索与权限规则访问。



    <title size="md">L3 · 文件与产物隔离</title>
    任务临时文件、下载文件、生成素材和中间产物拥有明确的归属、版本与访问范围。



    <title size="md">L4 · 资源与权限隔离</title>
    任务只能使用获得授权的工具、文件范围、模型预算和设备资源；一个任务不能通过另一个任务扩张权限。


## 3.1 哪些数据可以共享？

并不是所有内容都需要复制一份。

例如：

- 已验证的编程知识，可以由多个编程任务只读共享；
- 项目架构文档，可以被多个任务读取；
- 稳定模型适配策略，可以被多个符合条件的任务引用；
- 同一项目的文件，可以被多个任务读取，但并发修改需要额外控制。

真正需要隔离的是可变状态、未验证经验、执行中的临时上下文，以及可能产生冲突的写入操作。

## 3.2 哪些数据绝不能默认共享？

- 某个任务尚未验证的中间结论；
- 只对某次任务有效的临时记忆；
- 尚未发布的候选策略；
- 未授权任务的文件和工具权限；
- 某次执行的取消令牌；
- 某个任务独占的临时文件；
- 任务 A 尚未验收的产物，不能被任务 B 默认当作正式输入。

建议使用显式的作用域标识，例如：

`task_scope`、`project_scope`、`expert_scope`、`user_scope`、`global_scope`。

作用域是访问与治理边界，不只是存储目录的命名规则。

# 四、并发控制：两个任务同时修改同一个资源怎么办？

假设任务 A 和任务 B 同时处理同一个代码仓库。

任务 A 读取了文件版本 V1，开始修改；任务 B 也读取了 V1，并提交了自己的修改。随后任务 A 覆盖写入，任务 B 的改动就可能丢失。

这就是典型的并发写入冲突。

我建议根据资源类型，采用不同的并发策略，而不是所有资源都使用同一种锁。

## 4.1 四种资源并发策略

| 资源类型 | 建议策略 | 原因 |
|---|---|---|
| 不可变产物、稳定策略版本 | 共享只读 | 不会发生原地修改冲突 |
| 任务临时文件、独立工作区 | 独占写入 | 避免任务间互相覆盖 |
| 项目共享文件、项目配置 | 版本检查与受控写入 | 允许并发读取，但必须识别修改冲突 |
| GPU、并发 API 配额、全局预算 | 中央资源调度 | 避免超额占用和资源争抢 |

## 4.2 优先使用独立工作区，而不是长期持有全局锁

对于代码修改，建议每个任务在独立工作区或分支中完成修改和测试，再通过明确的合并流程提交。

这样，任务 A 可以持续分析代码，任务 B 也能独立工作，不需要从头到尾锁住整个仓库。

最终合并时，再检查基础版本是否变化、文件是否发生冲突、测试是否仍然通过。

如果两个任务修改了同一个文件，系统应当执行差异合并或请求人工处理，而不是默认后写入者覆盖先写入者。

## 4.3 使用乐观并发控制

对于适合版本检查的资源，可以采用类似以下机制：

1. 读取资源版本 V1；
2. 基于 V1 生成修改；
3. 提交时检查当前版本是否仍然为 V1；
4. 如果仍然是 V1，则允许提交并产生 V2；
5. 如果已经变成 V2 或更新版本，则拒绝旧版本覆盖，并进入合并或重新规划流程。

这可以通过数据库版本列、文件哈希、仓库提交 ID 或其他资源版本标识实现。

但需要注意：文件哈希只能帮助识别内容变化，并不能代替文件权限检查或证明修改在语义上正确。

## 4.4 锁需要有租约、持有者和恢复机制

某些资源确实需要独占访问，例如特定硬件设备或不支持并发写入的工具。

这时建议记录：

- `resource_id`；
- `lease_owner_task_id`；
- `lease_expires_at`；
- `fencing_token`；
- 获取与释放时间；
- 当前占用状态。

租约可以避免任务崩溃后资源永久锁死。

对于支持栅栏令牌的资源，还应当拒绝使用旧令牌提交的过期操作，防止一个已经失去租约的任务继续修改共享状态。

并不是所有文件系统和外部工具都支持完整的租约机制，因此具体执行器还需要根据资源能力选择合适的并发控制方式。

# 五、资源调度：任务多了，不能让所有任务一起抢资源

对于个人电脑或 Mini PC，EvoAgent 的资源可能包括：

- CPU 和内存；
- GPU 与显存；
- 本地模型运行时；
- 外部模型 API 并发额度；
- 文件系统和磁盘空间；
- 视频生成服务的并发任务数；
- 单日或单任务预算；
- 用户当前交互所需的响应能力。

这些资源不应该由每个专家各自管理，否则每个专家都可能认为自己可以启动新任务，最后导致整体过载。

建议建立统一的 **Resource Scheduler（资源调度器）**。

## 5.1 调度器负责什么？

- 为任务分配执行槽位；
- 检查资源是否满足任务需求；
- 控制模型调用并发；
- 管理 GPU、内存和磁盘压力；
- 控制任务费用和调用额度；
- 根据优先级决定执行顺序；
- 在资源不足时排队、降级、暂停或拒绝启动；
- 避免后台进化任务挤占用户当前任务所需资源。

任务可以提出资源需求，但不能自行宣布资源已经分配成功。

## 5.2 任务优先级与资源需求要分开

建议将优先级分成几个维度：

| 优先级类别 | 典型场景 |
|---|---|
| P0 · 安全与恢复 | 处理状态不一致、停止不安全操作、恢复关键任务 |
| P1 · 用户交互 | 当前用户正在等待的任务或确认 |
| P2 · 普通任务 | 用户提交的常规后台工作 |
| P3 · 后台进化 | 经验评测、非紧急回归测试、候选策略实验 |
| P4 · 维护任务 | 缓存整理、低优先级统计和非必要清理 |

这只是建议的默认顺序，具体调度仍然需要考虑截止时间、资源需求、用户设置和风险。

例如，一个 P1 任务可能需要 GPU，而 P3 任务正在运行本地模型。调度器应当依据可抢占性决定是否暂停后台任务、等待资源或使用其他执行路径。

但不能假设所有 GPU 操作都能安全抢占。有些任务需要先完成当前步骤或执行专门的取消流程。

## 5.3 防止低优先级任务永远得不到执行

如果用户持续提交高优先级任务，后台维护可能永远无法运行。

因此，建议采用有界等待、最低资源保留或适度优先级提升等策略，确保必要的维护和资源整理不会无限期饥饿。

对于安全恢复、用户当前任务和普通后台任务，可以使用不同的调度规则，而不是仅依靠一个简单的先进先出队列。

## 5.4 预算也属于资源调度

每个任务应当同时受到：

- 任务级预算；
- 阶段级预算；
- 节点级预算；
- 全局并发与总资源上限。

当任务达到预算上限时，系统应根据任务类型采取明确动作：

- 停止非必要推理；
- 结束无进展重试；
- 选择已经验证的低成本路径；
- 保存状态并等待用户决定；
- 或者以明确的失败原因结束任务。

预算不能被拆成多个子任务后绕过。父任务必须能够汇总子任务消耗，并对整体资源进行约束。

# 六、取消与暂停：发出请求不等于操作已经停止

这是长任务最容易出错的部分之一。

用户点击“取消”，只代表系统收到取消请求，并不代表外部工具、后台进程和模型调用已经全部停止。

例如，漫剧生成任务已经向外部服务提交了视频生成请求。用户随后取消任务，但外部服务仍然可能继续生成并收费。

因此，取消必须是一个具有明确语义的协调过程。

## 6.1 取消流程

  {#each [
    ["1. 持久化取消请求","任务状态变为 CANCEL_REQUESTED，阻止新的普通节点被调度。"],
    ["2. 传播取消信号","向可取消的节点、子任务、进程和外部工具发出取消请求。"],
    ["3. 处理执行中的操作","等待、终止或核查正在执行的操作，按工具契约处理不可取消步骤。"],
    ["4. 对账外部状态","检查已经提交的请求、文件写入和外部副作用是否仍在继续。"],
    ["5. 保存任务证据","记录已完成节点、未完成节点、未知状态和已经产生的产物。"],
    ["6. 提交取消结果","确认后进入 CANCELLED；无法安全确认时，进入 RECOVERY_REQUIRED。"]
  ] as item}


        {item[0].split(".")[0]}


        **{item[0].slice(item[0].indexOf(" ") + 1)}**
        {item[1]}


    {#if item[0]!=="6. 提交取消结果"}

    {/if}

## 6.2 取消后的产物如何处理？

不应该一律删除。

例如：

- 已完成且有效的中间产物，可以保留；
- 未完成的临时文件，可以在确认不再被使用后清理；
- 已经付费生成的视频，应记录其状态和费用；
- 仍在运行的外部任务，应按服务支持的方式查询或取消；
- 状态不明的文件或外部操作，应先核验再决定。

取消是停止后续执行，不是抹去已经发生的事实。

## 6.3 暂停与取消也必须分开

暂停通常允许任务稍后恢复，因此需要保留：

- 当前任务状态；
- 已完成节点；
- 正在运行或等待的外部操作；
- 可恢复的执行检查点；
- 资源租约和授权状态；
- 任务配置快照；
- 剩余预算。

恢复时必须重新检查权限、预算、资源和工具兼容性。原先有效的授权可能已经撤销，原先可用的外部服务也可能已经失效。

因此，恢复不是简单地把状态从 `PAUSED` 改成 `RUNNING`。

# 七、任务之间如何共享经验，又不互相污染？

这与你前面设计的记忆系统和经验治理直接相关。

假设编程任务 A 发现某个工具参数设置错误，任务 B 随后遇到类似问题。

系统确实应该能够利用任务 A 的经验，但不能把任务 A 的临时状态直接复制给任务 B。

建议将跨任务共享分为三个阶段。

## 7.1 阶段一：只共享经过验证的公共资产

例如：

- 已验证的工具使用方法；
- 稳定的编程专家策略；
- 已发布的工作流模板；
- 项目正式架构文档；
- 经过治理的全局规则。

这些资产可以通过版本化引用被多个任务只读使用。

## 7.2 阶段二：候选经验先隔离

任务 A 发现的新经验应该先进入候选区，并记录：

- 来源任务；
- 发生条件；
- 支持证据；
- 适用范围；
- 已知反例；
- 当前验证状态。

其他任务可以在明确允许的诊断流程中参考这条候选经验，但不能默认将其当作正式规则。

## 7.3 阶段三：正式晋升后再共享

只有经验通过相应的验证和治理流程后，才进入正式专家策略或共享资产库。

这与 MEEG 已经确定的经验生命周期一致。

另外，两个任务同时更新同一条记忆时，也需要并发控制。

建议使用版本检查或条件更新，避免后提交的任务无意覆盖先前有效的修改。如果出现冲突，应当合并、重新验证或进入人工处理，而不是简单采用最后写入者的内容。

# 八、任务运行期间配置发生变化怎么办？

这与模型路由、上下文压缩、记忆进化和策略发布密切相关。

假设一个编程任务开始时使用：

- 模型 A；
- 提示词版本 5；
- 上下文策略版本 3；
- 工作流版本 8。

任务运行过程中，系统发布了新模型和新版工作流。

如果任务突然在中途使用新版提示词，却仍然沿用旧版本的上下文结构，执行行为可能变得难以预测。

因此，我建议遵循：

**任务默认绑定启动时的执行配置快照；配置更新不会自动改变正在运行任务的语义。**

## 8.1 三种升级方式

| 方式 | 适用场景 |
|---|---|
| 新任务使用新版本 | 最安全、最简单的默认策略 |
| 当前任务继续旧版本 | 长任务、复杂工作流、需要稳定复现的任务 |
| 受控迁移到新版本 | 旧工具已不可用、存在严重缺陷或必须切换模型时 |

受控迁移必须明确：

- 哪些节点已完成；
- 哪些节点仍在执行；
- 旧版本与新版本的兼容性；
- 哪些上下文或记忆需要重新组装；
- 哪些节点需要重新验收；
- 是否会造成重复外部副作用；
- 是否需要用户批准。

如果迁移可能改变已承诺的结果、显著增加费用或影响用户原始约束，就应该进入相应的授权和确认流程。

## 8.2 已完成节点不应该自动全部重跑

当任务配置发生变化时，系统应根据产物依赖图和配置影响范围，确定哪些节点仍然有效。

例如，单纯升级一个与视频生成无关的日志组件，不应该使已经通过验收的全部视频素材失效。

但如果升级的是生成模型或提示词策略，相关产物可能需要重新评估。

关键在于依赖分析，而不是简单地把整个任务标记为过期。

# 九、建议的任务调度架构

结合前面确定的本地优先战略，我建议将任务治理实现为以下逻辑架构。


    **统一任务入口**
    接收请求、创建任务、关联用户与项目



    **Task Lifecycle Manager**
    状态机、暂停、恢复、取消、终态校验



    <grid-item>

        **Resource Scheduler**
        CPU、GPU、模型并发、费用与优先级

    </grid-item>
    <grid-item>

        **Isolation Manager**
        工作区、上下文、记忆、文件和权限范围

    </grid-item>
    <grid-item>

        **Concurrency Manager**
        锁、租约、版本检查与冲突解决

    </grid-item>
    <grid-item>

        **Recovery Coordinator**
        状态核查、补偿、重试和恢复检查点

    </grid-item>



    **持久化运行时**
    任务与节点状态、事件日志、资源租约、执行快照、产物注册表



    **实际执行层**
    专家、DAG、ReAct、模型、工具和本地/外部执行器


这些是逻辑模块，不需要拆成独立微服务。

对于个人电脑或 Mini PC，我建议优先采用：

- 一个本地任务协调进程；
- 一个权威任务数据库；
- 一个持久化事件与后台任务队列；
- 独立的任务工作区；
- 受控的工具执行器；
- 必要时使用独立子进程运行耗时或不可信任务。

这样既能实现多任务治理，又不会为了架构完整而过早增加大量服务部署与运维成本。

# 十二、下一专项：工具系统、执行环境与能力插件治理

现在，我们已经讨论了任务、状态、记忆、模型、权限、资源与恢复。

但还有一个基础问题值得单独深入：

**EvoAgent 如何安全、稳定地使用越来越多的工具，同时允许工具被替换、升级、测试和复用，而不让每个专家都直接耦合具体工具实现？**

例如，编程专家可能使用 AST 分析器、代码编辑器、测试运行器和 Git；漫剧专家可能使用图像生成、视频生成、配音和 FFmpeg；研究专家可能使用浏览器、搜索和文档解析。

这些工具的执行方式、可靠性、权限要求、成本和副作用差异很大。

如果所有工具都只是简单注册成一个函数，系统将难以统一处理：

- 工具能力发现与选择；
- 参数 Schema 与执行契约；
- 工具版本与兼容性；
- 超时、取消、重试与幂等性；
- 沙箱与权限隔离；
- 工具结果验证；
- 工具成本与资源占用；
- 工具失败诊断；
- 工具替换和回归测试；
- 工具的安装、启用、禁用与升级。

下一专项建议定义为：

**Tool Runtime & Capability Plugin Governance（工具运行时与能力插件治理，简称 TRCPG）。**

重点研究：

1. 如何区分工具、技能、工作流、专家与模型适配策略；
2. 如何为工具建立统一的能力描述、输入输出契约和副作用声明；
3. 如何根据任务需求、权限、环境和成本选择工具；
4. 如何对不可信或高风险工具执行进行沙箱隔离；
5. 如何处理超时、取消、重复调用和外部状态未知；
6. 如何验证工具返回的结果，而不是仅依赖工具自报成功；
7. 如何管理工具版本、兼容性、健康状态和退化；
8. 如何让多个专家复用工具，同时保留各自的权限与执行策略；
9. 如何通过工具评测集和真实运行证据改进工具选择与执行方式；
10. 如何在个人电脑、Mini PC 和 Android 设备上实现统一接口，并根据平台能力选择不同执行器。

这一专项将进一步明确 EvoAgent 的能力扩展边界：系统可以不断增加工具和领域能力，但每项能力都必须具备清晰的契约、权限、版本、验证与恢复机制。
