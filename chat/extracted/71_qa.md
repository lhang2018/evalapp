# EvoAgent 第十六专项：记忆生命周期、经验可信度与跨专家知识治理

这一轮我们继续深入智能体内部设计，不转向部署或产品规划。

你之前反复强调过一个非常重要的要求：EvoAgent 不是单纯记录所有执行过程，也不是让服务端总结出一些经验就全部推送给手机。它需要判断问题到底发生在哪里、什么经验真正有效、适用于哪个专家，以及是否值得改变已经稳定的能力。

**因此，记忆系统必须同时解决三个问题：记住什么、相信什么、允许什么能力使用这些记忆。**

这三个问题如果设计错了，记忆越多，系统不一定越聪明，反而可能越来越容易受到过时信息、错误诊断和跨领域经验污染的影响。

我建议将本专项定义为：

**Memory Lifecycle & Knowledge Governance Engine（记忆生命周期与知识治理引擎，简称 MLKG）。**

它不是单纯的记忆存储模块，而是负责记忆的产生、验证、分类、检索、更新、共享、失效和删除的完整治理机制。

## 一、第一性原理：记忆究竟是为了什么？

记忆的价值不是保存过去，而是改善未来的决策。

例如，EvoAgent 在编程任务中失败了一次。

它可以保存：

- 当时的用户请求；
- 模型使用了什么提示词；
- 调用了哪些工具；
- 工具返回了什么结果；
- 最终为什么没有通过测试。

这些内容适合保存在执行历史中，用于审计、复现和诊断。

但如果未来每次编程任务都把这段历史完整塞进上下文，不仅会增加成本，还可能引入无关信息。

真正有价值的长期经验可能只是：

> 在这个项目中，运行单元测试前必须先激活项目规定的 Python 虚拟环境，否则测试结果不可信。

即便如此，这条经验也需要明确适用项目、验证来源和失效条件，不能无条件用于其他项目。

因此，我们首先要建立一个重要区分：

  {#each [
    ["历史记录","保留发生过什么，用于追溯、复现和审计。"],
    ["记忆","保留未来任务可能需要的信息，用于改善理解、规划和执行。"],
    ["经验","基于案例提炼出的可复用判断或操作规则，需要证据支持。"],
    ["策略","实际影响系统行为的规则、参数或工作流，必须经过适当的验证与发布。"]
  ] as item}



        **{item[0]}**
        {item[1]}


  {/each}

它们之间存在关联，但不能自动互相转换。

一条历史记录可以产生记忆候选；多条案例可以支持一条经验；经过验证的经验可以成为策略候选。但任何一步都需要明确的转换条件。

**尤其不能让一条未经验证的模型解释，直接变成所有专家都会遵循的长期策略。**

# 二、建立六类记忆，而不是一个混合记忆库

我建议把 EvoAgent 的记忆按功能划分为六类。它们可以使用统一的存储基础设施，但必须拥有不同的数据结构、生命周期和检索策略。


    <title size="lg">M1 · 工作记忆 Working Memory</title>
    当前任务正在使用的信息：目标、约束、已完成步骤、当前状态、待解决问题和近期观察。
    生命周期：随任务更新；任务结束后归档必要检查点，其余内容按保留策略清理。


    <title size="lg">M2 · 情景记忆 Episodic Memory</title>
    过去发生过的具体事件：一次失败、一次成功、用户纠正、一次恢复过程及其证据。
    生命周期：根据复现价值、诊断价值和审计要求保留，不默认永久保存全部原始内容。


    <title size="lg">M3 · 语义记忆 Semantic Memory</title>
    相对稳定的事实与知识：项目架构、术语定义、已确认约束和领域知识。
    生命周期：随来源变化、有效期、版本更新和冲突证据重新验证。


    <title size="lg">M4 · 用户模型 User Memory</title>
    用户明确表达的偏好、长期工作习惯和交互方式。
    生命周期：支持修改、撤销、来源追踪和用户控制；绝不能自动替代当前授权。


    <title size="lg">M5 · 程序性记忆 Procedural Memory</title>
    已验证的操作方法、工作流、工具使用规范、恢复步骤和验收方法。
    生命周期：与工具、环境、模型适配和工作流版本绑定，升级后按影响范围重新验证。


    <title size="lg">M6 · 进化与诊断记忆 Evolution Memory</title>
    问题根因、改进实验、失败假设、候选结果、适用范围和已验证的进化结论。
    生命周期：保留证据链与版本历史；失效结论应被标记和隔离，而不是静默覆盖。


这六类记忆的关键不是名字，而是它们回答的问题不同。

例如：

- “用户希望尽量自动完成低风险任务”属于用户模型；
- “上一次代码重构因为遗漏回归测试而失败”属于情景记忆；
- “当前项目使用 Python 3.12”属于语义记忆，但需要绑定项目及来源；
- “先运行指定测试，再生成补丁”可能属于程序性记忆；
- “某项上下文压缩改动在对照实验中导致约束丢失率下降”属于进化与诊断记忆；
- “本次任务已经完成前两个 DAG 节点”属于工作记忆。

同一事件可以产生多个不同的记忆候选，但不能把所有内容无差别地复制到六类记忆中。

# 三、记忆必须有作用域：哪些信息能被哪些专家使用？

这是你之前强调的专家隔离问题，在记忆系统中尤其重要。

假设编程专家发现一种有效的 AST 重构方法。如果直接把它放进全局记忆，手机操作专家、旅游专家甚至漫剧专家都可能检索到这条经验。

即使检索算法认为它“语义相似”，也不代表它适用于当前任务。

所以，我建议把记忆的作用域设计成一个独立字段，而不是依靠向量相似度隐式决定。

## 3.1 五种记忆作用域

| 作用域 | 适用范围 | 示例 |
|---|---|---|
| `TASK` | 当前任务 | 当前漫剧项目的角色清单 |
| `PROJECT` | 指定项目 | 某个代码仓库的构建要求 |
| `EXPERT` | 指定领域专家 | 编程专家的 AST 分析经验 |
| `MODEL_ADAPTER` | 指定模型适配分支 | 模型 B 的上下文压缩参数 |
| `GLOBAL` | 经过验证、适用于全局的知识 | 工具结果必须经过实际状态核验 |

这里还需要特别区分 `GLOBAL` 和“所有专家都可以搜索”。

一条全局记忆也必须有适用条件。例如，“外部操作超时后应先核查状态再决定是否重试”是一条具有广泛价值的原则，但具体核查方法仍然取决于工具是否支持状态查询、是否存在副作用，以及当前操作是否幂等。

## 3.2 采用默认隔离、显式共享

我建议采用以下规则：

- 新经验默认保存在产生它的任务、项目或专家作用域内；
- 不允许仅凭语义相似就自动升级为全局记忆；
- 跨专家共享时，必须明确共享内容、目标专家和适用条件；
- 模型专属的行为补偿不得直接写入模型无关的共享记忆；
- 共享工具缺陷修复与共享知识经验分开治理；
- 记忆跨作用域迁移后，仍然保留原始来源与验证记录。

例如，编程专家发现工具接口缺少必填参数校验。

这条经验可以提炼为通用的工具契约设计原则，但不能据此把编程专家的整套提示词迁移到其他专家。

**共享的是被验证的规律和能力，而不是未经筛选的全部历史。**

# 四、每条记忆都应该有可信度、来源与适用范围

记忆系统最大的风险，不是忘记了有用信息，而是长期保存了错误信息，并且越来越频繁地使用它。

因此，不能只存一个文本字段和向量。

建议每条记忆都具有结构化的治理元数据。

## 4.1 记忆实体的数据结构

## 4.2 不要只用一个置信度数字

一条记忆的可信度至少涉及四个不同问题：

1. **来源可信度：** 信息从哪里来？是用户明确表达、工具实际返回，还是模型推测？
2. **内容可信度：** 内容是否被独立证据支持？
3. **适用可信度：** 在当前模型、项目和环境中是否仍然成立？
4. **时效可信度：** 信息是否可能因为时间、版本或外部状态变化而失效？

这四者不能混成一个分数。

例如，用户明确说“这个项目使用 Python 3.12”，来源可信度很高；但如果项目之后升级到 Python 3.13，这条信息对当前环境就已经过时。

反过来，某条经验可能来源于模型生成的假设，但之后通过大量独立测试得到了验证。它的来源仍然是模型提出的假设，而内容可信度可以随着证据增强。

因此，建议同时保存来源类型、验证状态、适用条件和最近验证时间。

## 4.3 记忆状态应该可追踪

建议至少包含以下状态：

- `CANDIDATE`：刚从任务或诊断中产生，尚未验证；
- `ACTIVE`：当前可以在适用范围内检索使用；
- `NEEDS_REVALIDATION`：环境或依赖发生变化，需要重新验证；
- `CONFLICTED`：存在相互冲突的有效证据；
- `DEPRECATED`：不再推荐使用，但保留历史；
- `REVOKED`：被正式撤销，不能继续作为有效记忆使用；
- `DELETED`：根据数据治理要求完成删除。

这里需要区分 `DEPRECATED` 和 `DELETED`。

一条旧的工具使用经验可能已经过时，但为了分析历史任务仍有价值，可以保留并禁止新任务使用。

如果用户要求删除某项个人信息，或者保留该数据不再具有合法或必要的依据，就需要走相应的删除流程，而不是仅仅将其标记为过时。

# 五、从任务记录到长期记忆：建立受控晋升流程

记忆生成不能采用“模型总结一下，然后直接写入长期记忆”的简单模式。

建议为记忆建立一条独立的晋升流水线。

  {#each [
    ["01","提取候选","从任务结果、用户纠正、工具事实和诊断案例中提取可能有价值的信息。"],
    ["02","识别类型","确定它属于事实、偏好、经验、程序性规则还是模型适配信息。"],
    ["03","检查来源","关联原始轨迹、工具证据、用户明确表达或诊断案例。"],
    ["04","确定作用域","判断它只适用于当前任务、项目、专家、模型适配还是全局。"],
    ["05","检查冲突","检索现有记忆，识别重复、矛盾、过期和适用范围重叠。"],
    ["06","评估未来价值","判断它是否能改善未来决策，是否值得占用检索和存储资源。"],
    ["07","验证候选","对经验类记忆进行回放、测试或独立证据核验。"],
    ["08","正式入库","写入对应记忆库，保留版本、来源、验证状态和访问范围。"],
    ["09","持续维护","根据新证据、环境变化和实际使用效果更新状态。"]
  ] as item}

        {item[2]}

## 5.1 不同类型的记忆，需要不同的晋升标准

例如：

- 用户明确表达的偏好，可以在来源与作用范围明确后直接记录为用户记忆；但不能由此扩大权限。
- 工具返回的确定性结果，可以作为一次情景记录保存；如果要提炼成长期事实，还需要判断它是否具有持续有效性。
- 模型提出的诊断假设，默认只能成为候选，不能直接变成共享规则。
- 经过重复测试的程序性经验，可以在明确适用范围后晋升为专家级有效记忆。
- 跨模型适用的经验，需要有跨模型证据，或者被严格限定为尚待验证的候选。
- 涉及权限、安全和不可逆操作的规则，不允许只通过普通记忆晋升流程改变，必须遵循独立的治理门禁。

这样可以避免系统把“发生过一次”误认为“普遍规律”，把“模型认为有效”误认为“已经被证明有效”。

## 5.2 一次成功是否足以形成经验？

通常不够。

假设某个提示词在一次复杂编程任务中成功了。成功可能来自提示词，也可能来自任务本身较简单、工具状态较好或模型随机生成了正确结果。

对于低风险、明确的项目事实，一次权威来源可能已经足够。

对于会影响执行策略的经验，则应该根据风险和不确定性决定所需证据强度。可以采用重复回放、对照实验、反例测试，或者跨环境验证。

不需要给所有记忆设定统一的“成功三次即可晋升”规则，因为不同类型信息的可靠性来源不同。

# 六、记忆检索不能只靠向量相似度

这是另一个容易出现隐性错误的地方。

假设用户正在编程，系统检索到一条“生成视频时应保持角色一致性”的经验。它与当前任务可能共享“保持一致性”这个语义，但并不适用于当前的代码修改。

因此，记忆检索必须是一个多阶段过程。

## 6.1 推荐的检索流程

  {#each [
    ["第一步：硬过滤","先检查记忆类型、权限、作用域、模型适配范围、状态和有效期。"],
    ["第二步：语义召回","从符合条件的记忆中检索与当前任务相关的候选。"],
    ["第三步：适用性判断","检查任务条件是否满足经验的前提，是否存在例外和冲突。"],
    ["第四步：证据与新鲜度排序","结合来源、验证状态、最近验证时间和反例情况排序。"],
    ["第五步：上下文预算分配","只将真正有帮助的记忆加入上下文，保留来源引用和必要约束。"],
    ["第六步：使用后反馈","记录记忆是否被采用、是否有效，以及是否出现反例。"]
  ] as item}

        {item[1]}


    {#if item[0]!=="第六步：使用后反馈"}

    {/if}
  {/each}

## 6.2 排序时应该考虑什么？

建议至少考虑：

- 语义相关性；
- 作用域匹配程度；
- 证据强度；
- 当前环境与记忆适用条件的匹配程度；
- 时效性；
- 冲突状态；
- 使用成本；
- 对当前任务决策的预期价值。

这里最重要的是：**先确定允许使用，再判断是否相关。**

不能先把所有记忆混在一起进行语义搜索，然后指望模型自己识别哪些内容不应该使用。

权限范围、明确过期状态和已撤销状态，应当由程序先行过滤。

## 6.3 检索到记忆，不代表必须执行记忆

记忆应该为当前决策提供证据，而不是取代当前任务目标。

例如，记忆中写着“用户通常喜欢快速完成任务”，但当前用户明确要求“这次请仔细验证每一步”，系统就应当遵循当前明确要求。

同样，过去某条修复经验曾经有效，但当前工具版本不同，系统应该先检查适用性，而不是盲目执行。

记忆不能凌驾于当前明确指令、硬性权限和事实证据之上。

# 七、上下文压缩与记忆系统如何协作？

这是你之前特别关注的部分：上下文压缩到底是全局共享，还是每个专家独立？

我建议明确区分三个组件：

1. **全局上下文基础设施**：负责 token 预算、消息格式、引用、检查点、截断检测和通用压缩接口。
2. **任务与专家上下文策略**：决定哪些约束必须保留、哪些信息可以摘要、哪些工具结果必须原样引用。
3. **模型适配策略**：决定不同模型适合的压缩格式、上下文长度和信息组织方式。

也就是说，基础设施可以共享，策略不应该强制统一。

## 7.1 压缩不能把重要约束变成模糊摘要

假设用户要求：

“修改代码，但不得改变公开 API；所有测试必须通过；不要修改指定目录之外的文件。”

如果压缩后只剩下：

“用户要求修改代码并保持质量。”

那么上下文压缩实际上已经改变了任务约束。

因此，我建议将上下文划分为两部分：


    **不可丢失的结构化约束**
    原始目标、禁止事项、授权范围、验收条件、预算上限、关键依赖和未完成状态。
    通过结构化字段和独立存储维护，不只依赖摘要文本。


    **可压缩的辅助上下文**
    冗余解释、较早的对话细节、非关键观察、已完成步骤的摘要和可按需重新检索的内容。
    根据任务需要压缩、重排或重新检索。


压缩器可以改变信息的表达形式，但不能自行改变约束的含义。

## 7.2 记忆系统不应该强迫所有历史进入上下文

一个常见错误是把所有记忆检索结果都注入提示词。

更合理的方式是：

- 先装入当前任务的硬性约束；
- 再装入必须保持的任务状态；
- 检索与当前决策直接相关的记忆；
- 对高价值事实保留来源引用；
- 对不确定或存在冲突的记忆明确标记；
- 只有在确有需要时，才加载更长的历史记录。

这样既能降低 token 成本，也能减少无关记忆对模型判断的干扰。

## 7.3 全局压缩机制应该如何进化？

全局上下文引擎可以负责基础算法、预算管理和约束完整性检查。

但不同专家应有独立的保留规则。

例如：

- 编程专家必须保留文件路径、接口约束、测试结果和代码修改状态；
- 手机操作专家必须保留当前页面状态、目标控件、授权范围和操作结果；
- 漫剧专家必须保留角色设定、素材引用、镜头依赖、音画时长和预算状态。

因此，一项压缩算法改进可以在共享基础设施中实现，但必须使用多个领域的保护集进行验证。

某个专家发现的保留规则，也不能未经验证就成为所有专家的统一规则。

# 八、记忆冲突、过期和遗忘机制

记忆系统不可能永久保持所有内容都正确。

用户会改变偏好，项目会升级，工具会更新，模型会切换，原本有效的经验也可能出现反例。

因此，记忆生命周期必须支持更新、冲突、失效与遗忘。

## 8.1 冲突记忆如何处理？

假设记忆中存在两条信息：

- 旧记忆：项目使用 Python 3.11；
- 新证据：项目配置文件明确声明使用 Python 3.12。

系统不应该简单地把两条记忆一起塞进上下文，让模型自己猜哪条正确。

建议：

1. 检查两条记忆是否针对同一个项目和同一时间范围；
2. 检查来源是否权威，以及是否存在版本差异；
3. 如果新证据确实取代旧事实，将旧记忆标记为过时；
4. 如果两条信息分别适用于不同环境，则保留不同的作用范围；
5. 如果仍然无法判断，就标记冲突，并在影响任务时主动核验。

冲突解决不能只看“哪个记忆创建得更晚”。更新的来源可能只是模型推测，而较早的来源可能是权威配置文件。

## 8.2 遗忘不应该只依靠时间衰减

某条记忆很久没有被使用，不一定就没有价值。

例如，用户很少执行数据恢复，但相关恢复约束仍然可能非常重要。

反过来，一条每天都被检索的错误经验，也可能因为上下文匹配而被反复使用，却并不正确。

所以，建议将记忆价值分成几个维度：

- 未来任务的预期帮助；
- 来源与证据可靠性；
- 当前有效性；
- 实际使用后的收益；
- 维护成本；
- 存储与检索成本；
- 错误应用时的潜在损失。

对于高风险记忆，应该更加重视正确性与有效性；对于普通辅助经验，可以采用更积极的淘汰策略。

## 8.3 记忆删除必须有明确语义

需要区分：

- 不再参与检索；
- 标记过时；
- 从活动记忆库删除；
- 删除原始敏感内容；
- 删除或处理其派生副本；
- 保留必要的非敏感审计记录。

这些操作并不等价。

例如，某条经验被废弃，不代表历史评测结果必须删除；但如果原始内容包含用户要求删除的个人信息，就需要按相应的数据治理策略处理原始内容及其派生副本。

系统还应当记录删除传播是否完成，避免手机删除了记忆，而离线个人电脑恢复连接后又把旧副本重新上传。

# 九、跨专家知识共享：建立“共享候选”，而不是直接共享记忆

这是 EvoAgent 与普通个人知识库的一个重要区别。

普通知识库通常关心内容能否被搜索到；EvoAgent 还必须关心这条内容是否适用于当前智能体、是否有足够证据，以及是否会影响其他专家的稳定性。

因此，我建议建立一个独立的 `Knowledge Promotion Pipeline`（知识晋升流水线）。

## 9.2 什么经验适合共享？

比较适合共享的通常是跨领域的工程原则，例如：

- 工具调用成功不等于用户目标已经达成；
- 外部操作超时后应先核查实际状态，再决定是否重试；
- 长任务需要持久化检查点和明确恢复状态；
- 不确定的诊断假设不能直接成为稳定策略；
- 关键约束必须在上下文压缩后保持完整。

这些原则具有较强的通用性，但具体实现仍可能因工具和领域而异。

相反，以下内容不应自动全局共享：

- 某个模型特有的提示词补偿；
- 某个项目特有的目录结构；
- 某个应用的界面点击坐标；
- 某个漫剧角色的视觉设定；
- 只在单次任务中观察到的成功操作顺序；
- 尚未经过验证的根因解释。

## 9.3 共享知识也需要撤回机制

假设一条全局经验经过初步测试后被多个专家采用，但后续发现它只适用于某一类工具。

系统需要能够：

1. 将该经验标记为 `CONFLICTED` 或 `NEEDS_REVALIDATION`；
2. 停止将它推荐给不适用的专家；
3. 查找哪些已发布策略引用了这条经验；
4. 评估是否需要回滚相关策略；
5. 保留原始证据与错误传播链；
6. 在修正后重新发布适用范围更明确的版本。

这意味着记忆之间需要保存引用关系。没有引用关系，系统就很难知道一条错误经验已经影响了哪些能力。

# 十、个人使用的工程实现：记忆系统不需要变成庞大的分布式服务

结合你确定的手机优先方向，我建议采用一个统一的逻辑记忆系统，底层可以按存储类型分开，但不需要为六类记忆建立六个独立服务。

## 10.1 推荐的逻辑架构


    **Memory API**
    统一读写接口、作用域校验、访问控制与版本检查



    <grid-item>

        **Memory Lifecycle**
        候选、验证、晋升、失效、删除

    </grid-item>
    <grid-item>

        **Retrieval Engine**
        过滤、检索、排序、冲突检查

    </grid-item>



    <grid-item>

        **Structured Store**
        SQLite、关系、状态、版本和来源

    </grid-item>
    <grid-item>

        **Content Index**
        全文索引或向量索引，可按需启用

    </grid-item>


    **Evidence & Sync**
    原始来源引用、内容哈希、离线同步与删除传播


这里的 SQLite、全文索引和向量索引只是可选实现。早期不需要强制引入向量数据库，结构化过滤、全文检索和清晰的作用域管理可能更有价值。

当记忆规模和语义检索需求确实增长时，再增加向量索引；它应该是检索能力的增强，而不是记忆正确性的基础。

## 10.2 建议的模块接口

| 接口 | 职责 |
|---|---|
| `propose_memory()` | 从任务或诊断中创建候选记忆 |
| `validate_memory()` | 检查来源、证据、适用条件与冲突 |
| `promote_memory()` | 将通过门禁的候选写入指定作用域 |
| `retrieve_memories()` | 按权限和适用范围检索记忆 |
| `update_memory()` | 修改记忆的内容、版本或有效状态 |
| `deprecate_memory()` | 停止推荐过时记忆，但保留必要历史 |
| `revoke_memory()` | 撤销某项记忆的有效使用资格 |
| `delete_memory()` | 根据数据治理策略删除指定记忆及其派生内容 |
| `share_memory()` | 将经验提交到跨专家共享审核流程 |
| `revalidate_scope()` | 在模型、工具或环境变化后检查受影响记忆 |

这些接口应当由程序层实现权限和状态校验。模型可以提出操作请求，但不能直接绕过生命周期管理，向数据库随意写入共享有效记忆。

## 10.3 数据库至少需要哪些实体？

建议从以下实体开始：

- `memories`：记忆主记录；
- `memory_versions`：记忆内容和状态的历史版本；
- `memory_sources`：原始任务、事件和证据引用；
- `memory_links`：支持、冲突、替代和派生关系；
- `memory_scopes`：适用范围与访问规则；
- `memory_evaluations`：验证结果与评测记录；
- `memory_usage_events`：检索、采用、反馈和失效事件；
- `memory_deletion_jobs`：删除请求及传播状态。

这些可以存储在同一个数据库中，通过事务保证关键状态更新的一致性。

# 十一、记忆系统如何与上下文、模型适配和进化引擎协同？

这里需要明确四个模块之间的边界，否则它们很容易相互覆盖职责。

| 模块 | 核心职责 | 不应该做什么 |
|---|---|---|
| 记忆系统 MLKG | 决定保存什么、适用于谁、是否有效 | 不直接决定每个任务的完整执行计划 |
| 上下文引擎 | 选择当前任务需要哪些信息，并组织、压缩和引用 | 不擅自改变记忆的可信度或授权范围 |
| 模型适配系统 | 判断不同模型如何使用这些信息，以及哪些策略需要重新校准 | 不自动把旧模型的补偿规则升级为通用记忆 |
| 进化与治理系统 | 根据真实结果决定哪些记忆、策略和工具改进值得发布 | 不绕过记忆验证与权限门禁直接修改稳定资产 |

它们的协作流程应该是：

1. 任务开始时，路由器确定领域与任务范围。
2. 记忆系统根据作用域、权限和有效状态提供候选记忆。
3. 上下文引擎选择适用于当前决策的信息，保留必要的来源和约束。
4. 专家执行任务，产生新的事件与证据。
5. 诊断系统判断哪些事件值得形成新记忆候选。
6. 记忆治理系统验证、分类并决定是否晋升。
7. 进化引擎评估这些经验是否值得转化为策略或工具改进。
8. 发布后的真实表现反过来更新记忆的适用范围和可信度。

这个流程形成闭环，但不意味着所有任务都必须执行完整的记忆晋升流程。简单任务可以只更新工作记忆和事件记录，只有具有未来价值的信息才进入后续治理。

# 十三、下一专项：上下文工程与长任务状态连续性

记忆系统解决了“长期保存什么”，但还没有完全解决另一个问题：

**当 EvoAgent 执行一个持续数十分钟、数小时甚至跨越多天的复杂任务时，如何保证它始终知道自己正在做什么、已经完成什么、还缺什么，以及哪些约束绝不能丢失？**

这比普通的对话历史压缩复杂得多。

例如，一项 AI 漫剧制作任务可能涉及：

- 用户最初的故事要求；
- 角色设定和素材版本；
- 分镜生成与视频生成；
- 配音和字幕；
- 任务 DAG 的依赖关系；
- 已经产生的文件；
- 外部生成服务的调用状态；
- 预算与剩余额度；
- 质量验收结果；
- 中断前尚未完成的步骤。

如果只保存一段不断压缩的摘要，系统可能忘记某个关键约束、重复生成已经完成的素材，或者在恢复任务时错误地跳过一个失败节点。

下一专项建议设计 **Context Engineering & Long-Running Task Continuity Engine（上下文工程与长任务连续性引擎）**，重点讨论：

1. 当前任务上下文、长期记忆、执行轨迹和持久化状态之间的边界；
2. 如何维护原始目标、不可变约束和动态任务状态；
3. 如何构建适合不同专家的上下文组装策略；
4. 如何在有限 token 预算下选择最有价值的信息；
5. 如何防止压缩丢失关键约束、来源和不确定性；
6. 如何为长任务建立检查点、断点恢复和幂等执行机制；
7. 如何处理中断、断网、模型切换和配置版本变化；
8. 如何区分“步骤已执行”“结果已确认”和“任务已验收”；
9. 如何避免上下文、记忆和 DAG 状态之间出现冲突；
10. 如何对上下文质量、恢复成功率、重复执行率和实际成本进行评测。

这一步将把 EvoAgent 的长期记忆进一步连接到实际执行状态，让它不仅记得过去发生过什么，还能在复杂任务持续推进时，始终准确掌握当前进度与下一步行动所需的信息。
