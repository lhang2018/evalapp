<WritingBlock id="61842" variant="document"># EvoAgent 专项设计 #78：候选改进对照实验与收益归因治理

**专项编号：** #78

**英文名称：** Candidate Improvement Experimentation & Benefit Attribution Governance

**文档版本：** 1.0

**所属体系：** EvoAgent 自进化智能体专项设计集

**关联专项：** #75 兼容性治理、#76 变更影响传播、#77 回归测试与证据治理

**设计性质：** 正式专项设计提案；实施效果与验收状态待实际验证。

## 一、专项目标

建立一套能够回答以下问题的实验治理体系：

1. 某次改进是否真正提高了任务完成质量？
2. 质量提升是否稳定，还是随机波动造成的假象？
3. 执行效率是否提高，成本和时延是否发生变化？
4. 是否存在某些任务改善、另一些任务退化的情况？
5. 观察到的变化究竟来自候选改进，还是模型、数据、环境和任务分布变化？
6. 什么证据足以支持自动发布，什么情况必须继续观察或拒绝发布？
7. 改进上线后，如果实际效果与实验结果不一致，系统如何识别并停止扩散？

本专项不负责再次验证候选版本是否满足基本功能要求。那是 #75—#77 的职责。

本专项关注的是：**在候选版本已经满足必要的兼容性和回归门槛之后，通过公平、可重复、可归因的对照实验，判断它是否比当前稳定版本更好。**

## 二、核心设计原则

### 2.1 质量优先，效率优化不能牺牲必要质量

EvoAgent 的目标不是单纯提高速度、减少 Token 或降低调用成本，而是在真实任务中提高综合执行能力。

因此，实验必须遵守以下优先顺序：

1. 安全、权限和数据完整性硬门槛；
2. 核心任务完成率与关键质量要求；
3. 稳定性、错误率和恢复能力；
4. 执行时延与资源效率；
5. 成本与额外能力收益。

这里的优先顺序不是说质量以外的指标不重要，而是不能允许成本或速度上的收益抵消严重的质量或安全退化。

### 2.2 每次实验必须有明确假设

不能因为某个参数可以调整，就直接开始自动优化。

每项候选改进都必须说明：

- 当前存在什么问题；
- 为什么认为这个改动能够解决问题；
- 预期改善哪个指标；
- 可能损害哪些其他指标；
- 哪些任务类型会受到影响；
- 需要什么测试与对照实验；
- 什么结果意味着成功；
- 什么结果意味着失败。

例如：

**候选假设：** 优化工具选择策略，可以减少编程任务中的无效工具调用。

**预期收益：** 在保持代码任务成功率和安全门槛的前提下，减少工具调用次数与执行时延。

**潜在副作用：** 工具选择过于激进，可能跳过必要的静态分析或验证步骤。

**实验结论标准：** 不仅要观察调用次数，还要检查代码正确性、必要验证覆盖、失败恢复和最终任务成功率。

### 2.3 实验结果不能只看一个综合分数

如果候选版本的平均得分提高，但高风险任务失败率上升，就不能仅凭综合评分发布。

系统必须保留分指标结果、严重故障记录和任务类型差异。

## 三、候选改进实验的完整生命周期

实验生命周期分为九个阶段。

| 阶段 | 主要工作 | 输出 |
|---|---|---|
| E1：提出假设 | 明确问题、原因与预期收益 | 实验假设 |
| E2：定义实验 | 确定指标、样本、基线和门槛 | 实验方案 |
| E3：验证准入 | 完成兼容性、影响分析和必要回归 | 准入证据 |
| E4：离线对照 | 使用固定任务集比较候选与稳定版 | 离线对照报告 |
| E5：受控验证 | 在隔离环境或影子运行中观察候选 | 受控运行报告 |
| E6：有限发布 | 在获准的低风险范围内进行真实验证 | 灰度实验结果 |
| E7：收益归因 | 分析效果差异、置信程度和副作用 | 收益归因报告 |
| E8：发布决策 | 由独立门禁决定发布、继续观察或拒绝 | 决策记录 |
| E9：效果追踪 | 观察上线后的实际效果 | 发布后验证记录 |

不是每项改进都必须进入真实用户灰度阶段。

对于纯离线、低风险、可以充分复现的改动，离线证据可能已经足够；对于会改变真实任务执行行为的改动，则需要更充分的受控验证。

实验阶段可以按风险调整，但不能跳过适用的强制安全与发布门禁。

## 四、实验对象与对照组设计

### 4.1 对照组

对照组使用当前批准的稳定版本，作为本次实验的基线。

基线必须明确记录：

- 稳定版本及资产版本；
- 模型档案；
- Router、Planner 和 Context Policy 版本；
- 专家与工作流版本；
- 工具及适配器版本；
- 评测集版本；
- 运行环境；
- 预算和超时配置。

如果基线在实验期间发生变化，应停止原有对照关系或创建新的实验批次，不能将不同基线的结果混合成一份实验结论。

### 4.2 候选组

候选组使用待验证的候选版本，并且必须固定其关键运行配置。

实验中应能够明确回答：

- 本次究竟修改了哪些内容；
- 候选组与对照组有哪些差异；
- 是否还有其他组件同时发生变化；
- 哪些变化属于本次实验之外的环境因素。

如果一次同时修改模型、提示词、路由器和工具参数，即使整体效果提高，也很难确定究竟是哪项改动带来了收益。

因此，默认采用**单一主要变量优先**的实验设计。

确实需要联合优化时，应明确记录联合变更，并在必要时通过因子实验或分阶段实验区分各变量的影响。

### 4.3 实验单位

实验单位根据任务类型选择：

- 简单问答：单个任务或独立测试案例；
- 多步骤任务：完整逻辑任务及其所有执行步骤；
- 长期项目：在项目级隔离后进行对照；
- 具有状态或记忆的任务：以独立的会话、项目或测试环境作为隔离单位；
- 有外部副作用的任务：优先使用离线回放、模拟环境或明确授权的隔离环境。

不能将同一个长任务的不同步骤随意分给不同版本，否则会导致上下文、记忆和执行状态相互污染。

### 4.4 随机分配与配对比较

在适用场景中，系统应使用预先定义的分配规则，将可比任务分配到对照组与候选组。

对于固定测试集，可以让两个版本处理相同输入，采用配对比较，降低任务难度差异造成的干扰。

对于随机性较强的模型任务，可以进行多次独立运行，并记录模型参数、随机性设置和环境差异。

如果无法做到严格随机分配，应明确说明实验采用的替代方法及其局限，不能把观察性比较直接当作确定的因果结论。

## 五、实验数据集与任务分层

### 5.1 建立稳定的评测基线

实验不能只依赖最近几个成功案例。

应维护具有明确版本和适用范围的任务集合，至少包括：

- 高频日常任务；
- 复杂多步骤任务；
- 工具调用任务；
- 异常恢复任务；
- 低频但高价值的任务；
- 安全与权限边界任务；
- 历史失败案例；
- 新增的真实任务类型。

不同专家应维护独立的领域评测集，同时保留共享内核的通用回归集。

### 5.2 分层评测

对于 EvoAgent 的多专家架构，应至少按以下维度分析实验结果：

- 专家类型；
- 任务复杂度；
- 是否使用外部工具；
- 是否依赖网络；
- 是否存在多步骤执行；
- 是否涉及恢复或权限审批；
- 模型与运行环境；
- 任务风险等级。

全局平均指标只能作为整体概览，不能代替领域和风险分层分析。

例如，候选路由器可能提高了旅游任务成功率，却降低了编程任务的路由准确率。若只查看整体成功率，可能会掩盖这种退化。

### 5.3 训练数据与评测数据隔离

候选优化过程不得通过直接修改评测答案来制造收益。

需要区分：

- 用于分析和改进的训练或开发样本；
- 用于日常回归的公开评测样本；
- 用于关键质量验证的受保护测试样本；
- 用于上线后观察的真实任务样本。

重要评测样本可以定期更新，但更新必须有版本记录，并保证候选与基线在可比条件下进行测试。

## 六、指标体系与收益判定

### 6.1 核心质量指标

建议优先使用以下指标：

| 指标 | 说明 |
|---|---|
| 任务成功率 | 是否满足任务契约中的必要目标 |
| 结果验收通过率 | 真实产物是否通过适用验收规则 |
| 严重错误率 | 关键事实、执行或安全错误的发生情况 |
| 工具调用成功率 | 工具是否正确完成预期动作 |
| 恢复成功率 | 发生故障后是否能够安全恢复 |
| 路由准确率 | 任务是否分配给适用的专家或执行路径 |
| 约束满足率 | 是否满足用户明确提出的限制 |
| 用户返工率 | 用户要求修正已交付结果的情况 |

指标定义必须统一。例如，任务成功率应以任务契约为依据，而不是以模型是否输出“已完成”来判断。

用户返工率可以作为辅助指标，但不能直接等同于质量错误，因为用户也可能在任务完成后主动改变目标。

### 6.2 效率指标

- 端到端完成时延；
- 模型调用次数；
- 工具调用次数；
- 平均与高分位时延；
- 重试次数；
- 恢复耗时；
- 资源消耗；
- 单个成功任务的实际成本。

其中，“单个成功任务的成本”比“每次模型调用的成本”更有参考价值。

如果某个候选版本降低了单次调用费用，却导致更多任务失败和重试，其真实成本可能反而更高。

### 6.3 稳定性指标

- 任务异常终止率；
- 工具超时率；
- 状态不一致率；
- 取消成功率；
- 断联恢复成功率；
- 兼容性故障率；
- 发布后回滚率。

### 6.4 收益判定原则

实验必须事先声明主要指标和保护性指标。

候选版本的判定逻辑是：

1. 安全与权限硬门槛必须通过；
2. 核心任务质量不得超出预设的退化容忍范围；
3. 稳定性必须达到规定要求；
4. 候选必须在至少一个预先指定的主要目标上获得可信改善，或证明具有明确且获批的其他价值；
5. 成本、时延和资源消耗必须符合预算约束；
6. 实验样本与证据必须足以支持结论。

对于关键质量指标，应优先采用非劣效检验或明确的退化上限，而不是只比较两个版本的平均分。

非劣效界限、样本量和统计方法应按任务风险、指标波动和实际业务要求配置，不能用同一个固定数值适用于所有专家。

## 七、收益归因机制

### 7.1 为什么需要归因

观察到候选版本比稳定版本更好，并不一定说明改动本身有效。

可能的混杂因素包括：

- 两组任务难度不同；
- 模型供应商或模型版本发生变化；
- 外部工具服务状态不同；
- 网络质量不同；
- 评测数据集发生变化；
- 上下文或记忆内容不同；
- 用户任务分布发生变化；
- 测试样本过少；
- 候选只对某些任务类型有效。

收益归因的目标，是判断观测到的差异在多大程度上能够合理地归因于本次候选改进。

### 7.2 基本归因方法

**方法 A：固定输入的配对比较**

让候选与稳定版本处理同一批任务输入，在尽可能一致的环境下比较结果。

适用于提示词、路由规则、工具参数和多数离线执行策略优化。

**方法 B：随机对照实验**

在满足安全和用户授权要求的情况下，将可比任务分配到对照组和候选组。

适用于需要真实运行数据、离线测试无法充分代表实际使用的改动。

**方法 C：分层对照**

按照专家、任务复杂度或环境等因素进行分层，分别比较候选与稳定版本。

适用于候选可能对不同领域产生不同影响的情况。

**方法 D：消融实验**

在联合改进中，分别关闭某项改动，观察其对结果的影响。

适用于模型、路由、工具策略等多个因素组合优化的场景。

### 7.3 归因报告

每次实验应明确记录：

- 主要假设；
- 对照组与候选组；
- 变量差异；
- 任务分配方法；
- 样本规模；
- 运行环境；
- 指标差异；
- 不确定性范围；
- 分层结果；
- 可能的混杂因素；
- 已知副作用；
- 归因结论；
- 结论适用范围。

归因结论应区分：

- 有充分证据支持改善；
- 观察到改善，但证据仍不足；
- 没有发现明确差异；
- 观察到退化；
- 由于环境或数据问题无法判定。

“没有发现差异”不等于证明两个版本完全等效。

## 八、实验统计与样本量治理

### 8.1 不允许随意停止实验

如果系统在观察到一次较好的结果后立即结束实验，容易产生选择偏差。

实验开始前，应定义：

- 主要指标；
- 目标效应或最小有意义改善；
- 样本量估计方法；
- 显著性或置信要求；
- 最长实验时间；
- 预算上限；
- 提前停止条件；
- 安全停止条件。

如果采用序贯检验或持续观察，应使用相应的统计方法，不能在任意时间点反复查看结果并按普通固定样本检验解释。

### 8.2 不确定性处理

对于模型输出具有随机性的任务，应报告效果估计和不确定性。

如果样本量不足，应将结论标记为 `INCONCLUSIVE`，而不是把一次成功运行当作普遍改善的证明。

对于低频但高风险的故障，单纯依赖平均发生率可能不够。必须结合针对性安全测试、故障注入和受保护回归案例。

### 8.3 多指标与多次实验

当同时比较大量指标或同时尝试多个候选时，偶然出现某项改善的概率会增加。

因此需要：

- 预先指定主要指标；
- 将探索性指标与正式发布指标分开；
- 对多重比较采用适当的统计控制；
- 保存全部候选实验结果；
- 不允许只汇报成功实验而隐去失败实验。

## 九、实验阶段与发布策略

### 9.1 阶段 A：离线回放

在固定数据、隔离环境和已知输入下比较候选与稳定版本。

主要检查质量、任务成功率、工具调用行为、成本和回归风险。

离线回放不能证明真实网络、真实设备或真实外部服务条件下的一切行为都正确。

### 9.2 阶段 B：影子运行

在不让候选执行真实外部副作用的条件下，比较候选与稳定版本对同一任务的判断或执行计划。

适用于路由策略、规划策略和部分工具选择逻辑。

影子运行必须隔离候选产生的外部操作。不能为了对照实验而让两个版本重复发送消息、修改文件、提交交易或执行其他不可逆动作。

### 9.3 阶段 C：有限灰度

仅对满足条件的低风险改进开放真实运行验证。

需要：

- 明确的灰度范围；
- 可回滚的候选版本；
- 受控的任务分配；
- 关键质量与安全监控；
- 明确的停止条件；
- 不影响无关专家的隔离机制。

灰度范围应由风险和实际样本量决定，不应为了尽快得到数据而扩大到未经授权的任务。

### 9.4 阶段 D：正式发布

当离线测试、必要的受控实验、收益归因与发布门禁全部满足要求后，才允许晋级。

发布后仍需继续观察实际效果。实验阶段的成功不等于上线后的永久成功。

## 十、实验结果状态与决策规则

建议使用以下结果状态：

| 状态 | 含义 | 后续动作 |
|---|---|---|
| `IMPROVED` | 主要目标获得可信改善，保护指标满足要求 | 可申请发布 |
| `NON_INFERIOR` | 核心质量满足非劣效要求，但没有明确的整体改善证据 | 根据预设价值目标决定是否继续 |
| `REGRESSED` | 关键指标出现不可接受的退化 | 拒绝或回滚 |
| `INCONCLUSIVE` | 证据不足，无法可靠判定 | 补充样本或结束实验 |
| `BLOCKED` | 兼容性、权限、环境或证据条件不满足 | 解决阻塞条件 |
| `STOPPED_SAFETY` | 触发安全停止条件 | 立即停止相关实验并调查 |

`NON_INFERIOR` 不应自动等同于发布通过。

例如，某项改进的目标是降低成本，如果它只是保持质量不变但成本也没有降低，就没有实现原先的优化目标。

### 10.1 自动发布边界

允许自动发布的低风险改进必须满足：

- 候选资产与实验方案经过授权；
- 兼容性检查通过；
- 必需回归测试通过；
- 收益判断满足预先批准的规则；
- 没有触发安全或质量保护条件；
- 回滚目标有效；
- 运行时配置可追踪；
- 发布范围在自动授权边界之内。

高风险变更、共享内核关键策略变更或涉及安全权限边界的变更，应进入更严格的审批路径。

候选版本不得自行调整实验阈值、删除失败证据或改变自动发布授权范围。

## 十一、实验契约与数据结构

本专项应扩展现有资产与评测体系，而不是建立与正式数据契约冲突的独立实验系统。

### 11.1 实验记录的逻辑结构

建议每个实验至少包含：

- `experiment_id`：实验标识；
- `change_id`：关联的变更记录；
- `hypothesis`：实验假设；
- `baseline_asset_refs`：稳定基线资产版本；
- `candidate_asset_refs`：候选资产版本；
- `evaluation_suite_ref`：评测集版本；
- `runtime_manifest_ids`：实际运行配置；
- `primary_metrics`：主要指标；
- `guardrail_metrics`：保护指标；
- `assignment_policy_ref`：任务分配规则；
- `sample_size_plan`：样本量计划；
- `stopping_policy_ref`：停止规则；
- `budget_ref`：实验预算；
- `evidence_refs`：实际运行证据；
- `attribution_report_ref`：收益归因报告；
- `decision_status`：实验结论；
- `release_id`：正式发布关联记录。

这些字段是本专项的逻辑设计，不代表现有接口已经全部实现。正式落地时，应先核对现有 Schema，再决定复用、扩展还是建立新的实验资产类型。

### 11.2 运行记录关联

实验中的每个任务都应能够关联：

- `task_id`；
- `run_id`；
- `runtime_manifest_id`；
- 实际资产版本；
- 对照组或候选组分配信息；
- 评测结果；
- 成本和时延；
- 必要的运行事件。

分组信息应采用稳定且可审计的分配规则，不应依靠模型临时决定当前任务属于哪一组。

### 11.3 证据引用

实验结论必须能够追溯到真实测试结果、运行事件和评测报告。

不能只保存一个最终评分或一段模型生成的“候选版本更好”的解释。

## 十二、与自进化闭环的衔接

本专项把已有的自进化流程进一步完善为：

1. 从运行日志中发现问题；
2. 形成可验证的改进假设；
3. 生成候选版本；
4. 通过兼容性检查；
5. 通过依赖影响分析；
6. 执行必要回归测试；
7. 开展候选与稳定版本对照实验；
8. 分析收益、成本和副作用；
9. 由独立门禁作出发布决策；
10. 对获准版本进行有限发布或正式发布；
11. 观察真实运行效果；
12. 将新发现的问题转化为下一轮改进输入。

需要特别区分三种结论：

- **功能正确：** 候选能够满足必要的功能与安全要求。
- **相对改善：** 候选在规定条件下比基线表现更好。
- **长期有效：** 候选在真实运行环境中持续保持预期效果。

三者需要不同的证据，不能混为一谈。

## 十三、与其他模块的职责边界

| 模块 | 职责 |
|---|---|
| 问题诊断器 | 发现问题并提出原因假设 |
| Evolution Controller | 生成或组织候选改进 |
| #75 MTRC-CCR | 判断候选组件组合是否兼容 |
| #76 依赖影响分析 | 确定受影响资产与测试范围 |
| #77 回归与证据治理 | 确保必要测试执行并保存有效证据 |
| #78 实验与收益归因 | 判断候选相对基线的真实收益 |
| Evaluation Gate Controller | 独立判定候选是否满足发布门槛 |
| Release Controller | 执行批准的发布、暂停和回滚 |
| Runtime Controller | 保障实际任务执行与停止规则 |

诊断器可以提出“工具调用过多”的假设，但不能自己宣布该问题已经解决。

候选生成器可以建议修改路由策略，但不能自行决定实验通过。

收益归因器可以提供统计证据，但不能绕过独立发布门禁。

## 十四、核心验收测试矩阵

| 测试 ID | 场景 | 通过条件 |
|---|---|---|
| EXP-01 | 候选与稳定版比较 | 使用明确且可追溯的基线 |
| EXP-02 | 同一批输入进行配对比较 | 两组输入与关键条件可比 |
| EXP-03 | 实验期间基线发生变化 | 原对照关系被停止或明确分批 |
| EXP-04 | 候选平均分提高但安全失败 | 不允许发布 |
| EXP-05 | 样本量不足 | 结果标记为无法判定 |
| EXP-06 | 多个指标中只有一个探索性指标改善 | 不自动宣称整体改善 |
| EXP-07 | 联合变更产生收益 | 报告明确说明无法独立归因的因素 |
| EXP-08 | 两组运行环境不同 | 明确报告混杂因素和可比性限制 |
| EXP-09 | 影子运行涉及外部副作用 | 候选动作被隔离 |
| EXP-10 | 候选质量不变但成本降低 | 按预先定义的成本优化目标判断 |

| EXP-12 | 多次查看结果并提前停止 | 使用预先批准的统计停止规则 |
| EXP-13 | 实验结果只保留成功样本 | 完整性检查失败 |
| EXP-14 | 候选修改自己的评测阈值 | 权限边界阻止该操作 |
| EXP-15 | 灰度期间出现严重故障 | 停止相关实验并进入安全处理流程 |
| EXP-16 | 离线实验通过但真实环境未验证 | 不宣称已验证所有生产条件 |
| EXP-17 | 收益归因报告生成 | 指标差异、样本、环境和证据均可追溯 |
| EXP-18 | 正式发布后效果退化 | 触发后续监控与发布治理流程 |

## 十五、关键指标与治理要求

建议重点跟踪：

- 候选改善的可信比例；
- 实验结论为 `INCONCLUSIVE` 的比例；
- 候选上线后实际效果与实验结果的一致程度；
- 候选引入的严重退化率；
- 每项可信改善所消耗的实验成本；
- 不同专家之间的改善与退化分布；
- 实验结果复现率；
- 低风险自动发布后的回滚率；
- 从问题发现到可信验证的平均周期。

这些指标用于优化实验体系本身，而不是鼓励系统不断制造更多候选。

如果候选数量增加但可信改善比例持续下降，系统应提高候选筛选质量，而不是进一步扩大实验规模。

## 十六、完成判定

本专项的设计与实施应分别验收。

设计完成至少需要：

1. 统一的实验记录和收益归因契约；
2. 稳定基线与候选版本的绑定规则；
3. 实验单位、分配方法和任务分层规则；
4. 主要指标与保护性指标定义；
5. 统计不确定性和提前停止规则；
6. 受控验证、灰度与自动发布边界；
7. 完整的证据引用和归因报告；
8. 与独立评测门禁和发布控制器的接口映射。

实施验收还需要通过本文件的关键测试，并使用真实实验数据证明结果可追踪、可解释、可复现。

**最终目标：让 EvoAgent 不仅能够不断产生改进候选，还能够用可信实验判断哪些改进真正提高了任务完成质量、执行效率与稳定性，并且只让有充分证据支持的改进进入稳定版本。**</WritingBlock>
