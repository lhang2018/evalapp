## 用户

我有个问题，优化的部分放在app里面，还是放在服务端，优化通过什么方式优化，就可以思考架构冻结了

## ChatGPT

这个问题非常关键，而且确实应该在架构冻结之前解决。

因为它决定了 EvoAgent 的部署架构、数据流、版本管理、安全边界，以及未来能否真正实现你想要的“长期自进化”。

我的建议先说结论：

**采用“手机端稳定执行 + 服务端负责主要进化 + 手机端执行经过验证的更新”的混合架构。** 但不意味着所有优化都放在服务端，也不意味着服务端可以随意修改手机端的一切。

我们需要先区分三个问题：

1. **优化在哪里发生？** 手机端、服务端，还是两边协同？
2. **究竟优化什么？** 提示词、ReAct、上下文、记忆、工具、工作流，还是模型路由？
3. **如何实施优化？** 通过配置调整、代码修改、实验学习、工作流演进，还是模型训练？

这三个问题必须分别设计，不能笼统地称为“自我进化”。

# 一、先确定总体架构：端侧稳定执行，云端深度进化




      <title size="lg">Android App：稳定执行端</title>

    负责实时交互、手机操作、权限控制、任务状态、基础记忆、离线能力、运行日志采集，以及执行已批准的配置与工作流。

    可以调整：允许范围内的运行参数、经过验证的本地策略、工作流版本、模型路由配置。
    不允许：自行修改核心安全边界、绕过权限、直接把未经验证的候选部署到稳定运行内核。




      脱敏事件、评测结果、版本清单、签名更新包





      <title size="lg">服务端：进化与验证中心</title>

    负责跨任务问题分析、根因诊断、候选方案生成、隔离实验、自动评测、成本分析、版本分支、发布门禁和模型适配。

    主要优化：提示词、Planning/ReAct 策略、上下文治理策略、记忆检索策略、工具适配器、工作流定义和模型路由。
    输出：经过测试的候选版本、评测证据、发布清单和可回滚更新包。


为什么我倾向于这样设计？

- 手机资源有限，不适合长期运行大量候选模型和回归实验。
- 手机操作涉及真实设备状态和权限，执行端必须拥有最终安全控制权。
- 服务端可以集中管理模型 API、实验环境、Git 分支和评测资源。
- 你希望为不同模型建立独立适配版本，服务端更适合管理这些版本及其证据。
- 即使网络断开，手机端仍然应该能执行已安装且允许离线运行的基本功能。

这里有一个边界必须特别明确：

**服务端可以提出更新、验证更新和签发更新；手机端必须验证更新的来源、兼容性、权限范围和发布资格，才允许应用。**

而且，服务端不是绝对可信的。即使服务端自身的进化系统发生故障，也不能让手机端失去硬性权限边界。

# 二、哪些优化放在手机端，哪些放在服务端？

我建议把优化划分为四个等级，而不是简单地按模块归属决定。



      <title size="lg">L0</title>


      **运行时自适应：手机端即时完成**

      例如在已批准范围内调整重试次数、选择备用工具、缩短无效规划、恢复检查点或切换已验证的降级路径。

      方式：规则、状态机、有限策略选择。无需等待服务端，也不必每次都启动进化实验。





      <title size="lg">L1</title>


      **轻量策略优化：服务端为主，端侧执行**

      例如优化提示词、调整 Planning 深度、改善记忆检索排序、选择更合适的模型、修改上下文预算分配。

      方式：候选配置生成、离线评测、有限对照实验、版本化发布。通过门禁后，下发配置或策略包。





      <title size="lg">L2</title>


      **复杂能力优化：服务端隔离实验**

      例如修改工具适配器、ReAct 控制策略、上下文引擎、工作流编排和错误恢复逻辑。

      方式：创建 Git 分支、修改实现、运行测试与回归、生成制品，再由发布控制器决定是否部署。






        <title size="lg">L3</title>


        **高风险或基础设施优化：受保护的变更流程**

        例如权限模型、核心状态机、安全策略、数据库迁移、更新验证机制，以及模型训练或底层执行引擎变更。

        方式：更严格的测试、独立审批、兼容性检查和专门的回滚方案，不允许仅凭普通自动评测直接发布。




注意，这四个等级描述的是**变更风险与验证强度**，不只是计算量。一个很小的权限逻辑改动也可能属于 L3；一份较大的静态知识库更新则未必具有同样的风险。

另外，手机端的 L0 自适应也必须受约束。例如，系统可以在允许的范围内切换到备用工具，但不能因为工具失败，就自行扩大无障碍权限或绕过用户确认。

# 三、具体通过什么方式优化？

这是架构冻结前必须明确的第二个核心问题。

我的建议是：EvoAgent 不采用一种万能的自优化算法，而是建立一个**多种优化方法共存、由诊断结果选择方法的进化引擎**。

不同问题使用不同的优化方法。

## 3.1 优化对象与方法对照表

| 优化对象 | 首选优化方法 | 如何判断有效 |
|---|---|---|
| 系统提示词、专家提示词 | 候选生成、版本对比、提示词消融实验 | 相同任务集上的质量、成本与约束遵循表现 |
| ReAct 循环 | 状态机规则修正、轨迹分析、故障注入测试 | 循环异常、工具调用错误、恢复成功率 |
| Planning | 规划策略对照、计划质量评测、动态调整规则 | 任务完成率、计划执行偏差、无效步骤数 |
| 上下文治理 | 预算分配、记忆排序、压缩策略实验 | 关键约束保留率、召回质量、最终任务表现 |
| 记忆系统 | 记忆写入与检索策略实验、冲突检测改进 | 记忆准确率、召回率、过期记忆误用率 |
| 工具系统 | 契约修复、参数校验、错误分类和恢复策略 | 工具调用成功率、结果正确性、重复副作用 |
| 工作流 | DAG 调整、节点拆分、条件分支和恢复策略优化 | 端到端成功率、失败恢复率、执行成本 |
| 模型路由 | 基于任务类别的候选模型比较 | 质量、费用、时延、可靠性与风险 |
| 模型适配 | API 兼容测试、专用提示词与参数调优 | 模型兼容性、能力回归和运行稳定性 |
| 进化决策器 | 阈值校准、预算分配实验、诊断准确性分析 | 无效实验率、回滚率、单位资源的真实收益 |

这些优化方法有一个共同点：**先定义需要改善的结果，再决定改变什么，而不是先修改某个模块，再试图证明它有用。**

例如，工具调用失败率升高时，系统首先应区分参数错误、网络错误、接口变化和模型输出错误。不同根因对应不同优化方案，不能统一用“修改工具提示词”解决。

## 3.2 V0.1 不需要训练自己的大模型

第一版应主要通过以下方式实现进化：

- 提示词与策略配置优化。
- ReAct、Planning 和上下文管理规则优化。
- 工具与工作流实现修复。
- 模型选择和参数配置优化。
- 评测集、诊断规则和发布门禁改进。

这已经能够产生真实的能力提升，而且容易追踪每次改动的影响。

后续如果积累了足够多的高质量任务轨迹，可以考虑训练专用路由器、轻量分类器或记忆排序模型。但这属于后续阶段，不是 V0.1 的前提。

特别是，LoRA 微调或其他模型训练并不能自动解决工具故障、状态管理错误或错误的权限设计。应该先把工程控制链路做好，再判断训练是否值得投入。

# 四、真正的自进化闭环应该怎么运行？

我建议把服务端进化过程设计成一条可审计的流水线。

<CodeBlock language="mermaid" editable={false}>flowchart TD
    A[手机端运行任务] --> B[采集事件与结果]
    B --> C[服务端问题登记]
    C --> D[根因诊断与影响分析]
    D --> E[选择优化方法]
    E --> F[生成候选版本]
    F --> G[隔离环境测试]
    G --> H[质量、成本、安全门禁]
    H --> I{是否通过}
    I -->|否| J[拒绝候选并记录证据]
    I -->|是| K[生成签名发布包]
    K --> L[手机端验证兼容性]
    L --> M{本地准入通过}
    M -->|否| N[拒绝安装并报告原因]
    M -->|是| O[影子运行或受控启用]
    O --> P{线上指标稳定}
    P -->|否| Q[停止推广并回滚]
    P -->|是| R[正式晋级并归档证据]</CodeBlock>

这里有几个关键设计。

### 1. 问题记录与优化方案必须分离

手机端只需要可靠地记录异常、任务结果、版本信息和必要的执行证据。

服务端再判断问题属于环境、工具、模型、记忆还是执行策略。

不要让手机端每遇到一次失败，就自动生成并安装新的提示词。

### 2. 一个候选版本必须声明自己的改动范围

例如：

```text
candidate_id: context-policy-023
target: context_assembly
baseline: context-policy-017

hypothesis:
  减少无关历史记忆注入，可以降低关键约束遗漏。

changes:
  - 调整记忆排序权重
  - 增加约束保留检查

evaluation:
  - 关键约束保留率
  - 任务成功率
  - 上下文 token 数
  - 单任务费用
  - 其他专家回归

rollback:
  context-policy-017
```

这只是示例结构，实际实现应使用经过校验的配置格式和明确的字段类型。

重点是：每次改动都必须知道自己改了什么、试图解决什么，以及怎样证明有效。

### 3. 发布包不仅包含配置，还要包含证据

一个完整的发布制品至少应关联：

- 版本标识与内容摘要。
- 基线版本和变更清单。
- 兼容的 App、模型与工具版本。
- 测试集版本和评测报告。
- 质量、成本、时延和安全门禁结果。
- 发布范围、有效期与回滚版本。
- 发布签名和来源证明。

手机端不应该只因为服务端说“测试通过”就接受更新。它还要验证签名、兼容性、配置完整性和本地安全策略。

# 五、App 和服务端之间，究竟交换什么数据？

这里涉及隐私、成本和诊断质量，需要在架构冻结时明确。

我的建议是：**默认上传结构化诊断事件和必要的脱敏证据，而不是无条件上传全部对话、屏幕内容和用户文件。**




      **默认可上传的数据**

    任务类别、成功或失败状态、错误码、组件版本、工具调用元数据、成本与时延、评测结果，以及经过权限和隐私过滤的必要诊断信息。





      **需要额外授权的数据**

    完整对话、屏幕截图、无障碍界面内容、用户文件、代码片段和原始工具返回。只有诊断确实需要且授权允许时，才应上传。





      **下发到手机的数据**

    已批准的提示词与策略配置、工作流定义、模型路由规则、兼容性元数据、版本清单和签名验证信息。


另外，手机端需要支持不同的运行模式：

- **在线模式：** 上传允许共享的运行证据，接收已批准的更新。
- **离线模式：** 使用本地稳定版本和已安装的工作流继续执行基础任务。
- **受限网络模式：** 缓存诊断事件，网络恢复后再同步；不因等待进化服务而阻塞正常执行。

如果用户拒绝上传某些内容，系统仍应能够在本地记录必要状态，并提供基础诊断能力。隐私授权不能成为执行基本功能的隐性强制条件。

# 六、哪些优化可以自动发布，哪些绝对不能自动发布？

你之前明确提出：希望系统可以自动发布通过门禁的低风险改进，但不能无限增加成本，也不能让某个领域的修改影响其他领域。

因此，我建议采用四类发布权限。

| 改动类型 | 自动实验 | 自动发布 |
|---|---|---|
| 低风险提示词、检索权重和非关键配置 | 允许 | 通过全部门禁后允许 |
| 领域专家的 Planning、工具策略和工作流 | 允许 | 满足严格的领域回归、影响范围和回滚要求后，按预先授权的范围发布 |
| 共享内核、上下文引擎、公共工具接口 | 允许隔离实验 | 默认需要更严格的批准；初期不开放全自动发布 |
| 权限、安全、硬预算、发布控制器及核心状态机 | 允许在隔离环境测试 | 不允许普通进化流程自行发布 |

需要强调的是，提示词也不一定天然属于低风险。若它影响手机操作、外部支付、数据删除或其他高风险行为，就必须按实际影响范围提高发布等级。

自动发布的资格应该由**改动内容、影响范围、风险等级和证据强度共同决定**，而不是仅仅根据文件类型决定。

## 七、如何防止优化让模型调用成本不断膨胀？

这一点必须在架构层面解决，而不是等成本超支以后再补救。

我建议为每个候选版本同时设置三类门槛。


    **质量门槛**

    必须达到目标任务的最低质量要求，关键任务不能发生不可接受的退化。



    **资源门槛**

    设置单任务费用、单次实验费用、每日或每月进化预算，以及最大调用次数和延迟限制。



    **边际收益门槛**

    如果质量提升不足以抵消新增成本，或者在预算内存在更便宜的等效方案，就不应该自动发布该改进。


例如，新策略将成功率从 90% 提高到 93%，但每个成功任务的费用增加了一倍。

系统不能直接认为这是优秀的改进。它应当进一步比较：

- 能否只在困难任务上启用新策略？
- 能否让简单任务继续使用低成本路径？
- 能否通过更好的工具验证而不是额外调用大模型取得相同效果？
- 质量收益是否在足够多的真实任务中重复出现？

这意味着，EvoAgent 不只是要优化“能力”，还要优化**在给定预算下获得能力的方式**。

## 九、我建议下一步正式交付什么？

不再继续增加概念，而是直接进入工程蓝图。

建议按照这个顺序交付：

1. **EvoAgent 总体架构规范 v1.0**：完整模块图、数据流、职责边界和架构决策记录。
2. **V0.1 工程目录与数据库设计**：包括稳定运行内核、后台进化控制器、模型适配、记忆、日志、评测和发布管理。
3. **核心接口与配置契约**：确保不同专家、工具、工作流和模型可以独立迭代。
4. **最小可运行代码**：接入云端模型 API，跑通一个带工具调用、结果验证、故障记录和检查点恢复的任务。
5. **进化闭环实现**：能够创建候选分支、执行评测、判断是否通过门禁，并对获准的低风险改动完成受控发布。
6. **Android 接入计划**：在核心执行与进化闭环验证后，逐步接入手机操作和离线能力。

我的建议是，第一版先在本地开发环境中验证核心内核和进化闭环，再将稳定执行能力接入 Android。这样可以避免同时调试移动端权限、网络、模型 API、任务状态和自动发布，导致问题难以定位。

**最终目标不是让服务端替手机思考一切，也不是让手机自己无限修改自己，而是建立一套稳定执行、独立诊断、受控进化、可验证发布的完整系统。**

到这一步，我认为总体架构可以正式冻结，开始编写《EvoAgent 总体架构规范与 V0.1 工程实施蓝图》。
