# 一、为什么有了记忆系统，仍然不等于能够积累真正的能力？

EvoAgent 已经规划了多个领域专家、独立记忆命名空间、共享通用内核、任务工作流和持续进化机制。

按照这个设计，系统每次执行任务，都可以记录：

- 用户提出了什么需求；
- 任务经过了哪些步骤；
- 调用了哪些工具；
- 哪些步骤成功或失败；
- RCAE 分析出了什么原因；
- 系统尝试了哪些修复；
- UEEDA 的评测结果如何；
- CARE-LBV 是否确认了改进收益；
- SECIASRG 最终发布了什么版本。

但这些数据即使全部保存下来，也不代表 EvoAgent 真正学会了什么。

例如，代码专家曾经遇到工具参数生成错误。

它经过诊断、修改和回归测试，最终通过增加结构化参数校验解决了问题。

一个月后，手机操作专家又遇到类似的问题：工具调用参数缺失，导致自动化操作失败。

如果系统只是保存了历史日志，它可能仍然需要重新分析、重新生成方案、重新运行实验。

如果系统直接复制代码专家的解决方案，又可能把不适用于手机操作的代码逻辑强行迁移过去。

这说明，经验积累至少存在三个不同层次。

| 层次 | 系统拥有的内容 | 实际价值 |
|---|---|---|
| 数据积累 | 保存历史日志、任务结果和失败记录 | 能够回顾发生过什么 |
| 知识沉淀 | 归纳问题模式、原因、解决方案和适用条件 | 能够识别以前遇到过的相似问题 |
| 能力复用 | 将经过验证的经验转化为工具、规则、工作流或可调用模块 | 能够减少重复试错并稳定完成任务 |

EvoAgent 真正需要追求的是第三层，同时保留前两层作为证据基础。

因此，本专项的核心不是简单地增加一个向量数据库，也不是让模型把历史对话总结得更长。

**真正需要建立的是一条从运行证据到可复用能力资产的治理链路。**

它必须回答：

1. 什么样的经历值得保存？
2. 什么样的经验可以被视为可信知识？
3. 如何区分一次偶然成功与可重复的方法？
4. 如何将自然语言经验转化为真正可执行的能力？
5. 哪些经验可以跨专家共享？
6. 哪些经验必须留在专家私有空间？
7. 如何判断一项经验在新模型、新工具和新环境下仍然有效？
8. 如何防止错误经验污染长期知识库？
9. 如何将反复成功的任务固化成稳定工作流？
10. 如何在经验失效后及时撤销，而不是让错误知识长期影响执行？

# 二、第一性原理：知识、经验、策略与能力不是同一种资产

EvoAgent 不能把所有历史信息都放进一个统一的“长期记忆”中，再依赖模型自行区分。

不同信息的可信度、用途、生命周期和复用方式完全不同。

建议首先建立明确的知识资产分类。

## 2.1 八类核心资产

| 资产类型 | 说明 | 示例 |
|---|---|---|
| 原始证据 | 真实发生的事件与观测结果 | 工具调用记录、错误码、执行耗时 |
| 故障模式 | 在特定条件下重复出现的问题特征 | 某类参数缺失会导致工具调用失败 |
| 诊断知识 | 已有证据支持的原因及其适用范围 | 接口版本不匹配导致字段校验失败 |
| 修复经验 | 针对特定问题经过验证的解决方法 | 增加参数校验并提供明确错误信息 |
| 执行策略 | 在特定任务条件下选择行动的规则 | 低置信度时先验证接口，不直接重试 |
| 能力组件 | 可独立调用、测试和版本化的工具或模块 | 参数校验器、AST 检查器 |
| 工作流资产 | 经过验证的多步骤任务流程 | 脚本生成、分镜生成、配音与视频合成 |
| 反模式与限制 | 已知无效方法、风险和禁止条件 | 不应对具有副作用的操作进行盲目重试 |

这八类资产之间存在关联，但不能相互替代。

例如，一条历史日志只能证明某次事件发生过。

一条故障模式可以帮助系统识别类似情况。

一项修复经验可以提供处理建议。

一个可执行的参数校验组件，则可以直接承担相应的运行职责。

**长期知识库负责保存和检索经过治理的知识；能力资产库负责保存可执行、可测试、可发布的能力。两者必须协同，但不能混为一体。**

## 2.2 经验不应因为被重复引用就自动变得可信

假设一条未经验证的诊断被写入知识库。

随后三个专家检索了它，并在各自的任务总结中再次引用。

如果系统把引用次数当成可信度，那么一个错误判断就可能因为不断传播而成为“共识”。

因此，知识可信度必须主要依赖：

- 原始证据；
- 独立验证；
- 可重复性；
- 适用条件；
- 反向证据；
- 实际运行效果；
- 失效与回滚历史。

引用次数、模型自信程度和文本相似度只能作为辅助信息，不能代替验证。

# 四、知识分层：哪些内容应该共享，哪些内容不能共享？

这是 EvoAgent 多专家架构中必须明确的设计问题。

代码专家、旅游专家、AI 漫剧专家和手机操作专家拥有不同的知识需求。

如果全部使用一个共享记忆库，可能产生跨领域干扰。

如果完全隔离，又会重复解决大量相同的基础问题。

建议建立五级知识空间。

## 4.1 五级知识空间

| 空间 | 主要内容 | 默认可见范围 |
|---|---|---|
| L0 原始事件空间 | 日志、任务轨迹、错误与工具结果 | 受访问策略约束 |
| L1 通用经验空间 | 跨领域适用的诊断方法、通用原则和验证经验 | 经批准后可供多个专家检索 |
| L2 专家知识空间 | 代码、旅游、漫剧、手机操作等领域知识 | 默认限于对应专家 |
| L3 任务与项目空间 | 当前任务的状态、约束、临时结论和项目资料 | 当前任务或项目 |
| L4 可执行能力空间 | 工具、策略、工作流、验证规则和可调用模块 | 通过能力依赖与权限策略开放 |

需要特别注意：L0 到 L4 不是简单的知识可信度等级。

原始事件可以非常可信，但它本身未必具有通用性。

通用经验可能已经通过充分验证，但仍然不能直接执行。

可执行能力也必须具有版本、权限和运行时约束。

因此，知识空间与可信度、执行权限和生命周期状态应采用相互独立的维度进行管理。

## 4.2 共享的应该是经过验证的机制，而不是整个专家记忆

例如，代码专家发现：

“工具参数在进入执行器之前，应当经过结构化校验。”

经过验证后，这个原则可能适用于多个专家。

但代码专家的完整项目记忆、源代码路径、私有工具配置和特定编译环境，不应该因此自动共享。

因此，建议采用：

- 通用知识可以跨专家检索；
- 专家私有知识默认不跨专家暴露；
- 任务记忆只在授权的任务或项目范围内可见；
- 可执行能力通过显式依赖声明开放；
- 涉及敏感数据或高风险操作的经验必须经过额外审查。

**共享的是经过验证、边界明确的知识与能力，不是整个专家的记忆空间。**

# 五、经验生命周期：从一次经历到正式能力资产

建议建立统一的 `Knowledge Lifecycle Manager`。

一条经验不能因为被自动总结出来，就直接进入全局知识库。

## 5.1 七阶段生命周期

```text
OBSERVED
   ↓
EXTRACTED
   ↓
EVIDENCE_REVIEWED
   ↓
VALIDATED
   ↓
SCOPED
   ↓
PUBLISHED
   ↓
MONITORED
   ├── RETAINED
   ├── NEEDS_REVALIDATION
   ├── DEPRECATED
   └── REVOKED
```

各阶段的含义如下。

**OBSERVED：观察到经历。**

系统记录了真实事件，但还没有将其抽象成经验。

**EXTRACTED：已抽取候选知识。**

系统从一个或多个事件中提取了故障模式、可能原因或解决方法。

**EVIDENCE_REVIEWED：已审查证据。**

确认来源可追溯，检查是否存在明显矛盾、数据缺失或错误归因。

**VALIDATED：已通过适当验证。**

根据知识类型执行复现、回归测试、受控实验或其他合理的验证方法。

**SCOPED：已明确适用范围。**

明确适用的任务、专家、模型、工具、环境和限制条件。

**PUBLISHED：已发布到指定知识或能力空间。**

这不意味着它自动成为全局知识，也不意味着它可以在所有环境中直接执行。

**MONITORED：已进入持续观察。**

实际复用结果会继续反馈给知识治理体系。

随后可能保留、重新验证、废弃或撤销。

## 5.2 不同知识类型需要不同的晋级门槛

例如：

- 通用诊断原则需要证据支持，并检查适用范围；
- 确定性工具规则需要单元测试和契约测试；
- 概率性执行策略需要代表性任务评测；
- 工作流模板需要端到端验收；
- 涉及外部副作用的能力需要权限与恢复测试；
- 高风险共享能力需要更严格的跨专家回归和发布门禁。

不能要求所有知识都执行相同的验证流程。

同样，也不能因为一项经验只是自然语言总结，就免除其可信度和适用性审查。

# 六、经验抽取：如何从运行日志中得到真正有价值的知识？

原始运行记录通常包含大量细节。

例如，一次代码修改任务可能记录了数百条模型消息、工具调用和文件变更。

直接把全部记录塞进长期记忆，既浪费资源，也很难帮助后续任务。

建议建立 `Experience Extraction Pipeline`。

## 6.1 抽取流程

1. 识别值得沉淀的事件；
2. 关联任务、版本、模型、工具和环境；
3. 判断是否属于已有故障模式；
4. 提取问题条件与实际表现；
5. 区分已确认事实、诊断假设和未知信息；
6. 提取采取过的行动；
7. 记录各行动的结果；
8. 关联 CARE-LBV 的收益验证；
9. 生成候选经验；
10. 根据知识类型决定是否进入进一步验证。

## 6.2 经验对象的数据模型

建议建立 `ExperienceRecord`。

| 字段 | 含义 |
|---|---|
| `experience_id` | 经验唯一标识 |
| `source_event_refs` | 原始事件引用 |
| `task_id` | 来源任务 |
| `capability_id` | 来源能力 |
| `failure_signature` | 故障特征 |
| `observed_conditions` | 观察条件 |
| `known_facts` | 已确认事实 |
| `hypotheses` | 根因假设 |
| `actions_attempted` | 已尝试行动 |
| `action_outcomes` | 行动结果 |
| `negative_results` | 无效或有害的尝试 |
| `evidence_refs` | 支持与反向证据 |
| `environment_fingerprint` | 环境特征 |
| `applicability_scope` | 适用范围 |
| `validation_status` | 验证状态 |
| `lifecycle_status` | 生命周期状态 |

## 6.3 不能只总结成功步骤

假设某个任务尝试了四种修复方法，最后一种成功。

如果系统只记录最终成功方案，就会丢失前三种方案失败的原因。

但如果系统把前三种方案永久标记为无效，也可能错误地排除未来在新环境下有效的方法。

因此，经验抽取必须同时保存：

- 成功方案；
- 失败方案；
- 失败条件；
- 已排除的原因；
- 尚未解决的疑问；
- 方案适用的环境；
- 后续是否需要重新验证。

负面经验应当用于减少重复试错，而不是生成无条件的永久禁令。

# 七、知识可信度：如何避免错误经验污染长期知识库？

这是本专项最重要的治理机制之一。

模型生成的经验总结可能出现：

- 将相关性误判为因果关系；
- 把偶然成功归因于某项修改；
- 遗漏导致失败的环境条件；
- 忽略同时发生的模型或工具变化；
- 将专家私有经验错误地推广为全局规则；
- 从少量案例中得出过度普遍的结论。

建议建立 `Knowledge Evidence Profile`。

## 7.1 证据类型

| 证据类型 | 说明 | 主要用途 |
|---|---|---|
| 单次观察 | 某个案例出现特定结果 | 提出经验候选 |
| 重复观察 | 多个案例呈现相似现象 | 识别稳定模式 |
| 可复现测试 | 在明确条件下可以重复观察结果 | 支持特定机制或规则 |
| 对照实验 | 比较不同方案的结果 | 评估方案差异 |
| 长期运行证据 | 实际使用中持续观察到的效果 | 判断实际价值和稳定性 |
| 反向证据 | 出现与经验不一致的案例 | 限定范围或推翻原结论 |

这些证据并不是严格的单向等级。

例如，一个精心设计的对照实验可能比大量重复但存在同一偏差的观察更有说服力。

因此，系统应根据具体主张评估证据，而不是简单累计证据条数。

## 7.2 建立主张级证据，而不是整条经验一个置信度

一条经验可能同时包含多个主张。

例如：

1. 某工具参数缺失会导致调用失败；
2. 结构化校验可以拦截该错误；
3. 结构化校验能够降低所有专家的失败率；
4. 该校验在新模型下仍然有效。

第一项可能有充分证据。

第二项可能已经通过测试。

第三项可能尚未进行跨专家验证。

第四项可能需要在模型切换后重新验证。

因此，建议将经验拆分成多个 `KnowledgeClaim`，每个主张分别关联：

- 支持证据；
- 反向证据；
- 适用范围；
- 验证方法；
- 当前状态；
- 最近验证时间；
- 已知限制。

**不能因为经验中的一个结论已经得到验证，就把整条经验中的其他推断一起升级为可信事实。**

# 八、经验迁移：如何判断一个专家的经验能否被另一个专家使用？

这是多专家架构区别于单一智能体记忆系统的关键。

经验迁移不是复制粘贴。

它应该先判断目标任务与原经验是否满足必要条件。

## 8.2 迁移适用性评估

建议建立 `TransferabilityAssessment`，至少检查：

- 任务目标是否相似；
- 原问题与目标问题的机制是否相似；
- 输入与输出契约是否兼容；
- 前置条件是否满足；
- 运行环境是否一致；
- 模型依赖是否一致；
- 工具依赖是否兼容；
- 安全与权限边界是否一致；
- 目标专家的评测集是否覆盖关键风险；
- 原经验是否有明确的失效条件。

最终输出不应该只是一个相似度分数。

建议给出：

- 迁移模式；
- 可直接复用的部分；
- 必须适配的部分；
- 禁止迁移的部分；
- 需要补充的证据；
- 目标环境的验证要求。

## 8.3 迁移后必须重新验证

即使两个专家的底层机制相似，也不能自动认定经验在目标环境中成立。

例如：

代码专家的失败恢复机制可以安全地重新读取文件、检查 AST 并重新执行测试。

手机操作专家如果直接重试一个具有副作用的点击动作，可能重复提交表单、发送消息或创建订单。

因此，迁移时必须保留原经验的机制，同时重新审查目标环境中的副作用和恢复语义。

# 九、知识检索：不要只依靠向量相似度

假设手机操作专家正在处理一个任务：

“点击按钮后没有任何反应。”

知识库中可能存在以下记录：

- 代码工具调用失败；
- 浏览器自动化元素定位失败；
- Android 无障碍节点不可见；
- 网络请求超时；
- 应用界面仍在加载；
- 按钮已经被禁用。

这些记录在自然语言层面可能非常相似，但原因完全不同。

如果系统只根据向量相似度检索，可能得到看起来相关、实际上不适用的经验。

建议采用混合检索。

## 9.1 五阶段检索流程

**第一阶段：结构化过滤。**

先根据以下条件筛选：

- 当前专家；
- 任务类型；
- 工具类型；
- 环境；
- 权限；
- 版本兼容性；
- 生命周期状态。

**第二阶段：语义检索。**

在符合基本条件的候选中，利用语义相似度寻找可能相关的经验。

**第三阶段：依赖与机制匹配。**

比较故障特征、工具契约、前置条件和因果机制。

**第四阶段：证据与适用范围检查。**

优先返回证据充分、适用条件明确、当前仍然有效的经验。

**第五阶段：复用策略生成。**

根据匹配结果，决定直接调用、适配后验证、仅作为启发，还是拒绝迁移。

## 9.2 检索结果必须附带适用条件

检索结果不能只返回一段经验文本。

建议返回：

- 经验 ID；
- 经验版本；
- 适用范围；
- 已验证的环境；
- 依赖能力；
- 证据摘要；
- 已知反例；
- 当前生命周期状态；
- 迁移模式建议；
- 必须执行的验证步骤。

这样，专家才能判断为什么可以使用这条经验，以及使用前需要满足什么条件。

# 十、从经验到能力：如何把成功的任务固化成可执行资产？

这是本专项最重要的产出方向。

很多任务在第一次执行时，需要模型动态规划。

但经过多次成功执行后，其中一部分步骤已经稳定、重复且容易验收。

这时，系统应该判断是否值得将其固化为可复用工作流。

## 10.1 三种能力固化方式

**方式一：规则化。**

适用于稳定、确定、可直接判断的规则。

例如：

- 工具参数必须通过 Schema 校验；
- 关键文件写入后必须检查结果；
- 高风险操作必须先验证目标和权限。

**方式二：工具化。**

适用于重复出现、能够独立测试的操作逻辑。

例如：

- AST 分析器；
- 图片尺寸检查器；
- 视频时长校验器；
- 结构化结果验证器。

**方式三：工作流化。**

适用于多个步骤之间具有明确依赖、输入输出和验收条件的任务。

例如：

- 代码修改与测试；
- 漫剧脚本、分镜、素材生成、配音与合成；
- 手机应用操作与结果验证；
- 旅行信息检索、路线规划与行程整理。

## 10.2 固化工作流的判定条件

不能因为某个任务成功一次，就直接将其固化为稳定工作流。

建议至少检查：

1. 任务输入是否可以明确描述；
2. 主要步骤是否能够被稳定识别；
3. 步骤之间的依赖是否明确；
4. 关键步骤是否具有可验证的输出；
5. 失败是否能够被识别；
6. 是否存在可接受的恢复方案；
7. 关键外部依赖是否明确；
8. 预算和资源消耗是否可控；
9. 是否存在足够的代表性测试；
10. 工作流是否具有明确的版本与适用范围。

对于高度开放、变化频繁的任务，可以只固化其中的稳定子流程，而不是把整个任务变成僵化的固定 DAG。

## 10.3 固化之后仍然保留动态规划能力

例如，AI 漫剧的稳定主流程可以是：

```text
脚本
  ↓
分镜
  ↓
角色与场景素材
  ↓
视频生成
  ↓
配音
  ↓
FFmpeg 合成
  ↓
质量验收
```

但实际执行时可能遇到：

- 某个镜头生成失败；
- 某个角色外观不一致；
- 配音时长与画面不匹配；
- 合成失败；
- 最终时长不符合要求。

因此，固化工作流应当定义：

- 必须执行的核心步骤；
- 可选步骤；
- 分支条件；
- 重试策略；
- 替代方案；
- 验收规则；
- 预算上限；
- 失败退出条件。

**最佳模式不是在固定 DAG 与完全自由规划之间二选一，而是固化稳定部分，让模型在受控范围内动态处理变化部分。**

# 十一、能力资产的依赖、组合与版本管理

一项可复用能力通常依赖多个基础组件。

例如，代码专家的“自动修复与验证”能力可能依赖：

- 文件读取与写入工具；
- AST 分析器；
- 静态分析工具；
- 测试执行器；
- 变更差异检查器；
- 结果验收规则；
- 失败恢复策略。

如果只保存一个“自动修复代码”的能力名称，却没有记录这些依赖，系统就无法可靠地复用它。

## 11.1 建立 Capability Package

建议每项可复用能力都具有统一的能力包描述。

核心字段包括：

| 字段 | 含义 |
|---|---|
| `capability_package_id` | 能力包 ID |
| `capability_version` | 能力版本 |
| `purpose` | 能力用途 |
| `input_contract` | 输入契约 |
| `output_contract` | 输出契约 |
| `dependencies` | 工具和能力依赖 |
| `preconditions` | 前置条件 |
| `postconditions` | 成功后必须满足的条件 |
| `failure_modes` | 已知失败模式 |
| `recovery_policy` | 恢复策略 |
| `security_profile` | 权限与安全要求 |
| `resource_profile` | 资源与成本特征 |
| `evaluation_suite` | 对应评测集 |
| `applicability_scope` | 适用范围 |
| `provenance_refs` | 来源证据 |
| `release_status` | 发布状态 |

## 11.2 版本必须包含完整依赖信息

例如，能力包 v1.4 使用工具接口 v2，而当前环境已经升级到接口 v3。

系统不能仅因为能力包仍然标记为“已验证”，就直接在新环境中执行。

建议采用：

- 语义版本或明确的兼容版本；
- 依赖锁定；
- 输入输出契约测试；
- 版本兼容性检查；
- 迁移说明；
- 变更记录；
- 回滚方案。

能力版本变化后，应判断哪些测试需要重新执行。

如果修改只影响文档描述，不一定需要重新运行完整的端到端测试。

如果修改影响工具接口、执行顺序、权限或恢复逻辑，则需要更严格的验证。

# 十二、模型切换与环境变化：经验何时失效？

EvoAgent 支持不同专家使用不同模型，也支持模型切换后继续迭代。

这意味着，经验不能仅绑定在一个模型名称上，也不能假设所有经验在模型切换后都继续有效。

## 12.1 三类经验依赖

**模型弱相关经验。**

例如：

- 某个工具接口的字段定义；
- 文件格式规范；
- 已验证的确定性参数校验规则。

这类经验通常可以跨模型复用，但仍需检查工具和环境兼容性。

**模型行为相关经验。**

例如：

- 某个模型对特定提示词的响应方式；
- 特定模型容易出现的结构化输出问题；
- 模型在长上下文中的已知限制。

这类经验在模型切换后需要重新评估。

**环境强相关经验。**

例如：

- 某个 Android 版本的无障碍节点行为；
- 某个外部工具版本的调用限制；
- 某个 GPU 环境下的资源约束。

这类经验主要受环境变化影响，而不是单纯由模型版本决定。

## 12.2 建立重新验证触发器

以下事件应触发适当的经验有效性检查：

- 模型版本变化；
- 工具接口变化；
- 专家配置变化；
- 工作流版本变化；
- 操作系统或设备环境变化；
- 关键依赖升级；
- 原故障特征再次出现；
- 长期指标出现退化；
- 出现与已知经验相矛盾的案例；
- 能力包的安全策略发生变化。

并不是所有变化都要求所有知识重新验证。

系统应根据依赖图、经验适用范围和变更影响，选择需要重新检查的资产。

这样可以避免每次模型升级都重新运行所有测试，也可以避免关键依赖变化后继续盲目使用旧经验。

# 十三、知识冲突、过期与撤销

随着经验不断积累，系统必然会遇到知识冲突。

例如：

- 旧经验建议失败后重试；
- 新经验建议先检查状态，再决定是否重试；
- 某个专家认为应优先调用工具 A；
- 另一个专家在特定环境下发现工具 B 更稳定。

这些经验未必互相矛盾。

它们可能分别适用于不同的环境和任务。

因此，知识治理不能采用简单的“新知识覆盖旧知识”机制。

## 13.1 冲突处理顺序

建议依次检查：

1. 两条知识是否针对同一个问题；
2. 适用范围是否一致；
3. 前置条件是否一致；
4. 依赖版本是否一致；
5. 是否存在明确的优先级或例外规则；
6. 是否需要新的对照实验；
7. 是否应将两条知识拆分成不同的适用分支。

如果冲突无法解决，应将其标记为未决冲突，并限制自动迁移。

## 13.2 经验的生命周期操作

知识资产应支持：

- `retain`：继续保留；
- `update`：更新适用范围或内容；
- `supersede`：由新版本替代；
- `deprecate`：停止推荐新任务使用；
- `quarantine`：暂时隔离，等待进一步验证；
- `revoke`：撤销错误或有害知识的有效状态。

撤销经验时，还应检查它是否已经被用于：

- 专家提示词；
- 工作流模板；
- 工具参数；
- 路由规则；
- 自动化策略；
- 其他派生知识资产。

如果有，需要建立依赖追踪，确定哪些下游资产必须重新验证。

不能只从向量数据库中删除一条文本，就认为整条传播链已经被清理。

## 13.3 过期不等于错误

某项经验可能在原环境中完全正确，但随着工具或模型变化，不再适用。

因此，应区分：

- 内容本身错误；
- 原本正确但已经过期；
- 证据不足；
- 适用范围被缩小；
- 被更好的方案替代。

不同状态对应不同处理方式。

# 十四、知识治理与全局进化预算协同

知识沉淀本身也会消耗资源。

包括：

- 历史轨迹整理；
- 重复模式识别；
- 经验抽取；
- 知识验证；
- 向量索引更新；
- 工作流固化；
- 能力包回归测试；
- 失效资产检查。

如果系统不断抽取经验，却很少检索和复用，就可能形成大量低价值知识。

因此，知识治理也必须纳入 SEDG-IPGRA 的全局资源分配。

## 14.1 知识沉淀优先级

建议优先处理以下情况：

1. 严重故障或安全事件；
2. 高频重复失败；
3. 多个专家共同遇到的基础问题；
4. 已经反复成功、适合固化的工作流；
5. 能够显著减少重复模型调用的经验；
6. 影响长期稳定性的关键机制；
7. 具有明确验证证据的高价值改进。

对于一次性、低影响且难以复用的任务，不必强行生成长期知识资产。

原始事件可以按保留策略保存，但不必全部进入高成本的知识抽取流程。

## 14.2 衡量知识资产是否真正产生价值

建议记录：

- 被检索次数；
- 被采纳次数；
- 直接复用成功率；
- 适配后复用成功率；
- 失败与回滚次数；
- 节省的模型调用；
- 节省的运行时间；
- 减少的重复故障；
- 维护成本；
- 重新验证成本。

这些指标必须区分相关性与实际贡献。

例如，某项经验被检索了 1000 次，并不代表它产生了 1000 次收益。

系统应尽可能记录它是否被实际采纳、是否改变了执行方案，以及结果是否优于没有使用该经验时的合理基线。

知识复用的真实收益应反馈至 CARE-LBV 与 SEDG-IPGRA，用于决定是否继续维护该资产。

# 十五、工程目录与核心接口

建议新增以下模块：


# 十六、端到端验收场景

建议至少建立以下十二个验收场景。

## 场景 A：一次故障转化为可复用经验

**初始条件：** 代码专家多次遇到同类工具参数错误。

**验收过程：**

1. 从运行记录中识别故障模式；
2. 关联原始证据；
3. 建立根因假设；
4. 验证修复方案；
5. 明确适用范围；
6. 将经验发布到代码专家知识空间。

**验收重点：** 经验能够追溯到真实案例，并具有明确的验证状态。

## 场景 B：代码经验迁移到手机操作专家

**初始条件：** 手机操作专家出现类似的工具参数问题。

**验收过程：**

1. 检索代码专家的相关经验；
2. 比较工具契约和运行机制；
3. 识别可迁移的参数校验原则；
4. 重新设计目标工具适配；
5. 在隔离环境中进行验证；
6. 通过门禁后再发布目标能力。

**验收重点：** 迁移的是可复用机制，而不是未经审查的实现细节。

## 场景 C：错误诊断被反复引用

**初始条件：** 一条未经验证的根因假设被多个专家引用。

**验收过程：**

1. 检查原始证据；
2. 识别其仍处于假设状态；
3. 阻止自动晋级为通用知识；
4. 追踪相关派生记录；
5. 补充反向证据并修正知识状态。

**验收重点：** 引用次数不能自动提升知识可信度。

## 场景 D：一次成功任务转化为工作流

**初始条件：** AI 漫剧生成任务已经多次成功执行。

**验收过程：**

1. 归纳重复出现的稳定步骤；
2. 提取输入输出契约；
3. 建立任务 DAG；
4. 定义失败恢复与预算限制；
5. 执行端到端回归；
6. 生成版本化工作流候选。

**验收重点：** 工作流固化建立在可重复性和可验收性之上。

## 场景 E：新模型上线后重新验证经验

**初始条件：** 某专家切换了模型，但原有提示词经验仍在知识库中。

**验收过程：**

1. 检查经验的模型依赖；
2. 识别受影响的知识主张；
3. 对相关主张执行重新验证；
4. 保留仍然有效的经验；
5. 隔离失效的模型相关经验。

**验收重点：** 模型切换不会导致所有经验无条件失效，也不会让所有旧经验无条件继续生效。

## 场景 F：两个知识主张存在冲突

**初始条件：** 两条经验针对相似任务给出了不同执行策略。

**验收过程：**

1. 比较适用条件；
2. 检查环境和工具版本；
3. 判断是否可以通过范围划分解决；
4. 必要时建立对照实验；
5. 无法解决时标记未决冲突。

**验收重点：** 系统不会简单地让最新记录覆盖所有旧经验。

## 场景 G：经验已经过期

**初始条件：** 原有工具接口发生变化，旧经验开始导致调用失败。

**验收过程：**

1. 检测接口版本变化；
2. 根据依赖关系识别受影响知识；
3. 将相关经验标记为待重新验证；
4. 暂停不兼容的直接复用；
5. 完成适配和验证后更新资产版本。

**验收重点：** 系统能够根据实际依赖变化管理经验有效性。

## 场景 H：高相似度但不可迁移

**初始条件：** 某桌面自动化经验与手机操作任务语义相似。

**验收过程：**

1. 检索到相关经验；
2. 检查权限与外部副作用；
3. 发现原恢复策略不适用于手机操作；
4. 禁止直接迁移；
5. 只保留可借鉴的部分并重新设计方案。

**验收重点：** 语义相似度不能覆盖安全与环境兼容性要求。

## 场景 I：错误经验已经派生出多个能力资产

**初始条件：** 某条错误经验已经被多个提示词、规则和工作流引用。

**验收过程：**

1. 撤销原经验的有效状态；
2. 查询派生资产关系；
3. 识别受影响的能力；
4. 逐项重新验证或撤销；
5. 保留完整的变更记录。

**验收重点：** 撤销能够沿依赖关系传播，而不是只删除原始记录。

## 场景 J：知识库规模增长但复用价值下降

**初始条件：** 系统不断增加知识资产，但实际任务成功率没有改善。

**验收过程：**

1. 统计知识检索与实际采纳情况；
2. 检查无效和重复资产；
3. 评估维护与验证成本；
4. 调整知识抽取优先级；
5. 对低价值资产进行合并、归档或废弃。

**验收重点：** 知识库规模不被直接视为进化效果。

## 场景 K：工作流复用后出现局部失败

**初始条件：** 某个已验证工作流在新任务中遇到未覆盖的特殊情况。

**验收过程：**

1. 识别失败节点；
2. 检查工作流的适用范围；
3. 判断应当局部恢复还是退出工作流；
4. 记录新案例；
5. 在验证后决定是否扩展工作流分支。

**验收重点：** 工作流可以吸收新经验，但不会因为单个异常就被无条件整体修改。

## 场景 L：经验复用没有产生预期收益

**初始条件：** 系统检索并采纳了历史经验，但任务成本和成功率没有改善。

**验收过程：**

1. 记录实际采纳情况；
2. 对比合理的基线；
3. 检查经验是否适用；
4. 分析是否增加了额外步骤或模型调用；
5. 更新收益记录；
6. 决定继续使用、调整或废弃该经验。

**验收重点：** 被复用的经验必须根据实际结果持续评估，而不是永久视为有效。

# 十七、专项验收标准

SKEC-ETCR 至少需要满足以下要求：

1. 能够区分原始事件、故障模式、诊断知识、修复经验、策略、能力组件、工作流和反模式。
2. 能够建立具有完整来源和版本信息的经验记录。
3. 能够将事实、假设和未知信息分别记录。
4. 能够为每个重要知识主张关联支持证据和反向证据。
5. 能够根据知识类型采用不同的验证机制。
6. 能够防止单次偶然成功自动升级为正式能力。
7. 能够建立全局、专家、项目和可执行能力等不同知识空间。
8. 能够遵循专家独立记忆与显式共享的边界。
9. 能够区分知识检索权限与能力执行权限。
10. 能够识别重复故障模式并减少重复试错。
11. 能够使用结构化过滤、语义检索、依赖匹配和适用范围检查进行知识检索。
12. 能够为检索结果提供来源、验证状态、版本和限制条件。
13. 能够区分直接复用、适配后复用、启发式借鉴和禁止直接迁移。
14. 能够对迁移后的经验进行目标环境验证。
15. 能够阻止权限不兼容或风险不可接受的经验直接迁移。
16. 能够将重复成功的任务转化为规则、工具或工作流候选。
17. 能够为能力包记录输入输出契约、依赖、前置条件、失败模式和恢复策略。
18. 能够建立能力资产的版本管理与依赖锁定。
19. 能够在模型、工具、工作流或环境变化后识别需要重新验证的知识。
20. 能够区分过时、错误、证据不足和被替代的知识。
21. 能够检测知识冲突，并在无法解决时限制自动复用。
22. 能够撤销失效知识并追踪相关派生资产。
23. 能够记录经验复用的实际结果、成本和收益。
24. 能够识别被频繁检索但没有实际价值的知识资产。
25. 能够通过全局资源治理限制经验抽取、验证与索引的成本。
26. 能够与 CARE-LBV 共享收益验证记录。
27. 能够与 SEDG-IPGRA 协同安排知识治理优先级。
28. 能够与 EOACA 协同管理可执行能力及依赖关系。
29. 能够在 Windows、Android 和 mini Linux 环境下保持统一的知识标识和生命周期语义。
30. 能够在离线期间保存必要的经验记录，并在恢复连接后进行增量同步与冲突处理。
31. 能够通过重复案例测试验证经验抽取的可重复性。
32. 能够通过跨专家测试验证迁移边界。
33. 能够通过故障注入验证知识撤销与派生资产治理。
34. 能够通过模型切换测试验证经验重新验证机制。
35. 能够通过端到端任务测试验证知识复用是否真正减少重复成本。
36. 能够保证任何知识资产的发布都不自动绕过相应的执行权限与安全门禁。

以上为目标架构验收要求，不代表相关模块已经实现或通过测试。

# 十九、完成第六十九专项后，EvoAgent 获得了什么样的进化能力？

前三个专项分别解决了不同层次的问题。

| 专项 | 核心问题 |
|---|---|
| CARE-LBV | 如何证明某项改进真正有效？ |
| SEDG-IPGRA | 有限资源应该优先投入哪些改进？ |
| SKEC-ETCR | 已验证的经验如何转化为长期可复用的能力？ |

三者结合后，EvoAgent 的目标进化闭环将进一步扩展：

```text
真实任务运行
      ↓
发现问题与收集证据
      ↓
根因分析与候选修复
      ↓
全局优先级和预算分配
      ↓
隔离实验与独立评测
      ↓
验证修复效果和实际收益
      ↓
受控发布
      ↓
将有效结果沉淀为知识与能力资产
      ↓
检索与复用已验证经验
      ↓
在新任务、新环境中检查适用性
      ↓
记录复用收益与失效情况
      ↓
更新知识、能力与全局进化策略
```

这使 EvoAgent 不再需要把每次任务都当成完全独立的问题。

它可以优先寻找已经验证的解决方案，在适用条件满足时直接复用；在条件不同的时候进行适配和验证；在证据不足的时候重新实验；在发现原经验失效时撤销或修正。

但必须强调：知识沉淀不意味着系统能够自动获得无限的通用能力。它仍然受到模型能力、数据质量、工具可用性、评测覆盖率、环境变化和资源预算的限制。

真正的进步是减少不必要的重复试错，让已经得到验证的成果能够持续发挥作用。

# 二十、下一专项：自进化系统的可组合能力、动态工作流与跨专家协同执行体系

完成第六十九专项后，还存在一个更高层次的问题。

EvoAgent 已经拥有多个领域专家，也能积累和复用工具、规则与工作流。

但现实中的复杂任务往往不会严格属于单一专家。

例如，用户提出：

“帮我制作一部 45 秒的 AI 漫剧，先研究题材和受众，写脚本，生成角色与分镜，完成视频和配音，再合成、检查质量，最后整理项目文件。”

这个任务可能涉及：

- 信息检索专家；
- 内容创作专家；
- AI 漫剧专家；
- 图像与视频工具；
- 配音与音频处理能力；
- 文件管理工具；
- 质量验收模块；
- 预算与资源管理器。

如果把整个任务交给一个专家，它可能缺乏其他领域的专业能力。

如果简单地让所有专家轮流执行，又可能出现上下文丢失、重复工作、任务依赖不清晰、预算失控和结果验收不完整。

如果提前把所有流程固化成一个固定 DAG，又难以处理开放任务中的变化。

因此，下一专项需要解决的是：

**如何将经过验证的专家、工具、规则和工作流组合成一个可动态调整、可验证、可恢复、可追溯的跨专家执行系统？**

建议定义为：

**Composable Capabilities, Dynamic Workflow Orchestration & Cross-Expert Collaboration，简称 CCDWO-CEC。**

核心研究方向包括：

1. 如何建立统一的能力契约与调用协议；
2. 如何描述能力之间的输入输出、前置条件和后置条件；
3. 如何将多个领域专家组合成一个任务执行图；
4. 如何判断任务应由单个专家完成，还是需要跨专家协作；
5. 如何区分固定 DAG、动态 DAG 与开放式 Plan；
6. 如何在任务执行中根据实际结果调整工作流；
7. 如何保证专家之间的上下文交接准确；
8. 如何避免多个专家重复执行相同任务；
9. 如何解决专家之间对目标、约束和结果的理解不一致；
10. 如何在共享能力与专家私有能力之间建立安全边界；
11. 如何处理能力依赖、版本兼容与执行顺序；
12. 如何实现子任务失败后的局部恢复，而不是整个任务从头开始；
13. 如何协调多个专家之间的预算、并发与资源竞争；
14. 如何验证组合后的系统效果，而不只是分别验证每个专家；
15. 如何将经过多次验证的跨专家流程固化成可复用的组合能力；
16. 如何避免工作流编排器成为新的单点故障；
17. 如何在网络断联或某个专家不可用时降级执行；
18. 如何在 Android、Windows 和 mini Linux 等不同设备环境中调度能力；
19. 如何追踪跨专家任务的完整数据流、状态变化和责任归属；
20. 如何让组合能力既能动态适应复杂任务，又不会破坏已有稳定能力。

**核心原则：专家提供专业能力，ReAct 提供执行与观察循环，Plan 提供任务分解，DAG 表达依赖关系，工作流编排器负责协调执行，能力治理体系负责验证和复用。它们不是相互替代的系统，而是共同组成 EvoAgent 的任务执行架构。**

这一专项将进一步解决 EvoAgent 从“拥有多个独立专家”，走向“能够可靠组合多个专家完成复杂任务”的关键问题。
