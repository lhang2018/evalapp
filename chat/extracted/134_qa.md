# EvoAgent Mobile：Android 个人智能体产品与工程实施方案

我建议正式把这个项目定义为 **EvoAgent Mobile + EvoAgent Evolution Platform**：一个安装在 Android 手机上、能够理解自然语言、操作手机应用、完成多步骤任务，并通过独立进化系统持续提高可靠性的个人智能体。

你选择的四个方向，决定了产品的基本形态：

- **交互：** 语音入口 + 专属 App 双入口。
- **操作：** Android 原生接口 + 无障碍服务 + 视觉识别，按场景选择最可靠的方式。
- **自主程度：** 尽可能自动完成任务，但敏感操作、权限边界和安全门禁不能被模型自行取消。
- **网络：** 云端模型负责复杂理解与规划，本地负责应用启动、确定性操作、状态管理和基本恢复。

我会以一个明确的产品原则来设计：

> **前台智能体专注于稳定完成任务；后台进化系统专注于验证怎样做得更好。实验不能直接改变正在为你服务的稳定版本。**

这不是把原来的 EvoAgent 简单移植到手机，而是要重新设计执行内核、Android 权限体系、交互体验和版本发布机制。

### 第一版的验收任务

我建议先用以下任务作为真实手机上的验收集：

1. “打开设置。”——打开系统设置并验证前台应用。
2. “打开计算器，帮我计算 125 × 36。”——打开应用或调用可靠的计算能力，并核对结果。
3. “帮我找到某个应用的通知设置。”——定位设置页面，先不擅自改变状态。
4. “帮我总结当前屏幕上的内容。”——在用户明确触发且允许读取的情况下获取屏幕信息。
5. “帮我执行一个两到三步的操作。”——规划、执行、观察、恢复和验收。
6. 模拟网络断开、应用打不开、界面改变和工具异常——确保智能体不会陷入无限点击或无限重试。

这六类任务能验证真正重要的产品能力，而不是只证明大模型可以输出一段看起来合理的计划。

第一版暂不承诺任意第三方 App 的完整自动化，也不把支付、密码输入、验证码、发送消息等敏感动作默认设为完全自主。应当先验证技术能力、权限边界和可靠性，再逐步扩大范围。

# 九、一个必须提前解决的现实问题：Android 权限与应用分发政策

这部分我建议在写代码之前就做架构决策。

Android 技术上确实提供了 `AccessibilityService`，可以在用户启用后接收界面事件、读取允许访问的窗口节点，并执行部分节点操作或手势。界面节点也可能过时或发生变化，所以每次操作后仍然需要重新观察。<Cite refs={["turn454870search0","turn454870search3","turn454870search13"]}/>

但是，**技术上可实现，不代表可以不受限制地通过 Google Play 分发。**

Google Play 当前的 Accessibility API 政策对通用 AI 助手有一个重要限制：用于自动规划和执行操作的通用自动化助手，不会仅仅因为使用了无障碍服务就被视为合规的无障碍工具。若产品不是专为帮助残障用户设计的无障碍工具，就不能把 `isAccessibilityTool=true` 当作绕过限制的办法；还需要遵循相关声明、醒目披露、用户同意和用途限制。<Cite refs={["turn533801search0","turn533801search1"]}/>

因此，我建议采用两条产品路线：

<box border radius="lg" padding={3} gap={2}>
  <title size="md">路线 A：个人设备验证版</title>
  - 先在你自己的 Android 手机上安装调试 APK。
  - 优先实现 Intent、Deep Link、官方 API 和确定性的本地快捷操作。
  - 对无障碍能力进行独立技术验证，并明确授权、数据读取范围和用户可随时关闭的机制。
  - 不把私人设备上的可行性误认为已经满足应用商店分发要求。
  <divider/>
  <title size="md">路线 B：面向公众的产品版</title>
  - 将官方 API、系统接口、应用自有集成和用户明确触发的操作作为主要路径。
  - 无障碍服务只在产品用途和适用政策允许的范围内使用。
  - 对不允许自动化的应用，提供跳转到目标页面、显示操作指引或请求用户接管的降级方式。
  - 在开发阶段就完成分发政策审查，而不是等到上架时才处理。
</box>

另外，Android 12 及更高版本对后台启动前台服务有明确限制；Android 14 及更高版本还要求相应服务类型和权限。不能把“手机上一直有一个后台 AI 服务”当成不需要设计的默认条件。<Cite refs={["turn454870search2","turn454870search6","turn454870search7"]}/>

第一版因此采用**用户主动启动任务、任务执行期间清楚显示状态、支持随时停止**的设计。后续再按实际需求决定是否增加语音快捷入口、前台服务或系统支持的其他交互方式。

这条路线既能在个人设备上验证核心能力，也不会从一开始就把整个产品押注在一种可能受到分发政策限制的自动化手段上。

### 2. 应用启动模块

对于明确要求打开某个应用的任务，先走原生 Intent，而不是调用大模型识别屏幕。

例如：

<CodeBlock language="kotlin" editable>
class AppLauncher(private val context: Context) {

    fun launch(packageName: String): Boolean {
        val intent = context.packageManager
            .getLaunchIntentForPackage(packageName)
            ?: return false

        return try {
            intent.addFlags(Intent.FLAG_ACTIVITY_NEW_TASK)
            context.startActivity(intent)
            true
        } catch (e: ActivityNotFoundException) {
            false
        } catch (e: SecurityException) {
            false
        }
    }
}
</CodeBlock>

实际工程还需要导入 Android 对应的类、记录错误原因，并区分应用不存在、未安装、没有可启动入口和启动被系统拒绝等情况。

Android 11 及以上对应用包可见性进行了限制，所以应用发现能力应使用尽可能窄的包查询声明，而不是默认申请访问所有已安装应用的权限。直接启动某些已知应用和查询全部应用列表是两件不同的事。<Cite refs={["turn454870search10"]}/>

产品上可以先提供一个“已授权应用列表”，由你选择允许 EvoAgent 操作哪些应用。这样也能避免仅凭相似名称就打开错误软件。

## 十一、意图识别：从用户的话变成可以执行的任务

我建议使用两阶段识别，而不是让大模型直接输出一串点击动作。

### 第一阶段：轻量意图路由

本地先判断任务是否属于已知的确定性操作：

- 打开某个应用。
- 打开 EvoAgent 的某个页面。
- 查询本地任务状态。
- 执行已经定义好的快捷流程。
- 需要复杂规划的通用任务。

例如，“打开设置”可以直接匹配已定义的系统操作，不必调用云端模型。

### 第二阶段：复杂任务结构化解析

对于复杂请求，让云端模型返回经过 Schema 校验的任务对象。

<CodeBlock language="kotlin" editable>
data class IntentResult(
    val intent: String,
    val targetApp: String?,
    val entities: Map<String, String>,
    val constraints: List<String>,
    val requiresClarification: Boolean,
    val riskLevel: String,
    val successCriteria: List<String>
)
</CodeBlock>

这份对象不能直接控制手机。它只是一个经过校验的意图描述，之后还需要：

1. 校验目标是否明确。
2. 检查目标应用是否允许访问。
3. 生成可执行的计划。
4. 检查每个动作是否在授权范围内。
5. 执行后验证结果。

### 意图识别的产品规则

- **确定性高、风险低：** 直接执行。
- **目标不明确：** 先澄清。
- **执行路径不确定：** 先观察当前状态，再规划。
- **高风险或不可逆：** 必须经过专门的授权流程。
- **模型离线：** 仅执行本地已支持的操作；不能假装复杂意图也已经可靠识别。

这会比单纯追求模型的意图分类准确率更实用，因为真正的成功标准是任务能否被正确、安全地执行。

## 十二、手机端 ReAct 循环：每一步都必须观察真实状态

手机上的 ReAct 和普通聊天 Agent 有一个本质区别：执行动作会改变真实设备状态。

因此，不能让模型一次生成 20 个点击坐标，然后连续执行。正确做法是每次执行一个有明确前置条件的动作，再观察界面，判断下一步是否仍然成立。

<CodeBlock language="text" editable={false}>RECEIVED
   ↓
PARSE_INTENT
   ↓
CHECK_PERMISSION
   ↓
PLAN_TASK
   ↓
OBSERVE_SCREEN
   ↓
SELECT_ACTION
   ↓
VALIDATE_ACTION
   ↓
EXECUTE_ONE_ACTION
   ↓
OBSERVE_NEW_STATE
   ↓
VERIFY_STEP
   ├── success → next step
   ├── recoverable error → recovery manager
   ├── uncertain state → stop and ask
   └── target reached → verify final result
   ↓
COMPLETE / FAILED / NEEDS_USER
</CodeBlock>

核心引擎可以先写成下面这种 Kotlin 结构：

<CodeBlock language="kotlin" editable>
suspend fun executeTask(task: Task): TaskResult {
    var state = observer.observe()
    var stepCount = 0

    while (stepCount < task.maxSteps) {
        if (task.cancelled) {
            return TaskResult.Cancelled
        }

        val next = planner.nextAction(task, state)
            ?: return verifier.verifyFinal(task, state)

        val decision = actionGuard.check(next, state)

        when (decision) {
            is GuardDecision.Deny ->
                return TaskResult.Blocked(decision.reason)

            is GuardDecision.RequireApproval -> {
                if (!approvalManager.confirm(decision)) {
                    return TaskResult.NeedsUser(decision.reason)
                }
            }

            GuardDecision.Allow -> Unit
        }

        val result = executor.execute(next)

        eventStore.record(task.id, next, result)

        if (!result.success) {
            val recovery = recoveryManager.recover(task, state, result)
            if (!recovery.canContinue) {
                return TaskResult.Failed(recovery.reason)
            }
        }

        state = observer.observe()
        if (!verifier.stepSucceeded(next, state)) {
            return TaskResult.NeedsUser(
                "无法可靠确认操作结果"
            )
        }

        stepCount++
    }

    return TaskResult.Failed("超过最大执行步数")
}
</CodeBlock>

这是核心流程示意，完整工程还需要实现协程取消传播、超时、持久化、异常捕获、状态机校验和具体的观察器与执行器。

### ReAct 的关键设计

**第一，计划和执行分离。** 模型可以建议操作，但最终是否允许执行，由独立的 `ActionGuard` 决定。

**第二，每一步都重新观察。** 不能假定上一步执行成功，也不能使用已经失效的界面节点。

**第三，限制恢复次数。** 同一个失败动作不能无限重试；重复失败时，应转入备用路径或要求用户介入。

**第四，任务状态需要持久化。** App 切到后台、进程被系统回收或网络中断时，应该能恢复任务状态，而不是从头重复执行。

**第五，停止也是一种正确结果。** 当系统不能确认当前页面、操作对象或执行结果时，安全停止优于继续猜测。

## 十三、无障碍服务和视觉识别如何配合？

我建议建立一个统一的 `ScreenObserver`，对外只提供标准化的界面状态，而不让任务规划器直接依赖某种底层实现。

例如：

<CodeBlock language="kotlin" editable>
data class ScreenState(
    val packageName: String?,
    val pageDescription: String?,
    val nodes: List<UiNode>,
    val observedAtMillis: Long,
    val source: ObservationSource,
    val confidence: Float
)

data class UiNode(
    val text: String?,
    val contentDescription: String?,
    val resourceId: String?,
    val className: String?,
    val clickable: Boolean,
    val enabled: Boolean,
    val bounds: Rect
)

enum class ObservationSource {
    ACCESSIBILITY,
    VISION,
    NATIVE_API
}
</CodeBlock>

执行策略按照以下优先级选择：

1. 官方 API 或原生接口能够完成的操作，优先使用。
2. 有可靠语义节点时，优先使用无障碍节点的明确操作。
3. 只有在授权且确实需要时，才考虑视觉识别与坐标操作。
4. 页面无法识别或置信度不足时，停止自动执行。

无障碍服务应负责观察系统回调、读取允许访问的节点和执行被授权的操作；视觉模块负责将图像转化为候选控件和页面描述；`ActionGuard` 则负责决定能不能执行。

这样，未来即使更换视觉模型或无障碍实现，ReAct 引擎也不需要重写。

### 一个非常重要的安全细节

不能因为模型认为按钮是“确定”，就直接点击它。应检查按钮的文本、所在页面、操作类型、当前任务授权以及前置状态。

例如，打开一个设置页面和关闭一个账户，虽然都可能只需要点击一次，但两者的风险完全不同。

对于无法可靠区分的界面，应该要求用户确认，而不是让视觉模型猜测。

## 十四、稳定版本和后台进化轨道：手机产品最核心的工程机制

我会将版本管理分为两个独立层面：

- **软件版本：** Android APK、Agent Core、工具实现和数据库结构。
- **能力配置版本：** 模型 ID、提示词、上下文策略、工具路由和已经验证的任务模板。

这两类版本的发布机制不同。不能为了调整一段提示词，就重新构建整个 APK；也不能把不兼容的核心代码当作普通配置直接下发。

### 1. 稳定轨道的目录与职责

<CodeBlock language="text" editable={false}>stable/
├── mobile-release/
│   ├── app-version
│   ├── core-version
│   └── database-schema-version
│
├── agent-profile/
│   ├── model-profile
│   ├── prompt-profile
│   ├── context-policy
│   └── tool-routing-policy
│
├── task-capabilities/
│   ├── app-launch
│   ├── device-settings
│   └── approved-workflows
│
└── release-manifest.json</CodeBlock>

稳定轨道只加载经过验证的版本。任务执行过程中，不能中途切换模型策略或更新工具配置，否则同一个任务可能前后使用不同的行为规则。

### 2. 后台进化轨道

<CodeBlock language="text" editable={false}>evolution/
├── observations/
├── issue-reports/
├── tool-health/
├── candidate-profiles/
├── isolated-tests/
├── regression-reports/
├── promotion-decisions/
└── release-candidates/</CodeBlock>

进化系统不直接操作稳定版的内存状态，而是生成带有版本号、依赖条件和测试证据的候选资产。

这里建议把更新分为三个等级：

| 更新类型 | 例子 | 发布策略 |
|---|---|---|
| L1：配置更新 | 温度、上下文预算、非敏感提示词 | 自动评测通过后可自动发布 |
| L2：能力策略更新 | 工具路由、页面识别策略、任务模板 | 更严格的回归与兼容性检查，必要时小范围试运行 |
| L3：核心软件更新 | ReAct 内核、无障碍服务、权限机制、数据库迁移 | 独立构建和测试，保留明确的升级与恢复路径 |

手机端不要允许远程进化服务随意下载并执行新的可执行代码。Android APK 更新应走受支持的安装与签名机制；能力配置则使用严格的 Schema、签名清单和兼容性校验。

特别要注意：**签名和完整性校验只能证明更新来源与内容完整性，不能证明更新本身正确。** 还需要独立测试、版本兼容性检查和发布后监控。

### 4. 进化系统如何知道该优化什么？

它不应该简单按照“出现问题的次数”排序。

我建议问题优先级综合考虑：

- 对用户任务成功率的影响。
- 发生频率与影响范围。
- 安全严重程度。
- 是否可以稳定复现。
- 修复成本和实验成本。
- 修复后能否用独立测试验证。

例如，一个每天发生多次的工具超时问题，可能比一个罕见的提示词格式问题更值得优先处理。

但如果某个低频问题涉及敏感数据泄露或未经授权操作，即使频率低，也必须优先处理。

## 十五、手机端与进化平台之间的数据协议

手机端不应该把整块屏幕、所有用户操作和全部聊天记录无差别上传到服务器。

我建议采用“任务数据”和“诊断数据”分离的协议。

### 任务执行请求

<CodeBlock language="json" editable={false}>{
  "protocol_version": "1.0",
  "task_id": "task-uuid",
  "profile_version": "profile-0.1.0",
  "intent": {
    "name": "launch_app",
    "target": "settings"
  },
  "constraints": {
    "offline_allowed": true,
    "max_steps": 5,
    "allow_sensitive_actions": false
  },
  "success_criteria": [
    "target_app_in_foreground"
  ]
}</CodeBlock>

这是内部协议示例。真实请求不需要把用户的全部历史聊天或手机全部已安装应用列表都传给模型。

### 运行事件

每个执行步骤应记录：

- 任务 ID、稳定版本和能力配置版本。
- 当前阶段、使用的工具和执行结果。
- 失败分类、恢复次数、耗时和必要的质量指标。
- 是否请求用户授权，以及授权结果。
- 最终验收是否通过。

原始屏幕截图、消息内容和敏感文本默认不应进入后台日志。只有在明确授权且确有诊断必要时，才允许上传经过范围限制和脱敏的材料。

### 后台进化平台接口

第一版可以设计以下 API：

| 接口 | 作用 |
|---|---|
| `POST /v1/tasks/plan` | 获取复杂任务的结构化计划 |
| `POST /v1/runs/events` | 上传允许记录的运行事件 |
| `POST /v1/evaluations` | 上传任务验收结果 |
| `GET /v1/profiles/current` | 获取当前稳定能力档案 |
| `GET /v1/releases/latest` | 查询适用于当前客户端的候选更新 |
| `POST /v1/releases/ack` | 确认更新激活或上报回滚结果 |

这些是建议的 API 契约，不代表服务端已实现。

还应增加设备认证、请求签名或适当的身份验证机制、重放保护、限流、版本兼容检查和隐私保留策略。更新接口不能仅凭客户端请求就接受任意候选配置。

## 十六、第一版数据库怎么设计？

Android 端建议使用 Room，而不是直接把服务端 SQLite 数据库搬到手机里。手机端保存必要的本地状态，服务器端保存跨任务分析和实验数据。

| 数据表 | 关键字段 | 主要用途 |
|---|---|---|
| `tasks` | `task_id`、`intent`、`status`、`profile_version` | 任务状态与恢复 |
| `task_steps` | `task_id`、`step_index`、`action_type`、`result` | 每一步执行记录 |
| `runtime_events` | `event_id`、`task_id`、`event_type`、`timestamp` | 运行诊断与回放 |
| `tool_registry` | `tool_id`、`version`、`risk_level`、`enabled` | 工具能力和授权范围 |
| `tool_health` | `tool_id`、`health_state`、`error_rate` | 工具异常检测 |
| `agent_profiles` | `profile_id`、`version`、`model_id`、`manifest_hash` | 稳定能力档案 |
| `release_history` | `release_id`、`previous_version`、`status` | 更新和回滚 |
| `approvals` | `task_id`、`action_id`、`decision`、`timestamp` | 高风险操作授权 |

其中 `approvals` 非常重要。用户确认的应该是明确的操作内容，而不是一个笼统的“允许 Agent 做任何事”。

例如，授权“发送这条消息给这个联系人”不应自动授权发送其他消息，也不应允许模型修改授权规则。

## 十九、我建议第一版明确不做什么

为了避免项目越做越复杂，第一版暂不实现：

- 全时段、无条件后台语音监听。
- 不受限制地操作所有第三方应用。
- 自动处理支付、密码、验证码和其他高风险操作。
- 让云端模型直接向手机下发任意代码并执行。
- 在任务运行过程中热切换核心策略。
- 未经测试就自动更新 APK 或修改系统权限。
- 为了追求“持续进化”，而让稳定版频繁变化。

这些不是说未来永远不能增加相关能力，而是必须先证明必要性、技术可行性和安全性，再逐步开放。

## 二十、下一步应该直接进入工程实现

我的建议是先建立一个独立的 Android 工程，完成 **M0 + M1 的真实设备验证**，然后再实现 M2 的屏幕观察与受控操作。

这个顺序有两个好处：

1. 先证明手机端能正确接收意图、调用云端模型并启动应用，避免一开始就陷入无障碍服务、视觉识别和系统权限的复杂问题。
2. 先把任务协议、日志和权限模型设计好，后面增加 ReAct、界面识别、工具自检和进化平台时，就不必推倒重来。

第一版的核心成功标准不是它能控制多少应用，而是：

**当你对手机说一句话时，它能正确理解你想做什么，选择合适的执行路径，在授权范围内完成操作，并且能够证明操作成功；一旦失败，它知道如何停止、恢复和记录问题。**

这才是 EvoAgent 从一个技术概念，真正变成每天可以使用的个人智能体的起点。
