这一步我们要做一个关键收敛：**冻结首发产品的交付范围，但不冻结 EvoAgent 的长期进化目标。**

这两个概念必须分开。我们仍然保留完整的个人通用智能体、多领域专家、主动帮助和持续进化体系；但首发产品不能因为追求所有能力同时成熟，而一直停留在设计阶段。

还有一条必须写进发布规则：**核心任务质量、执行效率和稳定性优先于主动智能和后台进化。** 任何新功能都必须证明它不会破坏这三个基础指标。

<WritingBlock id="84621" variant="document"># EvoAgent 首发产品范围冻结与发布门禁

**文档编号：** EA-REL-005  
**版本：** 1.0  
**文档类型：** 产品范围控制、发布准入与稳定性治理规范  
**适用范围：** EvoAgent Android 首发产品、共享执行内核、领域专家、主动智能与后台进化系统。

## 一、范围冻结的目的

EvoAgent 已经形成较完整的长期产品方向。当前最大的项目风险，不是缺少更多想法，而是不断增加设计和技术专项，却迟迟无法明确一个真正可用的产品应该具备什么、何时交付、依据什么宣布完成。

因此，本文件确立三个原则。

1. **长期愿景保持完整。** 不因为首发范围有限，就放弃多领域专家、主动智能、受控自主和持续进化。
2. **首发范围明确冻结。** 开发过程中新增需求必须经过评估，不能随意插入首发版本。
3. **发布必须有证据。** 只有真实运行、实际验收和发布门禁通过，才能宣布首发可用。

范围冻结不是停止开发，而是让开发围绕明确的产品目标持续推进。

## 二、首发产品的定义

首发产品必须能够在 Android 手机上提供一个真实可用的个人智能体入口。

用户能够通过文字或已经接入的语音能力提出任务，系统使用真实配置的模型和实际可用的工具执行工作，跟踪任务状态，检查结果，交付成果，并在失败时进行可控恢复。

同时，系统必须具备基本的运行记录和质量改进机制，确保后续优化有真实证据可用。

### 2.1 首发产品必须交付的四项价值

| 价值 | 用户能够实际体验到的结果 |
|---|---|
| 任务完成 | 不只是给建议，而是在支持范围内真正执行并交付 |
| 结果可信 | 能检查实际结果，不把模型自述当作完成证据 |
| 执行可控 | 有明确的状态、预算、授权、取消和失败处理 |
| 持续改善 | 能记录运行问题、开展评测，并验证候选改进是否有效 |

### 2.2 首发不代表所有领域能力成熟

首发产品可以只开放经过验证的一组能力，但必须明确告诉用户哪些能力可用、哪些依赖外部服务、哪些尚未开放。

例如，编程、手机操作和 AI 漫剧可以继续沿用统一任务内核，但各自的专业工具、工作流和验收规则应分阶段开放。

不能因为架构中预留了某个专家的接口，就宣称对应的专业能力已经交付。

## 三、首发范围冻结清单

### 3.1 必须交付：P0

以下能力属于首发产品的硬性范围。

| 编号 | 能力 | 首发要求 | 不满足时的处理 |
|---|---|---|---|
| R01 | 统一任务入口 | 可以创建和追踪真实任务 | 阻止发布 |
| R02 | 基础任务理解 | 能识别目标、约束和必要的澄清条件 | 阻止发布 |
| R03 | 真实模型接入 | 使用实际配置的模型服务，而非仅靠模拟响应 | 阻止发布 |
| R04 | 基础工具执行 | 至少有一组真实、注册且可验证的工具 | 阻止发布 |
| R05 | 任务状态管理 | 状态合法、可持久化、可追溯 | 阻止发布 |
| R06 | 结果验收 | 能根据任务类型检查实际结果 | 阻止发布 |
| R07 | 成果交付 | 至少一条真实任务链可以交付可使用的成果 | 阻止发布 |
| R08 | 失败与取消 | 有停止、错误说明和安全恢复机制 | 阻止发布 |
| R09 | 预算与权限 | 资源上限有效，受保护动作遵守授权规则 | 阻止发布 |
| R10 | 运行记录 | 能关联任务、运行、配置版本和错误 | 阻止发布 |
| R11 | Android 基础体验 | 可以安装、启动、输入任务并查看结果 | 阻止发布 |
| R12 | 基础质量评测 | 有固定测试集、实际测试报告和回归机制 | 阻止发布 |
| R13 | 进化基础闭环 | 能从运行问题形成候选，并通过独立评测决定是否准入 | 阻止发布 |

这里的“进化基础闭环”要求系统至少具备问题记录、候选管理和独立评测的可验证链路。**首发并不要求立即开放无人监督的自动生产发布。** 自动发布低风险改进是后续能力，必须建立在发布门禁已经经过验证的基础上。

### 3.2 首发允许简化的能力

以下能力可以采用基础实现，但不能破坏核心任务质量。

- 简单的聊天与工作模式切换；
- 基础任务历史；
- 基础文件交付；
- 简单的项目状态记录；
- 有限的专家注册和路由；
- 少量已经验证的工作流；
- 基础诊断日志和手动导出；
- 云端优先的模型调用；
- 明确范围内的离线缓存与恢复。

允许简化的是交互复杂度和开放范围，而不是安全、正确性和结果验收。

### 3.3 首发可以关闭的能力

| 能力 | 首发策略 | 开放条件 |
|---|---|---|
| 高频主动提醒 | 默认关闭或严格限制 | 主动价值和误打扰评测通过 |
| 自动整理所有近期对话 | 不默认开放 | 数据范围、授权和纠错机制完善 |
| L3 高自主执行 | 不默认开放 | 具体能力具有可靠的权限和停止机制 |
| 自动修改生产提示词 | 关闭 | 候选评测、发布隔离和回滚通过 |
| 自动升级所有专家 | 关闭 | 逐专家具备兼容性和回归门禁 |
| 任意 Android 应用操作 | 不作全面承诺 | 每类操作经过独立授权与实际状态验证 |
| 全自动编程与代码提交 | 按实际能力开放 | 测试、审查、权限和变更回滚机制通过 |
| 全自动 AI 漫剧生产 | 按实际能力开放 | 真实生成链路、预算控制和产物验收通过 |
| 多设备统一运行 | 后续扩展 | 对应设备适配和兼容性测试通过 |

这些功能没有被从长期产品路线中删除，只是不能成为首发交付的阻塞条件。

## 四、首发必须打通的真实任务链

首发不能只证明 App 能启动、模型能回答或某个工具能单独工作。

必须至少有一条完整的端到端任务链。

建议使用“资料整理并生成报告”作为第一条主验收链。

### 4.1 正常执行路径

1. 用户提交任务和必要资料。
2. 系统建立任务记录与验收契约。
3. 系统调用真实模型并执行必要的资料处理工具。
4. 系统保存运行状态和关键事件。
5. 系统生成实际文件。
6. 独立验收器检查文件和内容是否符合要求。
7. 系统交付成果并展示验收状态。
8. 系统记录本次运行结果，供后续质量分析使用。

### 4.2 必须覆盖的异常路径

同一任务链还必须测试：

- 输入资料不完整；
- 模型服务超时；
- 工具执行失败；
- 预算耗尽；
- 用户取消；
- 应用中途退出；
- 结果验收失败；
- 文件生成失败；
- 网络中断；
- 运行状态无法确认。

系统可以报告部分完成，但不得用部分完成冒充全部成功。

### 4.3 首发任务链的验收证据

每次正式验收运行至少保存：

- 任务与运行标识；
- 使用的模型和工具配置；
- 实际执行结果；
- 关键状态变化；
- 实际生成的产物；
- 验收规则及结果；
- 错误、恢复与预算记录；
- 对应的测试版本。

没有这些证据，就不能据此宣称任务链已经通过正式验收。

## 五、发布门禁：七道必须通过的关卡

发布门禁不是一个综合分数。每一道门禁都有自己的否决权，关键安全问题不能被其他指标的提升抵消。

### G0：构建与安装

必须证明：

- Android 工程可以按规定流程构建；
- 应用能够安装和启动；
- 必需配置与外部依赖明确；
- 基础入口和任务界面可用。

**失败处理：** 不进入后续产品验收。

### G1：核心任务质量

必须证明：

- 固定评测集中的任务达到预先设定的质量目标；
- 关键约束得到保留；
- 实际产物满足验收要求；
- 不合格结果不会被标记为成功。

首轮可将简单、低风险、范围明确的任务集成功率目标暂定为不低于 85%，但应在正式试运行前冻结任务集、样本和评分规则。这个数字是建议的初始目标，不是当前系统已达到的成绩。

复杂开放式任务应另行分层评测，不能与简单任务混合计算。

**失败处理：** 修复问题或缩小开放能力范围，不允许通过降低验收标准掩盖退化。

### G2：安全与权限

以下属于硬性门禁：

- 未授权的高风险动作：0 次；
- 未注册工具被执行：0 次；
- 已知越权路径未被拦截：0 次；
- 未验证的外部操作被伪装成成功：0 次。

测试必须覆盖授权拒绝、权限撤销、任务目标变更和动作状态不确定等情况。

**失败处理：** 直接阻止发布，不允许用质量或效率提升抵消安全缺陷。

### G3：稳定性与恢复

必须证明：

- 取消操作能够按规定停止新增动作；
- 超时和预算限制有效；
- 进程重启后能够恢复已保存状态；
- 未知外部副作用状态不会被盲目重放；
- 部分完成、失败和成功状态可以正确区分。

**失败处理：** 修复状态机、幂等处理或恢复策略后重新测试。

### G4：效率与成本

必须记录：

- 单次成功任务的实际成本；
- 模型和工具调用次数；
- 任务完成时间；
- 重试和恢复成本；
- 不同任务类别的资源分布。

初次发布可以先建立基线，但必须在发布前确定预算上限和超限行为。后续优化必须与明确基线比较，不能仅凭“调用更少”或“速度更快”就宣称效果更好。

**失败处理：** 超出硬性预算的任务必须安全停止；不能通过跳过必要验收换取速度。

### G5：后台非干扰

必须在后台评测或诊断运行期间执行并行核心任务测试。

验收要求：

- 后台使用独立资源配额；
- 核心任务具有更高的执行优先级；
- 资源紧张时后台可以暂停、降级或取消；
- 后台失败不会改变核心任务状态；
- 候选版本不能直接替换正在执行任务的关键配置。

**失败处理：** 关闭相关后台功能，直到隔离机制通过测试。

### G6：版本、发布与回滚

必须证明：

- 每次运行的关键配置可以追溯；
- 候选版本与稳定版本隔离；
- 评测门禁独立于候选版本；
- 未通过门禁的候选不能激活；
- 已发布版本可以回滚；
- 回滚后能够恢复稳定配置。

**失败处理：** 保持当前稳定版本，不允许候选覆盖生产配置。

### G7：产品可用性与运维准备

必须证明：

- 用户知道任务处于什么状态；
- 用户能找到实际成果；
- 失败时有清晰说明和后续选项；
- 关键配置、权限和外部依赖有说明；
- 存在基本的诊断与问题导出机制；
- 已知限制明确记录；
- 发布版本有可复现的测试报告。

**失败处理：** 不宣布首发完成；补齐交付、诊断或用户体验缺口。

## 六、稳定执行与后台进化的发布关系

EvoAgent 应采用稳定执行轨道与后台进化轨道分离的方式。

### 稳定执行轨道

负责当前用户任务，使用已经批准的模型配置、工具版本、专家、工作流和策略。

### 后台进化轨道

负责分析运行问题、生成候选、运行评测、比较版本和准备发布。

两个轨道可以共享必要的只读运行记录，但不能共享无约束的生产写权限。

后台候选的发布顺序必须是：

**问题证据 → 根因假设 → 候选改进 → 独立评测 → 安全与兼容性门禁 → 发布审批或受控自动准入 → 健康观察 → 保留或回滚。**

只有明确满足预设条件的低风险改进，才能考虑自动准入。权限策略、核心安全规则、评测门禁和发布控制机制不得被候选自行修改。

## 七、首发后的能力开放计划

首发不是最终形态。发布后按照实际用户价值和测试证据扩展。

| 阶段 | 开放内容 | 开放前提 |
|---|---|---|
| R1：首发可用版 | 真实任务闭环、基本验收、失败恢复、运行追溯 | G0—G7 全部通过 |
| R1.1：可靠性增强 | 更完整的项目状态、恢复能力、稳定工作流 | 回归测试与兼容性通过 |
| R1.2：个人效率增强 | 项目整理、L1 完成后增强、有限主动建议 | 非阻塞和主动价值评测通过 |
| R1.3：持续改进增强 | 自动候选生成、隔离评测、受控低风险发布 | 候选隔离、发布与回滚门禁通过 |
| R2：领域扩展 | 编程、旅游、手机操作、AI 漫剧等能力包 | 各领域专用验收通过 |
| R3：跨端扩展 | Windows、其他设备与个人服务器协同 | 跨端契约与兼容性验证通过 |

阶段名称用于表达交付顺序，不代表已有版本或功能已经完成。

## 八、范围变更规则

首发范围冻结后，新增需求只能通过明确的变更流程进入。

### 允许直接纳入的变更

- 修复安全缺陷；
- 修复核心任务质量问题；
- 修复稳定性和数据完整性问题；
- 修复导致首发验收失败的问题；
- 满足必要的法律、隐私或平台要求。

### 需要评估后再决定的变更

- 新增领域专家；
- 新增复杂主动智能；
- 新增自动执行权限；
- 新增跨设备能力；
- 新增大型后台优化流程；
- 大幅调整模型或工具架构。

每项变更都必须回答：

1. 解决哪个真实用户问题？
2. 为什么不能在首发后实施？
3. 会影响哪些现有能力？
4. 是否增加外部依赖、成本或权限？
5. 需要重跑哪些回归测试？
6. 如果失败，如何回滚？

如果无法证明新增功能对首发可用性具有必要价值，应当进入后续路线，而不是挤占首发交付资源。

## 九、发布前必须具备的交付包

首发发布不仅需要 App 安装包，还需要一组能够复现和维护产品的交付资料。

1. Android 可安装构建产物；
2. 实际依赖与配置说明；
3. 核心任务端到端测试报告；
4. 固定评测集及版本记录；
5. 安全、权限和恢复测试结果；
6. 资源使用和成本基线；
7. 已知限制与暂未开放的能力清单；
8. 运行诊断与日志导出说明；
9. 稳定版本标识及回滚操作说明；
10. 发布决策记录和未解决问题清单。

交付包中的每个状态都必须反映真实情况。测试尚未运行时标记为未测试；存在外部依赖时明确说明；没有验证过的能力不得标记为正式支持。

## 十、首发发布决策表

正式发布时，应由实际证据决定结果。

| 决策项 | 判定方式 |
|---|---|
| 构建和安装 | 必须通过 |
| 核心任务质量 | 达到预先冻结的目标 |
| 高风险动作与权限 | 硬性门禁全部通过 |
| 任务取消和恢复 | 关键异常场景通过 |
| 成本与预算 | 限制有效且超限行为正确 |
| 后台非干扰 | 并行负载测试通过 |
| 版本隔离与回滚 | 端到端验证通过 |
| 用户交付体验 | 真实成果能够查看和使用 |
| 文档与运维准备 | 必需交付资料齐全 |

任何硬性门禁失败，都不能通过计算综合平均分来放行。
