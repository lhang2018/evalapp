## 用户

就是说服务端优化是吧，那如果服务端离线或者app离线，使用过程中遇到问题怎么办呢。

## ChatGPT

对，**主要的深度优化放在服务端，但手机端必须具备独立运行、故障恢复和问题记录能力。** 不能因为服务端离线，EvoAgent 就失去工作能力；也不能因为手机离线，就丢失运行中遇到的问题。

这恰好是架构冻结前必须解决的一个问题。我建议把它设计成：**双端独立运行、问题本地闭环、联网后协同进化。**

## 一、先区分三种离线情况






      **情况 A：服务端离线，手机有网**

      继续运行

      手机端继续使用已安装的稳定版本、可用的云端模型 API、已批准的工具和工作流。无法访问服务端进化中心时，本地缓存问题记录，暂不进行需要服务端的深度优化。

      注意：如果模型 API 也不可用，就需要切换到本地模型或进入降级模式。








      **情况 B：手机完全离线**

      本地降级运行

      使用端侧规则、离线任务、已安装的工作流和必要的本地模型完成可离线任务。遇到依赖云端模型、在线搜索或外部服务的任务，则明确告知用户当前限制，不假装已经完成。

      本地继续保存日志、任务状态、错误证据和待同步事件。








      **情况 C：模型 API、工具或其他依赖故障**

      故障隔离与恢复

      手机端先判断失败原因，执行有限重试、切换已经验证的备用路径、恢复检查点或安全停止。不会因为一次失败就无限重试，也不会擅自扩大权限。

      如果当前问题无法修复，就保留现场与证据，等待联网后交给进化系统继续诊断。



这里要特别注意：服务端离线和模型 API 离线是两回事。服务端负责深度进化，并不意味着每次执行任务都必须经过它。

## 二、遇到问题时，手机端自己能做什么？

我建议手机端内置一个轻量级的**本地故障处理器**。它不负责无限制地修改自身，而是先尽可能安全地解决当前问题。

例如，用户让它打开 App 并完成某个操作，结果操作失败。

手机端按照以下顺序处理：



    **第一步：重新观察**

  重新读取当前页面、应用状态、工具返回和任务检查点，判断是不是状态识别错误。



    **第二步：尝试已知恢复方案**

  例如重新定位控件、重新获取页面状态、对临时网络故障进行有限重试，或使用已批准的备用工具。



    **第三步：选择已有稳定策略**

  在兼容性已经验证的前提下，切换到备用模型、工具或工作流。离线时不能临时下载并执行未经验证的代码。



    **第四步：记录无法解决的问题**

  保存错误类型、执行轨迹、当前状态、尝试过的恢复方案和最终结果，供之后诊断。

如果问题依然无法解决，手机端应该停止危险操作，并在可能的情况下保存检查点，而不是不断试错。

**关键区别是：手机端可以自动恢复当前任务，但不应该在没有证据和验证的情况下，把临时恢复措施直接固化成永久能力改动。**

## 三、服务端离线时，能不能在手机上直接优化自己？

可以做一部分，但需要区分三个层次。

| 能力 | 离线时能否进行 | 建议 |
|---|---|---|
| 调整有限的运行参数 | 可以 | 在预先批准的范围内调整，例如有限重试次数、任务超时和已有策略选择 |
| 分析日志、归纳问题 | 可以 | 使用本地规则，必要时使用可用的本地小模型；记录结论及不确定性 |
| 修改核心提示词、ReAct、上下文或工具实现 | 有条件 | 可以创建本地候选，但必须隔离运行并通过适当测试 |
| 修改安全边界、权限系统和核心状态机 | 不允许普通离线进化直接发布 | 进入受保护的变更流程 |
| 运行昂贵的多模型对照实验 | 通常不适合 | 保存候选和证据，联网后交给服务端执行 |

我建议第一版手机端只具备**有限自适应 + 本地诊断 + 候选记录**，暂时不让它独立修改并发布核心代码。

原因很简单：手机端硬件、测试环境和评测资源有限，而且离线时无法可靠地调用云端模型验证复杂候选。我们不应该因为服务端暂时不可用，就降低正式发布的标准。

## 四、最重要的设计：离线问题不能丢，联网后还能继续处理

这是我建议必须纳入 V0.1 的机制。

手机端需要一个本地持久化的事件队列，而不是把所有日志实时上传到服务端。

<CodeBlock language="mermaid" editable={false}>flowchart TD
    A[手机执行任务] --> B[本地持久化事件与检查点]
    B --> C{问题能否本地恢复}
    C -->|能| D[恢复执行并记录结果]
    C -->|不能| E[安全停止或降级]
    D --> F[事件进入待同步队列]
    E --> F
    F --> G{服务端是否可用}
    G -->|否| H[本地保留并持续积累]
    H --> G
    G -->|是| I[同步允许共享的事件]
    I --> J[服务端诊断与实验]
    J --> K[生成经过验证的更新]
    K --> L[手机验证更新并受控应用]</CodeBlock>

为了让它可靠运行，本地事件队列还需要具备：

- **持久化：** App 被关闭或手机重启后，待同步事件仍然存在。
- **去重：** 同一个事件重复上传，不会造成重复的诊断任务或发布动作。
- **断点续传：** 大量日志或附件同步中断后，可以继续上传。
- **隐私过滤：** 不需要上传的屏幕内容、文件和用户数据默认留在本地。
- **容量控制：** 磁盘空间有限时，优先保留关键错误、任务结果、版本信息和检查点，普通调试日志按策略轮转。
- **数据完整性：** 事件包含唯一 ID、发生时间、关联任务和版本引用，避免联网后无法还原现场。

还有一个重要细节：不是所有事件都应该永久保存。原始日志可以有保留期限，但未解决的关键故障、发布证据和必要的审计记录应采用明确的保留策略。

## 五、如果 App 自身崩溃了呢？

这比普通任务失败更严重，因为 App 可能来不及记录最后的错误。

所以，关键执行状态不能只放在内存里。

我建议：

1. 每完成一个重要步骤，就持久化任务检查点。
2. 在执行有副作用的操作之前，记录操作意图和幂等键。
3. 重启后先检查上次任务的执行状态，再决定继续、验证还是停止。
4. 对无法确认是否成功的操作，优先检查实际状态，不要盲目重复执行。
5. 如果本地数据库损坏或状态无法恢复，就进入安全模式，并保留能够读取的诊断信息。

例如，用户要求发送一条消息，App 在点击发送后突然崩溃。重新启动时，系统不能直接再发送一次。它应当先检查消息是否已经发送成功；如果无法确认，就暂停并请求用户处理。

这需要工作流引擎、任务状态存储和工具适配器共同支持，不能只靠 ReAct 提示词解决。

**我的最终建议：把离线运行、故障恢复、本地事件队列和联网后续进化，全部纳入 V0.1 的基础架构，而不是等系统上线后再补。**

这样，即使服务端暂时离线，EvoAgent 也能继续做它有能力做的事情，安全处理它无法解决的问题，并完整保存经验。等服务恢复后，再由服务端进行更深入的诊断、验证和进化。

这才是真正面向长期运行的自进化智能体，而不是一个只有网络正常时才能工作的 AI 客户端。
