# EvoAgent 第四十八专项：目标价值评估、任务选择与自主性治理

本轮研究 EvoAgent 从“能够完成任务”走向“能够自主判断应该做什么”的关键问题。

此前，我们已经逐步设计了多专家系统、Router、Plan、ReAct、DAG、记忆与上下文、工具运行时、任务恢复、资源调度、安全治理、版本管理、因果诊断和质量验收。

这些能力让 EvoAgent 有可能完成复杂的长期任务。但能力越强，另一个问题就越突出：

**系统应该把能力用在什么地方？什么时候主动行动？什么时候先问用户？什么时候应该停止？**

例如：

- 用户只说“帮我把这个项目做好”，系统应该先澄清目标，还是直接分析项目？
- 系统发现代码存在一个与当前需求无关的潜在问题，要不要顺便修复？
- 一个任务已经达到验收标准，是否还应该继续优化？
- 有三个待办任务，应该先做最紧急的、最有价值的，还是最容易完成的？
- 系统发现自己的工具使用效率很低，可以主动启动优化实验吗？
- 某项改进理论上收益很高，但可能消耗大量资源，是否值得尝试？

这些都不是单纯的规划问题，也不是 Router 的职责。它们涉及目标理解、价值判断、行动范围、资源分配与用户控制权。

建议将本专项定义为：

**Goal Value Assessment & Autonomy Governance，简称 GVAAG。**

它是 EvoAgent 的目标与自主性治理层，负责判断目标是否明确、任务是否值得执行、行动是否超出授权范围、资源投入是否合理，以及何时应该继续、暂停或结束。

一个真正可靠的智能体，至少应具备四种能力：

**系统可以主动思考和提出建议，但不能把自己发现的每一个机会都变成必须执行的新任务。**

- Router 判断由哪个专家处理；

- UQEAG 判断最终结果是否达到验收要求；
- LTAR 负责任务状态持久化、恢复和生命周期管理。

GVAAG 不替代这些模块，而是决定它们何时开始工作，以及何时应当停止继续消耗资源。

# 三、目标模型：系统必须知道自己正在追求什么

如果目标只存在于一段很长的对话里，系统很容易在执行过程中偏离原意。

建议建立统一的 `GoalRecord`，把目标转化为可以追踪、分解、评估和关闭的结构化对象。

## 3.1 GoalRecord 的核心字段

| 字段 | 含义 |
|---|---|
| `goal_id` | 目标唯一标识 |
| `parent_goal_id` | 上级目标，用于表达目标层级 |
| `goal_source` | 用户明确指令、用户授权的长期目标、系统建议等 |
| `goal_type` | 任务目标、维护目标、改进目标或研究目标 |
| `goal_statement` | 目标的自然语言描述 |
| `success_criteria` | 目标成功的判定条件 |
| `constraints` | 时间、成本、范围、质量和安全约束 |
| `scope` | 目标允许影响的项目、资源和系统范围 |
| `authorization_ref` | 关联的授权记录 |
| `priority` | 当前优先级 |
| `uncertainty` | 目标理解中的不确定因素 |
| `status` | 目标当前生命周期状态 |
| `created_at` | 创建时间 |
| `updated_at` | 最近更新时间 |

不是每个目标都需要人工填写全部字段。系统可以从自然语言中自动提取，并在必要时进行澄清。

但有一条必须明确：

**系统推断出的目标必须保留其推断来源，不能被伪装成用户明确提出的要求。**

## 3.2 区分四种目标来源

建议至少区分以下类型。

<box border radius="xl" padding={3} gap={3}>
  <box gap={1}>
    <title size="md">G1 · 用户明确目标</title>
    <text color="secondary" size="sm">用户明确要求完成的工作。例如：“修复这个测试失败的问题。”这是最直接的任务依据，但仍然受安全与权限规则约束。</text>
  </box>
  <divider color="subtle"/>
  <box gap={1}>
    <title size="md">G2 · 用户已授权的持续目标</title>
    <text color="secondary" size="sm">用户事先允许系统持续推进的工作。例如：“每次提交前运行测试，并在失败时分析原因。”其有效范围、期限和资源限制必须明确。</text>
  </box>
  <divider color="subtle"/>
  <box gap={1}>
    <title size="md">G3 · 由原目标合理推导的子目标</title>
    <text color="secondary" size="sm">为完成现有任务所必需的步骤。例如，修复代码前先运行测试，或在生成视频后检查音轨。</text>
  </box>
  <divider color="subtle"/>
  <box gap={1}>
    <title size="md">G4 · 系统主动发现的候选目标</title>
    <text color="secondary" size="sm">系统发现可能有价值，但并非完成当前任务所必需的事项。例如发现另一处潜在技术债，或提出优化自己的路由策略。</text>
  </box>
</box>

G1、G2 和 G3 可以在授权与约束范围内进入执行流程。

G4 默认应先进入候选目标队列，经过价值评估后决定是否建议用户、暂存，或者在明确的长期授权范围内进行低风险处理。

例如，代码专家发现与当前任务无关的安全隐患，可以记录并提出建议；但不能仅凭“这可能有价值”，就自动开始修改其他模块。

## 3.3 目标层级必须有边界

建议采用如下结构：

- **长期目标：** 用户希望持续实现的方向；
- **阶段目标：** 长期目标中的一个阶段性成果；
- **任务目标：** 当前需要交付的结果；
- **子目标：** 完成任务所必需的中间目标；
- **行动：** 具体工具调用、代码修改或其他操作。

例如：

长期目标：建设可持续进化的 EvoAgent。

阶段目标：提高代码专家的执行质量。

任务目标：降低指定测试集中的代码修改失败率。

子目标：识别主要失败类型、验证候选修复策略、比较新旧版本。

行动：运行测试、读取日志、执行隔离实验。

这种结构可以避免系统从一个宏大目标直接跳到无限量的改进任务，也可以让每个子任务解释自己为什么存在。

# 四、价值评估模型：什么事情值得做？

这是 GVAAG 的核心决策问题。

系统不能只看任务是否容易完成，也不能只看用户提出任务时的紧迫程度。它还需要考虑任务带来的收益、完成概率、资源成本、失败风险，以及执行这件事会占用哪些其他任务的资源。

建议建立 `GoalValueAssessment`，统一评估目标的预期价值。

## 4.1 先做硬约束检查，再做价值比较

价值评估必须分成两个阶段。

第一阶段检查目标是否合法、是否被授权、是否超出范围、是否违反安全规则。

第二阶段才比较通过准入检查的目标之间哪个更值得执行。

例如，一个任务即使预计收益很高，只要它需要访问未经授权的数据，就不能因为收益高而获得执行许可。

## 4.2 使用多因素价值模型

对于可以合理估计的目标，可以采用以下简化模型：

\[
V(g)=P_s(g)\cdot B(g)-C(g)-R(g)-O(g)
\]

其中：

- \(P_s(g)\)：目标成功的估计概率；
- \(B(g)\)：成功带来的预期收益；
- \(C(g)\)：时间、计算、API 调用和其他资源成本；
- \(R(g)\)：失败、损害和副作用的预期代价；
- \(O(g)\)：执行该目标所放弃的其他机会价值。

这个公式是一种辅助决策模型，而不是要求所有目标都转换成一个精确的数字。

对于很难量化的任务，可以使用定性等级、区间估计或多指标比较。系统必须保留估计依据和不确定性，不能把未经验证的主观数字当作客观事实。

## 4.3 不要把所有因素都混成一个总分

建议将目标评估分成以下维度：

| 维度 | 需要回答的问题 |
|---|---|
| 目标价值 | 完成后对用户有什么实际帮助？ |
| 紧迫程度 | 延迟执行会带来什么影响？ |
| 成功概率 | 目前是否具备完成条件？ |
| 资源成本 | 需要多少时间、计算和外部费用？ |
| 风险 | 失败或副作用会造成多大影响？ |
| 机会成本 | 是否会挤占更重要任务的资源？ |
| 信息价值 | 先调查或澄清能否显著改善后续决策？ |
| 可逆性 | 失败后是否容易恢复？ |

其中，安全约束和用户授权不是普通评分维度，而是准入条件。对于高影响风险，也不能只通过平均分稀释。

## 4.4 评估信息本身的价值

有时候，系统最值得做的不是直接执行目标，而是先获得信息。

例如，用户要求优化一个项目，但没有说明优先考虑速度、内存还是可维护性。

系统可以直接进行低成本、只读的项目分析，确认当前瓶颈；也可以先询问用户最关注的指标。

建议使用信息价值判断：

\[
VOI(a)=
\mathbb{E}[\text{获取信息后的决策收益}]
-\text{获取信息的成本}
\]

如果一次只读检查就能显著减少错误决策，系统应优先考虑先调查。

如果缺失信息会导致完全不同的实施方案，且执行错误的代价很高，则应优先澄清。

如果信息缺失对结果影响很小，则可以采用安全、可逆的默认方案继续推进，而不必频繁打断用户。

## 4.5 价值评估必须考虑不确定性

系统可能对收益、成本和成功概率都没有可靠数据。

因此建议输出：

- 预期价值范围；
- 主要不确定因素；
- 估计依据；
- 最可能影响决策的未知信息；
- 是否值得先做一个低成本实验。

如果两个候选目标的估计价值差异很小，而估计误差很大，就不应该假装能够精确地排出绝对顺序。

在这种情况下，可以优先选择可逆性更高、成本更低、信息价值更大的行动。

# 五、自主性分级：系统可以自己决定到什么程度？

这是整个专项最重要的治理问题之一。

之前的 TERSO 已经有工具操作风险等级 R0～R4。本专项还需要一个独立的**自主性等级**。

两者不能混为一谈：

- 风险等级决定某项具体操作需要什么安全措施；
- 自主性等级决定系统可以在多大程度上自行选择目标、规划任务和作出决策。

一个低风险操作也可能超出当前任务范围；一个高价值任务也可能包含必须经过单独授权的高风险操作。

建议建立五级自主性模型。

这里的 A4 不代表无限制自主，也不意味着系统能够自行决定所有事情。

即使系统拥有长期运行能力，也必须受到明确的目标范围、资源限制、安全规则、授权撤销和人工接管机制约束。

## 5.1 自主性应当按目标和操作分别判定

不能只给整个 EvoAgent 设置一个全局自主等级。

例如，同一个系统可以：

- 在 A3 授权下自动运行每日测试；
- 在 A2 范围内自主修改指定项目；
- 对发布到外部平台的操作要求单独批准；
- 对修改自身安全策略的操作保持禁止。

因此建议采用：

`AutonomyPolicy = 主体 × 目标范围 × 操作类型 × 资源上限 × 时间范围`

系统在每次关键行动前，都应检查当前授权与自主策略是否允许该行动。

## 5.2 自主等级不能由智能体自行提升

系统表现良好可以成为用户重新评估授权的参考，但不能自动升级自己的自主等级。

例如，某个专家连续完成 100 次代码任务，不代表它可以自行从修改项目代码升级到发布软件、访问所有文件或修改安全策略。

自主性升级必须通过独立的授权与治理流程。

# 六、目标范围治理：防止任务无限扩张

这是长时间自主运行中非常容易出现的问题。

用户要求修复一个错误，系统发现附近还有三个潜在问题；解决这三个问题后，又发现可以重构整个模块；重构过程中又发现依赖版本较旧。

如果每个新发现都自动变成执行任务，原本一个小任务就会演变成无穷无尽的工程。

建议建立 `GoalScopePolicy`，专门控制任务范围及其扩张。

## 6.1 每个目标都应定义范围边界

至少明确：

- 目标需要交付什么；
- 哪些工作属于必要子目标；
- 哪些资源允许被修改；
- 哪些事项明确不在本次范围内；
- 允许投入多少预算；
- 允许执行多少次返工；
- 哪些变化必须重新获得批准。

例如，“修复测试失败”可以合理包含定位原因、修改相关代码、运行测试和核验结果。

但自动升级整个项目的依赖、重构无关模块或部署到生产环境，不应该因为它们可能有帮助，就被视为默认子目标。

## 6.2 新发现进入候选队列，而不是直接插入当前任务

建议所有非必要发现先进入 `GoalCandidateQueue`。

每个候选目标包含：

- 发现来源；
- 与当前目标的关联；
- 预期收益；
- 预计成本；
- 风险与可逆性；
- 是否属于当前授权范围；
- 建议处理方式；
- 是否需要用户确认。

然后由 GVAAG 决定：

- 作为当前目标的必要子任务；
- 排入后续待办；
- 作为建议通知用户；
- 暂时忽略；
- 因风险或授权不足而拒绝。

## 6.3 允许紧急情况触发升级，但不能借机无限扩权

如果系统发现可能造成严重损失的问题，可以按照预先批准的安全策略暂停相关操作、保存证据并通知用户。

但发现紧急问题不意味着系统可以不受限制地修改其他资源。

例如，发现代码可能泄漏凭据时，可以停止相关的外传操作并启动安全处置流程；但是否可以自动轮换凭据、修改部署环境或撤销其他服务的权限，仍取决于事先批准的应急授权。

**范围扩张需要理由、授权和记录；紧急程度不能成为无限扩大行动范围的通行证。**

# 七、继续还是停止：建立正式的停止决策机制

很多智能体擅长开始任务，却缺少可靠的停止规则。

它们可能在结果已经合格后继续尝试优化，也可能在遇到困难时不断重试，消耗大量资源却没有实质进展。

GVAAG 应建立独立的 `StopDecisionEngine`。

## 7.1 定义六种停止或转移条件

| 条件 | 决策 |
|---|---|
| 已满足验收条件 | 停止当前任务，准备交付 |
| 继续改进的预期收益低于成本 | 停止优化，说明剩余局限 |
| 预算或时间上限达到 | 停止或暂停，等待用户决定 |
| 关键前置条件缺失 | 请求澄清或进入等待状态 |
| 风险或授权边界被触发 | 阻断相关操作，进入安全处置 |
| 反复尝试无进展 | 停止重复执行，转入根因诊断 |

这里需要区分任务停止与目标永久关闭。

例如，任务可能因为预算不足而暂停，但目标仍然有效；也可能因为用户撤销授权而终止；还可能因为达到验收标准而正常完成。

这些情况应该使用不同的状态，而不是统一标记为 `STOPPED`。

## 7.2 设定边际收益门槛

对于已经合格的结果，系统可以估算继续优化的边际收益：

\[
\Delta V = \Delta B-\Delta C-\Delta R
\]

其中：

- \(\Delta B\)：继续改进带来的预期收益；
- \(\Delta C\)：新增资源成本；
- \(\Delta R\)：新增风险的预期代价。

如果进一步优化的收益很小，成本明显增加，就应考虑停止。

但这只是辅助规则。对于不可妥协的硬性质量要求，不能因为成本太高就将不合格结果伪装成合格结果。

正确做法是报告无法在当前预算下达到目标，并向用户提供选项，例如增加预算、降低非关键要求、缩小范围或停止任务。

## 7.3 反复失败必须触发诊断

建议设置有上限的重试策略。

例如，同一个节点连续失败时：

1. 先判断是否属于瞬时错误；
2. 对可安全重试的操作执行有限重试；
3. 如果失败模式相同，则停止重复；
4. 将事件交给 SOCDEA 分析；
5. 根据根因证据选择修复、替代工具或请求用户介入。

不能通过无限次重试来假装自主能力很强。

## 7.4 停止后必须形成可交付的状态

停止决策还需要确保：

- 当前任务状态已经持久化；
- 未完成的节点被明确标记；
- 外部副作用已经核验或标记为未知；
- 剩余预算与资源已经释放或保留；
- 已有产物和未验证事项可以追溯；
- 用户能够理解任务为什么停止，以及接下来可以做什么。

这与 LTAR、TERSO、UQEAG 和 SOCDEA 共同构成完整的停止与恢复闭环。

# 八、多任务价值排序：系统应该先做哪件事？

当 EvoAgent 同时管理多个长期任务时，仅按任务创建时间或紧急程度排序是不够的。

例如：

- 一个任务非常紧急，但只需要两分钟；
- 一个任务长期重要，却没有立即截止时间；
- 一个任务价值很高，但当前成功概率很低；
- 一个任务正在等待外部服务恢复；
- 一个任务已经投入大量资源，但继续投入可能不再划算。

建议建立 `GoalPortfolioManager`，负责管理所有已授权目标的组合，而不是孤立地评估每一个目标。

## 8.1 任务排序需要考虑四类因素

1. **价值与时效：** 不做会造成多大影响，延迟是否会使价值下降？
2. **执行准备度：** 现在是否具备必要输入、资源与依赖？
3. **机会成本：** 执行该任务是否会阻塞其他更重要的任务？
4. **连续性成本：** 中断一个已经运行的长期任务，是否会造成昂贵的恢复或重复工作？

系统可以根据这些因素生成排序建议，但不能把排序分数当作强制执行许可。

例如，低价值任务即使排在第一位，也必须满足授权与资源准入；高价值任务如果缺少关键输入，也可能需要先等待或澄清。

## 8.2 防止低优先级任务永远得不到执行

如果系统永远只选择当前价值最高的任务，某些长期任务可能一直被推迟。

建议为长期任务设置明确的调度策略，例如：

- 截止时间接近时提高优先级；
- 等待过久时适当增加调度权重；
- 对长期维护任务保留有限资源；
- 对高价值但暂时受阻的任务进行定期重新评估；
- 对没有新信息、没有进展的任务降低重复评估频率。

这些策略应由 MTSRIC 负责实际资源调度，GVAAG 提供目标价值和任务优先级建议。

## 8.3 区分任务重要性与资源投入

一个重要任务不一定应该一次性消耗大量资源。

例如，复杂代码优化可以先运行低成本基准测试，再决定是否开展更大规模的性能实验。

建议优先采用分阶段投入：

- 第一阶段：低成本调查；
- 第二阶段：验证关键假设；
- 第三阶段：开展主要工作；
- 第四阶段：验收与必要返工。

每个阶段结束后重新评估剩余价值与成本。

这样可以避免在最初假设错误时，已经投入大量计算、时间和外部费用。

# 九、长期主动目标：系统发现问题后，怎样决定是否主动推进？

EvoAgent 的自进化目标意味着它不仅会响应用户，还可能发现自身的缺陷。

例如：

- Router 对某类任务的选择准确率下降；
- 某个专家频繁触发不必要的重试；
- 某个工具适配器的稳定性较差；
- 上下文压缩导致特定任务类别的信息损失；
- 任务恢复过程中存在重复执行风险。

这些发现可能值得主动改进，但不应全部立即执行。

建议建立 `ProactiveGoalPolicy`，规定系统可以主动开展哪些类型的工作。

## 9.1 将主动行为分成三类

<box border radius="xl" padding={3} gap={3}>
  <box gap={1}>
    <title size="md">P1 · 被动观察</title>
    <text color="secondary" size="sm">收集已授权的运行指标、发现异常、记录候选问题。通常不产生额外的高影响副作用。</text>
  </box>
  <divider color="subtle"/>
  <box gap={1}>
    <title size="md">P2 · 低风险主动调查</title>
    <text color="secondary" size="sm">在明确授权与资源限制内运行只读分析、历史回放或隔离实验，用于判断问题是否值得修复。</text>
  </box>
  <divider color="subtle"/>
  <box gap={1}>
    <title size="md">P3 · 主动实施改进</title>
    <text color="secondary" size="sm">修改生产配置、更新模块、改变任务策略或执行其他可能影响实际运行的操作，需要满足相应的独立发布与授权条件。</text>
  </box>
</box>

即使系统被允许主动调查，也不代表它被允许主动实施所有改进。

## 9.2 建立自进化目标准入条件

一项自主改进至少应该具备：

- 明确的问题证据；
- 可描述的改进假设；
- 预期收益；
- 成本和资源上限；
- 影响范围；
- 隔离验证方法；
- 失败后的恢复路径；
- 对应的发布治理要求。

如果只是“我觉得可以优化一下”，就不应该直接创建长期自主任务。

## 9.3 系统不应以维持自身运行作为默认目标

这是自进化系统尤其需要明确的一点。

EvoAgent 的目标应来自用户明确设定或明确授权的长期目标，而不是由系统为了延续自身运行、增加调用量或证明能力而自行创造。

系统可以发现自己的问题，可以提出改进，也可以建议用户扩大授权范围，但不能把“持续进化本身”视为可以无限消耗资源的理由。

**进化是服务用户目标的手段，不是凌驾于用户目标之上的终极目标。**

# 十、目标与自主性评测：怎样知道系统决策越来越好了？

GVAAG 本身也需要独立评测。

如果系统主动启动的任务越来越多，却没有更好地完成用户目标，那么自主性并没有真正提高。

建议从五个维度衡量。

| 维度 | 核心指标 |
|---|---|
| 目标理解 | 用户目标提取准确率、必要澄清识别率、目标漂移率 |
| 价值判断 | 高价值任务识别率、资源投入合理性、价值预测校准 |
| 自主边界 | 未授权行动率、范围外执行率、应询问而未询问的比例 |
| 停止决策 | 无效重试率、过度优化率、过早停止率 |
| 组合调度 | 重要任务延迟、长期任务饥饿率、单位资源带来的有效收益 |

其中，有些指标是硬性安全指标，例如未授权行动率不能通过其他指标提高而抵消。

## 10.1 使用真实任务回放验证目标判断

建议建立不同类型的评测样本：

- 目标明确的任务；
- 需求存在关键歧义的任务；
- 目标与约束冲突的任务；
- 容易发生范围扩张的任务；
- 资源不足但仍有部分价值的任务；
- 已经合格但可以继续优化的任务；
- 系统发现了相关问题但没有获得扩展授权的任务；
- 高价值但高风险的候选任务；
- 多个目标同时竞争资源的任务。

每个样本都需要明确预期行为，例如直接执行、询问、提出建议、暂停或拒绝。

## 10.2 不要把自主性评分直接转换为更多权限

如果系统在目标判断、价值预测和停止决策方面表现良好，可以据此改进任务规划策略。

但这不能自动增加文件访问权限、外部操作权限或安全策略修改权限。

能力评测与授权变更必须保持独立。

# 十一、与现有架构的集成关系

GVAAG 应作为目标决策层，与已有模块建立清晰的职责边界。

| 模块 | 协作关系 |
|---|---|
| Router | 选择专家，不负责决定目标本身是否值得执行 |
| Planner / DAG | 将准入的目标分解为计划与任务依赖 |
| MTSRIC | 根据价值、优先级和资源限制实际调度任务 |
| ARCBG | 管理预算和资源消耗约束 |
| TERSO | 执行具体工具操作，并遵守风险与授权规则 |
| ASGTB / SBAAG | 决定身份、权限和安全边界，GVAAG 不得覆盖 |
| LTAR | 持久化目标与任务状态，支持暂停、恢复和终止 |
| UQEAG | 判断结果是否达到验收标准 |
| SOCDEA | 分析失败原因、低收益行为和无效重复执行 |
| SELCIA | 管理自主改进候选的评测、发布和回滚 |
| MEEG / CLEK | 提供相关记忆与知识，但不能自行创造执行权限 |

这里需要特别明确：

- GVAAG 可以决定“值得调查这个问题”；
- SOCDEA 可以判断“问题可能来自上下文压缩”；
- SELCIA 可以管理“是否发布改进候选”；
- 但是否允许修改受保护配置，仍由独立的安全治理与授权机制决定。

这种分工可以避免一个模块同时拥有目标创建、价值判断、执行、验收和自我批准的全部权力。

# 十三、下一专项：人机协作、用户控制权与可接管性

GVAAG 解决了系统应该追求什么目标、是否值得行动，以及何时停止的问题。

但还有一个直接影响实际体验的问题：

**当 EvoAgent 越来越自主时，用户如何知道它正在做什么、为什么这样做，以及如何在需要时改变方向或接管任务？**

如果每一步都要求用户确认，智能体会退化成一个需要不断人工操作的工具；如果所有事情都自动完成，用户又可能失去对目标、资源和结果的控制。

因此，下一专项建议定义为：

**Human-Agent Collaboration & Control Governance，简称 HACCG。**

重点研究：

1. 如何让用户清楚理解当前目标、执行状态和剩余工作；
2. 如何设计低打扰的授权与确认机制；
3. 如何区分通知、建议、确认请求和必须阻断的安全事件；
4. 如何让用户随时暂停、取消、修改目标或接管任务；
5. 如何处理用户中途修改要求、撤销授权和改变优先级；
6. 如何设计适合手机优先、桌面协作和微型 Linux 主机长期运行的交互方式；
7. 如何在后台任务运行期间提供有价值的进度，而不频繁打扰用户；
8. 如何在任务失败时展示证据、未知因素和可选处理方案；
9. 如何让用户批准某项操作时，清楚知道批准的范围、期限和副作用；
10. 如何防止系统通过模糊措辞、信息过载或默认选项诱导用户批准；
11. 如何让用户反馈影响未来行为，同时避免一次反馈被无限泛化；
12. 如何评估用户对系统的理解程度、控制能力和实际使用成本。

本专项的核心原则是：

**自主智能体应当减少用户的操作负担，而不是削弱用户的控制权。用户不必监督每一个内部步骤，但必须能够理解关键决策、控制授权范围，并在必要时及时接管。**

这将进一步补齐 EvoAgent 的人机协作闭环，使它不仅能够自主执行和持续进化，还能够以可理解、可控制、可接管的方式长期服务于用户。
