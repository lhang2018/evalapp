# EvoAgent 深度设计第二轮：把“能力图谱”变成真正可运行的系统

这次我们不再停留在架构理念上，而是继续从第一性原理推导：**EvoAgent 应该用什么数据模型描述能力，如何确定能力归属，如何追踪依赖，以及如何让能力在安全边界内独立进化。**

我先提出一个核心判断：

> EvoAgent 不应该只管理智能体和工作流，而应该管理一套可验证、可组合、可版本化的能力资产。

智能体是能力的运行载体，模型是推理引擎，工具是执行接口，记忆是状态与知识来源，工作流是执行组织方式，进化系统则负责改善这些资产。

如果未来更换模型、增加专家，甚至重写部分 Harness，只要能力定义、接口和验收标准保持兼容，我们就不应该被迫重建所有能力。

反过来，即使智能体的代码没有变化，只要模型、工具或记忆策略变化导致任务表现退化，系统也应该能够发现。

这就是为什么能力图谱需要成为 EvoAgent 的基础数据模型，而不只是文档里的示意图。

# 一、首先纠正一个潜在的设计误区：能力不等于组件

假设我们定义了一项能力：

**Python 异步错误诊断。**

它可能由以下内容共同实现：

- 一个编程专家。
- 一份专用提示词。
- 一个代码执行工具。
- 一组 Python 异步编程记忆。
- 一套诊断与修复工作流。
- 一个用于验证修复效果的测试器。
- 某个模型及其适配参数。

如果我们把“能力”直接等同于“编程专家”或“某个工作流”，就无法独立管理这些组成部分。

例如，我们可能想保留工作流，只更换模型；或者保留模型，只优化提示词；或者改进测试器，却不改变任务执行逻辑。

因此，我建议把系统拆成四种不同的对象：


    <title size="lg">1. 能力定义 Capability</title>
    描述要完成什么任务、适用范围、输入输出、前置条件和成功标准。
    例如：诊断 Python 异步错误并提出经过测试的修复。



    <title size="lg">2. 能力实现 Implementation</title>
    描述如何完成任务，包括模型、提示词、工具、记忆策略、代码和工作流。
    同一项能力可以有多个实现，并在相同条件下比较。



    <title size="lg">3. 能力证据 Evidence</title>
    描述实现经过哪些测试、在哪些环境下有效、出现过哪些失败、实际成本是多少。
    证据必须关联具体实现版本和测试条件，不能只保存一个总分。



    <title size="lg">4. 能力发布版本 Release</title>
    描述正式运行时，哪些能力实现及依赖版本被组合在一起。
    例如：Python 异步诊断 v3 使用某个模型适配、工具版本和测试器版本。


这四类对象要分别管理。

能力定义可以长期稳定；实现可以频繁实验；证据会随着新测试和真实运行持续增加；发布版本则必须保持可复现、可追溯和可回滚。

这也是我们后续能够做到模型切换、专家独立进化和工作流长期复用的基础。

# 二、能力图谱应该包含哪些节点和关系？

我建议第一版先不要把它做成复杂的知识图谱数据库，而是用关系数据库保存权威数据，再用显式的依赖关系表构建能力图。

原因很简单：EvoAgent 目前更需要可靠的版本管理、事务、查询和审计，而不是为了“图谱”这个概念引入额外基础设施。未来关系复杂到需要图数据库时，再考虑迁移。

## 2.1 节点：系统到底要管理哪些资产？

| 节点类型 | 具体内容 | 示例 |
|---|---|---|
| Capability | 能力定义 | 代码调试、旅游规划、工具故障诊断 |
| Expert | 领域专家 | 编程专家、旅游专家 |
| Implementation | 能力实现 | 提示词、模型策略、工具链、工作流实现 |
| Component | 可复用工程组件 | ReAct 引擎、上下文组装器、权限检查器 |
| Tool | 外部工具或设备能力 | Python 执行器、地图 API、Android 无障碍适配器 |
| Memory Policy | 记忆管理策略 | 编程项目记忆检索、偏好冲突处理 |
| Workflow | 可执行流程 | 代码修复 DAG、旅行规划流程 |
| Evaluation Suite | 评测集 | 异步错误诊断测试集、行程约束测试集 |
| Evidence | 运行与测试证据 | 任务轨迹、回归结果、成本记录 |
| Release | 已批准的版本组合 | 编程专家稳定版、手机操作稳定版 |

这些节点不应该全部采用相同的数据结构。能力定义关注语义和契约；工具关注接口与权限；记忆策略关注数据范围；评测集关注测试案例和评分规则；发布版本关注依赖组合和验收结果。

## 2.2 关系：节点之间如何关联？

我们至少需要以下几种关系：

- `DECOMPOSES_TO`：一项能力由哪些子能力组成。
- `DEPENDS_ON`：一个组件或实现依赖哪些其他组件。
- `IMPLEMENTS`：某个实现实现哪项能力。
- `USES`：专家或工作流使用哪些能力、工具或记忆策略。
- `VALIDATED_BY`：某项能力或实现由哪些评测集验证。
- `SUPPORTED_BY`：某项能力的成熟度由哪些证据支持。
- `OWNED_BY`：谁拥有该资产的修改权。
- `DERIVED_FROM`：候选版本从哪个稳定版本演化而来。
- `PROMOTED_TO`：经过批准的局部经验晋级到了哪个共享资产。

例如：

<CodeBlock language="mermaid" editable={false}>flowchart TD
    C1[Python 异步错误诊断能力] -->|由...组成| C2[异常定位子能力]
    C1 -->|由...组成| C3[修复验证子能力]

    I1[诊断实现 v3] -->|实现| C1
    I1 -->|依赖| T1[代码执行工具]
    I1 -->|使用| M1[编程记忆策略]

    C1 -->|由...验证| E1[异步诊断评测集]
    I1 -->|产生| EV1[评测与运行证据]

    X1[编程专家] -->|使用| I1
    R1[编程稳定发布版] -->|锁定| I1
    R1 -->|锁定| T1</CodeBlock>

这里有一个关键约束：**关系本身也需要类型、版本和适用范围。**

比如，编程专家“使用”某个共享上下文组件，不代表它必须采用该组件的所有实验性配置；它可能只绑定到某个已验证版本。

同样，某项能力“依赖”某个模型，不代表它永远只能使用这个模型，而是当前实现对该模型存在明确的兼容性要求。

这使依赖图既能描述逻辑关系，也能用于真实的工程变更分析。

# 三、能力所有权应该怎么设计？

这里我建议使用一个比“每个专家拥有自己的目录”更严格的机制：**资产所有权 + 修改权限 + 共享范围，三者分开管理。**

例如，编程专家可以拥有自己的代码生成策略，但它使用的预算控制器属于共享内核。编程专家有权调用预算控制器，却没有权自行修改全局预算上限。

  <title size="lg">所有权模型</title>


      **专家私有**


      **修改权：对应专家的进化流程**

      包括领域提示词、专用工作流、领域记忆策略、领域工具选择策略和领域评测集。修改默认只影响该专家。





      **受控共享**


      **修改权：共享组件维护与验收流程**

      包括通用错误分类、可复用规划策略、上下文策略和通用工具恢复方法。局部专家可以提交候选，但不能直接把候选推广到其他专家。





      **受保护内核**


      **修改权：独立的高风险变更流程**

      包括权限边界、硬预算上限、发布门禁、审计和关键状态机。普通进化任务不能修改这些限制，也不能绕过它们。



我还建议给每个资产增加四个独立字段：

- `owner_scope`：资产归属哪个专家或系统范围。
- `mutation_policy`：允许谁修改、通过什么流程修改。
- `sharing_policy`：是否允许共享、允许共享到什么范围。
- `promotion_policy`：从局部候选晋级到稳定或共享状态，需要满足什么条件。

注意，所有权不是说只有某个专家才能提出改进，而是说谁有权批准改动生效。

例如，旅游专家发现共享工具恢复机制存在缺陷，可以提出问题并提交复现案例；但它不能直接覆盖共享恢复机制。共享组件的候选版本必须经过相应测试和发布流程。

这会避免“使用权等于修改权”这一常见架构漏洞。

# 四、数据库应该怎样设计？

V0.1 不需要一开始建立几十张复杂的表，但数据模型必须能够支撑未来的独立进化。

我建议使用 SQLite 起步，采用关系表保存权威数据。后续多用户、多设备、并发任务增长时，再迁移到 PostgreSQL。事件量较大时，可以独立扩展事件存储，但不要一开始就引入过多基础设施。

第一版至少需要以下核心表。

| 表 | 主要职责 |
|---|---|
| `capabilities` | 能力定义、适用范围、输入输出契约 |
| `experts` | 专家身份、领域和配置入口 |
| `components` | Harness、记忆策略、工具适配器等工程组件 |
| `implementations` | 某项能力的具体实现版本 |
| `capability_edges` | 能力依赖、分解、使用与实现关系 |
| `ownership_policies` | 所有权、修改权限和共享规则 |
| `evaluation_suites` | 测试集及其版本 |
| `evaluation_runs` | 每次评测的结果、成本和环境信息 |
| `runtime_events` | 任务执行轨迹、错误和工具结果 |
| `evolution_proposals` | 诊断结论、改进假设和候选变更 |
| `releases` | 已批准的专家或系统版本 |
| `release_dependencies` | 发布版本锁定的组件与实现版本 |

还需要单独管理记忆数据、工作流定义和任务检查点。它们可以在第一版采用独立的数据表或模块，但都必须能关联到具体的任务、专家和版本。

## 最重要的几个数据原则

**第一，所有可进化对象都要有稳定 ID 和不可变版本。**

例如，`capability_id` 表示“Python 异步错误诊断”这个长期能力定义；`implementation_version` 表示它的某个具体实现。不能因为修改提示词，就把历史实现直接覆盖掉。

**第二，运行证据必须关联当时的真实环境。**

一条评测结果至少应当关联：

- 专家与能力 ID。
- 实现版本和发布版本。
- 模型及其适配配置版本。
- 工具版本与关键依赖。
- 评测集版本。
- 运行参数、实际成本和最终结果。

否则，系统可能把新模型的提升错误归因于提示词修改，或者无法复现一次失败。

**第三，关系变更也需要版本化。**

例如，一个专家从上下文组件 v2 切换到 v3，即使专家自身的提示词没有变化，这也应该被记录为依赖变更。发布系统需要能够准确还原此前运行时使用的组件组合。

# 五、能力图谱如何真正指导一次进化？

我们用一个具体案例，把前面的数据模型串起来。

假设编程专家发现 Python 异步调试成功率偏低。


    **步骤 1：建立问题记录**

    关联失败任务、模型版本、工具结果、上下文快照和验收证据。此时只记录现象，不直接断言编程能力退化。



    **步骤 2：定位关联资产**

    从失败任务追踪到 Python 异步诊断能力，再查找对应实现、记忆策略、工具和上下文组件。



    **步骤 3：分析影响范围**

    如果证据指向 Python 专用提示词，就先修改该实现；如果指向共享上下文压缩组件，则识别所有依赖该组件的专家。



    **步骤 4：创建隔离候选**

    创建新的实现版本，保留稳定版本，记录修改内容、预期收益、适用范围、依赖和实验预算。



    **步骤 5：执行分层评测**

    先验证目标缺陷，再运行相关回归集。如果修改共享组件，还需要测试其他依赖方及核心约束。



    **步骤 6：发布或拒绝**

    独立门禁根据证据决定是否发布。通过后更新相应发布清单；失败则保留旧版本并记录原因。


这里有一个值得强调的细节：能力图谱不能只回答“哪些东西相关”，还必须回答“改动之后哪些测试是必需的”。

因此，每个组件除了声明依赖，还应声明关键不变量、已知风险、验证方法和变更影响规则。

不过，自动计算出来的影响范围只是最低测试要求，不是完整保证。实际运行中还需要监测意外回归，并支持停止扩散和回滚。

# 六、如何防止能力图谱自身变得混乱？

如果每次任务失败都新增一种能力，每次成功都新增一项技能，能力图谱很快就会膨胀成无法维护的庞大网络。

因此，我建议建立三个约束。

**1. 不是每个问题都需要新增能力。**

如果某次失败只是参数错误，通常只需要修复当前任务或补充已有能力的测试，不必创建新的能力节点。

**2. 新能力必须有明确的独立价值。**

只有当它具有清晰的职责边界、可描述的输入输出、独立的验收方法，或者需要单独管理版本和权限时，才值得成为独立能力资产。

**3. 能力合并和拆分也必须受控。**

例如，未来发现“异常定位”和“修复验证”长期作为两个独立子能力更便于复用，可以将它们分开管理；如果两个节点实际上没有独立契约和维护价值，也可以合并。

但拆分、合并不能删除历史关系。系统需要保留迁移记录，确保旧版工作流和历史评测仍然可追溯。

# 七、这一轮之后，我建议形成的正式架构决策

我们已经可以把能力图谱的第一版原则明确下来。




      **决策 A：能力与实现分离**

      能力定义、具体实现、验证证据和发布版本是不同的对象。






      **决策 B：能力采用多关系图模型**

      能力支持层级、依赖、交叉复用和版本化关系，而不是只属于一棵领域树。






      **决策 C：所有权、修改权和共享权分离**

      专家可以使用共享能力，但不能因此直接修改共享实现或绕过发布门禁。






      **决策 D：变更范围决定最低验证范围**

      系统依据能力依赖图、组件类型和变更风险选择回归测试，并通过实际运行监测补充静态依赖分析。






      **决策 E：所有进化都可追溯、可拒绝、可回滚**

      候选改动保留来源、实验结果、实际成本、发布决定和历史版本，不允许覆盖稳定资产后再补记日志。



## 八、下一步真正需要解决的难题

到这里，我们基本明确了能力图谱的概念模型、所有权规则和数据库方向。

但还有一个比存储结构更难的问题：

**如果编程专家形成了一项新经验，EvoAgent 怎样判断它应该继续作为编程专家的私有能力，还是可以推广给其他专家？**

这不是简单地检查它是否在编程测试中成功。

我们需要判断：

- 它的有效性来自什么机制？
- 适用条件是否可以明确描述？
- 其他领域是否存在相同的问题结构？
- 迁移后是否会引入新的风险？
- 需要哪些跨领域测试才能批准共享？
- 推广之后如果某个领域退化，如何撤回共享能力而不破坏其他领域？

我认为下一轮应该专门研究这个问题：**从局部经验到领域能力，再到共享通用能力的晋级与迁移机制。**

因为这一步决定了 EvoAgent 最终能否同时做到两件事：一方面让各专家独立成长，另一方面又能把真正有价值的经验沉淀为整个系统的通用能力。
