# EvoAgent 第五十六专项：质量工程、评测体系与进化治理

<text color="secondary" size="sm">QEEG · Quality Engineering & Evaluation Governance</text>

前面我们已经讨论了专家系统、任务 DAG、记忆与上下文、GECO 观测、TSEG 安全、RERA 可靠性，以及 APRO 性能与成本优化。

现在进入一个决定 EvoAgent 能否真正持续进化的核心专项：**如何定义好坏、如何验证改进，以及如何防止系统错误地认为自己已经进步。**

这次需要从第一性原理重新思考。

假设 EvoAgent 的编程专家升级了一个版本：

- 任务完成速度提高了 30%；
- Token 消耗减少了 25%；
- 模型自评的满意度从 80 分提高到了 92 分；
- 但实际回归测试通过率从 95% 降到了 88%。

这个版本算不算进步？

显然，不能只看速度、成本或模型自己的评分。对于代码交付，回归测试退化可能意味着整个改进不可接受。

再假设另一种情况：一个版本的成功率从 80% 提高到 85%，但只测试了 10 个任务，而且这些任务比旧版本简单得多。这也不能证明能力真正提高了。

更复杂的是，如果负责改进的智能体能够修改测试用例、评测器或成功标准，它甚至可能通过降低难度，让自己的分数越来越高。

因此，QEEG 不能只是一个评分模块。它必须成为贯穿 EvoAgent 所有专家、技能、工作流、路由策略和自进化方案的**独立质量验证体系**。

本专项要回答九个问题：

1. 什么才算任务真正完成？
2. 不同领域的质量应该怎样定义？
3. 哪些结果可以自动验证，哪些需要人工判断？
4. 怎样评测 Router、Planner、ReAct、专家和记忆系统？
5. 怎样证明多专家协作比单专家更好？
6. 如何区分真实进步、随机波动和任务难度变化？
7. 如何防止评测器被优化对象操纵？
8. 如何将评测结果接入 SELCIA 的发布与回滚流程？
9. 怎样让用户反馈持续改善质量，而不让系统被少数异常反馈带偏？

核心原则是：

**系统可以自行提出改进、生成测试和解释结果，但正式晋升必须依据独立、可追溯、与任务目标一致的证据。**

# 一、第一性原理：质量不是一个分数

智能体很容易把复杂任务压缩成一个看似精确的数字，例如“质量 92 分”。

但不同任务的质量结构完全不同。

- 代码能否正确运行，不能只看代码是否整洁；
- 研究报告是否可靠，不能只看文字是否流畅；
- 漫剧是否合格，不能只看画面是否漂亮；
- 手机自动化是否成功，不能只看操作步骤是否执行；
- 记忆系统是否有效，不能只看检索结果是否相关；
- Router 是否准确，不能只看它是否选中了某个热门专家。

因此，QEEG 首先要将质量从单一分数拆成**质量契约、验证证据、约束门槛和综合评价**。

## 1.1 四层质量模型

这四层不能简单互相抵消。

例如，任务极快完成，但没有满足用户的核心要求，就不能因为速度优势获得高质量结论。

同样，代码测试全部通过，但程序未经授权修改了用户目录之外的文件，也不能被判定为合格交付。

## 1.2 区分硬性门槛与可权衡指标

建议把质量要求分为两类。

**硬性门槛：**

- 必须满足的用户约束；
- 必须通过的功能测试；
- 必须遵守的安全和授权规则；
- 必须达到的产物完整性要求；
- 必须完成的关键验收步骤。

**可权衡指标：**

- 完成速度；
- 成本；
- 可读性；
- 维护便利性；
- 视觉表现；
- 用户体验；
- 非关键的优化程度。

可权衡指标可以在不同任务之间采用不同权重，但硬性门槛不能被平均分抵消。

建议将正式验收表示为：

\[
\operatorname{Accept}(x)
=
\operatorname{GatesPass}(x)
\land
\operatorname{EvidenceSufficient}(x)
\]

其中 \(x\) 是待验收产物。

通过所有必要门槛且证据充分，才有资格进入综合质量评价。如果必要证据缺失，应标记为“未能确认合格”，而不是默认通过。

# 二、建立统一质量契约：每项任务先明确怎样才算成功

QEEG 的核心对象不是一个抽象的“评分”，而是 `QualityContract`。

它定义当前任务需要交付什么、必须满足哪些条件、如何验证，以及证据不足时应该怎样处理。

## 2.1 质量契约包含哪些内容？

建议至少包括：

| 字段 | 作用 |
|---|---|
| `goal_ref` | 关联用户目标与任务契约 |
| `deliverables` | 明确需要交付的产物 |
| `acceptance_criteria` | 定义合格条件 |
| `hard_gates` | 定义不可被综合评分抵消的门槛 |
| `validators` | 指定需要运行的测试、规则或评审方法 |
| `evidence_requirements` | 定义通过验收必须提供的证据 |
| `quality_dimensions` | 定义可比较的质量维度 |
| `risk_profile` | 确定验证深度与人工确认要求 |
| `budget_constraints` | 记录时间、费用与资源约束 |
| `version` | 追踪契约变更 |
| `unknown_policy` | 规定证据缺失、无法验证时的处理方式 |

质量契约可以由用户明确提供，也可以由 Planner 根据请求生成候选，再通过结构化澄清或已验证的默认规则确定。

对于低风险、目标清楚的任务，不必每次都打断用户确认全部细节。

但对于高风险或验收条件不明确的任务，系统不能默默假设一个宽松标准。

## 2.2 质量契约不能被待验收对象随意修改

例如，编程专家生成了代码，并且测试失败。

它可以提出修复方案，但不能为了让当前代码通过而自行删除失败测试或降低验收标准。

如果发现原始质量契约存在错误，可以提出单独的契约变更请求。

变更必须记录：

- 原始要求；
- 修改原因；
- 新旧契约差异；
- 对任务结果的影响；
- 谁或哪个受控流程批准了变更。

如果要求来自用户，涉及用户目标或交付标准的实质性变更，应按照授权策略请求用户确认。

这也是 QEEG 与 TSEG 的重要接口：质量标准可以演进，但不能被待评测的对象悄悄重写。

## 2.3 质量契约与领域专家如何配合？

建议采用两级结构：

- **全局质量契约：** 目标符合性、安全、可靠性、交付完整性、证据要求。
- **领域质量契约：** 编程、漫剧、研究、数据分析等领域自己的专业标准。

例如，代码专家可以增加单元测试、静态分析和接口兼容性要求；漫剧专家可以增加角色一致性、音画同步、时长和画面质量要求。

领域专家可以提出专业验收条件，但不能覆盖全局硬性门槛。

# 三、评测体系：不同问题必须使用不同的验证方法

不是所有任务都能通过同一种方法判断质量。

代码可以运行测试，数据分析可以检查计算结果，研究报告需要核对来源，创意作品需要综合评价，而 Router 的准确性需要对照真实任务意图和适用专家能力。

因此，QEEG 应建立统一的评测编排机制 `Evaluation Orchestrator`，但允许不同领域使用专门的验证器。

## 3.1 建立六类评测器

<box border radius="xl" padding={3} gap={3}>
  {#each [
    ["E1 · 确定性验证器","使用测试、Schema 校验、文件完整性检查、数值校验和规则引擎验证明确条件。"],
    ["E2 · 执行验证器","在受控环境中实际运行程序、工作流或工具，观察行为是否符合预期。"],
    ["E3 · 证据验证器","检查来源、引用、版本、数据血缘和事实证据是否支持结果。"],
    ["E4 · 模型辅助评审器","评价难以完全规则化的内容，例如表达质量、解释完整性和视觉连贯性。"],
    ["E5 · 人工评审器","处理高风险、存在实质歧义或必须由用户决定的事项。"],
    ["E6 · 真实结果评估器","在有可靠反馈与明确统计口径时，评估用户后续采用、实际效果和长期表现。"]
  ] as item}
    <box gap={1}>
      <title size="md">{item[0]}</title>
      <text color="secondary" size="sm">{item[1]}</text>
    </box>
    {#if item[0]!=="E6 · 真实结果评估器"}
      <divider color="subtle"/>

这些评测器可以组合使用。

例如，一份研究报告可以同时经过结构检查、来源核验、事实交叉验证和模型辅助评审。模型评审不能替代来源核验，格式检查也不能证明结论正确。

## 3.2 建立证据等级

建议统一记录评测结论的证据状态：

- `PASS`：必要条件已通过验证；
- `FAIL`：有证据表明必要条件不满足；
- `INCONCLUSIVE`：证据不足，无法判断；
- `NOT_APPLICABLE`：该条件不适用于当前任务；
- `BLOCKED`：因权限、依赖或环境限制，无法执行必要验证。

这些状态不能随意互相转换。

例如，测试环境不可用时，不能将 `BLOCKED` 自动转成 `PASS`；模型认为代码“看起来正确”，也不能替代实际执行测试。

最终任务状态应结合所有必要门槛判定，而不是把五个通过项和一个未知项平均成一个高分。

## 3.3 确定性验证应优先

凡是可以用低成本、稳定、可复现的方式验证的条件，都应优先使用确定性方法。

例如：

- JSON 输出是否符合 Schema；
- 代码是否通过规定的测试；
- 文件是否存在且哈希正确；
- 数据总量是否守恒；
- 生成视频是否满足时长与编码要求；
- 任务是否遵守预算；
- 指定的操作是否真的完成；
- 引用的来源是否存在且支持相关结论。

只有无法通过确定性方法充分判断的部分，才需要增加模型辅助评审或人工评审。

这不仅能够提高可靠性，还能降低评测费用和模型评审的随机性。

# 四、领域评测：每种专家都需要自己的质量标准

EvoAgent 的专家体系不能只区分“谁负责什么”，还必须区分“怎样证明该专家做得好”。

建议建立 `DomainEvaluationPack`，让每个专家绑定一套领域专用评测集、评测器和质量契约。

## 4.1 编程专家

<box border radius="lg" padding={3} gap={2}>
  <title size="md">核心质量维度</title>
  - 功能正确性与回归测试
  - 接口兼容性与需求符合度
  - 静态分析、类型检查与必要的 AST 结构检查
  - 安全性与依赖风险
  - 代码可维护性与复杂度
  - 修改范围与副作用控制
  <divider color="subtle"/>
  <title size="md">主要证据</title>
  <text color="secondary" size="sm">测试结果、代码差异、静态分析报告、执行日志、依赖版本、变更范围和验收契约。</text>
</box>

编程任务不能只靠另一个模型阅读代码后给出高分。

如果存在可运行的测试，应优先执行；如果缺乏测试，则应明确标记验证覆盖不足，而不是把模型评审当成完整替代品。

## 4.2 AI 漫剧专家

<box border radius="lg" padding={3} gap={2}>
  <title size="md">核心质量维度</title>
  - 剧情与分镜的一致性
  - 角色外观与身份连续性
  - 画面质量、构图与镜头连贯性
  - 配音、字幕和画面的同步
  - 时长、分辨率、帧率和音视频编码
  - 生成费用、返工率与交付完整性
  <divider color="subtle"/>
  <title size="md">主要证据</title>
  <text color="secondary" size="sm">角色素材 ID、分镜与时间线、生成服务任务记录、视频抽帧、音频检测、FFmpeg 输出日志及最终文件验证。</text>
</box>

部分技术条件可以自动检测，但剧情感染力、视觉风格和角色一致性的整体感知通常需要多种证据结合。

单个视觉模型的评分不能直接等同于观众的真实体验。

## 4.3 研究与文档专家

<box border radius="lg" padding={3} gap={2}>
  <title size="md">核心质量维度</title>
  - 事实准确性与来源可靠性
  - 引用是否真实支持对应结论
  - 论证是否完整、存在矛盾或遗漏
  - 事实、推断与假设是否清晰区分
  - 是否覆盖用户要求的范围
  - 结构、可读性与交付格式
  <divider color="subtle"/>
  <title size="md">主要证据</title>
  <text color="secondary" size="sm">原始来源、引用映射、事实核验结果、覆盖清单、论证结构与文档格式检查。</text>
</box>

对于研究报告，流畅的语言并不能证明结论可靠。尤其是高影响结论，需要更严格的来源核验和不确定性说明。

## 4.4 数据分析专家

核心质量维度应包括：

- 数据输入与 Schema 正确性；
- 数据清洗和转换可追溯性；
- 计算逻辑与统计方法正确性；
- 可复现性；
- 结果解释是否超出证据范围；
- 可视化是否准确表达数据。

主要证据包括原始数据引用、转换步骤、计算代码、校验结果和可复现输出。

## 4.5 Router 与 Planner 本身也需要评测

不能只评测最终产物，还要评测决定任务如何执行的上游组件。

Router 应评测：

- 是否选择了适合的专家；
- 是否正确识别多领域任务；
- 是否能够发现能力缺口；
- 是否在不确定时合理澄清或回退；
- 是否避免不必要的专家调用。

Planner 应评测：

- 是否覆盖所有必要子目标；
- DAG 依赖是否正确；
- 是否存在无意义节点；
- 是否遗漏关键验收步骤；
- 计划是否符合预算与执行环境；
- 上游变更后是否正确识别下游影响。

但需要注意，Router 选择了与标准标签不同的专家，不一定意味着路由错误。只要另一专家同样具备所需能力，并且实际完成质量合格，就应允许评测记录多个合理路径。

因此，Router 的评测不能完全依赖单一的“标准答案专家 ID”。

# 五、ReAct、Plan、专家和 DAG：怎样分别评测？

这是 EvoAgent 架构中的一个关键问题。

Router、Planner、ReAct 循环、专家和 DAG 处于不同层级。如果全部使用最终任务成功率来评价，就很难知道到底是哪一部分产生了改善或退化。

建议建立分层评测模型。

| 对象 | 主要评测目标 | 关键证据 |
|---|---|---|
| Router | 能力匹配、路由准确性、澄清与回退质量 | 任务标签、候选专家、路由决策与最终结果 |
| 专家 | 领域任务质量、约束遵守和专业能力 | 领域评测集、产物与验收结果 |
| Planner | 子目标覆盖、依赖正确性、计划成本与可执行性 | DAG 版本、依赖图、执行结果 |
| ReAct 循环 | 行动选择、反馈利用、无进展检测和停止时机 | 每轮动作、观察结果、策略变化 |
| 工具执行器 | 操作正确性、幂等性、权限与副作用控制 | 操作账本、工具回执和实际状态 |
| 记忆系统 | 检索相关性、事实保持、过期信息处理 | 记忆引用、来源、检索结果和下游表现 |
| 上下文系统 | 关键约束保留、压缩损失和 Token 效率 | 压缩前后信息覆盖、任务结果 |
| 专家团队 | 协作增益、交接质量、重复劳动与协调成本 | 工作包、交接事件、产物与团队总成本 |
| DAG 执行器 | 调度效率、恢复能力、依赖失效处理 | 节点状态、关键路径和恢复记录 |
| 自进化控制器 | 改进候选质量、评测有效性与回滚能力 | 实验记录、评测报告、发布及回滚结果 |

## 5.1 评测过程能力与最终结果必须分开

例如，一个任务最终失败，但 Planner 的分解完全合理，真正的问题是外部 API 长时间不可用。

不能因此直接判定 Planner 质量很差。

同样，某个任务最终成功了，也不意味着 ReAct 策略优秀。如果它调用了十次不必要的工具，只是偶然得到了正确结果，那么它的效率和稳定性仍然值得改进。

因此，QEEG 需要把以下两类结论分别记录：

- **结果质量：** 最终交付是否满足要求；
- **过程质量：** 路由、规划、工具使用、恢复和协作是否合理。

两者相关，但不能相互替代。

## 5.2 ReAct 不能仅凭轮数评价

ReAct 循环的目标不是尽可能减少思考轮数，而是通过观察和行动逐步解决问题。

一个简单任务只需要一轮就完成，是合理的；一个复杂故障可能需要多轮诊断和验证。

因此，ReAct 评测应关注：

- 每轮是否获得了有价值的新信息；
- 动作是否有明确目的；
- 观察结果是否改变了后续决策；
- 是否重复尝试已经证明无效的方法；
- 是否识别出无进展循环；
- 是否在证据充分时停止；
- 是否在达到预算或安全边界时及时停止。

这样才能将“有效探索”和“无效循环”区分开。

# 六、评测集设计：系统如何知道自己有没有进步？

没有可靠的评测集，就无法可靠地比较版本。

但单一的固定测试集也不够。随着 EvoAgent 不断改进，它可能逐渐适应已有案例，却无法处理新的任务分布。

建议建立四类互补的评测集。

<box border radius="xl" padding={3} gap={3}>
  {#each [
    ["1. 固定回归集","长期保留，用于比较版本并发现已经修复的问题是否再次出现。"],
    ["2. 领域基准集","覆盖编程、研究、漫剧、数据分析等领域的代表性任务。"],
    ["3. 困难与对抗案例集","覆盖边界条件、歧义任务、提示注入、故障恢复与容易失败的案例。"],
    ["4. 新鲜度评测集","定期引入未参与调参的新任务，检查能力是否能迁移到未知场景。"]
  ] as item}
    <box gap={1}>
      <title size="md">{item[0]}</title>
      <text color="secondary" size="sm">{item[1]}</text>
    </box>
    {#if item[0]!=="4. 新鲜度评测集"}
      <divider color="subtle"/>
    {/if}
  {/each}
</box>

## 6.1 固定回归集：保证过去解决的问题不会反复出现

假设编程专家曾经发生过一个严重问题：修改代码时错误地删除了一个兼容接口。

修复之后，应将这个案例及其验证条件加入固定回归集。

后续修改 Router、Planner、上下文压缩、代码技能或执行器时，只要相关依赖发生变化，就应重新运行适用的回归测试。

但回归集不应该无限增长而不做治理。应保留高价值案例，并合并重复、失效或不再适用的测试，同时记录测试集版本和变更原因。

## 6.2 困难案例集：重点测试系统容易犯错的地方

困难案例可以来自：

- GECO 发现的真实失败；
- SOCDEA 已确认或高度怀疑的根因；
- 用户纠正过的结果；
- 曾经导致返工的任务；
- 边界条件和罕见输入；
- 跨专家协作失败；
- 模型切换或断网后的恢复问题；
- 自进化过程中出现的回归。

这些案例可以形成一个持续扩展的知识资产，但需要脱敏、版本化和适当的隐私控制。

## 6.3 防止评测集污染

如果候选模型能够提前看到所有正式测试案例，并针对这些案例专门调整，它可能在评测集上表现很好，却没有真正提高泛化能力。

建议将评测数据分成：

- 开发集：允许用于调试和改进；
- 验证集：用于比较候选策略；
- 保留测试集：用于正式晋升判定；
- 真实运行观察集：用于评估部署后的实际表现。

对于个人项目，不一定需要复杂的数据科学平台，但至少要避免让候选版本随意修改正式测试集及其预期结果。

当保留测试集被大量重复用于优化时，也应考虑数据泄漏和过拟合风险，必要时引入新的独立案例。

## 6.4 评测集必须跟随任务分布变化

用户的使用方式可能改变，模型和工具也可能升级。

因此，评测集应同时包含历史代表性任务和近期真实任务。

如果 EvoAgent 从主要处理简单问答，逐渐转向代码工程和复杂视频制作，那么仅依赖早期的通用问答集就不再足以衡量系统的真实能力。

但新任务也不能直接覆盖旧的回归集。正确做法是保留历史稳定基线，并通过版本化更新扩展评测覆盖。

# 七、模型评审的局限：评测者自己也可能出错

对于代码风格、文档质量、视觉连贯性等难以完全规则化的任务，模型辅助评审具有实际价值。

但如果评测者和被评测者存在相同的盲点，或者评测提示词对某种风格有偏好，评分就可能产生系统性偏差。

因此，QEEG 不应把单个模型的主观评分当成绝对真值。

## 7.1 建立模型评审的校准机制

建议对模型评审器持续检查：

- 与人工评审的一致程度；
- 对同一结果重复评审的稳定性；
- 是否偏好较长、较流畅或特定风格的输出；
- 是否能识别事实错误和证据不足；
- 是否容易被无关的措辞、排序或格式影响；
- 在不同任务类型中的表现是否一致。

评审器可以有自己的版本、评测集和发布记录。

如果评审器本身发生变化，就需要重新检查其评分与历史结果之间的可比性。

## 7.2 使用多种证据，而不是简单堆叠多个模型

三个模型给出相同判断，并不必然意味着结论可靠，尤其当它们共享类似的训练偏差或信息来源时。

更合理的做法是让不同评测方法承担不同职责。

例如：

- 测试验证代码能否正确运行；
- 静态分析检查特定缺陷；
- 独立模型审查设计与可维护性；
- 人工评审处理重要的架构取舍。

这些方法提供的是不同类型的证据，比单纯增加相似模型的投票数量更有价值。

## 7.3 评分必须提供依据

模型辅助评审至少应输出：

- 评价维度；
- 评分或结论；
- 支持该结论的产物引用；
- 发现的问题；
- 证据不足的部分；
- 评审器版本；
- 是否需要人工复核。

如果评审器无法指出结果中具体存在什么问题，就不应该让它单独决定高风险任务的发布。

## 7.4 不确定时应该升级，而不是伪造精确度

对于主观任务，可以采用等级或区间，而不是强行给出精确到小数点的分数。

例如，视觉连贯性可以标记为“符合要求”“存在可改进问题”或“无法确认”。

如果某项评测结果对发布决策非常关键，而评审器又缺乏足够的校准证据，就应该增加独立评审或人工检查。

# 八、统计显著性与真实进步：如何避免被随机波动欺骗？

即使评测方法正确，也可能因为样本太少而得出错误结论。

例如，某个 Router 版本在 20 个任务中正确选择了 18 次，另一个版本正确选择了 19 次。

这一个任务的差异不足以证明新版本一定更好。

对于随机性较强的模型，评测还会受到生成随机性、外部服务变化、运行环境和任务难度的影响。

## 8.1 建立配对比较机制

当比较两个版本时，尽量让它们使用相同的任务集、相同的验收标准和可比的运行条件。

例如：

- 旧 Router 与新 Router 使用相同的请求集；
- 旧技能与新技能处理相同的代码修复案例；
- 旧上下文压缩策略与新策略使用相同的任务输入；
- 旧恢复机制与新恢复机制注入相同类型的故障。

配对比较能够减少任务难度差异带来的干扰。

但对于会产生外部副作用的真实任务，应在隔离环境或模拟工具中进行比较，不能为了测试而重复提交真实订单、消息或其他不可逆操作。

## 8.2 同时报告效果大小与不确定性

建议评测报告包含：

- 样本量；
- 指标变化；
- 任务类型分布；
- 统计不确定性；
- 失败案例；
- 资源成本；
- 是否满足所有硬性门槛。

对于成功率这类比例指标，可以使用置信区间或其他适合的方法；对于主观评分，应关注评审一致性和评分分布。

统计显著性也不等于实际价值显著。一个极小的提升即使在大样本下具有统计显著性，也可能不足以抵消新版本的维护成本。

## 8.3 建立多目标晋升规则

例如，某个版本：

- 成功率提高；
- 成本下降；
- 延迟略有上升；
- 安全测试没有退化；
- 可靠性指标保持稳定。

它可能是一个值得晋升的候选，但是否晋升仍取决于任务类型和预先确定的约束。

建议采用以下判定顺序：

1. 检查安全与权限硬门槛；
2. 检查必要的功能和质量门槛；
3. 检查可靠性与恢复要求；
4. 比较成本、延迟与资源表现；
5. 评估统计不确定性和实际收益；
6. 决定发布、继续测试、人工复核或拒绝。

不能把所有指标压缩成一个综合分数，再让高效率抵消严重的安全或质量退化。

# 九、多专家协作是否真的有价值：建立反事实评测

EvoAgent 采用多专家架构，但不能默认多专家一定优于单专家。

有些任务需要专业分工；有些任务增加专家，只会增加协调开销和重复推理。

因此，QEEG 应单独评估协作机制的真实收益。

## 9.1 建立三种对照方案

以一个复杂代码修复任务为例，可以比较：

- A：由单个编程专家完成；
- B：由编程专家完成，并使用独立测试专家；
- C：由多个专家分工，包括分析、实现、测试和代码审查。

比较时，应尽可能使用相同的任务目标、验收标准、资源约束和可比的模型能力。

需要注意，公平比较不一定意味着所有方案使用相同数量的模型调用。多专家方案本身就可能需要更多调用，因此应同时比较：

- 在相同预算下的质量；
- 达到相同质量所需的成本；
- 完成时间；
- 返工率；
- 缺陷漏检率；
- 协调开销；
- 最终交付的稳定性。

## 9.2 建立协作净收益指标

可以用以下形式表达协作净收益：

\[
G_{\text{team}}
=
V_{\text{team}}
-
V_{\text{baseline}}
-
C_{\text{coordination}}
\]

其中：

- \(V_{\text{team}}\)：团队方案相对于任务目标的综合价值；
- \(V_{\text{baseline}}\)：基线方案的综合价值；
- \(C_{\text{coordination}}\)：额外的协调、重复工作和资源成本。

实际评测时，各项需要采用统一口径，不能直接把不同单位的原始数值相减。

如果团队方案提高了缺陷检测率，但明显增加成本，那么它可能适合高风险任务，却不适合简单修改。

## 9.3 建立按任务类型选择协作策略的规则

建议最终形成一套有证据支持的策略：

- 简单任务优先单专家；
- 存在独立验证价值的任务采用双专家或专家加确定性验证器；
- 可分解且具有明显并行收益的任务采用小团队；
- 高风险任务增加独立审查；
- 协作收益不足或协调成本过高时，回退到更简单的执行方案。

这使 MEODT 的动态组队不只是根据任务描述决定“找几个人”，而是根据历史评测确定不同组队策略在什么条件下真正有效。

# 十、用户反馈：怎样把真实使用中的问题变成可靠改进？

固定评测集能够发现已知问题，但无法覆盖用户所有真实需求。

因此，QEEG 还需要利用用户反馈和真实任务结果。

不过，用户反馈也不是绝对真值。

用户可能因为结果不符合预期而给出低分，也可能因为表达流畅而给出高分，即使结果中存在事实错误。

## 10.1 区分反馈类型

建议把反馈分为：

- **目标修正：** 用户说明原本真正想要的结果；
- **事实纠正：** 用户指出明确的错误；
- **质量评价：** 用户评价可读性、视觉效果、代码风格等；
- **行为纠正：** 用户指出系统做了不该做的操作；
- **效率反馈：** 用户指出过程太慢、太贵或过于繁琐；
- **长期结果反馈：** 用户报告产物在真实使用中是否有效。

不同反馈需要不同的处理方式。

例如，用户说“这个答案太长”，可以作为表达偏好的证据，但不能直接推导出所有任务都应该缩短上下文。

用户指出“这个函数返回错误值”，则应进一步通过代码、测试或实际行为核验。

## 10.2 建立反馈到评测案例的闭环

建议采用以下流程：

<box border radius="xl" padding={3} gap={2}>
  {#each [
    ["1. 收集反馈","记录反馈类型、关联任务、产物版本和用户明确表达的要求。"],
    ["2. 判断反馈性质","区分目标变化、真实缺陷、主观偏好与证据不足的意见。"],
    ["3. 核验问题","通过测试、来源核验、产物检查或必要的用户澄清确认问题。"],
    ["4. 形成回归案例","把已确认、可复现且具有长期价值的问题加入适当评测集。"],
    ["5. 生成改进候选","由对应专家或 SOCDEA 提出修复方案。"],
    ["6. 独立评测","验证新方案是否解决问题，以及是否引入新的退化。"],
    ["7. 受控发布","由 SELCIA 按晋升规则发布并持续观察。"]
  ] as item}
    <box gap={1}>
      <title size="md">{item[0]}</title>
      <text color="secondary" size="sm">{item[1]}</text>
    </box>
    {#if item[0]!=="7. 受控发布"}
      <divider color="subtle"/>
    {/if}
  {/each}
</box>

## 10.3 用户习惯与客观质量必须分开

这一点与此前讨论的用户记忆系统直接相关。

例如，用户长期偏好简洁的代码解释，这是可以逐步学习的个人偏好。

但如果用户偏好简短回答，并不代表系统可以省略必要的安全警告、测试结果或关键限制。

建议将用户偏好纳入个性化质量契约，而不是修改全局的客观正确性门槛。

这样，EvoAgent 可以逐渐适应用户，同时不至于把个人偏好误当成适用于所有人的普遍规则。

## 10.4 真实结果反馈应考虑延迟和归因

一些任务的真实价值要过一段时间才能体现。

例如：

- 生成的代码可能在后续集成时才暴露缺陷；
- 研究报告可能在决策时才发现引用不准确；
- 漫剧可能在发布后才获得真实观众反馈；
- 自动化工作流可能运行数周后才显现维护成本。

因此，QEEG 应允许长期结果反馈与原任务关联。

但不能把后续出现的所有问题都归因于最初的智能体版本。中间的需求变化、环境变化和用户修改也需要纳入分析。

# 十一、与现有模块的职责边界

| 模块 | 在 QEEG 中的职责 |
|---|---|
| QEEG | 定义统一评测协议、质量契约、评测集治理和晋升证据要求 |
| UQEAG | 执行任务级验收，确认产物是否满足质量契约 |
| Router | 提供路由决策及相关证据，接受路由质量评测 |
| Planner / DAG | 提供计划与执行结构，接受计划质量和调度结果评测 |
| MEODT | 提供专家分工、交接和协作数据，接受协作净收益评测 |
| GECO | 提供事件、追踪、版本、产物血缘和运行证据 |
| SOCDEA | 分析失败原因，提出根因假设与改进候选 |
| RERA | 提供故障恢复、状态一致性和可靠性评测结果 |
| APRO | 提供成本、延迟、资源和调度效率数据 |
| TSEG / PCP | 保护正式评测集、权限规则和评测发布边界 |
| CEKCE / CIL | 管理能力版本与复用情况，关联技能级评测 |
| MEEG / CLEK / ACMO | 提供记忆与上下文相关的质量证据 |
| SELCIA | 根据独立评测证据管理候选晋升、部署与回滚 |
| HACCG | 呈现用户可理解的结果、限制与必要的人工确认 |

这里要特别明确：

**UQEAG 负责判断一个具体任务是否合格，QEEG 负责定义并治理整个系统怎样证明合格。**

两者密切相关，但不能混为一个模块。

## 13.1 第一版必须通过的验收测试

建议用一个真实的代码修复任务完成质量闭环。

1. 用户提出需求，Router 选择编程专家。
2. Planner 生成任务 DAG 和明确的验收契约。
3. 专家完成代码修改，GECO 记录执行过程和产物版本。
4. UQEAG 执行测试、静态分析及必要的人工确认。
5. QEEG 汇总证据，分别判断硬门槛与可权衡指标。
6. 系统记录任务质量、成本、耗时和失败原因。
7. 将该任务加入适当的回归集，保留契约与评测版本。
8. 生成一个改进候选，在相同评测条件下与旧版本比较。
9. 如果质量或安全硬门槛失败，候选不得晋升。
10. 如果证据不足，系统应保留不确定状态，而不是自行宣布进步。

这条链路跑通后，EvoAgent 才具备真正可操作的质量进化基础。

# 十四、下一专项：知识资产、技能生命周期与能力复用治理

目前，我们已经设计了能力的执行、观测、安全、恢复、资源优化与质量评测。

但还存在一个重要问题：随着系统持续运行，它会积累越来越多的技能、工作流、记忆、修复方案和经验案例。

如果不对这些资产进行系统治理，EvoAgent 可能逐渐出现：

- 同一种能力被重复实现；
- 新旧技能互相冲突；
- 过期技能继续被 Router 选中；
- 某次偶然成功被误认为通用经验；
- 工作流升级后，依赖它的技能仍然使用旧接口；
- 技能数量不断增加，但真正可复用的能力没有提高；
- 历史失败被记录了，却没有转化为可验证的长期知识。

因此，下一专项建议定义为：

**Knowledge & Capability Lifecycle Governance，简称 KCLG。**

重点研究：

1. 如何区分用户记忆、领域知识、技能、工作流、评测案例和执行经验；
2. 如何判断新能力应该创建、扩展现有能力，还是复用已有能力；
3. 如何建立能力的版本、依赖、来源和适用范围；
4. 如何判断一次成功究竟是可复用经验，还是偶然结果；
5. 如何防止错误记忆、过期知识和未经验证的经验进入共享能力库；
6. 如何评估技能的真实复用价值与维护成本；
7. 如何管理技能的晋升、降级、冻结、弃用与退役；
8. 如何在技能升级后识别受影响的工作流和依赖节点；
9. 如何避免多个专家重复创建相似技能；
10. 如何把 GECO 的故障证据和 QEEG 的评测案例转化为长期能力改进；
11. 如何让领域专家拥有专业知识，同时避免全局记忆被某一领域的经验污染；
12. 如何在本地存储有限的情况下进行知识压缩、去重和归档；
13. 如何让系统在复用旧能力时检查版本兼容性、安全状态和适用条件；
14. 如何判断某项能力应该继续维护、重新设计，还是彻底退役。

这个专项与 CEKCE、CIL、MEEG 和 CLEK 密切相关，但职责仍然需要明确：记忆系统负责保存和检索信息，能力系统负责执行与复用，KCLG 则治理这些资产从产生到退役的整个生命周期。

其核心原则是：

**积累更多记忆和技能，不等于获得更多可靠能力；只有来源清晰、适用范围明确、经过验证且能够持续维护的知识资产，才能真正提高 EvoAgent 的长期能力。**

完成 KCLG 后，我们就能进一步解决 EvoAgent 的长期成长问题：不仅能从失败中改进，还能将有效经验沉淀为可复用、可验证、可维护的能力资产，并避免系统随着时间推移变得越来越臃肿、混乱和脆弱。
