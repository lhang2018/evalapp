## ChatGPT

是的，而且这恰恰是 EvoAgent 架构中非常重要的一点。**EvoAgent 不是一个通用智能体包办所有任务，而是一个统一入口、多个领域专家、共享基础能力、独立进化的智能体系统。**

我刚才梳理 Android 设备边界时，没有把多专家架构完整展开。这部分应该补回总体设计，而且会直接影响路由、记忆、工作流和进化机制。

## 二、为什么一定要划分专家？

因为我们要解决的不是简单的多角色对话，而是**不同能力的独立优化与互不干扰**。

例如：

- 编程专家优化了代码调试策略，不应自动改变旅游专家的行程规划策略。
- 手机操作专家发现某个应用的界面定位失败，应先检查应用适配器、无障碍权限和界面变化，而不是直接修改通用 ReAct 内核。
- AI 漫剧专家优化分镜生成流程，不应让通用任务专家的模型调用成本无条件增加。
- 通用内核发现跨领域的上下文截断问题，才应考虑进行共享基础能力改进，并重新评测所有受影响的专家。

这意味着每一次改进都必须回答两个问题：

1. **问题属于哪一层？** 通用内核、某个专家、具体工具、某个工作流，还是特定模型适配？
2. **改进影响哪些对象？** 只影响一个任务实例、一个工作流、一个领域专家，还是多个专家共同使用的基础能力？

不能仅凭一条失败日志就认定某个组件有问题。

## 三、专家应该拥有哪些独立能力？

| 组成部分 | 是否独立 | 说明 |
|---|---|---|
| 专家身份、职责和提示词 | 是 | 各专家拥有独立的专业配置和版本 |
| 专家 Planning / ReAct 策略 | 可独立配置 | 根据领域复杂度和风险采用不同执行策略 |
| 领域记忆 | 是 | 专业经验、任务案例与领域知识分区管理 |
| 工具与工作流 | 是，按需复用 | 每个专家声明可使用的工具和工作流 |
| 模型配置 | 可独立配置 | 可选不同模型、参数、路由和成本预算 |
| 通用安全与权限内核 | 共享且受保护 | 专家不能自行放宽系统权限 |
| 运行日志与评测 | 独立分组 | 既能分析单个专家，也能评估跨专家影响 |
| 进化控制器 | 统一治理、分域执行 | 管理所有专家的候选改进和发布门禁 |

这里有一个细节：并不是每个专家都必须拥有完全独立的记忆数据库。更合理的是统一记忆基础设施，使用独立命名空间、访问策略和记忆分类，必要时再对共享事实进行授权复用。

## 四、用户的复杂任务可以由多个专家协作吗？

可以，而且不能只支持单专家路由。

例如，用户说：

“帮我制作一部 60 秒的 AI 漫剧，主题是未来城市，同时发布到指定平台。”

任务入口可能识别出多个子任务：


    **总任务规划器**
    拆解目标、依赖关系、预算与验收标准


    <grid-item>

        **漫剧专家**
        剧本、角色、分镜

    </grid-item>
    <grid-item>

        **媒体生成能力**
        图片、视频、配音

    </grid-item>
    <grid-item>

        **媒体处理能力**
        FFmpeg、合成、质检

    </grid-item>
    <grid-item>

        **手机操作专家**
        发布前准备与授权操作

    </grid-item>


    **总任务验收**
    检查时长、画面、音频、文件完整性与发布结果


实际执行时由总任务规划器建立 DAG，明确哪些步骤可以并行、哪些必须等待前置结果，以及失败后重试、回滚或请求用户确认的规则。媒体生成能力可以是工具服务，不一定非要设计成一个独立智能体。

涉及真正发布内容、公开发送信息等外部副作用时，还要执行对应的权限和确认策略。

## 五、专家系统与自进化系统是什么关系？

这是整个 EvoAgent 最核心的架构关系之一：

- **专家系统负责做事。**
- **共享运行时负责执行和治理。**
- **进化系统负责分析问题、提出改进、验证效果和受控发布。**

每个专家可以有独立的进化分支和版本档案，例如：

```text
EvoAgent
├── shared-core
│   ├── context-management
│   ├── memory-engine
│   ├── react-runtime
│   └── safety-kernel
├── experts
│   ├── general
│   ├── coding
│   ├── travel
│   ├── phone-operation
│   └── ai-drama
├── model-profiles
│   ├── model-A
│   └── model-B
└── release-manifests
```

这只是逻辑组织示意，不要求 Git 仓库必须采用完全相同的目录。

当模型切换时，可以保存旧模型适配配置和对应的专家版本，再从新模型的适配分支继续优化。切换模型不应自动覆盖原来已经验证过的版本。

**最终应该形成的是：一个统一入口、多个领域专家、共享但受保护的通用内核、统一进化治理、独立专家版本，以及面向不同设备的执行适配器。**

这样既能让每个专家持续提升，又能避免某个场景的局部改进破坏其他领域的稳定性。
