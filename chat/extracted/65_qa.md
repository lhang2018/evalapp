# EvoAgent 第十专项：不确定性判断与主动决策系统

这一轮我们继续研究智能体内部的核心智能机制。

前面已经设计了路由、规划、ReAct、记忆、经验学习、自我诊断和自我修复。现在需要解决一个贯穿所有模块的问题：

**EvoAgent 在什么情况下应该相信当前判断，什么情况下应该进一步验证，什么情况下应该向用户提问，以及什么情况下应该停止行动？**

这决定了智能体究竟是一个真正可靠的个人助手，还是一个看起来很有能力、实际却可能盲目行动的系统。

举几个例子：

- 用户说“帮我打开微信”，目标明确、风险低，通常不需要反复询问。
- 用户说“把这个整理一下”，但没有提供对象，系统可能需要澄清。
- 用户让智能体修改代码，模型认为已经完成，但测试尚未运行，就不能直接宣布全部成功。
- 用户让智能体发送一条消息，收件人和内容虽然明确，但发送会产生外部副作用，需要满足相应授权条件。
- 云端请求超时，系统无法判断任务是否已执行，这不是简单的失败，而是结果不确定。
- 一个问题连续修复三次仍然失败，系统应该考虑更换策略或停止，而不是继续消耗预算。

所以，我们需要的不是一个简单的“模型置信度”，而是一套贯穿理解、决策、执行、验证和恢复的**不确定性治理机制**。

## 一、首先区分五种不确定性

我建议不要把所有不确定性都压缩成一个数字。它们的来源不同，解决方法也不同。


    <title size="lg">U1：意图不确定性</title>
    系统是否理解了用户真正想要的结果？
    示例：用户说“把它处理一下”，但不知道“它”指什么，也不知道期望的处理方式。


    <title size="lg">U2：知识不确定性</title>
    系统是否掌握足够可靠的信息来作出判断？
    示例：模型不确定某个 Android API 在当前系统版本中的行为。


    <title size="lg">U3：状态不确定性</title>
    系统是否知道真实环境当前处于什么状态？
    示例：启动应用的请求已经提交，但无法确认应用是否进入前台。


    <title size="lg">U4：结果不确定性</title>
    即使操作已经完成，系统是否有足够证据确认结果满足目标？
    示例：代码已保存，但还没有运行测试。


    <title size="lg">U5：策略不确定性</title>
    系统是否知道哪种执行方案最适合当前任务？
    示例：不确定使用 AST 重构还是简单文本补丁更稳妥。


这五类不确定性不能用同一种方法解决。

- 意图不确定，可能需要询问用户。
- 知识不确定，可能需要检索资料或调用专业工具。
- 状态不确定，应该重新观察实际环境。
- 结果不确定，应该执行验收。
- 策略不确定，可以比较方案、开展低风险试验，或选择更稳妥的执行方式。

这是本专项的第一项核心原则：**先判断不确定性来自哪里，再决定如何降低它。**

# 二、建立独立的不确定性评估引擎

建议增加 `Uncertainty Assessment Engine`，但它不应该成为每个任务都必须调用一次的大模型。

它的主要职责是整合多个组件已有的信号，判断当前任务的哪些部分仍然不确定，以及这种不确定性是否会影响下一步决策。

它可以使用四类信息：

1. **确定性信号**：工具返回码、参数校验、测试结果、状态查询结果。
2. **模型判断信号**：多个方案的差异、未解决的假设、对任务理解的分歧。
3. **历史经验信号**：当前能力在相似任务、相同模型和相似环境中的实际表现。
4. **环境信号**：网络状态、权限、资源限制、界面变化、远端任务是否可查询。

注意：这不是把四类信号简单平均成一个分数。不同信号回答的问题不同，而且可靠程度也不同。

例如，编译器报告语法错误，是关于语法正确性的强证据；模型说“我有 95% 把握代码正确”，则不能代替编译和测试。

## 2.1 统一的不确定性记录

每个关键决策可以产生一条 `UncertaintyAssessment`：

重点在于：系统不只是记录“我不确定”，还要说明**具体不确定什么、缺少什么证据、判断错了有什么后果，以及下一步哪种动作最有价值**。

## 2.2 不确定性评估不必每一步都调用模型

建议采用两级机制：

- **快速评估层**：通过规则、任务状态和现有证据判断是否存在明显缺口。
- **深度评估层**：当问题复杂、证据冲突或风险较高时，调用模型进行分析，必要时使用独立评审或专项工具。

例如，测试尚未运行时，快速评估层就可以判断“代码正确性尚未得到测试验证”，不需要额外调用大模型来回答这个问题。

只有当系统需要判断“是否值得运行昂贵的集成测试，还是先进行更便宜的静态分析”时，才可能需要更复杂的决策。

这样既能控制成本，也能避免把本来可以确定性解决的问题交给模型自由推理。

# 三、不要把置信度当成真实概率

这是整个系统必须特别注意的地方。

模型给出 0.9 的置信度，并不意味着它在类似任务中有 90% 的概率正确。

因此，EvoAgent 应该区分三个概念：

| 概念 | 含义 | 例子 |
|---|---|---|
| 主观置信度 | 模型或判断器认为答案有多可信 | 模型认为某个 API 用法正确 |
| 经验校准概率 | 相似条件下，历史判断实际正确的比例 | 同类代码诊断在独立测试集上的准确率 |
| 证据充分性 | 当前是否具备足够证据支持这个结论 | 编译和必要测试是否通过 |

它们不能相互替代。

一个模型可能对答案非常自信，但知识已经过时；一个判断器可能在相似任务中表现很好，但当前输入缺少关键条件；一个结论即使概率上很可能正确，也可能因为后果严重而必须进一步验证。

## 3.1 如何校准能力判断？

建议按任务类型、模型版本、执行环境和风险级别，使用历史可验证结果进行校准。

例如，对编程任务分别统计：

- 语法分析是否正确；
- 修改方案是否满足目标；
- 测试结果是否符合预期；
- 最终验收是否成功。

对手机操作任务，则可以统计：

- 目标应用识别是否正确；
- 页面状态识别是否正确；
- 操作是否产生预期状态变化；
- 是否需要人工纠正。

这些指标比一个笼统的“智能体成功率”更有价值。

同时，校准数据需要保留样本量和不确定范围。只有三次成功的能力，不能因为成功率是 100%，就被认为已充分证明可靠。

## 3.2 不确定性也需要独立评测

建议评估：

- 高风险错误是否能被识别为不确定；
- 明显正确且证据充分的任务是否被过度质疑；
- 不确定性评分是否与实际错误率相关；
- 新模型和新工具上线后，旧校准是否仍然有效；
- 证据缺失时，系统是否能够拒绝作出无依据的成功声明。

最后一点尤其重要：**一个好的不确定性系统，不只是尽量答对，还应该尽量避免把没有证据的判断说成已经确认的事实。**

# 四、核心决策：下一步应该做什么？

识别不确定性之后，系统还必须选择行动。

我建议建立 `Active Decision Policy`，把下一步分成六类：

  {#each [
    ["A","直接执行","目标明确、证据足够、风险可接受，继续当前计划。"],
    ["B","补充证据","重新观察状态、读取文件、查询远端任务或运行测试。"],
    ["C","获取知识","检索资料、调用专业工具或向更合适的模型询问。"],
    ["D","比较方案","评估不同执行路径的成功可能性、成本、风险和可恢复性。"],
    ["E","向用户澄清","缺少的信息会显著改变执行方案，且无法安全推断。"],
    ["F","暂停或停止","风险不可接受、授权不足、预算耗尽或无法安全确认状态。"]
  ] as item}


        <title size="md">{item[0]}</title>


        **{item[1]}**
        {item[2]}


  {/each}

这些动作不是固定顺序。系统应该选择最符合当前不确定性来源、任务目标和风险边界的行动。

例如：

- 不知道当前手机页面是什么：先观察，不要问用户。
- 不知道用户想删除哪一个文件：应当澄清目标。
- 不知道代码是否正确：运行适当测试。
- 不知道某项外部 API 的最新行为：查阅权威资料或进行受控验证。
- 无法确认某个外部支付是否成功：暂停重复提交，优先查询状态。

## 4.1 引入“信息价值”判断

每一次额外行动都需要成本。系统应该判断：再做一步，能否实质性降低不确定性，并改善决策？

例如，代码修改后运行单元测试通常成本较低，而且能提供直接证据；再调用三个大模型评价同一段代码，可能成本更高，却没有增加多少独立证据。

因此，我建议引入 `Value of Information`（信息价值）机制。

其核心问题是：

> 获取这条新信息，能否改变当前决策？如果能，改变决策所带来的预期收益是否大于获取信息的成本？

概念上可以表示为：

\[
VOI(a)=
\mathbb{E}[\text{获得信息后最优决策的收益}]
-\text{当前最优决策收益}
-\text{获取信息的成本}
\]

这里的收益不仅包括成功率，还应考虑时间、费用、错误后果和恢复成本。

这个公式是决策框架，不意味着所有收益都能准确转换为一个数字。对于权限、安全和不可逆操作，仍然需要硬性规则，不能仅凭期望收益为正就自动执行。

## 4.2 一个实际例子

用户要求修改代码中的一个函数。

系统有三种选择：

- 直接应用补丁；
- 先解析 AST，再应用补丁；
- 调用更强的模型重新分析整个项目。

如果修改范围小、目标明确、补丁可逆，直接应用补丁并运行相关测试可能最划算。

如果涉及跨文件符号引用，AST 分析可能显著降低误改风险。

如果涉及复杂架构决策、需求本身存在冲突，才可能值得调用更强模型。

所以，系统不应该永远选择最便宜的方案，也不应该永远选择最强的模型，而应该选择**在当前风险与预算约束下，预期综合表现最好的方案**。

# 五、什么时候应该向用户提问？

个人智能体最容易出现两个极端：

- 过度自主：不确定也继续做，最后做错；
- 过度谨慎：一点不确定就问用户，用户反而成了系统的执行控制器。

EvoAgent 应该根据“这条信息是否会改变行动”和“错误行动的代价”来决定是否澄清。

## 5.1 建议采用四类判断

| 情况 | 建议行为 |
|---|---|
| 目标明确、低风险 | 直接执行 |
| 目标大体明确，细节可以安全推断 | 采用合理默认值，必要时告知用户 |
| 多种解释会导致明显不同的结果 | 先澄清 |
| 存在权限、隐私或重大不可逆风险 | 满足授权条件前暂停 |

例如，用户说“帮我整理桌面”，系统可以先检查桌面文件类型，提出分类方案；如果要批量删除文件，就不能把“整理”擅自解释成“删除”。

如果用户说“帮我给他发消息”，而“他”指代不明确，系统应该先确认收件人。即使历史记忆显示用户通常联系某个人，也不应在存在实质歧义时自动选择并发送。

## 5.2 设计澄清阈值，而不是统一置信度阈值

不同任务不应使用同一个提问阈值。

例如：

- 推荐一部电影：可以容忍较大的偏好不确定性；
- 制定旅行计划：可以先给出方案，再让用户调整偏好；
- 修改项目代码：可以在可逆范围内先分析和提出补丁；
- 删除文件、发送消息、支付：需要严格满足目标明确性和授权条件。

所以，澄清策略应该结合任务类别、错误代价、可逆性和用户负担，而不是规定“置信度低于 80% 就提问”。

## 5.3 用户偏好也可以影响澄清方式

如果用户已经明确表达了某些长期工作习惯，系统可以据此调整交互：

- 用户偏好先看方案：复杂任务先提供计划；
- 用户希望减少打扰：对低风险、可逆的细节采用合理默认值；
- 用户要求谨慎操作：扩大需要确认的操作范围。

但这些偏好不能覆盖当前明确指令，也不能绕过权限边界。用户希望“尽可能自动”不等于允许系统在目标不明确时自行执行不可逆动作。

# 六、什么时候应该停止继续思考或尝试？

这是控制成本和防止无效循环的关键。

前面已经设计了 ReAct 的步数限制和自我修复预算，但还缺少一个更智能的判断：即使预算还没有耗尽，是否已经不值得继续？

我建议区分三种停止。


    **成功停止**
    目标已经通过验收，继续调用模型或工具没有足够的额外收益。


    **暂时停止**
    缺少授权、等待网络恢复、远端任务仍在运行，或需要用户补充信息。


    **失败停止**
    已达到预算上限、连续尝试没有进展、存在不可接受风险，或现有能力无法可靠完成任务。


这里有一个很重要的区别：停止当前行动，不一定意味着放弃整个任务。

例如，云端视频生成服务暂时不可用时，智能体可以保存已完成的剧本、角色素材和分镜，暂停生成节点，等待服务恢复，而不需要重新执行整个漫剧工作流。

## 6.1 无进展检测

建议结合以下信号判断是否陷入循环：

- 连续调用相同工具，结果没有变化；
- 连续生成相同或高度相似的计划；
- 反复尝试已被证明无效的策略；
- 新一轮推理没有产生新的有效证据；
- 任务状态没有推进；
- 额外成本持续增加，但成功可能性没有明显改善。

当检测到无进展时，系统可以先切换诊断策略，再决定是否继续。

不能仅仅因为连续两次调用同一工具，就认定任务陷入循环。有些操作本来就需要重复执行，例如逐个处理多个文件。真正要判断的是：**重复是否符合当前计划，是否带来了预期状态变化。**

## 6.2 预期收益递减

假设某个代码错误已经经过三轮诊断：

- 第一次发现可能是类型不匹配；
- 第二次检查确认类型问题；
- 第三次修复后仍然测试失败，且没有新的证据。

此时继续使用相同方法的价值可能很低。系统应该切换到不同的诊断手段，或停止并报告剩余的不确定性。

但如果每一轮都产生了新证据，那么即使已经尝试三次，也可能值得继续。

因此，停止条件应结合预算、风险、信息价值和实际进展，而不是只依赖固定次数。

# 八、系统如何形成真正的闭环？

我建议让不确定性系统贯穿一次任务的完整生命周期。

  {#each [

这里最重要的是第 5 步：每次行动后，系统都应重新评估当前状态，而不是继续沿用执行前的判断。

例如，手机界面发生变化后，之前对按钮位置的判断可能已经失效；模型切换后，之前针对旧模型校准的能力概率也可能不再适用。

不确定性不是任务开始时评估一次就结束的静态属性，而是随着环境、证据和执行结果持续变化的状态。

# 十、下一专项：模型适配、能力迁移与版本进化

接下来，我建议进入一个与你最初的目标直接相关、但还没有彻底解决的专项：

**当 EvoAgent 从当前大语言模型切换到另一个模型时，如何保留已经积累的能力，又避免把只适用于旧模型的经验、提示词和执行策略错误地迁移过去？**

你最初提出的目标，是把当前环境、当前模型下已经优化好的智能体保存下来，在新的分支上继续优化另一种模型。这实际上要求系统具备明确的模型适配与能力迁移机制。

下一专项应该深入：

1. 哪些组件与模型无关，哪些高度依赖特定模型；
2. 如何保存模型版本、提示词、上下文策略、路由策略和评测结果的完整适配快照；
3. 如何判断某条经验是通用规律，还是旧模型特有的行为补偿；
4. 新模型上线时，如何评估工具调用、规划、记忆检索和验收能力；
5. 如何通过对照评测决定继承、重新校准、隔离或废弃旧策略；
6. 如何管理多个模型的独立优化分支；
7. 如何根据任务难度、成本和质量选择不同模型；
8. 如何避免模型切换后出现能力退化、成本失控或诊断错误；
9. 如何在保留旧模型稳定版本的同时，让新模型独立进化；
10. 如何将跨模型验证成功的改进晋升为真正通用的能力。

这会把 EvoAgent 的自进化机制进一步推进到一个重要目标：**不仅能适应一个模型，而且能持续适配不同模型，同时保留历史成果、控制迁移风险，并让每个模型的优化互不污染。**
