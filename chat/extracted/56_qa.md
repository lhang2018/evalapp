# EvoAgent 全量记忆系统设计：从存储信息到可治理、可验证、可进化的记忆

这一步我们要把 EvoAgent 的记忆系统单独设计完整。它不是一个简单的聊天历史数据库，也不是一个向量数据库，而是智能体长期运行的基础设施。

我建议先确定一个核心原则：

**记忆系统负责保存、组织、检索和治理信息；上下文系统负责决定本次推理使用什么信息；专家负责运用这些信息；评测与进化系统负责判断这些机制是否真的有效。**

这四个职责必须分开。

例如，编程专家曾经在某个项目中使用 AST 重构成功，这个事实可以保存为经验，但不能自动变成“所有代码重构都必须使用 AST”的全局规则。它还需要记录适用条件、证据和验证状态。

这里的分类有一个重要区别：用户记忆、项目记忆、领域记忆主要描述**信息属于谁、适用于哪里**；工作记忆描述**信息在任务执行生命周期中的用途**；事实和证据则描述**信息的内容、来源和可靠性**。

它们并不完全处于同一个分类维度。因此，一条项目事实也可以是某个任务的工作记忆，同时关联一条原始证据。

我们不应该为这些分类各自建立互不相通的数据库，而应该通过统一的数据模型和访问策略管理它们。

# 二、六类记忆分别负责什么？

先把每类记忆的职责、边界和共享规则冻结下来。

## 1. 用户记忆：跨任务了解用户

保存能够改善未来交互的稳定信息，例如：

- 用户明确要求长期遵守的偏好；
- 常见的沟通方式和输出格式；
- 稳定的工作习惯；
- 用户纠正后确认的交互规则。

**不能做的事：** 把一次临时要求直接升级成永久偏好，或者将模型对用户的猜测当作已确认事实。

## 2. 项目记忆：维持工作连续性

保存一个项目的：

- 项目目标和范围；
- 已经确认的架构决策；
- 技术选型和约束；
- 当前进度与待办事项；
- 历史问题、重要产物及依赖关系。

例如，EvoAgent 的 Android 优先战略、专家系统分层和独立进化控制器，都属于项目级的架构决策，而不是所有项目通用的用户偏好。

## 3. 领域记忆：积累某个专家的专业知识

由编程、旅游、AI 漫剧、手机操作等专家使用，包含：

- 领域概念和专业规则；
- 已验证的解决策略；
- 技术能力的适用条件；
- 领域常见故障与排查方法；
- 领域特定的验收标准。

领域记忆也不能成为一组未经验证、不断增长的提示词。它应该能够引用来源、关联专业技术能力，并标记规则是否仍然有效。

## 4. 经验记忆：保存执行过程中的经验

我建议把成功经验和失败经验分开管理，但使用统一的数据结构。

| 经验类型 | 保存内容 | 后续用途 |
|---|---|---|
| 成功经验 | 任务条件、采用的策略、验证证据 | 检索相似任务，复用有效方案 |
| 失败经验 | 失败阶段、可能根因、反例与证据 | 避免重复错误，辅助故障诊断 |
| 修复经验 | 故障与修复之间的验证关系 | 推荐已验证的修复方法 |
| 反例经验 | 某种策略在哪些条件下不适用 | 防止错误泛化 |
| 实验经验 | 候选版本、实验条件、结果和成本 | 支持进化决策 |

一次任务成功不意味着其全部执行步骤都值得复用；一次任务失败也不意味着所用策略完全错误。经验必须绑定具体条件，并且允许存在反例。

## 5. 工作记忆：保存当前任务的运行状态

工作记忆与普通长期记忆不同，它服务于任务的连续执行。

例如，一项复杂编程任务需要记住：

- 当前目标和不可违反的约束；
- 当前计划版本；
- 已完成的节点；
- 尚未完成的节点；
- 已尝试过的方法及其结果；
- 当前阻塞原因；
- 下一步可执行动作；
- 当前预算和剩余资源。

这部分信息不能只存在模型上下文中，否则上下文被压缩、App 被系统终止或网络断开时，任务就可能丢失进度。

**工作记忆应以可持久化的任务状态为依据，而不是依赖模型每次重新总结整个对话。**

## 6. 事实与证据：所有记忆的可信基础

事实和证据不应该被当成普通文本随意覆盖。

例如：

- 用户明确确认了一项要求；
- 工具实际返回某个测试失败；
- 评测器验证某个视频时长为 45 秒；
- 模型推测某个失败可能与上下文压缩有关。

这四种信息的证据强度完全不同。

因此，记忆系统需要区分**事实陈述、来源证据、模型推断和经过验证的结论**。后续记忆可以引用这些证据，但不能因为被反复复制，就自动获得更高可信度。

# 三、记忆的共享范围：全局可访问，不代表全局可见

这点对于你之前提出的多专家架构非常重要。

我建议采用分层命名空间与显式共享规则。


    **用户级记忆**
    经过授权的跨领域偏好与个人规则



    **项目级记忆**
    仅对指定项目及获授权的参与者可见



    <grid-item>

        **编程专家**
        编程知识与经验

    </grid-item>
    <grid-item>

        **漫剧专家**
        制作知识与经验

    </grid-item>



    **任务工作记忆**
    当前任务的状态、观察和恢复信息


这只是逻辑上的组织关系，不是严格的父子继承关系。

例如：

- 用户的输出偏好可以被编程专家和漫剧专家共同使用。
- 某个项目的技术选型不能自动泄露给其他无关项目。
- 编程专家验证的一条 Python 经验，可以在其他编程任务中复用，但不能自动成为所有专家的通用规则。
- 某个专家发现的通用改进建议，可以提交给共享能力评测流程，但不能直接修改共享内核。
- 工作记忆默认绑定具体任务，不应该因为内容有价值就永久保存。

我还建议引入**显式记忆共享机制**：某条记忆需要跨项目、跨专家使用时，应当明确其共享范围、适用条件和授权，而不是默认所有专家可以读取全部记忆。

# 四、记忆从产生到退出，需要完整生命周期

记忆系统最容易出现的问题不是“存不进去”，而是存进去之后没有治理，最终充满过期事实、错误经验和相互矛盾的规则。

因此，我建议所有长期记忆采用统一生命周期。

    ["04","质量检查","检查重复、冲突、敏感性、时效性和潜在误泛化。"],

这里需要区分三种操作：

- **更新**：旧信息被新信息修正或替代，必要时保留历史审计记录。
- **失效**：信息不再适用，例如旧 API 版本的使用经验，但可能仍有历史价值。
- **删除**：根据授权与数据生命周期规则，删除实际存储及应同步清理的副本、索引和缓存。

不能把删除简单实现为给数据库记录加一个 `deleted=true`，却继续在向量索引、缓存或其他副本中检索到已删除内容。

## 4.1 记忆状态与可信度应该分开

我建议至少区分两个维度。

生命周期状态

- `CANDIDATE`：候选，尚未正式接受。
- `ACTIVE`：当前可用。
- `STALE`：可能过期，需要重新验证。
- `SUPERSEDED`：被新版本替代。
- `REVOKED`：已撤销，不再用于正常推理。
- `ARCHIVED`：归档，仅在特定历史查询中使用。

证据与验证状态

- `USER_CONFIRMED`：用户明确确认。
- `SOURCE_OBSERVED`：来源或工具实际观察到。
- `INFERRED`：系统推断。
- `EXPERIMENTALLY_VALIDATED`：在明确的实验条件下验证。
- `INDEPENDENTLY_VERIFIED`：有独立验证证据支持。

这两个维度不能合并。例如，一条曾经被独立验证的 API 使用经验，随着 API 升级仍然可以保留原始证据，但其当前适用状态应变为 `STALE`。

同样，用户确认的偏好可以具有明确的来源，但这不意味着它在所有未来情境下都必须生效；当前明确指令仍然可能覆盖它。

# 五、统一记忆数据模型：不要只存一段文本

建议以关系型数据库作为结构化记忆的权威记录，并根据检索规模选择全文索引、向量索引或关系索引作为辅助。

一条长期记忆至少应具有以下逻辑字段：

| 字段 | 作用 |
|---|---|
| `memory_id` | 稳定唯一标识 |
| `owner_id` | 所属用户或主体 |
| `namespace_id` | 用户、项目、专家或任务范围 |
| `memory_type` | 偏好、事实、经验、约束等 |
| `content_ref` | 内容本身或受控内容引用 |
| `source_refs` | 原始消息、工具结果、证据或文档引用 |
| `scope` | 适用范围及限制条件 |
| `verification_status` | 信息来源和验证状态 |
| `confidence` | 适用时使用的置信度或不确定性 |
| `valid_from` / `valid_until` | 有效时间范围 |
| `status` | 当前生命周期状态 |
| `sensitivity` | 隐私和访问级别 |
| `version` | 记忆版本 |
| `supersedes_id` | 被替代的旧记录 |
| `created_at` / `updated_at` | 生命周期时间戳 |

此外，还需要独立管理记忆之间的关系，例如：

- 支持或反驳；
- 与另一条记忆冲突；
- 派生自某条证据；
- 适用于某种任务条件；
- 替代另一条规则；
- 由某次实验验证。

这些关系可以独立存储，不需要把所有内容压进一个 JSON 字段。

## 5.1 记忆类型也需要结构化

例如，偏好记忆可以额外记录：

- 偏好维度；
- 倾向方向；
- 适用场景；
- 用户明确程度；
- 最近一次确认时间。

经验记忆则需要记录：

- 原始任务条件；
- 采用的策略；
- 观察到的结果；
- 验收证据；
- 适用边界；
- 失败案例或反例。

这意味着底层可以使用统一记忆接口，但不同类型需要各自的验证规则。不能把“用户喜欢详细回答”和“某种代码重构策略通过测试”使用完全相同的可信度判断逻辑。

# 六、检索机制：不是越相关越应该进入上下文

记忆检索的目标不是尽可能多地找出相关信息，而是找到**当前任务真正需要、允许使用、可信且适用的信息**。

我建议采用分阶段检索。


    **第一阶段：权限与范围过滤**
    先排除无权访问、跨项目隔离、已撤销和不适用的记忆。



    **第二阶段：候选召回**
    根据任务类型、实体、关键词、语义相关性和关系索引召回候选。



    **第三阶段：适用性判断**
    检查时间、版本、前置条件、证据强度和是否存在反例。



    **第四阶段：排序与去重**
    综合任务相关性、可信度、时效性、信息增益和重复程度。



    **第五阶段：按预算提供给上下文引擎**
    保留必要证据引用，超出预算时可以延迟加载细节。


这里有两个容易犯的错误。

第一，不能只依赖向量相似度。两个记忆可能语义高度相似，但一个适用于 Python，另一个适用于 Java；一个针对旧版本 API，另一个针对新版本。

第二，不能让模型生成的内容因为被多次检索而变得越来越可信。重复引用不等于独立证据。

因此，检索时应尽量返回结构化记忆及其来源、适用条件和状态，而不是只返回一段脱离背景的摘要。

# 七、记忆冲突处理：不能简单地让新记忆覆盖旧记忆

这是 EvoAgent 必须重点设计的机制。

假设系统存在三条信息：

- 用户平时希望回答详细。
- 当前项目要求所有报告控制在两页以内。
- 用户这次明确要求只给一句结论。

它们并不一定相互矛盾，而是分别属于全局偏好、项目约束和当前任务指令。

我建议采用以下处理顺序：

1. **权限和安全约束**：任何记忆都不能绕过。
2. **当前明确任务要求**：优先决定本次任务怎么做。
3. **项目级约束**：在不与当前明确要求冲突的前提下生效。
4. **已确认的长期偏好**：作为默认行为。
5. **推断出的习惯与经验**：作为低优先级建议，必要时验证。

这不是所有信息都适用的简单优先级排序。例如，项目的安全限制不能因为用户当前说了一句相反的话就自动失效；系统还需要根据权限和约束类型判断能否覆盖。

对于真正的事实冲突，例如两个版本的 API 文档给出不同参数，系统应该检查来源、版本和有效时间，而不是直接选择最新的一条。

## 冲突处理结果应该有明确类型

| 结果 | 系统行为 |
|---|---|
| 已解决 | 根据来源、范围和规则选定当前有效信息 |
| 条件共存 | 保留多条记忆，但标明不同适用范围 |
| 待确认 | 证据不足或冲突可能影响重要决策时，向用户询问 |
| 暂停使用 | 无法判断哪条信息有效时，不将冲突记忆作为确定事实 |
| 已被替代 | 保留必要历史记录，当前任务使用新版本 |

尤其要注意：**系统不能为了让上下文看起来一致，就静默删除不一致的证据。**

# 八、记忆写入与更新：什么情况下自动保存？

这是个性化与自进化的入口。如果写入规则不合理，记忆系统最终会变成噪声仓库。

建议将写入分成四种路径。




      **路径 A：明确指令**
      用户明确要求长期记住的事项，可以直接进入记忆处理流程，但仍需执行权限、隐私和范围检查。






      **路径 B：项目决策**
      经过确认的架构决策、项目约束和里程碑，可以进入项目记忆，并关联决策记录和证据。






      **路径 C：行为推断**
      系统发现用户反复纠正相同问题时，先生成候选偏好；必要时通过后续行为验证，不急于永久固化。






      **路径 D：执行经验**
      任务完成或失败后，先保存可追溯的执行记录，再根据证据判断是否形成可复用经验。



有一个重要区别：**原始事件可以先记录，长期结论则需要经过筛选。**

例如，系统可以保留一次工具调用失败的结构化日志，但不能仅凭这一次失败就把该工具标记为不可靠，更不能直接把“不要使用该工具”写入所有专家的长期记忆。

同样，用户一次说“简单回答”只应影响当前任务；如果用户反复明确表达某种跨任务偏好，才有理由形成长期习惯。

# 九、记忆如何与上下文压缩协同？

记忆系统设计完成后，接下来最容易出问题的地方就是上下文。

我建议采用三个独立层次：

- **权威数据层**：保存任务状态、记忆原文、证据和必要的历史记录。
- **上下文工作层**：选择当前模型调用需要的信息，并控制 Token 预算。
- **压缩表示层**：把信息转化为紧凑的结构化摘要，同时保留恢复所需的引用。

例如，某个复杂编程任务积累了 100 次工具调用。上下文不应该把所有日志重新发给模型，而应保留：

- 当前目标与不可违反的约束；
- 已完成和未完成的计划节点；
- 已尝试方案及失败原因；
- 当前代码和关键产物的版本引用；
- 关键测试结果；
- 仍未解决的问题；
- 下一步需要使用的证据。

如果模型需要了解某次历史失败的完整堆栈，再根据引用定向读取，而不是始终携带所有原始内容。

但要注意，**摘要不能成为唯一的事实来源**。压缩后的上下文必须能够回溯到权威状态和原始证据。若摘要与原始记录发生冲突，应重新核验，而不是默认相信摘要。

# 十、记忆系统本身也需要独立进化

这与 EvoAgent 的整体进化架构直接相关。

假设某个专家经常因为检索不到正确经验而失败，系统不能立刻判断是记忆系统出了问题。

可能的原因包括：

- 经验根本没有写入；
- 写入时错误地分类到其他专家；
- 检索条件过于严格；
- 语义召回正确，但排序错误；
- 记忆过期后没有重新验证；
- 上下文预算不足，相关记忆被截断；
- 记忆本身错误；
- 专家没有正确使用检索结果。

因此，应该为记忆链路建立分阶段指标。

| 环节 | 关键指标 |
|---|---|
| 写入 | 有价值信息捕获率、错误写入率、重复率 |
| 分类 | 命名空间正确率、范围误判率 |
| 检索 | 召回率、精确率、过期记忆命中率 |
| 排序 | 关键记忆排名、无关信息占比 |
| 上下文组装 | 必要信息覆盖率、约束遗漏率 |
| 压缩 | 关键事实保留率、恢复成功率、Token 节省量 |
| 最终效果 | 任务质量变化、重复错误率、成本变化 |

这些指标需要通过可复现的专项测试与真实任务反馈联合评估，而不是只看检索命中率。

例如，召回率提高了，但错误记忆也更多地进入上下文，最终任务成功率反而下降，这不能算作记忆系统进化成功。

## 十一、我建议最终采用的记忆架构决策

经过这轮梳理，可以先确立以下设计基线。

  {#each [
    "采用统一记忆协议，但保留用户、项目、领域、经验和工作记忆的不同治理规则。",
    "采用明确的命名空间和授权机制，禁止默认跨项目、跨专家无限共享。",
    "将记忆内容、来源证据、适用条件、生命周期和可信度分开管理。",
    "区分长期记忆与当前任务的权威状态，避免用摘要替代真实状态。",
    "先记录事件，再筛选长期经验；未经验证的推断不得自动升级为通用规则。",
    "将记忆检索、上下文组装与压缩作为不同阶段独立评测。",
    "支持冲突、失效、替代、撤销、删除及跨端同步后的清理。",
    "所有记忆策略变更都必须经过专项评测，并检查对多个专家的影响。"
  ] as item}



        {item}


  {/each}

这些是建议冻结的架构原则，不代表数据库、检索算法和所有边界规则已经完成实现验证。

## 十二、下一步深入什么？

我建议接下来进入第二个独立设计领域：**用户习惯识别与个性化系统**。

需要进一步解决：

1. 如何从普通聊天和工作行为中识别偏好；
2. 如何区分长期习惯、项目习惯和临时要求；
3. 如何防止用户画像误判；
4. 如何处理用户习惯之间的冲突；
5. 如何将偏好注入不同专家的上下文；
6. 如何评估个性化究竟改善了体验，还是让智能体形成了刻板假设；
7. 如何允许用户查看、纠正和撤销系统对自己的理解。

这部分完成后，再进入上下文组装与压缩的专项设计，整个记忆与上下文体系才会形成完整闭环。
