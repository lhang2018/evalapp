# EvoAgent 深度设计第五轮：如何证明智能体真的变强了？

这一轮，我们要研究整个自进化系统最关键的可信度问题：

**EvoAgent 如何知道一次改动真正改善了能力，而不是碰巧成功、测试有偏差，或者只是学会了应付自己的评测？**

前面几轮，我们已经设计了能力图谱、经验迁移、进化决策和成本控制。它们都依赖同一个前提：系统能够可靠地判断某项能力是否改善。

如果这个前提不成立，进化系统就可能形成一个危险的循环：

- 模型提出一个改进。
- 模型自己认为改进有效。
- 评测系统给出高分。
- 系统发布改动。
- 实际任务表现反而下降。

这不是一个虚构的边缘问题，而是所有自动优化系统都必须面对的核心风险。

我建议把 EvoAgent 的评测体系设计成一个独立的**能力验证与因果诊断系统**。它不只回答“结果好不好”，还要回答“为什么变好、适用于什么条件、付出了什么代价，以及我们有多大把握”。

## 一、第一性原理：我们究竟要证明什么？

假设我们修改了编程专家的提示词，随后 100 个任务中成功了 92 个，而旧版本成功了 88 个。

表面上看，新版本提高了 4 个百分点。

但这个结果还不能直接证明提示词改进有效。

因为我们还不知道：

- 新旧版本是否执行了相同难度的任务。
- 两组任务是否使用了相同的模型和工具版本。
- 成功率差异是否来自随机波动。
- 新版本是否增加了调用次数和费用。
- 是否有某一类任务明显退化。
- 测试案例是否已经被候选版本间接记住。
- 评测器是否能发现隐藏的错误。

因此，我们必须区分三个不同层次的结论。


    <title size="lg">层次一：观察到结果改善</title>
    新版本在某次测试中获得更高分。

    这是观察结果，不足以证明稳定提升。



    <title size="lg">层次二：有证据支持改进有效</title>
    在合理的对照条件下，新版本反复表现更好，且差异不太可能只是随机波动。

    这是发布决策的主要依据。



    <title size="lg">层次三：知道改进在哪些条件下有效</title>
    系统能识别收益的适用范围、成本变化、已知反例，以及尚未验证的环境。

    这是长期能力迁移与持续进化的基础。


我们的目标不是追求数学意义上的绝对证明，而是建立足够可靠、可复现、与风险相匹配的证据。

对于低风险的提示词调整，证据门槛可以相对轻量；对于共享内核、权限控制或会影响多个专家的改动，则需要更严格的验证。

# 二、第一项基础设施：建立多层评测集，而不是一个总测试集

我建议每项可进化能力都拥有自己的评测资产，同时共享一套基础回归与安全测试。

评测集至少分为五类。






      **1. 缺陷复现集**

      专门验证当前要修复的问题是否真正改善。

      例如：编程专家是否还会在某类 Python 异步任务中遗漏取消状态处理。








      **2. 能力回归集**

      检查目标能力原有的成功场景是否仍然正常。

      例如：改善异步调试后，是否损害普通 Python 调试、代码解释或测试生成。








      **3. 依赖方影响集**

      检查共享组件改动对其他专家的影响。

      例如：修改上下文压缩机制后，检查旅游规划、漫剧制作和手机操作中的关键约束是否被保留。








      **4. 安全与边界集**

      检查权限、预算、隐私和不可逆操作的保护机制。

      这类测试不能因为其他指标提升就被抵消，也不能完全依赖模型评分。








      **5. 泛化与隐藏测试集**

      检查改进是否适用于未参与候选开发的新案例。

      包括不同任务表达、不同环境、边界条件和对抗性案例，降低对已知测试的过拟合。



这五类评测集的用途不同，不能全部合并成一个分数。

例如，一个候选可能通过缺陷复现集，却让其他任务退化；也可能提高常见任务的表现，却在安全测试中失败。

评测系统应该保留这些独立结果，让发布控制器依据硬门槛和适用范围作出决定。

# 三、如何区分“真的改好了”和“碰巧做对了”？

这是评测设计的核心。

我建议 EvoAgent 在条件允许时采用**配对对照实验**，而不是简单比较新旧版本各自的平均成功率。

例如，我们要测试编程专家的新提示词。

与其让旧版本跑 100 个任务、新版本跑另外 100 个任务，不如让两个版本分别运行相同的任务案例，并尽可能控制模型版本、工具版本、环境和评测规则。


    **基线版本 A**
    旧提示词 + 相同模型 + 相同工具版本 + 测试案例集合 T



    **候选版本 B**
    新提示词 + 相同模型 + 相同工具版本 + 同一测试案例集合 T



    **比较每个任务上的结果差异**
    记录谁成功、谁失败、质量变化、调用成本、延迟和错误类型，再评估整体差异是否稳定。


这样可以减少任务难度不同带来的干扰。

但这里还有一个细节：同一个模型在相同输入上可能产生随机差异。因此，必要时需要重复运行，或者控制采样参数，并记录每次运行的种子、模型版本和环境信息（如果服务支持）。

对于有副作用的任务，不能为了对照实验而直接重复执行真实操作。应当使用模拟环境、隔离副本或安全的测试替身。

## 3.1 不要只看平均成功率

假设新旧版本的结果如下：

| 指标 | 旧版本 | 新版本 |
|---|---:|---:|
| 总体成功率 | 88% | 92% |
| 高难度任务成功率 | 70% | 62% |
| 平均任务成本 | ¥0.20 | ¥0.31 |
| 平均执行时长 | 20 秒 | 29 秒 |

这时，新版本的总体成功率提高了，但高难度任务明显退化，成本增加了 55%，时长也增加了。

这不一定意味着新版本毫无价值，但显然不能仅凭总体成功率提升就自动发布。

系统需要进一步判断：

- 高难度任务的退化是否真实且具有统计意义？
- 质量提升是否值得增加成本？
- 能否只在适合的任务上启用新策略？
- 是否可以用更便宜的方式取得类似收益？

这也再次说明，能力评测应该以任务分组为基础，而不是只保存一个总分。

## 3.2 如何判断差异是否可靠？

对成功率，可以估计置信区间；对配对任务，可以比较同一案例在新旧版本之间的结果差异；对连续型指标，例如耗时和成本，可以分析差异的分布。

如果样本量很小，系统应该明确标记证据不足，而不是强行判断候选有效或无效。

同时，需要注意：统计显著不等于实际价值足够大。一个非常微小的质量提升，即使在大样本下显著，也可能不值得增加大量成本。

所以发布门槛至少要同时考虑：

- 估计的改善幅度。
- 不确定性范围。
- 最低有意义的改善幅度。
- 成本和延迟变化。
- 重要子任务是否退化。
- 安全和硬约束是否全部通过。

# 四、如何判断到底是哪个组件导致了问题？

这比比较新旧版本更难。

假设 EvoAgent 同时修改了：

- 系统提示词。
- 上下文压缩策略。
- 模型路由。
- 工具重试逻辑。

结果成功率从 80% 提高到 90%。

我们知道整个组合可能更好，却不知道哪项改动真正起作用。

如果下一步要将改进迁移给旅游专家，就会遇到问题：究竟应该迁移提示词、上下文策略、模型路由，还是工具恢复逻辑？

因此，我建议建立**分阶段因果诊断机制**。

## 4.1 首先遵循最小改动原则

当有多个可能的根因时，不要一开始就同时修改所有相关模块。

例如，怀疑工具故障导致任务失败，可以先：

1. 保持提示词、模型和上下文不变。
2. 修复或替换工具适配器。
3. 重跑缺陷复现集和相关回归集。
4. 检查是否恢复了预期行为。

如果结果支持这个假设，就不必再改动其他组件。

如果没有改善，再考虑其他原因。

## 4.2 什么时候需要更复杂的实验？

当多个因素可能互相影响时，单独修改一个组件未必能解释问题。

例如：

- 新提示词只在新模型上有效。
- 新上下文策略只有在特定路由下才有收益。
- 工具重试策略与任务类型存在交互作用。

此时可以使用分阶段的因子实验或小规模消融实验，分别比较组件组合。

假设我们要研究提示词 A 和上下文策略 B 的影响：

| 实验组 | 提示词 | 上下文策略 |
|---|---|---|
| 1 | 旧版 | 旧版 |
| 2 | 新版 | 旧版 |
| 3 | 旧版 | 新版 |
| 4 | 新版 | 新版 |

这可以帮助我们估计两个改动各自的作用，以及它们是否存在交互效应。

但不是每个任务都需要跑完整的组合实验。我们应该根据问题的重要性、不确定性、预算和初步证据决定实验规模。

## 4.3 必须允许系统保留“不知道”

这一点我认为尤其重要。

如果证据不足以区分模型能力不足、工具故障和上下文丢失，系统应该记录多个竞争性假设，并提出下一步最有价值的诊断实验。

它不应该因为进化流程要求必须填写一个根因，就随便选择一个看似合理的解释。

**诊断质量的一个重要指标，不只是正确找出根因，还包括在证据不足时避免过早下结论。**

# 五、评测器本身可能出错，应该怎样保护它？

这是一个容易被低估的问题。

EvoAgent 可能使用大模型判断代码质量、评估规划结果或评价漫剧分镜。但如果候选版本知道评测标准，甚至能够影响评测流程，就可能出现“结果得分很高，实际质量却没有提高”的情况。

我建议采用多种验收方式，而不是让另一个大模型给候选打一个总分。


    <title size="lg">第一层：客观验证</title>
    使用可执行测试、结构校验、权限检查、文件完整性、任务状态检查等方法。

    例如，代码修复后运行测试；手机操作后检查目标页面或实际状态；视频合成后检查文件是否完整、时长是否符合要求。



    <title size="lg">第二层：独立语义评测</title>
    对无法完全程序化的任务，使用独立评测器检查结果是否符合目标、约束和质量标准。

    评测器与候选实现分离，采用固定的评分规则，并在已知正反例上定期校准。



    <title size="lg">第三层：人工抽检与校准</title>
    对高风险、主观性强或评测器分歧较大的案例，保留人工审查。

    通过人工标注校验评测器的准确性，发现系统性偏差后，修订评测规则并重跑受影响的历史结果。


这里有四条必须遵守的规则：

1. 候选版本不能自行修改用于验收自己的评分规则。
2. 评测器和评测集必须独立版本化，历史结果要记录当时的评测器版本。
3. 隐藏测试案例不能全部暴露给候选生成器，否则系统可能逐渐针对测试集过拟合。
4. 对高风险结果，不能用大模型的主观判断代替客观验证和必要的授权。

还要注意：多个大模型给出相同结论，并不必然代表结论正确。如果它们共享类似的偏差，可能一起犯错。因此，独立评测最好结合不同类型的证据，而不是简单增加模型裁判数量。

# 六、怎样防止智能体把评测集“学会了”？

随着 EvoAgent 不断运行，它会积累越来越多的失败案例。如果每个案例都直接加入公开回归集，候选生成器可能逐渐针对这些案例优化。

这本身不是坏事。修复已知缺陷就是回归测试的价值。

问题在于：**如果我们只用这些已经公开、反复使用的案例判断能力是否提升，就无法可靠地估计它在新任务上的表现。**

因此，我建议把评测数据分成四个用途不同的集合。

| 数据集合 | 用途 | 候选开发者能否查看详细内容 |
|---|---|---|
| 诊断集 | 定位具体问题、复现失败 | 可以 |
| 开发集 | 调整候选实现 | 可以 |
| 回归集 | 检查已知能力是否退化 | 受控访问，记录使用情况 |
| 隐藏验收集 | 评估泛化能力和发布资格 | 默认不暴露完整案例 |

隐藏验收集不应该永远不更新。否则它也可能逐渐失去代表性。

我们可以定期从新的真实任务、经过授权的脱敏案例和专门构造的边界测试中补充案例，并保留一部分未参与候选开发的测试数据。

另外，不能因为某个案例曾经失败，就只保留失败案例。测试集还需要包含成功案例、边界案例、反例和不同难度的任务，否则候选可能学会一种过度保守的策略，表面上减少了错误，却牺牲了正常任务的能力。

## 一个特别重要的原则

**进化系统可以利用历史失败来学习，但不能仅凭历史失败集的成绩证明自己已经具备泛化能力。**

已知案例用于修复，独立案例用于检验，真实运行用于持续校准。三者缺一不可。

# 七、怎样把评测证据沉淀到能力图谱中？

前面我们设计的能力图谱，不应该只记录“编程专家 v3 比 v2 好”。

它还应该记录：在哪些条件下更好、证据有多强、有哪些已知退化，以及哪些领域尚未验证。

我建议每次评测至少形成一份结构化的证据记录：

  <title size="lg">评测证据记录示例</title>

    目标能力
    Python 异步错误诊断



    基线与候选
    实现 v2 → 候选 v3



    实验条件
    模型版本、工具版本、运行环境、测试集版本、执行参数



    质量结果
    成功率变化、配对差异、置信区间、重要任务分组表现



    资源变化
    每个成功任务的成本、调用次数、执行时长



    副作用
    发现的退化、失败类型变化、未验证的适用范围



    验收决定
    通过、拒绝、继续取证或仅允许局部启用，并记录原因


有了这种证据记录，进化决策器才能在以后做出更好的判断。

例如，如果某个提示词改动在模型 A 上有效、模型 B 上无效，那么系统不应该简单地把它推广为通用经验。它可以保留为模型 A 适配配置中的有效策略，并将模型 B 标记为尚未验证或不兼容。

如果一项共享上下文策略在旅游和编程任务中有效，但在漫剧任务中导致素材约束丢失，那么能力图谱应该记录这一反例，限制该策略的适用范围。

**能力图谱中的每一项重要能力，都应该逐渐积累关于其有效性、成本、适用范围和已知限制的证据。**

# 八、V0.1 应该如何实现这套评测系统？

我不建议第一版就做复杂的统计平台或自动因果发现系统。先建立最小、可靠、可复现的评测闭环。

## 第一版需要实现的六个模块

| 模块 | V0.1 实现方式 |
|---|---|
| 测试集管理 | 按专家、能力、任务类别保存版本化测试案例 |
| 实验运行器 | 对基线和候选运行相同的测试，记录输入、环境和结果 |
| 结果验证器 | 优先使用确定性测试；无法自动判定时使用独立语义评测 |
| 对照分析器 | 比较成功率、配对差异、成本、延迟和分组表现 |
| 影响范围测试器 | 根据能力依赖图选择目标回归集和受影响专家的测试 |
| 验收控制器 | 按硬门槛、最低收益、证据要求和预算决定通过、拒绝或继续取证 |

数据库可以在现有的能力图谱模型上增加以下几张表：

- `evaluation_cases`：测试案例及其版本。
- `evaluation_suites`：测试集定义与用途。
- `evaluation_runs`：一次完整的实验运行。
- `evaluation_results`：每个案例的结果、评分、成本和错误分类。
- `evidence_records`：与能力、实现版本和环境关联的证据。
- `evaluation_decisions`：验收结论、依据和审批记录。

这些表应通过稳定 ID 关联，而不是将全部信息塞进一段 JSON 或日志文本中。原始轨迹可以独立存储，但评测结果必须能够被结构化查询和重现。

## 第一版的实际验收目标

我们可以先选择一个明确的缺陷，例如编程专家在工具调用失败后重复执行操作。

V0.1 应当能够完整完成：

1. 记录一个真实或可复现的失败案例。
2. 形成一个有明确假设的候选改进。
3. 在隔离环境中运行基线和候选版本。
4. 通过自动化测试检查目标问题是否改善。
5. 检查相关能力是否退化，以及成本是否超出预算。
6. 生成带有证据的发布建议。
7. 保存结果、保留旧版本，并支持拒绝或回滚。

只要这个闭环跑通，我们就已经有了真正的进化基础，而不是只有一套能够生成优化建议的系统。

# 九、这一轮最终形成的原则

我认为我们已经明确了五条非常重要的设计规则：

1. **结果改善不等于能力提升。** 必须有合理的对照实验和可复现证据。
2. **评测系统不能由候选版本控制。** 测试数据、验收规则和发布权限必须独立管理。
3. **根因诊断必须允许不确定。** 证据不足时，应继续取证或保持现状，而不是强行选一个原因。
4. **平均分不能掩盖关键退化。** 必须同时检查重要任务分组、安全门槛、成本和延迟。
5. **每项能力都要积累长期证据。** 记录有效条件、已知反例、模型兼容性和实际运行结果，才能支持后续迁移与进化决策。

这意味着，EvoAgent 的进化闭环已经逐渐形成了完整结构：

**发现问题 → 诊断根因 → 提出候选 → 选择实验 → 独立评测 → 验收发布 → 监测真实收益 → 更新能力证据。**

但这里还有一个需要特别谨慎的地方：评测结果本身也会随着模型、工具、任务分布和评分标准变化而失效。因此，评测集、评分规则和评测器同样需要版本管理与持续校准。

## 下一轮，我建议研究一个新的关键问题

我们已经知道如何管理能力、迁移经验、选择改进和验证收益。但还没有充分解决：

**当 EvoAgent 从一个模型切换到另一个模型，或者模型 API、工具和运行环境发生变化时，如何保留已有能力资产，同时判断哪些策略需要重新适配？**

这会涉及模型适配档案、能力与模型的依赖关系、跨模型回归、配置迁移、版本分支和自动兼容性测试。

它也直接关系到你最初提出的目标：为当前模型和当前环境逐步优化出一个稳定版本；未来切换模型时，保留旧版本的成果，从新的模型分支继续进化，而不是把之前积累的能力全部推倒重来。
