# EvoAgent 深度设计第八轮：记忆系统与上下文治理

这一轮，我认为我们触及了 EvoAgent 最容易被低估、却可能影响所有能力的基础系统。

你最初的目标不是做一个只会完成任务的智能体，而是做一个能长期运行、记录问题、识别原因、优化自身，并且在模型切换后继续积累能力的智能体。

要实现这个目标，记忆系统就不能只是一个向量数据库，也不能只是把历史对话塞进提示词。

**EvoAgent 需要的是一套可追溯、可治理、可验证、可过期、可独立进化的记忆与上下文系统。**

它必须解决六个根本问题：

1. 什么信息值得长期保留？
2. 哪些信息属于用户、项目、领域专家或系统内核？
3. 执行任务时，究竟应该检索哪些记忆？
4. 如何防止过时、错误或相互矛盾的记忆污染当前判断？
5. 上下文长度有限时，怎样保留真正影响任务结果的信息？
6. 记忆系统自身出现问题时，怎样诊断并改进，而不把错误记忆变成新的错误能力？

这次我们从第一性原理推导，不先假设所有信息都应该进入同一个记忆库。

---

# 一、第一性原理：记忆不是“存储信息”，而是“保存未来有用的信息”

假设 EvoAgent 今天完成了一个复杂的编程任务。

它产生了大量信息：

- 用户最初提出的要求。
- 项目的代码和目录结构。
- 模型调用记录。
- 中间规划。
- 工具执行结果。
- 失败和重试过程。
- 最终代码。
- 测试报告。
- 一次偶然成功的提示词。
- 一条尚未验证的故障原因假设。

这些信息并不应该采用相同的方式保存。

例如：

- 用户明确提出的硬性约束，可能必须在任务结束前始终保留。
- 项目目录结构，可能在整个项目期间都有价值。
- 某次工具调用的完整日志，可能只需短期保存用于排查。
- 一次失败后的猜测，不应该立即变成长期事实。
- 已经通过多个任务验证的恢复原则，可能值得沉淀为可复用能力资产。

所以，记忆系统不能只回答“要不要存”，还必须回答：

**保存什么、保存多久、归谁所有、何时使用、可信度如何，以及什么时候应该撤销或重新验证。**

这意味着，记忆需要具有明确的类型、来源、适用范围、生命周期和权限，而不是只有一段文本和一个向量。

## 二、必须把记忆拆成不同的系统，而不是一个无限膨胀的数据库

我建议 EvoAgent 采用七类逻辑记忆。它们可以先存储在同一个 SQLite 数据库中，但必须有独立的数据结构、写入规则、检索策略和生命周期。






      **1. 用户偏好记忆**

      保存用户明确表达、长期有用的偏好，例如回答风格、常用工作方式和明确授权的默认选择。

      边界：不能因为一次临时要求，就推断为永久偏好。








      **2. 项目与任务状态记忆**

      保存当前项目目标、决策、约束、进度、依赖关系、未完成事项和检查点。

      边界：项目状态变化时必须更新，不能用旧状态覆盖新事实。








      **3. 领域知识记忆**

      保存经过确认的编程知识、旅游规则、漫剧制作知识，以及其他领域的事实和方法。

      边界：记录来源、适用条件、有效期和版本依赖；时效性知识需要重新核验。








      **4. 技能与工作流记忆**

      保存可复用的任务步骤、工作流定义、输入输出契约、失败恢复方法和验收规则。

      边界：正式工作流是有版本的执行资产，不应该只存在于一段自然语言记忆里。








      **5. 运行经验记忆**

      保存失败模式、成功案例、工具异常、诊断结果、解决方案及其实际效果。

      边界：成功案例、未经验证的假设和已确认的根因必须分开标记。








      **6. 模型与环境适配记忆**

      保存特定模型、API、工具版本、运行环境下的行为特征、已知限制和经过验证的适配策略。

      边界：必须明确适用的模型与环境，不能自动推广为跨模型通用知识。








      **7. 运行轨迹与审计记录**

      保存任务事件、工具调用、状态转换、关键决策、验证结果和版本引用。

      边界：这是证据来源，不等于可以直接注入提示词的记忆。原始日志不应该自动变成经验。



这里要特别区分两种东西：

- **记忆资产**：系统经过整理、准备在未来使用的信息。
- **运行证据**：证明某件事发生过、某个结论可能成立的原始记录。

例如，工具调用日志显示某次请求超时，这是证据；“这个工具在所有情况下都不可靠”则是一个需要验证的结论。

如果把两者混为一谈，系统很容易把一次偶然故障固化成长期错误认知。

# 三、记忆还必须有第二个维度：归属与权限

上面的七类是按照内容用途划分的，还不够。

同一类记忆可能属于不同范围。

例如，一条编程经验可能是：

- 当前项目专用的经验。
- 编程专家的领域经验。
- 经过跨领域验证的共享原则。
- 只适用于模型 A 的适配经验。

所以，我建议采用两个独立维度：

**记忆类型决定如何使用它；记忆归属决定谁可以访问、修改和推广它。**

  <title size="lg">记忆归属范围</title>


      **任务级**


      当前执行过程中的临时状态、观察结果、待完成步骤和恢复检查点。

      任务结束后按需要归档，不默认成为长期记忆。





      **项目级**


      项目目标、技术选型、项目结构、设计决策、项目约束和当前进度。

      只在有权限的项目上下文中使用，避免跨项目污染。





      **专家级**


      编程、旅游、漫剧或手机操作领域的专用知识和经过验证的策略。

      由对应领域的记忆策略管理，不因被其他专家调用而自动共享。





      **模型级**


      特定模型及 API 版本下的行为特点、提示词适配和兼容性结果。

      模型切换后保留历史，但必须重新验证其适用性。





      **共享级**


      已经通过规定验证、获准供多个专家使用的通用原则、基础知识和组件经验。

      共享范围由发布规则控制，不能由某个专家自行决定。



还需要一个独立的用户数据权限维度。项目记忆和用户偏好可能包含私有信息，即使它们对多个专家有用，也不能因此自动扩大访问范围。

例如，某个项目中发生的错误可以提炼出不含私有代码的通用经验，但原始代码、项目日志和用户数据仍然遵循原有权限边界。

这也意味着，**记忆的“共享级”不是最高权限，而是一种经过授权的复用范围。** 共享知识不等于可以访问所有来源数据。

# 四、一次任务执行时，究竟应该把哪些记忆交给模型？

这就是上下文治理的核心。

即使记忆系统存储得很好，如果每次任务都把大量历史记忆塞进上下文，仍然可能降低执行质量。

因为上下文并不是越多越好。

无关记忆会增加干扰；旧事实可能与新状态冲突；未经验证的经验可能被模型当成规则；大量日志还会挤占当前任务真正需要的信息。

因此，我建议把记忆系统和上下文组装器彻底分开。

- **记忆系统负责保存、检索、更新、验证和治理信息。**
- **上下文组装器负责决定当前任务应该看到哪些信息，以及以什么形式呈现。**

模型不应该直接读取整个记忆库，也不应该拥有任意修改所有记忆的权限。

## 4.1 建立一个分层的上下文结构


    <title size="md">第一层：不可丢失的任务约束</title>
    用户明确要求、权限限制、硬预算、安全约束和任务完成条件。



    <title size="md">第二层：当前任务状态</title>
    当前目标、已完成步骤、未完成事项、工具执行结果、检查点和待验证假设。



    <title size="md">第三层：与任务相关的记忆</title>
    项目知识、用户偏好、领域经验、适用工作流和模型适配信息。



    <title size="md">第四层：当前执行所需的证据</title>
    关键工具返回、相关日志片段、必要文件内容和最新状态检查结果。



    <title size="md">第五层：执行策略与工作流</title>
    当前任务允许使用的 ReAct 策略、工具说明、流程节点和验收方法。


这五层是逻辑结构，不代表必须以五段固定文本拼接给模型。

例如，硬预算和权限限制应当由程序化控制器强制执行，而不是仅仅写进提示词。任务状态应当由可靠的状态存储维护，而不是完全依赖模型记住历史消息。

同样，某些工作流可以通过结构化 DAG 执行，根本不需要把整个工作流反复序列化进上下文。

**上下文是模型理解当前任务所需的信息视图，不应该成为整个系统状态的唯一存储位置。**

## 4.2 记忆检索不能只靠向量相似度

假设用户正在处理一个 Python 项目。

向量检索可能找出以下内容：

- 过去一次 Python 调试经验。
- 一个旅游规划任务中的失败恢复经验。
- 一条关于上下文压缩的共享原则。
- 三个月前某个项目中已经废弃的技术选型。

它们可能在语义上都与当前任务相似，但不一定都应该进入上下文。

因此，检索需要多重判断：

1. **权限过滤**：当前专家和任务是否有权访问？
2. **适用范围过滤**：该记忆是否适用于当前领域、项目和模型？
3. **有效性检查**：是否过期、已撤销或依赖旧版本？
4. **相关性排序**：与当前任务的目标和子问题有多相关？
5. **可信度判断**：来源是否可靠，结论是否经过验证？
6. **预算控制**：加入这条记忆是否值得占用上下文空间？

我建议使用“先过滤，再排序，最后预算选择”的检索架构。

不能让高语义相似度覆盖权限边界，也不能让一条未经验证的经验仅仅因为很相关，就被当成可靠规则。

# 五、记忆必须能够被质疑、更新和撤销

这是我认为 EvoAgent 与普通记忆增强型智能体最应该拉开差距的地方。

普通记忆系统经常默认：写入成功，就可以长期使用。

但在一个持续进化的系统里，记忆可能是错误的、过时的、不完整的，甚至只在特定环境中有效。

因此，每条重要记忆都应该具有明确的状态。

  {#each [{t:"候选",d:"刚从任务或日志中提取，尚未经过充分验证。"},{"t:"已验证",d:"通过相应的事实核验、任务测试或重复实验。"},{"t:"受限使用",d:"仅在明确的任务、项目、模型或环境范围内有效。"},{"t:"待复核",d:"因环境变化、证据冲突或长期未验证而暂时降低可信程度。"},{"t:"已撤销",d:"已发现错误、被新证据推翻或不再适用，不允许作为有效知识继续检索。"}] as s}

      **{s.t}**
      {s.d}

    {#if s.t !== "已撤销"}{/if}
  {/each}

这里有一个重要区别：记忆的可信度和记忆的适用范围不能混为一谈。

例如，一条 Python 版本兼容性知识可能完全正确，但只适用于某个旧版本的运行环境。

它不是“错误记忆”，而是“适用范围有限的记忆”。

另一方面，一条在多次测试中表现良好的恢复策略，也不意味着它在所有任务中都有效。

因此，每条重要记忆至少应当记录：

- 来源和生成方式。
- 验证证据。
- 适用领域和环境。
- 关联模型、工具或工作流版本。
- 创建和最近复核时间。
- 当前状态。
- 冲突或反例。
- 撤销原因与替代记忆。

## 5.1 记忆冲突时，不能简单地“新覆盖旧”

假设项目记忆中写着：

> 使用 Python 3.11。

后来任务日志显示，某个部署环境已经升级到 Python 3.12。

这时，系统不能直接删除旧记录，因为它可能仍然适用于其他环境。

正确做法是识别作用范围：

- 项目开发环境：Python 3.12。
- 旧部署环境：Python 3.11。
- 某个历史工作流：依赖 Python 3.11。

只有在确认某项旧信息已经不再适用时，才更新对应范围的状态。

因此，记忆系统需要维护事实之间的关系，例如：

- `SUPERSEDES`：新事实替代旧事实。
- `CONTRADICTS`：两个结论存在冲突。
- `VALID_IN`：某个结论适用于指定环境。
- `SUPPORTED_BY`：某个结论由哪些证据支持。
- `DERIVED_FROM`：某个经验从哪个任务或实验产生。

这样，记忆系统才能真正管理知识变化，而不是简单累积越来越多的文本。

# 六、上下文治理：当信息超出模型窗口时，应该如何压缩？

这个问题不能简单地用“保留最近几轮对话”解决。

因为最近发生的信息不一定最重要，早期的用户硬约束也可能必须保留。

同样，模型生成的长摘要也不能自动视为完整、准确的任务状态。

我建议 EvoAgent 使用四种不同的上下文管理方式。

## 6.1 硬约束独立保存，不参与普通摘要淘汰

例如：

- 用户明确规定的交付格式。
- 不允许执行的操作。
- 预算上限。
- 必须通过的测试。
- 不能改变的项目约束。

这些信息应当保存在结构化任务状态中，由上下文组装器在每次需要时重新注入。

对于真正的安全边界，还需要由程序化权限系统强制执行，不能依赖模型每次都正确记住提示词。

## 6.2 当前任务状态使用结构化检查点

长任务不应该依靠不断累积聊天记录来维持状态。

例如，AI 漫剧制作任务可以记录：

```text
task_id: drama_001
current_stage: video_generation
completed:
  - script_approval
  - character_design
  - storyboard
pending:
  - generate_scene_04
constraints:
  duration_seconds: 45
  budget_limit: ...
artifacts:
  storyboard_version: v3
  character_asset_version: v2
validation:
  previous_stage: passed
next_action:
  - generate_scene_04
```

这只是结构示例。实际数据应当使用明确的类型和数据库字段，并为关键状态变化保存审计记录。

当任务暂停或模型调用失败时，系统从检查点恢复，而不是要求模型重新阅读所有历史对话后猜测当前进度。

## 6.3 历史轨迹采用分层摘要

对于已经完成的步骤，可以保存：

- 简短的阶段摘要。
- 关键决策及其理由。
- 重要工具结果。
- 失败和恢复记录。
- 可重新读取的原始证据引用。

这样，模型只需看到与当前步骤有关的摘要，遇到不确定问题时再回到原始日志或文件获取细节。

**摘要是导航索引，不是原始证据的替代品。**

## 6.4 压缩后必须验证信息完整性

我建议为每次上下文压缩生成一份结构化的保留清单：

- 用户硬约束是否全部保留。
- 当前任务状态是否一致。
- 已完成步骤是否有证据。
- 未完成事项是否仍然存在。
- 重要文件和工具结果是否保留引用。
- 是否引入了原文中不存在的新结论。

压缩完成后，系统应比较原始结构化状态与压缩结果。关键约束可以通过确定性检查验证；语义摘要则可以通过独立评测或抽检检查。

如果发现关键状态丢失，就不能直接把压缩结果用于后续执行，而应重新组装或恢复相关信息。

# 七、记忆系统本身也需要进化，但必须分开诊断

现在我们终于可以把记忆系统与前面讨论的进化闭环连接起来。

假设编程专家连续几次没有找到正确的项目配置。

表面上看，像是代码理解能力不足。

但根因可能是：

- 项目记忆没有被写入。
- 记忆检索使用了错误的项目命名空间。
- 检索结果虽然正确，但被上下文预算过滤掉。
- 摘要压缩丢失了文件路径。
- 旧记忆覆盖了新项目状态。
- 模型在上下文中看到了正确路径，却仍然选择错误的文件。

这些问题对应完全不同的修复方式。

我建议为记忆与上下文建立独立的可观测性链路：

<CodeBlock language="mermaid" editable={false}>flowchart TD
    A[任务执行出现记忆相关异常] --> B[检查原始事实是否存在]
    B --> C{事实是否正确保存}
    C -->|否| D[诊断写入与更新策略]
    C -->|是| E[检查检索与权限过滤]
    E --> F{正确记忆是否被召回}
    F -->|否| G[诊断检索、排序与适用范围]
    F -->|是| H[检查上下文组装与压缩]
    H --> I{关键信息是否保留}
    I -->|否| J[诊断预算分配与压缩策略]
    I -->|是| K[检查模型是否正确使用信息]
    K --> L[分析规划、指令遵循或推理问题]
    D --> M[生成局部候选并验证]
    G --> M
    J --> M
    L --> M
    M --> N[独立回归与发布门禁]</CodeBlock>

这个流程非常重要。

如果正确记忆没有被召回，就不应该首先修改模型提示词；如果正确记忆已经进入上下文，但模型仍然误用它，那么才应该进一步检查指令、规划或模型行为。

这样可以防止记忆系统的问题被错误地归因于其他能力。

## 7.1 记忆质量需要独立指标

我建议至少跟踪以下指标：

| 指标 | 说明 |
|---|---|
| 记忆写入准确率 | 被写入的事实或经验是否与来源一致 |
| 记忆召回率 | 任务需要的有效记忆是否被找到 |
| 召回精确率 | 检索结果中有多少真正适用 |
| 关键约束保留率 | 压缩或上下文组装后，重要约束是否完整 |
| 过期记忆命中率 | 失效或不再适用的信息被使用的频率 |
| 记忆冲突处理正确率 | 多条冲突记录是否得到合理区分和处理 |
| 记忆收益 | 使用记忆后，任务质量和效率是否实际改善 |
| 记忆引入的错误率 | 错误或无关记忆导致的任务退化情况 |

其中，记忆召回率高不代表系统更好。如果它同时召回大量无关信息，可能会提高上下文噪声。

因此，必须把记忆检索质量与最终任务表现关联起来评估。

**记忆的价值不在于存得多、召回得多，而在于需要时能提供正确、适用、值得信任的信息。**

# 八、V0.1 的记忆系统应该怎样落地？

第一版不需要建立复杂的分布式记忆平台。我们可以采用 SQLite + 文件存储 + 可选向量检索，先把正确的数据治理和调用流程跑通。

建议建立以下核心表：

| 表 | 职责 |
|---|---|
| `memory_items` | 保存记忆内容、类型、归属、状态和生命周期 |
| `memory_sources` | 关联原始任务、日志、文件或验证证据 |
| `memory_relations` | 记录替代、冲突、派生和支持关系 |
| `memory_access_policies` | 管理访问范围、修改权限和共享规则 |
| `memory_validation_runs` | 保存记忆事实核验、适用性检查和回归结果 |
| `task_checkpoints` | 保存长任务的结构化状态与恢复点 |
| `context_build_runs` | 记录每次上下文组装、预算分配和最终注入内容的引用 |
| `context_validation_runs` | 检查压缩、摘要和上下文组装是否丢失关键约束 |
| `memory_feedback_events` | 记录记忆使用后带来的收益、冲突和错误 |

重要记忆可以采用版本化记录，不直接覆盖历史内容。撤销时将其标记为无效或限制使用，并保留审计记录。

对于原始日志和大文件，优先保存受权限控制的文件引用及内容摘要，避免数据库无限膨胀。向量检索只负责候选召回，权限检查、有效性判断和最终选择仍然由记忆治理模块负责。

## 九、建议采用怎样的记忆写入流程？

我建议任何来源的记忆都经过统一入口，但不同类型采用不同的验证规则。

<CodeBlock language="mermaid" editable={false}>flowchart TD
    A[新信息或任务结束] --> B[识别信息类型与来源]
    B --> C[检查隐私、权限与数据范围]
    C --> D{是否值得长期保存}
    D -->|否| E[仅保留任务状态或短期日志]
    D -->|是| F[生成候选记忆]
    F --> G[检查重复、冲突与适用范围]
    G --> H[验证事实或记录为待验证假设]
    H --> I[确定归属、有效期与访问策略]
    I --> J[保存版本与来源引用]
    J --> K[在未来任务中受控检索]
    K --> L[收集使用结果与反例]
    L --> M[更新可信状态或触发复核]</CodeBlock>

这里不能把所有记忆都强制走同样复杂的流程。

用户明确提出的项目决策，可以根据来源和权限直接保存为项目状态；从运行日志推断出来的根因，则需要保持为候选假设，直到有足够证据。

此外，记忆提取模型不能自行扩大数据访问权限。任何涉及用户私有数据、跨项目共享或长期保留的行为，都必须遵循预先定义的权限与保留规则。

## 十一、下一轮：ReAct、Planning 和工作流如何真正协同？

到这里，我们已经讨论了：

- 能力图谱与所有权。
- 经验晋级和跨领域迁移。
- 进化决策与资源分配。
- 独立评测和因果诊断。
- 模型切换与版本管理。
- 环境健康与故障归因。
- 记忆治理与上下文管理。

接下来，最值得深入研究的是 **EvoAgent 的执行控制架构**。

因为这些模块最终都要落到真实任务执行上。我们需要回答：

1. ReAct 循环、Planning 和工作流 DAG 各自负责什么？
2. 什么时候让模型动态决策，什么时候必须走固定流程？
3. 如何防止 ReAct 无限制循环、反复调用工具或重复执行副作用操作？
4. 任务状态、检查点、记忆和上下文怎样协同？
5. 当一个任务中途失败、模型切换或应用状态变化时，如何安全恢复？
6. 一条经过验证的工作流，怎样沉淀为稳定能力，又怎样在后台独立进化？

我尤其建议研究一个核心原则：

**ReAct 负责局部观察与行动，Planning 负责任务分解与调整，工作流负责稳定执行约束，运行时控制器负责状态、权限、预算和终止条件。**

但这只是一个初步分工。下一轮我们应该进一步明确它们之间的接口、状态所有权、控制权和故障恢复机制，避免多个模块同时决定下一步该做什么，导致智能体出现循环、冲突或不可预测的行为。
