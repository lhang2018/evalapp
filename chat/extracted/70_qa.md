# EvoAgent 第十五专项：可观测性、因果归因与可解释执行引擎

这一轮要解决 EvoAgent 自我进化中最基础、也最容易被低估的问题：

**系统必须知道自己做过什么、为什么这么做、哪里出了问题，以及有什么证据证明一次改进真的有效。**

前面我们已经设计了执行、记忆、上下文、专家路由、ReAct、Planner、工具调用、结果验收、自我修复、模型适配、进化调度、全局治理和权限控制。

这些模块如果没有统一的可观测性体系，就会形成一个很大的盲区：

智能体可能越来越复杂，但我们无法可靠地解释它为什么成功、为什么失败，也无法确定下一步应该优化什么。

例如，一次代码任务失败，表面上是编程专家写错了代码，实际根因可能是：

- 路由器选择了不合适的专家；
- 记忆检索返回了过时的项目约束；
- 上下文压缩删除了关键接口信息；
- Planner 漏掉了必要的测试步骤；
- ReAct 在观察结果后仍然重复原来的动作；
- 工具执行失败，但返回状态被错误解释；
- 验收器没有发现实际缺陷；
- 自我修复策略选择了错误的修复方向。

如果系统只记录最终回答和异常堆栈，它很可能优化错对象。

我建议把本专项设计为：

**Observability, Causal Attribution & Explainable Execution Engine，简称 OCAE。**

它负责将任务执行、问题诊断、能力评估和持续进化连接到同一套可验证的证据体系。

## 一、第一性原理：记录不是目的，证据才是目的

我们先区分四件事。

  {#each [
    ["记录事实","系统实际收到了什么输入、调用了什么工具、观察到了什么结果。"],
    ["解释行为","系统为什么选择这个专家、计划、工具或恢复策略。"],
    ["定位原因","哪个因素对失败或性能变化产生了实际影响。"],
    ["验证改进","修改之后，目标指标是否真的改善，其他关键能力是否退化。"]
  ] as item}



        **{item[0]}**
        {item[1]}


  {/each}

这四个层次不能混为一谈。

例如，日志显示某次任务中路由器选择了编程专家，只能证明发生了这次选择；它不能证明选择编程专家就是失败的根因。

同样，模型解释“因为上下文不足，所以任务失败”，也只能视为一个诊断假设，而不是事实。

真正的根因需要结合执行轨迹、工具结果、任务约束、对照实验和其他证据来判断。

因此，OCAE 必须遵守一条原则：

**事实记录、模型解释、诊断假设和实验结论，必须使用不同的数据类型和可信度标记。**

这能防止 EvoAgent 把自己生成的解释当作事实，再把错误诊断写进长期记忆，最终导致后续进化不断强化错误判断。

# 二、建立统一执行轨迹：一项任务必须能够完整追溯

建议建立 `Execution Trace`（执行轨迹）作为整个系统的核心可观测性实体。

每次用户请求都创建一个根任务，随后发生的专家路由、模型调用、记忆检索、上下文组装、规划、工具执行、验收和恢复，都关联到这条任务轨迹。

复杂任务可以包含多个子任务、多个专家以及一张 DAG，但仍然需要能够回溯到原始用户目标。

## 2.1 统一的追踪层级


    **Task Trace**
    原始请求、任务目标、最终状态、验收结论与总成本



    <grid-item>

        **Agent Span**
        专家选择、任务规划、ReAct 循环、记忆和上下文处理

    </grid-item>
    <grid-item>

        **Workflow Span**
        DAG 节点、依赖关系、检查点、重试与恢复

    </grid-item>



    **Operation Span**
    模型调用、工具调用、检索、文件操作、验证与状态变化



    **Events & Evidence**
    时间、输入输出摘要、执行结果、错误码、证据引用和版本信息


这里的 Span 指一次有明确开始和结束的执行区间，Event 则记录该区间内的重要状态变化。

例如，模型调用是一个 Span；模型返回结构化工具请求是一个 Event；工具实际执行和验收又分别有自己的 Span。

这样就能看出时间消耗发生在哪个环节，也能分辨模型提出了操作、工具接受了操作、操作真正完成，以及最终结果通过验收这四件不同的事。

## 2.2 每条轨迹必须关联哪些 ID？

建议至少包含以下标识：

| 标识 | 作用 |
|---|---|
| `task_id` | 贯穿用户请求及其全部子任务 |
| `trace_id` | 关联一次完整的执行轨迹 |
| `span_id` | 唯一标识一个执行区间 |
| `parent_span_id` | 记录父子关系，重建执行层级 |
| `attempt_id` | 区分同一操作的不同尝试 |
| `workflow_run_id` | 关联一次工作流运行 |
| `expert_id` | 标识参与执行的专家 |
| `model_snapshot_id` | 标识模型及其适配版本 |
| `config_snapshot_id` | 标识提示词、路由、上下文和策略配置 |
| `evolution_run_id` | 将实验、候选改进与相关任务连接起来 |

其中，`task_id` 应在任务从 Android 手机传到个人电脑时保持不变。服务端接收任务时可以生成新的本地 `trace_id`，但必须保留任务关联关系。

**任务关联 ID 不是用户身份，也不是权限凭证。** 任何知道某个 `task_id` 的组件都不应该因此获得访问任务内容的权限。

## 2.3 轨迹必须保存真实顺序与因果关系

复杂工作流不一定按顺序执行。

例如，漫剧制作中，角色素材生成和背景素材生成可能并行；编程任务中，不同模块的静态分析可能并行运行。

因此，不能仅靠日志时间戳重建整个 DAG。

建议同时保存：

- 父子执行关系；
- 工作流节点依赖；
- 显式的先后关系；
- 任务检查点；
- 事件发生时间；
- 事件被系统接收的时间；
- 必要的跨设备关联信息。

这样既能重建实际执行顺序，也能区分“发生得更早”和“真正导致了后续动作”。

# 三、统一事件模型：不能让每个专家各记各的日志

如果编程专家使用自己的日志格式，手机操作专家使用另一套格式，漫剧专家又使用第三套格式，那么全局治理引擎就很难比较它们的表现。

建议建立统一的 `Agent Event Schema`，所有专家、工具、工作流和进化模块都通过同一事件接口记录重要事实。

## 3.1 建议的事件分类

  {#each [
    ["任务事件","TASK_CREATED、TASK_STARTED、TASK_COMPLETED、TASK_FAILED、TASK_CANCELLED"],
    ["路由事件","ROUTE_SELECTED、ROUTE_FALLBACK、ROUTE_REJECTED"],
    ["上下文事件","MEMORY_RETRIEVED、CONTEXT_ASSEMBLED、CONTEXT_COMPRESSED"],
    ["规划事件","PLAN_CREATED、PLAN_REVISED、STEP_BLOCKED"],
    ["执行事件","TOOL_REQUESTED、TOOL_STARTED、TOOL_SUCCEEDED、TOOL_FAILED"],
    ["验收事件","VERIFICATION_STARTED、VERIFICATION_PASSED、VERIFICATION_FAILED"],
    ["恢复事件","RECOVERY_PROPOSED、RECOVERY_ATTEMPTED、RECOVERY_SUCCEEDED"],
    ["治理事件","AUTHORIZATION_ALLOWED、AUTHORIZATION_DENIED、BUDGET_LIMIT_REACHED"],
    ["进化事件","ISSUE_DETECTED、CANDIDATE_CREATED、EVALUATION_COMPLETED、CANDIDATE_PROMOTED"]
  ] as item}

      **{item[0]}**
      {item[1]}


  {/each}

这些事件名称是建议的规范化词汇，并不是要求每个模块都实现全部事件。正式 Schema 应当定义字段、必填条件、事件版本和状态转换约束。

例如，工具执行不能只记录一个 `TOOL_SUCCEEDED`，还应该区分：

- 请求是否通过授权；
- 工具是否真正开始执行；
- 工具接口是否返回成功；
- 外部状态是否发生预期变化；
- 最终验收是否通过。

这样才能避免把“API 调用成功”误认为“用户任务成功”。

## 3.2 事件记录应该包含什么？

建议采用如下结构：

<CodeBlock language="json" editable>
{
  "event_id": "evt-001",
  "schema_version": 1,
  "event_type": "TOOL_FAILED",
  "task_id": "task-884",
  "trace_id": "trace-884",
  "span_id": "span-019",
  "parent_span_id": "span-012",
  "sequence_no": 42,
  "occurred_at": "2026-10-20T10:30:15Z",
  "recorded_at": "2026-10-20T10:30:16Z",
  "component": {
    "name": "file_tool",
    "version": "tool-v5"
  },
  "context": {
    "expert_id": "coding",
    "model_snapshot_id": "model-b-snapshot-04",
    "config_snapshot_id": "config-21"
  },
  "outcome": {
    "status": "FAILED",
    "error_code": "MISSING_REQUIRED_FIELD",
    "retryable": false
  },
  "evidence_refs": [
    "evidence-102"
  ]
}
</CodeBlock>

这是概念示例。正式实现还需要定义字段校验、时钟来源、脱敏规则和证据保留策略。

其中 `occurred_at` 表示事件发生时间，`recorded_at` 表示记录时间。两者不同，可能是因为离线缓存或日志批量上传。

对于同一设备，可以使用单调递增的本地序列号辅助排序；跨设备事件则应保留各自的时钟信息和因果关联，不能假设不同设备的系统时间绝对一致。

## 3.3 事件记录不能无限膨胀

不是所有内部细节都值得永久保存。

例如，简单的工具调用可以记录请求摘要、结果、耗时和错误码；只有出现异常、触发诊断或进入进化实验时，才按策略保留更详细的上下文。

建议分成三种记录级别：

- **基础轨迹：** 每项任务都记录，用于恢复、统计和审计。
- **诊断轨迹：** 发生失败、异常或明显退化时，增加更细粒度的事件。
- **实验轨迹：** 对照实验、模型适配和候选进化任务记录完整的版本差异与评测证据。

这样可以控制磁盘占用、模型分析费用和隐私风险。

# 四、最关键的设计：事实、假设、根因和结论必须分开

这是 OCAE 与普通日志系统最大的区别。

我建议建立独立的 `Diagnostic Case`（诊断案例）实体，而不是把模型生成的故障分析直接写进日志或长期记忆。

## 4.1 诊断案例的生命周期

  {#each [
    ["D1：发现异常","检测到失败、超时、指标退化、用户纠正或结果与预期不一致。"],
    ["D2：形成假设","提出一个或多个可能的原因，并列出支持证据与反例。"],
    ["D3：收集证据","查看执行轨迹、复现案例、工具结果和配置差异。"],
    ["D4：区分假设","选择成本合理、能够区分不同原因的诊断实验。"],
    ["D5：确认或保留未知","记录得到支持的原因，或者明确标记为尚未确定。"],
    ["D6：产生改进候选","将有足够依据的根因转化为具体、可验证的改进方案。"],
    ["D7：验证实际效果","对比基线和候选结果，确认修复是否解决目标问题并检查回归。"],
    ["D8：沉淀经验","保存根因、适用条件、反例和证据来源，供后续诊断使用。"]
  ] as item}


        {item[0].split("：")[0]}


        **{item[0].split("：")[1]}**
        {item[1]}


    {#if item[0]!=="D8"}

    {/if}
  {/each}

注意，诊断案例不一定必须走完全部阶段。

如果只是一个可重复的工具参数错误，可以快速形成诊断和修复候选；如果涉及多个模块、难以复现的偶发故障，则可能需要长时间保留多个竞争假设。

## 4.2 一个诊断假设应该包含什么？

例如，系统怀疑编程任务失败是因为上下文压缩丢失了接口约束。

这条假设应该记录：

- `hypothesis_id`：假设标识；
- `target_component`：疑似相关组件；
- `supporting_evidence`：支持证据；
- `contradicting_evidence`：反例或冲突证据；
- `confidence_state`：当前证据状态；
- `testable_prediction`：如果假设正确，预计观察到什么；
- `test_plan`：如何验证；
- `result`：验证后支持、否定或仍然未知。

例如：

> 假设：上下文压缩丢失了某个接口的必填参数约束。

可检验的预测是：使用原始完整上下文回放时，模型更可能正确调用工具；使用压缩后的上下文回放时，错误更容易出现。

如果实验结果并不支持这一预测，就不应该因为最初的解释听起来合理而继续修改压缩器。

## 4.3 根因应该允许多因素共同成立

真实失败经常不是单一原因。

例如，路由器将任务分给了一个不合适的专家，同时上下文压缩又丢失了关键约束，最后验收器也没有发现问题。

这时不能强迫系统只选一个根因。

建议支持：

- 直接触发原因；
- 促成失败的因素；
- 未能拦截问题的防护缺陷；
- 与本次失败无关的伴随现象。

这样，系统才能分别改进执行环节与防护环节，而不是只修复最接近错误发生位置的组件。

# 五、如何区分相关性与真正的因果关系？

这是整个专项最难的技术问题之一。

假设在最近 100 次失败任务中，70 次都使用了模型 B。

这不代表模型 B 一定是失败根因。

可能是系统最近把更多复杂任务路由给了 B；也可能是这 70 次任务恰好使用了有缺陷的工具版本；还可能是 B 真的存在某种能力退化。

单纯统计相关性，无法区分这些情况。

## 5.1 建立四级因果证据

| 证据等级 | 说明 | 可以支持的结论 |
|---|---|---|
| E0：观察到关联 | 两个现象经常同时出现 | 形成诊断假设 |
| E1：可重复复现 | 同样条件下能够重复观察到问题 | 证明现象稳定存在 |
| E2：对照实验支持 | 控制其他条件后，改变某个因素会改变结果 | 支持该因素对结果有影响 |
| E3：跨场景验证 | 在不同任务、样本或环境中得到一致证据 | 增强对因果机制与适用范围的信心 |

这不是绝对的科学证明等级，而是用于指导工程决策的证据分类。

某些问题无法完全复现，也无法进行随机实验。例如，已经发生的外部状态变化不能随意重新执行。这时系统应该保留不确定性，使用日志、状态快照和其他证据综合判断，而不是强行给出确定根因。

## 5.2 对照实验比反复询问模型更有价值

假设怀疑 Planner 的计划过于复杂，导致模型调用成本增加。

可以构造一组代表性任务，比较：

- 当前 Planner；
- 降低规划深度的候选；
- 保持规划不变、只减少冗余验证的候选。

尽量固定模型版本、工具版本、任务输入、预算和验收标准，再比较任务成功率、调用次数、耗时和回归情况。

如果只比较两段不同时间的生产日志，无法排除任务难度和环境变化带来的影响。

对于具有随机性的模型，还应当重复运行、记录随机性相关参数（如果可控），并报告结果的波动范围，而不是只选择最好的一次。

## 5.3 需要控制实验风险

因果实验不意味着可以随意在生产环境中改变系统。

建议优先使用：

1. 离线日志回放；
2. 模拟工具或沙箱；
3. 固定评测集上的候选对照；
4. 不产生外部副作用的影子执行；
5. 低风险、受控的灰度测试；
6. 经过授权的真实任务验证。

对于发送消息、删除文件、支付等有外部副作用的操作，不能为了比较两种策略而重复执行真实动作。

必须优先选择模拟、状态快照、只读观察或可安全撤销的测试方案。

# 六、如何追踪一次复杂任务的完整决策过程？

OCAE 不能只追踪调用了哪些工具，还需要记录关键决策的输入依据。

但这里有个重要边界：我们不需要、也不应该要求模型输出一份看似完整的内心思考过程，才能实现可追溯性。

真正有工程价值的是**可核验的决策摘要、候选选项、约束条件、选择结果和执行证据**。

## 6.1 记录什么样的决策信息？

例如，用户要求 EvoAgent 自动修复一个 Python 项目的测试失败。

系统可以记录：


    决策节点 1 · 专家路由
    **选择编程专家**
    依据：用户要求修改代码；项目检测到 Python 文件和测试配置。



    决策节点 2 · 任务规划
    **先复现失败，再定位代码，最后执行回归测试**
    约束：不得修改项目范围之外的文件；不得直接发布。



    决策节点 3 · 工具选择
    **运行指定测试命令**
    依据：测试配置存在，命令属于已授权的本地执行范围。



    决策节点 4 · 结果核验
    **测试失败，任务不能标记为完成**
    证据：退出码、失败测试名称和测试报告。



    决策节点 5 · 恢复策略
    **生成修复候选并重新测试**
    约束：限制修改范围；修复后必须重新执行相关回归集。


这种记录足以回答关键工程问题：

- 为什么选择这个专家？
- 为什么执行这项操作？
- 当时有哪些硬性约束？
- 哪些证据支持下一步行动？
- 为什么任务没有被提前判定为完成？
- 哪次修改真正改变了执行结果？

相比保存大段模型自由生成的解释，这种结构化记录更容易被程序检查、被测试复现，也更适合用于长期进化。

## 6.2 必须保留“当时的状态”，而不只是最终配置

假设某次任务失败后，系统更新了提示词。

如果日志只保存最新提示词，后续就无法还原任务失败时究竟使用了什么配置。

因此，关键执行轨迹必须引用不可变的配置快照，至少覆盖：

- 模型标识与适配版本；
- 系统提示词及相关指令版本；
- 路由、规划、ReAct 和上下文策略版本；
- 记忆检索策略版本；
- 工具与工作流版本；
- 关键预算参数；
- 验收器版本；
- 运行环境信息。

不一定每条事件都复制完整配置内容，但必须能够通过快照 ID 和内容哈希准确定位到当时使用的版本。

如果外部模型版本无法固定，也必须记录这一限制，避免误以为同样的配置一定能够产生完全相同的输出。

# 七、从日志到进化：如何让每项改进都有证据链？

这是 OCAE 与 EPRA、GOCG、模型适配系统协同的关键。

我建议为每项进化候选建立一个 `Evidence Bundle`（证据包），将问题、诊断、改动、评测和发布结果关联起来。

## 7.1 证据包的结构

<CodeBlock language="json" editable>
{
  "evolution_candidate_id": "candidate-042",
  "source_diagnostic_id": "diagnostic-019",
  "target_scope": {
    "component": "context_compressor",
    "expert": "coding",
    "model_snapshot": "model-b-snapshot-04"
  },
  "problem_evidence": [
    "trace-101",
    "trace-115",
    "trace-127"
  ],
  "hypothesis": {
    "summary": "Compression may drop required interface constraints",
    "status": "SUPPORTED_BY_EXPERIMENT"
  },
  "change": {
    "baseline_config": "context-v7",
    "candidate_config": "context-v8",
    "code_revision": "commit-reference"
  },
  "evaluation": {
    "dataset_version": "coding-eval-v12",
    "baseline_result_ref": "eval-baseline-51",
    "candidate_result_ref": "eval-candidate-52",
    "protection_suite_passed": true
  },
  "governance": {
    "decision": "PENDING_REVIEW",
    "reason": "Awaiting broader regression validation"
  }
}
</CodeBlock>

这里的 ID 都是示例。正式实现中，证据包还应包含数据集内容哈希、统计结果、置信区间或其他不确定性信息、成本记录、依赖版本以及发布审批记录。

## 7.2 一条完整的进化证据链

建议使用如下关系：

  {#each [
    ["Execution Trace","原始任务执行事实"],
    ["Diagnostic Case","问题假设与证据"],
    ["Improvement Candidate","针对根因提出的改动"],
    ["Evaluation Run","基线和候选的对照结果"],
    ["Governance Decision","批准、拒绝或继续验证"],
    ["Release Snapshot","发布后的稳定版本"],
    ["Post-Release Observation","真实运行中的后续表现"]
  ] as item}

      **{item[0]}**
      {item[1]}

    {#if item[0]!=="Post-Release Observation"}

    {/if}
  {/each}

这条链的价值在于：当发布后的真实表现退化时，系统可以回溯到具体候选、诊断证据和改动，而不是只能看到“最近一次更新后效果变差”。

同时，也能验证一次进化是否产生了预期收益，或者只是改善了评测集上的表现。

## 7.3 不要让证据链本身变成新的成本黑洞

不是所有改进都需要昂贵的因果实验。

对于简单且明确的错误，例如工具必填参数缺失，修复后通过契约测试和相关回归测试就可能足够。

对于跨模型迁移、上下文压缩、复杂规划和高风险权限逻辑等问题，则需要更强的证据。

建议根据变更风险、影响范围和诊断不确定性决定证据强度，而不是对每个候选一律执行同样昂贵的流程。

# 八、个人设备架构：手机、个人电脑与离线日志如何协作？

结合你之前确定的方向，EvoAgent 是手机优先的个人智能体，个人电脑或 Mini PC 承担更重的分析和进化工作。

因此，可观测性不能假设所有设备始终在线，也不能把全部原始对话和屏幕内容都上传到服务端。

建议采用“本地事件账本 + 可选诊断证据 + 跨设备同步”的结构。

## 8.1 手机端负责什么？

Android 端负责记录：

- 用户请求与任务 ID；
- 当前使用的专家和策略版本；
- 本地模型与远端模型调用的基本元数据；
- 应用操作、无障碍操作和原生接口调用结果；
- Android 权限状态及授权决策；
- 任务状态变化和关键检查点；
- 本地错误、超时、取消和恢复结果；
- 需要上传但尚未同步的事件。

手机端应该优先记录结构化元数据，而不是默认保存全部屏幕截图、完整模型上下文和所有语音原文。

## 8.2 个人电脑或 Mini PC 负责什么？

本地服务端可以负责：

- 汇总不同任务和设备的执行轨迹；
- 统计失败模式、成本与延迟；
- 构建诊断案例；
- 运行回放和本地测试；
- 比较稳定版本与候选版本；
- 生成进化证据包；
- 保存长期评测历史和版本关联；
- 将经过验证的改进发布为新的配置或适配快照。

这些职责不要求一开始就拆成多个独立服务。对于个人使用，优先实现一个模块化的本地进化服务，内部保持清晰的模块边界即可。

## 8.3 离线事件同步协议

建议每条待同步事件具有：

- 全局唯一的 `event_id`；
- 本地设备 ID；
- 本地递增序列号；
- 事件 Schema 版本；
- 记录时间；
- 任务和轨迹关联 ID；
- 同步状态；
- 载荷校验和。

同步采用至少一次投递，并通过唯一事件 ID 实现幂等去重。

也就是说，同一条事件可以因为断网被重复上传，但服务端不能重复计算它对任务统计的贡献。

事件同步成功与任务执行成功是两个完全不同的状态。日志上传失败，不应该导致已经完成的手机任务被重新执行。

### 一个典型的离线场景

1. 手机离线执行一项已授权的低风险任务。
2. 手机把任务事件和结果写入本地持久化队列。
3. 任务结束后，事件仍然保存在本地，不依赖服务端确认。
4. 网络恢复后，手机批量同步未确认事件。
5. 服务端根据 `event_id` 去重，并验证事件格式。
6. 服务端更新任务轨迹、诊断统计和待分析候选。
7. 进化系统生成新配置后，通过独立的版本发布机制返回手机。
8. 手机验证配置签名、兼容性和适用范围后，才允许启用。

如果日志包含尚未上传的敏感数据，系统应提供本地删除、脱敏和保留期限控制。对于已在服务端形成的派生诊断记录，也需要明确其数据来源和删除策略，避免原始日志删除后仍然保留不必要的敏感内容。

# 九、隐私与安全：可观测性不能成为另一个监控系统

这是个人智能体尤其需要重视的地方。

为了诊断问题，系统可能涉及语音转录、消息内容、屏幕截图、代码、文件路径和用户偏好。

如果全部永久保存，即使诊断能力变强，也会产生严重的隐私与存储风险。

我建议采用以下原则。

## 9.1 默认保存最少必要证据

优先保存：

- 事件类型；
- 错误码；
- 组件和版本标识；
- 时间、耗时和成本；
- 必要的状态摘要；
- 验收结果；
- 指向经过授权的诊断证据的引用。

只有当详细内容对故障诊断有明确价值时，才在授权范围内保留更完整的证据。

例如，普通的应用启动失败通常不需要永久保存完整屏幕截图；但如果某个 UI 识别错误反复发生，短期保存脱敏后的界面结构或用户批准的截图，可能有助于复现问题。

## 9.2 将原始内容与诊断元数据分开存储

建议区分：

- **事件元数据：** 用于统计和追踪；
- **原始内容：** 用户对话、代码、截图、语音等；
- **诊断证据：** 为特定问题选取的必要内容；
- **长期经验：** 从问题中提炼的、适用范围明确的规则。

这几类数据的访问权限和保留期限应该不同。

例如，诊断记录可以长期保留“工具必填参数校验缺失导致失败”的结论，但不一定需要永久保留当时完整的用户文件内容。

## 9.3 诊断证据不能直接变成长期记忆

原始错误案例中可能包含：

- 过期的项目路径；
- 临时令牌；
- 用户消息中的敏感内容；
- 错误的模型生成建议；
- 只适用于某个模型版本的补偿规则。

因此，长期记忆应保存经过筛选和验证的经验，并保留来源、适用范围和失效条件。

不要把所有日志自动向量化后写入共享记忆库。否则，错误经验可能被检索到其他专家中，形成跨领域污染。

# 十、如何让诊断结果反过来改进其他模块？

OCAE 的价值不仅是解释过去，还要为其他智能组件提供可靠输入。

建议建立标准化的诊断输出接口，让各模块通过结构化结果协作，而不是各自读取一堆日志、独立猜测根因。

例如：

<CodeBlock language="json" editable>
{
  "diagnostic_id": "diagnostic-019",
  "target": {
    "component": "context_compressor",
    "scope": "coding_expert"
  },
  "problem_type": "CONSTRAINT_LOSS",
  "evidence_level": "E2",
  "status": "SUPPORTED",
  "affected_task_classes": [
    "multi_file_refactoring"
  ],
  "estimated_impact": {
    "direction": "NEGATIVE",
    "magnitude": "NOT_YET_CALIBRATED"
  },
  "recommended_actions": [
    "ADD_CONTEXT_REGRESSION_CASE",
    "CREATE_COMPRESSION_POLICY_CANDIDATE"
  ],
  "required_validation": [
    "CODING_REGRESSION_SUITE",
    "CONTEXT_PRESERVATION_SUITE"
  ],
  "promotion_allowed": false
}
</CodeBlock>

这是概念接口，正式版本还需要定义枚举、字段约束、证据引用和版本兼容规则。

注意其中的 `promotion_allowed` 不应由诊断模型自行决定。它只能表示当前治理流程的状态；最终发布权限仍属于独立的门禁系统。

## 10.1 各模块如何消费诊断结果？

| 模块 | 可以利用的诊断信息 |
|---|---|
| 路由器 | 哪类任务在什么条件下容易路由错误 |
| 记忆系统 | 哪些经验有效、过期或不适用于当前模型 |
| 上下文引擎 | 哪些约束在压缩后容易丢失 |
| Planner | 哪些计划模式导致重复步骤或遗漏关键检查 |
| ReAct 控制器 | 哪些动作在观察后没有根据新证据调整 |
| 工具系统 | 哪些参数、状态码或副作用处理存在缺陷 |
| 验收器 | 哪些检查遗漏了真实失败，或产生了错误拒绝 |
| 自我修复系统 | 哪些恢复策略有效，哪些只增加成本 |
| EPRA | 哪些候选值得优先投入资源 |
| GOCG | 候选是否真的改善整体目标，是否存在局部退化 |
| 模型适配系统 | 问题是否与特定模型、版本或上下文策略有关 |

这样，各模块不需要自行从原始日志中重复推理，而是可以共享已经整理好的诊断证据。

但必须保留一个原则：**诊断结果是可追踪的输入，不是不可质疑的真理。** 当新证据出现时，诊断可以被修正，原有结论也必须保留历史版本。

## 11.2 推荐的个人部署方式

可以采用：

- Android 本地数据库保存任务状态和待同步事件；
- 个人电脑或 Mini PC 使用 SQLite 或其他合适的本地数据库保存事件索引和诊断元数据；
- 原始诊断证据使用独立的受控文件存储；
- 通过唯一事件 ID、内容哈希和版本引用管理关联关系；
- 用结构化查询和本地报表分析任务失败、成本与延迟；
- 仅在确有需要时接入更专业的日志和指标工具。

这样既保留完整的架构扩展能力，又不会让个人使用的 EvoAgent 一开始就承担不必要的运维成本。

## 11.3 与之前架构的边界

OCAE 不应该成为所有模块都必须通过的同步中间层。

正常执行任务时，日志记录应该尽可能轻量，不阻塞关键动作。诊断和进化可以在后台异步处理。

但某些安全审计、授权决策和关键状态检查属于执行正确性的一部分，不能因为日志系统不可用就被跳过。

因此，应当区分：

- **普通遥测：** 可以缓冲、延迟或在明确策略下丢弃低价值记录；
- **关键审计事件：** 必须可靠保存，否则需要按风险策略阻止相关高风险动作；
- **任务状态与检查点：** 必须由任务执行系统负责持久化，不能只依赖遥测；
- **进化证据：** 在候选发布之前必须达到对应证据要求。

这能避免出现一种错误架构：为了保证日志完整而让所有任务停摆，或者为了保证任务继续运行而丢失关键授权记录。

# 十二、如何衡量可观测性与因果归因的效果？

可观测性本身也需要评测，否则系统可能记录了越来越多的日志，却没有提高诊断能力。

建议重点关注以下指标。

| 指标 | 目的 |
|---|---|
| 轨迹完整率 | 关键任务是否拥有足够的执行记录 |
| 版本关联完整率 | 能否确定任务实际使用的模型、工具和配置版本 |
| 失败复现率 | 是否能够在相近条件下重现关键问题 |
| 诊断准确率 | 诊断假设是否得到后续证据支持 |
| 错误归因率 | 是否经常把相关因素误判为根因 |
| 根因未知率 | 仍无法确定根因的问题占比 |
| 诊断成本 | 找到有用结论需要多少模型调用、时间和计算资源 |
| 修复有效率 | 发布后是否真正改善目标问题 |
| 回归发现率 | 是否能及时发现其他能力的退化 |
| 证据可追溯率 | 进化结论是否能回溯到原始任务、实验和发布记录 |
| 离线同步完整率 | 断网期间的重要事件是否能够正确补传和去重 |
| 敏感信息暴露率 | 诊断与存储是否发生不必要的敏感内容暴露 |

这里有两个特别重要的判断。

第一，根因未知率不能简单追求越低越好。面对证据不足的问题，诚实地保留未知状态，比强行给出错误诊断更好。

第二，轨迹完整率也不能靠永久保存所有原始内容来提升。真正的目标是以合理的存储和隐私成本，保留足以支持任务追溯、问题诊断和进化验证的证据。

# 十四、下一专项：记忆生命周期、经验可信度与跨专家知识治理

现在，我们已经为 EvoAgent 建立了比较完整的执行证据链。

但还有一个问题必须继续深入：

**当系统积累了越来越多的任务记录、失败案例、用户偏好和修复经验时，究竟应该把什么保存为记忆，保存多久，允许谁使用，又如何判断它仍然有效？**

这是你之前反复强调的记忆系统核心问题，也是长期自进化最容易发生隐性退化的地方。

例如：

- 某个编程专家从模型 A 的错误中总结出一条提示词补偿规则；
- 路由器把一条过时经验用于新的领域；
- 用户修改了偏好，但旧记忆仍然影响任务行为；
- 某个工作流在旧工具版本上成功，却在新版本上不再可靠；
- 一条错误诊断被写入长期记忆，之后反复影响新的判断；
- 上下文压缩把不同来源、不同可信度的经验混在一起；
- 某项经验长期没有被使用，但仍占据检索空间；
- 多个专家对同一问题形成相互冲突的结论。

下一专项建议设计 **Memory Lifecycle & Knowledge Governance Engine（记忆生命周期与知识治理引擎）**，重点讨论：

1. 如何区分工作记忆、情景记忆、语义记忆、用户偏好和程序性经验；
2. 哪些内容应该永久保存，哪些只需要在当前任务中存在；
3. 如何为经验记录来源、证据强度、适用范围和失效条件；
4. 如何防止未经验证的诊断进入共享记忆；
5. 如何让专家拥有独立记忆，同时共享经过验证的通用知识；
6. 如何处理冲突、过期、重复和错误记忆；
7. 如何判断记忆是否值得继续保留；
8. 如何设计记忆检索、重排、压缩和遗忘机制；
9. 如何让用户偏好更新、撤销和删除具有一致的传播语义；
10. 如何让记忆在模型切换、断网、跨设备同步和版本回滚时保持可追溯。

这一专项将进一步明确：EvoAgent 如何从一次次任务中积累真正有用的长期能力，而不是仅仅变成一个越来越庞大、却越来越难以控制的历史记录库。

## 十五、先确立记忆系统的核心原则

在进入下一专项之前，我建议先冻结三个基本原则：

1. **记录不等于记忆。** 一次任务的完整执行轨迹应当进入可追溯的历史记录，但只有经过筛选、具有未来价值的内容，才应该进入长期记忆。
2. **记忆不等于事实。** 记忆必须保留来源、可信度、适用范围和有效性状态，不能因为某条信息被反复检索，就自动认为它正确。
3. **共享不等于全局可用。** 某条经验可以被多个专家检索，不代表它适用于所有专家；共享范围必须受到适用条件和证据的约束。

这也意味着，记忆系统不能仅仅是一个向量数据库。它需要与执行轨迹、诊断案例、模型适配、权限治理和全局目标共同协作。

下一轮应该从记忆分类与数据模型开始，逐步深入到记忆生成、验证、检索、更新、冲突处理、失效、遗忘和跨设备同步，最终形成一套可以直接落入 EvoAgent 全量架构的记忆治理设计。
