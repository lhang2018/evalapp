<WritingBlock id="689142" variant="document"># EvoAgent 专项设计 #89：知识检索、上下文注入与运行时知识使用治理

**英文名称：** Knowledge Retrieval, Context Injection & Runtime Knowledge Governance

**文档版本：** 1.0

**关联专项：** #75—#88

**设计状态：** 专项设计基线，待实施与验收。

## 一、专项目标

建立一套能够为当前任务检索、筛选、组织、注入和验证知识的运行时机制。

系统需要解决：

1. 如何从通用知识、领域知识、项目知识和历史经验中找到当前真正需要的内容？
2. 如何区分文本相似、语义相关与实际适用？
3. 如何防止旧版本经验、错误假设和未经验证的知识进入执行上下文？
4. 如何确定不同来源的指令、事实、记忆和经验之间的优先级？
5. 如何在上下文预算有限时保留最重要的信息？
6. 如何压缩长对话，同时保留任务目标、关键约束、用户决策和已验证结果？
7. 如何避免一个专家的知识污染其他专家？
8. 如何处理知识之间的冲突、过期、缺失和不确定性？
9. 如何防止检索到的外部内容包含恶意指令，进而影响智能体行为？
10. 如何判断注入的知识究竟改善了任务质量，还是只增加了上下文长度和模型成本？
11. 如何在网络中断时继续使用已验证的本地知识？
12. 如何让检索与上下文治理自身也能够持续改进？

**核心原则：检索是候选发现，适用性判断是使用许可，注入是上下文组织，结果验证是效果依据。四者不能合并为一次简单的相似度搜索。**

## 二、总体架构

### 2.1 逻辑组件

| 组件 | 核心职责 |
|---|---|
| Context Query Builder | 从当前任务、执行状态和未解决问题构建检索请求 |
| Knowledge Retriever | 从允许访问的知识空间中召回候选资产 |
| Eligibility Filter | 检查知识状态、权限、版本、适用条件和有效性 |
| Knowledge Reranker | 综合任务相关性、证据质量和适用性重新排序 |
| Context Assembler | 按优先级组织任务上下文和知识引用 |
| Context Budget Manager | 控制上下文长度、成本与必要信息保留 |
| Context Integrity Checker | 检查关键约束、引用、状态和不确定性是否丢失 |
| Knowledge Usage Tracker | 记录知识使用情况及其实际效果 |

这些是逻辑职责，可以先实现为共享内核中的模块，不要求分别部署成独立服务。

### 2.2 运行流程

```text
当前任务与执行状态
        ↓
提取目标、约束和未解决问题
        ↓
生成检索请求
        ↓
从允许的知识空间召回候选
        ↓
过滤权限、状态、版本和适用范围
        ↓
重排序并评估证据质量
        ↓
选择必要知识与原始证据引用
        ↓
构建分层上下文
        ↓
预算检查与关键约束完整性检查
        ↓
交给当前执行器或领域专家
        ↓
执行并验证结果
        ↓
记录知识的实际使用效果
        ↓
反馈给知识治理与独立评测体系
```

如果没有找到适用知识，系统应允许正常执行，而不是为了使用知识库而强行注入无关内容。

## 三、上下文的优先级与分层

上下文不能只是历史对话、记忆和检索结果的简单拼接。不同信息具有不同的权威性、时效性和作用范围。

### 3.1 六类上下文

**C1：系统安全与运行规则**

包括系统必须遵守的安全边界、工具调用规则和运行约束。检索到的知识、历史记忆和用户文件均不能覆盖这些规则。

**C2：当前任务契约**

包括当前用户目标、明确指令、约束、验收标准、授权范围和预算。

当前任务的明确要求，优先于从用户历史行为中推断出来的偏好。

**C3：当前执行状态**

包括当前计划、节点状态、已完成工作、未解决问题、工具结果、已验证事实和待确认事项。

这部分决定智能体当前实际处于什么状态，不能仅依赖历史对话重新猜测。

**C4：适用的已验证知识**

包括经过验证的通用知识、领域经验、兼容性规则和成熟工作流。

只有通过适用性检查的内容才能进入当前执行上下文。

**C5：项目与用户长期上下文**

包括已确认的项目约定、持续有效的用户偏好、长期目标及相关历史决策。

这些信息用于提高连续性，但不能自动替代当前任务的明确要求。

**C6：候选信息与探索性内容**

包括尚未验证的假设、检索到的参考资料、备选方案和待核实事实。

必须显式标记其不确定性，不能混入已确认事实。

### 3.2 优先级不是简单的单一排序

上述层次用于确定权威性和组织方式，不意味着越靠后的信息永远不重要。

例如，一份当前项目的实际配置文件，可能比通用知识更能决定某个依赖是否兼容。

因此，冲突处理应综合考虑：

- 信息的来源；
- 对当前任务的适用范围；
- 是否为明确指令或实际观察；
- 发生时间与版本；
- 是否有独立验证证据；
- 是否存在更权威的当前事实。

对于真正的指令冲突，不能用检索相关性或多数意见代替规则优先级判断。

### 3.3 当前用户要求与历史偏好冲突

例如，用户过去经常要求简洁回答，但当前明确要求完整架构设计。

系统应遵循当前任务要求，而不是为了匹配历史偏好而缩减必要内容。

同样，用户曾经允许某类任务自动执行，不代表该授权自动扩展到其他任务、其他设备或更高风险的操作。

## 四、知识检索流水线

### 4.1 第一步：构建任务检索请求

检索请求不能只使用用户原话作为搜索词。

系统应提取：

- 当前目标；
- 任务类型；
- 当前专家；
- 未解决的问题；
- 必要的技术实体；
- 环境与版本信息；
- 关键约束；
- 需要查找的知识类型；
- 允许访问的命名空间；
- 当前预算与时延限制。

例如，用户要求修复 Python 项目的依赖问题时，检索请求应该包含相关错误、依赖名称、版本约束和运行环境，而不只是“如何修复依赖错误”。

如果关键信息缺失，系统可以先进行低成本检索或环境检查。只有当缺失信息确实影响正确性时，才需要向用户询问。

### 4.2 第二步：多路召回

建议支持以下检索方式：

- 关键词与精确匹配；
- 语义向量检索；
- 元数据过滤；
- 结构化字段查询；
- 依赖关系检索；
- 通过已知知识资产引用追踪来源；
- 根据历史故障案例检索相似模式。

不同检索方式可以组合使用，但不要求每个任务都调用全部检索器。

简单任务可以直接使用精确匹配；复杂故障诊断则可以采用多路召回，再通过适用性判断筛选。

### 4.3 第三步：硬性资格过滤

候选知识进入排序之前，必须先检查不可妥协的条件：

1. 当前任务是否有权访问该知识；
2. 资产是否允许使用；
3. 版本和依赖是否兼容；
4. 适用条件是否满足；
5. 是否存在已知的失效或撤销状态；
6. 是否违反项目隔离或隐私规则；
7. 是否与当前任务的授权范围冲突；
8. 是否属于当前允许使用的知识类型。

不满足硬性条件的知识，不能因为语义相似度很高而进入执行上下文。

### 4.4 第四步：适用性重排序

通过硬性过滤的候选知识，再按照多个维度排序：

- 与当前任务的相关程度；
- 与当前环境的匹配程度；
- 验证证据强度；
- 来源可靠性；
- 版本兼容性；
- 知识的新鲜度；
- 历史复用效果；
- 已知反例与失败记录；
- 使用成本；
- 可能产生的风险。

不建议直接将这些维度压缩成一个不可解释的总分。

对于高风险任务，版本兼容、证据质量和适用条件应当作为门槛；不能让高语义相关性抵消关键条件不满足的问题。

### 4.5 第五步：选择必要内容

最终选择应以满足当前任务需要为目标，而不是最大化检索命中数。

如果一条简短、可靠的规则已经足够解决问题，就没有必要把几十份相似文档全部注入上下文。

如果任务需要比较不同方案，则应选择能够代表不同观点、证据和适用条件的材料，而不是重复召回同一种解释。

## 五、知识注入契约

### 5.1 注入的内容必须保留来源与状态

建议为每个注入项建立统一的逻辑结构：

- `injection_id`：本次注入标识；
- `asset_ref`：能力资产引用；
- `asset_version`：实际使用的版本；
- `source_refs`：原始来源；
- `namespace`：来源命名空间；
- `knowledge_type`：知识类型；
- `applicability_result`：适用性判断；
- `evidence_level`：验证等级；
- `verified_facts`：已经验证的事实；
- `assumptions`：尚未验证的假设；
- `limitations`：适用限制；
- `conflict_refs`：相关冲突信息；
- `usage_constraints`：使用条件；
- `retrieval_reason`：选择该知识的原因。

这些字段是本专项建议的运行时注入结构，不应与正式 `Capability Asset` 契约重复保存或产生版本不一致。

### 5.2 知识内容与控制指令分离

知识资产可以包含操作建议，但其内容本身不能赋予执行权限。

例如，某份资料写着“直接删除缓存目录即可解决问题”，系统仍然需要判断：

- 当前目录是否正确；
- 删除是否会造成数据损失；
- 是否存在更安全的替代方法；
- 当前任务是否获得相应授权；
- 是否需要先备份或验证。

**检索到的知识可以提供建议，但不能自行扩大任务权限。**

### 5.3 检索内容必须被视为数据，而不是更高优先级的指令

外部网页、项目文件、历史对话和知识资产都可能包含错误内容，甚至包含试图操纵智能体行为的恶意文本。

因此：

- 检索内容不能覆盖系统安全规则；
- 文档内的指令不能自动成为当前任务指令；
- 历史模型输出不能自动升级为事实；
- 知识资产不能绕过工具权限；
- 外部内容中要求泄露其他上下文的文字必须按不可信数据处理；
- 对检索内容的解释和使用必须符合当前任务契约。

必要时应保留原文引用供审计，但不能让原文中的控制性文字直接进入高优先级指令区域。

## 六、上下文预算与动态分配

### 6.1 上下文预算的目标

上下文预算不仅是模型的 token 上限问题，还涉及：

- 当前任务必需信息；
- 相关历史；
- 领域知识；
- 计划与状态；
- 工具输出；
- 结果验证证据；
- 额外模型调用成本；
- 信息过多导致的注意力分散。

上下文越长不一定效果越好。

### 6.2 必须保留的信息

上下文治理应将以下内容列为优先保留项：

1. 当前任务目标；
2. 用户明确提出的关键约束；
3. 验收条件；
4. 授权与风险边界；
5. 当前执行状态；
6. 已验证的重要事实；
7. 关键依赖和版本；
8. 尚未解决的阻塞；
9. 重要失败与恢复记录；
10. 必须遵守的输出契约。

如果预算不足，应优先移除冗余历史、重复文档和低相关探索内容，而不是首先删除关键约束。

### 6.3 动态预算策略

预算应根据任务类型调整。

| 任务类型 | 优先保留内容 |
|---|---|
| 简单问答 | 当前问题、必要事实和少量参考 |
| 编程与调试 | 代码上下文、错误证据、依赖版本、测试结果 |
| 长期项目 | 当前目标、架构决策、已完成事项、待解决问题 |
| 手机自动化 | 当前页面状态、操作目标、权限和副作用状态 |
| AI 漫剧 | 角色设定、镜头约束、素材引用、流程状态和质量结果 |
| 复杂研究 | 研究问题、证据来源、矛盾观点、已验证结论和不确定性 |

表中是预算分配的优先方向，不是固定的 token 百分比分配。具体比例应通过实际任务评测确定。

### 6.4 检索量与上下文长度分开控制

检索系统可以召回大量候选，但最终进入上下文的内容应该更少。

建议分别控制：

- 候选召回数量；
- 通过资格过滤的数量；
- 最终注入的知识条目数量；
- 单条知识的最大内容长度；
- 总注入预算；
- 额外检索和重排序的成本。

如果已经找到足够证据，就应停止继续检索。

如果关键证据不足，则应增加针对性检索，而不是重复搜索相同内容。

## 七、上下文压缩与完整性检查

### 7.1 压缩不能改变任务事实

上下文压缩的目标是减少冗余，而不是重新解释或改写任务本身。

应尽可能保留：

- 用户明确确认的决策；
- 未完成任务及其当前状态；
- 重要约束和验收标准；
- 关键错误和修复尝试；
- 版本、标识符和必要引用；
- 已验证事实与未验证假设的区别；
- 被否决方案及其原因；
- 仍然存在的不确定性。

### 7.2 必须区分四种信息

压缩时，应明确区分：

- **事实：** 有实际证据支持；
- **决策：** 用户明确决定或有权组件正式批准；
- **假设：** 尚待验证；
- **建议：** 系统提出但尚未被采纳。

不能把“系统建议采用方案 A”压缩成“用户决定采用方案 A”。

### 7.3 压缩后完整性检查

压缩结果应与压缩前的任务契约及关键状态进行比较，检查：

- 是否丢失关键目标；
- 是否遗漏约束；
- 是否改变用户决策；
- 是否丢失必要的版本信息；
- 是否将不确定结论变成确定事实；
- 是否丢失重要失败记录；
- 是否错误合并互相矛盾的信息。

如果检查发现关键内容丢失，应恢复相应信息或重新构建上下文，不能继续执行一个已经失真的摘要。

### 7.4 压缩失败时的降级

如果系统无法证明压缩结果保留了关键状态：

1. 保留原始任务契约；
2. 恢复必要的原始证据引用；
3. 重新生成摘要或减少压缩程度；
4. 在必要时重新检索；
5. 对关键约束重新执行一致性检查。

不能为了节约 token 而牺牲任务正确性。

## 八、知识冲突与证据优先级

### 8.1 冲突类型

应区分：

- 事实冲突；
- 版本冲突；
- 适用范围冲突；
- 历史偏好与当前要求冲突；
- 用户决策与系统推断冲突；
- 不同专家的结论冲突；
- 旧知识与新观察冲突。

不同冲突应使用不同处理规则。

### 8.2 处理流程

1. 识别冲突的具体字段或结论；
2. 检查来源、时间和版本；
3. 确定各自适用范围；
4. 检查是否存在更直接的当前证据；
5. 必要时执行独立验证；
6. 无法消除冲突时保留多个结论；
7. 对影响任务正确性的关键冲突，暂停依赖该结论的动作。

不能通过简单多数投票、最高语义分数或最新时间戳决定所有事实冲突。

### 8.3 当前观察与历史知识的关系

历史知识可以帮助解释当前观察，但不能覆盖真实的当前状态。

例如，知识库记录某个工具通常返回某种结果，而当前实际返回了不同结果，系统应记录差异并进一步核验，而不是强行将实际结果解释成旧知识预期的内容。

## 九、上下文隔离与专家协同

### 9.1 命名空间隔离

检索系统应复用现有知识命名空间：

- `protected_core`；
- `shared_validated`；
- `domain_private`；
- `project`；
- `task`。

每次检索都应根据当前任务、专家身份和授权范围确定允许访问的集合。

不能因为多个专家共享同一个运行进程，就允许它们默认访问彼此的全部项目知识、任务记忆或私有数据。

### 9.2 跨专家知识传递

专家之间优先传递经过整理的任务产物、事实引用、状态和明确约束，而不是复制整段内部对话。

例如，编程专家向通用协调器提供：

- 修改结果；
- 测试证据；
- 依赖变化；
- 尚未解决的问题；
- 适用范围和风险。

协调器再根据下一位专家的需求，选择必要内容进行传递。

### 9.3 防止专家间的错误传播

如果一个专家提供的是未经验证的假设，下游专家必须能够识别其不确定性。

跨专家传递的内容应保留来源、版本、验证状态和适用限制。

共享通用内核可以统一传递机制，但不能自动把某个领域的假设转化为所有专家都必须遵循的规则。

## 十、运行时知识使用效果评估

### 10.1 每次注入不必调用额外模型评估

为了避免监控和知识检索反过来拖慢任务，系统应优先记录低成本的结构化指标：

- 检索到哪些资产；
- 哪些资产通过了资格过滤；
- 哪些资产实际进入上下文；
- 注入了多少内容；
- 使用了哪个资产版本；
- 相关任务是否通过验收；
- 是否出现知识不适用或冲突。

只有当任务失败、知识使用产生明显收益，或者需要评估候选检索策略时，才进一步开展深度分析。

### 10.2 不能把“知识被使用”当成成功

知识可能被检索、被注入、被模型引用，但仍然没有改善任务结果。

应区分：

1. 检索成功；
2. 适用性判断成功；
3. 正确注入；
4. 正确使用；
5. 任务结果改善。

只有最后的实际效果，才能证明知识使用具有价值。

### 10.3 评估方法

在条件允许时，可以对同类任务进行对照：

- 基线：使用现有检索策略；
- 候选：使用新的检索、过滤或注入策略；
- 共同条件：保持任务集、验收标准和运行环境尽可能一致。

比较最终质量、成功率、成本、时延、上下文长度和失败类型。

不能只比较模型回答是否更长、更详细，或是否引用了更多知识。

## 十一、缓存与离线策略

### 11.1 缓存必须与版本绑定

检索缓存应考虑：

- 查询目标；
- 当前专家与命名空间；
- 知识资产版本；
- 兼容性状态；
- 权限范围；
- 相关运行环境；
- 资产失效或撤销状态。

如果知识资产已经降级或废弃，不能仅因为缓存仍然存在，就继续将其作为有效知识注入。

### 11.2 离线知识使用

Android 设备或个人服务器离线时，可以使用符合离线策略且已验证的本地知识。

如果缺少在线更新或关键版本信息，应限制知识适用范围。

例如，离线设备可以继续使用已缓存的稳定操作流程，但不能假设云端服务的最新接口、库存、价格或状态仍然有效。

### 11.3 重新连接后的处理

重连后，应根据正式的资产版本、兼容性声明和同步回执更新本地知识状态。

发现本地知识与服务端版本冲突时，应明确选择、验证或降级，而不是静默覆盖正在使用的稳定知识。

## 十二、与无限优化闭环的结合

本专项的进化对象包括：

- 检索策略；
- 候选召回方法；
- 适用性过滤规则；
- 排序策略；
- 上下文组装方法；
- 压缩策略；
- 知识冲突处理；
- 预算分配策略。

改进流程如下：

1. 收集知识检索与任务结果的关联证据；
2. 识别错误检索、错误注入、知识缺失和上下文失真；
3. 分析问题是否由检索策略、资产质量或上下文治理造成；
4. 生成候选策略；
5. 使用固定评测集进行对照；
6. 检查任务质量、稳定性、成本和时延；
7. 通过现有进化发布门禁；
8. 受控发布；
9. 观察实际任务效果；
10. 出现退化时降级或回滚。

必须区分：

- 知识内容发生变化；
- 知识检索策略发生变化；
- 上下文组织方式发生变化；
- 模型或执行器发生变化。

否则，系统很难确定性能改善或退化究竟由什么引起。

## 十五、完成判定

只有满足以下条件，才能认定本专项实施验收完成：

- 系统能够根据任务需要检索知识，而不是无差别加载全部记忆；
- 知识检索与适用性判断相互独立；
- 不兼容、过期或无权访问的知识不会直接进入执行上下文；
- 上下文中能够区分事实、决策、假设和建议；
- 当前任务的关键约束在压缩和注入过程中得到保留；
- 检索内容不能覆盖更高优先级的安全与运行规则；
- 不同专家的私有知识能够按范围隔离；
- 上下文预算能够在成本与质量之间进行受控管理；
- 系统能够验证知识使用的实际效果；
- 离线和缓存场景能够保持版本可追溯；
- 检索策略的改进经过独立评测和正式门禁；
- 所有关键验收场景均有真实执行证据。

**最终目标：让 EvoAgent 在正确的时间，为正确的任务，使用正确的知识，同时保留必要的约束、证据和不确定性。知识的价值不在于被检索了多少次，而在于它是否帮助智能体更可靠、更高效地完成用户真正需要的任务。**</WritingBlock>

## 下一项专项：#90

建议继续推进 **#90：长期记忆、用户状态建模与主动帮助触发治理**。

这项专项将回到你之前特别强调的面向用户的问题：智能体不能只是被动完成指令，也应该在合适的时候发现用户正在推进的事情、识别遗漏或风险，并提供有价值的资料、建议和意想不到的便利。

但它必须与执行质量优先的原则结合起来。

#90 将重点设计：

1. 如何从最近对话和已授权的历史信息中，提取用户正在推进的项目与事项。
2. 如何区分用户明确表达的目标、系统推断出的目标和仅仅可能存在的机会。
3. 如何判断什么时候应该主动提醒、补充资料、提出建议，什么时候应该保持安静。
4. 如何避免把过时记忆、错误推断或一次性的需求当成长期用户状态。
5. 如何在主动帮助与当前任务执行之间进行资源隔离。
6. 如何验证主动帮助是否真的节省了用户时间、减少了遗漏或改善了决策。
7. 如何让用户能够纠正、拒绝或调整主动帮助，而不必因此失去其他智能体能力。
8. 如何让长期记忆和主动辅助持续进化，同时不影响正常任务的质量、时延和稳定性。

最重要的架构原则是：**主动帮助是增强用户价值的独立能力，不是执行链路的必经步骤。** 用户正在等待一个高质量的任务结果时，系统不能为了分析用户状态、生成额外建议或展示自主性而打断核心执行。
