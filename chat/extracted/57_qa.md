# EvoAgent 用户习惯识别与个性化系统：全量设计

这一轮，我们专门设计第二个核心子系统：**让 EvoAgent 在长期聊天和工作中逐渐理解用户的习惯，但不因为几次偶然行为就误判用户，也不让个性化损害通用能力和领域专家。**

这对 EvoAgent 特别重要，因为它不是只回答问题的聊天机器人。它既要处理日常聊天，也要完成编程、手机操作、复杂项目、AI 漫剧制作等长任务。

不同场景下，用户的行为可能完全不同。

例如，同一个用户可能：

- 日常聊天时喜欢简短回答；
- 讨论系统架构时喜欢深入推演；
- 写代码时优先要求正确性和测试；
- 制作视频时更关注画质、成本和速度的平衡；
- 在某个项目中要求所有重要决策先经过讨论。

如果系统只建立一个简单的“用户喜欢详细回答”标签，就可能把用户的日常聊天也变成长篇大论。

所以，我们要解决的不是简单的用户画像问题，而是：

**如何学习用户在什么情境下、为了什么目标、倾向于怎样协作，以及何时不应该套用这种习惯。**

# 一、首先明确：个性化不能改变智能体的基本能力

我建议将 EvoAgent 的个性化设计分成四个相互独立的层次。


    <title size="lg">第一层：用户身份与明确偏好</title>
    用户明确告诉系统的长期要求、语言偏好、默认输出方式和授权范围。


    <title size="lg">第二层：情境化习惯</title>
    用户在编程、研究、日常聊天、项目规划等不同场景下表现出的不同偏好。


    <title size="lg">第三层：协作策略</title>
    决定何时先给结论、何时追问、何时深入分析、何时直接执行、何时展示进度。


    <title size="lg">第四层：效果反馈</title>
    评估这些偏好是否真的减少沟通成本、提高任务质量，并根据反馈调整。


这里有一个硬性边界：

- 用户偏好可以影响回答形式、协作方式和默认策略。
- 用户偏好不能覆盖当前明确指令、安全约束、权限要求或任务的客观验收标准。
- 推断出的习惯只能作为有条件的建议，不能被提升为不可更改的规则。
- 个性化系统不能直接修改编程专家、旅游专家等领域专家的底层能力，只能通过经过治理的偏好配置影响其运行。

例如，用户习惯直接让智能体执行任务，不代表智能体可以跳过支付、删除文件或发送消息等操作所需的授权。

# 二、用户习惯从哪里来？建立六种信号来源

系统不能只靠分析聊天文本，也不能只靠统计用户点击了什么。我们需要区分不同信号的可靠程度。

| 信号来源 | 示例 | 默认处理 |
|---|---|---|
| 明确声明 | “以后复杂任务先给完整方案” | 直接形成有范围的偏好记录 |
| 明确纠正 | “我说的是全量设计，不是 MVP” | 优先修正当前任务理解，并评估是否需要更新长期偏好 |
| 重复选择 | 多次选择先看方案、再开始执行 | 形成习惯候选，结合场景验证 |
| 任务行为 | 经常要求补充测试、验收和失败恢复 | 推断可能的工作方式，不直接认定为全局偏好 |
| 显式反馈 | 用户评价回答太长、遗漏关键条件 | 形成针对特定输出维度的反馈 |
| 任务结果 | 某种协作方式减少返工、提高成功率 | 作为效果证据，但不能单独证明用户的主观偏好 |

这里需要严格区分两件事：

**用户喜欢什么**与**什么对用户的任务有效**并不是同一个问题。

例如，用户可能偏好一次性得到完整方案，但在某些简单任务中，先问一个关键问题反而更高效。系统可以据此调整执行策略，但不能因为某种策略提高了成功率，就擅自宣称用户喜欢它。

## 2.1 观察不等于记忆

我建议建立一个两阶段机制。

第一阶段是信号观察。系统记录经过允许的交互事件，例如用户明确纠正了某种输出、反复选择某种工作方式，或者某个项目反复出现同类要求。

第二阶段才是个性化更新。系统评估这些信号的范围、可靠性和实际价值，决定是否建立或更新偏好。

这可以避免每一条聊天消息都变成长期记忆。

对于不需要长期保存的信号，可以只在当前任务中使用；对于需要进一步验证的信号，可以保留有限期限的候选记录；对于用户明确确认的偏好，则可以直接进入已确认状态。

# 三、最关键的设计：每种习惯都必须带有适用范围

我建议每条习惯至少回答四个问题：

1. 用户倾向于什么？
2. 在什么场景下适用？
3. 依据什么证据得出？
4. 哪些情况不应该套用？

例如：


    <title size="lg">习惯记录示例</title>
    已确认示例

  以下内容用于展示数据结构，不代表系统自动认定的用户偏好。

  偏好内容
  复杂架构任务优先提供完整设计，再逐步深入实现细节。
  适用范围

    系统架构
    复杂工程规划
    长期项目设计

  不适用条件
  用户明确要求简短回答、快速查值，或当前任务只需要一个直接答案。
  证据类型
  用户明确声明，或多次在类似场景中确认。
  使用方式
  作为默认协作策略；当前明确指令优先。

这样，个性化系统学到的就不是一个脱离背景的标签，而是一条具有条件的策略。

## 3.1 适用范围需要支持层级

我建议至少包括：

- 全局：跨大多数任务适用；
- 交互类型：例如聊天、问答、语音交流；
- 领域：例如编程、旅游、视频制作；
- 项目：例如 EvoAgent 的架构设计；
- 任务：只在当前任务中生效。

其中，范围越广，越应该有充分的证据支持。

一个偏好可以从局部逐步扩展到更广的范围，但不应该因为用户在一个项目中反复提出要求，就自动升级为全局习惯。

# 四、如何从行为中学习，而不误判用户？

这是个性化系统最难的部分。

我不建议使用“出现三次就自动记住”这种简单规则。频次只能作为证据之一，还需要考虑任务相似性、时间跨度、明确程度和反例。

建议为习惯建立五个状态：

  {#each [
    ["OBSERVED","观察到信号","只用于当前任务，尚未形成稳定判断。"],
    ["CANDIDATE","形成候选","出现重复模式或有价值的行为信号，等待更多证据。"],
    ["CONFIRMED","已确认","用户明确确认，或系统有充分证据支持其在特定范围内稳定适用。"],
    ["REVIEW_REQUIRED","需要复核","出现冲突、长期未使用或新的反例。"],
    ["REVOKED","已撤销","用户撤销或该偏好已不再适用。"]
  ] as item}


        {item[0]}


        **{item[1]}**
        {item[2]}


  {/each}

注意，用户明确说“以后都这样做”，可以直接建立已确认偏好；不必强迫用户重复确认。

但行为推断需要更加谨慎。例如，系统发现用户经常要求完整文档，可以先在复杂工程设计场景中建立候选，而不是立刻把所有回答都变长。

## 4.1 评估习惯时考虑哪些因素？

建议采用规则与统计相结合的方式：

- **明确程度**：是直接表达偏好，还是系统推测？
- **场景一致性**：行为是否发生在相似任务中？
- **时间跨度**：是集中在一天内出现，还是长期持续？
- **独立性**：是否只是同一条要求被重复引用？
- **反例**：用户是否曾明确表示不喜欢这种做法？
- **效果**：是否真的减少了重复纠正或改善了任务结果？
- **时效性**：偏好是否可能随着项目或阶段变化？

不能把这些因素简单加权成一个万能分数。明确指令、用户撤销和适用范围应当具有确定性的规则；统计评分主要用于排序候选和决定是否需要复核。

## 4.2 负反馈应该怎样处理？

假设系统连续几次给出冗长回答，用户说：“不要每次都解释这么多。”

系统至少要做三件事：

1. 立即调整当前对话的回答方式。
2. 判断用户是在纠正当前回答，还是在表达更长期的偏好。
3. 如果含义明确且范围清楚，再更新相应的偏好记录。

不能仅仅降低一个“详细程度”分数，却不保留用户纠正的具体含义。

同样，用户在一次紧急任务中要求简短回答，也不意味着他从此不再需要详细分析。

# 五、个性化系统如何与多专家路由协同？

这是 EvoAgent 与普通聊天机器人的一个重要区别。

我们已经设计了通用入口、意图识别和领域专家路由。现在，用户习惯必须进入这条链路，但不能让路由器直接读取并使用所有记忆。

我建议采用以下流程：


    **用户输入**



    **意图与任务识别**
    识别领域、目标、风险和任务复杂度



    **个性化策略查询**
    只查询当前任务相关、授权可用的偏好



    <grid-item>

        **通用智能体**
        通用对话与推理

    </grid-item>
    <grid-item>

        **领域专家**
        专业任务与领域策略

    </grid-item>



    **上下文组装与执行**
    合并适用偏好、当前指令和领域约束



    **结果反馈**
    记录显式纠正和可用的效果信号


这里最重要的是，**用户习惯不应该直接决定路由结果，而应该辅助路由后的协作策略。**

例如，用户喜欢详细解释，不应该因此让一个旅游问题错误地路由到编程专家；用户习惯先讨论方案，也不应该阻止一个简单的手机操作任务直接执行。

路由判断任务属于什么领域，个性化系统判断在当前场景下怎样与用户协作。这两个判断相互补充，但职责不同。

## 5.1 同一偏好如何作用于不同专家？

假设用户有一个已确认的全局偏好：“复杂任务先给整体方案，再逐步执行。”

那么：

- 编程专家可以先给架构、修改计划和测试方案；
- 漫剧专家可以先给制作流程、预算和交付计划；
- 手机操作专家可以先判断任务风险和执行步骤；
- 普通聊天则可以直接回答，不必每次都生成完整计划。

同一偏好在不同领域中的具体表现，应由各专家的适配策略决定，而不是机械复制同一段提示词。

# 六、个性化怎样进入上下文，又怎样避免干扰模型？

我建议个性化系统不要直接向每个专家拼接一长段“用户画像”。它应该输出一份结构化的 **Personalization Profile**，由上下文引擎根据当前任务选择相关条目。

例如：

<CodeBlock language="json" editable>
{
  "profile_version": "profile-v12",
  "task_scope": {
    "domain": "software_architecture",
    "project_id": "evoagent"
  },
  "applicable_preferences": [
    {
      "preference_id": "pref-001",
      "behavior": "先给整体设计，再逐层深入",
      "scope": "complex_architecture_tasks",
      "status": "CONFIRMED",
      "priority": "DEFAULT"
    }
  ],
  "current_task_overrides": [
    {
      "instruction": "本次先完成全量设计，不裁剪为MVP"
    }
  ],
  "excluded_preferences": [],
  "source_refs": [
    "preference-source-ref"
  ]
}
</CodeBlock>

这是概念示例。正式协议还需要包括权限校验结果、适用条件、冲突处理结果、过期状态以及必要的审计信息。

### 上下文引擎需要遵守什么规则？

1. 只加载与当前任务相关的偏好。
2. 优先使用明确且适用的偏好，不把低置信度推断写成命令。
3. 保留当前任务指令的原始语义，不让历史偏好覆盖它。
4. 对高风险动作，绝不因为用户习惯追求效率就降低授权门槛。
5. 记录哪些偏好实际进入了模型上下文，便于分析错误来源。
6. 当偏好没有帮助时，可以停止注入或调整其适用范围。

最后一点很重要。个性化不能成为一套只进不出的提示词系统，否则随着使用时间增长，用户画像会越来越长，既浪费 Token，也会让模型被过多历史假设干扰。

# 七、如何评估个性化是否真的有效？

EvoAgent 的目标不是收集最多的用户习惯，而是让用户更高效、更稳定地完成任务。

因此，个性化系统需要独立评测，不能只看记忆数量或用户纠正次数。

| 评测维度 | 需要回答的问题 |
|---|---|
| 偏好识别准确率 | 系统是否正确理解用户真正想要的协作方式？ |
| 范围识别准确率 | 是否把项目习惯误判为全局习惯？ |
| 偏好调用准确率 | 是否只在合适的任务中使用偏好？ |
| 用户纠正率 | 相似任务中，用户是否仍然需要反复纠正同一个问题？ |
| 任务完成质量 | 个性化是否提高了实际结果质量？ |
| 交互效率 | 是否减少了不必要的追问、重复说明和返工？ |
| Token 与成本 | 是否因为加载更多偏好而增加了不必要的模型开销？ |
| 负面影响 | 是否造成刻板假设、隐私风险或跨任务干扰？ |

评测时还要区分相关性与因果关系。

例如，用户纠正次数下降，可能是因为系统学到了偏好，也可能是因为后续任务变简单了。对于重要改动，可以在适当的测试任务上比较基线策略与候选策略，并固定其他主要条件。

如果个性化提高了偏好预测准确率，却没有改善实际任务体验，就不应该仅凭预测指标认定它进化成功。

## 七个关键保护机制

我建议至少落实以下保护：

- 不把未经证实的推断自动升级为全局规则。
- 不因为用户没有反对，就认定他同意某种长期画像。
- 不将敏感信息作为普通习惯随意推断和保存。
- 允许用户查看、纠正、暂停使用和删除个性化记录。
- 允许用户针对单次任务覆盖长期偏好。
- 对偏好变更保留必要的来源和版本记录，但遵循用户的数据删除要求。
- 进化系统不得仅凭任务成功率就修改用户偏好；需要区分用户明确反馈与系统推断。

# 八、个性化系统的数据模型与进化边界

为了与前面设计的记忆系统保持一致，我建议增加以下实体，而不是再造一套独立的记忆数据库。

| 实体 | 职责 |
|---|---|
| `Preference` | 当前生效的偏好及适用范围 |
| `PreferenceObservation` | 用户行为、明确声明和纠正等观察记录 |
| `PreferenceEvidence` | 支持或反对某个偏好的证据 |
| `PreferenceVersion` | 偏好的历史版本及变更原因 |
| `PersonalizationProfile` | 某个任务可使用的偏好集合 |
| `PersonalizationDecision` | 本次为什么选择或排除了某项偏好 |
| `PersonalizationEvaluation` | 个性化策略的评测结果 |

这些对象应该关联到前面统一的任务、记忆和运行版本清单。

例如，系统可以追溯：某次编程任务为什么采用详细解释模式、使用了哪一版偏好、偏好来自什么证据，以及这次选择最终有没有改善任务效果。

个性化策略本身可以独立进化，但用户偏好的内容与系统采用偏好的算法必须分开管理。

- **用户偏好数据**：表达用户想要什么。
- **个性化策略**：决定如何识别、选择和应用偏好。
- **专家策略**：决定如何在领域内完成任务。

这样，即使我们优化了偏好识别算法，也不会无意间修改用户已确认的偏好内容，更不会直接改变其他专家的核心能力。

# 九、这一轮建议冻结的架构决策

  {#each [
    "明确偏好与推断习惯分开管理，行为推断必须保留证据。",
    "所有偏好都必须有适用范围，支持从任务级到全局的不同层级。",
    "当前明确指令优先于普通历史偏好，但不能覆盖安全与授权边界。",
    "个性化系统与专家路由分离，偏好影响协作方式而不是直接决定领域。",
    "偏好数据、个性化策略和领域专家能力分别版本化。",
    "只将当前任务需要的偏好注入上下文，并记录实际使用情况。",
    "个性化的成功标准是改善用户体验和任务结果，而不是积累更多用户画像。",
    "用户可以查看、纠正、暂停和删除个性化数据。"
  ] as item}

  {/each}

## 十、下一步应该继续设计什么？

我建议接下来进入第三个领域：**工作记忆与任务状态系统**。

原因是，长期记忆和用户个性化解决的是“以后应该记住什么”，但 EvoAgent 还需要解决一个更直接的问题：

当一个任务持续数小时、跨越多个专家、调用几十次工具，甚至经历手机进程被杀、网络断开和任务恢复时，智能体如何准确知道自己正在做什么、已经完成什么、哪些方案失败过，以及下一步应该做什么？

我们需要进一步明确：

1. 工作记忆与长期记忆的精确边界；
2. 工作记忆与 Plan、DAG、ReAct 的关系；
3. 哪些信息必须持久化，哪些只需要临时保留；
4. 如何保存执行检查点并恢复中断任务；
5. 如何避免重复执行已产生副作用的操作；
6. 如何在上下文压缩后恢复必要的任务信息；
7. 如何在 Android 本地、云端任务服务和多个专家之间保持状态一致。
