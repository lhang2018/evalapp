## 3. 本地启动步骤

建议先在电脑上解压 ZIP，再打开终端进入 `evoagent-v0.1` 目录。

### 第一步：安装环境

要求 Python 3.11 或更高版本，并安装 Git。

<CodeBlock language="bash" editable>
python -m venv .venv

# Windows PowerShell
.venv\Scripts\Activate.ps1

# macOS / Linux 则使用：
# source .venv/bin/activate

pip install -e ".[dev]"
</CodeBlock>

### 第二步：配置云端模型

复制 `.env.example` 为 `.env`，填写你所使用服务商的 API 地址、密钥和模型 ID。

<CodeBlock language="dotenv" editable>
EVOAGENT_API_BASE=https://api.openai.com/v1
EVOAGENT_API_KEY=替换为你的API密钥
EVOAGENT_MODEL=替换为你实际可调用的模型ID
</CodeBlock>

上面是 OpenAI 兼容接口的配置示例。使用其他服务商时，应以其实际 API 地址、模型 ID 和工具调用兼容性为准。

不要把真实密钥写进 Git 仓库或提交到公开代码平台。

### 第三步：初始化稳定版本

<CodeBlock language="bash" editable>
git init
git branch -M main
git add .
git commit -m "feat: EvoAgent V0.1 baseline"
</CodeBlock>

如果你已经在该目录初始化过 Git，就不必重复执行 `git init`。

### 第四步：运行第一个任务

<CodeBlock language="bash" editable>
evoagent doctor

evoagent run "计算 (17 * 19) + 23，并解释结果。"

evoagent status

evoagent eval
</CodeBlock>

程序首次运行时会创建 SQLite 数据库和 JSONL 日志文件。

默认位置：

- `data/evoagent.sqlite3`
- `data/events.jsonl`

## 5. 如何运行第一次进化实验？

先确认固定评测集可以运行，再尝试改变一个低风险参数。

项目内有一个示例候选文件：

`workspace/candidate.example.json`

内容类似：

<CodeBlock language="json" editable>
{
  "reason": "降低温度，测试工具调用一致性",
  "changes": {
    "agent.temperature": 0.1
  }
}
</CodeBlock>

执行：

<CodeBlock language="bash" editable>
evoagent evolve workspace/candidate.example.json
</CodeBlock>

实际运行时，系统会：

1. 检查当前 Git 工作区是否干净。
2. 检查是否从稳定分支启动。
3. 校验修改字段是否在白名单中。
4. 在稳定分支上运行基线评测。
5. 创建 `exp/` 开头的实验分支并应用候选修改。
6. 运行候选评测并比较结果。
7. 达到门槛则合并到稳定分支，否则切回稳定分支并保留实验分支供分析。

当前配置中要求至少 3 个评测案例，候选成功率达到 80%，且相对基线的成功率下降不超过 2 个百分点。正式用于自主发布前，应根据实际任务扩充评测集，并为工具权限、成本、延迟和关键回归增加独立门禁。

**重要限制：** 当前自动晋级只允许修改白名单内的运行配置，不会让模型直接修改 Python 代码。示例中的温度调整也不保证提升质量；只有实测结果满足门槛才会晋级。

## 6. 接下来如何演进到真正的自进化系统？

V0.1 建好后，我建议按以下顺序推进，而不是立刻让 Agent 重写自己。

<list marker="number" gap={2}>
  <list-item>**V0.2：问题自动归因。** 统计重复失败、工具调用错误、上下文裁剪和异常恢复失败，自动生成带证据的问题报告。</list-item>
  <list-item>**V0.3：模型提出候选。** 将问题报告输入独立的优化模型，生成结构化变更提案。优化模型只拥有提案权限，不直接修改正式环境。</list-item>
  <list-item>**V0.4：模型适配档案。** 为每个具体模型保存提示词、工具调用策略、上下文配置、环境信息和独立评测基线。</list-item>
  <list-item>**V0.5：受控自动发布。** 对低风险配置自动实验、晋级和回滚；对代码、工具实现和核心 Harness 的修改，先在隔离工作区验证。</list-item>
  <list-item>**V1.0：自主编排进化。** 让系统能够根据问题频率、预期收益、实验成本和风险，自主决定先优化什么、如何验证以及何时停止。</list-item>
</list>

还有两个需要提前注意的工程问题：

- **固定评测集不能一直固定不变。** 应当同时维护稳定回归集和新增的真实失败案例，并防止候选优化只针对已知测试过拟合。
- **自动发布需要原子性。** 目前的 Git 流程是最小实现，尚不是完整的生产发布事务。下一阶段应增加进程锁、候选隔离、评测报告持久化、合并失败恢复以及发布后健康检查。

我的建议是先把 V0.1 在本地真实跑通，尤其确认你使用的云端模型能正确处理工具调用。等这个基础闭环稳定后，再把“自动发现问题并生成候选修改”的优化模型接进去。这样每一阶段都有明确的验收标准，也不会因为过早开放自修改权限而失去整个系统的可控性。
