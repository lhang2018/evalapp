# EvoAgent 第二十一专项：自我诊断、根因归因与改进实验治理

这一轮我们进入整个 EvoAgent 自进化体系中最关键的部分之一：**系统如何发现自己哪里出了问题，判断为什么出问题，并证明改进确实有效。**

前面已经设计了专家系统、意图路由、记忆、上下文压缩、Planner、ReAct、动态 DAG、工具执行、模型适配和成本治理。

这些模块能够让 EvoAgent 完成任务，但它们也可能相互影响。

例如，一次代码任务失败了，表面上看是代码生成错误，实际原因却可能是：

- 用户意图识别不完整；
- 路由到了不合适的专家；
- 记忆检索到了不适用的经验；
- 上下文压缩丢失了关键约束；
- Planner 漏掉了一个依赖；
- ReAct 选择了错误的工具；
- 工具执行结果不完整；
- 模型本身无法解决当前难度的问题；
- 测试环境存在异常；
- 验收器错误地判断了结果。

如果系统只记录“任务失败”，然后自动增加提示词、换一个模型或多试几次，它就不是在真正进化，而是在盲目调整。

我建议将本专项定义为：

**Root Cause Analysis & Improvement Experiment Engine，简称 RCAE。**

它不是一个负责修改所有模块的超级智能体，而是一个独立的诊断与实验治理系统，负责建立证据、提出假设、验证根因，并将经过验证的改进交给正确的模块。

## 一、第一性原理：失败是观察结果，不是根因

首先要严格区分五个概念。

  {#each [
    ["现象 Symptom","用户看到的结果，例如任务失败、速度变慢、输出质量下降。"],
    ["证据 Evidence","实际观察到的事实，例如测试报告、工具错误码、上下文版本和执行轨迹。"],
    ["假设 Hypothesis","对问题原因的可检验解释，例如关键接口约束没有进入上下文。"],
    ["根因 Root Cause","经过足够证据和验证支持，能够解释问题并指导修复的原因。"],
    ["改进 Improvement","针对原因实施的修改，并通过对照评测证明其产生预期效果。"]
  ] as item}

      <title size="md">{item[0]}</title>
      {item[1]}

    {#if item[0]!=="改进 Improvement"}

    {/if}
  {/each}

例如，编程专家修改代码后测试失败。

- 现象：测试没有通过。
- 证据：测试报告显示某个函数返回值不符合预期。
- 假设 A：模型误解了函数的业务规则。
- 假设 B：上下文中缺少调用方的接口约束。
- 假设 C：测试环境使用了过期依赖。
- 根因判断：需要进一步检查证据，不能仅凭错误表象确定。
- 改进：修复被证实的问题，并通过对照测试验证。

特别要注意：一个问题可能有多个原因。例如，上下文缺失是直接原因，而上下文组装策略未能保留关键接口约束，才是更上游的系统性原因。

**RCAE 的任务不是尽快找一个听起来合理的解释，而是找到证据足够、可被反驳、能够指导有效改进的解释。**

# 二、RCAE 在整个 EvoAgent 中处于什么位置？

我建议将 RCAE 设计成独立于具体专家、模型和执行器的横向系统。

它能够观察所有专家的运行情况，但不直接接管所有执行权；它可以诊断和提出改进建议，但不能因为发现一次失败就自动修改生产配置。


    **运行中的 EvoAgent**
    路由、专家、记忆、上下文、Planner、ReAct、工具、模型与验收器



    **统一证据采集层**
    任务事件、状态变更、工具结果、模型调用、成本、产物与验收记录



    <title size="lg" textAlign="center">RCAE 诊断与实验治理</title>

      <grid-item>

          **故障检测**
          发现异常与退化

      </grid-item>
      <grid-item>

          **根因分析**
          提出并检验假设

      </grid-item>
      <grid-item>

          **实验设计**
          建立对照与评测

      </grid-item>
      <grid-item>

          **效果与风险评估**
          决定是否晋升

      </grid-item>




    **受控进化治理层**
    候选改进、权限审批、版本管理、灰度发布与回滚



    **对应模块的改进版本**
    只修改经过诊断确认的目标模块，并重新验证相关能力


这里有一个重要的架构边界：

- OCAE 负责运行时可观测性和证据采集。
- RCAE 负责故障分析、根因假设和改进实验。
- 进化治理系统负责候选版本的批准、发布、回滚与范围控制。
- 各专家、模型适配器、上下文引擎和工具仍然拥有自己的实现与配置。

如果前面设计的 OCAE 已经承担部分异常检测功能，不需要再重复建设一套监控系统。RCAE 应该消费 OCAE 提供的事件和指标，并补足因果分析与实验治理能力。

## 2.1 诊断器不能成为新的执行风险源

RCAE 可能发现某个工具存在缺陷，但它不应该在正在运行的任务中直接替换工具实现。

正确流程应该是：

1. 保存原始证据；
2. 生成诊断假设；
3. 评估影响范围；
4. 构建候选修复；
5. 在隔离环境中验证；
6. 通过治理门禁发布；
7. 观察实际效果；
8. 必要时回滚。

如果问题正在影响用户当前任务，任务控制器可以采取已经授权的临时保护措施，例如停止重试、切换到已验证的备用工具或暂停任务。这属于运行时故障处置，不等于允许 RCAE 自行修改生产系统。

# 三、统一故障证据链：没有证据，就不能可靠诊断

RCAE 能否成功，很大程度上取决于证据质量。

如果系统只保存最终回答和一条“任务失败”的日志，就无法知道问题到底发生在哪一步。

因此，建议为每个任务建立可关联的证据链。

## 3.1 一次任务需要关联哪些信息？

| 证据类别 | 必须能够回答的问题 |
|---|---|
| 目标与约束 | 用户最初要求什么？哪些约束不可违反？ |
| 路由记录 | 为什么选择这个专家？路由依据和版本是什么？ |
| 记忆记录 | 检索了哪些记忆？来源、适用范围和版本是什么？ |
| 上下文记录 | 实际传给模型的上下文包是什么？哪些信息被压缩或省略？ |
| 规划记录 | 使用了哪个计划版本？节点依赖为什么这样设置？ |
| 模型记录 | 调用了哪个模型、提示词和适配版本？ |
| 工具记录 | 调用了什么工具、参数是什么、实际结果如何？ |
| 状态记录 | 节点和任务状态在什么时间发生了什么变化？ |
| 验收记录 | 哪些标准通过、哪些失败、使用了什么证据？ |
| 资源记录 | 花费了多少 Token、费用、时间和重试预算？ |
| 进化记录 | 当时使用了哪个稳定配置和哪些候选策略？ |

这些记录必须通过统一的 `task_id`、`node_id`、`trace_id`、`tool_call_id`、版本号等标识关联。

同时，需要区分原始证据和后续生成的诊断结论。模型生成的“根因解释”不能覆盖实际工具结果或原始任务事件。

## 3.2 证据需要保留到什么程度？

不是所有内容都需要永久保存完整原文。

建议采用分级保存：

- **关键状态与审计事件：** 保留必要的结构化事实、版本、时间和结果。
- **关键决策证据：** 保留实际使用的提示词版本、上下文包引用、计划版本和工具参数。
- **大型产物：** 保存文件、报告和数据的引用、哈希、版本与存储位置。
- **模型中间内容：** 按诊断需要和隐私策略保存，必要时保存摘要或引用。
- **敏感内容：** 根据最小化原则进行脱敏、访问控制和生命周期管理。

需要注意，哈希只能帮助检测内容是否变化，不能单独证明内容真实或正确；摘要也不能代替原始证据。

对于个人电脑或 Mini PC 部署，证据链可以优先采用本地追加式事件日志、SQLite 元数据和文件产物引用实现，不需要为 RCAE 单独搭建大型服务器。

# 四、根因分析：如何区分局部错误与通用能力缺陷？

这是你之前反复强调的一个核心原则：

**某个场景出错，不代表整个通用能力有问题；某种代码写法失败，也不代表这种写法本身完全错误。**

RCAE 必须将这一原则落实到诊断算法中。

我建议为每个问题建立四个层级的归因范围。

  {#each [
    ["L1 · 单次执行异常","只在某一次任务、特定输入或特定环境中出现。首先检查该次执行的证据。"],
    ["L2 · 局部策略缺陷","同一任务类型或某个明确条件下重复出现，例如某个提示词分支遗漏特殊输入。"],
    ["L3 · 领域通用能力缺陷","多个不同案例反复暴露同一领域能力的系统性问题，例如编程专家的跨文件依赖分析不足。"],
    ["L4 · 共享基础设施缺陷","不同专家都受到同一基础设施问题影响，例如上下文装配错误、工具网关状态不一致或预算计算错误。"]
  ] as item}

      <title size="md">{item[0]}</title>
      {item[1]}

    {#if item[0]!=="L4 · 共享基础设施缺陷"}

    {/if}
  {/each}

这四个层级不是简单的严重程度排序，而是不同的故障作用范围。一个单次故障也可能非常严重；一个通用能力问题也可能只影响低风险任务。

## 4.1 不能仅凭发生次数判断通用性

假设编程专家连续三次在同一个项目中写错了某种结构。

这并不能证明它在所有编程任务中都存在同样缺陷，因为三次错误可能都来自同一个过时接口、同一个缺失文件或同一个错误假设。

反过来，如果错误分别出现在不同项目、不同输入和不同工具环境中，却都指向相同的约束遗漏，就更有理由怀疑存在领域通用问题。

因此，诊断系统应该考虑：

- 案例之间是否真正独立；
- 是否共享同一个根因；
- 是否存在共同环境因素；
- 是否覆盖了不同输入和边界条件；
- 是否有反例；
- 现有证据能否区分多个竞争性解释。

## 4.2 建立影响范围，而不是一次性扩大修复

建议每个诊断结果都带有明确的作用范围：

- 仅当前任务；
- 指定工作流；
- 指定专家；
- 指定任务类型；
- 指定模型与适配版本；
- 指定共享基础设施；
- 多个专家共享的通用能力。

如果问题只发生在某个编程工作流，就先修复该工作流，不要直接修改所有专家的系统提示词。

如果确认问题来自共享上下文引擎，则应修复共享组件，并评估所有依赖它的专家。

这能避免局部问题污染全局能力，也能避免真正的基础设施缺陷被错误地分散修补。

# 五、因果归因：如何知道究竟是谁导致了失败？

证据关联并不等于因果关系。

例如，失败任务通常使用较强模型，这可能只是因为系统会把困难任务路由给强模型，并不代表强模型导致了失败。

同样，使用较长上下文的任务成功率更低，也可能是因为复杂任务本身更难，而不是上下文越长越差。

如果 RCAE 直接根据统计相关性修改策略，就可能得出错误结论。

## 5.1 建立可检验的因果假设

以代码修改失败为例，可以提出以下假设：

- H1：上下文缺失导致模型误解接口；
- H2：Planner 漏掉了必要的依赖节点；
- H3：工具修改方式破坏了文件结构；
- H4：测试环境与目标环境不一致；
- H5：当前模型无法可靠处理该类跨文件修改。

每个假设都应该说明：

1. 支持它的证据是什么；
2. 哪些观察与它冲突；
3. 如果假设成立，应该出现什么现象；
4. 哪个测试能够区分它与其他假设；
5. 修复它后，预期哪些指标会改善；
6. 哪些指标不应该受到明显影响。

例如，如果 H1 成立，那么在不改变模型、工具和计划的情况下，补充缺失的接口约束应该能改善相应案例的结果。

如果补充约束后问题依旧存在，就需要降低对 H1 的信心，继续检查其他原因。

## 5.2 诊断不应只有一个“根因答案”

复杂失败可能存在多个原因，而且原因之间可能存在依赖关系。

例如：

- 上下文引擎没有保留接口定义；
- Planner 没有安排接口核查节点；
- 模型生成补丁时没有识别不兼容调用；
- 验收器只运行了局部测试。

这四项问题可能共同导致最终失败。

建议区分：

- **直接原因：** 直接导致当前失败的因素；
- **促成因素：** 提高失败概率或扩大影响的因素；
- **上游机制缺陷：** 让问题反复发生的系统性原因；
- **检测缺陷：** 未能及时发现或阻止错误的因素。

并不是每次失败都必须找到唯一的根因。证据不足时，系统应该保留多个候选假设，或者明确标记“根因尚未确定”。

## 5.3 使用干预实验，而不是只做事后解释

当问题具有足够复现性时，最有价值的方法是控制变量。

例如，比较两种策略：

- A：现有上下文组装方式；
- B：保留接口定义和调用关系的新策略。

在相同评测样本、相同模型版本、相同工具和相同验收标准下运行，比较结果。

如果 B 的成功率显著提高，而且没有增加不可接受的成本和副作用，就能为该改进提供更强的因果证据。

但如果同时更换模型、修改提示词、调整工具和增加测试，结果即使改善，也很难判断究竟是哪项修改起作用。

因此，RCAE 应优先采用可解释、可对照的实验；必要时再通过多因素实验分析多个改进之间的交互作用。

# 六、诊断算法：从异常信号到可验证结论

我建议将 RCAE 的诊断过程设计为一个受控的证据分析流程，而不是让一个大模型读取全部日志后自由发挥。

## 6.1 第一步：检测异常并建立故障案例

故障可以来自不同渠道：

- 最终验收失败；
- 节点异常终止；
- 超时或预算超限；
- 重复重试却没有进展；
- 工具结果与预期状态不一致；
- 用户明确指出结果错误；
- 质量指标持续下降；
- 新版本表现明显差于稳定版本；
- 不同设备或模型之间出现状态不一致。

系统首先生成唯一的 `incident_id`，并关联相关任务、节点、工具调用、模型版本和证据引用。

一次任务可能产生多个故障案例；多个任务也可能最终关联到同一个系统性问题。不能把故障案例和根因一一对应。

## 6.2 第二步：重建实际执行事实

诊断前先回答“实际发生了什么”。

例如：

- 任务原始目标是什么？
- 实际使用了哪个计划版本？
- 哪些节点已完成？
- 失败前最后一个可信状态是什么？
- 模型实际收到哪些上下文？
- 工具实际执行了什么操作？
- 外部副作用是否已经发生？
- 验收器依据什么证据作出判断？

这一步优先使用持久化事件、工具记录、状态快照和真实产物，而不是让模型凭对话历史重新推断。

如果关键证据缺失，应当把缺失本身记录为诊断限制，而不是自动补造一个看似合理的执行过程。

## 6.3 第三步：生成候选假设

诊断器根据故障类型、历史案例和当前证据，生成有限数量的候选假设。

每个假设都应具有：

- `hypothesis_id`；
- `incident_id`；
- 可能的责任模块；
- 支持证据；
- 反对证据；
- 预期观察；
- 区分性测试；
- 预期修复方向；
- 潜在副作用。

模型可以参与假设生成，但假设的优先级应该由证据、可检验性和预期诊断价值决定，而不是只依据语言表达的自信程度。

## 6.4 第四步：选择最有价值的诊断实验

不是所有假设都值得测试。

建议优先选择满足以下条件的实验：

- 能够明显区分竞争性假设；
- 成本可接受；
- 不会破坏现有数据；
- 能在隔离环境中执行；
- 结果容易解释；
- 即使失败，也能提供新的有效证据。

例如，怀疑代码补丁错误时，先运行相关测试，通常比立即更换模型更有诊断价值。

怀疑上下文遗漏时，可以比较实际上下文包与原始证据，先确认约束是否真的缺失，而不是直接修改压缩算法。

## 6.5 第五步：更新诊断结论

实验结束后，RCAE 更新每个假设的证据状态：

- 已获得较强支持；
- 部分支持；
- 证据不足；
- 与观察冲突；
- 已被反例推翻；
- 仍需进一步测试。

这里不必强行生成一个精确的根因概率。只有在有足够数据、校准方法和明确统计假设时，才应输出有意义的概率估计。

对于证据不足的案例，正确的结果可以是“当前无法区分 H1 与 H2”，而不是强行选择一个原因。

# 七、改进实验治理：如何证明修改真的让系统变好了？

RCAE 不应该止步于诊断结论。

只有改进经过验证，才真正完成了进化闭环。

我建议将每次改进设计为一个独立的 `Improvement Experiment`。

## 7.1 实验记录必须包含什么？

| 字段 | 含义 |
|---|---|
| `experiment_id` | 实验唯一标识 |
| `root_cause_ref` | 对应的诊断结论或候选假设 |
| `target_component` | 计划修改的模块 |
| `baseline_version` | 当前稳定版本 |
| `candidate_version` | 候选改进版本 |
| `evaluation_dataset` | 使用的任务集和样本版本 |
| `primary_metric` | 最主要的改善指标 |
| `guardrail_metrics` | 必须保持的质量、安全和成本指标 |
| `test_environment` | 模型、工具、上下文与执行环境 |
| `experiment_result` | 对照结果、失败案例和统计限制 |
| `promotion_decision` | 晋升、继续实验或拒绝 |
| `rollback_plan` | 如何恢复到稳定版本 |

这使得每次进化都能够追溯：为什么要改、改了什么、如何验证，以及为什么最终允许或拒绝发布。

## 7.2 实验必须有主指标和护栏指标

例如，优化编程专家的上下文策略。

主指标可以是特定任务集上的验收通过率；护栏指标则包括：

- 关键约束遗漏率；
- 代码回归失败率；
- 平均调用成本；
- 平均任务耗时；
- 无进展重试率；
- 其他编程任务的退化情况。

如果新策略让目标案例成功率提高，却使其他常见任务的失败率明显上升，就不能只根据主指标宣布优化成功。

对于影响共享基础设施的改进，必须扩大回归测试范围，覆盖依赖该组件的多个专家。

## 7.3 小样本不能被误判为全面提升

假设一个候选提示词在五个案例中全部成功，而旧版本在其中四个案例成功。

这可能是改善，也可能是样本过少、任务难度差异或偶然波动。

因此，系统应根据指标类型、样本规模和错误代价选择评测方法，并记录结论的适用范围。

对于罕见但严重的安全问题，即使没有足够样本进行统计推断，也可以通过确定性测试和安全门禁阻止明显不安全的改动。

**没有足够证据证明改进有效时，应该保持现有稳定版本，而不是为了追求持续进化而强行发布。**

# 八、如何防止诊断系统误判？

自我诊断系统本身也会出错。

它可能把偶然错误判断为通用缺陷，把相关性当成因果关系，或者因为缺少日志而把责任归给错误模块。

因此，RCAE 需要自己的质量控制机制。

## 8.1 四类典型诊断风险

  {#each [
    ["过度归因","一次局部失败被解释为整个专家能力不足，导致无必要的全局修改。"],
    ["归因不足","只修复直接错误，却没有发现导致错误反复发生的上游机制缺陷。"],
    ["错误归因","把模型输出错误归咎于模型，实际上是上下文、工具或验收环节的问题。"],
    ["虚假确定性","日志不完整，但诊断器仍然输出单一、肯定的根因结论。"]
  ] as item}

      <title size="md">{item[0]}</title>
      {item[1]}

    {#if item[0]!=="虚假确定性"}

    {/if}
  {/each}

## 8.2 建立诊断器自己的评测集

RCAE 应当拥有独立于业务任务的诊断评测集，包含：

- 已知根因的历史故障；
- 多个原因都合理的模糊案例；
- 日志不完整的案例；
- 具有误导性相关性的案例；
- 多个模块共同导致失败的案例；
- 同一表面错误对应不同根因的案例；
- 已有假设被反例推翻的案例。

评估指标应包括：

- 根因定位准确性；
- 不确定时拒绝过度判断的能力；
- 假设覆盖率；
- 错误修复建议率；
- 诊断成本；
- 诊断所需时间；
- 改进实验的实际有效率。

其中，最值得重视的是**错误诊断导致的负面影响**。

如果诊断器偶尔无法找到根因，但能够明确表示证据不足，影响可能有限；如果它经常自信地把问题归错模块，并触发自动发布，那么风险就很大。

## 8.3 诊断与发布必须分权

我建议明确分离：

- RCAE：负责证据分析与改进建议；
- 实验执行器：负责在受控环境运行实验；
- 进化治理器：负责检查发布条件与批准权限；
- 发布控制器：负责部署、灰度、监测与回滚。

这几个模块可以部署在同一台个人电脑上，但逻辑权限应该分离。

这样，即使 RCAE 的诊断模型出现错误，也不能仅凭自己的结论直接修改生产提示词、全局记忆、模型路由和共享基础设施。

# 九、一个完整案例：编程专家为什么连续写错代码？

现在用一个具体案例检验整套机制。

假设 EvoAgent 接到一个跨文件 Python 修改任务，连续两次生成的补丁都没有通过测试。

## 9.1 故障证据

系统收集到：

- 原始需求与约束；
- 两次执行的计划版本；
- 实际模型和提示词版本；
- 两次使用的上下文包；
- AST 分析结果；
- 补丁差异；
- 测试失败报告；
- 工具调用与重试记录；
- 实际资源消耗。

诊断系统发现，两次失败都发生在修改某个接口调用时。

这只是一个线索，还不能确定根因。

## 9.2 提出三个候选假设



      H1
      **上下文遗漏**

    模型没有收到被修改函数的完整调用方约束。




      H2
      **规划缺陷**

    任务计划没有安排跨文件引用检查，导致修改范围不完整。




      H3
      **模型能力限制**

    即使提供完整上下文，当前模型仍无法稳定完成该类修改。


## 9.3 通过低成本实验区分假设

首先检查实际上下文包。

如果调用方约束确实缺失，就能为 H1 提供直接证据。

然后在隔离评测环境中，保持模型、工具和任务不变，只补充缺失的接口定义，再重新执行。

假设补充接口定义后，相关测试通过。

这会增强 H1 的可信度，但还不能立即证明所有问题都由上下文引起。还需要在其他具有相同特征的案例中验证，确认这不是一次偶然成功。

接下来，系统可能发现跨文件引用检查也有助于减少此类错误。于是针对 H2 设计第二组实验，判断是否需要修改 Planner 的工作流。

H3 则暂时保留，只有当上下文与规划问题得到控制后仍存在失败，才进一步评估模型能力限制。

## 9.4 只修改证据支持的模块

最终，系统可能做出如下决定：

- 在编程专家的特定跨文件修改策略中补充接口约束；
- 对符合条件的任务增加符号引用检查；
- 暂时不修改全局通用提示词；
- 暂时不升级所有编程任务使用的模型；
- 为跨文件修改增加对应评测集；
- 观察新策略是否同时改善成功率与成本。

如果后续发现该问题只发生在一种旧项目结构中，就可以把改进限制在该场景，而不必扩大到所有编程任务。

这个例子体现了我们一直坚持的原则：

**局部问题优先局部诊断，局部修复优先局部验证，只有证据表明问题具有更广泛影响时，才扩大改进范围。**

# 十、离线与在线进化：个人电脑断网时怎么办？

结合 EvoAgent 的部署方向，主要运行环境可能是 Android 手机、个人电脑或 Mini PC，服务端并不一定持续在线。

因此，RCAE 不能依赖远程服务器才能诊断和处理故障。

我建议采用本地优先、联网增强的双层设计。

## 10.1 本地即时诊断

设备离线时，仍然可以完成：

- 记录故障事件和执行证据；
- 识别已知错误类型；
- 检查状态不一致；
- 执行确定性诊断规则；
- 使用本地模型生成有限的候选假设；
- 运行本地可执行的测试；
- 应用已经批准的恢复策略；
- 将问题保存为待处理诊断案例。

如果本地没有足够的模型能力或评测资源，系统应当明确标记诊断结果的局限，而不是假装已经完成根因确认。

## 10.2 联网后的增强诊断

联网后，可以进一步：

- 使用更强的模型分析复杂故障；
- 运行耗时较长的对照实验；
- 检索外部技术资料；
- 获取最新模型与工具兼容性信息；
- 生成更完整的候选修复；
- 评估跨任务、跨版本的系统性退化。

这些增强能力可以提高诊断深度，但不应改变离线期间已经确认的任务事实。

## 10.3 离线期间的诊断结果如何同步？

建议每个故障案例包含：

- 本地唯一 `incident_id`；
- 原始事件的时间与序号；
- 相关任务和配置版本；
- 证据引用与完整性校验信息；
- 当前诊断状态；
- 已执行的恢复动作；
- 是否需要联网进一步验证。

重新连接后，系统按事件 ID 和版本进行同步，避免重复提交同一个故障案例。

如果本地诊断期间已经修复了问题，联网后的增强诊断应当基于当时的历史证据分析，而不是直接把当前配置覆盖回旧版本。

对于离线产生的候选改进，建议默认保存在本地候选区；只有通过相应评测和发布门禁后，才能晋升为稳定配置。

# 十二、下一专项：记忆进化与经验治理

RCAE 解决了“系统如何知道自己哪里出了问题”，但还有一个直接相关的问题尚未完整解决：

**诊断得到的经验，究竟应该进入哪里，才能让系统真正变得更好，同时不把一次偶然经验误认为通用规律？**

例如，编程专家在一次任务中发现，先分析 AST 再修改代码能够避免错误。

这条经验可能有几种不同的去向：

- 作为当前项目的临时经验；
- 作为某类代码修改任务的工作流规则；
- 作为编程专家的长期记忆；
- 作为特定模型的适配策略；
- 作为工具契约的改进建议；
- 作为经过评测的领域通用能力；
- 或者仅仅保留为一个尚未证实的诊断假设。

如果没有严格的经验分类与晋升机制，RCAE 即使能够找到问题，也可能把错误结论写入长期记忆，最终让系统越进化越混乱。

下一专项建议定义为：

**Memory Evolution & Experience Governance Engine（记忆进化与经验治理引擎，简称 MEEG）。**

重点研究：

1. 如何区分事实、用户偏好、任务状态、执行经验、诊断假设和稳定规则；
2. 如何决定一条经验应该进入哪个专家、哪个记忆空间或哪个工作流；
3. 如何从单次成功和失败中提取候选经验，而不是直接生成通用规则；
4. 如何通过重复案例、反例和评测决定经验是否值得晋升；
5. 如何判断一条旧经验已经过时、不再适用或与新规则冲突；
6. 如何处理通用记忆、领域记忆、用户记忆和任务记忆之间的优先级；
7. 如何避免模型生成的错误结论污染长期记忆；
8. 如何让经验被检索时同时考虑适用范围、可信程度、版本和时效性；
9. 如何将有效经验转化为提示词、上下文策略、工作流或工具改进，而不是全部堆进记忆；
10. 如何撤回错误经验，并确保撤回后不会继续通过缓存、摘要或其他引用影响执行。

这一步与前面的 RCAE 形成闭环：

**执行产生证据 → RCAE 分析问题 → 实验验证改进 → MEEG 管理经验 → 进化治理发布规则 → 新版本在后续任务中接受验证。**

我建议下一轮重点讨论一个核心问题：**什么样的经验才有资格成为 EvoAgent 的长期能力，以及如何防止经验从一次局部有效，错误地升级成所有场景都必须遵守的规则。**
