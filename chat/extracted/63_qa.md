# 第八专项：智能体的学习、经验提炼与泛化系统

它要回答一个根本问题：

**EvoAgent 每天执行任务、遇到错误、解决问题之后，究竟应该学到什么？怎样才能让下次做得更好，又不把偶然经验误认为通用规律？**

这比单纯记录日志、增加记忆或修改提示词更深入。

例如，编程专家今天把一个 Python 错误修好了。系统不应该只是保存这次对话，也不应该立即把解决方法写进通用提示词。它首先要判断：

- 这是一个一次性的代码错误，还是反复出现的故障模式？
- 是模型知识不足、工具缺陷，还是上下文缺失？
- 解决方法是否只适用于当前项目？
- 是否可以提炼成通用编程能力？
- 是否适用于其他模型？
- 是否有足够证据证明这项经验有效？
- 如果推广到其他任务，会不会产生副作用？

这正是学习与泛化系统的职责。

## 一、先区分四件事：记录、记忆、学习、进化

这四者很容易混淆，但它们应该是不同的系统职责。

| 机制 | 核心问题 | 示例 |
|---|---|---|
| 运行记录 | 实际发生了什么？ | 调用某个工具失败，返回超时 |
| 记忆 | 哪些信息值得以后使用？ | 用户习惯先看方案，再决定是否执行 |
| 学习 | 从经历中发现了什么规律？ | 这个工具在特定参数组合下经常失败 |
| 进化 | 如何改变系统并验证改变有效？ | 更新工具校验逻辑，经过测试后发布 |

它们之间存在依赖，但不能直接画等号。

**记录不等于记忆，记忆不等于知识，知识不等于已验证的改进。**

## 二、EvoAgent 应该建立五层经验体系

我建议将经验按照适用范围分层，而不是所有经验都放进一个全局知识库。


    **E1：单次任务经验**
    记录本次任务发生了什么、哪些步骤有效、哪些地方失败，以及结果是否经过验收。通常与具体任务绑定。
    示例：这次漫剧的第三个镜头生成失败，重试后成功。


    **E2：项目经验**
    在某个项目中反复有效的约束、决策和操作方法。
    示例：当前项目的角色参考图必须先统一，再批量生成镜头。


    **E3：领域经验**
    适用于特定领域或任务类型的方法，需要在相应领域中得到验证。
    示例：Python 重构后应检查符号引用、运行测试并审查差异。


    **E4：跨领域通用经验**
    在多个不同任务和环境中得到支持的通用执行原则。
    示例：外部操作返回超时，不代表操作一定没有执行，应先查询状态再决定是否重试。


    **E5：已验证的系统改进**
    已经通过相应测试并正式生效的策略、工具、工作流或配置版本。它不再只是经验，而是可追溯的系统变更。


这五层不是必须逐级晋升的阶梯。

某些经验始终只适用于一个项目；某些工具缺陷一旦被可靠复现，就可以直接产生工具修复候选，不需要等待它积累成跨领域经验。

**经验的推广范围必须由证据决定，而不是由经验写得多漂亮决定。**

## 三、最关键的机制：如何防止把偶然现象当成规律？

这正是自进化系统最容易犯的错误。

假设某次代码任务失败，模型修改提示词后任务成功了。

系统可能得出结论：“原提示词不够详细，以后所有代码任务都应该增加详细规划。”

但实际上，这次成功可能是因为：

- 第二次输入的信息更多；
- 工具服务刚好恢复；
- 模型随机生成了更好的代码；
- 测试环境发生了变化；
- 新提示词确实有效。

仅凭前后两次结果，无法确定是哪一个因素导致改善。

因此，EvoAgent 需要一个**经验可信度与适用范围判定机制**。

### 3.1 为每条经验建立证据档案

每条经验至少记录以下内容：

| 字段 | 作用 |
|---|---|
| `observation` | 实际观察到的现象 |
| `hypothesis` | 对现象原因的解释 |
| `evidence_refs` | 支持结论的运行记录、测试或其他证据 |
| `counterexamples` | 已发现的反例 |
| `applicability_scope` | 适用任务、项目、模型和环境 |
| `confidence_status` | 当前证据状态 |
| `validation_method` | 如何验证经验是否有效 |
| `last_validated_at` | 最近一次验证时间 |
| `expiration_conditions` | 哪些变化会使经验失效 |

建议将经验状态分为：

- `OBSERVED`：只观察到现象；
- `HYPOTHESIS`：提出了原因假设；
- `SUPPORTED`：有重复观察或针对性证据支持；
- `VALIDATED`：通过预先定义的测试验证；
- `REJECTED`：被证据否定；
- `STALE`：可能因环境或版本变化而过期。

这里需要注意：重复出现并不自动意味着因果关系成立。例如，同一个工具每天都发生超时，可能是同一个长期未解决的网络问题，并不能仅凭出现频率就断言工具实现有缺陷。

### 3.2 经验推广需要分级验证

例如，EvoAgent 发现“超时后先查询状态，再决定是否重试”可以减少重复操作。

可以按三个阶段验证：

1. **单场景验证：** 在某个支持状态查询的工具上验证。
2. **同类场景验证：** 在不同的远端任务 API 上验证。
3. **跨领域验证：** 检查该原则在文件操作、消息发送和其他有副作用的任务中是否仍然成立。

最后得到的也不一定是一条适用于所有工具的绝对规则。更合理的知识可能是：

> 对于支持可靠状态查询的远端操作，发生超时后应先查询原操作状态，再决定是否重试。若工具不支持状态查询，则使用该工具契约规定的恢复策略。

这就是从一次成功经验提炼成**有前置条件、有适用范围、有例外处理的知识**。

### 3.3 反例必须成为经验系统的一等公民

如果系统只保存成功案例，知识就会不断偏向那些看起来有效的方法。

例如，某种提示词在简单代码任务中效果很好，但在大型项目中导致过度规划和成本上升。

正确的做法不是直接删除所有旧经验，而是缩小适用范围：

- 简单代码修改：继续使用原策略；
- 大型项目重构：使用另一种经过验证的策略；
- 无法判断复杂度：先进行低成本分析，再选择策略。

所以，经验系统不应该只有“成功经验库”，还需要失败案例、反例、适用条件和已知限制。

# 四、经验提炼不能只靠模型写总结

我们需要让模型参与经验分析，但不能把模型生成的自然语言总结直接当成可靠知识。

建议将经验提炼拆成四个独立步骤。

## 4.1 事实提取

先从运行轨迹中提取确定事实：

- 实际执行了哪些动作；
- 每个工具返回了什么；
- 哪些状态发生了变化；
- 哪些验收条件通过；
- 哪些步骤发生了失败；
- 是否发生了重试；
- 任务最终是否完成。

这一步尽量依赖结构化事件和原始证据，而不是模型对整个过程的自由回忆。

## 4.2 根因分析

随后分析失败或成功的可能原因。

例如：

> 观察：视频合成失败。
> 事实：输入视频存在，音频文件存在，FFmpeg 返回了编码参数错误。
> 假设：当前编码参数与目标媒体格式不兼容。
> 待验证：替换编码参数后，是否能够在相同输入和环境下成功合成。

这一步应该保留多个可能的根因，而不是为了快速生成经验，强制选择一个解释。

## 4.3 形成可执行经验

有效的经验应当能指导未来行动，而不只是描述过去。

例如：

- 不够好的经验：“视频生成偶尔会失败。”
- 更好的经验：“当远端视频生成请求超时且服务支持任务状态查询时，先查询原任务；只有确认任务未执行或失败且重试安全时，才提交新的生成请求。”

后者明确了触发条件、动作和限制。

## 4.4 验证与晋升

经验候选生成后，系统要决定：

- 仅保存为任务案例；
- 写入当前项目记忆；
- 加入领域经验库；
- 生成工具或工作流改进候选；
- 提交通用策略优化实验。

不是每条经验都需要修改系统，更不是每次失败都应该产生一条新规则。

如果某个问题已经通过一次性修复解决，并且没有复用价值，那么保留任务记录就足够了。

# 五、运行时如何使用经验，而不是把经验全部塞进上下文？

经验库再丰富，如果检索不准、选择不当，仍然会伤害智能体。

假设编程专家处理一个 Python 类型错误。如果上下文引擎把过去所有 Python 故障案例都放进来，不仅成本高，还可能让模型套用错误的方法。

因此，经验系统需要和前面设计的上下文引擎协同，但不应该与上下文引擎合并成同一个模块。

我建议采用以下机制。


    **当前任务**
    目标、约束、环境、阶段和已知问题



    **经验检索**
    先按权限、适用范围和版本筛选，再按相关性排序



    **适用性判断**
    检查前置条件、反例、过期状态与可信程度



    **经验应用策略**
    直接应用已验证方法、作为参考，或先做低成本验证



    **执行与反馈**
    记录是否适用、是否有效以及有没有新反例


## 5.1 经验选择需要考虑什么？

至少要考虑：

- 与当前任务的相关性；
- 是否属于相同的领域或项目；
- 运行环境和模型是否兼容；
- 前置条件是否满足；
- 经验的验证状态；
- 最近一次验证时间；
- 已知反例；
- 过去应用后的效果；
- 引入这条经验的 Token 和执行成本。

这里有一个重要原则：**经验越通用，不代表它越应该优先使用。**

一个在当前项目中反复验证有效的特定规则，可能比一条宽泛的通用建议更适合当前任务。

同时，用户明确指定的当前要求不能被历史经验覆盖。例如，用户这次明确要求“不要修改原始文件”，即使历史经验显示直接修改效率更高，也必须遵守当前约束。

## 5.2 经验需要区分“建议”和“强制规则”

我建议将经验分为三个使用级别：

- **参考经验：** 提供给模型作为建议，可以根据当前任务判断是否使用。
- **已验证策略：** 在明确适用条件下，作为默认执行策略。
- **受保护规则：** 由确定性控制层执行，不能依赖模型自由决定是否遵守。

例如，“Python 重构后建议运行相关测试”可以是已验证策略；“未经授权不得删除用户文件”则必须是受保护规则，而不能仅仅作为经验库中的一条建议。

这样可以避免经验系统在不断积累过程中，把临时方法、用户偏好和安全规则混为一谈。

# 六、用户习惯、项目记忆和通用经验，怎样避免互相污染？

这也是你之前特别重视的部分。

假设用户习惯先看方案再执行，这种偏好应该影响通用智能体的交互方式，但不应该被错误地解释成“所有任务都必须先生成详细计划”。

同样，某个项目要求严格遵循特定代码风格，也不应该自动变成所有编程任务的全局规则。

建议为经验和记忆建立不同的命名空间。

| 命名空间 | 内容 | 默认使用范围 |
|---|---|---|
| 用户偏好 | 表达风格、确认习惯、工作方式 | 经过授权的相关个人任务 |
| 会话记忆 | 当前对话中的目标、约束和未决事项 | 当前会话 |
| 项目记忆 | 项目架构、约定、决策和历史问题 | 对应项目 |
| 领域经验 | 编程、旅游、漫剧等专业方法 | 匹配的领域任务 |
| 通用经验 | 多个场景验证过的执行原则 | 满足适用条件的任务 |
| 系统规则 | 权限、安全和运行控制 | 对应系统边界内的所有相关操作 |

这些命名空间之间可以有受控的晋升机制，但不能自动互相复制。

例如：

- 用户在一个项目里偏好使用某个框架：默认留在项目记忆；
- 用户多次明确表示所有工作都希望先看方案：可以形成候选用户偏好；
- 多个独立场景都证明某种工具恢复策略有效：可以形成通用经验候选；
- 某个经验通过专项和回归测试：可以生成正式的系统策略改进。

即使用户偏好重复出现，也不应自动升级成强制规则。偏好应该是可调整的，当前明确要求优先于历史偏好。

# 七、经验系统必须解决遗忘、过期与知识冲突

如果 EvoAgent 只会增加经验，不会更新、降级和淘汰经验，最终就会形成一个越来越庞大的矛盾知识库。

例如：

- 旧版本模型在某种提示词下表现更好；
- 新版本模型已经不需要该提示词；
- 某个工具升级后，原来的恢复方式不再适用；
- 某项目已经迁移到新架构；
- 用户以前偏好详细解释，现在要求简洁输出。

这些都不能只靠在新经验前面增加一条记录来解决。

## 7.1 经验生命周期

建议为经验建立完整生命周期：

  {#each [
    ["候选","刚从运行记录中提取，尚未验证。"],
    ["有效","满足适用条件，并有证据支持。"],
    ["受限","发现部分场景不适用，需要缩小适用范围。"],
    ["过期","环境、模型、工具或项目发生变化，原结论需要重新验证。"],
    ["被替代","新版本经验取代旧版本，但保留历史与依赖关系。"],
    ["归档","不再参与默认检索，但为审计、历史任务和必要回放保留引用。"]
  ] as item}


        {item[0]}


        {item[1]}


  {/each}

## 7.2 什么情况下需要重新验证？

可以由事件触发，而不只是定期扫描：

- 模型版本发生变化；
- 工具契约或实现发生变化；
- 项目依赖升级；
- 用户纠正了相关经验；
- 最近的应用结果与经验预测明显不符；
- 出现新的反例；
- 经验依赖的外部服务发生重大变化。

例如，某条经验专门针对模型 A 的工具调用行为。当系统切换到模型 B 时，不应该直接删除这条经验，但应该将它的适用范围限制为模型 A，或者把它标记为需要在模型 B 上验证。

## 7.3 不要用简单的时间衰减替代适用性判断

一条稳定的数学事实不会因为半年没有使用就自动过期；一个依赖特定 API 的调用技巧，却可能在 API 升级当天失效。

因此，经验的有效性应主要由它所依赖的条件、版本、反例和重新验证结果决定。时间可以作为辅助信号，但不应成为唯一判断依据。

# 八、学习系统的数据库与核心模块

现在将概念落实到 EvoAgent 的工程设计中。

建议增加一个独立的 Experience Learning Engine，由以下模块组成：

  {#each [
    ["Experience Extractor","从任务轨迹中提取事实、异常、成功模式与候选经验。"],
    ["Evidence Analyzer","关联证据，分析反例，区分事实、假设和结论。"],
    ["Experience Store","保存经验、适用范围、验证状态和历史版本。"],
    ["Experience Retriever","根据当前任务检索符合条件的经验。"],
    ["Applicability Evaluator","判断经验能否迁移到当前模型、工具、项目和环境。"],
    ["Experiment Manager","将经验转化为可测试的策略、工具或工作流改进候选。"],
    ["Promotion Controller","管理经验晋升、正式发布、过期、替代和回滚。"]

这些模块可以作为一个逻辑上独立的子系统，部署时不必拆成七个服务。对于个人使用的 EvoAgent，我建议先采用模块化单体：共享一个进程或一组轻量进程，通过明确接口划分职责，只有确实需要隔离的工具执行和任务才放进独立进程。

## 8.1 建议的核心数据实体

| 实体 | 用途 |
|---|---|
| `ExperienceRecord` | 经验本身，包括内容、范围、状态与来源 |
| `ExperienceEvidence` | 支持或反驳经验的证据引用 |
| `ExperienceRelation` | 经验之间的支持、冲突、替代和依赖关系 |
| `ExperienceApplication` | 记录某条经验在哪次任务中被使用以及效果如何 |
| `ExperienceEvaluation` | 经验的验证记录、测试集与结果 |
| `LearningCandidate` | 由经验产生的系统改进候选 |
| `PromotionHistory` | 经验或改进的晋升、降级和发布历史 |

不建议把所有原始运行日志直接复制到经验库。经验应该引用原始事件或证据存储，并只保留后续判断所需的摘要和结构化字段。

这样可以减少存储冗余，也便于在原始日志达到保留期限时，按隐私政策删除不再需要的数据，同时明确哪些经验失去了原始证据支持。

# 九、如何证明经验学习真的提高了能力？

这里要避免一个陷阱：经验库越来越大，并不代表智能体越来越聪明。

我们需要衡量的是经验是否被正确提取、正确使用，并最终改善任务结果。

建议建立五组指标。

| 评测维度 | 指标 |
|---|---|
| 经验提取 | 有效经验发现率、重复经验比例、事实提取错误率 |
| 经验质量 | 证据覆盖率、根因验证率、反例发现率 |
| 经验检索 | 相关经验命中率、错误经验使用率、过期经验使用率 |
| 泛化能力 | 在新任务、新项目、新环境中的迁移成功率 |
| 实际收益 | 任务成功率、返工率、恢复时间、单次成功任务成本 |

还需要两个非常关键的指标：

**负迁移率：** 一条经验从原场景推广到新场景后，反而降低任务表现的比例。

**经验依赖成本：** 为检索、读取、判断和执行经验增加的 Token、延迟与工具调用费用。

例如，一条复杂的经验可能只提升 0.5% 的成功率，却使每个任务都多调用两次大模型。如果它没有显著降低失败恢复成本，可能不值得默认加载。

## 9.1 采用对照实验

对于可复现的任务，可以比较三种条件：

- A：不使用新经验；
- B：检索新经验，但只作为参考；
- C：使用经过验证的策略改进。

在相同任务集、相同模型和尽可能一致的运行条件下，比较质量、稳定性和成本。

这样可以区分：

- 经验是否有用；
- 检索机制是否有效；
- 将经验固化为策略是否真的更好。

对于模型输出具有随机性的任务，需要使用足够的样本、合理的统计分析和独立测试集，避免因为一次偶然成功就发布改进。

# 十、进一步深入：让 EvoAgent 知道自己擅长什么、不擅长什么

经验学习之后，还有一个更深层的问题：**系统如何形成对自身能力的准确判断？**

一个成熟的智能体不仅应该积累经验，还应该逐渐了解：

- 哪些任务自己通常能做好；
- 哪些任务需要调用专业工具；
- 哪些任务必须增加验证；
- 哪些任务需要更强的模型；
- 哪些环境下自己的表现明显下降；
- 哪些能力虽然理论上存在，但尚未经过可靠验证。

我建议把它作为一个独立的子系统：**Capability Self-Model（能力自我模型）**。

它不是让模型自我评价“我很擅长编程”，而是根据真实任务数据建立可更新的能力画像。

  能力画像还应记录样本量、评测集、模型版本、环境条件、置信区间与最近验证时间。单独一个百分比不能证明能力稳定。

这类数据可以帮助调度器决定是否直接执行、增加独立测试、调用辅助专家或选择更强的模型。

但能力画像不能变成僵化的限制。例如，复杂并发问题的历史成功率较低，不意味着永远不应该尝试；它意味着系统应该采用更谨慎的执行和验收策略。

## 10.2 能力画像与经验系统有什么区别？

- 经验系统回答：以前发生了什么、什么方法在什么条件下有效。
- 能力自我模型回答：当前系统在什么条件下能够可靠完成什么任务。
- 路由器根据这些信息决定选择哪种执行方案。
- 进化系统通过新任务与对照实验，持续更新能力画像。

四者必须形成闭环，但不能混为一个数据库字段。

## 10.3 如何避免能力画像自我强化错误？

假设系统认为自己不擅长复杂代码重构，因此总是拒绝处理这类任务。由于它几乎不再尝试，后续也没有新的成功案例，能力画像就会一直停留在低水平。

这是一种反馈偏差。

建议引入有限的探索机制：

- 对低风险任务尝试成本可控的新方法；
- 对有潜力的候选策略进行沙箱测试；
- 记录未尝试任务和选择偏差；
- 对高不确定性任务增加验证，而不是简单拒绝；
- 只根据有效证据更新能力画像。

探索同样要受预算、安全和用户授权约束，不能为了学习而在真实环境中反复执行高风险操作。

# 十二、下一专项建议：智能体的自我诊断与自我修复能力

这里需要进一步区分两个问题：

- **学习系统**：从过去的经历中提炼有价值的知识。
- **自我诊断与修复系统**：当当前任务或智能体自身发生异常时，判断哪里出了问题，并采取安全、有效的修复行动。

我们已经设计过故障归因，但还没有完整解决自我修复策略本身。

下一轮应该重点研究：

1. 如何发现智能体正在重复犯错，而不是只发现任务失败；
2. 如何识别模型幻觉、上下文丢失、工具故障、规划缺陷和状态损坏；
3. 如何判断应该立即恢复、重新规划、切换模型、替换工具还是暂停；
4. 如何避免修复动作制造新的故障；
5. 如何判断问题已经真正解决，而不是暂时绕过；
6. 如何让诊断器自身也接受独立评测，防止错误诊断导致系统持续退化；
7. 如何让自修复尽量自动化，同时保留硬性权限和成本边界。

这会让 EvoAgent 不只是“从经验中学习”，而是能够在运行中发现问题、诊断问题、尝试修复、验证修复，并将经过验证的成果沉淀为长期能力。
